# 挿絵の図案設計・検収

章の本文を読んだうえで「何枚・どこに・何を描くか」を決めるための指針。この設計が生成品質をほぼ決めるため、**オーケストレーター本体（Opus）が担当**する。

## 枚数の決め方

引数で指定が無い場合の既定。

| 章の内容量 | 枚数 | 目安 |
|-----------|------|------|
| 概念紹介中心・見出し3つ以下 | 1枚 | 章全体像の1枚だけ |
| 標準的な章（見出し4〜6） | **2〜3枚（既定）** | 章全体像 ＋ 中核プロセスの図解 ＋（あれば）比較/分類 |
| 手順や概念が多い章（見出し7以上） | 4〜5枚 | 全体像 ＋ 主要プロセス ＋ 比較/分類 ＋ 変化の対比 ＋ 用語の地図 |

- **1章あたり5枚を上限**とする。図が多すぎると本文が分断され、読み手の負荷が上がる。
- 上記はあくまで**上限側の目安**であり、枠を埋めることが目的ではない。**「重複棚卸し」を通過した図案の数がそのまま枚数**になる。判定表で `不採用` が続き切り口が尽きたら、レンジの下限を割り込んでも構わない（標準的な章で1枚、多い章で2枚でもよい）。
- 既に Mermaid 図・比較表・カードが充実している章ほど、採用できる図案は少なくなる。**同じ情報を二重に描かない**。画像は「文字だけでは伝わりにくい対応関係・変化・全体像」に使う。

## 重複棚卸し（設計前の必須手順）

図案を考える**前に**、対象章に既にあるビジュアル要素をすべて洗い出す。これを飛ばすと、本文の Mermaid 図・比較表・「表示イメージ」ブロックと同じ内容の画像を作ってしまう（実際に Markdown ガイド第1〜3章で発生した）。

```bash
grep -n 'class="mermaid"\|<table\|表示イメージ\|language-\|grid-cols-\|<figure' \
  astro-system/src/chapters/<分類パス>/<slug>/<slug>-learning-material-<NN>.html
```

洗い出した要素ごとに「その情報は何か」を1行でメモし、次の判定を通す。

| 画像と既存要素の関係 | 判定 | 対応 |
|---------------------|------|------|
| 画像が既存要素を**完全に含み、さらに情報を足す**（上位互換） | 採用 | 画像を既存要素の位置に置き、**既存要素はコメントアウトして退避**する（行ごと削除しない。指示書に「置換」と明記） |
| 画像と既存要素が**まったく別の切り口** | 採用 | 両方残す |
| 画像が既存要素の**要約・言い換え**にすぎない | **不採用** | その図案は捨て、別の切り口を探す。切り口が無ければ枚数を減らす |
| 既存要素の方が情報量が多い（列・項目・例が多い） | **不採用** | 本文を残す。画像側を無理に作らない |

### 章導入画像の特則

章導入（学習目標カード直後）の1枚は**章全体の見取り図**であってよいが、**後続節のダイジェストにしてはいけない**。

- ダメな例: 1.2 のコード例と表示イメージ、1.3 の比較表、1.4 の利用先リストを4分割で並べただけの図 → 読者は同じ内容を2回読むことになる
- 良い例: 各節が「章の中でどう繋がるか」を示す関係図・ステップ図。個々の節の中身は描かず、**節どうしの関係と順序**だけを描く

### 画像内サンプルの重複

画像に描くコード片・例文は本文と用語をそろえる（既定ルール）が、**演習（やってみよう）で学習者が入力するサンプルと同一の文字列は避ける**。演習の答えを先に見せることになり、かつ二重掲載に見える。別の題材に差し替える。

## 画像で価値が出る箇所（優先順）

1. **章全体の見取り図** — その章で扱う概念の関係を1枚に。差し込み先は**学習目標カードの直後**（章の導入ビジュアル）。
2. **Before → After / 入力 → 出力** — 「書いたもの」と「表示されるもの」、コマンド実行前後など、**変化の対比**。
3. **ステップフロー** — 3〜5工程の処理の流れ。既存 Mermaid 図と同じ流れを描くなら、**直前に並べて補完するのではなく置き換える**（同じ流れの図が2つ続くのは重複。「重複棚卸し」の判定表に従う）。
4. **役割分担・比較** — 2〜3者の守備範囲の対比（例: ローカルとリモート、構造と見た目）。
5. **分類・地図** — 用語や機能のグルーピング。

避けるもの: 単なる装飾イラスト、本文に無い情報、文字を大量に詰めたスライド的な図。

## 図案の記述粒度（重要）

codex に渡す図案は、**画像内に描く日本語文字列まで確定**させる。曖昧な指示は誤字・意味不明な文字列の原因になる。

各画像について次を決める。

| 項目 | 内容 |
|------|------|
| 役割 | その図が本文のどの理解を助けるか（1文） |
| タイトル | 画像上部に描く見出し文字列（例: `Markdownとは？`） |
| レイアウト | 段組み・カード数・矢印の向き（例: 上段に Before→After の2カード、下段に2カード） |
| 各パーツの文字列 | ラベル・見出し・1行説明を**そのまま**列挙する |
| アイコン | **既定は「描かない」**。入れる場合のみ、全カード分を汎用の名詞で列挙する（歯車・ファイル・ブラウザ窓・吹き出し）。一部だけ指定すると空枠が残る |
| 論理名 | `<slug>-chapter<NN>-<topic>.png` |
| 差し込み位置 | 章HTMLのどのブロックの直前/直後か |
| キャプション / alt | figcaption 用の1文と、内容を述べる日本語 alt |

## 画像内テキストの規約（再生成を減らす最重要ポイント）

画像モデルが安定して描けない文字列を指定すると、**プロンプトをいくら強めても直らず、リトライを空回りさせる**。実測（VBAガイド21枚・`codex-imagegen.md`「実測データ」）で判明した制約に従う。

- **日本語**。長文は入れず、**短い語句＋1行説明**まで。
- **1つのカード・帯に入れる文字は最大14文字程度**。これを超えると画像モデルが**勝手に短縮する**（実測: 第5・6章でリトライを空転させた）。
  - 章の節タイトルをそのまま使わない。**設計段階で14文字以内の短縮ラベルを確定**し、その文字列を図案に書く。
  - 例: `6.2 Cellsで行・列の番号から指定する` → 図には `6.2 Cellsで指定する`
- **記号を描かない**: `―` `—` `–` `〜` `/` は**長音記号や別の記号に化ける**（実測: 第10・12章）。
  - タイトルに区切りが要る場合は、改行するか帯を2つに分ける。
  - `第7章 条件分岐 ― 章の地図` ではなく `第7章 条件分岐` ＋ 下段に `章の地図`、もしくは `第7章 条件分岐の地図`。
- **アイコンは既定で描かない**。指定すると一部のカードだけ**中身の無い空の枠**が残ることがある（実測: 第7章で唯一の作り直し要因）。アイコンを入れたい場合は「全カードに必ず描く／空欄を残さない」と明記する。
- 教材本文と**用語を一致**させる（本文が「パーサー」なら図も「パーサー」）。
- コード片を描くときは本文の例と**同じ文字列**を使う。ただし14文字制約を優先し、長い式は図に載せない。
- 数字は丸数字（①②③）など視認性の高い形にする。
- 実在サービスの**ロゴマーク・商標は描かない**。必要なら日本語の一般名詞ラベルにする（`GitHub` → `ソースコード管理`）。

## ビジュアル規約（既存教材との統一）

- クリーンな**フラットベクター風の教育用インフォグラフィック**。**最終成果物の背景は透過**（角丸カード、細い枠線、明快な矢印、余白たっぷり）。※codex への指示では背景をマゼンタのベタ塗りにする。
- フォントは日本語ゴシック（Noto Sans JP 風）。文字は大きく。
- 配色は**対象ガイドの技術色**に合わせる。`astro-system/src/data/guides/<分類パス>/<slug>.ts` から取得する。
  - 主役 = `primary.500`（例 Markdown: `#3b82f6`）
  - 濃色 = `primary.600` / `primary.700`
  - アクセント = `splashStop1`（多くは `#06b6d4` 系のシアン）
  - 面 = ごく薄いグレーブルー。過剰な彩色をしない。
- 写実表現・強いグラデーション・立体シャドウは使わない。
- 人物は必要最小限（顔つきの詳細な描き込みはしない）。
- **既定サイズ 1536x1024（横長）** — リポジトリの既存教材画像がすべてこの寸法。縦長の内容でも横長に収める構図にする。

> 教材HTML側の配色・ダーク対応の規約は CLAUDE.md「v1 デザイン」「テキスト視認性・ダーク可読性ルール」を参照。画像は**背景透過**で作り、`<figure>` 側にも背景色は付けない（ページの地色がそのまま図の背景になる）。

## 透過を前提とした作図規約（重要）

本スキルの**最終成果物**は背景透過（アルファ付き PNG）だが、**codex にはクロマキー（マゼンタ `#ff00ff` のベタ塗り背景）で生成させ、透明化は Claude 側で行う**（手順は `references/codex-imagegen.md`「生成方式（クロマキー・既定）」）。透明背景の直接生成は市松模様として描画されるため使わない。

図案段階では「マゼンタの地がそのまま透明になる」と考えて次を満たすよう設計する。

1. **地の上に情報を置かない**。タイトル・ラベル・注釈・細い矢印を、透過される背景の上に直接置かない。**すべて不透明な面（白カード・淡色カード・角丸の帯）の中に入れる**。
   - タイトルは「画面上部に大きな黒文字」ではなく、**不透明な角丸帯の中の文字**として設計する。ライトでは白地に見え、ダークでは帯だけが浮くので両モードで読める。
2. **面は不透明**にする。カードの塗りは `#ffffff` またはごく薄いグレーブルーの**不透明色**。半透明の重ねは使わない（透過後に背景が透けて濁る）。
3. **影・グラデーションを使わない**。背景に落ちるドロップシャドウは、透過後にキー色の汚れ・輪郭のフリンジとして残る。
4. **半透明の発光・グロー・ぼかしを図版に入れない**。透明背景に汚れとして残り、ダークで灰色のにじみになる。
   - あわせて、**キーカラー（既定 `#ff00ff` のマゼンタ）を図版の内部に使わない**配色にする。技術色がマゼンタ／ピンク系のガイドでは、キーを `#00ff00` に切り替える前提で図案を組む。
5. **透過部にまたがる線・矢印は、技術色の濃さで描く**（`primary.500`〜`600`）。ライト地・ダーク地のどちらでも視認できる中間の明度にする。極端に薄いグレーの線は透過部で消える。
6. 図版の外周には十分な余白を取り、要素を画面端で見切らせない（透過後、余白がそのまま本文と馴染む部分になる）。

## 検収チェック（Step 4 の合否基準）

生成後、**必ず画像を Read で開いて目視**し、以下をすべて満たすか確認する。1つでも欠ければ再生成。

1. **寸法**: `file` の出力が既定サイズ（既定 1536x1024 PNG）。
2. **日本語が読める**: 誤字・意味不明な文字列・文字化けが無い。
   - **完全一致は求めない。**軽微な短縮・助詞の違い・折り返し位置の違いは**許容する**（作り直しの費用に見合わない）。
   - 不合格にするのは「**意味が変わる/誤解を生む**」場合だけ。
3. **レイアウト**: 要素の重なり・見切れ・極端な余白の偏りが無い。矢印の向きが論理と一致している。
   **中身の無い空の枠・灰色のプレースホルダーが残っていない。**
4. **内容の正しさ**: 本文の説明と矛盾しない（順序・対応関係・用語）。
5. **配色**: 技術色の主役色が効いている。原色の多用や無関係な色調になっていない。
6. **禁止物が無い**: 実在ロゴ・商標・読めない英字ダミーテキストが無い。
7. **本文と重複していない**: 「重複棚卸し」の判定表を再適用し、`不採用` に該当しないこと。該当したら差し込まずに図案からやり直す。
8. **透過が正しい**: `mode` が `RGBA`、四隅の alpha が 0、透明率が概ね 10〜60%。縁のにじみ・図版内の抜け落ちが無い（検証コマンドは `references/codex-imagegen.md`「透過の検証」）。`mode` が `RGB` なら透過に失敗しているので再生成する。
9. **ダークでも読める**: ダーク背景（`#0f172a`）へ合成した `_check-dark-*.png` を目視し、消える文字・読めない線が無い。あれば「透過を前提とした作図規約」1.〜5. に照らして図案を直し、再生成する。

軽微なゆらぎ（本文の助詞まで完全一致していない等）は許容してよい。**誤解を生む誤りは許容しない**。

## 再生成のコツ

**まず「生成し直しても直らない不合格」を見分ける。** 次はプロンプトを強めても直らないので、**図案を直してから**1回だけ作り直す。

| 症状 | 直し方 |
|------|--------|
| ラベルが勝手に短縮される | 図案側の文字列を**14文字以内に詰める**（プロンプト強化では直らない） |
| タイトルの区切り記号が長音に化ける | 記号を**使わない**構成に変える（改行・帯の分割） |
| カードに空のアイコン枠が残る | **アイコンを外す** |
| 要素が潰れる・見切れる | **1枚を2枚に分割**するか要素を削る |
| ダークで文字が読めない | しきい値では直らない。**その要素を不透明面の中へ移す** |

一方、次は**そもそも不合格にしない**（実測でリトライの最大要因だったが、透明化に影響しない）。

- 背景マゼンタの色むら・近似色・わずかなグラデーション
- カードや帯のわずかな陰影・質感
- 助詞の違い・折り返し位置の違い

図案を直しても2回続けて不合格なら、無限リトライせず所見をユーザーに報告する。
