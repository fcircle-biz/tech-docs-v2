ファイルを読み書きする - 順ファイル処理の基本

業務システムの COBOL プログラムは、ファイルからデータを読み込み、計算して、結果をファイルや帳票に書き出すのが仕事です。この章では、いちばん基本的な「順ファイル」を 1 件ずつ読む方法と、書き出す方法、そして「ファイルの終わり」や「ファイルが無い」といった状況を正しく扱う方法を学びます。ここから、いよいよ本物の業務プログラムらしくなってきます。

この章で学ぶこと

  • ファイル処理の流れ（開く → 1件ずつ読む → 処理 → 書く → 閉じる）を説明できる
  • 環境部の FILE-CONTROL とデータ部の FILE SECTION（FD）で、ファイルとレコードを定義できる
  • OPEN・READ・CLOSE と「先読み」のパターンで、ファイルを最後まで読める
  • WRITE で出力ファイルを作り、ファイル状態（FILE STATUS）でエラーを見分けられる

12.1 ファイル処理の全体像

これまでの章では、データはプログラムの中に書き込むか、キーボードから入力していました。しかし、実際の業務では「1 日分の売上が数万件」のように、データの量が桁違いです。そこで、データをファイルに入れておき、プログラムがそれを読み込んで処理します。

用語 帳簿にたとえると この章の例
ファイル 1 冊の帳簿 売上を記録した sales.txt
レコード 帳簿の 1 行 1 件の売上（日付・商品・数量・単価）
データ項目 1 行の中の「欄」 日付の欄、商品コードの欄、数量の欄 など

レコードは、1 件分のまとまったデータのことです。COBOL のファイルの多くは、どのレコードも長さが同じ（固定長）で、「何桁目から何桁目が何の欄」と決まっています。第9章で作った売上レコード SALES-REC（20 バイト）が、まさにその例です。

ファイルを扱うプログラムは、どんなに大きくなっても、次の流れが基本形です。

flowchart TD A["ファイルを開く（OPEN）"] --> B["最初の1件を読む（READ）"] B --> C{"読む行はもう無い？"} C -->|"まだある"| D["1件ぶんの処理をする"] D --> E["次の1件を読む（READ）"] E --> C C -->|"終わり（終端）"| F["ファイルを閉じる（CLOSE）"]

図の説明: ファイルを最後まで読むときの基本の流れです。「最初に 1 件読む」ことと、「処理のあとに次の 1 件を読む」ことが大切なポイントです（12.5 で詳しく説明します）。

flowchart LR A["入力ファイル
sales.txt"] -->|"READ"| B["COBOLプログラム
1件ずつ処理"] B -->|"WRITE"| C["出力ファイル
big.txt"] B -->|"DISPLAY"| D["画面"]

図の説明: この章で作るプログラムの全体像です。入力ファイルを READ で 1 件ずつ読み、結果を WRITE で出力ファイルへ、確認用に DISPLAY で画面へ出します。

用語: 順ファイルと行順ファイル

順ファイル（順編成ファイル）は、レコードを先頭から順番に並べて保存したファイルで、読むときも先頭から順番に読みます。カセットテープのように、3 曲目を聞くには 1 曲目と 2 曲目を通り過ぎる必要があるイメージです。本ガイドでは、順ファイルのなかでも行順ファイル（LINE SEQUENTIAL）を使います。これは「1 行 = 1 レコード」のテキストファイルで、メモ帳や VS Code でそのまま中身を見たり、書き換えたりできます。学習にはとても便利です。

12.2 練習用のデータファイル sales.txt を作る

まず、読み込む相手のファイルを用意します。作業フォルダ（cobol-study）に、次の内容で sales.txt を作成してください。文房具店の売上 6 件分のデータです。

sales.txt データファイル 
20261001A00100300120
20261001A00200500080
20261002B00100201500
20261002A00301000150
20261003C00100100980
20261003B00200400500

1 行がちょうど 20 桁で、第9章で定義した売上レコード SALES-REC の形に対応しています。区切り文字（カンマなど）はなく、桁の位置で項目を区別するのが固定長ファイルの特徴です。

桁の位置を確認する目盛り 
----+----1----+----2
20261001A00100300120
DDDDDDDDIIIIQQQPPPPP

目盛りの下の D は日付、I は商品コード、Q は数量、P は単価の桁を表します。

桁 項目名 PICTURE句 1行目の値 意味
1〜8 SR-DATE PIC X(8) 20261001 売上日（2026年10月1日）
9〜12 SR-ITEM PIC X(4) A001 商品コード
13〜15 SR-QTY PIC 9(3) 003 数量（3 個）
16〜20 SR-PRICE PIC 9(5) 00120 単価（120 円）

データファイルを作るときの注意

1 行をぴったり 20 桁にしてください。桁が 1 つでもずれると、数量や単価の欄に別の項目の文字が入ってしまいます。行末に余分な空白を入れないこと、全角文字を入れないこと、文字コードは UTF-8 で保存することも守ってください。最後の行の末尾に改行があっても問題ありません。

12.3 環境部で「どのファイルを使うか」を宣言する

プログラムでファイルを使うには、2 か所に書く必要があります。1 つめが環境部（ENVIRONMENT DIVISION）の FILE-CONTROL で、「プログラムの中で使うファイルの名前」と「実際のファイル」を結び付けます。

FILE-CONTROLの書き方 ENVIRONMENT DIVISIONの抜粋 
      * 使うファイルと実際のファイルを結び付ける
       FILE-CONTROL.
           SELECT SALES-FILE ASSIGN TO "sales.txt"
               ORGANIZATION IS LINE SEQUENTIAL.
  • SELECT SALES-FILE … プログラムの中で使う名前（プログラム内のファイル名）を決めます。以降の OPEN や READ ではこの名前を書きます。
  • ASSIGN TO "sales.txt" … ディスク上の実際のファイル（sales.txt）を指定します。
  • ORGANIZATION IS LINE SEQUENTIAL … 「1 行 = 1 レコードのテキストファイル」であることを指定します。

コラム: メインフレームではどうなる？

メインフレームの順ファイルは、改行のない固定長レコードの並びが一般的です（可変長の形式もあります）。ファイルの置き場所は JCL（ジョブ制御言語）という別の指示書で決め、プログラムには ASSIGN TO SALESIN のような短い呼び名（DD名）だけを書き、JCL でその呼び名と実際のデータセットを結び付けます。つまり、プログラム側にはファイルの実際の名前を書かず、JCL 側で差し替えるのが現場の流儀です。本ガイドの ASSIGN TO "sales.txt" のようにファイル名を直接書く方法は、GnuCOBOL で手軽に学ぶための書き方です。考え方（読む・書く・閉じる）は同じなので、安心してください。

flowchart LR A["プログラム内の名前
SALES-FILE"] -->|"SELECT ... ASSIGN TO"| B["実際のファイル
sales.txt"] A -->|"FD で定義"| C["レコードの形
SALES-REC"]

図の説明: SELECT で、プログラムの中の名前と実際のファイルを結び付けます。FD（12.4）はその名前に対応するレコードの形を定義します。

もう 1 つ、エラーを調べるために FILE STATUS IS という句を付けることができます。これは「ファイルの操作が成功したか失敗したかを、この項目に入れてください」という指定です。くわしくは 12.7 で扱います。

FILE STATUS句を付けた場合 ENVIRONMENT DIVISIONの抜粋 
      * FILE STATUSで操作の結果を受け取る
       FILE-CONTROL.
           SELECT SALES-FILE ASSIGN TO "sales.txt"
               ORGANIZATION IS LINE SEQUENTIAL
               FILE STATUS IS WS-FS.

ヒント: FILE-CONTROL を書く場所

FILE-CONTROL は、環境部（ENVIRONMENT DIVISION）の中の INPUT-OUTPUT SECTION に書きます。「ENVIRONMENT DIVISION → INPUT-OUTPUT SECTION → FILE-CONTROL → SELECT 文」という入れ子です。SELECT 文の最後（ピリオド）まで 1 つの文なので、ORGANIZATION 句の行末のピリオドを忘れないでください。FILE STATUS 句があるときは、ピリオドはいちばん最後の句の後に 1 つだけです。

12.4 データ部でレコードの形を定義する（FILE SECTION と FD）

2 つめがデータ部（DATA DIVISION）の ファイル節（FILE SECTION）です。ここに FD（File Description：ファイル記述）を書いて、ファイルの中のレコードがどんな形をしているかを定義します。第9章で学んだ SALES-REC を、そのまま FD の下に置きます。

ファイル節の書き方 DATA DIVISIONの抜粋 
      * ファイル節: レコードの形を定義する
       FILE SECTION.
       FD  SALES-FILE.
       01  SALES-REC.
           05  SR-DATE     PIC X(8).
           05  SR-ITEM     PIC X(4).
           05  SR-QTY      PIC 9(3).
           05  SR-PRICE    PIC 9(5).
  • FD SALES-FILE. … FILE-CONTROL で決めたファイル名と同じ名前を書きます。FD は A 領域（8 桁目）から書き始めます。
  • 01 SALES-REC. … FD のすぐ下に、レコードの定義を書きます。READ をすると、ファイルから読んだ 1 行がこのレコードの領域に入ります。

ヒント: ファイルのレコード領域は「窓口」

FD の下に書いたレコード領域は、ファイルとプログラムのあいだにある受け渡しの窓口のようなものです。READ をするたびに窓口に 1 行ぶんのデータが置かれ、プログラムは SR-ITEM や SR-QTY のように項目名でそれを取り出します。WORKING-STORAGE SECTION とは別の場所なので、ファイル節の項目には VALUE 句で初期値を付けません（規格では書けない決まりで、GnuCOBOL では書いてもエラーにならず無視されます）。作業用の項目は、別途 WORKING-STORAGE SECTION に用意しましょう。

ファイルの形とプログラムの定義がずれると

ファイルの 1 行は 20 桁なのに、レコードの定義を PIC 9(4) のように間違えると、数量や単価の読み取り位置がずれて、おかしな値になります。ファイルの設計書（どの桁に何があるか）とレコード定義は、1 桁もずらさず一致させることが大切です。

12.5 OPEN・READ・CLOSE でファイルを読む

準備ができたので、手続き部（PROCEDURE DIVISION）でファイルを読みます。使う命令は 3 つだけです。

命令 書き方の例 はたらき
OPEN OPEN INPUT SALES-FILE ファイルを開く。INPUT は「読むために開く」
READ READ SALES-FILE AT END ... END-READ 次の 1 レコードを読む。もう無ければ AT END の処理へ
CLOSE CLOSE SALES-FILE ファイルを閉じる。使い終わったら必ず閉じる

READ と「ファイルの終わり」

READ は、呼ぶたびにファイルの次の 1 行を読み進めます。ファイルの最後まで読み終えたあとにもう一度 READ すると、「もう読むものが無い」状態、つまりファイルの終端（end of file）になります。これを検知するのが AT END です。ここでは、第7章で学んだ条件名（88 レベル）を使い、終端に達したら WS-EOF-YES を真にして知らせます。

終端を知らせる目印（作業場所節） DATA DIVISIONの抜粋 
      * 終端を知らせる目印を用意する
       WORKING-STORAGE SECTION.
       01  WS-EOF          PIC X VALUE "N".
           88  WS-EOF-YES  VALUE "Y".
READ文の基本形 PROCEDURE DIVISIONの抜粋 
      * ファイルの終端でフラグを立てる
           READ SALES-FILE
               AT END SET WS-EOF-YES TO TRUE
           END-READ

「先読み」のパターン

ファイルを読むプログラムには、定番の型があります。ループに入る前に最初の 1 件を読んでおき（先読み）、ループの最後で次の 1 件を読む、という形です。ループの先頭で「終わりか？」を判断し、終わりでなければ処理して、最後に次を読みます。

flowchart TD A["OPEN"] --> B["READ（先読み）"] B --> C{"終端？"} C -->|"いいえ"| D["処理（DISPLAYなど）"] D --> E["READ（次の1件）"] E --> C C -->|"はい"| F["CLOSE"]

図の説明: 先読みのパターンです。「読む → 終わりか確認 → 処理 → 次を読む」の順なので、処理に入った時点では、必ず「読み込みに成功したレコード」が手元にあります。

この型を使った完成形が次のプログラムです。ファイルの全レコードを画面に表示します。環境部・データ部と手続き部の 2 つの部品に分けて掲載します。それぞれ単独では動きません。順につなげて 1 つのファイル（readsale.cob）に保存します。必要な見出し行（IDENTIFICATION DIVISION. から WORKING-STORAGE SECTION. までは部品 1 に、PROCEDURE DIVISION. は部品 2 の先頭に）は、どちらも部品の中に含まれています。

readsale.cob（部品 1/2） 見出し部・環境部・データ部の抜粋 
      * 売上ファイルを1件ずつ読んで表示する
       IDENTIFICATION DIVISION.
       PROGRAM-ID. READSALE.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT SALES-FILE ASSIGN TO "sales.txt"
               ORGANIZATION IS LINE SEQUENTIAL.
       DATA DIVISION.
       FILE SECTION.
       FD  SALES-FILE.
       01  SALES-REC.
           05  SR-DATE     PIC X(8).
           05  SR-ITEM     PIC X(4).
           05  SR-QTY      PIC 9(3).
           05  SR-PRICE    PIC 9(5).
       WORKING-STORAGE SECTION.
       01  WS-EOF          PIC X VALUE "N".
           88  WS-EOF-YES  VALUE "Y".
readsale.cob（部品 2/2） PROCEDURE DIVISIONの抜粋 
       PROCEDURE DIVISION.
       MAIN-PROC.
      * 先読み: 最初の1件を読む
           OPEN INPUT SALES-FILE
           READ SALES-FILE
               AT END SET WS-EOF-YES TO TRUE
           END-READ
      * 終端まで、表示→次を読む を繰り返す
           PERFORM UNTIL WS-EOF-YES
               DISPLAY SR-DATE " " SR-ITEM " " SR-QTY " " SR-PRICE
               READ SALES-FILE
                   AT END SET WS-EOF-YES TO TRUE
               END-READ
           END-PERFORM
           CLOSE SALES-FILE
           STOP RUN.

コンパイルして実行しましょう。sales.txt は同じフォルダに置いておきます。

ターミナル 
cobc -x readsale.cob
./readsale
実行結果 
20261001 A001 003 00120
20261001 A002 005 00080
20261002 B001 002 01500
20261002 A003 010 00150
20261003 C001 001 00980
20261003 B002 004 00500

6 件の売上が、日付・商品コード・数量・単価に分かれて表示されました。DISPLAY の間に " " を入れているので、項目の境目がわかります。

先読みをしないと何が起きるか

先読みの型を使わず、ループの先頭で READ して、そのまま処理を続けるとどうなるでしょうか。やってみましょう。

よくある誤り（読んだ直後に終端を確認していない） PROCEDURE DIVISIONの抜粋 
      * 誤り: 読んだ直後に終端を確かめずに表示している
           PERFORM UNTIL WS-EOF-YES
               READ SALES-FILE
                   AT END SET WS-EOF-YES TO TRUE
               END-READ
               DISPLAY SR-DATE " " SR-ITEM " " SR-QTY " " SR-PRICE
           END-PERFORM
実行結果（誤り） 
20261001 A001 003 00120
20261001 A002 005 00080
20261002 B001 002 01500
20261002 A003 010 00150
20261003 C001 001 00980
20261003 B002 004 00500
20261003 B002 004 00500

最後の 1 件（20261003 B002 ...）が2 回表示されてしまいました。7 回目の READ では終端に達して AT END が実行されますが、その直後に DISPLAY が実行され、レコード領域に残っていた前回のデータを表示してしまったからです。

終端に達したあとのレコード領域

終端に達したあとのレコード領域の内容は、COBOL の規格では保証されていません（上の例は GnuCOBOL での結果です）。「READ → 終端かどうか確認 → 処理」の順を守る先読みの型を、必ず使いましょう。

重要ポイント: ファイルの読み方の型

ファイルを読むプログラムは、OPEN → READ（先読み）→ ループ（処理 → READ）→ CLOSE の型で書きます。型どおりに書けば、「最後の 1 件を処理し忘れる」「最後の 1 件を 2 回処理する」といった事故を防げます。業務プログラムの大半は、この型の上に作られています。

OPEN の前に READ しない・閉じ忘れない

OPEN する前の READ や、すでに開いているファイルへの OPEN は、実行時エラーの原因になります（くわしくは 12.7）。また、CLOSE を忘れると、出力ファイルの最後のデータがディスクに書き込まれないことがあります。「開いたら、必ず閉じる」を習慣にしましょう。

12.6 WRITE でファイルに書き出す

今度は、読んだデータを加工して別のファイルに書き出してみましょう。出力ファイルを使うには、入力ファイルと同じように FILE-CONTROL に SELECT を書き、FD でレコードを定義します。違いは、OPEN するときに OUTPUT を指定することと、READ の代わりに WRITE を使うことです。

OPEN の種類 使いどき ファイルが既にあると
OPEN INPUT 読み込む 先頭から読める（無いとエラー）
OPEN OUTPUT 新しく書き出す 中身を空にして、最初から書き直す
OPEN EXTEND 既存のファイルの末尾に追記する 元の内容を残して、後ろに足す

次のプログラムは、sales.txt を 1 件ずつ読み、「商品コードと金額（数量 × 単価）」を整形して amount.txt に書き出します。ここも 2 つの部品に分けて掲載します。それぞれ単独では動きません。順につなげて 1 つのファイル（writeamt.cob）に保存します。見出し行のうち WORKING-STORAGE SECTION. は部品 1 にあり、部品 2 の 01 WS-LINE. はその続きです（見出しの書き足しは不要）。PROCEDURE DIVISION. は部品 2 に含まれています。

writeamt.cob（部品 1/2） 見出し部・環境部・データ部の抜粋 
      * 売上を読み、商品コードと金額を書き出す
       IDENTIFICATION DIVISION.
       PROGRAM-ID. WRITEAMT.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT SALES-FILE ASSIGN TO "sales.txt"
               ORGANIZATION IS LINE SEQUENTIAL.
           SELECT AMT-FILE ASSIGN TO "amount.txt"
               ORGANIZATION IS LINE SEQUENTIAL.
       DATA DIVISION.
       FILE SECTION.
       FD  SALES-FILE.
       01  SALES-REC.
           05  SR-DATE     PIC X(8).
           05  SR-ITEM     PIC X(4).
           05  SR-QTY      PIC 9(3).
           05  SR-PRICE    PIC 9(5).
       FD  AMT-FILE.
       01  OUT-REC         PIC X(12).
       WORKING-STORAGE SECTION.
       01  WS-EOF          PIC X VALUE "N".
           88  WS-EOF-YES  VALUE "Y".
       01  WS-AMOUNT       PIC 9(7).
writeamt.cob（部品 2/2） DATA DIVISION（続き）・PROCEDURE DIVISIONの抜粋 
      * 書き出す行を作業場所節で組み立てる
       01  WS-LINE.
           05  WS-L-ITEM   PIC X(4).
           05  FILLER      PIC X VALUE SPACE.
           05  WS-L-AMT    PIC ZZZ,ZZ9.
       PROCEDURE DIVISION.
       MAIN-PROC.
           OPEN INPUT SALES-FILE
           OPEN OUTPUT AMT-FILE
           READ SALES-FILE
               AT END SET WS-EOF-YES TO TRUE
           END-READ
           PERFORM UNTIL WS-EOF-YES
               COMPUTE WS-AMOUNT = SR-QTY * SR-PRICE
               MOVE SR-ITEM TO WS-L-ITEM
               MOVE WS-AMOUNT TO WS-L-AMT
               WRITE OUT-REC FROM WS-LINE
               READ SALES-FILE
                   AT END SET WS-EOF-YES TO TRUE
               END-READ
           END-PERFORM
           CLOSE SALES-FILE AMT-FILE
           STOP RUN.

ポイントは、書き出す行を作業場所節の WS-LINE にいったん組み立ててから、WRITE OUT-REC FROM WS-LINE で書くところです。FROM を付けると、WS-LINE の内容が出力レコード OUT-REC に移されてから書き出されます。金額は編集項目 ZZZ,ZZ9（第5章）を通すことで、桁区切りが付いた読みやすい形になります。

ターミナル 
cobc -x writeamt.cob
./writeamt
cat amount.txt
amount.txt の中身 
A001     360
A002     400
B001   3,000
A003   1,500
C001     980
B002   2,000

画面には何も表示されませんが、amount.txt が作られ、6 行が書き込まれました。cat は、ファイルの中身を画面に表示するコマンドです（Windows でも WSL2 の Ubuntu のターミナルなら、同じく cat で見られます）。

READ はファイル名、WRITE はレコード名

READ ではファイルの名前（READ SALES-FILE）を、WRITE ではレコードの名前（WRITE OUT-REC）を書きます。間違えやすいので、「READ は“どのファイルから読むか”を、WRITE は“どのレコードを書くか”を書く」（Read a file, Write a record）と覚えましょう。なお GnuCOBOL では、行順ファイルに書き出すときにレコード末尾の空白が取り除かれます（この例は金額を右寄せしているので、どの行も 12 桁です）。規格・処理系によっては扱いが異なります。

OPEN EXTEND で追記する

OPEN OUTPUT は、すでにあるファイルの中身を消してしまいます。ログのように「前の内容を残したまま、後ろに足していきたい」ときは OPEN EXTEND を使います。

追記する場合の手続き（イメージ） PROCEDURE DIVISIONの抜粋 
      * 既存のログの末尾に1行追記する
           OPEN EXTEND LOG-FILE
           MOVE "20261004D00100100200" TO LOG-REC
           WRITE LOG-REC
           CLOSE LOG-FILE

ヒント: EXTEND はファイルが無いとエラー

GnuCOBOL 3.1.2 で確認したところ、追記先のファイルが存在しないと、OPEN EXTEND は「ファイルが無い（状態 35）」というエラーになりました。最初の 1 回だけ OPEN OUTPUT で作る、あらかじめ空のファイルを用意しておく、などの工夫が必要です。また、SELECT 文に OPTIONAL を付けて SELECT OPTIONAL LOG-FILE ASSIGN TO "log.txt" と書くと、ファイルが無いときは新しく作られます（GnuCOBOL 3.1.2 で確認。このときファイル状態は 05 になります）。処理系によって動作が異なる部分なので、現場ではその環境の仕様を確認します。

12.7 ファイル状態（FILE STATUS）でエラーに備える

ファイルの操作は、いつでも成功するとは限りません。ファイルが存在しない、すでに開いている、といった理由で失敗することがあります。FILE-CONTROL で FILE STATUS IS WS-FS と書いておくと、OPEN・READ・WRITE・CLOSE のたびに、その結果が 2 桁の文字として WS-FS に入ります。これがファイル状態（FILE STATUS）です。

受け取る項目は、作業場所節に PIC XX（2 文字）で用意します。

ファイル状態を受け取る項目 DATA DIVISIONの抜粋 
      * ファイル状態を受け取る2文字の項目
       WORKING-STORAGE SECTION.
       01  WS-FS           PIC XX.
値 意味 どんなとき
00 正常 操作が問題なく成功した
10 ファイルの終端 READ で、もう読むレコードが無かった
35 ファイルが無い OPEN INPUT したが、ファイルが存在しない（名前の書き間違い、置き場所の違い）
41 すでに開いている 開いているファイルに、もう一度 OPEN した
42 開いていない 開いていないファイルを CLOSE した
47 読める状態になっていない OPEN する前のファイルを READ した
48 書ける状態になっていない INPUT で開いたファイルに WRITE した

上の値は、GnuCOBOL 3.1.2 で実際に起こして確認したものです。2 桁のうち左の数字が大まかな分類（0 = 成功、1 = ファイルの終わり、3 = ファイルが無いなど、やり直しても直らないエラー、4 = 開いていないのに読むなど、命令の使い方の誤り）を、右の数字が詳しい理由を表します。これらの値は規格で決められていて、メインフレームの COBOL でも多くが同じ意味ですが、細かな値は処理系によって異なることがあります。

実際にファイル状態の変化を見てみましょう。次のプログラムは、OPEN と READ のたびに WS-FS を表示します。READ の後ろに AT END を書いていませんが、FILE STATUS を指定してあるので、終端に達しても止まらずにファイル状態 10 が入ります。2 つの部品に分けて掲載します。それぞれ単独では動きません。順につなげて 1 つのファイル（chkfs.cob）に保存します。見出し行は、部品 1 に IDENTIFICATION DIVISION. から WORKING-STORAGE SECTION. まで、部品 2 の先頭に PROCEDURE DIVISION. が含まれています。

chkfs.cob（部品 1/2） 見出し部・環境部・データ部の抜粋

       PROGRAM-ID. CHKFS.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.

               ORGANIZATION IS LINE SEQUENTIAL
               FILE STATUS IS WS-FS.

       FILE SECTION.
       FD  SALES-FILE.
       01  SALES-REC.
           05  SR-DATE     PIC X(8).
           05  SR-ITEM     PIC X(4).
           05  SR-QTY      PIC 9(3).
           05  SR-PRICE    PIC 9(5).
       WORKING-STORAGE SECTION.
       01  WS-FS           PIC XX.
chkfs.cob（部品 2/2） PROCEDURE DIVISIONの抜粋 
      * 手続き部: ファイル状態を表示しながら読む
       PROCEDURE DIVISION.

           OPEN INPUT SALES-FILE
           DISPLAY "OPEN後の状態  : " WS-FS

OPEN も READ も 00 で成功し、6 件を読み終えたあとの 7 回目の READ で 10（終端）になりました。次に、sales.txt が無いフォルダで同じプログラムを実行してみます。

実行結果（sales.txt が無い場合） 
OPEN後の状態  : 35
ファイルを開けません

ファイルが無いので OPEN で 35 が返り、プログラムが「ファイルを開けません」と表示して安全に終了しました。FILE STATUS を調べていれば、エラーでもプログラムが突然止まらず、自分で後始末や案内メッセージを出せます。

flowchart TD A["OPEN INPUT"] --> B{"ファイル状態は00？"} B -->|"はい"| C["READのループへ進む"] B -->|"いいえ（35など）"| D["エラーメッセージを表示して終了"]

図の説明: OPEN のあとにファイル状態を確認する流れです。00 以外ならメッセージを出して終了し、00 なら読み込みを続けます。

では、FILE STATUS を書かなかったプログラムで、同じようにファイルが無いと何が起きるでしょうか。先ほどの readsale（FILE STATUS なし）を、sales.txt の無いフォルダで実行すると、次のようになります。

実行結果（FILE STATUS を書かなかった場合） 
libcob: error: file does not exist (status = 35) for file SALES-FILE ('sales_txt' => sales.txt)

実行時にエラー（status = 35）が表示されて、プログラムが強制的に止まりました。FILE STATUS を指定しないと、プログラム側でエラーに対処できません。

重要ポイント: 業務プログラムでは FILE STATUS を必ず付ける

現場の業務プログラムでは、すべてのファイルに FILE STATUS を付け、OPEN の直後に必ず確認するのが基本です。夜間のバッチ処理が突然止まっても、運用担当者はすぐには対応できません。「どのファイルで、どんな状態だったか」をメッセージに出して終了すれば、原因の調査が格段に楽になります。

やってみよう 12-1: 売上明細を表示し、1,000円以上だけ big.txt に書き出そう

sales.txt を読み、明細の表示と集計、そして大きな売上だけを別ファイルに抜き出すプログラム salesrpt.cob を作ります。

手順

  • 1 sales.txt を読み、1 件ごとに商品コード・数量・単価・金額（数量 × 単価）を表示する。
  • 2 最後に、読み込んだ件数と合計金額を表示する。
  • 3 金額が 1,000 円以上のレコードだけを、元の 20 桁のまま big.txt に書き出す。
  • 4 sales.txt と big.txt のどちらも、開けなかったらファイル状態を表示して終了する。

ヒント

  • ・処理を INIT-PROC（初期処理）・DETAIL-PROC（明細処理）・TERM-PROC（終了処理）の段落に分けると読みやすくなります（第8章）。
  • ・READ の命令は何度も使うので、READ-PROC という段落にまとめると、先読みとループ末尾で同じ段落を呼べます。
  • ・金額の判定は IF WS-AMOUNT >= 1000、書き出しは WRITE BIG-REC FROM SALES-REC です。
解答例を表示

4 つの部品に分けて掲載します。それぞれ単独では動きません。順につなげて 1 つのファイル（salesrpt.cob）に保存します。見出し行のうち WORKING-STORAGE SECTION. と PROCEDURE DIVISION. は部品 2 に含まれ、部品 3・4 は手続き部の続き（段落）です。

      * 初期処理と読み込みの段落
       INIT-PROC.
           OPEN INPUT SALES-FILE
           IF WS-FS NOT = "00"
               DISPLAY "sales.txtを開けません 状態=" WS-FS
               STOP RUN
           END-IF
           OPEN OUTPUT BIG-FILE
           IF WS-FS-BIG NOT = "00"
               DISPLAY "big.txtを開けません 状態=" WS-FS-BIG
               STOP RUN
           END-IF
           DISPLAY "商品  数量    単価    金額"
           PERFORM READ-PROC.
       READ-PROC.
           READ SALES-FILE
               AT END SET WS-EOF-YES TO TRUE
           END-READ.
salesrpt.cob（部品 4/4） PROCEDURE DIVISIONの抜粋 
      * 明細処理と終了処理の段落
       DETAIL-PROC.
           COMPUTE WS-AMOUNT = SR-QTY * SR-PRICE
           ADD 1 TO WS-COUNT
           ADD WS-AMOUNT TO WS-TOTAL
           MOVE SR-PRICE TO WS-PRICE-ED
           MOVE WS-AMOUNT TO WS-AMT-ED
           DISPLAY SR-ITEM "  " SR-QTY "  " WS-PRICE-ED "  " WS-AMT-ED
           IF WS-AMOUNT >= 1000
               WRITE BIG-REC FROM SALES-REC
           END-IF.
       TERM-PROC.
           CLOSE SALES-FILE BIG-FILE
           MOVE WS-TOTAL TO WS-TOTAL-ED
           DISPLAY "件数: " WS-COUNT " 件"
           DISPLAY "合計金額: " WS-TOTAL-ED " 円".

解説

  • ・MAIN-PROC が「初期処理 → 明細処理と読み込みの繰り返し → 終了処理」を呼び出す、第8章で学んだ構造化の形です。
  • ・初期処理で OPEN したあと、ファイル状態（WS-FS、出力側は WS-FS-BIG）が 00 でなければメッセージを出して終了します。続けて先読み（PERFORM READ-PROC）を行います。
  • ・金額が 1,000 円以上の 3 件（3,000 円・1,500 円・2,000 円）だけが big.txt に書き出され、その元レコードは 20 桁のまま出力されます。
  • ・件数と合計は、明細処理のたびに ADD で積み上げ、終了処理で編集項目に移して表示しています。単価と金額も、数字項目のまま計算してから編集項目へ MOVE して表示しています。

理解度確認クイズ

  • Q1. 環境部の SELECT SALES-FILE ASSIGN TO "sales.txt" と、データ部の FD SALES-FILE は、それぞれ何を決めていますか？

    回答を表示

    SELECT 〜 ASSIGN は、プログラムの中で使うファイル名（SALES-FILE）と、ディスク上の実際のファイル（sales.txt）を結び付けます。FD は、そのファイルの中のレコードの形（どの桁に何の項目があるか）を定義します。

  • Q2. ファイルを読むとき、ループに入る前に READ を 1 回行う（先読みする）のはなぜですか？

    回答を表示

    ループの先頭で「終端かどうか」を判断してから処理に入れるようにするためです。先読みをせずに READ の直後に処理すると、終端に達したあとも前のレコードの内容が残っていて、最後の 1 件を 2 回処理してしまうなどの事故が起きます。

  • Q3. ファイル状態が 10 と 35 のとき、それぞれ何が起きていますか？

    回答を表示

    10 は、READ でもう読むレコードが無いファイルの終端です（エラーではなく、ファイルを読み終えたという合図）。35 は、OPEN INPUT したファイルが存在しないエラーです。ファイル名の書き間違いや、置き場所の違いが主な原因です。

  • Q4. すでにある log.txt に、内容を残したまま 1 行追記したいとき、OPEN の種類は何を指定しますか？ OPEN OUTPUT を使うとどうなりますか？

    回答を表示

    OPEN EXTEND を指定します。OPEN OUTPUT だと、すでにあるファイルの中身が空にされてから書き込まれるため、それまでの内容が消えてしまいます。
