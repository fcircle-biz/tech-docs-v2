ホーム Struts 1 第6章
第6章 所要時間: 約90分

DBと連携する

第1〜5章で「画面から Action までの流れ」を固めました。この章ではその先——Action が DB とどうやりとりするかを学びます。合言葉は「Action に SQL を書かない」です。JavaBeans（DTO）・DAO という2つの部品を導入し、一覧表示と検索処理を実際に組み立てます。

この章で学ぶこと

  • Struts（Action）と DAO の責務分担（「画面制御」と「データアクセス」の分離）を説明できる
  • JavaBeans（DTO）の役割と、JSP から使えるための getter の必要性を理解する
  • DAO で Connection・PreparedStatement・ResultSet を安全に扱えるようになる
  • 一覧表示・検索処理を Action → DAO → DB → JSP の流れで組み立てられる
  • SQL 文字列連結を避けるべき理由（SQL インジェクション）を説明できる

6.1 Struts と DAO の責務分担

第1章の MVC 対応表を思い出してください。Model の実体は「ActionForm・JavaBeans・DAO」でした。この章ではその中の JavaBeans（DTO） と DAO を扱います。まず大切なのは、それぞれの担当を明確に線引きすることです。

登場人物 担当すること 担当しないこと
Action 画面制御（DAOの呼び出し、結果をrequestへ渡す、遷移先の決定） SQL を書くこと
DAO データアクセス（SQL の実行、ResultSet の詰め替え） 画面遷移や入力チェック
JavaBeans（DTO） データの運び屋（1件分のデータを保持する入れ物） SQL・画面制御のどちらも

業務ロジックが複雑になる場合は、Action と DAO の間に Service（任意） を挟むこともあります（6.6 で扱います）。まずはこの一連の流れとデータの戻り方を図で確認しましょう。

なぜ「Action に SQL を書かない」のか

理由は3つあります。①テストしやすさ: DAO を分けると DB 接続なしでロジックだけをテストしやすくなります。②再利用性: 同じ SQL 処理を別の Action からも呼び出せます。③可読性: Action を開けば「何をする画面か」が一目で分かり、SQL の詳細は DAO を見ればよいと役割が明確になります。既存システムを読むときも、この線引きを知っていれば「この処理はどこに書いてあるはずか」を予測できます。

6.2 JavaBeans（DTO）を用意する

DAO が DB から取得した1件分のデータを、Java のオブジェクトとして持ち運ぶための入れ物が JavaBeans（DTO: Data Transfer Object）です。ここでは「社員」を表す Employee クラスを作ります。

com/example/dto/Employee.java — フィールド定義 
package com.example.dto;

import java.util.Date;

// 社員情報を表すJavaBeans（DTO）
public class Employee {
    private int id;                  // 社員ID
    private String name;             // 氏名
    private String department;       // 所属部署
    private Date hireDate;           // 入社日
    // ここから先はgetter/setterのみ（下のコードを参照）
}

各フィールドに getter/setter を用意します。第5章で学んだ <bean:write> は、内部で getter を呼び出して値を取得しています。getter が無いフィールドは JSP から表示できません。

com/example/dto/Employee.java — getter/setter（抜粋） 
// Employeeクラスの続き（departmentも同様に用意する）
public int getId() { return id; }
public void setId(int id) { this.id = id; }
public String getName() { return name; }
public void setName(String name) { this.name = name; }
public Date getHireDate() { return hireDate; }
public void setHireDate(Date hireDate) { this.hireDate = hireDate; }

JSP 側での対応関係も確認しておきましょう。property に指定した名前から、Struts は決まったルールで getter メソッド名を組み立てます。

JSP側の記述 呼び出されるgetter
property="name" getName()
property="department" getDepartment()

DTOとActionFormは似ているが役割が違う

第4章で学んだ ActionForm も getter/setter を持つ入れ物でしたが、役割は「画面からの入力を受け取る」ことでした。一方 DTO は「DB から取り出したデータを運ぶ」役割です。似た形でも用途が違う、と覚えておくと既存コードを読むときに混乱しません。

6.3 DAOの実装

DAO（Data Access Object）は「DB とやりとりする専門の窓口」です。Connection の取得、PreparedStatement の実行、ResultSet から List への詰め替えという一連の作業を、いつも同じ手順で行います。まずはフィールド部分です。

com/example/dao/EmployeeDao.java — 接続情報 
package com.example.dao;

import java.sql.*;
import java.util.*;
import com.example.dto.Employee;

public class EmployeeDao {
    // JDBC接続情報（本来は設定ファイルなどから読み込む）
    private static final String URL  = "jdbc:mysql://localhost:3306/sample";
    private static final String USER = "app_user";
    private static final String PASS = "app_pass";
}

ResultSet の1行を Employee に詰め替える処理は、複数のメソッドで共通して使うのでメソッドに切り出しておきます。

com/example/dao/EmployeeDao.java — 行の詰め替え 
// 1行分のResultSetをEmployeeへ詰め替える（findAll・検索処理で共通利用）
private Employee toEmployee(ResultSet rs) throws SQLException {
    Employee e = new Employee();
    e.setId(rs.getInt("id"));
    e.setName(rs.getString("name"));
    e.setDepartment(rs.getString("department"));
    e.setHireDate(rs.getDate("hire_date"));
    return e;
}

いよいよ全件取得の findAll() です。Struts 1 が現役だった時代は Java 7 未満の現場も多く、try-with-resources（Java 7 で追加）が使えないことがあります。そのため finally で明示的にクローズする書き方を基本形として覚えてください。

com/example/dao/EmployeeDao.java — findAll()（前半） 
public List<Employee> findAll() throws SQLException {
    String sql = "SELECT id, name, department, hire_date "
               + "FROM employee ORDER BY id";
    List<Employee> list = new ArrayList<Employee>();
    Connection con = null;
    PreparedStatement ps = null;
    ResultSet rs = null;
    try {
        con = DriverManager.getConnection(URL, USER, PASS);
        ps = con.prepareStatement(sql);
        rs = ps.executeQuery();
com/example/dao/EmployeeDao.java — findAll()（後半） 
        while (rs.next()) {
            list.add(toEmployee(rs));   // 詰め替えはtoEmployeeに任せる
        }
    } finally {
        // Java 7未満の現場も多く、try-with-resourcesが使えないことがある
        if (rs != null) try { rs.close(); } catch (SQLException ignore) {}
        if (ps != null) try { ps.close(); } catch (SQLException ignore) {}
        if (con != null) try { con.close(); } catch (SQLException ignore) {}
    }
    return list;
}

List<Employee> のようなジェネリクス表記は、比較的新しめの環境（Java 5 以降）で使えます。古い現場のコードでは、型を指定しない素の List のまま書かれていることもあります。動きは同じなので、読むときは読み替えてください。

補足: Connectionの取得方法いろいろ

上の例は学習用に DriverManager を直接使っていますが、現場では次のような方法もよく見られます。

  • DriverManager 直接: 学習用・小規模向け。接続のたびにコネクションを新規作成する。なお JDBC 4 未満（Java 6 以前）の旧環境では、DriverManager.getConnection() の前に Class.forName("com.mysql.jdbc.Driver") のようにドライバクラスを明示的にロードする一文が必要になる（JDBC 4 以降は自動検出されるため不要）
  • DataSource（JNDI・commons-dbcp 等）: 実務で主流。コネクションプールにより接続を使い回し、性能とリソース管理に優れる
  • Struts 1 の <data-sources>: struts-config.xml で DB 接続を定義できる古い機能。現在は非推奨であり、新規に使うべきではない（既存コードで見かけたら「昔の書き方」と理解する程度でよい）

6.4 一覧表示を作る

部品が揃ったので、第3章で学んだ Action と第5章で学んだ <logic:iterate> を使って、実際に一覧画面をつなげます。流れは第1章 1.4 で見た全体像そのものです。

com/example/action/ListAction.java 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    // DAOを呼び出して社員一覧を取得する（SQLはここに書かない）
    EmployeeDao dao = new EmployeeDao();
    List<Employee> employees = dao.findAll();
    // JSPへ渡す（属性名"employees"はJSP側のnameと一致させる）
    request.setAttribute("employees", employees);
    return mapping.findForward("success");
}

JSP 側は、request.setAttribute("employees", ...) と同じ名前 name="employees" を <logic:iterate> に指定してループ表示します。

list.jsp — 一覧表示 
<table>
  <logic:iterate id="employee" name="employees">
    <tr>
      <td><bean:write name="employee" property="id" /></td>
      <td><bean:write name="employee" property="name" /></td>
      <td><bean:write name="employee" property="department" /></td>
    </tr>
  </logic:iterate>
</table>

struts-config.xml 側の定義は第2章で学んだ形と同じです。/employee/list.do が来たら ListAction を呼び、成功時に list.jsp へ進みます。

struts-config.xml — 一覧画面の対応 
<action path="/employee/list"
        type="com.example.action.ListAction"
        scope="request">
    <forward name="success" path="/list.jsp" />
</action>

ここまでで「画面 → .do → Action → DAO → DB → JSP」という一連の流れが、第1〜6章で学んだ知識だけで説明できることに気づいたはずです。次は、これに検索条件を加えます。

6.5 検索処理を作る

検索画面では、第4章で学んだ ActionForm（EmployeeForm）が入力値（氏名・部署）を受け取り、それを DAO に渡して SQL の条件に反映します。ここで絶対にやってはいけない書き方から見ておきましょう。

NG例 — 文字列連結でSQLを組み立てる 
// NG: nameをそのまま文字列連結している
String sql = "SELECT * FROM employee WHERE name LIKE '%" + name + "%'";
Statement stmt = con.createStatement();
ResultSet rs = stmt.executeQuery(sql);  // name次第で任意のSQLが実行されうる

SQL文字列連結はSQLインジェクションの原因になる

検索キーワードに ' OR '1'='1 のような文字列が入力されると、意図しない SQL が実行されてしまいます。これをSQLインジェクションと呼びます。既存の Struts 1 システムで文字列連結の SQL を見つけたら、それは修正すべき脆弱性として扱ってください。対策は次に示す PreparedStatement の ?（プレースホルダ）を使うことです。

正しくは、SQL に ? を書いておき、値は setString() などであとから安全にバインドします。JDBC ドライバが特殊文字を適切にエスケープしてくれるため、値がそのまま SQL の一部として解釈されることはありません。

com/example/dao/EmployeeDao.java — search() 
// name・department条件で検索する（?プレースホルダなのでSQLインジェクションの心配がない）
public List<Employee> search(String name, String department) throws SQLException {
    // 空文字・nullは全件相当の条件にする（LIKE '%'は全件ヒット）
    String nameCond = (name == null || name.length() == 0) ? "%" : "%" + name + "%";
    String deptCond = (department == null || department.length() == 0) ? "%" : "%" + department + "%";
    String sql = "SELECT id, name, department, hire_date "
               + "FROM employee WHERE name LIKE ? AND department LIKE ? ORDER BY id";
    List<Employee> list = new ArrayList<Employee>();
    PreparedStatement ps = con.prepareStatement(sql);  // ※ Connection の取得とクローズは 6.3 と同じため省略
    ps.setString(1, nameCond);
    ps.setString(2, deptCond);
    ResultSet rs = ps.executeQuery();
    while (rs.next()) list.add(toEmployee(rs));
    return list;
}

コード中のコメントの通り、Connection の取得と finally によるクローズ処理は紙面の都合上省略していますが、実際には findAll()（6.3）とまったく同じ手順で書きます。省略してよいのは紙面上の話だけで、実装では必ず書いてください。

検索条件が「氏名」「部署」の2つだけでなく「入社日の範囲」など、さらに条件が増える場合は、StringBuilder で SQL を組み立てながら、条件が指定された項目だけ AND でつなぐのが基本方針です。この場合も値は必ず ? でバインドし、値そのものを文字列連結しないという原則は変わりません。

動的SQLの組み立て方針（イメージ） 
// SQL文の"骨組み"はStringBuilderで作るが、値は連結しない
StringBuilder sql = new StringBuilder("SELECT * FROM employee WHERE 1=1");
if (department != null) sql.append(" AND department = ?");   // 条件を追加
if (from != null) sql.append(" AND hire_date >= ?");        // さらに追加
// ps.setString(1, department) のように、追加した順に値をバインドしていく

6.6 Service層を挟むかどうか

ここまでは Action → DAO の2階建てで話を進めてきました。小〜中規模の画面ではこれで十分です。しかし、次のようなケースでは間に Service（業務ロジック層） を挟むことがあります。

業務ロジックが複雑

複数の判定・計算をまとめる場合、Action に書くと肥大化するため Service に切り出します。

複数DAOを1つのトランザクションに

例えば「社員登録」と「履歴登録」を同時に行い、両方成功して初めてcommit、片方失敗したら両方rollbackする場合。

flowchart LR subgraph 小規模 A1["Action"] --> A2["DAO"] end subgraph トランザクションが必要 B1["Action"] --> B2["Service
commit／rollbackを制御"] B2 --> B3["DAO その1"] B2 --> B4["DAO その2"] end

既存の Struts 1 システムでは、Service 層のクラス名に統一されたルールはなく、現場ごとに次のような命名がよく使われます。読むときは、名前から役割を推測してください。

よく見る命名 傾向
EmployeeService 業務処理をまとめて呼ぶ、比較的新しめの命名
EmployeeLogic 「業務ロジック」を意味する命名。国内の現場でよく見られる
EmployeeBusiness Logic と同様の位置づけ。命名規約は現場ごとに異なる

迷ったら「まずAction→DAO」でよい

本ガイドの第7章では、学習をシンプルに保つため Action → DAO の2階建てで CRUD を作ります。Service を挟むかどうかは後からでも変更できる設計判断です。まずは責務分担の基本形（6.1）を体に染み込ませましょう。

つまずきやすいポイント

DB 連携は既存システムの不具合調査で頻繁に出会う領域です。よくあるつまずきを事前に押さえておきましょう。

ResultSetの閉じ忘れ

finally でクローズし忘れると接続が枯渇し、しばらく動いた後に急にエラーが出るようになります。

例外の握りつぶし

DAOで catch (Exception e) {} のように空のcatchを書くと、失敗しても原因が分からなくなります。最低限ログに残しましょう。

getterの欠落

DTOにgetterが無いと、JSPで No getter method というエラーになります（6.2参照）。

文字コードによる文字化け

DB接続URLの文字コード指定（例: characterEncoding=UTF-8）が抜けていると、日本語が化けることがあります。

属性名の不一致

request.setAttribute("employees", ...) のキーと、JSP側 <logic:iterate name="..."> のname属性が1文字でも違うと、一覧が空のまま表示されます（エラーにならないぶん気づきにくい）。

やってみよう 6-1: 社員一覧をDBから取得して表示する

DTO → DAO → Action → JSP という一連の流れを、実際に手を動かして組み立ててみましょう。

手順

  1. 1 Employee クラス（DTO）を作成し、id・name・department・hireDate の4フィールドと getter/setter を用意する。
  2. 2 EmployeeDao に findAll() を実装する。try/finally でのクローズを忘れないこと。
  3. 3 ListAction を作成し、DAO を呼び出して request.setAttribute("employees", ...) する。
  4. 4 struts-config.xml に /employee/list の <action> を追加し、list.jsp への <forward> を設定する。
  5. 5 list.jsp に <logic:iterate> と <bean:write> で一覧テーブルを書き、/employee/list.do にアクセスして表示を確認する。

理解度確認クイズ

  1. Q1. 「Action に SQL を書かない」べき理由を2つ以上挙げてください。

    回答を表示

    テストしやすさ（DBなしでロジックだけテストしやすい）、再利用性（同じDAOを別のActionからも呼べる）、可読性（Actionを見れば画面の流れが分かり、SQLの詳細はDAOに集約される）の3点です。

  2. Q2. JSPの<bean:write property="name">が正しく動くために、DTO側に何が必要ですか？

    回答を表示

    getName()というgetterメソッドが必要です。<bean:write>は内部でgetterを呼び出しているため、getterが無いと「No getter method」というエラーになります。

  3. Q3. SQL文字列連結の代わりにPreparedStatementの?を使うべき理由は何ですか？

    回答を表示

    文字列連結でSQLを組み立てると、入力値に悪意あるSQL断片が混ざるSQLインジェクションのリスクがあるためです。?プレースホルダに値をバインドすれば、値がSQLの一部として解釈されず安全になります。

  4. Q4. どのような場合にAction→DAOの間にServiceを挟むことを検討しますか？

    回答を表示

    業務ロジックが複雑でActionに書くと肥大化する場合や、複数のDAO呼び出しを1つのトランザクション（commit／rollback）としてまとめたい場合です。小規模な画面ではAction→DAOの2階建てで十分です。
