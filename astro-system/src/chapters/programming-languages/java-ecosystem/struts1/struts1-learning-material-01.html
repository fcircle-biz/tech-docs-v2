ホーム Struts 1 第1章
第1章 所要時間: 約60分

Struts 1とは何か

あなたはすでに Servlet と JSP で Web アプリを作る方法を知っています。この章では、その知識を土台に「Servlet/JSP だけで作ったアプリが、Struts 1 によってどう整理されるのか」を理解します。そして本ガイド全体を貫く1本の処理フロー——画面から .do を経て JSP に戻ってくるまで——を最初に俯瞰します。

この章で学ぶこと

  • Servlet/JSP だけで作った Web アプリが抱える課題を説明できる
  • Struts 1 を使う目的（何を肩代わりしてくれるのか）を理解する
  • Struts 1 における MVC の対応（Model・View・Controller が何にあたるか）を理解する
  • Struts 1 の処理フロー全体像を、登場人物の順番で説明できる

1.1 Servlet/JSPだけで作るとどうなるか

まずは「Struts を使わない世界」を思い出すところから始めましょう。Servlet と JSP だけで小さな画面を作るぶんには何の問題もありません。ところが、画面が 10 枚、50 枚と増えていくと、だんだん同じような悩みが現れます。Struts 1 は、この悩みに対する当時の答えとして生まれました。

よくある「分岐だらけのServlet」

1つの Servlet でいくつもの機能を受け持つと、次のようなコードになりがちです。見覚えがあるかもしれません。

EmployeeServlet.java — 機能が増えるほど膨らむ分岐 
// リクエストパラメータで機能を切り替える書き方
String mode = request.getParameter("mode");

if ("list".equals(mode)) {
    // 一覧の処理を書く（入力チェック・DB検索・画面へ渡す）
    request.getRequestDispatcher("/list.jsp").forward(request, response);
} else if ("search".equals(mode)) {
    // 検索の処理を書く
    request.getRequestDispatcher("/list.jsp").forward(request, response);
} else if ("update".equals(mode)) {
    // 更新の処理を書く
    request.getRequestDispatcher("/done.jsp").forward(request, response);
}   // ← 機能が増えるたびに if が伸びていく

3つの悩み

このような作り方を続けると、規模が大きくなったときに次の3点で行き詰まります。

① 分岐が肥大化する

1つの Servlet に機能を詰め込むほど if が伸び、どこを直せばよいか分からなくなります。

② JSPにロジックが混ざる

スクリプトレットで DB アクセスや判定を書くと、画面とロジックが分離できません。

③ 画面遷移が散らばる

遷移先の JSP 名が Java コードのあちこちに直書きされ、全体像が誰にも見えなくなります。

Struts はゼロから何かを発明したわけではない

Struts 1 も、内部では Servlet と JSP を使っています。魔法の技術ではなく、「Servlet/JSP をこう書くと整理できる」という型（フレームワーク）を用意したものだと考えてください。あなたが学んだ Servlet/JSP の知識は、そのまま Struts の理解に直結します。

1.2 Struts 1を使う目的

Apache Struts 1 は、2000 年代前半に広く普及した Java の Web アプリケーションフレームワークです。前節の3つの悩みに対して、Struts 1 は次のような「決まった置き場所」を用意します。

Servlet/JSPだけの場合 Struts 1 の場合
1つの Servlet に if で機能を詰め込む 機能ごとに1つの Action クラスを作る
遷移先 JSP を Java コードに直書きする 設定ファイル（struts-config.xml）に画面遷移を一覧で書く
request.getParameter() を1つずつ呼んで変換する ActionForm が入力値を自動でセットしてくれる
入力チェックを毎回自前で書く validate() という決まった置き場所に書く
JSP でスクリプトレットを書く Struts タグ（html・bean・logic）で書く

ポイントは、「どこに何を書くか」が全員で共通になることです。誰が書いても同じ構造になるため、他人のコードが読めますし、数年後に保守する人も迷いません。これがフレームワークを使う最大の価値です。

Struts 1 はサポート終了済み（新規開発には使わない）

Struts 1 は 2013 年に EOL（サポート終了）となり、セキュリティ修正も提供されていません。新しくシステムを作るために学ぶものではありません。それでも学ぶ価値があるのは、金融・公共・製造などの分野で Struts 1 製システムが今も数多く稼働しており、その保守・改修ができる人材が必要とされているからです。本ガイドの最終目標も「作れること」ではなく「読めること・直せること」に置いています。

1.3 Struts 1におけるMVC

MVC という考え方自体はすでにご存じでしょう。ここで大事なのは、Struts 1 では MVC の各役割が「具体的にどのクラス・どのファイル」なのかを覚えることです。この対応表が、以降のすべての章の地図になります。

役割 Struts 1 での実体 担当すること 学ぶ章
Controller ActionServlet＋struts-config.xml＋Action リクエストの受付、処理の振り分け、次の画面の決定 第2〜3章
Model ActionForm・JavaBeans・DAO 入力値の保持、業務データの表現、DB アクセス（ActionForm は画面と Controller の境界に立つ「入力の入れ物」） 第4章・第6章
View JSP ＋ Struts タグライブラリ 画面の表示、入力フォームの生成、エラーの表示 第5章

Struts 1 の Controller は「2段構え」

Struts 1 の Controller は1つのクラスではありません。全リクエストの受付窓口である ActionServlet（Struts が提供・自分では書かない）と、機能ごとの処理を書く Action（自分で書く）の2段構えです。両者を結びつけるのが設定ファイル struts-config.xml です。この3点セットが Struts 1 の心臓部だと覚えてください。

実際のコードで流れを覗いてみる

言葉だけではイメージしづらいので、実物を少しだけ先取りしましょう。まず、画面（JSP）のフォームは .do 宛てに送信されます。

search.jsp — 画面側（第5章で詳しく学びます） 
<%-- Strutsタグでフォームを作る。action="/employee/search" が /employee/search.do になる --%>
<html:form action="/employee/search">
    <html:text property="name" />   <%-- ActionFormのnameプロパティと対応 --%>
    <html:submit value="検索" />
</html:form>

送信先の /employee/search.do を受けて、どの Action を呼ぶかを決めているのが設定ファイルです。

struts-config.xml — 対応表（第2章で詳しく学びます） 
<!-- /employee/search.do が来たら SearchAction を呼び、結果に応じて画面へ飛ばす -->
<action path="/employee/search"
        type="com.example.action.SearchAction"
        name="employeeForm"
        scope="request"
        validate="true"
        input="/list.jsp">
    <forward name="success" path="/list.jsp" />
</action>

そして呼び出される Action は、処理を実行して「次はこの画面へ」という札（ActionForward）を返すだけです。

SearchAction.java — 処理本体（第3章で詳しく学びます） 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    // 業務処理（この章では中身は気にしなくてOK）
    List employees = new EmployeeDao().findAll();
    // 検索結果をJSPへ渡す
    request.setAttribute("employees", employees);
    // 「success」という名前の行き先を struts-config.xml から探して返す
    return mapping.findForward("success");
}

JSP名がコードから消えていることに注目

Action のコードには list.jsp という文字列がどこにも出てきません。書いてあるのは "success" という論理名だけです。実際の遷移先は struts-config.xml が握っています。これが「画面遷移を1か所に集める」という Struts の考え方であり、既存システムを読むときにまず struts-config.xml を開く理由でもあります。

学習を進めるうえでの心構え

「暗記」より「たどる」

クラス名を覚えることが目的ではありません。URL からファイルへ、ファイルからファイルへたどれることが実務の力になります。

設定ファイルが主役

Struts 1 では XML の設定ファイルが処理の流れを決めます。Java だけを追っても全体はつかめません。

古い書き方に出会う前提で

現場のコードは perform() やスクリプトレットなど古い書き方が残っています。第3章以降で違いを説明します。

手元のコードで確認する

担当システムのソースがあるなら、各章の内容を実物と照らし合わせながら読むと定着が段違いです。

理解度確認クイズ

  1. Q1. Servlet/JSP だけで作る場合と比べて、Struts 1 が整理してくれることを3つ挙げてください。

    回答を表示

    ①機能ごとに Action クラスを分けるので、1つの Servlet に分岐が集中しない。②画面遷移を struts-config.xml に集約するので、遷移先 JSP が Java コードに散らばらない。③ActionForm が入力値の受け取りと入力チェックの置き場所を決めてくれる。加えて、Struts タグで JSP からスクリプトレットを減らせる点も挙げられます。

  2. Q2. Struts 1 における MVC の Controller は、具体的に何にあたりますか？

    回答を表示

    受付窓口である ActionServlet（Struts が提供するもので自分では書かない）と、機能ごとの処理を書く Action（自分で書く）の2段構えです。両者を結びつけているのが設定ファイル struts-config.xml です。

  3. Q3. Action のコードに遷移先の JSP 名を直接書かないのはなぜですか？

    回答を表示

    Action は "success" のような論理名を mapping.findForward() に渡すだけで、実際の遷移先は struts-config.xml が持ちます。こうすると画面遷移が1か所にまとまり、遷移先を変えたいときに Java の修正・再コンパイルが不要になります。既存システムを読むときに struts-config.xml から見るべき理由もここにあります。

  4. Q4. 本ガイドが「Struts 1 でゼロからシステムを作れること」を最終目標にしていないのはなぜですか？

    回答を表示

    Struts 1 は 2013 年に EOL となっており、新規開発では使われないためです。一方で稼働中のシステムは数多く残っているため、実務で求められるのは「既存のコードを読み解き、修正箇所を特定して安全に直せること」です。本ガイドはその力を第8章で仕上げます。
