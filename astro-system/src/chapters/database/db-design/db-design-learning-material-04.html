ホーム DB設計入門 第4章
第4章 所要時間: 約75分

ER図の読み方・書き方

第3章で「さくら文具」から見つけたエンティティと属性を、いよいよ図として描きます。この章では ER図を構成する3つの要素、IE記法（鳥の足記法）を中心とした主な記法の違い、線の端の記号でカーディナリティとオプショナリティを読み取る方法、概念・論理・物理の3段階の描き分け、そして Mermaid の erDiagram による実際の記述方法を学びます。

この章の学習目標

  • ER図の3つの構成要素（エンティティ・属性・リレーションシップ）を説明できる
  • IE記法・IDEF1X・Chen記法の違いを挙げ、本ガイドが IE記法を使う理由を説明できる
  • IE記法の記号（||・o|・}|・o{）から、カーディナリティ（1か多か）とオプショナリティ（0を許すか）を読み取れる
  • 概念ER図・論理ER図・物理ER図それぞれで何を描くか区別できる
  • Mermaid の erDiagram 記法で、自分で ER図を書ける

4.1 ER図を構成する3つの要素

第3章では、業務の説明文からエンティティ（顧客・商品・受注など）と属性（顧客名・単価など）を洗い出しました。ER図（実体関連図、Entity-Relationship Diagram）は、これらに加えてリレーションシップ（エンティティ同士の関係）を1枚の図にまとめたものです。構成要素は次の3つだけです。

要素 図での表現 さくら文具の例
エンティティ（実体） 四角い箱。1つの箱が1つの表（将来テーブル）になる customers・products・orders など
属性（アトリビュート） 箱の中に並ぶ項目名。将来の列になる customer_name・unit_price など
リレーションシップ（関連） 箱と箱をつなぐ線。線の端の記号で「関係の強さ」を表す 「顧客が受注する」「受注が明細を持つ」など

まずは細部を省いた、箱と線だけの図を見てみましょう。第3章で洗い出した「さくら文具」の主なエンティティを、業務担当者と会話した言葉のまま線でつないだものです。

erDiagram customers ||--o{ orders : "注文する" staff ||--o{ orders : "受け付ける" orders ||--|{ order_details : "明細を持つ" products ||--o{ order_details : "明細に含まれる" categories ||--o{ products : "分類する"

この段階では属性を書き込んでいません。まず「何と何が、どんな言葉でつながるか」だけを固めるのが、次の4.4で説明する概念ER図の役目です。線の端についた小さな記号（|| や o{ など）が何を意味するかは、4.3で詳しく学びます。

ヒント: リレーションシップには「名前」を付ける

「customers と orders がつながっている」だけでは、実は「注文する」なのか「注文をキャンセルする」なのか分かりません。線に "注文する" のような動詞（述語）を添えると、あとで図を見返した人にも関係の意味が伝わります。業務担当者に「この2つはどういう関係ですか？」と質問して、その答えをそのまま線のラベルにするとよいでしょう。

4.2 ER図の主な記法 — IE記法・IDEF1X・Chen記法

ER図には複数の「描き方の流派（記法）」があります。同じ内容を描いても、記法によって線の記号や箱の飾りが変わります。代表的な3つを比較します。

記法 通称 関係の表し方 よく使われる場面
IE記法 鳥の足記法（Crow's Foot） 線の端に「鳥の足」に似た記号（o{ など）を付けて多重度を表す 実務での画面共有・ツール（draw.io、A5:SQL Mk-2、Mermaid）に広く対応。本ガイドの標準
IDEF1X アイデフ・ワンエックス 鳥の足に加え、箱の角（四角か丸角か）で「依存／非依存」関係を区別する 米国防省規格由来。金融・官公庁系の大規模システムで採用例あり
Chen記法 チェン記法 リレーションシップ自体をひし形の箱として描き、多重度は線のそばに「1」「N」と文字で書く 学術・教科書での説明に多い。図が大きくなりやすく実務ツールでの対応は少ない

本ガイドはIE記法（鳥の足記法）を採用します。理由は、Mermaid をはじめ多くの作図ツールが対応していること、記号がコンパクトで大きな ER図でも見やすいこと、そして実務の現場で最もよく目にする記法だからです。以降の章もすべて IE記法で ER図を描きます。

用語メモ：多重度 — 1つのエンティティのインスタンス（例: 特定の1人の顧客）が、相手のエンティティのインスタンスと「いくつ」対応するかを表す言葉です。「カーディナリティ」とほぼ同じ意味で使われます。

4.3 IE記法の読み方 — カーディナリティとオプショナリティ

IE記法の線の端には、必ず2種類の情報が同時に描かれています。この2つを分けて理解することが、ER図を正しく読むいちばんのコツです。

カーディナリティ（多重度）

相手のインスタンスが「1つ」なのか「多数」なのかを表す。線の先端の記号が直線（|）なら1、鳥の足（{ ）なら多。

オプショナリティ（必須性）

相手のインスタンスが「必ず存在する（0を許さない）」のか「存在しなくてもよい（0を許す）」のかを表す。丸（o）があれば0を許す、なければ必須。

この2つを組み合わせると、線の端の記号は次の4パターンに整理できます。

IE記法の記号 カーディナリティ オプショナリティ 日本語で言うと Mermaidでの記号（左側／右側）
|| 1（直線） 必須（丸なし） ちょうど1つ ||／||
o| 1（直線） 任意（丸あり） 0または1つ |o／o|
}| 多（鳥の足） 必須（丸なし） 1つ以上（多数） }|／|{
o{ 多（鳥の足） 任意（丸あり） 0個以上（多数） }o／o{

用語メモ：記号の左右 — 手書きや draw.io でも Mermaid でも、読み方は「線の、そのエンティティの箱に近い側の記号を読む」だけです。Mermaid の erDiagram では、-- の左に左側エンティティ側の記号、右に右側エンティティ側の記号を書きます（customers ||--o{ orders なら || が customers 側、o{ が orders 側）。鳥の足は常に箱の方へ開くため、左側に書くときは }o・|o、右側に書くときは o{・o| のように記号の向きが左右反転します。

実際の例で確認しましょう。「顧客が受注する」という関係を、customers 側と orders 側、それぞれの端から読んでみます。

erDiagram customers ||--o{ orders : "注文する"
読む位置 記号 意味 業務としての意味
customers 側の端 || ちょうど1つ 1件の受注には、注文した顧客がちょうど1人いる（顧客なしの受注や、複数顧客の共同受注はない）
orders 側の端 o{ 0個以上（多数） 1人の顧客は、受注が0件（会員登録しただけ）でも、複数件でもよい

つまりこの図は「1人の顧客は0件以上の受注を持ち、1件の受注は必ずちょうど1人の顧客に属する」と読みます。読む位置を必ず「相手側の箱に近い端」に固定するのがコツです。

重要: カーディナリティとオプショナリティは別の質問で決める

記号を決めるときは、必ず2つの質問を分けて業務担当者に確認してください。①「1人の顧客が持てる受注は、最大でいくつですか？」（カーディナリティ＝直線か鳥の足か）②「受注が0件の顧客は存在しますか？」（オプショナリティ＝丸を付けるか）。この2問を混同すると、「1人1件しか注文できない」と「1人0件でもよい」を取り違えるミスが起きます。

もう1つ、受注と受注明細の関係も確認しておきましょう。

erDiagram orders ||--|{ order_details : "明細を持つ"

orders 側の端は ||（ちょうど1つ）、order_details 側の端は |{（1つ以上、丸なしなので必須）です。「1件の受注には、必ず1件以上の明細がある（商品ゼロの注文は存在しない）」という業務ルールを表しています。1.2で見た「1つのセルに複数の商品コード」の問題は、この「1件の受注に対して明細が複数ある」多重度をきちんと表現することで解決されます。

4.4 概念ER図・論理ER図・物理ER図の描き分け

第1章の3つの工程（概念設計・論理設計・物理設計）に対応して、ER図にも3段階の描き方があります。同じ「顧客と受注の関係」を例に、段階ごとに図に描き込む情報が増えていく様子を見てみましょう。

ER図の種類 対応する工程 箱の中に描くもの 主な読み手
概念ER図 概念設計 エンティティ名と関係だけ（属性は省略、または主要なものだけ） 業務担当者・発注者も含めた全員
論理ER図 論理設計 正規化済みの全属性、主キー・外部キーの区別（PK / FK） 設計者・開発者
物理ER図 物理設計 実際のデータ型・制約・インデックスまで含めた、実テーブルそのままの姿 開発者・DBA（データベース管理者）

まず概念ER図です。エンティティ名と関係の言葉だけで、属性は書きません。4.1で見た図がこれにあたります。次に論理ER図では、属性とキーを書き込みます。

erDiagram customers ||--o{ orders : "注文する" customers { int customer_id PK string customer_code UK string customer_name } orders { int order_id PK date order_date int customer_id FK string status }

論理ER図の段階では、まだ「単価を numeric(10,2) にするか integer にするか」のような製品固有の話は出てきません。データ型・NOT NULL・インデックスまで含めた物理ER図（＝実テーブルの完全な姿）は第10章で作ります。段階を分ける理由は、「まだ決めなくてよいこと」を先に決めてしまうと、後で直す範囲が広がるからです。概念設計の段階で PostgreSQL 固有の型を気にする必要はありません。

ヒント: 迷ったら「今どの段階の会話か」を確認する

打ち合わせ中に「この列は NULL を許すべきか」という話と「そもそもこのエンティティは必要か」という話が同時に出てくることがあります。前者は論理〜物理設計の話、後者は概念設計の話です。話が混ざって噛み合わないときは、「今は概念の話をしていますか、それとも列の話をしていますか」と一度整理すると、議論がスムーズになります。

4.5 Mermaidの erDiagram で描く

本ガイドでは Mermaid Live Editor や、この教材内の図と同じ erDiagram 記法で ER図を書きます。基本の書式は次の3行に集約できます。

er-basic.mmd 
erDiagram
    エンティティA 記号--記号 エンティティB : "関係の名前"
    エンティティA {
        型 列名 PK
    }

属性を書く波かっこ { } の中では、「型 → 列名 → キー種別（省略可）→ コメント（省略可）」の順に書きます。キー種別は PK（主キー）・FK（外部キー）・UK（一意キー）を使い、複数持つ場合は PK, FK のようにカンマ区切りで並べます。

order_details-er.mmd 
order_details {
    int order_id PK, FK "受注ヘッダを指す"
    int line_no PK
    int product_id FK
    numeric unit_price "注文時点の単価"
    int quantity
}

コメントに日本語を使うときは、必ずダブルクォートで囲んでください（コメントなしなら不要です）。到達点の order_details は、order_id と line_no の2列を組み合わせた複合主キーを持ちます（この主キーに至る経緯は第7〜9章で扱います）。これらを積み上げると、「さくら文具」の到達点である6テーブルの論理ER図が次のように描けます。

erDiagram customers ||--o{ orders : "注文する" staff ||--o{ orders : "受け付ける" orders ||--|{ order_details : "明細を持つ" products ||--o{ order_details : "明細に含まれる" categories ||--o{ products : "分類する" customers { int customer_id PK string customer_code UK string customer_name string email string address } categories { int category_id PK string category_name } products { int product_id PK string product_code UK string product_name int category_id FK numeric unit_price } staff { int staff_id PK string staff_name } orders { int order_id PK date order_date int customer_id FK int staff_id FK string status } order_details { int order_id PK, FK int line_no PK int product_id FK numeric unit_price "注文時点の単価" int quantity }

この図が、本ガイドが最終的に目指す論理ER図です。第5〜9章でこの構造ができあがる過程（多対多の解消・正規化・キー設計）を1つずつ確認し、第10章でこの図を PostgreSQL の CREATE TABLE 文（物理ER図）に落とし込みます。

注意: 記号の向きを書き間違えやすい箇所

orders ||--|{ order_details のように、両側とも必須（丸なし）の関係を書くときに、片方だけ丸付き記号（o{）を書いてしまう間違いがよくあります。「明細を持たない受注は存在するか？」を必ず自分に問いかけてから記号を選んでください。さくら文具では「商品ゼロの受注」は業務上あり得ないため、|{（必須・多）が正しい記号です。

4.6 手書きで描くときのコツ

打ち合わせの場では、PC を開くよりも紙やホワイトボードにさっと描く方が話が早いことがよくあります。手書きで ER図を描くときは、次の順番で進めると迷いません。

手順 やること コツ
1 エンティティを箱として、まばらに配置する 後で線を引くスペースを空けるため、最初から詰めて描かない
2 関係がありそうな箱同士を直線で結ぶ（記号はまだ書かない） 「本当に関係があるか」だけに集中し、多重度は後回しにする
3 各線ごとに「AはBを最大いくつ持つか」を両方向から質問する 4.3の2つの質問（カーディナリティ→オプショナリティ）の順で聞く
4 両端に記号を描き込む 直線か鳥の足か（多重度）を先に決め、丸（オプショナリティ）を後から付ける
5 主要な属性だけを箱の中に書き足す この段階ではまだ概念ER図。全属性を書く必要はない

手書きで固まった内容は、あとで Mermaid Live Editor や draw.io に清書すると、修正やチーム内共有がしやすくなります。清書のタイミングで、4.5の書式に沿って属性とキーを補っていけば、そのまま論理ER図に育てられます。

やってみよう 4-1: products と categories の関係を IE記法で描く

「さくら文具の商品は、必ず1つの商品分類（筆記具・ノート・ファイル・事務用品）に属する。1つの分類には、商品が0個でも複数でも登録できる」という業務ルールを、紙またはメモアプリで ER図にしてください。

手順

  1. 1 categories と products の2つの箱を描き、直線で結ぶ。
  2. 2 「1つの商品は、分類をいくつ持つか」「その分類は必ず存在するか」を自問し、products 側の端の記号を決める。
  3. 3 「1つの分類は、商品をいくつ持てるか」「商品が0個の分類はあり得るか」を自問し、categories 側の端の記号を決める。
  4. 4 決めた記号を Mermaid の書式（categories 記号--記号 products : "分類する"）で書き出してみる。

ねらい: 正解は categories ||--o{ products : "分類する" です。products 側は「必ず1つの分類に属する」ので ||、categories 側は「商品0個の分類もあり得る（新設した直後など）」ので o{ になります。第5章では、この「1対多」の関係を外部キーでどう表現するかを詳しく学びます。

理解度確認クイズ

  1. Q1. IE記法の記号 o| は、カーディナリティとオプショナリティをそれぞれどう表していますか。

    回答を表示

    |（直線）がカーディナリティ「1」を、o（丸）がオプショナリティ「任意（0を許す）」を表します。合わせて「0または1つ」という意味になります。

  2. Q2. 本ガイドが Chen記法や IDEF1X ではなく IE記法（鳥の足記法）を採用している理由を2つ挙げてください。

    回答を表示

    (1) Mermaid をはじめ多くの作図ツールが対応している、(2) 記号がコンパクトで大きな ER図でも見やすい、という2点です（実務で最もよく使われる記法である、という理由も挙げられます）。

  3. Q3. 次のうち、概念ER図で描く情報として適切でないものはどれですか。(a) エンティティ名 (b) リレーションシップの名前 (c) 列のデータ型（numeric(10,2) など）

    回答を表示

    (c) です。データ型は使う RDBMS に依存する物理設計の情報であり、概念ER図では扱いません。概念ER図はエンティティ名と関係の名前が中心で、属性は書いても主要なものだけにとどめます。

  4. Q4. orders ||--|{ order_details : "明細を持つ" という行を読み、order_details 側の端の記号が意味する多重度とオプショナリティを説明してください。

    回答を表示

    |{ は「1つ以上（多数）」で、丸が付いていないため「必須」です。つまり「1件の受注には、必ず1件以上の受注明細がある」ことを表しています。
