ホーム DB設計入門 第11章
第11章 所要時間: 約75分

非正規化・履歴・アンチパターン

第10章で「さくら文具」の全テーブルを DDL として完成させました。しかし実務では、正規化されたテーブルだけでは足りない場面があります。「注文時点の単価をどう残すか」「顧客が複数の配送先を持つとき注文時の宛先はどう記録するか」「商品の値段が変わった履歴をどう管理するか」。この章では、正規化と上手に付き合うための非正規化の判断基準、時間とともに変わるデータ（履歴）の設計、そして避けるべきアンチパターンを、さくら文具の題材で学びます。

この章の学習目標

  • order_details.unit_price が「注文時単価」であり、正規化違反の冗長データではなく別の事実の記録であることを説明できる
  • 顧客の複数配送先（customer_addresses）と、注文時の配送先スナップショットの必要性を設計できる
  • 商品価格の改定履歴を「適用開始日・終了日」を持つ履歴テーブルで表現できる
  • 意図的な非正規化（合計金額の保持など）を行う判断基準と、そのリスク・維持コストを説明できる
  • 論理削除の是非を判断でき、カンマ区切り列・EAV・万能テーブル・意味を持つIDといった代表的アンチパターンを見分けられる

11.1 正規化との付き合い方 — 非正規化は「知らずに崩す」ことではない

第6〜8章で学んだ正規化は、更新異常を防ぐための手順でした。事実ごとに表を分ければ、同じ値を何か所も直す必要がなくなります。しかし表を分けるほど、データを1つの意味ある形に戻すには JOIN が必要になり、テーブル数も増えます。

非正規化とは、この「正しさを保ちやすい正規化された構造」を、理解した上で意図的に崩し、冗長なデータを許容する設計判断です。第1章で「まず整合性と妥当性を優先する」と学びましたが、それは「性能のために構造を崩してよい場面がまったく無い」という意味ではありません。判断の順序が重要で、先に正しく正規化してから、必要な箇所だけ意図的に崩すのが正しい進め方です。

観点 正規化を保つ理由 非正規化を検討する理由
更新のしやすさ 1つの事実を1か所だけ直せば済み、矛盾が起きない 冗長な列を持つと、複数箇所を同時に直す責任が生まれる
読み取りのしやすさ 表が増えるほど JOIN が複雑になる よく使う集計値を持たせておけば JOIN や集計を省略できる
履歴の保持 最新の値だけを1か所に持つのが基本形 「あの時点でどうだったか」を残す必要がある場面がある（11.2〜11.4）

注意: 「面倒だから正規化しない」は非正規化ではない

正規化の手順を踏まずに最初から1つの表に詰め込むのは、非正規化ではなく単なる設計不足です。非正規化と呼べるのは、いったん正規化された構造を理解した上で、リスクと維持コストを引き受けて意図的に崩す場合だけです。この違いを区別できないと、「正規化は面倒だから最初から崩してよい」という誤解につながります。

11.2 スナップショットは正規化違反ではない — 注文時単価

第10章で完成させた order_details には unit_price 列があります。一見すると「products.unit_price と同じ値を2か所に持っている」ので正規化違反（冗長）に見えるかもしれません。しかし、これはまったく別の事実を記録しているため、正規化違反ではありません。

列 表す事実 関数従属の相手
products.unit_price 現在この商品を売る定価 product_id（商品そのものに従属）
order_details.unit_price その注文明細1行が成立した時点で合意された単価 (order_id, line_no)（この注文明細1行に従属）

商品の定価は今後も変わり続けますが、過去に成立した注文の金額は変わってはいけません。もし order_details に単価を持たせず、都度 products.unit_price を参照する設計にしてしまうと、商品の値上げのたびに過去の注文の合計金額まで変わってしまうという重大な不具合になります。単価を明細行に記録するのは冗長化ではなく、「この明細行は何円で成立したか」という明細行自身の事実を正しく持たせているだけです。

order_details.sql 
-- 受注明細（第10章のDDLと同じ。unit_price は「注文時点で確定した単価」）
CREATE TABLE order_details (
    order_id   integer NOT NULL
        REFERENCES orders (order_id) ON DELETE CASCADE,
    line_no    integer NOT NULL,
    product_id integer NOT NULL
        REFERENCES products (product_id) ON DELETE RESTRICT,
    unit_price numeric(10,2) NOT NULL CHECK (unit_price >= 0),  -- 成立時点の単価
    quantity   integer NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, line_no)
);

重要: 「同じ列名・同じ型」でも従属先が違えば別の事実

正規化違反かどうかを見分けるコツは、「値が同じかどうか」ではなく「その値は何に従属しているか」を確認することです。products.unit_price は商品に従属する「現在の定価」、order_details.unit_price は注文明細に従属する「成立時点の単価」で、従属先（主キー）が異なる別の事実です。これから学ぶ配送先スナップショット・価格履歴も同じ考え方で理解できます。

11.3 顧客の複数配送先と注文時の配送先スナップショット

これまでの設計では、顧客の住所は customers.address の1つだけでした。しかし実際のさくら文具では、顧客は自宅・会社・実家など複数の配送先を登録できるようにしたい、という要件が出てきます。これは第5章で学んだ「1対多」の関係そのもので、新しい配送先エンティティを追加します。

erDiagram customers ||--o{ customer_addresses : "配送先を登録する" customers ||--o{ orders : "注文する"
customer_addresses.sql 
-- 顧客の配送先マスタ（1人の顧客が複数件登録できる）
CREATE TABLE customer_addresses (
    address_id   integer      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  integer      NOT NULL REFERENCES customers(customer_id),
    label        varchar(20)  NOT NULL,        -- 「自宅」「会社」等
    postal_code  varchar(8)   NOT NULL,
    address      varchar(200) NOT NULL,
    is_default   boolean      NOT NULL DEFAULT false  -- 既定の配送先
);

ここで注意が必要なのは、orders から customer_addresses へ外部キーだけを引くのでは不十分だという点です。もし注文後に顧客が配送先を編集・削除してしまうと、過去の注文が「実際にはどこへ送ったか」を失ってしまいます。そこで orders 自身にも、注文時点の配送先をコピー（スナップショット）として持たせます。

orders_shipping.sql 
-- orders に追加する配送先スナップショット列（抜粋。既存行が無い前提）
ALTER TABLE orders
    ADD COLUMN shipping_address_id integer   -- 配送先が削除されたら NULL にする
        REFERENCES customer_addresses(address_id) ON DELETE SET NULL,
    ADD COLUMN shipping_postal_code varchar(8)   NOT NULL,  -- 注文時点の郵便番号を複製
    ADD COLUMN shipping_address     varchar(200) NOT NULL;  -- 注文時点の住所を複製

shipping_address_id は「どの配送先を選んだか」という参照のために残し、shipping_postal_code・shipping_address は「実際に届けた先」を後から編集・削除の影響なしに再現するために複製します。11.2 の単価スナップショットと同じ考え方で、「注文に従属する事実（実際に届けた先）」と「配送先マスタに従属する事実（今の登録内容）」は別物だから両方を持つ、と理解してください。

ヒント: 「マスタ」と「スナップショット」を混同しない

customer_addresses は「今、顧客が使える配送先の一覧」というマスタで、時間とともに増減・変更されます。一方 orders.shipping_address は「その注文が確定した瞬間の宛先」という記録で、後から変わってはいけません。マスタを更新しても、過去の注文のスナップショットは変わらないことを確認してください。

11.4 時間とともに変わるデータ — 商品価格の改定履歴

11.2 では「注文が成立した瞬間の単価」を明細行に残しました。しかし別の要件として、「4月時点でボールペン黒は何円だったか」「来月から値上げする価格をあらかじめ登録しておきたい」のように、商品の定価そのものの変化を追跡したい場合があります。これは products.unit_price を1つの値で持つだけでは表現できません。

こうした「時間軸を持つデータ」は、適用開始日・終了日を持つ履歴テーブルに分けて表現するのが定石です。さくら文具では product_prices を新設します。

erDiagram products ||--o{ product_prices : "価格改定履歴を持つ"
product_prices.sql 
-- 商品価格の改定履歴（valid_to が NULL の行が現在有効な価格）
CREATE TABLE product_prices (
    price_id   integer       GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id integer       NOT NULL REFERENCES products(product_id),
    unit_price numeric(10,2) NOT NULL,
    valid_from date          NOT NULL,   -- この価格の適用開始日
    valid_to   date,                     -- 適用終了日（この日は含まない）。NULL は現在も有効
    CHECK (valid_to IS NULL OR valid_from < valid_to)
);

「今日時点で有効な単価」を調べるには、valid_from と valid_to の範囲に対象の日付が入る行を1件だけ探します。

current_price.sql 
-- 商品 P01（product_id = 1 とする）の、本日時点で有効な単価を取得
SELECT unit_price
FROM product_prices
WHERE product_id = 1
  AND valid_from <= CURRENT_DATE
  AND (valid_to IS NULL OR valid_to > CURRENT_DATE);

値上げを登録するときは、現在有効な行の valid_to を新しい適用開始日に更新し、新しい単価の行を valid_to = NULL で追加します。products.unit_price を直接書き換えないため、過去の価格が失われません。この設計になった後、products テーブル自身の unit_price 列は不要になり、product_prices の現在有効な行に一本化できます。

重要: 履歴テーブルは正規化の延長であり非正規化ではない

product_prices を追加するのは、「商品の単価」という1つの属性が実は時間によって複数の値を持つことに気づき、正しく別テーブルへ分けた結果です。これはむしろ第7章の第1正規形（繰り返しをなくす）の考え方の延長で、非正規化ではありません。次の11.5で扱う「合計金額の保持」との違いを区別してください。

11.5 意図的な非正規化 — orders に合計金額を持たせる

正規化どおりに考えれば、1件の注文の合計金額は order_details の unit_price × quantity を SUM すれば常に求められるので、orders に列を持つ必要はありません。しかし、注文一覧画面を開くたびに何千件もの注文それぞれで order_details を集計するのは負荷が大きく、orders.total_amount という集計済みの列を持たせたい、という判断が実務では起こります。これが本章で初めて登場する「純粋な非正規化」の例です。

orders_total.sql 
-- orders に持たせる集計列（本来は order_details から常に再計算できる値）
ALTER TABLE orders
    ADD COLUMN total_amount numeric(12,2) NOT NULL DEFAULT 0;
-- 明細の追加・変更時に、アプリまたはトリガーで再計算して更新する

非正規化してよいかどうかは、次の3点を確認して判断します。

判断基準 orders.total_amount の場合
読み取りの頻度・コストが十分高いか 注文一覧・検索で毎回集計するのは負荷が大きく、頻度も高い → 該当する
整合性を保つ仕組みを用意できるか 明細の追加・変更・削除のすべての経路で再計算する処理（トリガー等）を必ず通す必要がある
崩れたときの検知・修復手段があるか 定期的に SUM の結果と比較する検証バッチを用意できるか

注意: 非正規化には「維持コスト」という負債が伴う

集計列を持たせた瞬間から、明細を更新するすべてのプログラムが「合計金額も忘れずに更新する」責任を負います。更新経路が1つでも漏れると、total_amount と実際の明細の合計が食い違う不整合が発生します。非正規化は性能を買うために整合性の維持コストを支払う取引であり、「維持できる体制があるか」を先に確認してから採用してください。

11.6 論理削除の是非

「キャンセルされた注文」や「退会した顧客」を、行ごと DELETE するのではなく、is_deleted や deleted_at のような列を立てて「削除済みの印」を付けるだけにする方法を論理削除と呼びます。実際に行を消す物理削除と対になる考え方です。

観点 論理削除の利点 論理削除の欠点
参照整合性 他テーブルから外部キーで参照されていても削除できる（staff が退職しても過去の orders は残る） —
誤削除からの復旧 印を外すだけで復元できる —
クエリの安全性 — すべての SELECT に WHERE deleted_at IS NULL を付け忘れると削除済み行が漏れて見える
一意制約 — customer_code の UNIQUE が、削除済みの値も塞いだままになり、コードの再利用ができない

判断の目安として、「他のテーブルから参照され続ける行（顧客・商品・担当者などのマスタ）」や「法令・社内規程で一定期間の保持が求められる行」は論理削除が向いています。一方、「一時的な作業データ」や「参照されず復元の必要もない行」は物理削除で十分です。さくら文具では、staff（過去の注文から参照される）や customers は論理削除、下書きの一時データなどは物理削除、というようにテーブルごとに使い分けるのが実務的です。

ヒント: 「全テーブルに is_deleted を付ける」は目的を忘れた例

論理削除は「参照整合性を保ちたい」「復元したい」という具体的な理由があって選ぶ手段です。理由を確認せずに全テーブルへ機械的に is_deleted を付けると、クエリの付け忘れというリスクだけを増やして、得られる利点は活かされません。

11.7 避けるべき代表的なアンチパターン

非正規化は「理解した上で選ぶ」判断でしたが、ここで紹介する4つはそもそも避けるべき設計です。いずれも「一見手軽だが、後から必ず困る」という共通点があります。

アンチパターン 何が起きるか 代わりにどうするか
カンマ区切りの列 第1章の「P01, P03」のように1セルに複数値。集計・検索のたびに文字列分解が必要で、外部キー制約も効かない order_details のように行を分ける（第1正規形、第7章）
EAV（何でも入る属性テーブル） entity_id, attr_name, attr_value の3列だけの表に何でも詰め込む。型やNOT NULLの制約が効かず、単純な検索にも自己結合が必要になる 属性ごとに列を定義する。商品分類が増える程度ならcategories の行を増やせば対応できる
万能テーブル（ポリモーフィック関連） related_type, related_id のような列で「顧客にも商品にも担当者にも」1つの表からリンクさせる。外部キー制約を張れず、参照先を型ごとに JOIN で切り分ける必要がある 関連先ごとに専用の中間テーブルを作る（第5章の中間エンティティ）
IDに意味を持たせる（スマートキー） 例: 商品コードの先頭2桁を分類コードにする。分類変更のたびにIDそのものを直す必要が生まれ、第9章で学んだ「主キーは業務の都合で変わらない値にする」という原則に反する 識別だけを担う連番のサロゲートキーと、意味を持つ業務コード（product_code 等）を分ける（第9章）

注意: アンチパターンは「柔軟に見える」から選ばれてしまう

EAV や万能テーブルは「将来どんな属性・どんな関連先が増えても、テーブルを変更せずに対応できそうだ」という理由で選ばれがちです。しかし実際には、RDBMS が保証してくれる型・NOT NULL・外部キーといった制約の力を自ら手放すことになり、アプリ側でその責任を負う羽目になります。「柔軟性」と「制約による安全性」はトレードオフだと理解して選んでください。

やってみよう 11-1: 非正規化するかどうかを判断する

さくら文具の運営チームから、次の3つの相談が来たとします。11.5 の判断基準（読み取り頻度・整合性維持の可否・検知手段）を使って、それぞれ「非正規化してよい」「するべきではない」を判断し、理由をメモしてください。

相談内容

  1. 1 「トップページに『総顧客数』を表示したいので、customers の行数を数える代わりに、どこかに数値を持たせたい」
  2. 2 「注文確認メールに商品名を載せたいので、order_details に商品名の列も追加して products への JOIN を省きたい。ただし商品名は将来変更されることがある」
  3. 3 「担当者ごとの月間受注件数ランキングを毎朝の会議で見るので、深夜バッチで集計して専用テーブルに書き出したい」

ねらい: 相談1は更新頻度が低く読み取りも軽いため非正規化の必要は薄い一方、相談3はバッチで整合性を保証できるため妥当な非正規化です。相談2は要注意です。「商品名が将来変わる」ことを考えると、order_details にコピーした商品名は注文成立時点の名称（スナップショット）として扱うべきで、11.2・11.3 と同じ考え方が当てはまります。単純な性能目的の非正規化と、事実として残すべきスナップショットを混同しないことが大切です。

理解度確認クイズ

  1. Q1. 「order_details.unit_price は products.unit_price と同じ値を2か所に持っているだけの冗長データだ」という意見に、どう反論しますか。

    回答を表示

    2つの列は従属先が異なる別の事実です。products.unit_price は商品に従属する「現在の定価」、order_details.unit_price は注文明細に従属する「その注文が成立した時点の単価」です。商品の定価は今後も変わりますが、成立済みの注文の金額は変わってはならないため、両方を別々に持つ必要があり、正規化違反ではありません。

  2. Q2. orders に shipping_address（配送先住所の複製）を持たせず、customer_addresses への外部キーだけを持たせた場合、どのような問題が起きますか。

    回答を表示

    顧客が後から customer_addresses の住所を編集したり削除したりすると、過去の注文が参照する配送先の内容まで変わって（あるいは参照先が消えて）しまい、「実際にどこへ送ったか」という履行の事実を失います。注文時点の住所をスナップショットとして複製しておく必要があります。

  3. Q3. orders.total_amount（合計金額）を持たせる非正規化を採用する場合、必ず用意しなければならない仕組みは何ですか。

    回答を表示

    明細（order_details）の追加・変更・削除のすべての経路で total_amount を再計算して更新する仕組み（アプリのロジックやトリガー）、および値が食い違っていないかを確認する検証手段（定期バッチなど）が必要です。これが無いと合計金額が実際の明細と食い違う不整合が発生します。

  4. Q4. 「顧客・商品・注文・在庫など、あらゆる種類のデータを entity_id, attr_name, attr_value の3列だけの1つの表に格納する」という設計を提案されました。何というアンチパターンで、どんな問題がありますか。

    回答を表示

    EAV（Entity-Attribute-Value）と呼ばれるアンチパターンです。列の型やNOT NULL・外部キーといったRDBMSの制約が一切効かなくなり、単純な条件検索にも自己結合を何度も重ねる必要が生じて、性能面・保守面の両方で不利になります。属性ごとに列を定義した通常のテーブル構成にするべきです。
