ホーム Jev 第16章
第16章 所要時間: 約3時間

実践課題: 問い合わせ自動振り分けシステム

これまで学んだ State 設計・3つの Primitive・Atomic Question・Confidence による振り分けを、1つのアプリケーションに統合する総合演習です。顧客からの問い合わせを Jev で判断し、その結果をコードで合成して FAQ データベース・LLM・人間のオペレーターへ振り分ける「問い合わせ自動振り分けシステム」を最初から最後まで組み立てます。

この章で学ぶこと

  • 1つの State と3つの Question で判断を取得する設計ができる
  • Choice / Score / Noul の結果をコードで合成して振り分けられる
  • confidence が低い場合に人間レビューへ回す経路を実装できる
  • これまでの全章の知識を1つのアプリケーションに統合できる

16.1 課題の全体像

本章で作るのは、カスタマーサポート向けの問い合わせ自動振り分けシステムです。顧客から届いた問い合わせ本文を Jev に渡し、「どのカテゴリか（Choice）」「どれくらい緊急か（Score）」「クレームかどうか（Noul）」という3つの判断を1回のリクエストで取得します。Jev が返すのはあくまで3つの判断という部品であり、それらを組み合わせて「FAQ データベースで即答する」「LLM に返信文を書かせる」「人間のオペレーターに回す」のどれにするかを決めるのは、第1章から一貫して強調してきたとおりコードの役割です。 

inquiry_router.py
├─ inquiry_state          Stateを組み立てる（16.3）
├─ category_question      Choice: カテゴリ判定（16.4）
├─ urgency_question       Score: 緊急度判定（16.4）
├─ complaint_question     Noul: クレーム判定（16.4）
├─ route_inquiry()        3つの判断を合成する（16.5）
└─ _route_by_category()   カテゴリから振り分け先を決めるヘルパー（16.5）

全体のデータの流れを図にすると、次のようになります。

flowchart TD A["顧客からの問い合わせ"] --> B["Jev（1リクエストで3つのQuestionを評価）"] B --> C["category（Choice）"] B --> D["urgency（Score）"] B --> E["is_complaint（Noul）"] C --> F["route_inquiry関数（コードで合成）"] D --> F E --> F F -->|クレーム＋緊急 または 確信度不足| G["人間のオペレーター"] F -->|FAQで回答できる| H["FAQデータベース"] F -->|それ以外| I["LLMが返信文を生成"]

Jev への入力は1つの State（問い合わせ本文＋判断に必要な情報）と3つの Questionだけです。複雑に見えるシステムでも、Jev に投げる部分はいつも通りシンプルなままにする——これが本教材を通じて繰り返してきた設計の型です。

16.2 要件の整理

コードを書き始める前に、このシステムが満たすべき機能要件を箇条書きで整理します。

  • 顧客からの問い合わせ本文を受け取る
  • 問い合わせ本文と、判断に必要な顧客情報だけを JSON の State として Jev に渡す
  • 1回のリクエストで3つの Question（category: Choice ／ urgency: Score ／ is_complaint: Noul）を評価する
  • 3つの判断結果をコードで合成し、「FAQ データベース」「LLM」「人間のオペレーター」のいずれかへ振り分ける
  • confidence が閾値未満の場合、または「クレームかつ緊急」の場合は、自動判断せず人間のオペレーターへ回す
  • 振り分けの基準（しきい値）は、コード上で調整しやすい形にしておく

この要件は、実はここまでの章で学んだ内容の組み合わせにすぎません。

この章でやること 対応する既習内容
State に判断材料だけを渡す 第3章
Choice ／ Score ／ Noul を使い分ける 第4章
3つの Question を1回のリクエストで評価する 第11章
複合的な依頼を Atomic な Question へ分解する 第8章
confidence で自動処理／人間を振り分ける 第9章・第12章

16.3 State を設計する

第3章の原則を思い出しましょう。State に入れるのは判断に必要な情報だけです。名前や住所のような、今回の3つの判断に関係しない個人情報は含めません。

手順

  1. 1 問い合わせ本文を1つ用意し、message フィールドに入れる
  2. 2 緊急度やクレーム度合いの判断に関係しそうな付随情報だけをフィールドとして追加する
  3. 3 氏名・メールアドレスなど、判断に無関係な個人情報を含めていないか見直す
State の設計例 
{
  "message": "注文番号12345の商品がまだ届きません。購入から10日経ちました。至急返金してください。",
  "days_since_purchase": 10,
  "contact_count": 2
}

それぞれのフィールドを選んだ理由は次のとおりです。

  • message — 3つの判断すべての材料になる、問い合わせ本文そのもの
  • days_since_purchase — 緊急度判断の手がかり（放置期間が長いほど緊急度が上がりやすい）
  • contact_count — クレーム判断の手がかり（同じ内容で問い合わせを繰り返すほど不満が強い可能性がある）

関連: 第13章「jev-1.13の弱点と注意点」

顧客の氏名や過去の全購入履歴のような、判断に関係しない情報を State に詰め込むと、Jev が本来注目すべき情報を見失いやすくなります（巨大な State の弱点）。State は「その判断に本当に必要か？」で毎回絞り込みましょう。

16.4 Question を設計する

次に、3つの Question を Python で定義します。第4章で学んだとおり、Choice には選択肢ごとの criteria（辞書）を、Score には段階ごとの criteria（リスト）を、Noul には true と false の意味を定義する criteria（オブジェクト）を渡します。第10章の原則どおり、判断基準は長い1つの文章にせず、構造として分けて書きます。

手順

  1. 1 category_question・urgency_question・complaint_question をそれぞれ定義する
  2. 2 criteria の文言を、実務で区別したい基準に合わせて具体的に書く
  3. 3 questions 辞書にまとめ、client.system_one() を1回だけ呼び出す
inquiry_router.py（Stateの準備） 
# 16.3節で設計したStateを辞書として渡す
inquiry_state = {
    "message": "注文番号12345の商品がまだ届きません。購入から10日経ちました。至急返金してください。",
    "days_since_purchase": 10,
    "contact_count": 2,
}
inquiry_router.py（続き: Choiceの定義） 
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

# 問い合わせのカテゴリを4択で判定する
category_question = Choice(
    instructions="この問い合わせは、次のうちどのカテゴリに最も近いですか？",
    criteria={
        "faq": "料金プランや使い方など、ヘルプページに載っている一般的な質問",
        "billing": "請求・支払い・返金など、会計処理に関する問い合わせ",
        "technical": "エラーや不具合など、技術的なトラブルの報告",
        "other": "上記のいずれにも当てはまらない問い合わせ",
    },
)
inquiry_router.py（続き: Scoreの定義） 
# 緊急度を4段階で評価する（criteriaの並び順が0〜3に対応する）
urgency_question = Score(
    instructions="この問い合わせの緊急度はどの程度ですか？",
    criteria=[
        "急ぎではない。時間をかけて対応してよい。",
        "通常対応でよい。数日以内の返信で問題ない。",
        "早めの対応が望ましい。業務に支障が出ている可能性がある。",
        "即時対応が必要。サービス停止や金銭的損失が発生している。",
    ],
)
inquiry_router.py（続き: Noulの定義とリクエスト送信） 
# クレーム（明確な不満・怒りの表明）かどうかを判定する
complaint_question = Noul(
    instructions="この問い合わせは、顧客が明確な不満や怒りを表明しているクレームですか？",
    criteria={
        "true": "強い言葉、明確な不満、怒り、繰り返しの訴えがある",
        "false": "単なる質問、確認、通常の要望であり、明確な不満や怒りはない",
    },
)
inquiry_router.py（続き: 1回のリクエストで送信） 
# 3つのQuestionを1回のリクエストにまとめて送る（第11章: 並列評価）
client = TypeSafeClient()
response = client.system_one(
    state=inquiry_state,
    questions={
        "category": category_question,
        "urgency": urgency_question,
        "is_complaint": complaint_question,
    },
    model="jev-1.13.0",  # 本番ではエイリアスではなくバージョンを固定する（後述）
)

レスポンスには probabilities や legend も含まれますが（第9章）、今回の振り分けロジックで実際に使うのは choice / score / noul と confidence だけです。なお confidence が付くのは Choice と Score だけで、is_complaint のような Noul には confidence はありません。Noul は noul の値自体が Yes である確率なので、後述の振り分けでは noul をそのまましきい値と比較します。

本番運用の前に確認する2点

  • ① モデルはバージョンで固定する — jev-latest は現時点で jev-1.13.0 を指しますが、エイリアスは新リリース時に移動するため結果が変わりえます。本課題のように confidence のしきい値を特定バージョン向けに調整した場合は、エイリアスではなくバージョン ID を固定し、新バージョンへは評価のうえ明示的に切り替えます（第6章）。学習・検証では jev-latest、本番では jev-1.13.0 のような使い分けが実務的です。
  • ② 日本語での精度を実データで検証する — 公式ドキュメントは英語が主要な学習言語であり現時点で最も精度が高いと明記しています。日本語を含む CJK 言語も扱えますが同等の精度ではありません。本課題は日本語の問い合わせを扱うため、本番投入前に自分の日本語データで confidence の分布と誤分類率を確認してください（第1章・第6章）。

16.5 判断をコードで合成する

ここが本教材の集大成です。Jev から返る3つの判断結果は、そのままでは部品にすぎません。「どこへ振り分けるか」を決めるのはコードの責務です（第8章・第9章）。振り分けの優先順位は次の4段階です。

  1. 1 クレーム かつ 緊急度が高い → 必ず人間のオペレーターへ
  2. 2 confidence が閾値未満 → 自動判断せず人間のオペレーターへ
  3. 3 カテゴリが FAQ で答えられる → FAQ データベースから即回答
  4. 4 それ以外 → LLM に返信文の生成を任せる
優先度 条件 振り分け先
1 クレーム（noul が 0.6 超）かつ緊急度が3以上 人間
2 confidence（category と urgency の小さい方）が 0.6 未満 人間
3 category.choice が "faq" FAQ データベース
4 上記のいずれにも該当しない LLM

手順

  1. 1 しきい値を定数として先頭にまとめる
  2. 2 route_inquiry() にクレーム＋緊急度の判定を実装する
  3. 3 confidence が低い場合の人間レビュー経路を実装する
  4. 4 残りをカテゴリ判定で振り分けるヘルパー関数にまとめる
inquiry_router.py（しきい値の定義） 
# 振り分けの基準となるしきい値（この3つだけ調整すればチューニングできる）
COMPLAINT_THRESHOLD = 0.6      # これ以上ならクレームとみなす
URGENT_SCORE_THRESHOLD = 3     # 緊急度スコアがこれ以上なら「緊急」
CONFIDENCE_THRESHOLD = 0.6     # これ未満なら自動判断せず人間に回す
inquiry_router.py（判断の合成本体） 
def route_inquiry(response):
    """Jevの3つの判断結果を合成し、振り分け先を決定する"""
    category = response.answers["category"]
    urgency = response.answers["urgency"]
    complaint = response.answers["is_complaint"]

    # 優先度1: クレーム かつ 緊急度が高い → 必ず人間が対応
    if complaint.noul > COMPLAINT_THRESHOLD and urgency.score >= URGENT_SCORE_THRESHOLD:
        return "human"

    # 優先度2: 確信度が低い → 自動判断せず人間に確認してもらう
    if min(category.confidence, urgency.confidence) < CONFIDENCE_THRESHOLD:
        return "human"

    return _route_by_category(category)
inquiry_router.py（カテゴリによる振り分け） 
def _route_by_category(category):
    """カテゴリに応じてFAQデータベースかLLMかを決める"""
    # 優先度3: FAQで答えられるカテゴリ → データベースから即回答
    if category.choice == "faq":
        return "database"
    # 優先度4: それ以外は文章生成が必要なのでLLMに任せる
    return "llm"

呼び出す側は destination = route_inquiry(response) の1行だけです。判断ロジックが1つの関数に閉じているので、しきい値のチューニングや優先順位の見直しがしやすくなっています。この優先順位を図にすると次のようになります。

flowchart TD A["3つの判断結果"] --> B{"クレーム＋緊急？"} B -->|はい| H["人間へ"] B -->|いいえ| C{"確信度は十分？"} C -->|いいえ| H C -->|はい| D{"FAQで回答できる？"} D -->|はい| F["FAQデータベースへ"] D -->|いいえ| L["LLMへ"]

重要ポイント

Jev は「カテゴリ」「緊急度」「クレームか」という3つの独立した判断しか返しません。「だから人間に回すべきだ」という最終結論は、Jev のどの返却値にも入っていません。この結論を組み立てるのが route_inquiry() であり、AI の判断とコードの責務を分ける、本教材で最も重要な設計です。

16.6 動作確認

実装した route_inquiry() が意図通りに動くか、性質の異なる3種類の問い合わせで確認します。

手順

  1. 1 inquiry_state の message を、下の3種類の入力に書き換えてそれぞれ実行する
  2. 2 出力された destination（"database" / "llm" / "human"）を記録する
  3. 3 下のチェックリストの期待結果と一致するか確認する
  4. 4 一致しない場合は、しきい値または criteria の文言を調整して再実行する

動作確認チェックリスト

  • 軽微な質問: 「解約の手続き方法を教えてください」
    → category.choice = "faq"、confidence は高い想定 → destination = "database"
  • 緊急のクレーム: 「先週から3回問い合わせていますが、まだ返金されていません。もう我慢できません。」（contact_count = 3）
    → is_complaint.noul と urgency.score がともに高い想定 → destination = "human"（優先度1）
  • 判断が曖昧なもの: 「なんとなく前と違う気がします。」
    → 情報が少なく confidence が閾値を下回る想定 → destination = "human"（優先度2）

3つとも期待通りに振り分けられれば、Jev の判断とコードの合成ロジックが正しく噛み合っていることが確認できます。実際の confidence の値はモデルの応答によって変動するため、想定と異なる結果が出た場合は criteria の文言をより具体的にする、またはしきい値を調整することで改善します（第13章）。

16.7 発展課題

基本形が動いたら、次の拡張に挑戦してみましょう。いずれも本教材で扱った考え方の応用です。

Composite Scoring による優先度の算出

urgency と、別途取得した「顧客重要度」などの Score を重み付きで合成し、単一の「対応優先度」を算出する（第12章）。

ガードレール用 Question の追加

個人情報や不正な内容が含まれるかを判定する Noul を追加し、route_inquiry() の優先度0として「即ブロック」経路を作る。

人間レビュー結果のロギングとしきい値調整

人間が実際にどう対応したかを記録し、しきい値（COMPLAINT_THRESHOLD など）が適切かどうかを定期的に見直す仕組みを作る。

JavaScript SDK での再実装

同じ振り分けロジックを JavaScript SDK で実装し、Web フロントエンドやチャットウィジェットに組み込む。

Intent Routing の拡張

category の値ごとに異なる LLM プロンプトやハンドラーを出し分け、第14章の Decision Layer 構成へ発展させる。

本教材の最終到達目標

  • Jev と一般的な LLM の違いを説明できる
  • System One モデルの考え方を説明できる
  • 判断に必要な情報だけを含む State を設計できる
  • Choice / Score / Noul を判断内容に応じて使い分けられる
  • 複雑な判断を Atomic Question へ分解できる
  • probabilities と confidence を区別して扱える
  • 複数の Question を1リクエストで組み合わせられる
  • 複数の判断結果をコードで合成して最終判断を組み立てられる
  • Confidence による Human Review の振り分けを設計できる
  • Jev・LLM・通常コードの役割を適切に分けられる
  • Jev を既存アプリケーションへ組み込める
  • Jev を Decision Layer として利用したシステムを設計できる

本教材で強調した5原則

  1. 1. Jev に Reasoning させすぎない — 一つの明確な判断に限定する
  2. 2. Question は Atomic にする — 複合的な依頼は分解する
  3. 3. State には必要な情報だけを渡す — 無関係な情報は精度を下げる
  4. 4. AI の判断をコードで合成する — 最終判断はコードの責務
  5. 5. Confidence を使って「判断しない」選択肢を作る — 不確実なら人間へ
