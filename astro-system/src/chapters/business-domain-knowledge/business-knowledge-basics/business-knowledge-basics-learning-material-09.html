業務システムの基本用語

設計書や打ち合わせでは、「マスタ」「トランザクション」「伝票」「ステータス」「締め処理」「バッチ処理」「システム連携」という言葉が絶えず飛び交います。これらは販売・購買・人事のどれか特定の業務の言葉ではなく、業務システムであれば分野を問わず登場する「システム側の共通語」です。この章では、第2章から第8章で見てきた具体的な業務を思い出しながら、それらがシステムの中でどう表現されているのかを、この7つの言葉で整理してつなげます。

この章で学ぶこと

  • マスタとトランザクションの違いを、具体例を挙げて説明できる
  • 伝票の「ヘッダ」と「明細」という2階層構造を、受注伝票の例で説明できる
  • ステータスの役割と、締め処理・バッチ処理がなぜ必要なのかを説明できる
  • システム連携の代表的な方式とタイミングを理解し、起きやすいトラブルを説明できる

基本 はまず押さえたい内容、 発展 は用語の由来や仕組みを深掘りした内容です。「発展」は最初は読み飛ばしても構いません。

9.1 マスタ 基本

マスタとは、あらかじめ登録しておく「基準となるデータ」のことです。誰が得意先で、どんな商品を扱っていて、誰が社員なのか。業務が動き出す前に、まず整えておく必要がある土台のデータだと考えてください。第1章〜第8章で登場した得意先・仕入先・商品・社員・倉庫といった情報は、いずれもマスタとしてシステムに登録されています。

得意先マスタ

さくら商事が商品を売る相手の一覧。会社名・住所・締め日・支払条件などを登録します（第2章）。

商品マスタ

扱っている商品の一覧。商品コード・商品名・単価・在庫単位などを登録します（第2〜4章）。

社員マスタ

社員の一覧。社員番号・氏名・所属部門・給与条件などを登録します（第8章）。

マスタには2つの大きな特徴があります。1つ目は頻繁には変わらないことです。新しい得意先と取引を始めた時や、商品の単価を改定した時など、変更は限られたタイミングでしか起こりません。2つ目は、間違っていると全業務に影響することです。もし商品マスタでボールペンの単価を100円のところ誤って10円と登録してしまったら、その商品を注文した受注データが軒並み、誤った金額のまま計算されてしまいます。

だからこそ、新システムを導入するプロジェクトでは、マスタの整備が最初の関門になります。既存のシステムや紙・Excelで管理していたマスタ情報を、新システムに合わせた形式へ移し替える作業をデータ移行と呼びます。長年運用してきたマスタには、同じ得意先が表記ゆれで2件登録されているといった重複がよく見つかり、その整理（名寄せ）だけでも大きな工数がかかることがあります。

また、マスタは「今」の状態だけでなく履歴を持つことがあります。取引を停止した得意先はレコードごと削除するのではなく有効／無効フラグで「無効」に切り替えて残しますし、商品の単価改定では「いつから、いくらで販売するか」を管理するために適用開始日を持たせる設計もよく使われます。

用語: コード

マスタの各レコードには、一意に識別するための「コード」（得意先コード、商品コードなど）が振られます。名前ではなくコードで紐付けるのは、「株式会社さくら商事」と「さくら商事（株）」のような表記ゆれがあっても、システムが同じ相手だと確実に判断できるようにするためです。

よくある落とし穴: マスタは物理的に消してはいけない

取り扱いをやめた商品だからといって、商品マスタからレコードごと削除してしまうと、過去に売った受注伝票がその商品コードを参照できなくなり、過去の売上明細が表示できないといった障害につながります。マスタを消すのではなく、無効フラグを立てて「新規では選べないが、過去データとしては参照できる」状態にするのが定石です。

9.2 トランザクション 基本

トランザクションとは、日々発生する「取引・出来事のデータ」のことです。受注、出荷、売上、入金、入出庫、勤怠など、「いつ・何が起きたか」を記録するデータはすべてトランザクションにあたります。第2章の受注データ、第4章の入出庫データ、第8章の勤怠データは、いずれもトランザクションの具体例です。

マスタとトランザクションは、業務システムを理解するうえで、まず押さえておきたい対比です。次の表で違いを整理します。

観点 マスタ トランザクション
何を表すか あらかじめ登録しておく基準となるデータ 日々発生する取引・出来事の記録
変わる頻度 低い（得意先の新規登録、単価改定の時など） 高い（毎日何十件・何百件と発生する）
件数の増え方 ゆるやかに増える（得意先は数百件程度） どんどん積み上がる（受注は1年で数万件も）
消してよいか 基本的に消さない（無効フラグで運用） 消してはいけない（証跡として保存する）
具体例 得意先マスタ、商品マスタ、社員マスタ 受注データ、出荷データ、入金データ

もう1つ重要なのは、トランザクションは単独では成立せず、マスタを参照して初めて意味を持つという関係です。受注データは、取引の相手や対象の商品を「得意先コード」「商品コード」という形で持ち、会社名・住所・商品名といった付随する情報は、そのコードでマスタを参照して取得します。

ただし、何もかもをマスタ参照で済ませてよいわけではありません。受注単価のような「取引時点の条件」は、後からマスタが変更されても過去の取引内容が変わらないよう、トランザクション側にも値を持たせる（スナップショットとして保持する）のが一般的です。

なぜマスタを見に行くだけではいけないのか、単価改定の例で考えてみましょう。ボールペンの単価が3月までは100円で、4月に120円へ改定されたとします。もし受注データが単価を持たず、金額を表示するたびに商品マスタの単価を取り直す設計だったら、4月に単価を改定した瞬間、3月に受注した分の金額まで120円で計算し直されてしまいます。すでに得意先へ請求した金額と合わなくなり、過去の記録として使えません。だからこそ、受注時に採用した単価は、受注データ自身が抱えておくのです。

整理すると、「誰と・何を、を指し示すコードはマスタを参照する。取引時点で決まった条件はトランザクションにも持つ」という使い分けになります。得意先の住所のように常に最新の値を見たい情報はマスタ参照のままにする、といった判断も含め、どの項目をコピーして持たせるかは、業務要件に応じたデータモデル設計の重要な検討ポイントです。

用語: スナップショット（取引時点の値を写し取る）

受注データが受注時点の単価を自分で持っていれば、商品マスタの単価を後から改定しても、すでに確定した受注データの単価は変わりません。このように「その時点でいくらだったか」をトランザクション側へ写し取っておく持ち方をスナップショットと呼びます。単価・掛率・消費税率など、後から変わり得る条件については、スナップショットとして持たせるかどうかを設計時に検討します。

9.3 伝票 基本

伝票とは、業務上の1件の処理をまとめた単位のことです。第2章で登場した見積書・注文書・請求書は、すべて伝票の一種です。伝票は、ヘッダ（1件に1つだけ存在する情報）と明細（1件の伝票に対して複数行存在する情報）という2階層構造を持つのが特徴です。

さくら商事が得意先「株式会社文具堂」からボールペンと付箋の注文を受けた、受注伝票の例で見てみましょう。伝票番号・受注日・得意先・合計金額は伝票全体で1つに決まる情報なのでヘッダに、注文された商品ごとの内訳は行数が変わる情報なので明細に記録されます。

伝票ヘッダ（1件に1つ）

伝票番号 JU-2026081501
受注日 2026-08-15
得意先 株式会社文具堂
合計金額 55,000円

明細（複数行）

行 商品 数量 単価 金額
1 ボールペン（黒） 500本 100円 50,000円
2 付箋（大） 100個 50円 5,000円

伝票番号は、担当者が手入力するのではなくシステムが自動で採番するのが基本です。「JU（受注）＋年月＋連番」のようなルールで採番すれば、番号を見るだけでいつ・どの種類の伝票かが分かり、採番の重複も防げます。ただし、自動採番でも欠番はなくなりません。番号を採った後に伝票がキャンセルされたり、登録処理がエラーになって取り消し（ロールバック）されたりすると、その番号は使われないまま飛んでしまうためです。監査などの理由で欠番を許容しない業務要件がある場合は、欠番を記録して報告する仕組みを用意するなど、別途対応を検討する必要があります。

では、確定した伝票の金額を間違えていたことに気づいたら、その場で数字を書き換えてよいのでしょうか。答えはノーです。業務システムでは、元の伝票はそのまま残し、取消のための伝票を新たに起票して元の内容を打ち消し、必要であれば正しい内容で新しい伝票を起票し直す、という運用が一般的です。

受注伝票のテーブル定義（イメージ） 
-- 受注伝票ヘッダ（1伝票につき1行）
CREATE TABLE 受注伝票ヘッダ (
    伝票番号     VARCHAR(12) PRIMARY KEY,
    受注日       DATE,
    得意先コード VARCHAR(8),
    合計金額     DECIMAL(12,0)
);
-- 受注伝票明細（1伝票につき複数行）
CREATE TABLE 受注伝票明細 (
    伝票番号     VARCHAR(12),
    明細行番号   INT,
    商品コード   VARCHAR(8),
    数量         INT,
    単価         DECIMAL(10,0)
);

用語: 赤伝（あかでん）発展

元の伝票を打ち消すために起票する、マイナスの金額を持つ伝票を「赤伝」と呼びます。紙の伝票を使っていた時代に、取消であることが一目で分かるよう金額を赤字で書いたことに由来する用語です。直接書き換えず赤伝を起こすのは、「いつ、誰が、何を訂正したか」という記録（監査証跡）を残すためです。

9.4 ステータス 基本

ステータスとは、伝票が今どの段階にあるかを表す状態のことです。ここで第2章を思い出してください。「見積 → 受注 → 出荷 → 売上 → 請求 → 入金」という販売の流れは、1枚の伝票が姿を変えていくのではなく、見積・受注・出荷・売上・請求・入金がそれぞれ別のデータとして作られ、伝票番号でつながっていく流れでした。そしてそれぞれの伝票が、自分自身のステータスを持ちます。

提出済／受注済／失注"] -->|"見積番号でつながる"| J["受注データ
受注済／出荷指示済／出荷完了／完了"] J -->|"受注番号でつながる"| S["出荷データ
出荷指示済／出荷済"] S -->|"出荷番号でつながる"| U["売上データ
計上済／請求済"] U -->|"売上番号でつながる"| R["請求データ
発行済／入金済"]

たとえば受注伝票なら、ステータスは「受注済 → 出荷指示済 → 出荷完了 → 完了」のように遷移します。受注した直後は「受注済」ですが、倉庫に出荷を依頼した時点で「出荷指示済」に変わり、出荷データが登録されて受注残がなくなった時点で「出荷完了」、一連の処理が終われば「完了」になります。得意先都合でキャンセルになるケースもあるため、受注済や出荷指示済の段階から「キャンセル」へ分岐する経路も用意しておきます。

flowchart TD A["受注済"] --> B["出荷指示済"] B --> C["出荷完了"] C --> D["完了"] A -.->|"取消"| X["キャンセル"] B -.->|"取消"| X

では、売上が計上されたか、請求書を発行したかは、どこで分かるのでしょうか。これらは受注伝票ではなく、売上データや請求データが、それぞれ自分のステータスとして持ちます（さくら商事は出荷基準を採用しているため、第2章で見たとおり売上の計上日は出荷日です。月末に行われるのは請求の締め処理です）。とはいえ、営業担当者が「あの注文は今どこまで進んだのか」を1画面で知りたい、という要望はよくあります。そこでシステムによっては、関連する伝票の進み具合をまとめた集約ステータス（進捗ステータス）を受注伝票側にも持たせ、出荷や売上の登録にあわせて更新する設計をとることもあります。

ステータスが重要なのは、それがあるおかげで「次に誰が何をすべきか」をシステムが判断できるからです。倉庫担当者の画面には「出荷指示済」の受注伝票だけを一覧表示し、経理担当者の請求バッチは「まだ請求済になっていない売上データ」だけを対象にする、というように、業務システムの多くの処理は「特定のステータスのデータを探して、次のステータスに進める」という形で組み立てられています。

重要ポイント

「この伝票、今どうなっていますか」という質問に答えられるのがステータスの価値です。逆に言えば、ステータスの遷移を正しく設計できていない業務システムでは、「今どこまで進んでいるか」が誰にも把握しづらくなります。打ち合わせで新しい業務を聞き取る時は、「その処理の後、どの伝票のステータスが何から何に変わりますか」と確認する習慣をつけましょう。

9.5 締め処理 基本

締め処理とは、一定期間で区切って数字を確定させることです。代表的なのが月次締めで、「8月分の数字はここまで」と区切りをつける処理を指します。締め処理を行うと、締め日以降はその期間の伝票を修正できないようにするのが基本です。この「修正できなくする」操作をロックと呼びます。

なぜロックが必要なのでしょうか。締め処理の後に誰かが自由に前の月の伝票を直せてしまうと、すでに得意先へ提出した請求書や、経営会議で報告した数字と、システム上の数字が食い違ってしまいます。締めるという行為は、「この数字で確定し、次のステップ（請求・決算・給与振込など）に進みます」という意思表示でもあるのです。

とはいえ、締めた後に入力ミスが見つかることは実務では珍しくありません。その場合の対応は大きく2通りです。1つは翌月で調整する方法で、前月分を直接直さず、翌月の伝票としてプラスまたはマイナスの調整を行います。もう1つは、特別な訂正処理として、締め解除の権限を持つ管理者だけが実行できる操作で例外的に前月分を修正する方法です。どちらを採用するかは、業務ごとに事前に決めておく必要があります。

締め処理は、これまでの章で何度も登場しています。第2章の請求締め（得意先ごとの締め日で1か月分の売上をまとめて請求書にする処理）、第7章の月次決算（1か月分の仕訳を締めて損益を確定する処理）、第8章の勤怠締め（給与計算のために1か月分の勤怠を確定する処理）は、いずれも「一定期間で区切って数字を確定させ、以降は動かせないようにする」という同じ考え方の応用です。

よくある落とし穴: 締めた後の修正依頼はよく発生する

「締めた後は絶対に直せません」という設計だけでは、現場は回りません。締め処理を設計する際は、「締めた後に間違いが見つかったら、翌月調整で対応するのか、特別な訂正処理を用意するのか」を事前に決めておきましょう。これを決めずに本番を迎えると、締め直後に運用が止まってしまいます。

9.6 バッチ処理 基本

バッチ処理とは、まとまったデータを一括で処理することです。担当者が画面から1件ずつ入力・確認するオンライン処理と対比すると分かりやすくなります。

観点 オンライン処理 バッチ処理
処理の単位 画面から1件ずつ まとまったデータを一括で
実行するタイミング 利用者が画面を操作した時（随時） 夜間や決まった時刻に自動実行
処理時間の目安 数秒以内（待たせると使いものにならない） 数分〜数時間かかることもある
代表例 受注入力、在庫照会、得意先検索 締め処理、請求書一括発行、給与計算

締め処理

1か月分の受注・出荷・入出庫データをまとめて集計し、数字を確定させます（9.5）。

請求書一括発行

締め日を迎えた得意先を対象に、請求書をまとめて作成・発行します（第2章）。

給与計算

全社員分の勤怠データをまとめて集計し、給与を一括で計算します（第8章）。

ここからは少し発展的な話題です。実際の現場では、複数のバッチ処理を決まった順序でつなげて実行します。この一連の実行順序をジョブネットと呼びます。たとえば「受注データ集計 → 在庫引当確認 → 請求書発行 → 会計連携」のように、前の処理の結果を次の処理が使う場合、順序を間違えると正しい結果になりません。多くの企業では、こうした夜間バッチを人が寝ている間に自動実行し、翌朝には結果ができあがっているようにしています。

バッチが途中で異常終了した場合は、原因を直してから改めて実行します。これをリラン（再実行）と呼びます。ここで注意すべきなのは、「二重に実行してはいけない処理がある」という点です。たとえば給与の振込データを作成するバッチを誤って2回実行すると、社員の口座に給与が二重に振り込まれるデータを作ってしまう恐れがあります。リランする際は、「どこまで処理済みか」を確認し、処理済みの分をもう一度実行しないように設計・運用しておくことが大切です。

用語: ジョブネット発展

複数のバッチ処理（ジョブ）を、実行する順番や依存関係にしたがってつなげたものをジョブネットと呼びます。「Aが正常終了したらBを実行し、Bが正常終了したらCを実行する」というように連鎖させることで、夜間の一連の処理を自動で流せるようにします。

9.7 システム連携 基本

システム連携とは、別々のシステムがデータを受け渡すことです。販売管理システムで計上した売上を会計システムへ渡す、人事給与システムで計算した給与を会計システムへ渡す、といった社内のシステム間の連携のほか、自社と取引先との間でも連携は行われます。受発注データを電子的にやり取りする仕組みはEDI（Electronic Data Interchange／電子データ交換）と呼ばれ、さくら商事のような卸売会社でも、取引量の多い得意先とはEDIで受注データを直接連携しているケースがあります。

連携の方式にはいくつかの種類があり、それぞれ得意なタイミングが異なります。

連携方式 概要 主なタイミング 注意点
ファイル連携 決まった形式のファイル（CSV等）を出力し、相手システムが取り込む 日次バッチが多い ファイルが届くまでタイムラグがある
API連携 システム同士がネットワーク経由で直接データをやり取りする リアルタイム連携でよく使われる（非同期にもできる） 同期的に呼び出す場合は、相手システムが稼働している必要がある
データベース直接参照 片方のシステムがもう片方のデータベースを直接参照する リアルタイム 相手側のテーブル変更の影響を受けやすい

API連携は「リアルタイム＝相手システムがその瞬間に動いていないと成立しない」と思われがちですが、いつもそうとは限りません。呼び出してすぐ結果を受け取る同期APIのほかに、受け付けだけ先に済ませて処理は後から行う非同期APIや、送りたいデータをいったんメッセージキューに預け、相手システムが自分のタイミングで取り出すメッセージング連携という方式もあります。キューを介す方式なら、相手システムが一時的に停止していても、復旧後にたまったデータをまとめて処理できます。どこまでリアルタイム性が必要か、相手が止まったときにどうしたいかによって、方式を選び分けます。

システム連携でよく起きるトラブルの代表が、「片方だけ処理が終わっている」状態です。たとえば、販売管理システム側では売上が計上済みになっているのに、夜間バッチが何らかの理由で失敗し、会計システム側にはまだそのデータが届いていない、というズレが典型例です。この不整合に気づかないまま決算を進めてしまうと大きな問題になるため、件数や金額の合計を両システムで突き合わせるチェック処理を連携の仕組みにあわせて用意しておくことが重要です。

重要ポイント

なぜ連携が必要なのかを突き詰めると、答えは「システムが分かれているから」です。第1章で紹介したERPのように、会社全体の業務を1つの製品でまかない、共通のマスタと統合された業務プロセスを使えば、社内システム間の連携を減らしやすくなります。ただし、それでもEDI・ECサイト・銀行・給与計算サービスといった外部システムとの連携は残るのが一般的です。実際には、コストや導入のしやすさから、販売と会計だけERPで、人事給与は専用パッケージ、取引先とはEDIというように、一部だけ連携を残す構成が多いのが実情です（ERPと連携の関係は次の第10章10.3で詳しく扱います）。マスタ・トランザクション・伝票・ステータス・締め処理・バッチ処理・システム連携。この7つを押さえておくと、初めて見る業務システムの設計書でも、ぐっと読みやすくなります。次の第10章では、これらの言葉を使いながら、さくら商事の業務全体を1枚の図でつなげて振り返ります。

やってみよう 9-1: 身近な取引を7つの共通語で分解する

この章で学んだ7つの言葉は、実際の伝票やデータに当てはめてみると理解が定着します。さくら商事の受注伝票（9.3の例）を題材に、次の手順で整理してみましょう。

手順

  1. 1 9.3の受注伝票について、ヘッダ項目と明細項目をそれぞれノートに書き出す。
  2. 2 その伝票データが参照しているマスタを、3つ以上挙げる。
  3. 3 9.4の図を参考に、この受注伝票がたどるステータスの遷移を矢印で書いてみる。キャンセルになる分岐も忘れずに書く。あわせて、出荷データ・売上データが別の伝票として作られ、伝票番号でつながることも図に加えてみる。
  4. 4 この業務のどこかにバッチ処理が使われるとしたら、どんな処理が該当するか（締め処理、一括発行など）を考えて書く。

ポイント: 「これはマスタか、トランザクションか」「今のステータスは何か」を自分で言い当てられるようになれば、初めて見る業務の設計書でも、システム側の構造を素早く読み解けるようになります。

理解度確認クイズ

  1. Q1. マスタとトランザクションの違いを、それぞれ具体例を挙げて説明してください。

    回答を表示

    マスタは、あらかじめ登録しておく基準となるデータで、変更頻度が低く（例: 得意先マスタ、商品マスタ）、原則として削除せず無効フラグで運用します。トランザクションは、日々発生する取引・出来事の記録で、件数がどんどん積み上がり（例: 受注データ、入金データ）、証跡として消してはいけません。また、トランザクションはマスタのコードを参照して初めて成立しますが、受注単価のように取引時点で決まった条件は、後からマスタが変わっても過去の記録が変わらないよう、トランザクション側にもスナップショットとして保持するのが一般的です。

  2. Q2. 伝票の「ヘッダ」と「明細」とは何ですか。受注伝票を例に説明してください。

    回答を表示

    ヘッダは、1件の伝票につき1つだけ存在する情報で、受注伝票では伝票番号・受注日・得意先・合計金額などが該当します。明細は、1件の伝票に対して複数行存在する情報で、受注伝票では注文された商品ごとの商品名・数量・単価・金額が該当します。伝票はこの2階層構造を持つのが特徴です。

  3. Q3. 締め処理の目的は何ですか。締めた後に誤りが見つかった場合、どのように対応しますか。

    回答を表示

    締め処理の目的は、一定期間で区切って数字を確定させ、締め日以降はその期間の伝票を修正できないようロックすることです。これにより、確定した数字が後から勝手に変わってしまう事態を防ぎます。締めた後に誤りが見つかった場合は、前月分を直接書き換えず、翌月の伝票として調整するか、締め解除の権限を持つ管理者による特別な訂正処理で対応します。
