AI時代のPower BI

これまでの11章では、Power BI Desktop を操作してデータを取り込み、モデルを組み、DAX で指標を計算し、レポートを作って共有するところまでを、人が手を動かす手順として学んできました。最終章となるこの章では視点を変え、Power BI の世界で今まさに進んでいるAI活用の方向性を俯瞰します。Copilot によるレポート下書きや DAX 作成支援、AI エージェントが直接編集できる PBIP 形式、Fabric 上のスキルや MCP サーバーといった話題を紹介したうえで、本ガイド全12章を振り返り、次にどこへ学びを進めればよいかを一緒に考えます。

この章で学ぶこと

12.1 Power BI と AI の関係

注意: 本章の内容は執筆時点の情報です

この章で紹介する Copilot・PBIP・Fabric 上のスキル・MCP サーバーなどの AI 関連機能は、Power BI の中でも変化が速い領域です。ここに書かれているのは執筆時点の情報であり、機能の名称・提供範囲・利用条件は今後変わる可能性があります。実際に使う際は、必ず Microsoft の最新情報を確認してください。

第2章から第11章まで、みらい商事の売上分析を題材に、データの取得からモデリング、DAX、レポート作成、共有・運用までを人が手を動かして進めてきました。Power BI はもともと「人が Desktop で作り込むツール」として設計されていますが、近年はAI がその作成作業そのものを支援する方向に進化しています。

従来: 人がゼロから作る

要件を聞き取り、Power Query での整形、モデルのリレーション、DAX メジャー、レポートのレイアウトまで、すべての工程を人が手作業で組み立てます。第2章〜第11章で学んできた進め方です。

現在: AI が下書きを支援する

Copilot などの AI 機能が、レポートページの草案や DAX の候補、データの要約を自動で作成します。人はその草案を確認し、正しさを判断する役割に変わります。

本章を貫く原則: AIは下書き役、正しさの確認は人

AI がどれだけ速く、それらしい下書きを作れても、その数字や式が業務の意図と一致しているかを最終的に判断するのは人です。この原則は、この章で紹介するどの機能にも共通して当てはまります。

12.2 Copilot in Power BI

Copilot in Power BI は、Power BI に組み込まれた生成 AI の機能です。既存のモデルをもとにレポートページの草案を自動で組み立てたり、表示されている指標を自然な文章で要約したり、DAX 式の生成や説明を行ったりする、と紹介されています。

以前からあるQ＆A機能（自然言語で質問すると、既存のモデルに対応するビジュアルを表示する機能）と混同されがちですが、役割は異なります。Q＆A が「今あるデータに質問して答えを引き出す」機能であるのに対し、Copilot は「新しいレポートページや DAX 式そのものを生成する」機能です。

活用領域 AI がしてくれること 人が確認すべきこと
レポートページの下書き モデルの内容からビジュアルの組み合わせ案を自動生成する 見せたい指標と合っているか、ビジュアルの種類が適切か
データの要約 画面に表示中の指標や傾向を自然な文章にまとめる 数値の解釈に誤りがないか、前提の期間・条件が抜けていないか
DAX の生成・説明 自然言語の指示から DAX 式を作る、既存の式を平易に説明する 意図した集計になっているか、実際の数値と検算したか
Q＆A（従来機能） 既存モデルへの質問に対応するビジュアルを提示する 質問に対応するフィールドがモデル内に存在するか

利用条件と、精度を上げるコツ

Copilot の利用には、対象のライセンスや Fabric の容量が必要になる場合がある、と案内されています。また AI はテーブル名や列名から意味を読み取って動くため、第6章・第7章で扱ったように分かりやすい名前（CustomerNameなど）を付けておくほど、生成される下書きの精度が上がるといわれています。

12.3 AI による DAX 作成支援

第7章で学んだ DAX は、CALCULATEやDIVIDEなど、覚えることの多い言語です。AI による作成支援は、この負担を減らす代表的な使いどころとして紹介されています。自然言語で「〇〇ごとの合計を求めるメジャーを作って」と指示すると DAX の候補が生成されたり、逆に既存の DAX 式を貼り付けて「これは何をしている式か説明して」と尋ねると平易な説明が返ってきたりします。既存の式の書き直し（リファクタ）を提案してもらう使い方も紹介されています。

ただし、生成された式はあくまで候補です。次の例のように、AI に依頼して得られた式であっても、必ず自分で結果を検算してから使いましょう。

DAX（AIが生成した候補） 
// 「文具カテゴリの売上金額を求めるメジャーを作って」と
// AIに依頼して得られた候補（あくまで下書き）
文具カテゴリ売上金額 =
CALCULATE(
    [売上金額],
    Products[Category] = "文具"
)
// 検算: フィルターを手動で設定した場合の金額と一致するか確認する

AI に DAX を依頼するときは、次の3点を意識すると精度が上がるといわれています。

  1. 1 対象のテーブル名・列名を明示する（例:「Sales テーブルの Amount 列を…」）。名前だけで曖昧に頼むと、意図と違う集計になりやすい。
  2. 2 集計の粒度や条件を書く（例:「カテゴリごとに」「今年度のみ」）。第7章で学んだフィルターコンテキストの考え方が、そのまま指示のヒントになる。
  3. 3 生成後は小さいデータで検算してから本番に組み込む。既知の合計値やカードビジュアルの数値と突き合わせ、一致してから採用する。

12.4 PBIP（Power BI Project 形式）

これまでの章で扱ってきた .pbix は、レポート・モデル・取り込んだデータが1つのバイナリファイルにまとめて保存される形式でした。手軽に持ち運べる一方で、中身は人にも Git にも読めないひとかたまりのデータです。

PBIP（Power BI Project）はこれと異なり、レポートとモデルの定義をフォルダの中の複数のテキストファイルとして保存する形式です。中身がテキストであることから、次のような利点があると紹介されています。

比較する点 .pbix PBIP（Power BI Project）
保存の形 1つのバイナリファイル フォルダ＋複数のテキストファイル
Git での差分表示 ほぼ不可能（変更のたびにファイル全体が置き換わる） 可能（変更した箇所だけが差分として見える）
コードレビュー 困難 テキストなので、通常のプログラムのコードと同様にレビューできる
CI/CD との連携 難しい パイプラインに組み込みやすいと紹介されている
AI エージェントによる編集 バイナリのため、ファイルを直接読み書きするのは困難 テキストファイルなので、AI エージェントが直接編集できる

AI時代にPBIPが重要な理由

AI エージェントは基本的にテキストを読み書きすることで動きます。モデルやレポートの定義がテキストファイルになっている PBIP は、AI エージェントが Power BI の開発に関わっていくための土台になる形式だと位置づけられています。

12.5 Skills for Fabric と MCP

PBIP によってモデルやレポートがテキストとして扱えるようになると、次に出てくるのは「AI エージェントがそのテキストをどうやって扱うか」という話です。ここで登場するのがSkills for FabricとMCPです。

用語: MCP（Model Context Protocol）

MCP とは、一言でいうとAIツールが外部システムを扱うための共通の接続規格です。AI エージェントと Power BI・Microsoft Fabric のような外部システムとの間をつなぐ、共通の「差し込み口」だとイメージすると分かりやすいでしょう。

Microsoft Fabric（Power BI を含む Microsoft のデータ分析基盤）上では、AI エージェントに Power BI の作成作業を行わせるためのスキルが提供されており、powerbi-authoring@fabric-collection というスキルがその一つとして紹介されています。また、Power BI のモデリング作業を MCP 経由で AI エージェントに扱わせる仕組みとして、Power BI Modeling MCP Serverという MCP サーバーも提供されています。

これらの詳細な機能や設定方法は変化が速いためここでは深追いしませんが、「AI エージェントが Power BI を操作するための、共通の入り口が整いつつある」という方向性だけ押さえておけば十分です。

12.6 AI エージェントによる Power BI 開発の全体像と、これからの学び方

ここまで見てきた Copilot・DAX 作成支援・PBIP・Skills for Fabric・MCP を一つの流れとして並べると、Power BI の開発は次のように変わりつつあります。

従来のフロー

flowchart LR A["要件を聞く"] --> B["人がPower Query・モデル・
DAXをDesktopで作成"] B --> C["人がレポートを配置"] C --> D["人がレビュー・修正"] D --> E["発行・共有"]

AI時代のフロー

flowchart LR A2["要件を聞く"] --> B2["AIがレポート下書き・
DAX候補をPBIPで生成"] B2 --> C2["人が正しさを確認・修正"] C2 --> D2["人が最終判断して発行・共有"]

工程そのもの（要件を聞く → 作る → 確認する → 共有する）が無くなるわけではありません。「作る」の中身が人の手作業から AI との共同作業に置き換わり、「確認する」の重みが増している、という変化として捉えると分かりやすいでしょう。

やってみよう 12-1: AIに下書きさせたい作業を書き出す

Copilot などの AI 機能を実際に試せる環境が手元になくても、「どこに AI を使い、どこを人が確認するか」を考える練習はできます。自分の担当業務やみらい商事の売上分析を題材に、次の手順で整理してみましょう。

手順

  1. 1 自分が関わる Power BI の作業のうち、「AI に下書きを任せたい」ものを3つ書き出す（例: 月次レポートページの叩き台作成、DAXメジャーの初稿、レポート内容の要約文の作成）。
  2. 2 それぞれについて「AIの出力のどこを、どうやって確認するか」を1行で書き添える（例: 合計金額を既存レポートの数値と突き合わせる）。
  3. 3 3つのうち最も検証しやすいものを1つ選び、「依頼 → AIの下書き → 人の確認 → 修正 → 反映」の順で試すとしたら何をするかを具体的に書き出す。
  4. 4 書き出した内容をチームや上長と共有し、「AIに任せてよい範囲」の認識をそろえておく。

理解度確認クイズ

  1. Q1. Power BI で Copilot などの AI 機能を使うとき、AI に任せてよい範囲と、必ず人が確認すべき範囲はそれぞれ何ですか。

    回答を表示

    AI に任せてよいのは、レポートページの下書き作成、データの要約、DAX 式の生成・説明といった「たたき台づくり」です。一方、生成された内容が業務の意図と一致した集計になっているか、実際の数値と検算が取れているか、最終的に公開してよい内容かどうかの判断は、必ず人が行います。「AIは下書き役、正しさの確認は人」という原則です。

  2. Q2. PBIP（Power BI Project）形式が、従来の .pbix と比べて Git や AI エージェントと相性が良いのはなぜですか。

    回答を表示

    .pbix はレポート・モデル・データが1つのバイナリファイルにまとめられているため、Git で差分を確認できず、AI エージェントが中身を直接読み書きするのも困難です。PBIP はフォルダの中の複数のテキストファイルとして保存されるため、変更箇所だけが差分として見え、コードレビューや CI/CD パイプラインに組み込みやすく、AI エージェントがテキストとして直接編集できます。

  3. Q3. MCP とは何ですか。一言で説明してください。

    回答を表示

    MCP（Model Context Protocol）は、AI ツールが外部システムを扱うための共通の接続規格です。Power BI Modeling MCP Server のように、この規格を通じて AI エージェントが Power BI や Microsoft Fabric のようなシステムを操作できるようにする仕組みが紹介されています。
