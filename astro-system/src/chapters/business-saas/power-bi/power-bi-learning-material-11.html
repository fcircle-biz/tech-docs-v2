ホーム Power BI 第11章
第11章 所要時間: 約60分

セキュリティと運用

せっかく作ったレポートも、正しい相手に正しい範囲だけ見せられなければ安心して使えません。この章では、ワークスペースのロール・アプリの対象者・個別共有という3つの層でアクセスを整理する考え方と、同じレポートでも見る人によって行を出し分けるRLS（行レベルセキュリティ）の作り方を学びます。あわせて、社内のデータベースとクラウドをつなぐオンプレミスデータゲートウェイの役割、スケジュール更新が止まってしまう典型的な原因、そして運用でつまずきやすいポイントも扱います。第10章で発行したレポートを、安全に長く使い続けるための知識です。

この章で学ぶこと

  • ワークスペースのロール・アプリの対象者・個別共有という3層でアクセス制御を整理できる
  • RLS（行レベルセキュリティ）が何を守るための機能かを説明し、DAXフィルターで作成できる
  • オンプレミスデータゲートウェイの役割と、標準モード・個人用モードの違いを説明できる
  • スケジュール更新が失敗する代表的な原因と、運用でつまずきやすい点への対策を説明できる

11.1 アクセス制御の考え方

「このレポートは誰が見られるようにするか」を考えるとき、いきなり細かい設定から入ると迷子になります。Power BI のアクセス制御は広い範囲から狭い範囲へ、3つの層に分けて考えると整理しやすくなります。まずワークスペースのロールで「誰が作り手側の権限を持つか」を決め、次にアプリの対象者で「誰に閲覧用として配るか」を決め、最後に必要であれば個別共有やRLSで「同じレポートの中でもさらに細かく絞る」という順番です。

flowchart TD A["① ワークスペースのロール
誰が編集・管理できるか（第10章）"] --> B["② アプリの対象者
誰に閲覧用として配布するか"] B --> C["③ 個別共有・RLS
同じレポートの中で誰にどの行を見せるか"]

それぞれの層が何を制御し、どこで設定するのかを整理すると次のとおりです。①と②の詳細は第10章で扱ったので、この章では③の個別共有とRLSに重点を置いて学びます。

層 何を制御するか 主な設定場所
① ワークスペースのロール レポートを編集・管理できるかどうか（作り手側の権限） ワークスペースの「アクセス」設定
② アプリの対象者 閲覧用アプリを誰に配布するか、対象者ごとにどのページを見せるか アプリの「対象ユーザー」設定
③ 個別共有／RLS 特定の1人にレポートを直接共有する、同じレポートで見える行を人ごとに変える 共有リンク、モデルの「ロールの管理」

まずはワークスペースのロールで考える

「見せたくない人がいる」と相談を受けたとき、最初に確認すべきは③の個別共有ではなく①のワークスペースのロールです。編集権限を持つ人が想定より多いと、意図せずレポートやデータソースの設定を変更されてしまうことがあります。土台となる①が正しく設定されて初めて、②③の細かい調整が意味を持ちます。

11.2 RLS（行レベルセキュリティ）とは

RLS（Row-Level Security、行レベルセキュリティ）とは、同じ1つのレポートを開いても、見る人によって表示される行を変える仕組みです。「東日本担当の営業と西日本担当の営業に、それぞれ別のレポートを作って配る」のではなく、レポートは1つのまま、見る人に応じてPower BI側が自動的に行を絞り込んで見せる点がポイントです。

たとえば、みらい商事の営業担当者向けに「地域別売上レポート」を1つだけ発行しておき、東日本担当の佐藤さんがログインするとCustomers[Region]が「東日本」の売上だけが見え、西日本担当の鈴木さんがログインすると「西日本」の売上だけが見える、という使い方をします。レポートを地域の数だけ複製する必要がなく、修正もメンテナンスも1か所で済みます。

重要: RLSが守っているのは「レポートの見え方」

RLSはレポートに表示する行を絞り込む機能であり、データベースそのものへのアクセス権限を変更する機能ではありません。元のSalesテーブルのデータは削除も分割もされず、そのままモデルの中に存在し続けます。Power BIがレポートを描画するタイミングで「このユーザーにはこの条件でフィルターをかける」と判断し、見せる行だけを絞り込んでいるにすぎません。誰がSQL Serverへ直接接続できるかといったデータベース側のアクセス制御とは、まったく別の話だと理解しておきましょう。

RLSはロールという単位で定義します。ロールには「どのテーブルに」「どんな条件のフィルターをかけるか」をDAXの論理式で登録し、Power BI Serviceで実際のユーザーやセキュリティグループをロールに割り当てます。同じレポートに対して、ロールを割り当てられたユーザーだけがフィルター後の行を見ることになります。

割り当てられたロール 適用されるフィルター条件 見える範囲
ロールなし（管理者など） フィルターなし 全国すべての売上
東日本担当 Customers[Region] = "東日本" 東日本の顧客に紐づく売上のみ
西日本担当 Customers[Region] = "西日本" 西日本の顧客に紐づく売上のみ

CustomersテーブルにフィルターをかけるだけでSalesの見える行まで絞り込まれるのはなぜでしょうか。理由は第5章で学んだフィルターは「1」側から「多」側へ流れるという性質にあります。Customers（1）からSales（多）へリレーションが正しく張られていれば、顧客を絞り込むフィルターは自動的に売上明細にも伝わります。RLSも通常のスライサーやフィルターと同じ、モデルのフィルターの仕組みに乗っているだけなのです。

11.3 RLSの作り方

RLSはPower BI Desktopでロールを定義し、Power BI Serviceでユーザーを割り当てるという2段構えで設定します（現在は Power BI Service 上でロール自体を定義することもできますが、本ガイドでは第2章から使ってきた Desktop での手順で説明します）。「東日本担当」ロールを例に、手順を確認しましょう。

  1. 1 Power BI Desktopで対象の.pbixを開き、モデリング → ロールの管理を選ぶ（バージョンにより名称やリボンの位置が異なる場合があります）。
  2. 2 ロールの作成で名前を付ける（例: 「東日本担当」）。あとで誰を割り当てたか分かるよう、具体的な名前にする。
  3. 3 フィルターをかけたいテーブル（Customers）を選び、DAXの論理式を入力する。式の結果がTRUEになる行だけが、そのロールに見える。
  4. 4 ロールとして表示を使い、自分がそのロールになったつもりでレポートを開き、見える行が意図どおり絞り込まれているかDesktop上で検証する。
  5. 5 Power BI Serviceに発行したあと、セマンティックモデルのセキュリティ設定を開き、作成したロールに実際のユーザーやセキュリティグループを割り当てる。

手順3で入力するDAXの論理式が、RLSの心臓部です。Customersテーブルを東日本だけに絞る式は次のようになります。

ロールのフィルター式（Customersテーブル） 
// 東日本担当ロール: Region列が「東日本」の行だけを許可する
[Region] = "東日本"

西日本担当ロールなら[Region] = "西日本"とするだけです。テーブルとロールの組み合わせを増やせば、地域だけでなくカテゴリ担当や店舗担当といった軸にも応用できます。

ロールを地域の数だけ手作業で追加するのではなく、ログインしているユーザー自身の情報を使って自動的に絞り込む方法もあります。これを動的RLSと呼びます。たとえば、DAXのUSERPRINCIPALNAME()関数（現在ログインしているユーザーのメールアドレスを返す）を使い、担当者マスタと突き合わせる形で組み立てます。

動的RLSの考え方（概念例） 
// ログイン中のユーザーのメールと担当者マスタを突き合わせて絞り込むイメージ
[担当者メール] = USERPRINCIPALNAME()

動的RLSは、担当者が増減してもロールを作り直す必要がないという利点がありますが、担当者とメールアドレスを対応づけるマスタの整備が前提になります。入門段階ではまず地域ごとに静的なロールを作る方法を身につけ、担当者数が多く頻繁に入れ替わる現場に出会ったときに動的RLSを検討する、という順番で十分です。

注意: 編集権限を持つ人にはRLSが効かない

セマンティックモデルを編集できる権限を持つ人——つまりワークスペースの管理者・メンバー・共同作成者——には、ロールを割り当ててもRLSは適用されず、全データが見えます。RLSが実際に効くのはビューアーです。「この人には自分の地域だけを見せたい」のであれば、ロールを割り当てるだけでなく、その人のワークスペースロールをビューアーにする（編集権限を外す）必要があります。ここを取り違えると、制限したつもりで全社の数字が見えたままになる事故につながります。

11.4 オンプレミスデータゲートウェイ

Power BI Serviceはクラウド上で動いていますが、みらい商事のSalesデータが入ったSQL Serverは社内ネットワークの中にあり、外部から直接アクセスできません。この「クラウドと社内ネットワークの間の壁」を安全に越えるための中継役がオンプレミスデータゲートウェイです。社内のPCやサーバーにインストールしておくと、Power BI Serviceからの更新要求を受け取り、社内のデータベースに問い合わせた結果を暗号化してクラウドへ送り返します。

flowchart LR A[(社内のSQL Server)] --> B["オンプレミスデータゲートウェイ
社内のPC・サーバーに常駐"] B -->|暗号化された通信| C["Power BI Service
クラウド"] C --> D["スケジュール更新
Salesなどのデータを最新化"] D --> E["利用者がブラウザで最新のレポートを閲覧"]

OneDrive for Business や SharePoint 上のファイル、Azure SQL Database などのクラウド上のデータソースのように、Power BI Service から直接読みに行けるデータだけを使う場合はゲートウェイは不要です。クラウド上のデータベースであれば、社内ネットワークを経由しないためゲートウェイなしでスケジュール更新できます。一方、社内データベース・社内ファイルサーバー・手元の PC 上のファイルなど、Power BI Service から直接アクセスできない場所にあるデータを扱う場合は、スケジュール更新でも DirectQuery・Live 接続でもゲートウェイが必要になります。ゲートウェイには、用途に応じて2つのモードが用意されています。

比較する点 標準モード 個人用モード
主な用途 組織で共有して使う本番運用の中継役 自分のレポートのスケジュール更新専用
共有 複数人・複数レポートで共有できる。管理者がまとめて管理する 自分だけが使う。他のユーザーと共有できない
対応する接続方法 Import・DirectQuery・Live接続など幅広く対応 Importのスケジュール更新のみ
可用性 複数台をクラスター化して冗長化できる 1台のみ。そのPCが起動していないと更新できない
向いているケース 部署・全社で継続的に使う本番運用 個人の検証や小規模な一時利用

注意: ゲートウェイが止まると更新も止まる

ゲートウェイをインストールしたPCの電源が切れていたり、サービスが停止していたりすると、そのゲートウェイを経由するスケジュール更新はすべて失敗します。個人用モードを自分のノートPCに入れている場合はとくに起こりやすい落とし穴です。本番運用では、常時起動しているサーバーに標準モードのゲートウェイを入れておくのが基本です。

11.5 スケジュール更新の運用

第10章で触れたとおり、発行したセマンティックモデルはスケジュール更新を設定すれば、決まった時刻に自動でデータを最新化できます。更新できる回数はライセンスによって異なります（執筆時点では Pro は1日あたり数回まで、Premium・Fabric容量ではより高頻度、という程度に押さえておけば十分です。上限や提供条件は変更されることがあるため、実際の運用前に最新の公式情報を確認してください）。業務の締め時刻に合わせて頻度を決めます。ただし、スケジュール更新は「設定すれば終わり」ではなく、止まっていないかを日常的に見守る運用が欠かせません。

更新が失敗する原因は多岐にわたりますが、新人SEがまず押さえておくべき代表的なパターンは次の4つです。

症状 よくある原因 対処のヒント
更新失敗の通知メールが届く データソースの資格情報（パスワード）が期限切れ・変更された セマンティックモデルの設定で資格情報を登録し直す
ある日から数字が更新されない オンプレミスデータゲートウェイが停止・オフラインになっている ゲートウェイの状態を確認し、常時起動のマシンに置く
エラーに列名やテーブル名が出る 接続先の表構造が変わった（列の追加・削除・改名） Power Queryの定義を修正し、動作確認のうえ再発行する
更新に時間がかかりタイムアウトする データ量が増えすぎた、不要な列・行まで読み込んでいる Power Queryで不要な列・行を早い段階で削減する

いずれの場合も、まず確認すべき画面は共通しています。セマンティックモデルの設定画面にある更新履歴です。ここには、いつ・成功したか失敗したか・どのくらい時間がかかったか・失敗した場合はどんなエラーメッセージだったかが記録されています。「レポートの数字がおかしい」と言われたら、まずこの更新履歴を確認する習慣をつけましょう。

失敗通知は誰に届くか

スケジュール更新が失敗すると、既定ではセマンティックモデルの所有者（発行した人）にメール通知が届きます。所有者が退職・異動した場合に通知が誰にも届かなくなるのは、まさに次の11.6で扱う「作成者が1人だけ」の問題そのものです。

11.6 運用でつまずきやすい点

機能の使い方を覚えても、チームで長く運用していくと別の壁にぶつかります。ここでは、新人SEが配属先で最初に遭遇しやすい3つの落とし穴と、その対策を整理します。

つまずきやすい点 何が起きるか 対策
作成者が1人だけに集中する（属人化） その人が休む・異動すると、更新も修正もできなくなる ワークスペースに複数人を共同作成者として登録しておく
.pbixの版が分からなくなる 「どれが最新か」を探すのに毎回時間がかかり、古い版を配ってしまう事故も起きる 保存場所とファイル名の規則をチームで統一する（将来はPBIP化も選択肢、第12章で紹介）
個人用ワークスペースで作り込んでしまう 本人しかアクセスできず、他のメンバーへの共有や引き継ぎができない 早い段階で共有ワークスペースに移す（第10章の「個人用に作り込まない」原則）

この3つに共通するのは、「1人・1台・1個人フォルダ」に閉じた状態を早めに解消するという考え方です。作り始めた直後は自分1人で完結しているほうが速く感じますが、レポートが業務で使われ始めた瞬間から、それは「引き継げない資産」というリスクに変わります。RLSやゲートウェイの設定と同じく、アクセス制御・運用の整備も「レポートを本番で使い始める前に済ませておくもの」だと意識しておきましょう。

やってみよう 11-1: 「東日本の担当者」ロールを作って見え方を確認する

第5章で作ったモデルを使い、地域で絞り込むRLSを実際に設定して、見える行が変わることを自分の目で確認しましょう。

手順

  1. 1 Power BI Desktopでモデリング → ロールの管理を開き、「東日本担当」という名前のロールを新規作成する。
  2. 2 Customersテーブルを選び、フィルター式に[Region] = "東日本"と入力する。
  3. 3 レポートビューに戻り、ロールとして表示で「東日本担当」を選択する。カテゴリ別売上のグラフやカードの数字が、切り替える前と比べてどう変わるかを確認する。
  4. 4 同じ手順で「西日本担当」ロールも作成し、ロールとして表示を切り替えながら、見える売上金額の合計がロールごとに異なることを比べる。
  5. 5 最後にロールとして表示を解除し、フィルターなしの状態（全国の合計）に戻ることを確認する。

理解度確認クイズ

  1. Q1. RLS（行レベルセキュリティ）は何を制御する機能ですか。データベースへのアクセス権限との違いも含めて説明してください。

    回答を表示

    RLSは、同じレポートを開いても見る人によって表示される行を変える機能で、ロールに登録したDAXフィルター式に基づいて表示する行を絞り込みます。あくまでレポートの見え方（表示）を制御するものであり、SQL Serverなどデータベース本体への接続・アクセス権限を変更するものではありません。元のテーブルのデータ自体は変わらず存在し続けます。

  2. Q2. オンプレミスデータゲートウェイが必要になるのはどのようなケースですか。

    回答を表示

    社内のSQL Serverや社内ファイルサーバー、手元のPC上にあるExcel／CSVファイルなど、Power BI Serviceから直接アクセスできない場所にあるデータをServiceから更新したり、DirectQuery・Live接続で参照したりするときに必要です。クラウドとオンプレミス環境の間の壁を安全に越える中継役の役割を果たします。逆に、OneDrive for BusinessやSharePoint上のファイル、Azure SQL Databaseなどのクラウド上のデータソースだけを使う場合は不要です。要否を決めるのはファイルの形式ではなく、「Power BI Serviceから直接届く場所にあるかどうか」です。

  3. Q3. スケジュール更新が失敗する代表的な原因を2つ挙げてください。

    回答を表示

    代表的なのは、データソースの資格情報（パスワード）が期限切れ・変更されたことと、オンプレミスデータゲートウェイが停止・オフラインになっていることです。ほかにも、接続先の表構造の変更やデータ量の増加によるタイムアウトが原因になることもあります。セマンティックモデルの更新履歴を確認することで、どの原因かを切り分けられます。
