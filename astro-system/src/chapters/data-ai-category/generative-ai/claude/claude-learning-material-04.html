ホーム Claude入門 第4章
第4章 所要時間: 約25分

より良い結果を得るために

Claude を使い始めると、期待していたものとは少し違う回答が返ってくる場面に出会うことがあります。これはごく自然なことであり、アプローチを磨いていくチャンスでもあります。この章では、初心者がつまずきやすい5つの課題とその対処法、そして「反復しながら改善する」という考え方を身につけます。

この章で学ぶこと

  • AI 利用初期によく起きる5つの課題を識別し、それぞれの対処法を適用できる
  • 「最初のプロンプトは会話の出発点」という反復前提のマインドセットを説明できる
  • Claude の出力に含まれうる誤情報を検証する手立てを挙げられる
  • やり直し（新しいチャットの開始）を選ぶべきタイミングを判断できる

4.1 よくある5つの課題とその対処法

Claude の回答が「期待と少し違う」と感じたとき、多くの場合は Claude の性能不足ではなく、プロンプトに足りない情報があることが原因です。ここでは代表的な5つの課題を、原因と対処法とあわせて確認していきます。

課題 何が起きているか 試してみること
①回答が一般的すぎる プロンプトに、あなたの具体的な状況についての文脈が十分に含まれていない 想定読者・役割・制約などの詳細を追加する
②回答が長すぎる／短すぎる Claude が適切な長さを推測しているだけ 「2段落の要約」「100語以内」のように具体的に指定する
③指定した形式に従わない 「何を」求めているかは理解できても「どのように」提示してほしいかまでは伝わっていない 説明だけでなく実例を見せ、構成を明示する
④自信満々に見えて誤っている情報 特に具体的な事実やニッチな話題で、もっともらしいが誤った情報を生成することがある 重要度の高い作業では主要な事実を別途検証。情報源・確信度の提示を求める、web検索を有効にする
⑤トーンが合わない デフォルトは親切かつプロフェッショナルなトーンだが、それがニーズに合わないことがある 望むトーンを平易な言葉で伝え、文章例を示す

課題①: 文脈を足して具体化する

もっとも起きやすいのがこの課題です。同じ依頼でも、文脈の有無で結果は大きく変わります。

悪いプロンプト例 
プロジェクトの遅延についてメールを書いて
良いプロンプト例 
ソフトウェア統合が2週間遅れることを
エンタープライズ顧客に説明するメールを書いてください。
これまで辛抱強く待っていただいていますが、
今回で2度目の遅延です。
丁寧かつ謝罪の意を込めた、
プロフェッショナルなトーンでお願いします。

後者には「誰に（エンタープライズ顧客）」「何が起きたか（2週間遅延・2度目）」「どんなトーンで（丁寧・謝罪・プロフェッショナル）」という文脈の3点セットが入っています。これは第2章で学んだプロンプトの3要素（状況・タスク・ルール）そのものです。

課題③: 説明ではなく実例で構成を示す

形式のずれも初心者がよく直面する課題です。「見やすくして」だけでは Claude はどんな見た目を望んでいるかを推測するしかありません。

悪いプロンプト例 
この提案を分かりやすくまとめて
良いプロンプト例 
この提案を「背景」「提案内容」「期待効果」の
3セクションに分け、各セクションに
太字の見出しをつけた箇条書きでまとめてください。

課題④は特に注意して読んでください

Claude は、特に具体的な事実やニッチな話題について、もっともらしいが誤った情報を、自信ありげな口調のまま生成してしまうことがあります。これは Claude に限らず AI 全般が持つ性質です。「Claude は間違えない」と思い込まず、重要度の高い作業では主要な事実を別途検証する習慣を持ちましょう。情報源や確信度の提示を求めたり、web検索を有効にして最新情報に基づかせたりするのも有効な対処法です。

課題⑤: トーンは言葉と文例で伝える

Claude のデフォルトは親切かつプロフェッショナルなトーンです。「もっと会話調にしてください」「権威があり、フォーマルな雰囲気にしてください」のように平易な言葉で望むトーンを伝えるだけでも変化しますが、希望するスタイルの文章例を1つ見せるとさらに精度が上がります。

4.2 症状から探す: トラブルシューティング決定木

回答に違和感があるとき、どの課題に当てはまるかをすぐに特定できると、対処が速くなります。次の決定木を、困ったときのチェックリストとして使ってください。

想定読者・役割・制約を追加"] B -->|"長さが合わない"| D["長さの指定漏れ
文字数・段落数を明示"] B -->|"形式が違う"| E["構成の伝達不足

事実を検証し出典・確信度を確認"] B -->|"トーンが違う"| G["トーン未指定
望むトーンと文例を伝える"] C --> H["プロンプトを修正して再送信"] D --> H E --> H F --> H G --> H H --> I{"改善したか？"} I -->|"はい"| J["そのまま進める"] I -->|"いいえ・話がそれた"| K["新しいチャットで
明確なプロンプトから始める"]

ポイントは、症状（一般的すぎる・長さ・形式・情報・トーン）から原因を逆算し、原因に対応する具体的な指示を1つ足すという手順を機械的に繰り返すことです。慣れないうちはこの表と決定木を手元に置きながら進めるとよいでしょう。

4.3 反復しながら改善するというマインドセット

Claude を使う上でもっとも重要な意識の転換のひとつは、「最初のプロンプトで完璧な結果が得られることはめったにない」と理解することです。それで問題ありません。最初のプロンプトは、一発勝負のリクエストではなく会話の出発点だと考えましょう。

Claude を効果的に使いこなす人は、次のようなことをしています。

  • 最初の下書きを出発点として扱う。Claude が生成したものを確認し、うまくいっている点とそうでない点を見極めたうえで、改善していく。
  • 具体的なフィードバックを伝える。「もっと短くして」でも悪くはないが、「最初の2段落を削除して、結論部分をもっと行動につながる内容にして」のように伝えるほうが効果的。
  • やり直すタイミングを見極める。会話が本筋からそれてしまった場合、軌道修正を試みるより、もっと明確なプロンプトで新しいチャットを始めたほうが早いこともある。
flowchart LR A["プロンプトを送る"] --> B["Claude の出力"] B --> C["評価する"] C -->|"改善点がある"| D["具体的なフィードバックを伝える"] D --> A C -->|"本筋からそれた"| E["新しいチャットで
明確なプロンプトから始める"] C -->|"十分に良い"| F["完成・活用する"]

「もっと短く」より「どこを削るか」

フィードバックは抽象的な感想（もっと短く／もっと良く）より、具体的な操作（最初の2段落を削除する／結論を行動につながる内容にする）のほうが Claude に正確に伝わります。第3章で学んだフォローアップ・フィードバック・方向修正・プロンプト編集の4手段を、この意識で使い分けてみてください。

なお、この反復のマインドセットは次章で学ぶ Discernment（見極め）とDiligence（注意深さ）という力の実践そのものです。トラブルシューティングは特別なテクニックではなく、Claude と協働するうえでの基本動作だと捉えておきましょう。

やってみよう 4-1: つまずきをテクニックで直す

第3章で作成したファイル要約やフィードバックのやり取りを振り返り、5つの課題のうち実際に遭遇したもの（または今後起こりそうなもの）を1つ選んで、対応テクニックを使ってプロンプトを書き直してみましょう。

手順

  1. 1 4.1 の表から、直近の Claude とのやり取りで実際に感じた課題を1つ選ぶ（一般的すぎる／長さ／形式／誤情報／トーンのいずれか）。
  2. 2 元のプロンプトをそのまま Claude に送り、出力を控えておく（Before）。
  3. 3 4.1・4.2 で紹介した対処法（文脈追加／長さ指定／実例で構成を示す／検証を求める／トーン指定）をプロンプトに反映し、再送信する（After）。
  4. 4 Before と After を見比べ、どの一言の追加が結果を変えたのかをメモに残す。

ヒント: 一度にすべての要素を直そうとせず、まずは1つの対処法だけを足して結果を比べると、何が効いたのかが分かりやすくなります。

理解度確認クイズ

  1. Q1. 回答が「一般的すぎる」と感じたとき、何が原因で、どう対処すればよいですか。

    回答を表示

    プロンプトに、自分の具体的な状況についての文脈が十分に含まれていないことが原因です。想定読者・役割・制約などの詳細を追加することで解決できます（例: 「メールを書いて」ではなく、顧客属性・遅延の経緯・望むトーンまで指定する）。

  2. Q2. Claude の出力に「自信満々に見えるが誤っている情報」が含まれることがあるのはなぜですか。また、どう対処すればよいですか。

    回答を表示

    Claude は、特に具体的な事実やニッチな話題について、もっともらしいが誤った情報を自信ありげな口調のまま生成することがあります。重要度の高い作業では主要な事実を別途検証し、情報源や確信度の提示を求めたり、web検索を有効にしたりすることが対処法です。

  3. Q3. 「最初のプロンプトは会話の出発点」とはどういう意味ですか。また、会話が本筋からそれてしまったときはどうするのがよいですか。

    回答を表示

    最初のプロンプトで完璧な結果が得られることはめったにないため、出力を確認しながら具体的なフィードバックで改善していく前提で使う、という考え方です。会話が本筋からそれてしまった場合は、その場で軌道修正しようとするより、明確なプロンプトで新しいチャットを始めたほうが早いことがあります。
