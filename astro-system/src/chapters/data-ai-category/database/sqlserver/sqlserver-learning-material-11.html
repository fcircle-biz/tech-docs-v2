インデックスと性能の基礎

クエリが遅いとき、原因の多くは「インデックスが使われていない」ことにあります。この章では、本の索引にたとえてインデックスの仕組みを理解し、クラスター化・非クラスター化インデックスの違い、実行プランの読み方、インデックスが効かなくなる書き方までを学びます。

この章で学ぶこと

  • インデックスがなぜ検索を速くするのか、身近な例で説明できる
  • クラスター化インデックスと非クラスター化インデックスの違いを説明できる
  • CREATE INDEXでインデックスを作成し、複合インデックスとINCLUDE列を使い分けられる
  • 実行プランを見て、Index ScanとIndex Seekの違いを判断できる
  • インデックスが効かなくなる書き方（関数適用・前方一致でないLIKE・暗黙の型変換）を避けられる

11.1 インデックスとは

インデックス（索引）は、本の巻末にある「索引」や電話帳と同じ役割をデータベースの中で果たします。索引がない分厚い専門書で「トランザクション」という単語を探すとき、私たちは最初のページから1枚ずつめくって探す（全ページ探索）しかありません。しかし巻末の索引を見れば「トランザクション → 245ページ」とすぐに分かり、そのページへ直行できます。

SQL Server も同じです。学習用データベース SampleShop の Orders テーブルに数十万行のデータがあるとして、WHERE CustomerId = 123 で検索したとします。インデックスが無ければ SQL Server は先頭から1行ずつすべての行を読んで条件に合うか確認します。これをスキャン（Scan）と呼びます。インデックスがあれば、索引を使って該当行だけに直接たどり着けます。これをシーク（Seek）と呼びます。

操作 本にたとえると SQL Serverでの動き
スキャン（Scan） 最初のページから1枚ずつめくって探す テーブル（またはインデックス）の全行を読む
シーク（Seek） 巻末の索引で当たりをつけて直行する インデックスを使い必要な行だけに直接アクセスする

ただし索引にも代償があります。本の索引を最新に保つには、ページが増えるたびに索引ページも書き直す必要があります。データベースのインデックスも同様に、INSERT・UPDATE・DELETE のたびに更新され、書き込みが遅くなり、ディスク容量も余分に消費します。「インデックスは読み取りを速くする代わりに、書き込みと容量を犠牲にするトレードオフ」だと覚えておきましょう。

ヒント: インデックスは多いほど良い、は誤解

「検索が速くなるならたくさん作ればいい」と考えがちですが誤りです。テーブルへの書き込みが発生するたびに、そのテーブルに紐づく関係するインデックスが更新対象になります（行の追加・削除は基本的に全ての非クラスター化インデックスが対象、更新は変更した列を含むインデックスが対象です）。使われないインデックスは、容量とメンテナンスコストだけを増やす「保守されない索引」になってしまいます（11.6節で詳しく扱います）。

11.2 クラスター化インデックスと非クラスター化インデックス

SQL Server のインデックスには2種類あります。この違いを理解することが、この章全体の土台になります。

クラスター化インデックス

リーフレベル（末端）がデータ行そのもので、データがキーの順に論理的に整理される仕組み。国語辞典が五十音順に並んでいるイメージ。1テーブルに1つだけ作れる。

非クラスター化インデックス

データ本体とは別に作る「索引」。索引語＋ページ番号のように、キーと「データ行への参照」を持つ。複数作成可能。

より正確に言うと、クラスター化インデックスは、そのリーフレベル（末端）がデータ行そのもので構成され、データがインデックスキーの順に論理的に整理される仕組みです。国語辞典が五十音順に並んでいるイメージに近いですが、ディスク上で物理的に連続して並んでいることまでは保証されません。ページ分割やデータの追加・更新・削除を繰り返すと、論理的な並び順と実際の格納位置にズレが生じます（これを断片化と呼びます）。だからこそ 11.6節で扱うメンテナンスが必要になります。

SQL Server では、そのテーブルにまだクラスター化インデックスが存在せず、かつ NONCLUSTERED を明示していない場合に、主キー（PRIMARY KEY）を定義すると既定でその列にクラスター化インデックスが作成されます（第5章参照）。すでに別の列にクラスター化インデックスが存在する場合や、PRIMARY KEY NONCLUSTERED と明示した場合は、主キーは非クラスター化インデックスとして作成されます。クラスター化インデックスが1つも無いテーブルはヒープ（Heap）と呼ばれ、データが特定の順序を持たずに格納されます。

primary_key_nonclustered.sql 
-- 例：主キーをあえて非クラスター化インデックスとして作成する
CREATE TABLE dbo.Orders (
    OrderId    INT  NOT NULL,
    CustomerId INT  NOT NULL,
    OrderDate  DATE NOT NULL,
    CONSTRAINT PK_Orders PRIMARY KEY NONCLUSTERED (OrderId)
);

-- 明示的に作成する、といった運用で使う

重要ポイント

非クラスター化インデックスでヒットしても、SELECT * のようにインデックスに含まれない列が必要な場合、SQL Server は索引からデータ本体（クラスター化インデックスまたはヒープ）へ改めて行を取りに行く動作が発生します。この追加アクセスが多いと性能低下の原因になります（11.4節）。

発展: 用語 — Key Lookup / RID Lookup

非クラスター化インデックスだけでは足りない列を取りに、クラスター化インデックス側へ追加で行を取りに行く動作をKey Lookupと呼びます。同じ動作のうち、クラスター化インデックスが無いテーブル（ヒープ）で行の物理位置を辿って取りに行くものはRID Lookupと呼びます。どちらも実行プラン上に演算子として表示されます（11.4節）。

11.3 インデックスを作る

非クラスター化インデックスは CREATE NONCLUSTERED INDEX 文で作成します。Orders テーブルに対して、よく CustomerId で絞り込む検索が多いなら、次のように作成します。

create_index_basic.sql 
-- CustomerIdで絞り込む検索を高速化する
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId
ON dbo.Orders (CustomerId);

複数の列を組み合わせた複合インデックス（Composite Index）も作成できます。このとき重要なのが列の順番です。列の順番は、実際のクエリパターンをもとに決めるのが基本です。Microsoft のインデックス設計ガイドラインが示す基本方針は次のとおりです。

  • WHERE の比較条件（=、>、<、BETWEEN など）や JOIN の結合条件で使われる列を先頭に置く
  • 残りの列は、値の種類が多い（重複が少ない）順に並べる
  • ORDER BY の並び順と一致させると、実行プランから並べ替え（Sort）処理を省ける場合がある

なお、「等値条件（=）の列を先頭に、範囲条件（>・<・BETWEEN）の列を後ろに置く」という言い方も実務ではよく聞きますが、これはMicrosoft公式の推奨事項ではなく、一般に知られている実務上の経験則です。公式ガイドラインの本質は「比較条件で使う列を先頭に、残りは値の種類が多い順に並べる」という考え方にあります。

注意: 先頭列が条件に含まれないと効かない

複合インデックスは先頭列がクエリの条件に含まれて初めて効果を発揮します。たとえば (CustomerId, OrderDate) の順で作成したインデックスは WHERE CustomerId = 123 を含む検索には使えますが、WHERE OrderDate >= '2025-01-01' のように OrderDate だけで絞り込む検索には使われません。

create_index_composite.sql 
-- 複合インデックス：CustomerId・OrderDateともに比較条件で使う列。
-- ここではCustomerIdの方が値の種類が多い(重複が少ない)と考え先頭に置く
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId_OrderDate
ON dbo.Orders (CustomerId, OrderDate);

-- このインデックスが効きやすいクエリの例
SELECT OrderId, OrderDate, Quantity
FROM dbo.Orders
WHERE CustomerId = 123
  AND OrderDate >= '2025-01-01';

さらに INCLUDE 句を使うと、検索条件には使わないが結果として取得したい列をインデックスに「間借り」させられます。これにより非クラスター化インデックスだけで必要な列がすべてそろい、データ本体へ追加で行を取りに行く動作が不要になるため、この状態をカバリングインデックス（Covering Index）と呼びます（この追加動作については 11.2節の発展欄を参照）。

create_index_covering.sql 
-- OrderDate・ProductId・QuantityをINCLUDEし、データ本体への追加アクセスを不要にする
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId_Covering
ON dbo.Orders (CustomerId)
INCLUDE (OrderDate, ProductId, Quantity);

ヒント: 既存のインデックスを確認する

SSMS のオブジェクトエクスプローラーで Orders テーブル配下の「インデックス」フォルダーを開くと一覧できます。クエリで確認したい場合は EXEC sp_helpindex 'dbo.Orders'; でも一覧が得られます。

11.4 実行プランを読む

「インデックスが実際に使われているか」を確認する方法が実行プラン（Execution Plan）です。SSMS のクエリエディタで、ツールバーの「実際の実行プランを含める」（Ctrl+M）を有効にしてからクエリを実行すると、結果グリッドの隣に図で処理の流れが表示されます。

演算子 意味 速さの目安
Index Seek インデックスを使い、必要な行だけに直接アクセスする 速い（理想形）
Index Scan インデックスは使うが、端から端まで全件読む 行数が多いと遅くなる
Table Scan インデックスがない（ヒープの）テーブルを全件読む 大きい表では特に遅い

各演算子の下にはコストが相対的な割合（%）で表示され、1つのクエリのプラン内で合計が100%になります。バッチに複数のクエリを含めた場合は、プランの上部に「バッチに対するクエリ コスト（相対値）」がクエリごとに表示され、こちらの合計が100%になります。演算子にマウスを重ねると、推定行数・実際の行数・アクセスしている列（例: Seek Predicate）などの詳細が確認できます。

このほか、非クラスター化インデックスだけでは列が足りず、データ本体へ追加で行を取りに行く演算子が表示されることもあります（詳しくは 11.2節の発展欄を参照）。

重要ポイント

初心者はまず「Scanか、Seekか」だけを見る習慣をつけましょう。行数が多いテーブルに対する検索で Index Scan や Table Scan が出ていたら、「インデックスが無い」または「11.5節で扱う理由でインデックスが使えていない」可能性を疑います。

11.5 インデックスが効かない書き方

インデックスを作っても、WHERE 句の書き方によっては使われないことがあります。WHERE 句の中で列に関数を使うと、インデックスの検索（Seek）が使えなくなり、全体を読む（Scan）動きになりやすくなります。ここでは代表的なパターンを見ていきます。

発展: 用語 — SARGable

インデックスの検索（Seek）が使える形の条件式のことをSARGable（サーガブル、Search ARGument able の略）と呼びます。この節で紹介する「効きにくくなる書き方」は、裏を返せば「非SARGableな条件にしてしまう書き方」です。

(1) 列に関数を適用している

OrderDate 列に YEAR() 関数をかけると、SQL Server はインデックスのキー値と直接比較できなくなり、行ごとに関数を計算してから比較する必要が生じます。その結果、OrderDate にインデックスがあっても Seek が使えず、Scan になりやすくなります。

index_not_used_function.sql 
-- ビフォー：列に関数を適用（インデックスが効きにくい）
SELECT OrderId, CustomerId, OrderDate
FROM dbo.Orders
WHERE YEAR(OrderDate) = 2025;

-- アフター：範囲条件に書き換える（インデックスの検索(Seek)が使える形に）
SELECT OrderId, CustomerId, OrderDate
FROM dbo.Orders
WHERE OrderDate >= '2025-01-01'
  AND OrderDate <  '2026-01-01';

(2) 前方一致でない LIKE

LIKE '山田%' のように先頭が固定されていれば、インデックスは「山田」から始まる範囲を Seek できます。しかし LIKE '%山田%' のように先頭がワイルドカード（%）だと、どこから一致するか分からないため全件を確認するしかなく Scan になります。

index_not_used_like.sql 
-- ビフォー：前方一致でないLIKE（インデックスが効かない）
SELECT CustomerId, CustomerName
FROM dbo.Customers
WHERE CustomerName LIKE N'%山田%';

-- アフター：前方一致に業務要件を変更できるなら効くようになる
SELECT CustomerId, CustomerName
FROM dbo.Customers
WHERE CustomerName LIKE N'山田%';
-- 中間一致がどうしても必要な場合は全文検索(Full-Text Search)の
-- 利用も検討する

(3) 暗黙の型変換

比較する両辺のデータ型が異なると、SQL Server はどちらかを暗黙的に変換します。このとき変換が列側にかかると、その列のインデックスを検索（Seek）に使えなくなり、Scanになりやすくなります。たとえば列が varchar 型なのに比較値を N'...'（Unicode）で書くと、nvarchar の方がデータ型の優先順位が高いため列側が変換対象になります。次の例は、本ガイドの Customers.CustomerName（NVARCHAR）が仮に varchar 型だった場合を想定したものです。

index_not_used_conversion.sql 
-- ビフォー：CustomerNameが仮にvarchar列だとしてN'...'で比較
-- （型変換が列側にかかりインデックスが効きにくくなる）
SELECT CustomerId, CustomerName
FROM dbo.Customers
WHERE CustomerName = N'山田太郎';

-- アフター：列の型に合わせてリテラル/パラメータの型を揃える
SELECT CustomerId, CustomerName
FROM dbo.Customers
WHERE CustomerName = '山田太郎';

注意

アプリケーション側でパラメータの型を明示的に指定していないと、想定と違う型でSQL Serverに渡され、意図せず暗黙の型変換が発生することがあります。実行プランで演算子に「!」の警告アイコンが付いていたら、型変換や統計情報の古さを疑いましょう。

11.6 統計情報とメンテナンス

SQL Server は「この条件に一致する行はだいたい何件か」を予測するために統計情報（Statistics）を使います。統計情報は列の値の分布を要約したデータで、クエリオプティマイザが Seek と Scan のどちらを選ぶか、テーブルをどの順序で結合するかを判断する材料になります。既定では AUTO_CREATE_STATISTICS・AUTO_UPDATE_STATISTICS が有効なため、統計情報は自動的に作成・更新されます。手動で最新化したい場合は次のように実行します。

update_statistics.sql 
-- Ordersテーブルの統計情報を手動で更新する
UPDATE STATISTICS dbo.Orders;

もう1つの重要な運用作業が断片化（Fragmentation）への対処です。データの追加・更新・削除が繰り返されると、インデックスのページが物理的にバラバラの場所へ分散し、本来の並び順と実際の格納順にズレが生じます。断片化率は sys.dm_db_index_physical_stats で確認でき、目安として以下のように対処します。

断片化率の目安 対処コマンド 特徴
5% 〜 30% ALTER INDEX ... REORGANIZE 既存ページを軽く並べ替える。処理中もテーブルを使い続けられる
30% 超 ALTER INDEX ... REBUILD インデックスを作り直す。より効果的だが負荷は大きい（Enterprise Editionは ONLINE=ON でロックを避けやすい）

ヒント: インデックスの作りすぎに注意

INSERT・DELETE は、そのテーブルに設定されたすべての非クラスター化インデックスが更新対象になります（UPDATE の場合は、変更した列をキーまたは INCLUDE 列に含むインデックスだけが対象です）。インデックスが10個あれば、書き込みのたびに最大10個の構造を保守することになり、容量・バックアップ時間・統計更新の負荷も増えます。「使われていないインデックス」は定期的に見直して削除しましょう。

11.7 PostgreSQLとの違い

インデックスと実行プランの考え方は SQL Server と PostgreSQL で大きく異なる部分です。とくに「クラスター化インデックス」の扱いは根本的に違うので注意しましょう。

PostgreSQLとの違い（インデックスと実行プラン）

観点 SQL Server PostgreSQL
クラスター化インデックス 概念があり、条件を満たせば主キーに既定で作成される 概念がなく、テーブルは常にヒープ構造
データの並び順維持 クラスター化インデックスが論理的な並び順を常に維持 CLUSTER コマンドで一度だけ並べ替え可能（以後は維持されない）
実行プランの確認 SSMSのグラフィカルプラン／SET SHOWPLAN_ALL EXPLAIN ／ EXPLAIN ANALYZE
統計情報の更新 自動更新＋UPDATE STATISTICS autovacuumが自動実行＋ANALYZE
特殊なインデックス 標準的なB-treeが中心 部分インデックス(WHERE付き)・式インデックス・GIN/GiSTなど多様
カバリングインデックス INCLUDE 列（SQL Server 2005〜） INCLUDE 列（PostgreSQL 11〜、考え方は共通）
断片化対策 REBUILD / REORGANIZE VACUUM / REINDEX

PostgreSQLでは「テーブルは常にヒープ」という前提があるため、SQL Serverの「主キー＝クラスター化インデックス」という感覚のまま設計すると混乱しがちです。PostgreSQLでは代わりに部分インデックスや式インデックスなど、条件を絞った柔軟なインデックス設計がよく使われます。

やってみよう 11-1: 実行プランがScanからSeekに変わる様子を確認する

SampleShopの Orders テーブルに非クラスター化インデックスを作る前後で、実行プランがどう変化するかを実際に確認します。

手順

  1. 1 SSMSでSampleShopに接続し、新しいクエリウィンドウを開く。ツールバーの「実際の実行プランを含める」（Ctrl+M）をオンにする。
  2. 2 SELECT OrderId, OrderDate, Quantity FROM dbo.Orders WHERE CustomerId = 5; を実行し、「実行プラン」タブで演算子を確認する（Index Scan または Table Scan になっているはず）。
  3. 3 CREATE NONCLUSTERED INDEX IX_Orders_CustomerId ON dbo.Orders (CustomerId); を実行してインデックスを作成する。
  4. 4 手順2と同じ SELECT 文をもう一度実行する。演算子が Index Seek に変わり、推定コストが下がっていることを確認する。
  5. 5 確認できたら、後片付けとして DROP INDEX IX_Orders_CustomerId ON dbo.Orders; でインデックスを削除しておく。

ねらい: インデックスの効果は説明を読むだけでは実感しにくいものです。同じクエリの実行プランが目に見えて変わる体験を通じて、「Scan/Seek」という言葉の意味を体で覚えることが目的です。

理解度確認クイズ

  1. Q1. 実行プランに表示される「Index Seek」と「Index Scan」は、それぞれどのような処理を意味しますか。違いを説明してください。

    回答を表示

    Index Seek は、インデックスを使って必要な行だけに直接アクセスする処理で高速です。Index Scan は、インデックスは使うもののキー値を先頭から順に全件読んでいく処理で、行数が多いほど遅くなります。

  2. Q2. WHERE YEAR(OrderDate) = 2025 という書き方は、OrderDate にインデックスがあっても効きにくいと言われます。なぜですか。

    回答を表示

    WHERE句の中で列に関数(YEAR)を適用すると、SQL Serverはインデックスのキー値をそのまま比較できず、行ごとに関数の計算結果を求めてから条件判定する必要が生じます。そのためインデックスを使ったSeekが使えず、Scanになりやすくなります。範囲条件（OrderDate >= '2025-01-01' AND OrderDate < '2026-01-01'）に書き換えると、インデックスの検索（Seek）が使える形（発展用語ではSARGableと呼びます）になり、インデックスが効くようになります。

  3. Q3. 1つのテーブルに複数作成できるのは、クラスター化インデックスと非クラスター化インデックスのどちらですか。理由も含めて答えてください。

    回答を表示

    非クラスター化インデックスです。クラスター化インデックスは、そのリーフレベル（末端）がデータ行そのもので構成され、データがインデックスキーの順に論理的に整理される仕組みです。1つのテーブルのデータ行が同時に持てる並び順は1通りしかないため、クラスター化インデックスは最大1つしか作成できません。一方、非クラスター化インデックスはデータ本体とは別の構造（キーと行への参照）なので、目的に応じて複数作成できます。
