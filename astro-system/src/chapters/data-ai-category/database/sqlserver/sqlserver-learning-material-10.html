トランザクションとロック

複数の更新を「まとめて成功させるか、まとめて取り消すか」を制御するトランザクションと、複数の利用者が同時にデータへアクセスしても矛盾が起きないようにするロックの仕組みを学びます。分離レベルや READ_COMMITTED_SNAPSHOT、デッドロックへの対処もあわせて理解します。

この章で学ぶこと

  • トランザクションがなぜ必要かを、ACID特性とあわせて説明できる
  • BEGIN TRAN / COMMIT / ROLLBACK を使い、TRY...CATCHで安全に書ける
  • ロックの粒度とブロッキングが起きる仕組みを理解する
  • ブロッキングとデッドロックの違いを説明し、デッドロックへの基本的な対策を挙げられる
  • 分離レベルの違いと、SQL Server と PostgreSQL の同時実行制御の違いを説明できる

10.1 トランザクションとは

銀行振込を例に考えてみましょう。Aさんの口座から1,000円を引き、Bさんの口座に1,000円を足す処理は、SQLで書けば UPDATE 文が2回実行されます。もし1回目の「引く」が成功した直後に、停電やシステム障害で2回目の「足す」が実行されなかったら、1,000円がこの世から消えてしまいます。

これを防ぐのがトランザクションです。複数のSQL文を1つの「ひとまとまりの作業」として扱い、「全部成功したことにする」か「全部なかったことにする」かのどちらかしか許さない仕組みです。「引く」と「足す」の間で処理が止まっても、トランザクションが正しく使われていれば、データベースは振込前の状態に自動的に巻き戻ります。

特性（ACID） 意味
原子性（Atomicity） トランザクション内の処理は「全部成功」か「全部なかったことにする」かのどちらかしかない
一貫性（Consistency） トランザクションの前後で、制約やルールに反したデータが生まれない
分離性（Isolation） 複数のトランザクションが同時に動いても、互いの途中経過が見えず干渉しない
永続性（Durability） 一度コミットされたデータは、その後障害が起きても失われない

用語: ACID

Atomicity（原子性）・Consistency（一貫性）・Isolation（分離性）・Durability（永続性）の頭文字です。SQL Server に限らず、まともなRDBMSであればすべてこの4つを満たすように設計されています。この章の10.3〜10.5は、主に分離性（Isolation）をどう実現するかという話です。

10.2 T-SQLでの書き方

SQL Server は既定で自動コミットモードで動作します。つまり、明示的にトランザクションを開始しない限り、UPDATE や INSERT を1文実行するたびに、その文単独が自動的にコミットされます。複数の文をひとまとめにしたい場合は、BEGIN TRAN（BEGIN TRANSACTION の省略形）で明示的に開始します。

BEGIN TRAN

ここからひとまとまりの作業として扱う、という開始の合図。

COMMIT

ここまでの変更を確定する。以降、変更は他の利用者からも見える。

ROLLBACK

ここまでの変更をすべて取り消し、トランザクション開始前の状態に戻す。

実務では「エラーが起きたら必ずロールバックする」ことを保証するため、TRY...CATCH（第9章）と組み合わせるのが定石です。

この節の Accounts は説明用の仮想テーブルです

「口座から口座へお金を移す」というトランザクションの典型例を示すため、Accounts（口座）というテーブルを使って説明します。これは第5章で作った学習用データベース SampleShop には存在しないテーブルなので、そのまま実行するとエラーになります。ここでは書き方の型を読み取ってください。実際に手を動かす実習は、この章の後半で SampleShop のテーブルを使って行います。

transfer.sql 
-- 振込処理を安全なトランザクションで実行する型
BEGIN TRY
    BEGIN TRAN;
        UPDATE Accounts SET Balance = Balance - 1000 WHERE AccountId = 1;
        UPDATE Accounts SET Balance = Balance + 1000 WHERE AccountId = 2;
    COMMIT TRAN;
END TRY
BEGIN CATCH
    -- @@TRANCOUNTが1以上なら、開いたままのトランザクションが残っている
    IF @@TRANCOUNT > 0
        ROLLBACK TRAN;
    THROW;  -- エラー内容を呼び出し元に伝える
END CATCH;

@@TRANCOUNT は、現在ネストして開いているトランザクションの数を返すシステム関数です。0なら未開始、1以上なら開始中を意味します。また、SET XACT_ABORT ON をバッチの先頭に置くと、実行時エラーが発生した際に SQL Server がトランザクション全体を確実に取り消すようになり、「一部の文だけ失敗して更新が中途半端に残る」事故を防げます。ストアドプロシージャの冒頭ではよく使われる設定です。ただし TRY...CATCH と併用した場合はトランザクションがコミット不可の状態で CATCH に入るだけなので、上の例のようにCATCH内で明示的に ROLLBACK を書くことは省略できません。

10.3 ロックの基本

複数の利用者が同時に同じデータへアクセスしても矛盾が起きないよう、SQL Server はデータへの「鍵」であるロックを自動的にかけます。代表的なロックには次の2種類があります。

共有ロック（S）

読み取りの際にかかるロック。他の共有ロックとは共存できるが、後述の排他ロックとは共存できない。

排他ロック（X）

更新・削除・挿入の際にかかるロック。他のどのロックとも共存できない。ロックベースの読み取り（既定のREAD COMMITTEDなど）がこの行にアクセスしようとすると、待たされることがある。

ロックがかかる範囲を粒度と呼びます。SQL Server は状況に応じて行ロック（1行だけ）、ページロック（8KB単位のまとまり）、テーブルロック（表全体）を自動的に使い分けます。行ロックが増えすぎたときに、SQL Server がまとめてテーブル単位などの粗いロックへ切り替える動作をロックエスカレーション（正式名称: ロックエスカレーション）と呼びます。基本的にはSQL Serverの最適化に任せればよく、開発者が粒度を細かく指定する必要はほとんどありません。

あるセッションが排他ロックを保持している間、既定の READ COMMITTED のようなロックベースの読み取りでは、他のセッションがそのデータを読もうとすると、ロックが解放されるまで待たされることがあります。この「待たされる状態」をブロッキングと呼びます。ブロッキング自体は異常ではなく、同時実行制御の正常な動作です。一方、10.5で説明する READ_COMMITTED_SNAPSHOT や 10.4 の SNAPSHOT 分離レベルでは、読み取り側が更新前の行バージョンを読むため、待たされずに済む場合があります。次の図は、既定のロックベースの読み取りでセッションBが待たされる例です。

sequenceDiagram participant A as セッションA participant B as セッションB participant DB as SQL Server A->>DB: BEGIN TRAN A->>DB: UPDATE 商品テーブル 行1（排他ロックX取得） B->>DB: SELECT 商品テーブル 行1 DB-->>B: 待機（Aのロック解放待ち＝ブロッキング） A->>DB: COMMIT TRAN DB-->>A: ロック解放 DB-->>B: 待機が解け、結果を返す

セッションBは何もおかしなことをしていません。単にセッションAがトランザクションを終えるまで待たされているだけです。この待ち時間が長いと「アプリが固まった」ように感じられるため、トランザクションはできるだけ短く保つことが重要になります。

10.4 分離レベル

同時に動いている他のトランザクションの影響を、どこまで見せるか／遮断するかの強さの設定を分離レベル（正式名称: トランザクション分離レベル）と呼びます。分離レベルを厳しくするほどデータの矛盾は起きにくくなりますが、その分ブロッキングが増え、性能は落ちる傾向にあります。

分離レベル 概要
READ UNCOMMITTED 最も緩い。他のトランザクションがまだコミットしていない変更も読めてしまう
READ COMMITTED（既定） コミット済みのデータしか読まない。SQL Serverの初期設定（RCSIが有効なデータベースでは行バージョンベースの読み取りになる。10.5参照）
REPEATABLE READ 一度読んだ行は、同じトランザクション内では常に同じ値が読める
SERIALIZABLE 最も厳格。同じ条件で再検索しても、新しい行の出現すら許さない
SNAPSHOT 標準SQLにはない追加レベル。行バージョンを使い、読み取りが書き込みをブロックしない（利用にはデータベースで ALLOW_SNAPSHOT_ISOLATION を ON にする必要がある）

分離レベルの違いは、次の3つの「望ましくない現象」がどこまで起きるかで整理すると分かりやすくなります。

分離レベル ダーティリード 反復不能読み取り ファントムリード
READ UNCOMMITTED 発生する 発生する 発生する
READ COMMITTED 発生しない 発生する 発生する
REPEATABLE READ 発生しない 発生しない 発生する
SERIALIZABLE 発生しない 発生しない 発生しない
SNAPSHOT 発生しない 発生しない 発生しない

ダーティリードはまだコミットされていない変更を読んでしまうこと、反復不能読み取りは同じ行を2回読んだら値が変わっていたこと、ファントムリードは同じ条件で再検索したら行が増減していたことを指します。

repeatable-read.sql 
-- このセッションの分離レベルをREPEATABLE READに変更
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRAN;
    SELECT Balance FROM Accounts WHERE AccountId = 1;
    -- ここで他セッションからの更新はブロックされる
COMMIT TRAN;

10.5 READ_COMMITTED_SNAPSHOT

既定の READ COMMITTED はロックベースで動くため、「読み取り（SELECT）」が「書き込み中の行」に対してブロッキングされることがあります（10.3参照）。これを避けたい場合、読み取りがロック待ちをせず「更新前の姿」を読むように切り替える設定を、データベース単位で有効化できます。これをRCSI（正式名称: RCSI＝READ_COMMITTED_SNAPSHOTの略。データベース単位のオプション）と呼びます。

enable-rcsi.sql 
-- データベース単位でスナップショット読み取りを有効化
ALTER DATABASE SampleShop
    SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;

この設定の切り替えにはデータベースへの排他アクセスが必要なため、他の接続を切断して即座に適用する WITH ROLLBACK IMMEDIATE を付けています（学習環境では安全ですが、本番では影響を確認してから実行してください）。RCSIを有効にすると、SELECT は更新中の行に対して、その行バージョン（更新される前の姿）を読み取るようになり、書き込みを待たなくなります。分離レベルの名前は変わらず「READ COMMITTED」のままですが、RCSIが有効なデータベースでは、同じ READ COMMITTED でも内部の実現方式がロックベースから行バージョンベースに変わる、という点がポイントです。

発展: 行バージョンはどこに保存される？

従来、RCSIが生成する行バージョンは tempdb 内の「バージョンストア」に保持されます。ただし、Accelerated Database Recovery（ADR、高速データベース復旧）が有効なデータベースでは、そのデータベース自身の中にある Persistent Version Store（PVS）に行バージョンが保持される場合があります（ADR はオンプレミスの SQL Server では既定で無効なので、通常は tempdb 側と考えて構いません）。どちらの方式でも「読み取りは更新前の行バージョンを読むので待たされにくい」という基本的な仕組みは変わりません。なおAzure SQL Database ではRCSIが既定で有効になっています。

注意: WITH (NOLOCK) を安易に使わない

SELECT ... FROM Table WITH (NOLOCK) は「ロックを一切気にせず読む」ヒントで、ブロッキングを避ける目的でよく使われます。しかしこれは実質的にREAD UNCOMMITTEDと同じ動作で、コミット前の中途半端なデータ（ダーティリード）を読んでしまう可能性があります。集計結果がずれる、存在しないはずのデータが見えるといった不具合につながるため、性能改善が必要な場合は NOLOCK ではなく READ_COMMITTED_SNAPSHOT の有効化やインデックスの見直し（第11章）を検討しましょう。

10.6 デッドロック

ブロッキングが「片方が終われば解決する」一時的な待ちであるのに対し、デッドロックは2つ（以上）のセッションが互いに相手のロック解放を待ち合う「相互待ち」の状態です。たとえばセッションAが行1をロックして行2を待ち、同時にセッションBが行2をロックして行1を待つと、DBMSが介入しない限り、両者とも相手のロックが解放されるのを永遠に待ち続けることになります。

SQL Server はこの状況を自動的に検出し、どちらか一方（一般に処理コストが小さい方）をデッドロックの犠牲者（victim）として選び、そのトランザクションを強制的にロールバックしてエラー（エラー番号1205）を返します。もう一方は処理を継続できます。アプリケーション側では、このエラーを捕捉して処理をリトライする実装が定石です。

重要ポイント: デッドロックの主な対策

  • 複数テーブル・複数行を更新するときは、常に同じ順序でアクセスする
  • トランザクションはできるだけ短くし、不要な処理を中に含めない
  • 検索条件に合った適切なインデックスを張り、ロックする行数自体を減らす（第11章）

10.7 PostgreSQLとの違い

同時実行制御は、SQL Server と PostgreSQL でもっとも設計思想の違いが表れる分野の1つです。「既定の分離レベルの名前は同じでも、内部の仕組みが違う」という点をしっかり押さえておきましょう。

PostgreSQL との違い（トランザクションとロック）

観点 SQL Server PostgreSQL
既定の分離レベル READ COMMITTED（既定はロックベース） READ COMMITTED（常にMVCCで実現）
読み取りが書き込みを待つか 既定では待つ（ブロッキングされうる） 待たない（読み取りは常に旧版を見る）
同等の挙動を得るには READ_COMMITTED_SNAPSHOT を ON にする （既定でMVCCのため設定不要）
明示トランザクションの開始 BEGIN TRAN BEGIN
READ UNCOMMITTED 指定するとダーティリードが実際に発生する 指定してもREAD COMMITTEDとして動作（実質存在しない）
行バージョンの保管場所 tempdb（既定。詳細は10.5） テーブル内に旧バージョン行を保持し、VACUUMで回収
NOLOCK 相当のヒント WITH (NOLOCK) で明示指定できる 相当する機能がない
現在のロックを確認する方法 sys.dm_tran_locks pg_locks

PostgreSQLは常にMVCC（同じデータの「更新前の姿」を別に取っておき、読み取る人は更新中でも待たずに更新前の姿を読める仕組み。正式名称: MVCC＝多版型同時実行制御。SQL Serverでは行バージョン管理と呼びます）で動くため「読み取りが書き込みをブロックしない」のが基本です。一方SQL Serverは既定でロックベースのため、その挙動に近づけたい場合は明示的に READ_COMMITTED_SNAPSHOT（RCSI）を有効化する、という発想の違いを押さえておきましょう。

やってみよう 10-1: ブロッキングを体験する

SSMSで2つのクエリウィンドウを開き、実際に「待たされる」感覚を体験してみましょう。

手順

前提: この実習は RCSI が無効な状態（既定）で行ってください。10.5 の ALTER DATABASE SampleShop SET READ_COMMITTED_SNAPSHOT ON を実行済みの場合、読み取りは行バージョンを読むためブロックが起きず、手順3の「実行中のまま止まる」状態を再現できません。その場合は READ_COMMITTED_SNAPSHOT OFF に戻してから試してください。

  1. 1 SSMSで「新しいクエリ」を2つ開く（ウィンドウ1・ウィンドウ2）。
  2. 2 ウィンドウ1で BEGIN TRAN; の後、任意の1行を UPDATE する（COMMIT はまだ実行しない）。
  3. 3 ウィンドウ2で、同じ行を対象に SELECT を実行する。クエリが完了せず「実行中」のまま止まることを確認する。
  4. 4 ウィンドウ1に戻り ROLLBACK; を実行する。ウィンドウ2のSELECTが即座に結果を返すことを確認する。

ねらい: ロックによるブロッキングは目に見えない現象ですが、この手順で「待たされている」状態を実際に体験できます。COMMITではなくROLLBACKを使うのは、練習データを変更したままにしないための配慮です。

理解度確認クイズ

  1. Q1. トランザクションのACID特性のうち、「複数のSQL文をひとまとまりとして、全部成功か全部なかったことにするかのどちらかにする」性質は何と呼ばれますか。

    回答を表示

    原子性（Atomicity）です。トランザクション内の処理が途中で終わることを許さず、全部成功か全部なかったことにするかのどちらかしかない、という性質を指します。

  2. Q2. ブロッキングとデッドロックの違いを説明してください。

    回答を表示

    ブロッキングは、先にロックを取得したセッションの処理が終われば解決する一時的な待ちです。デッドロックは、2つ以上のセッションが互いのロック解放を待ち合う「相互待ち」の状態で、DBMSが介入しなければ解決しません。ただしSQL Serverはこの状態を自動的に検出し、片方を犠牲者（victim）として強制的にロールバックする（エラー番号1205）ため、処理が永久に止まったままにはなりません。

  3. Q3. SQL Server の既定の分離レベルと PostgreSQL の既定の分離レベルは名前こそ同じ「READ COMMITTED」ですが、何が違いますか。また SQL Server で PostgreSQL に近い挙動を得るにはどう設定しますか。

    回答を表示

    SQL Serverの既定はロックベースで、読み取りが書き込み中の行をブロックされることがあります。PostgreSQLは行バージョン管理（MVCC）で動作するため、通常の読み取りが書き込みの完了を待つことは基本的にありません。SQL Serverで同様の挙動にするには、データベースで ALTER DATABASE ... SET READ_COMMITTED_SNAPSHOT ON; を実行します（Azure SQL Databaseでは既定でON）。
