データベースとテーブルの作成

前章までで SSMS の操作に慣れました。この章では、いよいよ自分専用のデータベース SampleShop を作り、その中に Customers（顧客）・Products（商品）・Orders（注文） という3つのテーブルを作成します。ここで作るデータベースは第6章以降もずっと使い続けるので、データ型・制約・自動採番の考え方をしっかり押さえておきましょう。

この章で学ぶこと

  • CREATE DATABASE / USE でデータベースを作成し、切り替えられる
  • 主なデータ型の使い分け（nvarchar と varchar の違いを含む）を説明できる
  • CREATE TABLE でテーブルを作成し、主キー・外部キーなどの制約を設定できる
  • IDENTITY による自動採番の仕組みを理解する
  • ALTER TABLE / DROP TABLE でテーブルを変更・削除できる

5.1 データベースを作る

SQL Server では、1つのインスタンスの中に複数のデータベースを作成できます（第2章で学んだ構造を思い出しましょう）。本ガイドでは SampleShop という名前のデータベースを1つ作り、第14章まで一貫してこれを使います。まずはクエリエディタで次のように実行します。

5-1_create_database.sql 
-- SampleShop データベースを作成
CREATE DATABASE SampleShop;
GO

-- 以降の命令は SampleShop に対して実行する
USE SampleShop;
GO

1つ目の GO は「ここまでをひとつのバッチとして実行する」区切りです（第4章参照）。USE SampleShop; を実行すると、以降のクエリは特に指定しない限り SampleShop データベースに対して実行されます。SSMS のクエリエディタ右上のドロップダウンに SampleShop と表示されていれば成功です。

GUI でも同じことができる

オブジェクトエクスプローラーで「データベース」を右クリック→「新しいデータベース」からも作成できます。GUI はダイアログの内部で結局 CREATE DATABASE 文を組み立てて実行しているだけなので、仕組みを理解するにはまず SQL で書けるようになるのが近道です。

5.2 主なデータ型

テーブルの列（カラム）には、それぞれ「どんな種類のデータが入るか」を示すデータ型を指定します。SQL Server には数十種類のデータ型がありますが、まずは次の6種類を覚えれば業務システムの大半をカバーできます。

データ型 用途 例
int / bigint 整数。件数・数量・IDなど int は約±21億、桁が足りない時は bigint
decimal(p, s) 正確な小数。金額・数量単価など decimal(10,2) ＝全10桁・小数2桁
nvarchar(n) / varchar(n) 可変長の文字列 nvarchar(100) ＝最大100文字
date / datetime2 日付、または日付＋時刻 誕生日は date、記録日時は datetime2
bit 真偽値（有効／無効など） 0＝偽・1＝真の2値（NULLも可）
uniqueidentifier 世界中で重複しないように作られる、とても長い識別子（正式名称: GUID／UUID。SQL Server の型名は uniqueidentifier） 複数システムでキーが衝突しては困る場合に使用

重要: nvarchar と varchar の違い

varchar は照合順序（Collation）に対応する文字コードでデータを格納する型です。既定の照合順序（多くの場合、日本語などを表現できない非 Unicode の文字コード）のまま保存すると、対応していない文字は「?」に置き換わってしまうことがあります。一方 nvarchar は常に Unicode（UTF-16）で保存するため、照合順序の設定によらず日本語・絵文字を含むあらゆる文字を安全に扱えます。本ガイドでは、文字列の列は原則すべて nvarchar を使います。照合順序の設定を意識しなくても確実に多言語を扱えるためです。また、nvarchar 列に文字列リテラルを入れるときは N'山田 太郎' のように先頭に N を付けます。これを忘れると、環境によって日本語が正しく変換されないことがあります。

発展: varchar と Unicode

SQL Server 2019 以降では、UTF-8 に対応した照合順序（末尾に _UTF8 が付く照合順序。例: Japanese_XJIS_140_CI_AS_UTF8）をデータベースや列に指定することで、varchar でも日本語や絵文字を含む Unicode 文字を正しく扱えるようになりました。ただしこれは照合順序という設定に依存する話であり、既定の照合順序のままでは前述のとおり文字化けの可能性が残ります。また、UTF-8 対応照合順序が影響するのは char / varchar だけで、nvarchar の動作は変わりません。さらに varchar(10) の「10」は文字数ではなくバイト数を表し、日本語は UTF-8 では1文字3バイト（UTF-16 なら2バイト）を使うため、日本語が中心のデータでは容量の面でも nvarchar のほうが有利です。初心者のうちは設定の有無を意識しなくても確実に動く nvarchar を基本とし、UTF-8 対応の照合順序は「こういう選択肢もある」と知っておく程度で十分です。

金額に float を使わない

float は近似値を扱う浮動小数点型のため、金額の計算に使うと丸め誤差が発生することがあります。金額・単価など「1円単位で正確に一致してほしい」値には、必ず decimal(p, s) を使いましょう。

5.3 テーブルを作る

テーブルは CREATE TABLE テーブル名 (列名 データ型 制約, ...); という書式で作成します。ここでは第6章以降で使い続ける3つのテーブル、Customers（顧客）・Products（商品）・Orders（注文）を順に作成します。

Customers（顧客）テーブル

5-2_create_customers.sql 
-- 顧客テーブルを作成
CREATE TABLE Customers (
    CustomerId   INT IDENTITY(1,1) PRIMARY KEY,   -- 顧客ID（自動採番）
    CustomerName NVARCHAR(100)     NOT NULL,      -- 顧客名（日本語対応）
    Email        NVARCHAR(256)     UNIQUE,        -- メールアドレス（重複禁止）
    CreatedAt    DATETIME2         NOT NULL DEFAULT SYSDATETIME()  -- 登録日時
);

Products（商品）テーブル

5-3_create_products.sql 
-- 商品テーブルを作成
CREATE TABLE Products (
    ProductId   INT IDENTITY(1,1) PRIMARY KEY,       -- 商品ID（自動採番）
    ProductName NVARCHAR(100)     NOT NULL,          -- 商品名
    UnitPrice   DECIMAL(10,2)     NOT NULL           -- 単価（円）
                CHECK (UnitPrice >= 0),              -- 0円未満を禁止
    IsActive    BIT               NOT NULL DEFAULT 1 -- 販売中フラグ（1=有効）
);

Orders（注文）テーブル

5-4_create_orders.sql 
-- 注文テーブルを作成（顧客・商品を外部キーで参照）
CREATE TABLE Orders (
    OrderId    INT       IDENTITY(1,1) PRIMARY KEY,      -- 注文ID
    CustomerId INT       NOT NULL,                       -- どの顧客の注文か
    ProductId  INT       NOT NULL,                       -- どの商品の注文か
    Quantity   INT       NOT NULL CHECK (Quantity > 0),  -- 数量（1以上）
    OrderDate  DATETIME2 NOT NULL DEFAULT SYSDATETIME(), -- 注文日時
    FOREIGN KEY (CustomerId) REFERENCES Customers(CustomerId),
    FOREIGN KEY (ProductId)  REFERENCES Products(ProductId)
);

3つとも実行できたら、オブジェクトエクスプローラーの「データベース」→「SampleShop」→「テーブル」を右クリック→「更新」すると、作成した3つのテーブルが表示されます。

5.4 制約でデータを守る

先ほどのテーブル定義には、データ型のあとにいくつかの制約（Constraint）を付けました。制約は「おかしなデータを保存できないようにする」ためのルールです。

制約 意味 使用例
PRIMARY KEY その行を一意に識別する主キー。重複・NULL不可 CustomerId, ProductId, OrderId
NOT NULL 値の未入力（NULL）を許さない CustomerName, ProductName
UNIQUE 列内で値の重複を許さない（SQL Server では NULL も1行分しか入れられない） Email
DEFAULT 値を省略した時に自動で入る既定値 CreatedAt, OrderDate, IsActive
CHECK 条件式を満たす値しか許さない UnitPrice ≧ 0、Quantity ＞ 0
FOREIGN KEY 他のテーブルの主キーを参照し、存在する値しか許さない Orders.CustomerId → Customers.CustomerId

とくに FOREIGN KEY（外部キー）は初心者がつまずきやすい制約ですが、意味はシンプルです。Orders テーブルの CustomerId 列に外部キーを設定すると、SQL Server は「その値が Customers テーブルの CustomerId に本当に存在するか」を毎回チェックします。

flowchart LR A["Customers
顧客"] -->|"CustomerIdを参照"| C["Orders
注文"] B["Products
商品"] -->|"ProductIdを参照"| C

外部キーがあると、次のような事故を防げます。

  • 存在しない CustomerId（例: 9999）を指定した注文が登録されてしまう
  • ある顧客がまだ注文を持っているのに、その顧客のレコードだけをうっかり削除してしまう（既定では拒否され、エラーになる）

重要ポイント

制約は「面倒なルール」ではなく、「アプリ側のバグが混入しても、データベースの中身までは壊れないようにする最後の防波堤」です。アプリのコードにミスがあっても、制約が正しく設定されていれば矛盾したデータの保存を防げます。

5.5 IDENTITY で連番を振る

CustomerId や OrderId のような主キーに、毎回自分で番号を考えて INSERT するのは大変ですし、重複のミスも起こります。そこで使うのが IDENTITY(開始値, 増分値) です。IDENTITY(1,1) は「1から始めて、1件ごとに1ずつ増やす」という意味で、値を指定せずに INSERT すると SQL Server が自動で採番してくれます。

5-5_identity_sample.sql 
-- 新しい顧客を1件登録する（CustomerIdは指定しない）
INSERT INTO Customers (CustomerName, Email)
VALUES (N'山田 太郎', N'yamada@example.com');

-- 直前に採番された CustomerId を取得する
SELECT SCOPE_IDENTITY() AS NewCustomerId;

SCOPE_IDENTITY() は、直前の INSERT で採番された IDENTITY 値を取得する関数です。アプリケーションのコードから「今登録した行のID」を知りたいときによく使います（第9章のストアドプロシージャでも登場します）。

採番に「穴」が空くことがある

INSERT がロールバック（取り消し）された場合や、トランザクションが失敗した場合でも、消費された IDENTITY の番号は戻りません。そのため「1, 2, 3, 5, 6」のように連番に欠番ができることがあります。これは異常ではなく仕様です。IDENTITY 値は「一意性」を保証するものであり、「連続性」までは保証しない、と覚えておきましょう。

5.6 テーブルの変更と削除

テーブルを作った後で「列を追加したい」「型を変更したい」ということはよくあります。そんな時に使うのが ALTER TABLE です。

5-6_alter_table.sql 
-- Customers テーブルに電話番号の列を追加する
ALTER TABLE Customers
    ADD PhoneNumber NVARCHAR(20) NULL;

-- CustomerName の最大長を150文字に変更する
ALTER TABLE Customers
    ALTER COLUMN CustomerName NVARCHAR(150) NOT NULL;

テーブルそのものが不要になった場合は DROP TABLE テーブル名; で削除します。たとえば DROP TABLE Orders; です。

警告: DROP TABLE は簡単には元に戻せない

DROP TABLE はテーブルの構造ごと、中身のデータも含めてすべて削除します。実行前の確認ダイアログもありません。明示的なトランザクションの中（BEGIN TRAN 〜）で実行していれば ROLLBACK で取り消せますが、コミット後（トランザクションを明示していない通常の実行を含む）でバックアップなどが無い場合は容易には元に戻せないため、非常に注意が必要です。本番環境であればバックアップからの復元という手段もありますが、復旧には時間がかかるうえ、直前までの変更が失われる可能性があります。学習中であっても「本当にこのテーブルを消してよいか」「今どのデータベースに接続しているか（SSMS 画面左上を確認）」を必ず確認してから実行する習慣をつけましょう。

5.7 PostgreSQLとの違い

テーブル定義まわりは、SQL Server と PostgreSQL で名前や既定の挙動が異なる部分が多く出てきます。ここで代表的な違いを整理しておきましょう。

PostgreSQL との違い（データ型・採番）

観点 SQL Server PostgreSQL
文字列型 nvarchar(n) / varchar(n)（長さ指定が基本） text（長さ無制限）と varchar(n)。実務では text が既定的に使われる
真偽値 bit（0/1で表現） boolean（true/falseで表現）
日時型と既定値 datetime2。現在日時は GETDATE() / SYSDATETIME() timestamp。現在日時は now() / CURRENT_TIMESTAMP
自動採番 IDENTITY(1,1) を列定義に付与 serial 型、または標準準拠の GENERATED BY DEFAULT AS IDENTITY
識別子の大文字小文字 既定の照合順序では大文字小文字を区別しない（Customers と customers は同じ扱い） 引用符なしの識別子は自動的に小文字化される（Customersはcustomersとして扱われる）

実務では「PostgreSQL の文字列はとりあえず text、SQL Server の文字列は原則 nvarchar(n)」くらいの大づかみな理解で十分です。細かい互換性はデータ移行の際に見直せば問題ありません。

ヒント: なぜ識別子の大文字小文字が違うのか

SQL Server は Windows 文化圏で育った製品で、ファイル名やコマンドと同じく「大文字小文字を区別しない」既定を長く採用してきました。一方 PostgreSQL は、引用符で囲まない識別子をすべて小文字へ畳み込むルールを採用しています（標準 SQL は大文字への畳み込みを定めており、PostgreSQL はそこを意図的に変えています）。どちらも一貫したルールですが、他方の DB に慣れていると最初は戸惑いやすいポイントです。

やってみよう 5-1: SampleShop データベースを構築する

この章で学んだ内容を使って、実際に SampleShop データベースと3つのテーブルを作成し、SSMS の画面で確認してみましょう。

手順

  1. 1 SSMS で新しいクエリを開き、5.1 の CREATE DATABASE SampleShop; と USE SampleShop; を実行する。
  2. 2 5.3 の Customers → Products → Orders の順に CREATE TABLE 文を実行する（Orders は Customers と Products を参照するため、必ず後に作成する）。
  3. 3 オブジェクトエクスプローラーで「データベース」→「SampleShop」→「テーブル」を右クリックし「更新」を選び、3つのテーブルが表示されることを確認する。
  4. 4 「dbo.Customers」を展開して「列」フォルダを開き、CustomerId・CustomerName・Email・CreatedAt が定義どおりのデータ型になっているか確認する。
  5. 5 5.5 の INSERT 文を実行し、SCOPE_IDENTITY() の結果として採番された CustomerId が返ってくることを確認する。

ねらい: ここで作った SampleShop・Customers・Products・Orders は第6章以降のすべての章で使い続けます。今のうちに正しく作成できているか、必ず自分の目で確認しておきましょう。

理解度確認クイズ

  1. Q1. 日本語を含む文字列を保存する列には nvarchar と varchar のどちらを使うべきですか。理由もあわせて答えてください。

    回答を表示

    nvarchar を使うべきです。varchar は照合順序（Collation）に対応する文字コードで保存する型で、既定の照合順序のままでは日本語が「?」に置き換わることがあります（SQL Server 2019 以降の UTF-8 対応照合順序を使えば varchar でも扱えますが、設定に依存します）。nvarchar は常に Unicode で保存するため、照合順序の設定によらず日本語を含むあらゆる文字を安全に扱えます。文字列リテラルには N'...' を使います。

  2. Q2. Orders テーブルの CustomerId 列に FOREIGN KEY 制約を設定すると、どのような不正なデータの登録を防げますか。

    回答を表示

    Customers テーブルに存在しない CustomerId を持つ注文が登録されるのを防げます。また、注文が残っている顧客を誤って削除しようとした場合も、既定では削除がエラーとなり拒否されます。

  3. Q3. IDENTITY(1,1) で採番した値に欠番（穴）ができることがあるのはなぜですか。

    回答を表示

    INSERT がロールバックされたり失敗したりしても、一度消費された IDENTITY の番号は戻らないためです。IDENTITY は値の一意性を保証しますが、連続性までは保証しません。
