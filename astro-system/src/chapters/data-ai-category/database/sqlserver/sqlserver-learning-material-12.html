ホーム SQL Server 第12章
第12章 所要時間: 約60分

セキュリティとユーザー管理

データベースは大切な情報の保管庫だからこそ、「誰が・何を・どこまでできるか」を制御する仕組みが欠かせません。この章では、Windows 認証と SQL Server 認証、ログインとユーザーの二層構造、ロールによる権限のまとめ方、そして GRANT / DENY / REVOKE による権限の細かい制御までを学びます。

この章で学ぶこと

  • 最小権限の原則を理解し、なぜ全員が sa で接続してはいけないのか説明できる
  • Windows 認証と SQL Server 認証（混合モード）の違いを説明できる
  • ログイン（サーバーレベル）とユーザー（データベースレベル）の関係を図で説明できる
  • サーバーロール・データベースロールを使い、GRANT / DENY / REVOKE で権限を制御できる

12.1 なぜ権限管理が必要か

SQL Server をインストールした直後は、多くの場合インストールを行った自分の Windows アカウントが sysadmin 権限を持ち、管理者としてすべての操作ができてしまいます（sa アカウントがどういう状態になっているかは12.2で詳しく説明します）。学習中はそれで問題ありませんが、実際の業務システムで「全員が管理者アカウントで接続する」状態のまま運用すると、次のような危険があります。

  • 参照だけで良いはずの担当者が、誤操作で本番データを DELETE してしまう
  • アプリケーションのプログラムミスが、想定外のテーブルまで書き換えてしまう
  • パスワードが漏えいした場合に、被害がシステム全体に及んでしまう

こうした事故を防ぐ基本的な考え方が最小権限の原則（Principle of Least Privilege）です。「その人・そのアプリが業務上どうしても必要な権限だけを与え、それ以上は与えない」というシンプルなルールです。

身近な例え: オフィスの鍵

オフィスビルを想像してみましょう。清掃スタッフには共用部分の鍵だけ、経理担当には経理室の鍵だけ、そして経営陣だけがすべての部屋のマスターキーを持つ、という運用が普通です。全員にマスターキーを配ることはしません。データベースの権限管理も同じ発想で、「その人の役割に必要な鍵（権限）だけを渡す」のが基本です。

この章では、SQL Server がどのようにして「誰が・どのデータベースの・何に対して・何をしてよいか」を管理しているのかを、順を追って学んでいきます。

12.2 認証モード

SQL Server に接続するには、まず「あなたは誰か」を確認する認証（Authentication）が必要です。第3章のインストール時にも触れましたが、SQL Server には2つの認証モードがあります。

認証モード 仕組み 利点
Windows 認証 Windows にログインしたアカウント情報をそのまま利用する パスワードを別途管理不要。ドメインのアカウント無効化と連動できる。既定で推奨
SQL Server 認証（混合モード） SQL Server 内部で管理する「ログイン名＋パスワード」で接続する Windows ドメインに属さない環境（Linux／Docker／クラウド／他OSのアプリ）から接続できる

「混合モード（Mixed Mode）」とは、この2つの認証方式を両方とも受け付ける設定のことです。Windows 認証だけを許可するモードも選べますが、本教材で使う学習用の Docker 環境や、Web アプリケーションのようにドメインアカウントを持たない仕組みから接続する場合は、混合モードを有効にして SQL Server 認証を利用することが多いです。

用語: sa アカウント

sa（system administrator）は SQL Server 認証の組み込み管理者アカウントで、有効になっていれば常に最高権限（sysadmin）を持ちます。ただし初期状態はインストール時に選んだ認証モードによって異なります。Windows 認証モードでインストールした場合、sa ログイン自体は作成されますが無効（disabled）の状態で、そのままでは接続に使えません。一方、混合モードでインストールした場合は、インストール時に設定したパスワードで sa が有効な状態になります。後から Windows 認証モードのインスタンスを混合モードへ切り替えた場合は、ALTER LOGIN sa ENABLE; で明示的に有効化したうえで、パスワードを設定し直す必要があります。

注意: sa を日常的に使わない

sa は名前が推測しやすく、攻撃対象になりやすいアカウントです。実務では、無効のまま使わない・名前を変更する・強固なパスワードを設定するといった対策を取り、sa を日常の接続・運用には使わないのが基本です。日常の管理作業には、後述するサーバーロール sysadmin を持つ個人名のログインを使います。

参考: Windows 認証系の仕組みは Windows 専用ではない

「Windows 認証＝ Windows 環境専用」というわけではありません。Linux 版の SQL Server でも、Windows ドメインのアカウントを一元管理する仕組みである Active Directory と連携する認証（AD 認証）を構成すれば、Windows 認証を利用できます。また Azure SQL Database・Azure SQL Managed Instance では、Microsoft のクラウド型ID管理サービスである Microsoft Entra ID（旧 Azure AD）による認証を利用できます。本教材では学習のしやすさを優先して SQL Server 認証（混合モード）を中心に扱いますが、実務ではこうした選択肢もあることを覚えておきましょう。

12.3 ログインとユーザーの二層構造

SQL Server の権限管理を理解するうえで、最初につまずきやすいのが「ログイン」と「ユーザー」という似た2つの用語です。この2つは階層が異なる、別のオブジェクトです。

  • ログイン（Login）: SQL Server インスタンス全体（サーバーレベル）への「玄関の鍵」。第2章で学んだインスタンスに対して作成する
  • ユーザー（User）: 個々のデータベース（データベースレベル）への「部屋の鍵」。データベースごとに作成する

つまり、1つのログインでサーバーに接続した後、実際にどのデータベースの中で何ができるかは、そのデータベース内に対応するユーザーが存在するかどうかで決まります。

flowchart TD A["Windowsアカウント
または SQL Serverログイン
（サーバーレベル）"] --> B{"接続先データベースに
対応するユーザーが存在するか"} B -->|はい| C["データベースユーザー
（DBレベル）"] B -->|いいえ＝孤立| D["孤立ユーザー
（orphaned user）"] C --> E["ロール・権限に従って
テーブル操作などを許可"] D --> F["エラー、または
権限なしで拒否される"]

実際の手順としては、まず CREATE LOGIN でサーバーレベルの鍵を作り、続けて対象データベースの中で CREATE USER ... FOR LOGIN ... を実行して、そのログインに対応するユーザーを作ります。この2段階を踏んで初めて、データベース内のテーブルなどへアクセスできるようになります。

用語: 孤立ユーザー（orphaned user）

データベースだけを別のサーバーへバックアップ・復元すると、データベース内の「ユーザー」情報はそのまま移りますが、対応する「ログイン」が新しいサーバーに存在しないことがあります。この、対応するログインを失ったユーザーを孤立ユーザーと呼びます。復元後にログインできない場合は、まずこの状態を疑いましょう（第13章のバックアップ・復旧で改めて扱います）。

12.4 ロールで権限をまとめる

ユーザーが増えてくると、一人ひとりに個別に権限を設定するのは大変です。そこで使うのがロール（Role）です。ロールは「権限の詰め合わせセット」で、ユーザーをロールに追加するだけで、そのロールが持つ権限をまとめて与えられます。ロールにもサーバーレベルとデータベースレベルの2種類があります。

階層 ロール名 できること
サーバーロール sysadmin サーバー上のすべての操作が可能な最高権限（sa 相当）
〃 dbcreator データベースの作成・変更・削除ができる
データベースロール db_owner そのデータベース内のすべての操作が可能
〃 db_datareader すべてのテーブルを SELECT（参照）できる
〃 db_datawriter すべてのテーブルに INSERT / UPDATE / DELETE できる
〃 db_ddladmin テーブルの作成・変更など DDL（CREATE / ALTER / DROP）を実行できる

ユーザーをデータベースロールに追加するには ALTER ROLE ... ADD MEMBER ... を使います。

add-role-member.sql 
-- SampleShop データベースを対象に切り替える
USE SampleShop;
GO

-- ReadOnlyUser を db_datareader ロールに追加する
-- これだけで全テーブルの SELECT 権限がまとめて付与される
ALTER ROLE db_datareader ADD MEMBER ReadOnlyUser;

1人のユーザーを複数のロールに同時に所属させることもできます。「参照はできるが更新はできない」担当者には db_datareader だけ、「アプリの実行アカウント」には db_datareader と db_datawriter の2つ、というように組み合わせるのが基本的な考え方です。ただしこれは学習のための単純化した例で、実務ではさらに踏み込んだ権限設計を行うことがあります（12.6で扱います）。

12.5 権限の付与と剥奪

あらかじめ用意されたロールでは足りない、もっと細かい制御をしたい場合は、個別のオブジェクト（テーブル・ビューなど）やスキーマ単位で直接権限を操作します。使う命令は3つです。

命令 意味
GRANT 権限を許可する
DENY 権限を明示的に拒否する。他のどんな GRANT よりも最優先される
REVOKE 以前に GRANT または DENY した設定を取り消し、「未設定」の状態に戻す

ここで最も間違えやすいのが DENY と REVOKE の違いです。REVOKE は「許可も拒否もしていないニュートラルな状態」に戻すだけなのに対し、DENY は「たとえロールから SELECT を許可されていても、絶対にこの操作はさせない」という強制的な拒否です。仮にユーザーが db_owner ロールに入っていても、個別に DENY された操作は実行できません。ただしサーバーロール sysadmin のメンバーは権限チェック自体を通らないため、DENY でも止められない点だけは例外として覚えておきましょう。

権限はテーブル1つ1つに与えることもできますが、SCHEMA:: を使えば、そのスキーマに属するすべてのオブジェクトへまとめて付与できます。第2章で学んだ既定スキーマ dbo を例に見てみましょう。

grant-deny-revoke.sql 
-- dbo スキーマ配下の全オブジェクトに SELECT 権限を許可する
GRANT SELECT ON SCHEMA::dbo TO ReadOnlyUser;

-- Orders テーブルへの更新だけは明示的に拒否する（GRANTより優先）
DENY UPDATE ON dbo.Orders TO ReadOnlyUser;

-- 付与した SELECT 権限を取り消す（未設定の状態に戻る）
REVOKE SELECT ON SCHEMA::dbo FROM ReadOnlyUser;

重要ポイント

ロールでまとめて権限を管理し、例外的に禁止したい操作だけを DENY で個別に上書きする、というのが実務の定石です。1人ずつ細かく GRANT を積み上げるより、後から見て意図が分かりやすくなります。

12.6 実務での設計例

ここまで学んだ知識を組み合わせると、実際の業務システムでよく見られる「用途別に3種類のユーザーを分ける」設計ができます。

参照専用ユーザー

db_datareader のみ。レポート作成担当や BI ツールの接続用。誤って更新できないので安心して渡せる。

アプリ用ユーザー

db_datareader＋db_datawriter。業務アプリの接続専用。テーブル構造の変更（DDL）はできない。学習用に単純化した例で、実務での設計はこの後で説明します。

管理者ユーザー

db_owner や sysadmin。テーブル設計やメンテナンスを行う個人名アカウント。日常運用では極力使わない。

こうしてユーザーを分けておくと、「アプリのソースコードが漏えいしても、参照専用ユーザーの権限しか奪われない」「レポートツールの設定ミスでデータが消える心配がない」など、被害の範囲を最小限に抑えられます。

なお、先ほどの「アプリ用ユーザーには db_datareader＋db_datawriter を与える」という例は学習用に単純化した例です。この2つの組み込みロールは、データベース内のすべてのテーブルに対する SELECT／INSERT／UPDATE／DELETE をまとめて許可してしまうため、本来そのアプリが触れる必要のないテーブルまで読み書きできてしまいます。

より実務に近い設計では、まず専用のデータベースロールを作成し（CREATE ROLE）、そのアプリが本当に必要とするスキーマ・テーブル・ストアドプロシージャに対してだけ権限を与えます。このように「そのアプリが本当に必要とする操作だけを許す」という考え方も、12.1で紹介した最小権限の原則を、より具体的な権限設計に落とし込んだものです。

app-role-least-privilege.sql 
-- 1. 注文処理アプリ専用のデータベースロールを作成する
CREATE ROLE app_order_role;

-- 2. そのアプリが実際に使うテーブルにだけ、必要な操作を許可する
--    db_datareader / db_datawriter と違い、対象テーブルも操作も絞り込める
GRANT SELECT, INSERT ON dbo.Orders TO app_order_role;
GRANT SELECT ON dbo.Products TO app_order_role;
GRANT SELECT ON dbo.Customers TO app_order_role;

-- 3. 特定のストアドプロシージャの実行だけを許可する
GRANT EXECUTE ON dbo.usp_CreateOrder TO app_order_role;

-- 4. アプリ用ユーザーをこのロールに追加する
ALTER ROLE app_order_role ADD MEMBER AppUser;

db_datareader・db_datawriter のような組み込みロールは、学習中に「まず動かしてみる」段階では便利です。実務でも小規模なシステムでは十分なことがありますが、扱うデータの重要度が上がるほど、こうしてアプリごとに必要な範囲だけへ絞ったロールを設計する価値が大きくなります。

警告: 接続文字列にパスワードを直書きしない

アプリ用ユーザーを作っても、そのパスワードをソースコードや設定ファイルにそのまま書いてリポジトリへコミットしてしまっては意味がありません。パスワードは環境変数や、Azure Key Vault のようなシークレット管理サービス・OS のパスワード管理機能に保存し、コードからは参照だけする運用を徹底しましょう。GitHub などに誤って公開してしまう事故は、この直書きが原因であることがほとんどです。

12.7 PostgreSQLとの違い

権限管理は、SQL Server と PostgreSQL で設計思想がはっきり異なる分野です。PostgreSQL には「ログイン」と「ユーザー」という区別自体がありません。

PostgreSQL との違い（セキュリティ・ユーザー管理）

観点 SQL Server PostgreSQL
管理の単位 ログイン（サーバー）＋ユーザー（DB）の二層構造 ロールに一元化。ユーザーとグループの区別がない
接続の可否制御 エンドポイント／ファイアウォール＋認証モードで制御 pg_hba.conf で接続元・認証方式を定義
明示的な拒否 DENY で強制的に拒否できる DENY に相当する機能はなく、REVOKE で許可を取り消すのみ
既定の所有スキーマ dbo public（v15以降は public への CREATE 権限が既定で外れた）
最上位権限 サーバーロール sysadmin（sa） 属性 SUPERUSER（既定は postgres ロール）
権限の確認方法 sys.fn_my_permissions・sys.database_permissions psql の \dp、information_schema

PostgreSQL では「ロール」1種類だけを使い、ログイン権限のあるロールを従来の「ユーザー」、ログイン権限のないロールを従来の「グループ」として使い分けます。また PostgreSQL 15 から、新規作成データベースの public スキーマに対して、一般ロールが既定で CREATE（オブジェクト作成）できなくなり、SQL Server の dbo より安全側に寄った点は覚えておく価値があります。

ヒント: DENY がない代わりに

PostgreSQL に SQL Server の DENY のような「強制拒否」はありません。権限を与えないことと、明示的に拒否することを区別できない代わりに、権限そのものをロール階層で慎重に設計する（不要な権限を最初から与えない）ことで安全性を保つ、という発想の違いがあります。

やってみよう 12-1: 参照専用ユーザーを作って動作を確認する

SampleShop データベースに参照専用のログイン・ユーザーを作成し、「SELECT はできるが INSERT はできない」ことを実際に確認します。SSMS のクエリエディタで作業してください。

手順

  1. 1 sysadmin 権限のアカウントで接続し、CREATE LOGIN ReadOnlyUser WITH PASSWORD = 'Practice#2026'; を実行してサーバーレベルのログインを作成する。
  2. 2 USE SampleShop; の後、CREATE USER ReadOnlyUser FOR LOGIN ReadOnlyUser; でデータベースユーザーを作成する。
  3. 3 ALTER ROLE db_datareader ADD MEMBER ReadOnlyUser; を実行し、参照専用ロールに追加する。
  4. 4 SSMS の「新しい接続」から ReadOnlyUser（SQL Server 認証）でログインし直し、SELECT * FROM dbo.Customers; が成功することを確認する。
  5. 5 同じ接続で INSERT INTO dbo.Customers (...) VALUES (...); を試し、権限不足のエラーになることを確認する。

ねらい: ロールに追加するだけで「できること」と「できないこと」が実際に切り替わることを、自分の手で体感するのが目的です。エラーメッセージに「The INSERT permission was denied」のような文言が出れば成功です。

理解度確認クイズ

  1. Q1. 「ログイン」と「ユーザー」の違いを、階層の観点から説明してください。

    回答を表示

    ログインは SQL Server インスタンス全体（サーバーレベル）への接続を許可する仕組みで、ユーザーは個々のデータベース（データベースレベル）内での操作を許可する仕組みです。1つのログインに対応するユーザーが各データベースに作成され、対応がない場合は孤立ユーザーになります。

  2. Q2. あるユーザーが db_owner ロールのメンバーですが、特定のテーブルに対して DENY UPDATE が設定されています。このユーザーはそのテーブルを更新できますか。理由も答えてください。

    回答を表示

    更新できません。DENY はロール経由で得た GRANT を含む、いかなる許可よりも優先される強制拒否だからです。db_owner のような強い権限を持っていても、個別に DENY された操作は実行できません。

  3. Q3. アプリケーション用の接続アカウントを設計するとき、db_owner をそのまま使うべきではない理由を、最小権限の原則の観点から説明してください。

    回答を表示

    db_owner はテーブルの削除や構造変更まで含むすべての操作ができてしまうため、アプリのバグや認証情報の漏えいが起きたときの被害が最大化します。アプリに必要なのは、そのアプリが実際に使うテーブルへの読み書きだけです。組み込みロールの db_datareader・db_datawriter でも、データベース内のすべてのテーブルが対象になってしまうため、実務では専用のデータベースロールを作り、必要な範囲だけを許可します（12.6 参照）。業務上必要な権限だけを与える最小権限の原則に沿った設計が重要です。
