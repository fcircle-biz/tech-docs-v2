ホーム SQL Server 第13章
第13章 所要時間: 約60分

バックアップと復旧・運用

データベースは、いつか必ず「壊れる」「消える」「動かなくなる」ことを前提に運用します。この章では、なぜバックアップが必要なのかという基本の考え方から、復旧モデル、完全・差分・ログの3種類のバックアップ、実際の復元手順、そして日常の運用チェックまでを学びます。

この章で学ぶこと

  • バックアップが必要な理由と、RPO・RTOという2つの指標を説明できる
  • 単純・完全・一括ログという3つの復旧モデルの違いと使い分けが分かる
  • 完全・差分・トランザクションログバックアップを実行し、正しい順序で復元できる
  • SQL Server Agent によるジョブ自動化と、日常の運用確認項目を理解する

13.1 なぜバックアップが必要か

どれほど堅牢に設計されたシステムでも、データが失われる可能性をゼロにはできません。代表的な原因を3つ挙げます。

ハードウェア障害

ディスクの故障、サーバーの電源異常、火災や水害など物理的なトラブルでデータファイルごと失われることがあります。

操作ミス

WHERE 句を付け忘れた DELETE、誤った DROP TABLE など、人為的なミスは今でも主要な原因のひとつです。

ランサムウェア

データを暗号化して身代金を要求する攻撃です。バックアップ自体が同時に暗号化・削除されないよう、隔離された場所への保管が重要です。

「バックアップを取る」だけでは不十分で、「どこまで戻ってよいか」「どれだけ早く戻すか」という目標をあらかじめ決めておく必要があります。これを表す2つの指標が RPO と RTO です。

指標 意味 バックアップ設計への影響
RPO
目標復旧地点		 障害発生時、どこまでのデータを失ってよいか（例: 「直近15分以内のデータまでは失ってもよい」） RPOが短いほど、ログバックアップの頻度を上げる必要がある
RTO
目標復旧時間		 障害発生から、どれだけ早くシステムを復旧させるか（例: 「2時間以内に復旧する」） RTOが短いほど、復元の練習と手順の自動化が重要になる

たとえ話: RPOとRTO

RPO は「巻き戻してよい時間の幅」、RTO は「復旧作業にかけてよい時間の長さ」と覚えるとイメージしやすいです。ネットショップなら「直近5分の注文は失いたくない（RPOが短い）」、社内の日報システムなら「半日止まっても業務に支障は出ない（RTOが長い）」というように、システムの重要度によって目標値は変わります。

13.2 復旧モデル

SQL Server のデータベースには、トランザクションログをどのように扱うかを決める 復旧モデルという設定があります。データベース作成時に既定値が決まり、後から変更することもできます。3種類の復旧モデルを比較します。

復旧モデル ログバックアップ 特定時点への復旧 ログの肥大化
単純
SIMPLE		 不可（ログは自動的に切り捨てられる） 不可。最後の完全／差分バックアップ時点まで 起きにくい。管理が簡単
完全
FULL		 可能（むしろ必須。取らないとログが肥大化し続ける） 可能。任意の時点まで戻せる ログバックアップを怠ると肥大化する
一括ログ
BULK_LOGGED		 可能 一括操作を含む期間は不可な場合がある 大量データ投入時のログ量を抑えられる

一括ログは、大量データの一括インポートなど特定の作業を一時的に高速化するための特殊なモデルで、常用するものではありません。初心者のうちは単純と完全の2つを使い分けられれば十分です。

重要ポイント: 使い分けの目安

本ガイドのように学習・検証用のデータベースは「単純」で構いません。データが多少失われても学習し直せるからです。一方、業務で使うデータベースは基本的に「完全」を選び、ログバックアップを定期的に取得して、障害直前まで復旧できるようにしておきます。

recovery-model.sql 
-- 現在の復旧モデルを確認する
SELECT name, recovery_model_desc
FROM sys.databases
WHERE name = 'SampleShop';

-- 業務データベース向けに「完全」へ変更する
ALTER DATABASE SampleShop SET RECOVERY FULL;

13.3 バックアップの種類

SQL Server の代表的なバックアップは3種類あり、組み合わせて使います。それぞれ「何を取得するか」が異なります。

種類 取得する内容 頻度の目安
完全バックアップ データベース全体のコピー 週1回程度（すべての基点になる）
差分バックアップ 直近の完全バックアップ以降に変更されたデータのみ 1日1回程度
トランザクションログバックアップ 直近のログバックアップ以降の、すべての更新履歴 15分〜1時間ごと（RPOに応じて）

まずは完全バックアップを取得します。バックアップ先フォルダはあらかじめ作成しておいてください（Windows の例では C:\Backup\、Linux コンテナの例では /var/opt/mssql/backup/）。

backup-full.sql 
-- 完全バックアップ: データベース全体を取得する
BACKUP DATABASE SampleShop
TO DISK = 'C:\Backup\SampleShop_Full.bak'
WITH INIT,          -- 既存の同名ファイルを上書きする
     COMPRESSION,   -- バックアップを圧縮して容量を節約する
     STATS = 10;    -- 進捗を10%刻みで表示する

続いて差分バックアップです。WITH DIFFERENTIAL を付けるだけで、直近の完全バックアップからの差分のみが記録されます。

backup-diff.sql 
-- 差分バックアップ: 直近の完全バックアップ以降の変更分のみ取得
BACKUP DATABASE SampleShop
TO DISK = 'C:\Backup\SampleShop_Diff.bak'
WITH DIFFERENTIAL,  -- 差分バックアップであることを指定する
     COMPRESSION,
     STATS = 10;

最後にログバックアップです。復旧モデルが「完全」または「一括ログ」の場合のみ実行できます（「単純」では BACKUP LOG はエラーになります）。

backup-log.sql 
-- トランザクションログバックアップ:
-- 直近のログバックアップ以降の更新履歴をすべて取得する
BACKUP LOG SampleShop
TO DISK = 'C:\Backup\SampleShop_Log.bak'
WITH COMPRESSION,
     STATS = 10;

13.4 復元する

復元（リストア）は、取得したバックアップを正しい順序で適用していく作業です。基本の流れは次のとおりです。

復元の基本手順

  1. 1 （可能であれば）末尾のログバックアップ（tail-log backup）を取得する — 障害発生時点までの未バックアップの更新分を退避しておきます。
  2. 2 完全バックアップを WITH NORECOVERY で復元する。
  3. 3 （差分バックアップがあれば）最新の差分バックアップを WITH NORECOVERY で復元する。
  4. 4 復旧させたい時点までに必要なトランザクションログバックアップを、取得した順（古い順）に、途切れなくすべて WITH NORECOVERY で適用する。1本だけではありません。復元の基点（完全または差分）より後に取得されたログバックアップを、順番どおりに全部適用します。
  5. 5 最後の1本だけ WITH RECOVERY を指定し、データベースを利用可能な状態に戻す。

差分バックアップとログバックアップでは、復元時に使う本数の考え方が異なります。差分バックアップは常に直近の完全バックアップからの累積のため、復元時に使うのは最新の1本だけで十分です。一方、ログバックアップは直近のログバックアップ以降の更新分でしかないため、必要な分をすべて、取得した順に適用しなければ、途中の更新が抜け落ちてしまいます。

用語: NORECOVERY と RECOVERY

WITH NORECOVERY は「まだ後続のバックアップを適用する」ことをSQL Serverに伝えるオプションです。この状態のデータベースは「復元中」で、まだ接続して使うことはできません。一方 WITH RECOVERY を実行すると、その時点でデータベースは「使える状態」に確定し、それ以降はログを追加で適用できなくなります。RECOVERY は省略時の既定値です。続きのバックアップを適用するつもりで WITH NORECOVERY を書き忘れると、そこで復旧が確定してしまい、以降のログを適用できなくなるので注意してください。

restore-sequence.sql 
-- 1. （可能なら）末尾のログバックアップを取得しておく
BACKUP LOG SampleShop
TO DISK = 'C:\Backup\SampleShop_Log_Tail.bak'
WITH NORECOVERY;

-- 2. 完全バックアップを「復旧中」状態で復元する（この後も適用するのでRECOVERYしない）
RESTORE DATABASE SampleShop
FROM DISK = 'C:\Backup\SampleShop_Full.bak'
WITH NORECOVERY;

-- 3. 差分バックアップを重ねて復元する（あれば。最新の1本でよい）
RESTORE DATABASE SampleShop
FROM DISK = 'C:\Backup\SampleShop_Diff.bak'
WITH NORECOVERY;

-- 4. 差分より後のログバックアップを「古い順に、必要な分すべて」適用する
RESTORE LOG SampleShop
FROM DISK = 'C:\Backup\SampleShop_Log_01.bak'
WITH NORECOVERY;

RESTORE LOG SampleShop
FROM DISK = 'C:\Backup\SampleShop_Log_02.bak'
WITH NORECOVERY;

-- 5. 末尾のログバックアップまで含め、最後の1本だけRECOVERYで締める（ここでデータベースが使える状態になる）
RESTORE LOG SampleShop
FROM DISK = 'C:\Backup\SampleShop_Log_Tail.bak'
WITH RECOVERY;

ログバックアップを使うと、STOPAT オプションで「誤って削除する直前」のような特定時点まで戻す復元ができます。STOPAT は完全または一括ログの復旧モデルで利用できます（一括ログ復旧モデルでは、一括操作を含む期間の途中の時点には戻せない場合があります）。目標の時刻が既存のログバックアップの範囲に含まれているのであれば、この復元のために新たに末尾のログバックアップを取得する必要はありません（STOPAT を指定すること自体が、後述する安全確認のうち「末尾ログの未取得」に関する確認を満たします）。

注意: STOPAT は「目的の1本だけ」に付けるのではない

STOPAT は、復元シーケンス中のすべての RESTORE LOG 文に、同じ値を指定します。「目的の時刻を含むログバックアップだけに付ける」のは誤りです。また、STOPAT を使う復元では、末尾の復旧確定は RESTORE LOG ... WITH STOPAT = '…', RECOVERY のように1文にまとめず、ログをすべて WITH NORECOVERY で適用したあと、RESTORE DATABASE SampleShop WITH RECOVERY; を単独で実行して締めるのが基本の書き方です。指定した時刻が最後のログバックアップより後だった場合、データベースは復旧が確定しない（NORECOVERYの）ままになるため、対象時刻を含むログバックアップが揃っているか事前に確認してください。

restore-stopat.sql 
-- 特定時点（誤操作の直前）まで復旧する例
-- 1. 完全バックアップを復元する（まだ使える状態にしない）
--    STOPATを添えることで「特定時点への復元」であることを明示できる
--    （末尾ログを取っていない場合の安全確認もこれで通る）
RESTORE DATABASE SampleShop
FROM DISK = 'C:\Backup\SampleShop_Full.bak'
WITH NORECOVERY, STOPAT = '2026-08-28 10:15:00';

-- 2. 復旧させたい時点までのログバックアップを、古い順にすべて適用する
--    STOPATは「目的の1本だけ」ではなく、すべてのRESTORE LOGに同じ値を指定する
RESTORE LOG SampleShop
FROM DISK = 'C:\Backup\SampleShop_Log_01.bak'
WITH NORECOVERY, STOPAT = '2026-08-28 10:15:00';

RESTORE LOG SampleShop
FROM DISK = 'C:\Backup\SampleShop_Log_02.bak'
WITH NORECOVERY, STOPAT = '2026-08-28 10:15:00';

-- 3. 最後に RESTORE DATABASE を単独で実行し、復旧を確定する
RESTORE DATABASE SampleShop
WITH RECOVERY;

バックアップファイルの中身（論理ファイル名）を確認したいときは RESTORE FILELISTONLY を使います。また、元とは別の名前・別のパスへ復元したい場合は WITH MOVE でファイルの配置先を指定します。この章末の「やってみよう 13-1」でも使う書き方です。

restore-move.sql 
-- バックアップに含まれる論理ファイル名を確認する
RESTORE FILELISTONLY
FROM DISK = 'C:\Backup\SampleShop_Full.bak';

-- 別名データベースとして、別のパスに復元する（動作確認用）
RESTORE DATABASE SampleShop_Test
FROM DISK = 'C:\Backup\SampleShop_Full.bak'
WITH MOVE 'SampleShop' TO 'C:\Data\SampleShop_Test.mdf',
     MOVE 'SampleShop_log' TO 'C:\Data\SampleShop_Test_log.ldf',
     RECOVERY;

警告: 復元はデータを上書きします

安全確認（次の注意ボックスを参照）を通過して RESTORE DATABASE が実行されると、対象のデータベースはバックアップ時点の内容に置き換わります。本番環境で同名のデータベースに対して実行すると、それまでのデータが失われます。まずは本章の実習のように別名（例: SampleShop_Test）で復元して中身を確認するのが安全な手順です。本番のデータベースへ上書き復元する際は、対象名・対象環境（本番かどうか）を作業前に必ず指差し確認しましょう。

注意: WITH REPLACE は安全確認を上書きするオプション

SQL Server の RESTORE は既定で、誤った復元を防ぐための安全確認（safety check）を行います。「復元先と同じ名前のデータベースが既に存在し、かつそのバックアップセットが記録している元のデータベース名が復元先の名前と異なる」場合、別のデータベースを誤って上書きしてしまうのを防ぐため RESTORE はエラーで停止します。また、完全または一括ログ復旧モデルのデータベースを、末尾のログバックアップも取らず、STOPAT も指定せずに上書きしようとした場合も、失われるログがないか確認できないため停止します。WITH REPLACE は、こうした安全確認（別データベースの上書き・末尾ログ未取得での上書き・既存ファイルの上書き）を上書き（回避）して、強制的に復元を進める強いオプションです。Microsoft のドキュメントも「REPLACE の使用は稀であるべきで、十分に検討したうえでのみ使うこと」と明記しています。状況を十分に確認したうえで、本当に必要な場合にだけ使用してください。

13.5 定期実行と日常運用

バックアップは人手で毎回実行するものではなく、自動化しておくのが基本です。SQL Server には SQL Server Agent という組み込みのジョブスケジューラがあり、「毎日23時に完全バックアップ」のような処理を自動実行できます。

注意: Express Edition では Agent が使えない

SQL Server Agent は Developer / Standard / Enterprise では利用できますが、Express Edition では機能自体が搭載されていません。Express でバックアップを自動化したい場合は、Windows のタスクスケジューラや Linux の cron から sqlcmd でバックアップスクリプトを起動する方法が代わりになります。 また、本章の例で使っている WITH COMPRESSION（バックアップ圧縮）も Express Edition では利用できないため、Express で試す場合はこのオプションを外してください。

SSMS のオブジェクトエクスプローラーから「SQL Server Agent」→「ジョブ」を右クリックして新規ジョブを作成すると、実行するTSQL（バックアップコマンドなど）とスケジュール（毎日・毎週など）をGUIで設定できます。あわせて「メンテナンスプラン」というウィザードを使うと、バックアップに加えてインデックスの再構成や整合性チェック（DBCC CHECKDB）などをまとめて自動化できます。

自動化したら「動いているはず」で終わらせず、日常的に次の項目を確認する習慣をつけましょう。

日常運用チェックリスト

  • バックアップジョブの成功可否 — ジョブ履歴でエラー終了していないか確認する
  • バックアップ先のディスク空き容量 — 空きが尽きるとバックアップ自体が失敗する
  • SQL Server エラーログ — 予期しないエラーや警告が出ていないか（SSMSの「管理」→「SQL Server ログ」）
  • メンテナンスジョブの実行結果 — インデックス再構成・整合性チェックが正常に完了しているか

13.6 「バックアップは取れているか」より大事なこと

バックアップジョブが毎日「成功」と表示されていても、それだけでは安心できません。バックアップファイル自体が壊れていたり、必要なファイルの一部だけ取り漏れていたりしても、ジョブの見た目上は「成功」のままだからです。

重要ポイント: 復元テストこそが本当のバックアップ確認

「バックアップが取れている」と「必要なときに復元できる」はまったく別の話です。定期的に別名・別環境へ実際にRESTOREしてみて、中身が正しいことを確認する（＝復元テスト）まで行って、はじめて「バックアップが機能している」と言えます。本番と同じ手順を練習しておけば、実際の障害時にも落ち着いて対応でき、RTO（目標復旧時間）の短縮にも直結します。

13.7 PostgreSQLとの違い

バックアップ・復旧のしくみは、SQL Server と PostgreSQL で用語も設計思想もかなり異なります。あらかじめ対応関係を押さえておくと、どちらの製品のドキュメントを読んでも迷いにくくなります。

PostgreSQL との違い（バックアップと復旧）

観点 SQL Server PostgreSQL
論理バックアップ SSMS のスクリプト生成や BACPAC（.bacpac）。BACKUP DATABASE は論理形式ではない pg_dump / pg_dumpall（SQL文形式のダンプ）
物理バックアップ 同じ BACKUP DATABASE のバックアップファイル（.bak） pg_basebackup（データディレクトリ全体を複製）
特定時点への復旧 完全復旧モデル＋ログバックアップ（STOPAT） WALアーカイブ＋PITR（recovery_target_time）
「復旧モデル」という概念 単純／完全／一括ログを明示的に切り替える この概念自体が存在しない。WALは常に出力され、アーカイブするかどうかを設定で決める
スケジューラ SQL Server Agent（製品に内蔵） 製品には内蔵されず、cron や pg_cron など外部で組む
復元の手順 RESTORE DATABASE と RESTORE LOG を NORECOVERY で順に重ね、最後の1本だけ RECOVERY pg_restore（ダンプの場合）や、ベースバックアップ＋WAL再生（PITRの場合）

大きな違いは、SQL Server が「復旧モデル」という設定でログの扱いを切り替えるのに対し、PostgreSQL は常に WAL を出力し続け、それをアーカイブするかどうかだけを設定する点です。目的（特定時点への復旧）は同じでも、たどり着き方の設計が異なります。

用語: WAL と PITR

WAL は、データ本体を書き換える前に「何をどう変えるか」をログへ先に書き込む方式です（英語で Write-Ahead Logging、略して WAL。日本語では先行書き込みログと呼びます）。PITR は「何月何日の何時何分の状態」を指定して戻す復元のやり方です（正式名称: PITR＝特定時点復旧）。SQL Server の STOPAT による復元も、PostgreSQL の PITR も、目指すところは同じです。

ヒント: 用語だけ覚えれば概念は共通

「完全バックアップ＝ベースの複製」「ログ／WAL＝そこからの差分の記録」「特定時点への復旧＝ベース＋差分の記録を途中まで適用すること」という骨格はSQL ServerでもPostgreSQLでも同じです。製品ごとのコマンド名と設定項目の対応さえ押さえれば、片方の知識をもう片方に応用できます。

やってみよう 13-1: バックアップ→削除→復元で中身を確認する

実際に手を動かして「バックアップは復元できてこそ意味がある」ことを体感します。第5〜7章で作成した SampleShop データベースを使います。

手順

  1. 1 SampleShop の完全バックアップを取得する（13.3節の BACKUP DATABASE を実行）。
  2. 2 SampleShop の中の任意のテーブルをひとつ選び、DROP TABLE で削除する（実際の事故を再現）。
  3. 3 13.4節の WITH MOVE の例を参考に、手順1のバックアップから 別名（SampleShop_Test）で復元する。
  4. 4 SampleShop_Test 側で手順2で削除したテーブルが残っていること、データが正しいことを SELECT で確認する。
  5. 5 確認が終わったら DROP DATABASE SampleShop_Test; で検証用データベースを片付ける。

ねらい: 「バックアップを取る」だけでなく「復元して中身を確認する」までを一通り経験することで、13.6節の復元テストの重要性を実感として身につけます。SampleShop_Test という別名を使うことで、元の SampleShop を壊さずに安全に検証できる点にも注目しましょう。

理解度確認クイズ

  1. Q1. 差分バックアップとトランザクションログバックアップは、それぞれ何を取得しますか。違いを説明してください。

    回答を表示

    差分バックアップは「直近の完全バックアップ以降に変更されたデータそのもの」を取得します。一方、トランザクションログバックアップは「直近のログバックアップ以降の更新履歴（操作の記録）」を取得するもので、これを使うと特定時点まで正確に巻き戻せます。差分は直近の完全バックアップを基点としてしか使えず、ログバックアップは復旧モデルが「完全」または「一括ログ」のときだけ利用できます。 なお復元するときは、差分は最新の1本だけでよいのに対し、ログはその基点より後のものを古い順にすべて適用する必要があります。

  2. Q2. 復旧モデルが「単純（SIMPLE）」のデータベースでは、なぜトランザクションログバックアップが取得できないのですか。

    回答を表示

    「単純」モデルでは、コミットが完了したトランザクションのログはSQL Serverによって自動的に切り捨てられ、ログバックアップの対象として保持されないためです。そのため特定時点への復旧はできず、最後に取得した完全／差分バックアップの時点までしか戻せません。管理は簡単になりますが、RPO（許容できるデータ損失の範囲）は長くなります。

  3. Q3. 「バックアップジョブが毎日成功と表示されている」だけでは十分と言えない理由は何ですか。どう対応すればよいですか。

    回答を表示

    ジョブが「成功」と表示されていても、バックアップファイル自体が壊れていたり、実際に復元すると必要なデータが欠けていたりする可能性を否定できないためです。「取れているはず」で終わらせず、定期的に別名・別環境へ実際にRESTOREして中身を確認する復元テストを行うことで、初めてバックアップが機能していると確認できます。
