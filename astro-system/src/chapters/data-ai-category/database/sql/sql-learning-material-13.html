トランザクションと同時実行制御

これまでの章では、1つの INSERT や UPDATE を単発で実行してきました。しかし実務では「在庫を減らす」と「注文を登録する」のように、複数の変更をワンセットで確定させたい場面がほとんどです。この章では、その仕組みであるトランザクションと、複数人が同時にデータベースを使うときに何が起きるかを学びます。

この章はボリュームがあります。まずは 13.1 と、BEGIN / COMMIT / ROLLBACK とオートコミット（13.3・13.5）までを確実に身につければ十分です。それ以外（13.2・13.4・13.6〜13.9）は発展の内容なので、必要になったときに読み返せば問題ありません。

この章の学習目標

  • トランザクションがなぜ必要か、銀行振込の例で説明できる
  • ACID 特性の4つの意味を、自分の言葉で言い換えられる
  • BEGIN / COMMIT / ROLLBACK / SAVEPOINT を書ける
  • pgAdmin 4 と A5:SQL Mk-2 の自動コミット設定の違いを説明できる
  • ダーティリード・反復不能読み取り・ファントムリードの違いが分かる
  • 分離レベルと PostgreSQL の MVCC、デッドロックの基本を理解する

この章のSQLを実行する前に： 本章には、変更を COMMIT; で確定する例（13.3・13.4）と、BEGIN を付けずに実行して即座に確定される例（13.5）が出てきます。そのまま実行すると shop_db の在庫数や注文件数が実際に書き換わります。これらの例には直後に「後片付け」の SQL を用意してあるので、確認が終わったら必ず実行して元の状態に戻してください。そうすれば第14章まで、第5章の投入直後と同じデータで進められます。戻し方が分からなくなった場合は、第10章の「困ったときは: shop_db を元に戻す」（reset_shop_db.sql）の手順で作り直せます。

13.1 なぜトランザクションが必要か 必須

銀行の口座振替を思い浮かべてください。「Aさんの口座から1万円を引いて、Bさんの口座に1万円を足す」という処理は、内部的には2つの独立した更新です。もしこの2つを別々にバラバラに実行していたらどうなるでしょうか。

flowchart TD A["A口座から1万円を引く"] --> B{"ここでシステム障害が発生？"} B -->|"いいえ（正常に継続）"| C["B口座に1万円を足す"] C --> D["まとめて確定（COMMIT）
→ 合計金額は変わらず整合性が保たれる"] B -->|"はい（電源断・接続切れなど）"| E["B口座への入金は
実行されないまま処理が中断"] E --> F["Aさんからは引かれたのに
Bさんには届いていない
→ 1万円が消えてしまう"]

これは決して起きてはならない事態です。この問題を防ぐ考え方がトランザクションです。トランザクションとは、複数の SQL 文を「1つのまとまった作業」として扱い、「全部まとめて成功」か「まとめて無かったことにする」のどちらかしか許さないという仕組みです。

用語の整理: トランザクション

英語の transaction は「取引」の意味です。データベースの世界では「これ以上分割できない、ひとまとまりの処理単位」を指します。途中でどんなに多くの SQL 文を実行しても、最終的に確定（COMMIT）するか取り消す（ROLLBACK）かのどちらかしかありません。

13.2 ACID特性 — トランザクションが守る4つの約束 発展

トランザクションが満たすべき性質は、頭文字を取って ACID（アシッド）特性と呼ばれます。難しい用語ですが、1つずつ平易に言い換えれば怖くありません。

特性 一言で言うと 振込の例で言えば
原子性
Atomicity		 「全部やる」か「全部やらない」かのどちらかだけ 引き出しだけ成功して入金が失敗する、という中途半端な状態は起きない
一貫性
Consistency		 処理の前後で、決められたルールが必ず守られている 振込の前後で、全口座の残高合計は変わらない
独立性
Isolation		 他の処理が同時に動いていても、お互いに影響し合わない 自分の振込処理の途中経過が、他の人が見ている残高に紛れ込まない
永続性
Durability		 一度確定した結果は、その直後に停電が起きても消えない COMMIT 直後にサーバーが落ちても、振込結果はディスクに残っている

このうち独立性（Isolation）は少し特殊で、「どこまで厳密に他人の影響を遮断するか」を段階的に選べます。これが 13.7 で学ぶ分離レベルです。まずは「トランザクションはこの4つを守る約束事」という全体像を押さえておけば十分です。

13.3 基本の書き方 — BEGIN・COMMIT・ROLLBACK 必須

PostgreSQL でトランザクションを明示的に扱うには、BEGIN; で開始し、うまくいったら COMMIT; で確定、失敗や取り消したい事情があれば ROLLBACK; で全部を無かったことにします。shop_db を使って、「在庫を1つ減らして、注文を登録する」処理をまとめてみましょう。

transaction-order.sql 
-- 在庫を減らして注文を登録する処理を1つのまとまりとして実行
BEGIN;

UPDATE products
SET stock_quantity = stock_quantity - 1
WHERE product_id = 3;

INSERT INTO orders (customer_id, order_date, status)
VALUES (1, CURRENT_DATE, '受付');

COMMIT;  -- ここで初めて両方とも確定される

後片付け： 上の例を COMMIT; まで実行すると、注文が1件増え、在庫が1つ減った状態が確定します。第14章までデータを第5章の投入直後の状態に保っておきたい場合は、次の手順で元に戻しておきましょう。

cleanup-13-3.sql 
-- ①いま追加された注文の order_id を確認する
SELECT order_id, customer_id, order_date FROM orders ORDER BY order_id DESC LIMIT 1;

-- ②確認した order_id を指定して、追加した注文と減らした在庫を元に戻す
BEGIN;

DELETE FROM orders WHERE order_id = 16;   -- ①で確認した値に読み替える

UPDATE products
SET stock_quantity = stock_quantity + 1
WHERE product_id = 3;

COMMIT;

COMMIT; を実行するまで、この変更は自分の接続からしか見えません。他の人が同時に SELECT しても、まだ変更前の値が見えます。では実際に ROLLBACK すると本当に元に戻るのか、SELECT で確認してみましょう。

rollback-check.sql 
BEGIN;

SELECT stock_quantity FROM products WHERE product_id = 3;  -- 例: 20

UPDATE products SET stock_quantity = stock_quantity - 1
WHERE product_id = 3;

SELECT stock_quantity FROM products WHERE product_id = 3;  -- 例: 19

ROLLBACK;  -- ここで変更を取り消す

SELECT stock_quantity FROM products WHERE product_id = 3;  -- 20に戻っている

重要: 「先にSELECTで確認」の習慣がここでも活きる

第10章で「UPDATE の前に SELECT で対象を確認する」習慣を学びました。トランザクションでも同じです。COMMIT する前に SELECT で変更後の状態を確認し、想定と違えば ROLLBACK すればやり直しがききます。

13.4 SAVEPOINT — 一部分だけを取り消す 発展

ROLLBACK はトランザクション全体を取り消しますが、「注文ヘッダーはそのまま残し、明細の登録だけをやり直したい」ということもあります。そこで使うのが途中に目印を置く SAVEPOINT です。

savepoint-example.sql 
BEGIN;

INSERT INTO orders (customer_id, order_date, status)
VALUES (2, CURRENT_DATE, '受付');

SAVEPOINT before_items;  -- ここに目印を置く

-- order_id は直前のINSERTで採番された実際の値に読み替える（例では16と仮定）
-- product_id = 99 は products に存在しないため、この行はエラーになる
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (16, 99, 1, 500);  -- 商品IDを間違えてしまった

ROLLBACK TO SAVEPOINT before_items;  -- 明細の失敗だけを取り消す

COMMIT;  -- 注文ヘッダーはそのまま確定される

ROLLBACK TO SAVEPOINT 名前; は、トランザクション自体は継続したまま、その目印より後の変更だけを取り消します。1つのトランザクション内に複数の SAVEPOINT を置くこともできます。

この例の product_id = 99 は products に存在しない商品なので、INSERT は外部キー制約違反のエラーになります。PostgreSQL では、トランザクションの途中でエラーが起きると、それ以降の SQL は「現在のトランザクションはアボートしました」というエラーで実行できなくなります。しかし SAVEPOINT を置いてあれば、ROLLBACK TO SAVEPOINT で失敗の直前の状態まで戻り、そのまま処理を続けられます。これが SAVEPOINT の実用的な使いどころです。

後片付け： この例も COMMIT; まで実行すると注文ヘッダーが1件残ります。第14章までデータを第5章の投入直後の状態に保っておきたい場合は、下の SQL で取り消しておきましょう。

cleanup-13-4.sql 
-- ①いま確定された注文の order_id を確認する
SELECT order_id, customer_id, order_date FROM orders ORDER BY order_id DESC LIMIT 1;

-- ②確認した order_id を指定して削除する（明細は登録されていないので orders だけでよい）
DELETE FROM orders WHERE order_id = 17;   -- ①で確認した値に読み替える

用語メモ：シーケンス — GENERATED ALWAYS AS IDENTITY の連番を発行している裏方の仕組みです。行を DELETE しても発行済みの番号は戻らないため、次に追加する注文の order_id は 16・17 ではなく、その続きの番号になります。件数さえ元に戻っていれば、以降の章の学習に支障はありません。

13.5 自動コミット — BEGINを書かなかったらどうなるか 必須

ここまでの章では、一度も BEGIN を書かずに UPDATE や INSERT を実行してきました。それでも変更はきちんと反映されています。これは PostgreSQL が「BEGIN を書かない単独の SQL 文は、実行した瞬間に自動的に COMMIT される」という自動コミット（オートコミット）の仕組みを持っているためです。

autocommit.sql 
-- BEGINを書かない単独のUPDATEは、実行した瞬間に確定する
UPDATE products
SET stock_quantity = stock_quantity - 1
WHERE product_id = 5;
-- この後でROLLBACKしても、既に確定済みなので取り消せない

-- 後片付け：確認できたら在庫を元に戻す（この文も実行した瞬間に確定する）
UPDATE products
SET stock_quantity = stock_quantity + 1
WHERE product_id = 5;

ただし、この「自動コミットかどうか」はツール側の設定によっても変わります。本ガイドで使う2つのツールでは、既定の挙動が異なるので必ず押さえておきましょう。

ツール 既定の挙動 切り替え方法
pgAdmin 4 クエリツールは既定で自動コミット。BEGIN を書かなければ1文ごとに即確定される クエリツールのメニューから自動コミットのオン／オフを切り替え可能
A5:SQL Mk-2 接続設定で自動コミットのオン／オフを選択できる。オフの場合は明示的な COMMIT が必須 接続情報の編集画面にある自動コミット設定を確認・変更する

注意: コミット忘れは「自分専用の変更」を作ってしまう

A5:SQL Mk-2 で自動コミットをオフにしている場合、UPDATE を実行しても COMMIT を忘れると変更が確定しません。それだけならまだしも、変更した行はロックされたままになり、他の人がその行を更新しようとすると自分が接続を切るまで待たされ続けます。「更新したら忘れずに COMMIT」を必ず習慣にしてください。

13.6 同時実行で起こる問題 発展

複数の人が同時に同じテーブルを読み書きすると、1人で使っているときには起きない、奇妙な見え方の問題が起こることがあります。代表的な3つを押さえておきましょう。

現象 何が起きるか（具体例）
ダーティリード
Dirty Read		 他のトランザクションがまだ COMMIT していない変更を読んでしまう。その後、相手が ROLLBACK すると、自分が読んだ値は存在しなかったことになる
反復不能読み取り
Non-Repeatable Read		 同じトランザクションの中で同じ行を2回 SELECT したのに、間に他人の COMMIT が挟まって1回目と2回目で値が変わってしまう
ファントムリード
Phantom Read		 同じ条件で2回 SELECT したのに、間に他人が行を INSERT して COMMIT したことで、2回目だけ「幽霊」のような行が増えて見える

3つとも「自分の処理の途中に、他人の変更が割り込んでくる」ことが原因です。この割り込みをどこまで防ぐかを決めるのが、次の分離レベルです。

13.7 分離レベル — どこまで他人の影響を遮断するか 発展

SQL 標準では4段階の分離レベル（Isolation Level）が定義されています。レベルを上げるほど同時実行時の制約は強くなりますが、それは単に「待たされやすくなる」だけではありません。PostgreSQL では、競合を検知したトランザクションが待たされるのではなく、直列化失敗（serialization failure）というエラーで中断されることがあります（この節の後半で扱います）。まずは標準SQLが定義する4段階と、PostgreSQL の実装の対応を見てみましょう。

分離レベル
（標準SQLの名称）		 標準SQLの定義
（防ぐと定義されている問題）		 PostgreSQL の実装
（実際に防げる問題）
READ UNCOMMITTED 何も防がない（ダーティリードを許す） 指定してもREAD COMMITTED として動作する（PostgreSQL 独自の挙動）。ダーティリードは発生しない
READ COMMITTED ダーティリードのみ防ぐ PostgreSQL の既定値。文（SELECT 1回など）ごとに最新の COMMIT 済みデータを見る
REPEATABLE READ ダーティリード＋反復不能読み取りを防ぐ（ファントムリードは標準SQLの定義上は起こりうる） ファントムリードも発生しない（PostgreSQL 独自の挙動。詳細は次の補足を参照）
SERIALIZABLE 3つすべてを防ぐ 最も厳格。複数のトランザクションが「順番に1つずつ実行した」のと同じ結果を保証する。競合を検知すると片方が直列化失敗エラーで中断されることがある

補足: PostgreSQL の REPEATABLE READ ではファントムリードは発生しない

標準SQLでは REPEATABLE READ でもファントムリードが起きうると定義されていますが、PostgreSQL の REPEATABLE READ では、ファントムリードは発生しません。 これは、PostgreSQL がこの分離レベルを「トランザクション開始時点のデータの断面（スナップショット）を最後まで見続ける」という仕組みで実装しているためです。トランザクション中に他人が行を INSERT して COMMIT しても、自分のスナップショットには反映されないので、同じ条件の SELECT を何度実行しても行数は増えません。標準SQLの最低ラインより厳しい動作になっている一例です。

分離レベルは、トランザクションの先頭で SET TRANSACTION ISOLATION LEVEL を使って指定します。

isolation-level.sql 
-- このトランザクションだけ分離レベルをREPEATABLE READにする
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT stock_quantity FROM products WHERE product_id = 3;
-- 他の接続がこの行を更新してCOMMITしても…

SELECT stock_quantity FROM products WHERE product_id = 3;
-- トランザクション開始時点と同じ値が返る

COMMIT;

注意: 分離レベルを上げると「待たされる」だけでなく「エラーで中断される」ことがある 発展

READ COMMITTED より厳しい分離レベル（REPEATABLE READ・SERIALIZABLE）では、他のトランザクションとの競合を検知すると、PostgreSQL が待たせる代わりに直列化失敗（serialization failure）というエラーを返してそのトランザクションを中断することがあります。エラーメッセージの例は次のとおりです。

ERROR:  could not serialize access due to concurrent update

このため、REPEATABLE READ や SERIALIZABLE を使う場合は、アプリケーション側で「直列化失敗のエラーを受け取ったらトランザクションを最初からやり直す」処理を組み込んでおく必要があります。READ COMMITTED のみを使う一般的な業務処理では、通常はこの考慮は不要です。

普段の学習や多くの業務システムでは、既定の READ COMMITTED のままで問題ありません。「集計結果の一貫性が特に重要な処理」や「在庫の取り合いのような競合が起きやすい処理」でのみ、より厳しいレベルを検討します。

13.8 PostgreSQL の MVCC — 読み取りが書き込みを邪魔しない仕組み 発展

「複数人が同時に読み書きしても安全」と言われても、内部では何が起きているのでしょうか。PostgreSQL は MVCC（Multi-Version Concurrency Control／多版型同時実行制御）という方式を採用しています。

ポイントは、行を更新するとき、古いデータをその場で上書きせず、新しい版を追記するという点です。古い版はしばらくディスク上に残り続けます。この「追記型」のおかげで、次のような特徴が生まれます。

重要: 通常の SELECT と UPDATE は互いをブロックしにくい

通常の SELECT と UPDATE は、MVCC により、互いをブロックしにくくなっています。誰かが行を更新している最中でも、他の人は更新前の古い版を読み続けられるため、SELECT は UPDATE の完了を待たされにくく、逆に SELECT が実行中でも UPDATE は待たされにくくなっています。「読み取り専用のロックで書き込みが止まる」という、単純なロック方式でありがちな渋滞が起きにくいのが PostgreSQL の強みです。

ただし例外があります。 SELECT ... FOR UPDATE のように行にロックをかける SELECT（発展）は、他のトランザクションの更新と待ち合わせになります。また ALTER TABLE などの一部の操作は通常の SELECT ともぶつかります。

これは、更新のたびに同じ場所を直接書き換える「ロック方式」を採る一部の RDBMS とは異なる考え方です（製品や設定によって細部は異なります）。いずれの方式でも、更新する行同士が競合したときは待たされる点は共通です（13.9 で扱います）。

一方で、追記型ゆえの副作用もあります。古い版はいつまでも増え続けるわけにはいかないため、不要になった古い版を回収する仕組みが必要です。これを担うのが VACUUM というコマンドです。VACUUM の詳しい役割は、運用の基礎を扱う第14章で学びます。

13.9 ロックとデッドロック 発展

MVCC は読み取りと書き込みの競合を避けてくれますが、同じ行を同時に更新しようとする書き込み同士は話が別です。ある行を UPDATE しているトランザクションがコミットまたはロールバックするまで、その行に対する他の UPDATE は行ロックによって待たされます。

通常はこの「待ち」は一瞬で解消されますが、2つのトランザクションがお互いの持っている行を、お互いが待ち合う状況になると、永遠に解決しない膠着状態が生まれます。これをデッドロックと呼びます。

flowchart LR T1["トランザクション1
行Aをロック中"] -->|"行Bを更新しようとして待機"| T2["トランザクション2
行Bをロック中"] T2 -->|"行Aを更新しようとして待機"| T1

トランザクション1は行Bが空くのを待ち、トランザクション2は行Aが空くのを待ち続け、どちらも一生解放されません。幸い、PostgreSQL はデッドロックを自動的に検出し、どちらか一方のトランザクションを強制的にエラーで中断します。中断されなかった方は処理を続けられます。

ヒント: デッドロックを防ぐ2つのコツ

(1) 更新する順序をアプリ全体で揃える: 常に「products を先に、orders を後に」のようにルールを決めておけば、お互いが逆順で待ち合う状況が生まれません。

(2) トランザクションを短く保つ: BEGIN してから COMMIT するまでの間に、画面入力待ちのような長い処理を挟まないこと。ロックを持ち続ける時間が短いほど、他人と鉢合わせる確率も下がります。

やってみよう 13-1: 2つの接続で「COMMIT前後の見え方」を確認する

pgAdmin 4 のクエリツールを2つ（または pgAdmin 4 と A5:SQL Mk-2 を1つずつ）開き、片方の変更がもう片方からいつ見えるようになるかを実際に目で確認します。

手順

  1. 1 接続ウィンドウA・Bをそれぞれ開き、両方で SELECT stock_quantity FROM products WHERE product_id = 3; を実行して今の値を控える。
  2. 2 ウィンドウAで BEGIN; の後、UPDATE products SET stock_quantity = stock_quantity - 1 WHERE product_id = 3; を実行する（COMMIT はまだしない）。
  3. 3 ウィンドウBで同じ SELECT を実行する。ウィンドウAの変更はまだ見えず、手順1と同じ値のはずである。
  4. 4 ウィンドウAで COMMIT; を実行する。その後ウィンドウBで再度 SELECT すると、今度は減った値が見えることを確認する。
  5. 5 余裕があれば、手順4の代わりに ROLLBACK; を実行し、ウィンドウBから見える値が最初のまま変わっていないことも確認してみる。
  6. 6 後片付け: 手順4で COMMIT; まで実行した場合は、在庫数が1つ減ったままになっています。UPDATE products SET stock_quantity = stock_quantity + 1 WHERE product_id = 3; を実行して、元の値に戻しておく。

ねらい: 「COMMIT するまで他の接続からは変更が見えない」という独立性（Isolation）を、頭ではなく手で体感することが目的です。ウィンドウAで UPDATE 中にウィンドウBが待たされないことにも注目してください（読み取りは書き込みをブロックしない）。

理解度確認クイズ

  1. Q1. ACID特性のうち「独立性（Isolation）」とは何ですか。一言で説明してください。

    回答を表示

    複数のトランザクションが同時に実行されても、お互いの途中経過が影響し合わない性質です。ただし「どこまで厳密に遮断するか」は分離レベルによって段階的に選べます。

  2. Q2. pgAdmin 4 のクエリツールと A5:SQL Mk-2 では、自動コミットの扱いにどのような違いがありますか。

    回答を表示

    pgAdmin 4 のクエリツールは既定で自動コミットになっており、メニューから切り替えられます。A5:SQL Mk-2 は接続設定で自動コミットのオン／オフを選べ、オフにした場合は明示的な COMMIT を忘れると変更が確定しないだけでなく、行がロックされたままになり他の人をブロックしてしまいます。

  3. Q3. 同じトランザクション内で同じ行を2回 SELECT したら、間に他人の COMMIT が挟まって値が変わっていた。これは何と呼ばれる現象ですか。

    回答を表示

    反復不能読み取り（Non-Repeatable Read）です。分離レベルを REPEATABLE READ 以上にすることで防げます。

  4. Q4. PostgreSQL の MVCC によって、通常の SELECT と UPDATE が互いをブロックしにくくなっているのはなぜですか。また、ブロックされる例外にはどのようなものがありますか。デッドロックが起きたときに PostgreSQL はどう対応しますか。

    回答を表示

    更新時に古いデータをその場で上書きせず、新しい版を追記する「多版型（追記型）」の仕組みだからです。他の人は更新中でも古い版を読み続けられるため、通常の SELECT は UPDATE の完了を待たされにくくなっています。ただし SELECT ... FOR UPDATE のように行にロックをかける SELECT は他の更新と待ち合わせになり、ALTER TABLE なども通常の SELECT とぶつかります。デッドロックが発生した場合、PostgreSQL は自動的に検出し、どちらか一方のトランザクションを強制的にエラーで中断します。
