ホーム SQL入門 第10章
第10章 所要時間: 約60分

データの追加・更新・削除

ここまでの章では、データベースの中身を読み取る SELECT 文を学んできました。この章からは視点を変えて、データを書き換える3つの命令 —— INSERT（追加）・UPDATE（更新）・DELETE（削除） —— を学びます。SELECT と違い、これらの命令は実行すると元のデータが失われ、簡単には元に戻せません。書き方そのものはシンプルですが、この章では「事故を起こさない使い方」を中心テーマとして扱います。

この章の学習目標

  • INSERT・UPDATE・DELETE が SQL の中でどのような役割を持つかを理解する
  • 列を指定した安全な INSERT の書き方、複数行の追加、別テーブルからのコピーができる
  • UPDATE で SET と WHERE を正しく組み合わせ、既存の値を使った更新ができる
  • WHERE 句を書き忘れる事故を防ぐための実務的な確認手順を身につける
  • DELETE と TRUNCATE の違い、RETURNING 句・ON CONFLICT の使いどころが分かる

10.1 データを書き換える3つの命令の位置づけ

第1章で見た SQL の4分類のうち、SELECT・INSERT・UPDATE・DELETE はまとめて DML（データ操作言語）に分類されます。SELECT はテーブルの中身をただ読み取るだけで、何度実行してもデータそのものは変化しません。ところがこれから学ぶ3つの命令は、実行するとテーブルの中身が実際に書き換わります。

flowchart LR A[("customersテーブル")] -->|INSERT| B["行が増える"] A -->|UPDATE| C["既存の行の値が変わる"] A -->|DELETE| D["行が減る"]
命令 役割 テーブルへの影響
INSERT 新しい行を追加する 行数が増える
UPDATE 既存の行の値を書き換える 行数は変わらず、中身が変わる
DELETE 既存の行を取り除く 行数が減る

重要: これらの命令は「元に戻せない」のが基本

SELECT は何度実行してもデータを壊しませんが、INSERT・UPDATE・DELETE は実行した瞬間にテーブルの中身が書き換わります。うっかり実行してしまっても、初期状態のようにボタン一つで元に戻す仕組みは標準では用意されていません。第13章で学ぶトランザクション（BEGIN / COMMIT / ROLLBACK）を使うと「確定する前に取り消す」ことができるようになりますが、この章ではまず、トランザクションに頼らなくても事故を起こさない書き方・確認の仕方を身につけます。

10.2 INSERT — 新しい行を追加する

INSERT の基本形は「どのテーブルの、どの列に、どんな値を入れるか」を書くことです。列名を明示する書き方を必ず使うようにしましょう。

insert-basic.sql 
-- 列名を明示する書き方（推奨）
-- 値の対応関係が一目で分かり、列の順序が変わっても壊れない
INSERT INTO customers (customer_name, email, prefecture, registered_at)
VALUES ('高橋 健太', 'kenta.takahashi@example.com', '福岡県', current_date);

列名を省略して INSERT INTO customers VALUES (...) と書くこともできますが、これは非推奨です。テーブルの全列に、定義された順序どおりの値を渡さなければならず、後から列を追加・並べ替えた瞬間にこの SQL は壊れてしまいます。

insert-omit-columns.sql 
-- 列名を省略する書き方（非推奨）
-- テーブルの全列に、定義順どおりの値を渡す必要がある
-- customer_id は自動採番でも、DEFAULT を明示的に書かなければならない
INSERT INTO customers
VALUES (DEFAULT, '鈴木 愛', 'ai.suzuki@example.com', '愛知県', '1988-02-20', current_date);
-- 列の追加や順序変更があると、このSQLは即座に動かなくなる

複数の行を一度に追加したいときは、VALUES の後ろにカンマ区切りで複数の組を並べます。1行ずつ INSERT を実行するより効率的です。

insert-multi.sql 
-- 複数行を1回のINSERTでまとめて追加する
INSERT INTO products (product_name, category, unit_price, stock_quantity, is_active)
VALUES
    ('方眼ノートB5', '文具', 350, 200, true),
    ('蛍光ペン5色セット', '文具', 480, 300, true),
    ('クリアファイル10枚組', '文具', 220, 150, true);

customer_id のように GENERATED AS IDENTITY（第5章）で自動採番される列は、INSERT の列一覧からそのまま省略すれば PostgreSQL が自動的に採番してくれます。列一覧に含めたい場合だけ、値の位置に DEFAULT と書きます。また、別のテーブルからデータをコピーしたい場合は VALUES の代わりに SELECT を書く INSERT ... SELECT が使えます。

insert-select.sql 
-- 東京都の顧客だけを、バックアップ用テーブルへコピーする
-- customers_backup は同じ列構成であらかじめ用意しておく
INSERT INTO customers_backup (customer_id, customer_name, prefecture)
SELECT customer_id, customer_name, prefecture
FROM customers
WHERE prefecture = '東京都';

ヒント: INSERT ... SELECT は「SELECT文が書ければ何でも流し込める」

SELECT 部分には WHERE・JOIN・集計などをそのまま組み込めます。「条件に合う行だけを別テーブルへ移す」「集計結果を集計用テーブルに保存する」といった使い方が、実務ではよく登場します。

10.3 UPDATE — 既存の行を書き換える

UPDATE の基本形は次のとおりです。SET で「どの列をどんな値に変えるか」を、WHERE で「どの行を対象にするか」を指定します。

update-basic.sql 
-- 商品番号3の単価を130円に変更する
UPDATE products
SET unit_price = 130
WHERE product_id = 3;

SET にはカンマ区切りで複数の列を並べられます。さらに、更新後の値に更新前の自分自身の値を使うこともできます。「在庫を1つ減らす」のように、現在の値を基準に増減させたい場面でよく使う書き方です。

update-multi-existing.sql 
-- 複数列を同時に更新し、既存の値を使って在庫を1つ減らす
UPDATE products
SET unit_price = 1200,
    stock_quantity = stock_quantity - 1
WHERE product_id = 7;

stock_quantity = stock_quantity - 1 は「右辺の stock_quantity（更新前の値）から1を引いた結果を、左辺の stock_quantity（更新後の値）にする」という意味です。プログラミング未経験の方には少し不思議に見えるかもしれませんが、Excel のセルに =A1-1 と入れる感覚に近いものです。

10.4 WHERE 忘れの事故を防ぐ（この章でいちばん大事な話）

UPDATE・DELETE の WHERE 句は、SELECT の WHERE 句と違って省略すること自体はエラーになりません。しかし省略すると「テーブルの全行」が対象になります。次の例を見てください。

where-mistake.sql 
-- 危険な例: WHEREを書き忘れると全商品が対象になる
UPDATE products
SET unit_price = unit_price * 0.9;
-- 「文具だけ1割引きにしたかった」つもりでも
-- 12件すべての商品の単価が9割になってしまう

警告: WHERE忘れは実務で実際に起きる代表的な事故

「WHERE を書き忘れた UPDATE で全顧客のメールアドレスが同じ値に上書きされた」「WHERE なしの DELETE で本番テーブルのデータが全件消えた」という事故は、実際の開発現場でたびたび報告されています。ミスをした人の能力の問題ではなく、確認せずにいきなり実行する習慣そのものが原因です。次の手順を身につけることで、この事故はほぼ防げます。

事故を防ぐ考え方はシンプルです。UPDATE / DELETE をいきなり書かず、まず同じ条件で SELECT するのです。

flowchart TD A["①同じ条件でSELECT
対象行を目で確認する"] --> B["②件数を数える
count(*)で件数を把握"] B --> C["③UPDATE／DELETEに書き換える
WHERE条件はSELECTと同じにする"] C --> D["④実行結果の件数を確認
想定した件数と一致するか"] D -->|一致する| E["完了"] D -->|一致しない| F["ロールバックし
WHERE条件を見直す"]

事故を防ぐ4ステップ

  1. 1 これから使う WHERE 条件のまま、まず SELECT して対象行を目で確認する。
  2. 2 SELECT count(*) で件数を数え、想定と合っているかを確認する。
  3. 3 問題なければ、まったく同じ WHERE 条件のまま SELECT を UPDATE / DELETE に書き換えて実行する。
  4. 4 実行結果に表示される件数（後述の UPDATE 3 等）が、手順2で数えた件数と一致するか確認する。

コツ: SELECT からUPDATE/DELETEへ書き換えるときは、WHERE より前の部分だけを書き換え、WHERE 句そのものはコピー＆ペーストで使い回すと取りこぼしがありません。

safe-procedure.sql 
-- ①同じ条件でSELECTし、対象行を目で確認する
SELECT product_id, product_name, unit_price FROM products WHERE category = '文具';

-- ②件数を数える
SELECT count(*) FROM products WHERE category = '文具';

-- ③確認できたら、同じWHERE条件でUPDATEに書き換える
UPDATE products SET unit_price = unit_price * 0.9 WHERE category = '文具';

10.5 DELETE と TRUNCATE — 行を削除する2つの方法

DELETE は WHERE 句で条件を指定し、条件に合う行だけを削除します。前章までと同じ感覚で、SELECT の WHERE をそのまま使い回せます。

delete-basic.sql 
-- キャンセルされた注文を1件削除する（事前にSELECTで確認済みとする）
DELETE FROM orders
WHERE order_id = 20;

WHERE を付けずに DELETE FROM orders; と書くと、テーブルの全行が削除されます。似たことをする命令に TRUNCATE TABLE がありますが、両者は仕組みがまったく異なります。

truncate.sql 
-- テーブルの中身を全件削除し、自動採番も1から振り直す
TRUNCATE TABLE order_items RESTART IDENTITY;
観点 DELETE（WHEREなし） TRUNCATE TABLE
条件を絞れるか WHERE で一部の行だけ削除できる できない。常に全行が対象
実行速度 1行ずつ処理するため、行数が多いと遅い テーブルごと初期化するイメージで高速
トランザクション内での取り消し COMMIT前ならROLLBACKで取り消せる PostgreSQLではROLLBACK可能（製品による）
自動採番のリセット リセットされない（続きの番号から採番） RESTART IDENTITY を付ければ1から再開

本ガイドの shop_db では、orders.customer_id が customers を、order_items.order_id / order_items.product_id がそれぞれ orders / products を外部キーで参照しています（第2章・第5章）。参照されている側の行は、参照している行が残っている限り削除できません。

fk-error.sql 
-- 顧客3番を削除しようとすると、ordersから参照されているため失敗する
DELETE FROM customers WHERE customer_id = 3;
-- エラー: update or delete on table "customers" violates foreign key constraint
-- ON DELETE CASCADE を設定していれば、関連する注文も連動して削除される

用語の整理: ON DELETE CASCADE

外部キー制約を定義するとき（第5章）に ON DELETE CASCADE を付けておくと、参照される側（例: customers）の行を削除した際に、参照している側（例: orders）の関連行も自動的に一緒に削除されます。便利な反面、意図せず大量の関連データを巻き込んで消してしまう可能性もあるため、業務データでは慎重に採否を検討します。

10.6 PostgreSQL 独自の便利機能 — RETURNING と ON CONFLICT

PostgreSQL の INSERT・UPDATE・DELETE には、標準SQLにはない便利な句がいくつかあります。まずは RETURNING です。書き換えた行の内容を、その場で SELECT のように受け取れます。

returning-insert.sql 
-- 追加した行のIDをその場で受け取る
-- 自動採番されたcustomer_idの取得に便利
INSERT INTO customers (customer_name, email)
VALUES ('伊藤 桜', 'sakura.ito@example.com')
RETURNING customer_id;

自動採番される customer_id は、INSERT する時点ではまだ何番になるか分かりません。RETURNING を使えば、その場で発番された番号を受け取り、続けて注文を登録するといった処理にすぐ使えます。UPDATE・DELETE でも同様に使えます。

returning-update-delete.sql 
-- 更新後の在庫数をその場で確認する
UPDATE products SET stock_quantity = stock_quantity - 1
WHERE product_id = 5
RETURNING product_id, stock_quantity;

-- 削除した行の内容をその場で確認する
DELETE FROM orders WHERE order_id = 20 RETURNING *;

もう1つが INSERT ... ON CONFLICT、通称 UPSERT（UPDATE と INSERT を合わせた造語）です。UNIQUE 制約や主キーが重複したときの動きを、その場で指定できます。

upsert.sql 
-- emailが重複していれば名前を上書きし、なければ新規追加する（UPSERT）
INSERT INTO customers (customer_name, email)
VALUES ('伊藤 桜', 'sakura.ito@example.com')
ON CONFLICT (email)
DO UPDATE SET customer_name = EXCLUDED.customer_name;

-- 重複していたら何もしない（無視する）
INSERT INTO customers (customer_name, email)
VALUES ('伊藤 桜', 'sakura.ito@example.com')
ON CONFLICT (email) DO NOTHING;

用語の整理: EXCLUDED

EXCLUDED は「今回INSERTしようとして重複した、その新しい値」を指す特別な名前です。EXCLUDED.customer_name は「これから入れようとしていた新しい氏名」を意味します。ON CONFLICT には、先に ON CONFLICT (対象の列) のように、重複判定に使う UNIQUE 制約・主キーの列を指定する必要があります。

10.7 実行結果の読み方

pgAdmin 4 でクエリを実行すると、下部の Messages タブに実行結果が表示されます（A5:SQL Mk-2 でも同様の情報が表示されます）。この表示を読めるようになると、「想定どおりの件数が処理されたか」をその場で確認できます。

messages.txt 
INSERT 0 1
UPDATE 3
DELETE 1
TRUNCATE TABLE
表示例 意味
INSERT 0 1 1行が追加された（先頭の0は昔のPostgreSQLで使われていた識別子の名残で、現在は常に0）
UPDATE 3 3行が更新された
DELETE 1 1行が削除された
TRUNCATE TABLE テーブルが初期化された（件数は表示されない）

重要: 数字を見る癖をつける

UPDATE 3 と表示されたのに、事前の SELECT で数えた対象は1件だけだった —— このズレに気づけるかどうかが、事故を未然に防げるかの分かれ目です。実行結果の数字は、必ず一度目を通す習慣をつけましょう。

やってみよう 10-1: 顧客・商品を追加し、在庫を更新し、注文を削除する

shop_db に対して INSERT・UPDATE・DELETE を実際に実行してみましょう。UPDATE・DELETE の前には必ず SELECT で対象を確認するのがこの演習の一番大事なルールです。

手順

  1. 1 列名を明示した INSERT で、customers に新しい顧客を1件追加する。実行後 RETURNING customer_id を付けて、発番された顧客番号を確認する。
  2. 2 products に新しい商品を1件追加する。VALUES (...), (...) を使い、2件まとめて追加してもよい。
  3. 3 手順1で追加した顧客番号を条件に、まず SELECT * FROM products WHERE product_id = ... のように対象商品を確認してから、stock_quantity = stock_quantity - 1 で在庫を1つ減らす UPDATE を実行する。
  4. 4 SELECT count(*) FROM orders WHERE status = 'キャンセル'; でキャンセル注文の件数を数え、その中の1件を order_id で指定して DELETE で削除する。
  5. 5 各操作の実行結果（INSERT 0 1 / UPDATE 1 / DELETE 1）の件数が、想定どおりかを確認する。

ねらい: 「SELECTで確認 → 件数を数える → 書き換える → 結果件数を確認する」という一連の流れを、実際に手を動かして体に覚え込ませることが目的です。ここで身につけた習慣は、次章以降のJOINを使った複雑なUPDATE・DELETEでも変わらず有効です。

理解度確認クイズ

  1. Q1. INSERT文で列名を省略せず明示すべき理由を説明してください。

    回答を表示

    列名を省略すると、テーブルの全列に定義順どおりの値を渡さなければならず、後から列を追加・削除・並べ替えた瞬間にSQLが壊れてしまいます。列名を明示すれば、値と列の対応関係が一目で分かり、テーブル構造の変更にも強くなります。

  2. Q2. WHERE句を書き忘れる事故を防ぐための4ステップを順番に説明してください。

    回答を表示

    (1) 同じWHERE条件でSELECTし対象行を確認する。(2) SELECT count(*) で件数を数える。(3) 同じWHERE条件のままUPDATE／DELETEに書き換えて実行する。(4) 実行結果に表示される件数が、手順2で数えた件数と一致するか確認する。

  3. Q3. DELETE と TRUNCATE TABLE の違いを2つ挙げてください。

    回答を表示

    (1) DELETEはWHEREで対象行を絞れるが、TRUNCATEは常に全行が対象で絞り込めない。(2) DELETEは1行ずつ処理し自動採番もリセットされないが、TRUNCATEはテーブルごと初期化するため高速で、RESTART IDENTITYを付ければ自動採番を1から振り直せる。

  4. Q4. RETURNING句とON CONFLICTは、それぞれどんな場面で使いますか。

    回答を表示

    RETURNINGは、INSERT・UPDATE・DELETEで書き換えた行の内容(自動採番されたIDなど)をその場で受け取りたいときに使います。ON CONFLICTは、UNIQUE制約や主キーが重複した場合の動きを指定したいとき(既存行を更新するUPSERT、または何もしない)に使います。
