ホーム SQL入門 第7章
第7章 所要時間: 約75分

条件を指定して絞り込む（WHERE）

第6章では WHERE をひとつの条件だけで使いましたが、実務ではもっと複雑な条件が必要になります。「東京都に住んでいて、かつ2024年以降に登録した人」「書籍または文具のどちらか」「都道府県が未登録の人」——こうした条件をSQLでどう表現するかを、この章でじっくり学びます。特に NULL（値が無い状態） の扱いは、初心者がもっとも混乱しやすい落とし穴なので、丁寧に時間をかけます。

この章の学習目標

  • 比較演算子（= ・<> ・< ・> など）を使い分けられる
  • AND／OR／NOT を括弧で正しく組み合わせられる
  • BETWEEN・IN・LIKE による範囲・列挙・あいまい検索ができる
  • NULL が「値が無い」ことの意味を理解し、IS NULL を正しく使える
  • CASE 式で値を条件分岐して表示できる

7.1 WHERE の役割 — 1行ずつ「残すか・捨てるか」を判定する

WHERE 句がしていることは、実はとてもシンプルです。テーブルの行を1行ずつ調べて、指定した条件に一致する（真＝TRUEになる）行だけを残す、それだけです。条件に合わない行は結果から除外されます。

flowchart TD A["customers テーブルの全10行"] --> B{"1行ずつ判定
prefecture = '東京都' ？"} B -->|TRUE| C["結果に残す"] B -->|FALSE| D["結果から除外"] B -->|"UNKNOWN（NULLが絡む場合）"| D

ポイントは、判定結果が TRUE（真）・FALSE（偽）・UNKNOWN（不明） の3種類あるということです。TRUE の行だけが結果に残り、FALSE と UNKNOWN の行はどちらも除外されます。この「UNKNOWN」が、7.6節で扱う NULL と深く関係しています。

思い出そう: SQL の評価順序（第6章）

WHERE は FROM の直後、SELECT より前に評価されます。つまり「まず表を作り、次に行を絞り込み、最後にどの列を見せるか決める」という順番です。この章で条件を複雑にしていく間も、この順番は変わりません。

7.2 比較演算子 — 値どうしを比べる

条件の基本部品が比較演算子です。PostgreSQL で使える主な比較演算子は次のとおりです。

演算子 意味 例
= 等しい category = '書籍'
<> または != 等しくない status <> 'キャンセル'
< より小さい unit_price < 1000
> より大きい stock_quantity > 0
<= 以下 order_date <= '2024-06-30'
>= 以上 order_date >= '2024-04-01'

比較する値の書き方には決まりがあります。文字列はシングルクォート（'東京都'）で囲み、数値はクォート不要（1000）、日付は文字列と同じくシングルクォートで囲んだ '2024-04-01' の形式を使います。実際に商品テーブルで試してみましょう。

where-compare.sql 
-- 単価が1000円未満の商品を、単価の安い順に表示
SELECT product_name, category, unit_price
FROM products
WHERE unit_price < 1000
ORDER BY unit_price;

結果イメージ:

product_name category unit_price
ボールペン（黒） 文具 150.00
ノートA5 文具 280.00
付箋セット 文具 320.00
緑茶ティーバッグ 食品 650.00
コーヒー豆（200g） 食品 980.00

7.3 論理演算子 — 条件を組み合わせる（AND / OR / NOT）

1つの条件だけでは足りない場面がほとんどです。複数の条件を組み合わせるには AND（かつ）・OR（または）・NOT（〜ではない）を使います。

where-and-or.sql 
-- 東京都在住 かつ 2024年4月以降に登録した顧客
SELECT customer_name, prefecture, registered_at
FROM customers
WHERE prefecture = '東京都'
  AND registered_at >= '2024-04-01';

重要な罠: AND は OR より優先される

SQL では算数の「かけ算はたし算より先」と同じように、AND は OR より先に評価されます。AND と OR を1つの条件式に混在させるときは、意図を明確にするため括弧を付けることを強くおすすめします。付け忘れると、意図と異なる行が返ってくることがあります。

「書籍または文具で、かつ単価が500円未満の商品」を取り出したい例で、括弧の有無による違いを比べてみましょう。

where-parentheses-bad.sql（括弧なし・意図と異なる） 
-- 一見「書籍or文具 かつ 500円未満」に見えるが…
SELECT product_name, category, unit_price
FROM products
WHERE category = '書籍' OR category = '文具'
  AND unit_price < 500;

AND が先に評価されるため、これは実際には 「書籍である」 OR 「文具であり、かつ500円未満」 という意味になります。結果、500円以上の書籍まで含まれてしまいます。

where-parentheses-good.sql（括弧あり・意図どおり） 
-- 括弧で「書籍or文具」をひとかたまりにする
SELECT product_name, category, unit_price
FROM products
WHERE (category = '書籍' OR category = '文具')
  AND unit_price < 500;

括弧を付けたことで「（書籍または文具）であり、かつ500円未満」という本来の意図どおりに評価されます。NOT は条件全体を反転させる演算子で、NOT (category = '家電') のように使います。

重要ポイント: 迷ったら必ず括弧を書く

AND と OR を混在させる条件式では、優先順位を覚えるより常に括弧で明示する習慣をつけるほうが安全です。括弧はコストゼロで事故を防げます。

7.4 範囲と列挙 — BETWEEN と IN

「500円から1500円まで」のような範囲を指定するとき、unit_price >= 500 AND unit_price <= 1500 と書く代わりに BETWEEN を使うと簡潔に書けます。両端の値を含む点に注意してください。

where-between-in.sql 
-- 単価が500円〜1500円（両端を含む）の商品
SELECT product_name, unit_price
FROM products
WHERE unit_price BETWEEN 500 AND 1500;

-- カテゴリが 書籍・文具・食品 のいずれかの商品
SELECT product_name, category
FROM products
WHERE category IN ('書籍', '文具', '食品');

IN (...) は「いずれかに一致すればよい」列挙です。category = '書籍' OR category = '文具' OR category = '食品' と書くのと同じ結果になりますが、IN のほうが短く読みやすくなります。反対に「いずれにも一致しない」を表すには NOT IN (...) を使いますが、これには7.6節で説明する重要な注意点があります。

7.5 あいまい検索 — LIKE

「名前に『田』が付く人」のように、完全一致ではなく部分的な一致で探したいことがあります。そのための演算子が LIKE で、2種類の特殊記号（ワイルドカード）を使います。

記号 意味 例
% 0文字以上の任意の文字列 '田%' → 「田」で始まる
_ 任意の1文字（ちょうど1文字） '佐_' → 「佐」＋任意の1文字
where-like.sql 
-- 前方一致: 氏名が「田」で始まる顧客
SELECT customer_name FROM customers WHERE customer_name LIKE '田%';

-- 後方一致: 氏名が「子」で終わる顧客
SELECT customer_name FROM customers WHERE customer_name LIKE '%子';

-- 部分一致: 氏名のどこかに「藤」を含む顧客
SELECT customer_name FROM customers WHERE customer_name LIKE '%藤%';

前方一致（'田%'）・後方一致（'%子'）・部分一致（'%藤%'）の3パターンを使い分けます。なお PostgreSQL には 大文字小文字を区別しない ILIKE という独自演算子もあり、product_name ILIKE '%coffee%' のように英字混じりのデータで重宝します（標準SQLには無い PostgreSQL 独自の機能です）。

ヒント: 先頭に % を置くと検索が遅くなりやすい

'%子' や '%藤%' のように先頭に % を置く検索（中間一致・後方一致）は、通常の B-tree インデックスが使われにくく、表全体を順に読む処理になりやすいため、データが多いと遅くなりがちです。「必ず遅い」わけではありませんが、注意が必要です。

前方一致とインデックスの関係 発展

前方一致（'田%'）は、条件によっては通常の B-tree インデックスを利用できる場合があります。ただし実際にインデックスを使うかどうかは PostgreSQL が判断するため、必ず使われるとは限りません。また、日本語などを扱うロケールでは text_pattern_ops という指定を付けたインデックスが必要になる場合があります。インデックスの詳しい仕組みは第14章で扱います。

7.6 NULL の扱い — 「値が無い」を正しく理解する

ここが本章でいちばん大切なテーマです。NULL は「まだ値が入力されていない」「そもそも値が存在しない」ことを表す特別な印であり、空文字（''）でも数値の0でもありません。本ガイドのサンプルデータでは、customers テーブルのうち都道府県が未登録の顧客の prefecture 列が NULL になっています。

最重要の罠: 「= NULL」は絶対に真にならない

「NULL かどうか」を prefecture = NULL と書いても、この式は常に UNKNOWN になり、行は1件も返りません。NULL は「不明な値」なので、「不明 と 何かが等しい」かどうかも不明としか言えないためです。NULL を判定するには専用の IS NULL ／ IS NOT NULL を使ってください。

where-is-null.sql 
-- 誤り: これは常に0件（結果が返らない）
SELECT customer_name FROM customers WHERE prefecture = NULL;

-- 正しい: 都道府県が未登録の顧客を探す
SELECT customer_name FROM customers WHERE prefecture IS NULL;

-- 正しい: 都道府県が登録済みの顧客を探す
SELECT customer_name FROM customers WHERE prefecture IS NOT NULL;

なぜこうなるのか。標準SQLでは条件式の結果が TRUE・FALSE の2値ではなく、TRUE・FALSE・UNKNOWN の3値になる場面があります。これを3値論理と呼びます。NULL = 100 のように NULL を比較に使うと、結果は TRUE でも FALSE でもなくUNKNOWN（不明）になります。「不明な値」と「何か」を比べても、結論は「不明」としか言えないためです。

式 結果
100 = 100 TRUE
100 = 200 FALSE
100 = NULL UNKNOWN
NULL = NULL UNKNOWN

WHERE 句は、この3つの結果のうちTRUE の行だけを残します。FALSE の行はもちろん、UNKNOWN の行も結果には含まれません（7.1節の図）。だから NULL を探したいときは = NULL ではなく、TRUE／FALSEをはっきり返す IS NULL を使う必要があります。

AND・OR に UNKNOWN が絡んだときの結果は次のとおりです。

A B A AND B A OR B
TRUE UNKNOWN UNKNOWN TRUE
FALSE UNKNOWN FALSE UNKNOWN
UNKNOWN UNKNOWN UNKNOWN UNKNOWN

NOT についても同様で、UNKNOWN を反転させても UNKNOWN のままです。

A NOT A
TRUE FALSE
FALSE TRUE
UNKNOWN UNKNOWN

WHERE 句は結果が TRUE の行だけを残すので、FALSE と同様に UNKNOWN の行も除外されることを思い出してください（7.1節の図）。これが「NULL が絡む式はだいたい結果に含まれない」という直感につながります。

警告: NOT IN に NULL が混ざると結果が消える 発展

サブクエリなどで作った列挙リストに1件でも NULL が含まれていると、NOT IN はすべての行を除外し、結果が0件になります。たとえば WHERE customer_id NOT IN (1, 2, NULL) は「1でも2でもない」を期待して書いても、常に0件です。理由は NOT IN が内部的に「<> 1 AND <> 2 AND <> NULL」のように展開され、<> NULL の部分が必ず UNKNOWN になるため、AND 全体も UNKNOWN（＝除外）になってしまうからです。NULL を含む可能性がある列挙には NOT IN を避け、NOT EXISTS（第12章）を使うのが安全です。

最後に、サンプルデータの prefecture が NULL の顧客を実際に確認してみましょう。

where-null-example.sql 
-- 都道府県が未登録（NULL）の顧客だけを一覧表示
SELECT customer_id, customer_name, prefecture
FROM customers
WHERE prefecture IS NULL;

結果イメージ:

customer_id customer_name prefecture
7 山本 恵子 NULL（未登録）

7.7 CASE 式 — 条件によって表示を変える

CASE 式を使うと、値を条件によって別の表現に変換できます。書き方には2種類あり、特定の列の値を1つずつ比較する単純CASEと、任意の条件式を並べられる検索CASEがあります。実務でよく使うのは検索CASEです。

where-case.sql 
-- 検索CASE: 単価を3つの価格帯に区分して表示
SELECT
    product_name,
    unit_price,
    CASE
        WHEN unit_price >= 3000 THEN '高価格帯'
        WHEN unit_price >= 1000 THEN '中価格帯'
        ELSE '低価格帯'
    END AS price_range
FROM products
ORDER BY unit_price DESC;

結果イメージ:

product_name unit_price price_range
旧型キーボード 4200.00 高価格帯
モバイルバッテリー 3500.00 高価格帯
データベース設計の教科書 3200.00 高価格帯
SQL入門ガイド 2800.00 中価格帯
ワイヤレスマウス 2400.00 中価格帯
焼き菓子詰め合わせ 1800.00 中価格帯
USBメモリ64GB 1600.00 中価格帯
コーヒー豆（200g） 980.00 低価格帯
緑茶ティーバッグ 650.00 低価格帯
付箋セット 320.00 低価格帯
ノートA5 280.00 低価格帯
ボールペン（黒） 150.00 低価格帯

CASE 式は WHEN を上から順に評価し、最初に条件が TRUE になったものの THEN の値を返します。どれにも当てはまらなければ ELSE の値（省略時は NULL）になります。ORDER BY の中でも CASE を使えば、「キャンセルを一番下に回す」といった独自の並び順も作れます。

where-case-orderby.sql 
-- キャンセルされた注文だけを一覧の末尾に回す
SELECT order_id, status, order_date
FROM orders
ORDER BY CASE WHEN status = 'キャンセル' THEN 1 ELSE 0 END,
         order_date;

理解度確認クイズ

  1. Q1. WHERE category = '書籍' OR category = '文具' AND unit_price < 500 という条件式には、意図と異なる結果になりやすい問題があります。何が問題で、どう直せばよいですか。

    回答を表示

    AND は OR より優先して評価されるため、この式は「書籍である」OR「文具であり、かつ500円未満」という意味になり、500円以上の書籍まで含まれてしまいます。(category = '書籍' OR category = '文具') AND unit_price < 500 のように括弧で囲み、OR の部分をひとかたまりにする必要があります。

  2. Q2. customers テーブルで都道府県が未登録の顧客を探すのに、WHERE prefecture = NULL と書いたところ、結果が0件になりました。理由と正しい書き方を答えてください。

    回答を表示

    NULL は「不明な値」であり、「不明 と 何かが等しいか」も不明（UNKNOWN）としか判定できないため、= NULL は常にUNKNOWNになり、決してTRUEになりません。正しくは WHERE prefecture IS NULL を使います。

  3. Q3. customer_id NOT IN (1, 2, NULL) という条件を書いたら、意図に反して結果が0件になりました。何が起きていますか。

    回答を表示

    NOT IN は内部的に「<> 1 AND <> 2 AND <> NULL」のように展開されます。<> NULL の部分が必ずUNKNOWNになり、AND全体もUNKNOWN（＝除外）になるため、リストにNULLが1件でも混ざるとNOT IN全体が常に0件を返してしまいます。NULLを含む可能性がある列挙にはNOT INを避けるのが安全です。

  4. Q4. LIKE '%コーヒー%' と LIKE 'コーヒー%' の違いを説明してください。また、どちらが大量データで速く動作しやすいですか。

    回答を表示

    '%コーヒー%' は「コーヒー」をどこかに含む部分一致、'コーヒー%' は「コーヒー」で始まる前方一致です。% を先頭に置く部分一致は通常のインデックスが効きにくく、データ量が増えると遅くなりがちなので、前方一致のほうが速く動作しやすいです。
