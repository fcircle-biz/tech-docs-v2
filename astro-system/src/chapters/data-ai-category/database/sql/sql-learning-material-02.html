リレーショナルデータベースの構造

前章で「データベースは Excel の表に似ている」と学びました。この章では、その表がどんな部品でできているのか（行・列・データ型）、1行を確実に指し示す主キー、そして「なぜ表を分けて関係づけるのか」という RDBMS の核心を学びます。ここで身につけた考え方は、第5章でテーブルを作るときにそのまま活きてきます。

この章の学習目標

  • テーブル・行（レコード）・列（カラム）という基本単位を Excel の表と対応づけて説明できる
  • 主キーが「重複禁止・NULL禁止で1行を確実に指し示す列」であることを理解する
  • 1枚の大きな表に詰め込むと何が困るかを具体例で説明し、表を分ける理由を言える
  • 外部キーによるテーブル間の関係と、ER 図・PostgreSQL の階層構造を読める

2.1 テーブル・行・列 — 表の3つの部品

RDBMS の表は、Excel のシートと同じ3つの部品でできています。呼び方だけデータベース用語に置き換えて覚えましょう。

Excel での呼び方 データベースでの呼び方 意味
シート（表全体） テーブル（table） 同じ種類のデータをまとめた入れ物。1つの RDBMS の中に複数のテーブルを持てる
横1行 行（row）／レコード（record） 1件分のデータのまとまり。顧客テーブルなら「顧客1人ぶん」
縦1列（見出し） 列（column）／カラム／フィールド データの項目。顧客テーブルなら「氏名」「都道府県」など

本ガイドで使う共通サンプルデータベース shop_db の customers（顧客）テーブルで確認してみましょう。

customer_id customer_name prefecture registered_at
1 佐藤 花子 東京都 2024-01-10
2 鈴木 一郎 大阪府 2024-01-15

この表全体がテーブル（customers）、「1, 佐藤 花子, 東京都, 2024-01-10」という横1本が行、「customer_name」という縦1列が列です。この3つの用語は今後の章で何度も出てくるので、ここでしっかり結びつけておきましょう。

2.2 データ型 — 列に入れてよい値の種類を決める

Excel のセルにはどんな値でも自由に入力できますが、RDBMS のテーブルでは列ごとに「入れてよい値の種類」を決めておくことができます。これをデータ型と呼びます。たとえば「氏名」の列に日付を入れようとしたり、「登録日」の列に文字列を入れようとしたりすると、データベースが登録を拒否してくれます。

代表的なデータ型を大づかみに紹介します。細かい種類や書き方は、実際にテーブルを作る第5章で詳しく扱うので、ここでは「こういう分類がある」という地図を持っておけば十分です。

分類 具体例 shop_db での使用例
整数 1, 2, 100 のような整数値 customer_id（顧客番号）、quantity（数量）
文字列 氏名やメールアドレスなどの文字の並び customer_name（氏名）、email
数値（金額） 小数を含む正確な数値 unit_price（単価）
日付・日時 年月日、または年月日＋時刻 birth_date（生年月日）、registered_at（登録日時）
真偽値 真（true）か偽（false）の2択 is_active（販売中かどうか）

ヒント: データ型があると何が嬉しいのか

Excel では「数量」の列に誤って「三個」と文字で入力できてしまい、あとから集計しようとして初めて気づく、という事故が起こりがちです。データ型を決めておけば、そもそも登録の時点で拒否されるため、不正なデータが表に紛れ込むのを未然に防げます。

2.3 主キー — 1行を確実に指し示す列

テーブルの中から「この1行だけ」を確実に取り出したいとき、頼りになる目印が必要です。この目印になる列（または列の組み合わせ）を主キー（PRIMARY KEY）と呼びます。主キーには、次の2つの条件が課されます。

重複禁止

同じ値を持つ行が2行以上あってはいけません。customer_id が 1 の顧客は、テーブル中にただ1人だけです。

NULL禁止

「値が入っていない」状態（NULL）が許されません。指し示す相手がいない目印には意味がないからです。

主キーには2つの選び方があります。氏名やメールアドレスのようにもともとデータが持っている値を使う自然キーと、システム側で機械的に採番する代理キー（サロゲートキー）です。

種類 例 特徴
自然キー メールアドレス、マイナンバーなど 意味が分かりやすい半面、途中で値が変わる・重複しうる項目を選ぶと後で困る
代理キー customer_id のような連番 業務的な意味を持たないため値が変わらず安定する。本ガイドでは基本的にこちらを採用

shop_db の customers テーブルでは、customer_id が主キーです。実際に作成するときは、第5章で学ぶ CREATE TABLE 文の中で次のように指定します（今は雰囲気だけつかめば十分です）。

primary-key-preview.sql 
-- customers（顧客）テーブルの主キー指定（第5章で詳しく学びます）
CREATE TABLE customers (
    customer_id integer PRIMARY KEY,  -- 重複禁止・NULL禁止の目印
    customer_name varchar(50) NOT NULL,
    email varchar(100)
);

2.4 なぜ表を分けるのか — 1枚にまとめる弊害

「顧客・商品・注文の情報を、全部まとめて1枚の大きな表にすればいいのでは？」と考えるのは自然な発想です。まずは実際にやってみて、何が起こるかを見てみましょう。

注文ID 顧客名 都道府県 商品名 単価
1 佐藤 花子 東京都 ノート 150
1 佐藤 花子 東京都 ボールペン 100
2 佐藤 花子 東京都 ノート 150

1つの注文に複数の商品が入るだけで、「佐藤 花子」「東京都」という顧客の情報が何度も繰り返し書かれています。この重複が、次のような具体的な問題を引き起こします。

問題 具体的に起こること
更新漏れ（更新時異常） 佐藤さんが引っ越したとき、3行すべての都道府県を書き換えないと、同じ人物なのに住所がバラバラになってしまう
登録できない（挿入時異常） 「注文」の列がまだ埋まらない新商品を、注文が発生するまでこの表に登録できない
消えてしまう（削除時異常） ある顧客の唯一の注文をキャンセルして行を削除すると、その顧客の情報自体が表から消えてしまう
表記ゆれ 同じ人のはずが「佐藤花子」「佐藤 花子」のように別の書き方で入力され、同一人物と気づけなくなる

解決の方向性はシンプルです。「顧客の情報」「商品の情報」「注文という出来事」を、それぞれ別のテーブルに分けて持つのです。そして、バラバラになった情報を後から関連付けられるように、共通の目印（主キー）を使って結びつけます。この「表を分けて関係づける」設計の考え方を正規化と呼びます。正規化の詳しい手順は設計・モデリングの専門教材で扱いますが、ここでは「重複をなくすために表を分ける」という入り口の発想をつかめば十分です。

重要: 「1つの表は1つのテーマだけを扱う」

迷ったら「この表は何についての情報か」を自問してください。「顧客について」なら customers、「商品について」なら products。1つの表に複数のテーマ（顧客のことと商品のこと）が混ざっていたら、分割のサインです。

2.5 外部キーとリレーション — 表と表をつなぐ

表を分けたら、次は「どの注文が、どの顧客のものか」を分かるようにしなければなりません。そこで登場するのが外部キー（FOREIGN KEY）です。外部キーとは、別のテーブルの主キーの値を、自分のテーブルの列として持つことで、行同士を関連付ける仕組みです。

orders（注文）テーブルの customer_id 列がその例です。これは orders 自身の主キーではなく、customers テーブルの主キー customer_id を借りてきた値です。この列を見れば、その注文が「どの顧客のものか」がすぐに分かります。

foreign-key-preview.sql 
-- orders（注文）テーブルの外部キー指定（第5章で詳しく学びます）
CREATE TABLE orders (
    order_id integer PRIMARY KEY,
    customer_id integer REFERENCES customers(customer_id), -- 外部キー
    order_date date,
    status varchar(20)
);

1人の顧客は何回も注文できますが、1つの注文は1人の顧客にしか属しません。このような関係を1対多の関係と呼びます。shop_db では「1人の顧客 → 複数の注文」「1つの注文 → 複数の注文明細」「1つの商品 → 複数の注文明細」がすべて1対多の関係です。

さらに外部キーには、存在しない顧客番号を注文に登録できないようにする参照整合性という役割もあります。たとえば customer_id = 999 という顧客が存在しないのに、その番号を持つ注文を登録しようとすると、PostgreSQL がエラーを返して拒否します。データの矛盾を、入力の時点で機械的に防いでくれるわけです。

用語の整理: リレーション

「リレーショナルデータベース」のリレーションは、まさにこの「表と表の関係」を指しています。外部キーによって表同士がつながっている状態そのものが、RDBMS という名前の由来です。

2.6 ER図の読み方 — shop_db の全体像

テーブルの数が増えてくると、文章だけで関係を把握するのは大変になります。そこで使われるのがER図（Entity-Relationship Diagram、実体関連図）です。テーブルを箱、関係を線で表し、全体の構造をひと目で見渡せるようにします。本ガイドで使い続ける shop_db の4テーブルを ER 図にすると、次のようになります。

erDiagram customers ||--o{ orders : "注文する" orders ||--|{ order_items : "明細を持つ" products ||--o{ order_items : "明細に含まれる" customers { int customer_id PK string customer_name string email string prefecture date birth_date timestamp registered_at } orders { int order_id PK int customer_id FK date order_date string status } order_items { int order_item_id PK int order_id FK int product_id FK int quantity decimal unit_price } products { int product_id PK string product_name string category decimal unit_price int stock_quantity boolean is_active }

線につく記号は「その関係が最小と最大で何件になりうるか」（カーディナリティ）を表します。読み方を覚えておくと、他の教材や実務の設計書でも困りません。

記号 意味 shop_db での例
|| 必ず1件（1対1側） 1つの注文には、必ず1人の顧客が結び付く
o{ 0件以上（多の側、0も許す） 1人の顧客は、注文が0件（まだ未購入）のこともあれば複数件のこともある
|{ 1件以上（多の側、必ず1件はある） 1つの注文には、必ず1件以上の注文明細がある

なぜ order_items（注文明細）というテーブルが別に必要なのでしょうか。1つの注文（例: 注文1）の中に、ノートとボールペンという2つの商品が含まれる場合、「注文」と「商品」を直接1対多で結ぶだけでは表現できません。そこで、「どの注文の、どの商品を、何個」という組み合わせそのものを1行として持つ order_items を間に挟むことで、注文と商品の多対多の関係を表現しています。

2.7 PostgreSQL の階層構造

最後に、テーブルより一段上の階層を整理しておきましょう。PostgreSQL をインストールすると、その中に次のような入れ子構造ができます。

flowchart TD A["データベースクラスタ
（PostgreSQLサーバー1台ぶん）"] --> B["データベース: shop_db"] A --> C["データベース: postgres
（管理用の既定データベース）"] B --> D["スキーマ: public
（既定のスキーマ）"] D --> E["テーブル: customers"] D --> F["テーブル: products"] D --> G["テーブル: orders"] D --> H["テーブル: order_items"]

いちばん外側にあるのがデータベースクラスタで、PostgreSQL サーバー1台が管理する全データベースの集まりを指します。その中に複数のデータベース（shop_db など）を作ることができ、さらにデータベースの中はスキーマという名前空間で区切られています。特に何も指定しなければ、public という既定のスキーマが使われます。そして最後に、スキーマの中に customers のようなテーブルが入っています。

ヒント: 本ガイドでスキーマを意識しなくてよい理由

本ガイドでは既定の public スキーマだけを使い続けます。複数のスキーマを使い分ける設計は中〜上級の話題になるため、まずは「データベースの中にスキーマがあり、その中にテーブルがある」という階層だけ覚えておけば十分です。

やってみよう 2-1: ごちゃまぜの1枚表を分割する

紙またはメモアプリを用意してください。パソコンの操作は不要です。以下の1枚表を、複数のテーブルに分割する練習をします。

お題の表（1枚にまとめた注文記録）

列: 注文ID／顧客名／都道府県／商品名／単価／数量／注文日

手順

  1. 1 この1枚表に3件ほど架空データを埋めて、同じ顧客が2回以上注文したケースを作ってみる。
  2. 2 「顧客について」「商品について」「注文について」という3つのテーマに列を仕分ける。
  3. 3 仕分けた3テーマをそれぞれ表にし、各表に主キー（顧客ID・商品ID・注文ID）を1つずつ付ける。
  4. 4 「注文」の表に「顧客ID」の列（外部キー）を追加し、どの注文がどの顧客のものか線で結んでみる。商品名と単価はどちらの表に置くべきかも考える。

ねらい: 分割後は、同じ顧客名や住所を何度も書かずに済むはずです。この「分けた結果、重複が消える」という感覚が正規化の第一歩です。ここで作った表は、第5章の CREATE TABLE の設計にそのまま応用できます。

理解度確認クイズ

  1. Q1. Excel の「シート」「横1行」「縦1列」は、データベースではそれぞれ何と呼びますか？

    回答を表示

    シートはテーブル、横1行は行（レコード）、縦1列は列（カラム／フィールド）と呼びます。

  2. Q2. 主キーが満たすべき2つの条件は何ですか。

    回答を表示

    (1) 同じ値を持つ行が2行以上あってはならない（重複禁止）。(2) 値が入っていない状態（NULL）が許されない（NULL禁止）。この2つを満たすことで、主キーの値だけで行を1つに絞り込めます。

  3. Q3. 「顧客・商品・注文」を1枚の大きな表にまとめると、どんな問題が起こりますか。本文の具体例を1つ挙げて説明してください。

    回答を表示

    例: 顧客が引っ越したとき、その顧客が注文した行すべての都道府県を書き換えないと住所がバラバラになる「更新漏れ」が起こる。ほかに、注文がないと商品を登録できない「挿入時異常」、唯一の注文を削除すると顧客情報ごと消えてしまう「削除時異常」も正解です。

  4. Q4. 外部キーとは何ですか。orders テーブルを例に説明してください。

    回答を表示

    外部キーとは、別のテーブルの主キーの値を自分のテーブルの列として持ち、行同士を関連付ける仕組みです。orders テーブルの customer_id は、customers テーブルの主キー customer_id を参照する外部キーで、「どの注文がどの顧客のものか」を表します。存在しない顧客IDは登録できないという参照整合性のチェックも働きます。
