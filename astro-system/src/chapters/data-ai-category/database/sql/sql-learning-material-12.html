サブクエリとビュー

この章では、SQL の中に SQL を書く「サブクエリ」という考え方を学びます。WHERE 句のサブクエリ・IN・EXISTS・FROM 句のサブクエリ（導出テーブル）を一通り経験したあと、それらを読みやすく書き直す WITH 句（CTE）、そしてよく使う SELECT に名前を付けて保存する CREATE VIEW を学びます。最後に発展として、集計しても行が消えないウィンドウ関数の入口にも触れます。

必須 発展 この章は 12.2〜12.3 のスカラサブクエリ・IN、12.5 の FROM句のサブクエリ、12.7 の CREATE VIEW / DROP VIEW の基本が必須、12.4 の相関サブクエリ・12.6 のCTE・12.8 のウィンドウ関数は発展です。まずは必須の項目を確実にしましょう。

この章の学習目標

  • サブクエリが「内側のSELECTの結果を、外側のSELECTが使う」入れ子の仕組みであることを説明できる
  • スカラサブクエリ・IN・EXISTS を使い分けられる
  • FROM 句のサブクエリ（導出テーブル）と WITH 句（CTE）で段階的な集計を書ける
  • CREATE VIEW でよく使う SELECT に名前を付けて再利用できる

12.1 サブクエリとは — 「SQL の中に書く SQL」

第11章までに学んだ SELECT は、いつも「1回書けば1回で完結する」ものでした。しかし実務では、「まず〇〇を求めて、その結果を使って△△を絞り込む」という二段階の問い合わせが頻繁に必要になります。たとえば「平均単価より高い商品を知りたい」という要求には、(1) 平均単価を求める、(2) その値より高い商品を絞り込む、という2つの手順が隠れています。

この2つの手順を1つの SQL 文の中に入れ子（ネスト）にして書けるのがサブクエリ（副問い合わせ）です。カッコで囲んだ内側の SELECT の結果を、外側の SELECT が材料として使う、と考えると理解しやすくなります。

flowchart TD A["① 内側のSELECT（サブクエリ）の結果を先に考える"] --> B["② 内側の結果（値・値のリスト・表）ができたとみなす"] B --> C["③ 外側のSELECTが②の結果を材料として使う"] C --> D["④ 外側の実行結果が最終的な答えになる"]

これはSQL を読み解くための論理的な順序です。実際にどのような順序・方法でサブクエリを処理するかは、PostgreSQL のオプティマイザ（最も速いと判断した実行方法を自動的に選ぶ仕組み）が実行のたびに決めます。「内側の結果を外側が使う」と考えれば SQL の意味は正しく読み解けますが、物理的に必ずその順番で処理が行われるとは限らない、ということは覚えておきましょう。

サブクエリは、どこに書くかによって返せる形と使い道が変わります。この章では代表的な3つの位置を順番に見ていきます。

書く位置 サブクエリが返すもの 主な用途 節
WHERE 句 1つの値、または値のリスト 条件式の一部として絞り込みに使う 12.2〜12.4
FROM 句 1つの表（導出テーブル） 集計結果をさらに集計するなど二段階の処理に使う 12.5
WITH 句（先頭） 1つ以上の名前付きの表 複雑なサブクエリを上から順に読める形に整理する 12.6

12.2 WHERE句のサブクエリ（スカラサブクエリ） 必須

スカラサブクエリとは、実行結果が「1行1列＝1つの値」だけになるサブクエリのことです。= > < >= などの比較演算子は、比較する相手が1つの値である必要があるため、スカラサブクエリと相性がよく使われます。第9章で学んだ集約関数はまさに「表全体から1つの値を返す」ものなので、ここで生きてきます。

「平均単価より高い商品」を求めてみましょう。

scalar-subquery.sql 
-- 商品の平均単価より高い商品だけを取り出す
SELECT product_name, unit_price
FROM products
WHERE unit_price > (
    SELECT avg(unit_price) FROM products
)
ORDER BY unit_price DESC;

内側の SELECT avg(unit_price) FROM products の結果は1つの数値（1823.33）になり、外側からは WHERE unit_price > 1823.33 と書いたのと同じ結果になります。平均値をあらかじめ調べて数値を打ち込む必要がない点が最大の利点です。もし商品が追加されて平均が変われば、同じ SQL を実行するだけで結果も自動的に更新されます。

product_name unit_price
旧型キーボード 4200.00
モバイルバッテリー 3500.00
データベース設計の教科書 3200.00
SQL入門ガイド 2800.00
ワイヤレスマウス 2400.00

注意: サブクエリが2行以上返るとエラーになる

スカラサブクエリの位置に、複数行を返す可能性がある SELECT を書くとエラーになります。次の例は unit_price どうしを比較しているので型は合っていますが、内側の SELECT が products の全件（複数行）を返してしまいます。

scalar-error.sql 
-- エラーになる例：サブクエリが複数行を返してしまう
SELECT product_id, product_name, unit_price
  FROM products
 WHERE unit_price = (SELECT unit_price FROM products);

実行すると、次のようなエラーメッセージになります。

Messages 
ERROR:  more than one row returned by a subquery used as an expression

スカラサブクエリとして使うには、内側の SELECT が1行だけ返るように集約関数などで絞り込みます。

scalar-fixed.sql 
-- 1行だけ返るようにする（最も高い単価の商品を取り出す）
SELECT product_id, product_name, unit_price
  FROM products
 WHERE unit_price = (SELECT max(unit_price) FROM products);

-- 複数行を相手にしたいときは = ではなく IN を使う
SELECT product_id, product_name, unit_price
  FROM products
 WHERE unit_price IN (SELECT unit_price FROM products WHERE category = '家電');

1つ目の例は max(unit_price) が 4200.00（product_id=12「旧型キーボード」）になるため、この商品だけが1件返ります。

12.3 IN を使うサブクエリ 必須

サブクエリが複数行を返す場合は、= ではなく第7章で学んだ IN を使います。「東京都の顧客が出した注文」を、注文（orders）を軸に求めてみましょう。

in-subquery.sql 
-- 東京都の顧客が出した注文だけを取り出す
SELECT order_id, order_date, status
FROM orders
WHERE customer_id IN (
    SELECT customer_id FROM customers
    WHERE prefecture = '東京都'
)
ORDER BY order_date;

内側の SELECT が「東京都の顧客番号の一覧」（1, 4, 8）を返し、外側は customer_id IN (1, 4, 8) と書いたのと同じ意味になります。第11章の JOIN でも同じ結果は作れますが、「注文の列だけが欲しく、顧客側の列は結果に出したくない」場合は IN サブクエリのほうが素直に書けます。

重要な復習: NOT IN と NULL の罠（第7章）

第7章で学んだ通り、NOT IN のリストの中に NULL が1つでも混じると、比較結果が「不明」になり行が1件も返らなくなることがあります。危険なのは、内側の SELECT が「NULL を含みうる列」を返しているときです。customers.prefecture には NULL の行（customer_id=7「山本 恵子」）があるため、次のような書き方は危険です。

danger-not-in.sql 
-- 危険: 内側のSELECTが返す prefecture に NULL が混ざるため、結果が0件になる
-- やりたいこと: 「注文実績のある顧客が誰も住んでいない都道府県」の顧客を探す
SELECT customer_id, customer_name, prefecture
FROM customers
WHERE prefecture NOT IN (
    SELECT prefecture FROM customers
    WHERE customer_id IN (SELECT customer_id FROM orders)
);

本来なら、注文が1件もない「渡辺 大輔（福岡県）」の1件が返ってほしいところですが、内側の SELECT が返す都道府県のリストに NULL が1つ混じっているため、結果は0件になります。

安全に書くには、内側に WHERE prefecture IS NOT NULL を足してリストから NULL を取り除くか、次に学ぶ NOT EXISTS を使います（NOT EXISTS は値そのものを比較しないため、この罠が起きません）。

12.4 EXISTS — 「存在するかどうか」だけを判定する 発展

EXISTS は、サブクエリが1行でも返せば真、1行も返さなければ偽と判定する演算子です。値そのものではなく「該当する行があるかどうか」だけに関心がある場合に使います。特徴的なのは、EXISTS の中で使うサブクエリは外側の行を参照できるという点です。これを相関サブクエリと呼びます。

相関サブクエリは、「外側の SELECT が1行処理するたびに、その行の値を使って内側のサブクエリが評価される」と考えると理解しやすくなります。実際にどのような手順で処理するかは、これも PostgreSQL のオプティマイザが決めます。「注文のない顧客」を NOT EXISTS で求めてみましょう。

not-exists.sql 
-- 1件も注文をしていない顧客を探す
SELECT c.customer_id, c.customer_name
FROM customers AS c
WHERE NOT EXISTS (
    -- 顧客ごとに「この顧客のorders行があるか」を確認する
    SELECT 1 FROM orders AS o
    WHERE o.customer_id = c.customer_id
);

内側の o.customer_id = c.customer_id が、外側の顧客1人ぶんごとに評価される「相関」の部分です。SELECT 1 は「値は何でもよく、行があるかどうかだけを見たい」という意図を表すための慣習的な書き方です。

この結果は、第11章で学んだ LEFT JOIN ... WHERE ... IS NULL（外部結合で相手がいない行を探す書き方）と同じ結果になります。2つを比べてみましょう。

書き方 SQL 考え方
NOT EXISTS
（本章）		 WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id) 「一致するorders行が存在しない」ことを直接問う
LEFT JOIN + IS NULL
（第11章）		 FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id WHERE o.order_id IS NULL まず全顧客を残す結合をしてから、相手がいない（NULLになった）行だけを残す

結果はどちらも同じ「注文のない顧客」の一覧になります。どちらを選んでも構いませんが、存在確認だけなら NOT EXISTS のほうが意図が読み取りやすい、結合した相手の列も一緒に使いたいなら LEFT JOIN のほうが自然、という目安を持っておくとよいでしょう。

ヒント: EXISTS は NULL の罠に強い

EXISTS / NOT EXISTS は「行があるか無いか」だけを見る演算子で、値そのものを比較しないため、12.3で見た NOT IN と NULL の罠が起きません。「存在しないことを確認したい」場面では NOT IN より NOT EXISTS を選ぶのが安全です。

12.5 FROM句のサブクエリ（導出テーブル） 必須

サブクエリは FROM 句にも書けます。この場合、サブクエリの実行結果は1つの表として扱われ、外側の SELECT はその表に対して普通に列を選んだり条件を付けたりできます。この一時的な表を導出テーブルと呼びます。

「顧客ごとの購入金額を出してから、その平均を求める」という二段階の集計をやってみましょう。avg(sum(...)) のように集約関数を二重に重ねて書くことはできないため、このような場面こそ導出テーブルの出番です。

derived-table.sql 
-- ①顧客ごとの合計購入金額を作り、②その平均を求める
SELECT round(avg(total_amount), 2) AS avg_customer_total
FROM (
    SELECT o.customer_id, sum(oi.quantity * oi.unit_price) AS total_amount
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.order_id
    GROUP BY o.customer_id
) AS customer_totals;

上の例の AS customer_totals のように、導出テーブルには別名（エイリアス）を付けています。PostgreSQL 16 以降では、FROM 句のサブクエリの別名は省略できます（それより前のバージョンでは、省略すると文法エラーになりました）。ただし、別名を付けておくと customer_totals.total_amount のように別名.列名の形でサブクエリの列を参照でき SQL が読みやすくなるうえ、別名が必須のデータベース製品もあるため他のデータベースへ移植しやすくなります。そのため本教材では、FROM 句のサブクエリには別名を付けることを推奨します。外側から見ると customer_totals という名前の、customer_id と total_amount という2つの列を持つ表がある、という扱いです。

avg_customer_total
6488.89

12.6 WITH句（CTE・共通テーブル式） 発展

12.5 のように FROM 句の中にサブクエリを入れ子にしていくと、段階が増えるほどカッコの中にカッコがある状態になり、どこからどこまでが1つのまとまりか読み取りにくくなります。この問題を解決するのが WITH 句、通称 CTE（共通テーブル式）です。WITH 句は PostgreSQL 独自の機能ではなく標準SQLの一部で、他の主要なデータベース製品でもほぼ同じ書き方が使えます。基本の書き方は次の通りです。

with-syntax.sql 
-- WITH 名前 AS ( ... ) の形で、先に名前を付けた表を作る
WITH 名前 AS (
    SELECT ...
)
SELECT ...
FROM 名前;

12.5 の例を WITH 句で書き直すと、上から下へ「まず何を作り、それを使って何をするか」の順に読める文章になります。

Before: FROM句のサブクエリ

before.sql 
-- 顧客ごとの合計を導出テーブルとして作り、その平均を求める
SELECT round(avg(total_amount), 2)
FROM (
    SELECT o.customer_id,
           sum(oi.quantity * oi.unit_price)
             AS total_amount
    FROM orders AS o
    JOIN order_items AS oi
      ON oi.order_id = o.order_id
    GROUP BY o.customer_id
) AS customer_totals;

After: WITH句（CTE）

after.sql 
-- 顧客ごとの合計をCTEとして先に定義しておく
WITH customer_totals AS (
    SELECT o.customer_id,
           sum(oi.quantity * oi.unit_price)
             AS total_amount
    FROM orders AS o
    JOIN order_items AS oi
      ON oi.order_id = o.order_id
    GROUP BY o.customer_id
)
SELECT round(avg(total_amount), 2)
FROM customer_totals;

得られる結果は同じですが、customer_totals という名前が先に宣言されるぶん、「顧客ごとの合計を作る → その平均を求める」という2段構えの意図が一目で伝わります。WITH 句はカンマで区切ることで複数並べることもでき、3段階・4段階の集計でも入れ子を深くせずに書き進められます。

multiple-cte.sql 
-- 複数のCTEをカンマで並べて段階的に組み立てる
WITH customer_totals AS (
    SELECT o.customer_id, sum(oi.quantity * oi.unit_price) AS total_amount
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.order_id
    GROUP BY o.customer_id
),
high_spenders AS (
    SELECT customer_id, total_amount FROM customer_totals
    WHERE total_amount > (SELECT avg(total_amount) FROM customer_totals)
)
SELECT c.customer_name, h.total_amount
FROM high_spenders AS h
JOIN customers AS c ON c.customer_id = h.customer_id
ORDER BY h.total_amount DESC;

重要: WITH句は「読みやすさ」のための道具

導出テーブルと WITH 句は、多くの場合どちらでも同じ結果が得られます。違いは主に読みやすさです。段階が2つ以上になったら WITH 句を使う、と決めておくと、後で見返したときや他の人が読むときに理解の速さが大きく変わります。

12.7 ビュー（VIEW） 必須

WITH 句は1回のクエリの中だけで使える「その場限りの名前」でした。もし同じ複雑な SELECT を何度も繰り返し使うのであれば、データベースに恒久的な名前として登録してしまう方法があります。それがビューです。

create-view.sql 
-- 「顧客ごとの合計購入金額」に名前を付けて保存する
CREATE VIEW customer_totals_view AS
SELECT o.customer_id, sum(oi.quantity * oi.unit_price) AS total_amount
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.order_id
GROUP BY o.customer_id;

-- 以降は、テーブルと同じ感覚でSELECTできる
SELECT * FROM customer_totals_view WHERE total_amount > 5000;

ここで初心者がつまずきやすいのが、「ビューはデータを持っているのか」という点です。答えは持っていません。ビューの実体は保存された SELECT 文そのもので、customer_totals_view を参照するたびに、裏側で元の SELECT が実行され直します。そのため orders や order_items のデータが更新されれば、ビューの結果も自動的に最新のものになります。

不要になったビューは DROP VIEW で削除します。

drop-view.sql 
-- 不要になったビューを削除する（データ本体には影響しない）
DROP VIEW customer_totals_view;

ビューの主な用途は2つです。

複雑なSQLを隠す

何段にも結合・集計した長い SELECT を1つの名前にまとめておけば、利用する側は SELECT * FROM ビュー名 と書くだけで済みます。

見せる列を絞る

元テーブルに個人情報などの列があっても、ビューでは必要な列だけを選んで見せることで、権限的な使い方（アクセス制御の入口）ができます。

12.8 ウィンドウ関数の入口 発展

ここからは発展の内容です。第9章の GROUP BY による集計には、1つの弱点がありました。グループ化すると、元の行が集約されて行数が減ってしまうのです。「各顧客の注文を1件ずつ見せながら、その隣に顧客の合計金額も表示したい」といった要求には応えられません。

この「集計しても行が消えない集計」を実現するのがウィンドウ関数です。OVER というキーワードが目印です。ウィンドウ関数も WITH 句と同じく標準SQLの機能で、PostgreSQL 独自のものではありません。

発展・次の学習段階への入口
window-preview.sql 
-- ①注文ごとの小計をCTEで作る
WITH order_totals AS (
    SELECT o.customer_id, o.order_id, o.order_date,
           sum(oi.quantity * oi.unit_price) AS order_total
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.order_id
    GROUP BY o.customer_id, o.order_id, o.order_date
)
-- ②注文を1件ずつ表示しつつ、連番と顧客合計も付ける
SELECT customer_id, order_id,
    ROW_NUMBER() OVER (
        PARTITION BY customer_id ORDER BY order_date
    ) AS order_no,
    sum(order_total) OVER (PARTITION BY customer_id) AS customer_total
FROM order_totals
ORDER BY customer_id, order_no;

末尾の ORDER BY は表示順を揃えるためのものです。ORDER BY を付けないと、SELECT の結果の行順は保証されません。なお、この SQL は全15行を返します。下の表はその先頭4行の抜粋です。

customer_id order_id order_no customer_total
1 1 1 6880.00
1 4 2 6880.00
1 15 3 6880.00
2 2 1 11300.00

GROUP BY なら顧客ごとに1行へまとめられてしまう場面でも、OVER (PARTITION BY ...) は「顧客ごとのまとまり（ウィンドウ）を意識しつつ、行は1件ずつ残す」という動きをします。ROW_NUMBER() は「そのまとまりの中で何番目か」という連番を振る関数です。ウィンドウ関数には他にも RANK()・LAG()・LEAD() など多くの種類があり、ランキング表示や前月比の算出などに使われますが、詳しい使い方は本ガイドの次の学習段階（応用編）で扱います。ここでは「集計しても行が消えない、こういう仕組みがある」ということを覚えておけば十分です。

やってみよう 12-1: サブクエリとCTEで同じ問題を解いて読みやすさを比べる

「カテゴリ別の平均単価より高い商品を、そのカテゴリ名と一緒に一覧表示する」という同じ問題を、2通りの書き方で解いて比較します。

手順

  1. 1 まず FROM 句の導出テーブルだけを使って、「カテゴリごとの平均単価」を計算するSELECTを書き、実行して結果を確認する。
  2. 2 手順1の導出テーブルと products を結合し、「自分のカテゴリの平均より単価が高い商品」だけを絞り込むSELECT文を、導出テーブル方式（FROM句にサブクエリを直接書く）で完成させる。
  3. 3 同じ問題を、今度は WITH category_avg AS (...) という WITH 句を使って書き直す。実行結果が手順2と同じになることを確認する。
  4. 4 2つのSQL文を見比べて、「どちらが後から読んだときに理解しやすいか」「何行目を見ればカテゴリ平均の計算だと分かるか」を自分の言葉でメモに書く。

ねらい: 導出テーブルとWITH句は結果が同じでも読みやすさが違う、という体感を得ることが目的です。段階が2つ以上ある集計では、まずWITH句で書く癖をつけましょう。

理解度確認クイズ

  1. Q1. スカラサブクエリとは何ですか。WHERE unit_price = (SELECT unit_price FROM products) がエラーになる理由も説明してください。

    回答を表示

    スカラサブクエリとは、実行結果が「1行1列＝1つの値」だけになるサブクエリです。例の SELECT unit_price FROM products は products の全件、つまり複数行を返す可能性があります。= の相手には1つの値しか使えないため、実行時に「more than one row returned by a subquery used as an expression」というエラーになります。1行だけ返すよう max(unit_price) のような集約関数を使うか、複数行を相手にしたいなら IN を使います。

  2. Q2. 「注文のない顧客」を求めるとき、NOT IN ではなく NOT EXISTS を使うべき理由を説明してください。

    回答を表示

    NOT IN は、比較するリストの中に NULL が1件でも混ざると3値論理により結果が「不明」となり、行が1件も返らなくなる罠があります。NOT EXISTS は値そのものを比較せず「一致する行があるかどうか」だけを判定するため、この罠が起きず安全です。

  3. Q3. FROM 句にサブクエリ（導出テーブル）を書くとき、AS 別名 は省略できますか。省略した場合と付けた場合で何が変わりますか。

    回答を表示

    PostgreSQL 16 以降では省略できます（それより前のバージョンでは省略すると文法エラーになりました）。ただし別名を付けると 別名.列名 の形でサブクエリの列を参照でき読みやすくなり、別名が必須のデータベース製品にも移植しやすくなるため、本教材では別名を付けることを推奨しています。

  4. Q4. ビュー（VIEW）はテーブルのようにデータを保持していますか。CREATE VIEW と CREATE TABLE ... AS SELECT の違いを踏まえて答えてください。

    回答を表示

    保持していません。ビューの実体は保存されたSELECT文そのものであり、参照するたびに元の SELECT が実行し直されるため、元テーブルの更新が常に反映されます。これに対し（テーブルとしてコピーを作る）CREATE TABLE ... AS SELECT はその時点のデータを実体としてコピーするため、元テーブルが更新されても自動では追従しません。
