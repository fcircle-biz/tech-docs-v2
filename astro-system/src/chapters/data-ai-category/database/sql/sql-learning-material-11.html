ホーム SQL入門 第11章
第11章 所要時間: 約75分

テーブルを結合する（JOIN）

第2章で学んだとおり、shop_db は顧客・商品・注文・注文明細という4つの表に分かれています。この章では、その分かれた表を JOIN（結合）でつなぎ直し、「どの顧客が、いつ、何を、いくつ買ったか」のような、1つの表だけでは答えられない問いに SQL で答えられるようになります。INNER JOIN・外部結合・自己結合・UNION まで、結合の全体像を一気に押さえましょう。

この章の学習目標

  • なぜ表を分けたままではなく結合が必要になるのか説明できる
  • INNER JOIN とテーブル別名（エイリアス）の書き方、ON と WHERE の役割の違いを理解する
  • LEFT / RIGHT / FULL OUTER JOIN の違いを理解し、「注文が1件もない顧客」を探せる
  • 3つ以上のテーブルの結合、結合と GROUP BY の組み合わせができる
  • 自己結合と UNION / UNION ALL（縦の結合）の使いどころが分かる

11.1 なぜ結合が必要か

第2章で見たように、shop_db では「顧客」と「注文」を1つの巨大な表にまとめず、customers（顧客）と orders（注文）という別々の表に分けています。ところが業務では「注文一覧に、注文番号や日付だけでなく顧客の名前も一緒に出したい」という要望がほぼ必ず出てきます。

orders の中には顧客の名前は入っていません。入っているのは customer_id という「顧客番号」だけです。つまり、名前を表示するには orders.customer_id と customers.customer_id が同じ値どうしを突き合わせて、2つの表を横につなぎ直す必要があります。これが 結合（JOIN）です。

orders の customer_id = 1 と customers の customer_id = 1 をつなげば、「注文1は佐藤花子さんの注文」だと分かります。この「つなぐ」処理を SQL でどう書くのか、11.2 から見ていきます。

11.2 INNER JOIN — 両方に存在する行だけをつなぐ 必須

最も基本の結合が INNER JOIN（内部結合）です。「両方の表に存在するもの同士」だけをつなぎます。orders と customers を customer_id でつないでみましょう。

inner-join.sql 
-- 注文一覧に顧客名を付けて表示する
SELECT o.order_id, c.customer_name, o.order_date, o.status
FROM orders o
INNER JOIN customers c
    ON o.customer_id = c.customer_id
ORDER BY o.order_id;

orders o ・ customers c の o と c はテーブル別名（エイリアス）です。FROM orders o と書くと、以降はその文の中だけ orders を o と呼べます。エイリアスを付ける理由は、orders にも customers にも customer_id という同じ名前の列があるためです。何も付けずに customer_id とだけ書くと、データベースは「どちらの表の customer_id か」を判断できずエラーになります。o.customer_id のように「テーブル別名.列名」で修飾すれば、曖昧さがなくなります。

order_id customer_name order_date status

2 鈴木 一郎 2024-02-03 発送済
3 田中 美咲 2024-02-10 発送済
4 佐藤 花子 2024-02-15 発送済
…（以下、order_id 5〜15 と続く）

ここで注目してほしいのは、注文が1件もない顧客（後述の「渡辺 大輔」さん）は結果に1行も出てこないという点です。INNER JOIN は「両方に対応するデータがある行」しか残さないからです。

ヒント: ON と WHERE は役割が違う

ON は「2つの表をどう突き合わせるか」という結合条件です。WHERE は結合が済んだ後の結果を「絞り込む」条件です。上の例に WHERE o.status = '発送済' を追加すれば、「発送済みの注文だけ」にさらに絞り込めます。結合の仕方（ON）と、欲しい行の条件（WHERE）を混ぜて考えないようにしましょう。

11.3 外部結合 — 片方の表を全部残す

INNER JOIN では「注文がない顧客」が消えてしまいました。しかし「注文がない顧客も含めて、全顧客を一覧にしたい」という場面もあります。そのために使うのが 外部結合（OUTER JOIN）です。OUTER というキーワードは省略でき、LEFT JOIN と書けば LEFT OUTER JOIN と同じ意味になります。

結合の種類 残る行 対応が無い側
LEFT (OUTER) JOIN 必須 FROM に書いた左側の表は全行残る 右側の表の列はすべて NULL になる
RIGHT (OUTER) JOIN 発展 JOIN に書いた右側の表は全行残る 左側の表の列はすべて NULL になる
FULL (OUTER) JOIN 発展 両方の表の全行が残る 対応が無い側の列は NULL になる

RIGHT OUTER JOIN と FULL OUTER JOIN は発展項目です — 実務では RIGHT OUTER JOIN は表の順番を入れ替えて LEFT OUTER JOIN に書き換えて表現するのが一般的です。まずは INNER JOIN と LEFT OUTER JOIN を確実に使えるようにしましょう。

実務では LEFT JOIN が圧倒的によく使われます。「主役の表を先（左）に書き、そこに関連情報を足す」という書き方が自然だからです。customers を左にして orders を LEFT JOIN してみましょう。

left-join.sql 
-- 全顧客を対象に、注文があれば注文番号も表示する
SELECT c.customer_name, o.order_id, o.order_date
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id
ORDER BY c.customer_id;

11.4 外部結合の代表的な用途 — 「存在しない」を探す

LEFT JOIN の最も定番の使い方は、「注文が1件もない顧客」のように、関連データが存在しない行だけを探すことです。11.3 の結果を見ると、注文がない顧客は order_id が NULL になっていました。そこで第7章で学んだ IS NULL を組み合わせます。

customers-without-orders.sql 
-- 一度も注文したことがない顧客を探す
SELECT c.customer_id, c.customer_name
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;
customer_id customer_name
6 渡辺 大輔

なぜ WHERE c.order_id IS NULL ではなく WHERE o.order_id IS NULL なのか、疑問に思うかもしれません。c.customer_id（顧客側の主キー）は決して NULL にならないため意味を持ちません。一方 o.order_id（注文側の列）は、対応する注文が無い顧客の行では LEFT JOIN によって NULL で埋められています。だからこそ「注文側の列が NULL」であることが、「注文が存在しない」ことの目印になるのです。

重要: LEFT JOIN + IS NULL は「未〇〇」検索の定石

LEFT JOIN ... WHERE 右側.列 IS NULL という形は、「未購入の会員」「未処理のタスク」「まだレビューが付いていない商品」など、業務システムで非常によく使う検索パターンです。ぜひこの形を覚えてください。

11.5 CROSS JOIN — すべての組み合わせ 発展

CROSS JOINは、条件を指定せず、左の表の各行と右の表の各行をすべて組み合わせる結合です。顧客が10件、商品が12件あれば、結果は 10 × 12 = 120行になります。「全顧客に全商品を1回ずつ案内するダミー明細を作る」といった特殊な用途で使いますが、日常的に使う結合ではありません。

cross-join.sql 
-- 全顧客 × 全商品のすべての組み合わせを作る
SELECT c.customer_name, p.product_name
FROM customers c
CROSS JOIN products p;

警告: 意図せず CROSS JOIN になってしまう書き方

次の2つは、意図せず CROSS JOIN と同じ結果になってしまう典型的なミスです。

  • JOIN の後ろに ON を書き忘れる（結合条件が無いため全組み合わせになる）
  • FROM orders o, customers c のようにカンマ区切りで表を並べる古い書き方をし、WHERE での絞り込みを忘れる

表の行数が多いと、想定外に巨大な結果（数百万行など）が返ってきて処理が固まることがあります。JOIN ... ON の形を必ずセットで書く習慣をつけましょう。

11.6 3つ以上のテーブルの結合 必須

JOIN は2つの表だけでなく、3つ以上つなげることもできます。「どの注文で、どの商品が、何個売れたか」を知るには、orders（注文）→ order_items（注文明細）→ products（商品）の3つを順につなぐ必要があります。

three-table-join.sql 
-- 注文ごとに、どの商品が何個売れたかを表示する
SELECT o.order_id, p.product_name, oi.quantity
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id
ORDER BY o.order_id;
order_id product_name quantity
1 SQL入門ガイド 1
1 ボールペン（黒） 2
1 コーヒー豆（200g） 1
2 ワイヤレスマウス 1
…（以下、order_id 2〜15 の残りの明細と続く）

ポイントは、JOIN を1つ書くごとに ON で「その2つの表をどうつなぐか」を1つずつ指定していくことです。orders と products は直接つながっている列を持ちませんが、間に立つ order_items を経由することで、たどり着けます。

11.7 結合と集計の組み合わせ

第9章で学んだ GROUP BY は、JOIN と組み合わせたときに真価を発揮します。まずは顧客別の購入金額合計です。1件の注文明細の金額は「数量 × 単価」なので、これを sum で足し上げます。

customer-total.sql 
-- 顧客別の購入金額合計（キャンセルも含めた単純集計）
SELECT c.customer_id, c.customer_name,
       sum(oi.quantity * oi.unit_price) AS total_amount
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY c.customer_id, c.customer_name
ORDER BY total_amount DESC;

補足： GROUP BY c.customer_name のように氏名だけでグループ化すると、同姓同名の顧客がいた場合に別人の注文が1つにまとめられてしまいます。顧客を一意に識別できる customer_id をグループ化のキーに含めるのが原則です。

次に、視点を変えて商品カテゴリ別の集計を出してみます。今度は customers は使わず、order_items と products だけを結合します。

category-sales-naive.sql 
-- 商品カテゴリ別の合計金額（注文された金額の単純合計）
SELECT p.category,
       sum(oi.quantity * oi.unit_price) AS category_total
FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
GROUP BY p.category
ORDER BY category_total DESC;

この集計は order_items と products しか結合していないため、キャンセル済みの注文（order_id = 5、customer_id = 4、商品「USBメモリ64GB」1,600円）も含んだ「注文された金額の合計」になっています。実際の売上として集計するには、orders も結合してキャンセル分を除外する必要があります。

そこで orders も結合し、status が「キャンセル」の注文を除外した、正しいカテゴリ別売上を出してみましょう。

category-sales.sql 
-- 商品カテゴリ別の売上（キャンセル済みの注文を除外する）
SELECT p.category,
       sum(oi.quantity * oi.unit_price) AS category_sales
FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
JOIN orders o ON oi.order_id = o.order_id
WHERE o.status <> 'キャンセル'
GROUP BY p.category
ORDER BY category_sales DESC;
category category_sales
家電 19,800.00
書籍 18,000.00
食品 13,380.00
文具 5,620.00

キャンセル済みの1,600円が家電カテゴリから除かれたことで、家電の合計が 21,400.00 円から 19,800.00 円に変わりました。「JOIN で必要な表をつなぎ、GROUP BY でまとめる」という組み立て方は業務レポート作成の基本パターンですが、どの注文を「売上」として数えるかは業務ルール次第であることも意識しておきましょう。第9章の GROUP BY は、実は結合とセットになって初めて完成する、と言ってもよいでしょう。

11.8 自己結合 — 同じ表を2回使う 発展

JOIN は、必ずしも異なる2つの表をつなぐとは限りません。同じ表を2回登場させて自分自身とつなぐことも可能で、これを自己結合（セルフジョイン）と呼びます。例として、「同じカテゴリの商品どうしを、価格を比べられるようにペアで並べる」を products の自己結合で書いてみます。

self-join.sql 
-- 文具カテゴリの商品どうしを価格比較用にペアにする
SELECT p1.product_name AS 商品A, p2.product_name AS 商品B,
       p1.category
FROM products p1
JOIN products p2
    ON p1.category = p2.category
    AND p1.product_id < p2.product_id
WHERE p1.category = '文具';
商品A 商品B category
ボールペン（黒） ノートA5 文具
ボールペン（黒） 付箋セット 文具
ノートA5 付箋セット 文具

※ ORDER BY を付けていないため、表示順は実行環境や状況によって変わることがあります。

自己結合では、products という同じ表を p1 と p2 という異なる別名で2回呼び出しています。別名を付けなければ、SQL 自身も「どちらの products のことか」を区別できません。また p1.product_id < p2.product_id という条件を加えているのは、これが無いと「ボールペン（黒）×ノートA5」と「ノートA5×ボールペン（黒）」のような同じペアの重複や、「ボールペン（黒）×ボールペン（黒）」のような自分自身とのペアまで出てきてしまうためです。WHERE p1.category = '文具' は、結果を文具カテゴリだけに絞って全体像を見やすくするための条件で、外せば書籍・家電・食品を含むすべてのカテゴリのペアが出力されます。

11.9 UNION と UNION ALL — 縦につなぐ結合

ここまでの JOIN は、複数の表を横に並べて列を増やす結合でした。これに対して UNION は、複数の SELECT の結果を縦に積み重ねて行を増やす結合です。両者の違いを図で比べてみましょう。

JOIN（横につなぐ＝列が増える）

customer_name order_id
佐藤 花子 1

UNION（縦につなぐ＝行が増える）

customer_name 区分
佐藤 花子 東京都在住
鈴木 一郎 家電購入あり

UNION を使うには、つなぎ合わせる各 SELECT の列数がそろっていて、対応する列の型に互換性がある必要があります。「東京都在住の顧客」と「家電を買ったことがある顧客」をまとめて1つの注意リストにする例です。

union.sql 
-- 東京都在住の顧客
SELECT customer_name, '東京都在住' AS 区分
FROM customers WHERE prefecture = '東京都'
UNION
-- 家電を買ったことがある顧客（結合結果の重複はDISTINCTで除く）
SELECT DISTINCT c.customer_name, '家電購入あり' AS 区分
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id
WHERE p.category = '家電';

UNION はすべての列の値が一致する行を1行にまとめて除去します。判定の単位は「行全体」であって、特定の1列ではありません。上の例では 区分 の値が異なるため、東京都在住であり、かつ家電も購入している顧客（高橋 健太さん）は UNION を使っても「東京都在住」「家電購入あり」の2行として出力されます。一方 UNION ALL は重複除去を行わないため、行全体が同じ行が複数あってもそのまま残ります。重複を気にせず、単純に結果を積み上げたいだけの場合は UNION ALL の方が余計な重複チェックが走らない分、処理も軽くなります。

ヒント: UNION と UNION ALL の使い分け

「重複があってはならない一覧を作りたい」なら UNION。「単純に複数のクエリ結果を積み上げたいだけで、重複が出ても構わない、あるいは重複が発生しないと分かっている」なら UNION ALL、と覚えておきましょう。

JOIN と同様に、UNION／UNION ALL の結果も行の並び順は保証されません。順序が必要な場合は、まとめ終えたクエリ全体の最後に1つだけ ORDER BY を書きます（各 SELECT の中に個別の ORDER BY は書けません）。

やってみよう 11-1: 結合SQLを自分で書いてみる

問題

  1. 1 orders と customers を INNER JOIN し、注文番号・顧客名・注文日を新しい順に一覧表示してください。期待結果: 注文が存在する分だけの行数（注文がない顧客は含まれない）。
  2. 2 LEFT JOIN と IS NULL を使い、一度も注文したことがない顧客だけを抽出してください。期待結果: 「渡辺 大輔」の1件だけが返る。
  3. 3 orders・order_items・products の3表を結合し、「注文番号・商品名・数量・(数量×単価)の小計」を一覧表示してください。期待結果: 注文明細と同じ件数の行が返り、小計が正しく計算されている。
  4. 4 結合と GROUP BY を組み合わせ、顧客ごとの購入金額合計を金額の多い順に並べてください。期待結果: 注文実績のある顧客だけが、合計金額の降順で並ぶ。

ねらい: 「どの表を左に置くか」「ON に何を書くか」「WHERE で何を絞るか」を自分の頭で組み立てる練習です。うまくいかないときは、まず結合だけのSELECTを実行して結果を目で確認してから、条件や集計を1つずつ足していくと原因を切り分けやすくなります。

理解度確認クイズ

  1. Q1. INNER JOIN と LEFT JOIN の違いを、「顧客」と「注文」の例を使って説明してください。

    回答を表示

    INNER JOIN は両方の表に対応するデータがある行だけを残すため、注文が1件もない顧客は結果に出てきません。LEFT JOIN は左側（例: customers）の表の行をすべて残し、対応する注文が無い顧客については右側（orders）由来の列を NULL で埋めて1行として残します。「存在しないデータを探したい」ときは LEFT JOIN が必要です。

  2. Q2. JOIN の ON 句と WHERE 句は、それぞれどんな役割を持ちますか。

    回答を表示

    ON は「2つの表をどの列どうしで突き合わせて結合するか」という結合条件を指定します。WHERE は、結合が終わった後の結果に対して「どの行を残すか」を絞り込む条件です。役割が異なるため、結合の仕方の指定と結果の絞り込みを混同しないことが大切です。

  3. Q3. 意図せず CROSS JOIN（全組み合わせ）になってしまうのは、どのような書き方をしたときですか。2つ挙げてください。

    回答を表示

    (1) JOIN の後ろに ON 句（結合条件）を書き忘れた場合。(2) FROM orders o, customers c のようにカンマ区切りで表を並べる古い書き方をして、WHERE 句での絞り込みを忘れた場合。どちらも結合条件が無いため、両方の表の全組み合わせが返ってしまいます。

  4. Q4. UNION と UNION ALL の違いは何ですか。

    回答を表示

    UNION は複数の SELECT の結果を縦に積み重ねたうえで、重複する行（すべての列の値が一致する行）を1行にまとめて除去します。UNION ALL は重複除去を行わず、すべての行をそのまま積み重ねます。重複の可能性があり、それを取り除きたいなら UNION、単純に積み上げるだけでよいなら UNION ALL を使います。
