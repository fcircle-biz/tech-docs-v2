14.1 インデックスとは — 「本の索引」の考え方

分厚い専門書で特定の用語を探すとき、私たちは巻末の索引を使います。索引がなければ、1ページ目から順番にすべてのページをめくって探す（全件走査）しかありません。データベースのテーブルも同じで、行数が増えるほど「先頭から1行ずつ全部確認する」検索は遅くなります。この全件走査のことを、PostgreSQL ではシーケンシャルスキャン（Seq Scan）と呼びます。

インデックスは、この本の索引にあたる仕組みです。特定の列の値を、あらかじめ検索しやすい形（既定では B-tree という木構造）に整理しておき、目的の行へすばやくたどり着けるようにします。CREATE INDEX で作成し、DROP INDEX で削除します。

create-index.sql 
-- customers テーブルの prefecture 列にインデックスを作成
-- （PostgreSQL の既定はB-tree方式）
CREATE INDEX idx_customers_prefecture
    ON customers (prefecture);

-- 不要になったインデックスは削除できる
DROP INDEX idx_customers_prefecture;

ヒント: インデックス名の慣例

idx_テーブル名_列名 のように命名すると、あとで見返したときにどのテーブルの何のためのインデックスか一目で分かります。本ガイドでもこの慣例に従っています。

14.2 どの列にインデックスを作るとよいか

実は、PRIMARY KEY 制約を付けた列には、テーブル作成時に自動でユニークインデックスが作られます。第5章で customer_id などに主キーを設定したときから、皆さんは既にインデックスの恩恵を受けていたことになります。

では、主キー以外にどの列へインデックスを追加するとよいのでしょうか。目安は次の2点です。

目安 説明 具体例
WHERE / JOIN でよく使う列 絞り込みや結合の条件に頻繁に登場する列は候補になる orders.customer_id（第11章の結合条件）
カーディナリティが高い列 値の種類が多く、1つの値で行を大きく絞り込める列ほど効果が出やすい email（ほぼ全行が異なる値）

逆に、orders.status のように値の種類が「受付／発送済／キャンセル」の3つしかない列（カーディナリティが低い列）は、インデックスを作っても効果が薄いことが多くなります。次の14.3で理由を見ていきます。

14.3 インデックスが効かないケース

インデックスを作っても使われない（＝ Seq Scan のままになる）代表的なケースが3つあります。第7章・第8章で「これは後の章で説明します」と予告していた内容の回収です。

ケース 具体例 理由
列に関数を適用している WHERE upper(customer_name) = 'SATO'（第8章の文字列関数） 索引は「元の値」を並べたもの。upper() で変換した後の値は索引に無い
前方ワイルドカードの LIKE WHERE product_name LIKE '%ノート%'（第7章のLIKE） 先頭が不明だと、索引の「先頭文字から辿る」性質を活かせない
対象行が多すぎる（低選択性） WHERE status = '受付'（全体の大半を占める値） 索引を辿ってから本体を1行ずつ見に行くより、最初から全件を読んだほうが速いとプランナが判断する

つまり、インデックスを作ったからといって必ず使われるわけではありません。実際に使われているかどうかは、次の14.5で紹介する EXPLAIN で確認する必要があります。

14.4 インデックスの代償 — 「とりあえず全列」が誤りである理由

ここまで読むと「検索が速くなるなら、全部の列にインデックスを作ればよいのでは」と思うかもしれません。しかし、インデックスは無料の仕組みではありません。主に2つの代償があります。

  • 追加・更新・削除が遅くなる — INSERT / UPDATE / DELETE のたびに、テーブル本体だけでなく、そこに付いているすべてのインデックスも更新しなければならない
  • ディスク容量を消費する — インデックス自体もデータであり、テーブル本体とは別に保存領域を必要とする

注意: 「とりあえず全列にインデックス」は誤り

検索は速くなりますが、書き込みのたびにすべてのインデックスを更新するコストがのしかかり、更新の多いテーブルほど全体が遅くなります。WHERE や JOIN の条件で実際によく使う列に絞って作るのが基本方針です。迷ったら、まずインデック無しで運用し、実際に遅いクエリが見つかってから14.5の EXPLAIN で原因を確認し、必要な列にだけ追加しましょう。

14.5 実行計画を見る — EXPLAIN と EXPLAIN ANALYZE

PostgreSQL は SELECT を実行する前に「どういう手順でデータを取り出すか」という実行計画を立てます。この計画を覗き見るのが EXPLAIN です。実際にはクエリを実行せず、計画だけを表示します。

explain-before.sql 
-- インデックス作成前の実行計画を確認する
EXPLAIN SELECT customer_name
FROM customers
WHERE prefecture = '東京都';

インデックス作成前は、次のように Seq Scan（シーケンシャルスキャン＝全件走査）と表示されます。

実行結果（インデックス無し） 
                          QUERY PLAN
------------------------------------------------------
 Seq Scan on customers  (cost=0.00..1.12 rows=1 width=20)
   Filter: (prefecture = '東京都'::text)

idx_customers_prefecture を作成後、同じクエリを実行すると次のように Index Scan（索引利用）へ切り替わります。

実行結果（インデックス作成後） 
                                QUERY PLAN
------------------------------------------------------------------
 Index Scan using idx_customers_prefecture on customers
   (cost=0.14..8.16 rows=1 width=20)
   Index Cond: (prefecture = '東京都'::text)

cost=0.14..8.16 の部分は「開始コスト..合計コスト」という推定の重さを表す目安の数値で、単位は秒ではありません。今の段階では「小さいほど軽いと見積もられている」とだけ覚えておけば十分です。実際に実行して本当の時間まで測りたいときは EXPLAIN ANALYZE を使います。

実行結果（EXPLAIN ANALYZE） 
 Index Scan using idx_customers_prefecture on customers
   (cost=0.14..8.16 rows=1 width=20)
   (actual time=0.021..0.023 rows=2 loops=1)
   Index Cond: (prefecture = '東京都'::text)
 Planning Time: 0.082 ms
 Execution Time: 0.041 ms

actual time はミリ秒単位の実測値です。EXPLAIN ANALYZE は実際にクエリを実行してしまう点に注意してください。DELETE や UPDATE の計画を確認するときにうっかり本当に実行してしまわないよう、対象は基本的に SELECT にとどめましょう。

ヒント: pgAdmin の「Explain」ボタン

pgAdmin 4 のクエリツールには、SQL を書いたあと押すだけで実行計画を図（ツリー）として表示してくれる「Explain」ボタンがあります。文字の出力より直感的に読めるので、まずはこちらで全体の形をつかみ、細かい数値をテキスト出力で確認する、という使い分けがおすすめです。

14.6 ユーザーと権限 — ロールと GRANT / REVOKE

PostgreSQL では「ユーザー」と「グループ」を区別せず、ロールという1つの概念にまとめています。ロールには、ログインしてSQLを実行できる「ログインロール」と、権限をまとめておくだけの「グループロール」がありますが、作り方はどちらも CREATE ROLE です。

roles-and-grant.sql 
-- アプリケーション専用のロールを作成する
CREATE ROLE app_user LOGIN PASSWORD 'secure_password';

-- customers テーブルの参照だけを許可する
GRANT SELECT ON customers TO app_user;

-- orders テーブルは参照と追加のみ許可する
GRANT SELECT, INSERT ON orders TO app_user;

-- 追加の権限が不要になったら取り消す
REVOKE INSERT ON orders FROM app_user;

ここで意識したいのが最小権限の原則です。「そのユーザーが本当に必要な操作だけを許可し、それ以外はすべて拒否する」という考え方で、権限管理の基本方針になります。

注意: アプリ用ユーザーに postgres を使ってはいけない

インストール時に作られる postgres はすべての操作を行えるスーパーユーザーです。アプリケーションの接続にこれを使うと、SQLインジェクションなどでアプリが乗っ取られた場合にデータベース全体が危険にさらされます。アプリごとに最小限の権限を持つ専用ロールを作り、postgres は管理作業のときだけ使うのが鉄則です。

14.7 バックアップと復元

どれだけ気をつけて運用していても、操作ミスやハードウェア障害でデータが失われる可能性はゼロにできません。だからこそ、定期的なバックアップが欠かせません。PostgreSQL には pg_dump というコマンドがあり、データベースの内容を1つのファイル（論理バックアップ）として書き出せます。

backup-and-restore.sh 
# shop_db をカスタム形式でバックアップする
pg_dump -U postgres -Fc shop_db > shop_db_backup.dump

# 練習用データベース shop_db_practice へ復元する
pg_restore -U postgres -d shop_db_practice shop_db_backup.dump

# SQL形式（プレーンテキスト）で書き出した場合は psql で復元する
psql -U postgres -d shop_db_practice -f shop_db_backup.sql

コマンドを覚えなくても、pgAdmin 4 ではデータベースを右クリックして「Backup...」「Restore...」を選ぶだけで、同じ操作を画面から行えます。日常の運用では、こちらの GUI から実行することが多くなるでしょう。

注意: 復元は必ず練習用データベースで試す

pg_restore や「Restore」を本番のデータベースに直接試すのは絶対にやめましょう。復元先を間違えると、現在のデータが上書き・混在してしまう危険があります。まず練習用のデータベース（shop_db_practice のような別名）を作って復元を試し、手順に問題がないことを確認してから本番の運用計画に組み込みます。

14.8 メンテナンス — VACUUM と ANALYZE

第13章で「PostgreSQL は更新のたびに古い行の版を残す MVCC という仕組みで動いている」と学びました。この不要になった古い版をそのままにしておくと、テーブルが無駄に膨らんでいきます。それを回収するのが VACUUM です。

maintenance.sql 
-- 不要になった古い行の領域を回収する
VACUUM customers;

-- 実行計画のもとになる統計情報を更新する
ANALYZE customers;

-- 2つをまとめて実行することも多い
VACUUM ANALYZE customers;

ANALYZE は「この列にはどんな値がどれくらいの割合で入っているか」という統計情報を更新するコマンドです。14.5で見た実行計画は、この統計情報をもとにプランナが立てているため、統計が古いままだと不適切な計画（本来 Index Scan にすべきなのに Seq Scan を選ぶなど）を選んでしまうことがあります。

実際には、PostgreSQL は自動バキューム（autovacuum）という仕組みを標準で備えており、テーブルの更新量に応じて自動的に VACUUM と ANALYZE を実行してくれます。個人学習やごく小規模な運用では、これに任せておくだけで基本的に困りません。日常の確認項目としては、次のようなものを覚えておきましょう。

  • バックアップが定期的に、かつ正常に取得できているか
  • ディスクの空き容量が十分にあるか
  • 特定のクエリだけ極端に遅くなっていないか（遅ければ14.5の EXPLAIN で原因を調べる）

やってみよう 14-1: インデックスの前後で実行計画を見比べる

14.5で紹介した EXPLAIN を、自分の手で実行して確かめてみましょう。orders テーブルを customer_id で絞り込むクエリを題材にします。

手順

  1. 1 インデックスを作る前に EXPLAIN SELECT * FROM orders WHERE customer_id = 3; を実行し、結果に Seq Scan と表示されることを確認する。
  2. 2 CREATE INDEX idx_orders_customer_id ON orders (customer_id); を実行してインデックスを作成する。
  3. 3 同じ EXPLAIN を再実行し、Index Scan に変わったか確認する。pgAdmin の「Explain」ボタンで図として見比べるのもおすすめ。
  4. 4 練習が終わったら DROP INDEX idx_orders_customer_id; で後片付けする。

注意: 本ガイドの orders は約15件しかないため、行数が少なすぎるとプランナが「全件見ても大差ない」と判断し、インデックス作成後も Seq Scan のままになることがあります。それ自体が誤りではなく、データ量が少ないときはプランナが賢く判断しているという良い学びです。実務で数百万行のテーブルに対して同じ実験をすると、より明確に Index Scan への変化が見られます。

理解度確認クイズ

  1. Q1. インデックスを作成すると検索が速くなる一方で、何が遅くなりますか。またその理由も答えてください。

    回答を表示

    INSERT / UPDATE / DELETE が遅くなります。これらの操作のたびに、テーブル本体だけでなく、そのテーブルに付いているすべてのインデックスも更新する必要があるためです。あわせてディスク容量も消費します。

  2. Q2. WHERE upper(customer_name) = 'SATO' のように書くと、customer_name にインデックスを作っていても効かないことがあります。なぜですか。

    回答を表示

    インデックスは列の「元の値」を整理して並べたものです。upper() で変換した後の値はインデックスの中に存在しないため、そのままでは索引を使って絞り込めず、全件走査（Seq Scan）になってしまいます。

  3. Q3. アプリケーションの接続ユーザーに、スーパーユーザーである postgres をそのまま使うべきではない理由を説明してください。

    回答を表示

    postgres はすべての操作を無制限に行えるスーパーユーザーです。アプリがSQLインジェクションなどで乗っ取られた場合、データベース全体が危険にさらされます。最小権限の原則に従い、アプリごとに必要な操作だけを許可した専用ロールを作成して使うべきです。

  4. Q4. pg_dump で取得したバックアップを pg_restore で復元する練習をするとき、真っ先に守るべきことは何ですか。

    回答を表示

    復元先を本番のデータベースにしないことです。復元先を間違えると現在のデータが上書き・混在してしまう危険があるため、必ず練習用の別データベースを用意し、そこに復元して手順を確認してから本番の運用に組み込みます。
