ホーム Oracle 第13章
第13章 所要時間: 約1.5時間

インデックスと性能の基礎

第12章までで「正しく動くSQL」が書けるようになりました。この章では「速く動くSQL」に踏み込みます。データが数百万行に増えても、大量データから必要な行を探す処理を高速化できる場合がある仕組みであるインデックス（索引）の正体を、書籍の索引にたとえて理解し、実行計画の読み方、インデックスが裏目に出る書き方、そして「付けすぎ」の弊害までを学びます。

この章で学ぶこと

  • インデックスの仕組みを比喩で説明でき、CREATE INDEX / DROP INDEX で作成・削除できる
  • インデックスが使われない代表的な書き方を挙げ、回避できる
  • EXPLAIN PLAN / DBMS_XPLAN や SQL Developer で実行計画を確認できる
  • インデックスの副作用（更新が遅くなる・容量を使う）を理解し、付けすぎない判断ができる

13.1 なぜ検索は遅くなるのか

第6章から何度も書いてきた SELECT ... WHERE ... は、これまでほとんど待たされずに結果が返ってきました。employees 表がたった10件しかなかったからです。しかし実務のデータベースでは、1つの表に数百万行が入っていることも珍しくありません。何も工夫しなければ、Oracle は条件に合う行を探すために表の1行目から最終行まで、すべての行を順番に読んで確認します。この動作をフルテーブルスキャン（全表走査）と呼びます。

たとえるなら、索引のない分厚い辞典から「トランザクション」という言葉を探すのに、1ページ目から1枚ずつめくって探すようなものです。数十ページの薄い冊子なら気になりませんが、1,000ページを超える辞典だと現実的ではありません。データベースの表も同じで、行数が少ないうちは全表走査でもさほど時間はかかりませんが、行数が増えるほど読む量に比例して時間がかかるようになります。

用語メモ: フルテーブルスキャン（TABLE ACCESS FULL）

表の全行を先頭から順番に読む動作のことです。実行計画（13.4節）の中では TABLE ACCESS FULL という表記で現れます。行数が少ない表や、表の大半を取得したい問い合わせでは、むしろ最も効率の良い選択になることもあります。「常に悪」ではなく「使いどころがある動作」だと覚えておきましょう。

では、辞典であれば私たちは何を使うでしょうか。巻末の索引です。「トランザクション → 245ページ」のように調べたい語とページ番号が対応付けられており、そこから目的のページへ直行できます。Oracle にも、この「索引」に相当する仕組みがあります。それが本章の主役、インデックスです。

13.2 インデックスとは何か 必須

インデックス（索引）とは、特定の列の値をあらかじめ検索しやすい形に整理しておき、目的の行へすばやくたどり着けるようにする仕組みです。図書館で目的の本を探すとき、書架を端から端まで歩いて探す人はいません。蔵書目録（書名や著者名から本の場所を調べる仕組み）を引いて、棚の場所を先に調べてから直行します。書籍の巻末索引も同じ発想です。Oracle のインデックスは、この「目録」や「索引」をデータベースの中に自動的に作る機能だと考えてください。

Oracle が既定で作成するインデックスはB*Tree索引（ビースター・ツリー。値を整列させて木構造に格納し、どの枝をたどっても根っこから葉までの深さが同じになるよう自動で調整される索引）と呼ばれる形式です。「整列された値を木構造でたどる」というイメージを、図で確認しましょう。

flowchart TD Root["ルートブロック
大小関係でどちらの枝へ進むか判定"] --> B1["ブランチブロック
値が10～49の範囲"] Root --> B2["ブランチブロック
値が50～99の範囲"] B1 --> L1["リーフブロック
10, 15, 23, 31（整列済み）"] B2 --> L2["リーフブロック
55, 61, 78, 92（整列済み）"] L1 -->|ROWIDで直行| T1["表employeesの該当行"] L2 -->|ROWIDで直行| T2["表employeesの該当行"]

一番上のルートブロックから始まり、ブランチブロック（中間層。値の範囲ごとに次にどこへ進むかを振り分ける）を経由して、一番下のリーフブロック（葉。実際の値が整列した状態で並ぶ末端の層）にたどり着きます。リーフブロックには、値そのものに加えてROWID（表の中でその行が物理的にどこにあるかを示す住所のようなもの）が格納されており、ここから表の該当行へ1回で直行できます。

重要ポイント: 行数が増えても検索を高速化しやすい理由

B*Treeの1つのブロックには、大量のキー（索引の値）を詰め込めます。そのため行数が10倍・100倍に増えても、ルートからリーフまでの深さ（階層の数）はほとんど増えません。多くの場合、数百万行の表でも3〜4段たどるだけで目的の行に到達できます。「全部読む」全表走査が行数に比例して遅くなるのに対し、インデックスを適切に利用すると、大量データから必要な行を探す処理を高速化できる場合があります。ただしインデックスは万能ではありません。更新のたびに索引も書き換える必要があるなど代償もあるため、詳しくは13.7節で確認します。

13.3 インデックスを作る・消す 必須

インデックスは CREATE INDEX で作成し、DROP INDEX で削除します。表そのものを変更するわけではないので、employees や departments のデータには一切影響しません。

create_drop_index.sql 
-- department_idでの検索によく使うので索引を作る
CREATE INDEX idx_emp_dept ON employees(department_id);

-- 索引が増えたことを確認する
SELECT index_name FROM user_indexes WHERE table_name = 'EMPLOYEES';

-- 動きを確認できたので、いったん削除しておく
DROP INDEX idx_emp_dept;

実は employees と departments には、すでにインデックスが存在します。第5章で PRIMARY KEY 制約を付けたときに、Oracle が自動的に一意索引（UNIQUE INDEX）を作成していたからです。UNIQUE 制約を付けた場合も同様です。自分の索引を確認するには、データディクショナリ（Oracle自身が管理情報を保存している表）の USER_INDEXES / USER_IND_COLUMNS を使います。

check_pk_indexes.sql 
-- 自分が持っている索引と、その対象列を確認する
SELECT i.index_name, i.table_name, i.uniqueness, c.column_name
  FROM user_indexes i
  JOIN user_ind_columns c ON i.index_name = c.index_name
 WHERE i.table_name IN ('EMPLOYEES', 'DEPARTMENTS')
 ORDER BY i.index_name, c.column_position;
INDEX_NAME       TABLE_NAME    UNIQUENES  COLUMN_NAME
---------------- ------------- ---------- --------------
PK_DEPARTMENTS   DEPARTMENTS   UNIQUE     DEPARTMENT_ID
PK_EMPLOYEES     EMPLOYEES     UNIQUE     EMPLOYEE_ID

主キー制約を作ったときの索引だけが見つかりました。外部キー制約（fk_emp_dept）には、Oracle は索引を自動生成しません。これは初心者が見落としやすい点です。外部キー列に索引が無いと、親表（departments）側を更新するときに子表（employees）側の関係する行がロックされやすくなる、という運用上の注意点があります（詳しくは13.7節）。

参考 複数の列をまとめて1つにしたインデックスを複合索引（複合インデックス）と呼びます。列の並び順が重要で、先頭の列を条件に含めないと使われにくいという特徴があります（詳しくは次のヒントを参照）。たとえば「部署ごとに給与順で調べる」ことが多いなら、次のように書きます。

composite_index_example.sql 
-- department_id → salary の順に並んだ複合索引を作る
CREATE INDEX idx_emp_dept_salary ON employees(department_id, salary);

-- 列の並び順（構造）を確認する
SELECT column_name, column_position
  FROM user_ind_columns
 WHERE index_name = 'IDX_EMP_DEPT_SALARY'
 ORDER BY column_position;

-- 構造を確認できたので、いったん削除しておく
DROP INDEX idx_emp_dept_salary;

ヒント: 複合索引は「先頭列」が命

電話帳は「姓 → 名」の順に並んでいます。「田中さん」は姓から探せますが、名前が「太郎さん」だけでは電話帳をどこから開けばよいか分かりません。複合索引も同じで、(department_id, salary) の順で作った索引は、WHERE department_id = 10 のように先頭列（department_id）を条件に含む検索でよく使われます。WHERE salary = 400000 のように先頭列を飛ばして2番目の列だけ条件にしても、この索引は使われにくくなります。

13.4 実行計画の読み方 参考

「このSQLは索引を使っているのか、全表走査なのか」を推測ではなく確認する方法が実行計画（Execution Plan）です。Oracle がその SQL をどんな手順で処理するつもりかを、実際には実行せずに表示してくれます。最も基本的な確認方法は EXPLAIN PLAN FOR（Oracle標準のSQL文です。SQL*Plus専用のコマンドではなく、SQL Developerなど別のツールからも実行できます）と DBMS_XPLAN（実行計画を整形して表示するパッケージ）の組み合わせです。

注意: 実行計画は環境によって変わる

実行計画は、表の行数・データの偏り・統計情報（表の行数や値の分布などを表すデータ。13.6節で説明します）の状態・SQLの書き方・実行環境などによって変わります。同じSQLでも、統計情報が更新されたりデータが増えたりすると、Oracle が選ぶ実行計画は変わることがあります。本章に掲載する実行計画やCostの値はあくまで一例です。みなさんの環境の結果がここに書かれている値と一致しなくても、問題はありません。

explain_full_scan.sql 
-- 実行計画を組み立てるだけで、SQLは実際には実行されない
EXPLAIN PLAN FOR
SELECT * FROM employees WHERE department_id = 10;

-- 組み立てた計画を表示する
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

department_id には索引が無いため（13.3節で作った idx_emp_dept と idx_emp_dept_salary はどちらも構造を確認したうえで削除済みです）、次のように TABLE ACCESS FULL と表示されます。 

--------------------------------------------------------------
| Id  | Operation         | Name      | Rows | Cost (%CPU)|
--------------------------------------------------------------
|   0 | SELECT STATEMENT  |           |    3 |     3   (0)|
|*  1 |  TABLE ACCESS FULL| EMPLOYEES |    3 |     3   (0)|
--------------------------------------------------------------

一方、主キーの索引がすでにある employee_id で検索すると、様子が変わります。

explain_unique_scan.sql 
-- 今度は主キー(employee_id)で検索してみる
EXPLAIN PLAN FOR
SELECT * FROM employees WHERE employee_id = 105;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
-------------------------------------------------------------------
| Id  | Operation                   | Name         | Rows | Cost |
-------------------------------------------------------------------
|   0 | SELECT STATEMENT            |              |    1 |    1 |
|   1 |  TABLE ACCESS BY INDEX ROWID| EMPLOYEES    |    1 |    1 |
|*  2 |   INDEX UNIQUE SCAN         | PK_EMPLOYEES |    1 |    0 |
-------------------------------------------------------------------

実行計画は下（内側）から上（外側）へ読みます。上の例なら「まず一番下の PK_EMPLOYEES 索引を1件に絞り込み（INDEX UNIQUE SCAN）、その住所（ROWID）を使って表本体から1行だけ取り出す（TABLE ACCESS BY INDEX ROWID）」という順で読みます。まずは次の3つの用語だけ覚えれば十分です。

表記 意味
TABLE ACCESS FULL 表を先頭から最後まで全部読む（全表走査）
INDEX RANGE SCAN 索引を使って値の範囲を絞り込む（複数行がヒットしうる）
INDEX UNIQUE SCAN 一意索引を使って1行だけを特定する

SQL*Plus では SET AUTOTRACE ON を実行しておくと、SQL を実行するたびに結果と一緒に実行計画が自動表示されます（初回のみ管理者に PLUSTRACE ロールの付与を依頼する必要がある場合があります）。SQL Developer なら、ワークシートで SQL を選択してF10（実行計画）を押すだけで、同じ内容がツリー形式で表示されます（第4章のショートカット表で予告した機能です）。

注意: Cost（コスト）は「秒数」ではない

Cost は Oracle が見積もった相対的な重さであり、単位は秒でも回数でもありません。同じSQLを書き換える前後で比較するための数字であって、まったく別のSQL同士を比べる指標ではありません。「Cost が小さいから速い」と早合点せず、あくまで目安として使いましょう。

13.5 インデックスが効かない書き方 必須

索引を作っても、WHERE 句の書き方によっては使われないことがあります。ここでは代表的な3つのパターンを、実際に employees で確認してみましょう。

index_not_used_patterns.sql 
-- (1) 列に関数を適用：TRUNCで時刻部分を切り捨てて比較している
SELECT * FROM employees WHERE TRUNC(hire_date) = DATE '2015-04-01';

-- (2) 前方一致でないLIKE：先頭が%だと索引をたどれない
SELECT * FROM employees WHERE last_name LIKE '%藤';

-- (3) IS NULLの検索：単一列のB*Tree索引にはNULLが格納されない
SELECT * FROM employees WHERE department_id IS NULL;

この3つはいずれも実行計画を見ると TABLE ACCESS FULL になります（現時点では該当する索引が無いためです）。それぞれの理由と対策を整理します。

用語メモ: 選択性（せんたくせい、selectivity）

ある条件によって、表の行がどれくらい絞り込まれるかの割合のことです。たとえば「該当するのは全体の1%だけ」のようにごく少数の行に絞り込める条件は選択性が高いといい、索引が効果を発揮しやすくなります。逆に「該当するのが全体の80%」のように多くの行が当てはまる条件は選択性が低いといい、索引を使うより表を全部読んだほうが効率的な場合があります。下の表の「選択性が低い」の行が、この考え方にあたります。

書き方 なぜ効かないか 対策
索引列に関数を適用
例: WHERE TRUNC(hire_date) = …		 索引には「加工前」の生の値しか入っていない。関数を適用した後の値と直接は比較できない 加工後の値に対するファンクション索引を作るか、範囲指定に書き換える
前方一致でない LIKE
例: WHERE last_name LIKE '%藤'		 索引は値の先頭から整列している。先頭が不確定だと、どこから探せばよいか決められない 可能であれば前方一致（'藤%'）に書き換える
IS NULL の検索 単一列のB*Tree索引は、その列がNULLの行を格納しない仕様になっている NULLを含む行が多い場合は、そもそも全表走査でよいと割り切る
暗黙の型変換 列と比較する値の型が違うと、Oracleがどちらかを自動変換する。変換が列側にかかると索引が使えなくなる 比較する値の型を、列の型に明示的に合わせる
選択性が低い
表の大半が該当する条件		 索引経由で1行ずつ表を見に行くより、表を最初から読み切るほうが読み込み回数が少なく済む 対策不要。Oracleの正常な判断であり、全表走査のままでよい

発展 Oracle固有 (1) の対策であるファンクション索引（関数索引）（列の値をそのままではなく、UPPER(name) のように関数を適用した結果に対して作るインデックス）を実際に作ってみましょう。hire_date は第8章で学んだとおり時刻まで持つ DATE 型なので、日付だけで検索したい場面は今後も出てきます。

function_based_index.sql 
-- TRUNC(hire_date)の計算結果そのものに索引を作る
CREATE INDEX idx_emp_hire_trunc ON employees(TRUNC(hire_date));

-- これでWHERE句の書き方は変えずに済む
SELECT * FROM employees WHERE TRUNC(hire_date) = DATE '2015-04-01';

補足: employeesは10件しかない

ここで索引を作っても、employees はわずか10件しかないため、Oracle が「索引をたどるより全部読んだほうが速い」と判断し、実行計画が TABLE ACCESS FULL のままのことがあります。これは異常ではありません。索引の効果をはっきり確認するには、もっと多くの行が必要です。この後の「やってみよう」で、5万行の表を使って確かめます。

索引が使われるかどうかを判断する流れを、図でも整理しておきましょう。

INDEX RANGE SCAN など"]

13.6 統計情報とバインド変数 参考

Oracle は勘で実行計画を選んでいるわけではありません。実行計画を決める Oracle 内部の機能をオプティマイザ（Optimizer）と呼びます。オプティマイザは統計情報（表の行数、列の値の分布、索引の高さなど、表の"体格"を表すデータ）をもとに、どの方法が最も安く済むかを見積もっています。大量にデータを入れた直後や、表の中身が大きく変わった後は、統計情報が古いままだと見積もりを誤ることがあるため、手動で更新します。

gather_stats.sql 
-- employees表の統計情報を最新化する
-- 第1引数USERは「自分のスキーマ」、第2引数は表名
EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'EMPLOYEES');

なお EXEC はSQL文ではなく、SQL*Plus（やSQL Developerなど多くのGUIツール）が用意しているコマンドです。PL/SQLの BEGIN ... END; を1行で書くための省略記法だと考えてください。DBMS_STATS.GATHER_TABLE_STATS 自体はOracleが提供するPL/SQLパッケージのプロシージャです。

もう1つ、性能に関わる基本テクニックがバインド変数（SQL文の中で値を直接書かず、後から差し込む変数）です。WHERE department_id = 10 と WHERE department_id = 20 は値が違うだけの"別のSQL"として扱われ、そのたびに解析（構文チェックと実行計画の作成）が行われます。バインド変数を使うと形が同じSQLとして扱われ、第2章で学んだ共有プール（一度解析したSQLの結果を使い回す領域）に載った解析結果を再利用でき、無駄な解析を減らせます。

bind_variable.sql 
-- SQL*Plusでバインド変数を宣言する
VARIABLE v_dept NUMBER
EXEC :v_dept := 10;

-- 値を直接書かず、バインド変数として渡す
SELECT last_name, salary FROM employees WHERE department_id = :v_dept;

上のコードのうち VARIABLE 宣言と EXEC はSQL*Plusのコマンドで、最後の SELECT 文だけが実際のSQLです。初心者のうちは「値を直書きせずバインド変数を使うと、解析結果を使い回せて効率が良い」という考え方だけ覚えておけば十分です。PL/SQL（第10章）の中で書くSQLは、変数を使うだけで自動的にバインド変数と同じ扱いになります。

13.7 インデックスの代償と設計の勘所

ここまで読むと「検索を速くしたいなら、とりあえず全部の列に索引を作ればよいのでは」と思うかもしれません。これは誤りです。索引には見過ごされがちな代償があります。

書き込みが遅くなる

INSERT / UPDATE / DELETE のたびに、その列を含むすべての索引も書き換える必要があります。索引が多いほど、1回の更新にかかる手間が増えます。

容量を消費する

索引そのものも表と同じようにディスク領域（表領域）を使います。索引を増やすほど、必要な容量も増えていきます。

つまり索引は「検索を速くする代わりに、書き込みと容量を差し出す」トレードオフです。どの列に付けるべきかは、次の基準で判断します。

状況 索引を付けるべきか
WHERE や JOIN の条件によく使う列 付ける候補
外部キーの列（第9章の結合、第12章のロック両方に効く） 付ける候補
値の種類が少ない列（例: 性別、真偽フラグ） 効果が薄い
更新が非常に多い表 書き込みが遅くなるので慎重に
数百行しかない小さな表 ほぼ不要（全件読んでも速い）

注意: 「とりあえず全列に索引」は誤り

使われない索引は、検索を速くする効果を一切生まないまま、書き込みコストと容量だけを消費し続けます。まずは索引無しで運用し、実際に遅いクエリが見つかってから13.4節の実行計画で原因を確認し、必要な列にだけ追加するのが基本方針です。使われていないと分かった索引は DROP INDEX で削除しましょう。

やってみよう 13-1: 索引の効果を実行計画で確かめる

13.5節の補足のとおり、employees の10件では索引の効果を体感できません。検証専用の5万行の表を作り、索引を付ける前後で実行計画がどう変わるかを確認しましょう（employees / departments のデータには影響しません）。

注意: 以下に示す実行計画・Costの値・実行時間はあくまで一例です。結果や実行計画は、データ量・統計情報の状態・Oracleのバージョンなど、みなさんの環境によって異なります。掲載した数値と完全に一致しなくても問題ありません。「TABLE ACCESS FULLからINDEX RANGE SCANに変わったか」「Costが下がる方向に動いたか」という傾向を確認することが目的です。

  1. 1
    検証用の表 big_emp を5万行作り、統計情報を集める。
    step1_create_big_emp.sql 
    -- LEVELという疑似列を使って5万行を一気に生成する
CREATE TABLE big_emp AS
SELECT LEVEL AS emp_no,
       '社員' || LEVEL AS emp_name,
       MOD(LEVEL, 50) + 1 AS dept_no
  FROM dual
CONNECT BY LEVEL <= 50000;

-- 統計情報を集める（Oracleが正しく見積もれるようにする）
EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'BIG_EMP');
  2. 2
    索引を作る前の実行計画を確認する。
    step2_explain_before.sql 
    -- 索引を作る前の実行計画を確認する
EXPLAIN PLAN FOR
SELECT * FROM big_emp WHERE emp_no = 12345;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
    --------------------------------------------------------------
| Id  | Operation         | Name    | Rows | Cost (%CPU)|
--------------------------------------------------------------
|   0 | SELECT STATEMENT  |         |    1 |   45   (3)|
|*  1 |  TABLE ACCESS FULL| BIG_EMP |    1 |   45   (3)|
--------------------------------------------------------------
    索引が無いので、5万行を全部読むTABLE ACCESS FULLになります（数値は環境により変わります）。
  3. 3
    検索でよく使う emp_no 列に索引を作る。
    step3_create_index.sql 
    -- 検索条件によく使うemp_no列に索引を作る
CREATE INDEX idx_big_emp_no ON big_emp(emp_no);
  4. 4
    同じSQLで、索引を作った後の実行計画を確認する。
    step4_explain_after.sql 
    -- 索引を作った後、同じSQLの実行計画を確認する
EXPLAIN PLAN FOR
SELECT * FROM big_emp WHERE emp_no = 12345;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
    ------------------------------------------------------------------
| Id  | Operation                   | Name           | Rows | Cost|
------------------------------------------------------------------
|   0 | SELECT STATEMENT            |                |    1 |   2 |
|   1 |  TABLE ACCESS BY INDEX ROWID| BIG_EMP        |    1 |   2 |
|*  2 |   INDEX RANGE SCAN          | IDX_BIG_EMP_NO |    1 |   1 |
------------------------------------------------------------------
    TABLE ACCESS FULLがINDEX RANGE SCANに変わり、Costが大きく下がっていれば成功です。「体感」ではなく「計画の変化」で確認する、という本章のねらいそのものです。
  5. 5
    かたづけ: 検証用の表と、13.5節で作った索引を削除し、基準状態に戻す。
    step5_cleanup.sql 
    -- 13.5節で作ったファンクション索引を削除する
DROP INDEX idx_emp_hire_trunc;

-- 検証用の表を完全に削除する（big_emp用の索引も一緒に消える）
DROP TABLE big_emp PURGE;

ねらい: インデックスの効果は「なんとなく速くなった気がする」で判断するものではありません。実行計画という証拠を見て、狙いどおりに動いているかを確認する習慣を、この章で身につけてください。

理解度確認クイズ

  1. Q1. last_name に索引があるのに、WHERE last_name LIKE '%藤' では索引が使われません。なぜですか。

    回答を表示

    索引は値の先頭の文字から整列しています。検索条件の先頭が%（不確定）だと、索引のどこから探し始めればよいか決められないため使えません。書籍の索引が「〜で終わる語」を引けないのと同じです。前方一致（'藤%'）であれば索引を活用できます。

  2. Q2. 検索を速くしたいので、表の全列に索引を作りました。この判断の問題点は何ですか。

    回答を表示

    INSERT / UPDATE / DELETEのたびに、関係するすべての索引を更新する必要があるため書き込みが遅くなり、ディスク容量も余計に消費します。索引は「WHEREやJOINの条件によく使われ、絞り込みがよく効く列」に絞って付けるのが基本です。

  3. Q3. PRIMARY KEY 制約と FOREIGN KEY 制約では、索引の自動作成に違いがあります。どう違いますか。

    回答を表示

    PRIMARY KEY（およびUNIQUE）制約を付けると、Oracleは自動的に一意索引を作成します。一方FOREIGN KEY制約には索引は自動生成されません。結合や親表更新時のロック競合を減らしたい場合は、外部キー列に自分で索引を作る必要があります。
