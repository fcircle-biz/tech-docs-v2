14.1 ユーザーを作る・変える・消す — 入館証の発行 必須

会社に新しい社員が入ると、まず入館証を発行し、そのあとで「どの部屋に入れるか」を決めます。Oracle のユーザー管理もまったく同じ構造です。ユーザーを作ることは入館証を発行することであり、そのユーザーに何ができるかを決めるのが次の14.2で学ぶ権限です。第5章で学んだとおり、Oracle ではユーザー＝スキーマなので、「ユーザーを作る」ことは同時に「そのユーザー専用のオブジェクトの入れ物を作る」ことでもあります。

実は、第3章で次のようなコマンドを何気なく実行していました。CREATE USER hr IDENTIFIED BY ... でユーザーを作り、GRANT CONNECT, RESOURCE TO hr で権限を与え、ALTER USER hr QUOTA UNLIMITED ON USERS で表領域の割当を与える。この3行こそ、本章のテーマそのものです。ここで、その意味を一つずつきちんと理解し直しましょう。

ユーザーを作る前に必ず確認すべきことがもう一つあります。「今どのコンテナに接続しているか」です。第2章・第3章で学んだとおり、CDB$ROOT（コンテナ全体の土台）で作れるのは C## から始まる共通ユーザー（すべての PDB に存在するユーザー）だけです。業務用のユーザーは FREEPDB1 のような PDB の中に作るローカルユーザー（その PDB だけに存在するユーザー）にします。接続先を間違えたまま CREATE USER すると、第3章で遭遇した ORA-65096（共通ユーザー名が不正です）が再び発生します。SHOW CON_NAME で今の接続先を確認する習慣を、ここでも忘れないでください。

create-user.sql 
-- FREEPDB1 に接続した状態で実行する（ローカルユーザーなのでC##は不要）
-- DEFAULT TABLESPACE: 表を作るときの既定の置き場所
-- TEMPORARY TABLESPACE: 並べ替えなどの作業で一時的に使う置き場所
CREATE USER app_user IDENTIFIED BY AppPw12345
  DEFAULT TABLESPACE users
  TEMPORARY TABLESPACE temp;

-- この時点ではまだ何もできない（権限を1つも与えていないため）
-- ログインすらできない。権限は14.2で付与する

作ったユーザーは、あとから ALTER USER で変更できます。パスワードの変更、アカウントのロック（一時的に使えなくすること）とアンロック、次回ログイン時のパスワード変更強制などが代表的です。異動や休職で一時的にアクセスを止めたい場合にも使います。

alter-user.sql 
-- パスワードを変更する
ALTER USER app_user IDENTIFIED BY NewAppPw99;

-- アカウントを一時的に使えなくする（退職・休職など）
ALTER USER app_user ACCOUNT LOCK;

-- 再び使えるようにする
ALTER USER app_user ACCOUNT UNLOCK;

-- 次回ログイン時にパスワード変更を強制する
ALTER USER app_user PASSWORD EXPIRE;

ロックされたユーザーで接続しようとすると ORA-28000（アカウントはロックされています）というエラーになります。「パスワードを何度も間違えたら自動的にロックされる」というプロファイル（パスワードの有効期限やログイン失敗回数の上限などをまとめた規則）の設定が既定で有効になっているためです。学習中にロックされてしまった場合も、上記の ACCOUNT UNLOCK で解除できると覚えておくと安心です。

不要になったユーザーは DROP USER で消せます。ただし、そのユーザーが表などのオブジェクトを1つでも持っていると、そのままでは削除できません。

drop-user.sql 
-- ※ 次の2つはどちらか一方だけを実行します（両方続けて実行すると2文目はORA-01918になる）
-- 所有オブジェクトが無いユーザーは、そのまま削除できる
DROP USER app_user;

-- そのユーザーが表などのオブジェクトを持っている場合はCASCADEを使う
-- （CASCADE無しだとORA-01922: CASCADEを指定してください、になる）
DROP USER app_user CASCADE;

ヒント: 接続し直さずにコンテナを切り替える

system のような管理者ユーザーは、いったん接続したあとでも ALTER SESSION SET CONTAINER = FREEPDB1; を実行すれば、接続をやり直さずに今のセッションのまま PDB を切り替えられます。ただし hr のような PDB のローカルユーザーは、そもそも自分の PDB 以外に切り替える先を持っていません。この使い分けを覚えておきましょう。

14.2 権限の2種類 — 「できること」を許可する 必須

入館証（ユーザー）を発行しただけでは、まだどの部屋にも入れません。部屋ごとの入室許可にあたるのが権限（プリビレッジ）です。Oracle の権限は大きく2種類に分かれます。この違いを取り違えると、あとで紹介する確認方法もうまく使えないので、最初にはっきり区別しておきましょう。

システム権限

「〜できる」という行為そのものへの許可。対象となる表などは指定しない。

CREATE SESSION（接続できる）、CREATE TABLE（表を作れる）、CREATE VIEW（ビューを作れる）など。

オブジェクト権限

「この表に対して〜できる」という、対象付きの許可。

SELECT ON hr.employees（employees表を参照できる）、INSERT ON hr.employees（行を追加できる）など。

権限を与えるコマンドが GRANT、取り消すコマンドが REVOKE です。書き方はどちらの権限でもほぼ同じ形をしています。

grant-revoke.sql 
-- ログインできるようにする（システム権限）
GRANT CREATE SESSION TO app_user;

-- 自分の表を作れるようにする（システム権限）
GRANT CREATE TABLE TO app_user;

-- hrのemployees表を参照できるようにする（オブジェクト権限）
GRANT SELECT ON hr.employees TO app_user;

-- 更新も許可する場合はカンマで並べる
GRANT SELECT, INSERT, UPDATE ON hr.employees TO app_user;

-- 与えた権限を取り消す
REVOKE INSERT, UPDATE ON hr.employees FROM app_user;

注意: 権限があっても ORA-01950 になることがある

CREATE TABLE 権限を与えても、実際に CREATE TABLE を実行した瞬間に ORA-01950（表領域に対する権限がありません）が出ることがあります。原因は、表領域にデータを書き込むための割当（クォータ）が別に必要だからです。第3章で ALTER USER hr QUOTA UNLIMITED ON USERS; を実行していたのは、まさにこのためでした。「権限」と「クォータ」は別の設定だと覚えておきましょう。

14.3 ロールで権限をまとめる — 最小権限の原則 必須

ユーザーが増えてくると、1人ずつ同じ権限を何行も GRANT するのは大変です。そこで使うのが ロール（権限をひとまとめにした束）です。会社にたとえるなら「人事部用の入館証セット」のようなもので、あらかじめ必要な権限をロールにまとめておき、それをユーザーに渡すだけで済みます。

Oracle にはあらかじめ用意された定義済みロールが2つあります。CONNECT（実質的に CREATE SESSION だけを含む、接続専用のロール）と、RESOURCE（表・シーケンス・プロシージャなど、自分のオブジェクトを作る権限をまとめたロール）です。第3章で GRANT CONNECT, RESOURCE TO hr; と実行したのは、この2つのロールをまとめて渡していたのでした。ただしRESOURCE ロールを与えても、表領域のクォータは含まれません。14.2の注意点と合わせて覚えておきましょう。

学習環境専用の簡略設定であることに注意 学習環境専用

第3章や本章で使っている GRANT CONNECT, RESOURCE TO hr; と ALTER USER hr QUOTA UNLIMITED ON USERS; は、学習をすぐに始められるようにするための簡略設定であり、本番環境向けの最小権限設定ではありません。QUOTA UNLIMITED（表領域を無制限に使える設定）は、本番では意図しない容量消費につながりやすいため、通常は QUOTA 500M ON USERS のように具体的な上限を指定します。アプリケーション開発者向けの権限セットを実務で検討する際は、CONNECT / RESOURCE の代わりに、Oracle Database 23ai で追加され 26ai でも利用できる DB_DEVELOPER_ROLE（開発者に必要な権限一式をまとめて与える、より新しい定義済みロール。GRANT DB_DEVELOPER_ROLE TO ユーザー名; で付与）も参考にしてください 参考。

独自のロールを作ることもできます。「参照専用」のように、業務でよく使う権限のまとまりを1つのロールにしておくと、ユーザーが増えても管理が楽になります。

create-role.sql 
-- 「参照専用」の権限セットを作る
CREATE ROLE readonly_role;
GRANT SELECT ON hr.employees   TO readonly_role;
GRANT SELECT ON hr.departments TO readonly_role;

-- ロールをユーザーに与える（1回で複数の権限が渡る）
GRANT readonly_role TO app_user;
flowchart LR A["app_user（ユーザー）"] -->|付与| B["readonly_role（ロール）"] B -->|まとめて持つ| C["SELECT ON employees"] B -->|まとめて持つ| D["SELECT ON departments"] A -->|直接付与| E["CREATE SESSION（システム権限）"] A -.->|表領域の割当・権限とは別| F["QUOTA ON USERS"]

図の点線は「権限とは別の設定」であることを表しています。ロールでどれだけ権限をまとめても、表領域のクォータだけは ALTER USER ... QUOTA で別途与える必要がある、という点は本章で繰り返し出てくる重要な注意点です。

警告: DBAロールを安易に付けない（最小権限の原則）

「動かないから、とりあえず GRANT DBA TO app_user; すればいい」は避けるべき近道です。DBA ロールは、ユーザーの作成・削除、他人の全データの参照・変更、データベース全体の設定変更まで、ほぼすべての操作を許可してしまう非常に強力なロールです。アプリケーション用のユーザーが DBA 権限を持ったまま SQL インジェクションなどで乗っ取られると、被害はそのアプリの表だけでなくデータベース全体に及びます。必要な操作を洗い出し、必要な分だけを GRANT する——これが最小権限の原則です。

14.4 自分の権限とユーザーを確認する 参考

第4章では「迷子になったら DESC・SHOW USER・USER_TABLES」と学びました。権限まわりにも同じように、確認用のビュー（データディクショナリ）が用意されています。自分に何が許されているか分からなくなったら、まずこれらを見る習慣をつけましょう。

check-privileges.sql 
-- 自分が持っている表の一覧（第4章のUSER_TABLESの応用）
SELECT table_name FROM user_tables ORDER BY table_name;

-- 自分に付与されているロール
SELECT granted_role, admin_option FROM user_role_privs;

-- 自分に付与されているシステム権限
SELECT privilege FROM user_sys_privs ORDER BY privilege;

-- 他人の表に対して自分が持っている権限
SELECT owner, table_name, privilege FROM user_tab_privs;

もう1つ、ALL_USERS というビューもあります。これは自分の権限とは関係なく、データベースに存在するユーザー名の一覧を表示する、比較的公開度の高いビューです。

all-users.sql 
-- データベースに存在する全ユーザーの一覧を確認する
SELECT username, created FROM all_users ORDER BY username;

USER_ で始まるビューは「自分に関係する範囲だけ」、ALL_ で始まるビューは「自分から見える範囲すべて」を表す、という接頭辞の違いも覚えておくと、今後さまざまなデータディクショナリに出会ったときに迷いにくくなります。

14.5 バックアップの考え方 — 論理と物理 必須

どれだけ注意していても、操作ミスやハードウェア障害でデータが失われる可能性をゼロにはできません。だからこそバックアップ（データの複製を別に保存しておくこと）が欠かせません。Oracle のバックアップは、大きく2つの考え方に分かれます。

アルバムにたとえると分かりやすいでしょう。Data Pumpは「アルバムから必要な写真だけを選んで、別のアルバムに焼き増しする」イメージです。表やスキーマといった論理的な単位で、データと定義だけを取り出し、別のデータベースへ取り込みます。つまり Data Pump の正体は「バックアップ専用ツール」というより、論理的なエクスポート／インポートの仕組みです。一方RMANは「アルバムそのものを丸ごとコピーする」イメージで、データファイル・制御ファイル（データベースの構成情報を記録した小さな管理用ファイル）・アーカイブREDOログ（データベースへのすべての変更を記録しておき、あとで巻き戻し・やり直しに使うログファイル）といった物理的なファイルを対象に、障害からデータベース全体を復旧するための、バックアップ・復旧を目的とする仕組みです。

Data Pump（論理的なエクスポート／インポート） RMAN（物理バックアップ・復旧）
対象の単位 スキーマ・表など、論理的な単位で選べる データファイル・制御ファイル・アーカイブREDOログなど、物理的な単位（データベース全体・表領域）
主な用途 別環境への移行、特定スキーマの複製・復元 障害からのデータベース全体の復旧
出力 ダンプファイル（.dmp） データファイルなどのコピー（バックアップセット）
主な実行者 開発者も使う 主に DBA（データベース管理者）
戻せる時点 エクスポートした時点 ARCHIVELOGモードなら直前まで

表からも分かるとおり、判断の軸はシンプルです。「特定のスキーマや表だけを別の環境へ持っていきたい」ならData Pump、「データベース全体が壊れてしまい、障害から復旧したい」ならRMANを使います。両者はどちらか一方を選ぶ代替関係ではなく、目的が異なる別々の道具だと理解しておくと迷いません。

14.6 Data Pumpでバックアップと復元を体験する 必須

Data Pump は、スキーマや表の単位でデータを取り出す論理バックアップの仕組みで、書き出し（エクスポート）に expdp、読み込み（インポート）に impdp というコマンドを使います。使う前に、出力先を指定するディレクトリオブジェクト（サーバー上の実際のフォルダに Oracle が付ける「名前」）が必要です。Oracle AI Database 26ai Free には既定で DATA_PUMP_DIR というディレクトリオブジェクトが用意されています。ただし既定では hr のような一般ユーザーには公開されていないため、使う前に管理者から読み書き権限をもらう必要があります。

重要: CREATE DIRECTORY のパスは「サーバー側」のパス

CREATE DIRECTORY で指定するパスは、あなたが SQL*Plus や SQL Developer を操作しているクライアントPCのパスではなく、Oracle Database が動作しているサーバー側のファイルシステム上のパスです。初心者が最も誤解しやすい点なので、必ず区別してください。第3章のようにコンテナで Oracle を動かしている場合、そのパスはコンテナの中のパスを指します。コンテナの外（手元のPC）にファイルを取り出すには、後述する docker cp やボリュームマウント（コンテナとホストのフォルダをあらかじめ結びつけておく仕組み）が別途必要です。

また、Oracle Database 側の DIRECTORY オブジェクトへの READ / WRITE 権限を GRANT しただけでは不十分な場合があります。OS（サーバーのオペレーティングシステム）側でも、Oracle のプロセスを動かしているユーザー（Linuxでは通常 oracle ユーザー）が、そのフォルダへ実際に読み書きできる必要があります。OS側の権限が不足していると、Oracle側の設定が正しくても ORA-39002 ／ ORA-39070（ディレクトリオブジェクトの作成に失敗しました）／ ORA-29283（ファイル操作エラー）のようなエラーになることがあります。

環境 ディレクトリパスの例 CREATE DIRECTORY の例
Windows に直接インストール C:\oracle\dpdump（Windowsのパス） CREATE DIRECTORY dp_dir AS 'C:\oracle\dpdump';
コンテナ（Linux、第3章の構成） /opt/oracle/dp（コンテナ内のパス） CREATE DIRECTORY dp_dir AS '/opt/oracle/dp';

既定の DATA_PUMP_DIR が実際にどのパスを指しているかも、環境によって異なります。次の SQL で、いま接続している環境の実際のパスを確認する習慣をつけましょう。

check-directories.sql 
-- 既定で用意されているディレクトリオブジェクトを確認する
SELECT directory_name, directory_path FROM all_directories;

-- 独自の出力先を作る場合（systemなど管理者ユーザーで実行する。CREATE ANY DIRECTORY権限が必要）
CREATE DIRECTORY dp_dir AS '/opt/oracle/dp';
GRANT READ, WRITE ON DIRECTORY dp_dir TO hr;

-- 既定のDATA_PUMP_DIRを使う場合も同様に、hrなど一般ユーザーには
-- 既定で権限が無いため、管理者(system等)で読み書き権限を付与しておく
GRANT READ, WRITE ON DIRECTORY DATA_PUMP_DIR TO hr;

つまずきポイント: 権限付与を忘れると ORA-39002 / ORA-39087

DATA_PUMP_DIR は既定では hr のような一般ユーザーに公開されていません。管理者で GRANT READ, WRITE ON DIRECTORY DATA_PUMP_DIR TO hr; を実行し忘れたまま expdp / impdp を実行すると、ORA-39002（無効な処理です）に続けて ORA-39087（ディレクトリ名 DATA_PUMP_DIR が無効です）が発生して失敗します。実行前に必ず権限付与を済ませておきましょう。

hr への権限付与が済んだら、hr スキーマ全体をエクスポートしてみましょう。ここが最も間違えやすい点ですが、expdp / impdp は SQL ではなく OS のコマンドラインから実行します。SQL*Plus のプロンプトに貼っても動きません。GRANT や CREATE USER、CREATE DIRECTORY が SQL*Plus 上で実行するSQLであるのに対し、expdp / impdp はターミナル（コマンドプロンプトやシェル）に入力する、まったく別の種類のコマンドです。

重要: パスワードをコマンドラインに直接書かない

expdp hr/パスワード@... のようにパスワードをコマンドラインへ直接書くと、シェルの実行履歴（~/.bash_history など）に残ったり、同じサーバーにログインしている他のユーザーが ps コマンドで実行中プロセスの引数を見たりすることで、パスワードが漏れてしまう可能性があります。SQL*Plus の公式ドキュメントでも「パスワードを平文で書くのはセキュリティ上のリスクであり、省略してプロンプトで入力することで回避できる」と明確に警告されています。下のコード例のように、ユーザー名だけをコマンドラインに書き、パスワードは Password: プロンプトで入力する方法を習慣にしましょう。

export.sh 
# hrスキーマ全体をエクスポートする（SQLではなくOSのコマンド）
# directory はサーバー側のディレクトリオブジェクト名
# パスワードを省略しているので、実行するとPassword:プロンプトが表示される
# 接続識別子を引用符で囲むのは、シェルやexpdpがコロン(:)やスラッシュ(/)を
# 誤って解釈しないようにするため（Oracle公式ドキュメント推奨の書き方）
expdp hr@"localhost:1521/FREEPDB1" \
  schemas=HR \
  directory=DATA_PUMP_DIR \
  dumpfile=hr_backup.dmp \
  logfile=hr_export.log

# 実行すると次のように表示されるので、hrのパスワードを入力する
# Password:

取得したダンプファイルは、別のスキーマ名を付けて取り込む（インポートする）こともできます。移行や、練習用に複製を作りたいときに便利です。

import.sh 
# 取得したダンプを別のスキーマ名で取り込む（パスワードは省略し、プロンプトで入力する）
impdp system@"localhost:1521/FREEPDB1" \
  directory=DATA_PUMP_DIR \
  dumpfile=hr_backup.dmp \
  remap_schema=HR:HR_COPY \
  logfile=hr_import.log

# 実行すると次のように表示されるので、systemのパスワードを入力する

ヒント: コンテナ環境では docker cp でファイルを取り出す

directory= が指すのはサーバー（コンテナ）側のパスです。第3章のようにコンテナで Oracle を動かしている場合、ダンプファイルはコンテナの中に作られます。手元の PC に取り出したいときは docker cp oracle-free:/opt/oracle/admin/FREE/dpdump/hr_backup.dmp . のように docker cp コマンドを使います。ただし DATA_PUMP_DIR が実際に指すパスは環境によって異なります（PDB では末尾にランダムな英数字のフォルダが付くことがあります）。上で確認した ALL_DIRECTORIES の directory_path の値に読み替えてください。

14.7 RMANと日々の運用 発展

RMAN（Recovery Manager / Oracle 標準の物理バックアップツール）は、データベース全体を対象にした障害復旧のための仕組みです。専用のコマンドラインから rman target / で起動し、BACKUP DATABASE; を実行するのが基本形です。expdp / impdp と同じく、rman も SQL ではなく OS のコマンドラインから実行します。細かい操作方法は本ガイドの範囲を超えますが、「こういうものがある」ことは押さえておきましょう。

RMANはどこで実行するコマンドか

rman target / はOS認証（オペレーティングシステムへのログイン情報を使ってOracleに接続する仕組み）を使うため、実行できる場所が限られます。Oracle Database が動作しているサーバー上で、かつ Oracle のソフトウェア所有者（Linuxでは oracle ユーザー、Windowsでは ORA_DBA グループに属するユーザー）としてログインした状態で実行する必要があります。第3章のようにコンテナで動かしている場合は、docker exec -it <コンテナ名> bash でコンテナの中に入ってから rman を起動します。target / の / は「今OSにログインしているユーザーの資格で、管理者として接続する」という意味です。手元のPCのSQL*PlusプロンプトやSQL Developerからは実行できません。

rman-basic.sh 
# RMANを起動してデータベースに接続する
rman target /

# データベース全体をバックアップする
RMAN> BACKUP DATABASE;

# 取得済みのバックアップの一覧を確認する
RMAN> LIST BACKUP SUMMARY;

RMAN の運用でよく出てくるのがARCHIVELOGモードです。稼働させたまま（止めずに）バックアップを取れて、障害が起きても直前の状態まで戻せるようになる運用モードです。対して既定のNOARCHIVELOGモードでは、データベースを停止してのバックアップになり、戻せるのはバックアップを取った時点までに限られます。本番運用では ARCHIVELOG モードにしておくのが基本方針だと覚えておいてください。

flowchart TD A{"何から守りたい？"} A -->|特定のスキーマを壊した／別環境へ移したい| B["Data Pump（expdp / impdp）"] A -->|データベース全体が壊れた| C["RMAN（BACKUP DATABASE）"] A -->|表をうっかりDROPしただけ| D["リサイクルビンからFLASHBACK TABLE"] C --> E{"直前まで戻したい？"} E -->|はい| F["ARCHIVELOGモードで運用する"]

重要ポイント: 小さなミスにはリサイクルビン

RMAN も Data Pump も大がかりな仕組みです。「表を1つうっかり DROP TABLE してしまった」程度の小さなミスなら、第5章で学んだ FLASHBACK TABLE ... TO BEFORE DROP のほうが手軽な復旧手段です。バックアップは「最後の砦」、リサイクルビンは「日常のやり直しボタン」と使い分けましょう。

日々の運用では、大がかりな障害対応だけでなく、次のような点を定期的に確認します。

(1) 表領域の使用率 — 自分に割り当てられた表領域の使用状況は、USER_TS_QUOTAS で確認できます。

tablespace-usage.sql 
-- 自分に割り当てられた表領域の使用状況を確認する
SELECT tablespace_name, bytes/1024/1024 AS "使用MB", max_bytes
  FROM user_ts_quotas;
-- max_bytes が -1 の場合はUNLIMITED（無制限）を意味する

(2) セッションの状況 — 第12章ではロック待ちの原因調査に V$SESSION の BLOCKING_SESSION 列を使いました。日々の運用でも、今どんな接続があるかを一覧するために使います。

check-sessions.sql 
-- 管理者ユーザー（systemなど）で、接続中のセッション一覧を確認する
SELECT username, status, program FROM v$session
 WHERE username IS NOT NULL;
-- hrのような一般ユーザーではORA-00942になることが多い
-- （V$ビューの参照にはSELECT_CATALOG_ROLEなどの権限が必要）

(3) アラートログの存在 — Oracle は起動・停止・エラーなど主要な出来事をアラートログ（データベースの"日誌"）に記録し続けています。詳しい参照方法（ADRCI などの専用ツール）は上級者向けの領域ですが、「何か調子が悪いときは、まずアラートログを見る」という存在だけは、今のうちに覚えておきましょう。

  • Enterprise Edition: Diagnostics Pack は追加費用のオプションで、EEのライセンスだけでは使えず別途ライセンスが必要
  • Standard Edition 2: Diagnostics Pack 自体が利用できない
  • Oracle AI Database 26ai Free: Diagnostics Pack / Tuning Pack が含まれており、初期化パラメータ CONTROL_MANAGEMENT_PACK_ACCESS の既定値が DIAGNOSTIC+TUNING のため、本ガイドの学習環境では AWR レポートを試すことができる

SHOW PARAMETER control_management_pack_access

Diagnostics Pack が使えない環境（Standard Edition 2 など）では、無償のStatspackが代替として使われることがあります（26ai への同梱状況は環境により異なるため、実際のファイルの有無を確認してください）。

やってみよう 14-1: 最小権限のアプリ用ユーザーを作ってみる

14.2・14.3で学んだ最小権限の原則を、実際に手を動かして確かめましょう。

  1. system で FREEPDB1 に接続し、app_user を作成する（パスワードは自分で決める）。
  2. CREATE SESSION 権限と、hr.employees への SELECT 権限だけを与える。DBA ロールは与えない。
  3. app_user で接続し直し、SELECT * FROM hr.employees; が成功することを確認する。
  4. 続けて INSERT INTO hr.employees (last_name, hire_date) VALUES ('テスト', SYSDATE); を試し、ORA-01031（権限が不足しています）になることを確認する。
  5. 確認が終わったら system に戻り、DROP USER app_user CASCADE; で片づける。

ポイント: 手順4のORA-01031は、むしろ正しく動いている証拠です。「エラーが出ない」ことより「意図した操作だけが通る」ことのほうが、権限設計では重要だと覚えておきましょう。

理解度確認クイズ

  1. Q1. 新しく作ったユーザーに GRANT CONNECT, RESOURCE を与えたが、CREATE TABLE を実行すると ORA-01950 が発生した。原因と対処法を答えよ。

    回答を表示

    表領域にデータを書き込むための割当（クォータ）が与えられていないため。ALTER USER ユーザー名 QUOTA UNLIMITED ON USERS;（または必要な容量を指定）を実行する。権限とクォータは別の設定である。

  2. Q2. hr スキーマだけを別の環境にコピーしたい。Data Pump と RMAN のどちらを使うべきか、理由も含めて答えよ。

    回答を表示

    Data Pump（expdp / impdp）。スキーマ単位で取り出して別環境に取り込める論理バックアップだから。RMAN はデータファイル単位の物理バックアップで、データベース全体の障害復旧が主な用途であり、スキーマ単位の移行には向かない。

  3. Q3. アプリケーション用のユーザーに、いきなり DBA ロールを付与するのは、なぜ避けるべきか。

    回答を表示

    DBAロールはユーザーの作成・削除や他人の全データへのアクセスなど、ほぼすべての操作を許可してしまう。アプリがSQLインジェクションなどで乗っ取られた場合、被害がそのアプリの表だけでなくデータベース全体に及んでしまう。最小権限の原則にもとづき、必要な操作だけを許可した専用のロールを作って与えるべきである。

  4. Q4. ARCHIVELOGモードで運用することの利点を、NOARCHIVELOGモードとの違いを含めて説明せよ。

    回答を表示

    ARCHIVELOGモードでは、データベースを稼働させたままバックアップを取得でき、障害が発生しても直前の状態まで復旧できる。対してNOARCHIVELOGモードでは、データベースを停止してバックアップを取る必要があり、復旧できるのはバックアップを取得した時点までに限られる。
