ホーム Oracle 第7章
第7章 所要時間: 約1.5時間

データの追加・更新・削除

前章では SELECT 文で表からデータを「読む」方法を学びました。本章ではいよいよデータを「書く」番です。INSERT・UPDATE・DELETE の使い方に加えて、Oracle を学ぶうえで重要な考え方の一つ——INSERT・UPDATE・DELETEなどの変更は、通常はCOMMITするまで確定されないという仕組みをじっくり体験します（利用するクライアントツールや自動コミットの設定によって動作が変わる場合があるので、その点にも触れます）。「データを入れたはずなのに、いつの間にか消えていた」という初心者が経験しやすい現象の正体を、ここで解き明かしましょう。

この章で学ぶこと

  • INSERT・UPDATE・DELETE を使って表のデータを追加・更新・削除できる
  • DML（INSERT・UPDATE・DELETEなど）は通常 COMMIT するまで確定しないことを理解し、COMMIT・ROLLBACK を適切に使い分けられる
  • WHERE 句を書き忘れる危険性を理解し、実行前に対象を確認する安全な手順を実践できる
  • DELETE と TRUNCATE TABLE の違いを説明できる

7.1 INSERT文でデータを追加する

第5章で作った departments 表・employees 表には、すでに部署 4 件・社員 10 件のデータが入っています。ここに新しい行を書き足す命令が INSERT です。第5章で学んだ CREATE TABLE のような「表という入れ物を作る・変える・消す」命令を DDL（Data Definition Language / データ定義言語）と呼んだのに対し、INSERT・UPDATE・DELETE のように「表の"中身"を出し入れする」命令のグループを DML（Data Manipulation Language / データ操作言語）と呼びます。本章の主役はこの DML 3兄弟です。

列名を明示した基本形（推奨）

INSERT INTO 表名 (列名, ...) VALUES (値, ...); の形が基本です。列名は必ず明示することを習慣にしてください。 どの値がどの列に入るのかを読んだだけで判断でき、将来表に列が追加されても既存の INSERT 文が壊れにくくなります。以下の例では部署番号に 50 を使います。第5章でシーケンスが払い出したものの ROLLBACK したため、50番は欠番のまま空いているので安心して使えます。

insert_basic.sql 
-- 列名を明示して部署を1件追加する
-- (推奨: どの値がどの列に入るか、あとで読んでもすぐ分かる)
INSERT INTO departments (department_id, department_name, location)
VALUES (50, '広報部', '名古屋');

列名を省略すると、表の定義順にすべての列へ値を渡す必要があります。列の並び順を覚えていないと、値がずれて入る事故のもとになるため、通常は避けます。

insert_no_columns.sql 
-- 列名を省略した書き方(非推奨: 列の並び順に依存してしまう)
INSERT INTO departments VALUES (150, '経理部', '福岡');

複数行の追加とINSERT ... SELECT

Oracle 19c までの INSERT 文は、1回の実行につき VALUES 句を1組しか書けませんでした。複数行をまとめて追加したい場合は、Oracle 独自の INSERT ALL 構文を使う必要があったのです(23aiで導入され、26aiでも利用できる新しい書き方は、この後すぐに紹介します)。

insert_all.sql 
-- INSERT ALL でまとめて複数行を追加する(Oracle独自の書き方)
INSERT ALL
  INTO departments (department_id, department_name, location) VALUES (200, '経理部', '福岡')
  INTO departments (department_id, department_name, location) VALUES (210, '広報部', '札幌')
SELECT * FROM dual;

ヒント: 学習中は1件ずつでも構わない

INSERT ALL は覚えておくと便利ですが、学習の段階では1件ずつ INSERT 文を書くほうがシンプルで読みやすい場合も多いです。本ガイドの以降の章でも、基本は1件ずつの INSERT を使います。「そういう書き方もある」と知っておけば十分です。

既存の表から取り出した結果を、そのまま別の行として追加することもできます。VALUES の代わりに SELECT 文を書く形です。

insert_select.sql 
-- 開発部(20)の内容を元に、新しい部署番号でコピーする
INSERT INTO departments (department_id, department_name, location)
SELECT department_id + 100, department_name, location
  FROM departments
 WHERE department_id = 20;

VALUES句の複数行指定（23aiで導入され、26aiでも利用できます）

ここまでの INSERT ALL は Oracle 19c 以前でも使える書き方です。Oracle Database 23ai で、MySQL や PostgreSQL などと同じように VALUES 句に複数組をカンマ区切りで並べて書ける機能(Table Value Constructor)が追加され、本ガイドが対象とする Oracle AI Database 26ai Free でも引き続き利用できます。

insert_multi_values.sql 
-- 23aiで導入され、26aiでも利用できる書き方。VALUES句に複数行をカンマ区切りで書ける
-- (上のINSERT ALLと同じ結果になるため、実行済みならこのブロックは実行不要)
INSERT INTO departments (department_id, department_name, location)
VALUES (200, '経理部', '福岡'),
       (210, '広報部', '札幌');

ただし実務では Oracle 19c 以前の既存システムもまだ多く残っており、そこでは INSERT ALL が広く使われています。新しい VALUES (...), (...) の書き方と、昔からある INSERT ALL の両方を知っておくと安心です。

シーケンスとIDENTITY列を使った自動採番

第5章では、主キーを自動採番する仕組みとして シーケンス（連番を1つずつ払い出す「番号札の発券機」のようなオブジェクト）と IDENTITY列を用意しました。ここで実際に使ってみましょう。

insert_sequence.sql 
-- シーケンス dept_seq(第5章で作成)から次の番号を取り出して追加する
INSERT INTO departments (department_id, department_name, location)
VALUES (dept_seq.NEXTVAL, '法務部', '東京');

シーケンス名.NEXTVAL と書くたびに、シーケンスは次の番号を払い出します。一度払い出した番号は、たとえ後述の ROLLBACK で INSERT を取り消しても戻ってきません（欠番になります）。第5章で体験したとおり、ROLLBACK しても番号は戻らないため欠番が生じることがあります。番号を自分で決め打ちせず、NEXTVAL が返した値をそのまま使うのが基本です。番号が飛び飛びになっても、壊れているわけではないので心配は不要です。

insert_identity.sql 
-- employee_id(IDENTITY列)は指定しないと自動で採番される
INSERT INTO employees (last_name, first_name, hire_date, job_title, salary, department_id)
VALUES ('斎藤', '涼', DATE '2025-04-01', 'エンジニア', 320000, 20);

第5章のとおり employee_id は GENERATED BY DEFAULT AS IDENTITY で定義されているため、値を指定しなければ自動的に採番されます（GENERATED BY DEFAULT なので、必要であれば番号を明示的に指定することもできます）。

7.2 【重要】DMLの変更はCOMMITするまで確定しない Oracle固有

ここからが本章の核心です。結論を先に言います。INSERT・UPDATE・DELETE などの DML は、通常は COMMIT するまでデータベースに確定されません。 自分の画面には反映されて「見えます」が、それはまだ仮の状態です。COMMIT という命令を打つまで、他の利用者からは見えません。ただし、これは利用するクライアントツールや自動コミット（オートコミット）の設定によって動作が変わる場合があります。 例えば SQL*Plus では SET AUTOCOMMIT ON と設定すると、DML文を1つ実行するたびに自動的に COMMIT されるようになります（これは SQL の文法ではなく、SQL*Plus 側のクライアント設定です）。SQL Developer など他のツールにも、同様の自動コミット設定が用意されていることがあります。本ガイドでは特に断りのない限り、自動コミットを設定していない既定の状態を前提に説明します。COMMIT しないまま接続が終わると、変更が取り消される場合があります。 SQL*Plus で EXIT と入力して正常終了した場合は既定で自動的に確定されますが、ウィンドウを閉じる・接続が切れるといった異常終了ではロールバックされることがあります。ツールや終了のしかた、自動コミットの設定によって挙動が変わるため、確実に残したい変更は自分で明示的に COMMIT を実行する習慣をつけてください。

日常生活の比喩で考えてみましょう。ネット通販でカートに商品を入れただけでは、まだ注文は完了していませんね。「注文を確定する」ボタンを押して初めて、お店にあなたの注文が届きます。Oracle の INSERT・UPDATE・DELETE は「カートに入れる」段階、COMMIT は「注文を確定するボタンを押す」段階だとイメージしてください。カートに入れたままブラウザを閉じれば、注文は無かったことになります。

この「一連の変更をひとまとまりとして確定・取り消しできる仕組み」を トランザクション（Transaction / 一連の処理をひとまとめにして扱う単位）と呼びます。詳しい理屈は第12章で学びますが、本章では次の2つのコマンドだけ覚えれば十分です。この COMMIT・ROLLBACK のように、トランザクションを制御する命令のグループを TCL（Transaction Control Language / トランザクション制御言語）と呼びます。DDL（表の定義を操作する命令）・DML（表の中身を操作する命令）と並ぶ、3つ目の分類だと覚えておいてください。

  • COMMIT — それまでの変更を確定し、全員から見える状態にする。実行後は取り消せない。
  • ROLLBACK — それまでの変更をすべて取り消し、直前に確定した状態に戻す。

重要: 既定の設定ではDMLはCOMMITするまで確定しない

MySQL や SQL Server は既定で「1文ごとに自動的に確定（オートコミット）」する設定になっていることが多いのに対し、SQL*Plus など Oracle のクライアントツールは既定でオートコミットが無効になっています。 SQL*Plus や SQL Developer で INSERT・UPDATE・DELETE を実行しても、既定の設定のままでは明示的に COMMIT を打つまでは仮の状態のままです。「さっきデータを入れたのに、次に開いたら消えている」という現象の多くはこれが原因です。自動コミットの設定を変更していない限り、DML の後は COMMIT（または取り消すなら ROLLBACK）を打つ、を口癖にしてください。

まずは全体の流れを図で確認しましょう。DML を実行した直後は「自分だけに見える仮の状態」で、そこから COMMIT か ROLLBACK のどちらかに分岐します。図の下から伸びる矢印（DDLの実行）については、次の7.3節で詳しく説明します。

それともROLLBACKする？"} C -->|COMMIT| D["確定。全員から見える。もう取り消せない"] C -->|ROLLBACK| E["取り消し。実行前の状態に戻る"] F["CREATE・ALTER・DROP・TRUNCATEなどのDDLを実行"] -.->|強制的に確定させる| D

2つの画面で「見えない」ことを確認する

既定の設定では本当に自動コミットされないことを、SQL*Plus をもう1つ立ち上げて2つの画面（セッション）で確かめてみましょう。

session_a_1.sql 
-- 【画面A】社員103の給与を更新する(まだCOMMITしない)
UPDATE employees SET salary = 500000 WHERE employee_id = 103;

SELECT salary FROM employees WHERE employee_id = 103;  -- 500000 と表示される
session_b_1.sql 
-- 【画面B・別のSQL*Plusを新しく開いて実行】同じ行を見ると…
SELECT salary FROM employees WHERE employee_id = 103;  -- まだ380000のまま
session_a_2.sql 
-- 【画面Aに戻って】確定する
COMMIT;
-- 【画面Bでもう一度同じSELECTを実行すると】500000に変わって見える

同じ流れを、時間の経過とともにシーケンス図でも確認しておきましょう。

sequenceDiagram autonumber participant A as 画面A（自分） participant O as Oracle（FREEPDB1） participant B as 画面B（別セッション） A->>O: UPDATE employees SET salary=500000 ... A->>O: SELECT salary ... O-->>A: 500000（自分には見える） B->>O: SELECT salary ... O-->>B: 380000（まだ古い値のまま） A->>O: COMMIT B->>O: SELECT salary ... O-->>B: 500000（確定後は全員に見える）

この実験から分かるのは、COMMIT を打つまでの変更は完全に「自分だけの世界」の出来事だということです。この性質のおかげで、Oracle は大勢の人が同時にデータを読み書きしても互いに干渉しにくい設計になっています（第12章で詳しく学びます）。

ROLLBACKで取り消す

取り消しの動きも体験しておきましょう。ROLLBACK は「セーブする前まで、ゲームをやり直す」ようなものです。ただし使えるのは COMMIT していない間だけです。一度 COMMIT すると、ROLLBACK では戻せません。

rollback_example.sql 
-- WHEREを書き忘れて全社員の給与を0にしてしまった…という想定
UPDATE employees SET salary = 0;

-- COMMITしていなければ、まだ取り消せる
ROLLBACK;

-- 元の値に戻っていることを確認する
SELECT employee_id, salary FROM employees ORDER BY employee_id;

7.3 DDLは暗黙的に確定される・SAVEPOINT Oracle固有

もう一つ、Oracle 初心者が驚く重要な仕様があります。CREATE・ALTER・DROP・TRUNCATE などの DDL を実行すると、その前後で「暗黙の COMMIT」が行われます。 つまり、DDL を一つ実行しただけで、それまで確定していなかった DML の変更まで、まとめて確定してしまうのです。

ddl_implicit_commit.sql 
-- ①部署150番(7.1で追加した経理部)をDELETEする(まだCOMMITしていない)
DELETE FROM departments WHERE department_id = 150;

-- ②動作確認用に表を1つ作る(DDL)
CREATE TABLE memo (id NUMBER);

-- ③さっきのDELETEを取り消すつもりが…
ROLLBACK;  -- 効果なし。DELETEは②の時点で既に確定済み

②の CREATE TABLE を実行した瞬間に、①の DELETE は暗黙的に確定されています。③の ROLLBACK は「もう戻せるものが残っていない」状態で実行されるため、何も起こりません。「表を作っただけなのに、さっきの変更が取り消せなくなった」というのはこの仕組みが原因です。

実務での教訓

DML の作業中は、CREATE / ALTER / DROP / TRUNCATE などの DDL をうっかり挟まないようにしましょう。「ついでに確認用の表を1つ作っておこう」は、意図せず未確定の変更を確定させてしまう危険な癖です。

SAVEPOINTで部分的に取り消す

1回のトランザクションの中で「ここまでは残したいが、この先だけ取り消したい」という場面もあります。そこで使うのが SAVEPOINT（セーブポイント。トランザクションの途中に置く"目印"）です。ゲームのセーブポイントと同じ発想で、目印まで戻ってやり直せます。

savepoint_example.sql 
-- 営業部の給与を10%上げる
UPDATE employees SET salary = salary * 1.1 WHERE department_id = 10;
SAVEPOINT sp_eigyou;  -- ここまでの変更に目印を付ける

-- 続けて開発部の給与も10%上げてみる
UPDATE employees SET salary = salary * 1.1 WHERE department_id = 20;

-- 開発部の分だけ取り消したい場合、目印まで戻す
ROLLBACK TO sp_eigyou;

-- 営業部の変更だけが残った状態で確定する
COMMIT;

ROLLBACK TO セーブポイント名 は、そのセーブポイントより後の変更だけを取り消します。セーブポイント自体やそれ以前の変更には影響しません。

7.4 UPDATEで安全に更新する

UPDATE は、すでにある行の値を書き換える命令です。書式は UPDATE 表名 SET 列 = 値 WHERE 条件;。最も注意すべきなのは WHERE を書き忘れると表の全行が更新されてしまうという点です。

update_basic.sql 
-- 社員102の役職を「係長」に変更する
UPDATE employees
   SET job_title = '係長'
 WHERE employee_id = 102;

複数の列を同時に更新したい場合は、SET の後にカンマ区切りで並べます。

update_multi_columns.sql 
-- 社員103の役職と給与をまとめて更新する(カンマ区切りで複数列)
UPDATE employees
   SET job_title = '主任',
       salary    = 420000
 WHERE employee_id = 103;

WHEREを忘れると全行が対象になる

UPDATE employees SET salary = 0; のように WHERE を書かずに実行すると、「10行が更新されました」と表示され、全社員の給与が0円になってしまいます。 実務事故の第1位がこのパターンです。次に紹介する4ステップを必ず習慣にしてください。

安全な4ステップ手順

実務では、UPDATE を打つ前に必ず次の4ステップを踏みます。これは本章末の実習でも実際に練習します。

  1. 同じ WHERE 条件で SELECT し、対象の行と件数を目で確認する
  2. 問題なければ同じ WHERE で UPDATE を実行する
  3. 更新後にもう一度 SELECT して結果を確認する
  4. 意図どおりであれば COMMIT、おかしければ ROLLBACK
update_safe_4steps.sql 
-- ①同じ条件でSELECTし、対象が意図どおりか確認する
SELECT employee_id, last_name, salary FROM employees WHERE department_id = 20;

-- ②確認できたら同じ条件でUPDATEする(開発部の給与を5%上げる)
UPDATE employees SET salary = salary * 1.05 WHERE department_id = 20;

-- ③更新後の値を確認する
SELECT employee_id, last_name, salary FROM employees WHERE department_id = 20;

-- ④問題なければ確定、おかしければ取り消す
COMMIT;    -- または ROLLBACK;

重要ポイント

①の SELECT で「更新される行数」を事前に目で数えておくことが、事故を防ぐ最大のコツです。件数が想定と違えば、WHERE 条件を打ち間違えているサインです。

7.5 DELETEとTRUNCATE TABLEの違い、MERGE文

DELETE は行を削除する命令です。UPDATE と同様、WHERE を忘れると全行が削除されるので注意してください。

delete_basic.sql 
-- 部署50番(本章7.1で追加した広報部)を削除する
DELETE FROM departments WHERE department_id = 50;

社員が所属している部署を消そうとすると、第5章で付けた外部キー制約に守られてエラーになります。

delete_fk_error.sql 
-- 開発部(20)には社員が所属しているため、消そうとすると…
DELETE FROM departments WHERE department_id = 20;
-- ORA-02292: 整合性制約(HR.FK_EMP_DEPT)に違反します-子レコードが見つかりました

ORA-02292 は「この行を参照している別の行がまだ存在する」というエラーです。外部キー制約が、うっかり親を消してしまう事故を防いでくれている証拠だと捉えてください。

TRUNCATE TABLE

表の中身をまるごと空にしたいだけなら、TRUNCATE TABLE という命令もあります。

truncate_example.sql 
-- 表memo(7.3で作成)の中身を全部空にする(DDLなので暗黙コミットされる)
TRUNCATE TABLE memo;
DELETE TRUNCATE TABLE
種類 DML DDL
WHERE 使える(条件を指定できる) 使えない(全行削除のみ)
ROLLBACK できる(COMMIT前なら) できない(実行時に自動コミット)
速さ 削除行数に比例して遅くなりやすい 一括処理のため高速
向く場面 一部の行だけ消したいとき 表を丸ごと空にしたいとき

TRUNCATE TABLE は DDL なので、実行した瞬間に自動的に確定され、ROLLBACK では戻せません。「とりあえず全部消してみよう」で気軽に使うと取り返しがつかないため、本当に全件削除でよいか一呼吸置いてから実行しましょう。

MERGE文の紹介 発展

最後に、応用として MERGE 文を紹介します。「対象の行があれば更新し、なければ追加する」という処理を、条件分岐を自分で書かずに1つの命令で表現できます。初心者の方は、この節は読み飛ばして次章に進んでも構いません。実務で「更新か追加かを自動判定したい」という場面に出会ったときに、改めて読み返してください。

merge_example.sql 
-- 部署80番があれば所在地を更新、なければ新規に追加する
MERGE INTO departments d
USING (SELECT 80 AS department_id, '広報部' AS department_name, '仙台' AS location FROM dual) s
   ON (d.department_id = s.department_id)
 WHEN MATCHED    THEN UPDATE SET d.location = s.location
 WHEN NOT MATCHED THEN INSERT (department_id, department_name, location)
                        VALUES (s.department_id, s.department_name, s.location);

USING の後に指定した仮の1行を「元データ」として、ON の条件に一致する行があるかを調べ、あれば WHEN MATCHED（更新）、なければ WHEN NOT MATCHED（追加）を実行します。今はまず「そういう命令がある」と知っておけば十分で、使いこなすのは実務で必要になったときで構いません。

7.6 章末のかたづけ

本章では部署番号 50・60・80・120・150・200・210番の追加、社員「斎藤 涼」さんの追加、確認用の表 memo の作成、そして社員102・103番をはじめとする複数の社員の給与と役職(job_title)の変更を行いました。次章以降は「departments 4件・employees 10件」という基準状態から説明を始めるため、最後にすべて片付けておきましょう。

cleanup_1_delete.sql 
-- 本章で追加した部署を削除する
-- (確認用の表memoは、7.3で学んだDDLの暗黙コミットを避けるため最後に削除する)
DELETE FROM departments WHERE department_id >= 50;

-- 本章で追加した社員(斎藤さん)も削除する

やってみよう 7-1: UPDATEの前に必ずSELECTで確認する

7.4節で紹介した「安全な4ステップ」を、自分の手で実際に実行してみましょう。対象は総務部（department_id = 30）です。

  1. まず SELECT employee_id, last_name, salary FROM employees WHERE department_id = 30; を実行し、対象になる人数と現在の給与をメモに書き出す。
  2. 同じ条件で UPDATE employees SET salary = salary + 10000 WHERE department_id = 30; を実行する。
  3. もう一度①と同じ SELECT を実行し、メモした人数・給与のとおりに更新されているか確認する。
  4. 意図どおりであれば、この実習では基準状態を保つために COMMIT ではなく ROLLBACK; を実行して元に戻す。

ヒント: もし①を省略し、WHERE department_id = 30 を打ち間違えて条件そのものを書き忘れていたら、全10件が対象になってしまいます。①の SELECT で「更新されるはずの行数」を事前に目で数えておくことこそが、実務でも通用する事故防止のコツです。

理解度確認クイズ

  1. Q1. DELETE FROM departments WHERE department_id = 30; を実行した直後に CREATE TABLE test_tbl (id NUMBER); を実行し、その後 ROLLBACK; を行いました。総務部（30番）のデータは元に戻りますか。

    回答を表示

    戻りません。CREATE TABLE は DDL であり、実行の前後で暗黙のコミットが行われるため、直前の DELETE もその時点で既に確定してしまっています。ROLLBACK を実行しても、取り消せる変更はもう残っていません。

  2. Q2. 表の全行を消したいのですが、あとで取り消せる可能性を残しておきたいです。DELETE と TRUNCATE TABLE のどちらを使うべきですか。

    回答を表示

    DELETE（WHERE 句なし）を使います。DELETE は DML なので、COMMIT するまでは ROLLBACK で取り消せます。TRUNCATE TABLE は DDL で実行時に自動的に確定されるため、あとから取り消すことはできません。

  3. Q3. UPDATE employees SET salary = salary * 1.1; を実行してから、WHERE 句を書き忘れて全社員が対象になっていたことに気づきました。まだ COMMIT していません。どうすれば元に戻せますか。

    回答を表示

    ROLLBACK; を実行します。COMMIT 前であれば変更はまだ確定していないため、ROLLBACK で実行前の状態にすべて戻せます。ただし COMMIT 済みなら戻せないため、7.4節で紹介した「同じ WHERE でまず SELECT して確認してから UPDATE する」安全な手順を徹底することが何より重要です。
