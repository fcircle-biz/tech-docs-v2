ホーム Jev 第5章
第5章 所要時間: 約45分

最初のリクエストを送る

第4章では、Choice・Score・Noul という3つの Primitive がそれぞれ何を返すのかを学びました。この章では実際に手を動かし、curl コマンドで Jev に最初のリクエストを送ります。同じ State に3種類の Question を投げて、返ってくる結果を見比べることがこの章の山場です。

この章で学ぶこと

  • API キーを取得し、環境変数として安全に扱える
  • curl で Jev に最初のリクエストを送れる
  • 同じ State に3種類の Question を投げて、返却値の違いを比較できる
  • レスポンス JSON の answers と usage を読み取れる

5.1 API キーを用意する

Jev の API を呼び出すには、TypeSafe AI のコンソール（https://console.typesafe.ai/keys）で発行する API キーが必要です。ブラウザでアクセスしてログインし、案内に従って新しい API キーを1つ発行してください。発行された文字列は、次の 5.2 で環境変数に設定します。

API キーは、Jev があなたのアカウントを識別し、リクエストを認可するための資格情報です。第三者に渡ってしまうと、あなたのアカウントの権限でリクエストを送られてしまいます。

API キーをソースコードに直接書かない

API キーの文字列をそのままコードに書き込む（ハードコードする）と、Git リポジトリへコミットした際に外部へ漏えいする危険があります。キーは必ず環境変数として渡し、コードには変数名だけを書いてください。誤って公開リポジトリにキーを含めてしまった場合は、コンソールで速やかにそのキーを無効化し、新しいキーを再発行してください。

5.2 環境変数に設定する

取得した API キーは、環境変数 TYPESAFE_API_KEY に設定します。ターミナルで次のコマンドを実行してください。

terminal — 環境変数の設定 
# 発行したAPIキーを環境変数に設定する
export TYPESAFE_API_KEY="ここに取得したキーを貼り付ける"

# 設定できたか確認する（値の先頭だけ表示）
echo ${TYPESAFE_API_KEY:0:8}

この export はそのターミナルを閉じると消えます。毎回設定し直すのが面倒な場合は、シェルの設定ファイル（~/.bashrc や ~/.zshrc など）に追記しておくと、次回以降のターミナル起動時に自動で読み込まれます。

5.3 最初のリクエスト（Noul 1つ）

準備が整ったら、実際に Jev へリクエストを送ってみましょう。エンドポイントは POST https://api.typesafe.ai/v1/systemone です。State には「Stripe 連携が3日間失敗していて売上を失っている」という問い合わせ文を渡し、Question は「緊急性を感じるか」という Noul を1つだけにします。

terminal — 最初のリクエスト 
# stateとquestions（Noul 1つ）をPOSTする
curl -X POST https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "state": "Hi, I have been trying to connect my Stripe account for 3 days and the integration keeps failing. I am losing sales. Please help ASAP.",
    "model": "jev-latest",
    "questions": {
      "urgency": { "type": "noul", "instructions": "Does this message express urgency?" }
    }
  }'

リクエストヘッダーは Authorization: Bearer <API_KEY> と Content-Type: application/json の2つです。model には jev-latest（実行時点の最新版を使う指定）を渡しています。

実行すると、answers.urgency の中に { "type": "noul", "noul": 1.0 } という形で結果が返ります。第4章で学んだとおり、Noul は真偽を 0〜1 の確率で返す Primitive でした。1.0 は「緊急性がある」とほぼ確信を持って判断したことを表します。

5.4 3種類の Question を同時に投げる

Jev の強みは、同じ State に対して複数の Question を1回のリクエストでまとめて評価できることです。先ほどと同じ問い合わせ文を State にして、第4章で学んだ3つの Primitive（Choice・Score・Noul）を1つずつ、合計3つの Question を投げてみましょう。

3つの設問は questions オブジェクトの中に、Question ID をキーとして並べます。全体は長くなるので、設問ごとに抜粋して見ていきます。

questions抜粋 — department（Choice） 
"department": {
  "type": "choice",
  "instructions": "Which team should handle this",
  "criteria": {
    "billing": "Payment or subscription issues",
    "technical": "Bugs or integration problems",
    "sales": "Pricing or account questions"
  }
}
questions抜粋 — frustration（Score） 
"frustration": {
  "type": "score",
  "instructions": "How frustrated the customer appears",
  "criteria": [
    "Calm, just stating facts",
    "Frustrated but civil",
    "Very angry, strong language"
  ]
}
questions抜粋 — is_urgent（Noul） 
"is_urgent": {
  "type": "noul",
  "instructions": "The message conveys urgency or time-sensitivity"
}

この3つを questions オブジェクトにまとめ、state と model を添えて送信すると、1回のリクエストで3つの判断が同時に返ってきます。返ってきた answers も、Question ID ごとに抜粋して見てみましょう。

answers抜粋 — department 
"department": {
  "type": "choice",
  "choice": "technical",
  "confidence": 0.78,
  "probabilities": {
    "technical": 0.85,
    "sales": 0.0,
    "billing": 0.15
  }
}
answers抜粋 — frustration 
"frustration": {
  "type": "score",
  "score": 1.0,
  "confidence": 1.0,
  "legend": {
    "0": "Calm, just stating facts",
    "1": "Frustrated but civil",
    "2": "Very angry, strong language"
  },
  "probabilities": { "0": 0.0, "1": 1.0, "2": 0.0 }
}
answers抜粋 — is_urgent 
"is_urgent": {
  "type": "noul",
  "noul": 1.0
}

3つを見比べると、Primitive ごとに返却されるフィールドが違うことがわかります。

Primitive 返却フィールド 意味
Choice choice・confidence・probabilities 選んだ選択肢と、選択肢ごとの確率
Score score・confidence・legend・probabilities 尺度上の値と、各段階の説明・確率
Noul noul のみ 0〜1の確率値のみ。選択肢や段階の説明は無い

5.5 レスポンスの読み方

ここまでのレスポンスは、いつも同じ3つのトップレベル要素で構成されていました。整理しておきましょう。

フィールド 内容 例
model 実際に処理したモデルのバージョン "jev-1.13.0"
answers Question ID ごとの回答オブジェクト department・frustration・is_urgent
usage 今回のリクエストで消費したトークン数 input_tokens: 392・output_tokens: 65

model に注目してください。リクエストでは "jev-latest" と指定しましたが、レスポンスの model には "jev-1.13.0" という具体的なバージョン名が入ります。jev-latest は「その時点の最新版を使う」という指定なので、実際にどのバージョンが処理したのかはレスポンスを見て確認します。

usage は、そのリクエストで消費したトークン数を表します。input_tokens は State と Question を合わせた入力側、output_tokens は判断結果を返すために使われた出力側のトークン数です。Jev は文章を生成しないため、Question の数を増やしても output_tokens は比較的小さく収まる傾向があります。

重要ポイント: answers のキーは自分で付けた Question ID

department や is_urgent という名前は、Jev があらかじめ用意した固定の項目名ではありません。リクエストの questions オブジェクトで自分が付けた Question ID が、そのままレスポンスの answers のキーとして返ってくるだけです。ID を q1 にすれば answers.q1 が、is_billing_issue にすればそのまま answers.is_billing_issue が返ります。プログラムから読み取りやすい ID を付けておくことが、次章以降のコード連携の土台になります。

動作確認チェックリスト

ここまでの手順を終えたら、次の3点を確認しておきましょう。

  • API キーが正しく通り、エラーにならずにレスポンスが返ってきた
  • answers の中に、自分が questions で付けた Question ID（department・frustration・is_urgent）がそのままキーとして入っている
  • Primitive ごとに返却フィールドが違う（Choice は choice、Score は score、Noul は noul）ことを、実際のレスポンスで確認できた

やってみよう 5-1: 自分の問い合わせ文で3種類の Question を試す

実際に手を動かして、State を変えても同じ枠組みで3つの判断が得られることを確認しましょう。

手順

  1. 1 自分の業務やアプリでありそうな問い合わせ文を1つ考え、State として用意する（日本語・英語どちらでも構わない）。
  2. 2 5.4 の questions を参考に、Choice・Score・Noul を1つずつ、自分の問い合わせ内容に合わせて instructions と criteria を書き換える。
  3. 3 5.3 の curl コマンドを書き換えて実行し、返ってきた answers の内容をメモに書き出す。
  4. 4 3つの Primitive の結果を見比べ、「この判断は State の内容と合っているか」「confidence や probabilities の値は納得できるか」を考察する。

確認の目安

この演習に決まった正解はありません。answers の中に自分が付けた3つの Question ID がすべて含まれていること、Choice の結果には choice と probabilities、Score の結果には score と legend、Noul の結果には noul だけが入っているという対応関係を、自分の問い合わせ文でも再現できていれば、この章の目的は達成できています。

理解度確認クイズ

  1. Q1. curl で Jev にリクエストを送るとき、必ず指定する2つのヘッダーは何ですか？

    回答を表示

    Authorization: Bearer <API_KEY> と Content-Type: application/json の2つです。API キーは環境変数 TYPESAFE_API_KEY から埋め込みます。

  2. Q2. 同じ State に Choice・Score・Noul の3つの Question をまとめて送りたいとき、リクエストは何回に分けて送ればよいですか？

    回答を表示

    1回です。questions オブジェクトの中に3つの Question をそれぞれ別の ID で並べれば、1回のリクエストで3つの判断がまとめて返ってきます。State を3回に分けて送る必要はありません。

  3. Q3. レスポンスの answers.department という「department」というキーは、どこで決まりますか？

    回答を表示

    Jev 側の固定名ではなく、リクエストの questions オブジェクトで自分が付けた Question IDがそのまま使われます。ID を変えれば、レスポンスのキーもそれに合わせて変わります。
