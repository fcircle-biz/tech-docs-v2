ホーム Jev 第11章
第11章 所要時間: 約45分

複数Questionと並列評価

前章では1つの Question を instructions と criteria で構造化する方法を学びました。しかし実務では「担当部署は？」「緊急度は？」「返金要求か？」のように、1件の入力に対して複数の判断を同時に知りたい場面がほとんどです。この章では、同じ State に複数の Question をまとめて送り、それぞれが独立・並列に評価される仕組みと、そのレイテンシ・コストへの影響を学びます。

この章で学ぶこと

  • 1つの State に複数の Question を送れることを理解する
  • 各 Question が独立・並列に評価される仕組みを説明できる
  • Question を増やしたときのレイテンシとコストの振る舞いを理解する
  • 「1つの巨大なプロンプト」ではなく「多数の小さな Question」で設計できる

11.1 1リクエストに複数の Question

Jev の questions は、1つだけでなく複数のキーを持つ辞書として渡せます。State は1回だけ渡し、その State に対して知りたいことを Question の数だけ並べる、という形です。まずは全体像を図で見てみましょう。

flowchart TD S["State（1件の問い合わせ本文）"] S --> Q1["Question: department"] S --> Q2["Question: urgency"] S --> Q3["Question: is_refund_request"] S --> Q4["Question: is_complaint"] S --> Q5["Question: sentiment"] Q1 --> J["Jev（1回のリクエスト）"] Q2 --> J Q3 --> J Q4 --> J Q5 --> J J --> R["1回のレスポンス
answersに5件まとめて格納"]

同じ State（問い合わせ本文）に対して、5つの Question をすべて同時に投げています。ネットワークの往復は1回だけです。Python SDK では、まず Question をキーごとにまとめた辞書を用意します。

questions の定義（5件をまとめて用意する） 
from typesafe_sdk import TypeSafeClient, Choice, Score, Noul

# 1件の問い合わせ本文に対して判断したい5項目を定義する
questions = {
    "department": Choice(instructions="担当部署はどこか", criteria={"technical": None, "billing": None, "sales": None}),
    "urgency": Score(instructions="対応の緊急度はどの段階か", criteria=["low", "medium", "high", "critical"]),
    "is_refund_request": Noul(instructions="返金を要求しているか"),
    "is_complaint": Noul(instructions="クレームの内容を含むか"),
    "sentiment": Score(instructions="文面から読み取れる感情の傾向", criteria=["negative", "neutral", "positive"]),
}

この辞書をまとめて system_one に渡すと、1回のリクエストで5件すべての判断が返ってきます。

1リクエストで送信し、結果をまとめて取り出す 
# 1回のリクエストで5つのQuestionをまとめて送信する
with TypeSafeClient() as client:
    response = client.system_one(
        state={"inquiry": inquiry_text},
        questions=questions,
        model="jev-1.13.0",
    )

# 結果はPrimitiveの種類ごとの辞書からキーで取り出す
dept = response.answers["department"].choice
urgency = response.answers["urgency"].score
is_refund = response.answers["is_refund_request"].noul
is_complaint = response.answers["is_complaint"].noul
sentiment = response.answers["sentiment"].score
print(dept, urgency, is_refund, is_complaint, sentiment)

HTTP レスポンスの中身は、第1章で見た形がそのまま5件分に広がったものです。questions に渡したキー名が、そのまま answers のキー名になります。score は criteria のラベル文字列ではなく段階の確率加重値（数値）で返る点に注意してください（第4章・第7章）。ラベルは legend から引きます。

レスポンス例（5件のQuestionに対応するanswers・抜粋） 
{
  "model": "jev-1.13.0",
  "answers": {
    "department": { "type": "choice", "choice": "billing", "confidence": 0.81 },
    "urgency": { "type": "score", "score": 2.35, "confidence": 0.58,
                 "legend": { "0": "low", "1": "medium", "2": "high", "3": "critical" } },
    "is_refund_request": { "type": "noul", "noul": 0.92 },
    "is_complaint": { "type": "noul", "noul": 0.81 },
    "sentiment": { "type": "score", "score": 0.42, "confidence": 0.63,
                   "legend": { "0": "negative", "1": "neutral", "2": "positive" } }
  }
}

ヒント: キー名がそのままレスポンスのキーになる

questions の辞書に付けたキー名（department など）は、そのまま response.answers のキーとして返ってきます。呼び出す側とレスポンスを読む側の両方にとって、意味の分かるキー名を選ぶことが後の章（11.5）で効いてきます。

11.2 独立・並列に評価される

1リクエストにまとめて送れることは分かりました。ここで気になるのは、「5つも一緒に聞いたら、後半の Question は前半の Question の影響を受けてしまわないか？」という点です。公式ドキュメントは、この点をはっきり否定しています。

公式ドキュメントより

Jev は state を一度だけ読み込み、そのすべての Question をそれに対して並列に評価します。さらに公式 Cookbook でも「各 Question は独立して State に対して採点され、ある Question の答えが他の Question に依存しない」ことが明記されています。

これは、ChatGPT や Claude のような LLM との長い会話とは根本的に違う性質です。長い会話では、やり取りを重ねるうちに前の指示の影響が薄れたり、直前の発言に引きずられたりすることがあります。Jev の複数 Question にはこの現象が起きません。

観点 LLM との長い会話 Jev の複数 Question
各指示の扱われ方 やり取りが進むほど、前の指示の影響が薄れることがある Question ごとに毎回 State に対して独立に評価される
Aの結果がBに与える影響 直前のやり取りの流れに引きずられることがある 影響しない（並列・独立評価）
Question・発言の順序 聞く順番によって答えが変わりうる Question の順序や他 Question の答えは、推論上の文脈として利用されない

重要ポイント: 公式 Cookbook の検証では、バッチによる品質劣化は観測されていない

公式 Cookbook の検証では、同じ Question を5回繰り返し実行したところ、1件ずつ送っても複数件まとめて送ってもほぼ全ての回答が同じ値になり、標準偏差はちょうど0.0だったと報告されています。さらに13件の Question をすべて1リクエストにまとめた場合と、1件ずつ個別に送った場合を比較しても統計的に同じ結果が得られています。まとめて送ることによる「コンテキストの劣化」は、この検証条件では確認されていません。

ただしこれは特定の条件下での実験結果であり、「何度実行しても完全に同一の値が返る」という決定性の保証ではありません。仕様として保証されているのは「各 Question が同じ State に対して独立・並列に評価され、他の Question の答えを参照しない」ことです。自分のデータでも同様かどうかは、実運用前に検証してください。

11.3 レイテンシとコスト

「State を1回読み込み、全 Question を並列に評価する」という仕組みは、レイテンシとコストにも直接影響します。まず課金の仕組みを公式ドキュメント（docs.typesafe.ai/models）で確認しましょう。

入力トークン: 課金対象

100万トークンあたり0.042ドル。State と Question の instructions / criteria がここに含まれます。

出力トークン: 無料

公式ドキュメントは「入力トークンに対してのみ課金し、出力トークンは無料」と明記しています。

ここから導かれるのは、Question を1つ追加したときの追加コストは、その Question 自身の instructions / criteria 分のトークンだけで済むということです。State（問い合わせ本文など、多くの場合いちばん長い部分）は1回しか送信されないため、13回に分けて送るときのように State を13回分課金されることがありません。

公式 Cookbook は、約54,000文字の Wikipedia 記事を State にし、13件の Question を投げた検証例を公開しています。1回のリクエストにまとめた場合と、13回に分けて個別に送った場合を比較した結果です。

13件を1リクエストにまとめた場合

  • コスト: 0.000497ドル
  • 所要時間: 0.27秒

13回に分けて個別に送った場合

  • コスト: 0.006090ドル
  • 所要時間: 2.71秒

この条件では、まとめて送る方が12.2倍安く、10.0倍速いという結果になっています。差が大きくなる理由は、State（記事本文）がリクエスト全体のトークン数の大半を占めており、個別送信ではその State を13回分課金・送信し直しているためです。State に対して Question の文字数が小さいほど、この差は大きくなる傾向にあります。逆に State が短い場合は、この倍率がそのまま自分のケースに当てはまるとは限らない点には注意してください。ただし「State は1回だけ送ればよく、往復回数も1回で済む」という構造そのものは、State の長さに関わらず成り立ちます。

上限にも注意する

公式ドキュメントによれば、1リクエストあたりの上限は64,000トークンで、そのうち32,000トークンは state と最も長い1件の Question の組み合わせに割り当てられます。Question を増やしすぎると、この上限に近づいていきます。「増やせば増やすほど無条件に得」ではなく、State のサイズと Question 数のバランスを見ながら設計する必要があります。

11.4 巨大プロンプト vs 小さな Question 群

並列評価の仕組みが分かると、設計の指針も見えてきます。「department も urgency も返金要否もクレームかどうかも感情も、まとめて1つの指示で聞いてしまおう」というのは、Jev の使い方として避けるべき書き方です。Before / After で比べてみましょう。

Before: 1つの巨大な指示に詰め込む

1件の Question の instructions に「担当部署も、緊急度も、返金要求の有無も、クレームかどうかも、感情の傾向も全部まとめて答えて」と書いてしまう。

  • どの判断が外れたか分からない
  • 1箇所を直すと他の判断まで揺れるおそれがある
  • 結局1つの型にしかならず、5つの値を安全に取り出せない

After: 小さな Question を並べる

11.1 のように、department・urgency・is_refund_request ... と Atomic な Question を5つ並べ、1リクエストで送る。

  • 5つの判断がそれぞれ独立した型付きの値で返る
  • 1件だけ直しても他の4件に影響しない
  • コストは State 1回分＋Question 5件分の小さな追加のみ

After の設計が優れている理由は、次の3点に整理できます。

①どの判断が外れたか分かる

5件がそれぞれ独立した結果として返るため、間違っていた判断だけをピンポイントで特定できます。

②Question単位で改善できる

11.2 の独立評価の性質により、1件の instructions / criteria を調整しても、他の4件は影響を受けません。

③型が決まる

Choice / Score / Noul として型付きで返るため、自由形式の文章を解析する処理が不要になります。

11.5 設計への影響

複数 Question を並列評価できることを踏まえると、実務でリクエストを設計するときに意識すべき点が3つあります。

  • Question の ID は意味が分かる名前にする — q1・q2 ではなく department・is_refund_request のような名前にします。11.1 で見た通り、このキー名はそのまま response.answers のキーになるため、レスポンスを読むコードの可読性が直接変わります。
  • 判断ごとに criteria を独立させる — 「Question A で technical と答えたなら、Question B の選択肢はこう変わる」といった、他の Question を前提にした criteria は書きません。11.2 で学んだ独立評価の性質上、各 Question は他の Question の存在を知らないものとして単独で完結させます。
  • 結果の合成はコードで行う — department・urgency・is_refund_request など5件の答えをどう組み合わせて「自動処理する／人間に回す」を決めるかは、Jev ではなくコードの責務です。第8章の Atomic Question の原則の延長であり、具体的な組み合わせ方は第12章のデザインパターンで扱います。

重要ポイント

Jev への設計は「大きな1問」ではなく「小さな Question を1リクエストにまとめる」ことが基本形です。State は1回だけ読み込まれ、すべての Question が独立・並列に評価されるため、Question を増やしてもコストは追加分のトークンだけ、レイテンシもほぼ変わりません。この性質を前提に、次章ではこれらの判断を組み合わせる具体的なデザインパターンを学びます。

やってみよう 11-1: 自分の入力に5つの Question を設計する

コードを書く必要はありません。紙やメモに、自分の業務やアプリで扱う入力に対する「1リクエスト分の questions 設計」を書き出してみましょう。

手順

  1. 1 自分が扱う入力を1つ選ぶ（例: サポートチケット、商品レビュー、SNS投稿、ログの1行など）。
  2. 2 その入力について判断したい項目を5つ書き出す。
  3. 3 各項目に Primitive（Choice / Score / Noul）と意味の分かる ID を1つずつ割り当てる。
  4. 4 5項目を1つの questions 辞書としてまとめ、他の Question を前提にした書き方になっていないか見直す（11.5 の指針を確認）。

解答の目安（「商品レビュー」を入力にした場合の例）

category（Choice: electronics / apparel / food ...）、satisfaction（Score: low / medium / high）、is_defect_report（Noul: 不良品の報告か）、mentions_repeat_purchase（Noul: リピート購入への言及があるか）、tone（Score: negative / neutral / positive）の5件。いずれも他の項目の結果を前提とせず、単独で答えられる形になっている点がポイントです。

理解度確認クイズ

  1. Q1. 1つのリクエストに複数の Question を送るには、Python SDK でどうすればよいですか？

    回答を表示

    questions 引数に、複数のキーを持つ辞書（各値は Choice / Score / Noul のインスタンス）を渡します。state は Question の数に関わらず1回だけ渡せば十分です。

  2. Q2. 複数の Question を1リクエストで送ったとき、それぞれの評価はどう行われますか。LLM との長い会話と何が違いますか？

    回答を表示

    Jev は State を一度だけ読み込み、すべての Question をそれに対して独立・並列に評価します。ある Question の答えが他の Question に影響することはありません。LLM との長い会話では、やり取りを重ねるうちに前の指示の影響が薄れることがありますが、Jev の複数 Question ではこのような劣化は公式の検証でも確認されていません。

  3. Q3. Question を1つ追加すると、コストと応答時間はどうなりますか？

    回答を表示

    課金は入力トークンのみ（出力トークンは無料）で、State は1回しか送信されないため、追加コストはその新しい Question 自身の instructions / criteria 分のトークンだけで済みます。公式 Cookbook のベンチマーク（約54,000文字の記事＋13件の Question）でも、1リクエストにまとめる方が13回に分けるより12.2倍安く、10.0倍速いという結果が報告されています。

  4. Q4. 「部署も緊急度も返金要否も全部教えて」という1つの巨大な指示を書く場合と、5つの Atomic な Question に分けて1リクエストで送る場合で、何が違いますか？

    回答を表示

    後者では5つの判断がそれぞれ独立した型付きの値として返るため、どの判断が外れたかが分かり、Question単位で改善でき、型も最初から決まっています。前者は1つの塊としてしか答えが返らないため、これらのメリットが得られません。
