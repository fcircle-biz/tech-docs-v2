ホーム Jev 第10章
第10章 所要時間: 約45分

Questionを構造化する

長いプロンプトを1本書く代わりに、判断条件そのものをデータ構造として設計します。この章では instructions と criteria の役割分担を理解し、比較対象や着目点を構造として分離する書き方、そして両者を矛盾なく揃える方法を学びます。

この章で学ぶこと

  • instructions と criteria の役割分担を説明できる
  • 長いプロンプトを書く代わりに、判断条件をデータ構造として設計できる
  • 比較対象や着目点を構造として分離できる
  • instructions と criteria が矛盾しないように書ける

10.1 長いプロンプトを書かない

LLM 向けにプロンプトを書くとき、私たちはつい「前提・手順・注意点」を全部1つの文章に詰め込みがちです。条件が増えるほど文章は長くなり、どの一文がどの条件に対応しているのかが読み手にも分かりにくくなります。

Jev でも instructions に文章（string）を渡すことはできます。しかし Jev の本領は「文章を工夫して書く」ことではなく、判断条件そのものをデータ構造として設計することにあります。公式ドキュメントは「System One モデルは構造を理解するように訓練されている」と説明しており、instructions・Choice の選択肢・Score の段階・Noul の基準は、いずれも文字列だけでなくオブジェクトや配列を受け取れます。

フィールド 適用対象 許容される形
instructions Choice ／ Score ／ Noul 文字列／オブジェクト／配列／null
criteria（選択肢の説明） Choice 文字列／オブジェクト／配列／null
criteria（段階の説明） Score 文字列／オブジェクト／配列／null
criteria.true ／ criteria.false Noul 文字列／オブジェクト／配列／null

データ構造として設計する"] --> B2["instructions ＋ criteria"] end

では、いつ構造化すべきでしょうか。公式ドキュメントは2つの場面を挙げています。1つは質問が複数の要素を含み、キーを分けたほうが明確になるとき。もう1つは判断に使う情報がすでにJSON（スキーマ・分類体系・DBの1レコードなど）であるときです。この場合は文字列テンプレートに埋め込み直さず、JSON をそのまま渡すか、必要なサブフィールドだけを渡します。

構造化は Choice ／ Score ／ Noul のすべてに使える

「構造化」は特定の Primitive 専用のテクニックではありません。上の表のとおり、instructions はどの Primitive でも共通ですし、criteria も Choice・Score・Noul それぞれの形でオブジェクトや配列を受け取れます。

10.2 instructions と criteria の役割分担

構造化の出発点は、2つのフィールドの役割を混ぜないことです。instructions は「何を判断してほしいか」を表す問いと評価の枠組みです。criteria は「どういう基準で線引きするか」を表す評価軸で、Choice では各選択肢の説明、Score では各段階の説明、Noul では true／false の境界の説明になります。

片方に情報を詰め込みすぎると、この役割分担が崩れます。次の例を見比べてください。どちらも「問い合わせの担当チームを選ぶ」という同じ Choice ですが、線引きの情報をどこに書くかが違います。

Before: instructions に全部詰め込んだ例 
{
  "department": {
    "type": "choice",
    "instructions": "問い合わせ本文を読み、billing（課金・請求・返金・サブスクの話。配送やログインの話は含めない）、orders（注文状況・配送・キャンセル・返品の話。課金の話は含めない）、account（ログイン・パスワード・プロフィールの話。課金や配送の話は含めない）のいずれかを選んでください。",
    "criteria": { "billing": null, "orders": null, "account": null }
  }
}

1つの instructions 文字列に「問い」と「3つの選択肢それぞれの境界」が全部混ざっています。文が長くなるほど、どこまでが billing の説明でどこからが orders の説明なのか、人間にもモデルにも読み取りにくくなります。criteria は選択肢のキーを並べているだけで、線引きの説明を何も持っていません。

After: instructions と criteria を分離した例 
{
  "department": {
    "type": "choice",
    "instructions": {
      "question": "この問い合わせはどのチームが対応すべきですか？",
      "focus": "顧客の主な要件を1つ選ぶ。複数の話題が混ざっていても主要な用件を優先する。"
    },
    "criteria": {
      "billing": { "what": "課金・請求・返金・サブスク", "not_for": "配送や注文状況の話題" },
      "orders": { "what": "注文状況・配送・キャンセル・返品", "not_for": "課金の話題" },
      "account": { "what": "ログイン・パスワード・プロフィール", "not_for": "課金や配送の話題" }
    }
  }
}

After 版では、instructions.question が「何を判断してほしいか」だけに専念し、instructions.focus が着目点を一言で添えています。線引きの詳細は criteria の各選択肢に what（何を指すか）と not_for（何を含まないか）として分散されました。公式ドキュメントはこの書き方を「選択肢が何をカバーし、何をカバーしないかをモデルに伝える」ものだと説明しており、境界をさらに絞り込みたい場合は各選択肢に examples（具体例の配列）を添えることもできます。

重要ポイント

迷ったときの目安はシンプルです。「これは何を判断してほしいかの話か？」なら instructions。「これは選択肢・段階・真偽をどう線引きするかの話か？」なら criteria。1つの情報を両方に重複して書く必要はありません。

10.3 判断条件を構造として書く

instructions をオブジェクトにすると、「問い」以外の要素も独立したキーとして書き出せます。公式ドキュメントは、複数の項目を比較・確認するような指示には配列が向くと説明しています。「送信者が名乗っている組織名と、メールアドレスのドメインが食い違っていないか」を判定する Noul を例に見てみましょう。

sender_identity_mismatch（比較対象と着目点を分離） 
{
  "sender_identity_mismatch": {
    "type": "noul",
    "instructions": {
      "question": "名乗っている組織名と、メールのドメインは食い違っていますか？",
      "compare": ["sender.display_name", "sender.email"],
      "focus": "組織名とメールのドメイン部分だけを見比べる。"
    },
    "criteria": {
      "true": { "what": "組織名とドメインが無関係、または別の会社を示している" },
      "false": { "what": "ドメインが組織名と一致・関連している" }
    }
  }
}

ポイントは instructions.compare です。「AとBを見比べて」と1文で書く代わりに、比較したい State のフィールド名を配列 ["sender.display_name", "sender.email"] として明示しています。さらに instructions.focus で「何に着目して比べるか」を一言に絞り込み、criteria.true ／ criteria.false で真偽それぞれの意味を分けて書いています。「問い」「比較対象」「着目点」「境界」がそれぞれ別のキーに収まっている状態です。

応用: 判定対象を1箇所にまとめる

公式ドキュメントには、判定対象を field（name・type・description）というオブジェクトで1箇所にまとめ、複数の Question がそれを共通で参照する書き方も紹介されています。同じ対象について「値は合っているか（Noul）」「どの分類か（Choice）」「金額の規模はどのくらいか（Score）」のように、視点違いの Question を並べたいときに使えます。

10.4 矛盾を避ける【重要】

instructions と criteria を分けて書けるようになると、逆に起きやすくなる失敗があります。2つが別々のことを尋ねてしまうという矛盾です。

instructions と criteria が食い違うと性能が落ちる

jev-1.13 の既知の弱点として、公式ドキュメントは次のように明記しています。「instructions と criteria が異なることを尋ねていると、jev-1.13 は混乱することがある」。例として、Noul の true が実質「いいえ」を、false が実質「はい」を意味するような食い違った設計は、性能が落ちると具体的に挙げられています。対策は「criteria を instructions の延長として扱い、明確で正確な言葉で両者を揃える」ことです。

具体例で見てみましょう。次の Question は、instructions で「返金要求かどうか」を尋ねているのに、criteria は「苦情の強さ」という別の軸の4段階になっています。

Before: instructions と criteria が矛盾した例 
{
  "wants_refund": {
    "type": "score",
    "instructions": "この問い合わせは返金を要求していますか？",
    "criteria": ["穏やかな不満", "やや強い不満", "強い怒り", "非常に強い怒り"]
  }
}

「返金を要求しているか」は本来 Yes／No の判断です。しかし criteria は「怒りの強さ」という段階を定義しており、返金要求の有無とは別のものを測っています。直し方は2つの軸を1つに揃えることです。ここでは Yes／No にふさわしい noul へ型を変え、criteria.true ／ criteria.false を「返金要求」という同じ軸で書き直します。

After: instructions と criteria を揃えた例 
{
  "wants_refund": {
    "type": "noul",
    "instructions": "この問い合わせは返金を要求していますか？",
    "criteria": {
      "true": { "what": "返金・払い戻しを明確に求めている" },
      "false": { "what": "返金以外の要求、または要求そのものがない" }
    }
  }
}

怒りの強さを測りたいなら、それは wants_refund とは別の Question（例えば complaint_intensity という Score）として切り出します。1つの Question に2つの軸を混ぜないことが、矛盾を防ぐ最も確実な方法です。

矛盾を避けるべきもう1つの理由が、jev-1.13 の「文字通りに読む」という性質です。公式ドキュメントは「jev-1.13 は、あなたが書いた問いに答える。あなたが意図した問いには答えない」と述べ、範囲を限定する言葉・否定・暗黙の条件がそのまま字面通りに読まれると説明しています。

境界のケースまで明示して書く

公式の対策はこうです。「正確な条件を instructions に書く。具体的に書く。境界となるケースは criteria に置く」。誤った回答を見て「本当はこう言いたかったのに」と説明したくなったら、その説明こそ instructions に書き足すべき後半部分です。10.2 の not_for や 10.3 の focus は、この境界を明示するための具体的な手段でした。

10.5 構造化の効果

判断条件をデータ構造として設計することは、Jev の精度だけの話ではありません。開発チームで Question を書き・読み・直していく上でも効果があります。

レビューしやすい

「問い」「線引き」「境界」がキーごとに分かれているため、長文を読み解かなくてもレビューアがどこを確認すべきか一目で分かります。

差分が追いやすい

「focus の一文だけを直した」「billing の not_for を追加した」のように、変更点がキー単位の差分として残ります。長文の書き直しに比べて意図が伝わります。

コードから組み立てやすい

criteria がスキーマや分類体系と同じ形をしていれば、レコードをループして Question を動的に生成できます。1件ずつ手で文章を書く必要がありません。

重要ポイント

この章の要点は3つです。(1) instructions は「何を判断するか」、criteria は「どう線引きするか」で役割を分ける。(2) 比較対象は compare、着目点は focus のように、条件ごとに独立したキーへ分離する。(3) 両者は同じ軸を向いていなければならず、ずれると jev-1.13 は混乱する。次章では、こうして構造化した Question を複数まとめ、1回のリクエストで並列に評価する方法を学びます。

やってみよう 10-1: Question を instructions と criteria に分離する

次の Question は、判断条件が1つの instructions 文字列に全部詰め込まれています。分離し直し、矛盾がないかも確認してみましょう。

分離前の Question 
{
  "priority": {
    "type": "score",
    "instructions": "この問い合わせについて、緊急かどうかを次の4段階で判定してください: 全く不満なし／軽い不満／強い不満／非常に強い怒り",
    "criteria": []
  }
}

手順

  1. 1 instructions に書かれている「問い」の部分と「4段階の線引き」の部分を見分ける。
  2. 2 「問い」は instructions に残し、「4段階の線引き」は criteria の配列へ書き出す。
  3. 3 分離してみると、問いの言葉と段階の言葉が同じ軸を向いているか確認する。ずれていれば、10.4 を参考にどちらを直すべきか考える。

解答の目安

「緊急かどうかを判定してください」という問いに対して、4段階の中身は「不満なし〜怒り」という不満の強さの尺度になっており、軸がずれています（矛盾）。直し方は2通りあります。1つは instructions.question を「顧客の不満はどれくらい強いですか？」に書き換え、段階もそのまま criteria に残す方法。もう1つは、問いを「緊急か」のまま残し、criteria を「即対応が必要／当日中でよい／数日待てる／急ぎではない」のように緊急度の段階へ書き直す方法です。どちらでも構いませんが、問いと段階を同じ軸に揃えることが必須です。

理解度確認クイズ

  1. Q1. instructions と criteria の役割の違いを、それぞれ一言で説明してください。

    回答を表示

    instructions は「何を判断してほしいか」を表す問いと評価の枠組みです。criteria は「どういう基準で線引きするか」を表す評価軸で、Choice なら選択肢の説明、Score なら段階の説明、Noul なら true／false の境界の説明になります。

  2. Q2. 「送信者の組織名とメールドメインが食い違っていないか」を判定する Question で、instructions.compare はどんな役割を果たしますか？

    回答を表示

    見比べたい State のフィールド名を配列として明示する役割です。「AとBを比べて」と1つの文で書く代わりに ["sender.display_name", "sender.email"] のように書くことで、何と何を比較するかが曖昧さなく伝わります。

  3. Q3. 「返金要求かどうか」を尋ねる instructions に対して、criteria が「苦情の強さ」の4段階になっている Question の何が問題ですか？

    回答を表示

    instructions と criteria が別々のことを尋ねているという矛盾です。公式ドキュメントは、この食い違いがあると jev-1.13 が混乱し性能が落ちると明記しています。criteria は instructions の延長として、同じ軸を明確な言葉で揃える必要があります。

  4. Q4. jev-1.13 の「文字通りに読む」性質があるため、境界となる際どいケースはどこに書くべきですか？

    回答を表示

    criteria に明示的に書きます。jev-1.13 は書かれた言葉の通りに答え、意図を汲み取って補ってはくれません。誤答を見て「本当はこう言いたかった」と説明したくなったら、その説明こそ instructions や criteria に書き足すべき情報です。
