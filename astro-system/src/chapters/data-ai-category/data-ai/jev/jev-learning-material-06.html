ホーム Jev 第6章
第6章 所要時間: 約1時間

HTTP APIから利用する

前章では curl で Jev の挙動を体感しました。この章では POST /v1/systemone のリクエスト／レスポンス構造を仕様として整理し、モデルの指定方法・エラーコード・レート制限を受けたときの再試行方針まで、アプリケーションに組み込むために必要な知識を固めます。

この章で学ぶこと

  • POST /v1/systemone のリクエスト／レスポンス構造を説明できる
  • state・model・questions と answers の対応関係を理解する
  • 使用するモデル名とエイリアスを指定できる
  • 主なエラーコードを見分け、レート制限時の再試行方針を説明できる

6.1 エンドポイントと認証

前章で curl から叩いた宛先が、Jev の評価用エンドポイントです。Choice も Score も Noul も、すべてこの同じ入口から呼び出します（この他に、利用可能なモデル一覧を取得する GET /v1/models があります。6.6 で扱います）。

POST https://api.typesafe.ai/v1/systemone

すべてのリクエストには、次の2つのヘッダーが必要です。どちらが欠けても、後述する 401 や 422 のエラーになります。

ヘッダー 値 役割
Authorization Bearer <API_KEY> APIキーによる認証
Content-Type application/json リクエストボディの形式

アプリケーションから呼び出すときの流れを図にすると、次のようになります。curl のときと違うのは、JSON を組み立てて送るのが人間ではなくコード自身になる点だけです。

flowchart LR A["アプリケーション"] -->|"POST /v1/systemone"| B["Jev API"] B -->|"state・model・questionsを解釈"| C["Jevモデル（jev-1.13.0）"] C -->|"answers ＋ usageを生成"| B B -->|"200 OK（JSON）"| A

6.2 リクエストボディ

リクエストボディは3つのトップレベルフィールドだけで構成されます。第3・4章で学んだ State と Question が、そのまま JSON のフィールドに対応します。

フィールド 型 必須 説明
state string / object / array 必須 判断対象のコンテンツ。平文でもJSON構造でも渡せる
model string 必須 使用するモデル名。公式は jev-latest の指定を推奨
questions map（string → Question） 必須 キーは自由に決められる。判断してほしい内容をQuestionオブジェクトとして1つ以上定義する

questions の中身は、第4章で学んだ Choice／Score／Noul のいずれかです。どの型でも type と instructions は共通で必須、選択肢や段階を定義する criteria は型ごとの形式に従います。実際のリクエストは、次のようにとても短く書けます。

リクエストボディの例 
{
  "state": "Help! My payouts have been failing for 3 days.",
  "model": "jev-latest",
  "questions": {
    "is_urgent": {
      "type": "noul",
      "instructions": "Does this convey urgency?"
    }
  }
}

6.3 レスポンスボディ

先ほどのリクエストを送ると、次のようなレスポンスが返ります。フィールドは3つだけで、構造はリクエストと対になっています。

フィールド 型 説明
model string 実際にリクエストを処理したモデル名（例: jev-1.13.0）
answers map（string → Answer） questions と同じキーで、Question IDごとの回答が返る
usage object input_tokens・output_tokens を含むトークン使用量
レスポンスボディの例 
{
  "model": "jev-1.13.0",
  "answers": {
    "is_urgent": {
      "type": "noul",
      "noul": 0.95
    }
  },
  "usage": { "input_tokens": 296, "output_tokens": 20 }
}

重要ポイント: キーは呼び出し側が決め、そのまま返ってくる

上の例では is_urgent というキーを自分で決めています。Jev はこのキーを一切変更せず、answers.is_urgent としてそのまま返します。分かりやすいキー名を付けておけば、レスポンスをパースする処理を書かずにそのまま辞書として扱えるのはこの仕組みのおかげです。

6.4 モデルの指定

model には、固定バージョンのIDか、それを指すエイリアスを指定します。

指定値 種別 説明
jev-latest エイリアス（推奨） 最新の安定版を指す。SDKの既定値でもあり、新しいバージョンが出ると自動的に追従する
jev-preview エイリアス 最新のプレビュー版を指す。現時点では jev-latest と同じ版を指している
jev-1.13.0 固定バージョンID 現在2つのエイリアスが指している実体。バージョンを明示的に固定できる

jev-latest のようなエイリアスを使うと、TypeSafe が新しいモデルをリリースするたびに自動で追従します。運用の手間は減りますが、ある日突然、判断のクセがわずかに変わる可能性があります。逆に jev-1.13.0 のようにバージョンを固定すると挙動は変わりませんが、新しいモデルが出ても自分で切り替えない限りそのままです。本番環境では、このどちらの方針を取るかをチームで決めておく必要があります。

アカウントで使用できるモデルとエイリアスの一覧は GET /v1/models で取得できます。名前・説明・リリース日を含む一覧が、モデルまたはエイリアスごとに1件ずつ返ります。

利用可能なモデル一覧を取得 
# GET /v1/models で利用可能なモデル・エイリアスを取得する
curl https://api.typesafe.ai/v1/models \
  -H "Authorization: Bearer $TYPESAFE_API_KEY"

6.5 エラーと再試行

API から返る主なエラーコードは次の4種類です。

ステータス 意味 主な原因
401 Unauthorized 認証エラー APIキーが欠落している、または無効
422 Unprocessable Entity リクエスト検証エラー 必須フィールドの欠落など、ボディの内容が不正
429 Too Many Requests レート制限超過 トークン数またはリクエスト数の上限を超えた
529 Overloaded サーバー過負荷 TypeSafe側が一時的に高負荷の状態にある

429（レート制限）と529（過負荷）は、時間を置けば成功する可能性がある一時的なエラーです。公式ドキュメントは、これらを受け取った場合に指数バックオフで再試行するよう案内しています。SDKを使う場合は、この再試行がデフォルトで組み込まれます（第7章）。

401・422は再試行しても直らない

401や422は、待っても状況が変わらない恒久的なエラーです。再試行の前に、401なら Authorization ヘッダーの値を、422ならリクエストJSONの必須フィールドや型を見直してください。指数バックオフの対象は429と529だけです。

HTTP呼び出しに指数バックオフを組み込むと、次のようになります。

retry.py 
import time, random, requests

def call_systemone(url, headers, body, max_retries=5):
    """429・529のときだけ指数バックオフで再試行する"""
    for attempt in range(max_retries):
        res = requests.post(url, headers=headers, json=body)
        if res.status_code not in (429, 529):
            return res  # 成功、または再試行対象外のエラー
        wait = 2 ** attempt + random.random()  # 待機時間を倍々に＋ばらつき
        time.sleep(wait)
    return res  # 上限まで再試行しても改善しなかった最後の応答

6.6 制限とコスト

本番投入の前に知っておくべき数値上の制限と、課金の仕組みを整理します。

項目 内容
コンテキスト長（合計） 1リクエストあたり64,000トークンまで
コンテキスト長（state＋最長Question） 32,000トークンまで
レート制限 250,000トークン／秒、1,200リクエスト／分
課金対象 入力トークンのみ。100万トークンあたり$0.042（出力トークンは無料）
入力形式 テキストのみ（文字列・JSONオブジェクト・配列）。画像・音声・動画は非対応

公式ドキュメントによれば、レート制限の数値は固定ではなく動的に調整されます。上表の値は目安として捉え、実装では429応答そのものをハンドリングする前提で設計してください。

日本語など英語以外の言語を使う場合の注意

公式ドキュメントは、英語が主要な学習言語であり、現時点で最も精度が高いと明記しています。日本語を含むCJK言語も扱えますが、英語と同等の精度ではありません。日本語の問い合わせ文を state に渡す場合は、本番投入前に自分のユースケースで十分な精度が出るかを検証してください。

コスト管理のヒント

課金は input_tokens だけで決まり、output_tokens は無料です。レスポンスの usage を毎回ログに残しておけば、機能別のコストを後から集計できます。state に無関係な情報を詰め込みすぎないことが、そのままコスト削減にもつながります（第3章）。

やってみよう 6-1: department・urgency・frustration を1リクエストで判定する

1つの問い合わせ文から、担当部署・緊急度・不満度という3つの異なる判断を、1回のAPIリクエストで取得してみましょう。第9・11章で扱う「複数Questionの並列評価」の最初の一歩です。

手順

  1. 1 分析したい問い合わせ文を1つ用意する（自作でよい。困っていて急いでいる内容だと判断の違いが分かりやすい）。
  2. 2 department（Choice）・urgency（NoulまたはScore）・frustration（Score）の3つのQuestionを設計する。
  3. 3 3つを1つの questions オブジェクトにまとめ、curl で POST /v1/systemone へ送信する。
  4. 4 返ってきたJSONの answers に、指定した3つのキーがそのまま含まれていることを確認する。
解答例を表示
解答例（curl） 
# department・urgency・frustration を1回のリクエストで判定する
curl https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
  "state": "3日前に注文した商品がまだ発送されず、問い合わせ窓口に2回連絡しましたが返信がありません。至急対応してください。",
  "model": "jev-latest",
  "questions": {
    "department": {"type": "choice", "instructions": "対応すべき部署はどこですか？", "criteria": {"logistics": "配送遅延に関する内容", "support": "一般的な問い合わせ", "sales": "購入前の相談"}},
    "urgency": {"type": "noul", "instructions": "緊急対応が必要な内容ですか？"},
    "frustration": {"type": "score", "instructions": "顧客の不満の強さを評価してください。", "criteria": ["不満なし", "やや不満", "強い不満"]}
  }
}'

3つとも type が異なる点に注目してください。Choice・Noul・Score を混在させても、questionsにまとめれば1回のリクエストで並列に評価されます。

理解度確認クイズ

  1. Q1. リクエストの questions に指定したキーは、レスポンスのどこに、どのように反映されますか？

    回答を表示

    answers の中に、同じキー名でそれぞれの回答が返ります。例えば questions.department と指定すれば、回答は answers.department に入ります。キー名は呼び出し側が自由に決められます。

  2. Q2. model に jev-latest ではなく jev-1.13.0 のような固定バージョンIDを指定するのは、どんな場面に向いていますか？

    回答を表示

    本番環境で挙動を固定したい場合です。エイリアスは新しいバージョンへ自動追従するため出力が変わる可能性がありますが、バージョンを固定すれば、TypeSafe が新モデルを出しても自分で切り替えるまで動作は変わりません。

  3. Q3. APIリクエストが 429 Too Many Requests を返した場合、アプリケーション側はどう対応するべきですか？

    回答を表示

    公式ドキュメントの指針に従い、指数バックオフで再試行します（529も同様）。待機時間を試行のたびに倍々に増やすことで、サーバー側の負荷が下がるのを待ちます。401や422のような恒久的なエラーは再試行しても解決しないため、区別して扱う必要があります。

  4. Q4. レスポンスの usage に含まれる input_tokens と output_tokens のうち、課金対象になるのはどちらですか？

    回答を表示

    input_tokens（入力トークン）だけです。Jev は出力トークンを無料としているため、output_tokens の値はコストに影響しません。
