ホーム Jev 第2章
第2章 所要時間: 約45分

System Oneという考え方

第1章では、Jev が「文章を生成しないAI」であることを見ました。この章では一歩踏み込んで、Jev が採用する「System One」という設計思想と、Jev に投げる Question の良し悪しを見分ける基準を学びます。複雑な依頼を小さな判断へ分解する考え方は、この教材全体を通じて何度も登場する重要な土台になります。

この章で学ぶこと

  • System One モデルが担う「高速・限定的・構造化された判断」を説明できる
  • 良い Question の基準（熟練者が数秒で判断できる一つの判断）を使って自分の Question を評価できる
  • Jev に向かない「複雑な Reasoning 依頼」を見分けられる
  • 複雑な問題を小さな判断へ分解する手順をたどれる

2.1 System One モデルとは

「System One」という呼び方は、心理学者ダニエル・カーネマンの著書『ファスト＆スロー（Thinking, Fast and Slow）』が示した考え方に由来します。人間の思考には、直感的で高速な「System 1」と、じっくり考える論理的な「System 2」の2種類がある、という整理です。Jev が担うのは前者、つまり速く、的が絞られた判断です。

用語: System 1 と System 2

公式ドキュメントは、Jev の名前の由来をこのカーネマンの区分だとはっきり説明しています。強調したいのは速さそのものではなく、焦点を絞った判断（fast, focused judgments）という点です。文章を書いたり段階を追って推論したりする「じっくり考える」役割は、これまでどおり LLM が担います。

公式ドキュメントは System One モデルを、「ソフトウェアがそのまま使える、高速で構造化された判断を下すために作られた一群のAIモデル」と定義しています。Jev は TypeSafe AI が提供する System One モデルの中で最初のモデル（flagship）です。LLM と同じように自然言語の入力を理解しますが、返すのは生成された文章ではなく型付きの判断と確率です。

構造化されている

判断と確率は、あらかじめ決めた型に必ず従います。生成された文章から値を取り出す処理は不要です。

並列に評価される

複数の Question は互いに独立して並列に評価されます。ある判断の結果が別の判断に隠れた前提として影響することはありません。

確信度が較正されている

確率は結果に対して調整（較正）され、実際の不確実性を反映します。ただし較正は多数の判断をまとめて見たときに成り立つもので、1件ごとの正しさを保証するものではありません。

たとえば公式ドキュメントでは、多くのクエリが約100ミリ秒で完了すると説明されています。この速さがあるからこそ、Web アプリケーションのリクエスト処理の中に、待たせることなく判断を組み込めます。

公式ドキュメントの定義: System One がしないこと

公式ドキュメントは System One モデルについて、「返信を書く（write replies）」「コードを生成する（produce code）」「自らの推論を説明する文章を作る（generate explanations of their reasoning）」ことはしない、とはっきり定義しています。第1章で見た「文章を生成しない」という特徴は、この定義に基づいています。

2.2 良い Question の基準

第1章では、Jev の適用範囲を「その分野をよく知る人が、必要な情報を見て数秒で判断できること」という基準で紹介しました。この章では、この基準をもう一歩具体化し、一つの Question が満たすべき条件として整理します。

TypeSafe の設計ガイドは、明確で・範囲が狭く・具体的で・Atomic（一つに分解された判断）な Question を問うことを、ガイドの中でもっとも重要な考え方だと位置づけています。曖昧で幅広い Question は、複数の判断を1つの答えの裏に隠してしまい、後から個別に確認したり調整したりすることができません。

良い Question チェックリスト

  • 一つの判断だけに絞られているか（Atomic）
  • その分野の熟練者なら、与えられた情報を見て数秒で判断できるか
  • 答えは Choice／Score／Noul のいずれかの型で表現できるか
  • 判断に必要な情報だけが State に含まれているか
  • 返信文や説明を求めていないか（Jev は説明文を作らない）

実際の Question で比べてみましょう。左は上のチェックリストを満たす例、右は満たさない例です。

良い Question

  • 「この問い合わせは返金を要求していますか？」（Noul）
  • 「緊急度はどのレベルですか？」（Score）
  • 「担当すべき部署はどこですか？」（Choice）

向かない Question

  • 「この文章の問題点をまとめてください」（要約＝文章生成）
  • 「対応方法を考えて、返信文まで書いてください」（複数の作業が混在）
  • 「このメールは大丈夫そうですか？」（何を判断するのか不明確）

2.3 Jev 向きでない依頼

次のような依頼を想像してください。「この問い合わせを分析して、問題点を整理して、対応方法を決めてください」。一見、自然な業務指示に見えますが、Jev の Question としては向いていません。

なぜこの依頼は Jev に向かないのか

  • 「分析して」「整理して」「決めて」という複数の作業が1つの依頼に混ざっている（＝複数の判断が隠れている）
  • 「対応方法を決めてください」は、実質的に文章での説明や回答を期待している。しかし System One モデルは説明文を作らない
  • 一つひとつの判断が数秒で下せるほど絞り込まれていない。熟練者でも「何を根拠に、どう判断すればよいか」を聞き返すはずである

TypeSafe の設計ガイドも、「曖昧で幅広い Question は、複数の判断を1つの答えの裏に隠してしまう」ことを、設計上もっとも注意すべき点として挙げています。実際に公式ガイドは、「このメッセージは迷惑メールですか？」という1つの判断に丸投げする代わりに、「本文が認証情報の入力を求めているか」「差出人の表示名とメールアドレスのドメインが一致しているか」のような複数の Noul 判定に分解する例を示しています。

2.4 複雑な問題を分解する

先ほどの依頼を、Jev が扱える形に分解してみましょう。「分析して、整理して、対応方法を決めて」という1つの依頼は、次の4つの Atomic な Question へ分解できます。

flowchart TD A["複合的な依頼：
「分析して、整理して、対応方法を決めて」"] --> B{"4つのAtomicなQuestionへ分解"} B --> C["緊急か？（Noul）"] B --> D["返金要求か？（Noul）"] B --> E["クレームか？（Noul）"] B --> F["技術問題か？（Noul）"] C --> G["Jevが4つを並列に評価"] D --> G E --> G F --> G G --> H["コードが回答を組み合わせて
最終的な対応方法を決定（第8章）"]

4つの Question は、すべて独立した「数秒で答えられる判断」です。緊急かどうかを判断するのに、返金要求かどうかの答えは必要ありません。だからこそ、この4つは1回のリクエストで並列に評価できます。

Jev から4つの回答を受け取ったら、それらを組み合わせて最終的な対応方法を決めるのはコードの役割です。この「複数の判断を合成する」設計は第8章「Atomic Question」で詳しく学びますが、ここでは考え方だけ先に見ておきましょう。

4つの回答を組み合わせる例（抜粋） 
# Jevから受け取った4つの判断結果を組み合わせる（詳細は第8章）
answers = response.answers
is_urgent = answers["is_urgent"].noul > 0.7
is_refund = answers["is_refund"].noul > 0.7
is_complaint = answers["is_complaint"].noul > 0.7
is_technical = answers["is_technical"].noul > 0.7

if is_urgent and is_refund:
    action = "最優先で返金処理チームへ"
elif is_complaint:
    action = "カスタマーサクセスへエスカレーション"
elif is_technical:
    action = "技術サポートチームへ"
else:
    action = "通常キューで対応"

重要なのは、Jev はあくまで4つの部品を返すだけで、「最優先で返金処理チームへ」という最終判断そのものは行わない、という点です。

2.5 System One と System Two の役割分担

ここまでの内容を整理すると、AI を活用したソフトウェアの判断は、Jev・コード・LLM という3つの役割に分けられます。

公式ガイドの整理: 3種類のソフトウェア構成

TypeSafe の設計ガイドは、AI を使うソフトウェアの構成を3つに分類しています。伝統的なソフトウェアは、信頼できる単純な部品を組み合わせた決定木です。LLM エージェントは指示を読んで次の一手を自分で選びますが、ループを繰り返すたびに脱線するリスクが増えます。AI搭載ソフトウェアは、コードが制御フローを持ち続け、AI は「プログラムでは扱いにくい常識的判断」や「構造化されていないデータの解釈」が必要な場所にだけ、狭く限定して使われます。Jev が前提としているのは、この3つ目の構成です。

役割 担当すること 例
Jev（System One） 高速・限定的な構造化判断 緊急か？／どの部署か？／満足度は？
コード 判断結果の合成、正確な計算、制御フロー 複数Questionの重み付け合成、期限の計算、担当への振り分け
LLM 文章生成、複雑な推論、対話 返信メールの下書き、FAQ回答文の生成

この役割分担を意識すると、「この処理は誰の仕事か」を迷わず判断できるようになります。次の第3章では、Jev に渡すStateの設計方法——どんな情報を、どんな形で渡すべきか——を詳しく学びます。

やってみよう 2-1: 複合的な依頼を Atomic な Question へ分解する

あるメールが届き、上司から一言「これ、詐欺かどうか判断して」と頼まれました。この判断には、実は複数の観点が混ざっています。紙の上で分解してみましょう。

手順

  1. 1 次のメールを判断するためのAtomic な Noul Questionを3〜5個、書き出す。
    件名「緊急：社員ボーナスを受け取ってください」／本文「あなたは1,000ドルのボーナス対象に選ばれました。今すぐ給与システムのパスワードを入力して受け取ってください」／差出人表示名「Acme Payroll」／差出人アドレス「rewards@claim-bonus.example」
  2. 2 書き出した各 Question を、2.2 のチェックリスト（一つの判断か／数秒で答えられるか）で確認する。
  3. 3 4つの回答を「詐欺らしさ」という1つの結論にまとめるとしたら、コード側でどう組み合わせるか（重み付け・しきい値など）を1文で書いてみる。

解答の目安

  • 本文が認証情報（パスワードなど）の入力を求めていますか？
  • 差出人の表示名とメールアドレスのドメインは一致していますか？
  • 身に覚えのない報酬や当選を通知していますか？
  • 件名や本文は「今すぐ」のように緊急性を煽っていますか？

それぞれの回答（0〜1の確率）に重みを付けて合計し、しきい値を超えたら「詐欺の疑いが高い」と判定する、という組み合わせ方が考えられます。重み付けの具体的な設計は、第12章のComposite Scoring（コンポジット・スコアリング）というデザインパターンで学びます。

理解度確認クイズ

  1. Q1. 「System One」という名前は、どのような考え方に由来していますか？

    回答を表示

    心理学者ダニエル・カーネマンの著書『ファスト＆スロー』が示した、人間の思考の「System 1（速い思考）」と「System 2（遅い思考）」という区分に由来します。Jev が担うのは、速く直感的な判断を下す System 1 側の役割です。

  2. Q2. 良い Question の基準を一言で言うと、どのようなものですか？

    回答を表示

    「その分野をよく知る人が、与えられた情報を見て数秒で判断できる、一つの判断」であることです。判断が複数混ざっていたり、考え込まないと答えられなかったりする Question は、Jev には向きません。

  3. Q3. 「この問い合わせを分析して、問題点を整理して、対応方法を決めてください」という依頼が Jev に向かない理由を2つ挙げてください。

    回答を表示

    （1）「分析する」「整理する」「決める」という複数の判断が1つの依頼に混ざっている点、（2）「対応方法を決めてください」が実質的に文章での説明・回答を求めており、System One モデルは説明文を作らない、という点です。

  4. Q4. Jev・コード・LLM の3者は、それぞれ何を担当しますか？

    回答を表示

    Jev は高速・限定的な構造化判断、コードは判断結果の合成や正確な計算・制御フロー、LLM は文章生成や複雑な推論・対話を担当します。この役割分担が、本教材全体を貫く設計方針です。
