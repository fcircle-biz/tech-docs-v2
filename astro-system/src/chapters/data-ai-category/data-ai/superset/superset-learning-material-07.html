ホーム Apache Superset 第7章
第7章 所要時間: 約60分

メトリクスと計算列

前章でデータセットという「分析対象の範囲」を整えました。この章では、その上に「売上高」「注文件数」「客単価」といった指標を定義し、チャート間で使い回す方法を学びます。メトリクス（集計値）と計算列（行ごとの式）を区別し、比率の指標を安全に定義し、表示フォーマットを整える——ここを理解すると、第8章以降のチャート作成が驚くほど楽になります。

この章で学ぶこと

  • チャートごとに集計式を書くとなぜ数字がズレるのかを説明し、データセットにメトリクスを集約する利点を理解する
  • メトリクス（集計値）と計算列（行ごとの式）を定義し、それぞれの使いどころを判断できる
  • 比率のメトリクスを安全に定義できる（加重平均との違い・ゼロ除算対策）
  • 表示フォーマットを設定し、アドホックメトリクスを正式なメトリクスへ昇格させる判断ができる

7.1 なぜ指標をデータセット側に定義するのか

第6章までで、データセットという「分析対象の範囲」は整いました。次に必要になるのが、その範囲から何を計算するかという指標の定義です。ここで多くのチームがやってしまいがちなのが、チャートを作るたびにその場で集計式を書いてしまうことです。

一見問題なさそうに見えますが、担当者が増えたり時間が経ったりすると、同じ「売上高」のつもりで書いた式が少しずつ違ってきます。返品分を引くかどうか、キャンセル済みの注文を含めるかどうか——こうした小さな判断の違いが積み重なり、「同じ売上のはずなのに、チャートによって数字が違う」という事態を引き起こします。

チャート 担当者が書いたSQL式 集計結果
月次売上レポート SUM(amount) 1,200万円
商品別ランキング SUM(amount) - SUM(refund_amount) 1,150万円
経営ダッシュボードKPI SUM(amount)（完了済みの注文のみ） 1,080万円

3つとも「売上高」のつもりで書かれていますが、返品分を引くか、完了済みの注文だけに絞るかの判断が担当者ごとに違うため、数字が一致しません。どれが正しいかを後から関係者で議論するのは、大きな手戻りになります。

Superset では、この判断をデータセット側に1度だけ定義し、すべてのチャートがその定義を参照する仕組みが用意されています。これがメトリクス（Metrics）です。定義を1箇所に集約しておけば、後から「返品分を引く」という仕様に変えたくなっても、メトリクスの定義を1箇所直すだけで、それを使っている全チャートに反映されます。

flowchart TD M["メトリクス定義（データセット側）
売上高 = SUM(amount)"] --> C1["チャートA: 月次売上推移"] M --> C2["チャートB: 商品別売上ランキング"] M --> C3["チャートC: 地域別売上マップ"] M --> C4["ダッシュボードのBig Number"]

重要ポイント

メトリクスは「チャートの便利機能」ではなく、組織として指標の定義をそろえるための仕組みだと捉えてください。データセットを整備する第6章・第7章に時間をかけるほど、第8章以降のチャート作成は迷いなく進められます。

7.2 メトリクス（集計値）を定義する

データセット一覧から対象データセットの編集アイコンを開き、上部タブの中から Metrics を選ぶと、既存メトリクスの一覧と、新しいメトリクスを追加する操作が現れます（タブの名称や配置はバージョンによって多少異なる場合があります）。1件のメトリクスには、主に次の項目を設定します。

  • メトリクス名（Metric Name） — 内部で使われる識別用のキー。半角英数字とアンダースコアで付けます。
  • ラベル（Label） — チャート画面に表示される名前。「売上高」のように日本語で分かりやすく付けます。
  • SQL式 — 実際に集計する式。集計関数（SUM・COUNT・AVGなど）を含める必要があります。
  • 説明（Description） — この指標が何を表すかのメモ。チャート上でアイコンにカーソルを合わせると表示されます。
  • 表示フォーマット（D3 format） — 桁区切りやパーセントなど、数値の見せ方。詳細は7.6で扱います。

代表的なSQL式の例を見てみましょう。どの式にも、必ず何らかの集計関数が含まれている点に注目してください。

用途 メトリクス名（例） SQL式 集計の意味
売上高 sum_amount SUM(amount) 金額列を合計する
件数 count COUNT(*) 行数を数える
顧客数（重複なし） count_distinct_customer COUNT(DISTINCT customer_id) 重複を除いた人数を数える
平均単価 avg_amount AVG(amount) 金額列の平均を求める

はじめから存在する「count」メトリクス

データセットを作成すると、多くの場合 count（COUNT(*) で行数を数えるメトリクス）が自動的に用意されています。まずはこれをチャートで使ってみると、メトリクスがどう働くのかを実感しやすいでしょう。表示される名称や有無はバージョンによって異なる場合があります。

SQL式は単純な集計だけでなく、条件を組み合わせた式も書けます。たとえば「完了ステータスの注文だけを合計した売上高」は、集計関数の中にCASE式を入れることで表現できます。

SQL式（条件付き売上高メトリクス） 
-- 完了ステータスの注文だけを合計する売上高メトリクス
-- CASE式は行ごとに評価されるが、外側のSUMで集計されるためメトリクスになる
SUM(CASE WHEN status = 'completed' THEN amount ELSE 0 END)

7.3 計算列（行ごとの式）を定義する

同じ編集画面には Calculated columns という別タブがあります。ここに追加する式は、メトリクスとは根本的に性質が異なります。集計される前の、1行ごとに評価される式として扱われる点を押さえてください。集計関数を含む必要はなく、むしろ含めません。

  • 列名（Column Name）／ラベル — チャートの軸（ディメンション）として表示される名前。
  • SQL式 — 行ごとに計算される式。集計関数は使いません。
  • データ型（Type） — 計算結果を文字列（STRING）・数値（NUMERIC）・日時（DATETIME）・真偽値（BOOLEAN）のどれとして扱うかを指定します。
  • 時間軸として使うかどうか — 式が日付・日時を返す場合、時間列として扱う設定を有効にすると、時間範囲フィルタや時系列チャートの軸に使えるようになります。

代表的な計算列の例を見てみましょう。

用途 SQL式（例） データ型
金額帯の区分 CASE WHEN amount >= 100000 THEN '高額' WHEN amount >= 10000 THEN '中額' ELSE '少額' END STRING
小計（単価×数量） unit_price * quantity NUMERIC
氏名の結合 last_name || ' ' || first_name STRING
注文日からの年月抽出 DATE_TRUNC('month', order_date) DATETIME

上の式は接続先データベースのSQL方言に従います。|| による文字列連結や DATE_TRUNC は PostgreSQL 系の書き方であり、MySQL など方言が異なるデータベースではそのままでは動作しません。

データ型は自己申告

計算列のデータ型は、Supersetが自動判定するのではなく自分で指定します。日付を返す式なのにデータ型を文字列のままにすると、時間範囲フィルタの対象に選べなかったり、日付として正しく並び替えられなかったりします。日付・日時を返す式は、必ずDATETIME系のデータ型に合わせましょう。

7.4 メトリクスと計算列の違い

ここまでの内容を整理すると、メトリクスと計算列は名前が似ているだけで、性質はほとんど正反対です。表にまとめて比較しましょう。

観点 メトリクス 計算列
評価のタイミング グループごとに1つの値になる 元テーブルの行ごとに評価される
SQLのどこに展開されるか SELECT句に、集計関数を含む式としてそのまま展開される SELECT句やGROUP BY句に、そのまま1つの列として
使える式 集計関数を含む式 集計関数を含まない、1行の値だけで決まる式
チャートでの使われ方 「Metrics」欄に置き、測る値として使う 文字列・日時を返す式なら「Dimensions」欄に置き分ける軸として、数値を返す式なら「Metrics」欄で SUM などの集計関数をかけて使う

具体例で見ると、どちらに向くかがはっきりします。

メトリクスに向く例

  • 売上合計（SUM）
  • 注文件数（COUNT）
  • 平均単価（AVG）
  • 重複なし顧客数（COUNT DISTINCT）

計算列に向く例

  • 金額帯の区分（CASE WHEN）
  • 小計（単価×数量）
  • 氏名の結合
  • 注文日からの年月抽出

重要ポイント

迷ったら「集計関数が要るならメトリクス、1行だけ見て値が決まるなら計算列」で判断してください。式の中にSUM・COUNT・AVGのような集計関数が入っているかどうかが、最も分かりやすい見分け方です。

7.5 割合・比率のメトリクス

割合や比率をメトリクスにするときは、足し算・引き算の指標より注意が必要です。特によくある勘違いが、「SUM(a) / SUM(b)」と「AVG(a / b)」は同じ結果にならないという点です。具体的な数字で確認してみましょう。

商品 売上 利益 行ごとの利益率
商品A 1,000円 100円 10%
商品B 100,000円 5,000円 5%
合計 101,000円 5,100円 （行ごとの値は単純合算できない）

この2商品をまとめて「全体の利益率」を出す場合、計算方法によって結果がまったく変わります。SUM(profit) / SUM(amount) は (100 + 5,000) ÷ (1,000 + 100,000) ≈ 5.05% となり、売上規模の大きい商品Bの影響を強く受けた「加重平均」です。一方 AVG(profit / amount) は (10% + 5%) ÷ 2 = 7.5% となり、商品ごとの行を等しく扱った「単純平均」です。どちらが正しいかは分析の目的次第ですが、ビジネスで「全体の利益率」を聞かれたときに使うべきなのは、通常は前者の加重平均（SUMの比）です。

ゼロ除算に注意

分母となるメトリクスの合計が0になる期間や条件があると、割り算はエラーになるか、データベースによっては予期しない値を返します。分母を NULLIF(分母の式, 0) で包み、0のときはNULLを返すようにしておくと、チャートの表示が壊れずに済みます。

SQL式（利益率メトリクス） 
-- 利益率 = 利益合計 ÷ 売上合計（加重平均になる書き方）
-- NULLIFで分母が0のときはNULLを返し、ゼロ除算エラーを避ける
SUM(profit) / NULLIF(SUM(amount), 0)

7.6 表示フォーマットを整える

メトリクスには、集計結果をどう表示するかという表示フォーマットも設定できます。あらかじめ書式を指定しておけば、チャートを作るたびに桁区切りやパーセント表示を手直しする必要がなくなります。Superset の表示フォーマットは D3.js の数値フォーマット記法に従います。

フォーマット指定 表示例 用途
,d 12,345 整数を桁区切りで表示する
,.0f 12,345 小数を四捨五入し桁区切りで表示する
$,.2f $12,345.67 通貨表示（小数2桁＋桁区切り）
.1% 12.3% パーセント表示（小数1桁）
SMART_NUMBER 12.3k 桁数に応じて自動でk・M等に省略表示する

.1% のようなパーセント書式は値を100倍してから%を付けて表示する点に注意してください。7.5 の SUM(profit) / NULLIF(SUM(amount), 0)（例: 0.0505）にこの書式を当てれば5.1%と正しく表示されますが、SQL側で既に100倍した値に同じ書式を当てると505%という誤表示になります。

時間列の書式には性質の異なる2種類がある点にも注意してください。データセット側（Columns タブ）の日時列に設定する書式は、6.6で扱ったDatetime formatであり、これは表示用ではなくPython の日時書式文字列で文字列やエポック値を日時として読み取る（パースする）ための指定です。一方、チャートに表示する際の見え方（年月だけを表示する、曜日を表示するなど）はExplore 画面のチャート設定にある Time formatで指定し、こちらはD3 の時刻フォーマットに従います。指定する場所と書式の文法が異なるので混同しないようにしてください。

単位はラベル名にも書いておく

$,.2f のように通貨記号を含められる書式もありますが、日本円のように記号が定着していない単位や、パーセント以外の独自単位（件・人・日など）は書式だけでは表現できません。メトリクスのラベルに「売上高（円）」「解約率（%）」のように単位を書いておくと、チャートを見る人が数字を誤読しにくくなります。

7.7 アドホックメトリクスと「昇格」

ここまではデータセット側に正式なメトリクスを定義する方法を見てきました。ただし、チャートを作る画面「Explore」では、データセットに登録されていない集計をその場で作ることもできます。これをアドホックメトリクスと呼びます。

Explore画面の「Metrics」欄にある追加ボタンから、列と集計方法（SUM・COUNT・AVGなど）を選ぶか、カスタムSQLを直接入力すると、そのチャート専用の集計を即席で作れます（画面上のボタン名や配置はバージョンによって異なる場合があります）。ちょっとした確認や、そのチャートでしか使わない特殊な集計には便利な機能です。

問題は、同じアドホックメトリクスを別のチャートでも使いたくなったときです。式をコピーして使い回すと、結局は7.1で見た「担当者ごとに微妙に違う定義」の問題が再発します。同じ集計を2つ目・3つ目のチャートでも使うようになったら、データセット側の正式なメトリクスへ「昇格」させる——これが実務での基本的な運用方針です。

昇格させるときの注意

アドホックメトリクスのカスタムSQLは、接続しているデータベースの方言（関数名や書き方の違い）に依存することがあります。別のデータベースに接続し直すと動かなくなる式もあるため注意してください。また、既にあるメトリクスの定義を変更すると、それを参照しているすべてのチャートに一括で影響します。便利な反面、変更前には「どのチャート・ダッシュボードが影響を受けるか」を確認してから直す習慣をつけましょう。

指標の定義がデータセット側にそろえば、あとは「どの軸で見るか」を選ぶだけでチャートが作れるようになります。次の第8章では、Explore画面でこれらのメトリクスと計算列を実際に使いながら、チャートを組み立てていきます。

やってみよう 7-1: 売上データセットにメトリクスと計算列を定義する

サンプルの売上データセット（第6章で作成したもの、またはSupersetのサンプルデータに含まれる注文系のテーブル）を使って、実際にメトリクスと計算列を定義してみましょう。ここで作ったメトリクスは、第8章以降のチャート作成でそのまま使います。

手順

  1. 1 Datasets一覧から対象のデータセットを開き、編集画面の Metrics タブへ進む。
  2. 2 次の3つのメトリクスを、表示フォーマット付きで追加する。(1) 売上高：金額列の合計（ラベル例: 「売上高（円）」／フォーマット例: ,d）　(2) 注文件数：行数のカウント（フォーマット例: ,d）　(3) 客単価：売上高 ÷ 注文件数の考え方だが、メトリクス式は他のメトリクスを名前で参照できないため SUM(amount) / NULLIF(COUNT(*), 0) のようにそのまま書き下す（ラベル例: 「客単価（円）」／フォーマット例: ,d）
  3. 3 Calculated columns タブへ切り替え、CASE WHEN を使って「金額帯の区分（高額／中額／少額）」という計算列を追加する。
  4. 4 保存し、Explore画面でこれらのメトリクス・計算列が選択肢に表示されることを確認する。

解答の目安

  • ・売上高: SUM(amount)
  • ・注文件数: COUNT(*)
  • ・客単価: SUM(amount) / NULLIF(COUNT(*), 0)
  • ・金額帯区分（計算列）: CASE WHEN amount >= 100000 THEN '高額' WHEN amount >= 10000 THEN '中額' ELSE '少額' END

客単価は「1件あたりの平均購入額」なので、考え方としては売上高 ÷ 注文件数です。ただし Superset のメトリクス式はデータセットに対する生SQLであり、他のメトリクスを名前で参照することはできないため、売上高・注文件数それぞれの式をそのまま書き下して SUM(amount) / NULLIF(COUNT(*), 0) と定義します。NULLIF(COUNT(*), 0) は、注文が0件の期間で分母が0になりエラーになるのを避けるためのものです。

理解度確認クイズ

  1. Q1. なぜチャートごとに個別の集計式を書くのではなく、データセット側にメトリクスとして定義したほうがよいのですか？

    回答を表示

    チャートごとに担当者がSQLを書くと、返品分を引くかどうかなどの細かい判断が少しずつ食い違い、「同じ売上のはずなのに数字が違う」という不整合が起きやすいからです。データセットに1度だけメトリクスとして定義すれば、すべてのチャートが同じ定義を参照するようになり、後から定義を修正した場合もその1箇所を直すだけで全チャートに反映されます。

  2. Q2. メトリクスと計算列を使い分ける基準は何ですか？

    回答を表示

    式に集計関数（SUM・COUNT・AVGなど）が必要かどうかで判断します。集計後に1つの値になる式はメトリクス、集計を挟まず1行のデータだけを見て値が決まる式は計算列です。メトリクスはチャートの「Metrics」欄、計算列は多くの場合「Dimensions」欄で使います。

  3. Q3. SUM(profit) / SUM(amount) と AVG(profit / amount) は、なぜ違う結果になることがあるのですか？

    回答を表示

    前者は利益の合計を売上の合計で割った「加重平均」で、売上規模の大きい行の影響を強く受けます。後者は行ごとの比率を単純に平均した「単純平均」で、各行の売上規模の違いを無視してしまいます。どちらも「平均の利益率」に見えますが計算の仕組みが異なるため、結果は一致しないのが普通です。

  4. Q4. Explore画面で作ったアドホックメトリクスは、どのタイミングでデータセット側の正式なメトリクスへ昇格させるべきですか？

    回答を表示

    同じ集計を2つ目・3つ目のチャートでも使うようになったタイミングです。アドホックメトリクスのままコピーして使い回すと、定義が少しずつ食い違う問題が再発します。正式なメトリクスへ昇格させれば定義が1箇所に集約され、後から仕様を変えたときも全チャートへ一貫して反映されます。
