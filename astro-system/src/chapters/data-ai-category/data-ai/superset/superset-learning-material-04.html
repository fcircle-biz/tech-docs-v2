ホーム Apache Superset 第4章
第4章 所要時間: 約60分

データベースに接続する

前章までで Superset の画面には慣れました。この章では、いよいよ自分の分析対象データベースへ接続します。接続に必要な情報の意味、SQLAlchemy URI の組み立て方、画面からの接続追加、そして Docker 環境ならではのつまずきどころまで、順を追って理解していきましょう。

この章で学ぶこと

  • Superset がデータベースに接続するために必要な5つの情報と、「DBドライバ」の役割を説明できる
  • SQLAlchemy URI の形式を分解して理解し、主要なデータベースの接続文字列を組み立てられる
  • Docker コンテナから外部のデータベースへ接続する際に、localhost で失敗する理由と正しいホスト名の指定方法を説明できる
  • Expose database in SQL Lab・Allow DDL and DML などの接続設定の意味を理解し、読み取り専用ユーザーで接続する理由を説明できる

4.1 接続に必要な情報

Superset の画面から新しい接続を作るとき、最低限次の5つの情報を用意します。どれも「そのデータベースサーバーに、いつも使っているクライアントツール（例: psql や DBeaver）で接続するときに入力する情報」と同じだと考えると分かりやすいです。

  • ホスト名（Host） — データベースサーバーの所在地。IPアドレスまたはドメイン名で指定します。
  • ポート番号（Port） — サーバー内でデータベースが待ち受けている番号。既定値は PostgreSQL が 5432、MySQL が 3306 です。
  • データベース名（Database） — 接続先サーバー内で、どのデータベースを使うか。
  • ユーザー名（Username） — データベースへログインするアカウント。
  • パスワード（Password） — そのユーザーの認証情報。

この5つに加えてもう1つ、画面上には直接出てこない重要な存在があります。それがDBドライバです。Superset 自身はデータベースの種類ごとの通信手順を知りません。代わりに SQLAlchemy という Python のライブラリに処理を任せ、SQLAlchemy はさらに「DBドライバ」と呼ばれる部品を通じて、実際の通信プロトコルでデータベースとやり取りします。

flowchart LR S["Superset"] --> SA["SQLAlchemy
（DB操作の共通層）"] SA --> DR["DBドライバ
（例: psycopg2）"] DR --> DB[("データベース
PostgreSQL など")]

用語: DBドライバとは

データベースの種類ごとに用意された、通信を仲介するソフトウェア部品です。PostgreSQL 用には psycopg2、MySQL 用には mysqlclient のように、データベースごとに異なるドライバが必要です。Superset のサーバー側にこのドライバが入っていないと、接続情報が正しくても接続できません（4.5で扱います）。

4.2 SQLAlchemy URI の書き方

4.1で挙げた5つの情報とDBドライバは、Superset の内部では SQLAlchemy URI と呼ばれる1本の文字列にまとめて表現されます。画面のフォームに個別に入力した場合も、最終的にはこの形式に変換されて保存されます。まずは形を分解して見てみましょう。

flowchart LR A["方言 ＋ ドライバ"] --> B["ユーザー：パスワード"] B --> C["ホスト：ポート"] C --> D["DB名"]
部分 意味 例
方言（dialect） 接続先データベースの種類 postgresql
ドライバ 方言の中でどの Python ライブラリを使うか psycopg2
ユーザー:パスワード 認証情報 admin:pass
ホスト:ポート 接続先サーバーの場所 db:5432
DB名 接続先データベースの名前 analytics

代表的なデータベースについて、実際の URI の形を並べると次のようになります。DB名の前が方言、+ の後がドライバです。バージョンによって推奨ドライバが変わる場合があるため、迷ったら公式ドキュメントも確認してください。

データベース SQLAlchemy URI の例 備考
PostgreSQL postgresql+psycopg2://user:pass@host:5432/dbname 最も広く使われる組み合わせ
MySQL mysql+mysqldb://user:pass@host:3306/dbname ドライバ名はライブラリにより異なる場合あり
SQL Server mssql+pyodbc://user:pass@host:1433/dbname?driver=ODBC+Driver+17+for+SQL+Server ODBCドライバ名の指定が必要
SQLite sqlite:///path/to/example.db ファイル自体がDBのため、ユーザー・パスワード・ホストは不要

パスワードに記号が含まれる場合の注意

URI の中では @ や : がユーザー・パスワード・ホストの区切りとして特別な意味を持ちます。パスワード自体にこれらの記号が含まれていると、どこまでがパスワードか正しく解釈できず接続に失敗します。その場合はパスワードを URL エンコードしてから埋め込みます（@ は %40 に、: は %3A に置き換えるなど）。画面のフォームでパスワード欄が独立している場合は Superset 側が変換してくれるため、自分で1本のURI文字列を組み立てて貼り付けるときにだけ意識すれば十分です。

4.3 画面から接続を追加する

情報が揃ったら、実際に画面から接続を作ってみましょう。手順自体は難しくありませんが、途中の「テスト」を必ず行う習慣をつけることが大切です。

  1. 右上の設定アイコンから Settings を開く。
  2. メニューから Database Connections（データベース接続の一覧）を開く。
  3. 右上の + Database ボタンをクリックする。
  4. 接続先のデータベースの種類を一覧から選ぶ。種類ごとに個別フィールドの入力画面が出るか、SQLAlchemy URI を直接貼り付ける画面が出るかは、バージョンによって異なる場合があります。
  5. ホスト名・ポート・DB名・ユーザー名・パスワードなど、基本情報を入力する。
  6. Test Connection ボタンをクリックし、接続できるかどうかを確認する。
  7. 成功のメッセージが表示されたら、内容を確認して保存する。

ここで重要なのは、保存する前に必ず Test Connection を押すことです。情報が1文字でも違っていると保存後の動作で初めて気づくことになり、原因の切り分けが面倒になります。

テストが通らないときに見るポイント

  • ホスト名 — タイプミスがないか、名前解決できる相手か。
  • ポート番号 — データベース側が実際に待ち受けているポートと一致しているか。
  • 認証情報 — ユーザー名・パスワードが正しいか、そのユーザーに接続権限があるか。
  • ネットワーク到達性 — Superset が動いている場所から、そのホストへそもそも到達できるか。Docker環境で特につまずきやすいポイントです（4.4）。

4.4 Docker の中から外のDBへつなぐ

第2章の手順どおり Superset を Docker コンテナで動かしている場合、接続作成で最もよくつまずくのがホスト名に localhost を指定してしまうケースです。手元のPCで動いているツールの感覚だと自然に思えますが、Docker環境ではこれが失敗の原因になります。

「localhost」はコンテナ自身を指す

Docker のコンテナはそれぞれ独立したネットワークの世界を持っています。Superset コンテナの中から見た localhost（127.0.0.1）は、あなたのPCではなくSuperset コンテナ自身を指します。そのため「PCに直接インストールしたPostgreSQLへ localhost で接続する」という指定は、Docker環境では成立しません。

つなぎたい相手がどこにいるかによって、ホスト名に書くべき値は変わります。

接続先 ホスト名に書くもの 補足
ホストマシン（自分のPC）で直接動くDB host.docker.internal Docker Desktop が用意する特別なホスト名。環境により追加設定が必要な場合あり
同じ compose 内の別コンテナのDB サービス名（例: db） docker-compose.yml のサービス名がそのままホスト名として解決される
ネットワーク上の別のサーバー そのサーバーのIPアドレスまたはドメイン名 通常のネットワーク接続と同じ考え方

なお、同じ Docker Compose 内の別コンテナに接続する場合は、Superset コンテナと接続先のDBコンテナが同じ Docker ネットワークに参加している必要があります。別々の docker compose up で立てた環境同士は、初期状態では別のネットワークに属しているため、サービス名を指定しても届きません。

4.5 ドライバが無いときの対処

接続情報もホスト名も正しいのに、Test Connection で「ドライバが読み込めない」といった趣旨のエラーになることがあります。これは4.1で触れたDBドライバが Superset のサーバー側に入っていないために起きます。

なぜ最初から全部入っていないのか

Superset が対応できるデータベースの種類は非常に多く、ドライバを全て同梱するとイメージが肥大化してしまいます。そのため公式の Docker イメージには、代表的な一部を除き、多くのドライバがあらかじめ入っていません。「自分が使うものだけ、あとから追加する」という設計です。どのドライバが最初から入っているかは、使うイメージによって違います（下記）。

対処の考え方はシンプルで、必要な Python パッケージを追加インストールしたイメージを自分で用意することです。追加が必要になるかどうかは、使うイメージと接続先データベースの組み合わせで決まります。

イメージ 同梱されるDBドライバ 追加作業
apache/superset:<ver>
標準（本教材が使うもの）		 PostgreSQL 用 psycopg2-binary と MySQL 用 mysqlclient が同梱 PostgreSQL / MySQL なら追加不要。それ以外のDBに繋ぐときだけ追加する
apache/superset:<ver>-lean
最小構成		 DBドライバは一切入っていない メタデータDB用のドライバも含め、必要なものを全て自分で追加する

標準イメージを使っていて追加が必要になる代表例としては、Snowflake 用の snowflake-sqlalchemy、BigQuery 用の sqlalchemy-bigquery、Trino 用の trino、SQL Server 用の pymssql などがあります。

Dockerfile（考え方の例） 
# 公式イメージをベースにする（タグは使用するバージョンに合わせる）
FROM apache/superset:6.1.0
# インストールのため一時的に root へ切り替える
USER root
# 接続したいDBのドライバを追加する（例: Snowflake）
RUN pip install --no-cache-dir snowflake-sqlalchemy
# 実行ユーザーを元に戻す
USER superset

具体的な手順（ベースイメージの選び方やビルド方法など）はバージョンや構成によって変わるため、必ず公式ドキュメント（superset.apache.org/user-docs/databases/）で対象データベースの推奨手順を確認してください。

4.6 接続ごとの重要な設定

接続の作成・編集画面には Advanced タブがあり、その接続の使われ方を細かく制御できます。項目数が多いので、まずは特に重要な5つを整理します。名称や配置はバージョンによって異なる場合があります。

設定項目 意味 既定の考え方
Expose database in SQL Lab この接続を SQL Lab の対象として表示する 既定オン。SQL Lab に出したくない接続だけ明示的にオフにする
Allow DDL and DML DDL（CREATE・DROP・TRUNCATE など）と DML（INSERT・UPDATE・DELETE など）を許可する 既定オフ＝SELECTのみ
CTAS／CVAS の許可 クエリ結果を新しいテーブル・ビューとして保存することを許可する 既定オフ
非同期クエリ実行 重いクエリをバックグラウンドのワーカーに任せて実行する 別途ワーカー環境の設定が必要（概要は第5章、設定は第14章）
チャートのキャッシュタイムアウト この接続に紐づくチャート結果を、どれだけの時間再利用するか 未設定なら全体の既定値に従う（第14章）

重要ポイント

Allow DDL and DML・CTAS/CVAS のように既定でオフの設定は、必要になるまでオフのまま使うのが安全です。分析用の接続でうっかり有効にしてしまうと、SQL Lab から実行した1本のクエリで本番データを書き換えたり、テーブルを削除してしまう事故につながります。必要になったときに、影響範囲を理解したうえで個別にオンにする、という順序を徹底しましょう。

4.7 読み取り専用ユーザーで接続する

Allow DDL and DML をオフにしておけば安心、というわけではありません。分析用の接続では、データベース管理者ユーザーではなく、SELECT権限だけを持つ専用ユーザーを作って接続するのが基本の考え方です。理由は主に3つあります。

  • 誤った更新・削除の防止 — Superset側の設定ミスや操作ミスがあっても、データベース側の権限が最後の砦として止めてくれます。
  • 監査のしやすさ — 「Superset用の接続がどのユーザーで何をしたか」を、他の業務アプリのアクセスと切り分けて追跡できます。
  • 最小権限の原則 — 分析に必要な範囲だけにアクセスを絞ることで、万が一認証情報が漏れたときの被害を小さくできます。

最小権限は「更新させない」だけでなく、「見せる範囲を絞る」ことも含みます。データベース全体ではなく、分析に必要なスキーマやテーブルだけに SELECT 権限を付与するようにしましょう。PostgreSQL では、次のような SQL でこれを実現できます。

setup_readonly_user.sql 
-- Superset専用の読み取り専用ユーザーを作成する
CREATE USER superset_reader WITH PASSWORD 'ここに強いパスワード';

-- 対象データベースへの接続権限を付与
GRANT CONNECT ON DATABASE analytics TO superset_reader;

-- 対象スキーマの参照権限を付与
GRANT USAGE ON SCHEMA public TO superset_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO superset_reader;

-- 今後追加されるテーブルにも自動でSELECTを付与する
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT ON TABLES TO superset_reader;

この superset_reader のようなユーザーで組み立てた SQLAlchemy URI を Superset の接続に使えば、Superset 側の設定がどうであれ、データベース側で更新系SQLは実行できません。Superset の設定（4.6）とデータベース側の権限、二重の防御で安全性を確保するのが基本方針です。

やってみよう 4-1: 分析用データベースへの接続を作る

第2章の環境には、Superset自身が使うメタデータ用PostgreSQLとは別に、同じPostgreSQLコンテナ内に動作確認用のサンプルデータが入ったデータベースがあり、接続値は次のとおりです。ホスト db／ポート 5432／DB名・ユーザー・パスワードはいずれも examples。ただしこの examples という接続名はサンプルデータ読み込み時に自動作成済みなので、(a) 既存の接続を開いて読み解くか、(b) 別名で新規作成してテストを通すか、どちらかで進めましょう。

手順

  1. 1 Settings → Database Connections を開く。(a) は一覧の examples を Edit で開く。(b) は + Database から新規作成し、名前を my_examples など別名にする。
  2. 2 ホスト・ポート・DB名・ユーザー名・パスワードが上記の値になっているか確認する（(b) はこれから入力する）。localhost ではなく db を使う理由は4.4のとおりです。
  3. 3 Test Connection をクリックし、成功のメッセージが出ることを確認する。
  4. 4 Advanced タブを開き、Expose database in SQL Lab・Allow DDL and DML など4.6で扱った設定がどうなっているか確認してから保存する。
  5. 5 SQL Lab を開き、左側のデータベース選択に、今確認・作成した接続が表示されることを確認する。

解答の目安

SQLAlchemy URI に組み立てると postgresql+psycopg2://examples:examples@db:5432/examples です。「方言＋ドライバ://ユーザー:パスワード@ホスト:ポート/DB名」の形に、上記の接続値を1つずつ当てはめれば組み立てられます。つまずきやすいのは、(1) ホスト名 — Docker環境では localhost ではなく compose のサービス名 db を使う（4.4）、(2) 接続名の重複 — examples は既に存在するため新規作成時は別名にする、(3) Expose database in SQL Lab — 既定でオンだが、念のため確認してから保存する、の3点です。Test Connectionが失敗する場合は、4.3の「テストが通らないときに見るポイント」を上から順に確認してください。

理解度確認クイズ

  1. Q1. SQLAlchemy URI の「方言＋ドライバ」の部分は、それぞれ何を表しますか？

    回答を表示

    「方言（dialect）」は接続先データベースの種類（PostgreSQL、MySQLなど）を表し、「ドライバ」は Superset が実際にそのデータベースと通信するために使う Python ライブラリを表します。同じ PostgreSQL でも使うドライバによって URI の書き方（例: postgresql+psycopg2://）が変わります。

  2. Q2. Superset をDockerコンテナで動かしているとき、ホストマシン上で直接動くデータベースへ「localhost」で接続できないのはなぜですか？

    回答を表示

    Dockerのコンテナはそれぞれ独立したネットワークの世界を持っており、コンテナ内から見た localhost はそのコンテナ自身を指すためです。ホストマシン上のDBに接続するには、host.docker.internal のような特別なホスト名を使う必要があります（環境により設定が異なる場合があります）。

  3. Q3. 接続テスト時に「ドライバが見つからない」というエラーが出るのはなぜですか？

    回答を表示

    Superset の公式Dockerイメージには、全てのデータベース用ドライバがあらかじめ同梱されているわけではないためです（PostgreSQL用の psycopg2-binary と MySQL用の mysqlclient は同梱済みですが、それ以外の多くは含まれません）。必要なドライバ（例: Snowflake用の snowflake-sqlalchemy）を追加インストールしたカスタムイメージを用意するといった対処が必要になります。

  4. Q4. 分析用の接続を、データベース管理者ユーザーではなくSELECT権限だけの読み取り専用ユーザーで作るのはなぜですか？

    回答を表示

    誤った更新・削除を防ぎ、最小権限の原則に沿って必要な範囲だけにアクセスを絞り、誰が何にアクセスしたかを監査しやすくするためです。Superset の Allow DDL and DML をオフにするだけでなく、データベース側の権限でも二重に制限しておくことで、より安全になります。
