ホーム Apache Superset 第6章
第6章 所要時間: 約60分

データセットを作る

この章では、Superset の中心概念であるデータセットを作ります。既存のテーブルやビューをそのまま使う物理データセットと、SQL の結果を定義として保存する仮想データセットを作り分け、列に「これは時間軸」「これはフィルタに使う」といった意味づけを与えていきます。地味な画面操作に見えますが、第7章のメトリクス定義とあわせて本教材でもっとも重要な2章です。焦らず進めましょう。

この章で学ぶこと

  • データセットが「チャートが見るデータの範囲」を定義する層であり、単なるテーブルの別名ではないことを説明できる
  • 物理データセットと仮想データセットをそれぞれ作成し、向き・不向きを判断できる
  • データセット編集画面（Edit dataset）の各タブが何を担当するかを整理できる
  • 列の時間軸・フィルタ可否・表示名を適切に設定し、後工程の Explore 画面を使いやすく整えられる

6.1 データセットとは

データセットとは、一言でいえば「チャートが見るデータの範囲に名前を付けたもの」です。Superset でチャートを作るとき、テーブルや SQL を直接指定することはありません。必ずどれか1つのデータセットを選び、そのデータセットが公開している列だけを使ってグラフを組み立てます。

ここで誤解しやすいのが、「データセット＝テーブルの別名」という理解です。実際にはデータセットは、テーブルの列に意味づけを追加する層でもあります。「どの列が日時か」「どの列でフィルタしてよいか」「どの集計を『売上高』と呼ぶか」——こうした情報はテーブル自体には存在せず、データセット側に保存されます。同じテーブルから複数のデータセットを作り、用途ごとに異なる意味づけを与えることもできます。

なぜ「データセット」という層を挟むのか

Superset がテーブルへ直接チャートを向けられたら、この層は不要に思えるかもしれません。しかしテーブルには「意味」がありません。created_at という列があっても、それが分析の基準にしてよい時刻なのかはテーブル定義だけでは分かりません。データセットは、そうした業務上の意味づけをデータベースの外側（Superset側）に持たせるための場所です。

flowchart LR DB[("データベース接続")] --> DS["データセット
例: orders"] DS --> C1["チャート: 日別売上推移"] DS --> C2["チャート: カテゴリ別内訳"] DS --> C3["チャート: 今月の件数"]

重要ポイント

図のとおり、1つのデータセットから何枚でもチャートを作れますが、1つのチャートが属せるデータセットは常に1つだけです。この関係があるため、データセット側の設定（表示名・時間軸の指定など）を直すと、それを使っているすべてのチャートに影響が及びます。逆に言えば、データセットを丁寧に整えるほど、あとから作るチャートが楽になります。

6.2 物理データセットを作る

物理データセットは、データベースにすでにあるテーブルやビューを、そのままデータセットとして登録する方法です。SQL を書く必要がなく、画面上で選んでいくだけで完成します。まずはこの方法から試すのが基本です。

  1. ナビゲーションバーの Datasets を開く。
  2. 右上の + Dataset ボタンをクリックする。
  3. DATABASE に、第4章で作成したデータベース接続を選択する。
  4. SCHEMA に対象のスキーマを選択する（対象のデータベースにスキーマの概念がある場合）。
  5. TABLE に対象のテーブルまたはビューを選択する。
  6. CREATE DATASET AND CREATE CHART（バージョンによっては Add）で保存する。

ビュー（VIEW）も物理データセットにできる

データベース側にあらかじめ用意されたビューも、Superset から見ればテーブルと同じ1つの表です。JOIN や集計をあらかじめビューとして定義しておけば、Superset 側はそれを選ぶだけで済み、物理データセットの手軽さを保ったまま複雑な形のデータを扱えます。ボタン名や画面項目はバージョンによって異なる場合があります。

物理データセットの利点は、この手順の少なさに尽きます。元のテーブルがすでに分析にちょうどよい形（1つの表で完結している）であれば、無理に SQL を書く必要はありません。

6.3 仮想データセットを作る

仮想データセットは、SQL の実行結果に名前を付けて保存する方法です。複数テーブルの JOIN や、特定条件での絞り込みなど、1つのテーブルだけでは表現できない「分析用の形」をあらかじめ用意できます。作り方は主に2通りあります。1つは第5章で扱った SQL Lab でクエリを実行し、結果画面の Save から Save dataset を選ぶ方法。もう1つは、データセットの新規作成・編集画面で直接 SQL を入力する方法です。

仮想データセット定義SQLの例 
-- 注文テーブルと顧客テーブルを結合し、
-- 分析に必要な列だけを持つ仮想データセット用のSQL
SELECT
    o.order_id,
    o.order_date,
    o.amount,
    c.customer_name,
    c.prefecture
FROM orders AS o
JOIN customers AS c
    ON o.customer_id = c.customer_id
WHERE o.status != 'canceled'

仮想データセットのSQLで避けること

Superset はチャートを表示するたびに、この SQL を土台にして絞り込みや集計を追加したクエリを組み立てます。つまり保存した SQL はサブクエリとして外側から包まれる前提で書く必要があります。そのため、末尾のセミコロン（;）は構文エラーの原因になりやすく、ORDER BY や LIMIT は外側のクエリで別途指定されるため内側に書いても意味がない（DBによってはエラーになる）ことがあります。この3つは書かないのが安全です。

6.4 物理と仮想の使い分け

どちらを選ぶべきかは、次の5つの観点で比較すると判断しやすくなります。

観点 物理データセット 仮想データセット
作りやすさ GUIでテーブルを選ぶだけ。数クリックで完成する SQLを書く必要があり、JOINやWHEREの知識が要る
柔軟性 元テーブルの列構成のまま。加工はできない JOIN・絞り込み・列の整形など自由に形を作れる
性能 テーブル本来の性能（インデックスなど）をそのまま活かせる SQLの書き方に左右される。重いJOINは表示のたびに再計算されやすい
変更への強さ 元テーブルの列追加は同期（6.7）で追従しやすい 列名や結合条件を変えるにはSQL自体の修正が必要
再利用性 元テーブル単位でしか切り出せない 「分析用に整形済みの形」を複数のチャートで使い回せる

判断に迷ったら、次の順番で考えてみてください。

flowchart TD A["テーブルはそのまま分析に使える形か？"] -->|はい| B["物理データセットにする"] A -->|いいえ・JOINや絞り込みが必要| C["仮想データセットにする"] C --> D{"重い集計・何度も使われる？"} D -->|はい| E["DB側に集計済みテーブル／ビューを用意し
物理データセットに戻す"] D -->|いいえ| F["仮想データセットのまま運用する"]

つまり「まず物理、必要になったら仮想、重くなったらDB側に集計済みの表を用意して物理に戻す」という一往復が基本の考え方です。仮想データセットは便利ですが、複雑なSQLを仮想データセットに閉じ込め続けると、性能問題が起きたときに原因を追いにくくなります。

6.5 データセットの編集画面

物理・仮想のどちらで作ったデータセットも、作成後の調整はすべて Edit dataset（データセット一覧の鉛筆アイコン）から行います。編集画面はいくつかのタブに分かれており、それぞれ役割が異なります。タブ名は Superset のバージョンによって多少異なる場合があります。

タブ 役割
Source 接続先データベース、対象テーブル（物理）または SQL 本文（仮想）を確認・変更する
Metrics 集計済みの指標を定義する（第7章で扱う）
Columns 列ごとの時間軸・フィルタ可否・表示名などを設定する（6.6で扱う）
Calculated columns 既存の列から式で新しい列を作る（第7章で扱う）
Settings 説明文、キャッシュタイムアウト、所有者などの管理情報を設定する

この章では Source と Columns を扱い、Metrics と Calculated columns は第7章で扱います。Settings は、誰が見ても用途が分かるように説明文と所有者を必ず埋めておくと、6.7で触れる「使われなくなったデータセットの整理」がしやすくなります。

6.6 列の設定を整える

Columns タブでは、データセットが持つ列ごとに設定を行います。物理・仮想のどちらのデータセットでも、この設定こそが「テーブルに意味を与える」作業の中心です。

設定項目 意味 効果
Is temporal この列を時間軸として扱ってよいか 時系列チャートの時間軸の候補に表示される
Is filterable フィルタの対象にしてよいか Explore やダッシュボードのフィルタで選べるようになる
Is dimension グループ化の軸（ディメンション）にしてよいか チャートの「軸」の候補に表示される
Label 画面に表示する名前 列名の代わりに日本語名などを表示できる
日時フォーマット（Datetime format） 文字列やエポックで入っている日時列を、どう日時として読み取るかの指定（Python の日時書式文字列、または epoch_s・epoch_ms） ネイティブな日時型でない列も時間軸として使えるようになる。なお、チャート上の日付の見え方は Explore 側の Time format で指定する
Default datetime Is temporal な列が複数あるとき、どれを主たる時間列にするか 時系列チャートを作成した際に、時間軸として最初から選択された状態になる

時間列の設定を忘れるとどうなるか

日時が入っている列でも、Is temporal がオフのままだと時系列チャート（折れ線グラフなど）の時間軸の候補に出てきません。「使いたい列が選択肢に見当たらない」と感じたときは、まずこの設定を疑ってください。第8章でチャートを作り始める前に、この章のうちに直しておく価値があります。

逆に、分析に使わない列は Is filterable や Is dimension をオフにしておくと、Explore 画面の候補一覧から余計な列が消え、選ぶべき列を見つけやすくなります。列を1つ残らず有効にしておく必要はありません。

6.7 運用上の注意

データセットは一度作って終わりではありません。チームで使い続けるうちに気をつけたい点を4つ紹介します。

  • Sync columns from source — 元テーブルに列が増えても、データセット側には自動で反映されません。Columns タブにある同期ボタンで最新の列一覧を取り込みます。同期するとIs temporal の指定が外れたり、ソース側から消えた列の設定が失われたり、増えた列が既定値で追加されたりすることがあるため、同期後は 6.6 の設定（特に Is temporal）を見直しましょう。
  • 仮想データセットを重ねすぎない — 仮想データセットのSQLの中から、別の仮想データセットを参照するような構成は避けます（詳細は下の警告を参照）。
  • 命名規則を決める — 在庫_滞留日数_物流チーム のように、用途が分かる日本語名と所有者（チーム名）をセットで付けておくと、後から見た人が迷いません。
  • 使われていないデータセットを整理する — Charts 一覧をデータセット名で絞り込むと、どのチャートが参照しているか確認できます。参照されていないデータセットは定期的に見直しましょう。

仮想データセットの上に仮想データセットを重ねない

「仮想データセットAのSQLの中で、仮想データセットBを参照する」という構成は一見便利ですが、実行時には何重にもサブクエリが重なったクエリになります。性能が落ちやすいうえ、表示が遅くなったときにどの層のSQLが原因か追いにくくなります。共通で使う加工は、可能であればデータベース側のビューにまとめ、Superset 側は物理データセットとして参照する形に戻すことを検討してください。

やってみよう 6-1: 物理データセットと仮想データセットを作ってみる

サンプルデータを使って、物理データセットと仮想データセットを1つずつ作り、どちらも列の設定まで仕上げてみましょう。

手順

  1. 1 サンプルデータのテーブルを1つ選び、6.2の手順で物理データセットを作る。
  2. 2 関連する2つのテーブルを JOIN するSQLをSQL Labで書いて実行し、仮想データセットとして保存する（下の解答例を参考にしてよい）。
  3. 3 作った2つのデータセットそれぞれについて、Columns タブで日時列の Is temporal をオンにし、分かりやすい Label を付ける。
手順2で使えるSQLの例 
-- 注文明細と商品マスタを結合し、
-- カテゴリ別の販売状況を確認できる仮想データセット用SQL
SELECT
    o.order_date,
    p.category,
    p.product_name,
    o.quantity,
    o.quantity * p.unit_price AS sales_amount
FROM order_items AS o
JOIN products AS p
    ON o.product_id = p.product_id
WHERE o.quantity > 0

解答の目安

上のSQLを仮想データセットとして保存すると、order_date・category・product_name・quantity・sales_amount の5列を持つデータセットができます。物理・仮想のどちらも、order_date のような日時列で Is temporal をオンにするのを忘れないでください。もし設定を忘れると、第8章で折れ線グラフなどの時系列チャートを作ろうとしたときに、時間軸を選ぶ項目にその列が出てこず、「軸にできる列がない」状態でチャート作成が止まってしまいます。

理解度確認クイズ

  1. Q1. データセットが「テーブルの別名」ではないとすれば、テーブルに対して何を追加で持っているといえますか？

    回答を表示

    列への意味づけ（どれが時間軸か、どれでフィルタしてよいかなど）と、指標の定義（第7章のメトリクス）です。データセットは「チャートが見るデータの範囲」を定めるだけでなく、テーブルには無いこれらの情報を保持する層でもあります。

  2. Q2. 物理データセットと仮想データセットの違いを、作り方の観点から説明してください。

    回答を表示

    物理データセットは既存のテーブルやビューをそのまま選んで作ります。仮想データセットはSQLの実行結果に名前を付けて保存し、JOINや絞り込みなど1つのテーブルでは表現できない形を自由に作れます。

  3. Q3. 仮想データセットのSQLの末尾にセミコロンや ORDER BY・LIMIT を書くべきではないのはなぜですか？

    回答を表示

    Superset はチャート表示のたびに、保存したSQLをサブクエリとして外側から包んだクエリを組み立てるためです。末尾のセミコロンは構文エラーの原因になりやすく、ORDER BY や LIMIT は外側のクエリで別途指定されるため、内側に書いても意味がない、あるいはエラーになることがあります。

  4. Q4. 列の Is temporal をオフにしたまま放置すると、後の作業でどのような症状が出ますか？

    回答を表示

    日時が入っている列でも、時系列チャート（折れ線グラフなど）を作る際の時間軸の候補に表示されなくなります。「使いたい列が選択肢に出てこない」と感じたら、まず Columns タブの Is temporal 設定を確認します。
