ホーム Keycloak 第7章
第7章 所要時間: 約50分

ロールとグループで権限を管理する

第6章では、ユーザーという「人」を作りました。この章では、その人に「何をしてよいか」を割り当てる方法を学びます。1人ずつ個別に権限を設定するのではなく、ロール（役割）という単位にまとめて、人にはロールを割り当てる——この考え方（RBAC）を身につけると、ユーザーが何百人・何千人に増えても管理が破綻しません。

この章で学ぶこと

  • ロールベースアクセス制御（RBAC）の考え方を、身近なたとえで説明できる
  • レルムロールとクライアントロールを使い分けられる
  • ロールを作成し、ユーザーに割り当てられる
  • 複合ロールとグループの仕組みを理解し、設計に活かせる
  • ロールがアクセストークンのどこに載るのかを知る

7.1 認可の基本的な考え方 — ロールベースアクセス制御（RBAC）

「山田さんには経費精算の承認を許可、佐藤さんには許可しない」というように、人ごとに権限を1つずつ設定していくとどうなるでしょうか。最初は10人程度なら管理できても、人数が増え、異動や退職が発生するたびに「誰にどの権限を与えていたか」を1人ずつ確認して直す必要が出てきます。これは第1章で見た「ログイン機能の自作」と同じ構造の問題です。

そこでKeycloakは、権限を人に直接付けるのではなく、ロール（役割）という中間の単位にまとめます。第1章の「ビルの共用受付」のたとえで続けると、ロールは「入れる階の指定」にあたります。「3階までの入館証」「全フロア入館証」のように、まず役割の種類を決めておき、個々の訪問者にはその役割を1つ（または複数）割り当てるだけにします。これがロールベースアクセス制御（RBAC: Role-Based Access Control）という考え方です。

図1: 人・ロール・できることの関係

flowchart LR U1["ユーザー: 山田"] --> R1["ロール: app-admin"] U2["ユーザー: 佐藤"] --> R2["ロール: app-user"] U3["ユーザー: 鈴木"] --> R2 R1 --> P1["ユーザー一覧の閲覧"] R1 --> P2["ユーザーの追加・削除"] R2 --> P3["自分のデータの閲覧・編集"]

この形にしておくと、「誰が何をできるか」を変えたいときは、人ではなくロール側の割り当てを変えるだけで済みます。山田さんが異動して権限を落としたければ、`app-admin` ロールを外して `app-user` ロールを付け替えるだけです。個々の権限設定を1つずつ探して直す必要がありません。

重要ポイント

認可の設計は「人に権限を付ける」のではなく「ロールに権限の意味を持たせ、人にはロールを割り当てる」のが基本です。この章の残りは、Keycloakでこの考え方をどう実現するかを見ていきます。

7.2 レルムロールとクライアントロールの違い

Keycloakのロールには2種類あります。この違いを最初に押さえておかないと、後で「どちらに作ればよかったのか」で迷うことになります。

レルムロール

レルム全体で共通に使える役割です。例えば `admin`（管理者）や `user`（一般利用者）のように、どのアプリからも同じ意味で使いたい役割を作るときに選びます。第4章で作った学習用レルムに1つだけ存在します。

クライアントロール

特定のクライアント（アプリ）の中だけで意味を持つ役割です。例えば第5章で登録した `demo-app` の中だけで通用する `order-manager`（注文管理者）のように、そのアプリ固有の業務上の役割を表すときに選びます。

判断に迷ったときは、次の表を目安にしてください。

観点 レルムロール クライアントロール
通用する範囲 レルム内のすべてのアプリ そのクライアント（アプリ）の中だけ
作成場所 左メニュー Realm roles Clients → 対象クライアント → Roles タブ
典型的な例 admin、user、app-admin order-manager（demo-app専用）
向いている場面 複数アプリ共通の「立場」を表したいとき そのアプリだけの業務機能を表したいとき

7.3 レルムロールを作る手順

実際にレルムロールを1つ作ってみましょう。ここでは `app-admin` というロールを例にします。

  1. ① 管理コンソール左メニューのRealm rolesをクリックする。
  2. ② 右上のCreate roleボタンをクリックする。
  3. ③ Role name欄に `app-admin` と入力する（Descriptionには「アプリの管理者」のような説明を書いておくと後で分かりやすい）。
  4. ④ Saveをクリックする。

同じ手順で `app-user` というレルムロールも作っておきましょう（やってみよう 7-1 で実際に手を動かします）。

7.4 クライアントロールを作る手順

続いて、`demo-app` というクライアントの中だけで通用するクライアントロールを作る手順です。

  1. ① 左メニューのClientsをクリックし、一覧からdemo-appを選ぶ。
  2. ② クライアント詳細画面上部のタブからRolesを選ぶ。
  3. ③ Create roleをクリックし、Role nameに `order-manager` と入力してSaveする。

画面上の操作はレルムロールとほぼ同じですが、どこから作業を始めたか（Realm roles か、特定のクライアントの中か）で、通用する範囲が変わる点を意識してください。

7.5 ユーザーにロールを割り当てる手順

ロールを作っただけでは、誰にも権限は付きません。第6章で作成したユーザーに、実際にロールを割り当てましょう。

  1. ① 左メニューのUsersから、対象のユーザーをクリックして詳細画面を開く。
  2. ② 上部タブのRole mappingを選ぶ。
  3. ③ Assign roleボタンをクリックする。
  4. ④ 一覧上部の絞り込みでFilter by realm roles（レルムロールを探す場合）またはFilter by clients（クライアントロールを探す場合）を選び、目的のロールを見つける。
  5. ⑤ 付けたいロールにチェックを入れ、Assignをクリックする。

Role mapping タブの一覧に、割り当てたロールが表示されれば成功です。同じ画面からUnassignで外すこともできます。

7.6 既定ロール（default-roles-<レルム名>）

Role mapping タブを開くと、自分で割り当てた覚えのないロールが最初から付いていることに気づくはずです。これは default-roles-<レルム名> という既定ロールで、新規ユーザーを作成すると自動的に付与されます。

既定ロールの中身も確認・調整できる

Realm roles の一覧から default-roles-<レルム名> を開くと、それ自体が複合ロール（7.7参照）であることが分かります。中には `offline_access` や `uma_authorization` といった、Keycloakの基本機能に必要なロールが含まれています。ここに自分たちの `app-user` を追加すれば、「新規ユーザーには自動で app-user を付ける」という運用にできます。

7.7 複合ロール（Composite role） — ロールの中にロールを含める

「管理者は、一般利用者ができることは全部できて、それに加えて管理機能も使える」というのはよくある要件です。このとき `app-admin` に一般利用者の権限を1つずつ複製するのではなく、`app-admin` の中に `app-user` を含めることができます。これが複合ロール（Composite role）です。

作り方は次のとおりです。

  1. ① Realm roles から複合ロールにしたいロール（例: `app-admin`）を開く。
  2. ② 右上のActionメニューからAdd associated rolesを選ぶ。
  3. ③ 含めたいロール（例: `app-user`）を選んでAddする。

これで `app-admin` を割り当てられたユーザーは、`app-user` の権限も自動的に持つことになります。組織の役職の階層（一般 → リーダー → 管理者）を表現するのに便利な仕組みです。

入れ子にしすぎない

複合ロールは、さらに別の複合ロールを含めることもできます。しかし何段階にも入れ子にすると、「結局このユーザーは何ができるのか」を追うのが非常に難しくなります。実務では1〜2段階までに留め、複雑な条件分岐が必要な場合はロール構成ではなく別の仕組み（Authorization Servicesなど、本教材の範囲外）を検討しましょう。

7.8 グループ — 組織構造をまとめる入れ物

ロールが「何ができるか」を表すのに対して、グループは「営業部」「開発部」のような組織構造を表す入れ物です。グループにロールを割り当てておき、ユーザーをそのグループに入れるだけで、そのグループが持つロールがまとめて付与されます。

図2: グループ・ロール・ユーザーの関係

flowchart LR G["グループ: 開発部"] -->|ロールを割り当て| R["ロール: app-admin"] U1["ユーザー: 山田"] -->|グループに参加| G U2["ユーザー: 佐藤"] -->|グループに参加| G G -.->|権限が自動的に付与される| U1 G -.->|権限が自動的に付与される| U2

作成の流れは次のとおりです。

  1. ① 左メニューのGroupsからCreate groupをクリックし、「開発部」のようなグループ名を付ける（必要であればグループの中にサブグループも作れる）。
  2. ② 作成したグループを開き、Role mappingタブから、そのグループに持たせたいロールを Assign role で割り当てる。
  3. ③ ユーザー詳細画面のGroupsタブからJoin Groupを選び、対象のグループを選んで参加させる。

グループに参加したユーザーは、そのグループに割り当てられたロールを（自分に直接ロールを付けなくても）持つことになります。人事異動でグループを移動させるだけで、権限もまとめて切り替わります。

7.9 ロールとグループの使い分け

ここまでを整理すると、原則はシンプルです。ロールは「何ができるか（役割）」、グループは「どこに所属するか（組織）」を表します。

観点 ロール グループ
表すもの 何ができるか（役割・権限の種類） どこに所属するか（組織構造）
アプリが見るもの トークンに載ったロールを見て判定する 通常はグループを直接見ない（ロール経由で効く）
人事異動時に動かすもの 基本的には動かさない（役割の定義自体は変わらない） ユーザーの所属グループを付け替える
設計のコツ アプリの機能単位で細かく定義する 組織図に沿って作り、ロールをまとめて付与する

つまり、アプリのコード側が判断材料にするのは常にロールです。グループは、管理者が「大勢のユーザーに同じロールをまとめて付けるための便利な入れ物」と考えると整理しやすくなります。

7.10 ロールはトークンにどう現れるか

割り当てたロールは、ログイン後にKeycloakが発行するアクセストークンの中に書き込まれます。アプリはこのトークンを読み取って、「このユーザーは何をしてよいか」を判断します。レルムロールとクライアントロールは、トークンの中でも別々の場所に載ります。

access_token（抜粋） 
{
  "realm_access": {
    "roles": ["app-user", "app-admin"]
  },
  "resource_access": {
    "demo-app": {
      "roles": ["order-manager"]
    }
  }
}

レルムロールは realm_access.roles に、クライアントロールは resource_access.<クライアントID>.roles に、それぞれ配列として並びます。アプリはこの配列に目的のロール名が含まれているかどうかで、機能を出し分けます。実際にトークンをデコードして中身を確認する作業は、次の第8章で行います。

やってみよう 7-1: app-user / app-admin ロールを作り、複合ロールにする

この章で学んだレルムロールの作成・割り当て・複合ロールを、実際に手を動かして体験しましょう。第6章で作成したユーザーを使います。

手順

  1. 1 7.3節の手順で、レルムロール `app-user` を作成する。
  2. 2 同じ手順で、もう1つレルムロール `app-admin` を作成する。
  3. 3 7.5節の手順で、第6章で作成したユーザーの Role mapping から `app-user` を Assign する。
  4. 4 7.7節の手順で `app-admin` を開き、Action → Add associated roles から `app-user` を追加して複合ロールにする。
  5. 5 同じユーザーに `app-admin` も Assign し、Role mapping の一覧に両方のロールが表示されることを確認する（`app-user` は複合ロール経由でも持っていることになる）。

この章のまとめ

  • 権限は人に直接付けず、ロール（役割）にまとめて人へ割り当てる（RBAC）と管理が破綻しにくい。
  • レルムロールはレルム全体で共通、クライアントロールは特定のアプリの中だけで意味を持つ。
  • 複合ロールで他のロールを含められ、グループで組織構造にロールをまとめ付けできる。
  • ロールは「何ができるか」、グループは「どこに所属するか」——アプリが判断に使うのは常にロール。
  • 割り当てたロールは、アクセストークンの realm_access.roles / resource_access に載る。

確認問題

  1. Q1. ユーザー1人ずつに直接権限を設定する方式ではなく、ロールを介して権限を付ける方式（RBAC）を使う利点は何ですか。

    回答を表示

    権限をロールという単位にまとめておくことで、人数が増えても「誰にどのロールを割り当てるか」だけを管理すればよくなる。役割の変更（異動など）があっても、ロールの割り当てを変えるだけで済み、権限設定を1つずつ探して直す必要がない。

  2. Q2. レルムロールとクライアントロールの違いを説明してください。

    回答を表示

    レルムロールはレルム全体で共通に使える役割（例: admin、user）。クライアントロールは特定のクライアント（アプリ）の中だけで意味を持つ役割（例: demo-appの order-manager）。複数アプリ共通の立場を表したいならレルムロール、そのアプリ固有の業務機能を表したいならクライアントロールを選ぶ。

  3. Q3. ロールとグループの役割の違いを一言ずつで説明してください。

    回答を表示

    ロールは「何ができるか（役割・権限の種類）」を表す。グループは「どこに所属するか（組織構造）」を表す入れ物で、グループにロールを割り当ててユーザーを参加させると権限がまとめて付く。アプリのコード側が判断に使うのは常にロールで、グループはロールを配るための管理上の仕組み。
