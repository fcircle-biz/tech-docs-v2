ホーム Keycloak 第12章
第12章 所要時間: 約50分

外部ID連携とユーザーフェデレーション

これまでの章では、ユーザーの情報はすべてKeycloakの中に作成してきました。しかし実際の現場では、「GitHubやGoogleのアカウントでログインさせたい」「社員はすでに社内のActive Directoryに登録されている」というケースがよくあります。この章では、ログインそのものを外部に任せるアイデンティティプロバイダー連携と、ユーザー情報の保管場所を外部に置いたまま使うユーザーフェデレーションという2つの仕組みを学びます。

この章で学ぶこと

  • アイデンティティプロバイダー連携とユーザーフェデレーションの違いを説明できる
  • GitHub・Googleなどを使ったソーシャルログインを設定できる
  • 初回ログイン時のアカウント紐付けの挙動と注意点を理解する
  • LDAP / Active Directory 連携の設定項目と Edit mode の違いを理解する
  • ソーシャルログインとユーザーフェデレーションをどう使い分けるかを判断できる

12.1 「外部との付き合い方」は2種類ある

「外部の仕組みと連携する」と一言で言っても、Keycloakには性質の異なる2つの機能があります。ここを混同すると、後の設定画面で迷子になりやすいので、最初にはっきり区別しておきましょう。

  • アイデンティティプロバイダー（IdP）連携 — ログインそのものを外部（Google・GitHub・他社のKeycloakなど）に任せる。利用者は外部サービスの画面でログインし、Keycloakはその結果を受け取って自分のトークンを発行する「仲介役」になる。
  • ユーザーフェデレーション — ユーザー情報の保管場所を外部（LDAP / Active Directory）に置いたまま使う。ログイン画面はKeycloakのままで、入力されたIDとパスワードを裏側でLDAPに問い合わせて確認する。

12.2 ソーシャルログインの流れ — Keycloakが仲介役になる

「GitHubでログイン」ボタンを押したとき、実際には何が起きているのでしょうか。ポイントは、アプリはGitHubと直接話さず、あくまでKeycloakを窓口にするという点です。

図2: ソーシャルログインの流れ

sequenceDiagram participant U as 利用者 participant A as アプリ participant K as Keycloak participant G as GitHub U->>A: ページを開く A->>K: ログインへリダイレクト U->>K: "GitHubでログイン"を選択 K->>G: GitHubのログイン画面へリダイレクト U->>G: GitHubにログイン G->>K: ログイン結果を通知 K->>K: 初めての利用者か確認 K->>A: Keycloakのトークンを発行 A->>U: ログイン完了

重要ポイント

アプリ側の設定は何も変わりません。アプリが話す相手は最初から最後までKeycloakだけです。GitHubログインを追加しても、アプリが受け取るのは第8章で見たのと同じ形のKeycloakのトークンです。「連携先を増やす作業」はすべてKeycloak側で完結するという点が、この仕組みの大きな利点です。

12.3 アイデンティティプロバイダーを追加する手順

GitHubを例に、実際の追加手順を見てみましょう。Googleなど他のプロバイダーでも、大まかな流れは同じです。

  1. 1 管理コンソールの左メニューから Identity providers を開き、一覧から GitHub（Googleを使う場合は Google）を選ぶ。
  2. 2 設定画面に表示される Redirect URI（例: http://localhost:8080/realms/demo-realm/broker/github/endpoint）をコピーしておく。これはGitHub側に「ログイン結果をここに返してください」と伝えるための戻り先URLです。
  3. 3 GitHub側（Settings → Developer settings → OAuth Apps）で新しいOAuthアプリを登録し、Authorization callback URL に手順2でコピーしたRedirect URIを設定する。
  4. 4 GitHubで発行された Client ID と Client secret を、Keycloakの設定画面の同名の項目に入力する。
  5. 5 Add を押して保存する。以後、対象レルムのログイン画面に「GitHubでログイン」ボタンが自動的に表示されるようになる。

Redirect URI の読み解き方

/realms/demo-realm/broker/github/endpoint のうち、demo-realm がレルム名、github がここで付けたプロバイダーのエイリアス（識別名）です。複数のIdPを追加すると、プロバイダーごとに異なるRedirect URIが発行されます。

12.4 初回ログイン時の紐付け（First login flow）

GitHubでのログインに成功したとき、Keycloakはその人を「初めて見る人」として新しいユーザーを自動作成するのか、それとも「既存の誰か」として扱うのかを判断する必要があります。この判断ルールが First login flow です。

  • 新規ユーザーとして自動作成する — 一致する既存ユーザーがいなければ、GitHubから受け取った情報（メールアドレス・名前など）を使ってKeycloakに新しいユーザーを作る。
  • 既存ユーザーと紐付ける — GitHubのメールアドレスと同じメールアドレスを持つユーザーがKeycloak内に既にいれば、そのユーザーとして扱う（アカウントリンク）。

確認なしの自動紐付けはアカウント乗っ取りのリスクがある

「メールアドレスが一致したら自動的に既存アカウントへ紐付ける」設定は便利ですが、そのメールアドレスを名乗るGitHubアカウントを誰かが用意できてしまえば、他人のKeycloakアカウントに入り込める危険があります。特にメールアドレスの検証（確認）を行っていない外部プロバイダーと組み合わせる場合は注意が必要です。本番環境では、既存アカウントとの紐付けを利用者自身の操作（ログイン後に手動でリンク）に限定する、あるいはメール確認済みのプロバイダーのみ許可するといった対策を検討してください。

12.5 マッパー — 外部の情報をKeycloakの項目に対応づける

外部IdPから受け取れる情報は、メールアドレスや名前だけではありません。所属チームなどの追加情報が含まれる場合もあります。これらを、Keycloak側のユーザー属性やロールにどう対応づけるかを設定するのが、追加したIdPの Mappers タブです。「外部の項目Aを、Keycloakの属性Bに入れる」という対応を1つずつ登録できます。この章では概要にとどめ、実際の設定は必要になったときに公式ドキュメントを参照するとよいでしょう。

12.6 ユーザーフェデレーション（LDAP）とは

多くの企業には、社員の情報を管理する Active Directory や OpenLDAP といったディレクトリサービスが既に存在します。この社員名簿を、Keycloakにもう一度コピーして作り直すのは二度手間ですし、人事異動のたびに両方を更新する羽目になります。

たとえ話: 社員名簿は人事のシステムが持つ

社員名簿そのものは、これまでどおり人事のシステム（LDAP / AD）が管理し続けます。Keycloakはその名簿を参照するだけで、コピーを持ちません。利用者がKeycloakのログイン画面でIDとパスワードを入力すると、Keycloakは裏側でLDAPに「このIDとパスワードは正しいですか」と問い合わせ、答えを受け取ってログインを完了させます。

これがユーザーフェデレーションです。管理コンソールの User federation からLDAPサーバーの接続情報を登録するだけで、社員はこれまでどおりのID・パスワードでKeycloak経由のログインができるようになります。

12.7 LDAP連携の設定項目

LDAPプロバイダーを追加する画面では、多くの項目が並びます。代表的なものを整理します。

項目 意味・設定例
Vendor 接続先の種類。Active Directory または Other（OpenLDAP等）を選ぶ
Connection URL LDAPサーバーのアドレス。例: ldap://ldap.example.com:389
Bind type / Bind DN・credentials KeycloakがLDAPに検索アクセスするための管理用アカウント（simple認証なら識別名とパスワード）
Users DN ユーザーを検索する開始位置。例: ou=users,dc=example,dc=com
Username LDAP attribute ログインIDに対応する属性名。Active Directoryなら sAMAccountName、それ以外は多くの場合 uid
User object classes ユーザーとして扱うLDAPオブジェクトの種類（例: person, organizationalPerson, user）
Import users / 同期設定 LDAP情報をKeycloak内にキャッシュとして取り込むか。Periodic full sync（全件同期）・Periodic changed users sync（差分同期）を定期実行できる

中でも特に重要なのが Edit mode です。Keycloak側からLDAPのユーザー情報をどこまで書き換えてよいかを決める設定で、3つの選択肢があります。

Edit mode Keycloakからの変更 向いている場面
READ_ONLY 一切変更できない（パスワード変更も不可） 人事システムだけを唯一の真実の情報源にしたい、最も基本的な選択
WRITABLE Keycloak側の変更がLDAPにも反映される KeycloakのアカウントコンソールでパスワードやプロフィールをLDAPまで含めて更新したい場合
UNSYNCED Keycloak内だけで変更を保持し、LDAPには反映しない 認証はLDAPで行うが、Keycloak固有の追加属性だけ別管理したい場合

迷ったら READ_ONLY

社員情報の管理責任を持つのはあくまで人事のシステムです。Keycloakからうっかり書き換えてしまう事故を避けるため、まずは READ_ONLY から始め、必要になった場合にだけ WRITABLE を検討するのが安全です。

12.8 LDAPのグループをKeycloakのグループに対応づける

LDAPプロバイダーの設定画面には Mappers タブがあり、その中に group-ldap-mapper（LDAPグループマッパー）という項目を追加できます。これを使うと、LDAP側の組織単位やグループ情報を、第7章で学んだKeycloakのグループに対応づけられます。「LDAPの営業部グループに入っている人は、Keycloakでも自動的に営業部グループのメンバーとして扱う」といったことが可能になります。詳細な設定手順はここでは扱いませんが、「そういう仕組みがある」ことを覚えておいてください。

12.9 どちらを使うべきか

ここまで学んだ3つの連携方法は、目的によって使い分けます。状況に応じた判断の目安を整理します。

状況 おすすめの方法
社外の一般ユーザーに手軽にログインしてほしい ソーシャルログイン（IdP連携: GitHub / Google など）
社員が既にActive Directory / LDAPに登録されている ユーザーフェデレーション
取引先企業や他社のシステムとSSOしたい SAML / OIDC によるIdP連携（第2・9章で学んだ標準仕様の応用）

これらはどちらか一方しか使えない、という排他的な選択ではありません。1つのレルムに「社員はLDAPフェデレーションでログイン」「社外パートナーはGitHubログイン」を同時に設定することも可能です。実際の組織では、複数の連携方法を組み合わせて使うことがよくあります。

12.10 学習環境での試し方

実際に手を動かして確かめたい場合、最も手軽なのは GitHubのOAuthアプリです。GitHubアカウントさえあれば無料で登録でき、12.3節の手順どおりに設定すれば、手元のKeycloakにすぐソーシャルログインを追加できます。

LDAP連携を試したい場合は、検証用の OpenLDAPコンテナをDockerで立ち上げ、そこにテスト用ユーザーを何人か登録してからKeycloakのUser federationで接続する、という進め方が一般的です。具体的なコンテナの構築手順は環境によって異なるため本書では扱いませんが、「本番のADに直接つながず、まず検証用のLDAPで試す」という方針だけ覚えておくとよいでしょう。

やってみよう 12-1: ソーシャルログインを追加してみる

GitHub（またはGoogle）のIdPを実際に追加し、ログイン画面の変化を確認しましょう。外部アカウントを使いたくない場合は、下の代替課題に取り組んでください。

手順

  1. 1 GitHubで新しいOAuthアプリを登録する準備をする（Redirect URIは次の手順で確認してから設定する）。
  2. 2 Keycloak管理コンソールで Identity providers → GitHub を選び、表示されたRedirect URIをコピーしてGitHub側に設定する。
  3. 3 GitHubで発行されたClient IDとClient secretをKeycloakに入力し、Addで保存する。
  4. 4 対象レルムのログイン画面を開き直し、「GitHubでログイン」ボタンが増えていることを確認する。
  5. 5 実際にボタンを押してログインし、Keycloak側にユーザーが自動作成されたことを Users 一覧で確認する。

代替課題（外部アカウントを使いたくない場合）

12.3節に出てきたRedirect URI http://localhost:8080/realms/demo-realm/broker/github/endpoint を読み解き、「どの部分がレルム名で、どの部分がプロバイダー名（エイリアス）にあたるか」を自分の言葉で説明してみましょう。

この章のまとめ

  • IdP連携はログインそのものを外部に任せる仕組み、ユーザーフェデレーションはユーザー情報の保管場所を外部に置いたまま使う仕組み。
  • ソーシャルログインを追加してもアプリ側の設定は変わらない。Keycloakが仲介役として振る舞う。
  • 初回ログイン時の自動紐付けは便利だが、確認なしの自動紐付けはアカウント乗っ取りのリスクがある。
  • LDAP連携の Edit mode（READ_ONLY / WRITABLE / UNSYNCED）は、迷ったらREAD_ONLYが安全。
  • ソーシャルログイン・ユーザーフェデレーション・SAML/OIDC連携は併用が可能。目的に応じて使い分ける。

確認問題

  1. Q1. アイデンティティプロバイダー連携とユーザーフェデレーションの違いを、それぞれ一言で説明してください。

    回答を表示

    アイデンティティプロバイダー連携はログインそのものを外部（GitHub・Googleなど）に任せる仕組みで、ログイン画面が外部サービスに切り替わります。ユーザーフェデレーションはユーザー情報の保管場所を外部（LDAP / AD）に置いたまま使う仕組みで、ログイン画面はKeycloakのままです。

  2. Q2. 初回ログイン時に「既存ユーザーへの自動紐付け」を安易に有効化してはいけない理由を説明してください。

    回答を表示

    メールアドレスが一致するだけで既存アカウントに自動的に紐付けてしまうと、そのメールアドレスを名乗る外部アカウントを第三者が用意できれば、他人のKeycloakアカウントに入り込めるおそれがあるためです。メール確認済みのプロバイダーに限定する、利用者自身の操作で紐付けさせるといった対策が必要です。

  3. Q3. LDAP連携の Edit mode のうち、迷ったときに選ぶべきなのはどれで、それはなぜですか。

    回答を表示

    READ_ONLYです。社員情報の管理責任はあくまで人事のシステム（LDAP / AD）側にあり、Keycloakから書き換えてしまう事故を避けるためです。書き込みが本当に必要になった場合にのみ WRITABLE を検討します。
