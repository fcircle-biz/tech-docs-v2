ホーム Keycloak 第13章
第13章 所要時間: 約50分

本番運用に向けて

ここまでの12章では、Docker上の開発モードでKeycloakを動かしながら、レルム・クライアント・ユーザー・ロール・トークン・セキュリティ強化・外部連携までを学んできました。この最終章では視点を変え、「このKeycloakを本番環境で安全に運用するには何が足りないか」を確認します。データベース・HTTPS・バックアップ・監視・セキュリティチェックリストという、実務で必ず問われる項目を1つずつ押さえ、本教材全体のまとめとします。

この章で学ぶこと

  • 開発モード（start-dev）のままでは本番に出せない理由を説明できる
  • 外部データベース・HTTPS・ホスト名など本番構成に必要な設定項目を挙げられる
  • レルムのエクスポート／インポートによるバックアップと、その注意点を理解する
  • ログ・監視・バージョンアップの考え方を知り、本番前セキュリティチェックリストを使える

13.1 開発モードのままでは本番に出せない理由

第3章で、Keycloakを start-dev コマンドで起動しました。この「開発モード」は、学習や検証にはとても便利ですが、そのまま本番環境で使うことは想定されていません。理由は名前のとおり単純で、とにかく手軽に立ち上げることを優先し、安全性・耐久性・性能を犠牲にしているからです。

  • HTTPS不要 — 平文のHTTPで動くため、通信内容やトークンが盗聴されるおそれがある
  • 簡易な組み込みデータベース — コンテナを削除するとレルム・ユーザー・設定がすべて消える
  • キャッシュが無効 — 複数台での動作や高負荷を前提にしておらず、性能が最適化されていない
  • ホスト名の検証が緩い — 学習中はどのURLでアクセスしても動くが、本番では意図しないなりすましを招きかねない

本番運用では、これらの前提を1つずつ「安全側」に切り替えていきます。Keycloakには start という本番向けの起動コマンドがあり、いくつかの設定を明示しないと起動を拒否する仕組みになっています。これは「うっかり開発モードのまま公開してしまう」事故を防ぐための、意図された安全装置です。

観点 開発モード（start-dev） 本番モード（start）
通信 HTTPのみで起動できる HTTPS前提。設定なしでは起動を拒否
データの保存先 組み込みの簡易データベース（揮発しやすい） 外部データベース（PostgreSQLなど）を明示的に指定
ホスト名 未指定でも動作する KC_HOSTNAME の指定が事実上必須
性能・可用性 単一プロセス・キャッシュ無効を前提 複数台構成・キャッシュ有効を前提に最適化可能
用途 学習・検証・ローカル開発 実際の利用者が使う本番環境

13.2 本番構成の全体像

細かい設定に入る前に、本番でよく採用される構成の全体像を1枚の図で確認しておきましょう。利用者は直接Keycloakにアクセスするのではなく、リバースプロキシを経由します。プロキシがHTTPSの終端（暗号化・復号）を担当し、Keycloak自体は複数台に増やして負荷分散できるようにします。データはすべて外部のPostgreSQLのようなデータベースに保存します。

図1: 本番構成の全体像

flowchart LR U["利用者"] -->|HTTPS| P["リバースプロキシ
（HTTPS終端）"] P -->|HTTP/HTTPS| K1["Keycloak（1台目）"] P -->|HTTP/HTTPS| K2["Keycloak（2台目）"] K1 --> DB[("PostgreSQL")] K2 --> DB

本教材はKeycloakの基本操作を学ぶことが目的なので、複数台構成やクラスタリングの詳細までは扱いません。ここでは「プロキシがHTTPSを受け止め、Keycloakは複数台に増やせて、データは外部DBに一元化する」という形を頭に入れておけば十分です。以降の節では、この図の各要素を設定する方法を1つずつ見ていきます。

13.3 外部データベースの設定

レルム・クライアント・ユーザー・ロールなど、これまで管理コンソールで作ってきた設定は、すべてKeycloakの裏にあるデータベースに保存されています。つまりデータベースこそがKeycloakの「真実源」であり、これが失われるとすべての設定が失われます。開発モードの組み込みデータベースは検証専用なので、本番では必ずPostgreSQLなどの外部データベースに接続します。

環境変数 意味 設定例
KC_DB 使用するデータベースの種類 postgres
KC_DB_URL 接続先のJDBC URL jdbc:postgresql://db:5432/keycloak
KC_DB_USERNAME データベース接続ユーザー名 keycloak
KC_DB_PASSWORD データベース接続パスワード 強固なパスワードを別途管理
bash 
# 外部PostgreSQLを指定してKeycloakを起動する例（本番モード）
docker run -d --name keycloak-prod \
  -e KC_DB=postgres \
  -e KC_DB_URL=jdbc:postgresql://db:5432/keycloak \
  -e KC_DB_USERNAME=keycloak \
  -e KC_DB_PASSWORD=<強固なパスワード> \
  -p 8080:8080 \
  quay.io/keycloak/keycloak:26.0 start

なお、Keycloakには kc.sh build というビルド時最適化の仕組みもあります。あらかじめデータベースの種類などの固定的な設定を組み込んでイメージを最適化しておくことで、起動時間を短縮できます。start --optimized はこのビルド済みイメージを前提に高速起動するオプションですが、本教材では紹介にとどめ、通常の start で本番構成の考え方を押さえます。

13.4 HTTPSとホスト名

トークンやパスワードをやり取りするKeycloakは、管理コンソールを含め、必ずHTTPSで公開します。図1のようにリバースプロキシでHTTPSを終端する構成では、Keycloak自体は内部でHTTPのまま動かし、「自分は今HTTPSでアクセスされている」と正しく認識させるための設定が必要です。

設定項目 役割
KC_HOSTNAME 利用者からアクセスされる公開ホスト名（例: auth.example.com）を明示する
KC_PROXY_HEADERS リバースプロキシが付与するヘッダー形式を指定する（xforwarded または forwarded）
KC_HTTP_ENABLED プロキシ配下でKeycloak自体はHTTPのまま動かす場合にtrueにする

バージョンによって推奨設定が変わる

Keycloakはリリースのたびに、HTTPS・プロキシ関連の設定項目が見直されることがあります。ここで挙げた環境変数名は26系時点の代表的なものですが、実際に本番構築する際は必ず利用するバージョンの公式ドキュメント（Server Administration Guide）で最新の設定名を確認してください。管理コンソールは特に機密性が高いため、HTTP経由でのアクセスは一切許可しないようにします。

13.5 管理者アカウントの扱い

第3章でKeycloakを起動したとき、KC_BOOTSTRAP_ADMIN_USERNAME と KC_BOOTSTRAP_ADMIN_PASSWORD という環境変数で最初の管理者アカウントを作成しました。この名前が示すとおり、これは初回起動時にmasterレルムへ管理者を1人作るためだけの「ブートストラップ」用の仕組みです。

初期管理者をそのまま本番で使わない

学習中に使った初期パスワードは、環境変数やDockerの実行履歴に平文で残りがちです。本番では、管理コンソールから強固なパスワード（できれば二要素認証つき）を持つ管理者アカウントを新規に作り直し、初期アカウントは削除するか無効化してください。第4章で学んだとおり、masterレルムは管理専用に保ち、アプリの利用者や業務用ユーザーは学習用レルム（本教材の demo-realm に相当するもの）に作成します。masterレルムに業務ユーザーを混在させないことが、権限分離の基本です。

13.6 設定のバックアップと移行

レルムの設定は、管理コンソールの「Realm settings」画面にあるPartial export機能でファイルに書き出せます。クライアント・ロール・グループなどの構成をJSONファイルとしてまとめて出力し、別環境（検証環境から本番環境など）へインポートして移行するのに使います。コマンドラインからも同様の操作ができます。

bash 
# demo-realmの設定をエクスポートする例（コンテナ内で実行）
/opt/keycloak/bin/kc.sh export \
  --dir /opt/keycloak/data/export \
  --realm demo-realm

エクスポートファイルの取り扱いに注意

エクスポートしたJSONには、設定内容によってはクライアントシークレットなどの機密情報が含まれる場合があります。Gitリポジトリにそのままコミットしたり、権限のない相手に共有したりしないでください。また、レルムのエクスポートは「設定の移行」には便利ですが、真のバックアップとして頼るべきはデータベース自体のバックアップです。ユーザーのパスワードハッシュやセッション情報まで含めて確実に復旧するには、PostgreSQLなど利用しているデータベースの標準的なバックアップ手順（定期ダンプなど）を別途用意してください。

13.7 ログ・イベント・監査

「誰が、いつ、何をしたか」を後から追えるようにしておくことは、本番運用では欠かせません。Keycloakの管理コンソールでは、「Realm settings」の隣にあるEvents画面から、この記録機能を有効にできます。

項目 記録される内容
User events ログイン成功・失敗、パスワード変更など、利用者の操作履歴
Admin events 管理コンソールでの設定変更（クライアント作成、ロール付与など）の履歴
保存期間（Expiration） 記録をどれくらいの期間データベースに保持するかを設定できる

本番環境では、これらのイベントに加えて、Keycloakコンテナが出力する標準出力のログも重要な情報源です。コンテナオーケストレーターやログ収集基盤（Fluentdやログ集約サービスなど）で標準出力を継続的に収集し、外部のログ基盤に送る構成にしておくと、コンテナが再起動してもログが失われず、複数台構成でも一箇所で横断的に調査できます。

13.8 監視とヘルスチェック

複数台構成でKeycloakを運用する場合、「このKeycloakは正常に動いているか」を機械的に判定する仕組みが必要です。Keycloakはヘルスチェック用のエンドポイントとメトリクス（数値指標）の出力を、環境変数で有効化できます。

環境変数 / エンドポイント 役割
KC_HEALTH_ENABLED=true ヘルスチェック機能全体を有効にする
/health/live プロセスが生きているか（応答すれば生存とみなす）
/health/ready データベース接続なども含め、リクエストを受け付けられる状態か
KC_METRICS_ENABLED=true /metrics でリクエスト数などの数値指標を出力する

/health/live と /health/ready は、コンテナオーケストレーター（KubernetesのLiveness/Readinessプローブなど）が「このインスタンスに新しいリクエストを回してよいか」「再起動が必要か」を自動判定するのに使われます。/metrics は、稼働状況をダッシュボードで可視化したり、異常を検知して通知したりする監視基盤に取り込みます。

13.9 バージョンアップの考え方

Keycloakは開発が活発で、新しいバージョンが比較的短い間隔でリリースされます。機能追加やセキュリティ修正が受けられる一方、設定項目の名前が変わったり、非推奨になったりすることがある点には注意が必要です。本教材で扱った環境変数名も、将来のバージョンでは変わる可能性があります。安全にバージョンアップするための基本的な流れは、次のとおりです。

  1. リリースノート（Upgrading guide）を必ず読む — 破壊的変更（設定名の変更・非推奨化）がないかを確認する
  2. データベースをバックアップしてから上げる — 万一の不具合でも、すぐ元のバージョンに戻せる状態を確保する
  3. 検証環境で先に試す — 本番と同じデータ構成をコピーした環境で、ログインやアプリ連携が問題なく動くことを確認する
  4. 段階的に本番へ適用する — 問題なければ本番環境へ反映し、直後はログとイベントを注意深く確認する

13.10 本番前セキュリティチェックリスト

ここまでの内容と、これまでの章で学んだセキュリティ設定を、公開前に確認すべき項目としてまとめます。1つずつ、自分の構成に当てはめて確認してください。

1. 管理コンソールを含め、すべてHTTPSで公開しているか

2. 初期管理者アカウントを強固なものに置き換え、初期アカウントを無効化したか

3. masterレルムに、アプリ用・業務用のユーザーを混在させていないか

4. リダイレクトURIに広いワイルドカードを許可していないか

5. クライアントシークレットなどの機密情報をGitに含めていないか

6. パスワードポリシーとブルートフォース検知を有効にしたか

7. 管理者アカウントに二要素認証（OTP）を必須にしたか

8. User events / Admin eventsのイベントログを有効にしたか

本教材はあくまで入門です。より実践的なID基盤を構築・運用するために、次のようなテーマへ進むことをおすすめします。

認証・認可の基盤は地味に見えて、あらゆるアプリの土台を支える重要な仕組みです。ここまで読み切ったことは、確かな一歩です。ぜひ実際に手元のアプリをKeycloakにつないでみて、この教材で学んだ知識を血肉にしていってください。お疲れさまでした。

やってみよう 13-1: レルムをエクスポートし、本番前チェックリストを確認する

これまで学習に使ってきた環境で、バックアップの実感とセキュリティの棚卸しをまとめて行います。

手順

  1. 1 管理コンソールで学習用レルムを開き、「Realm settings」→「Action」メニューから Partial export を実行してJSONファイルをダウンロードする。
  2. 2 テキストエディタでファイルの中身を開き、クライアントやロールの設定がどのようなJSON構造で書かれているかを眺めてみる。パスワードやシークレットらしき値が含まれていないかも確認する。
  3. 3 13.10のセキュリティチェックリスト8項目を、自分が学習で使っている環境に当てはめ、○×で自己採点してみる。
  4. 4 ×が付いた項目について、「本番で公開するなら何を設定すればよいか」を、この章で学んだ環境変数名を使って1行で書き出してみる。

この章のまとめ

  • 開発モード（start-dev）はHTTPS不要・簡易DB・キャッシュ無効を前提とし、本番運用には向かない。本番モード（start）へ移行する。
  • 本番構成は「リバースプロキシ（HTTPS終端）→ 複数台のKeycloak → 外部データベース」が基本形。KC_DB系・KC_HOSTNAME・KC_PROXY_HEADERSなどを設定する。
  • 初期管理者は本番用に置き換え、レルムのエクスポートは移行に便利だが機密を含みうる。真のバックアップはデータベースのバックアップ。
  • Events・ヘルスチェック・メトリクスを有効にして監視し、バージョンアップはリリースノート確認とバックアップを徹底する。

確認問題

  1. Q1. 開発モード（start-dev）のままKeycloakを本番公開すべきでない理由を2つ挙げてください。

    回答を表示

    例: (1) HTTPSが不要な構成のため、通信内容やトークンが盗聴されるおそれがある。(2) 簡易な組み込みデータベースを使うため、コンテナを削除するとレルム・ユーザー・設定がすべて消える可能性がある。ほかに「キャッシュ無効で性能・可用性が考慮されていない」なども正解です。

  2. Q2. リバースプロキシ配下でKeycloakを動かす際、正しくHTTPSでアクセスされていると認識させるために使う環境変数を1つ挙げ、役割を説明してください。

    回答を表示

    例: KC_PROXY_HEADERS。リバースプロキシが付与するヘッダー形式（xforwarded または forwarded）を指定し、Keycloak自身がHTTP経由で受けたリクエストでも「元はHTTPSでアクセスされた」と正しく認識できるようにする設定です。あわせて公開ホスト名を明示するKC_HOSTNAMEも正解です。

  3. Q3. レルムのエクスポート（Partial export）と、データベースのバックアップは、それぞれ何のために使い分けますか。

    回答を表示

    レルムのエクスポートは、クライアントやロールなどの設定を別環境へ移行したいときに使います。一方、ユーザーのパスワードハッシュやセッションを含めて確実にシステムを復旧するための真のバックアップは、データベース自体のバックアップで行います。エクスポートファイルには機密情報が含まれうるため、取り扱いにも注意が必要です。
