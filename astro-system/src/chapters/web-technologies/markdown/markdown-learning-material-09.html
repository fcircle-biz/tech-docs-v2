ホーム Markdown 第9章
第9章 所要時間: 約35分

その他の便利な記法

これまでに学んだ基本の記法に加えて、知っていると差がつく応用的な記法をまとめて学びます。区切り線に潜む思わぬ「罠」から、記号をそのまま表示するエスケープ、HTMLタグの併用、コメント、脚注、絵文字コードまで一気に紹介し、最後に「Markdownにも方言（フレーバー）がある」という大切な事実を理解します。

この章で学ぶこと

  • 水平線（区切り線）の書き方と、見出しになってしまう「罠」を避ける方法が分かる
  • バックスラッシュ \ を使った「エスケープ」で、記号をそのまま文字として表示できる
  • <br> や <details> などHTMLタグをMarkdownに併用する方法と、使いすぎに注意すべき理由が分かる
  • コメント・脚注・絵文字コードなど、知っていると差がつく記法を使える
  • CommonMark と GitHub Flavored Markdown（GFM）という「方言」の違いを理解する

9.1 水平線（区切り線）を引く

文書の中に横向きの線（水平線・区切り線）を引いて、話題の切れ目を示したいことがあります。書き方はとても簡単で、-（ハイフン）・*（アスタリスク）・_（アンダースコア）のいずれかを、同じ記号だけで3つ以上並べた行を書くだけです。---、***、___ はどれも同じ横線として表示されます。

ところがこの水平線には、初心者がよくはまる「罠」があります。--- の直前の行に文字が書かれていて、間に空行がない場合、区切り線ではなく直前の行が見出しとして扱われてしまうのです。これは「Setext（セテクスト）見出し」という、古くからある別の見出し記法とルールが重なっているために起きる現象です。実際に見比べてみましょう。

NG: 空行を入れずに書く

bad.md 
今日の作業内容
---

表示イメージ

今日の作業内容

区切り線ではなく、見出しになってしまう。

OK: 前に空行を1つ入れる

good.md 
今日の作業内容

---

表示イメージ

今日の作業内容

段落 + 区切り線として正しく表示される。

覚え方: 区切り線の前後には必ず空行

水平線を書くときは、前の行との間に空行を1つ入れる癖をつければ、この罠にはまることはありません。第3章で学んだ「段落は空行で区切る」というルールとセットで覚えておきましょう。

9.2 エスケープ：記号をそのまま表示する

Markdownでは * や # などの記号に、装飾や見出しといった特別な意味が割り当てられています。では、その記号自体を「ただの文字」として表示したいときはどうすればよいでしょうか。答えは、記号の直前にバックスラッシュ \ を1つ置くことです。これをエスケープ（記号が持つ特別な意味を打ち消す、という意味）と呼びます。

表示したい文字 書き方 エスケープしないと…
* \* 太字・斜体の記号と解釈される
# \# 見出しの記号と解釈される
-（行頭） \- 箇条書きの記号と解釈される
[ ] \[ \] リンクの記号と解釈される
\ \\ エスケープ自体の記号なので、これも2つ重ねる

書いたテキスト（Markdown）

escape.md 
エスケープなし: *これは斜体になる*

エスケープあり: \*これはそのまま表示される\*

表示イメージ

エスケープなし: これは斜体になる

エスケープあり: *これはそのまま表示される*

豆知識: 全角記号なら気にしなくてよいことも

日本語の文章内で「＊」や「＃」のような全角の記号を使う場合は、Markdownの特殊記号（半角）とは別物として扱われるため、そもそもエスケープが不要なこともあります。用途に応じて使い分けましょう。

9.3 HTML タグを併用する

Markdownの記法だけでは表現しきれない部分があります。実はMarkdownには「文書の中に生のHTMLタグをそのまま書いてもよい」というルールがあり、対応している環境ではHTMLとして解釈・表示されます。代表的な例が、改行を強制する <br>（第3章で少し触れました）と、クリックで開閉できる「折りたたみ」を作る <details> ＋ <summary> です。

長いエラーログや補足情報など、「普段は隠しておいて、必要な人だけクリックして見る」ようにしたいときに <details> が役立ちます。

collapse.md 
<details>
<summary>クリックして詳細を表示</summary>

ここに詳しい説明を書きます。
ふだんは折りたたまれて隠れています。

</details>

表示イメージ（実際にクリックしてみてください）

クリックして詳細を表示

ここに詳しい説明を書きます。ふだんは折りたたまれて隠れています。

使いすぎ注意

HTMLタグは便利ですが、①セキュリティ上の理由から生のHTMLを無視・除去してしまう環境もあります（コメント欄やチャットツールなど）。②Markdownの良さは「シンプルさ」なので、HTMLタグを多用すると読みにくいソースになってしまいます。あくまで「Markdownだけでは表現できない部分を補う最終手段」として、必要最小限にとどめましょう。

9.4 コメント：表示されないメモを書く

文書の中に、読者には見えないメモ書きを残しておきたいことがあります。「後で直す」「ここにスクリーンショットを貼る」といった執筆者向けのメモです。HTMLコメントと同じ <!-- --> という記法を使うと、囲んだ部分は表示されなくなります。

notes.md 
公開したいドキュメント本文です。

<!-- TODO: ここに完成後のスクリーンショットを追加する -->

続きの本文です。

表示イメージ

公開したいドキュメント本文です。

続きの本文です。

↑ コメント部分は跡形もなく非表示になっている点に注目してください。

注意: 「見えない」だけで「消えている」わけではない

コメントは画面には表示されませんが、ファイルのソース自体には残っています。GitHubの「Raw」ボタンやブラウザの「ページのソースを表示」機能を使えば、誰でも中身を読むことができます。パスワードや個人情報などの秘密情報は、コメントの中であっても絶対に書かないでください。

9.5 脚注（対応環境のみ）

論文などでよく見る「文中に小さな番号を振って、ページの下にまとめて補足説明を書く」仕組みを、Markdownでも脚注という記法で再現できます。文中に [^1] のような参照を置き、文書のどこか（通常は末尾）に [^1]: 説明文 という定義を書くと、自動で番号が振られてリンクされます。

article.md 
Markdownは軽量マークアップ言語です[^1]。

普段のメモから技術文書まで幅広く使われています[^2]。

[^1]: 「軽量」とは、覚える記号が少なく学習しやすいという意味です。
[^2]: 対応していない環境では、この注釈自体が使えないことがあります。

表示イメージ

Markdownは軽量マークアップ言語です[1]。

普段のメモから技術文書まで幅広く使われています[2]。

1 「軽量」とは、覚える記号が少なく学習しやすいという意味です。

2 対応していない環境では、この注釈自体が使えないことがあります。

対応環境を確認しよう

脚注はGitHub Flavored Markdown（GFM）の拡張機能で、Markdown本来の標準仕様には含まれていません。GitHub上のファイルでは使えますが、Issueコメントやチャットツールなど対応していない場所も多いので、使う前に表示を確認する習慣をつけましょう。

9.6 絵文字コード

GitHubなど多くのサービスでは、:名前: のようにコロンで挟んで書く絵文字コードを入力するだけで、対応する絵文字に自動変換してくれます。キーボードで直接絵文字を入力しにくい環境でも、名前さえ分かれば簡単に使えます。

comment.md 
やったー :tada: ついに完成した！

これは良さそう :+1:

要確認 :warning: 締切に注意してください
絵文字コード 表示 よくある用途
:smile: 😄 ちょっとした感情表現
:tada: 🎉 リリース・お祝いの報告
:white_check_mark: ✅ 完了・確認済みの目印
:warning: ⚠️ 注意事項の強調

使えるコードはサービスによって違う

絵文字コードもGFMの拡張機能で、使える名前の一覧はサービスごとに微妙に異なります。GitHubの入力欄で : を入力すると候補が表示されるので確認してみましょう。Slackなど他のツールでも似た記法が使えますが、対応する絵文字が同じとは限りません。

9.7 方言（フレーバー）を知ろう

ここまで学んできた表・取り消し線・タスクリスト・脚注・絵文字コードには、実は共通点があります。それは、どれも「元祖Markdown」には無かった、後から追加された拡張機能だということです。

Markdownは2004年にJohn Gruberが考案した非公式な仕様で、細かい挙動があいまいな部分が多く残っていました。その後、様々なツールが独自の解釈で機能を拡張していった結果、「同じ記法なのにサービスによって表示が違う」という問題が起きるようになります。この状況を、プログラミング言語の方言（フレーバー）になぞらえて呼びます。

この曖昧さを解消するために、誰が実装しても同じ結果になることを目指した厳密な仕様CommonMarkが策定されました。そしてGitHubは、CommonMarkをベースに開発者にとって便利な機能を追加した方言GitHub Flavored Markdown（GFM）を採用しています。この教材の第5・第8章、そして本章で学んだタスクリスト・表・脚注などは、実はすべてGFMの拡張機能なのです。

記法 CommonMark（標準） GFM（GitHub） 学んだ章
見出し・段落・強調 ○ 対応 ○ 対応 第3・4章
取り消し線 ~~文字~~ × 非対応 ○ 対応 第4章
タスクリスト - [ ] × 非対応 ○ 対応 第5章
表（テーブル） × 非対応 ○ 対応 第8章
脚注・絵文字コード × 非対応 ○ 対応 第9章（本章）

全体の関係を図にすると、次のようになります。

flowchart TD A["CommonMark
（標準仕様）"] --> B["GitHub Flavored Markdown
（GFM）"] A --> C["各サービス独自の拡張"] B --> D["GitHub
（Issue・PR・README）"] C --> E["Qiita／Zenn"] C --> F["Slack／Discordなど
（簡易版）"]

重要ポイント

全部を暗記する必要はありません。見出し・段落・装飾・リスト・リンク・コードブロックなどの基本記法（第3〜7章）は、ほぼどこでも通じる「共通語」です。脚注や絵文字コードのような特殊な記法を使うときだけ、「今書いている場所（GitHubか、Slackか、Zennか）はこの記法に対応しているか」を確かめる習慣をつければ十分です。

やってみよう 9-1: 罠と便利ワザを体験しよう

実際に手を動かして、水平線の罠と、この章で紹介した便利な記法を体験してみましょう。

手順

  1. 1 VS Codeで新しいメモ（.md）を作り、1行目に「今日学んだこと」と入力し、改行してすぐ2行目に --- と書く。プレビュー（Ctrl+Shift+V）を開き、見出しになってしまうことを確認する。
  2. 2 1行目と --- の間に空行を1つ追加し、今度は正しく区切り線として表示されることを確認する。
  3. 3 同じファイルに、9.3で紹介した <details> ＋ <summary> を書き写し、プレビューで開閉できるか確認する（プレビューが対応していない場合は、GitHubにアップロードして確認する）。
  4. 4 GitHubのIssueや自分のリポジトリのコメント欄で :tada: や :rocket: と入力し、絵文字に変換されることを確認する。

理解度確認クイズ

  1. Q1. 水平線（区切り線）を書くときに注意すべき「罠」とはどのようなものですか。

    回答を表示

    直前の行に文字があり、間に空行がない状態で --- を書くと、区切り線ではなく直前の行が見出しとして扱われてしまう罠です。区切り線として表示させるには、前に空行を1つ入れる必要があります。

  2. Q2. Markdownで記号をそのまま文字として表示したいときは、どうすればよいですか。

    回答を表示

    記号の直前にバックスラッシュ \ を置いてエスケープします。例えば \*文字\* と書くと、斜体にならずに「*文字*」とそのまま表示されます。

  3. Q3. CommonMarkとGitHub Flavored Markdown（GFM）の違いを一言で説明してください。

    回答を表示

    CommonMarkはMarkdownのあいまいさを解消するために策定された標準仕様です。GFMはGitHubがCommonMarkをベースに、表・タスクリスト・取り消し線・脚注・絵文字コードなどの機能を追加した「方言」で、同じ記法でも対応状況がサービスによって異なることがあります。
