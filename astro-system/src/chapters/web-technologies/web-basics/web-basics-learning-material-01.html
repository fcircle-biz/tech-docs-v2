ホーム Webの仕組み 第1章
第1章 所要時間: 約30分

Webの仕組みの全体像

私たちは毎日ブラウザでWebページを見ていますが、URLを入力してから画面が表示されるまでの一瞬に、裏側ではいくつもの「やり取り」が行われています。この章では、そのやり取りの全体像を大づかみにし、これから学ぶ HTTP・JSON・REST API がそれぞれどこに登場するのかを確認します。専門用語は少しずつ説明しますので、気楽に読み進めてください。

この章で学ぶこと

  • 「インターネット」と「Web」の違いを説明できる
  • クライアントとサーバーの役割を説明できる
  • URLを入力してからページが表示されるまでの大まかな流れが分かる
  • HTTP・JSON・REST API がそれぞれ何の役目を持つのか、全体の中での位置づけが分かる

1.1 Webとは何か

「インターネット」と「Web」は、日常会話ではほとんど同じ意味で使われますが、技術の世界では区別されます。

インターネットは、世界中のコンピューターをつなぐ通信網（道路網）そのものです。その道路の上では、メール、オンラインゲーム、ビデオ通話など、さまざまなサービスが動いています。Web（World Wide Web）は、そうしたサービスのひとつで、「ページ同士がリンクでつながった文書の仕組み」として1990年ごろに生まれました。

インターネット

コンピューター同士をつなぐ世界規模の通信網。データを運ぶ「道路」にあたります。

Web

インターネットの上で動くサービスの1つ。URLで場所を示し、HTTPでやり取りし、HTMLで書かれたページを表示します。

ほかのサービス

メール、ファイル転送、オンラインゲームなども同じ道路を使いますが、Webとは別の約束事で動いています。

Webを支える技術は、突き詰めると次の3本柱です。この教材では、このうち URL と HTTP を中心に扱います（HTML は別教材「HTML学習教材」で学べます）。

  • URL — 情報が「どこにあるか」を示す住所（第2章）
  • HTTP — 情報を「どうやってやり取りするか」の約束事（第3〜8章）
  • HTML — 情報を「どう書くか」の形式（ページの中身）

用語: プロトコル

通信するうえでの「約束事」をプロトコルと呼びます。人間同士でも「電話をかけたら、まず名乗る」といった暗黙のルールがあるように、コンピューター同士も決められた手順と形式でデータを送り合います。HTTP は、Webのためのプロトコルです。

1.2 クライアントとサーバー

Webのやり取りには、必ず2つの立場が登場します。お願いをする側のクライアントと、お願いに応える側のサーバーです。レストランにたとえると分かりやすいでしょう。

Webの世界 レストランにたとえると 具体例
クライアント 注文するお客さん ブラウザ、スマホアプリ、curl コマンド
サーバー 注文を受けて料理を出す厨房 Webサーバー、APIサーバー
リクエスト 注文票（何がほしいか） 「トップページをください」
レスポンス 出てきた料理（と「品切れです」などの返事） HTMLファイル、画像、エラー通知

大事なのは、会話を始めるのはいつもクライアントだという点です。お客さんが注文しない限り、厨房から勝手に料理が出てくることはありません。Webでも、サーバーはリクエストを受け取ってはじめてレスポンスを返します。この「1回のお願いに1回の返事」という往復が、Webのすべての基本単位です。

（ブラウザ・アプリ）"] -- "リクエスト：このページをください" --> S["サーバー
（Webサーバー）"] S -- "レスポンス：はい、どうぞ（HTML）" --> C

重要ポイント

「クライアント」「サーバー」は機械の種類ではなく役割の名前です。同じコンピューターでも、ほかのサーバーにデータを取りに行くときはクライアントになります。たとえば、Webサーバーが裏で別の API サーバーに問い合わせるとき、そのWebサーバーはクライアントの立場です。

1.3 URLを入力してから表示されるまで

では、ブラウザのアドレスバーに https://example.com/ と入力して Enter キーを押したとき、何が起きているのでしょうか。細部は後の章で学ぶとして、まずは流れを4つの段階でつかみましょう。

sequenceDiagram participant B as ブラウザ participant D as DNSサーバー participant W as Webサーバー（example.com） B->>D: ①「example.com」の住所（IPアドレス）は？ D-->>B: 「93.184.215.14」です B->>W: ② 接続して暗号化の準備（HTTPS） B->>W: ③ HTTPリクエスト「GET / をください」 W-->>B: HTTPレスポンス「200 OK」＋HTML Note over B: ④ HTMLを読んで画面を組み立てる

① 住所を調べる（DNS）

「example.com」は人間向けの名前です。通信に必要な数字の住所（IPアドレス）を、DNS という電話帳のような仕組みに問い合わせます。

→ 第2章で学びます

② 接続する（TCP・TLS）

相手のサーバーと通信路をつなぎます。URL が https なら、盗み見されないよう暗号化の準備もここで行います。

→ 第2章・第8章で学びます

③ お願いと返事（HTTP）

「このページをください」というリクエストを送り、サーバーから「どうぞ」というレスポンスと一緒に HTML を受け取ります。

→ 第3〜7章で学びます

④ 画面を組み立てる（描画）

受け取った HTML を読み、文字や画像を配置して画面に表示します。ここはブラウザの内部の仕事です。

→ HTML・CSS 教材で学べます

この4段階が、たいていは1秒もかからずに終わります。普段は意識しませんが、「ページが開かない」「表示が遅い」といったトラブルは、この4段階のどこかで起きています。どの段階の問題なのかを切り分けられるようになることが、この教材の大きな目標の1つです。

図の IPアドレスについて

図中の「93.184.215.14」は説明用の一例です。IPアドレスは運用の都合で変わることがあり、あなたが調べると別の値が返ってくるかもしれません。第2章で、実際に自分の手で調べる方法を学びます。

1.4 1つのページは何回も通信している

1.3 では通信を1往復だけ描きましたが、実際のWebページはもっと多くの通信でできています。最初に受け取った HTML の中には、「この CSS も使う」「この画像も表示する」といった別ファイルへの参照が書かれており、ブラウザはそれを見つけるたびに、改めてリクエストを送るからです。

index.html（サーバーから届いたHTMLの一部） 
<!-- ブラウザはこれを見て、style.css を追加でリクエストする -->
<link rel="stylesheet" href="style.css">

<!-- 画像も1枚ずつ、別のリクエストで取りに行く -->
<img src="logo.png" alt="ロゴ">

<!-- JavaScript も同様 -->
<script src="app.js"></script>
flowchart TD A["① HTML をリクエスト"] --> B["HTML を受け取って読む"] B --> C["② style.css をリクエスト"] B --> D["③ logo.png をリクエスト"] B --> E["④ app.js をリクエスト"] E --> F["⑤ app.js がデータ（JSON）をリクエスト"] C --> G["すべてそろったら画面が完成"] D --> G F --> G

ニュースサイトやショッピングサイトでは、1ページを表示するだけで数十〜数百回のリクエストが行われることも珍しくありません。どれも仕組みは同じ「1回のお願いに1回の返事」です。図の ⑤ に登場した JSON については、次の節で説明します。

1.5 人のためのWebと、プログラムのためのWeb

ここまでは「人がブラウザでページを見る」場面を考えてきました。ところが今のWebでは、プログラム同士が同じ HTTP を使ってデータをやり取りする場面のほうが、むしろ多いくらいです。

たとえば天気予報アプリは、画面のデザインを毎回ダウンロードしているわけではありません。「東京の明日の天気」というデータだけをサーバーに問い合わせ、受け取ったデータをアプリ自身が画面に描いています。このとき、サーバー側に用意された「データを受け渡しする窓口」を Web API と呼び、受け渡すデータの書式として最もよく使われるのが JSON です。

人のためのレスポンス（HTML）

見た目を含む文書 
<h1>東京の天気</h1>
<p>明日は <strong>晴れ</strong>、
最高気温は 28℃ です。</p>

プログラムのためのレスポンス（JSON）

データだけ 
{
  "city": "東京",
  "weather": "晴れ",
  "maxTemp": 28
}

左の HTML は人が読むには便利ですが、プログラムが「最高気温はいくつか」を取り出すのは大変です。右の JSON なら、maxTemp という名前で 28 を確実に取り出せます。そして、こうした API をどういう URL とルールで提供すると使いやすいか、という設計の考え方の代表が REST です。

ここまでの話を1枚にまとめると、この教材で学ぶ内容の「地図」になります。

flowchart TD A["URL・DNS：相手を見つける（第2章）"] --> B["HTTP：お願いと返事の約束事（第3〜7章）"] B --> C["Cookie・HTTPS：状態と安全（第8章）"] B --> D["JSON：データの書き方（第9〜10章）"] C --> E["REST API：プログラム同士のつなぎ方（第11〜13章）"] D --> E E --> F["実践：APIを使うWebページ（第14章）"]

よくある勘違い

「API は特別な通信方法を使っている」と思われがちですが、Web API の通信はブラウザがページを取得するときとまったく同じ HTTP です。違うのは、返ってくる中身が HTML か JSON か、という点だけです。だからこそ、HTTP をしっかり理解すれば API もすぐに扱えるようになります。

やってみよう 1-1: 1ページで何回通信しているか数えてみよう

ブラウザに備わっている「開発者ツール」を使うと、目に見えない通信を一覧で確認できます。詳しい使い方は第7章で学ぶので、ここでは眺めるだけで構いません。

手順

  1. 1 Chrome または Edge で新しいタブを開き、F12 キーを押して開発者ツールを開く（Mac は Option+Command+I）。
  2. 2 上部のタブから Network（ネットワーク）を選ぶ。

理解度確認クイズ

  1. Q1. 「インターネット」と「Web」の違いを簡単に説明してください。

    回答を表示

    インターネットはコンピューター同士をつなぐ世界規模の通信網（道路）で、Web はその上で動くサービスの1つです。Web は URL・HTTP・HTML を使って、リンクでつながったページを閲覧する仕組みです。

  2. Q2. Webのやり取りで、会話を始めるのはクライアントとサーバーのどちらですか。

    回答を表示

    クライアントです。クライアントがリクエストを送り、サーバーはそれを受け取ってはじめてレスポンスを返します。

  3. Q3. ブラウザに URL を入力してから画面が表示されるまでの4つの段階を、順に挙げてください。

    回答を表示

    ① DNS でドメイン名から IPアドレスを調べる → ② サーバーに接続する（HTTPS なら暗号化の準備も） → ③ HTTP でリクエストを送りレスポンス（HTML）を受け取る → ④ ブラウザが HTML を読んで画面を組み立てる。

  4. Q4. Web API の通信は、ブラウザがWebページを取得する通信と何が同じで、何が違いますか。

    回答を表示

    どちらも同じ HTTP を使ったリクエストとレスポンスの往復である点は同じです。違うのは返ってくる中身で、Webページは人が読むための HTML、Web API はプログラムが扱いやすいデータ（多くは JSON）を返します。
