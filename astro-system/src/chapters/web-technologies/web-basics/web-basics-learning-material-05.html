ステータスコード

レスポンスの先頭には、必ず 3桁の数字 が付いています。この数字は「注文はうまくいきましたか、それとも何か問題がありましたか」という厨房からの返事の要約です。この章では、この3桁の数字の読み方と、よく出てくるコードの意味を学びます。

この章で学ぶこと

  • ステータスコードが1xx〜5xxの5つに分類されることを説明できる
  • 200・201・204・301・302・304 など頻出コードの違いを説明できる
  • 400・401・403・404・409・422・429 の違い、特に401と403の違いを説明できる
  • 4xx と 5xx の意味の違いから、トラブル時にまずどこを調べるべきか見当をつけられる

5.1 ステータスコードとは

第3章で見たとおり、レスポンスの1行目（ステータス行）には HTTP/1.1 200 OK のように、3桁の数字と、それに続く短い言葉（理由句）が書かれています。この3桁の数字がステータスコードです。

レスポンスの1行目 
HTTP/1.1 200 OK

レストランのたとえで言えば、ステータスコードは厨房からの一言メモです。「お待たせしました」「品切れです」「ご注文の内容が読み取れません」など、細かい理由を毎回文章で説明する代わりに、あらかじめ決められた3桁の番号で結果を伝えます。番号なら、人間もプログラムも一瞬で結果を判断できます。

理由句（OK や Not Found など）は人間が読むための補足で、機械的な判断には数字そのものが使われます。プログラムは「200番台なら成功」「400番台ならリクエストを見直す」というように、数字だけを見て処理を分岐させます。

理由句は自由に変えられる

理由句の文言はサーバーの実装によって変わることがあり、必ずしも標準どおりとは限りません。判断材料にすべきは数字のほうで、理由句は人間向けの目印程度に考えましょう。

5.2 5つの分類

3桁のうち、先頭の1桁を見るだけで、おおまかな結果が分かります。ステータスコードは先頭の数字によって5つのグループに分かれています。

分類 大まかな意味 代表例
1xx 情報 リクエストを受け取り、処理を続けているという途中経過 100 Continue
2xx 成功 リクエストは正常に処理された 200 OK
3xx リダイレクト 続きは別の場所を見てほしい（完了には追加の動作が必要） 301 Moved Permanently
4xx クライアントエラー リクエストに誤りがあるらしく、そのままでは処理できない 404 Not Found
5xx サーバーエラー 一見正しいリクエストを、サーバー側で処理できなかった 500 Internal Server Error

覚え方はシンプルです。2xx は「うまくいった（成功）」、4xx は「そのご注文は、このままではお受けできません」（注文の内容や宛先に問題があるらしい）、5xx は「ご注文は正しそうなのに、厨房（サーバー）側で作れませんでした」。この3つさえ押さえれば、日常でよく出会うコードの大半は判断できます。1xx と 3xx は、慣れてきたら押さえれば十分です。

重要ポイント

4xx と 5xx は「どちらが悪いか」という責任を表す分類ではありません。4xx は「リクエストに誤りがあるらしく、そのままでは処理できない」、5xx は「一見正しいリクエストを、サーバー側で処理できなかった」という意味の分類です。たとえば 404 は URL の打ち間違いでも、サーバー側でデータが削除された・設定を誤ったときでも返りますし、403 がサーバー側の権限設定のミスで返ることもあります。トラブル対応では、4xx ならまず送ったリクエストを、5xx ならまずサーバー側の状況を確認する、という調べ始める場所の目安として使いましょう。

5.3 2xx と 3xx

まずは「良い知らせ」を運ぶ2xxと、「もう一度別の場所を見てほしい」と伝える3xxを見ていきます。

200 OK

最も基本的な成功。リクエストどおりに処理が完了し、レスポンスボディにデータが入っている。

201 Created

POSTなどで新しいリソースが作られたときの成功。第4章の投稿作成はこれに当たる。

204 No Content

成功したがボディが空。DELETE や、返す内容が特にない更新でよく使われる。

3xx は「引っ越し先の案内」です。サーバーは自分で処理せず、Location ヘッダー（第6章で詳しく学びます）で示した場所へ、クライアントにもう一度リクエストし直してもらうよう促します（ただし 304 は例外で、転送ではなくキャッシュの確認に使われます）。

コード 名前 用途
301 Moved Permanently URLが恒久的に変わった（引っ越し先を覚えてよい）
302 / 307 Found / Temporary Redirect 一時的な転送（次は元のURLに戻るかもしれない）。307 はメソッドとボディを変えずに転送する
304 Not Modified 更新なし。手元のキャッシュをそのまま使ってよい（第6章で詳説）
308 Permanent Redirect 301と同じ恒久転送だが、メソッドとボディを変えずに転送する

5.4 4xx（クライアントエラー）

4xx はブラウザやアプリを使っていて最もよく遭遇するエラーです。原因の多くは、リクエストの内容・URL・認証情報のいずれかにあります。

コード 名前 典型的な原因
400 Bad Request リクエストの形式が壊れている（JSONの文法ミスなど）
401 Unauthorized そもそも誰か分からない（未ログイン・認証情報なし／誤り）
403 Forbidden 誰かは分かるが権限がない（一般会員が管理者ページへ）
404 Not Found 指定したURL・リソースが存在しない
405 Method Not Allowed そのURLではそのメソッドを受け付けていない
409 Conflict 現在の状態と矛盾する（同じ名前が既に使われている等）
422 Unprocessable Content（旧名 Unprocessable Entity） 形式は正しいが内容が業務ルールに反する（必須項目の欠落等）
429 Too Many Requests 短時間に送りすぎ（レート制限。しばらく待って再試行）

中でも間違えやすいのが 401 と 403 の違いです。401は「あなたが誰なのか証明できていない」、403は「あなたが誰なのかは分かったが、その操作は許可されていない」という違いがあります。空港の保安検査にたとえると、401は身分証を確認できない状態、403は身分証は確認できたが搭乗券がない（入れない）状態です。

401 は「未認証」であって「未ログイン」限定ではない

API では、Authorizationヘッダー（第8章）が無い・期限切れ・値が間違っている場合にも401が返ります。ログイン画面がなくても、APIキーやトークンを渡し忘れると401になることを覚えておきましょう。

5.5 5xx（サーバーエラー）とトラブルの切り分け

5xx は、一見正しいリクエストを、サーバー側で処理できなかったことを示します。多くの場合、クライアント側でリクエストの内容を直しても解決しないため、時間をおいて再試行したり、サーバーの管理者に知らせたりすることになります。

コード 名前 典型的な原因
500 Internal Server Error サーバー内部のプログラムでエラーが発生（バグ等）
502 Bad Gateway 中継サーバーが、奥のサーバーから不正な返事を受け取った
503 Service Unavailable メンテナンス中・アクセス集中で一時的に応答できない
504 Gateway Timeout 中継サーバーが、奥のサーバーからの返事を時間内に受け取れなかった

実際にトラブルに遭遇したときは、返ってきたステータスコードの先頭1桁を見るだけで、まずどこから調べるかの見当がつきます。

flowchart TD A["エラーが発生した"] --> B{"何xx？"} B -->|"4xx"| C{"401 or 403？"} C -->|"はい"| D["認証情報（ログイン・トークン）と権限を確認する"] C -->|"いいえ"| E["URL・メソッド・送信内容を見直す"] B -->|"5xx"| F["まずサーバー側の状況を確認
時間をおいて再試行 or サーバー管理者へ連絡"] B -->|"それ以外"| G["3xxはリダイレクト先を確認"]

この図はあくまで「調べ始める場所」の目安です。4xx でもサーバー側の設定ミス（URL の割り当てや権限設定の誤りなど）が原因のことがあり、5xx でも特定の入力のときだけサーバーのバグが表に出ている、ということもあります。当たりをつけたら、実際のリクエストとレスポンスの中身（第7章）やエラーメッセージを見て確かめましょう。

503 と 504 を混同しない

503は「サーバーが今は応答できない状態」、504は「途中の中継サーバーが待ちきれずタイムアウトした」という違いがあります。どちらも自分のリクエストを直しても解決しないため、時間をおいて再試行するのが基本です。

やってみよう 5-1: httpbin.org でステータスコードを見比べる

httpbin.org には、指定した番号のステータスコードをそのまま返してくれる便利なエンドポイントがあります。ブラウザと curl の両方で確認してみましょう。

手順

  1. 1 ブラウザで https://httpbin.org/status/404 を開き、表示された画面と、開発者ツールの Network タブでステータスを確認する。
  2. 2 ターミナルで下のコマンドを実行し、-i オプションでレスポンスヘッダー込みの出力を見る。
  3. 3 404 の部分を 500・301・429 に変えて実行し、返ってくるステータス行を比べる。
ターミナル 
# -i でレスポンスヘッダーも含めて表示する
curl -i https://httpbin.org/status/404

# Windows は curl.exe と打つ場合がある（第7章で詳説）

続けて、「記事一覧を表示 → 200」「未ログインで会員限定ページ → 401」「他人の投稿を削除しようとして拒否 → 403」「存在しないIDで検索 → 404」のように、身近な場面とコードを自分なりに対応させてみましょう。

理解度確認クイズ

  1. Q1. ステータスコードの先頭の数字が「4」と「5」では、それぞれどのような意味の分類ですか。また、トラブル時にまず確認するのはどこですか。

    回答を表示

    4xx は「リクエストに誤りがあるらしく、そのままでは処理できない」、5xx は「一見正しいリクエストを、サーバー側で処理できなかった」という分類です。まず確認するのは、4xx なら送ったリクエスト（URL・メソッド・認証情報・送信内容）、5xx ならサーバー側の状況です。ただし、これは調べ始める場所の目安であって、どちらの責任かを決めるものではありません。

  2. Q2. 401 Unauthorized と 403 Forbidden の違いを説明してください。

    回答を表示

    401は誰であるかを証明できていない（未認証）状態、403は誰であるかは分かっているがその操作を行う権限がない状態です。

  3. Q3. 新しい投稿をPOSTで作成し、無事に登録できたとき、返ってくる可能性が高いステータスコードは何番ですか。

    回答を表示

    201 Created です。新しいリソースが作成されたことを表します。

  4. Q4. 存在しないURLにアクセスしたときに返るのは何番のコードですか。また、429はどのような状況で返りますか。

    回答を表示

    存在しないURLには 404 Not Found が返ります。429 Too Many Requests は、短時間にリクエストを送りすぎてレート制限にかかったときに返ります。

  5. Q5. APIから 503 Service Unavailable が返ってきました。リクエストの内容を書き直せば解決しますか。

    回答を表示

    解決しません。503 は、メンテナンスやアクセス集中のためにサーバーが一時的にリクエストを処理できない状態を表すコードで、リクエストの書き方が原因ではないからです。時間をおいて再試行するか、サーバー側の復旧を待つ必要があります。
