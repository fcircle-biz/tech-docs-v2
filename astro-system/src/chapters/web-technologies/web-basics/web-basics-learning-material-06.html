ホーム Webの仕組み 第6章
第6章 所要時間: 約45分

HTTPヘッダーとボディ

第3章では、リクエストとレスポンスが「開始行・ヘッダー・空行・ボディ」でできていることを学びました。この章では、その中のヘッダーにもう一歩踏み込みます。ヘッダーは通信の「付帯情報」を運ぶ部分で、Content-Type によるデータ形式の指定、Accept によるやり取りの調整、そして再取得を省くキャッシュの仕組みまで、多くの役割を担っています。

この章で学ぶこと

  • ヘッダーが「名前: 値」の形式で書かれることを説明できる
  • Content-Type と MIMEタイプの役割を説明できる
  • Accept によるコンテンツ交渉の考え方が分かる
  • よく使うヘッダーの名前と役割を挙げられる
  • Cache-Control・ETag によるキャッシュの仕組みを説明できる

6.1 ヘッダーとは

ヘッダーは、HTTPメッセージの開始行のすぐ後ろに並ぶ「名前: 値」の行のことです。本文（ボディ）そのものではなく、「本文は何のデータか」「どのくらいの大きさか」「誰からのリクエストか」といった付帯情報を運びます。手紙にたとえるなら、便箋の中身（本文）に対して、封筒に書かれた宛先・差出人・切手のような情報がヘッダーです。

リクエストのヘッダー部分 
GET /users/1 HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0
Accept: application/json
Accept-Language: ja

ヘッダーには、リクエストに付くものをリクエストヘッダー、レスポンスに付くものをレスポンスヘッダーと呼びます。どちらも同じ「名前: 値」の形式で、1行に1つのヘッダーを書きます。

ヘッダー名は大文字・小文字を区別しない

Content-Type と content-type は同じヘッダーとして扱われます。ブラウザや curl の出力ではハイフン区切りの単語ごとに先頭が大文字（Content-Type）で表示されることが多いですが、これは見やすさのための慣習で、決まりではありません。

6.2 Content-Type と MIMEタイプ

数あるヘッダーの中でも特に重要なのが Content-Type です。「この本文（ボディ）は、どんな種類のデータか」を表し、受け取った側はこの値を見てから中身の解釈のしかたを決めます。値には MIMEタイプと呼ばれる「大分類/小分類」の書式を使います。

MIMEタイプ 意味 主な用途
text/html HTML文書 Webページの本体
application/json JSON形式のデータ Web APIのやり取り（第9〜13章）
image/png PNG画像 画像ファイル（jpeg・gif等も同様）
application/x-www-form-urlencoded フォームの値をkey=value&...で並べたもの HTMLフォームの標準送信形式
multipart/form-data 複数のデータ（ファイル含む）を分割して送る形式 ファイルアップロードを含むフォーム

文字を扱う MIMEタイプには、文字コードを示す charset=utf-8 が付くことがよくあります。

レスポンスヘッダーの例 
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 39

{"city": "東京", "weather": "晴れ"}

Content-Type を間違えると解釈を誤る

JSONを送っているのに Content-Type: text/plain のままだと、受け取った側が「ただの文字列」と解釈し、JSONとして正しく処理してくれないことがあります。第12章のAPI呼び出しでも、JSONを送るときは必ず Content-Type: application/json を指定します。

6.3 コンテンツ交渉

Content-Type がサーバーから見た「これを送ります」の宣言だとすれば、Accept はクライアントから見た「こういう形式が欲しいです」という希望です。同じURLでも、クライアントの希望に応じてサーバーが返す形式を変える仕組みをコンテンツ交渉と呼びます。

Accept

欲しいデータ形式。例: application/json

Accept-Language

欲しい言語。例: ja（日本語優先）

Accept-Encoding

対応できる圧縮方式。例: gzip

たとえば Accept-Encoding: gzip を送ると、サーバーは対応していれば本文を gzip 圧縮してから返し、レスポンスに Content-Encoding: gzip を付けます。データ量が小さくなるため、通信が速くなります。ブラウザはこの展開を自動で行うため、私たちが意識することはほとんどありません。

6.4 よく使うヘッダー一覧表

ヘッダーの種類は数十以上ありますが、まずはこの表に挙げるものを覚えておけば、開発者ツールやcurlの出力を読むときに困りません。

ヘッダー 向き 役割
Host リクエスト 接続先のホスト名（第2章）。1台のサーバーで複数サイトを区別するのに必須
User-Agent リクエスト クライアントの種類（ブラウザ名・OS・curlのバージョン等）
Authorization リクエスト 認証情報（トークン等）を渡す。詳しくは第8章
Referer リクエスト 直前にいたページのURL（スペルが歴史的に Referrer ではない点に注意）
Content-Length 両方 本文のバイト数。受け取り側が「どこまでが本文か」を知る手がかり
Location レスポンス リダイレクト先や、作成したリソースのURL（第5章の3xx・201）
Set-Cookie レスポンス クライアントにCookieを保存させる。詳しくは第8章
Server レスポンス サーバーソフトウェアの名前（セキュリティ上、隠すサイトも多い）

重要ポイント

ヘッダーを全部暗記する必要はありません。「このヘッダーは何のためにあるのか」を、開発者ツールやcurlの出力を見るたびに1つずつ調べる習慣があれば十分です。第7章で、実際にこれらのヘッダーを自分の目で確認します。

6.5 キャッシュ

1.4 で見たように、1つのページは画像やCSSなど多数のファイルを読み込みます。これらを毎回サーバーから取り直すのは無駄が多いため、ブラウザは一度取得したファイルを手元に保存しておき、次回は再利用します。これがキャッシュで、サーバー側はレスポンスヘッダーでキャッシュのルールを指示します。

Cache-Control

キャッシュの可否と有効期限を指定します。max-age=3600 なら「3600秒（1時間）は再取得せず使い回してよい」、no-store なら「保存しないで」という意味です。

ETag

ファイルの内容に対する「指紋」のような文字列です。内容が変わればETagの値も変わるため、変化の有無を確認するのに使えます。

有効期限が切れた後も、ブラウザはいきなり全部を取り直すわけではありません。If-None-Match ヘッダーに手元のETagを添えて「これと同じなら送らなくていいですよ」と問い合わせ、内容が変わっていなければサーバーは本文なしの 304 Not Modified（第5章）を返します。

sequenceDiagram participant B as ブラウザ participant S as サーバー B->>S: ① GET /style.css S-->>B: 200 OK（ETag: "abc123"、本文あり） Note over B: キャッシュに保存 B->>S: ② GET /style.css
If-None-Match: "abc123" S-->>B: 304 Not Modified（本文なし） Note over B: 保存済みのファイルをそのまま使う

304のレスポンスは本文を含まないため、通信量を大きく減らせます。「サーバーに問い合わせているのに毎回速い」と感じるページの多くは、この仕組みの恩恵を受けています。

「更新したのに反映されない」の正体

画像やCSSを更新したのにブラウザの表示が変わらない場合、古いキャッシュが使い回されていることがよくあります。開発者ツールの Disable cache（第7章）を有効にすると、キャッシュを使わず常に最新を取得できます。

やってみよう 6-1: 自分のブラウザが送るヘッダーを見てみよう

httpbin.org という「送ったリクエストをそのまま返すサービス」を使うと、自分のブラウザが普段どんなヘッダーを送っているのかを確認できます。

手順

  1. 1 ブラウザで https://httpbin.org/headers を開く。
  2. 2 画面に表示されたJSONの中から Accept・Accept-Language・User-Agent の値を見つける。
  3. 3 6.3 で学んだ内容と照らし合わせ、それぞれの値が何を意味しているか考える。

User-Agent の値はブラウザやOSによって異なります。同じサイトを別のブラウザで開いて見比べると、違いがよく分かります。

理解度確認クイズ

  1. Q1. Content-Type ヘッダーは何を表すヘッダーですか。

    回答を表示

    本文（ボディ）がどんな種類のデータであるかを、MIMEタイプ（例: application/json、text/html）で表すヘッダーです。受け取った側はこの値を見て中身の解釈のしかたを決めます。

  2. Q2. Content-Type と Accept の違いを説明してください。

    回答を表示

    Content-Type は「この本文は何の形式か」という送る側からの宣言で、Accept は「こういう形式が欲しい」というクライアントからの希望です。Accept などの希望をもとにサーバーが返す形式を選ぶ仕組みをコンテンツ交渉と呼び、選んだ結果が Content-Type で示されます。

  3. Q3. ブラウザが同じファイルを再取得せずに使い回せる理由を、ヘッダー名を挙げて説明してください。

    回答を表示

    サーバーが Cache-Control で有効期限を指定しているためです。有効期限内はブラウザが保存したファイルをそのまま使い、期限が切れても ETag と If-None-Match を使って変化がなければ 304 Not Modified を受け取り、本文なしで使い回せます。

  4. Q4. 304 Not Modified が返ってきたとき、レスポンスの本文はどうなっていますか。

    回答を表示

    本文は含まれません。内容に変化がないことをサーバーが伝えるだけのレスポンスで、ブラウザは手元に保存済みのファイルをそのまま使います。
