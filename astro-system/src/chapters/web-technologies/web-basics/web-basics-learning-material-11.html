Web APIとRESTの考え方

ここまでの章で、HTTP（リクエストとレスポンスの約束事）と JSON（データの書き方）を学びました。この章では、その2つを組み合わせて「プログラム同士が会話するための窓口」である Web API を扱います。特に、その代表的な設計スタイルである REST の考え方を理解し、次章から実際に API を呼び出す準備を整えます。

この章で学ぶこと

  • Web API がどのような役割を果たすか説明できる
  • 「リソース」を URI で表し、HTTPメソッドで操作するという考え方が分かる
  • REST の設計原則を挙げられる
  • RPC 形式や GraphQL など、REST以外のスタイルとの違いを概要レベルで説明できる

11.1 APIとは

API（Application Programming Interface）とは、あるプログラムが持つ機能やデータを、別のプログラムから使えるようにする「窓口」です。第1章のレストランのたとえで言えば、お客さんが厨房に直接入って調理するのではなく、メニューを見て「これをください」と注文するように、決められた呼び出し方が用意されています。

API には大きく2種類あります。プログラミング言語の中で関数として呼び出すライブラリAPI（例: JavaScript の Array.sort()）と、ネットワーク越しに HTTP で呼び出すWeb APIです。この教材で扱うのは後者で、呼び出す側と応える側が別のコンピューターにあり、第3〜8章で学んだ HTTP の仕組みがそのまま使われます。

ライブラリAPI

同じプログラムの中で関数やメソッドを呼び出す。通信は発生しない。

Web API

ネットワーク越しに HTTP で呼び出す。この教材ではこちらを扱う。

用語: Web API

この教材では「Web API」を半角スペースありで表記します。「HTTP でアクセスできるデータ・機能の窓口」という意味で使い、単に「API」と略すこともあります。

11.2 Web APIの利用例

Web API は、私たちの身の回りのいたるところで使われています。スマホの天気アプリは気象情報を提供する Web API を、地図アプリは地図データの Web API を呼び出しています。ネットショップの決済画面では、決済代行会社の Web API に金額やカード情報を渡して処理を依頼します。社内システムでも、勤怠管理システムと給与計算システムが Web API 経由でデータを連携する、といった使い方が一般的です。

こうした Web API の広がりを支えているのが、フロントエンドとバックエンドの分離という考え方です。画面を描く役割（フロントエンド）と、データを管理し処理する役割（バックエンド）を分け、両者を Web API でつなぎます。こうすると、同じバックエンドに対して、スマホアプリ・Webブラウザ・別会社のシステムなど、複数の「窓口の利用者」を用意できます。

第14章では、実際に自分の書いた HTML と JavaScript（フロントエンド）から、既存の Web API（バックエンド）を呼び出す小さなページを作ります。

11.3 リソースとURI

Web API を設計するときの基本的な考え方は、扱う対象をリソース（資源）として捉えることです。リソースとは「投稿」「ユーザー」「商品」のような、操作の対象となる名詞です。第4章で「メソッドは動詞」と学びましたが、リソースはその動詞が作用する対象、つまり名詞にあたります。

リソースは URI（第2章で学んだ URL とほぼ同じ意味で使われます）で表します。複数のリソースをまとめたコレクションと、その中の1件を指す個別リソースを区別するのが基本です。

URI 意味 分類
/posts 投稿の一覧すべて コレクション
/posts/1 id が 1 の投稿1件 個別リソース
/posts/1/comments 投稿1に紐づくコメント一覧 ネストしたコレクション

/posts/1/comments のように URI を親子関係でネストさせると、「投稿1に属するコメント」という関係を URI だけで表現できます。次章で実際に使う JSONPlaceholder という練習用 API も、このパターンで設計されています。

重要ポイント

URI には「何をするか」（動詞）を入れず、「何を対象にするか」（名詞）だけを入れます。「何をするか」は、次の11.4で学ぶHTTPメソッドが表します。URIとメソッドの役割分担が、REST の考え方を取り入れた API 設計の出発点です。

11.4 REST の原則

REST（Representational State Transfer）は、Roy Fielding氏が2000年に発表した博士論文の中で提唱した、Web のような分散システムのための設計スタイル（アーキテクチャスタイル）で、現在は Web API の設計指針として広く使われています。特定の製品や規格ではなく、「Webをうまく使うための設計の考え方」だと捉えてください。REST の原則に沿った API はRESTfulと呼ばれます。代表的な原則は次の通りです。

  • クライアント/サーバー — 画面の役割（クライアント）とデータ・処理の役割（サーバー）を分ける（11.2 と同じ考え方）
  • ステートレス — サーバーはリクエスト間で会話の状態を覚えない（第3章で学んだ通り）。必要な情報は毎回リクエストに含める
  • 統一インターフェース — どのリソースとも同じ決まった方法でやり取りする。Fielding氏の論文では、①リソースを識別子（URI）で指す、②リソースの「表現」（JSON などのデータ）を通じて操作する、③メッセージだけで意味が分かる（自己記述的メッセージ）、④レスポンスに含まれるリンクをたどって次の操作に進む（HATEOAS）、という4つの制約で定義されている
  • キャッシュ可能 — レスポンスをキャッシュしてよいかどうかを明示する（第6章の Cache-Control 等）
  • 階層化 — クライアントは、間にロードバランサーやキャッシュサーバーが挟まっていても意識しなくてよい

この教材で扱う「REST」の範囲

現在「REST API」と呼ばれている API の多くは、Fielding氏が定義した制約をすべて満たしているわけではなく、特に④の HATEOAS まで実装している例は多くありません。本教材では、REST のすべての制約を実装するのではなく、現在一般的な HTTP API 設計の入門として、「リソースを URI で表し、HTTPメソッドで操作する」ことを中心に扱います。

実務でいちばん意識するのは、統一インターフェースのうち「リソースを URI で指し、決まったメソッドで操作する」部分です。現在一般的な HTTP API では、URI（名詞）と HTTPメソッド（動詞）を組み合わせるだけで、システムに対する基本操作（CRUD: Create・Read・Update・Delete）を表現します。

CRUD HTTPメソッド URI の例
Create（作成） POST /posts
Read（読み取り） GET /posts または /posts/1
Update（更新） PUT・PATCH /posts/1
Delete（削除） DELETE /posts/1

同じ /posts/1 という URI でも、メソッドを変えるだけで「読む」「更新する」「削除する」を切り替えられます。これが第4章で学んだメソッドの知識と、11.3 のリソースの考え方をつなぐ、REST の考え方を取り入れた HTTP API 設計の中心的なアイデアです。

11.5 REST以外のスタイル

REST は広く使われていますが、Web API の設計スタイルはそれだけではありません。ここでは代表的な2つを概要だけ紹介します。名前を知っておけば、現場で見かけたときに戸惑わずに済みます。

RPC（Remote Procedure Call）形式は、「リモートの手続き（関数）を呼び出す」という考え方です。URIに動詞を含め、/getUser?id=1 や /deletePost のように、関数呼び出しに近い形で表現します。REST がリソース（名詞）を中心に据えるのに対し、RPC は「何をするか」（動詞）を URI に直接書く点が対照的です。

GraphQL は、クライアントが「欲しいデータの形」を1つのリクエストで指定できる仕組みです。REST では画面に必要なデータを揃えるために複数のエンドポイントを呼ぶことがありますが、GraphQL では1回のリクエストで必要な項目だけをまとめて取得できます。

なお、gRPC という名前も見かけることがありますが、これはGraphQLとは別の技術で、Googleが開発した高速な通信の仕組み（サーバー同士の内部連携などで使われる）です。名前が似ているため混同しないようにしましょう。

スタイル 基本の考え方 URI の例
REST リソース（名詞）をURI・メソッドで操作 GET /users/1
RPC形式 手続き（動詞）を直接呼び出す GET /getUser?id=1
GraphQL 欲しいデータの形を1回のリクエストで指定 POST /graphql

この教材では REST を扱います

現時点でもっとも広く使われているのが REST（またはそれに近い設計）です。次の第12章では REST API を実際に呼び出し、第13章では REST API を設計する視点を学びます。RPC や GraphQL はここでは名前を知っておくだけで十分です。

やってみよう 11-1: 「図書館システム」のリソースを設計してみよう

架空の「図書館システム」を題材に、REST の考え方でリソースと操作を洗い出してみましょう。扱う対象は「本」「利用者」「貸出（本と利用者を結びつける記録）」の3つです。

手順

  1. 1 「本」「利用者」「貸出」のそれぞれについて、コレクションのURI（例: /books）を考える。
  2. 2 「本を1冊登録する」「利用者一覧を見る」「本を1冊削除する」という3つの操作それぞれに、メソッドとURIの組を割り当てる。
  3. 3 「利用者1が借りている本の一覧を見る」という操作を、11.3 のネストの考え方を使って表してみる（/users/1/... の形）。
  4. 4 表（メソッド・URI・意味の3列）にまとめる。

解答例: 「本を1冊登録する」は POST /books、「本を1冊削除する」は DELETE /books/1、「利用者1が借りている本の一覧」は GET /users/1/loans のように表せます。動詞をURIに入れず、名詞＋メソッドで表現できているかを確認しましょう。

理解度確認クイズ

  1. Q1. ライブラリAPIとWeb APIの違いを説明してください。

    回答を表示

    ライブラリAPIは同じプログラムの中で関数やメソッドを呼び出す仕組みで通信は発生しません。Web APIはネットワーク越しにHTTPで呼び出す仕組みで、別のコンピューター上のサーバーとやり取りします。

  2. Q2. REST の設計では、URIには何を表し、HTTPメソッドには何を表しますか。

    回答を表示

    URIは操作の対象となる「リソース」（名詞）を表し、HTTPメソッドはそのリソースに対して「何をするか」（動詞）を表します。この役割分担が、REST の統一インターフェースの考え方を取り入れた、一般的な HTTP API 設計の基本です。

  3. Q3. REST を最初に提唱したのは誰で、いつのことですか。

    回答を表示

    Roy Fielding氏が2000年に発表した博士論文の中で提唱しました。特定の製品ではなく、Webをうまく使うための設計スタイル（考え方）です。

  4. Q4. /posts/1/comments という URI は、どのような関係を表していますか。

    回答を表示

    id が 1 の投稿に紐づくコメントの一覧、という親子関係（ネスト）を表しています。URIの階層だけで「どのリソースに属するか」を表現できます。

  5. Q5. REST と RPC 形式の URI の作り方は、どのように異なりますか。

    回答を表示

    RESTはリソース（名詞）をURIに置き、動詞はHTTPメソッドで表します（例: GET /users/1）。RPC形式はURIに動詞を直接含め、関数呼び出しに近い形で表します（例: GET /getUser?id=1）。
