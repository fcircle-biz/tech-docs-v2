HTTPメソッド

前章で、リクエストには GET /index.html HTTP/1.1 のように先頭に「動詞」が付くことを見ました。この GET の部分がHTTPメソッドです。この章では、メソッドが何を意味し、どう使い分けるのかを学びます。

この章で学ぶこと

  • 主要な HTTPメソッド（GET・POST・PUT・PATCH・DELETE・HEAD・OPTIONS）の用途を説明できる
  • GET と POST の違い（クエリとボディ、機密情報の扱い）を説明できる
  • PUT・PATCH・DELETE の使い分けが分かる
  • 「安全性」と「冪等性」という2つの性質を説明できる

4.1 メソッドは「動詞」

URL が「どのデータに対して」という名詞（対象・リソース）を表すのに対し、HTTPメソッドは「そのデータに対して何をしてほしいか」という動詞を表します。同じ URL でも、メソッドを変えるだけでサーバーに依頼する内容がまったく変わります。

リクエスト 日本語にすると
GET /posts/1 「投稿1番を見せて」
POST /posts 「新しい投稿を作って」
DELETE /posts/1 「投稿1番を削除して」
flowchart LR A["URL（名詞）
/posts/1"] --- B{"メソッド（動詞）"} B -->|GET| C["見せて"] B -->|POST| D["作って"] B -->|PUT・PATCH| E["直して"] B -->|DELETE| F["消して"]

用語: エンドポイント

「メソッド＋URL」の組み合わせ（例: GET /posts/1）をエンドポイントと呼びます。Web API のドキュメントには、たいていエンドポイントの一覧が載っています。

4.2 GET と POST

もっともよく使われるのが GET と POST です。HTML の <form> タグにも method 属性としてこの2つが登場します。

観点 GET POST
用途 データを取得する データを新しく送る・作る
データの場所 URL のクエリパラメータ（?key=value） ボディ（本文）の中
ブラウザ履歴・ブックマーク URL ごと残る 残らない
データ量の目安 URL の長さの制限を受ける 大きなデータも送れる

GET に機密情報を載せない

GET のクエリパラメータは URL の一部なので、ブラウザの履歴・サーバーのアクセスログ・共有した URL にそのまま残ります。パスワードやカード番号のような機密情報は、GET のクエリには絶対に載せず、POST のボディで（さらに HTTPS で暗号化して）送ります。

HTML フォームで確認してみましょう。method="get" の検索フォームを送信すると、入力値が URL に付きます。

search.html 
<!-- 送信すると URL が /search?q=web+api になる -->
<form method="get" action="/search">
  <input type="text" name="q">
  <button type="submit">検索</button>
</form>

4.3 PUT・PATCH・DELETE

すでにあるデータを更新・削除するときは、PUT・PATCH・DELETE を使います。PUT と PATCH はどちらも「更新」ですが、更新の範囲が異なります。

PUT（全体を置き換える）

送ったデータで丸ごと上書きします。省略した項目は消えることがあります。

PATCH（一部だけ直す）

送った項目だけを更新します。ほかの項目はそのまま残ります。

「タイトルだけ直したい」場面で PUT を使うと、うっかり本文まで消してしまう事故につながります。同じ投稿データを例に、違いを見比べましょう。

PUT /posts/1（全項目を送る）

request-put.json 
{
  "title": "新しいタイトル",
  "body": "本文もすべて再送する",
  "userId": 1
}

PATCH /posts/1（変える項目だけ）

request-patch.json 
{
  "title": "新しいタイトル"
}

削除は DELETE です。DELETE /posts/1 のように、削除したい対象を URL で指定するだけで、ボディは通常不要です。

4.4 HEAD・OPTIONS

ここまでの5つ（GET・POST・PUT・PATCH・DELETE）に加え、裏方として使われる2つのメソッドも押さえておきましょう。

メソッド 動作 使いどころ
HEAD GET と同じだが、ボディを返さずヘッダーだけ返す ファイルの存在確認や更新日時のチェックだけしたいとき
OPTIONS そのURLで使えるメソッド一覧などを問い合わせる ブラウザが安全確認のために自動送信することが多い

プリフライトは第14章で

JavaScript から別サイトの API を呼ぶとき、ブラウザが本番のリクエストの前に自動で OPTIONS を送って安全性を確認することがあります。これをプリフライトリクエストと呼び、CORS（第14章）で詳しく扱います。

4.5 安全性と冪等性

メソッドを正しく使い分けるうえで欠かせないのが、安全性と冪等性（べきとうせい）という2つの性質です。

安全性（Safe）

何度呼び出してもサーバーの状態を変えないこと。読み取り専用の操作が該当します。

冪等性（Idempotent）

同じリクエストを何回送っても、サーバーに与える効果（最終的な状態）が1回送ったときと変わらないこと。返ってくるレスポンスまで同じとは限りません。安全なメソッドは、すべて冪等でもあります。

メソッド 安全 冪等
GET / HEAD / OPTIONS はい はい
PUT いいえ はい
DELETE いいえ はい
POST いいえ いいえ
PATCH いいえ いいえ（場合による）

DELETE が「冪等」とされるのは少し不思議に感じるかもしれません。1回目に削除して 204、2回目は「もう無い」ので 404 が返りますが、「そのデータが存在しない」という最終的な状態は何回呼んでも同じだからです。

重要ポイント: POST の二重送信に注意

POST は冪等ではないため、「投稿する」ボタンを2回押すと投稿が2件作られるおそれがあります。通信が遅いときに焦って連打すると起きやすい事故です。フォームのボタンを送信後に無効化するなど、アプリ側の工夫が必要になります。

やってみよう 4-1: 場面に合うメソッドを選ぼう

ブログサービスを操作する、次の4つの場面に最も適した HTTPメソッドを考えてみましょう。

  1. 1 記事の一覧ページを見る
  2. 2 新しい記事を投稿する
  3. 3 投稿済みの記事のタイトルだけを直す
  4. 4 不要になった記事を削除する

答え: 1=GET /posts、2=POST /posts、3=PATCH /posts/{id}（タイトルだけなら全体を送り直す PUT より PATCH が自然）、4=DELETE /posts/{id}。余裕があれば https://httpbin.org/post に対して、ブラウザのアドレスバーからではなく後の章で学ぶ curl や開発者ツールを使って POST を送る様子を想像してみましょう。

理解度確認クイズ

  1. Q1. GET のクエリパラメータにパスワードを載せてはいけないのはなぜですか。

    回答を表示

    クエリパラメータは URL の一部なので、ブラウザの履歴やサーバーのアクセスログ、共有した URL にそのまま残ってしまい、第三者に見られる危険があるためです。

  2. Q2. PUT と PATCH の違いを説明してください。

    回答を表示

    PUT はデータ全体を送って丸ごと置き換えます。PATCH は送った項目だけを部分的に更新し、ほかの項目はそのまま残ります。

  3. Q3. 「安全性」と「冪等性」の違いを説明してください。

    回答を表示

    安全性は「呼び出してもサーバーの状態を変えない」こと（GET など）。冪等性は「何回呼んでもサーバーの最終的な状態が1回呼んだときと同じ」ことで、安全でなくても冪等な操作はあります（PUT・DELETE など）。

  4. Q4. POST が冪等でないことで、実際にどのような問題が起きやすいですか。

    回答を表示

    「投稿する」ボタンを2回押すなど、同じ POST リクエストを重複して送ってしまうと、同じデータが2件以上作成されてしまう「二重送信」の問題が起きやすくなります。
