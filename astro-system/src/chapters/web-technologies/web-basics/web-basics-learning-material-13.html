ホーム Webの仕組み 第13章
第13章 所要時間: 約45分

REST APIの設計の基本

前の章までは、すでに用意された API を使う側として動かしてきました。この章では立場を切り替え、API を作る側の視点で「分かりやすく、壊れにくい」設計の考え方を学びます。良い例と悪い例を比べながら、URI・ステータスコード・エラー・一覧の返し方・バージョニングという5つの観点を押さえていきましょう。

この章で学ぶこと

  • 分かりやすい URI（エンドポイント）の命名ルールを説明できる
  • 操作の種類に応じて、メソッドとステータスコードを正しく組み合わせられる
  • 統一された形式でエラーレスポンスを設計できる（RFC 9457 の考え方を知る）
  • 一覧APIのページネーション・ソート・絞り込みの工夫を説明できる
  • バージョニングの必要性と、互換性を壊す変更・壊さない変更の違いが分かる

13.1 URI設計のルール

第11章で「URI はリソース（名詞）を表し、動詞はメソッドが担う」と学びました。この原則を守るだけで、API はぐっと読みやすくなります。まずは代表的なルールを4つ押さえましょう。

  • 名詞を使う — URI に動詞（get・create・delete など）を入れない。「何をするか」はメソッドが表す
  • 複数形で統一する — コレクションは /users、個別は /users/1（第11章の復習）
  • 小文字とハイフンを使う — 単語の区切りは -（ケバブケース）。大文字や _ は避ける
  • 階層は浅く保つ — ネストは意味のある親子関係だけに使い、3階層を超えたら見直す（第11章 /posts/1/comments 程度まで）
やりたいこと 悪い例 良い例
ユーザー一覧を取得 GET /getAllUsers GET /users
投稿を新規作成 POST /createPost POST /posts
投稿1件を削除 GET /deletePost?id=1 DELETE /posts/1
単語の区切り方 /UserProfiles・/user_profiles /user-profiles

重要ポイント

悪い例の URI がだめな理由は「動作しないから」ではありません。GET /deletePost?id=1 でも実装すれば削除はできます。問題は、GET は「安全」なはず（第4章）というルールを破っており、キャッシュや先読みで意図せず削除が実行される事故につながる点です。URI とメソッドの役割分担を守ることが、事故を防ぐ設計です。

13.2 メソッドとステータスの対応表

第4章（メソッド）と第5章（ステータスコード）で学んだ内容を、API 設計の視点で組み合わせます。同じメソッドでも、成功か失敗か、何が起きたかによって返すステータスコードを使い分けます。

メソッド 成功時 代表的な失敗
GET /posts/1 200 OK ＋ 本体 404 Not Found（存在しない）
POST /posts 201 Created ＋ Location ヘッダー 400（形式エラー）／422（値が不正）
PUT /posts/1 200 OK（更新後を返す）／204 No Content 409 Conflict（競合。第6章の ETag を If-Match ヘッダーで送り返す楽観ロック等で検知）
DELETE /posts/1 204 No Content（返す本体が無い） 404 Not Found

201 Created のとき、レスポンスの Location ヘッダー（第6章）に「作られた資源の URI」を入れておくと、クライアントはすぐにその1件を取得できます。

POST /posts のレスポンス 
HTTP/1.1 201 Created
Content-Type: application/json
Location: /posts/501

{"id": 501, "title": "新しい投稿"}

200 と 204、どちらを使う？

「クライアントが更新後の中身をすぐ使いたいか」で決めます。使いたいなら本体付きの 200、使わないなら本体なしの 204 にして通信量を減らします。1つの API の中では、どちらかに統一しておくと迷いません。

13.3 エラーレスポンスの設計

ステータスコードだけでは「何が」「どう」間違っていたのかまでは伝わりません。第9章で学んだ JSON を使い、エラーの詳細を常に同じ形式で返すようにすると、クライアント側は1つのコードでエラーを処理できます。

よくある独自形式のエラー例 
{
  "error": "email is required",
  "field": "email"
}

これでも通じますが、キー名やエラーの粒度がエンドポイントごとにばらつきやすいのが弱点です。そこで近年は、RFC 9457（Problem Details for HTTP APIs）という標準形式が広く使われています。エラーの表現方法を統一する、いわば「エラー用の共通フォーマット」です。

RFC 9457 形式のエラー例 
{
  "type": "https://example.com/probs/invalid-param",
  "title": "入力値が不正です",
  "status": 422,
  "detail": "email は必須項目です",
  "instance": "/posts/501"
}
キー 意味
type エラーの種類を識別するURI（人間が読む解説ページでもよい）
title エラー種類の短い要約（同じ種類のエラーなら毎回同じ文言）
status HTTPステータスコードと同じ値を再掲
detail 今回の状況に応じた具体的な説明
instance 問題が発生したリクエスト固有のURI

RFC 9457 形式のレスポンスでは、Content-Type: application/problem+json（第6章の Content-Type の応用）を使い、「これは通常の JSON ではなくエラー詳細である」ことを明示するのが慣習です。

よくある勘違い

「エラーの詳細を JSON で返しているから 200 OK でよい」という設計は避けましょう。ステータスコードは第5章で学んだとおりクライアントが機械的に成否を判断する第一の手がかりです。本体の中身がエラー情報でも、ステータスコードは実際のエラー（4xx・5xx）にします。

13.4 一覧APIの工夫

GET /posts のような一覧取得は、件数が増えるほど「全部まとめて返す」わけにいかなくなります。そこで使われるのがページネーション（分割して返す仕組み）です。第12章のクエリパラメータ（?userId=1）の応用にあたります。

limit / offset 方式

?limit=20&offset=40 のように「何件飛ばして何件取るか」を指定。実装しやすく、ページ番号との対応もつけやすい。

弱点: データが追加・削除されると、途中で重複や抜けが起きやすい

カーソル方式

?cursor=abc123 のように「前回の最後の位置」を目印にして続きを取得。SNSのタイムラインなどでよく使われる。

弱点: 「〇ページ目に飛ぶ」といった操作がしにくい

一覧APIでは、ほかにもソート（並び替え）・絞り込み（フィルタ）・フィールド選択（返す項目を絞る）をクエリパラメータで指定できると使い勝手が上がります。

一覧APIのクエリパラメータ例 
GET /posts?limit=20&offset=0&sort=-createdAt&status=published&fields=id,title
Host: api.example.com

上の例では、sort=-createdAt（- は降順の意味）で新着順に並べ、status=published で公開済みだけに絞り、fields=id,title で必要な項目だけを取得しています。記法はAPIごとに異なるため、実際の仕様は必ずAPIドキュメント（第12章）で確認します。

ページネーションを使う一覧レスポンスには、全体像を伝えるメタ情報を添えるのが親切です。

メタ情報付きの一覧レスポンス例 
{
  "data": [{"id": 1, "title": "投稿A"}],
  "meta": {"total": 132, "limit": 20, "offset": 0}
}

13.5 バージョニングと互換性

API は公開後も改善が続きます。しかし仕様を急に変えると、すでにその API を使っているクライアント（他社のシステムやアプリ）が壊れてしまいます。そこで多くの API は、URI にバージョン番号を含めます。第8章・第12章の架空 API の例（/v1/users/me・/v1/weather）に出てきた /v1/ がこれにあたります。

flowchart LR A["/v1/posts
（既存クライアントが使用中）"] --> B["互換性のある変更
（項目の追加など）"] A --> C["互換性を壊す変更"] C --> D["/v2/posts を新設
旧クライアントは v1 のまま動く"]

すべての変更がバージョンアップを必要とするわけではありません。「壊す変更」と「壊さない変更」を区別できるようになりましょう。

後方互換を壊さない変更 後方互換を壊す変更
レスポンスに新しい項目を追加する 既存の項目を削除・リネームする
新しい任意（省略可能）のクエリパラメータを追加する 既存項目のデータ型を変える（文字列→数値など）
新しいエンドポイントを追加する これまで任意だった項目を必須にする

最後に、書き込み系のAPIでよく問題になる二重送信（第4章）への対策も紹介します。ネットワークが不安定なとき、クライアントは「リクエストが届いたか分からず、もう一度POSTする」ことがあります。Idempotency-Key ヘッダーにクライアント側で生成した一意な値を入れておくと、サーバーは同じキーの2回目以降のリクエストを「初回と同じ結果」として扱い、重複作成を防げます。決済 API（Stripe など）で広く採用されている方式で、IETF で標準化も進められています。

冪等キーを付けたPOSTリクエスト 
POST /v1/payments HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: 5f0e-a1b2-c3d4

冪等（べきとう）の復習

第4章で学んだとおり、PUT・DELETEはもともと「何回送ってもサーバーの最終的な状態が同じ」＝冪等です。POSTは本来そうではありませんが、Idempotency-Key を使うことで、POSTに疑似的な冪等性を持たせているのがこの仕組みです。

やってみよう 13-1: 「タスク管理API」を設計しよう

この章で学んだルールを使い、簡単な「タスク管理API」のエンドポイントを紙またはテキストエディタに書き出してみましょう。

手順

  1. 1 「タスク一覧の取得」「タスクの作成」「タスク1件の取得」「タスクの完了状態の更新」「タスクの削除」の5つの操作について、メソッド＋URIの表を作る（例: GET /v1/tasks）。
  2. 2 それぞれの操作について、成功時に返すステータスコードを13.2の表を参考に決める。
  3. 3 タスク1件のサンプルJSON（id・title・done など）を書く。
  4. 4 タスク一覧の取得に、13.4のページネーション（limit・offset）を追加する。

解答例: GET /v1/tasks?limit=20&offset=0（200）／POST /v1/tasks（201）／GET /v1/tasks/1（200、無ければ404）／PATCH /v1/tasks/1（200、{"done": true} のみ送る部分更新）／DELETE /v1/tasks/1（204）。「一覧取得」に動詞を使わず名詞の複数形にできていれば合格です。

理解度確認クイズ

  1. Q1. GET /getUserList という URI のどこが良くない設計ですか。

    回答を表示

    URI に動詞（get）が入っている点です。「何をするか」はメソッド（GET）がすでに表しているので、URI はリソースを表す名詞の複数形にし、GET /users とするのが適切です。

  2. Q2. POSTで新規作成に成功したとき返すべきステータスコードと、あわせて設定すると親切なヘッダーは何ですか。

    回答を表示

    201 Created です。あわせて Location ヘッダーに、作られた資源のURI（例: /posts/501）を入れておくと、クライアントはすぐにその1件を取得できます。

  3. Q3. RFC 9457（Problem Details）形式のエラーレスポンスに含まれる代表的な項目を2つ挙げてください。

    回答を表示

    type（エラー種類を識別するURI）・title（要約）・status（ステータスコード）・detail（具体的な説明）・instance（発生元のURI）のうち2つ。Content-Type は application/problem+json を使うのが慣習です。

  4. Q4. 一覧APIの limit / offset 方式と、カーソル方式の違いを簡単に説明してください。

    回答を表示

    limit / offset 方式は「何件飛ばして何件取るか」を指定する方式で実装しやすい一方、途中でデータが増減すると重複や抜けが起きやすい欠点があります。カーソル方式は前回の最後の位置を目印に続きを取得する方式で、SNSのタイムラインなどに向きますが、任意のページに飛ぶ操作には向きません。

  5. Q5. API のバージョニングで、v2 を新設すべき「後方互換を壊す変更」の例を1つ挙げてください。

    回答を表示

    既存のレスポンス項目を削除・リネームする、項目のデータ型を変える、これまで任意だった項目を必須にする、などが該当します。逆に、新しい項目や新しいエンドポイントの追加は互換性を壊さない変更です。
