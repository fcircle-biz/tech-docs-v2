ホーム JMeter 第9章
第9章 所要時間: 約1時間20分

相関：レスポンスの値を次のリクエストで使う

ログインのたびに発行されるトークンやセッション ID は、毎回違う値です。録画した固定値をそのまま送っても、本物の利用者のようには動きません。この章では、サーバーの応答から値を取り出して変数に入れ、次のリクエストで使い回す「相関（Correlation）」の方法を、JSON Extractor・Regular Expression Extractor・Boundary Extractor・Cookie Manager の4つで学びます。

この章で学ぶこと

  • 相関（Correlation）が必要になる理由と、「抽出 → 変数 → 再利用」の流れを説明できる
  • JSON Extractor で応答の値を取り出し、次のリクエストのヘッダーに渡せる
  • Regular Expression Extractor と Boundary Extractor の違いを理解し、使い分けられる
  • HTTP Cookie Manager でセッションを維持し、抽出に失敗したときの調べ方を身につける

9.1 相関（Correlation）とは

実際の Web システムでは、ログインに成功するとサーバーがトークンやセッション IDといった「あなたであることを示す札」を発行します。この札はログインのたびに違う値になり、以降のリクエストでは「この札を持っています」と示す必要があります。

第11章で学ぶ記録機能で操作を録画すると、そのときに発行された札の値がリクエストに固定値として書き込まれてしまいます。しかし、その値はすでに無効です。実行するたびにサーバーが新しい札を発行するため、古い固定値を送ると認証エラーになります。

この問題を解決するのが相関（Correlation）です。サーバーの応答から動的な値を抽出して変数に入れ、次のリクエストでその変数を再利用します。第8章で学んだ ${変数名} の形で参照できます。値の取り出しはPost Processor（後処理）に分類される「Extractor（抽出器）」が担当します。

sequenceDiagram participant J as JMeter（仮想ユーザー） participant S as go-httpbin（localhost:8080） J->>S: 1. GET /uuid（トークンの代わりに使う） S-->>J: 応答に uuid の値が入っている Note over J: 2. Extractor が uuid の値を取り出し、token 変数に保存 J->>S: 3. GET /bearer（Authorization ヘッダーに token 変数の値を付ける） S-->>J: 200 OK（token に送った値がそのまま返る）

本物のログイン API の代わりに、練習用サーバーの 2 つのエンドポイントを使います。/uuid は毎回違う値を返すので「トークンの発行」役、/bearer は Authorization: Bearer <トークン> ヘッダーがあれば（値は何でも）200 で、その値を token として返し、無ければ 401 を返すので「トークンが必要な API」役です。

用語: 変数はスレッドごと

第8章で学んだとおり、変数は仮想ユーザー（スレッド）ごとに独立しています。抽出した token も、他のスレッドには見えません。100人の仮想ユーザーがそれぞれ別のトークンを取得して使うので、本物の利用者と同じ状況を再現できます。

9.2 JSON Extractor

応答が JSON のときにいちばん手軽なのが JSON Extractor（JSON 抽出器）です。/uuid の応答は次のような JSON です。

GET /uuid の応答（値は毎回変わる） 
{
  "uuid": "6f1c2a3e-8b4d-4e5f-9a0b-1c2d3e4f5a6b"
}

値の場所は JSON Path という書き方で指定します。$ が JSON 全体（いちばん外側）を表し、.uuid でその中の uuid フィールドを指します。つまり $.uuid です。

設定は、/uuid の HTTP Request を右クリックして Add → Post Processors → JSON Extractor で追加します。Extractor をサンプラーの子に置くと、そのサンプラーの応答だけが対象になります。

項目 設定値 説明
Names of created variables token 取り出した値を入れる変数名。以降は ${token} で参照する
JSON Path expressions $.uuid 値の場所を示す JSON Path
Match No. (0 for Random) 1 複数見つかったときに何番目を使うか。1 で最初、0 でランダム、-1 ですべて
Compute concatenation var オフのまま 複数見つかった値を連結した変数（変数名_ALL）を作るかどうか。今回は使わない
Default Values NOT_FOUND 見つからなかったときに変数へ入れる値

重要ポイント: Default Values には必ず目印を入れる

Default Values を空のままにすると、抽出に失敗したときに変数が空になったり（JSON Extractor）、作られずに ${token} の文字のまま送られたり（Regular Expression Extractor）して、「取れなかった」のか「そもそも動いていない」のかが見分けにくくなります。NOT_FOUND のような目印を入れておけば、Debug Sampler や Request タブで NOT_FOUND が見え、抽出の失敗にすぐ気づけます。

9.3 抽出した値を使う

取り出した token を、/bearer のリクエストに付けます。ヘッダーを付けるのは第4章で使った HTTP Header Manager です。/bearer の HTTP Request を右クリックして Add → Config Element → HTTP Header Manager で、サンプラーの子として追加します。

Name Value
Authorization Bearer ${token}（Bearer のあとに半角スペースを1つ）

実行時、JMeter は ${token} をその場で取得済みの値に置き換えて送信します。実際に送られるリクエストは次のようになります。

/bearer に送られるリクエスト（イメージ） 
GET /bearer HTTP/1.1
Host: localhost:8080
Authorization: Bearer 6f1c2a3e-8b4d-4e5f-9a0b-1c2d3e4f5a6b

成功したかどうかは、第7章で学んだ JSON Assertion で確認します。/bearer の HTTP Request の子に追加し、次のように設定します。

項目 設定値
Assert JSON Path exists $.authenticated
Additionally assert value チェックを入れる
Expected Value true

さらに、相関が本当に効いていることを確かめておきましょう。HTTP Header Manager を一時的に無効化（Ctrl+T）して /bearer だけを実行すると、トークンが無いので 401 が返り、赤いアイコンになります。ヘッダーを有効に戻すと 200 になります。この「付ければ通る、外せば落ちる」の対比で、ヘッダーが必要なことは確かめられますが、値が正しく渡ったかは token の中身で確かめます。

/bearer はどんな値でも 200 を返すため、200 や authenticated だけでは値が正しく渡ったとは言えません。2つ目の JSON Assertion を追加し、応答の token が UUID の形をしていることを確認します。NOT_FOUND や ${token} のままなら、この Assertion が失敗します。

項目 設定値
Assert JSON Path exists $.token
Additionally assert value チェックを入れる
Match as regular expression チェックを入れる
Expected Value [0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}（UUID の形）
flowchart TD A["Thread Group"] --> B["HTTP Request: /uuid"] B --> B1["JSON Extractor
$.uuid を token 変数へ"] A --> C["HTTP Request: /bearer"] C --> C1["HTTP Header Manager
Authorization: Bearer token変数"] C --> C2["JSON Assertion
authenticated が true"] C --> C3["JSON Assertion
token が UUID の形"]

ツリーの順序にも注意してください。Extractor はサンプラーの実行後に動くため、/uuid は必ず /bearer より上に置きます。順序が逆だと、/bearer の時点で token がまだ存在しません。

9.4 Regular Expression Extractor

応答が HTML やプレーンテキストのときは JSON Path が使えません。そこで活躍するのが Regular Expression Extractor（正規表現抽出器）です。正規表現とは、「こういう並びの文字列」というパターンを書いて、文字列の中から該当部分を探す記法です。

/uuid の応答から値を取り出す正規表現は、次のとおりです。

Regular Expression 欄に入力する式 
"uuid":\s*"(.+?)"

初心者がまず覚えるべきは、次の記号だけです。

記号 意味
"uuid": そのままの文字列として一致させる（目印）
\s* 空白文字（スペースや改行）が0個以上続く。コロンの後ろに空白があってもなくても一致させるため
.+? 任意の文字が1文字以上。? を付けると「できるだけ短く」一致する（次の " で止まる）
( ) 取り出したい部分を囲む。囲んだ中身が1番目のグループ（$1$）になる

/uuid の HTTP Request を右クリックして Add → Post Processors → Regular Expression Extractor で追加し、次のように設定します。

項目 設定値 説明
Field to check Body どこから探すか。通常は応答ボディ（Body）。ヘッダーや URL も選べる
Name of created variable token2 値を入れる変数名（JSON Extractor の token と区別するため別名にする）
Regular Expression "uuid":\s*"(.+?)" 探すパターン
Template $1$ 変数に入れる形。$1$ は1番目のグループ（かっこの中）
Match No. (0 for Random) 1 最初に一致したものを使う
Default Value NOT_FOUND 見つからなかったときの値

ヒント: 取り出したい部分だけをかっこで囲む

かっこ ( ) の外側は「目印」として一致の判定に使われるだけで、変数には入りません。かっこを付け忘れると $1$ の中身が取れず、Default Value のままになります。まずは JSON Extractor のほうが簡単なので、応答が JSON なら JSON Extractor、そうでなければ正規表現、と使い分けるのが基本です。

9.5 Boundary Extractor

正規表現はパターンの書き方に慣れが必要です。Boundary Extractor（境界抽出器）は、取り出したい値の左側の文字列と右側の文字列を指定するだけで、その間にある部分を取り出せます。正規表現より設定が簡単で、処理も軽いのが特長です。

/uuid の応答 "uuid": "6f1c..." から値を取り出す場合、左の境界は "uuid": "、右の境界は " です。

項目 設定値 説明
Field to check Body 探す場所
Name of created variable token3 値を入れる変数名
Left boundary "uuid": " 値の直前にある文字列
Right boundary " 値の直後にある文字列
Match No. (0 for Random) 1 最初に見つかったものを使う
Default Value NOT_FOUND 見つからなかったときの値

注意: 境界の空白も1文字ずつ一致させる

境界文字列は空白も含めて完全一致が必要です。go-httpbin の応答はコロンの後ろに空白が入る形式ですが、サーバーによっては空白が無いこともあります。「見つからない」ときは、View Results Tree の Response data で実際の文字列を確かめ、左右の境界をコピーして貼り付けると確実です。

抽出器 向いている応答 特徴
JSON Extractor JSON JSON Path で場所を指定。構造が変わらない限り安定
Boundary Extractor HTML・テキスト・JSON 左右の文字列だけで指定でき、簡単で軽い。境界が一意であることが条件
Regular Expression Extractor HTML・テキスト・JSON もっとも柔軟だが、式の書き方に慣れが必要で、書き方次第で重くなる

9.6 HTTP Cookie Manager

Web サイトのセッションの多くは Cookie で維持されます。サーバーが応答の Set-Cookie ヘッダーで「この ID を覚えておいて」と伝え、ブラウザは以降のリクエストで Cookie ヘッダーとして自動的に送り返します。

JMeter はブラウザではないので、このやり取りを自動ではしてくれません。代わりに HTTP Cookie Manager を置くと、JMeter がブラウザと同じように Cookie を保存し、次のリクエストで送り返してくれます。Extractor で抽出する必要はなく、置くだけです。追加は Thread Group を右クリックして Add → Config Element → HTTP Cookie Manager です。

sequenceDiagram participant J as JMeter（Cookie Manager あり） participant S as go-httpbin J->>S: GET /cookies/set?session=abc S-->>J: 302 リダイレクト＋Set-Cookie（session=abc） Note over J: Cookie Manager が session を保存 J->>S: GET /cookies（保存した Cookie を自動で付ける） S-->>J: 200 OK（応答に abc が含まれる）

/cookies/set?session=abc は Cookie session=abc を設定したうえで /cookies へリダイレクトし、/cookies は受け取った Cookie を返します。リダイレクトはHTTP Request の Follow Redirects（既定でオン）により JMeter が自動でたどります。

状態 最終的な応答（/cookies） Response Assertion（Contains: abc）
Cookie Manager あり Cookie session=abc が送り返され、応答に表れる 成功
Cookie Manager なし Cookie が保存されず、abc が応答に表れない 失敗

ヒント: Cookie はスレッドごとに独立する

Cookie Manager が保存する Cookie も、スレッド（仮想ユーザー）ごとに別々です。ユーザーAのセッション ID がユーザーBに混ざることはありません。また、イテレーション（繰り返し）のたびに Cookie を消したいときは、Cookie Manager の Clear cookies each iteration? にチェックを入れます。

9.7 抽出がうまくいかないとき

相関でいちばん多いトラブルは「値が取れていない」ことです。次の順で調べます。

Debug Sampler で変数を見る

第8章で使った Debug Sampler（Add → Sampler → Debug Sampler）を Extractor の後ろに置くと、その時点の JMeter Variables に token=... が入っているかを View Results Tree で確認できます。NOT_FOUND なら抽出の失敗です。

View Results Tree のテスターを使う

View Results Tree の左側（サンプル一覧）の下にある表示形式のプルダウン（既定は Text）を切り替えると、JSON Path Tester・RegExp Tester・Boundary Extractor Tester が選べます。式を入力すると、その場で何が取れるかを試せるので、式を何度も実行し直さずに済みます。

症状 よくある原因 対処
変数が NOT_FOUND のまま JSON Path や境界文字列が実際の応答と合っていない Response data で応答を確認し、テスターで式を試す
/bearer が 401 のまま Authorization ヘッダーが送られていない（Header Manager が無効、または /bearer の子になっていない）、Bearer と値の間のスペース抜け、token が空 View Results Tree の Request タブで実際に送られたヘッダーを確認する
Request タブに ${token} の文字が残っている 変数が存在しない（抽出元のサンプラーが後ろにある、抽出器の置き場所違い、変数名の綴り違い）。go-httpbin はどんな値でも 200 を返すので、401 にならず気づきにくい Extractor を取得元サンプラーの子に置き、取得元を先に実行させる
1人目は成功するが他のスレッドは失敗 取得したはずの値が共有される前提で設計している 変数はスレッドごと。各スレッドが自分で取得する流れにする

やってみよう 9-1: /uuid から /bearer への相関を作る

go-httpbin を起動した状態で、/uuid で取得した値を /bearer に渡すテスト計画を作ります。保存名は jmeter-practice/ch09-correlation.jmx です。

手順

  1. 1 Test Plan → Thread Group（1スレッド・ループ1回）を作り、HTTP Request Defaults（http／localhost／8080）、View Results Tree を追加する。
  2. 2 HTTP Request「uuid」（Path: /uuid）を追加し、その子に JSON Extractor（変数名 token、JSON Path $.uuid、Match No. 1、Default Values NOT_FOUND）を置く。
  3. 3 その下に HTTP Request「bearer」（Path: /bearer）を追加し、子に HTTP Header Manager（Authorization ＝ Bearer ${token}）と JSON Assertion（$.authenticated が true）を置く。さらに2つ目の JSON Assertion を追加し、$.token、Additionally assert value と Match as regular expression にチェック、Expected Value に UUID の形 [0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12} を設定する。
  4. 4 実行し、View Results Tree で「bearer」が 200、応答に "authenticated": true と、uuid と同じ token が入っていることを確認する。
  5. 5 HTTP Header Manager を無効化（Ctrl+T）して再実行し、401 になることを確認してから有効に戻す。
確認ポイント: bearer の応答の token が、直前の uuid の応答と同じ値で、NOT_FOUND ではないことを確認できれば相関は成功です（go-httpbin の /bearer はどんな値でも 200 を返すため、200 だけでは判断できません）。2回実行してトークンの値が毎回変わることも確かめましょう。さらに余裕があれば、JSON Extractor を Regular Expression Extractor（token2）や Boundary Extractor（token3）に置き換え、Header Manager の変数名を差し替えても同じ結果になることを試してみましょう。

やってみよう 9-2: Cookie Manager の有無で比較する

同じ ch09-correlation.jmx に Cookie の確認を追加し、Cookie Manager の効果を比べます。

手順

  1. 1 Thread Group の直下に HTTP Request「cookie」（Path: /cookies/set、Parameters に session ＝ abc）を追加する。Follow Redirects がオンであることを確認する。
  2. 2 その子に Response Assertion（Field to Test: Text Response、Pattern Matching Rules: Contains、Patterns to Test: abc）を追加する。
  3. 3 Thread Group の直下に HTTP Cookie Manager を追加して実行し、成功（緑）になることを確認する。
  4. 4 Cookie Manager を無効化して再実行し、Response Assertion が失敗する（赤）ことを確認する。
確認ポイント: Cookie Manager の有無だけで結果が変わることが、「JMeter はブラウザではないので、Cookie の保存も自分で設定する」ことの実例です。確認が終わったら、Cookie Manager を有効に戻して保存しておきましょう。

理解度確認クイズ

  1. Q1. 録画したままのスクリプトに含まれるセッション ID の固定値が、なぜ実行時に問題になりますか？ 相関ではこれをどう解決しますか？

    回答を表示

    セッション ID はログインのたびにサーバーが新しく発行するため、録画時の固定値は実行時にはすでに無効で、認証エラーなどになります。相関では、サーバーの応答から Extractor で値を取り出して変数に入れ、次のリクエストで ${変数名} として使います。

  2. Q2. JSON Extractor の Default Values に NOT_FOUND のような目印を入れておくのは、なぜ良い習慣ですか？

    回答を表示

    空のままだと、抽出に失敗したときに変数が空になったり、作られずに ${token} の文字のまま送られたりして、「取れなかった」のか「そもそも動いていない」のかが見分けにくくなります。目印を入れておけば、Debug Sampler や Request タブで NOT_FOUND が見え、抽出の失敗にすぐ気づけます。

  3. Q3. /cookies/set?session=abc から /cookies への流れで、HTTP Cookie Manager を置かないと Response Assertion（Contains: abc）が失敗するのはなぜですか？

    回答を表示

    JMeter はブラウザではないため、Cookie Manager が無いとサーバーから受け取った Cookie（session=abc）を保存も送り返しもしません。そのため /cookies のリクエストに Cookie が付かず、応答に abc が含まれず、Contains のチェックが失敗します。
