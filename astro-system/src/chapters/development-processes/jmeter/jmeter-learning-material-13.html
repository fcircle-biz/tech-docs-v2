ホーム JMeter 第13章
第13章 所要時間: 約1時間20分

HTMLレポートで結果を分析する

負荷をかけて終わりではなく、結果を読んで「性能は目標を満たしているか」「どこに問題の兆候があるか」を判断するのが性能テストの本題です。この章では、JMeter が出力する HTML ダッシュボードレポートの構成と読み方、平均値とパーセンタイルの違い、APDEX、グラフの傾向、エラーの分析を学びます。

この章で学ぶこと

  • HTML レポートの構成（Dashboard と Charts）を説明できる
  • Statistics 表の各列を読み、最も遅いリクエストや 95 パーセンタイルを読み取れる
  • 平均値の罠とパーセンタイル、APDEX の考え方を理解する
  • グラフの傾向とエラー表から、限界に達したサインやエラーの原因の手がかりをつかむ

13.1 レポートの全体構成

第12章で -e -o report を付けて実行すると、report フォルダに HTML レポートが出力されます。report/index.html をブラウザで開いてください。レポートは大きく、全体をひと目で把握するDashboard（ダッシュボード）と、時間の流れに沿って傾向を見るCharts（グラフ）の2つの領域に分かれています。

補足: グラフ名の見つけ方

レポートの左側のメニューは「Over Time」「Throughput」「Response Times」の見出しでグラフをまとめています。グラフはマウスで範囲を拡大でき、凡例のクリックでリクエストごとの表示・非表示を切り替えられます。お使いの版でグラフ名が少し違って見える場合は、公式マニュアルの「Generating Report Dashboard」を確認してください。

13.2 Statistics 表の読み方

Dashboard の中心になるのが Statistics 表です。1行が1つのリクエスト（ラベル）で、最上段の「Total」行は全体の合計を表します。列の意味を押さえましょう。

列名意味見るときのポイント
#Samples 実行したサンプル（リクエスト）の件数 件数が少ないと他の数値の信頼性が低くなる
FAIL 失敗した件数 アサーション失敗や 4xx/5xx も含む
Error % 失敗の割合（FAIL ÷ #Samples） 目標（例: 1% 未満）と比べる
Average 応答時間の平均（ms） 極端に遅い値に引っ張られる。単独で判断しない
Min / Max 最小・最大の応答時間（ms） Max は外れ値の影響を受けやすい。1回の遅延でも大きくなる
Median 中央値。速い順に並べてちょうど真ん中の値 「普通の人が体験する時間」に近い
90th / 95th / 99th pct それぞれ 90%・95%・99% の件数がその時間以内に収まる値 遅い側の体感を表す。目標値の判定によく使う
Transactions/s 1秒あたりに処理した件数（スループット） 高いほど処理能力が高い
Received / Sent KB/sec 1秒あたりの受信・送信データ量（KB） 通信量の目安。帯域の限界を疑うときに見る

パーセンタイルの3つの値（90・95・99）は既定値で、user.properties の aggregate_rpt_pct1〜aggregate_rpt_pct3 で変更できます。

補足: 応答時間は何を測っているか

Average などの応答時間は、第4章で見た View Results Tree の Load time（Elapsed）と同じ、リクエスト送信から応答の受信完了までの時間です。第6章で学んだとおり、タイマーの待ち時間は含まれません。

13.3 平均値の罠とパーセンタイル

第1章で触れた「平均値の罠」を、数字で確かめましょう。10件のリクエストのうち9件が 0.2 秒、1件が 5 秒だった場合、平均は次のとおりです。

平均値の計算 
(0.2 x 9 + 5.0 x 1) / 10
= (1.8 + 5.0) / 10
= 0.68 秒

# 平均は0.68秒で「速そう」に見えるが、
# 10人に1人は5秒待たされている

次に、件数を100件に増やして、94件が 0.2 秒、6件が 5 秒のケースを考えます。

指標値読み方
Average (0.2 x 94 + 5.0 x 6) / 100 = (18.8 + 30.0) / 100 = 0.488 秒 約0.5秒。遅い人がいることが見えない
Median 0.2 秒 50 番目の値。ふつうの人は速い
90th pct 0.2 秒 速い順に 90 番目はまだ 0.2 秒の群の中
95th pct 5.0 秒 速い順に 95 番目は遅い群に入っている。「少なくとも5%の人は5秒以上待つ（この例では100件中6件）」
99th pct 5.0 秒 同様に遅い群
flowchart LR A["100件を速い順に並べる"] --> B["1〜94番目
0.2秒"] A --> C["95〜100番目
5.0秒"] B --> D["90パーセンタイル = 0.2秒"] C --> E["95パーセンタイル = 5.0秒"]

95パーセンタイルが「5秒」と出たことで、平均では見えなかった「少なくとも5%（この例では6件）の利用者が5秒待っている」という事実が明らかになりました。性能目標は「95パーセンタイルが2秒以内」のようにパーセンタイルで決めることが多く、実際に何をどの値で判定するかは第14章で扱います。

重要ポイント

平均値は全体の雰囲気をつかむために使い、合否の判定には 95・99 パーセンタイルと Error % を使うのが基本です。Max は1回の偶発的な遅延で大きくなるので、単独で判断材料にしません。

13.4 APDEX：満足度を1つの数値にする

APDEX（Application Performance Index）は、応答時間を「満足」「許容」「不満」の3つに分け、利用者の満足度を 0〜1 の1つの数値にまとめた指標です。レポートの APDEX 表には、リクエストごとの値が出ます。

区分判定条件（既定）考え方
Satisfied（満足） 応答時間が 500ms 以下 待たされた感覚がない
Tolerated（許容） 500ms を超え 1500ms 以下 遅いが我慢できる
Frustrated（不満） 1500ms を超える、またはエラー 待てない。離脱の原因
APDEX の計算式 
APDEX = (満足の件数 + 許容の件数 / 2) / 全件数

# 例: 100件中 満足70件・許容20件・不満10件
# = (70 + 20 / 2) / 100
# = 80 / 100 = 0.80

値は 1 に近いほど良好で、0 に近いほど不満が多いことを示します。一般には 0.94 以上を優秀、0.85〜0.94 を良好、0.7〜0.85 を普通などと評価しますが、これは目安であり、プロジェクトの目標に合わせて決めます。レポートの APDEX 表では、T 列に満足のしきい値（既定 500ms）、F 列に許容のしきい値（既定 1500ms）が表示されます。

しきい値（500ms と 1500ms）は、システムの性格に合わせて変更できます。bin/user.properties に次のように書きます（レポート生成時に読み込まれます）。

user.properties 
# 満足とみなす応答時間の上限（ミリ秒）。既定は500
jmeter.reportgenerator.apdex_satisfied_threshold=1000
# 許容とみなす応答時間の上限（ミリ秒）。既定は1500
jmeter.reportgenerator.apdex_tolerated_threshold=3000

注意: しきい値を変えたら記録しておく

しきい値を緩めると APDEX は簡単に上がります。結果を報告するときは、どのしきい値で計算した値かを必ず書き添えましょう。条件の違う実行同士の APDEX は比べられません。

13.5 Over Time グラフで傾向を見る

Statistics 表は「結果の要約」ですが、いつ・何が起きたかは Charts で見ます。特に次の3つのグラフを並べて読むのが基本です。

Response Times Over Time

時間の経過に伴う平均応答時間の推移。急に伸びた時刻がないかを見る。

Active Threads Over Time

同時に動いているスレッド（仮想ユーザー）数の推移。負荷がどう変化したかの基準線。

Transactions Per Second

1秒あたりの処理件数の推移。システムの処理能力そのもの（Charts → Throughput にあります）。

これらを重ねて読むと、システムの状態がわかります。典型的なパターンを整理します。

Active ThreadsTransactions/sResponse Times読み取れること
増える 一緒に増える ほぼ一定 まだ余裕がある。健全な状態
増え続ける 頭打ち（横ばい） 伸びていく 限界に達したサイン。これ以上スレッドを増やしても処理は増えず、待ち行列が長くなるだけ
さらに増える 下がる 急に伸びる 過負荷。処理が追いつかず、タイムアウトやエラーも出始める
一定 一定 徐々に伸びる 耐久テストで要注意。メモリ枯渇など時間とともに悪化する問題の疑い
flowchart TD A["スレッド数を増やす"] --> B{"スループットも増えた？"} B -->|はい| C["まだ余裕あり
さらに負荷を上げて確認"] B -->|いいえ 頭打ち| D{"応答時間は伸びた？"} D -->|はい| E["限界に達したサイン
この手前が処理能力の目安"] D -->|いいえ| F["JMeter 側の限界を疑う
CPU・メモリ・ネットワーク"]

Response Times Over Time が滑らかでなく、周期的に跳ね上がる場合は、バッチ処理やガベージコレクションなど周期的な処理の影響が疑われます。気になる時刻をグラフで拡大し、その時刻のサーバー側のログと照らし合わせましょう（13.8）。

ヒント: グラフの点が少ないとき

Over Time 系グラフは既定で1分（60000ms）ごとに集計されるため、数分以内の短いテストでは点が数個しか出ません。jmeter -g result.jtl -o report-5s -Jjmeter.reportgenerator.overall_granularity=5000 のように集計間隔を5秒にして作り直すと傾向が読みやすくなります（1000 未満にはしない）。

13.6 エラーの分析

Dashboard の Errors 表は、エラーの種類（ステータスコードやアサーション失敗のメッセージなど）ごとの件数と、全リクエストに占める割合を示します。Top 5 Errors by Sampler 表は、サンプラーごとに多いエラー上位5件を示します（Transaction Controller の行は既定で除外されます）。

練習用の go-httpbin には、指定した確率で失敗する /unstable があります。/unstable?failure_rate=0.1 を混ぜると、/unstable へのリクエストのうちおよそ 10% が 500 エラーになり、全体のエラー率も 1% を超えます。エラー率の目標が 1% 未満であれば、この結果は「不合格」と判定できます。

見るもの確認すること
Requests Summary 全体の成功率と失敗率。大づかみな健全性
Errors 表 どの種類のエラーが何件あるか（500 か、アサーション失敗か、タイムアウトか）
Top 5 Errors by Sampler どのリクエストにエラーが集中しているか
Response codes per second エラーが出始めた時刻と、負荷との関係（グラフ）

補足: エラーが出た時刻を探す

エラーが特定の時刻から急増していれば、負荷の増加と対応しているか（限界のサイン）、周期的か（バッチなどの影響）、最初から出ているか（スクリプトや環境の誤り）を切り分けます。スクリプトの誤りが疑われるときは、第7章・第9章のアサーションや相関の設定を見直します。

13.7 既存の結果からレポートを作り直す

レポートは、実行時だけでなく、保存してある結果ファイル（JTL）から後から作り直すこともできます。第12章で出力した result.jtl があれば、次のコマンドで別フォルダにレポートを生成できます。

ターミナル 
# 既存の結果ファイルからレポートを作り直す
# -g: 既存の JTL を指定  -o: 出力先（空か未作成のフォルダ）
jmeter -g result.jtl -o report2

# Windows は jmeter.bat を使う
# jmeter.bat -g result.jtl -o report2

たとえば APDEX のしきい値や集計間隔を変えたいとき、ウォームアップ（最初の立ち上がり）部分を除きたいときなどに、再実行せず条件だけ変えてレポートを作り直せます。しきい値は -J オプションでも指定できます。

ターミナル 
# しきい値を変えてレポートを作り直す
jmeter -g result.jtl -o report3 \
  -Jjmeter.reportgenerator.apdex_satisfied_threshold=1000 \
  -Jjmeter.reportgenerator.apdex_tolerated_threshold=3000

# Windows は1行で書く
# jmeter.bat -g result.jtl -o report3 -Jjmeter.reportgenerator.apdex_satisfied_threshold=1000 -Jjmeter.reportgenerator.apdex_tolerated_threshold=3000

注意: 出力先フォルダは空か未作成に

-o で指定するフォルダが存在して空でないと、JMeter はエラーで止まります。作り直すときは、出力先の名前を変えるか、古いフォルダを削除してから実行しましょう。

13.8 ボトルネック調査の入口

ここまでのレポートで JMeter が教えてくれるのは、「どこが（どのリクエストが）遅いか」「いつから遅くなったか」までです。「なぜ遅いか」は JMeter の外にあります。原因を探るには、テストの実行時間帯のサーバー側の情報と突き合わせます。

flowchart LR A["JMeter のレポート
どのリクエストが・いつ遅いか"] --> B["サーバー側の監視と突き合わせる"] B --> C["CPU・メモリ"] B --> D["データベース
遅いクエリ・接続数"] B --> E["アプリのログ
エラー・例外"] B --> F["ネットワーク・外部API"] C --> G["原因の仮説 → 修正 → 再テスト"] D --> G E --> G F --> G

調査の基本は仮説を立て、1つだけ変えて、同じ条件で再テストすることです。そのため、実行時刻・負荷条件・使った .jmx のバージョンを記録しておくと、前後の比較ができます。第14章の報告書でもこの記録が役立ちます。

注意: 学習環境の数値は目安

本ガイドでは JMeter と go-httpbin が同じ PC で動いているため、互いに CPU を奪い合います。レポートの数値は読み方の練習用であり、実際のシステムの性能値ではありません。

やってみよう 13-1: レポートから最も遅いリクエストを探す

第12章で出力したレポートを読み、数字から結論を引き出す練習をします。

手順

  1. 1 go-httpbin が起動していることを確認し、第12章の report/index.html をブラウザで開く（無ければ第12章の手順で再実行する）。
  2. 2 Dashboard の Statistics 表で、Average が最も大きいリクエストと、95th pct が最も大きいリクエストを探す。
  3. 3 そのリクエストの Average と 95th pct の差を確認し、差が大きい場合は「平均では見えない遅さがある」とメモする。
  4. 4 APDEX 表と Requests Summary を見て、全体の満足度と成功率を書き留める。
確認の目安: 第12章のシナリオは localhost 相手の軽いリクエストだけなので、どの行も数ms〜数十msで差は小さく出ます。違いをはっきり見たいときは HTTP Request（GET /delay/1）を1つ追加して再実行すると、その行が Average 約 1000ms で最上位に出ます。

やってみよう 13-2: エラーを混ぜて Errors を確認する

わざと失敗するリクエストを加えて、エラーがレポートにどう現れるかを確かめます。

手順

  1. 1 ch12-load.jmx を ch13-errors.jmx として保存し、Thread Group に HTTP Request（Path: /unstable、Parameters: failure_rate = 0.1）を追加する。
  2. 2 第12章と同じ要領で CLI から実行する。出力先は新しい名前にする（例: -l result13.jtl -e -o report13）。
  3. 3 report13/index.html で Requests Summary の失敗率、Errors 表のエラーの種類と件数、Top 5 Errors by Sampler を確認する。
  4. 4 さらに jmeter -g result13.jtl -o report13b でレポートを作り直せることを確かめる。
確認の目安: /unstable のエラーは 500 として Errors 表に出ます。Statistics 表の /unstable 行の Error % はおよそ 10% 前後（件数が少ないとばらつきます）です。Errors 表の % in errors は（500 しか無ければ）ほぼ 100%、% in all samples は全リクエスト中の割合なので 10% より小さくなりますが、それでも全体のエラー率は目標の 1% を上回ります。他のリクエストは成功のままです。

理解度確認クイズ

  1. Q1. 100件のリクエストで、90件が 0.3 秒、10件が 3.3 秒でした。平均値と 95 パーセンタイルはそれぞれいくつですか？

    回答を表示

    平均は (0.3 x 90 + 3.3 x 10) / 100 = (27 + 33) / 100 = 0.6 秒です。速い順に 95 番目は遅い群（3.3 秒）に入るので、95 パーセンタイルは 3.3 秒です。平均は 0.6 秒で良さそうに見えますが、10% の人は 3.3 秒待たされています。

  2. Q2. 100件のうち、満足が 60件、許容が 30件、不満が 10件でした。APDEX はいくつですか？

    回答を表示

    APDEX = (満足 + 許容 / 2) / 全件数 = (60 + 30 / 2) / 100 = 75 / 100 = 0.75 です。

  3. Q3. スレッド数を増やしてもスループットが頭打ちになり、応答時間だけが伸びました。何を意味し、次に何を確認しますか？

    回答を表示

    システムが限界に達したサインです。それ以上スレッドを増やしても処理は増えず、待ち行列が長くなるだけです。サーバー側の CPU・メモリ・DB・ログを実行時間帯と突き合わせ、原因を探します。また、JMeter 側のリソース不足でないかも確認します。
