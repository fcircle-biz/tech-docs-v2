JMeterと性能テストの全体像

Apache JMeter は、Web システムに「たくさんの利用者が同時にアクセスした状態」を再現し、速さと安定性を測るためのツールです。この章では、性能テストが何のために行われ、どんな種類があり、どの数値を見ればよいのか、そして JMeter がどのような仕組みで負荷をかけるのかという全体像をつかみます。

この章で学ぶこと

  • 機能テストと性能テストの違いを説明できる
  • 負荷テスト・ストレステスト・スパイクテスト・耐久テストの目的を区別できる
  • 応答時間・スループット・エラー率・同時ユーザー数の意味を理解する
  • 「スレッド＝仮想ユーザー」という JMeter の仕組みの全体像をつかむ

1.1 性能テストとは何か

システムのテストと聞くと、多くの人は「ボタンを押したら正しい画面が出るか」「計算結果が合っているか」を確かめる機能テストを思い浮かべます。しかし、1人で操作したときに正しく動くシステムでも、1,000人が同時にアクセスした途端に画面が表示されなくなることは珍しくありません。

性能テスト（パフォーマンステスト）は、たくさんの利用者が同時に使ったときにも、システムが十分に速く、安定して動くかを確かめるテストです。セールやキャンペーンの開始直後、チケットの発売開始時刻など、アクセスが集中する場面でシステムが止まると、売上や信用に直結する損失になります。こうした事態を本番前に見つけるのが性能テストの役割です。

機能テスト

「正しく動くか」を確かめる。

例: 商品をカートに入れると、カートの件数が1つ増えるか。

性能テスト

「たくさんの人が同時に使っても速く・安定して動くか」を確かめる。

例: 500人が同時にカートに入れても、2秒以内に応答し、エラーが出ないか。

性能テストを人手で行うのは現実的ではありません。500人を集めて同時にボタンを押してもらうわけにはいかないからです。そこで、大量の利用者の操作をプログラムで再現するツールを使います。その代表が、本ガイドで学ぶ Apache JMeter です。

1.2 性能テストの種類

性能テストは、どのような負荷を、どのくらいの時間かけるかによっていくつかの種類に分かれます。目的が違えば、JMeter の設定（同時ユーザー数や実行時間）も変わります。

種類 負荷のかけ方 目的・わかること
負荷テスト
Load Test		 想定される通常時〜ピーク時の負荷を、一定時間かける 目標の応答時間・スループットを満たすか。もっとも基本となるテスト
ストレステスト
Stress Test		 想定を超える負荷まで、段階的に上げていく どこが限界か。限界を超えたときにエラーを返すのか、停止するのか、負荷が下がれば回復するのか
スパイクテスト
Spike Test		 短時間に急激に負荷を上げる 発売開始時刻などの急なアクセス集中に耐えられるか
耐久テスト
Endurance / Soak Test		 通常の負荷を、数時間〜数日かけ続ける メモリリークやディスク・接続数の枯渇など、時間とともに悪化する問題がないか

用語: 呼び方の揺れについて

現場では「負荷テスト」が性能テスト全体を指す言葉として使われることもあります。本ガイドでは、総称を性能テスト、そのうち想定負荷で目標を満たすか確かめるものを負荷テストと呼び分けます。耐久テストは「ロングラン」と呼ばれることもあります。

1.3 見るべき指標

性能テストの結果は、主に次の4つの数値で語られます。JMeter のレポートにもこれらの値が並ぶので、まずは意味をしっかり押さえましょう。

応答時間（Response Time）

リクエストを送ってから、応答を受け取り終わるまでの時間。単位はミリ秒（ms）。利用者が「待たされる時間」に直結します。

スループット（Throughput）

単位時間あたりに処理できたリクエストの件数。単位は「件/秒」など。システムの「処理能力」を表します。

エラー率（Error %）

全リクエストのうち、失敗したものの割合。どれだけ速くても、エラーが多ければ合格とは言えません。

同時ユーザー数

同じ時間帯にシステムを使っている利用者の数。JMeter ではスレッド数として設定します（1.5 で説明）。「同時に処理中のリクエスト数」とは別の数です（第5章で整理します）。

応答時間を見るときは、平均値だけで判断しないことが大切です。たとえば10件のリクエストのうち9件が0.2秒、1件が5秒だったとします。平均は0.68秒で「速い」ように見えますが、10人に1人は5秒も待たされています。

そこで性能テストでは、パーセンタイルという見方をよく使います。「95パーセンタイルが2秒」とは、「全リクエストを速い順に並べたとき、95%が2秒以内に収まっている」という意味です。詳しくは第13章で、実際のレポートを読みながら学びます。

重要ポイント

4つの指標は互いに関係しています。同時ユーザー数を増やすとスループットは上がりますが、システムの限界に近づくとスループットが頭打ちになり、応答時間だけが伸び、やがてエラーが増え始めます。この変化を観察することが、性能テストの中心的な作業です。

1.4 Apache JMeter とは

Apache JMeter（ジェイメーター）は、Apache ソフトウェア財団が開発しているオープンソースの性能テストツールです。20年以上の歴史があり、性能テストの現場で広く使われています。Java で作られているため、Windows・macOS・Linux のどれでも同じように動きます。

無料で使える

オープンソース（Apache License 2.0）で、商用利用も含めて無料です。

GUI で組み立てる

画面上で部品を組み合わせてテスト計画を作れるため、コードを書かずに始められます。

幅広いプロトコル

HTTP/HTTPS を中心に、REST・SOAP、データベース（JDBC）、FTP、JMS なども扱え、プラグインで拡張できます。

性能テストツールは JMeter 以外にもあります。代表的なものと比べると、JMeter の立ち位置がわかります。

ツール テストの書き方 特徴
Apache JMeter GUI で組み立てる（保存形式は XML） プログラミング不要で始めやすい。情報量が多く、対応プロトコルも幅広い
Gatling Java・Scala・Kotlin などのコード 少ないリソースで大きな負荷をかけやすい
k6 JavaScript のコード 開発者向け。CI への組み込みがしやすい
Locust Python のコード Python でシナリオを柔軟に書ける

どのツールでも、性能テストの考え方（負荷の設計・指標の読み方・結果の判断）は共通です。本ガイドで JMeter を通して身につける考え方は、ほかのツールを使うときにもそのまま役立ちます。

1.5 JMeter の仕組み

JMeter の中心にあるのはスレッドという考え方です。スレッドとは、プログラムの中で並行して動く処理の単位のことで、JMeter では1つのスレッドが1人の仮想ユーザーとして振る舞います。100スレッドを設定すれば、100人の利用者が並行してシステムを使っている状態を再現できます。

ただし、100スレッドが、いつも100件のリクエストを同時に送っているわけではありません。各スレッドは、サーバーの応答を待っている時間や、次の操作までの待ち時間（第6章で学ぶ思考時間）を過ごしている時間もあるため、ある瞬間に処理中のリクエスト数は、スレッド数より少ないのがふつうです。また、システムの応答が遅くなると、各スレッドが次のリクエストを送るまでの間隔が延びるため、同じスレッド数でも1秒あたりのリクエスト数（スループット）は減ります。「仮想ユーザー数」「同時リクエスト数」「スループット」の違いは、第5章で整理します。

利用者の操作手順はテスト計画（Test Plan）として定義し、.jmx という拡張子のファイルに保存します。テストを実行すると、各スレッドがテスト計画に従ってリクエストを送り、その結果（応答時間や成否）を1件ずつ記録します。この1件分の結果をサンプルと呼びます。

flowchart TD A["Test Plan（テスト計画・.jmx）
利用者の操作手順を定義"] --> B["Thread Group（スレッドグループ）
仮想ユーザーをN人起動"] B --> C["各スレッドがリクエストを送る"] C --> D["テスト対象のサーバー"] D -->|応答| E["結果を1件ずつ記録（サンプル）"] E --> F["Listener（リスナー）／HTMLレポートで集計"] E -->|次の操作へ| C

ここで1つ注意があります。JMeter はブラウザではありません。JMeter が再現するのは、ブラウザとサーバーの間でやり取りされるHTTP の通信です。画面を描画したり、ページ内の JavaScript を実行したりはしません。

JMeter で測れるもの・測れないもの

JMeter で測れるのは「リクエストを送ってから、応答を受け取り終わるまでの時間（通信時間を含む）」です。ブラウザが画面を描き終えるまでの時間（画像の表示や JavaScript の処理を含む体感速度）は測れません。画面表示の速さを調べたいときは、ブラウザの開発者ツールなど別の道具を使います。

1.6 本ガイドの練習環境

本ガイドでは、自分の PC の中に練習用のサーバーを用意し、そこに対して負荷をかけます。練習用サーバーには、HTTP のテスト用に作られた go-httpbin を使います。送ったリクエストの内容をそのまま返したり、わざと応答を遅らせたり、エラーを返したりできるため、JMeter の練習相手に最適です（導入は第2章で行います）。

flowchart LR subgraph PC["あなたのPC"] J["JMeter
テスト計画を作成・実行"] -->|"HTTPリクエスト"| H["go-httpbin
localhost:8080"] H -->|"応答"| J end

学習は「GUI でテスト計画を作る → 少人数で動作を確かめる → 本番の負荷は CLI（コマンドライン）で実行する → レポートを分析する」という、実務と同じ流れで進めます。

警告: 許可のないサーバーに負荷をかけない

許可なく他人・他社のサーバーに負荷をかけることは、サービスを妨害する攻撃（DoS 攻撃）と同じ行為であり、法的責任を問われる可能性があります。練習のつもりでも、公開されている Web サイトに JMeter を向けてはいけません。実務でも、対象システムの管理者の許可と、実施日時・負荷の大きさについての合意を得てから実施します。

やってみよう 1-1: 性能が問題になる場面を考える

インストールの前に、身近なサービスで「性能が問題になりそうな場面」を考えてみましょう。テストの目的を言葉にできると、この先の設定の意味がつかみやすくなります。

手順

  1. 1 ふだん使っている Web サービスや、業務で関わっているシステムを1つ選ぶ。
  2. 2 アクセスが集中しそうな場面を2つ書き出す（例: 月初の勤怠締め、年末のキャンペーン開始直後）。
  3. 3 それぞれの場面に合うテストの種類（1.2）と、特に確認したい指標（1.3）を選び、理由を一言添える。
記入例: 「キャンペーン開始の瞬間にアクセスが急増する」→ スパイクテスト。エラー率を最優先で確認する（つながらないことが一番の問題だから）。

理解度確認クイズ

  1. Q1. 負荷テストとストレステストは、目的がどう違いますか？

    回答を表示

    負荷テストは、想定される通常〜ピーク時の負荷で、目標の応答時間やスループットを満たすかを確かめます。ストレステストは、想定を超える負荷まで段階的に上げ、どこが限界か、限界を超えたときにどう振る舞うか（エラーを返す・停止する・回復する）を調べます。

  2. Q2. 応答時間を平均値だけで判断してはいけないのはなぜですか？

    回答を表示

    平均値は一部の極端に遅いリクエストを隠してしまうからです。9件が0.2秒・1件が5秒なら平均は0.68秒ですが、10人に1人は5秒待っています。そのため「95%のリクエストが何秒以内か」を表す95パーセンタイルなどもあわせて確認します。

  3. Q3. JMeter の「スレッド」は何を表しますか？ また、JMeter で測れない時間は何ですか？

    回答を表示

    スレッドは1人の仮想ユーザーを表し、スレッド数が同時ユーザー数になります。JMeter はブラウザではなく HTTP の通信を再現するツールなので、ブラウザが画面を描き終えるまでの時間（JavaScript の実行や描画を含む体感速度）は測れません。
