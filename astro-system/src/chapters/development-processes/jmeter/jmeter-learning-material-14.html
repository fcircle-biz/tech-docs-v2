14.1 性能テストの進め方

ここまでは JMeter の「部品」を一つずつ学んできました。実務の性能テストは、部品を使う前後の段取りが成否を分けます。いきなり大きな負荷をかけるのではなく、目標を決め、小さく確かめ、段階的に負荷を上げ、結果を報告するという流れで進めます。

flowchart TD A["目的・目標の合意"] --> B["シナリオ設計"] B --> C["スクリプト作成（GUI）"] C --> D["スモークテスト
1ユーザーで動作確認"] D --> E{"全件成功か？"} E -->|いいえ| C E -->|はい| F["本番実行（CLI）
負荷を段階的に上げる"] F --> G["分析（HTMLレポート）"] G --> H["報告・次のアクション"]
工程 やること 主な章
目的・目標の合意 何のために測り、何が出れば合格かを数値で決め、関係者と合意する 第1章
シナリオ設計・スクリプト作成 利用者の操作の流れを決め、テスト計画（.jmx）に落とし込む 第3〜11章
スモークテスト 1ユーザー・1ループで、スクリプト自体が正しく動くか確かめる 第4章
本番実行 CLI モードで、負荷を小さい方から段階的に上げて実行する 第5・12章
分析・報告 レポートを読み、目標と比べて判定し、報告書にまとめる 第13章

重要ポイント: スモークテストを飛ばさない

スクリプトの間違い（URL のミス、相関の失敗など）を抱えたまま負荷をかけると、「システムが遅い」のか「スクリプトが間違っている」のか区別できなくなります。先に1ユーザーで正しさを確認し、それから負荷を上げるのが鉄則です。

14.2 演習の題材と目標

この演習では、練習用サーバー go-httpbin（localhost:8080）を「EC サイトの API」に見立てます。利用者は、トップページを開き、ログインし、商品を何度か閲覧し、商品を検索して、注文する、という流れで操作します。

flowchart LR T1["T01_Top
GET /html"] --> T2["T02_Login
POST /post
GET /uuid
GET /bearer"] T2 --> T3["T03_Browse（3回）
GET /get"] T3 --> T4["T04_Search
GET /delay/1"] T4 --> T5["T05_Order
POST /anything/orders"]
トランザクション名 EC サイトでの意味 実際に送るリクエスト
T01_Top トップ表示 GET /html
T02_Login ログイン（スレッドにつき1回） POST /post（CSV のユーザー）→ GET /uuid（トークン取得）→ GET /bearer（認証確認）
T03_Browse 商品閲覧（3回繰り返し） GET /get?item=${__Random(1,100,)}
T04_Search 商品検索（重い処理） GET /delay/1（1秒かかる処理に見立てる）
T05_Order 注文 POST /anything/orders

次に目標を決めます。目標が数値になっていないと、結果が出ても「良いのか悪いのか」を判断できません。本演習では次の目標を置きます（実務では、業務要件や過去の実績から関係者と合意して決めます）。

項目 目標
負荷条件 20ユーザーが同時に、3分間（180秒）操作を続ける
応答時間 各トランザクションの 95 パーセンタイルが 2000ms 以内
エラー率 全体で 1% 未満

警告: 負荷をかける先は localhost だけ

この演習の接続先は、自分の PC 上の go-httpbin（localhost:8080）だけです。他人・他社のサーバーへ許可なく負荷をかけることは DoS 攻撃と同じ行為で、法的責任を問われる可能性があります。実行前に、HTTP Request Defaults の Server Name が localhost であることを必ず確認してください。

ヒント: 既存のファイルを再利用する

第8〜10章で作った ch10-scenario.jmx などを 名前を付けて保存（File → Save Test Plan as...）で ch14-final.jmx として複製し、足りない部分だけ付け足すのが近道です。要素の名前（Name 欄）は、レポートに表示されるので、T01_Top のように意味の分かる名前にしておきましょう。

14.4 スモークテスト

スクリプトができたら、いきなり負荷をかけず、GUI で1ユーザー・1回だけ実行して動作を確認します。Thread Group の Number of Threads を ${__P(users,1)} のまま（既定の 1）にしておき、Loop Count を一時的に 1 にして、Specify Thread lifetime のチェックを外すと、1周だけで止まります。

確認する場所 期待する状態
View Results Tree すべてのサンプルに緑のアイコンが付く（赤が1つもない）
T02_Login の /bearer の Response data "authenticated": true が返っている（トークンの相関が成功）
T03_Browse の Request item= に ${...} のままではなく、1〜100 の数字が入っている
T02_Login の /post の Response data json の user に CSV の1行目のユーザー（alice）が入っている
Transaction の行 T01〜T05 のトランザクション行が表示され、T03_Browse は3回出る

スモークテストの合格ライン

「全サンプルが成功」「変数が埋まっている」「トークンが渡っている」の3つがそろったら合格です。1つでも崩れていれば、まだ本番実行に進んではいけません。Debug Sampler と JSON Path Tester（第9章）で原因を探してください。

合格したら、Thread Group の設定を元（Loop Count を Infinite、Specify Thread lifetime にチェック）に戻します。デバッグ用に小さくした値を戻し忘れるのは、第12章で見たとおり典型的な失敗です。

14.5 段階的な本番実行

本番実行は CLI モードで行います。目標は 20 ユーザーですが、最初から 20 ユーザーで実行せず、5 → 10 → 20 ユーザーと段階を踏みます。段階的に上げると、「どの負荷から応答時間が伸び始めるか」が見え、問題の起きた条件を特定しやすくなります。

段階 users duration（秒） 結果の保存先
1回目 5 60 results/u05
2回目 10 120 results/u10
3回目（目標条件） 20 180 results/u20

第12章で JMeter の bin フォルダに PATH を通した前提で、macOS/Linux では次のように実行します。-J で第8章の ${__P()} に値を渡し、結果ファイルとレポートの保存先を段階ごとに分けます（同じ名前のファイルがあるときは -f が上書きします）。

terminal（macOS / Linux） 
# 作業フォルダへ移動して、結果の保存先を用意する
cd ~/Documents/jmeter-practice
mkdir -p results

# 1回目: 5ユーザー・60秒（結果は results/u05 に保存）
jmeter -n -t ch14-final.jmx -f -Jusers=5 -Jduration=60 -l results/u05.jtl -e -o results/u05

# 2回目: 10ユーザー・120秒
jmeter -n -t ch14-final.jmx -f -Jusers=10 -Jduration=120 -l results/u10.jtl -e -o results/u10

# 3回目: 20ユーザー・180秒（目標の条件）
jmeter -n -t ch14-final.jmx -f -Jusers=20 -Jduration=180 -l results/u20.jtl -e -o results/u20

Windows（コマンドプロンプト）では、次のように実行します。

terminal（Windows） 
:: 作業フォルダへ移動して、結果の保存先を用意する
cd %USERPROFILE%\Documents\jmeter-practice
mkdir results

:: 3回目（20ユーザー・180秒）の例。1回目・2回目は users と duration を変える
jmeter.bat -n -t ch14-final.jmx -f -Jusers=20 -Jduration=180 -l results\u20.jtl -e -o results\u20

重要ポイント: 実行前の最終チェック（第12章の復習）

  • View Results Tree などの重いリスナーと Debug Sampler を無効化したか
  • 接続先が localhost になっているか（HTTP Request Defaults）
  • -o のフォルダが、空か未作成になっているか（-f を付ければ上書きされます）
  • 実行中は PC で別の重い作業をしていないか（測定値が歪みます）

14.6 結果の判定

results/u20/index.html を開き、14.2 で決めた目標と実測値を1行ずつ突き合わせます。応答時間は Statistics 表の 95th pct 列、エラー率は Total 行の Error % 列から読み取ります（第13章）。判定には Statistics 表の T01_Top〜T05_Order の行を使います。遅いトランザクションは、同じ表のリクエスト単位の行で、どのリクエストが遅いかを確かめます。判定の結果は、次のような表に書き込みます。

項目 目標 実測（記入例） 判定
T01_Top の 95th pct 2000ms 以内 12ms 合格
T02_Login の 95th pct 2000ms 以内 35ms 合格
T03_Browse の 95th pct 2000ms 以内 9ms 合格
T04_Search の 95th pct 2000ms 以内 1,012ms 合格
T05_Order の 95th pct 2000ms 以内 2,150ms 不合格
全体の Error % 1% 未満 0.00% 合格

※ 実測欄の数値は、判定表の書き方を示すための記入例（架空の値）です。あなたの環境で得られる値とは一致しません。T05_Order を不合格にしているのは、不合格が出たときの書き方を示すためです。

判定で大切なのは、合否だけでなく「なぜそうなったか」の仮説を添えることです。不合格の項目があれば、次の観点で原因を整理します。

  • 5 → 10 → 20 ユーザーの結果を並べたとき、どの段階から応答時間が伸びたか（限界に近づくサインは第13章）。
  • Errors 表に出たエラーの種類は何か。特定のトランザクションに偏っていないか。
  • JMeter を動かしている PC の CPU・メモリに余裕はあったか（測定側の限界ではないか）。
  • サーバー側の CPU・メモリ・DB・ログに異常はなかったか。JMeter が示すのは「どこが遅いか」までで、「なぜ遅いか」はサーバー側の調査が必要です。

14.7 報告書のまとめ方

性能テストは、結果を関係者が判断に使える形で伝えて初めて完結します。報告書は、次の構成にすると読み手が迷いません。1〜2ページに収まる簡潔さを目指しましょう。

項目 書く内容 記入例
目的 何のためにテストしたか 20ユーザー同時利用時に目標の応答時間を満たすかを確認する
対象 テストしたシステムとバージョン go-httpbin（Docker イメージ）を EC サイトの API に見立てたもの
環境 JMeter のバージョン、PC の性能、サーバーの構成、ネットワーク JMeter 5.6.3、JDK 21、同一 PC 上で実行（localhost）
シナリオ 操作の流れと、思考時間の設定 トップ → ログイン → 閲覧×3 → 検索 → 注文。思考時間は1〜2秒
負荷条件 ユーザー数、ランプアップ、実行時間 5→10→20ユーザー、ランプアップ10秒、各60/120/180秒
結果 主要な指標と、レポートへのリンクや抜粋 14.6 の判定表。results/u20 のレポートを添付
判定 目標に対する合否 6項目中5項目が合格、T05_Order の応答時間が不合格
考察 結果の理由についての仮説と、その根拠 10ユーザーまでは目標内で、20ユーザーで伸びた。注文処理が原因の可能性がある
次のアクション 誰が・何を・いつまでにするか サーバー側の監視を取りながら、注文処理を再測定する

報告書の注意: 学習環境の数値は本番の性能値ではない

この演習では、JMeter と go-httpbin が同じ PCで動き、ネットワークの遅延もありません。そのため、得られた数値は学習用の目安であり、本番システムの性能値ではありません。実務の報告書では、測定した環境と本番環境の違い（サーバーの性能、台数、ネットワーク、データ量）を必ず明記し、「この結果から本番についてどこまで言えるか」を書き添えましょう。

14.8 次のステップ

お疲れさまでした。これで性能テストの基本の流れを一通り体験できました。さらに力をつけたいときは、次のテーマに進んでみましょう。

分散テスト

1台の PC では出せない大きな負荷を、複数の PC（JMeter のリモート実行）に分けてかけます。まずは公式マニュアルの「Remote Testing」を読んでみましょう。

CI への組み込み

CLI モードはコマンド1つで動くため、GitHub Actions などで定期的に実行し、性能の劣化を早く見つけられます。.jmx はテキストなので Git で管理できます。

サーバー監視との併用

テスト中のサーバーの CPU・メモリ・DB・ログを同時に記録すると、「なぜ遅いか」を突き止められます。

プラグインの活用

Plugins Manager（第2章）から、段階的に負荷を上げる Custom Thread Groups などを追加できます。

関連する学習ガイドも、あわせて活用してください。

  • Docker 学習ガイド — テスト対象や JMeter の実行環境をコンテナで用意する
  • Linux・コマンドライン学習ガイド — サーバー上で CLI 実行やリソース監視を行う
  • Git/GitHub 学習ガイド — テスト計画（.jmx）をバージョン管理し、CI で実行する
  • JUnit 学習ガイド — 機能面の自動テストを学ぶ

やってみよう 14-1: テスト計画を作る

14.2 の目標と 14.3 のツリーに沿って、ch14-final.jmx を作成します。

手順

  1. 1 go-httpbin を起動し（docker start httpbin）、jmeter-practice に第8章で作った users.csv があることを確認する。
  2. 2 JMeter を英語表示で起動し、14.3 のツリーと設定表のとおりに要素を追加して、ch14-final.jmx として保存する（ch10-scenario.jmx の複製から始めてもよい）。
  3. 3 Thread Group に View Results Tree を追加し、すべてのトランザクションと HTTP Request の Name が T01_Top のように意味の分かる名前になっているか見直す。
確認: ツリーが 14.3 の構成図と一致し、HTTP Request Defaults の Server Name が localhost、Port が 8080 になっていれば完了です。

やってみよう 14-2: スモークテストで動作を確認する

1ユーザー・1ループで実行し、14.4 の表の内容をすべて確かめます。

手順

  1. 1 Thread Group で Loop Count を 1 にし、Specify Thread lifetime のチェックを外す。
  2. 2 Start（緑の三角）で実行し、View Results Tree で全サンプルが成功か、/bearer の応答が authenticated: true か、item に数字が入っているかを確認する。
  3. 3 赤いサンプルがあれば、Request と Response data を読んで原因を直し、全件成功するまで繰り返す。
  4. 4 合格したら、Loop Count を Infinite・Specify Thread lifetime のチェックありに戻し、View Results Tree を無効化（Ctrl+T）して保存する。
ヒント: /bearer の応答の token が NOT_FOUND になっていたら、抽出の失敗です（go-httpbin の /bearer はどんな値でも 200 を返すため、200 だけでは判断できません）。Header Manager が /bearer の子になっているかも確認してください。

やってみよう 14-3: 段階的に実行して報告書を書く

5 → 10 → 20 ユーザーで実行し、結果を判定して、1ページの報告書にまとめます。

手順

理解度確認クイズ

  1. Q1. 本番実行の前にスモークテストを行うのはなぜですか？ 何を確認しますか？

    回答を表示

    スクリプト自体の間違い（URL のミス、変数が埋まらない、トークンの相関の失敗など）を抱えたまま負荷をかけると、「システムが遅い」のか「スクリプトが間違っている」のか区別できなくなるからです。1ユーザー・1ループで実行し、全サンプルが成功すること、変数が正しく埋まっていること、トークンが次のリクエストに渡っていることを確認します。

  2. Q2. 負荷を一気に最大にせず、5 → 10 → 20 ユーザーと段階的に上げるのはなぜですか？ また、各段階の結果を別のフォルダに保存するのはなぜですか？

    回答を表示

    段階的に上げると、どの負荷から応答時間が伸びたりエラーが出たりするかが分かり、問題が起きた条件を特定しやすくなるからです。結果を段階ごとに別フォルダへ保存すれば、後から各段階のレポートを並べて比べられ、上書きによる結果の消失も防げます。

  3. Q3. この演習で得た応答時間の数値を、報告書にそのまま「本番の性能」として書いてはいけないのはなぜですか？

    回答を表示

    学習環境では JMeter と go-httpbin が同じ PC で動き、ネットワークの遅延もないため、サーバーの性能・台数・ネットワーク・データ量が異なる本番とは条件がまったく違うからです。得られた数値は学習用の目安にすぎないので、報告書には測定環境と本番との違いを明記し、結果から本番についてどこまで言えるかを書き添えます。
