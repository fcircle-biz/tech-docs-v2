ホーム JMeter 第7章
第7章 所要時間: 約1時間

アサーションで応答を検証する

「速く返ってきた」ことと「正しい中身が返ってきた」ことは別の話です。サーバーが過負荷になると、200 OK のままエラー画面や空のデータを返すことがあります。この章では、アサーション（Assertion）を使って応答の中身・応答時間・サイズを自動でチェックし、「速いが間違っている」応答を失敗として検出する方法を学びます。

この章で学ぶこと

  • ステータスコードだけでは成否を判断できない理由を説明できる
  • Response Assertion・JSON Assertion・Duration Assertion を設定できる
  • アサーションの失敗を View Results Tree や Summary Report で確認できる
  • 期待どおりのエラー（404 など）を成功扱いにする方法と、アサーションを入れすぎない心得を知る

7.1 なぜアサーションが必要か

第4章で見たように、JMeter は既定ではステータスコードが 4xx / 5xx のとき（や接続エラーのとき）だけサンプルを失敗とみなします。つまり、ステータスコードが 200 であれば、中身がどうであっても「成功」と数えてしまいます。

ところが現実のシステムでは、次のような「200 OK なのに実は失敗」というケースがよく起こります。

  • 負荷が高まると、アプリケーションが「ただいま混み合っています」というエラー画面を 200 で返す
  • データベースが応答できず、検索結果が空のリストで返ってくる
  • ログインに失敗しているのに、ログイン画面の HTML が 200 で返ってくる

これらを見逃すと、結果レポートには「エラー率 0%・応答時間も速い」と表示され、実際には壊れているのに合格に見えるという危険な状態になります。エラー画面は返すのが速いので、むしろ応答時間が良く見えてしまうことすらあります。

そこで登場するのがアサーション（Assertion、検証）です。アサーションは、サンプラーが受け取った応答に対して「この文字列が含まれているか」「この値が入っているか」「この時間以内に返ったか」といった条件を確かめ、満たさなければそのサンプルを失敗に変えます。

flowchart TD A["サンプラーがリクエストを送る"] --> B["応答を受け取る"] B --> C{"ステータスコードは
4xx か 5xx か"} C -->|はい| F["失敗"] C -->|いいえ| D{"アサーションの条件を
すべて満たすか"} D -->|はい| S["成功"] D -->|いいえ| F

※ 4xx/5xx を例外的に成功扱いにする方法（Ignore Status）は 7.7 で学びます。

アサーションは第3章で学んだとおり、サンプラーの実行後（Post Processor の後）に評価されます。置いた場所のスコープ内にあるサンプラーすべてに効き、サンプラーの子として置けばそのサンプラー1つだけに効きます。

重要ポイント

性能テストの目的は「速さ」だけでなく「正しい結果を返しながら速いこと」を確かめることです。応答時間やスループットの数字を信じる前提として、まずアサーションで「中身が正しい」ことを保証しておきましょう。

7.2 Response Assertion（応答の検証）

もっとも基本で、もっとも使うアサーションが Response Assertion（レスポンスアサーション）です。応答のさまざまな部分（本文・ステータスコード・ヘッダーなど）が、指定した文字列やパターンに合うかを確かめます。

追加するには、HTTP Request を右クリックして Add → Assertions → Response Assertion を選びます。サンプラーの子として追加すれば、そのサンプラーだけが検証対象になります。

項目 主な設定値 説明
Apply to Main sample and sub-samples／Main sample only／Sub-samples only／JMeter Variable Name to use どのサンプルを検証するか。通常は Main sample only（リダイレクトなどの子サンプルを含む場合に使い分ける）
Field to Test Text Response／Document (text)／URL Sampled／Response Code／Response Message／Response Headers／Request Headers／Request Data 応答のどの部分を検証するか。本文の確認は Text Response、ステータスは Response Code
Ignore Status チェックなし（既定）／あり チェックすると、先に失敗扱いになっていたサンプルも一度「成功」に戻してから検証する（7.7 で使う）
Pattern Matching Rules Contains／Matches／Equals／Substring（＋ Not・Or） パターンの照合方法（下の表を参照）
Patterns to Test Add ボタンで行を追加して入力 照合する文字列やパターン。複数行書くと、既定ではすべて満たす必要がある（Or を選ぶと1つでよい）
Custom failure message 任意の文章 失敗したときに結果へ表示するメッセージ。原因が一目でわかる文面にしておく

Pattern Matching Rules の4つの照合方法は、正規表現を使うかと全体一致か部分一致かで区別します。

ルール パターンの扱い 成功する条件
Contains 正規表現 応答のどこかに、パターンに合う部分がある（もっとも使いやすい）
Matches 正規表現 応答全体がパターンに合う（先頭から末尾まで）
Equals ただの文字列 応答全体がその文字列と完全に一致する（ステータスコードの確認に便利）
Substring ただの文字列 応答のどこかに、その文字列がそのまま含まれる（. や ( を含む文字列を正規表現の記号と誤解されずに探せる）

これらに加えて、Not（条件に合わないことを成功とする）と Or（複数パターンのどれか1つでよい）を組み合わせられます。たとえば「エラー」という文字が含まれていないことを確かめたいときは、Contains ＋ Not を選びます。

例: /html の本文に見出しがあることを確認する

go-httpbin の /html は、見出し <h1>Herman Melville - Moby-Dick</h1> を含む HTML ページを返します。本文に Herman Melville が含まれることを確かめる設定は次のとおりです。

項目 設定値 説明
Name 見出しがある 結果画面に表示される名前。何を確かめるかが伝わる名前にする
Apply to Main sample only リクエスト本体の応答を検証する
Field to Test Text Response 応答の本文を対象にする
Pattern Matching Rules Contains 本文のどこかに含まれていればよい
Patterns to Test Herman Melville 探す文字列
Custom failure message 見出しが見つかりません 失敗したときに表示される

ステータスコードを検証するには

Field to Test を Response Code、Pattern Matching Rules を Equals、Patterns to Test を 200 にすると「ステータスコードがちょうど 200 であること」を確かめられます。Contains はパターンを正規表現として扱い、部分一致で判定します。たとえば 20 と書くと 200・201・204 のどれにも一致してしまうため、ステータスコードは Equals で「ちょうどその値」かを確かめるのが安全です。

7.3 JSON Assertion（JSON の検証）

最近の Web API はほとんどが JSON を返します。本文を文字列として探す Response Assertion でも確かめられますが、JSON Assertion（JSON アサーション）を使うと、JSON の構造を理解したうえで特定の項目の存在や値を確かめられます。項目の場所は JSON Path（JSON の中の位置を指す書き方）で指定します。

JSON Path は、先頭の $ がルート（一番外側）を表し、. で階層をたどります。go-httpbin の /json は次のような JSON を返します（途中を省略しています）。

GET /json の応答（抜粋） 
{
  "slideshow": {
    "author": "Yours Truly",
    "date": "date of publication",
    "title": "Sample Slide Show",
    "slides": []
  }
}

この JSON では、$.slideshow.title が "Sample Slide Show"、$.slideshow.author が "Yours Truly" を指します（slides の中身は省略して空にしています）。

追加は Add → Assertions → JSON Assertion です。設定項目は次のとおりです。

項目 設定値（この例） 説明
Assert JSON Path exists $.slideshow.title この JSON Path が応答の中に存在することを確かめる
Additionally assert value チェックする 存在だけでなく、値も確かめる場合にチェックする
Match as regular expression チェックを外す 期待値を正規表現として扱うか。追加直後はチェックが入っている。今回は完全一致で確かめるので外す（入れたままでも、この期待値なら一致する）
Expected Value Sample Slide Show 期待する値。引用符（"）は付けずに書く
Expect null チェックしない 値が null であることを期待する場合にチェックする
Invert assertion チェックしない 結果を反転する。「この項目が存在しないこと」を確かめたいときに使う

同様に、$.slideshow.author の値が Yours Truly であることも確かめられます。JSON Assertion は1つにつき1つの JSON Path しか検証できないので、複数の項目を確かめたいときは JSON Assertion を複数並べます。

注意: 応答が JSON でないとどうなるか

サーバーがエラー時に JSON ではなく HTML を返した場合、JSON Assertion は「JSON として読めない」という理由で失敗します。これはアサーションが役目を果たしている状態です。失敗メッセージを確認して、原因が条件の書き間違いなのか、サーバーの異常なのかを見分けましょう。

7.4 Duration Assertion（応答時間の検証）

Duration Assertion（デュレーションアサーション）は、応答が返るまでの時間が指定したミリ秒以内かを確かめます。「このページは1.5秒以内に表示される」といった性能の合格ラインを、テストの中に直接書き込めます。

項目 設定値（この例） 説明
Duration in milliseconds 1500 許容する最大の応答時間（ミリ秒）。これを超えると失敗

動作を確かめるには、go-httpbin の /delay/2（2秒待ってから応答するエンドポイント）を対象にします。2秒かかるので、1500ms の条件には合わず失敗します。失敗時の結果には、次のようなメッセージが表示されます。

失敗メッセージの例 
# Assertion result 欄に表示される失敗メッセージ
# 下の英文は「2秒かかったが、1500ミリ秒を超えてはいけない」という意味
The operation lasted too long: It took 2,0xx milliseconds,
but should not have lasted longer than 1,500 milliseconds.

Duration Assertion の使いどころ

Duration Assertion で失敗扱いにすると、遅い応答もエラー率に反映されます。便利ですが、「遅いこと」と「壊れていること」が同じ Error % に混ざる点には注意が必要です。応答時間の良し悪しは第13章のレポートのパーセンタイルで分析するのが基本で、Duration Assertion は「この時間を超えたら明らかに許容できない」という絶対的な上限に使うと分かりやすくなります。

7.5 Size Assertion とその他のアサーション

Size Assertion（サイズアサーション）は、応答のサイズ（バイト数）が条件を満たすかを確かめます。「応答が空でないこと」や「ダウンロードしたファイルが一定以上の大きさであること」を手軽に確かめられます。

項目 設定値の例 説明
Response Size Field to Test Full Response／Response Headers／Response Body／Response Code／Response Message どの部分のサイズを測るか。本文なら Response Body
Size to Assert 100 比較の基準にするバイト数
Type of Comparison =／!=／>／<／>=／<= 比較方法。「100バイトより大きい」なら >

このほかにも、JMeter には次のようなアサーションがあります。本ガイドでは使いませんが、必要になったときに探せるよう名前だけ紹介します。

  • XPath2 Assertion: XML や HTML の特定の要素を XPath で検証する
  • XML Assertion: 応答が正しい XML として読めるかを検証する
  • MD5Hex Assertion: 応答の MD5 ハッシュ値が期待どおりかを検証する（ファイルが壊れていないかの確認など）
  • JSR223 Assertion: スクリプトで自由に検証ロジックを書く（複雑な条件向け）

初心者のうちは、Response Assertion・JSON Assertion・Duration Assertion の3つを使いこなせれば、ほとんどの検証をまかなえます。

7.6 アサーションの失敗を確認する

アサーションに失敗したサンプルは、View Results Tree で赤いアイコンの「失敗」として表示されます。結果の詳細を見る場所は次のとおりです。

確認する場所 わかること
View Results Tree のツリー 赤いサンプルの左の ▶ を開くと、失敗したアサーション名（例: Duration Assertion）が子として並ぶ。選ぶと右側の最初のタブが「Assertion result」になり、Assertion failure message に失敗理由が出る。原因調査の基本
Assertion Results リスナー サンプルごとの全アサーションの結果を一覧で見られる。Add → Listener → Assertion Results で追加する。View Results Tree と同じく、デバッグ専用。負荷実行の前には無効化する
Summary Report の Error % アサーション失敗もエラーとして集計される。全体のどれくらいが失敗したかを数値で把握できる

つまり、アサーションを仕込んでおけば、あとはいつもどおり Summary Report や HTML レポート（第13章）の Error % を見るだけで、「中身が壊れた応答」が混ざっていないかが分かります。失敗の内訳は、アサーションの Name と Custom failure message が手がかりになるため、7.2 で述べたように具体的な名前とメッセージを付けておきましょう。

7.7 期待するエラーを成功扱いにする

ここまでは「正しい応答が返ること」を確かめてきました。ところがテストによっては、わざと異常な操作をして、エラーが返ることを確かめたい場合があります（ネガティブテストと呼びます）。たとえば「存在しないページにアクセスしたら 404 が返ること」や、「トークン無しなら 401 が返ること」は、システムとして正しい動作です。

ところが JMeter は 404 や 401 を既定で失敗として数えるため、そのままでは「正しく 404 を返した」のにエラー率が上がってしまいます。このようなときは、Response Assertion の Ignore Status を使います。

項目 設定値 説明
対象のサンプラー GET /status/404 404 を返すエンドポイント。このサンプラーの子としてアサーションを置く
Field to Test Response Code ステータスコードを検証する
Ignore Status チェックする 404 による「失敗」判定をいったん取り消し、このアサーションの結果で成否を決め直す
Pattern Matching Rules Equals 完全一致で確かめる
Patterns to Test 404 404 が返ったら成功。200 が返ったらむしろ失敗になる

この設定にすると、「404 が返る」ことが成功、「それ以外が返る」ことが失敗となり、期待どおりのエラーがエラー率を汚さなくなります。

注意: Ignore Status は必ず「期待する値」とセットで

Ignore Status をチェックしただけでは、本物のエラー（想定外の 500 など）まで成功に変えてしまいかねません。必ず Response Code を Equals で期待値と照合するパターンを書き、想定外の応答は失敗になるようにしてください。また、サンプラー単位で効かせるために、アサーションはそのサンプラーの子に置きます。なお、Ignore Status はそれより前に評価されたアサーションの失敗も取り消してしまうため、そのサンプラーの子の中で最初に評価されるアサーションにだけ付けます。

7.8 アサーションを入れすぎない

アサーションは便利ですが、無料ではありません。応答を1件受け取るたびに、本文の検索や JSON の解析を行うため、JMeter 自身の CPU とメモリを消費します。大量のスレッドを動かす本番の負荷実行で、あらゆるリクエストに重いアサーションを付けると、JMeter 側がボトルネックになって測定値が不正確になるおそれがあります。

アサーションを付けたい応答

  • ログイン・注文など、業務上の重要な操作
  • 後続の処理が依存する応答（トークンを取り出す元など）
  • 負荷が高まると壊れやすい、検索などの重い処理

付けなくてよい応答

  • 画像・CSS・JavaScript などの静的ファイル
  • どのリクエストにも同じ内容を確かめるだけの検証
  • 応答全体を長大な正規表現で照合する検証

指針は3つです。(1) 重要な応答に絞る、(2) 検証は軽い方法を選ぶ（本文全体への複雑な正規表現より、Substring や JSON Path の存在確認など）、(3) アサーションはスコープを意識してサンプラーの子に置き、全サンプラーに一律で効かせない。

やってみよう 7-1: 3種類のアサーションを設定する

go-httpbin を起動した状態で、ch07-assertions.jmx を作ります。jmeter-practice フォルダに保存してください。

手順

  1. 1 Thread Group（1スレッド・ループ1回）の下に HTTP Request Defaults（http／localhost／8080）と View Results Tree を置く。
  2. 2 HTTP Request を3つ作る。名前と Path は「HTML」/html、「JSON」/json、「遅い応答」/delay/2。
  3. 3 「HTML」の子に Response Assertion（Text Response・Contains・Herman Melville）を追加する。
  4. 4 「JSON」の子に JSON Assertion を追加し、JSON Path $.slideshow.title、Additionally assert value にチェック、Match as regular expression のチェックを外し、Expected Value に Sample Slide Show を設定する。
  5. 5 「遅い応答」の子に Duration Assertion を追加し、3000 ミリ秒を設定する。
  6. 6 Start（緑の三角）で実行し、View Results Tree で3件とも緑のアイコン（成功）になることを確認する。
うまくいかないときは: アサーションが「サンプラーの子」になっているか（ツリーで一段深く表示されているか）を確認します。Thread Group 直下に置くと3つのサンプラー全部に効いてしまい、意図しない失敗になります。

やってみよう 7-2: わざと失敗させて結果の見え方を確認する

アサーションが失敗したとき、結果がどう見えるかを体験します。

手順

  1. 1 Duration Assertion の値を 1500 に下げて実行する。「遅い応答」が赤いアイコンになる。その ▶ を開いて Duration Assertion を選び、Assertion failure message に所要時間のメッセージが出ることを確認する。
  2. 2 Response Assertion のパターンを Jane Austen に書き換え、Custom failure message に「見出しが見つかりません」と入れて実行し、メッセージが表示されることを確認する。
  3. 3 Thread Group に Summary Report を追加して再実行し、TOTAL 行の Error % が 66.67%（3件中2件が失敗）になり、失敗させた2つの行（「HTML」「遅い応答」）は 100%、成功する行（「JSON」）は 0% になることを確認する。
  4. 4 （発展）/status/404 の HTTP Request を追加し、7.7 の設定（Ignore Status ＋ Response Code Equals 404）で成功扱いにする。Ignore Status を外すと失敗に戻ることも確かめる。
確認後: 元の値（Duration 3000、パターン Herman Melville）に戻して保存しておくと、後の章の復習で使いやすくなります。

理解度確認クイズ

  1. Q1. ステータスコードが 200 なのに、アサーションが必要になるのはなぜですか？

    回答を表示

    JMeter は既定では 4xx / 5xx のときだけ失敗とみなすため、200 で返ってきたエラー画面や空のデータも「成功」と数えてしまうからです。アサーションで応答の中身を確かめておけば、「速いが間違っている」応答を失敗として検出でき、エラー率や応答時間の数字を信頼できます。

  2. Q2. Response Assertion で、応答の本文のどこかに「Herman Melville」が含まれることを確かめるには、Field to Test と Pattern Matching Rules に何を選びますか？

    回答を表示

    Field to Test は「Text Response」、Pattern Matching Rules は「Contains」（または Substring）を選び、Patterns to Test に Herman Melville を入れます。Equals や Matches は応答全体との一致を見るため、「どこかに含まれる」確認には向きません。

  3. Q3. 存在しないページが 404 を返すことを確かめるテストで、エラー率を上げずに済ませるにはどう設定しますか？

    回答を表示

    そのサンプラーの子に Response Assertion を置き、Field to Test を「Response Code」、Pattern Matching Rules を「Equals」、パターンを 404 にして、Ignore Status をチェックします。404 による失敗判定を取り消したうえで、アサーションの結果（404 が返れば成功、それ以外は失敗）で成否が決まります。
