ホーム JMeter 第4章
第4章 所要時間: 約1時間10分

はじめてのHTTPリクエスト

いよいよ JMeter から実際にリクエストを送ります。この章では、接続先を共通化する HTTP Request Defaults、GET と POST のリクエスト、結果を確認する View Results Tree と Summary Report の読み方、そしてエラーがどのように見えるかを、練習用サーバー go-httpbin を相手に体験します。

この章で学ぶこと

  • HTTP Request Defaults で接続先をまとめ、GET リクエストを作成して実行できる
  • View Results Tree で Load time・Latency・Connect Time・応答内容を読める
  • HTTP Header Manager と Body Data で JSON を POST できる
  • Summary Report の主な列を読み、エラー（4xx／5xx）の見え方と実行の止め方を理解する

4.1 HTTP の基礎のおさらい

JMeter の HTTP Request が作っているのは、ブラウザが送るものと同じ HTTP リクエストです。画面の設定項目を理解しやすくするために、リクエストとレスポンスの構成要素を整理しておきましょう。

リクエスト（送るもの）

  • メソッド: GET（取得）、POST（送信）など
  • URL: 宛先（サーバー名・ポート・パス・クエリ）
  • ヘッダー: 付加情報（Content-Type など）
  • ボディ: 送るデータ本体（POST などで使う）

レスポンス（返ってくるもの）

  • ステータスコード: 結果を表す3桁の数字
  • ヘッダー: 応答の付加情報
  • ボディ: HTML や JSON などの本体

ステータスコードは、結果を大まかに分類する数字です。性能テストでは「成功したか失敗したか」の判定に使われるため、代表的なものを覚えておきましょう。

コード 意味 性能テストでの扱い
200 OK（成功） 成功として数えられる
302 別の URL へ移動せよ（リダイレクト） JMeter は既定で移動先まで自動で追いかける（第9章の Cookie の例で登場）
401 認証が必要（ログインしていない） 失敗として数えられる
404 見つからない（URL の誤り） 失敗として数えられる
500 サーバー内部のエラー 失敗として数えられる。負荷が高すぎるときに増えやすい

大まかには、2xx は成功、3xx は移動、4xx は呼び出し側の問題、5xx はサーバー側の問題です。

4.2 HTTP Request Defaults で接続先を共通化する

テスト計画には HTTP Request（HTTP リクエスト）を何本も作ります。そのたびに「localhost の 8080 番ポートへ」と書くのは手間ですし、接続先を変えるときに全部直すのは間違いのもとです。そこで、接続先を HTTP Request Defaults（HTTP リクエスト初期値設定）にまとめておきます。これは第3章で学んだ Config Element（設定エレメント）の一種で、スコープ内のすべての HTTP Request に既定値として効きます。

まず、第3章で作った構成を土台に、次のようなツリーを作ります。ch04-first-request.jmx という名前で保存してください。 

Test Plan
└── Thread Group
    ├── HTTP Request Defaults        ← 接続先をまとめる
    ├── HTTP Request  GET /get       ← 4.3 で作成
    ├── HTTP Header Manager          ← 4.5 で追加（JSON 用）
    ├── HTTP Request  POST /post     ← 4.5 で作成
    ├── HTTP Request  GET /status/500 ← 4.7 で作成
    ├── View Results Tree            ← 4.4 で追加
    └── Summary Report               ← 4.6 で追加

Thread Group を右クリックし、Add → Config Element → HTTP Request Defaults を選びます。Web Server 欄に次のように入力します。

項目 設定値 説明
Protocol [http] http 通信方式。練習用サーバーは暗号化なしの http
Server Name or IP localhost 接続先のサーバー名。自分の PC を指す
Port Number 8080 go-httpbin が待ち受けているポート番号

この設定をしておくと、各 HTTP Request では Path（パス）だけを書けば済みます。本番に近い環境へ切り替えるときも、ここ1か所を直すだけで全リクエストの宛先が変わります。

Defaults と個別設定の優先順位

HTTP Request 側の Server Name 欄などを空欄のままにしておくと、Defaults の値が使われます。個別のリクエストに値を書くと、そちらが優先されます。意図せず別の宛先に送らないよう、個別の欄は空にしておくのが基本です。

4.3 GET リクエストを作る

最初のリクエストを作りましょう。Thread Group を右クリックして Add → Sampler → HTTP Request を選びます。Sampler（サンプラー）は、実際にリクエストを送る要素です。Name 欄を GET /get のようにわかりやすい名前に変え、次のように設定します。

項目 設定値 説明
Name GET /get ツリーや結果に表示されるラベル
Method GET HTTP メソッド（プルダウンで選ぶ）
Path /get サーバー内の場所。接続先は Defaults から補われる
Parameters タブ name = jmeter Add ボタンで1行追加し、Name と Value を入れる。送信時に ?name=jmeter となる

Path に /get?name=jmeter と直接書くこともできますが、Parameters タブに分けて書くと値の管理や変数化（第8章）がしやすくなります。この設定は、ブラウザで http://localhost:8080/get?name=jmeter を開くのと同じ通信になります。

この /get は、受け取ったリクエストの内容を JSON にして返すエンドポイントです。応答は次のような形になります（見やすいよう一部のみ抜粋）。go-httpbin では args や headers の値が配列で返る点に注意してください。

GET /get?name=jmeter の応答（抜粋） 
{
  "args": {
    "name": ["jmeter"]
  },
  "headers": {
    "Host": ["localhost:8080"],
    "User-Agent": ["Apache-HttpClient/..."]
  },
  "method": "GET",
  "url": "http://localhost:8080/get?name=jmeter"
}

args に送ったパラメータ、headers に JMeter が付けたヘッダーが入っています。User-Agent が Apache-HttpClient で始まっていることから、「ブラウザではなく JMeter から送られた」ことが確認できます。

4.4 View Results Tree の読み方

リクエストを送っても、結果を見る場所がなければ何も確認できません。結果を表示する要素を Listener（リスナー）と呼びます。Thread Group を右クリックして Add → Listener → View Results Tree を追加しましょう。ツールバーの緑の再生ボタン（Start）を押すと、リクエストが1回実行され、結果が左側に一覧で現れます。

一覧の各行が1件のサンプル（第1章で学んだ「1回のリクエストの結果」）です。緑の盾マークは成功、赤は失敗を表します。サンプルをクリックすると、右側に3つのタブが並びます。

タブ 見られる内容
Sampler result 時間・サイズ・ステータスコードなどの測定値の一覧
Request 実際に送ったリクエスト（メソッド・URL・ヘッダー・ボディ）
Response data サーバーが返した本文。左下のプルダウン（既定は Text）を JSON に切り替えると整形されて読みやすくなる

Sampler result タブの主な項目は、次のとおりです。

項目 意味
Load time リクエストを送る直前から、応答を最後まで受け取るまでの時間（ms）。いわゆる応答時間で、性能テストで最も重視する値
Latency リクエストを送る直前から、応答の最初の部分が届くまでの時間（ms）
Connect Time サーバーとの接続を確立するのにかかった時間（ms）。https では暗号化の準備も含む
Response code ステータスコード（例: 200）
Size in bytes 受け取ったデータの大きさ（ヘッダー＋本文）

Load time・Latency・Connect Time は似た名前ですが、同じ起点から測った「どこまでの時間か」の違いです。次の図で位置関係をつかみましょう。

flowchart LR S["送信の直前
（計測の起点）"] --> C["接続の確立が完了
Connect Time の終点"] C --> L["最初の応答が到着
Latency の終点"] L --> E["応答を最後まで受信
Load time の終点"]

つまり、Connect Time ≦ Latency ≦ Load time の関係になります（Latency には接続の時間も含まれ、本文が小さいと Latency と Load time はほぼ同じ値になります）。なお、同じスレッドが接続を再利用（Keep-Alive）した2件目以降は接続の確立が要らないため、Connect Time は 0 と表示されます。同じ PC 内の go-httpbin では、どれも数ミリ秒程度の小さな値になります。Latency と Load time の差が大きい場合は、応答の本文が大きくて受信に時間がかかっていると読み取れます。

View Results Tree は負荷中に使わない

View Results Tree はリクエストと応答の中身をすべて記録するため、大量のメモリを使います。動作確認やデバッグ専用と考え、本番の負荷実行では無効にします（第12章）。

4.5 POST で JSON を送る

Web API では、データを JSON 形式でサーバーへ送る POST リクエストがよく使われます。JSON を送るには、「これは JSON ですよ」とサーバーに伝えるヘッダーと、ボディの内容の2つが必要です。

ステップ1: HTTP Header Manager でヘッダーを付ける

Thread Group を右クリックし、Add → Config Element → HTTP Header Manager を追加します。Add ボタンで1行追加し、次のように入力します。

Name Value 説明
Content-Type application/json ボディが JSON 形式であることを伝える

Header Manager も Config Element なので、置いた場所がスコープになります。Thread Group 直下に置くと、すべてのサンプラーに Content-Type: application/json が付きます。GET の /get に付いても害はありませんが、気になる場合は POST の HTTP Request の子要素として置けば、そのサンプラーだけに効きます（第3章のスコープの考え方です）。

ステップ2: POST の HTTP Request を作る

もう1つ HTTP Request を追加し、次のように設定します。ボディは Body Data タブに書きます（Parameters タブではありません）。

項目 設定値 説明
Name POST /post わかりやすいラベル
Method POST データを送信するメソッド
Path /post 受け取った内容を返すエンドポイント
Body Data タブ 下記の JSON 送信するボディをそのまま入力する
Body Data に入力する JSON 
{"user": "alice", "item": 1}

実行して Response data を JSON 表示にすると、json フィールドに送った内容がそのまま入って返ってきます。これで、サーバーが JSON として正しく受け取ったことを確認できます。

POST /post の応答（抜粋） 
{
  "json": {
    "user": "alice",
    "item": 1
  },
  "method": "POST",
  "url": "http://localhost:8080/post"
}

重要ポイント: 応答の中身で確認する癖をつける

ステータスコードが 200 でも、送った内容が正しく届いているとは限りません。Request タブで実際に送った内容を、Response data で返ってきた内容を、必ず目で確かめましょう。応答の中身を自動でチェックする方法（アサーション）は第7章で学びます。

4.6 Summary Report で集計する

View Results Tree は1件ずつ中身を見るのに向いていますが、「全体としてどうだったか」はわかりません。そこで、サンプルをラベル（HTTP Request の名前）ごとに集計する Summary Report を追加します。Add → Listener → Summary Report を選んでください。

実行すると、リクエストごとに1行、最後に全体の合計行（TOTAL）が表示されます。主な列は次のとおりです。

列 意味
# Samples 実行したリクエストの件数（サンプル数）
Average 応答時間（Load time）の平均（ms）
Min／Max 応答時間の最小値／最大値（ms）
Std. Dev. 応答時間のばらつき（標準偏差）。大きいほど不安定
Error % 失敗したサンプルの割合
Throughput 1秒あたりに処理した件数（件/秒）。1件/秒に満たないほど頻度が低いときは、表示が1以上になるよう「/min」「/hour」に単位が切り替わる（例: 0.5件/秒 → 30.0/min）

このほか Received KB/sec・Sent KB/sec・Avg. Bytes といった通信量の列もあります。なお、Summary Report にはパーセンタイルが出ません。90・95・99 パーセンタイルは、第12〜13章で学ぶ HTML レポートで確認します。

4.7 エラーの見え方

わざとエラーを起こして、失敗がどう表示されるかを見ておきましょう。go-httpbin の /status/コード は、指定したステータスコードをそのまま返します。3つ目の HTTP Request を作り、Name を GET /status/500、Method を GET、Path を /status/500 にして実行します。

View Results Tree では、このサンプルが赤いアイコンで表示され、Response code が 500 になります。Summary Report でも、この行の Error % が 100% になります。JMeter は、4xx や 5xx のステータスコードを自動的に失敗として扱うためです。

flowchart TD A["サーバーから応答が返る"] --> B{"ステータスコード"} B -->|"2xx または 3xx"| C["成功
緑のアイコン"] B -->|"4xx または 5xx"| D["失敗
赤いアイコン、Error % に加算"] A --> E["接続できない／時間切れ"] E --> D

「成功」は「中身が正しい」ではない

200 が返っていれば、JMeter は成功と数えます。たとえエラー画面や空のデータが返っていても同様です。このためステータスコードだけでは検証として不十分で、第7章のアサーションが必要になります。

4.8 実行・停止・結果のクリア

ツールバーにある実行まわりのボタン（メニューの Run からも同じ操作ができます）の違いを整理します。

ボタン 動作 使いどころ
Start
Run → Start（Ctrl + R）		 テスト計画を実行する 通常の実行
Stop
Run → Stop（Ctrl + .）		 実行中のスレッドをすぐに止める 設定ミスに気づいて緊急停止したいとき
Shutdown
Run → Shutdown（Ctrl + ,）		 新しい処理は始めず、実行中のリクエストの完了を待って穏やかに止める 結果を欠けさせずに終わらせたいとき
Clear All
Run → Clear All（Ctrl + E）		 リスナーに溜まった結果をすべて消す 再実行の前。消し忘れると前回の結果と混ざる

再実行の前に Clear All

リスナーの結果は、実行するたびに前回の続きに追加されます。Summary Report の件数や平均が思った値と違うときは、Clear All を忘れていないか確認しましょう。ほうきのアイコンは Clear（選択中のリスナーだけ消す）と Clear All（すべて消す）の2つがあるので、マウスを乗せて名前を確かめてください。実行中は、画面右上に動作中を示す小さな緑の四角が表示され、終わると灰色に戻ります。

宛先は localhost のままにする

この章のリクエストは1回ずつの少量ですが、今後の章では負荷を上げていきます。HTTP Request Defaults の Server Name が localhost であることを、実行前に必ず確認してください。他人・他社のサーバーへ許可なく送ってはいけません。

やってみよう 4-1: 3種類のリクエストを作って実行する

go-httpbin を起動した状態で（docker start httpbin）、GET・POST・エラーの3つのサンプラーを持つテスト計画を作り、1回実行して結果を確認します。

手順

  1. 1 JMeter を起動し、Test Plan → Thread Group（Number of Threads: 1、Loop Count: 1）を作る。
  2. 2 HTTP Request Defaults（http／localhost／8080）を追加する。
  3. 3 HTTP Request を3つ作る。GET /get（パラメータ name=jmeter）、POST /post（Body Data に JSON）、GET /status/500。POST 用に HTTP Header Manager（Content-Type: application/json）も追加する。
  4. 4 View Results Tree と Summary Report を追加し、jmeter-practice/ch04-first-request.jmx として保存する。
  5. 5 Start で1回実行し、View Results Tree で3件のサンプルを確認する。GET の args.name、POST の json.user を Response data（JSON 表示）で読む。
期待する結果: GET と POST は緑のアイコン（Response code 200）、/status/500 だけが赤いアイコン（Response code 500）になります。

やってみよう 4-2: Summary Report の値を読む

4-1 の結果を、集計の数字で読み解きます。

手順

  1. 1 Clear All で結果を消してから、もう一度 Start で実行する。
  2. 2 Summary Report の各行の # Samples と Error % を読み取る（3行とも1件、エラー率は 0%・0%・100% になる）。
  3. 3 TOTAL 行の Error % が約 33.33% になる理由を、「3件中1件が失敗」という言葉で説明する。
  4. 4 Clear All を押さずにもう一度 Start を押し、# Samples が増える（前回の結果に追加される）ことを確認する。
ヒント: 平均や最大の値は実行のたびに数ミリ秒単位でぶれます。同じ値にならなくても問題ありません。学習環境の数値は目安であり、本番の性能値ではないことも思い出しましょう。

理解度確認クイズ

  1. Q1. 接続先を HTTP Request Defaults にまとめると、どのような利点がありますか？

    回答を表示

    各 HTTP Request では Path だけを書けばよくなり、入力の手間と間違いが減ります。また、接続先を変えたいときも Defaults の1か所を直すだけで、スコープ内のすべてのリクエストの宛先を切り替えられます。

  2. Q2. View Results Tree の Load time・Latency・Connect Time を、短い順に並べてください。それぞれは何を表しますか？

    回答を表示

    Connect Time ≦ Latency ≦ Load time の関係です（本文が小さいと Latency と Load time はほぼ同じ値になります）。Connect Time は接続の確立まで、Latency は応答の最初の部分が届くまで、Load time は応答を最後まで受け取るまでの時間を表します（いずれも送信直前を起点に測ります）。性能テストでは、応答時間として Load time を主に見ます。

  3. Q3. /status/500 を実行したサンプルは、View Results Tree と Summary Report でどう表示されますか？ また、200 が返ったサンプルが「中身も正しい」とは限らないのはなぜですか？

    回答を表示

    JMeter は 4xx／5xx を自動的に失敗として扱うため、View Results Tree では赤いアイコン、Summary Report ではその行の Error % が 100% になります。一方、200 が返れば成功と数えられるので、エラー画面や空のデータが返っていても成功扱いになります。中身の検証には、第7章で学ぶアサーションが必要です。
