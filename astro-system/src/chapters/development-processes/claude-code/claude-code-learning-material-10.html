ホーム Claude Code 第10章
第10章 所要時間: 約45分

Git連携とコードレビュー

この章では、Claude Code に組み込まれた git 連携の機能を学びます。プルリクエスト（PR）をプッシュする前に code-reviewer サブエージェントでバイアスのないレビューを受け、/commit-push-pr でコミットから PR 作成までを一気に済ませ、Slack 通知でチームに共有し、後日 claude --from-pr で作業を再開する――という一連の流れを、それぞれの仕組みとあわせて追っていきます。

この章で学ぶこと

  • Claude Code に組み込まれた git 連携機能の全体像をつかむ
  • code-reviewer サブエージェントを読み取り専用に設計するベストプラクティスを説明できる
  • サブエージェントによるレビューが「まっさらな視点」になる理由を理解する
  • /commit-push-pr と Slack MCP 連携で、コミットからチーム通知までの流れを把握する
  • claude --from-pr で中断したPR作業を再開できることを理解する

10.1 Claude Code の Git 連携機能

Claude Code には、git を使った作業の流れを速くする機能がいくつも組み込まれています。第5〜6章では「1つの機能を実装してコミットする」までの Explore→Plan→Code→Commit ワークフローを学びましたが、実際のチーム開発では、プッシュする前のレビューや、PR作成後のやり取りも欠かせない工程です。この章では、その前後の工程を Claude Code がどう支援してくれるかを見ていきます。

大きく分けると、次の3つの場面で力を発揮します。

プッシュ前のレビュー

code-reviewer サブエージェントに、まっさらな視点で変更内容をチェックしてもらいます。

コミット〜PR作成

スキルでコミット・プッシュ・PR作成をひとまとめに実行します。

PR作業の再開

後日そのPRのセッションに戻って、続きから作業できます。

10.2 サブエージェントによるレビュー

PR をプッシュする前に、Claude にサブエージェントを使って変更内容をレビューしてもらいましょう。ポイントは、サブエージェントが独自のコンテキストウィンドウの中で動作することです。

そのセッションでコードを書き続けてきたメインエージェントが持っているバイアスを引きずらず、まっさらな視点でレビューできる。

自分（あるいはメインエージェント）がずっと向き合ってきたコードを、自分自身で見直すのは簡単ではありません。実装の経緯や「なぜこう書いたか」という文脈を覚えているぶん、無意識に見落としを正当化してしまうことがあるからです。code-reviewer サブエージェントは、その経緯を知らない状態で diff だけを渡されるため、初めて読むコードとして純粋に評価できます。

観点 メインエージェントが自分で見直す code-reviewer サブエージェントに任せる
保持している文脈 実装中の試行錯誤をすべて覚えている diff など、レビューに必要な情報だけを見る
視点 「自分が書いた」という先入観が働きやすい 初めて見るコードとして評価できる
コンテキストウィンドウ 実装作業で消費した分がそのまま残っている 新しいウィンドウを気兼ねなく使える

ヒント: 第9章の応用

サブエージェントが独自のコンテキストウィンドウを持つという仕組みは、第9章で学んだとおりです。code-reviewer は、その仕組みを「レビューの偏りをなくす」という目的のために活用した具体例といえます。

10.3 code-reviewer サブエージェント作成のベストプラクティス

code-reviewer のようなレビュー専用のサブエージェントを作成するときは、次の2つのベストプラクティスを押さえておきましょう。

1

読み取り専用のツールだけに制限する

レビュー担当は問題点を指摘するだけの役割で、ファイルを編集すべきではありません。tools に Read・Grep・Glob など読み取り系だけを列挙し、Edit・Write は含めません。こうすることで、「レビューのつもりが勝手に修正されていた」という事故を構造的に防げます。

2

設定をリポジトリにチェックインする

.claude/agents/code-reviewer.md を通常のファイルとしてコミットします。チーム全員が同じレビュー担当を使えるようになり、「人によってチェックの厳しさが違う」といったばらつきがなくなります（第8章で学んだ CLAUDE.md のチーム共有と同じ考え方です）。

第9章で学んだ YAML フロントマター形式に沿って、実際に読み取り専用へ制限した定義例を見てみましょう。

.claude/agents/code-reviewer.md 
---
name: code-reviewer
description: PRを作成する前にdiffをレビューし、問題点を指摘する。プロアクティブに使用する。
tools: Read, Grep, Glob, Bash
model: sonnet
---

あなたは経験豊富なコードレビュアーです。git diff の内容を確認し、
以下の観点で問題点を指摘してください。

- バグ・エッジケースの見落とし
- 命名や可読性
- 既存コードとの一貫性
- セキュリティ・パフォーマンスへの影響

指摘のみを行い、ファイルは一切編集しないこと。

tools に何を含め、何を含めないかを整理すると次のようになります。

ツール 役割 code-reviewer に含める
Read ファイルの内容を読む ○
Grep / Glob コードをキーワード・パターン検索する ○
Bash シェルコマンドを実行する（git diff の読み取りに使う） ○（settings.json の permissions.allow でコマンドを絞り込むのが前提）
Edit / Write / MultiEdit ファイルを書き換える ×

注意: tools に書けるのはツール名だけ

サブエージェント frontmatter の tools は、Read, Grep, Glob, Bash のようにツール名をカンマ区切りで列挙する書き方だけを受け付けます。Bash(git diff:*) のようにサブコマンド単位で絞り込む記法は frontmatter では機能しません。Bash のようなコマンド実行系ツールを許可する場合は、.claude/settings.json の permissions.allow 側で Bash(git diff:*) のように実行できるコマンドを絞り込むと安全です。レビュー担当はこの2段構えで、実質的に読み取り専用のツールだけに制限しましょう。

10.4 /commit-push-pr スキル

コミット・プッシュ・PR作成という3つの操作は、/commit-push-pr というスキルを用意しておくと、実行するだけでひとまとめに行えます。1つずつ手作業で行う代わりに、Claude がまとめて処理してくれます。

注意: /commit-push-pr は標準搭載のコマンドではない

/commit-push-pr は Claude Code に標準搭載されているコマンドではなく、スキルとして用意されている場合に使えるものです。素の Claude Code にはこのコマンドは存在しません。同じ流れは、「コミットしてプッシュし、PR を作成して」と自然文で依頼することでも実現できます。

terminal — /commit-push-pr 実行例 
$ claude
> /commit-push-pr

● 変更内容を確認しています…
● コミットメッセージを作成しました。
● リモートにプッシュしました。
● PR を作成しました: https://github.com/example/repo/pull/123

もっと詳しく: スキル（Agent Skills）とは

/commit-push-pr のように、名前を指定するだけで一連の手順をまとめて実行できる仕組みをスキル（Agent Skills）と呼びます。仕組みや自分で作る方法は、別ガイド「Claude Code Skills 入門」で詳しく学びます。ここでは「呼び出すだけでコミット〜PR作成が完了する」という体験を押さえておきましょう。

10.5 Slack MCP 連携でチームに自動通知

CLAUDE.md にチームの通知先チャンネルを記載した Slack MCP サーバーを設定していると、/commit-push-pr などで作成した PR のリンクが、そのままチームのチャンネルへ自動投稿されます。レビュー担当やチームメンバーに、改めて共有し直す必要がありません。

CLAUDE.md（抜粋） 
# Notifications

PRを作成したら、Slackの #dev-notify チャンネルに
リンクを共有してください。

第11章で詳しく

Slack MCP サーバーをどう追加し、どの範囲（スコープ）でチームと共有するかは、次の第11章「MCPで外部ツールとつなぐ」で扱います。ここでは、CLAUDE.md に一言書いておくだけで通知が自動化される、という体験だけ押さえておけば十分です。

10.6 --from-pr によるセッションの引き継ぎ

Claude が gh pr create を使って PR を作成すると、そのセッションは自動的にその PR に紐づけられます。gh は GitHub が提供するコマンドラインツール（GitHub CLI）で、別途インストールが必要です。後日そのPRに戻って作業したいとき――たとえばレビューコメントへの対応や、CI（継続的インテグレーション: プッシュのたびに自動でビルドやテストを実行する仕組み）のビルド失敗の修正が必要になったとき――は、次のコマンドを実行します。

terminal — セッション再開の例 
$ claude --from-pr 482
> PR #482 のセッションを再開しました。
> レビューコメントで指摘された null チェック漏れを直してください。

● src/api/user.ts の該当箇所を確認しています…
● null チェックを追加しました。
● npm test を実行しました（20件すべて成功）。
● 修正をコミットしてプッシュしますか？

重要ポイント: PR番号さえ覚えておけば同じ文脈に戻れる

gh pr list で PR 番号を確認し、claude --from-pr <PR_NUMBER> を実行するだけで、何日たっても中断したところから続きを再開できます。新しいセッションを立ち上げて、また経緯を説明し直す必要はありません。

10.7 まとめ: Git連携のライフサイクル

ここまで見てきた一連の流れを、1枚の図にまとめます。

flowchart TD A["実装
（Codeフェーズ）"] --> B["code-reviewerサブエージェントで
レビュー"] B -->|指摘あり| C["修正"] C --> B B -->|指摘なし| D["/commit-push-pr"] D --> E["コミット・プッシュ・
PR作成"] E --> F["Slack通知
（チームチャンネル）"] F -. 後日 .-> G["claude --from-pr で
セッション再開"] G --> C

プッシュする前には、サブエージェントを使って偏りのないコードレビューを行いましょう。コミットから PR 作成までの一連の流れは、/commit-push-pr のようなスキルを用意しておくとまとめて処理できます。そして、後日 PR の作業を再開するには claude --from-pr <PR_NUMBER> を使います。どれも小さな機能ですが、日々の作業から多くの手間を取り除いてくれます。

サブエージェント（第9章）や CLAUDE.md（第8章）と同じく、Git 連携の仕組みも「まっさらな視点を確保する」「繰り返しの手間を減らす」という Claude Code 全体の設計思想の延長線上にあります。次章では、この考え方をさらに外部ツールとの接続（MCP）へ広げていきます。

やってみよう 10-1: 自分のプロジェクト用に code-reviewer を設計する

実際に .claude/agents/code-reviewer.md を作成し、読み取り専用のレビュー担当を用意してみましょう。手を動かすことで、ベストプラクティスの意味が実感できます。

手順

  1. 1 自分のプロジェクトで直近レビューしてほしい観点を3つ書き出す（例: 命名規則・エラーハンドリング・テストの過不足）。
  2. 2 .claude/agents/code-reviewer.md を作成し、tools に読み取り専用のツールだけを列挙した YAML フロントマター（第9章の形式）を書く。
  3. 3 /agents の一覧に表示されることを確認したら、実際に小さな差分に対してレビューを依頼し、指摘だけでファイルが編集されていないことを確かめる。

理解度確認クイズ

  1. Q1. code-reviewer サブエージェントを設計する際に守るべき、2つのベストプラクティスは何ですか？

    回答を表示

    ①読み取り専用のツール（Read・Grep・Glob・Bash など）だけに制限し、ファイルを編集できないようにすること。②設定ファイル（.claude/agents/code-reviewer.md）をリポジトリにチェックインし、チーム全員が同じレビュー担当を使えるようにすること、の2つです。

  2. Q2. サブエージェントによるコードレビューが、メインエージェント自身による見直しよりも「まっさらな視点」になりやすいのはなぜですか？

    回答を表示

    サブエージェントは独自の（メインエージェントとは別の）コンテキストウィンドウで動作するため、diff などレビューに必要な情報だけを見て判断できるからです。メインエージェントはそれまでの実装の経緯や試行錯誤をすべて覚えているため、「自分が書いたコード」という先入観が入りやすくなります。

  3. Q3. claude --from-pr <PR_NUMBER> は、どのような場面で使うコマンドですか？

    回答を表示

    Claude が gh pr create で作成した PR は、そのセッションと自動的に紐づけられます。後日そのPRに戻って作業したいとき――たとえばレビューコメントへの対応やビルド失敗の修正が必要になったとき――に、このコマンドを実行すると前回中断したところから続きを再開できます。
