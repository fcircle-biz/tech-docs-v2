ホーム Claude Code 第13章
第13章 所要時間: 約40分

トラブルシューティング

ここまでの章で Claude Code の考え方や機能を一通り学んできましたが、実際に使っていると「あれ、思ったように動かない」という場面に出会うことがあります。この章では第1〜12章の内容を土台に、Claude Code を使ううえでよくある9つのつまずきを取り上げ、症状 → 考えられる原因 → 対処の順で整理するとともに、安全に使うためのチェックリストもまとめます。エラーメッセージや違和感に出会ったときに慌てず自力で切り分け、復旧できるようになることが本章のゴールです。

この章で学ぶこと

  • 起動できない・権限やアクセス範囲のエラーなど、環境まわりのつまずきを自分で切り分けられる
  • コンテキストの逼迫や、プランどおりに実装されない状況を、第5〜7章の知識を使って解消できる
  • 同じ間違いの繰り返しや、必要以上に凝った実装（over-engineering）を防ぐ手立てを説明できる
  • MCPサーバーやフックが動かないときに、/mcp・/hooksなどのコマンドで状態を確認し復旧できる
  • 安全に Claude Code を使い続けるためのチェックリストを、日々の運用に取り入れられる

13.1 起動できない

Claude Code でつまずいたときは、闇雲に試行錯誤するより先に、症状を大きな系統で切り分けると解決が早まります。まずは次のフローチャートで、自分の状況がどの系統に近いかを確認してみましょう。

flowchart TD Start["症状を確認する"] --> Q1{"claudeコマンドが起動する？"} Q1 -->|起動しない| S1["① 起動できない系
13.1／13.2"] Q1 -->|起動する| Q2{"実装結果が想定と違う？"} Q2 -->|はい| S2["② 実装がうまくいかない系
13.4〜13.6"] Q2 -->|いいえ| Q3{"応答が遅い・雑になった？"} Q3 -->|はい| S3["③ コンテキスト逼迫系
13.3"] Q3 -->|いいえ| Q4{"MCP・フックが動かない？"} Q4 -->|はい| S4["④ 外部連携が動かない系
13.7／13.8"] Q4 -->|いいえ| S5["13.9 途中で止めたいときは
Escキーで割り込み"]

ここからは①の起動できない系から順に見ていきます。もっとも多いのは、インストール直後に claude コマンドが認識されないケースです。

症状 考えられる原因 対処
command not found と表示される インストール直後で PATH がまだ反映されていない ターミナルを再起動してから再実行する
再起動しても認識されない インストールが途中で失敗している インストール手順（第3章 3.1）を見直し、OS別の手順や代替手段を再実行する
起動はするが応答がない・フリーズする ネットワークやサインインセッションの一時的な問題 Ctrl+C で一度終了し、claude を起動し直す

まずは次の1行で、インストール自体が成功しているかを確認しましょう。

terminal — 起動確認 
# インストール済みのバージョンを確認する（通常のターミナルで実行）
claude --version

起動できたら /help で確認

最初のプロンプトが表示されたら /help を実行してみましょう。使えるスラッシュコマンドの一覧が表示されれば、正常に起動できている証拠です（第3章 3.6）。

13.2 権限・アクセス範囲の問題

「そのファイルは見当たりません」と言われたり、逆に触ってほしくない範囲まで変更されそうになったりする場合は、アクセス範囲の勘違いが原因であることがほとんどです。第3章 3.3 で学んだとおり、Claude Code がアクセスできるのはclaude を実行したディレクトリと、そのすべてのサブフォルダだけです。

症状: 「そのファイルにアクセスできません」／意図しない範囲まで触られそうになる

考えられる原因

  • 起動ディレクトリの外側にあるファイルを指定してしまった
  • ホームディレクトリ直下など、広すぎる階層で起動してしまった

対処

  • 対象ファイルを含むプロジェクトのルートまで cd してから claude を起動し直す
  • 広い階層で起動してしまった場合は一度終了し、対象プロジェクトのディレクトリで起動し直す

注意: .env も例外ではない

アクセス範囲には機密情報を含むファイルも含まれます。ホームディレクトリ直下やファイルシステムのルートのような広い階層では絶対に起動しないようにしましょう（第3章 3.3）。

なお、アクセス範囲はあくまで「ファイルを見に行ける範囲」です。実際に変更・実行するかどうかは、第2章で学んだ許可モードによる確認が別途入ります。/status を実行すると、現在の作業ディレクトリと許可モードをあわせて確認できます。

13.3 コンテキストが逼迫する

回答が急に雑になった、前に伝えたはずのことを忘れている、自動圧縮の通知が頻繁に出る——これらはすべてコンテキストウィンドウの逼迫のサインです（第7章）。落ち着いて、次の3ステップで切り分けましょう。

1

内訳を確認する

/context で使用量とカテゴリ別の内訳を見る（第7章 7.4）

2

圧縮かリセットかを選ぶ

続きの作業なら /compact、新しい機能なら /clear（第7章 7.5）

3

消費源を見直す

MCPサーバーの整理（第11章）・サブエージェントの活用（第9章）

terminal — 逼迫時の確認・圧縮の例 
> /context
◐ コンテキスト使用量: 184,000 / 200,000 トークン（92%）
  内訳: MCPツール定義 18%／会話 40%／ツール実行結果 30%／その他 4%

> /compact
● 会話を圧縮しています…
● コンテキスト使用量: 92% → 25%（空き容量を確保しました）

※ 表示される数値やレイアウトは、利用しているモデルやバージョンによって異なります。

この例のようにMCPツール定義の比率が高い場合は、/mcp で使っていないサーバーを無効化すると、逼迫そのものが起きにくくなります（第11章 11.7）。探索のためのツール呼び出しが多い場合は、サブエージェントに切り出すことも有効です（第9章）。

13.4 プランどおりに実装されない

プランを承認したはずなのに、できあがったものが想定と違う——これは実装フェーズそのものより、探索・計画フェーズ（第5章）の詰めが甘かったことが原因であるケースが多いです。

症状: 承認したプランと違う実装になっている

考えられる原因

  • 「正しい」状態＝成功基準を明確にしないまま進めた
  • プランモードを使わず、いきなり実装を依頼した
  • 指示が抽象的で、解釈の幅が広すぎた

対処

  • 次回は依頼の前に「正しいとはどんな状態か」を1〜2文で書く（第6章 6.3）
  • Shift + Tab でプランモードに入り、実装前にプランを確認する（第5章）
  • ズレに気づいた時点で、プランの該当箇所を具体的に指摘して修正を依頼する

重要ポイント

コードが書かれたあとの手直しより、プラン段階での指摘のほうがずっと安く済みます（第5章 5.5）。「なんか違う」と感じたら、実装を進める前にプランへ戻る癖をつけましょう。

13.5 同じ間違いを繰り返す

「またそれ？」と感じるほど同じ指摘を繰り返している場合、対処は2段階で考えます。

flowchart LR A["同じ間違いに気づく"] --> B["段階1: CLAUDE.mdに
ルールを保存するよう依頼する"] B --> C{"それでも
繰り返される？"} C -->|いいえ| D["解決"] C -->|はい| E["段階2: フックで
決定的に強制する"]
1

CLAUDE.mdに保存を依頼する

「今の修正内容をCLAUDE.mdに保存しておいて」と明示的に依頼します（第8章 8.5）。ただしCLAUDE.mdへの指示は確率的なお願いであり、「たいてい」は守られても「常に」ではありません。

2

それでも直らなければフック

段階1で解決しない場合は、PreToolUse フックなどで決定的に強制します（第12章）。プロンプトへの記述とフックの違いは、まさに「確率的」か「決定的」かです。

13.6 必要以上に凝った実装をされる（over-engineering）

頼んでいないオプションや、過剰な抽象化レイヤーまで追加されている——第1章 1.6 で触れたover-engineeringです。Claude Code は間違えることもあるという心構えを、実際に体験する場面と言えます。

スコープが広がりやすい依頼

「ユーザー設定機能を作って」

→ 将来の拡張まで見越して、不要な抽象化や設定項目が増えがちです。

スコープを絞った依頼

「表示名の変更だけができるユーザー設定画面を作って。ほかの設定項目は今回追加しないで」

→ 触ってよい範囲と成功基準が明確で、脱線しにくくなります。

over-engineeringを防ぐ実践的な打ち手は、第5・6章で学んだ内容そのものです。

  • スコープを明示する——「今回は〜だけ」「〜には触らないで」と範囲を区切る
  • 成功基準を書く——「正しい」状態を先に言語化しておく（第6章 6.3）
  • プランの段階で止めて確認する——実装前に構成を見て、過剰な部分を削る（第5章）

13.7 MCPサーバーに接続できない

第11章で追加したMCPサーバーのツールが使われない、または呼び出そうとしてエラーになる場合は、/mcp でまず状態を確認します。

terminal — /mcp の実行例（切断あり） 
> /mcp
● linear             HTTP    接続済み   ツール 6件
● internal-db        Stdio   切断      ツール 0件

  Enterキーで詳細を表示（再接続・無効化・スコープの確認）
症状 考えられる原因 対処
サーバーが一覧に出てこない スコープの取り違え（Local／User／Projectのいずれか違う場所に登録されている） claude mcp add 時のスコープ指定を見直す（第11章 11.6）
「切断」と表示される（Stdio） ローカルで起動するはずのプロセスが起動していない・パスが誤っている /mcp から再接続する。起動コマンドと引数を確認する
「切断」と表示される（HTTP） 認証切れ・提供元サービス側の障害 再接続を試し、直らない場合は提供元サービスの状態を確認する

なお、接続はできていても使っていないなら無効化するのが基本です。使っていないサーバーもツール定義はコンテキストに常駐し続けます（第11章 11.7・本章13.3）。

13.8 フックが発火しない・効きすぎる

第12章で設定したフックが思ったとおりに動かないときは、/hooks で登録状況を確認してから、.claude/settings.json を見直します。

terminal — /hooks の実行例 
> /hooks
● PostToolUse   matcher: Edit|MultiEdit|Write   1件のフック
● PreToolUse    matcher: 未設定                 0件のフック
● Stop          matcher: 未設定                 0件のフック
発火しない場合

考えられる原因

  • イベントの選択ミス（例: 編集後なのにPreToolUseを指定）
  • matcherのパターンが対象ツール名と一致していない
  • スクリプトに実行権限がない
  • 相対パスで参照していて、作業ディレクトリのずれで見つからない

対処

  • イベント選びを見直す（第12章 12.4の表）
  • chmod +x で実行権限を付与する
  • CLAUDE_PROJECT_DIR を使って絶対パス化する（第12章 12.7）
効きすぎる場合

考えられる原因

  • matcherの範囲が広すぎて無関係な操作まで拾っている
  • 終了コードの使い方を誤り、正常な操作までブロックしている

対処

  • matcherを対象ツールだけに絞り込む
  • 終了コード（0=続行／2=ブロック）の使い分けを再確認する（第12章 12.6）

13.9 途中で止めたい・やり直したい

エラーではなくても、「明後日の方向に進んでいる」「一旦止めたい」と感じる場面はよくあります。状況に応じて、次の4つの手段を使い分けましょう。

状況 操作
今すぐ処理を止めたい Esc キーで割り込む（第4章 4.7）
方向性だけ軌道修正したい 割り込んだうえで、修正したい点を具体的に伝え直す
会話ごとまっさらにやり直したい /clear でコンテキストをリセットする（第7章）
ファイルの変更そのものを取り消したい Gitで差分を確認し、必要な範囲だけ元に戻す
terminal — Gitで変更を確認・取り消す 
# 直前の変更内容を確認する
git diff

# 特定ファイルの変更だけを取り消す（未コミットの場合）
git checkout -- src/example.js

# すべての未コミットの変更を破棄して直前のコミット状態に戻す
git reset --hard

注意: git reset --hard は元に戻せない

未コミットの変更をすべて破棄する破壊的な操作です。実行前に git diff で内容を確認し、必要なものが残っていないかを必ず確かめましょう。

13.10 安全に使うためのチェックリスト

最後に、これまでの章で学んできた内容を「安全に使い続けるための習慣」としてチェックリストにまとめます。トラブルの多くは、このリストを日頃から意識しておくことで未然に防げます。

自動承認モードは、内容を理解し信頼できる操作に限定する（第4章）。よくわからないまま任せきりにしない。

危険なコマンドや本番設定への書き込みは、フックで機械的にブロックする（第12章）。「たぶん大丈夫」に頼らない。

コミット前は、読み取り専用のサブエージェントにレビューさせる（第6・10章）。まっさらな視点で見直す一手間を惜しまない。

claude は必要な範囲のディレクトリだけで起動する（第3章）。ホームディレクトリ直下など広すぎる範囲では起動しない。

使っていないMCPサーバーは無効化する（第11章）。コンテキストの節約にも、管理範囲を狭めることにもつながる。

CLAUDE.md・サブエージェント定義・settings.json はバージョン管理にコミットする（第8・9・12章）。チームで同じ安全ルールを共有する。

慣れないうちは承認モード（都度確認）で進める（第1・2章）。挙動が読めるようになってから、任せる範囲を少しずつ広げる。

迷ったら止める（本章13.9）。Esc で割り込み、Gitの差分で変更内容を確認してからコミットする。

やってみよう 13-1: 自分の環境を一通り診断してみる

エラーが起きていなくても、確認用のコマンドは今のうちに一度触っておくと、いざというとき落ち着いて対処できます。実際に5つのコマンドを打ち、自分の環境の状態を確認してみましょう。

手順

  1. 1 通常のターミナルで claude --version を実行し、インストール済みのバージョンを確認する。
  2. 2 claude を起動し、/help で使えるスラッシュコマンドの一覧を表示する。
  3. 3 /status を実行し、現在の作業ディレクトリとサインイン中のアカウントを確認する（13.2）。
  4. 4 /context を実行し、コンテキスト使用量の内訳を確認する。今もっとも多くを占めているカテゴリはどれか確認してみる（13.3）。
  5. 5 /mcp と /hooks を順に実行し、現在設定されている外部連携とフックの一覧を確認する（何も設定していなければ空の表示になることを確認する）。

理解度確認クイズ

  1. Q1. claude コマンドがインストール直後に認識されない場合、まず何を試すべきですか。それでも解決しない場合はどうしますか。

    回答を表示

    まずターミナルを再起動します。PATHの反映にはターミナルの再起動が必要なことがあるためです。claude --versionで認識されるか確認し、それでも解決しない場合はインストール手順（第3章 3.1）を見直し、OS別の手順や代替手段を試します。

  2. Q2. コンテキストが逼迫してきたと感じたとき、最初に行うべきことと、そのあとの判断基準を説明してください。

    回答を表示

    まず/contextを実行し、何がコンテキストを多く占めているかの内訳を確認します（第7章）。そのうえで、同じ機能の続きなら/compact、新しい機能に着手するなら/clearを使い分けます。MCPツール定義の比率が高ければ/mcpで不要なサーバーを無効化し、探索が多いならサブエージェントの活用も検討します。

  3. Q3. Claude Code が同じ間違いを繰り返す場合、どのように2段階で対処すればよいですか。

    回答を表示

    まず、そのルールをCLAUDE.mdに保存するよう明示的に依頼します（第8章）。CLAUDE.mdへの指示はあくまで「確率的なお願い」であり、それでも繰り返される場合は、フックを使って「決定的に」強制します。たとえばPreToolUseフックで該当する操作をブロックすれば、例外なく毎回防げます（第12章）。
