ホーム Claude Skills 第11章
第11章 所要時間: 約45分

スキルの共有と配布

スキルは、あなた一人だけが使うものにとどめておく必要はありません。共有されることで、その価値は大きく高まります。この章では、リポジトリへのコミット・プラグイン・エンタープライズ向け管理設定という3つの配布方法を比較し、さらに「サブエージェントはスキルを自動的には引き継がない」という、多くの人がつまずく重要な落とし穴を確認します。

この章で学ぶこと

  • スキルを Git リポジトリにコミットしてチームと共有する方法を理解する
  • プラグインとマーケットプレイスを通じて、プロジェクトをまたいでスキルを配布する方法を知る
  • エンタープライズ向け管理設定（managed settings）で組織全体にスキルを展開する仕組みを理解する
  • サブエージェントにスキルを認識させるため、frontmatter の skills フィールドを設定できる

11.1 スキルは共有してこそ価値が高まる

第3章では、あなた自身のための PR レビュー用スキルを作りました。それだけでも十分便利ですが、そのスキルをチーム全体で共有すれば、コードレビューが標準化され、組織全体で一貫した体験が生まれます。ここからは、スキルを配布するさまざまな方法を見ていきます。

配布方法は3つあります。リポジトリへのコミット（最もシンプル）、プラグインを通じた配布（コミュニティ規模）、エンタープライズ向け管理設定（組織全体・最優先度）です。届く範囲が広がるほど、必要になる仕組みも大きくなります。

11.2 方法1: リポジトリへのコミット

最もシンプルな共有方法は、スキルを直接リポジトリにコミットすることです。.claude/skills に配置すれば、リポジトリをクローンした人は誰でも、追加のインストール作業なしで自動的にそのスキルを手に入れられます。

更新をプッシュすると、次に pull した人全員がその更新を受け取ります。第2章で学んだプロジェクト用スキルの置き場所が、そのまま共有の仕組みになっているわけです。

チームのコーディング標準

命名規則やレビュー観点など、人によってブレると困るもの。

プロジェクト固有のワークフロー

このリポジトリでしか通用しない手順・運用ルール。

コードベース構造の参照

このリポジトリのディレクトリ構成・設計方針を前提にした知識。

.claude ディレクトリはすべてバージョン管理される

.claude ディレクトリには、エージェント・フック・スキル・設定が含まれています。これらはすべてバージョン管理され、通常の Git ワークフロー（commit・push・pull）を通じてチームと共有されます。特別なインストーラーは必要ありません。

11.3 方法2: プラグインを通じた配布

プラグイン（plugins）は、チームやプロジェクトをまたいで共有できるカスタム機能で Claude Code を拡張する手段です。プラグインのプロジェクト内には、.claude ディレクトリとよく似たファイル構成の skills ディレクトリを作成します。各スキルは、内部に SKILL.md を持つ独自のフォルダを持つという点は、これまで見てきたスキルと変わりません。

プラグインをマーケットプレイス（marketplace）に配布すると、他のユーザーがそれを見つけて、自分の Claude Code にインストールできるようになります。

向いている場面

スキルの内容がプロジェクト固有すぎず、身近なチームを超えたコミュニティメンバーにとっても役立つ場合に向いています。特定のフレームワークの共通作法や、一般的なワークフロー改善などが該当します。

11.4 方法3: エンタープライズ向け管理設定

管理者は、管理設定（managed settings）を通じて組織全体にスキルを展開できます。第2章で学んだ優先順位を思い出してください。エンタープライズスキルは最優先度を持ち、同名の個人スキル・プロジェクトスキル・プラグインスキルより優先されます。

管理設定ファイルは、プラグインのインストール元を制御する strictKnownMarketplaces のような機能もサポートしています。承認済みのマーケットプレイスだけからプラグインを取得させたい場合、次のように指定します。

managed-settings.json（抜粋） 
"strictKnownMarketplaces": [
  {
    "source": "github",
    "repo": "acme-corp/approved-plugins"
  },
  {
    "source": "npm",
    "package": "@acme-corp/compliance-plugins"
  }
]

この設定を入れておくと、組織のメンバーは acme-corp/approved-plugins（GitHub）や @acme-corp/compliance-plugins（npm）以外の出所からプラグインを取り込めなくなります。

向いている場面

必須の標準、セキュリティ要件、コンプライアンスワークフロー、組織全体で一貫していなければならないコーディング慣行に適した選択肢です。ここでのキーワードは「must（必須）」です。任意で使ってほしいだけの知識には、プロジェクトスキルやプラグインのほうが向いています。

11.6 スキルとサブエージェント（重要な落とし穴）

ここで、多くの人が驚くポイントを取り上げます。サブエージェント（subagents）は、あなたのスキルを自動的には認識しません。タスクをサブエージェントに委任すると、そのサブエージェントはまっさらな、クリーンなコンテキストから開始します。第10章で学んだ「独立したコンテキスト」という性質が、ここでは思わぬ落とし穴になります。

ビルトインエージェント

Explorer・Plan・Verify などのビルトインエージェントは、スキルに一切アクセスできません。

カスタムサブエージェント

自分で定義したカスタムサブエージェントはスキルを使えますが、明示的にリストした場合に限ります。

もう一つ覚えておきたいのは、読み込まれるタイミングの違いです。スキルは、メインの会話のようにオンデマンドで読み込まれるのではなく、サブエージェントの起動時に読み込まれます。つまり、サブエージェントの frontmatter に指定されていないスキルは、会話の中でどれだけ関連していても、そのサブエージェントの中では存在しないのと同じです。

スキルを持つカスタムサブエージェントを作成するには、.claude/agents にエージェント用の Markdown ファイルを追加します。/agents コマンドを使えば、対話形式で作成することもできます。frontmatter には、どのスキルを読み込むかを指定する skills フィールドを書きます。

.claude/agents/frontend-security-accessibility-reviewer.md 
---
name: frontend-security-accessibility-reviewer
description: "フロントエンドのコードをアクセシビリティ観点で
  レビューする必要があるときに、このエージェントを使用します"
tools: Bash, Glob, Grep, Read, WebFetch, WebSearch, Skill
model: sonnet
color: blue
skills: accessibility-audit, performance-check
---

このサブエージェントに作業を委任すると、accessibility-audit と performance-check の両方のスキルが読み込まれた状態になり、すべてのレビューに適用されます。設定する前に、.claude/skills ディレクトリに対象のスキルが存在することを確認しておきましょう。

このパターンが特にうまく機能するのは、次のような場合です。

1

特定の専門知識を持たせた独立したタスク委任

サブエージェントに専門性を持たせつつ、メインの会話のコンテキストを消費しない。

2

サブエージェントごとに必要なスキルが異なるとき

フロントエンドレビュアーとバックエンドレビュアーでは、参照すべき基準が違う。

3

プロンプトに頼らず標準を強制したいとき

毎回プロンプトで指示するのではなく、frontmatter に固定しておくことで確実に適用させる。

つまずきやすいポイント: 「委任したのにスキルが効かない」

「メインの会話ではスキルがちゃんと働いているのに、サブエージェントに委任したら急に品質が落ちた」という相談は典型的な落とし穴です。原因のほとんどは、サブエージェントの frontmatter に skills フィールドを書き忘れていることにあります。委任先で標準を守らせたいときは、プロンプトで説明するのではなく、まず frontmatter を確認してください。

やってみよう 11-1: 自分のスキルを配布方法に当てはめる

第1章「やってみよう」で書き出したスキル、または第3章で作成した pr-description を例に、実際に配布する準備を進めてみましょう。

手順

  1. 1 11.5 の比較表を見ながら、自分のスキルに最も合う配布方法（リポジトリ／プラグイン／エンタープライズ）を1つ選び、理由を1文で書く。
  2. 2 「リポジトリへのコミット」を選んだ場合は、スキルのフォルダがプロジェクトの .claude/skills 配下にあることを確認し、git add・git commit・git push でチームに共有する。
  3. 3 チームメンバーの誰かに、リポジトリを pull した直後にそのスキルが使える状態になっているかを確認してもらう（追加のインストール作業が不要であることを確かめる）。

ヒント: もしそのスキルを使わせたいカスタムサブエージェントがすでにあるなら、あわせて frontmatter の skills フィールドに追記しておきましょう。委任した作業でも同じ標準が適用されるようになります。

理解度確認クイズ

  1. Q1. スキルをリポジトリにコミットして共有すると、クローンした人はどのようにそのスキルを手に入れますか？

    回答を表示

    .claude/skills に配置してコミットしておけば、リポジトリをクローンした人は誰でも、追加のインストール作業なしで自動的にそのスキルを手に入れられます。更新をプッシュすると、次に pull した人全員が更新を受け取ります。

  2. Q2. プラグインを通じた配布と、リポジトリへのコミットとの違いは何ですか？

    回答を表示

    リポジトリへのコミットは、そのリポジトリをクローンした人にしか届きません。プラグインはマーケットプレイス経由で配布でき、プロジェクト固有すぎず身近なチームを超えたコミュニティメンバーにも役立つスキルに向いています。

  3. Q3. エンタープライズ向け管理設定によるスキルの優先順位はどうなりますか？

    回答を表示

    エンタープライズスキルは最優先度を持ち、同名の個人スキル・プロジェクトスキル・プラグインスキルより優先されます。必須の標準・セキュリティ要件・コンプライアンスワークフローに適しています。

  4. Q4. サブエージェントにスキルを委任時に使わせたい場合、何をする必要がありますか？

    回答を表示

    サブエージェントはスキルを自動的には認識しないため、.claude/agents のカスタムサブエージェント定義の frontmatter に skills フィールドで明示的にリストする必要があります。ビルトインエージェント（Explorer・Plan・Verify など）はそもそもスキルに一切アクセスできません。
