ホーム Claude Code Skills 第12章
第12章 所要時間: 約45分

トラブルシューティングと次のステップ

スキルがうまく動作しないとき、原因は「トリガーされない」「読み込まれない」「競合が起きている」「ランタイムで失敗する」のいずれかにほぼ当てはまります。この最終章では、体系的な診断の進め方を身につけ、これまで12章にわたって学んだ内容を振り返ります。

この章で学ぶこと

  • デバッグの前に構造的な問題を見つけるため、agent skills verifier を使える
  • よくあるトリガーの問題・読み込みの問題を診断し、修正できる
  • エンタープライズ・個人・プロジェクト・プラグイン間の優先順位の競合を解決できる
  • 依存関係・権限・パスの問題を含むランタイムエラーをデバッグできる
  • 全12章の学習内容を振り返り、実務でスキルを育てていく次のステップを描ける

12.1 うまくいかないときは、まず落ち着いて分類する

ここまでの11章で、スキルの作成・設定・共有までを学んできました。しかし実際に運用していると、「思ったときに使われない」「なぜか動かない」といった場面に必ず出会います。

安心してください。スキルがうまく動作しないとき、問題は大きく分けて次の4つのカテゴリのどれかに当てはまります。

トリガーされない

スキルは存在しているのに、期待したタイミングで Claude が使ってくれない。

読み込まれない

「利用できるスキルは？」と聞いても、そもそも一覧に表示されない。

競合が起きている

誤ったスキルが使われる、または優先順位の高いスキルに隠れてしまう。

ランタイムで失敗する

スキルは読み込まれ実行されるが、途中でエラーになる。

幸いなことに、ほとんどの修正方法はとてもシンプルです。この章では、原因を切り分けるための最初の一手から順に見ていきます。

12.2 まず agent skills verifier を使う

個別の症状を追いかける前に、最初に試すべきコマンドが agent skills verifier です。インストール手順は OS によって異なりますが、uv を使うのが手早くセットアップする最も簡単な方法です。

インストールが終わったら、スキルのディレクトリに移動するか、どこからでもこのコマンドを実行します。イメージは次のとおりです。

ターミナル 
# uv を使うのが最も手軽（正確なパッケージ名・手順は公式ドキュメントで確認する）
# インストール手順は OS によって異なる

# 検証したいスキルのディレクトリへ移動して verifier を実行する
cd ~/.claude/skills/pr-description
# ここで verifier コマンドを実行する

重要ポイント

verifier は、他の部分のデバッグに時間を費やす前に構造的な問題を検出してくれます。「なぜトリガーされないのか」を悩む前に、まず「そもそも構造が正しいか」を機械的に確認する——これが最短ルートです。

12.3 診断の全体フロー

verifier で構造的な問題がないことを確認したら、次は症状に応じて原因を切り分けます。全体の流れを図にすると次のようになります。

flowchart TD A["スキルが期待通り動かない"] --> B["agent skills verifierで検証する"] B --> C{"構造的なエラーが見つかったか"} C -->|はい| D["エラー内容に従って修正する"] C -->|いいえ| E{"どの症状に近いか"} E -->|"トリガーされない"| F["descriptionを見直す"] E -->|"読み込まれない"| G["パス／ファイル名／claude --debugを確認"] E -->|"誤ったスキルが使われる"| H["説明文を区別しやすくする"] E -->|"優先順位に隠れている"| I["名前を変更 or 管理者に相談"] E -->|"プラグインが見当たらない"| J["キャッシュを消して再インストール"] E -->|"ランタイムで失敗"| K["依存関係／権限／パスを確認"]

つまり、「まず verifier、それでも解決しなければ症状別の対処」という2段構えです。次の節から、それぞれの症状ごとに具体的な対処を見ていきます。

12.4 症状別の対処

① トリガーされない

スキルは存在していて verifier にも通っているのに、期待したときに Claude が使ってくれない——この場合、原因はほぼ常に description にあります。Claude はセマンティックマッチング（意味的な一致）を使うため、あなたのリクエストが説明文の意味と十分に重なっていなければマッチしません。

  • 説明文が、実際にどうリクエストを言い回しているかと一致しているか確認する
  • ユーザーが実際に言いそうなトリガーフレーズを追加する
  • 「これのパフォーマンスを見てほしい」「なぜこれは遅いのか？」「これを速くして」といった言い回しのバリエーションでテストする
  • どれかのバリエーションでトリガーされなければ、そのキーワードを説明文に追加する（第5章の復習）

② 読み込まれない

Claude に「利用できるスキルは？」と聞いてもスキルが表示されない場合は、次の構造的な要件を確認します。

  • SKILL.md は、スキルのルート直下ではなく名前付きディレクトリの中になければならない
  • ファイル名は正確に SKILL.md でなければならない——「SKILL」はすべて大文字、「md」は小文字

claude --debug を実行して、読み込みエラーを確認します。自分のスキル名に言及しているメッセージを探しましょう。

ターミナル 
# デバッグモードで起動し、読み込みログを確認する
claude --debug

# 出力の中から自分のスキル名を含む行を探す
# 例: skill "pr-description" を読み込みました など

③ 誤ったスキルが使われる

Claude が間違ったスキルを使ったり、複数のスキルの間で混乱しているように見える場合、説明文が似すぎている可能性が高いです。もっと区別しやすくしましょう。できる限り具体的にすることは、Claude がいつあなたのスキルを使うべきか判断する助けになるだけでなく、名前の似た他のスキルとの競合も防いでくれます。

④ 優先順位の競合

個人のスキルが無視されている場合、エンタープライズなどより優先順位の高いスキルが同じ名前を使っている可能性があります（第2章の優先順位を復習）。 

エンタープライズ管理設定
  └─ skills/code-review/SKILL.md   ← 常にこちらが優先される

個人用 (~/.claude/skills)
  └─ code-review/SKILL.md          ← 名前が同じため無視されてしまう

取れる対処は次の2つです。

  • スキルの名前を、もっと区別しやすいものに変更する（たいていはこちらのほうが簡単）
  • エンタープライズ側のスキルについて管理者に相談する

⑤ プラグインのスキルが表示されない

プラグインをインストールしたのに、そのスキルが見当たらない場合は、キャッシュをクリアし、Claude Code を再起動して、再インストールしてください。それでもスキルが表示されない場合は、プラグインの構造自体が間違っている可能性があります。こういうときこそ、verifier ツールが真価を発揮します。

⑥ ランタイムエラー

スキルは読み込まれるものの、実行時に失敗する——よくある原因は次の3つです。

  • 依存関係の欠落: スキルが外部パッケージを使う場合、それらはインストールされていなければなりません。Claude が何が必要かを把握できるよう、スキルの説明文に依存関係の情報を追加してください。
  • 権限の問題: スクリプトには実行権限が必要です。スキルが参照するスクリプトに対して chmod +x を実行してください。
  • パスの区切り文字: Windows 上であっても、どこでもスラッシュ / を使ってください（第1章のコラムを復習）。
ターミナル 
# スキルが参照するスクリプトに実行権限を付与する
chmod +x scripts/format.sh

# 権限を確認する（x が付いていればOK）
ls -l scripts/format.sh

注意: 原因を推測で決めつけない

似た症状でも原因は異なることがあります。「多分 description の問題だろう」と決めつける前に、verifier と claude --debug で事実を確認してから対処するほうが結局早く解決します。

12.5 クイック・トラブルシューティング・チェックリスト

次の一覧を、困ったときの早見表として使ってください。

症状 対処
トリガーされない？ 説明文を改善し、トリガーフレーズを追加する。
読み込まれない？ パス、ファイル名、YAML構文を確認する。
誤ったスキルが使われる？ 説明文どうしをもっと区別しやすくする。
他のスキルに隠れてしまっている？ 優先順位の階層を確認し、必要なら名前を変更する。
プラグインのスキルが見当たらない？ キャッシュをクリアして再インストールする。
ランタイムで失敗する？ 依存関係、権限、パスを確認する。

やってみよう 12-1: 自分のスキルを検証プロセスに通す

これまでの章で作った（あるいは構想した）スキルを、チームに共有する前に点検しましょう。良いスキルほど、公開前の検証を経ています。

手順

  1. 1 対象のスキルに対して agent skills verifier を実行し、構造的なエラーがないか確認する。
  2. 2 自分が実際に使いそうな言い回しを3パターン用意し、期待通りトリガーされるかテストする。
  3. 3 12.5節のチェックリストを1項目ずつ確認し、当てはまる問題があれば対処してから共有する。

ヒント: 共有前にこの3ステップを習慣にしておくと、チームメンバーから「動かない」と報告される前に自分で気づけるようになります。

理解度確認クイズ

  1. Q1. スキルが動かないとき、なぜ最初に agent skills verifier を試すべきなのですか？

    回答を表示

    verifier は、他の部分（description の言い回しやランタイムなど）のデバッグに時間を費やす前に、SKILL.md の配置やファイル名といった構造的な問題を機械的に検出してくれるからです。原因の切り分けを最短で行える最初の一手です。

  2. Q2. スキルが一覧に読み込まれない場合、確認すべき構造的な要件は何ですか？

    回答を表示

    SKILL.md がスキルのルート直下ではなく名前付きディレクトリの中に置かれているか、そしてファイル名が正確に SKILL.md（「SKILL」は大文字、「md」は小文字）になっているかを確認します。加えて claude --debug を実行し、自分のスキル名に言及する読み込みエラーがないか探します。

  3. Q3. 個人用スキルがエンタープライズの同名スキルに常に負けてしまうのはなぜですか。どう対処しますか？

    回答を表示

    スキル名が重複した場合、優先順位の高いエンタープライズ管理設定が常に優先されるためです（第2章の優先順位を参照）。対処は、スキルの名前をより区別しやすいものに変更すること（たいていはこちらが簡単）、またはエンタープライズ側のスキルについて管理者に相談することです。

  4. Q4. ランタイムエラーの典型的な原因を3つ挙げてください。

    回答を表示

    ①外部パッケージがインストールされていない依存関係の欠落、②スクリプトに実行権限がない権限の問題（chmod +x で解決）、③Windows などでバックスラッシュを使ってしまうパスの区切り文字の問題（どこでもスラッシュ / を使う）の3つです。
