ホーム Claude Code Skills 第5章
第5章 所要時間: 約40分

効果的な description の書き方

前章で見たとおり、Claude はリクエストと description をセマンティックマッチング（意味的な一致）で照合してスキルを選びます。つまり、スキルが期待どおりに起動するかどうかは、ほぼ description の書き方だけで決まります。この章では、良い説明文が満たすべき条件と、トリガーされない説明文を改善する具体的な手順を身につけます。

この章で学ぶこと

  • Claude がセマンティックマッチングでスキルを選ぶ仕組みを説明できる
  • 良い説明文が答えるべき2つの問い（何をするか／いつ使うか）を理解する
  • 悪い説明文と良い説明文を比較し、何が足りないかを指摘できる
  • 言い回しのバリエーションでテストし、トリガーフレーズを追加して改善できる
  • 説明文を具体的にして、他スキルとの誤選択を防ぐ意義を理解する

5.1 なぜ description が最重要なのか

第4章で確認したとおり、Claude Code は起動時にすべてのスキルの name と description だけを読み込みます。そして、あなたのリクエストが送られてくると、その内容を各スキルの description と照らし合わせて「今このスキルが関連しそうか」を判断します。この照合方式がセマンティックマッチング（意味的な一致）です。

セマンティックマッチングは、キーワードが一字一句そろっているかを見るものではありません。しかしリクエストと説明文の意味が重なっている必要はあります。重なりが十分でなければ、Claude はそのスキルを候補として見つけられず、マッチしません。

スキルが思ったときに起動しない原因は、ほぼ常に description にあります。本文の指示がどれだけ優れていても、説明文がリクエストと噛み合わなければ、Claude はそのスキルにたどり着けません。

5.2 指示は明示的に

誰かに「あなたの仕事はドキュメント関連の手伝いです」とだけ言われたら、何をすればよいか分からないはずです。ドキュメントを新しく書くのか、既存のものを直すのか、どんな種類のドキュメントなのか——何も分かりません。Claude も、これと同じように考えます。

曖昧な説明文は、人にとって分かりにくいのと同じ理由で、Claude にとっても「いつ使うべきか」を判断する材料になりません。説明文を書くときは、初めてそのスキルを見る人に説明するつもりで、具体的に書くことを意識してください。

曖昧な説明文の例

description: ドキュメント関連の手伝いをします — 「ドキュメント」が何を指すのか、「手伝う」とはどんな作業なのかが分かりません。Claude はこの説明文だけでは、いつこのスキルを使うべきか判断できません。

5.3 良い説明文が答える2つの問い

良い説明文は、必ず次の2つの問いに答えます。説明文を書き終えたら、この2軸でチェックする習慣をつけましょう。

1

このスキルは何をするか？

スキルが実行する作業の内容を、具体的な動詞と対象で言い切ります。「手伝います」ではなく「〜を作成します」「〜をレビューします」のように書きます。

2

Claude はいつこれを使うべきか？

どんな場面・どんな依頼のときに有効化すべきかを書きます。「〜するときに使用します」という形で、発動条件を具体的に示します。

実際に、この2軸で悪い例と良い例を比べてみましょう。

悪い例

SKILL.md（frontmatter抜粋） 
description: ドキュメントを手伝います

何を作るのか、いつ使うのかのどちらも答えていません。

良い例

SKILL.md（frontmatter抜粋） 
description: APIリファレンスを作成します。エンドポイントの
  追加・変更時や、APIドキュメントの更新を依頼された
  ときに使用します。

「何をするか」（APIリファレンスの作成）と「いつ使うか」（エンドポイントの追加・変更時、更新依頼時）の両方に答えています。

重要ポイント

説明文を書き終えたら、「①何をするスキルか」「②いつ使うべきか」の2点が、その1〜2文の中に両方とも含まれているか読み返してください。片方しか答えていない説明文は、改善の余地があります。

5.4 トリガーフレーズを盛り込む

2つの問いに答えていても、想定通りにスキルがトリガーされないことがあります。よくある原因は、説明文の言葉づかいが、自分が実際にリクエストするときの言い回しとズレていることです。

たとえば、パフォーマンス調査のスキルを想定してみましょう。あなたは同じ意図を、状況によって次のように違う言い方で頼むかもしれません。

「これのパフォーマンスを見てほしい」

「なぜこれは遅いのか？」

「これを速くして」

説明文に「パフォーマンス」という単語しか入っていなければ、2つ目・3つ目の言い回しではマッチしないかもしれません。この場合は、「遅い」「速くする」といった言い換えのキーワードも説明文に追加することで、どの言い回しでも確実にトリガーされるようになります。

flowchart TD A["説明文を書く"] --> B["言い回しのバリエーションでテスト"] B --> C{"すべての言い回しでトリガーされたか"} C -->|いいえ| D["トリガーされなかった言い回しのキーワードを説明文に追加"] D --> B C -->|はい| E["説明文が完成"]

テストの進め方

自分が実際に使いそうな言い回しを3つほど用意し、それぞれで Claude Code に依頼してみます。ターミナルにスキル読み込みの表示が出ればトリガー成功、出なければ失敗です。失敗した言い回しのキーワードを説明文に足し、もう一度同じ言い回しで試します。

5.5 区別しやすさ — 似た説明文は誤選択のもと

説明文どうしが似すぎていると、Claude が誤ったスキルを選んでしまうことがあります。たとえば「ドキュメントを更新します」というスキルが2つあり、片方は API リファレンス用、もう片方は README 用だとしたら、Claude はどちらを使うべきか区別できません。

説明文をできる限り具体的にすることは、Claude の判断を助けるだけでなく、名前の似た他のスキルとの競合も防ぎます。「何を」「どの場面で」を具体的な言葉に置き換えることを意識してください。

注意: 誤ったスキルが使われる場合

Claude が期待と違うスキルを使ったり、複数のスキルの間で混乱しているように見えるときは、説明文が似すぎている可能性が高いです。詳しい切り分け方は第12章でまとめて扱います。

5.6 description の長さの目安

description には最大1,024文字まで書けます。「何をするか」「いつ使うか」の2つの問いに答えたうえで、必要ならトリガーフレーズも足すと、自然と1〜3文程度になることが多いでしょう。

frontmatter の他のフィールドは次章で

name・description の文字数制限や、allowed-tools・model といった任意フィールドの詳しい使い方は、次の第6章でまとめて扱います。

やってみよう 5-1: pr-description の description をテスト・改善する

第3章で作成した pr-description スキルの説明文を、実際の言い回しのバリエーションでテストし、必要ならキーワードを追加して改善しましょう。

手順

  1. 1 ~/.claude/skills/pr-description/SKILL.md を開き、現在の description を確認する。
  2. 2 Claude Code で、次の3つの言い回しをそれぞれ別に試す。「PRの説明を書いて」「この変更のPR文面を作って」「プルリクエストの説明文をまとめて」。
  3. 3 トリガーされなかった言い回しがあれば、その言い回しに含まれるキーワード（例:「プルリクエスト」「文面」）を description に追加する。
  4. 4 Claude Code を再起動し、同じ3つの言い回しで再テストして、すべてトリガーされることを確認する。

ヒント: 3つすべてが最初からトリガーされた場合は、さらに違う言い回し（例:「マージリクエストの説明を作って」）で試し、説明文の守備範囲を広げてみましょう。

理解度確認クイズ

  1. Q1. Claude はどのような仕組みでリクエストと description を照合していますか？

    回答を表示

    セマンティックマッチング（意味的な一致）で照合します。キーワードが一字一句そろっている必要はありませんが、リクエストと説明文の意味が重なっている必要があり、重なりが足りなければマッチしません。

  2. Q2. 良い説明文が答えるべき2つの問いは何ですか？

    回答を表示

    「①このスキルは何をするか」「②Claude はいつこのスキルを使うべきか」の2つです。この2軸の両方に答えているかを説明文のチェックに使います。

  3. Q3. 「これのパフォーマンスを見てほしい」ではトリガーされるのに、「なぜこれは遅いのか？」ではトリガーされないスキルがあるとき、どう改善すればよいですか？

    回答を表示

    トリガーされなかった言い回しに含まれるキーワード（この例では「遅い」）を description に追加し、その言い回しで再テストします。想定される複数の言い回しでテストし、抜けているキーワードを補っていくのが基本の改善手順です。

  4. Q4. 説明文が似すぎている2つのスキルがあると、何が起きますか？またどう対処しますか？

    回答を表示

    Claude が誤ったスキルを選んでしまったり、複数のスキルの間で混乱することがあります。それぞれの説明文を、できる限り具体的にして区別しやすくすることで防げます。
