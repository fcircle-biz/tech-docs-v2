ホーム Claude Code Skills 第1章
第1章 所要時間: 約30分

スキルとは何か

Claude Code のスキル（Agent Skills）は、「あることのやり方」を一度だけ書いておけば、関連する場面になるたびに Claude が自動的にその知識を適用してくれる仕組みです。この章では、スキルとは何か、どこに置かれるのか、そして CLAUDE.md やスラッシュコマンドと何が違うのかという全体像をつかみます。

この章で学ぶこと

  • Claude Code のスキルとは何か、どのように機能するかを説明できる
  • スキルが SKILL.md と frontmatter で構成されることを理解する
  • スキルがどこに置かれるか（個人用とプロジェクト用の違い）を知る
  • スキルと CLAUDE.md、スラッシュコマンドの違いを区別できる
  • スキルが適切なカスタマイズ手段となる場面を見極められる

1.1 「毎回同じ説明をしている」という問題

Claude Code を使い始めてしばらくすると、多くの人が同じ壁にぶつかります。毎回、同じことを説明しているのです。

コーディング規約

新しいコードを書かせるたびに、チームの規約を説明し直している。

PR レビューの観点

レビューのたびに、フィードバックの構成のしかたを伝え直している。

コミットメッセージ

コミットのたびに、好みのフォーマットを思い出させている。

こうした説明は、内容そのものは毎回ほとんど同じです。違うのは「いつ必要になるか」だけ。スキルは、まさにこの問題を解決するための機能です。

スキルとは、あることのやり方を一度だけClaude に教える Markdown ファイルです。以降 Claude は、関連する場面になるたびに、その知識を自動的に適用します。

1.2 スキルの正体 — SKILL.md を持つフォルダ

スキルは、Claude Code が発見し、タスクをより正確に処理するために利用できる指示とリソースをまとめたフォルダです。各スキルは SKILL.md というファイルを持ち、その先頭にある frontmatter に name と description を書きます。

実際の SKILL.md は、次のような見た目になります。

~/.claude/skills/pr-review/SKILL.md 
---
name: pr-review
description: PRのコード品質をレビューします。PRのレビューやコード変更の確認を行うときに使用します。
---

PR をレビューするときは、次の観点で確認してください。

1. 変更の意図が説明されているか
2. テストが追加・更新されているか
3. 命名が既存のコードと一貫しているか

ファイルは --- で区切られた2つの部分から成り立っています。上半分の frontmatter が「このスキルは何者か」を示すメタデータ、下半分が「有効になったとき Claude が従う指示」です。

flowchart TD A["SKILL.md"] --> B["frontmatter（--- で囲まれた部分）"] A --> C["指示本文（--- の下すべて）"] B --> B1["name: スキルの識別名"] B --> B2["description: いつ使うかの説明"] C --> C1["チェックリスト・手順・書式など"]

用語: frontmatter（フロントマター）とは

Markdown ファイルの先頭に --- で挟んで書く、YAML 形式のメタデータ領域のことです。本文そのものではなく、「このファイルは何か」をプログラムに伝えるために使われます。Claude Code はここに書かれた name と description を読み取って、スキルを管理します。

1.3 description がスキル選択の決め手

スキルの中で最も重要なフィールドは description です。Claude は、あなたのリクエストと、利用可能なすべてのスキルの description を照らし合わせて、「今このスキルが役に立ちそうか」を判断します。

たとえば「この PR をレビューして」と依頼すると、Claude はそのリクエストを各スキルの説明文と比較し、PRのレビューやコード変更の確認を行うときに使用します という説明を持つスキルを見つけ出して有効化します。

flowchart LR A["あなたのリクエスト
「この PR をレビューして」"] --> B["Claude が照合する"] B --> C["スキルA: PRレビュー用"] B --> D["スキルB: 図解作成用"] B --> E["スキルC: 議事録作成用"] C --> F["合致 → 有効化"]

重要ポイント

スキルが思ったときに起動しない原因は、ほぼ常に description にあります。「何をするか」と「いつ使うか」の両方を書くのが基本です。書き方のコツは第5章でじっくり扱います。

1.4 スキルはどこに置かれるのか

「誰がそのスキルを必要とするか」によって、置き場所を使い分けます。入門段階で押さえるべきは、次の2つです。

個人用スキル

ホームディレクトリの ~/.claude/skills に置きます。すべてのプロジェクトであなたについて回ります。

例: コミットメッセージのスタイル、ドキュメントの書式、コード説明の好み

プロジェクト用スキル

リポジトリのルートにある .claude/skills に置きます。リポジトリをクローンした人全員に共有されます。

例: 会社のブランドガイドライン、Web デザインの推奨フォント・カラー

Windows での置き場所

Windows の場合、個人用スキルは C:/Users/<your-user>/.claude/skills に置かれます。パスの区切りは、Windows 上でもスラッシュ / を使うのが安全です（第12章で再度取り上げます）。

プロジェクト用スキルはコードと一緒にバージョン管理へコミットされるため、チーム全体で自然に共有されます。この他にエンタープライズ（管理設定）とプラグインという置き場所もありますが、詳しくは第2章で4種類まとめて整理します。

1.5 スキル・CLAUDE.md・スラッシュコマンドの違い

Claude Code には動作をカスタマイズする方法がいくつかあります。スキルが独特なのは、自動的であり、かつタスク特化型である点です。違いは「いつコンテキストに読み込まれるか」で整理すると分かりやすくなります。

手段 読み込まれるタイミング 向いている内容
CLAUDE.md すべての会話に必ず読み込まれる 常時適用したい標準（例: TypeScript の strict モードを常に使う）
スキル リクエストに合致したときオンデマンドで タスク固有の専門知識（例: PR レビューのチェックリスト）
スラッシュコマンド 自分で明示的にタイプしたとき 意識的に呼び出したい定型処理

ここで効いてくるのが、Claude が最初に読み込むのは name と description だけという設計です。スキルをいくつ用意しても、実際に使われるまで本文はコンテキストを消費しません。デバッグ中に PR レビューのチェックリストが割り込むことはなく、レビューを依頼したときにはじめて読み込まれます。

flowchart TD A["Claude Code 起動"] --> B["全スキルの name と description だけ読み込む"] B --> C{"リクエストと合致するか"} C -->|合致しない| D["本文は読み込まれない（コンテキスト節約）"] C -->|合致する| E["SKILL.md の本文を読み込んで適用"]

Claude がリクエストに合わせてスキルを照合すると、ターミナル上にそのスキルが読み込まれる様子が表示されます。何が起きているかは常に目に見える形で確認できます。

1.6 スキルを使うタイミング

スキルは、特定のタスクに適用される専門知識に最も向いています。代表的な使いどころは次のとおりです。

1

チームの基準・プロセス

コードレビューの基準、好みのコミットメッセージのフォーマットなど、人によってブレると困るもの。スキルにすれば、誰が依頼しても同じ形になります。

2

組織のガイドライン・テンプレート

ブランドガイドライン、特定の種類のドキュメント用テンプレートなど、参照はするが毎回は必要ない知識。必要なときだけ読み込まれるのがスキルの強みです。

3

特定分野の手順書

特定のフレームワーク向けのデバッグ用チェックリストなど、状況が限られている代わりに手順が細かい知識。CLAUDE.md に書くと煩雑になるものが向いています。

基本の考え方はシンプルです。同じことを Claude に何度も説明していると気づいたら、それはスキルとして書き起こすべきタイミングです。

注意: 何でもスキルにすればよいわけではない

「常に守ってほしい制約」は CLAUDE.md、「独立したコンテキストで任せたい作業」はサブエージェント、「ファイル保存時に必ず走らせたい処理」はフックのほうが適しています。スキルに押し込みすぎると、かえって管理が難しくなります。使い分けは第9章・第10章で詳しく扱います。

やってみよう 1-1: スキル化したい「繰り返し」を洗い出す

最初のスキルは第3章で実際に作ります。その前に、自分の作業の中から「スキルにする価値のある繰り返し」を見つけておきましょう。良いスキルは、実際に困っていることから生まれます。

手順

  1. 1 直近1週間で Claude Code に依頼した内容を思い出し、2回以上同じ説明をした指示を3つ書き出す。
  2. 2 それぞれについて、自分だけに必要か（個人用）／チーム全員に必要か（プロジェクト用）を判定する。
  3. 3 1つ選び、スキル名（kebab-case）と説明文を1文ずつ書いてみる。例:「commit-message — コミットメッセージを作成します。コミットするときに使用します。」

ヒント: 迷ったら「これを説明し忘れたら、Claude の出力は困った形になるか？」を基準にしてください。答えが「はい」なら、スキルにする価値があります。

理解度確認クイズ

  1. Q1. スキルは、ファイルとしてどのような構成になっていますか？

    回答を表示

    スキルは SKILL.md を含むフォルダです。SKILL.md は --- で区切られた frontmatter（name と description）と、その下の指示本文の2つの部分から構成されます。

  2. Q2. Claude はどうやって「今このスキルを使うべきだ」と判断していますか？

    回答を表示

    リクエストの内容と、利用可能なすべてのスキルの description を照合して判断します。合致するものが見つかると、そのスキルを有効化します。したがって description がスキル選択の決め手になります。

  3. Q3. 個人用スキルとプロジェクト用スキルは、それぞれどこに置き、何が違いますか？

    回答を表示

    個人用は ~/.claude/skills（Windows は C:/Users/<user>/.claude/skills）に置き、すべてのプロジェクトで自分について回ります。プロジェクト用はリポジトリの .claude/skills に置き、バージョン管理を通じてクローンした人全員に共有されます。

  4. Q4. スキルが CLAUDE.md やスラッシュコマンドと違う点は何ですか？

    回答を表示

    CLAUDE.md はすべての会話に読み込まれ、スラッシュコマンドは明示的にタイプする必要があります。スキルはリクエストに合致したときだけ自動的に読み込まれます。最初は name と description しか読み込まれないため、コンテキストウィンドウを無駄に埋めません。
