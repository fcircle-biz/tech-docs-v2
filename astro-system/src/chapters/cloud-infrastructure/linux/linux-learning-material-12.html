第12章 所要時間: 約60分

ネットワークとリモート操作の基本

ここまでの章では、自分のマシンの中だけで作業が完結していました。この章では視野を外へ広げ、IPアドレスやポートといったネットワークの基礎を理解し、ping・curlで相手に届くかを確かめます。そしてSSHを使い、離れた場所にあるサーバーへ安全にログインして操作する方法を学びます。第1章で触れた「CLIなら遠隔操作ができる」を、実際に体験する章です。

この章で学ぶこと

  • IPアドレス・ホスト名・ポート番号の役割と、localhost（127.0.0.1）の意味を説明できる
  • ip a・hostname -Iで自分の環境のネットワーク設定を確認できる
  • ping・curl・wgetで相手への到達性を確認し、情報やファイルを取得できる
  • ss -tulnで自分のマシンが待ち受けているポートを確認できる
  • SSHの公開鍵認証の仕組みを理解し、ssh-keygen・ssh・scpでリモート操作とファイル転送ができる
  • 秘密鍵を安全に扱う理由と、最低限守るべき権限設定を説明できる

12.1 IPアドレス・ホスト名・ポートの基礎

ネットワーク上のマシンとやり取りするには、まず「どのマシンの、どの窓口に届けるか」を指定する必要があります。そのために使われるのがIPアドレス・ホスト名・ポート番号の3つです。

たとえ話: 手紙の宛先

IPアドレスは郵便物の住所（番地）にあたります。数字の並びなので正確ですが人間には覚えにくいものです。ホスト名は「〇〇ビル」のような建物の名前で、人間が覚えやすい形でマシンを指します。ポート番号は建物の中の部屋番号です。同じ住所（マシン）でも、22号室にはSSH係、80号室にはWeb係というように、部屋ごとに別々の係（プログラム）が応対しています。

IPアドレス（IPv4）は 192.168.64.5 のように、0〜255の数字4つをドットで区切って書きます。192.168.x.x・10.x.x.x・172.16.x.x〜172.31.x.x のようなプライベートアドレスは、家庭内LANや今回のWSL2・Multipassの仮想ネットワークなど限られた範囲の中だけで使われます。これに対し、後述の 8.8.8.8 のようなインターネット上のサーバーは、世界中から直接届くグローバルアドレスを持っています。ポート番号は0〜65535の数字で、22番はSSH、80番・443番はWeb（HTTP/HTTPS）というように、代表的な番号はあらかじめ役割が決まっています（これらは12.3〜12.5節で実際に使います）。

図1: 同じIPアドレスでも、ポート番号ごとに別々の係が応対する

flowchart LR C["あなたの端末
curlコマンドなど"] -->|"192.168.64.5 へ接続"| H["サーバー
IPアドレス：192.168.64.5"] H --> P1["ポート22
sshdが待ち受け中"] H --> P2["ポート80
Webサーバーが待ち受け中"] H --> P3["ポート8000
待ち受けているプロセスなし"] P1 --> R1["ssh接続として処理される"] P2 --> R2["Webページとして処理される"] P3 --> R3["接続できない（Connection refused）"]

最後に、この章で何度も登場する特別なアドレスが 127.0.0.1 です。これはループバックアドレスと呼ばれ、常に「自分自身」を指します。別名 localhost（ローカルホスト）とも呼ばれ、どちらを使っても同じ意味です。ネットワークにつながっていなくても使え、外部に公開する前に自分のマシンの中だけでサーバーの動作を試したいときに重宝します。12.4節の実習でも使います。

12.2 自分のネットワーク設定を確認する

まずは自分の環境に割り当てられているIPアドレスを確認しましょう。ip a（ip address の省略形）は、マシンが持つすべてのネットワークインターフェースと、それぞれに割り当てられたIPアドレスを一覧表示します。

見本: ネットワークインターフェースの一覧を表示します。

ターミナル 
# ネットワークインターフェースとIPアドレスを一覧表示する
ip a

WSL2 での出力例です（主要な行のみ抜粋）。

出力結果（例） 
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN group default qlen 1000
    inet 127.0.0.1/8 scope host lo
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc mq state UP group default qlen 1000
    inet 172.29.128.1/20 brd 172.29.143.255 scope global eth0

1つ目の lo が先ほど説明したループバックインターフェースで、常に 127.0.0.1 です。2つ目が実際のネットワークにつながるインターフェースで、inet の右側に表示されている数字が、そのインターフェースに割り当てられたIPアドレスです。

インターフェース名とアドレスは環境によって違う

2つ目のインターフェース名やアドレスの値は、仮想化の方式によって変わります。WSL2では eth0 に 172.16.x.x〜172.31.x.x 系（プライベートアドレス）、Multipassでは enp0s1 のような名前に 192.168.64.x 系のアドレスが付くことが多いです。ここに挙げた値はあくまで一例なので、自分の画面に表示された名前とアドレスに読み替えてください。

出力が長くて読みにくいときは、hostname -I（大文字の I）を実行するだけで、自分に割り当てられたIPアドレスだけを1行で手早く確認できます（上の例なら 172.29.128.1 とだけ表示されます）。

12.3 相手に届くか確かめる・情報を取得する

自分のアドレスが分かったところで、今度は外部と実際にやり取りしてみましょう。まずは、相手のマシンが応答するかどうかを確認する ping です。

見本: Googleが公開しているDNSサーバー（8.8.8.8）に応答があるか確認します。

ターミナル 
# 8.8.8.8へ4回だけpingを送る（-cを付けないと止めるまで送り続ける）
ping -c 4 8.8.8.8

応答時間の数値は環境によって変わります。

出力結果（例） 
student@ubuntu:~$ ping -c 4 8.8.8.8

64 bytes from 8.8.8.8: icmp_seq=1 ttl=113 time=8.42 ms
64 bytes from 8.8.8.8: icmp_seq=2 ttl=113 time=7.95 ms
64 bytes from 8.8.8.8: icmp_seq=3 ttl=113 time=8.71 ms
64 bytes from 8.8.8.8: icmp_seq=4 ttl=113 time=8.03 ms

--- 8.8.8.8 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3005ms
rtt min/avg/max/mdev = 7.950/8.277/8.710/0.283 ms
student@ubuntu:~$

icmp_seq は送った順番、time が応答にかかった時間です。最後の2行に、送信・受信できた数と、往復時間の統計がまとまります。ping はICMPというプロトコルを使いますが、企業のネットワークやクラウドの設定によっては、セキュリティ上の理由でICMPだけを遮断していることがあります。

pingが失敗 = サーバーが止まっている、とは限らない

ICMPだけを遮断しているサーバーやネットワークでは、Webサーバー自体は正常に動いていても ping の応答が返ってきません。「応答がない」ときは、この後で紹介する curl など別の方法でも確認してみましょう。

次は curl です。URLを指定してサーバーと通信できる万能ツールで、-I（大文字）を付けると、ページの中身は取得せずヘッダー情報だけを確認できます。

ターミナル 
# ヘッダー情報だけを取得する（ページの中身は取得しない）
curl -I https://example.com

主要な行のみ抜粋しています。

出力結果（例） 
student@ubuntu:~$ curl -I https://example.com
HTTP/2 200
content-type: text/html; charset=UTF-8
date: Wed, 23 Sep 2026 08:00:00 GMT
（以下、サーバーの設定によって行数・内容は変わります）
student@ubuntu:~$

1行目の HTTP/2 200 の 200 は「正常に応答した」ことを示すステータスコードです（404や500は、第7章・第8章で使ったサンプルのアクセスログにも出てきました）。ページの中身も保存したい場合は -o でファイル名を指定します。

ターミナル 
# ページの中身をpage.htmlという名前で保存する
curl -o page.html https://example.com

サイズや速度は環境によって変わります。

出力結果（例）

                                 Dload  Upload   Total   Spent    Left  Speed

student@ubuntu:~$ ls page.html

よく似た役割のコマンドに wget があります。Ubuntuに入っていない場合は、第11章で学んだ apt で追加してください。

sudo apt install wget

curl はヘッダーの確認やAPIとのやり取りなど通信の中身を細かく調べるのが得意で、結果は標準出力にそのまま流れるので | で他のコマンドに渡せます。一方 wget はファイルを丸ごと保存することに特化しており、大きなファイルの取得に向いています。

12.4 待ち受けポートを確認する

図1で見たとおり、サーバーではポートごとに別々のプログラムが待ち受けています。自分のマシンで今どのポートが待ち受け状態かを確認するのが ss です（古い教材では netstat が使われていましたが、ss がその後継です）。

オプション 意味
-t TCP（curl・sshなどが使う接続型の通信）を対象にする
-u UDP（DNS問い合わせなどが使う通信）を対象にする
-l 接続を待ち受けている（Listen）ものだけ表示する
-n ホスト名やサービス名に変換せず、数字のまま表示する（表示が速い）
ターミナル 
# 待ち受け中のTCP/UDPポートを一覧表示する
ss -tuln

インストール済みのソフトによって行数は変わります。

出力結果（例） 
student@ubuntu:~$ ss -tuln
Netid  State   Recv-Q  Send-Q     Local Address:Port     Peer Address:Port
udp    UNCONN  0       0        127.0.0.53%lo:53              0.0.0.0:*
student@ubuntu:~$

Local Address:Port が「自分のどのアドレスの、どのポートで」待ち受けているかです。上の例の 127.0.0.53%lo:53（%lo は lo インターフェースでだけ待ち受けていることを表します）は、名前解決を行う systemd-resolved というプログラムがポート53（DNS）で待ち受けていることを示します（環境によっては TCP の53番や 127.0.0.54 の行も表示されます）。実際に何か自分でサーバーを起動すると、ここに新しい行が増えることを次の実習で確認します。

やってみよう 12-1: 簡易Webサーバーを起動してポートを確認する

Pythonに標準で入っている簡易Webサーバーを起動し、ここまで学んだ curl・ss で「サーバーが立ち上がり、ポートが待ち受け状態になる」様子を実際に確認します。

手順

  1. 1 作業ディレクトリ（~/linux-practice/ch12）を作成して移動する。
  2. 2 8000番ポートで簡易Webサーバーをバックグラウンド起動する（&は第10章で学んだジョブ制御）。
  3. 3 curl でアクセスし、ディレクトリ一覧のHTMLが返ることを確認する。
  4. 4 ss で8000番ポートが待ち受け状態になっていることを確認する。
  5. 5 確認できたら、バックグラウンドジョブ1番（サーバー）を kill %1 で終了させる（ジョブ番号は第10章のjobsと同じ考え方）。
ターミナル 
# 第12章用の作業ディレクトリを作って移動する
mkdir -p ~/linux-practice/ch12 && cd ~/linux-practice/ch12

# 127.0.0.1の8000番ポートで簡易Webサーバーをバックグラウンド起動する
python3 -m http.server 8000 --bind 127.0.0.1 &
sleep 1

# 別コマンドとしてアクセスし、8000番ポートの状態も確認する
curl http://127.0.0.1:8000/
ss -tuln | grep 8000

# 確認できたらバックグラウンドジョブ1番（サーバー）を終了する
kill %1

最後の Terminated（終了）の表示は、次に Enter を押した直後に現れることがあります。

curl の直後の 127.0.0.1 - - [...] "GET / HTTP/1.1" 200 - は、バックグラウンドで動くサーバーが画面に書き出したアクセスログです（第7章の access.log とよく似た形式です）。curlにはch12ディレクトリの中身（ディレクトリ一覧）を示すHTMLが返り、ssには127.0.0.1:8000がLISTEN状態で表示されます。

もう1つ、ネットワークまわりで覚えておきたいファイルが /etc/hosts です。名前とIPアドレスの対応表で、普段はDNSという仕組みがドメイン名をIPアドレスに変換してくれますが、このファイルに書いた対応はDNSより先に優先して使われます。

ターミナル 
# 名前とIPアドレスの対応表を見る
cat /etc/hosts

実際のファイルには、# で始まるコメント行や IPv6 用の行がほかにもあります（ここでは主要な行だけ示します）。

出力結果（例） 
student@ubuntu:~/linux-practice/ch12$ cat /etc/hosts
127.0.0.1       localhost
127.0.1.1       ubuntu
::1             localhost ip6-localhost ip6-loopback
student@ubuntu:~/linux-practice/ch12$

127.0.0.1 の行が12.1節で説明した localhost、127.0.1.1 の行がこのマシン自身のホスト名（127.0.1.1 はDebian系（Ubuntuを含む）の慣習で、自分のホスト名をループバックアドレスに結び付けています）、::1 の行はIPv6版のlocalhostです。開発中に「このドメイン名だけ手元のテスト用サーバーに向けたい」といった場面で、この仕組みを使うことがあります。

12.5 SSHで安全にリモート操作する

SSH（Secure Shell）は、離れた場所にあるサーバーへ暗号化された通信でログインし、手元のターミナルと同じようにコマンドを実行できる仕組みです。第1章で触れた「CLIならサーバーを遠隔操作できる」を実現しているのがこのSSHです。パスワードでもログインできますが、実務では公開鍵認証を使うのが基本です。

公開鍵認証では、数学的に対になった2つの鍵ファイルを使います。公開鍵はサーバー側に登録しておく「鍵穴」のようなもので、人に見られても問題ありません。秘密鍵はその鍵穴に対応する「鍵本体」で、自分だけが持ち、誰にも渡してはいけません。

図2: SSH公開鍵認証の流れ

sequenceDiagram participant C as あなたの端末（クライアント） participant S as サーバー Note over C: 事前準備（1回だけ） C->>C: ssh-keygen で鍵ペア（公開鍵・秘密鍵）を作る C->>S: 公開鍵を authorized_keys に登録する Note over C,S: ssh接続のたびに行われるやり取り C->>S: ssh で接続を要求する Note over C,S: 通信を暗号化する準備をし、この接続だけの確認用データ（セッションID）を両者で共有する C->>C: 秘密鍵でそのデータに署名する C->>S: 公開鍵と署名を送る（秘密鍵そのものは送らない） S->>S: 登録済みの公開鍵か確かめ、その公開鍵で署名を検証する S-->>C: 署名が正しければログイン成功

ポイントは、秘密鍵そのものはネットワークに一度も流れないことです。サーバーへ送られるのは公開鍵と「秘密鍵で作った署名」だけです。署名が正しいかどうかは公開鍵で確かめられますが、署名や公開鍵から秘密鍵を逆算することはできません。だからこそ、秘密鍵は自分の手元から一歩も出してはいけないのです。

まずは鍵ペアを作りましょう。-t ed25519 は鍵の方式の指定で、現在推奨されている、短く安全な方式です。

ターミナル 
# ed25519方式の鍵ペアを作成する
ssh-keygen -t ed25519

指紋やランダムアートは鍵ごとに毎回変わります。

出力結果（例） 
student@ubuntu:~/linux-practice/ch12$ ssh-keygen -t ed25519
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/student/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /home/student/.ssh/id_ed25519
Your public key has been saved in /home/student/.ssh/id_ed25519.pub
The key fingerprint is:
SHA256:（鍵ごとに異なるランダムな文字列） student@ubuntu
The key's randomart image is:
（鍵ごとに異なる図柄が表示される）
student@ubuntu:~/linux-practice/ch12$

保存先を聞かれたら、通常はそのままEnterで既定の場所（~/.ssh/id_ed25519）にして構いません。すでに同じ名前の鍵があるとOverwrite (y/n)?と聞かれます。上書きすると元の秘密鍵は二度と戻らず、その鍵で入っていたサーバーに入れなくなるので、nと答えて中止してください。パスフレーズは、秘密鍵ファイル自体にかける追加のパスワードです。空欄のままEnterでも作成できますが、パスフレーズを設定しておくと、万が一秘密鍵ファイルが盗まれても、パスフレーズを知らない相手はすぐには使えません。実行結果として、公開鍵（id_ed25519.pub）と秘密鍵（id_ed25519）の2つのファイルが ~/.ssh/ に作られます。

秘密鍵は絶対に他人へ渡さない

id_ed25519（拡張子 .pub が付かない方）が秘密鍵です。これは家の鍵の実物と同じで、コピーして人に渡したり、公開リポジトリやチャット・メールに貼り付けたりしては絶対にいけません。誤って公開してしまったら、その鍵ペアは信頼できなくなったとみなし、新しい鍵を作り直してください。フォルダとファイルの権限も、第9章のchmodで次のように絞っておきます（ssh-keygenは通常これを自動で設定します）。~/.sshディレクトリは700（自分だけが出入りできる）、秘密鍵ファイルは600（自分だけが読み書きできる）です（chmod 700 ~/.ssh・chmod 600 ~/.ssh/id_ed25519）。

公開鍵の登録は、パスワードでログインできるサーバーなら ssh-copy-id ユーザー名@ホスト を1回実行するのが手軽です（相手の ~/.ssh/authorized_keys に公開鍵が追記されます）。クラウドのサーバーでは、作成時に管理画面で公開鍵を登録するのが一般的です。公開鍵をサーバーに登録できたら、ssh コマンドで接続します。書式は ssh ユーザー名@ホスト名またはIPアドレス です。

ターミナル 
# ubuntuユーザーとしてリモートサーバーへ接続する
ssh ubuntu@203.0.113.10

初めて接続する相手のときだけ表示される確認です。

出力結果（例） 
student@ubuntu:~/linux-practice/ch12$ ssh ubuntu@203.0.113.10
The authenticity of host '203.0.113.10 (203.0.113.10)' can't be established.
ED25519 key fingerprint is SHA256:（サーバー鍵の指紋）.
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Warning: Permanently added '203.0.113.10' (ED25519) to the list of known hosts.
Welcome to Ubuntu 24.04 LTS
ubuntu@remote-server:~$

初めて接続する相手には「本当にこのサーバーでよいか」の確認が表示されます。これは「なりすましサーバーに接続していないか」を確かめるための重要な仕組みなので、yes と答える前に、相手が本当に接続したいサーバーかを確認する習慣を付けましょう。プロンプトが ubuntu@remote-server:~$ に変わったら、以降のコマンドは手元ではなくリモートサーバー側で実行されます。exitで手元のターミナルに戻れます。

ファイルをやり取りするには scp（secure copy）を使います。SSHと同じ認証の仕組みで、暗号化した通信でファイルをコピーします。

ターミナル 
# ローカルのreport.pdfをリモートサーバーのdocsフォルダへ送る
scp report.pdf ubuntu@203.0.113.10:/home/ubuntu/docs/

# リモートサーバーのログファイルを手元にコピーする
scp ubuntu@203.0.113.10:/var/log/syslog ./syslog-backup.log
出力結果（例） 
student@ubuntu:~/linux-practice/ch12$ scp report.pdf ubuntu@203.0.113.10:/home/ubuntu/docs/
report.pdf                              100%  245KB   3.1MB/s   00:00
student@ubuntu:~/linux-practice/ch12$

コピー元・コピー先のどちらに ユーザー名@ホスト:パス を書くかで、送る方向と受け取る方向を指定できます。cp（第5章）とよく似た感覚で使えます。

接続するサーバーが増えてくると、毎回 ssh ubuntu@203.0.113.10 のように打つのは大変です。~/.ssh/config というファイルに接続先を登録しておくと、短い名前で接続できます。

~/.ssh/config 
Host myserver
    HostName 203.0.113.10
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519

これを保存しておけば、次からは ssh myserver だけで同じ接続ができます。scp でも myserver:/path のように Host 名を使えます。

WSLでは追加の起動操作が必要なことがある

WSLではsystemdが無効な場合があり、その場合 systemctl（第10章）が使えず、SSHサーバーが自動起動しません。sudo service ssh start で手動起動してください。

やってみよう 12-2（任意）: 自分自身にSSH接続してみる

リモートサーバーを用意しなくても、自分のマシンにSSHサーバーを立てれば、公開鍵認証の一連の流れを一人で体験できます。

手順

  1. 1 SSHサーバー機能を追加する（Multipassには最初から入っています）。
  2. 2 自分の公開鍵を「許可された鍵」のリストに登録し、正しい権限を付ける。
  3. 3 自分自身（localhost）へSSH接続する。初回は接続確認に yes と答える。
ターミナル 
# SSHサーバー機能をインストールする
sudo apt install openssh-server

# 自分の公開鍵をauthorized_keysに追記し、権限を絞る
cat ~/.ssh/id_ed25519.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

# 自分自身へSSH接続する
ssh localhost
出力結果（例） 
student@ubuntu:~/linux-practice/ch12$ ssh localhost
The authenticity of host 'localhost (127.0.0.1)' can't be established.
ED25519 key fingerprint is SHA256:（鍵の指紋）.
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Warning: Permanently added 'localhost' (ED25519) to the list of known hosts.
Welcome to Ubuntu 24.04 LTS
student@ubuntu:~$ exit
logout
Connection to localhost closed.
student@ubuntu:~/linux-practice/ch12$

ログイン先のパスワードを入力せずにログインできたはずです（ssh-keygen でパスフレーズを設定した場合は Enter passphrase for key … と聞かれます。これはサーバーのパスワードではなく、手元の秘密鍵を使うための合言葉です）。これが公開鍵認証の便利さで、図2の「秘密鍵で署名 → サーバーが公開鍵で確認」が自分の手元だけで完結したことになります。

この章のまとめ

  • IPアドレス（住所）・ホスト名（建物名）・ポート番号（部屋番号）の組み合わせで通信相手を指定する。127.0.0.1（localhost）は常に自分自身を指す特別なアドレス。
  • ip a・hostname -Iで自分のIPアドレスを、ss -tulnで待ち受け中のポートを確認できる。
  • pingで到達性を、curl・wgetで情報やファイルを取得できる。ただしICMP遮断でpingだけ失敗することもある。
  • SSHの公開鍵認証では、秘密鍵を送らずに署名だけをやり取りしてログインする。ssh-keygen・ssh・scp・~/.ssh/configを使い分ける。
  • 秘密鍵は誰にも渡さず、~/.sshは700、秘密鍵ファイルは600の権限で守る。

確認問題

  1. Q1. localhost（127.0.0.1）とは何を指すアドレスですか。開発中のテストに便利な理由も説明してください。

    回答を表示

    常に「自分自身」を指す特別なアドレス（ループバックアドレス）です。実際のネットワークにつながっていなくても使えるため、作ったサーバーを外部に公開する前に、自分のマシンの中だけで動作を確認できて便利です。

  2. Q2. SSHの公開鍵認証で、ネットワークに一度も流れないものは何ですか。実際にサーバーへ送られるのは何ですか。

    回答を表示

    秘密鍵そのものは一度もネットワークに流れません。サーバーへ送られるのは、接続ごとに異なる確認用データに対して秘密鍵で作った署名だけです。サーバーは、登録済みの公開鍵でその署名が正しいかを確認します。

  3. Q3. pingで応答が返ってこないとき、必ずしも「サーバーが停止している」とは言えないのはなぜですか。

    回答を表示

    pingが使うICMPというプロトコルだけを、セキュリティ上の理由で遮断しているネットワークやサーバーがあるためです。Webサーバー自体は正常に動いていてもpingには応答しないことがあるので、curlなど別の方法でも確認するとよいでしょう。

  4. Q4. ss -tulnの-t・-u・-l・-nは、それぞれ何を意味しますか。

    回答を表示

    -tはTCPを対象にする、-uはUDPを対象にする、-lは待ち受け（Listen）状態のものだけ表示する、-nは名前解決をせず数字のまま表示する、という意味です。
