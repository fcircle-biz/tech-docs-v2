パッケージ管理と環境変数

第2章では「今は意味が分からなくてよい」と言われるまま実行した sudo apt update && sudo apt upgrade -y。第5章・第10章では「入っていなければ後で入れます」と保留にしてきた tree や htop。この章では、それらの正体をまとめて回収します。Ubuntuのパッケージ管理コマンドaptでソフトを検索・導入・削除する方法、コマンドの実体がどこにあるかを調べるwhich・type、そしてシェルの挙動を決める環境変数とPATH、~/.bashrcのカスタマイズを学びます。

この章で学ぶこと

  • パッケージ・パッケージマネージャー・リポジトリの関係を説明できる
  • apt updateとapt upgradeの違いを理解し、install・search・show・removeでtreeとhtopを実際に導入できる
  • which・typeでコマンドの実体（実行ファイルの場所）を調べられる
  • シェル変数と環境変数の違いを理解し、exportで子プロセスに引き継げる
  • PATHの仕組み（左から順にディレクトリを探す）を説明できる
  • ~/.bashrcにalias・exportを安全に追記し、sourceで反映できる

11.1 パッケージとapt、リポジトリの仕組み

Windows で新しいソフトを使いたいとき、公式サイトからインストーラーをダウンロードして実行しますよね。Linuxにも同じような仕組みがありますが、やり方はまったく違います。Ubuntuでは、ソフトをパッケージという単位で管理し、パッケージマネージャーというツールでまとめて検索・導入・更新・削除します。

パッケージ

実行ファイル本体に加え、設定ファイルや「動かすために他に何が必要か（依存関係）」といった情報をひとまとめにした配布単位です。

パッケージマネージャー

パッケージの検索・導入・更新・削除をまとめて管理するツールです。Ubuntu（Debian系）ではaptを使います。

リポジトリ

パッケージが保管されているネット上の配布サーバーです。aptはここへ問い合わせて一覧を取得したり、ダウンロードしたりします。

sudo apt install パッケージ名を実行したとき、裏側では次のような流れが起きています。

図1: apt installが実行されるまでの流れ

flowchart LR R["リポジトリ
ネット上のパッケージ置き場"] -->|"① 一覧を取得"| L["パッケージ一覧
手元のキャッシュ"] L -->|"② 名前を検索"| F["目的のパッケージを特定"] F -->|"③ ダウンロード"| D["パッケージファイルを取得"] D -->|"④ 展開・配置"| I["インストール完了
コマンドとして使える"]

図の①にあたるのがapt updateです。②〜④をまとめて行うのがapt installです。ここで大事なのは、apt updateは「一覧を最新にするだけ」で、すでに入っているソフト自体は1つも変わらないという点です。入っているソフトを実際に新しくするのは、もう1つのapt upgradeの役目です。

コマンド 何をするか たとえるなら
apt update リポジトリから最新のパッケージ一覧を手元にダウンロードする 通販サイトの「新着・改訂情報」を確認する
apt upgrade 一覧をもとに、すでに入っているソフトを新しい版に置き換える 確認した新着情報をもとに、実際に商品を注文して入れ替える

第2章のコマンドの意味、ここで回収

第2章で実行したsudo apt update && sudo apt upgrade -yは、「①一覧を最新にする（update）→ ②成功したら、入っているソフトを一気に更新する（upgrade、-yは確認をすべて「はい」にする）」という2段階の処理を、&&（第8章で学んだ「前が成功したら次を実行」）でつないだものだったのです。updateだけではソフトは更新されないため、2つはセットで覚えておきましょう。

11.2 treeとhtopを実際に入れてみる

第5章では「ディレクトリ構造を絵で見たいならtreeというコマンドが便利だが、入っていなければls -Rで代用する」と保留にしていました。第10章のtopも「htopという見やすい版がある」と予告だけしていました。ここで両方を実際に導入します。まずは一覧を最新にしてから、パッケージ名をスペース区切りで並べて一度にインストールします。

ターミナル 
# パッケージ一覧を最新にする（ソフト自体はまだ変わらない）
sudo apt update
出力結果（例） 
student@ubuntu:~$ sudo apt update

student@ubuntu:~$

# tree（ディレクトリ構造表示）とhtop（プロセス監視）を一度に入れる
sudo apt install tree htop
出力結果（例） 
student@ubuntu:~$ sudo apt install tree htop

  htop tree

11.3 コマンドの居場所を調べる（which・type）

treeをインストールしたあと、「実際にどこに置かれたのか」を確認する方法が2つあります。1つ目はwhichです。

ターミナル 
# treeコマンドの実行ファイルがどこにあるか調べる
which tree
出力結果（例） 
student@ubuntu:~$ which tree
/usr/bin/tree

whichは、後述するPATHの中を探して見つかった実行ファイルのフルパスだけを表示する、シンプルな道具です。第3章で紹介したtypeでも同じように調べられますが、typeはさらに「エイリアスなのか」「シェル自体に組み込まれた機能（ビルトイン）なのか」まで区別してくれる、より守備範囲の広いコマンドです。

ターミナル 
# typeでも同じように調べられる（第3章の復習）
type tree
# cdはシェル自体の機能（ビルトイン）
type cd
出力結果（例） 
student@ubuntu:~$ type tree
tree is /usr/bin/tree
student@ubuntu:~$ type cd
cd is a shell builtin

（同じターミナルで直前にtreeを実行していると、tree is hashed (/usr/bin/tree)と表示されます。hashedは「一度探した場所をシェルが覚えている」という意味で、指している場所は同じです）treeは「実行ファイルの場所」が、cdは「シェル自体が持つ機能」だと表示されました。この違いは、11.6節で自分のaliasを作ったときにもう一度使います。

11.4 環境変数とシェル変数

プログラムは、動作に必要な情報の一部を「あらかじめシェルが用意した変数」から受け取ります。これを環境変数と呼びます。たとえば自分のホームディレクトリやユーザー名、使っているシェルの種類は、次のように調べられます。

ターミナル 
# 自分のホームディレクトリを確認する
echo $HOME
# 自分のユーザー名を確認する
echo $USER
# いま使っているシェルを確認する
echo $SHELL
出力結果（例） 
student@ubuntu:~$ echo $HOME
/home/student
student@ubuntu:~$ echo $USER
student
student@ubuntu:~$ echo $SHELL
/bin/bash

設定されている環境変数を全部まとめて見たいときはenvまたはprintenvを使います。どちらもほぼ同じ結果になります。

ターミナル 
# 設定されている環境変数を全部表示する
printenv
出力結果（例） 
student@ubuntu:~$ printenv
SHELL=/bin/bash
HOME=/home/student
USER=student
LANG=C.UTF-8
（中略。この他にも多数の環境変数が並ぶ）
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin
student@ubuntu:~$

envとprintenvの細かい違い

printenvは環境変数の表示専用のコマンドです。一方envは、本来「指定した環境変数のもとで別のコマンドを実行する」ためのコマンドで、コマンドを指定しなかった場合に一覧を表示する、という副次的な使い方をしています。一覧を見るだけなら、どちらを使っても構いません。

シェルでは変数名=値と書くだけで、自分で変数を作れます（=の前後に空白を入れないのがルールです。変数の詳しい使い方は第13章で学びます）。では、MY_VAR="hello"のように作った変数は環境変数なのでしょうか。実は違います。ただ代入しただけの変数はシェル変数で、今のシェルの中でしか使えません。exportを付けてはじめて、そこから起動する別のプログラム（子プロセス）にも自動的に引き継がれる環境変数になります。実際に確かめてみましょう。

ターミナル 
# exportを付けずにシェル変数を作る
MY_VAR="hello"
echo $MY_VAR
# 別のbash（子プロセス）を起動して確認する
bash -c 'echo $MY_VAR'
出力結果（例） 
student@ubuntu:~$ MY_VAR="hello"
student@ubuntu:~$ echo $MY_VAR
hello
student@ubuntu:~$ bash -c 'echo $MY_VAR'

student@ubuntu:~$

今のシェルではhelloと表示されたのに、子プロセスの中では何も表示されません（空行になる）。exportを付けて同じことを試すと、結果が変わります。（'echo $MY_VAR'をシングルクォートで囲むのは、今のシェルではなく子プロセスのbashに$MY_VARを展開させるためです。ダブルクォートにすると今のシェルが先に展開してしまい、違いを確かめられません）

ターミナル 
# 今度はexportを付けて環境変数にする
export MY_VAR="hello"
bash -c 'echo $MY_VAR'
出力結果（例） 
student@ubuntu:~$ export MY_VAR="hello"
student@ubuntu:~$ bash -c 'echo $MY_VAR'
hello

図2: exportの有無で子プロセスへの引き継ぎが変わる

flowchart TD subgraph NG["exportしない場合"] direction TB P1["親シェル：MY_VAR=hello"] -->|"子プロセスを起動"| C1["子プロセス（bash -c）
MY_VARは空っぽ"] end subgraph OK["exportした場合"] direction TB P2["親シェル：export MY_VAR=hello"] -->|"子プロセスを起動"| C2["子プロセス（bash -c）
MY_VARにhelloが届く"] end

重要ポイント

シェル変数は今のシェルの中だけで使える、いわばそのシェル専用のメモです。exportすると環境変数に昇格し、そのシェルから新しく起動するプログラム（子プロセス）すべてに、コピーの形で自動的に引き継がれます。$HOMEや$PATHがどのプログラムからも参照できるのは、あらかじめexportされているからです。

11.5 PATHの仕組み

11.2節でtreeという名前だけで実行できたのはなぜでしょうか。/usr/bin/treeとフルパスで指定しなくても動いたのは、PATHという環境変数のおかげです。PATHには「コマンドを探すディレクトリの一覧」が、コロン:区切りで入っています。

ターミナル 
# コマンドを探すディレクトリの一覧を表示する
echo $PATH
出力結果（例） 
student@ubuntu:~$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin

treeのようにコマンド名だけを入力すると、シェルはPATHに並んだディレクトリを左から順に探し、最初に見つかった実行ファイルをそのまま実行します。treeは/usr/binにあるので、①②③と探した末に④で見つかる、という流れです。

図3: PATHの探索の流れ（treeを実行する場合）

flowchart LR CMD["treeと入力"] --> D1["① /usr/local/sbin"] D1 -->|見つからない| D2["② /usr/local/bin"] D2 -->|見つからない| D3["③ /usr/sbin"] D3 -->|見つからない| D4["④ /usr/bin"] D4 -->|treeがある| RUN["/usr/bin/treeを実行"]

もしどのディレクトリにも見つからなければ、第3章・第6章で見たコマンド名: command not foundのエラーになります。逆に、PATHに登録されていない場所（たとえば第13章でスクリプトを置く~/linux-practice/ch13）にあるコマンドは、./script.shのように相対パスや絶対パスで直接指定しない限り実行できません（第13章で扱います）。なお、Ubuntuの~/.profileは、ホームにbinディレクトリがあると、ログイン時に自動でPATHへ追加する設定になっています。

WSLでは末尾にWindows側のパスが続く

WSLでecho $PATHを実行すると、Linux側のディレクトリの後ろに/mnt/c/Windows/system32のような/mnt/c/...から始まるパスがいくつも続きます。これはWindows側の実行ファイル（.exe）をLinux側からも名前だけで呼び出せるようにするための仕組みで、WSLならではの表示です。Multipassでは表示されません。

11.6 ~/.bashrcをカスタマイズする

~/.bashrcは、新しいターミナルを開いて対話的なbashが起動するたびに、自動で読み込まれる設定スクリプトです。ここに自分好みのalias（短縮コマンド）や環境変数を書いておくと、次にターミナルを開いたときから毎回自動で使えるようになります。実は、Ubuntuの~/.bashrcには最初から便利なaliasがいくつか仕込まれています。第3章でtype lsを実行したときに表示されたls --color=autoも、このファイルで設定されているaliasです。ほかにllというaliasも用意されています。

ターミナル 
# llの正体を調べる
type ll
出力結果（例） 
student@ubuntu:~$ type ll
ll is aliased to `ls -alF'

11.3節ではtreeが「実行ファイルの場所」、cdが「シェルのビルトイン」でしたが、llはls -alFという長いコマンドを短く呼び出すalias（エイリアス）だと分かります。ここに自分だけのaliasを追加してみましょう。まずは編集前に、念のためバックアップを取っておきます。

ターミナル 
# 編集前に念のためバックアップを取る
cp ~/.bashrc ~/.bashrc.bak
# nanoで.bashrcを開く（第6章の復習）
nano ~/.bashrc

nanoが開いたら、Ctrl+Endや矢印キーでファイルの一番下まで移動し、次の2行を追記します。

~/.bashrc（ファイル末尾に追記） 
# linux-practiceへ一発で移動するエイリアス
alias lp='cd ~/linux-practice'
# デフォルトのテキストエディタをnanoに指定する
export EDITOR=nano

書けたらCtrl+O→Enterで保存し、Ctrl+Xでnanoを終了します（第6章の復習）。ただし、~/.bashrcは新しいターミナルを開いたときにしか読み込まれないため、今開いているターミナルには反映されていません。sourceコマンドで、今のシェルに即座に反映させます。

ターミナル 
# 変更を今開いているシェルに反映する
source ~/.bashrc
# 追加したaliasを試す
lp
pwd
# 追加した環境変数を確認する
echo $EDITOR
出力結果（例） 
student@ubuntu:~$ source ~/.bashrc
student@ubuntu:~$ lp
student@ubuntu:~/linux-practice$ pwd
/home/student/linux-practice
student@ubuntu:~/linux-practice$ echo $EDITOR
nano

sourceは、指定したファイルの内容を「新しいプロセスを作らず、今のシェルの中でそのまま実行する」コマンドです（. ~/.bashrcのようにピリオド1つでも同じ意味になります）。もしbash ~/.bashrcのように実行すると、11.4節で見た「子プロセス」の中で実行されてしまうため、aliasやexportした結果が元のシェルには残りません。

プロンプトの見た目も変えられる

~/.bashrcには、プロンプト（student@ubuntu:~$の部分）の見た目を決めるPS1という変数もあります。色を付けたり、現在時刻を表示したりできますが、書式が複雑なため本ガイドでは扱いません。慣れてきたら「bash PS1 カスタマイズ」などで調べてみてください。

設定ファイルをいじるときは、特に慎重に

  • 追記のつもりが上書きになる — echo "alias lp='cd ~/linux-practice'" > ~/.bashrcのように、追記の>>と間違えて上書きの>（第8章）を使うと、既存の~/.bashrcの中身がすべて消え、llなどの標準aliasも失われます。だからこそ本節冒頭で~/.bashrc.bakを作りました。
  • PATHを丸ごと置き換えてしまう — export PATH=/some/dirのように$PATHを付け忘れると、それまでのPATHが消えて/some/dirだけになり、lsやtreeすら「command not found」になります。ディレクトリを追加したいときは、必ずexport PATH="$HOME/bin:$PATH"のように既存の$PATHを含めて書きます。
  • 壊してしまったら — /usr/bin/cp ~/.bashrc.bak ~/.bashrcのようにフルパスで元に戻し、ターミナルを開き直します（~/.bashrcに書かず、今のシェルでexportしただけなら、ターミナルを開き直すだけで元に戻ります）。
  • 出所不明のリポジトリ・スクリプトをsudoで入れない — sudoで実行する操作はシステム全体に影響します。信頼できない手順書のリポジトリ追加コマンドや、中身を確認していないインストールスクリプトをsudoで実行しないでください。

やってみよう 11-2: 自分だけのエイリアスを追加する

~/.bashrcに自分専用のaliasをもう1つ追加し、反映と動作確認までの一連の流れを自分の手で行います。

手順

  1. 1 すでに~/.bashrc.bakがあるか確認する（無ければcp ~/.bashrc ~/.bashrc.bakを実行する）。
  2. 2 nanoで~/.bashrcを開き、末尾にalias ..='cd ..'（1つ上の階層へ移動する）を追記して保存する。
  3. 3 source ~/.bashrcで反映し、適当なディレクトリで..を実行して動くか確認する。
  4. 4 type ..を実行し、自分が追加したaliasとして認識されていることを確認する。

この章のまとめ

  • Ubuntuはaptでパッケージを管理する。apt updateは一覧の更新、apt upgradeはソフト自体の更新で、役割が異なる。
  • install・search・show・remove・list --installedの基本操作を扱えるようになり、treeとhtopを実際に導入した。
  • which・typeでコマンドの実体（場所・ビルトイン・alias）を調べられる。
  • シェル変数は今のシェルだけ、exportすると環境変数として子プロセスにも引き継がれる。
  • PATHはコマンドを探すディレクトリの一覧で、左から順に探索される。
  • ~/.bashrcにalias・exportを追記しsourceで反映する手順と、バックアップの重要性を身につけた。

確認問題

  1. Q1. apt updateとapt upgradeは、それぞれ何をするコマンドですか。

    回答を表示

    apt updateは、リポジトリから最新のパッケージ一覧を手元にダウンロードするだけで、インストール済みのソフト自体は変更しません。apt upgradeは、その一覧をもとに、すでにインストールされているソフトを実際に新しい版へ更新します。

  2. Q2. シェル変数と環境変数の違いは何ですか。exportは何のためのコマンドですか。

    回答を表示

    シェル変数は、代入しただけの変数で今のシェルの中でしか使えません。環境変数は、そこから起動する別のプログラム（子プロセス）にも自動的に引き継がれる変数です。exportは、シェル変数を環境変数に昇格させ、子プロセスへ引き継がれるようにするコマンドです。

  3. Q3. PATHとは何ですか。コマンド名だけを入力したとき、シェルはどのような順序で実行ファイルを探しますか。

    回答を表示

    PATHは、コマンドの実行ファイルを探すディレクトリの一覧を、コロン区切りで保持した環境変数です。コマンド名だけを入力すると、シェルはPATHに並んだディレクトリを左から順に探し、最初に見つかった実行ファイルを実行します。どこにも見つからなければ「command not found」になります。

  4. Q4. export PATH=/some/dirのように$PATHを付けずに実行すると何が起きますか。ディレクトリを追加する正しい書き方も答えてください。

    回答を表示

    それまでのPATHの中身がすべて/some/dirだけに置き換わってしまい、lsやtreeなど、ほとんどのコマンドが「command not found」になります。正しくはexport PATH="$HOME/bin:$PATH"のように、既存の$PATHを含めて追加する形で書きます。
