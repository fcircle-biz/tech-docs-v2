運用の基礎 — キャッシュ・アラート・本番構成

これまでの章では、Docker Compose 上の学習環境で Superset の機能を一通り動かしてきました。最終章となるこの章では視点を変え、チームで使い続けるための運用を学びます。設定ファイルのまとめ方、表示を速くするキャッシュと非同期クエリ、定期配信のアラート＆レポート、環境を引っ越すためのエクスポート／インポート、そしてバックアップとバージョンアップの進め方を押さえ、学習環境を本番に近づけるための視点を身につけましょう。

この章で学ぶこと

  • 学習環境（第2章のDocker Compose構成）と本番環境で何を変える必要があるかを説明できる
  • 設定ファイル superset_config.py の役割と、代表的な設定項目を挙げられる
  • キャッシュ・非同期クエリ（Celery）・アラート＆レポートの仕組みを説明できる
  • エクスポート／インポートとバックアップの考え方を理解し、本番移行のチェックリストを作れる

14.1 学習環境と本番環境の違い

第2章で構築した Docker Compose 環境は、Superset 本体・メタデータDB・Redis・Celery ワーカーが一通りそろっており、機能を試したり評価したりするには十分な構成でした。ただしこの構成は学習をすぐ始められることを優先しており、そのままチームの業務で使い続ける（本番運用する）ことは想定していません。Apache Superset 公式も、Docker Compose 構成は開発・評価用途を主目的としており、本番用途には推奨・サポートしていないと明記しています（単一ホスト前提のため冗長化できないこと、データが Docker ボリュームに置かれバックアップ対象外であることが主な理由です）。本番相当の構成で動かす場合は、公式が案内する Kubernetes（Helm チャート）などの方式を検討します。

「Superset本体＋メタデータDB＋Redis＋Celeryワーカー」という部品の骨格そのものは、学習環境でも本番環境でも変わりません。変わるのは、それぞれの部品の中身をどれだけ丁寧に用意するかです。本番で最低限そろえておきたい要素を整理します。

項目 本番環境で必要なこと
メタデータDB 独立して管理された PostgreSQL（推奨）を使う。第2章の構成もPostgreSQLだが、使い捨てのコンテナ内DBではなく、バックアップ・監視の対象として独立して運用する点が異なる。SQLite は開発・評価用途には使えるが、公式はセキュリティ・スケーラビリティ・データ整合性の観点から本番メタデータDBとしての利用を強く非推奨（strongly discouraged）としている。本番ではサポート対象の PostgreSQL または MySQL を使う
SECRET_KEY 既定値から必ず変更し、環境変数やシークレット管理サービスなど、ソースコードに書かない方法で保管する
通信の暗号化 HTTPS を使う。多くの場合はリバースプロキシやロードバランサー側で暗号化を終端する
バックアップ メタデータDBを定期的にバックアップし、実際に復元できることまで確認しておく（14.7）
監視 プロセスが生きているか、ディスクやメモリを使い切っていないか、エラーログを継続的に確認できる仕組み

SQLite に気づいたら要注意

Superset のインストール方法によっては、メタデータDBの既定値が SQLite になっていることがあります。SQLite はインストール不要ですぐ始められるため開発・評価には有用ですが、同時アクセスや大量データに弱く、壊れたときの復旧手段も乏しいものです。公式は本番環境での SQLite 利用を強く非推奨としているため、複数人で使う環境では早い段階で PostgreSQL（または MySQL）へ切り替えてください。

14.2 設定ファイル superset_config.py

14.1 で挙げた項目の多くは、superset_config.py という1つの Python ファイルにまとめて書きます。Superset は起動時にこのファイルを読み込み、既定の設定を上書きします。Docker で動かしている場合は、コンテナにこのファイルを読み込ませる場所（環境変数 SUPERSET_CONFIG_PATH や、コンテナへのマウント）を compose ファイル側で指定します。

代表的な設定項目を確認しましょう。設定項目名はバージョンによって変わることがあるため、実際に設定するときは公式ドキュメントで最新の項目名を確認してください。

設定項目 役割
SECRET_KEY セッションやCookieの署名に使う鍵。漏れると認証を偽装されるおそれがある
SQLALCHEMY_DATABASE_URI メタデータDBへの接続文字列（第4章で学んだ接続URIと同じ書式）
FEATURE_FLAGS 実験的機能・個別機能のオン／オフを切り替える辞書
キャッシュ関連の設定 キャッシュの保存先とタイムアウトを用途別に指定する（14.3で扱う）
ROW_LIMIT チャートが一度に取得する行数の既定上限
Webサーバのタイムアウト 時間のかかるクエリの実行中に、途中で応答が打ち切られないようにする待ち時間の上限

最小構成の例を見てみましょう。値をファイルに直接書き込まず環境変数から読み込む形にしておくと、このファイル自体をGitで管理しても、パスワードなどの秘密情報が漏れる心配がありません。

superset_config.py 
# superset_config.py の最小構成例（値は環境変数から読み込む）
import os

# セッション署名の鍵。既定値のまま使わない
SECRET_KEY = os.environ["SUPERSET_SECRET_KEY"]
# メタデータDB（チャート・ダッシュボード定義の保存先）
SQLALCHEMY_DATABASE_URI = os.environ["SUPERSET_DATABASE_URI"]
# チャートのクエリ結果（データ）をキャッシュする設定
DATA_CACHE_CONFIG = {
    "CACHE_TYPE": "RedisCache",
    "CACHE_REDIS_URL": os.environ["SUPERSET_CACHE_URL"],
    "CACHE_DEFAULT_TIMEOUT": 86400,
}
# チャートが一度に取得する行数の上限
ROW_LIMIT = 10000

SECRET_KEY を既定値のまま使わない

サンプルの compose ファイルや公式チュートリアルに載っている SECRET_KEY は、あくまで動作確認用で誰でも知っている値です。既定値のまま公開環境で使うと、セッションの署名を偽装されるおそれがあります。バージョンによっては、既定値のまま起動しようとすると警告が表示されたり、起動できなかったりすることもあります。十分な長さのランダムな値へ変更し、コードには直接書かず環境変数などで渡してください。

14.3 キャッシュで表示を速くする

第1章で確認したとおり、Superset はチャートやダッシュボードを開くたびに接続先のデータベースへ SQL を発行します。同じダッシュボードを何度も開く、同じ集計を複数人が見る、といった場面ではまったく同じクエリが何度も実行されることになります。この無駄を減らすのがキャッシュです。一度実行した結果を Redis などに一時保存しておき、次に同じ問い合わせが来たときはデータベースへ聞きに行かず、保存しておいた結果をそのまま返します。

キャッシュは1種類ではなく、用途ごとに別々の設定があります。代表的なものを挙げます。

用途 キャッシュする内容 設定キー 要否
データ用キャッシュ チャートが発行したSQLの実行結果 DATA_CACHE_CONFIG 任意
フィルタ状態のキャッシュ ネイティブフィルタ（第11章）で選んだ値など、画面の状態 FILTER_STATE_CACHE_CONFIG 必須（※）
Explore の一時データ チャート編集中（第8章）の一時的な設定内容 EXPLORE_FORM_DATA_CACHE_CONFIG 必須（※）
メタデータキャッシュ ダッシュボード一覧など画面まわりの補助的な情報 CACHE_CONFIG 任意

※ 「必須」の意味: フィルタ状態と Explore の一時データは何らかのキャッシュが必要で、この2つを設定しなかった場合は、Superset がメタデータDBを保存先にする組み込みキャッシュへ自動的にフォールバックします。つまり「設定しないと動かない」のではなく、設定しないとメタデータDBに負荷がかかるということです。公式も専用のキャッシュ（Redis 推奨）の利用を推奨しているため、本番では明示的に設定してください。

それぞれに有効期限（タイムアウト）を設定します。ここには「鮮度」と「速さ」のトレードオフがあります。タイムアウトを短くすれば表示される数字は新しくなりやすい一方、キャッシュが効く時間が短くなりデータベースへの問い合わせが増えます。長くすれば表示は速く安定しますが、元データが更新されても、しばらく古い数字が表示され続けることになります。全体の既定タイムアウトとは別に、データセットやチャート単位でもタイムアウトを個別に設定できるため、「このダッシュボードは1日1回の更新で十分」「このチャートはほぼリアルタイムで見たい」といった使い分けが可能です。

重要ポイント

「元データを更新したのにダッシュボードの数字が変わらない」という問い合わせは、故障ではなくキャッシュが効いているために起きることがよくあります。まずタイムアウトの設定を疑い、必要であればキャッシュを使わずに再取得する操作で切り分けてください。表示が速いことと、数字が最新であることは常に両立するとは限りません。

14.4 非同期クエリと Celery

集計に何十秒もかかるような重いクエリを、画面からのリクエストが返ってくるまでずっと待たせたまま実行すると、Webサーバの応答が詰まったり、途中でタイムアウトして失敗したりします。この問題を避けるため、Superset は重い処理を別のプロセスに任せて非同期に実行する仕組みを持っています。登場する部品は3つです。

flowchart LR W["SupersetのWebサーバー"] -->|ジョブを登録| B[("メッセージブローカー
Redis")] B --> C["Celeryワーカー"] C -->|SQLを実行| DB[("分析対象のDB")] C -->|結果を保存| S[("結果の保存先
Redis など")] W -->|完了を確認して取得| S

Webサーバーは「このクエリを実行してほしい」というジョブをメッセージブローカー（第2章で導入した Redis）に登録するだけで、すぐに応答を返します。控えているCelery ワーカーがジョブを受け取って実際にSQLを実行し、終わったら結果を保存します。画面側は完了を確認できたタイミングで結果を取りに行くため、Webサーバーが長時間ブロックされません。多くの構成では、メッセージブローカーと結果の保存先はどちらも同じRedisが兼ねています。定期的にジョブを登録する処理（後述のアラート＆レポート）のためには、これに加えてCelery beatと呼ばれるスケジューラのプロセスも必要です。

この仕組みは、実は本教材ですでに一度登場しています。第5章の SQL Lab で非同期実行を選んだときに動いていたのが、まさにこの Celery ワーカーです。そして次に説明するアラート＆レポートの定期実行も、同じ Celery の仕組みの上で動いています。Celery ワーカーを止めてしまうと、非同期クエリだけでなくアラート＆レポートも動かなくなる、という関係を覚えておいてください。

14.5 アラートとレポート

Alerts ＆ Reports（アラート＆レポート）は、ダッシュボードやチャートを定期的に実行し、結果をメールや Slack へ自動で送る機能です。「毎朝、担当者がダッシュボードを開いて確認する」という作業を、Superset 側からの通知に置き換えられます。アラートとレポートは似ていますが、送られるタイミングの考え方が異なります。

項目 アラート（Alert） レポート（Report）
送られるタイミング 指定した条件（しきい値など）を満たしたとき 決まったスケジュール（毎朝9時など）
向いている目的 異常や注意すべき変化にいち早く気づく 定例の共有・配布
具体例 在庫数が一定を下回ったら通知する 毎週月曜の朝に先週の売上ダッシュボードを送る

どちらも画面上で条件やスケジュールを設定するだけで使えますが、裏側では複数の部品が連携して動いています。実際に動かす前に、次がそろっているか確認してください。

  • 機能フラグ ALERT_REPORTS — アラート＆レポートは既定で無効なため、FEATURE_FLAGS でこのフラグを有効にする必要がある
  • Celery ワーカーとスケジューラ（beat） — 14.4 の非同期の仕組み。決まった時刻・条件のチェックはこのスケジューラが担う
  • ヘッドレスブラウザ — ダッシュボードやチャートを画像として撮影（スクリーンショット化）するために使う、画面を持たないブラウザ。Superset 4.1.x以降はPlaywright ＋ Chromium（機能フラグPLAYWRIGHT_REPORTS_AND_THUMBNAILS）が公式推奨
  • メール／Slack の送信設定 — 送信元メールサーバの情報や、Slackへの投稿に使うトークン・Webhookなどの設定
  • ドライラン設定の確認 — 第2章のDocker Compose環境ではALERT_REPORTS_NOTIFICATION_DRY_RUN = Trueが既定になっており、スクリーンショットは撮られても実際にはメールやSlackへ送信されない。送信まで確認したい場合はこの設定を見直す

設定の詳細は公式ドキュメントを確認

アラート＆レポートを有効化する設定や、メール・Slack連携の具体的な手順はバージョンによって変わりやすい部分です。実際に設定する際は、必ず公式ドキュメント（Alerts and Reports）で最新の手順を確認してください。

14.6 エクスポートとインポート

ダッシュボードやデータセットは、画面の一覧からZIPファイルとして書き出せます。中身は YAML 形式の定義ファイルの集まりで、別の Superset 環境にインポートすれば同じダッシュボードを再現できます。この仕組みは、主に3つの場面で役立ちます。

  • 環境間の移行 — 検証環境で作って確認したダッシュボードを、本番環境へそのまま持ち込む
  • バックアップ — 誤って消してしまったときに戻せるよう、定義だけを退避しておく
  • Git での定義管理 — 書き出したYAMLをリポジトリにコミットし、誰が・いつ・何を変えたかを履歴として残す

便利な機能ですが、エクスポート・インポートのときは次の点に注意してください。

注意点 内容
接続情報は含まれない データベース接続のパスワードなどの認証情報はZIPに含まれない。インポート先の環境であらためて設定する必要がある
IDと依存関係 ダッシュボードはチャートに、チャートはデータセットに依存する。参照先がインポート先に存在しないと正しく復元できない
同名オブジェクトの扱い 同一の定義がインポート先に既にある場合、上書きするか別物として扱われるかの挙動を事前に確認しておく

14.7 バックアップとバージョンアップ

Superset の運用で最優先に守るべきものはメタデータDBです。分析対象のデータベースが無事でも、メタデータDBを失うと、これまで作り込んだチャート・ダッシュボード・権限の定義がすべて消えてしまいます。バックアップの基本は、このメタデータDBを対象にした定期的なバックアップ（多くの場合はデータベース標準のダンプ機能を使う）です。

バージョンアップも同じくメタデータDBを軸に考えます。Superset は開発が活発なぶん、バージョンによって設定項目や既定の挙動が変わることがあります。次の手順で、落ち着いて進めましょう。

  1. 1 アップグレード前にメタデータDBをバックアップする。何かあってもここに戻れる状態を作っておく
  2. 2 新しいバージョンのリリースノートを確認し、破壊的変更（Breaking Changes）や設定項目名の変更が無いかを調べる
  3. 3 検証環境で新しいバージョンを起動し、データベースマイグレーション（superset db upgrade など）を実行してメタデータDBの構造を更新する
  4. 4 続けてsuperset initを実行する。各ロールに紐づく権限が既定値へ再同期されるため、ロールをカスタムしている場合は差分が出ないか第13章13.7とあわせて確認する
  5. 5 検証環境で、主要なダッシュボード・権限（第13章）・アラート＆レポートが問題なく動作するか確認する
  6. 6 問題がなければ、本番環境でも同じ手順（バックアップ → マイグレーション → superset init → 確認）を実施する

「いきなり本番」を避ける

バージョンアップに限らず、superset_config.py の変更やアドオンの追加なども、まず検証環境で試してから本番へ反映するのが安全です。この考え方はSupersetに限らず、システム運用全般に共通する基本です。

14.8 学習のまとめと次のステップ

14章を通じて、Superset を使ったデータ分析基盤の作り方を一通り学びました。最後に、ここまでの流れを振り返っておきましょう。

flowchart TD S["環境構築"] --> A["DB接続"] A --> B["データセット"] B --> C["メトリクス／計算列"] C --> D["チャート"] D --> E["ダッシュボード ＆ フィルタ"] E --> F["ロール ＆ 行レベルセキュリティ"] F --> G["キャッシュ・アラート・本番運用"]

Superset の考え方をつかみ（第1章）、Docker で環境を立ち上げて画面に慣れ（第2〜3章）、データベースへつなぎ（第4章）、SQLで探索し（第5章）、データセットとメトリクスという土台を整え（第6〜7章）、チャートとダッシュボードに仕立て（第8〜11章）、Jinjaで動的なSQLを扱い（第12章）、誰に何を見せるかを制御し（第13章）、最後に運用へつなげる（第14章）——この流れそのものが、Supersetというツールの考え方です。個々の画面操作を忘れてしまっても、この順番さえ覚えていれば、公式ドキュメントを見ながら十分に作業を再開できます。

本教材はここで一区切りですが、Superset にはまだ発展的なトピックがあります。次に学ぶとよいものを挙げておきます。

  • REST API による自動化 — 画面操作の代わりにAPIでダッシュボードやユーザーを操作し、他システムと連携する
  • ダッシュボードの埋め込み（Embedded） — 自社の業務アプリの画面内に、ダッシュボードをそのまま組み込む
  • 独自チャートプラグインの開発 — 標準のチャート種別（第9章）で足りない表現を、自分たちで拡張する
  • dbt などデータ基盤との組み合わせ — Superset が見るテーブル自体を整備する、分析基盤の上流工程
  • SQL・データモデリングの深掘り — 第6〜7章で触れたデータセット設計は、SQLとモデリングの理解が深いほど質が上がる

お疲れさまでした

Superset は開発の速いオープンソースプロジェクトです。今後、画面の見た目や設定項目が本教材と変わっていくことは十分にありえます。迷ったときは公式ドキュメントと、活発なGitHubリポジトリ・コミュニティに立ち返ってください。本教材で身につけた「接続 → データセット → チャート → ダッシュボード → 権限 → 運用」という考え方の流れは、バージョンが変わっても土台であり続けます。

やってみよう 14-1: 運用の3点セットを体験する

キャッシュ・エクスポート／インポート・本番移行チェックリストという、この章で学んだ運用の要素を、実際に手を動かして確認しましょう。

手順

  1. 1 これまでに作った任意のダッシュボード（またはチャート）を1つ選び、キャッシュタイムアウトの設定を変更する。値を変えながら表示にかかる時間の体感を比べ、変化に気づけるか確認する。
  2. 2 同じダッシュボードをエクスポートしてZIPを取得する。展開してYAMLファイルの中身を眺め、どんな情報が定義として書かれているかを確認してから、インポートして元通り復元できるか試す。
  3. 3 14.1〜14.7の内容を踏まえ、自分（またはチーム）の環境を本番へ移行するときのチェックリストを書き出す。最低限、SECRET_KEY・メタデータDB・バックアップ・権限・キャッシュの5項目について、今の状態と本番までにやることを1行ずつ書く。

解答の目安

(1) は数値の正解を求める課題ではなく、「キャッシュが効いている状態」を自分の目と体感で確認することが目的です。タイムアウトを極端に短く／長くしてみて違いに気づければ十分です。(2) はYAMLの中身を見て、接続パスワードのような秘密情報が含まれていないことに気づけていれば理解できています。(3) の5項目は本章の14.1〜14.7がそれぞれ対応しており、埋められない項目があれば、その節を読み返す合図です。

理解度確認クイズ

  1. Q1. 第2章のDocker Compose構成をそのまま本番で使ってはいけないのはなぜですか。何を変える必要がありますか？

    回答を表示

    学習環境はすぐ試せることを優先した構成で、SECRET_KEYが既定値のまま、HTTPS未設定、バックアップや監視の仕組みが無いなど、公開・運用を前提にしていません。本番では独立して管理されたメタデータDB（PostgreSQL推奨）、SECRET_KEYの変更と安全な保管、HTTPS化、バックアップ、監視を用意する必要があります。

  2. Q2. キャッシュのタイムアウトを長くすると何が起き、短くすると何が起きますか？

    回答を表示

    長くすると表示は速く安定しますが、元データが更新されてもしばらく古い数字が表示され続けます。短くすると数字は新しくなりやすい一方、キャッシュが効く時間が短くなりデータベースへの問い合わせが増えます。「鮮度」と「速さ」はトレードオフの関係にあります。

  3. Q3. 非同期クエリの仕組みに登場するメッセージブローカーとCeleryワーカーは、それぞれどんな役割ですか？また同じ仕組みは他のどんな機能で使われますか？

    回答を表示

    メッセージブローカー（Redis）は「実行してほしいジョブ」を預かる列（キュー）の役割を果たし、Celeryワーカーがそのジョブを受け取って実際にSQLを実行し、結果を保存します。同じ仕組みは、第5章のSQL Labの非同期実行に加えて、アラート＆レポートの定期実行（14.5）でも使われています。

  4. Q4. ダッシュボードをエクスポートしたZIPファイルには何が含まれませんか？インポート先ではどんな作業が別途必要ですか？

    回答を表示

    データベース接続のパスワードなどの認証情報は含まれません。インポート先の環境で、接続情報をあらためて設定する必要があります。あわせて、参照するデータセットやデータベース接続がインポート先に存在するかという依存関係、同名オブジェクトが既にある場合の扱いにも注意が必要です。
