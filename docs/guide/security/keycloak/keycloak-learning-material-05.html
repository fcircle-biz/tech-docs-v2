第5章 所要時間: 約50分

クライアント登録 — アプリをつなぐ

前章では「レルム」という区画を作りました。この章では、そのレルムにアプリを登録します。Keycloakではこの登録単位をクライアント（client）と呼びます。クライアントIDやリダイレクトURIなど、初心者がつまずきやすい設定項目を1つずつ確認しながら、実際に demo-app という名前のクライアントを作成します。

この章で学ぶこと

  • 「クライアント」が利用者ではなくアプリを指す言葉であることを理解する
  • クライアントを実際に作成し、Capability config の各項目の意味を説明できる
  • パブリッククライアントと機密クライアントの違いを判断基準とともに理解する
  • Valid redirect URIs / Web origins が何を守っているのかを説明できる

5.1 クライアントとは — 「利用者」ではなく「アプリ」を指す言葉

Keycloakでいうクライアント（client）とは、「Keycloakにログイン機能を使わせてほしい」と登録されたアプリのことです。第1章のたとえでは、ビルの受付にあらかじめ登録済みの部屋にあたります。受付（Keycloak）は「この部屋（アプリ）は入館証を確認してよい相手だ」と知っているからこそ、安心して入館証（トークン）の情報を渡せます。

初心者が混同しやすい点

「クライアント」と聞くと利用者（お客さん）を思い浮かべがちですが、Keycloakのクライアントはアプリ・システムそのものを指します。ログインするのは「ユーザー」、ログインを受け入れる先が「クライアント」です。この2つを混同すると、後の章の設定画面で迷子になりやすいので、ここでしっかり区別しておきましょう。

レルム・クライアント・ユーザーの3つは、次の図のような関係になります。レルムという1つの区画の中に、複数のクライアント（アプリ）と複数のユーザー（利用者）が並んで存在し、ユーザーがクライアントにログインして使う、という構図です。

図1: レルム・クライアント・ユーザーの関係

（アプリの世界）"] --> CG["クライアント群
（登録されたアプリ）"] R --> UG["ユーザー群

（管理コンソール自身）"] UG --> U1["ユーザー: 田中さん"] UG --> U2["ユーザー: 鈴木さん"] U1 -.->|ログインして使う| C1

5.2 クライアントを作る手順

それでは実際にクライアントを作成します。管理コンソールの左上でレルムが demo-realm になっていることを確認してから進めてください（違うレルムに作成すると、後の章で「見当たらない」と混乱する原因になります）。

  1. 1 左側メニューの Clients をクリックする。
  2. 2 右上の Create client ボタンをクリックする。
  3. 3 Client type に OpenID Connect が選ばれていることを確認する（第2章で学んだ標準ルール）。Client ID に demo-app と入力し、Next をクリックする。
  4. 4 Capability config 画面が表示される。今回は初期状態のまま（Standard flow のみON）で Next をクリックする。各項目の意味は次の5.3で解説する。
  5. 5 Login settings 画面で Valid redirect URIs に http://localhost:8081/* と入力する（詳細は5.5・5.6）。
  6. 6 Save をクリックして保存する。クライアント一覧に demo-app が表示されれば成功。

5.3 Capability config — 「このアプリは何ができるか」の設定

Capability config は、そのクライアントにどの認証方式を許可するかを決める画面です。項目が多く見えますが、入門段階で理解すべきポイントは限られています。表で確認しましょう。

項目 意味 この章での扱い
Client authentication OFF＝パブリッククライアント（シークレット無し）／ON＝機密クライアント（シークレットで身元を証明） 今回は OFF のまま（詳細は5.4）
Authorization Keycloak内蔵の細かい認可制御機能（Authorization Services）を有効にするか OFF（入門では使わない発展機能）
Standard flow 認可コードフロー。ブラウザのログイン画面を経由する、最も標準的な方式（第8章で体験） ON（基本この方式を使う）
Direct access grants ユーザー名とパスワードを直接Keycloakに渡し、トークンと交換する方式 学習中の動作確認には便利だが、アプリがパスワードを扱うことになるため本番利用は非推奨
Service accounts roles 人ではなくアプリ自身が主体になってトークンを取得する方式（M2M連携） OFF（バッチ処理やサーバー間連携で使う。今回は扱わない）
Implicit flow トークンをURLに直接含めてしまう古い方式。セキュリティ上の理由から非推奨 OFF（現在は使わない）

5.4 パブリッククライアントと機密クライアントの違い

Client authentication の ON / OFF は、そのアプリが「秘密」を安全に隠せるかどうかで決まります。

パブリッククライアント（OFF）

ブラウザ上で動くSPA（シングルページアプリ）やモバイルアプリが該当します。コードが利用者の端末側にあるため、シークレットを埋め込んでも解析されて見えてしまいます。そのためシークレットを持たせないのが正しい設計です。

機密クライアント（ON）

サーバー側だけで動くWebアプリが該当します。コードは利用者から見えないサーバー上にあるため、クライアントシークレットを安全に保管でき、それを使って「自分は確かにこのアプリだ」と証明できます。

観点 パブリッククライアント 機密クライアント
具体例 React / Vue などのSPA、モバイルアプリ Spring Boot などサーバーサイドWebアプリ
クライアントシークレット 持たない（持たせても隠しきれない） 持つ。サーバーの安全な場所に保管
安全のための追加対策 PKCE（第8章で詳しく学ぶ）で認可コードの横取りを防ぐ シークレットの厳重管理（Gitに含めない等）

5.5 Login settings — アプリの場所とURLを教える

Login settings は、「このアプリはどこにあるか」「ログイン後どこに戻すか」をKeycloakに教える設定です。学習用の値の例と合わせて確認しましょう。

項目 意味 学習用の例
Root URL アプリの基準となるURL。他の相対パスの起点になる http://localhost:8081
Home URL Keycloak管理コンソール等からアプリへ直接飛ぶときの入口URL http://localhost:8081
Valid redirect URIs ログイン成功後に戻ってよいURLの一覧。最重要項目（5.6で詳説） http://localhost:8081/*
Valid post logout redirect URIs ログアウト後に戻ってよいURLの一覧（第10章で使用） http://localhost:8081/*
Web origins ブラウザからのAjax通信（CORS）を許可する送信元。未設定だとブラウザ経由の通信がブロックされる http://localhost:8081

5.6 リダイレクトURIという「安全装置」

Valid redirect URIs は、単なる「戻り先の入力欄」ではありません。Keycloakはここに登録されたURLにしか、ログイン成功後の情報を戻しません。これは、悪意のある第三者が偽の戻り先URLを使って入館証（トークン）を横取りするのを防ぐための、重要な安全装置です。

図2: リダイレクトURIによる防御

flowchart LR U["利用者がログイン成功"] --> K["Keycloak: 戻り先URLを確認"] K -->|"登録済みURLと一致"| OK["正規のアプリへ戻す（許可）"] K -->|"登録されていないURL"| NG["拒否（redirect_uriエラー）"]

ワイルドカードを広く許可する危険性

* や http://localhost:* のように広い範囲を許可すると、想定していない別のURL（攻撃者が用意したページなど）にもトークンが渡ってしまう可能性があります。学習環境では http://localhost:8081/* のようにできるだけ絞り込んだ範囲を指定し、本番環境では* のような広いワイルドカードを絶対に使わないでください。

5.7 クライアントシークレットはどこで確認する？

5.4で説明した機密クライアント（Client authentication を ON）にすると、クライアントの詳細画面に Credentials タブが新しく現れます。そこに Client secret という項目があり、これがそのアプリだけが知っている「秘密の合言葉」です。

クライアントシークレットの扱い

Client secret は文字どおり秘密です。Gitリポジトリにコミットしない、ログに出力しない、チャットやスクリーンショットで共有しないようにしてください。漏れてしまった場合は、Credentials タブの再生成機能ですぐに新しい値へ切り替えられます。

5.8 よくあるエラーと対処

クライアント設定でつまずいたときのために、代表的なエラーメッセージと原因・対処法をまとめておきます。

エラー よくある原因 対処
Invalid parameter: redirect_uri Valid redirect URIs に該当URLが未登録。末尾のスラッシュの有無が実際のURLと一致していない Valid redirect URIs を確認し、実際に使うURLと完全に一致するか、正しいワイルドカードを追加する
CORSエラー（ブラウザのコンソール） Web origins が未設定、またはアプリの送信元と不一致 Web origins にアプリのオリジン（例: http://localhost:8081）を追加する
Client not found Client ID のスペル違い、または別のレルムに向けてリクエストしている Client ID の綴りとレルム名（demo-realm）をあわせて確認する
invalid_client 機密クライアントでクライアントシークレットが一致していない Credentials タブでシークレットを確認し、アプリ側の設定と一致させる

やってみよう 5-1: demo-app クライアントを作成する

demo-realm を選んだ状態で、実際にクライアントを作成し、設定を見返してみましょう。

手順

  1. 1 Clients → Create client → Client ID に demo-app と入力し、Next で Capability config へ進む（Standard flow だけがONの初期状態のまま）。
  2. 2 Login settings で Valid redirect URIs に http://localhost:8081/* を入力し、Web origins に http://localhost:8081 を入力する。
  3. 3 Save をクリックして保存する。Clients 一覧に demo-app が表示されることを確認する。
  4. 4 demo-app をクリックして詳細画面を開き、Settings タブで自分が入力した Valid redirect URIs と Web origins が正しく保存されているかを見返す。
  5. 5 Client authentication のトグルをONにしてみて、新しく Credentials タブが現れることを確認する（確認したら、この章では OFF に戻しておいてよい）。

この章のまとめ

  • クライアントはKeycloakに登録されたアプリのこと。利用者（ユーザー）とは別の概念。
  • Capability config では Standard flow を基本とし、Direct access grants や Implicit flow の使いどころ・注意点を理解する。
  • 秘密を隠せないアプリはパブリッククライアント（PKCEで保護）、サーバー側アプリは機密クライアント（シークレットで保護）。
  • Valid redirect URIs は登録したURLにしか戻さない安全装置。広いワイルドカードは本番で使わない。

確認問題

  1. Q1. Keycloakにおける「クライアント」とは何を指しますか。「ユーザー」との違いも含めて説明してください。

    回答を表示

    クライアントは、Keycloakに登録されたアプリ・システムそのものを指します。ログインする「人」であるユーザーとは別の概念で、ユーザーがクライアント（アプリ）にログインして使う、という関係になります。

  2. Q2. ブラウザで動くSPAは、パブリッククライアントと機密クライアントのどちらにすべきですか。理由も答えてください。

    回答を表示

    パブリッククライアントにすべきです。SPAのコードは利用者の端末（ブラウザ）上で動くため、クライアントシークレットを埋め込んでも解析されて見えてしまい、安全に隠せません。そのため、シークレットを持たないパブリッククライアントとし、PKCEで保護するのが正しい設計です。

  3. Q3. Valid redirect URIs に * のような広いワイルドカードを設定すると、なぜ危険なのですか。

    回答を表示

    Valid redirect URIs は「ログイン後にどこへ戻してよいか」を制限する安全装置です。* のように広く許可すると、想定していない任意のURL（攻撃者が用意したページなど）にもログイン情報やトークンが渡ってしまう可能性があるためです。できるだけ絞り込んだURLのみを登録すべきです。
