ユーザー管理の基本

前章では「アプリを受付に登録する」クライアントを学びました。この章では、いよいよ受付を利用する「人」——ユーザー——を管理コンソールから作成します。パスワードの設定方法、初回ログイン時に強制できる作業、アカウントの有効・無効の切り替え、そして利用者自身が使う画面まで、日常的な運用操作を一通り体験します。

この章で学ぶこと

  • demo-realm にユーザーを作成し、パスワードを設定できる
  • 「Temporary（仮パスワード）」と「Required user actions」の意味を説明できる
  • ユーザーの有効・無効・削除を、退職などの場面に合わせて使い分けられる
  • 利用者自身が使うアカウントコンソールの役割を理解する

6.1 Keycloakにおけるユーザーとは

第5章で登録したクライアントは「受付に登録した部屋（アプリ）」でした。それに対してユーザーは、その受付を実際に利用する「人」です。ユーザーはレルムに属し、レルムごとに別々に管理されます。demo-realm のユーザーと master レルムのユーザー（管理者アカウント）は完全に別物であることを、まず思い出しておきましょう。

ユーザーには「一生」があります。入社してアカウントが作られ、パスワードが設定され、日々ログインして使われ、異動で権限が変わり、退職すれば無効化され、最終的には削除されることもあります。この一連の流れを1か所で管理できることこそが、第1章で学んだ IAM の価値でした。

クライアントとユーザーの違い

クライアント＝「ログインしてくるアプリ」、ユーザー＝「ログインする人」です。第5章の demo-app というクライアントに対して、この章で作る taro のようなユーザーがログインする、という関係になります。

6.2 ユーザーを作る手順

それでは実際に demo-realm にユーザーを作成しましょう。左メニューの Users をクリックし、以下の手順で進めます。

  1. 1 demo-realm を選択した状態で、左メニューの Users を開く。
  2. 2 右上の Add user ボタンをクリックする。
  3. 3 Username（必須）に taro のようなログイン名を入力する。
  4. 4 Email・First name・Last name を（任意で）入力する。
  5. 5 Email verified のスイッチを確認する（学習用なので ON にしておくと後の確認がスムーズです）。
  6. 6 Required user actions は今は何も選ばず空欄のままにする（6.4節で詳しく扱います）。
  7. 7 画面下の Create をクリックする。ユーザー一覧に taro が表示されれば成功。

Username は後から変えにくい

Username はログインIDとして使われ、他システムとの連携（第9章・第12章）でも参照されることがあります。作成後に変更すると影響範囲が読みにくくなるため、命名ルール（例: 社員番号、あるいは英字ID）をあらかじめ決めておくとよいでしょう。

6.3 パスワードの設定

ユーザーを作成しただけでは、まだパスワードが設定されていないためログインできません。作成した taro をクリックして詳細画面を開き、Credentials タブに移動します。

  • Set password ボタンをクリックする。
  • Password / Password confirmation にパスワードを入力する。
  • Temporary のスイッチを確認する。
  • Save（確認ダイアログが出る場合は Save password）をクリックする。

ここで意味を必ず押さえておきたいのが Temporary（仮パスワード） のON/OFFです。

Temporary ＝ ON

利用者は次回ログイン時に必ずパスワードの変更を求められます。管理者が仮のパスワードを渡し、本人だけが知る本パスワードに置き換えさせたいときに使います。

Temporary ＝ OFF

設定したパスワードが、そのまま本パスワードとして使われます。次回ログイン時に変更を求められません。今回は学習用に一度ログインするだけなら OFF でも構いません。

運用では ON が基本

実際の業務では、管理者がパスワードを設定する場面（新入社員のアカウント発行、パスワード忘れの再設定など）で Temporary を ON にするのが基本です。管理者が知っているパスワードをそのまま使い続けさせないことが、セキュリティ上重要だからです。

6.4 Required user actions（必須アクション）

Required user actions は、「次回ログイン時に、この作業を終えるまで先に進ませない」という指定です。Temporary パスワードの強制変更も、実はこの仕組みの1つ（Update Password）です。代表的な項目は次のとおりです。

アクション ログイン時に何が起きるか
Update Password パスワードの変更画面が表示され、変更するまで先に進めない
Verify Email 登録したメールアドレスに確認メールが送られ、リンクを開くまで先に進めない
Update Profile 氏名・メールなどのプロフィール入力画面が表示される
Configure OTP ワンタイムパスワード（二要素認証）の設定画面が表示される

Configure OTP は第11章で扱います

二要素認証そのものの仕組みと設定方法は、第11章「ログイン画面のカスタマイズとセキュリティ強化」でまとめて学びます。ここでは「ログイン時に強制できる作業の1つ」として名前だけ覚えておけば十分です。

6.5 ユーザーの有効・無効と削除

ユーザー詳細画面の Details タブには Enabled というスイッチがあります。これを OFF にすると、そのユーザーはログインできなくなります。ユーザー情報やロールの設定はそのまま残るため、再度 ON にすればすぐ元の状態に戻せます。

一方、ユーザー一覧から Delete を実行すると、そのユーザーに関する情報（プロフィール・割り当てられていたロールやグループの関連付けなど）は完全に消え、元に戻せません。

退職時はまず「無効化」、削除は慎重に

退職や異動でアカウントを止めたい場合、まず Enabled を OFF にするのが基本です。すぐに削除してしまうと「いつ・誰が・どんな権限を持っていたか」という監査の記録も同時に失われます。しばらく無効化した状態で保持し、社内の記録保持ルールに従って必要になったときに削除するのが安全です。

6.6 ユーザー属性（Attributes）

ユーザー詳細画面の Attributes タブでは、氏名やメール以外に「部署コード」「社員番号」のような、自社独自の項目を自由に追加できます。ここで登録した値は、後の章で学ぶプロトコルマッパーという仕組みを使うことで、Keycloakが発行するトークンの中に含めることもできます。つまり、アプリ側は「トークンを見るだけで、その利用者の部署が分かる」といったことも実現できます。詳しい設定方法は第9章以降で扱うため、ここでは「そういうことができる」と知っておくだけで十分です。

6.7 ユーザー自身が使うアカウントコンソール

ここまでは管理者が管理コンソール（Admin Console）から操作してきましたが、Keycloak には利用者本人が自分の情報を管理する画面も標準で用意されています。それがアカウントコンソール（Account Console）です。

アカウントコンソールのURL（demo-realm の場合）

URL 
http://localhost:8080/realms/demo-realm/account

taro のユーザー名とパスワードでこの画面にログインすると、利用者は管理者に頼らず次のようなことを自分で行えます。

  • パスワードの変更
  • 氏名・メールなど個人情報の更新
  • ログイン履歴（Signing in の Device activity）の確認
  • ログインしたままの端末（セッション）をログアウトさせる

重要ポイント

「パスワードを忘れた」「電話番号が変わった」といった問い合わせのたびに管理者が対応していては、管理コストが膨らみます。アカウントコンソールを使えば利用者が自分で解決できる範囲が広がり、管理者の手間が減ります。

6.8 ユーザーの自己登録（セルフサインアップ）

ここまではすべて管理者がユーザーを作成してきましたが、Keycloak には利用者自身にアカウントを作らせる設定もあります。Realm settings → Login タブの User registration スイッチを ON にすると、ログイン画面に「Register」リンクが表示され、誰でも自分でアカウントを作成できるようになります。

社内システムでは通常OFF

会員登録が前提の一般向けサービスでは User registration を ON にしますが、社内システムでは通常 OFF のままにします。社員のアカウントは人事情報などをもとに管理者（または第12章で学ぶ LDAP 連携）が作成するべきで、誰でも自由に登録できてしまうと管理が破綻するためです。

6.9 ユーザーの探し方と、大量ユーザーへの備え

Users 画面の検索欄には、ユーザー名やメールアドレスの一部を入力して絞り込めます。ユーザー数が数十人程度なら、この一覧と検索で十分に運用できます。

しかし、社員が数百人〜数千人規模になると、1件ずつ Add user で登録するのは現実的ではありません。そのような場合に備えて、Keycloak には次の2つの手段が用意されています。

  • LDAP / Active Directory 連携 — 社内に既にある名簿をそのまま参照する仕組み（第12章）
  • 一括インポート・エクスポート — JSON ファイルからまとめてユーザーを登録・移行する仕組み（第13章）

やってみよう 6-1: 仮パスワードでログインし、自分で変更してみる

demo-realm にユーザーを作成し、仮パスワードでのログインから本パスワードへの変更までを一通り体験します。

手順

  1. 1 demo-realm の Users で taro というユーザーを作成する（6.2節の手順）。
  2. 2 Credentials タブで Set password を行い、Temporary を ON にして保存する。
  3. 3 ブラウザで http://localhost:8080/realms/demo-realm/account を開く。
  4. 4 taro と仮パスワードでログインする。Temporary が ON のため、そのままパスワード変更画面に進むことを確認する。
  5. 5 新しいパスワードを設定し、アカウントコンソールのトップ画面が表示されることを確認する。

この章のまとめ

  • ユーザーはレルムに属する「人」で、Users → Add user から作成し、Credentials タブでパスワードを設定する。
  • Temporary を ON にすると次回ログイン時にパスワード変更が強制され、Required user actions でログイン時の作業を追加できる。
  • 退職などでアカウントを止めるときは、まず Enabled を OFF にし、削除は監査の観点から慎重に行う。
  • 利用者はアカウントコンソールから自分でパスワード変更や情報更新ができ、管理者の負担を減らせる。

確認問題

  1. Q1. Credentials タブでパスワードを設定する際、「Temporary」を ON にすると何が起きますか。

    回答を表示

    利用者はそのパスワードで一度ログインした後、次回ログイン時に必ずパスワードの変更を求められます。管理者が仮パスワードを発行し、本人だけが知る本パスワードに置き換えさせたい場合に使います。

  2. Q2. 退職者のアカウントを止めたいとき、「無効化（Enabled OFF）」と「削除」のどちらを先に検討すべきですか。理由も含めて答えてください。

    回答を表示

    まず無効化を検討すべきです。削除するとユーザー情報や権限の割り当て記録が完全に消えてしまい、「誰がいつどんな権限を持っていたか」という監査の記録も失われます。無効化であればすぐにログインを止めつつ、記録は保持できます。

  3. Q3. アカウントコンソールとは何ですか。管理コンソールとの違いも含めて説明してください。

    回答を表示

    アカウントコンソールは、利用者本人が自分のパスワード変更・個人情報の更新・ログイン履歴の確認・端末のログアウトなどを行うための画面です。これに対し管理コンソール（Admin Console）は、管理者がレルム・クライアント・ユーザーなど全体の設定を行うための画面であり、対象とする利用者が異なります。
