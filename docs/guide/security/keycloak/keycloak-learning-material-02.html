ホーム Keycloak 第2章
第2章 所要時間: 約50分

認証と認可のきほん

第1章では、Keycloakが「ビルの共用受付」としてログインと権限管理を一手に引き受けることを学びました。この章では、その受付が実際にどんな考え方・どんな共通ルールで動いているのかを掘り下げます。キーワードは認証・認可・OAuth 2.0・OpenID Connect・トークンです。どれも略語で身構えてしまいますが、中身は難しくありません。まだ手は動かさず、考え方だけをじっくりつかみましょう。

この章で学ぶこと

  • 認証（Authentication）と認可（Authorization）の違いを、自分の言葉で説明できる
  • なぜOAuth 2.0やOpenID Connectのような「共通ルール」が必要なのかを理解する
  • OAuth 2.0の4人の登場人物と、OpenID Connectとの関係を説明できる
  • IDトークン・アクセストークン・リフレッシュトークンの役割の違いを区別できる
  • JWTが「ヘッダー.ペイロード.署名」の3つで構成されることを理解する

2.1 認証（Authentication）と認可（Authorization）の違い

第1章の「ビルの共用受付」のたとえを、もう少し詳しく見てみましょう。受付では、実は2つの異なる作業が行われています。1つ目は身分証を確認して「あなたは本当にその人か」を確かめる作業。2つ目は入館証に「何階まで入れるか」を書いて渡す作業です。前者が認証（Authentication）、後者が認可（Authorization）にあたります。

この2つは英語も日本語も似ていて非常に混同されやすい言葉ですが、問いかけている内容がまったく違います。表で整理しましょう。

観点 認証（Authentication） 認可（Authorization）
問いかけ あなたは誰ですか？ あなたは何をしてよいですか？
ビル受付のたとえ 身分証の確認 入れる階の指定
アプリでの具体例 ID・パスワードでログインする 一般ユーザーは閲覧のみ、管理者は編集も可能にする
失敗したときの結果 ログインできない（本人確認ができない） ログインはできるが、その先の操作を拒否される
Keycloakでの主な設定場所 ユーザー・パスワード・二要素認証（第6・11章） ロール・グループ（第7章）

混同しやすいポイント: 「ログインできた」＝「何でもできる」ではない

身分証の確認（認証）に成功しても、入館証に書かれていない階には入れません。同じように、アプリに正しくログインできた（認証成功）としても、管理者専用の画面を開ける（認可）とは限りません。この違いを意識しておくと、後の章で出てくる「ログインはできるのに403エラーになる」という状況が理解しやすくなります。

2.2 なぜ共通ルール（標準仕様）が必要なのか

Keycloakと各アプリが認証・認可のやり取りをする方法を、もしKeycloakが独自に決めてしまったらどうなるでしょうか。アプリを作る側は、Keycloak専用のやり取り方法を1から実装しなければなりません。そして翌年、別の会社の別の認証サーバーを使うことになったら、また別のやり方を覚えて作り直しです。

そこで登場するのが、世界共通の「手順書」にあたる標準仕様です。これに沿って作られたアプリと認証サーバーは、作った会社が違っても、初対面同士で問題なくやり取りできます。ちょうど、電源プラグの規格が統一されていれば、どのメーカーの電化製品でも同じコンセントに挿せるのと同じ考え方です。この標準仕様にあたるのが、次に説明するOAuth 2.0とOpenID Connectです。Keycloakは、この2つの共通ルールをしゃべれる認証サーバーとして作られています。

独自ルールの場合

アプリごと・認証サーバーごとにやり取りの方法が異なる。組み合わせが変わるたびに作り直しが必要で、乗り換えのコストも大きい。

共通ルール（標準仕様）の場合

OAuth 2.0 / OpenID Connect という共通の手順書に従っていれば、Keycloakでも他社製品でも、アプリ側の実装をほぼ変えずに乗り換えられる。

2.3 OAuth 2.0の登場人物

OAuth 2.0は、「あるサービスが、別のサービスの持つ情報に、本人の許可を得たうえでアクセスしてよいか」を取り決めるための標準仕様です。ここで重要なのは、OAuth 2.0はもともと「認可」のための仕組みとして作られたという点です（「認証」の話は次の2.4節で出てきます）。OAuth 2.0には、次の4人の登場人物がいます。

  • リソースオーナー — 利用者本人。データや権限の持ち主
  • クライアント — 利用者に代わって操作したいアプリ（勤怠アプリなど）
  • 認可サーバー — 本人確認を行い、トークンを発行するサーバー。Keycloakが担う役割
  • リソースサーバー — 実際に守られているデータを持つAPI（勤怠データを返すAPIなど）

図1: OAuth 2.0の4つの登場人物の関係

flowchart TD RO["リソースオーナー
（利用者本人）"] -->|アプリの利用を許可する| C["クライアント
（アプリ）"] C -->|認可を要求する| AS["認可サーバー
（Keycloak）"] AS -->|トークンを発行する| C C -->|トークンを提示する| RS["リソースサーバー
（保護されたAPI）"] RS -->|データを返す| C

本教材でよく出てくる勤怠アプリの例に当てはめると、リソースオーナー＝あなた自身、クライアント＝勤怠アプリ、認可サーバー＝Keycloak、リソースサーバー＝勤怠データを持つAPIという対応になります。

2.4 OpenID Connect（OIDC）— 「認証」を追加した仕組み

先ほど説明したとおり、OAuth 2.0は本来「認可」のための仕組みで、「利用者が本当は誰なのか」を確認する標準的な方法までは決めていません。そこで、OAuth 2.0の仕組みの上に「本人確認（認証）」の機能を追加した拡張仕様が作られました。それがOpenID Connect（OIDC）です。Keycloakがアプリとやり取りする際、主に使うのはこのOpenID Connectです。

関係のイメージ

OAuth 2.0を土台（1階部分）、OpenID Connectをその上に建てた増築部分（2階部分）とイメージしてください。1階だけでも「アクセスを許可する」という認可の役割は果たせますが、2階が加わることで「誰がログインしたか」まで標準的な方法で確認できるようになります。Keycloakは、この2階建ての仕組みをまるごと備えた認可サーバーです。

OpenID Connectを使ったログインの大まかな流れを見てみましょう。細かい手順（認可コードフロー）は第8章で実際に手を動かしながら確認しますので、ここでは全体像だけをつかんでください。

図2: OpenID Connectによるログインの大まかな流れ

sequenceDiagram autonumber participant U as 利用者 participant A as アプリ participant K as Keycloak U->>A: アプリを開く A->>K: ログイン画面へ誘導する K->>U: ログイン画面を表示する U->>K: IDとパスワードを入力する K-->>A: トークンを発行する A->>K: トークンが正しいか確認する A-->>U: ログイン後の画面を表示する

2.5 3種類のトークン — それぞれの役割

Keycloakがログイン成功後に発行する「入館証」には、実は用途の異なる3種類があります。それぞれ役割が決まっており、使い方を間違えると思わぬ不具合やセキュリティ上の問題につながります。

トークン たとえ 用途
IDトークン 身分証そのもの 「誰がログインしたか」をアプリに伝えるための証明。アプリの画面表示（ようこそ、〇〇さん）などに使う
アクセストークン 入館証（通行許可証） APIを呼び出すときに提示する許可証。「このAPIを叩いてよい」ことを証明する
リフレッシュトークン 再発行の引換券 アクセストークンの有効期限が切れたとき、再ログインなしで新しいトークンと引き換えるためのもの

注意: IDトークンをAPIの認可に使わない

IDトークンは「誰がログインしたか」を示すための身分証であり、APIへのアクセスを許可するための入館証（アクセストークン）とは目的が違います。IDトークンをAPIの認可チェックに流用すると、本来意図していない形でAPIが呼び出せてしまう可能性があります。「本人確認はIDトークン」「API呼び出しはアクセストークン」と役割を分けて覚えておきましょう。

2.6 JWTの形 — トークンの中身をのぞいてみる

Keycloakが発行するトークンの多くは、JWT（JSON Web Token、ジョット、または ジェイダブリューティー）という形式で作られています。JWTは、次のように3つの部分をドット（.）でつないだ1本の文字列です。

ヘッダー.ペイロード.署名

  • ヘッダー — トークンの種類や、署名に使ったアルゴリズムの情報
  • ペイロード — 「誰が」「いつまで有効か」などの実際の中身（クレームと呼ぶ）
  • 署名 — ヘッダーとペイロードが改ざんされていないことを保証するための値

ペイロードの例を見てみましょう。実際にはBase64URLという方式で1行の文字列にエンコードされていますが、デコードすると次のようなJSONの形になっています。

IDトークンのペイロード（デコード後のイメージ） 
{
  "iss": "https://keycloak.example.com/realms/myrealm",
  "sub": "3f7e2c1a-90b1-4e2d-8f3a-1a2b3c4d5e6f",
  "aud": "my-app",
  "exp": 1735689600,
  "iat": 1735686000,
  "preferred_username": "yamada_taro",
  "email": "yamada@example.com"
}

iss（発行者）、sub（利用者を一意に表すID）、exp（有効期限）、preferred_username（ログインユーザー名）のように、それぞれの項目をクレームと呼びます。

重要: Base64URLは暗号化ではない

JWTのヘッダーとペイロードはBase64URLでエンコードされているだけで、暗号化はされていません。つまり、トークンを持っている人なら誰でも中身を読めます。署名があるのは「改ざんされていないこと」を保証するためであり、「中身を隠す」ためではありません。パスワードやマイナンバーのような機密情報を、絶対にペイロードへ含めてはいけません。

実際にKeycloakからトークンを受け取り、自分の目でデコードして中身を確認する作業は、第8章でブラウザの開発者ツールを使いながら行います。今はまだ「3つの部分に分かれていて、中身は読める文字列である」という形だけを覚えておけば十分です。

2.7 SAMLとの関係

認証・認可の標準仕様には、OpenID Connectよりも歴史の長いSAML（Security Assertion Markup Language）という規格もあります。主に企業向けの大規模なシステムで古くから使われており、Keycloakも対応しています。ただし、現在新しくシステムを作る場合は、より軽量でWebやモバイルアプリと相性のよいOpenID Connectが主流です。本教材でも、以降の章はすべてOpenID Connectを前提に進めます。

ヒント: SAMLはどこで見かける？

大企業の社内システムや、古くからある業務パッケージソフトの連携で「SAML認証」という表記を見かけることがあります。Keycloakを使えば、同じレルム内でOpenID ConnectのアプリとSAMLのアプリを併存させることもできます（第9章で扱うアプリ連携の応用にあたります）。

2.8 この章で出てきた重要用語の整理

略語が多く登場したので、ここで整理しておきましょう。以降の章で何度も出てくる言葉なので、今の段階では「意味のイメージ」がつかめていれば大丈夫です。

用語 たとえ 意味
認証 身分証の確認 「あなたは誰か」を確認すること。
認可 入れる階の指定 「何をしてよいか」を決めること。
OAuth 2.0 受付の共通ルール（認可編） 本人の許可を得てアクセスを認可するための標準仕様。
OpenID Connect 受付の共通ルール（認証つき増築版） OAuth 2.0に本人確認（認証）を追加した標準仕様。Keycloakが主に使う。
IDトークン 身分証そのもの 誰がログインしたかを示すトークン。
アクセストークン 入館証 APIを呼び出すための許可証。
リフレッシュトークン 再発行の引換券 期限切れのアクセストークンを取り直すためのトークン。
JWT 3つ折りの証明書 ヘッダー・ペイロード・署名をドットでつないだトークン形式。
クレーム 証明書に書かれた各項目 JWTのペイロードに含まれる個々の情報項目（iss・sub・expなど）。

やってみよう 2-1: 認証と認可を身のまわりの例で考える

この章もまだコマンドは打ちません。学んだ考え方を、身近な場面に当てはめて「人に説明できる」状態にしておきましょう。

手順

  1. 1 身近なサービスで「認証だけで済む場面」（ログインさえできれば誰でも同じことができる場面）を1つ挙げてみる。
  2. 2 同じく身近なサービスで「認証に加えて認可も必要な場面」（ログインした人によってできることが変わる場面）を1つ挙げてみる。例: 同じ会員サイトでも、無料会員と有料会員で見られるページが違う、など。
  3. 3 2.6節の警告を踏まえて、「JWTのペイロードに絶対入れてはいけない情報」を3つ書き出してみる。第8章で実際のトークンをデコードするときに答え合わせをします。

この章のまとめ

  • 認証は「あなたは誰か」、認可は「何をしてよいか」を確認する、別々の作業である。
  • OAuth 2.0は認可のための標準仕様、OpenID Connectはそこに認証を追加した拡張仕様。Keycloakは主にOpenID Connectを使う。
  • IDトークン（誰がログインしたか）・アクセストークン（APIの許可証）・リフレッシュトークン（取り直しの引換券）は、それぞれ役割が異なる。
  • JWTは「ヘッダー.ペイロード.署名」の3つで構成され、暗号化ではなくエンコードなので中身は読める。機密情報は入れてはいけない。

確認問題

  1. Q1. 認証と認可の違いを、それぞれ一言で説明してください。

    回答を表示

    認証は「あなたは誰か」を確認すること、認可は「あなたは何をしてよいか」を決めることです。ログイン（認証）に成功しても、必ずしもすべての操作が許可される（認可される）わけではありません。

  2. Q2. OAuth 2.0とOpenID Connectの関係を説明してください。

    回答を表示

    OAuth 2.0は、本人の許可を得たうえでアクセスを認可するための標準仕様です。OpenID Connectは、そのOAuth 2.0の仕組みの上に「本人確認（認証）」の機能を追加した拡張仕様です。Keycloakがアプリとのやり取りに主に使うのはOpenID Connectです。

  3. Q3. JWTのペイロードについて、正しく説明しているものを選んでください。「(A) 暗号化されているので第三者は中身を読めない」「(B) Base64URLでエンコードされているだけなので、誰でも中身を読める」。

    回答を表示

    正解は(B)です。JWTのヘッダーとペイロードはBase64URLでエンコードされているだけで、暗号化はされていません。トークンを持っていれば誰でも中身を読めるため、パスワードなどの機密情報を含めてはいけません。署名は改ざんの検知のためにあります。
