ホーム Keycloak 第9章
第9章 所要時間: 約60分

アプリをKeycloakで保護する

第8章までで、ブラウザから実際にKeycloakのログイン画面を通り、発行されたトークンの中身を確認しました。この章では、その続きとして「アプリ側は何を設定しているのか」を、Spring Bootのサンプルアプリを例に読み解きます。Javaに詳しくなくても心配ありません。コードは短くまとめ、1行ずつ日本語で意味を説明します。

この章で学ぶこと

  • アプリ側がやるべき「たった2つのこと」を説明できる
  • OAuth2 Client（ログインさせる側）とResource Server（トークンを検証する側）の役割の違いを理解する
  • issuer-uriを1つ設定するだけで、アプリが何を自動的に把握するのかを理解する
  • Spring Bootの設定ファイルを読んで、各項目が何を指しているか説明できる

Javaのコードが読めなくても大丈夫

この章のゴールは「Javaのコードを書けるようになる」ことではありません。設定ファイルの各項目が何を意味しているかを説明できるようになることが目標です。コード例はすべて15行以内に収め、1行ずつ日本語コメントを添えています。実際に環境が無くても、読むだけで十分に学べます。

9.1 アプリ側がやるべきことは、たった2つだけ

ここまでの章で、Keycloak側の設定（レルム・クライアント・ユーザー・ロール）はひととおり済んでいます。では、Keycloakと連携するアプリ側は何をすればよいのでしょうか。実は、アプリがやるべきことは次の2つだけです。

  • (1) 未ログインの人をKeycloakのログイン画面へ送る — 保護されたページに未ログインでアクセスされたら、Keycloakへリダイレクトする
  • (2) 戻ってきたトークンが本物か確かめる — Keycloakが発行したトークンの署名を検証し、なりすましや改ざんが無いことを確認する

パスワードの受け取りも、ログイン画面の作成も、アプリ側は一切行いません。第1章で学んだ「共用受付」のたとえのとおり、アプリは入館証（トークン）が本物かどうかだけを見ればよいのです。全体の流れを図で確認しましょう。

9.2 2つの役割 — OAuth2 Client と Resource Server

アプリの種類によって、先ほどの「2つのこと」のどちらを担当するかが変わります。画面を持つWebアプリと、画面を持たないAPIでは役割が異なるためです。この違いを表で整理します。

観点 OAuth2 Client
（ログインさせる側）		 Resource Server
（トークンを検証する側）
典型的なアプリ 画面のあるWebアプリ（社内ポータルなど） 画面を持たないAPI（バックエンドサービス）
担当する仕事 未ログインの人をKeycloakのログイン画面へ送る 送られてきたトークンが本物か検証する
受け取るもの ログイン後にKeycloakから渡される認可コード リクエストヘッダーに乗ったアクセストークン
起点となる設定 issuer-uri（Keycloakの場所） issuer-uri（Keycloakの場所）

どちらの役割も、issuer-uri（発行元のURL）を起点にしている点は共通です。9.3ではこのissuer-uriが何をしてくれるのかを見ていきます。

9.3 issuer-uri のしくみ — 1行の設定で自動的にわかること

アプリ側の設定でもっとも重要なのがissuer-uriです。値は次の1行だけです。

http://localhost:8080/realms/demo-realm

これは第4章で作成したレルム「demo-realm」を指すURLです。アプリはこのURLの末尾に/.well-known/openid-configurationを付けて自動的に読みに行きます。第4章で実際にブラウザで開いたことのあるURLと同じ場所です。このJSONファイルには、次の情報がまとめて書かれています。

  • 認可エンドポイント — ログイン画面がどこにあるか
  • トークンエンドポイント — トークンをどこで受け取るか
  • jwks_uri（公開鍵の場所） — トークンの署名を確認するための鍵をどこから取得するか

1行で済む理由

つまり、開発者が「ログイン画面のURLはここ」「鍵はここから取る」と1つずつ設定する必要はありません。issuer-uriさえ正しければ、残りは自動的に解決されるというのが、OpenID Connectの便利な点です。

9.4 Keycloak側の準備 — demo-appクライアントを整える

アプリ側の設定を書く前に、第5章で作成したdemo-appクライアントの設定を、今回のサンプルアプリに合わせて確認しておきます。

  • Client authenticationをONにする — アプリがシークレット（合言葉）を持つ「機密クライアント」として扱う
  • Credentialsタブに表示されるClient secretを控える — 後で設定ファイルに使う
  • Valid redirect URIsにhttp://localhost:8081/login/oauth2/code/keycloakを追加する — Spring Securityが既定で使うコールバックURL
  • Web originsにhttp://localhost:8081を追加する — このアプリからのアクセスを許可する

Valid redirect URIsは1文字も間違えられない

ここに登録したURLと、アプリが実際に使うコールバックURLが完全に一致しないと、ログイン後にエラーになります。ポート番号や末尾のパスまで正確に確認しましょう（9.11でエラー例を扱います）。

9.5 Spring Bootの依存関係 — 2つのスターターの違い

Spring Bootには、9.2で整理した2つの役割に対応する「スターター」（機能をまとめて追加する部品）が用意されています。プロジェクトに追加する依存関係の名前を見れば、そのアプリがどちらの役割かがわかります。

依存関係の名前 役割
spring-boot-starter-oauth2-client ログインさせる側。画面のあるWebアプリに追加する。未ログインの人をKeycloakへ誘導する機能を持つ
spring-boot-starter-oauth2-resource-server APIを守る側。画面を持たないAPIに追加する。送られてきたトークンを検証する機能を持つ

名前に「client」と付く方がログインを担当し、「resource-server」と付く方がAPIの防御を担当する——名前どおりの役割分担だと覚えておけば十分です。

9.6 設定ファイル application.yml（ログインさせる側）

画面のあるWebアプリでは、次のようなapplication.ymlを用意します。難しそうに見えますが、9.4で確認した内容をそのまま書き写しているだけです。

application.yml 
spring:
  security:
    oauth2:
      client:
        registration:
          keycloak:
            client-id: demo-app
            client-secret: ここにクライアントシークレット
            authorization-grant-type: authorization_code
            scope: openid, profile, email
        provider:
          keycloak:
            issuer-uri: http://localhost:8080/realms/demo-realm
項目 意味
client-id Keycloakに登録したクライアントID。第5章で作成した「demo-app」
client-secret 9.4で控えたシークレット。アプリ自身が「本物のdemo-appです」と証明する合言葉
authorization-grant-type 第8章で体験した「認可コードフロー」を使うという指定
scope どの情報をトークンに含めてほしいかの要求（プロフィール・メールアドレスなど）
issuer-uri 9.3で説明した、Keycloakのレルムを指すURL

シークレットを直接書かない

サンプルでは分かりやすさのためclient-secretを直接書いていますが、これをそのままGitに登録してはいけません。実際の開発では、環境変数（例: ${KEYCLOAK_CLIENT_SECRET}）や、専用のシークレット管理サービスを使って、設定ファイルの外に出すのが基本です。

9.7 最小限のセキュリティ設定を読んでみる

設定ファイルに加えて、「どのページをログイン必須にするか」を決めるコードが1つ必要です。次のコードは「トップページは誰でも見られる」「/secureはログインが必要」「それ以外もログインが必要」というルールを表しています。1行ずつ日本語コメントを付けています。

SecurityConfig.java 
@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        // "/" は誰でも見られるようにする
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/").permitAll()
            // "/secure" はログインしていないと入れない
            .requestMatchers("/secure").authenticated()
            // それ以外のパスもログイン必須にする
            .anyRequest().authenticated()
        )
        // Keycloakへのログイン画面遷移を有効にする
        .oauth2Login(Customizer.withDefaults());
    return http.build();
}

最後の1行.oauth2Login(...)が、9.1で説明した「(1) 未ログインの人をKeycloakのログイン画面へ送る」を実現している部分です。ここを有効にするだけで、Keycloakへのリダイレクトも、戻ってきたトークンの検証も、フレームワークが自動で行ってくれます。

9.8 APIを守る側（Resource Server）の設定

一方、画面を持たないAPIの場合は、ログイン画面へ誘導する必要がありません。すでにトークンを持っている前提で、そのトークンが本物かどうかだけを確認します。設定はさらに短くなります。

application.yml（API側） 
# APIを守る側（画面を持たない）の設定
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://localhost:8080/realms/demo-realm

こちらのアプリは、リクエストのAuthorizationヘッダーに乗ってきたアクセストークンを検証するだけです。呼び出し側は、次のようにBearerという単語に続けてトークンを添えてアクセスします。 

# アクセストークンを添えてAPIを呼び出す
curl -H "Authorization: Bearer <アクセストークン>" \
     http://localhost:8081/api/hello

9.9 動作確認の流れ

環境がある場合、実際の動きは次の順で確認できます。

  1. サンプルアプリを起動する
  2. ブラウザで http://localhost:8081/secure を開く
  3. 未ログインなので、自動的にKeycloakのログイン画面に切り替わる
  4. 第8章で使ったユーザーでログインする
  5. Keycloakからアプリへ戻り、保護ページ「/secure」が表示される

9.10 Java以外の選択肢

ここまではSpring Boot（Java）を例にしましたが、考え方はどの言語・技術でも同じです。代表的な選択肢を紹介します。

分野 代表的なライブラリ 特徴
フロントエンド（画面側） keycloak-js／oidc-client-ts ブラウザのJavaScriptから直接Keycloakと連携する
Node.js openid-client OpenID Connectの標準的な処理をひととおり提供するライブラリ
リバースプロキシ方式 oauth2-proxy アプリの手前にプロキシを置き、アプリ自体にはログイン処理を持たせない

言語が違っても骨格は同じ

どの技術を選んでも、設定するのは「issuer URL」「クライアントID」「リダイレクトURI」の3点という骨格は変わりません。この章でSpring Bootの例を通じて学んだ考え方は、そのまま他の言語にも応用できます。

9.11 よくあるエラーと対処

連携がうまくいかないとき、原因は限られたパターンに集約されます。よくある4つを押さえておきましょう。

エラー・症状 原因 対処
redirect_uri が一致しません Keycloakの「Valid redirect URIs」と、アプリが実際に使うURLが不一致 ポート番号・パスまで含めて9.4の設定を再確認する
invalid_client client-secretが間違っている、または再発行されている Keycloakの管理コンソールでCredentialsタブのシークレットを再度控える
issuer-uriに届かない アプリがDockerコンテナ内で動いていて「localhost」が自分自身を指してしまう host.docker.internalなどコンテナ間で到達できるホスト名に変更する
トークンの署名検証エラー issuer-uriが指すレルムと、実際にログインしたレルムが違う issuer-uriのレルム名（demo-realmなど）が正しいか確認する

やってみよう 9-1: サンプルアプリをKeycloakにつないでみる

Javaの実行環境がある場合は実際に手を動かしましょう。無い場合は、下の代替課題で理解度を確認してください。

手順

  1. 1 demo-appクライアントのClient authenticationをONにし、Credentialsタブからシークレットを控える。
  2. 2 Valid redirect URIsにhttp://localhost:8081/login/oauth2/code/keycloak、Web originsにhttp://localhost:8081を追加して保存する。
  3. 3 9.6のapplication.ymlを写経し、控えたシークレットを反映する。
  4. 4 アプリを起動し、http://localhost:8081/secureにアクセスする。
  5. 5 Keycloakのログイン画面が表示されることを確認し、ログインして保護ページが表示されるか確かめる。

代替課題（Java環境が無い場合）

9.6のapplication.ymlを見ながら、client-id・client-secret・issuer-uriの3つについて、それぞれ何を表しているかを自分の言葉で1文ずつ書き出してみましょう。人に説明できれば、この章の内容は理解できています。

この章のまとめ

  • アプリ側がやるべきことは、(1) 未ログインの人をKeycloakへ送る、(2) 戻ってきたトークンを検証するの2つだけ。
  • OAuth2 Client（ログインさせる側）とResource Server（トークンを検証する側）は役割が異なり、Spring Bootでは別々のスターターとして提供される。
  • issuer-uriを1行設定するだけで、認可エンドポイント・トークンエンドポイント・公開鍵の場所が自動的にわかる。
  • 言語やフレームワークが変わっても、設定する骨格（issuer URL・クライアントID・リダイレクトURI）は同じ。

確認問題

  1. Q1. アプリ側がやるべきことを2つ挙げてください。

    回答を表示

    (1) 未ログインの人をKeycloakのログイン画面へ送ること。(2) 戻ってきたトークンが本物か（署名が正しいか）を検証すること。この2つ以外、パスワードの受け取りやログイン画面の作成はアプリ側では行いません。

  2. Q2. issuer-uriを1行設定するだけで、アプリが自動的に把握できることを3つ挙げてください。

    回答を表示

    認可エンドポイント（ログイン画面の場所）、トークンエンドポイント（トークンを受け取る場所）、jwks_uri（署名検証に使う公開鍵の場所）の3つです。アプリは/.well-known/openid-configurationを自動的に読みに行き、これらを把握します。

  3. Q3. spring-boot-starter-oauth2-clientとspring-boot-starter-oauth2-resource-serverの違いを説明してください。

    回答を表示

    oauth2-clientは「ログインさせる側」で、画面のあるWebアプリに追加し、未ログインの人をKeycloakのログイン画面へ誘導する機能を持ちます。oauth2-resource-serverは「APIを守る側」で、画面を持たないAPIに追加し、送られてきたアクセストークンの検証だけを行います。
