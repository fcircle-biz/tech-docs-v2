スタースキーマ

第5章では、Sales に4つのマスタをリレーションでつなぎ、正しく集計が切り替わるモデルを作りました。この形には「スタースキーマ」という名前が付いています。この章では、なぜあの形が良いモデルなのかを、ファクトテーブルとディメンションテーブルという2つの役割から説明できるようになります。あわせて、やってしまいがちな「悪い形」とその直し方も押さえ、Power BI に限らず BI・データウェアハウス全般で通用する基礎知識として整理します。

この章で学ぶこと

  • スタースキーマとは何か、中心と周囲がそれぞれ何を表しているかを説明できる
  • ファクトテーブルとディメンションテーブルの違いを説明し、与えられた表をどちらかに分類できる
  • 日付テーブルを独立させて用意する理由を説明できる
  • フラットテーブルやスノーフレークなど、避けるべきモデルの形とその直し方を説明できる

6.1 スタースキーマとは

第5章で作ったモデルをもう一度思い出してください。中心に Sales（売上）を置き、そこから Products・Customers・Stores・DateTable という4つの表へリレーションを伸ばしました。この「中心に1つの表があり、そこから複数の表が放射状につながっている」形をスタースキーマ（star schema）と呼びます。図にすると、中心の表を囲むように周りの表が並び、線でつなぐとちょうど星（star）のように見えることが名前の由来です。

なぜこの形にすると分析しやすくなるのでしょうか。理由は2つあります。1つ目は、中心の表（売上の記録）と、周りの表（売上を説明する切り口）の役割がはっきり分かれることです。2つ目は、周りの表どうしが直接つながっておらず、必ず中心の表を経由するシンプルな構造になることです。第5章で学んだ「フィルターは1側から多側へ流れる」という向きも、この星形なら中心から見て迷わず追いかけられます。

この中心の表と周りの表には、それぞれ専用の呼び方があります。中心の表をファクトテーブル、周りの表をディメンションテーブルと呼びます。次の2節で、それぞれの特徴を詳しく見ていきましょう。

用語: ファクト（fact）とディメンション（dimension）

fact は英語で「事実・出来事」、dimension は「次元・切り口」という意味です。「売上が発生したという事実」を記録するのがファクトテーブル、「その事実をどの切り口（商品別・顧客別・店舗別・日付別）で眺めるか」を用意するのがディメンションテーブル、と覚えると名前と役割が結びつきやすくなります。

6.2 ファクトテーブル

ファクトテーブルとは、「いつ・誰が・何を・いくつ・いくらで」といった、発生した出来事を1行ずつ記録する表です。本ガイドの Sales（売上明細）がこれにあたります。売上は毎日・毎時間発生するため、ファクトテーブルは行数がどんどん増えていくのが特徴です。みらい商事のような会社であれば、1日に何百件もの受注が記録され、1年で数十万行になることも珍しくありません。

ファクトテーブルには、大きく2種類の列しか出てきません。ほかの表と結びつくためのキーと、QuantityやAmountのように集計・計算の対象になる数値です。この数値列が、第7章で作る集計（メジャー）の材料になります。Sales の列を役割ごとに整理すると次のようになります。

列名 役割
SalesID この売上明細1行を一意に特定する主キー
OrderDate DateTable と結びつく日付キー
ProductID / CustomerID / StoreID それぞれ Products・Customers・Stores と結びつく外部キー
Quantity / Amount 集計・計算の対象になる数値

つまりファクトテーブルは、ほかの表と結びつくための「キー」と、集計するための「数値」だけでできていると言い切ってしまってよいほどシンプルです。逆に言えば、商品名や顧客名のような文字列の属性は、ファクトテーブルにはほとんど出てきません。それらは次に説明するディメンションテーブルの役目だからです。

6.3 ディメンションテーブル

ディメンションテーブルとは、ファクトテーブルに記録された出来事をどの切り口で眺めるかを提供する表です。「商品別に見たい」「顧客の業種別に見たい」「店舗のエリア別に見たい」——こうした「〜別に」に対応する表がディメンションテーブルだと考えると分かりやすいでしょう。ファクトテーブルとは対照的に、行数は少なく、文字列の属性が多いのが特徴です。

Products（商品）

ProductNameやCategoryなど、「商品別・カテゴリ別」に見るための切り口を提供します。

Customers（顧客）

IndustryやRegionなど、「業種別・地域別」に見るための切り口を提供します。

Stores（店舗）

Areaなど、「店舗別・エリア別」に見るための切り口を提供します。

Products の列を見ると、ファクトテーブルとの違いがよく分かります。主キーの ProductID のほかは、ProductName（商品名）・Category（カテゴリ）のように、レポートの見出しや切り口として使う文字列の属性ばかりです。UnitPrice（単価）のように数値の列もありますが、これは集計対象ではなく商品ごとの参照情報として持っている点がファクトの数値とは違います。ProductID が表の中で重複しない一意な値である点も重要です。第5章で確認した「主キーは重複しない」という条件はディメンションの主キーにもそのまま当てはまり、もし重複していればリレーションを作ったときに集計が二重に膨らんでしまいます。

ここまでの内容を整理すると、ファクトテーブルとディメンションテーブルは次のように見分けられます。

観点 ファクトテーブル ディメンションテーブル
何を記録するか 発生した出来事（取引・イベント） 出来事を説明する切り口・属性
行数 非常に多い。日々増え続ける 比較的少ない。マスタなので安定している
列の中心 キーと、集計対象になる数値 名称・分類などの文字列の属性
更新頻度 高い。毎日・毎時追加される 低い。新商品の登録時などに限られる
本ガイドでの例 Sales Products・Customers・Stores・DateTable
Power BI での役割 メジャー（SUMなど）の計算元 スライサー・軸・凡例に使う切り口

迷ったときの見分け方

初めて見る表がファクトかディメンションか迷ったら、「行数が多くて増え続けるか」「数値の合計や件数を知りたい表か」を自問してください。どちらも Yes ならファクト、いいえなら、その表はおそらく何かを説明するディメンションです。

6.4 日付テーブルを必ず用意する

4つのディメンションのうち、DateTable（日付マスタ）だけは少し特別です。ほかの3つ（商品・顧客・店舗）は「業務システムに元からあるマスタを取り込む」のが普通ですが、日付だけは自分で作ることがほとんどです。理由は、日付には「年・四半期・月・曜日」のようにさまざまな切り口があり、それを1つの独立した表にまとめておくと、あらゆる分析で使い回せるからです。

DateTable には、次のような列を用意します。

列名 内容 使いどころ
Date 1日1行の日付（主キー） Sales[OrderDate] とのリレーション
Year 年（例: 2024） 年別の比較
Quarter 四半期（例: Q1） 四半期ごとの推移
Month / MonthName 月番号／月の表示名（例: 4月） 月別の推移、並び順の制御

こうして年・四半期・月といった列を用意しておくと、レポート側では Sales[OrderDate] を直接使わずに、DateTable[Year] や DateTable[MonthName] を軸に置くだけで、年別・月別の切り替えが自由にできるようになります。第9章で扱う「年→四半期→月→日」のドリルダウンも、この DateTable があって初めて成立します。

注意: 表の名前を「Calendar」や「Date」にしない

日付マスタの表名は DateTable のように、DAX の関数名と衝突しない名前にしましょう。CALENDAR や DATE は Power BI の DAX に元から存在する関数名なので、表名に使うと数式が読みにくくなったり、思わぬ混乱を招いたりします。本ガイドで一貫して DateTable という名前を使っているのはこのためです。

表を作ったら、Power BI にもう1つ伝えておくことがあります。モデルビューで DateTable を選び、テーブルツール → 日付テーブルとしてマークを実行し、日付が入っている列として Date を指定します。これにより、Power BI は「この表が日付専用のディメンションである」と認識し、年・四半期・月をまたぐ時系列の計算を正しく行えるようになります。バージョンにより、メニューの名称や位置が異なる場合があります。

6.5 やってはいけない形と直し方

スタースキーマの形が分かったところで、逆に避けるべき形も知っておきましょう。新人のうちは、良かれと思ってやった工夫が、実は分析をしづらくしていることがよくあります。代表的な2つのパターンを、正しい形と並べて見てみます。

3つ目のパターンとして、ファクトテーブル同士を直接つなぐ形も避けるべきものです（たとえば Sales と別の「返品」ファクトを直接リレーションでつなぐなど）。ファクト同士は行数が多いうえに関係が複雑になりやすく、意図しない重複集計を引き起こします。それぞれの症状・原因・直し方を整理すると次のとおりです。

症状 原因 直し方
列が数十〜百あり、同じ値が何度も重複している。読み込みや更新が重い フラットテーブル: 1枚の巨大な表にすべてを詰め込んでいる ファクトとディメンションに分割し、第5章の手順でリレーションをつなぎ直す
商品カテゴリを知るのに表を2つも3つもたどらないといけない スノーフレーク: ディメンションをさらに正規化し、枝分かれさせている ディメンションは多少の重複を許容してでも1枚にまとめる（非正規化）。行数が少ないので重複を気にしなくてよい
絞り込むと数字が想定より膨れ上がる、フィルターの効き方が予測できない ファクト同士の直結: 行数の多い表どうしを直接リレーションでつないでいる ファクト同士はつながない。共通のディメンションを介して間接的に関連づける

3つとも根っこにある考え方は同じです。行数の多いファクトは分けて軽くし、行数の少ないディメンションはまとめて単純にする。スタースキーマは、この2つのバランスを取った結果たどり着く形だと理解しておくと、応用が利くようになります。

6.6 BI・DWH の基礎知識としてのスタースキーマ

スタースキーマという考え方は、実は Power BI が発明したものではありません。もともとはデータウェアハウス（DWH：分析用にデータを蓄積する仕組み）の設計手法として何十年も前から使われてきたもので、Tableau や Looker といった他の BI ツール、SQL Server や Snowflake のようなデータベース製品でも同じ考え方が通用します。

つまり、この章で学んだ「ファクトとディメンションを見分け、星形につなぐ」という感覚は、Power BI 特有の小技ではなく、データ分析全般に通用する基礎知識です。将来、別の BI ツールやデータ基盤を扱うことになっても、この考え方はそのまま活きます。次章からは、こうして整った星形のモデルの上で、実際に数字を計算するDAXという言語を学んでいきます。

なぜ第7章の前にこの章があるのか

第7章で学ぶ DAX の関数は、どれも「ファクトテーブルの数値を、ディメンションテーブルの切り口で集計する」ことを前提に作られています。モデルの形が歪んでいると、DAX の書き方をいくら覚えても数字が合いません。この章で形を整理しておくことが、次章をスムーズに理解する近道です。

やってみよう 6-1: 5つの表をファクトとディメンションに仕分けする

ここまで例として使ってきた Sales・Products・Customers・Stores・DateTable の5つの表を、資料を見返さずに自分の手で仕分けしてみましょう。

手順

  1. 1 紙またはメモアプリに5つの表の名前を書き出し、それぞれ「ファクト」か「ディメンション」かを判断して分類する。判断の根拠（行数が多いか／数値が中心か文字列が中心か）も1行添える。
  2. 2 分類できたら、中心に Sales を置き、残り4つを周囲に配置した星形の図を自分の手で描いてみる（6.1のMermaid図を見ずに）。
  3. 3 描き終えたら6.1・6.3の内容と見比べ、ズレていた表があれば、なぜ迷ったのかを言葉にしておく。次に別のデータに出会ったときの判断材料になる。
  4. 4 余裕があれば、自分の職場で扱っているデータについても「ファクトはどれで、ディメンションはどれか」を1組挙げてみる。

理解度確認クイズ

  1. Q1. ある表がファクトテーブルかディメンションテーブルかを見分けるには、どこに注目すればよいですか？

    回答を表示

    行数と列の中心に注目します。行数が多く日々増え続け、列の中心が集計対象の数値とキーであればファクトテーブル（例: Sales）です。逆に行数が少なく安定していて、列の中心が名称や分類などの文字列の属性であればディメンションテーブル（例: Products・Customers・Stores）です。

  2. Q2. 日付だけを独立した DateTable として用意するのはなぜですか？

    回答を表示

    年・四半期・月・曜日など、日付にはさまざまな切り口があり、それらをあらかじめ列として持つ独立した表にしておくと、あらゆる分析で共通して使い回せるからです。Sales[OrderDate] を直接使うのではなく DateTable を軸にすることで、年別・月別の切り替えやドリルダウンが正しく行えるようになります。表名を Calendar や Date にしないのは、DAX の関数名と衝突するためです。

  3. Q3. スタースキーマとスノーフレークは何が違いますか？

    回答を表示

    スタースキーマはディメンションテーブルを1枚にまとめ、ファクトテーブルから直接つながる形です。スノーフレークは、ディメンションをさらに正規化して枝分かれさせた形（例: Products から Categories をさらに切り出す）です。ディメンションは行数が少ないため多少の重複（非正規化）を許容してでも1枚にまとめるほうが扱いやすく、Power BI ではスタースキーマが基本形として推奨されます。
