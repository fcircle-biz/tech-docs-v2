ホーム Power BI 第5章
第5章 所要時間: 約75分

データモデリング

第4章では、Power Query を使って売上データやマスタデータを分析しやすい形に整えました。しかし、整形しただけのテーブルは、まだバラバラの5枚の表のままです。この章では、売上明細と商品・顧客・店舗・日付という4つのマスタをリレーションシップ（関係）でつなぎ、Power BI が1つのデータのかたまりとして扱えるようにする方法を学びます。ここで作るつながりが、第6章で学ぶ「スタースキーマ」という形の土台になり、第7章の DAX 計算にもそのまま使われます。

この章で学ぶこと

  • Excel の VLOOKUP で1枚の表にまとめる方法に、どんな限界があるかを説明できる
  • 主キーと外部キーの違いを理解し、テーブルが一意かどうかを確認できる
  • モデルビューでテーブル同士のリレーションシップを作成できる
  • カーディナリティの種類と、フィルターが「1」側から「多」側へ流れる仕組みを説明できる

5.1 なぜ1枚の大きな表ではいけないのか

Power Query で整形が終わると、次は「全部まとめて1枚の表にしてしまおう」と考えたくなるかもしれません。Excel の VLOOKUP や XLOOKUP に慣れていると、Sales の各行に商品名やカテゴリを関数で引っ張ってきて、横に長い1枚の表にまとめるやり方が自然に思えるからです。まずは、この方法にどのような問題があるのかを具体的に見てみましょう。

SalesID ProductID 商品名 カテゴリ 金額
S0001 P001 クリアファイル 文具 3,600円
S0002 P001 クリアファイル 文具 1,800円
S0003 P002 コピー用紙 用紙 12,000円

ProductID が P001 の2行で、「クリアファイル」「文具」がそのまま繰り返されているのが分かります。ここに Customers や Stores の情報まで横に足していくと、重複はさらに増えます。売上明細が1万行あれば、この重複も1万回繰り返されることになります。この方式には、主に3つの問題があります。

重複

同じ商品名やカテゴリが、売上の行数だけ何度も書き写されます。情報は1つなのに、保存される回数だけ増えていきます。

更新漏れ

商品名を変更すると、その商品が登場するすべての行を書き換えないと、新旧の名前が混在してしまいます。

サイズ増大

重複した文字列が行数分積み重なるためファイルサイズが膨らみ、行数が増えるほど動作も重くなります。

テーブルを分けたままリレーションシップでつなぐと、商品名は Products に1回だけ持てばよく、名前を変更したいときも1行を直すだけで済みます。マスタは小さく保たれ、新しいマスタ表を追加したいときも表を足してつなぐだけで拡張できます。情報は1か所にだけ持ち、必要なときにリレーションシップでつなぎ合わせる——これが本章で学ぶ考え方の基本です。

5.2 テーブル・主キー・外部キー

複数の表を安全につなぐには、それぞれの表に「この1行を特定できる目印」が必要です。この目印を主キー（Primary Key）と呼びます。たとえば商品マスタ Products では、ProductID 列の値（P001、P002…）が主キーです。主キーには2つの条件があります。値が重複しないこと（同じ ProductID を持つ行が2つあってはならない）と、すべての行に値が入っていること（空欄があってはならない）です。

本ガイドで使う5つの表の主キーを整理すると、次のようになります。

テーブル 主キー 備考
Products ProductID 商品ごとに1行
Customers CustomerID 顧客ごとに1行
Stores StoreID 店舗ごとに1行
DateTable Date 日付ごとに1行
Sales SalesID 売上明細ごとに1行。ただし他の4表を指す列も持つ

一方、Sales テーブルにも ProductID という列がありますが、こちらは主キーではありません。同じ値が何度も登場してよい列で、これを外部キー（Foreign Key）と呼びます。外部キーは「よそのテーブルの主キーを指し示す列」で、値が重複していてもかまいません。むしろ、1つの商品が何度も売れるからこそ、Sales[ProductID] には同じ値が繰り返し登場するのが正常な状態です。

主キーが本当に一意かどうかを確かめる

第4章で学んだ「重複の削除」の考え方がここで役立ちます。テーブルビューで元の行数を確認し、その列だけを重複削除した場合の行数と比較して、両者が一致すれば一意といえます。数値としては同じに見えても、文字列の前後に余分な空白が入っていると別の値として扱われてしまう点にも注意しましょう。

5.3 リレーションの作り方

主キーと外部キーの対応が分かったら、実際にモデルビューでリレーションシップを作成します。操作自体はシンプルで、列を列へドラッグ＆ドロップするだけです。

  1. 左側のビュー切り替えアイコンから モデルビュー を開く（第2章 2.3 で紹介した3つのビューの1つです）。
  2. キャンバス上に Sales と4つのマスタテーブルが表示されていることを確認し、重ならないように配置を整える。
  3. Sales の ProductID 列を、Products の ProductID 列までドラッグ＆ドロップする。
  4. 2つのテーブルの間に線（リレーションシップ）が引かれれば成功。同様に CustomerID・StoreID・OrderDate（DateTable[Date] へ）も作成する。
  5. モデリング タブの リレーションシップの管理 を開き、4本のリレーションがすべてアクティブになっていることを確認する。

Excel や CSV を読み込んだ直後に、Power BI が列名とデータ型を見比べて自動的にリレーションシップを作成してくれることもあります（自動検出）。ただし自動検出は、列名が完全に一致しない場合や、名前は似ていてもデータ型が違う場合には働きません。バージョンにより挙動が異なる場合もあるため、作られたリレーションが意図したとおりかどうかを、必ず目で確認する習慣をつけましょう。

注意: 自動検出を過信しない

自動検出は便利ですが、列名がたまたま一致しただけで、意味の違う列同士がつながってしまうこともあります。作成されたリレーションシップは リレーションシップの管理 を開き、「どの表のどの列」がつながっているかを必ず確認してください。

5.4 カーディナリティとフィルターの方向

4本のリレーションシップができたところで、5つの表がどのようにつながっているかを図で確認しましょう。

erDiagram Products ||--o{ Sales : "販売される" Customers ||--o{ Sales : "購入する" Stores ||--o{ Sales : "取り扱う" DateTable ||--o{ Sales : "計上される" Products { string ProductID PK string ProductName string Category int UnitPrice } Customers { string CustomerID PK string CustomerName string Industry string Region } Stores { string StoreID PK string StoreName string Area } DateTable { date Date PK int Year int Quarter int Month string MonthName } Sales { string SalesID PK date OrderDate FK string ProductID FK string CustomerID FK string StoreID FK int Quantity decimal Amount }

図の中で、マスタ側の線の端についている記号が「1」、Sales 側の記号が「多」を表しています。この「1」と「多」の組み合わせをカーディナリティと呼び、代表的な4種類を整理すると次のようになります。

種類 意味 本ガイドでの例 使用頻度
1対多 「1」側の1件に対し「多」側が何件も対応する Products（1）→ Sales（多） 基本形。本ガイドの4本はすべてこれ
多対1 1対多と同じ関係を「多」側から見た呼び方 Sales（多）→ Products（1） 1対多の裏返し。呼び方が違うだけ
1対1 双方のテーブルで主キーが1件ずつ対応する 例: 従業員表と緊急連絡先表を分けた場合 まれ。多くは1つの表にまとめられる
多対多 どちらの側にも重複した値がありうる 例: 1つの注文が複数のキャンペーンに該当する 上級者向け。初心者はまず避ける

カーディナリティが分かったところで、次に大事なのがフィルターがどちら向きに流れるかです。既定のリレーションシップでは、フィルターは常に「1」側から「多」側へ流れます。具体的な場面で確認してみましょう。

flowchart TD A["① スライサーで
「カテゴリ＝文具」を選ぶ"] --> B["② Products（1側）が
文具の行だけに絞り込まれる"] B -->|リレーションに沿ってフィルターが伝わる| C["③ Sales（多側）も
文具に関連する行だけに絞り込まれる"] C --> D["④ 売上金額の合計が
文具だけの数字になる"]

クロスフィルターの方向は各リレーションシップの設定で確認・変更でき、既定は単一方向（1→多）です。双方向にすると多側の絞り込みが1側にも影響するようになりますが、表が増えるほどフィルターの経路があいまいになりやすいため、本ガイドでは原則として単一方向のまま使うことをおすすめします。また、1つの表に同じ相手への列が複数ある場合（たとえば Sales に注文日と出荷日の両方があり、どちらも DateTable と結びつけたい場合）、同時にアクティブにできるリレーションシップは1本だけです。2本目はモデルビュー上で点線として表示される非アクティブなリレーションシップになり、既定の集計には使われません。非アクティブなリレーションシップを計算に使う方法は、第7章で DAX を学んだ後に扱います。

5.5 セマンティックモデルとは

ここまでで、5つのテーブルがリレーションシップでつながり、1つの「データのかたまり」になりました。このテーブル＋リレーションシップ（さらに第7章で追加するメジャー）をまとめた全体を、Power BI ではセマンティックモデルと呼びます。

「モデル」という言葉のとおり、これは特定のグラフや表の見た目とは切り離された、分析の土台となるデータ構造です。第1章で見た「データがレポートになるまでの流れ」でいうと、ちょうど今取り組んでいる「モデルを作る」の工程にあたります。

セマンティックモデルは再利用される

第10章で扱いますが、Power BI Service に発行すると、セマンティックモデルとレポート（見た目のページ）は別々の項目として登録されます。1つのセマンティックモデルを土台に、目的の違う複数のレポートを作ることができるため、モデルをきちんと作り込んでおくほど、後の工程が楽になります。

やってみよう 5-1: Sales とマスタをつないでみる

第4章で整形した Sales に、Products・Customers・DateTable の3つのマスタをつなぎ、フィルターが正しく伝わることを確認しましょう。

手順

  1. 1 モデルビューを開き、Sales・Products・Customers・DateTable の4つのテーブルが表示されていることを確認する。
  2. 2 Sales[ProductID] を Products[ProductID] にドラッグしてリレーションシップを作成する。
  3. 3 Sales[CustomerID] を Customers[CustomerID] に、Sales[OrderDate] を DateTable[Date] にドラッグして、同様にリレーションシップを作成する。
  4. 4 リレーションシップの管理を開き、作成した3本がすべてアクティブになっていることを確認する。
  5. 5 レポートビューでテーブルビジュアルに Products[Category] と Sales の金額を配置し、スライサーに Customers[Region] を追加する。
  6. 6 スライサーで地域を切り替え、カテゴリ別の金額がそのたびに変わることを確認する。これがフィルターが「1」側から「多」側へ伝わっている証拠です。

理解度確認クイズ

  1. Q1. Products と Sales の1対多のリレーションシップで、「1」側になるのはどちらのテーブルですか。理由も説明してください。

    回答を表示

    「1」側は Products です。Products[ProductID] は商品ごとに1行しかない一意な値（主キー）ですが、Sales[ProductID] には同じ商品IDが何度も登場します（外部キー）。一意な値を持つ側が常に「1」側になります。

  2. Q2. フィルターはリレーションシップのどちら向きに流れるのが基本ですか。具体例で説明してください。

    回答を表示

    基本は「1」側から「多」側へ一方向に流れます。たとえば Products[Category] ＝「文具」というフィルターをスライサーでかけると、そのフィルターはリレーションシップを通じて Sales 側に伝わり、文具に関連する売上行だけに絞り込まれます。

  3. Q3. Excel の VLOOKUP ですべてを1枚の表にまとめる方法には、どのような問題がありますか。

    回答を表示

    商品名やカテゴリなどのマスタ情報が売上の行数だけ重複して持たれるため、ファイルサイズが大きくなり、名前を変更する際にはすべての行を書き換えないと新旧の情報が混在してしまいます。テーブルを分けてリレーションでつなげば、マスタ情報は1か所にだけ持てばよくなります。
