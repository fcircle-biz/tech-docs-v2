第12章 所要時間: 約90分

エラー処理とデバッグ

第11章までで、配列やDictionaryを使って何十件もの支店別データを一度に処理できるようになりました。コードが大きく複雑になるほど、シート名の打ち間違いや0での割り算といった小さなミスに出会う機会も増えていきます。この章では、そうした「止まってしまう瞬間」を怖がる代わりに、エラーメッセージをExcelからの案内として読み解き、自分の手で原因を突き止め、そして最初から壊れにくいマクロを書けるようになることを目指します。

この章で学ぶこと

  • コンパイルエラー・実行時エラー・論理エラーの3種類を区別し、原因の当たりを付けられる
  • On Error GoTo と On Error Resume Next を、危険性を理解したうえで使い分けられる
  • ブレークポイント（実行を一時停止させる目印）・ステップ実行・ローカルウィンドウ・ウォッチ式で不具合の原因を特定できる
  • Err オブジェクトからエラー番号と内容を取得し、利用者に分かるメッセージを出せる

12.1 エラーには3種類ある

複雑になったコードほど、思いどおりに動かない場面に出会う回数も増えます。ここでまず持っておきたいのが「エラーは失敗ではない」という考え方です。エラーメッセージは、Excelが「ここで困っています」と教えてくれる案内板のようなもので、読み方さえ知っていれば原因まで一直線にたどり着けます。まずはエラーを3つの種類に分けることから始めましょう。対処のしかたがまったく違うため、どの種類かを見分けることが原因調査の第一歩です。

① コンパイルエラー

文法そのものの誤りです。実行する前にVBEが指摘してくれます。例: If に対応する End If の書き忘れ。

② 実行時エラー

文法は正しいのに、動かしてみて初めて起きるエラーです。例: 存在しないシート名を指定した。本章の中心テーマです。

③ 論理エラー

エラーは何も出ないのに結果が間違っています。例: 第7章のクイズで扱った ElseIf の順序ミス。最も見つけにくいタイプです。

書いたコードをExcelが実行できる形へ翻訳する、実行直前の下準備をコンパイルと呼びます。この翻訳の段階で見つかる文法の誤りが「コンパイルエラー」です。コンパイルエラーは、文法の誤りを実行前の段階でVBEが指摘してくれるため、実は一番対処しやすいエラーです。ただしVBAは実行するモジュールから順に確認するため、別のモジュールの誤りが実行するまで見つからないこともあります。［ツール］→［VBAProjectのコンパイル］を実行すると、プロジェクト全体をまとめて確認できます。本章で重点的に扱うのは②の実行時エラーで、③の論理エラーについては「テスト用の少ないデータで、想定した答えと見比べる」という地道な確認が基本になります。まずは、思いどおりに動かないときにどう切り分けて考えればよいか、全体の流れをつかんでおきましょう。

flowchart TD A["思いどおりに動かない"] --> B{"エラーダイアログは出たか"} B -->|Yes| C["エラー番号を確認する"] C --> D["「デバッグ」ボタンで
該当行を特定する"] B -->|No・論理エラーの疑い| E["結果のどこが違うかを特定する"] E --> F["その直前にブレークポイントを置く"] F --> G["F8とローカルウィンドウで
変数の変化を追う"]

図の説明: エラーダイアログが出たら実行時エラーなので、エラー番号を手がかりに調べます（12.2〜12.4節）。ダイアログが出ないのに結果が違う場合は論理エラーなので、ブレークポイントとステップ実行で変数を1つずつ追いかけます（12.5節で詳しく扱います）。

12.2 よく出る実行時エラーの番号と原因

実行時エラーが起きると、Excelは画面の中央にダイアログを表示します。たとえば、存在しない「集計表」というシート名を指定してしまったときは、次のような表示になります。

実行時エラーダイアログの表示例 
実行時エラー '9':

インデックスが有効範囲にありません

この「9」という番号が、原因を絞り込む一番の手がかりです。第6章から第11章までに書いてきたコードで実際に出会いやすい番号を、原因とあわせて一覧にしました。

エラー番号 メッセージ 主な原因
9 インデックスが有効範囲にありません 存在しないシート名を指定した／配列の範囲外の添字を使った
11 0で除算しました 割り算の分母が0になった
13 型が一致しません 数値を扱うつもりの変数に文字列を代入しようとした
91 オブジェクト変数または With ブロック変数が設定されていません Set を書き忘れたままオブジェクトを使った
424 オブジェクトが必要です オブジェクトを期待する箇所に、値やオブジェクトでないものを渡した
1004 アプリケーション定義またはオブジェクト定義のエラーです 存在しないセル範囲を指定した／既にあるシート名で新規作成しようとした

ヒント: 「デバッグ」ボタンを押すと該当行が分かる

エラーダイアログには「終了」と「デバッグ」の2つのボタンがあります。「デバッグ」を押すと、VBEに切り替わってエラーが起きた行が黄色く反転表示されます。この機能だけでも「どの行で」止まったかが一目で分かるため、まずはエラー番号よりも先に「デバッグ」ボタンを押す習慣をつけましょう。

12.3 On Error GoTo でエラーを受け止める

エラー番号から原因が分かっても、業務で使うマクロが利用者の前で英語まじりのエラーダイアログを出して止まってしまっては困ります。On Error GoTo ラベル名 を使うと、それ以降でエラーが起きたときに、あらかじめ用意しておいた行へ処理をジャンプさせられます。ここでの「受け止める」は、エラーを消してしまうのではなく、利用者に分かる言葉で伝え、後片付けをしてから終えるという意味です。

SafeWriteSummary — On Error GoTo の基本形 
Sub SafeWriteSummary()
    Dim ws As Worksheet
    On Error GoTo ErrHandler          ' 以降でエラーが出たら ErrHandler へ飛ぶ
    Set ws = ThisWorkbook.Worksheets("集計")   ' シートがないとエラー9
    ws.Range("A1").Value = "支店別売上集計"
    MsgBox "書き込みが完了しました", vbInformation
    Exit Sub                          ' 正常時はここで終了する（重要）
ErrHandler:
    MsgBox "処理を中断しました" & vbCrLf & _
           "エラー " & Err.Number & ": " & Err.Description, vbExclamation
End Sub

ポイントは3つです。①On Error GoTo ErrHandler を先頭近くに書くと「これ以降でエラーが起きたら ErrHandler: というラベル（目印）へジャンプする」という約束になります。②正常に処理が終わった場合は Exit Sub でプロシージャを終え、ラベル以降のコードには進みません。③エラーでジャンプしてきた場合は、VBAが自動的に用意している Err オブジェクトの Err.Number（エラー番号）と Err.Description（エラーの説明文）を使って、利用者に何が起きたかを伝えます。

flowchart TD A["On Error GoTo ErrHandler"] --> B["通常の処理を実行"] B --> C{"エラー発生？"} C -->|Yes| E["ErrHandlerラベルへジャンプ"] C -->|No＋Exit Subあり| D["Exit Subで正常終了"] C -.->|No・Exit Subを忘れると…| E E --> F["Err.NumberとErr.Descriptionを表示"] F --> G["設定を元に戻す"] G --> H["End Sub"]

図の説明: エラーが起きればErrHandlerへジャンプし、起きなければExit Subで正常終了します。破線は「Exit Subを書き忘れた場合」を表しており、この場合はエラーが起きていないのに、そのままErrHandler以降のコードへ流れ込んでしまいます。

初心者のつまずきポイント: Exit Sub を書かないと、正常時にもエラーメッセージが出る

エラーハンドラのラベル（ErrHandler:）は多くの場合 End Sub の直前に置きます。VBAはコードを上から下へそのまま読み進めるため、Exit Sub がないと、エラーが起きていなくてもそのままラベル以降のコードへ流れ込み、正常に終わったはずなのにエラーメッセージが表示されてしまいます。「エラーハンドラの直前には必ず Exit Sub」とセットで覚えましょう。この点は第14章の理解度確認クイズでも扱います。

12.4 On Error Resume Next の使いどころと危険性

On Error Resume Next は「エラーが起きても、そこで止まらず次の行へ進む」という指定です。一見便利そうに見えますが、使い方を誤るとマクロの不具合そのものを見えなくしてしまう、本章でもっとも注意が必要な命令です。

注意: On Error Resume Next は「エラーを直した」わけではありません

On Error Resume Next がしているのは、「エラーが起きても止まらず、次の行へ進む」という指示だけです。エラーの原因そのものは何ひとつ解決していません。

これを広い範囲にかけてしまうと、シート名の打ち間違いのような本当に困るエラーまで黙って握りつぶされ、原因の分からない誤った結果がそのまま残ってしまいます。「とりあえずエラーが出なくなるから」という理由で、この命令を常用してはいけません。

DeleteSheetIfExists — 範囲を限定した正しい使い方 
Sub DeleteSheetIfExists()
    Application.DisplayAlerts = False
    On Error Resume Next              ' シートが無くてもエラーで止めない
    ThisWorkbook.Worksheets("作業用").Delete
    On Error GoTo 0                   ' 無視の設定はすぐ解除する（重要）
    Application.DisplayAlerts = True
    MsgBox "「作業用」シートを削除しました（元々無い場合は何もしません）"
End Sub

この例では「作業用シートがあれば消す、無ければ何もしない」という1行だけのためにエラー無視を使い、直後の On Error GoTo 0 ですぐに解除しています。On Error GoTo 0 は「エラー処理の指定をすべて解除し、通常の状態（エラーが起きたらダイアログを出す）に戻す」という意味です。ほかにも、Dictionaryに特定のキーがあるかどうかを確認する処理などで、同じように範囲を絞って使われます。

エラーを無視してよいのは、あくまで「失敗するかもしれないが、失敗しても対処できる」と分かっているごく短い範囲に限ります。次のように、シートの有無を確かめるだけの1行に絞り込むのが基本の型です。

シートの有無を確かめる — 範囲を1行に絞った基本形 
Sub CheckSummarySheet()
    Dim ws As Worksheet

    ' エラーを無視するのは、この1行だけに限定する
    On Error Resume Next
    Set ws = ThisWorkbook.Worksheets("集計")
    On Error GoTo 0          ' すぐに通常のエラー処理へ戻す

    If ws Is Nothing Then
        ' シートが無かった場合の処理をここで明示的に書く
        MsgBox "「集計」シートが見つかりません。", vbExclamation
    End If
End Sub

ポイントは2つです。①On Error Resume Next と On Error GoTo 0 をセットで書き、その間に挟むのは1〜2行だけにします。②無視したあとは If ... Is Nothing や If Err.Number <> 0 Then で結果を必ず確かめます。エラーを無視しただけで確認をしないと、ws が空のままその後のコードが実行され、結局どこかで別のエラーになってしまいます。

本章の基本方針は、これまで見てきた On Error GoTo ラベル によるエラー処理の記述です。On Error Resume Next は、シートの有無を確かめるときなど失敗が想定内である限定的な場面で使う道具、という位置づけで覚えてください。

警告: マクロの先頭に On Error Resume Next を書いてはいけません

やってはいけない典型例は、プロシージャの先頭に On Error Resume Next を書き、そのまま最後まで解除しないパターンです。こう書くと、プロシージャのどこでエラーが起きても気づかないまま処理が進み続けます。シート名を間違えていても、計算が0で割れていても、Excelは何も教えてくれません。結果だけがそっと間違っていく、原因究明がもっとも難しい不具合になります。

鉄則は「使うのは必要な数行だけ、使ったら直後に On Error GoTo 0 で解除する」ことです。範囲を絞れないなら、素直に On Error GoTo でエラーハンドラを用意する方法を選びましょう。

初心者のつまずきポイント: 解除し忘れて、以降のバグが全部隠れる

On Error GoTo 0 を書き忘れると、その行より後ろで発生するエラーもすべて無視され続けます。On Error Resume Next を書いたら、その場で「次の何行かで使って、すぐ On Error GoTo 0 を書く」ところまでをワンセットで入力してしまうと、書き忘れを防げます。

12.5 デバッグ機能を使いこなす

用語: デバッグ

思いどおりに動かない原因を探して直す作業を デバッグ と呼びます。バグ（bug＝虫）を取り除く、という意味の言葉です。

論理エラー（エラーは出ないのに結果が違う）を調べるには、コードを1行ずつ実行しながら変数の中身を確認するのが一番の近道です。VBEには、この「実行を一時停止して覗き見る」ための機能が揃っています。コードの実行を「この行の直前で一度止めて」と指示する目印をブレークポイントと呼びます。VBEで行の左端をクリック（または F9）すると、赤い丸の目印が付きます。

操作 キー できること
ブレークポイント F9 その行の直前で実行を一時停止する。もう一度押すと解除
ステップイン F8 コードを1行だけ実行し、次の行の手前で止まる
ステップオーバー Shift + F8 呼び出し先プロシージャの中には入らず、1行分だけ進める
カーソル行まで実行 Ctrl + F8 今止まっている場所から、カーソルを置いた行まで一気に進める
ローカルウィンドウ メニューから表示 中断中に、その時点の全変数の値を一覧表示する
ウォッチ式 メニューから追加 特定の変数だけを監視し、指定した条件が成立したら自動で停止する

次のコードで実際に試してみましょう。Debug.Print の行に F9 でブレークポイントを置いてから実行し、F8 で1行ずつ進めながらローカルウィンドウで i と total の値が増えていく様子を確認してください。

DebugPractice — F9とF8で変数の動きを追う 
Sub DebugPractice()
    Dim i As Long
    Dim total As Long
    For i = 1 To 5
        total = total + i
        ' 次の行に F9 でブレークポイントを置き、F8 で1行ずつ進めて
        ' ローカルウィンドウで i と total の変化を観察する
        Debug.Print "i=" & i & " / total=" & total
    Next i
    MsgBox "合計: " & total       ' 正しい答えは 15
End Sub

ヒント: 変数の上にマウスを乗せるだけでも値が見える

中断中（黄色い行で止まっている状態）は、コード上の変数名にマウスカーソルを乗せるだけで、その時点の値がポップアップで表示されます。ローカルウィンドウを開くほどでもない、ちょっとした確認に便利です。

初心者のつまずきポイント: 中断中にコードを書き換えると変数がリセットされる

黄色い行で止まっている状態のままコードを書き換えると、「プロジェクトはリセットされます」という警告が表示されます。このまま続けるとそれまで追いかけていた変数の値がすべて消えて、最初から実行し直しになります。原因を調べ終えてから修正するか、リセットボタン（■）で完全に停止してから編集するようにしましょう。

12.6 エラーに強いマクロの作法

最後に、これまで学んだことを「事後の対処」から「事前の備え」へ広げます。エラーが起きてから On Error GoTo で受け止めるだけでなく、そもそもエラーが起きにくいマクロを書くための3つの原則を押さえておきましょう。第14章の総合演習では、この3原則をすべて使います。

① 入口で前提条件を確認する

処理を始める前に「シートは存在するか」「データは1件以上あるか」を確認します。土台が崩れていれば、複雑な処理に入る前に穏やかに知らせて終了できます。

② 変更した設定は必ず戻す

ScreenUpdating・Calculation・DisplayAlerts を変更したら、途中でエラーが起きた場合でも元の状態に戻します。

③ 想定外のエラーは利用者に伝える

想定していないエラーを On Error Resume Next で握りつぶさず、Err.Description を添えて利用者に知らせます。

第11章で ScreenUpdating を元に戻すために On Error GoTo Cleanup を使いました。あれはエラー処理の典型的な形です。途中で何が起きても最後に必ず通る場所（後片付けの場所）を作っておく、という考え方を覚えてください。

次のコードは、②の原則を体現した例です。Application.ScreenUpdating = False で画面の更新を止めた直後にエラー（0での除算）が起きても、エラーハンドラの中で必ず変更前の値に戻しています。Application.ScreenUpdating = True のように決め打ちで戻さず、savedScreenUpdating に保存しておいた値へ戻すのは、第11章で学んだ原則です（呼び出し元がすでに ScreenUpdating = False にしていた場合でも、意図せず True にしてしまわないようにするためでした）。ここで注目してほしいのは、ラベル以降のコードは、エラー時だけでなく正常時にも通ってよいという点です。この形では Exit Sub を置かず、あえて後片付けの処理をエラーの有無にかかわらず1回だけ通しています。

RestoreSettings — エラー時も設定を必ず元に戻す 
Sub RestoreSettings()
    Dim divisor As Long, result As Double
    Dim savedScreenUpdating As Boolean
    savedScreenUpdating = Application.ScreenUpdating   ' 変更前の値を保存
    On Error GoTo ErrHandler
    Application.ScreenUpdating = False
    divisor = 0
    result = 100 / divisor            ' 0で割るのでエラー11が発生する
    Debug.Print result
ErrHandler:
    ' ここは正常時も通る。後片付けを必ず実行するための書き方
    Application.ScreenUpdating = savedScreenUpdating   ' 決め打ちのTrueではなく元の値に戻す
    If Err.Number <> 0 Then MsgBox "エラー: " & Err.Description, vbExclamation
End Sub

If Err.Number <> 0 Then という一文がポイントです。エラーが起きていなければ Err.Number は0のままなので、このチェックによって「後片付けは必ず行うが、メッセージ表示はエラー時だけ」という制御ができます。12.3節の書き方（Exit Sub で分ける）と、この書き方（後片付けだけ共通化する）は、どちらも実務でよく使われる型です。処理の内容に応じて使い分けてください。

やってみよう 12-1: エラーを起こしてから、飼いならす

実際にエラーを発生させ、デバッグしながら安全なコードへ改修していく一連の流れを体験します。

手順

  1. 1 存在しないシート名「集計表」（正しくは「集計」）を指定するマクロを書いて実行し、エラー9のダイアログが出ることを確認する。「デバッグ」ボタンを押して、該当行が黄色く反転する様子も見ておく。
  2. 2 手順1のマクロに On Error GoTo を追加し、「集計シートが見つかりません。先に PrepareSummarySheet を実行してください」という利用者向けの分かりやすいメッセージを出すように改修する。
  3. 3 DebugPractice の Debug.Print の行にブレークポイントを置き、F8 でステップ実行しながら、ローカルウィンドウで i と total の値の変化を記録する。
  4. 4 発展課題として、第11章で作った WriteBranchSummary に On Error GoTo と設定の復元処理を追加し、途中でわざとエラーを起こしても ScreenUpdating が必ず変更前の値に戻ることを確認する。

実行前 ― シートの状態

この演習は、下の状態から始めます。「売上明細」シートには通常どおり10件のデータが入っていますが、あらかじめ「集計」シートを削除しておいてください（シート見出しを右クリック→削除）。

「売上明細」シート: 2〜11行目に10件のデータあり（変更なし）
「集計」シート    : 削除済み（存在しない）

実行するコード

手順2で完成させる SafeWriteSummary（12.3節と同じコード） 
Sub SafeWriteSummary()
    Dim ws As Worksheet
    On Error GoTo ErrHandler          ' 以降でエラーが出たら ErrHandler へ飛ぶ
    Set ws = ThisWorkbook.Worksheets("集計")   ' シートがないとエラー9
    ws.Range("A1").Value = "支店別売上集計"
    MsgBox "書き込みが完了しました", vbInformation
    Exit Sub                          ' 正常時はここで終了する（重要）
ErrHandler:
    MsgBox "処理を中断しました" & vbCrLf & _
           "エラー " & Err.Number & ": " & Err.Description, vbExclamation
End Sub

期待される実行結果

「集計」シートが無いため Set ws = ... の行でエラー9が発生し、ErrHandler: 側の次のメッセージボックスが表示されます。

処理を中断しました
エラー 9: インデックスが有効範囲にありません。

理解度確認クイズ

  1. Q1. 実行してみるまでは分からず、動かして初めて発生するエラーの種類はどれですか。

    回答を表示

    実行時エラーです。コンパイルエラーは文法の誤りで、実行する前にVBEが指摘します。論理エラーはそもそもエラーダイアログ自体が出ず、結果を見比べて初めて気づきます。3種類は対処法がまったく違うため、どれに当たるかを見分けることが原因調査の第一歩です。

  2. Q2. On Error Resume Next の最も大きな危険性はどれですか。
    ア. 処理速度が遅くなる　イ. エラーが起きても気づけず、間違った結果のまま処理が続いてしまう　ウ. コンパイルエラーも無視されてしまう

    回答を表示

    正解: イ
    エラーを「無かったこと」にするため、原因不明のおかしな結果につながります。使うなら必要な数行だけに限定し、直後に On Error GoTo 0 で解除しましょう。なお、コンパイルエラーは実行前に検出されるため、この設定では無視できません。

  3. Q3. 実行時エラー9「インデックスが有効範囲にありません」の典型的な原因はどれですか。
    ア. Set を書き忘れた　イ. 存在しないシート名を指定した、または配列の範囲外の添字を使った　ウ. 数値の変数に文字列を代入した

    回答を表示

    正解: イ
    アはエラー91、ウはエラー13の典型的な原因です。エラー番号と原因の対応を覚えておくと、原因究明の時間を大きく短縮できます。

この章のまとめ

  • エラーにはコンパイルエラー・実行時エラー・論理エラーの3種類があり、対処法が異なるため見分けることが第一歩である。
  • よく出るエラー番号（9・11・13・91・424・1004）と原因を対応付けて覚えておくと、原因究明が速くなる。
  • On Error GoTo はエラーを利用者に分かる言葉で伝え、後片付けをしてから終えるための仕組みである。ハンドラの直前には Exit Sub を置く。ただし12.6節のように後片付けを共通化したい場合は、あえて置かず If Err.Number <> 0 Then で分ける型もある。
  • On Error Resume Next は必要な数行だけに限定し、直後に On Error GoTo 0 で解除する。マクロ全体に掛けるのは危険。
  • ブレークポイント（F9）・ステップ実行（F8）・ローカルウィンドウ・ウォッチ式を使えば、論理エラーの原因も1つずつ追いかけられる。
  • 入口で前提条件を確認する、変更した設定は必ず戻す、想定外のエラーは利用者に伝える——この3原則がエラーに強いマクロの土台になる。

これでマクロを「動かして終わり」ではなく「安心して人に渡せる」ところまで仕上げる技術が身につきました。次の第13章では、InputBox や MsgBox の選択肢、簡単な入力フォームを使って、利用者とやり取りしながら動くマクロの作り方を学びます。エラー処理と組み合わせることで、誰が使っても迷わないツールに近づいていきます。
