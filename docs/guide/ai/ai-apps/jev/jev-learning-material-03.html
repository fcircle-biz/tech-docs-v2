ホーム Jev 第3章
第3章 所要時間: 約1時間

State — 判断の材料を設計する

第1章では、Jev への入力が State（判断の材料）と Question（判断してほしい内容）の2つに分かれることを確認しました。この章では、その一方である State を「どんな形で」「何を」渡すかを具体的に設計します。文字列・オブジェクト・配列の使い分けと、精度を大きく左右する「必要な情報だけを渡す」という原則を身につけましょう。

この章で学ぶこと

  • State が「Jev が判断する対象となる情報」であることを理解する
  • 文字列・JSON オブジェクト・配列を適切に使い分けられる
  • 名前付きフィールドを持つオブジェクトが推奨される理由を説明できる
  • 「Question の判断に必要な情報だけを渡す」原則を自分の State に適用できる

3.1 State とは

第1章の図で見たとおり、Jev へのリクエストは State と Question の2つを組み合わせて送ります。公式ドキュメントは State を「Jev に評価してほしい内容（the content you ask a System One model to evaluate）」と定義しています。サポートメッセージ、文章の一節、あるいはアプリケーションの現在の状態など、判断のもとになる情報はすべて State です。

1回のリクエストで評価されるのは、常に「1つの State」に対する「1つ以上の Question」です。同じ State を複数の Question がそれぞれ独立に参照し、並列に評価されます（Choice・Score・Noul を1つのリクエストに混在させることもできます）。Question 自体の設計は第4章・第8章で扱うので、本章では判断の「材料」である State の設計に集中します。

flowchart LR S["State
（判断の材料・1つ）"] --> Q1["Question 1"] S --> Q2["Question 2"] S --> Q3["Question 3"] Q1 --> A1["回答1"] Q2 --> A2["回答2"] Q3 --> A3["回答3"]

たとえ話: 専門家の前に置く資料

公式ドキュメントは State を「判断を下す前に専門家のパネルへ提示する資料」にたとえています。専門家が正しく判断するには、必要な資料が過不足なく揃っている必要があります。資料が少なすぎれば判断できず、関係のない資料が混ざっていれば気が散ります。State の設計とは、この資料をどう用意するかということです。

3.2 単純なケース: 文字列の State

最も単純な State は、ただのテキストです。渡したい情報が「1件のメッセージ」「1本の記事」「1段落の文章」のように、ひとまとまりのテキスト1つだけなら、それをそのまま文字列として渡します。

state（文字列）の例 
# 判断してほしい内容が1つのテキストだけなら文字列で渡す
state = "My card was charged twice."

公式ドキュメントは、文字列が適するケースを「ユースケースが単純で、テキストが1つだけで済む場合」と説明しています。名前を付けるべき項目が複数ない、つまり要素どうしの「関係」を表現する必要がないケースでは、文字列のままで十分です。

3.3 複雑なケース: JSON オブジェクトの State

渡したい情報が2つ以上になったら、JSON オブジェクトを使います。たとえば「問い合わせ本文」と「注文ID」の2つを渡したい場合、次のように名前付きフィールドとして渡します。

state（オブジェクト）の例 
{
  "message": "My card was charged twice.",
  "order_id": "A-104"
}

公式の指針: 多くの場合オブジェクトを使う

公式ドキュメントは「ほとんどのリクエストではオブジェクトを使う」と明言しています。理由は「State の各部分に説明的な名前が付き、要素どうしの関係が明確に保たれる」ためです。文字列を使ってよいのは、渡す情報が1つのテキストだけで済む単純なケースに限られます。

オブジェクトはネストできるため、比較が必要な複数の情報を1つの State にまとめることもできます。次の例は、会話・注文・返金ポリシーという性質の異なる3つの情報を1つの State に統合したものです。

state（会話＋注文＋ポリシーを1つに統合） 
{
  "ticket": {
    "subject": "Duplicate charge",
    "messages": [
      { "from": "customer", "text": "I was charged twice for order A-104." },
      { "from": "support", "text": "We are checking the charges." }
    ]
  },
  "order": { "id": "A-104", "charges": [49, 49] },
  "refund_policy": "Duplicate charges are eligible for a refund."
}

1つの State の中に会話・注文・ポリシーが含まれていますが、これは無関係な情報の寄せ集めではありません。「重複請求か、返金対象か」を判断するには、この3つを比較する必要があるため、あえて1つにまとめています。公式ドキュメントも「判断のために各部分を比較する必要があるときは、関連する情報を1か所にまとめる」と述べています。

3.4 関連する複数データ: 配列の State

同じ種類のデータが順序を持って並ぶ場合は、配列を使います。公式ドキュメントは配列を「メッセージやレコードの並び」に使うものと説明しています。たとえばチャットの発言を発言順に渡す場合です。

state（配列 / 発言の並び）の例 
[
  "Hi",
  "My customer number is TS1337.",
  "My card was charged twice."
]

レコードが並ぶ場合も同様です。たとえば同じ注文の請求履歴を時系列で渡したいときは、名前付きフィールドを持つオブジェクトの配列にします。

state（配列 / 請求レコードの並び）の例 
[
  { "date": "2026-08-01", "amount_usd": 49, "status": "captured" },
  { "date": "2026-09-01", "amount_usd": 49, "status": "captured" }
]

配列を選ぶ基準はシンプルです。「同じ形をしたデータが複数個、順序を保ったまま並んでいるか」で判断します。順序に意味がなく、項目ごとに役割が異なるなら、3.3 のオブジェクトを選びます。

使い分けの整理

ケース 推奨する形 理由
1件のメッセージ・記事など、単一のテキストだけを渡す 文字列 名前を付ける項目が1つしかない
名前付きの複数項目（本文＋注文IDなど）を渡す オブジェクト 各項目に説明的な名前が付き、関係が明確になる
会話・ログなど、同種の要素が順序を持って並ぶ 配列 順序を保ったまま複数のメッセージ／レコードを渡せる
比較が必要な複数の情報（会話＋注文＋ポリシーなど）をまとめる ネストしたオブジェクト 比較に必要な情報を1つの State に統合できる

3.5 必要な情報だけを渡す【最重要】

State を設計するときに最も陥りやすい失敗は、「念のため」多くの情報を詰め込みすぎることです。しかし公式ドキュメントは、State に無関係な情報が含まれるほど精度が落ちると明言しています。

無関係な情報は distractor になる

公式ドキュメントは、判断と関係のない情報で State が肥大化するほど精度が落ちると説明したうえで、「無関係な詳細情報は distractor（気を散らす要因）として働き、State が大きくなるほど、どの部分が誤答の原因かを特定するのも難しくなる」と述べています。対策は明確で、「コード側で先に絞り込み、Question が必要とするフィールドだけを送る」ことです。

次の例で比較してみましょう。目的は「返金要求か？」という1つの Noul 判定だけです。Before は、手元にあるデータをそのまま全部詰め込んだ State です。

Before: 無関係な情報が混ざった state 
{
  "customer_name": "佐藤花子",
  "customer_since": "2021-11-03",
  "loyalty_tier": "シルバー",
  "newsletter_subscribed": false,
  "device": "iPhone 15",
  "browser_language": "ja-JP",
  "message": "先月分と今月分、2回とも同じ金額が引き落とされています。",
  "order_id": "A-207"
}

customer_name・loyalty_tier・device などは、「返金要求かどうか」の判断には一切関係しません。むしろ Jev が読むべき情報を薄めてしまいます。After は、判断に必要な項目だけに絞り込んだ State です。

After: 判断に必要な項目だけに絞った state 
{
  "message": "先月分と今月分、2回とも同じ金額が引き落とされています。",
  "order_id": "A-207"
}

重要ポイント

State は「手元にあるデータをすべて渡す場所」ではありません。その Question の判断に必要な情報だけを渡す場所です。絞り込みは Jev に投げる前に、コード側で行います。データベースやアプリケーションの状態から関係するフィールドだけを取り出してから State を組み立てる、と覚えておきましょう。

3.6 サイズの上限

「必要な情報だけを渡す」という原則は、精度のためだけでなく技術的な上限のためでもあります。jev-1.13 のコンテキスト長には、公式ドキュメントに明記された上限があります。

64k

トークン / 1リクエスト全体の上限
（state ＋ すべての question の合計）

32k

トークン / state ＋ 最も長い question の上限

公式ドキュメントは「1リクエストあたり64kトークン、state と最も長い question を合わせて32kトークン」と明記しています。Jev は state を一度だけ取り込み、リクエスト内のすべての question をそれに対して並列に評価します。64k の枠は state とすべての question の合計に、32k の枠は state と単一の最長 question の組み合わせに適用されます。

上限に達したら「削る」のではなく「絞る」

大きなデータをそのまま State に詰め込んで上限に達した場合、単純に末尾を切り捨てるのではなく、3.5 で扱った考え方に立ち返りましょう。コード側で必要なフィールドだけをあらかじめフィルタしてから渡すのが公式の推奨です。上限ぎりぎりまで詰め込む設計は、精度の面でも得策ではありません。トークン数の上限値はモデルのバージョンごとに変わり得るため、実装時は必ず公式の Models ページで最新の値を確認してください。

やってみよう 3-1: 冗長な問い合わせデータから State を設計し直す

次のデータは、社内システムからそのまま取得した問い合わせレコードです。ここから「返金要求か？」を Noul で判定するために本当に必要な項目だけを選び、State を設計し直してみましょう。

生データ（社内システムの問い合わせレコード） 
{
  "customer_name": "鈴木一郎",
  "referral_source": "instagram広告",
  "cart_abandoned_count": 3,
  "os_version": "Android 14",
  "support_channel": "チャット",
  "message": "同じ注文が2回に分けて請求されているようです。",
  "order_id": "B-330",
  "last_purchase_category": "アウトドア用品"
}

手順

  1. 1 上のデータのうち、「返金要求か？」の判断に本当に必要なフィールドだけを書き出す。
  2. 2 除外した残りのフィールドについて、なぜ判断に不要なのかを1つずつ理由を添えて説明する。
  3. 3 選んだフィールドだけを使い、名前付きオブジェクトとして state を書き直す。

解答の目安

必要なのは message と order_id の2つだけです。customer_name・referral_source・cart_abandoned_count・os_version・support_channel・last_purchase_category は、いずれも「返金要求かどうか」とは無関係な distractor です。書き直した state は次の形になります。{"message": "同じ注文が2回に分けて請求されているようです。", "order_id": "B-330"}

理解度確認クイズ

  1. Q1. State とは何ですか。一言で説明してください。

    回答を表示

    Jev に評価してほしい内容（判断の材料）です。公式ドキュメントでは「the content you ask a System One model to evaluate」と定義されており、サポートメッセージ・文章・アプリケーションの状態などが該当します。

  2. Q2. 次の3つのケースに最も適した state の形式（文字列／オブジェクト／配列）をそれぞれ答えてください。(a) 1件のクレームメッセージだけを渡す　(b) メッセージ本文と注文IDの2項目を渡す　(c) チャットの発言を発言順に3件渡す

    回答を表示

    (a) 文字列（テキスト1つだけなので名前を付ける必要がない）。(b) オブジェクト（2つの項目に説明的な名前を付けて関係を明確にする）。(c) 配列（同種の発言が順序を持って並ぶ）。

  3. Q3. 名前付きフィールドを持つオブジェクトが「多くのケースで推奨される」理由を説明してください。

    回答を表示

    State の各部分に説明的な名前が付き、要素どうしの関係が明確に保たれるためです。文字列だけでは、複数の情報が混ざったときにどの部分が何を表すのか区別できません。

  4. Q4. State に判断と無関係な情報を含めるとどうなりますか。また、その対策と、jev-1.13 のコンテキスト長の上限（公式値）を答えてください。

    回答を表示

    無関係な情報はdistractorとして働き精度を落とし、State が大きくなるほど誤答の原因も特定しにくくなります。対策は、Question の判断に必要なフィールドだけをコード側で先に絞り込んでから渡すことです。コンテキスト長は1リクエストあたり64kトークン、state ＋ 最も長い question で32kトークンが公式の上限です。
