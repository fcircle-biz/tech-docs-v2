ProbabilityとConfidence

Choice と Score の回答には、判断結果と一緒に probabilities（確率分布）と confidence（確信度）が返ってきます。この章では、この2つが別の情報であることを理解し、confidence を使って「自動処理してよい判断」と「人間に回すべき判断」を切り分ける設計を学びます。

この章で学ぶこと

  • probabilities と confidence の違いを説明できる
  • confidence が確率分布の「形」から導かれることを理解する
  • 閾値によって自動処理・確認・人間レビューを振り分ける設計ができる
  • 操作の重大さに応じて閾値を変える判断ができる

9.1 Jev が返す不確実性

第1章で見た Jev のレスポンス例をもう一度思い出してください。department という Choice の回答には、choice（選んだ結果）だけでなく、confidence と probabilities という2つの値が一緒に含まれていました。この章では、この2つがそれぞれ何を表す別の情報なのかを正確に理解します。

一言で言うと、probabilities は「何と判断したか」の内訳そのもの、confidence は「どれくらい確かか」を1つの数値に圧縮したものです。第8章では複合的な依頼を Atomic Question へ分解し、コードが最終判断を組み立てる責務分担を学びました。その組み立てを安全に行うには、Jev から返る個々の判断が「信頼できる判断」なのか「怪しい判断」なのかをコードが見分けられる必要があります。confidence はまさにそのための情報です。

probabilities

選択肢（Choice）やレベル（Score）ごとの確率分布そのもの。「technical に 0.90、billing に 0.06…」という内訳。

confidence

その内訳が「1つに偏っているか、バラけているか」という形を表す、0〜1の1つの数値。

次の9.2ではまず probabilities そのものを見て、9.3でそこから confidence がどう計算されるかを確認します。

9.2 probabilities

probabilities は、Choice では用意した選択肢ごとに、Score ではルーブリックの段階（レベル）ごとに、Jev がどれくらいの確率を割り当てたかを示す分布です。すべての値を合計すると、おおよそ 1.0 になります。

同じ「どの部署が担当すべきか」という Question（第1章の例）でも、問い合わせの内容によって分布の形はまったく異なります。次の2つを見比べてください。confidence は次の9.3で計算するので、ここでは probabilities の内訳だけに注目してください。

ケースA: 内容がはっきりしている問い合わせ（「ログインできない」など、技術的な内容だと一目で分かる）

probabilities が1つに集中している例 
{
  "type": "choice",
  "choice": "technical",
  "probabilities": {
    "technical": 0.90,
    "billing": 0.06,
    "sales": 0.04
  }
}

ケースB: 内容が曖昧な問い合わせ（「先月の件、まだ直ってませんよね」のように、技術・請求どちらとも取れる）

probabilities が割れている例 
{
  "type": "choice",
  "choice": "technical",
  "probabilities": {
    "technical": 0.34,
    "billing": 0.33,
    "sales": 0.33
  }
}

どちらも choice は "technical" です。しかしケースAは「ほぼ technical で決まり」、ケースBは「かろうじて technical が僅差で勝った」という、まったく違う状況を表しています。choice だけを見ていると、この違いは分かりません。

補足: Score の probabilities

Score でも考え方は同じです。「緊急度: 低・中・高」のようなレベルごとに確率が割り当てられ、その分布が1つのレベルに集中していれば confidence は高く、複数のレベルにまたがっていれば低くなります。

9.3 confidence

公式ドキュメントは confidence を、probabilities の形から導かれる1つの統計量だと説明しています。確率がすべて1つの選択肢に集中していれば confidence は 1.0 に近づき、均等にバラけているほど低くなります。

confidence は TypeSafe 側が probabilities から算出して返す値です。アプリケーションが自分で計算する必要はありません。

flowchart LR P["probabilities
（各選択肢・各段階の確率）"] --> C["TypeSafe 側で統計量を算出"] C --> R["confidence
（0.0〜1.0）"]

公式ドキュメントが保証しているのは、0.0〜1.0 の値であること、分布が1つに集中するほど高く、平坦になるほど低いこと、そして利用者が計算しなくてよいことまでです。どの統計量を使うかは実装の詳細として扱われており、具体的な計算式は API の契約として公開されていません。したがって、アプリ側で式を再実装せず、レスポンスとして返ってきた confidence をそのまま使ってください。

9.2で見た2つの例では、confidence は次のような値になります。

例 probabilities の形 confidence（レスポンス値）
ケースA（集中） 1つの選択肢に 0.90 が集中 0.85（高い）
ケースB（割れている） 3択にほぼ均等（0.34 / 0.33 / 0.33） 0.01（ほぼ 0）

確率が完全に均等に割れた場合、confidence は 0.0 に近づきます。ケースBはそれに近い「ほぼ五分五分」の状態だと分かります。一方ケースAの 0.85 は「ほぼ確信している」状態です。choice の文字列だけでは見分けられなかった違いが、confidence という1つの数値に表れます。重要なのは、confidence を「自分で計算する値」ではなく「レスポンスから読み取って閾値と比べる値」として扱うことです。内部の算出方法はモデルの更新とともに変わりうるため、式を前提にした実装は避けます。

注意: confidence は万能な指標ではない

公式ドキュメントは、confidence が probabilities の形から機械的に導かれる便宜的な指標であり、見ている対象によっては別の指標のほうが適している場合があると明言しています。だからこそ Jev は confidence だけでなく、計算の元になった probabilities 全体も一緒に返します。例えば「1位と2位の差だけを見たい」「特定の選択肢の確率だけを見たい」といった用途では、probabilities から自分で必要な統計量を計算したほうがよい場合があります。

9.4 Noul の場合

ここまでの confidence は、Score と Choice の回答にだけ含まれます。Noul の回答には confidence フィールドは含まれません。理由は単純で、Noul はもともと「選択肢」を持たない Primitive だからです。probabilities のような内訳を圧縮する対象がそもそも存在しません。

その代わり、Noul には別の手がかりがあります。noul の値そのものが「真である確率」であり、0.5 は「真か偽か、五分五分で判断がつかない」ことを表します。つまり 0.5 からどれだけ離れているかが、そのままその判断の確からしさの目安になります。

2つの Noul 回答の比較 
{
  "is_urgent": {
    "type": "noul",
    "noul": 0.52
  },
  "is_refund_request": {
    "type": "noul",
    "noul": 0.97
  }
}

is_urgent の 0.52 は 0.5 のすぐ近くにあり、「緊急かどうか、Jev もほぼ判断がついていない」状態です。一方 is_refund_request の 0.97 は 0.5 から大きく離れており、「返金要求である、とかなり確信している」状態だと読み取れます。

これは公式フィールドではなく自分で作る目安

「0.5 からの距離」は Jev が返す公式のフィールドではありません。9.3で見た「用途によっては自分で統計量を計算したほうがよい」という注意を、confidence を持たない Noul にそのまま当てはめた考え方です。例えば abs(noul - 0.5) * 2 のように計算すれば、0（五分五分）〜1（確信）の目安として自分のコードで扱えます。

9.5 閾値で振り分ける

confidence が数値として手に入れば、その値を閾値で区切って処理を振り分けられます。公式ドキュメントが示す基本パターンは3段階です。高い confidence は「モデルの判断がはっきりしているので自動処理してよい」、中程度は「念のため確認をはさんで進める」、低い confidence は「判断させず人間のレビューへ回す」という構えです。

route.py 
# confidence の値で処理を3段階に振り分ける
def route_by_confidence(answer: dict) -> str:
    confidence = answer["confidence"]
    if confidence >= 0.8:
        return "auto"       # 自動処理してよい
    elif confidence >= 0.5:
        return "confirm"    # 確認をはさんで進める
    else:
        return "human"      # 人間のレビューへ回す

図にすると、次のような分岐になります。

flowchart TD A["Choice／Scoreの回答"] --> B{"confidenceの水準"} B -->|"高い（0.8以上）"| C["自動処理"] B -->|"中程度（0.5〜0.8）"| D["確認をはさんで進める"] B -->|"低い（0.5未満）"| E["人間のレビューへ"]

ここで使った 0.8 や 0.5 という数値はあくまで説明用の例です。公式ドキュメントも「正しい閾値は自分のドメインとモデルの精度次第であり、まずは保守的な値から始め、自分のデータで試しながら調整すべきだ」と述べています。この3段階の振り分けは、正式には第12章で学ぶ Confidence-Gated Routing というデザインパターンの基礎になります。

9.6 操作の重大さで閾値を変える

公式ドキュメントが強調しているもう1つの重要な指針があります。confidence の閾値は1つの数値ではないということです。同じシステム、同じアプリケーションの中であっても、操作ごとに「間違えたときの影響の大きさ」が違うのであれば、操作ごとに別の水準でゲート（関門）を設けるべきだとされています。

公式の例では、残高を表示するだけの低リスクな操作は間違えても画面を出し直せば済むため緩めの基準でよい一方、送金を承認するような高リスクな操作は confidence が 0.9 を超える場合に限って進め、それ以外は先に人間の確認を挟む、という設計が示されています。

操作の例 間違えたときの影響 閾値の目安
FAQへの自動回答 小さい（言い直せる） 低め（例: 0.5前後）
担当部署への自動振り分け 中程度（転送すれば直せる） 中程度（例: 0.7〜0.8）
返金・送金の自動実行 大きい（金銭が動き取り消しにくい） 高め（例: 0.9以上）

表の下に行くほど「取り返しがつかない」操作になり、要求する confidence も高くなります。同じ 0.75 という confidence でも、FAQ の自動回答なら自動処理してよい値かもしれませんが、送金の自動実行にとっては全く足りない値かもしれません。閾値は confidence の値だけでなく、その先にある操作のリスクとセットで決めるものだと考えてください。

重要ポイント

Confidence は、AI に何でも判断させるための道具ではありません。むしろ「今回は判断しない」という選択肢を設計に組み込むための道具です。閾値を下回った判断を自動処理せず人間へ回すという仕組みそのものが、AIの限界を前提にしたシステム設計の一部になります。

やってみよう 9-1: 操作ごとに confidence 閾値を決める

次の3つの操作それぞれについて、「自動処理してよい confidence の閾値」を自分で決め、その理由を説明してみましょう。正解が1つに決まる問題ではなく、9.6の考え方を自分の言葉で使えるかを確認する演習です。

手順

  1. 1 次の3つの操作について、それぞれ「間違えたときに何が起きるか」を書き出す。
    (a) FAQ の自動回答　(b) 担当部署への自動振り分け　(c) 返金の自動実行
  2. 2 書き出した影響の大きさをもとに、(a)〜(c) それぞれに 0〜1 の confidence 閾値を1つずつ割り当てる。
  3. 3 3つの閾値の大小関係が、なぜその順番になるのかを「取り返しがつくか／つかないか」という言葉で説明してみる。

解答の目安

(a) FAQ の自動回答は閾値 0.5〜0.6 程度でよい。誤っても利用者が読んで違うと気づける程度の影響で、取り返しがつく。(b) 担当部署への振り分けは 0.7〜0.8 程度。誤ると対応が遅れるが、後から転送すれば直せる。(c) 返金の自動実行は 0.9 以上。実際にお金が動いてしまい、取り消しや回収が難しいため、confidence が非常に高い場合だけ自動化し、それ以外は人間の確認を挟むべき。閾値の大小関係は「間違えたときに取り返しがつくかどうか」の順に並ぶ。

理解度確認クイズ

  1. Q1. probabilities と confidence の違いを説明してください。

    回答を表示

    probabilities は選択肢（またはレベル）ごとの確率分布そのものです。confidence は、その分布が「1つに集中しているか、バラけているか」という形を1つの数値（0〜1）に圧縮したものです。分布が1つの選択肢に集中していれば confidence は1.0に近づき、均等にバラけているほど低くなります。

  2. Q2. 3つの選択肢の確率分布が [0.90, 0.06, 0.04] のときと [0.34, 0.33, 0.33] のときでは、confidence はどちらが高くなりますか。また、その値をアプリ側で計算してよいでしょうか。

    回答を表示

    [0.90, 0.06, 0.04] のほうが高くなります。確率が1つの選択肢に強く集中しているためです。逆に [0.34, 0.33, 0.33] はほぼ均等なので confidence は 0.0 に近づきます。なお、confidence は TypeSafe 側が probabilities から算出して返す値であり、計算式は API の契約として公開されていません。アプリ側で式を再実装せず、レスポンスの confidence を読み取って使ってください（1位と2位の差など独自の指標が必要な場合は、返ってきた probabilities から自分で計算します）。

  3. Q3. Noul の回答には confidence フィールドが含まれますか。含まれない場合、確からしさをどう見積もればよいですか。

    回答を表示

    含まれません。Score と Choice の回答にだけ confidence が付き、Noul にはありません。代わりに noul の値そのものが真である確率なので、0.5 からの距離を確からしさの目安として自分で計算できます（0.5 に近いほど五分五分、0か1に近いほど確信している）。

  4. Q4. なぜ「同じシステムの中でも操作によって confidence の閾値を変えるべき」なのですか。

    回答を表示

    操作ごとに「間違えたときの影響の大きさ」が異なるからです。誤っても取り返しがつく操作（表示のやり直しなど）は緩い閾値でよい一方、送金や返金のように取り返しがつかない操作は、誤りのコストが大きいため高い閾値（例: 0.9以上）を要求し、それ以外は人間の確認を挟むべきです。
