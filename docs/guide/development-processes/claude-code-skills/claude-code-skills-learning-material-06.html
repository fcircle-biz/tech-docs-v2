メタデータと allowed-tools

前章では description の書き方を掘り下げました。この章では視野を広げ、SKILL.md の frontmatter が持つ4つのフィールドを整理します。中心となるのは allowed-tools ——スキルが有効なあいだ Claude が使えるツールを制限する、ガードレールの仕組みです。

この章で学ぶこと

  • SKILL.md の frontmatter が持つ4つのフィールド（必須2つ・任意2つ）を説明できる
  • name と description の制約（文字種・文字数）を理解する
  • allowed-tools でツールアクセスを制限する書き方と挙動を理解する
  • allowed-tools を省略した場合の挙動（通常の権限モデル）との違いを説明できる
  • model フィールドでタスクの複雑さに応じたモデル選択ができることを知る

6.1 frontmatter の4つのフィールド

第1章で見たように、SKILL.md は --- で区切られた frontmatter と指示本文から成り立っています。agent skills open standard は、この frontmatter でいくつかのフィールドをサポートしており、うち2つが必須、残りは任意です。

フィールド 必須/任意 意味 制約
name 必須 スキルを識別する名前 小文字・数字・ハイフンのみ。最大64文字。ディレクトリ名と一致させるべき
description 必須 いつこのスキルを使うべきかを Claude に伝える 最大1,024文字。Claude がマッチングに使う最も重要なフィールド（第5章参照）
allowed-tools 任意 スキルが有効なとき Claude が使えるツールを制限する ツール名をカンマ区切りで列挙。省略時は制限なし
model 任意 そのスキルに使用する Claude のモデルを指定する 省略時はそのときの会話で使われているモデルを使用

基本的なスキルは name と description だけでも動作します。ここから先の2つ（allowed-tools・model）は、スキルをさらに実用的にする高度なオプションです。この章では、特に allowed-tools を中心に見ていきます。

6.2 allowed-tools によるツールの制限

「ファイルの読み取りだけを許可し、変更はさせたくない」——こうした要求を持つスキルが欲しくなる場面があります。allowed-tools はまさにこのためのフィールドです。セキュリティ上配慮が必要なワークフロー、読み取り専用のタスク、あるいはガードレールを設けたいあらゆる状況で役立ちます。

次の例を見てみましょう。新しく参加した開発者がコードベースを理解する手助けをする、読み取り専用のスキルです。

.claude/skills/codebase-onboarding/SKILL.md 
---
name: codebase-onboarding
description: Helps new developers understand how the system works.
allowed-tools: Read, Grep, Glob, Bash
model: sonnet
---

このスキルが有効なとき、Claude は許可を求めることなく Read・Grep・Glob・Bash だけを使用できます。編集も書き込みもできません。コードベースの案内役として、うっかりファイルを書き換えてしまう心配なく安心して使えるスキルになります。

用語: ガードレール（guardrail）とは

本来の意図から外れた操作（意図しないファイル変更など）が起きないよう、あらかじめできることの範囲を狭めておく仕組みのことです。allowed-tools は、スキル単位でこのガードレールを設定する手段だといえます。

6.3 「制限あり」と「省略時」の挙動の違い

allowed-tools を省略した場合、そのスキルは何も制限しません。Claude は通常の権限モデルを使用し、必要に応じて編集や書き込みの許可を求めながら作業を進めます。両者の違いを図で整理します。

flowchart TD A["スキルが有効化される"] --> B{"allowed-tools が設定されているか"} B -->|設定あり| C["列挙されたツールだけ使用可能"] C --> D["許可を求めずに実行（Read・Grep等）"] C --> E["範囲外のツールは使用不可（Edit・Write等）"] B -->|省略| F["制限なし＝通常の権限モデル"] F --> G["必要に応じて都度、許可を確認しながら実行"]
状態 使えるツール 向いている場面
allowed-tools あり 列挙したツールのみ（許可確認なしで使用可能） 読み取り専用の調査、セキュリティ上配慮が必要な作業、ガードレールが欲しい場面
allowed-tools 省略 通常の権限モデルに従いすべて（都度確認あり） 編集・実行を含む一般的な作業スキル

重要ポイント

allowed-tools は「使ってよいツールの許可リスト」です。ここに書かれていないツールは、そのスキルが有効なあいだそもそも選択肢に上がりません。書かれているツールについては、通常であれば発生する許可確認もスキップされます。

6.4 model フィールドの使いどころ

model フィールドは、そのスキルが有効なときに使用する Claude のモデルを指定します。省略した場合は、そのときの会話で使われているモデルがそのまま使われます。

ヒント: モデルの使い分け

定型的で判断の余地が少ない作業（ファイル名の照合、フォーマットの整形など）には軽量なモデルを、複雑な判断や設計が必要な作業（アーキテクチャ検討、コードレビューの妥当性判断など）には高性能なモデルを割り当てると、スキルごとに速度とコストのバランスを最適化できます。先ほどの codebase-onboarding の例では model: sonnet が指定されていました。

allowed-tools と model はどちらも任意のフィールドですが、組み合わせることで「このスキルは、このモデルで、この範囲のツールだけを使って動く」という安全かつ予測可能な振る舞いを設計できます。

注意: 制限をかけすぎると目的を果たせなくなる

allowed-tools を厳しく絞りすぎると、スキル本来の作業ができなくなってしまいます。たとえば調査の途中でメモを残したいスキルから Write を外してしまえば、そのステップだけ実行できずに止まってしまいます。allowed-tools を設定する前に、そのスキルが実際に必要とするツールを洗い出してから絞り込みましょう。迷ったときは、まず制限なしで動かしてみて、実際に使われたツールを確認してから制限をかける方法も有効です。

やってみよう 6-1: 読み取り専用スキルを作り、制限を確認する

allowed-tools の効果を実際に体験してみましょう。今回は、コードベースの案内役となる読み取り専用スキルを作ります。

手順

  1. 1 mkdir -p ~/.claude/skills/codebase-onboarding でディレクトリを作成する。
  2. 2 SKILL.md を作成し、本章の例と同じ frontmatter（name・description・allowed-tools: Read, Grep, Glob, Bash・model: sonnet）を書く。本文には「プロジェクトの構成をファイル一覧と主要ファイルの中身から説明する」旨の指示を書く。
  3. 3 Claude Code を再起動し、「このプロジェクトの構成を説明して」のように、スキルがトリガーされる依頼をする。
  4. 4 続けて「READMEに一言書き足して」のようにファイル変更を伴う依頼をしてみて、Edit や Write が使われず、書き込みが行われないことを確認する。

ヒント: 期待どおりに書き込みがブロックされたら、今度は allowed-tools の行を丸ごと削除して同じ依頼をしてみましょう。省略時は通常の権限モデルに戻り、許可を確認したうえで書き込みが行われることを比較できます。

理解度確認クイズ

  1. Q1. SKILL.md の frontmatter が持つ4つのフィールドのうち、必須なのはどれですか？

    回答を表示

    name（小文字・数字・ハイフンのみ、最大64文字）と description（最大1,024文字）の2つが必須です。allowed-tools と model は任意のフィールドです。

  2. Q2. allowed-tools: Read, Grep, Glob, Bash と設定したスキルが有効なとき、Claude は何ができますか？

    回答を表示

    Read・Grep・Glob・Bash の4つを、許可を求めることなく使用できます。ただしこれら以外のツール（Edit・Write など）は使えないため、ファイルの編集や書き込みはできません。

  3. Q3. allowed-tools を省略すると、そのスキルはどのような挙動になりますか？

    回答を表示

    何も制限されません。Claude は通常の権限モデルを使用し、必要に応じて許可を確認しながら、あらゆるツールを使って作業を進めます。

  4. Q4. allowed-tools を設定するときに注意すべき点は何ですか？

    回答を表示

    制限を厳しくしすぎると、スキルが本来の作業を完了できなくなってしまいます。設定する前に、そのスキルが実際に必要とするツールを洗い出しておくことが重要です。
