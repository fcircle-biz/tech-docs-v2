第6章 所要時間: 約50分

実装とコミット（Code・Commit）

第5章で立てたプランを、いよいよ実装に移す番です。この章では、承認されたプランをどう実行させるか、実装を成功させるための3つのコツ、そしてコミット前に押さえておきたいレビューの手順まで、Explore→Plan→Code→Commit ワークフローの後半（Code・Commit）を扱います。章末では4つのフェーズ全体を1枚の表に整理します。

この章で学ぶこと

  • プラン承認後、実装フェーズがどのように進むかを理解する
  • 自動承認と都度確認、それぞれの使いどころを判断できる
  • 実装を成功させる3つのコツ（成功基準・ツール追加・テストスイート）を説明できる
  • コミット前にサブエージェントでコードレビューする意義を理解する
  • Explore→Plan→Code→Commit の4フェーズ全体を、自分の言葉で振り返られる

6.1 プランが承認されたら：実装フェーズのはじまり

第5章では、「このコースから一つだけ持ち帰るとしたら、このワークフローにしてください」と紹介された Explore→Plan→Code→Commit ワークフローのうち、前半にあたる探索（Explore）と計画（Plan）を学びました。プランモードで、たとえば次のようなプロンプトからプランを立てさせた場面を思い出してください。

画像アップロードのパイプラインにWebP変換を追加したいです。パイプラインのどこで行うべきか、新しい依存関係が必要かどうか、どうアプローチすべきかを整理してください。

Claude が提示したプランの内容に問題がなければ、「approve（承認）」を選びます。ここから、この章のテーマである実装（Code）フェーズが始まります。

承認すると、Claude はプランに沿ってリストの項目を一つずつ進めていきます。このとき、ファイルの編集を自動的に承認させるか、それとも毎回自分の目で確認するかを選べます。この選択は、第4章で学んだ許可モードの延長線上にあるものです。慣れないうちや影響範囲が大きい変更は都度確認、勝手のわかった軽微な変更は自動承認というように、状況に応じて使い分けるとよいでしょう。

また、Claude はある作業を「完了」とみなす前に、できる限り自分自身でトラブルシューティングを行います。テストを実行して失敗すれば原因を調べ、コードを修正して再実行する——という具合です。ただし、それでも解決しない場合や、プロジェクト固有の知識・意思決定が必要な場面では、あなたの手を借りる必要が出てきます。「そこまで含めて全自動」とは考えず、要所では手を止めて確認する姿勢が大切です。

6.2 プランモードのもう一つの効能：文脈が実装まで生き続ける

プランモードには、安全に計画を立てられるという主目的のほかに、見落とされがちな利点があります。それは、実装が始まったあとも「なぜこの設計を選んだのか」「どのような情報をもとにこのプランに至ったのか」という文脈が、そのままセッションの中に残り続けることです。

この文脈は、実装中に Claude が判断に迷ったときの助けになります。たとえば実装の途中で別の実装方法との比較が必要になった場面でも、Claude は探索フェーズで集めた情報（既存コードの構造や依存関係など）を踏まえて判断できます。プランを立てずにいきなりコードを書かせた場合は、こうした背景情報がその場になく、行き当たりばったりの判断になりがちです。

先取り: コンテキストという背骨

「文脈が残り続けることで判断の助けになる」という考え方は、第7章で学ぶコンテキスト管理そのものです。探索や計画で集めた情報も、コンテキストウィンドウという有限の記憶領域を消費しています。この関係は、本ガイドの後半（第7・8・9・11章）で繰り返し登場します。

6.3 実装を成功させる3つのコツ

実装フェーズをスムーズに進め、手戻りを減らすために、原典で紹介されている3つのコツを見ていきましょう。いずれも「Claude に何をどう任せるか」を事前に設計しておく視点です。

1

成功基準を明確にする

Claude が自分の成果に自信を持てるようにするには、「正しい」とはどのような状態かを、あらかじめ明確にしておく必要があります。これはプランを書く段階（第5章）で明示的に言語化しておくのが効果的です。基準が曖昧だと、Claude は「とりあえず動いた」ところで完了と判断してしまい、あなたの期待とズレた結果になりやすくなります。

成功基準の書き方: 曖昧な例 → 明確な例

  • △ 曖昧：「アップロード機能をちゃんと動くようにする」
  • ◎ 明確：「JPEG/PNG画像をアップロードすると自動でWebPに変換され、元ファイルより30%以上ファイルサイズが小さくなること。既存のテスト（npm test）がすべて成功すること」
2

ツールを追加する

Claude が目標を達成する助けになるツールがあると、あなたとのやり取りの往復が大幅に減ります。第2章で学んだとおり、エージェントは「LLM＋ツール＋ループ」で成り立っています。使えるツールが増えるほど、Claude が自力で確認・検証できる範囲が広がるのです。

たとえば Web UI を構築しているなら、Claude in Chrome 拡張機能をインストールしておくと、Claude Code がブラウザタブを直接操作して実装した画面を開き、実際の見た目や動作を確認できるようになります。「ボタンを押したら期待どおりの表示になっているか」を、あなたが毎回スクリーンショットを撮って渡さなくても、Claude 自身が検証できるようになるわけです。

この発想は、外部ツールと接続する仕組みである MCP（第11章）にも通じます。「Claude に何をさせたいか」だけでなく「Claude に何を見せられるか」を増やすことが、実装フェーズの精度を底上げします。

3

テストスイートを用意する

Claude が自分の変更を継続的に検証できるように、テストスイートを渡しましょう。テストが無いプロジェクトであれば、テスト自体を Claude に書いてもらうことも可能です。動かしてみて失敗すれば、Claude はそこから自分で原因を調べ、修正できます。

ただし渡す前に一つ確認してください。そのテストは、誤検知（false positive）を招かない、信頼できる判断材料になっているかという点です（詳しくは次の注意ボックスで説明します）。

注意: テストの「誤検知（false positive）」に気をつける

Claude はテストが通れば「成功した」と判断します。しかし、そのテストの中身が信頼できるとは限りません。たとえば、例外を握りつぶして常に成功したことにしてしまうテストや、アサーション（検証条件）が緩すぎて何を変更してもパスしてしまうテストがあると、Claude は実際にはバグが残っているのに「完了しました」と報告してしまいます。Claude にテストを書かせた場合はもちろん、既存のテストスイートを渡す場合も、ざっと中身に目を通し、本当に確認したいことを確認できているかを人の目でチェックしておきましょう。

6.4 ちょっとしたコツ：同じ指摘を繰り返しているなら CLAUDE.md へ

実装フェーズを何度も繰り返していると、あるパターンに気づくことがあります。同じような指摘を、何度も Claude に伝え直している——という状況です。原典はここで、シンプルながら効果の大きいコツを紹介しています。

ちょっとしたコツ: 繰り返す指摘は CLAUDE.md に保存する

Claude が何度も同じ問題にぶつかっている、あるいはあなたが何度も同じ修正指示を出している場合は、その解決策を CLAUDE.md ファイルに保存するよう、Claude 自身に依頼してみましょう。次回のセッション以降、Claude は同じ間違いを繰り返しにくくなります。

CLAUDE.md はプロジェクトのルートに置く Markdown ファイルで、セッションが始まるたびに自動的に読み込まれる「プロジェクトの記憶」です。書き方・育て方は第8章でじっくり扱います。

6.5 コミットフェーズ：レビューしてから手放す

自分でも変更内容を実際に動かしてテストし、結果に納得できたら、いよいよコードをプッシュする番です。ただし、その前に欠かせないステップがあります。サブエージェントのコードレビュアーに、自分の作業を確認してもらうことです。

サブエージェントは、そのセッション中にメインエージェントが持ってしまっているかもしれない先入観を引きずらない、まっさらな視点でコードベースを確認してくれます。

メインエージェント——ここまでの会話を続けてきた Claude——は、実装を進める過程で「こう作ったはずだ」「ここは大丈夫だろう」という思い込みを少なからず抱えています。人間が自分で書いたコードのバグに気づきにくいのと同じ理由です。独立したコンテキストウィンドウで動くサブエージェントは、そうした思い込みを一切引き継がず、コードそのものだけを見て評価してくれます。だからこそ、自分自身での確認とは別に意味のあるレビューになるのです。

先取り: サブエージェントとコードレビュー

「独立したコンテキストウィンドウを持つサブエージェント」という仕組み自体は第9章で、コードレビュー専用のサブエージェントを実際に作成し、Git・GitHub と連携させる具体的な手順は第10章で扱います。ここでは「コミット前に、まっさらな視点でレビューさせる」という考え方をまず覚えておいてください。

レビューで指摘があれば実装フェーズに戻って直し、問題がなければ、あなたのスタイルに合わせたコミットメッセージを Claude に生成してもらいます。これを1サイクルとして繰り返していく——というのが、Explore→Plan→Code→Commit の全体像です。

6.1節の例（画像アップロードパイプラインへのWebP変換追加）の続きを見てみましょう。

terminal — コミット前のレビュー例 
> 実装が終わりました。コミット前にcode-reviewerサブエージェントで確認してください。

● code-reviewerサブエージェントを起動しています（独立したコンテキスト）…
● git diff で変更差分を確認しています…
● 指摘: WebP変換に失敗した場合のエラーハンドリングが1箇所抜けています。
● src/pipeline/webp.ts を修正しました。再度レビューし、問題なしを確認。
● コミットメッセージ案:
  "feat: 画像アップロードパイプラインにWebP変換を追加"
> 承認します。コミットしてください。
● コミットが完了しました。

6.6 4フェーズのまとめ：Explore・Plan・Code・Commit

ここまで2つの章にわたって、Explore→Plan→Code→Commit という4つのフェーズを見てきました。最後に、全体を1枚の表に整理しておきましょう。

フェーズ 目的 主な操作 学ぶ章
Explore（探索） プロジェクトに関する必要な文脈をClaudeに与える プランモードで関連ファイルを読み込ませる・Web検索させる 第5章
Plan（計画） Claudeが成功を判断する基準となる行動計画を作成する プランを提示させ、承認／特定箇所の修正／質問のいずれかを選ぶ 第5章
Code（実装） 最終的な成果に落ち着くまでの、あなたとClaudeとのやり取り approveで実行開始・自動承認/都度確認を選択・成功基準やツール、テストで精度を高める 第6章（本章）
Commit（コミット） コードをレビューしてプッシュし、次の機能に取りかかれるようにする サブエージェントでレビュー・自分のスタイルに合わせたコミットメッセージを生成 第6章（本章）

この4フェーズは一直線に終わるものではありません。コミットが終わったら、また次の機能のExploreへ戻るという循環です。

（第5章）"] --> B["Plan 計画
（第5章）"] B --> C["Code 実装
（第6章）"] C --> D["Commit コミット
（第6章）"] D -->|次の機能へ| A

重要ポイント

Claude Code を効果的に使う一番の近道は、いきなりコードを書かせないことです。探索して文脈を与え、計画で成功基準を決め、実装のあいだは要所で確認し、コミット前にまっさらな視点でレビューする——この4フェーズを回す習慣が、本ガイド全体の土台になります。

やってみよう 6-1: 成功基準を書いてから実装させ、コミットまで通してみる

自分のプロジェクトで見つけた小さな改善点を1つ選び、Explore→Plan→Code→Commit の後半（Code・Commit）を実際に体験してみましょう。

手順

  1. 1 直近で見つけた小さな改善点を1つ選ぶ（例: ボタンのラベル修正、簡単な入力チェックの追加など）。
  2. 2 実装を依頼する前に、「正しい」とはどんな状態かを1〜2文で書き出す（6.3節の成功基準）。
  3. 3 プランモードで簡単なプランを立てさせ、approveしたあとは承認モード（都度確認）で各ステップを見届ける。
  4. 4 実装が終わったら、コミット前に「変更内容をレビューしてください」と依頼し、指摘があれば直してもらう。
  5. 5 「自分のスタイルに合わせたコミットメッセージを提案してください」と依頼し、内容を確認してからコミットする。

理解度確認クイズ

  1. Q1. 実装フェーズで、プランの項目を進める際にファイルの編集について選べる2つのやり方は何ですか？

    回答を表示

    自動承認（ファイルの編集をClaudeに自動的に承認させる）と、都度確認（毎回自分の目で確認する）の2つです。慣れないうちや影響範囲が大きい変更は都度確認、勝手のわかった軽微な変更は自動承認というように使い分けます。

  2. Q2. Claudeにテストスイートを渡す・書かせる際に、特に注意すべき点は何ですか？

    回答を表示

    そのテストが誤検知（false positive）を招かない、信頼できる判断材料になっているかを確認することです。アサーションが緩すぎるテストや例外を握りつぶすテストがあると、Claudeはバグが残っていても「完了した」と誤って報告してしまいます。

  3. Q3. コミット前にサブエージェントのコードレビュアーに確認してもらう最大の利点は何ですか？

    回答を表示

    サブエージェントは独立したコンテキストウィンドウで動作するため、メインエージェントがそのセッション中に持ってしまっているかもしれない先入観を引きずらない、まっさらな視点でコードベースを確認できる点です。
