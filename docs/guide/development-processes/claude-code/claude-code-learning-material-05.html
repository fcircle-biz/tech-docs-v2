第5章 所要時間: 約50分

探索と計画（Explore・Plan）

Claude Code をもっとも効果的に使うための中心となる考え方が、探索（Explore）→計画（Plan）→実装（Code）→コミット（Commit）のワークフローです。原典では「このコースから一つだけ持ち帰るとしたら、このワークフローにしてください」と明言されるほど重視されています。本章ではその前半にあたる探索と計画に絞り込み、いきなりコードを書かせないことがなぜ結果的に一番の近道になるのかを学びます。

この章で学ぶこと

  • Explore→Plan→Code→Commitワークフローの全体像と、各フェーズの役割を説明できる
  • なぜこのワークフローが「一つだけ持ち帰るべきもの」と言われるほど重要なのかを理解する
  • プランモードを使って、実装前に文脈収集と計画立案を行う手順を実践できる
  • プラン提示時の3つの選択肢（承認／特定箇所の修正／質問）を状況に応じて使い分けられる
  • 変更せずコードベースの概要だけを知りたいときに使える手段を知る

5.1 このワークフローが最重要である理由

第4章までで、Claude Codeの起動・許可モードの切り替え・最初のプロンプトの送り方を身につけました。ここからは、原典がもっとも重みを置いて紹介している考え方に入ります。

このコースから一つだけ持ち帰るとしたら、このワークフローにしてください。探索（Explore）、計画（Plan）、実装（Code）、コミット（Commit）です。

なぜここまで強調されるのでしょうか。原典はその理由をこう説明しています。このワークフローを使わないと、多くの人はいきなりClaudeにコードを書かせてしまい、結果として後から軌道修正が多く必要になるのです。一見すると、要件を伝えてすぐに実装させたほうが早く感じられます。しかし、Claudeが前提を勘違いしたまま実装を進めてしまうと、あとから気づいたときにはコードの差分を読み解き、テストをやり直し、Claudeの意図を推測しながら手直しするという、かえって重い作業が発生します。

たとえるなら、設計図を描かずにいきなり家を建て始めるようなものです。骨組みが立ち上がってから間取りの間違いに気づけば、壊して建て直すコストは膨大になります。逆に、設計図の段階で間違いに気づければ、直すのは紙の上の線一本で済みます。Claude Codeにおける探索と計画は、まさにこの「実装前に設計図を描く」フェーズにあたります。

観点 いきなり実装させた場合 探索→計画を経た場合
最初の一手 Claudeがいきなりコードを書き始める 関連ファイルを読み込み、行動計画を文章化する
前提の共有 何を根拠に実装したか分かりにくい プランとして明示され、認識をすり合わせやすい
軌道修正のタイミング コードが書かれたあと（差分の手直しが必要） コードが書かれる前（文章への指摘で済む）
結果 手戻りが大きくなりやすい 手戻りが小さく、次の機能にも進みやすい

では、探索・計画・実装・コミットという4つのフェーズは、それぞれ具体的に何をするフェーズなのでしょうか。まずは全体像をつかみましょう。

5.2 4フェーズの全体像

原典は、4つのフェーズの役割を次のように整理しています。

① 探索（Explore）

プロジェクトに関する必要な文脈をClaudeに与えるフェーズ。関連ファイルを読み込み、必要ならWeb検索も行います。

② 計画（Plan）

Claudeが成功を判断する基準となる行動計画を作成するフェーズ。承認前に内容を確認できます。

③ 実装（Code）

最終的な成果に落ち着くまでの、あなたとClaudeとのやり取りそのもの。詳しくは第6章。

④ コミット（Commit）

コードをレビューしてプッシュし、次の機能に取りかかれるようにするフェーズ。詳しくは第6章。

この4つは一直線で終わりません。コミットが終わったら、それで完結するのではなく、次の機能のためにまた探索へ戻るという循環になっています。この循環を図にすると、次のようになります。

flowchart LR A["① 探索（Explore）
文脈を集める"] --> B["② 計画（Plan）
行動計画を作る"] B --> C["③ 実装（Code）
Claudeとやり取りする"] C --> D["④ コミット（Commit）
レビューしてプッシュ"] D -->|次の機能へ| A

Explore→Plan→Code→Commitの循環フロー（コミットが終わると、次の機能のための探索へ戻る）

本章で扱う範囲

本章（第5章）では、この循環の前半にあたる①探索と②計画を扱います。③実装と④コミットは、次の第6章で詳しく学びます。まずは「実装に入る前に何をするか」に集中しましょう。

5.3 探索と計画はプランモードで

探索と計画、この最初の2つのステップを進めるもっとも速い方法が、第4章で紹介したプランモード（Plan Mode）です。プランモードでは、Claudeはファイルを編集できません。実装にどう取り組むかの情報を集めるために、ファイルを読み込むだけです。

プランモードに入るには、テキスト入力欄の下にPlan mode onと表示されるまでShift + Tabを押します。モード切り替えの挙動そのものは第4章で確認した通りです。プランモードに入った状態で、実装してほしい内容をプロンプトとして書きます。

動作 プランモードでの可否
ファイルの読み込み 可能（内容を理解するために使う）
Web検索 可能（最新情報の収集に使う）
ファイルの編集 不可（実装フェーズ＝第6章まで待つ）
コマンドの実行 ファイルを変更するコマンドは不可（ls や git log のような読み取り専用の確認コマンドは可）

第2章・第4章のおさらい

第2章で学んだ許可の3モード（既定・自動承認・プランモード）のうち、プランモードは「読み取り専用ツールのみ」が使えるモードでした。第4章ではShift + Tabによる切り替え自体を練習しました。本章では、そのプランモードを探索と計画の実践に使います。

5.4 プロンプト例: 実際に探索・計画を依頼してみる

実際にプランモードでどのようなプロンプトを送ればよいのか、原典で紹介されている実例を見てみましょう。題材は「画像アップロードのパイプラインにWebP変換を追加する」という、既存の処理に手を加える典型的なタスクです。

画像アップロードのパイプラインにWebP変換を追加したいです。パイプラインのどこで行うべきか、新しい依存関係が必要かどうか、どうアプローチすべきかを整理してください。

一見ひとつの文章ですが、よく読むと3つの依頼が含まれています。第4章で触れた「できるだけ具体的に書く」ことの実例として、あわせて確認しておきましょう。

  • どこで行うべきか — パイプラインのどの段階でWebP変換を実行するのが適切か
  • 新しい依存関係が必要かどうか — 変換のために追加のライブラリが要るか
  • どうアプローチすべきか — 具体的な実装方針そのもの

プランモードでこのプロンプトを送ると、実際のやり取りは次のようなイメージで進みます。

terminal — プランモードでの探索・計画セッション例 
$ claude
> 画像アップロードのパイプラインにWebP変換を追加したいです。パイプラインのどこで行うべきか、新しい依存関係が必要かどうか、どうアプローチすべきかを整理してください。

● src/upload/ 配下のファイルを検索しています…
● src/upload/pipeline.ts を読み込みました。
● 画像変換ライブラリの最新情報をWeb検索しています…
● 実行プランを作成しました。内容を確認しますか？

Claudeは関連ファイルを読み込み、必要に応じてWeb検索を行ったうえで、実行プランを提示します。提示される内容はプロジェクトごとに異なりますが、たとえば次のようなイメージです。

提示されるプランのイメージ（WebP変換の例）

  1. 1 アップロード処理の直後、保存前のタイミングでWebP変換を行う
  2. 2 画像変換ライブラリを新しい依存関係として追加する
  3. 3 変換に失敗した場合は、元のフォーマットのまま保存するフォールバックを用意する
  4. 4 アップロードのテストにWebP変換のケースを追加する

※ 実際の提案内容はプロジェクトの構成によって変わります。ここでは理解のためのイメージを示しています。

プランが提示されたら、内容を確認し、自分の求める基準を満たしているかを判断します。満たしていなければ、そのまま実装させるのではなく、次の5.5で見る3つの選択肢から対応を選びます。

5.5 プラン提示時の3つの選択肢

プランが提示されたとき、あなたが取れる行動は3つに整理できます。

1

承認する（Approve）

提示された内容が求める基準を満たしていれば、そのまま承認します。承認するとプランが確定し、実装フェーズ（第6章）に進みます。

2

特定の部分の修正を依頼する

気になる箇所だけをピンポイントで指摘し、直しを依頼します。プラン全体を破棄してやり直す必要はありません。Claudeは指摘を反映したプランを再提示します。

3

質問する

なぜその方針を選んだのか、他の選択肢はなかったのかなど、意図や理由を確認します。認識をすり合わせてから先に進めます。

flowchart TD A["Claudeがプランを提示する"] --> B{"内容は求める基準を
満たしているか？"} B -->|満たしている| C["① 承認する（Approve）"] C --> D["実装フェーズへ
（第6章）"] B -->|一部だけ直したい| E["② 特定箇所の修正を依頼する"] E --> A B -->|意図や理由を確認したい| F["③ 質問する"] F --> A

プラン提示後の分岐フロー（修正依頼・質問はいずれもプランの再提示につながる）

注意: 内容を読まずに承認しない

3つの選択肢が用意されているのは、内容を吟味したうえで意思決定するためです。「とりあえず承認」を繰り返すと、結局はいきなり実装させるのと同じ状態に戻ってしまいます。プランに書かれている前提や方針が、自分の意図と合っているかを一つずつ確認する習慣をつけましょう。

重要ポイント

コードが書かれる前が、軌道修正の最適なタイミングです。プラン段階の指摘は文章の書き直しで済みますが、コードが書かれたあとの修正は、実装済みの差分を読み解き、テストをやり直し、意図を推測しながら手直しする必要があります。プランモードで文脈と計画を固める段階への投資が、結果的に一番の近道になります。

5.6 変更せず概要把握だけしたいとき

プランモードは「これから変更する」ことを前提にしたフローです。一方で、変更するつもりはなく、コードベースの構造や仕組みをざっと把握したいだけのときもあるはずです。そうした場合は、プランモードに入らなくても、探索を担当するexploreサブエージェントを単体で実行できます。探索を専門とするサブエージェントは、あらかじめ用意されているものを使う場合も、自分で定義する場合もあります（サブエージェントの作り方は第9章で学びます）。

呼び出したメインのやり取りとは別のコンテキストウィンドウで調査が行われ、完了すると要約だけが返ってきます。サブエージェントの仕組みそのものは第9章で詳しく学びます。ここでは「探索だけを行う専用の手段がある」ということを覚えておいてください。

状況 使う機能 得られる結果
これから変更を加えたい プランモード（Shift + Tabで切り替え） 承認・修正・質問ができる実行プラン
変更せず概要を知りたいだけ exploreサブエージェント単体 コードベースの説明・要約（第9章で詳述）

先取り: サブエージェントは第9章で

サブエージェントは、タスクを委任して独立したコンテキストウィンドウで並行実行できる仕組みです。exploreサブエージェントはその一例にすぎません。作り方や活用法は第9章でまとめて学びます。

ここまでで、探索と計画という前半2フェーズの考え方と実践方法を見てきました。次の第6章では、承認したプランをもとに実装を進め、レビューを経てコミットするまでの後半2フェーズを扱います。

やってみよう 5-1: プランモードで機能追加を計画してみる

実際にプランモードを使い、探索から計画までの流れを体験してみましょう。この段階では実装まで進める必要はありません（実装は第6章で行います）。

手順

  1. 1 自分の学習用プロジェクトで claude を起動し、Shift + Tab を押して「Plan mode on」と表示されるまでモードを切り替える。
  2. 2 追加したい小さな機能を1つ選び、5.4の書き方を参考に「どこで行うべきか」「新しい依存関係が必要か」「どうアプローチすべきか」を尋ねるプロンプトを書いて送信する。
  3. 3 提示されたプランを読み、5.5の3つの選択肢（承認／特定箇所の修正／質問）のうちどれを選ぶかを自分の言葉で書き出す。

理解度確認クイズ

  1. Q1. Explore→Plan→Code→Commitワークフローについて、原典がもっとも強調していることは何ですか？

    回答を表示

    「このコースから一つだけ持ち帰るとしたら、このワークフローにしてください」と言われるほど重要だという位置づけです。いきなりClaudeにコードを書かせると後から軌道修正が多く必要になるため、先に探索と計画を経ることが結果的に一番の近道になります。

  2. Q2. プランモードでClaudeができることと、できないことをそれぞれ答えてください。

    回答を表示

    できること: 関連ファイルの読み込み、Web検索、ls や git log のような読み取り専用の確認コマンドの実行。できないこと: ファイルの編集、ファイルを変更するコマンドの実行です。プランモードでは読み取り専用のツールしか使われません。

  3. Q3. プランが提示されたときに選べる3つの選択肢は何ですか。また、軌道修正にもっとも適したタイミングはいつですか？

    回答を表示

    ①承認する（Approve）、②特定箇所の修正を依頼する、③質問する、の3つです。軌道修正にもっとも適したタイミングは、コードがまだ書かれていない、プラン提示の段階です。
