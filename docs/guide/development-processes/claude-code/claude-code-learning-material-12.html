ホーム Claude Code 第12章
第12章 所要時間: 約50分

フックで動作を確実にする

第11章では MCP を使って外部のツールやデータソースとつながる方法を学びました。本章では視点を変え、Claude Code 自身の振る舞いを「確実に」制御する仕組みであるフック（Hooks）を学びます。CLAUDE.md への指示は「たいてい」実行される確率的なお願いですが、フックは「例外なく毎回」実行される決定的な仕組みです。自動フォーマットやチームで守るべき安全ルールなど、絶対に外せない処理をどう保証するのかを見ていきましょう。

この章で学ぶこと

  • フックが「決定的（deterministic）」であるとはどういうことか、CLAUDE.md への指示との違いを説明できる
  • フックの5つのイベント（PreToolUse／PostToolUse／UserPromptSubmit／Stop／Notification）を理解する
  • settings.json に PostToolUse フックを設定し、編集後の自動フォーマットを実現できる
  • PreToolUse フックで危険な操作をブロックする仕組みと、終了コードの意味を理解する
  • .claude/settings.json をチームで共有し、CLAUDE_PROJECT_DIR を使う理由を説明できる

12.1 フックとは何か

フック（Hooks）とは、Claude Code のライフサイクル上の特定のタイミング（イベント）で、あらかじめ登録しておいたシェルコマンドを自動的に実行できる仕組みです。「ファイルが編集された直後」「ユーザーがプロンプトを送信したとき」など、決まったタイミングに、決まった処理を差し込めます。

設定ファイルに登録しておいたコマンドを、Claude Code のライフサイクル上の特定のイベントで自動的に実行する仕組み

ここまでの章で学んできた CLAUDE.md（第8章）やサブエージェント（第9章）、MCP（第11章）は、いずれも Claude が「自分の判断で」使うかどうかを決める仕組みでした。フックはこれらとは根本的に性質が異なります。次の節で、その違いを詳しく見ていきましょう。

12.2 なぜフックが必要か——「決定的」という性質

たとえば CLAUDE.md（第8章）に「ファイルを編集するたびに Prettier を実行して」と書いておいたとします。多くの場合、Claude はその指示に従ってくれるでしょう。しかし、時には実行されないこともあります。CLAUDE.md はあくまで Claude への「お願い」であり、実行するかどうかの最終判断は Claude 自身に委ねられているからです。

フックはこの問題を解決します。フックとして設定した処理は、Claude の判断を介さず、条件に一致すれば例外なく毎回必ず実行されます。この性質を決定的（deterministic）と呼びます。

flowchart LR subgraph S1["CLAUDE.mdに書く（確率的）"] A1["編集のたびにPrettierを
実行してと記述する"] --> B1{"Claudeが実行するか判断"} B1 -->|たいてい| C1["実行される"] B1 -->|時には| D1["実行されない"] end subgraph S2["フックに設定する（決定的）"] A2["PostToolUseフックを設定する"] --> B2["ファイル編集イベントが発生"] B2 --> C2["例外なく毎回実行される"] end

重要ポイント

CLAUDE.md への指示は「確率的なお願い」、フックは「決定的な強制」です。「たいてい」で済ませられない処理は、プロンプトではなくフックに任せましょう。

12.3 フックの代表的な使い道

フックは、次のような「毎回必ず行いたい処理」を実現するために使われます。

編集後の自動フォーマット

ファイルを編集するたびに、Prettier や gofmt などのフォーマッターを自動実行します。

コンプライアンスのための記録

実行されたすべてのコマンドをログに残し、あとから監査できるようにします。

危険な操作のブロック

本番環境のファイル変更など、絶対に避けたい操作を実行前に食い止めます。

完了時の通知

Claude がタスクを完了したときに、自分宛てに通知を送ります。

共通しているのは、どれも「たまに忘れられては困る」処理だという点です。次節では、これらを実現するための土台となる5つのイベントを見ていきます。

12.4 フックの代表的な5つのイベント

フックは、Claude Code のライフサイクル上でよく使う5種類のイベントのいずれかに対して設定します。

イベント 発火タイミング 主な用途
PreToolUse ツール呼び出しの前 危険な操作のブロック・実行前チェック
PostToolUse ツール呼び出しが完了した後 自動フォーマット・ログ記録
UserPromptSubmit プロンプト送信時、Claude が処理を始める前 入力内容のチェック・補足情報の付与
Stop Claude が応答を終えたとき 完了時のログ記録・後処理
Notification Claude が通知を送るとき 通知の転送（Slack・メールなど）

※ このほかにも、セッションの開始・終了時などに発火するイベントがあります。最新の一覧は公式ドキュメントで確認してください。

この5つのイベントを時系列に並べると、次のような流れになります。

flowchart TD A["ユーザーがプロンプトを送信"] --> B["UserPromptSubmitフック"] B --> C["Claudeが処理を開始"] C --> D["PreToolUseフック"] D --> E["ツールを実行する"] E --> F["PostToolUseフック"] F -->|次のツール呼び出しへ| D F -->|応答が完了| G["Stopフック"] C -.->|随時発火| H["Notificationフック"]

第2章のエージェントループとのつながり

第2章で学んだエージェントループ（①プロンプト入力 → ②コンテキスト収集 → ③行動 → ④結果を検証 → ⑤終了 or ループ）を思い出してください。PreToolUse は③の直前、PostToolUse は④の直後に対応します。フックは、このループの決まった位置に「必ず割り込む」仕組みだと捉えると理解しやすくなります。

12.5 settings.json でフックを設定する

フックは、.claude/settings.json に設定します。設定方法は2通りあります。1つは Claude Code 内で /hooks コマンドを使う方法、もう1つは settings.json を直接編集する方法です。どちらも最終的には同じ設定ファイルに書き込まれます。

設定の構造はシンプルです。トップレベルの hooks キーの下にイベント名（例: PostToolUse）をキーとする配列を置きます。配列の各要素には、どのツールに適用するかを指定する matcher（正規表現パターン）と、実行するコマンドを定義する hooks 配列（各要素は type: "command" と command を持つ）を書きます。

.claude/settings.json 
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|MultiEdit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/format.sh"
          }
        ]
      }
    ]
  }
}

この設定は、Edit・MultiEdit・Write のいずれかのツールが使われてファイル編集が完了するたびに format.sh というスクリプトを実行します。もっとも使われるフックが、まさにこの編集後の自動フォーマットです。呼び出し先のスクリプト側では、対象ファイルの拡張子を確認し、TypeScript なら Prettier、Go なら gofmt というように、プロジェクトに応じたフォーマッターを実行するのが一般的です。

matcher の書き方

matcher に Edit|MultiEdit|Write のように複数のツール名を |（OR）でつなげて指定すると、いずれか1つのツールに一致した場合にフックが発火します。

12.6 PreToolUse によるブロック——絶対的なルールを強制する

数あるフックの中でも、もっとも強力なのが PreToolUse によるブロックです。フックは、ツール名と入力内容を JSON として標準入力（stdin）経由で受け取ります。つまりフック側のスクリプトは、Claude が「これから何をしようとしているか」を実行前に確認し、必要であれば止めることができるのです。

フックの動作は、スクリプトが返す終了コードによって決まります。

終了コード 動作
0 通常どおり処理を続行する。
2 操作をブロックする。標準エラー出力（stderr）のメッセージが Claude にフィードバックとして渡されるため、なぜブロックされたのかを理解し、対応を調整できる。
それ以外 処理を止めることはないが、非ブロッキングのエラーとしてユーザーに表示される。
flowchart TD A["PreToolUseフックが実行される"] --> B{"終了コードは？"} B -->|0| C["処理を続行する"] B -->|2| D["操作をブロックする"] D --> E["stderrのメッセージが
Claudeにフィードバックされる"] B -->|それ以外| F["処理は止めないが
非ブロッキングエラーとして表示"]

終了コード2で処理を止められるという仕組みが重要なのは、絶対的なルールを強制できるからです。「提案」ではなく「保証」が必要な場面、たとえば次のような操作をブロックするのに使われます。

本番設定ディレクトリへの書き込み

本番環境の設定ファイルをうっかり書き換えてしまう事故を防ぎます。

rm -rf を含むコマンド

意図しない範囲のファイルを一括削除してしまう危険なコマンドの実行をせき止めます。

main ブランチへの直接コミット

レビューを経ずに本流のブランチへ変更が入ってしまうことを防ぎます。

実際のスクリプトはどのようなものでしょうか。rm -rf を含む bash コマンドをブロックする、シンプルな PreToolUse フックの例を見てみましょう。標準入力から受け取った JSON は、jq（JSON を扱うコマンドラインツール）などで実行しようとしているコマンド文字列を取り出せます。

.claude/hooks/block-dangerous-bash.sh 
#!/bin/bash
# PreToolUseフック: 危険なbashコマンドをブロックする
# 標準入力からツール名と入力内容（JSON）を受け取る
input=$(cat)
command=$(echo "$input" | jq -r '.tool_input.command // empty')

# rm -rf を含むコマンドは実行させない
if echo "$command" | grep -qE 'rm\s+-rf'; then
  echo "危険: rm -rf を含むコマンドはブロックされました" >&2
  exit 2
fi

# 問題がなければ続行を許可する
exit 0

rm -rf を含むコマンドが検出されると、標準エラー出力にメッセージを書き出したうえで終了コード2を返します。このメッセージはそのまま Claude にフィードバックされるため、Claude は「なぜブロックされたか」を理解し、別の方法を提案するなど対応を調整できます。

12.7 チームでフックを共有する

.claude/settings.json はプロジェクトレベルの設定ファイルであり、CLAUDE.md（第8章）と同じようにリポジトリにチェックインできます。つまり、一度フックを整備すれば、チームの誰がクローンしても自動的に同じフックが有効になるということです。

フック関連ファイルの配置例 

プロジェクトルート/
├── .claude/
│   ├── settings.json           ← フックの設定（チェックイン対象）
│   └── hooks/
│       ├── format.sh           ← 自動フォーマット用スクリプト
│       └── block-dangerous-bash.sh
└── ...

ここで注意したいのが、コマンドの中でプロジェクト内のスクリプトを参照する方法です。Claude Code の作業ディレクトリは、起動した場所やその時々の操作によって変わりうるため、./hooks/format.sh のような相対パスでは正しいファイルを指せないことがあります。そこで使うのが、環境変数 CLAUDE_PROJECT_DIR です。

用語: CLAUDE_PROJECT_DIR

コマンドの中で $CLAUDE_PROJECT_DIR/.claude/hooks/format.sh のように書けば、Claude の現在の作業ディレクトリに関わらず、常にプロジェクト内に保存されたスクリプトを正しく参照できます。

ここまでの内容を、第8章で学んだ CLAUDE.md と比較して整理しましょう。

観点 CLAUDE.md（第8章） フック（本章）
性質 確率的な「お願い」 決定的な「強制」
実行の保証 たいてい実行される 例外なく必ず実行される
設定場所 プロジェクトルートの Markdown ファイル .claude/settings.json の JSON 設定
向いている用途 背景知識・規約・コーディングスタイルの伝達 絶対に守らせたいルール・自動化したい定型処理の強制

本章のまとめとして、次の一文を持ち帰ってください。

何かを「毎回必ず」実行させたいなら、それをプロンプトに書くのではなく、フックに設定しましょう。

やってみよう 12-1: PreToolUse ブロックルールを設計してみる

実際に手を動かす前に、自分が関わるプロジェクトで「絶対に自動実行してほしくない操作」を洗い出し、フックとして設計してみましょう。

手順

  1. 1 自分が普段使っているプロジェクトを1つ思い浮かべ、「絶対に自動で実行されては困る操作」を1つ書き出す（例: .env ファイルへの書き込み、特定ディレクトリの削除、本番用ブランチへの直接コミットなど）。
  2. 2 その操作はどのツール（Bash・Edit・Write など）のどんな入力に現れるかを考え、matcher パターンと判定条件を書き出す。
  3. 3 検証用のテスト用ディレクトリ（本番のプロジェクトではない場所）に .claude/settings.json を作成し、PreToolUse フックとして設定する。意図どおりに操作がブロックされ、終了コード2でメッセージが表示されることを確認する。

理解度確認クイズ

  1. Q1. フックが「決定的（deterministic）」であるとはどういう意味ですか。CLAUDE.md への記述と何が違いますか。

    回答を表示

    フックは、設定したイベントが発生し条件（matcher）に一致すれば、Claude の判断を介さず例外なく毎回必ず実行されるという性質を持ちます。これに対して CLAUDE.md への指示（例: 「編集のたびに Prettier を実行して」）は、実行するかどうかの最終判断が Claude に委ねられているためたいていは実行されるが時には実行されないこともある「確率的なお願い」です。絶対に外せない処理はフックで強制する必要があります。

  2. Q2. PreToolUse フックで操作をブロックしたいとき、終了コードは何にすべきですか。その際、Claude に理由を伝えるにはどうすればよいですか。

    回答を表示

    終了コード2で終了します。ブロックした理由は標準エラー出力（stderr）にメッセージとして出力すると、そのメッセージがそのまま Claude にフィードバックとして渡され、なぜブロックされたのかを理解したうえで対応を調整できます。なお終了コード0は続行、それ以外（2以外の非0）は処理を止めない非ブロッキングのエラー表示になります。

  3. Q3. .claude/settings.json をチームで共有する際、コマンドの中でプロジェクト内のスクリプトを確実に参照するために使うべき環境変数は何ですか。

    回答を表示

    CLAUDE_PROJECT_DIR です。この環境変数を使うことで、Claude の現在の作業ディレクトリに関わらず、プロジェクト内に保存されたスクリプトを正しく参照できます。.claude/settings.json 自体はプロジェクトレベルの設定としてリポジトリにチェックインできるため、チーム全員が自動的に同じフックを使えるようになります。
