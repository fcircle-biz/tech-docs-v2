ホーム JMeter 第3章
第3章 所要時間: 約1時間

テスト計画の構造と要素の種類

JMeter のテスト計画は、「要素」と呼ばれる部品をツリー状に組み合わせて作ります。この章では、要素にどんな種類があるのか、ツリーのどこに置くかで効く範囲（スコープ）がどう変わるのか、そして1回のリクエストの中で要素がどの順番で動くのかを学びます。この3つは、これから先のすべての章の土台になります。

この章で学ぶこと

  • テスト計画（.jmx ファイル）がツリー構造の XML であることを理解し、保存・命名ができる
  • 要素の種類（Thread Group・Sampler・Controller・Config・Pre/Post Processor・Assertion・Timer・Listener）の役割を説明できる
  • ツリー上の位置によって要素の効く範囲（スコープ）が決まることを理解する
  • 1回のリクエストで要素が動く順番を答えられ、有効/無効・複製などの便利な操作を使える

3.1 テスト計画（Test Plan）と .jmx ファイル

JMeter を起動すると、左側のツリーの一番上に Test Plan（テスト計画）が1つだけ表示されます。これがテストのすべてを入れる「入れ物」で、ツリーの根（ルート）にあたります。この下に、右クリックで要素（Element）を追加していき、ツリーを育てていきます。

テスト計画は .jmx ファイルとして保存されます。中身は XML というテキスト形式なので、メモ帳などで開いて読むことができ、Git で差分を管理することもできます。ツリーの親子関係は、XML の入れ子としてそのまま保存されます。次は、Thread Group の下に HTTP Request を1つ置いたテスト計画の抜粋です（実際のファイルにはほかの設定値も並びます）。

ch03-structure.jmx（抜粋・簡略化） 
<jmeterTestPlan version="1.2" properties="5.0" jmeter="5.6.3">
  <hashTree>
    <!-- ツリーの根が Test Plan -->
    <TestPlan testname="Test Plan"/>
    <hashTree>
      <!-- Thread Group は Test Plan の子 -->
      <ThreadGroup testname="一般ユーザー"/>
      <hashTree>
        <!-- HTTP Request は Thread Group の子 -->
        <HTTPSamplerProxy testname="GET /get"/>
        <hashTree/>
      </hashTree>
    </hashTree>
  </hashTree>
</jmeterTestPlan>

.jmx を手で書き換える必要はほとんどありませんが、「ツリーの構造がそのまま XML になっている」ことを知っておくと、ファイルを Git で比較したり、他の人から受け取ったファイルを読んだりするときに役立ちます。

保存と名前の付け方

  • 保存: File → Save Test Plan as… で名前を付けて保存します。こまめに Ctrl+S（macOS は Command+S）で上書き保存しましょう。
  • 開く: File → Open… で .jmx を選びます。
  • ファイル名: 本ガイドでは jmeter-practice フォルダに chNN-内容.jmx（例: ch03-structure.jmx）の名前で保存します。

もうひとつ、最初から身につけたい習慣があります。各要素には Name 欄があり、既定では「HTTP Request」「Thread Group」のような種類名が入っています。これを何をする要素なのかが一目でわかる名前に変えておきましょう。

既定の名前 わかりやすい名前の例 理由
HTTP Request GET /get、POST 注文 結果の一覧やレポートで、行の名前（ラベル）としてそのまま表示される
Thread Group 一般ユーザー、管理者 どの利用者像の負荷なのかがわかる
HTTP Header Manager 共通ヘッダー(JSON) 同じ種類の要素が複数あっても見分けられる

ヒント: サンプラーの名前は結果の「ラベル」になる

リクエストを送るサンプラーの Name は、後の章で見る Summary Report や HTML レポートの行名になります。全部 HTTP Request のままだと、どの行がどのリクエストなのか区別できません。

3.2 要素の種類

テスト計画に追加できる要素は、役割によって次の種類に分かれます。追加するときのメニュー（右クリック → Add）も、この分類のとおりに並んでいます。初出の英語名には日本語訳を添えますが、以降は英語名で呼びます。

種類（英語名） 日本語訳 役割 代表例
Thread Group スレッドグループ 仮想ユーザー（スレッド）の人数・起動のしかた・繰り返し回数を決める。テストの「出発点」 Thread Group、setUp / tearDown Thread Group
Sampler サンプラー 実際にリクエストを送り、結果（サンプル）を1件作る。テストの「主役」 HTTP Request、JDBC Request、Debug Sampler
Logic Controller ロジックコントローラ 配下のサンプラーを「いつ・何回・どの順で」実行するかを制御する（第10章） Loop Controller、If Controller、Transaction Controller
Config Element 設定エレメント サンプラーが使う共通設定やデータを用意する。自分ではリクエストを送らない HTTP Request Defaults、HTTP Header Manager、CSV Data Set Config、HTTP Cookie Manager
Pre Processor 前処理 サンプラーが実行される直前に、リクエストの準備やデータの加工を行う User Parameters、JSR223 PreProcessor
Post Processor 後処理 サンプラーの実行直後に、応答から値を取り出すなどの処理を行う（第9章） JSON Extractor、Regular Expression Extractor
Assertion アサーション 応答が期待どおりかを検証し、違えばそのサンプルを失敗にする（第7章） Response Assertion、JSON Assertion、Duration Assertion
Timer タイマー サンプラーを実行する前に待ち時間を入れ、利用者の思考時間を再現する（第6章） Constant Timer、Uniform Random Timer
Listener リスナー サンプルを受け取り、画面表示やファイル保存、集計を行う View Results Tree、Summary Report

追加メニューの場所も覚えておきましょう。たとえば Thread Group は Test Plan を右クリックして Add → Threads (Users) → Thread Group、HTTP Request は Add → Sampler → HTTP Request、View Results Tree は Add → Listener → View Results Tree です。Pre Processor は Add → Pre Processors、Post Processor は Add → Post Processors の中にあります。

重要ポイント: 「リクエストを送る」のはサンプラーだけ

ほかの要素は、サンプラーを支える役です。Config Element は共通設定を、Timer は待ち時間を、Assertion は検証を、Listener は表示を担当します。「どの要素がどのサンプラーを支えるのか」を決めるのが、次の節で学ぶスコープです。

補足: Test Plan にも設定欄がある

Test Plan の画面には、User Defined Variables（全体で使う変数を定義する表）や、Thread Group を順番に実行するか（Run Thread Groups consecutively）といった設定があります。変数は第8章で使います。

3.3 ツリーとスコープ

JMeter では、要素がツリーのどこに置かれているかによって、その要素がどのサンプラーに効くかが決まります。この「効く範囲」をスコープ（Scope）と呼びます。ルールはとてもシンプルです。

親に置くと、子孫すべてに効く

Thread Group の直下に置いた要素は、その Thread Group の中にあるすべてのサンプラーに適用されます。

サンプラーの子に置くと、そのサンプラーだけに効く

サンプラーの直下に置いた要素は、その1つのサンプラーだけに適用されます。

次のツリーで考えてみましょう。「共通ヘッダー」は Thread Group の直下にあるため、3つのサンプラーすべてに効きます。「検索の検証」は GET /html の子なので、その1つだけを検証します。「全結果」は Test Plan の直下にあるため、すべての Thread Group のすべてのサンプルを受け取ります。

flowchart TD TP["Test Plan"] --> L["View Results Tree 全結果"] TP --> TG["Thread Group 一般ユーザー"] TG --> H["HTTP Header Manager 共通ヘッダー"] TG --> S1["HTTP Request GET /get"] TG --> S2["HTTP Request GET /html"] TG --> S3["HTTP Request GET /uuid"] S2 --> A["Response Assertion 検索の検証"]
要素 置いた場所 効く範囲
共通ヘッダー（HTTP Header Manager） Thread Group の直下 GET /get、GET /html、GET /uuid の3つすべて
検索の検証（Response Assertion） GET /html の子 GET /html だけ（ほかの2つは検証されない）
全結果（View Results Tree） Test Plan の直下 すべての Thread Group の全サンプル

もうひとつ大事なのが、サンプラーと Logic Controller は「ツリーに並んだ順」に実行されるという点です。上にあるものから順に動くので、「ログイン → 商品閲覧 → 注文」のような手順は、ツリーの上から下へ並べて表現します。一方、Config Element・Timer・Assertion などは、並び順ではなくスコープで適用先が決まります。同じ階層に置いたからといって、「すぐ下のサンプラーだけ」に効くわけではありません。

よくある失敗: 置き場所を間違えてスコープがずれる

たとえば「1つのリクエストだけを検証したい」のに、Response Assertion を Thread Group の直下に置くと、すべてのサンプラーに同じ検証が適用され、無関係なリクエストが失敗扱いになります。逆に、サンプラーの子に置いた Config Element は、ほかのサンプラーには効きません。「効かない」「効きすぎる」ときは、まず要素の置き場所を疑いましょう。

同じ種類の設定が内側と外側に複数あるときは、サンプラーに近い（内側の）設定が優先されます。たとえば Thread Group に HTTP Request Defaults を置いたうえで、特定のサンプラーに別の接続先を直接書けば、そのサンプラーだけ個別の設定が使われます。

3.4 実行順序

スコープが決まったら、次はどの順番で動くかです。JMeter は、サンプラー1回分の実行ごとに、そのサンプラーに適用される要素を種類ごとに次の順で処理します（公式マニュアルの「Execution order」に記載されている順序です）。ツリーの見た目の並び順とは関係なく、この順序で動く点に注意してください。

flowchart LR C["1. Config Element
共通設定を適用"] --> PRE["2. Pre Processor
前処理"] PRE --> T["3. Timer
待ち時間を入れる"] T --> S["4. Sampler
リクエスト送信"] S --> POST["5. Post Processor
応答から値を抽出"] POST --> AS["6. Assertion
応答を検証"] AS --> LI["7. Listener
結果を表示・記録"]
順番 要素 この段階で起きること
1 Config Element 接続先・ヘッダー・Cookie などの共通設定が、サンプラーに反映される
2 Pre Processor リクエスト送信前の準備（変数の設定など）
3 Timer 指定した時間だけ待つ（サンプラーの「前」）
4 Sampler リクエストを送り、応答を受け取ってサンプルを作る
5 Post Processor 応答から値を取り出して変数に入れる
6 Assertion 応答が期待どおりか検証し、結果を成功/失敗にする
7 Listener 最終的なサンプルを画面に出す、ファイルに書く

重要ポイント: Timer は「前」に効く

名前から「リクエストの後に待つ」と誤解しがちですが、Timer はスコープ内の各サンプラーの実行前に待ちます。「ログイン後に3秒待つ」を再現したいなら、待ちたい次のサンプラーのスコープに Timer を置きます。詳しくは第6章で扱います。

この順序を知っていると、設定の意味が読み取れるようになります。たとえば第9章で行う「JSON Extractor（Post Processor）で取り出した値を、直後の Header Manager で使う」という相関では、前のサンプラーの 5（Post Processor による抽出）は、次のサンプラーの 1（Config Element＝Header Manager の適用）が始まる前に完了しているため、うまく受け渡せるのです。

補足: サンプラーがなければ動かない要素

Pre Processor・Timer・Post Processor・Assertion は、スコープ内にサンプラーがあって初めて動く要素です。サンプラーのないところに置いても、何も起きません。Timer や Assertion を Thread Group に置いても、配下にサンプラーが無ければ動かない、ということです。

3.5 便利な操作

テスト計画が大きくなってくると、ツリーの操作に慣れているかどうかで作業の速さが大きく変わります。ここでは、すぐに使える基本の操作をまとめます。macOS では Ctrl を Command に読み替えてください。

操作 方法 使いどころ
有効/無効の切り替え 要素を選んで Ctrl+T（右クリック → Enable / Disable も可） 要素を消さずに一時的に外す。無効な要素はツリー上で灰色の文字になり、実行されない
複製 要素を選んで Ctrl+Shift+C（右クリック → Duplicate） 似たリクエストを増やす。子要素ごと複製される
コピー＆貼り付け Ctrl+C → 貼り付け先の要素を選んで Ctrl+V 別の親（Thread Group など）の下へ同じ要素を置く
移動 ツリー上でドラッグ＆ドロップ 実行順の入れ替えや、スコープの変更（別の親の下へ移す）
コメント 要素の画面にある Comments 欄に記入 その要素を置いた意図をメモする
テンプレート File → Templates… 雛形から新しいテスト計画を作る（第11章で Recording テンプレートを使う）

ヒント: 「消す」より「無効にする」

原因を切り分けたいときは、要素を削除せず無効化して動作を比べるのが安全です。いつでも元に戻せます。ただし、要素を消すのとは違い、無効化した要素も .jmx には残るので、使わないものは最終的に整理しましょう。

注意: 実行中は編集しない

テストの実行中に要素を追加・変更しても、反映されない、または意図しない動きになることがあります。設定を変えたいときは、いったん Stop してから編集し、保存してから実行し直してください。

やってみよう 3-1: 最小のテスト計画ツリーを作る

Test Plan → Thread Group → HTTP Request → View Results Tree というツリーを作り、ch03-structure.jmx として保存します。まだリクエストの中身は空のままで構いません。ツリーを作る感覚をつかむことが目的です。

手順

  1. 1 JMeter を英語表示で起動する。左のツリーに Test Plan だけがあることを確認する。
  2. 2 Test Plan を右クリック → Add → Threads (Users) → Thread Group。Name を 一般ユーザー に変更する。
  3. 3 Thread Group を右クリック → Add → Sampler → HTTP Request。Name を GET /get に変更する（接続先や Path は空のまま）。
  4. 4 Test Plan を右クリック → Add → Listener → View Results Tree。Name を 全結果 に変更する。
  5. 5 jmeter-practice/ch03-structure.jmx として保存する（File → Save Test Plan as…）。
確認ポイント: ツリーが「Test Plan の下に、一般ユーザー（その下に GET /get）と、全結果が並ぶ」形になっていれば成功です。保存したファイルをテキストエディタで開き、<ThreadGroup や <HTTPSamplerProxy という文字が入れ子で並んでいることも見てみましょう。

やってみよう 3-2: 要素を無効化して変化を確認する

3-1 で作ったツリーを使い、要素の有効/無効と複製を試します。

手順

  1. 1 GET /get を選んで Ctrl+T（macOS は Command+T）を押す。ツリー上の見た目がどう変わるか観察する。
  2. 2 もう一度 Ctrl+T を押して有効に戻す。
  3. 3 GET /get を選んで Ctrl+Shift+C で複製し、複製された方の Name を GET /html に変更する。
  4. 4 GET /html の Comments 欄に「第7章でアサーションを付ける」とメモし、Ctrl+S で上書き保存する。
確認ポイント: 無効にした要素はツリー上で文字が灰色になります。有効に戻すと元の色に戻ります。（実際のリクエスト送信は第4章で行います。）

理解度確認クイズ

  1. Q1. Thread Group の直下に Response Assertion を置いた場合と、HTTP Request の子に置いた場合では、何が違いますか？

    回答を表示

    効く範囲（スコープ）が違います。Thread Group の直下に置くと、その Thread Group 内のすべてのサンプラーが検証の対象になります。HTTP Request の子に置くと、その1つのサンプラーだけが対象になります。特定のリクエストだけを検証したいときは、サンプラーの子に置きます。

  2. Q2. 1つのサンプラーを実行するとき、Timer・Assertion・Config Element・Sampler・Post Processor はどの順番で処理されますか？

    回答を表示

    Config Element → Timer → Sampler → Post Processor → Assertion の順です（間に Pre Processor が入る場合は、Config Element の次、Timer の前です。最後に Listener が結果を受け取ります）。Timer はサンプラーの「前」に待つ点がポイントです。

  3. Q3. 全サンプラーに共通のヘッダー（Content-Type など）を付けたいとき、HTTP Header Manager はツリーのどこに置くのがよいですか？ また、特定のリクエストにだけ別のヘッダーを付けたいときは？

    回答を表示

    全サンプラーに共通のものは、Thread Group の直下に置きます。特定のリクエストにだけ付けたいものは、そのサンプラーの子に置きます。スコープは「置いた場所とその配下」で決まるためです。
