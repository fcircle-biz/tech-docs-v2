総合演習：性能テストを計画・実施・報告する

最終章では、これまでの13章で学んだ要素をすべて組み合わせ、性能テストを最初から最後まで一通り実施します。練習用サーバーを「EC サイトの API」に見立て、目標の設定、テスト計画の作成、スモークテスト、段階的な負荷実行、結果の判定、報告書のまとめまでを体験しましょう。

この章で学ぶこと

  • 性能テストの進め方（目標合意から報告まで）の全体の流れを説明できる
  • これまでの要素を組み合わせて、業務シナリオのテスト計画を作れる
  • スモークテストで確認してから、負荷を段階的に上げて CLI で実行できる
  • 目標と実測を比べて合否を判定し、報告書にまとめられる
  • 集計の単位（リクエストか業務操作か）と評価する期間を明確にし、負荷をかける側の状態も含めて結果の信頼性を判断できる

14.1 性能テストの進め方

ここまでは JMeter の「部品」を一つずつ学んできました。実務の性能テストは、部品を使う前後の段取りが成否を分けます。いきなり大きな負荷をかけるのではなく、目標を決め、小さく確かめ、段階的に負荷を上げ、結果を報告するという流れで進めます。

flowchart TD A["目的・目標の合意"] --> B["シナリオ設計"] B --> C["スクリプト作成（GUI）"] C --> D["スモークテスト
1ユーザーで動作確認"] D --> E{"全件成功か？"} E -->|いいえ| C E -->|はい| F["本番実行（CLI）
負荷を段階的に上げる"] F --> G["分析（HTMLレポート）"] G --> H["報告・次のアクション"]
工程 やること 主な章
目的・目標の合意 何のために測り、何が出れば合格かを数値で決め、関係者と合意する 第1章
シナリオ設計・スクリプト作成 利用者の操作の流れを決め、テスト計画（.jmx）に落とし込む 第3〜11章
スモークテスト 1ユーザー・1ループで、スクリプト自体が正しく動くか確かめる 第4章
本番実行 CLI モードで、負荷を小さい方から段階的に上げて実行する 第5・12章
分析・報告 レポートを読み、目標と比べて判定し、報告書にまとめる 第13章

重要ポイント: スモークテストを飛ばさない

スクリプトの間違い（URL のミス、相関の失敗など）を抱えたまま負荷をかけると、「システムが遅い」のか「スクリプトが間違っている」のか区別できなくなります。先に1ユーザーで正しさを確認し、それから負荷を上げるのが鉄則です。

14.2 演習の題材と目標

この演習では、練習用サーバー go-httpbin（localhost:8080）を「EC サイトの API」に見立てます。利用者は、トップページを開き、ログインし、商品を何度か閲覧し、商品を検索して、注文する、という流れで操作します。

flowchart LR T1["T01_Top
GET /html"] --> T2["T02_Login
POST /post
GET /uuid
GET /bearer"] T2 --> T3["T03_Browse（3回）
GET /get"] T3 --> T4["T04_Search
GET /delay/1"] T4 --> T5["T05_Order
POST /anything/orders"]
トランザクション名 EC サイトでの意味 実際に送るリクエスト
T01_Top トップ表示 GET /html
T02_Login ログイン（スレッドにつき1回） POST /post（CSV のユーザー）→ GET /uuid（トークン取得）→ GET /bearer（認証確認）
T03_Browse 商品閲覧（3回繰り返し） GET /get?item=${__Random(1,100,)}
T04_Search 商品検索（重い処理） GET /delay/1（1秒かかる処理に見立てる）
T05_Order 注文 POST /anything/orders

次に目標を決めます。目標が数値になっていないと、結果が出ても「良いのか悪いのか」を判断できません。本演習では次の目標を置きます（実務では、業務要件や過去の実績から関係者と合意して決めます）。

項目 目標
負荷条件 20 仮想ユーザーで、3分間（180秒）操作を続ける（最初の10秒はランプアップ）
応答時間 各トランザクション（T01〜T05）の 95 パーセンタイルが 2000ms 以内
エラー率 各トランザクション（T01〜T05）で 1% 未満

目標では、何を1件と数えるかもそろえておきます。本演習の応答時間とエラー率は、どちらも業務操作の単位、つまり Transaction Controller の行（T01〜T05）で評価します。リクエスト単位の行と混ぜて合算すると、件数や割合の意味が変わってしまうためです（第10・13章）。

実務では、目標の数値と同じくらいその数値の根拠が大切です。たとえば EC サイトなら次のような性能要件を立てますが、「なぜ200ユーザーなのか」「なぜ2秒なのか」を説明できなければ、合否を判定しても意味のある結論になりません。

指標 性能要件の例 根拠として確認すること
同時利用者数 200ユーザー 過去のピーク時の利用者数（アクセスログ）、今後の伸びの見込み、「利用中の人数」と「同時に処理中のリクエスト数」のどちらの意味か（第5章）
注文処理 95 パーセンタイルで 2秒以内 業務上許容できる待ち時間、待ち時間と離脱の関係
検索処理 95 パーセンタイルで 1秒以内 利用頻度の高さ、画面上での使われ方
エラー率 0.1% 未満 失敗したときの業務への影響、再試行できるかどうか
スループット 50 リクエスト/秒以上 ピーク時間帯のリクエスト数（アクセスログ）。リクエスト単位か業務操作単位か
テスト時間 安定負荷で 30分間 安定した状態を十分に観測できる長さか、時間とともに悪化する問題を見つけたいか

※ 表の数値は説明用の例です。

警告: 負荷をかける先は localhost だけ

この演習の接続先は、自分の PC 上の go-httpbin（localhost:8080）だけです。他人・他社のサーバーへ許可なく負荷をかけることは DoS 攻撃と同じ行為で、法的責任を問われる可能性があります。実行前に、HTTP Request Defaults の Server Name が localhost であることを必ず確認してください。

14.3 テスト計画の作成

ここまでに学んだ要素を組み合わせて、ch14-final.jmx を作ります。まず全体のツリーを確認しましょう。第3章で学んだとおり、親子関係がそのまま適用範囲（スコープ）になります。

ch14-final.jmx のツリー構成

    ├── HTTP Cookie Manager          ← Cookie を保持
    ├── CSV Data Set Config          ← users.csv を読む
    ├── Uniform Random Timer         ← 思考時間
    ├── Transaction Controller（T01_Top）

    │       └── HTTP Request（GET /bearer）＋ Header Manager ＋ JSON Assertion

リスナーは、スモークテストのときだけ View Results Tree を Thread Group の下に置いて使い、本番実行の前に無効化（Ctrl+T）します。要素ごとの設定値は次の表のとおりです。

/bearer: $.authenticated／チェックする／true

ログインは Once Only Controller で1スレッド1回だけです。一方、CSV Data Set Config は周回ごとに次の行を読むため、2周目以降の ${user} は、実際にログインしたユーザーとは別の値に入れ替わります（第8章）。そこで、ログイン時の応答から実際にログインしたユーザー名を loginUser に保存し、注文では ${user} ではなく、この loginUser と、ログインで取得した token を使います。

ログインで使う CSV は、第8章で作った users.csv をそのまま使います。ch14-final.jmx と同じ作業フォルダ（jmeter-practice）に置いてください（相対パスは .jmx の場所が基準です）。内容は次のとおりで、見出し行はありません。

jmeter-practice/users.csv 
alice,pass1111
bob,pass2222
carol,pass3333
dave,pass4444
eve,pass5555

注意: この演習は「20人の異なる利用者」を再現していない

CSV は5行で、Recycle on EOF が True なので、20スレッドには5つのアカウントが繰り返し割り当てられます。つまり、本演習は5アカウントを20仮想ユーザーで共有する方式（第8章の方法A）です。go-httpbin はアカウントを管理しておらず、同じアカウントでの多重ログインも問題にならないため、学習用としてこの方式を使います。

実際のシステムで、同じアカウントの多重ログインを許さない場合や、ユーザーごとのデータ量の違いまで再現したい場合は、1仮想ユーザーに1アカウントを割り当てる方式（方法B）を使います。

  • 仮想ユーザー数以上のアカウントを用意する（20スレッドなら原則20アカウント以上）。
  • アカウントを使い回さず、不足したら気づける設定にする（Recycle on EOF を False・Stop thread on EOF を True）。
  • ログイン状態と CSV の行の対応を保つ。CSV は周回ごとに次の行を読むため、20行の CSV を用意するだけでは、周回をまたいでユーザーを固定できません。読み込むタイミングと変数の保存方法まで設計します（第8章 8.5）。

ヒント: 既存のファイルを再利用する

第8〜10章で作った ch10-scenario.jmx などを 名前を付けて保存（File → Save Test Plan as...）で ch14-final.jmx として複製し、足りない部分だけ付け足すのが近道です。要素の名前（Name 欄）は、レポートに表示されるので、T01_Top のように意味の分かる名前にしておきましょう。

14.4 スモークテスト

スクリプトができたら、いきなり負荷をかけず、GUI で1ユーザー・1回だけ実行して動作を確認します。Thread Group の Number of Threads を ${__P(users,1)} のまま（既定の 1）にしておき、Loop Count を一時的に 1 にして、Specify Thread lifetime のチェックを外すと、1周だけで止まります。

確認する場所 期待する状態
View Results Tree すべてのサンプルに緑のアイコンが付く（赤が1つもない）
T02_Login の /bearer の Response data "authenticated": true が返っている（トークンの相関が成功）
T03_Browse の Request item= に ${...} のままではなく、1〜100 の数字が入っている
T02_Login の /post の Response data json の user に CSV の1行目のユーザー（alice）が入っている
T05_Order の Request Body の user に loginUser の値（alice）、token に UUID が入っている（NOT_FOUND ではない）
Transaction の行 T01〜T05 のトランザクション行が表示され、T03_Browse は3回出る

スモークテストの合格ライン

「全サンプルが成功」「変数が埋まっている」「トークンが渡っている」の3つがそろったら合格です。1つでも崩れていれば、まだ本番実行に進んではいけません。Debug Sampler と JSON Path Tester（第9章）で原因を探してください。

合格したら、Thread Group の設定を元（Loop Count を Infinite、Specify Thread lifetime にチェック）に戻します。デバッグ用に小さくした値を戻し忘れるのは、第12章で見たとおり典型的な失敗です。

14.5 段階的な本番実行

本番実行は CLI モードで行います。目標は 20 ユーザーですが、最初から 20 ユーザーで実行せず、5 → 10 → 20 ユーザーと段階を踏みます。段階的に上げると、「どの負荷から応答時間が伸び始めるか」が見え、問題の起きた条件を特定しやすくなります。

段階 users duration（秒） 結果の保存先
1回目 5 60 results/u05/
2回目 10 120 results/u10/
3回目（目標条件） 20 180 results/u20/

第12章で JMeter の bin フォルダに PATH を通した前提で、macOS/Linux では次のように実行します。-J で第8章の ${__P()} に値を渡し、第12章で学んだとおり、結果ファイル（result.jtl）とレポート（report/）を段階ごとのフォルダに分けて保存します。前回の結果を消してしまわないよう、-f は付けません。

terminal（macOS / Linux） 
# 作業フォルダへ移動して、段階ごとの保存先フォルダを用意する
cd ~/Documents/jmeter-practice
mkdir -p results/u05 results/u10 results/u20

# 1回目: 5ユーザー・60秒（結果は results/u05 に保存）
jmeter -n -t ch14-final.jmx -Jusers=5 -Jduration=60 -l results/u05/result.jtl -e -o results/u05/report

# 2回目: 10ユーザー・120秒
jmeter -n -t ch14-final.jmx -Jusers=10 -Jduration=120 -l results/u10/result.jtl -e -o results/u10/report

# 3回目: 20ユーザー・180秒（目標の条件）
jmeter -n -t ch14-final.jmx -Jusers=20 -Jduration=180 -l results/u20/result.jtl -e -o results/u20/report

Windows（コマンドプロンプト）では、次のように実行します。

terminal（Windows） 
:: 作業フォルダへ移動して、段階ごとの保存先フォルダを用意する
cd %USERPROFILE%\Documents\jmeter-practice
mkdir results\u05 results\u10 results\u20

:: 3回目（20ユーザー・180秒）の例。1回目・2回目は users・duration と保存先を変える
jmeter.bat -n -t ch14-final.jmx -Jusers=20 -Jduration=180 -l results\u20\result.jtl -e -o results\u20\report

各段階のフォルダには、結果と一緒に実行条件のメモ（conditions.txt）をテキストエディタで作って残します。後から「この結果は、どんな条件で測ったものか」を追跡・再現できるようにするためです。

results/u20/conditions.txt（記入例） 
実行日時       : 2026-10-18 10:00〜10:03
テスト計画     : ch14-final.jmx
負荷条件       : users=20, rampup=10, duration=180
評価する期間   : 全スレッドがそろった後（開始から約10秒後〜終了）
テストデータ   : users.csv（5アカウントを20仮想ユーザーで共有）
環境           : JMeter 5.6.3 / JDK 21 / go-httpbin 2.25.0（同じ PC 上で実行）
JMeter 側の状態: CPU 最大 45%、メモリに余裕あり（タスクマネージャーで確認）
メモ           : 実行中は他の重い作業をしていない

同じ段階をやり直すときは、results/u20-2 のように新しいフォルダを作り、保存先を変えて実行します。前回の結果が不要だと確認できたときだけ -f を付けます（第12章）。

負荷をかける側（JMeter）も監視する

この演習では、JMeter と go-httpbin が同じ PCで動き、CPU やメモリを奪い合います。実行中はタスクマネージャー（Windows）、アクティビティモニタ（macOS）、top（Linux）で、JMeter（java のプロセス）と Docker の CPU・メモリを観察し、次の兆候がないか確かめます（第12章 12.7）。

  • JMeter の CPU 使用率が高止まりし、予定した負荷を生成できていない（Active Threads は増えたのに、スループットが伸びない）。
  • メモリが不足して、ガベージコレクション（GC）が頻発したり、OutOfMemoryError が出たりする。
  • View Results Tree などのリスナーが有効なままで、JMeter 自身が重くなっている。
  • PC 全体の CPU が上限に近く、JMeter とテスト対象のどちらが遅いのか区別できない。

観察した結果は conditions.txt に書き残します。負荷をかける側に余裕がなかった結果は、測定値として信頼できません。

重要ポイント: 実行前の最終チェック（第12章の復習）

  • View Results Tree などの重いリスナーと Debug Sampler を無効化したか
  • 接続先が localhost になっているか（HTTP Request Defaults）
  • 保存先（results/u05 など）が段階ごとに分かれていて、前回の結果を上書きしないか（-f は付けない）
  • 実行中は PC で別の重い作業をしていないか（測定値が歪みます）

14.6 結果の判定

results/u20/report/index.html を開き、14.2 で決めた目標と実測値を1行ずつ突き合わせます。判定には Statistics 表の T01_Top〜T05_Order の行（トランザクション行）を使い、応答時間はその行の 95th pct 列、エラー率は同じ行の Error % 列から読み取ります（第13章）。Total 行は、どの行がどう含まれた値かが読み取りにくいため、判定には使いません。遅いトランザクションがあれば、同じ表のリクエスト単位の行で、どのリクエストが遅いかを確かめます。判定の結果は、次のような表に書き込みます。

項目 目標 実測（記入例） 判定

重要ポイント: 評価する期間をはっきりさせる

性能テストでは、負荷を増やしているランプアップの期間と、目標の負荷に達した後の安定測定期間を区別します。180秒の結果には、最初の約10秒間（20ユーザーがそろう前）の値も含まれているため、180秒全体の結果が、そのまま「20ユーザーの定常負荷での性能」を表すわけではありません。この演習ではランプアップが全体の約6%と短いので影響は小さめですが、実務では次の手順で評価期間を決めます。

  • Active Threads Over Time で、目標の人数（20）に達した時刻と、最後まで維持できたかを確認する。
  • 起動直後のキャッシュなどが温まるまでのウォームアップと、ランプアップを除いた区間を評価の対象と決める。
  • 第13章 13.5 の方法で、その区間だけのレポートを作り直して判定する。

報告書には、ウォームアップ・ランプアップ・安定測定の時間、実際のアクティブスレッド数、対象期間のスループットとエラー率をあわせて書きます（14.7）。

判定で大切なのは、合否だけでなく「なぜそうなったか」の仮説を添えることです。不合格の項目があれば、次の観点で原因を整理します。

  • 5 → 10 → 20 ユーザーの結果を並べたとき、どの段階から応答時間が伸びたか（限界に近づくサインは第13章）。
  • Errors 表に出たエラーの種類は何か。特定のトランザクションに偏っていないか。
  • JMeter を動かしている PC の CPU・メモリに余裕はあったか（測定側の限界ではないか）。
  • サーバー側の CPU・メモリ・DB・ログに異常はなかったか。JMeter が示すのは「どこが遅いか」までで、「なぜ遅いか」はサーバー側の調査が必要です。

1つ目の観点は、3段階の結果を比較表にまとめると読み取りやすくなります。トランザクションごとに、次の表を作ってみましょう（スループットは、そのトランザクション行の Transactions/s ＝ 業務操作/秒です）。

  • 応答時間が急に伸びた段階があれば、どのような原因が考えられるか。
  • スループットが伸びなくなったとき、それは必ずサーバー側の限界を意味するか。JMeter 側の CPU・メモリ（14.5）や、ユーザー数を固定する負荷モデルの性質（第5章 5.4）も踏まえて考える。

報告書の注意: 学習環境の数値は本番の性能値ではない

この演習では、JMeter と go-httpbin が同じ PCで動き、ネットワークの遅延もありません。そのため、得られた数値は学習用の目安であり、本番システムの性能値ではありません。実務の報告書では、測定した環境と本番環境の違い（サーバーの性能、台数、ネットワーク、データ量）を必ず明記し、「この結果から本番についてどこまで言えるか」を書き添えましょう。

14.8 次のステップ

お疲れさまでした。これで性能テストの基本の流れを一通り体験できました。さらに力をつけたいときは、次のテーマに進んでみましょう。

分散テスト

1台の PC では出せない大きな負荷を、複数の PC（JMeter のリモート実行）に分けてかけます。まずは公式マニュアルの「Remote Testing」を読んでみましょう。

CI への組み込み

CLI モードはコマンド1つで動くため、GitHub Actions などで定期的に実行し、性能の劣化を早く見つけられます。.jmx はテキストなので Git で管理できます。

サーバー監視との併用

テスト中のサーバーの CPU・メモリ・DB・ログを同時に記録すると、「なぜ遅いか」を突き止められます。

プラグインの活用

Plugins Manager（第2章）から、段階的に負荷を上げる Custom Thread Groups などを追加できます。

関連する学習ガイドも、あわせて活用してください。

  • Docker 学習ガイド — テスト対象や JMeter の実行環境をコンテナで用意する
  • Linux・コマンドライン学習ガイド — サーバー上で CLI 実行やリソース監視を行う
  • Git/GitHub 学習ガイド — テスト計画（.jmx）をバージョン管理し、CI で実行する
  • JUnit 学習ガイド — 機能面の自動テストを学ぶ

理解度確認クイズ

  1. Q1. 本番実行の前にスモークテストを行うのはなぜですか？ 何を確認しますか？

    回答を表示

    スクリプト自体の間違い（URL のミス、変数が埋まらない、トークンの相関の失敗など）を抱えたまま負荷をかけると、「システムが遅い」のか「スクリプトが間違っている」のか区別できなくなるからです。1ユーザー・1ループで実行し、全サンプルが成功すること、変数が正しく埋まっていること、トークンが次のリクエストに渡っていることを確認します。

  2. Q2. 負荷を一気に最大にせず、5 → 10 → 20 ユーザーと段階的に上げるのはなぜですか？ また、各段階の結果を別のフォルダに保存するのはなぜですか？

    回答を表示

    段階的に上げると、どの負荷から応答時間が伸びたりエラーが出たりするかが分かり、問題が起きた条件を特定しやすくなるからです。結果を段階ごとに別フォルダへ保存すれば、後から各段階のレポートを並べて比べられ、上書きによる結果の消失も防げます。

  3. Q3. この演習で得た応答時間の数値を、報告書にそのまま「本番の性能」として書いてはいけないのはなぜですか？

    回答を表示

    学習環境では JMeter と go-httpbin が同じ PC で動き、ネットワークの遅延もないため、サーバーの性能・台数・ネットワーク・データ量が異なる本番とは条件がまったく違うからです。得られた数値は学習用の目安にすぎないので、報告書には測定環境と本番との違いを明記し、結果から本番についてどこまで言えるかを書き添えます。

  4. Q4. 5 → 10 → 20 ユーザーと増やしたところ、20ユーザーでスループットが伸びなくなりました。これは必ずサーバー側の限界を意味しますか？

    回答を表示

    必ずしもそうとは言えません。JMeter 側の CPU・メモリが限界に近く、予定した負荷を生成できていない可能性があります（特にこの演習では JMeter と go-httpbin が同じ PC でリソースを奪い合います）。また、ユーザー数を固定する負荷モデルでは、応答が遅くなるとリクエストの送信間隔も延びるため、スループットは自然に伸びにくくなります。JMeter 側のリソース、応答時間とエラーの推移、サーバー側の監視結果をあわせて確かめてから判断します。

  5. Q5. この演習の CSV（5アカウント）と 20 仮想ユーザーの組み合わせは、何を再現していて、何を再現していませんか？

    回答を表示

    20の仮想ユーザーが並行して操作する負荷は再現していますが、5つのアカウントを繰り返し共有しているため、「20人の異なる利用者」は再現していません。同じアカウントの多重ログインを許さないシステムや、ユーザーごとのデータの違いが性能に影響するシステムでは、仮想ユーザー数以上のアカウントを用意し、CSV の読み込みタイミングと変数の保存方法まで設計して、1仮想ユーザーに1アカウントを割り当てます。
