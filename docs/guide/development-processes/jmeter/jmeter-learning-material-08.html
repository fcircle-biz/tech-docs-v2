変数とCSVデータでパラメータ化する

これまでのテスト計画は、すべての仮想ユーザーが「同じ値」でリクエストを送っていました。現実の利用者はそれぞれ違うユーザー ID を使い、違う商品を見ます。この章では、変数・関数・プロパティ・CSV ファイルを使ってリクエストの値を差し替える「パラメータ化」を学び、ユーザーごとに異なるデータでテストを実行できるようにします。

この章で学ぶこと

  • パラメータ化が必要な理由を説明できる
  • 変数（${変数名}）と関数（${__Random(...)} など）をリクエストに埋め込める
  • CSV Data Set Config で CSV の各行を、スレッドごと・イテレーションごとに読み込める
  • 変数とプロパティの違いを理解し、${__P(...)} で外から値を渡す準備ができる
  • Debug Sampler で変数の中身を確認できる

8.1 なぜパラメータ化するのか

たとえば 100 人分の仮想ユーザーが、全員同じユーザー ID で、同じ商品ページを何度も開いたとします。サーバーやデータベースは「同じ問い合わせ」を繰り返し受けるため、結果をキャッシュ（一時保存）から返せてしまい、現実よりも速く見えることがあります。逆に、同じユーザーで同時にログインすると「二重ログイン」としてエラーになるシステムもあります。

このように、リクエストの中の固定値を、実行のたびに（またはユーザーごとに）変わる値へ置き換えることを、パラメータ化と呼びます。JMeter では次の 4 つの仕組みを使い分けます。

変数（Variable）

名前を付けた値の入れ物。${user} のように参照する。スレッドごとに独立している。

関数（Function）

乱数・現在時刻・連番・UUID などを、その場で計算して返す。${__Random(1,100,)} のように書く。

CSV データ

ユーザー ID・パスワードなどの一覧をファイルに用意し、1 行ずつ変数として読み込む。

プロパティ（Property）

JMeter 全体で共有される設定値。コマンドラインから -Jusers=20 のように外から渡せる。

flowchart LR A["値の出どころ
変数・関数・CSV・プロパティ"] --> B["リクエストの中の
${...} が実行時に置き換わる"] B --> C["スレッドごとに
異なる値でリクエスト送信"]

8.2 変数の基本

もっとも簡単な変数は、User Defined Variables（ユーザー定義変数）で作ります。Test Plan を選ぶと右側に「User Defined Variables」の表があり、そこに名前と値を書くだけです。専用の要素として追加する場合は、Thread Group を右クリックして Add → Config Element → User Defined Variables を選びます。

Name Value 説明
itemId 42 商品番号の固定値
keyword jmeter 検索キーワード

変数を使うときは、HTTP Request の Path や Parameters、Body Data など、文字を入力できる欄のほとんどに ${変数名} と書きます。実行時に JMeter がその部分を変数の値へ置き換えてからリクエストを送ります。たとえば Path に /anything/items/${itemId} と書けば、実際には /anything/items/42 へアクセスします。

変数はスレッドごとに独立している

JMeter の変数は、スレッド（仮想ユーザー）ごとに別々の値を持てます。スレッド 1 が user に alice を入れても、スレッド 2 の user には影響しません。後述の CSV Data Set Config や、第 9 章の相関で取り出した値も、このスレッドごとの変数に入ります。

注意: User Defined Variables は「実行中に値が変わる変数」には向かない

User Defined Variables は、テスト開始時にまとめて設定される「定数」のような使い方に向いています。ユーザーごとに変わる値は CSV Data Set Config や第 9 章の抽出機能で作る変数を使い、固定の共通値だけを User Defined Variables に置くと混乱しません。

8.3 関数

関数は、実行時に値を計算して返す小さな部品です。${__関数名(引数1,引数2,...)} という形で、変数と同じように入力欄へ書きます。関数名の前にはアンダースコアが 2 つ付きます。

書き方 返す値 使いどころ
${__Random(1,100,)} 1 以上 100 以下の整数の乱数（第 3 引数は結果を保存する変数名で、省略可） 商品番号をばらつかせる
${__time(yyyyMMddHHmmss,)} 指定した書式の現在日時（例: 20261018153045）。第 2 引数は結果を保存する変数名で省略可 注文番号や名前を一意にする
${__threadNum} そのスレッドの番号（1 から始まる） ユーザーごとに別の値を作る
${__UUID()} ランダムな UUID（毎回違う文字列） 重複しない ID を作る
${__counter(FALSE,)} 1 から始まる連番。FALSE は全スレッドで共有、TRUE はスレッドごとに数える。書いた場所ごとに別のカウンターになる その場所が実行された回数を番号にする

関数の引数の書き方を忘れても、JMeter のメニュー Tools → Function Helper Dialog から確認できます。ダイアログで関数を選んで引数を入力し、Generate ボタンを押すと、貼り付け用の文字列（例: ${__Random(1,100,)}）が表示されます。Copy and Paste function string の欄からコピーして、入力欄に貼り付けましょう。

重要ポイント: 末尾のカンマは省略した引数の場所

${__Random(1,100)} と書いても動きますが、本ガイドでは Function Helper Dialog が生成する形（末尾カンマ付き）に揃えます。

8.4 CSV Data Set Config

ユーザー ID とパスワードの組のように、決まったデータの一覧を使いたいときは CSV ファイルを用意します。CSV（Comma-Separated Values）は、値をカンマで区切って 1 行 1 件で書いたテキストファイルです。まず作業フォルダ jmeter-practice に、次の内容で users.csv を作ります。文字コードは UTF-8 で保存してください。

jmeter-practice/users.csv 
alice,pass1111
bob,pass2222
carol,pass3333
dave,pass4444
eve,pass5555

この例では 1 行目からデータを書いています（見出し行なし）。第14章でも同じ users.csv を使います。次に、Thread Group を右クリックして Add → Config Element → CSV Data Set Config を追加し、次のように設定します。

項目 設定値 説明
Filename users.csv CSV ファイルの場所。相対パスで書くと、.jmx ファイルがあるフォルダが基準になる
File encoding UTF-8 ファイルの文字コード。日本語を含めるなら必ず指定する
Variable Names (comma-delimited) user,password 各列に付ける変数名。左の列から順に割り当てられる
Ignore first line False 先頭行を読み飛ばすか。見出し行があるファイルでは True（Variable Names を書いたときだけ有効）
Delimiter (use '\t' for tab) , 列の区切り文字。タブ区切りなら \t
Allow quoted data? False 値をダブルクォートで囲む CSV（値の中にカンマを含む）のときだけ True
Recycle on EOF? True 最後の行まで読んだら先頭へ戻るか
Stop thread on EOF? False 最後の行まで読んだらスレッドを止めるか（Recycle が True のときは無視される）
Sharing mode All threads ファイルを誰と共有して読むか（8.5 で説明）

ヒント: 見出し行付きの CSV

1 行目に user,password という見出しがある CSV を使うなら、Ignore first line を True にします。Variable Names を空欄にすると、1 行目の見出しがそのまま変数名として使われます（この場合 Ignore first line は無効）。本ガイドでは、変数名を画面で見えるように Variable Names を明示する方式を使います。

8.5 CSV の読み込まれ方

CSV Data Set Config は、スレッドがテスト計画を 1 周（1 イテレーション）するたびに、次の 1 行を読み込んで変数に入れます。「スレッドが起動した瞬間に全行を読む」のではない点に注意してください。たとえば 1 スレッドでループ回数 5 なら、1 周目は alice、2 周目は bob、……と順に変わります。

flowchart TD A["1周目の開始"] --> B["CSVの1行目を読む
user=alice"] B --> C["リクエスト送信
user=alice"] C --> D["2周目の開始"] D --> E["CSVの2行目を読む
user=bob"] E --> F["リクエスト送信
user=bob"] F --> G["最終行まで来たら
Recycle on EOFなら先頭へ戻る"]

複数のスレッドがあるときに、行をどう配るかを決めるのが Sharing mode です。

Sharing mode 動き 向いている場面
All threads テスト計画内の全スレッドで 1 つのファイルを共有し、読むたびに次の行へ進む ユーザーごとに別の行を使いたい（既定値）
Current thread group 同じ Thread Group 内のスレッドだけで共有する Thread Group ごとに別のデータを使いたい
Current thread 各スレッドが、自分専用のコピーを先頭から読む 全ユーザーが同じ順序でデータを使ってよい
任意の識別子（Edit を選んで入力） 同じ文字列を入力した CSV Data Set Config どうしでファイルを共有する 複数の設定で同じファイルを共有したい
flowchart LR subgraph ALL["All threads"] F1["users.csv"] -->|"次の行を順番に配る"| T1["スレッド1: alice"] F1 --> T2["スレッド2: bob"] F1 --> T3["スレッド3: carol"] end subgraph CUR["Current thread"] G1["users.csvのコピー"] --> U1["スレッド1: alice, bob, ..."] G2["users.csvのコピー"] --> U2["スレッド2: alice, bob, ..."] end

注意: 行数より多く読むと値が繰り返される

データが 5 行しかないのに 10 ユーザーでテストすると、Recycle on EOF が True なら先頭に戻って同じユーザーが再登場します。「同じユーザーが同時に使うとエラーになる」システムでは、必要な数の行（下の重要ポイント）を用意し、Recycle on EOF を False・Stop thread on EOF を True にして、データが尽きたらスレッドを止めます。複数スレッドで読むときは、どのスレッドがどの行を取るかの順序は実行のたびに入れ替わりうるため、行と順番が一対一で決まるとは限りません。

重要ポイント: 仮想ユーザーとアカウントの対応を設計する

CSV の行は周回ごとに進みます。そのため、(1) 同じスレッドでも周回ごとに別のユーザーの値に入れ替わり、(2)「仮想ユーザー数ぶんの行」だけでは、2周目以降に行が足りなくなります。1人の仮想ユーザーがどのアカウントを使い続けるかは、次のどちらかの方針で決めましょう。

  • 方法A（アカウントを共有してよい場合）: Recycle on EOF を True にして行を繰り返し使います。ログインに使った値は別の変数に保存し、以後はその変数を使います（第14章で実践します）。少ないアカウントを多くの仮想ユーザーで共有するので、異なる利用者を人数ぶん再現しているわけではありません。同じアカウントの多重ログインを許さないシステムには使えません。
  • 方法B（1仮想ユーザー＝1アカウント）: 仮想ユーザー数以上のアカウントを用意し、行を使い回さない設定（Recycle on EOF を False・Stop thread on EOF を True）にして、不足したらスレッドが止まって気づけるようにします。ただし、行は周回ごとに消費されるため、何周もさせるなら「スレッド数 × 周回数」の行が必要です。周回をまたいで1スレッドを1アカウントに固定したいときは、__CSVRead 関数（スレッドが最初にファイルを参照したときに未使用の行を1つ割り当て、next を指定しない限り同じ行を返し続ける）を使うなど、読み込むタイミングと変数の保存方法まで含めて設計します。

8.6 プロパティで外から値を渡す

同じテスト計画を「10 ユーザー」「20 ユーザー」「50 ユーザー」と条件を変えて実行したいとき、そのたびに .jmx を開いて書き換えるのは面倒でミスのもとです。そこで、プロパティを使います。プロパティは JMeter の起動時に渡せる設定値で、${__P(プロパティ名,既定値)} という関数で読み取ります。

たとえば Thread Group の Number of Threads (users) 欄に ${__P(users,5)} と書いておくと、「users というプロパティが渡されていればその値、無ければ 5」をスレッド数に使います。こう書き換えておけば、次のようにコマンドラインから -Jusers=20 を渡してユーザー数を切り替えられます。

terminal（第12章で本格的に使います） 
# イメージ（実際に試すのは第12章）。jmeter-practice フォルダで実行する
# macOS / Linux
cd ~/Documents/jmeter-practice
~/tools/apache-jmeter-5.6.3/bin/jmeter -n -t ch08-parameters.jmx -Jusers=20
# Windows（PowerShell）
cd $HOME\Documents\jmeter-practice
C:\tools\apache-jmeter-5.6.3\bin\jmeter.bat -n -t ch08-parameters.jmx -Jusers=20

GUI から開いて動かすときは、-J を渡さない限り既定値の 5 が使われます。この「GUI では既定値、CLI では外から上書き」の形は、第 12 章で本格的に使います。

ここで、変数とプロパティの違いを整理しておきましょう。

比較項目 変数（Variable） プロパティ（Property）
範囲 スレッドごと（ユーザーごとに別の値） JMeter 全体で 1 つ（全スレッド共通）
参照方法 ${user} ${__P(users,5)}
値の与え方 User Defined Variables、CSV、抽出（第 9 章）など 起動時の -Jname=value、user.properties など
主な用途 ユーザーごとに違うデータ 負荷条件（ユーザー数・時間）や接続先の切り替え

8.7 値の確認（Debug Sampler）

「変数に思った値が入っているか分からない」ときは、Debug Sampler を使います。Thread Group を右クリックして Add → Sampler → Debug Sampler を追加し、設定は次のとおりにします。

項目 設定値 説明
JMeter properties False プロパティ一覧は出さない（量が多い）
JMeter variables True そのスレッドの変数一覧を応答として出す
System properties False Java のシステムプロパティは出さない

あとは View Results Tree を置いて実行し、Debug Sampler を選んで Response data タブを見ると、user=alice・password=pass1111 のように、その時点の変数が一覧で表示されます。ここに変数が出ていなければ、CSV Data Set Config の置き場所（スコープ）や Variable Names の綴りを疑います。

注意: Debug Sampler は確認が終わったら無効化する

Debug Sampler もサンプルとして記録されるため、残したまま負荷テストをするとレポートの件数や応答時間に混ざってしまいます。確認が終わったら要素を右クリックして Disable（または Ctrl+T）で無効にしましょう。第 12 章の実行前チェックリストにも入ります。

やってみよう 8-1: CSV のユーザーを POST のボディに埋め込む

go-httpbin を起動した状態で ch08-parameters.jmx を作り、CSV の user 列が実行のたびに変わることを、応答の json.user で確認します。

手順

  1. 1 jmeter-practice に 8.4 の users.csv を作り、JMeter で新しいテスト計画を作って ch08-parameters.jmx として同じフォルダに保存する。
  2. 2 Thread Group を追加し、Number of Threads を 1、Loop Count を 5 にする（1 人が 5 周するので、CSV の 5 行が順に使われる）。
  3. 3 Thread Group に HTTP Request Defaults（Protocol http／Server Name localhost／Port 8080）と CSV Data Set Config（8.4 の表の設定）を追加する。
  4. 4 HTTP Header Manager を追加し、Content-Type: application/json を設定する。
  5. 5 HTTP Request を追加し、Method を POST、Path を /post にして、Body Data に下のJSONを書く。
  6. 6 View Results Tree を追加して実行し、5 件のリクエストそれぞれの Response data で json の中の user が alice → bob → carol → dave → eve と変わることを確認する。
HTTP Request の Body Data 
{
  "user": "${user}",
  "password": "${password}"
}
確認ポイント: go-httpbin の /post は、送った JSON をそのまま応答の json フィールドに入れて返します。応答の user が <EOF> なら CSV ファイルが見つかっていません（Filename の綴り、.jmx と同じフォルダに保存したか、.jmx を保存済みか）。${user} のまま返ってきたら、Variable Names の綴りと Body Data の変数名が合っているかを確認しましょう（8.7 の Debug Sampler も役立ちます）。

やってみよう 8-2: 乱数で商品番号を変える

同じ ch08-parameters.jmx に、関数で毎回違う商品番号を使うリクエストを追加します。

手順

  1. 1 User Defined Variables を追加し、Name itemId／Value ${__Random(1,100,)} を登録する（実行開始時に 1 回だけ決まる値になる）。
  2. 2 新しい HTTP Request（GET）を追加し、Path を /anything/items/${__Random(1,100,)} にする（こちらはリクエストのたびに新しい乱数になる）。
  3. 3 Debug Sampler を追加し、JMeter variables だけ True にして実行する。View Results Tree で、アクセス先 URL が毎回違う番号になること、Debug Sampler の出力に itemId が表示されることを確認する。
  4. 4 確認できたら Debug Sampler を無効化し、ch08-parameters.jmx を保存する。
考えてみよう: 手順 1 の itemId は何度実行しても 1 回の実行中は同じ値で、手順 2 の Path 直書きはリクエストのたびに変わります。「ユーザーごと・リクエストごとにばらつかせたい」ときは、どちらを選ぶべきでしょうか。

理解度確認クイズ

  1. Q1. 変数（${user}）とプロパティ（${__P(users,5)}）の違いを、範囲と主な用途の面から説明してください。

    回答を表示

    変数はスレッド（仮想ユーザー）ごとに別の値を持てる入れ物で、ユーザーごとに違うデータ（CSV の行など）に使います。プロパティは JMeter 全体で共有される 1 つの設定値で、-Jusers=20 のように起動時に外から渡せるため、ユーザー数や実行時間などの負荷条件を切り替える用途に向いています。

  2. Q2. CSV Data Set Config の Filename に users.csv とだけ書いたとき、このファイルはどこから探されますか？ また、データが 5 行で 10 ユーザーが実行すると、Recycle on EOF が True の場合どうなりますか？

    回答を表示

    相対パスは、テスト計画（.jmx）が保存されているフォルダが基準になります。行数が足りなくなると、Recycle on EOF が True なので先頭の行へ戻り、同じユーザーのデータが再び使われます。同じユーザーの重複を避けたいときは、行数をユーザー数以上に増やすか、Recycle on EOF を False・Stop thread on EOF を True にします。

  3. Q3. 1 スレッド・ループ回数 5 のテスト計画に CSV Data Set Config を置くと、CSV の行はいつ読み込まれますか？ 変数の中身を確認するにはどの要素を使いますか？

    回答を表示

    スレッドがテスト計画を 1 周（1 イテレーション）するたびに次の 1 行が読み込まれるため、5 周で 5 行が順に使われます。変数の中身は Debug Sampler で JMeter variables を True にして実行し、View Results Tree の Response data で確認します。
