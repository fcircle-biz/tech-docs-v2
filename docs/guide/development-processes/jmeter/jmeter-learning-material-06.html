ホーム JMeter 第6章
第6章 所要時間: 約1時間

タイマーで現実的なアクセスを再現する

実際の利用者は、ページを読んだり入力したりしながら操作するため、リクエストの間に「間」があります。JMeter のスレッドは、何も指定しなければ待ち時間なしでリクエストを連打します。この章では、利用者の「間」（思考時間）の意味と、それを再現する Timer（タイマー）の種類・スコープ・使い方を学びます。

この章で学ぶこと

  • 思考時間（Think Time）の意味と、タイマーが無いと負荷が過大になる理由を説明できる
  • 主要なタイマーの違いを理解し、目的に合うものを選べる
  • タイマーのスコープと、複数のタイマーが合算されるルールを理解する
  • Constant Throughput Timer で目標スループットに合わせて負荷を制御できる

6.1 タイマーが無いとどうなるか

第5章で作ったスレッドグループは、スレッド（仮想ユーザー）がサーバーから応答を受け取ると、すぐに次のリクエストを送ります。人間の利用者なら、ページを読む、商品を比べる、フォームに入力するといった時間があるので、リクエストの間には数秒〜数十秒の「間」があります。この間を思考時間（Think Time）と呼びます。

思考時間を入れないと、1スレッドが現実の利用者何十人分ものリクエストを出してしまいます。たとえば応答に0.5秒かかるシステムで、実際の利用者が平均5秒おきに操作するなら、待ちなしのスレッドは約10倍の負荷を生みます。これでは「100人が使ったとき」ではなく「1,000人が使ったとき」のような過剰な負荷を測ってしまい、本来は問題のない性能を「遅い」と誤判定しかねません。

flowchart LR subgraph N["タイマー無し"] direction LR N1["リクエスト"] --> N2["応答"] --> N3["すぐ次のリクエスト"] end subgraph T["タイマーあり"] direction LR T1["リクエスト"] --> T2["応答"] --> T3["思考時間 待つ"] --> T4["次のリクエスト"] end

第5章 5.4 の式を思い出してください。同時ユーザー数 ＝ スループット ×（応答時間＋思考時間）でした。思考時間が0だと、同じスレッド数でもスループットが跳ね上がります。現実的な負荷を作るには、思考時間をタイマーで再現する必要があります。

用語: Timer（タイマー）

JMeter の Timer は「時計」ではなく、サンプラーを実行する前に待ち時間を挿入する要素です。第3章で学んだ実行順序のとおり、タイマーは各サンプラーの「前」に効きます。

6.2 タイマーの種類

タイマーは Thread Group を右クリックし、Add → Timer から追加します。目的別に代表的な5つを比べてみましょう。大きく分けて、待ち時間そのものを指定するタイプ（Constant・Uniform Random・Gaussian Random）と、目標スループットに合わせて待ち時間を自動調整するタイプ（Constant Throughput・Precise Throughput）があります。

タイマー 主な設定項目 待ち時間の決まり方・使いどころ
Constant Timer
固定の待ち時間		 Thread Delay (in milliseconds) 毎回同じ時間だけ待つ。もっとも単純。動作確認や、一定間隔で動く処理の再現に向く
Uniform Random Timer
一様乱数の待ち時間		 Random Delay Maximum (in milliseconds)
Constant Delay Offset (in milliseconds)		 待ち時間 ＝ Offset ＋ 0〜Maximum の乱数（どの値も同じ確率）。利用者ごとの「間」のばらつきを手軽に再現できる。最初の選択肢として使いやすい
Gaussian Random Timer
正規分布の待ち時間		 Deviation (in milliseconds)
Constant Delay Offset (in milliseconds)		 Offset を中心に、Deviation を標準偏差とする正規分布でばらつく（約7割が Offset ± Deviation に収まり、それより外れる値も出る）。「平均の付近が多く、極端な値は少ない」人間らしい間を表現できる
Constant Throughput Timer
目標スループットの制御		 Target throughput (in samples per minute)
Calculate Throughput based on		 全体の送信ペースが目標値（1分あたりの件数）に近づくよう待ち時間を自動で調整する。「毎秒○件の負荷」を狙いたいときに使う（6.4）
Precise Throughput Timer
より正確なスループット制御		 Target throughput (in samples per 'throughput period')、Throughput period (seconds)、Test duration (seconds) など 乱数でリクエストの到着間隔を生成し、指定した期間内の件数が目標に一致するよう制御する。短時間でも目標に収まりやすいが、設定項目が多い。紹介にとどめる

Uniform Random Timer の待ち時間を式で書くと次のとおりです。例として Constant Delay Offset = 2000、Random Delay Maximum = 1000 と設定すると、毎回 2000〜3000 ミリ秒（平均 2500 ミリ秒）の範囲で待つことになります。

Uniform Random Timer の待ち時間の計算 
# 待ち時間 = Constant Delay Offset + (0 以上 Random Delay Maximum 以下の乱数)
# Constant Delay Offset = 2000, Random Delay Maximum = 1000 の場合
待ち時間 = 2000 + (0 ～ 1000) = 2000 ～ 3000 ミリ秒

# 平均の待ち時間は Offset + Maximum / 2
平均 = 2000 + 1000 / 2 = 2500 ミリ秒（2.5秒）

重要ポイント: 待ち時間の単位はミリ秒

Constant Timer・Uniform Random Timer・Gaussian Random Timer の待ち時間はミリ秒で指定します（1000 ＝ 1秒）。「3秒待ちたい」のに 3 と入力してしまうミスが初心者に多いので注意しましょう。ただし、6.4 で説明する Constant Throughput Timer は1分あたりの件数、Precise Throughput Timer は指定した期間（秒）あたりの件数で指定します。

6.3 タイマーのスコープと合算

第3章で学んだスコープの考え方は、タイマーにも当てはまります。タイマーは自分の親の配下にある、すべてのサンプラーの前に実行されます。そのため、置く場所によって効く範囲が変わります。

  • Thread Group の直下に置く: その Thread Group 内のすべてのサンプラーの前で待つ。
  • サンプラーの子に置く: そのサンプラーの前だけで待つ。

さらに重要なルールがあります。同じサンプラーに効くタイマーが複数あるときは、待ち時間が合計されます（どれか1つが選ばれるのではありません）。次の図で、各サンプラーの前に何ミリ秒待つかを確認しましょう。

flowchart TD TG["Thread Group"] --> TA["Constant Timer 1000ms"] TG --> S1["HTTP Request: /get"] TG --> S2["HTTP Request: /html"] S2 --> TB["Constant Timer 500ms"] S1 -.- R1["/get の前に待つ時間: 1000ms"] S2 -.- R2["/html の前に待つ時間: 1000ms＋500ms＝1500ms"]

この例では、Thread Group 直下のタイマー（1000ms）が /get と /html の両方に効きます。さらに /html には子のタイマー（500ms）も効くため、合計 1500ms 待ちます。

注意: 最初のサンプラーの前でも待つ

タイマーは「サンプラーの前」に実行されるので、スレッドが起動して最初のサンプラーを実行する前にも待ち時間が入ります。「リクエストの間」だけに入ると思い込まないようにしましょう。また、タイマーはサンプラーが無い場所に置いても効果がありません（サンプラーが実行されなければ、待つ契機がないため）。

6.4 Constant Throughput Timer で目標スループットに合わせる

これまでのタイマーは「各スレッドが何ミリ秒待つか」を決めるものでした。しかし性能テストでは「サーバーに毎秒2件のリクエストを送り続けたい」のように、目標とするスループットが先に決まっていることも多くあります。このとき使うのが Constant Throughput Timer です。

項目 設定例 説明
Target throughput (in samples per minute) 120 目標とするスループット。1分あたりの件数で指定する。毎秒2件なら 2 × 60 ＝ 120
Calculate Throughput based on All active threads 目標をどの範囲のスレッドで分け合うかの選択（下表）

Calculate Throughput based on の選択肢は次のとおりです。

選択肢 目標スループットの意味
This thread only スレッド1つあたりの目標。スレッドが10個なら、全体では10倍になる
All active threads 起動中の全スレッドの合計が目標値になる（本ガイドの実習で使用）。Thread Group が複数あるときは、ほかの Thread Group にも同じ設定の Constant Throughput Timer が必要
All active threads in current thread group タイマーがあるスレッドグループ内の全スレッドの合計が目標値になる
All active threads (shared) All active threads と同じく全スレッドで目標を分け合う。ただし各スレッドの待ち時間を、自分の前回の実行ではなく、いずれかのスレッドが最後に実行した時刻を基準に計算する。全体のペースがより正確になる（shared でない方式は、スレッド間で件数が均等になりやすい）
All active threads in current thread group (shared) スレッドグループ内で目標を分け合い、グループ内のいずれかのスレッドが最後に実行した時刻を基準に待ち時間を計算する

スレッドグループが1つで、全体として毎秒2件に抑えたいだけなら、All active threads を選べば十分です。単位が「1分あたり」であることを、次の換算で確認しておきましょう。

毎秒の目標値を「毎分」に換算する 
# 目標: 毎秒 2 件 → 毎分に換算して入力する
Target throughput = 2 件/秒 × 60 秒 = 120

# 逆に、30 と入力した場合のペース
30 件/分 ÷ 60 = 0.5 件/秒（2秒に1件）

注意: 「上限を抑える」だけで「引き上げる」ことはできない

Constant Throughput Timer が行うのは、送信が速すぎるときに待ち時間を入れて目標に近づけることだけです。スレッドの数が足りなかったり、サーバーの応答が遅かったりして目標に届かないときに、自動で追加のリクエストを送ってはくれません。目標スループットを出したいなら、第5章 5.4 の式で必要なスレッド数を見積もり、余裕を持った数のスレッドを用意しましょう。

ヒント: 乱数の間とスループット制御の使い分け

「利用者の人間らしい間を再現したい」なら Uniform Random Timer や Gaussian Random Timer、「サーバーに毎秒○件の負荷をかけたい」なら Constant Throughput Timer が向いています。両方を同じスコープに置くと待ち時間が合算されて、目標どおりにならなくなりやすいので、目的に応じてどちらか一方を使うのが基本です。

補足: スループットの「上限」と「到着率」は別物

Constant Throughput Timer を使っても、負荷モデルは第5章 5.4 のユーザー数を固定する方式（クローズドモデル）のままです。各スレッドは応答を待ってから次のリクエストを送るので、システムが遅くなれば、目標の件数を下回ります。応答の遅さに関係なく「毎秒○件が届き続ける」状態（オープンモデル）を作りたいときは、Precise Throughput Timer や Open Model Thread Group を検討し、スレッド数にも十分な余裕を持たせます。どちらの場合も、テスト後に実際に出たスループットをレポートで確認することが大切です。

6.5 タイマーの待ち時間と応答時間

タイマーの待ち時間は、サンプルの応答時間（Load time）には含まれません。JMeter が計測するのは、サンプラーがリクエストを送り始めてから応答を受け取り終えるまでの時間だけです。思考時間として3秒待っても、View Results Tree や Summary Report の Average がその分だけ伸びることはありません。

flowchart LR A["タイマーの待ち時間
計測に含まれない"] --> B["サンプラーの実行
応答時間として計測"] --> C["次のタイマーの待ち時間
計測に含まれない"]

一方、複数のリクエストをまとめた「業務操作」の所要時間を計りたい場合は、Transaction Controller を使います。設定によってはタイマーの待ち時間を含めた時間を計ることもできます。これは第10章で学びます。

重要ポイント: 応答時間は変わらず、負荷だけが変わる

タイマーの待ち時間が、応答時間の数値に足されることはありません。タイマーで変わるのはサーバーに届くリクエストの頻度（スループット）です。タイマー無しで測った結果と、思考時間を入れて測った結果を比べると、同じスレッド数でも負荷の大きさがまったく違うことがわかります。なお、負荷が軽くなった結果として、サーバーの応答そのものが速くなることはあります。

やってみよう 6-1: タイマー無しと Uniform Random Timer を比べる

同じテスト計画で、タイマー無しの場合と思考時間を入れた場合のスループットを比べます。go-httpbin（localhost:8080）が起動していることを確認してから始めましょう。

手順

  1. 1 Test Plan に Thread Group を追加し、Number of Threads: 5、Ramp-up period: 1、Loop Count: 20 に設定する。
  2. 2 HTTP Request Defaults（Protocol http／Server localhost／Port 8080）と、Path が /get の HTTP Request、Summary Report を追加する。
  3. 3 jmeter-practice/ch06-timers.jmx として保存し、タイマー無しのまま実行。Summary Report の Throughput を控える。
  4. 4 結果を Clear All でクリアし、Thread Group を右クリック → Add → Timer → Uniform Random Timer を追加する。Random Delay Maximum (in milliseconds): 1000、Constant Delay Offset (in milliseconds): 2000 に設定する。
  5. 5 再び実行する（全リクエストが終わるまで約1分かかる）。Summary Report の Throughput を、タイマー無しの場合と比べる。
期待する結果: タイマー無しでは、ローカル環境なので1秒あたり数十〜数百件という高いスループットになります。タイマーを入れると、各スレッドが平均2.5秒おきに送るため、5スレッドの合計は 約2件/秒（5 ÷ 2.5）前後まで下がります。一方、Average（平均応答時間）はどちらもほぼ変わらないことも確認しましょう（6.5）。

やってみよう 6-2: Constant Throughput Timer で毎秒2件に制御する

スレッドの数に関係なく、全体の送信ペースを「毎分120件（毎秒2件）」に合わせてみます。

手順

  1. 1 6-1 で追加した Uniform Random Timer を無効化する（右クリック → Disable、または Ctrl+T）。
  2. 2 Thread Group を Number of Threads: 10、Loop Count: Infinite にチェック、Specify Thread lifetime にチェックして Duration (seconds): 60 に変更する。
  3. 3 Thread Group を右クリック → Add → Timer → Constant Throughput Timer を追加する。
  4. 4 Target throughput (in samples per minute): 120、Calculate Throughput based on: All active threads に設定して実行する。
  5. 5 60秒後、Summary Report の Throughput と # Samples を確認する。値を 30 に変えて再実行し、ペースが落ちることも確かめる。
期待する結果: Throughput は約 2.0件/秒、# Samples は60秒で約120件になります（起動直後は調整中のため多少ずれます）。目標を30にすると、# Samples は60秒で約30件に下がります。Throughput は1件/秒未満になるため、Summary Report では「/min」単位で表示されます（目安 30/min 前後。10スレッドが20秒おきにまとめて送るので、30/min より少し高めに出ることもあります）。スレッドを10個用意していても、全体のペースは目標値で抑えられる点に注目してください。

理解度確認クイズ

  1. Q1. タイマーを1つも置かずにテストを実行すると、なぜ現実より強い負荷になりますか？

    回答を表示

    各スレッドが応答を受け取ると待ちなしですぐ次のリクエストを送るためです。実際の利用者にはページを読む・入力するなどの思考時間があり、リクエストの間隔は数秒〜数十秒あります。待ちなしのスレッド1つは現実の利用者何十人分ものリクエストを出し、本来より過大な負荷を測ってしまいます。

  2. Q2. Thread Group 直下に Constant Timer（1000ms）を置き、その配下の HTTP Request A の子にさらに Constant Timer（500ms）を置きました。HTTP Request A の前に待つ時間は何ミリ秒ですか？ 同じ Thread Group 内の別の HTTP Request B ではどうなりますか？

    回答を表示

    A の前は 1000 ＋ 500 ＝ 1500ms です（同じサンプラーに効くタイマーは合計されます）。B には Thread Group 直下のタイマーだけが効くので 1000ms です。子のタイマーはその親のサンプラーにしか効きません。

  3. Q3. Constant Throughput Timer の Target throughput に 300 と入力しました。目標は毎秒何件ですか？ また、スレッドが少なすぎて目標に届かないとき、このタイマーは何をしてくれますか？

    回答を表示

    単位は「1分あたり」なので、300 ÷ 60 ＝ 毎秒5件です。このタイマーは、送信が速すぎるときに待ち時間を入れて目標へ近づけるだけで、スレッドが足りないときに負荷を引き上げることはしません。目標に届かない場合は、スレッド数を増やす必要があります。
