ロジックコントローラでシナリオを組み立てる

ここまでは、1つ1つのリクエストの作り方を学んできました。この章では、それらを「ログインは最初の1回だけ」「商品閲覧を3回繰り返す」「注文までをひとまとまりの操作として計測する」のように、実際の利用者の流れに沿って組み立てる方法を学びます。その役目を担うのが、ロジックコントローラです。

この章で学ぶこと

  • シナリオとロジックコントローラの役割を説明できる
  • Transaction Controller で複数リクエストを1つの業務操作として計測できる
  • Once Only・Loop・If の各コントローラで「1回だけ」「繰り返し」「条件分岐」を表現できる
  • Random Controller／Throughput Controller で操作の比率を表現し、入れ子の注意点を押さえる

10.1 シナリオとは

実際の利用者は、1つのページだけを延々と開き続けるわけではありません。たとえば EC サイトなら、「トップページを開く → ログインする → 商品を何度か見て回る → 注文する」というように、一連の操作を順に行います。この操作の流れをシナリオと呼びます。

性能テストでは、このシナリオを仮想ユーザー（スレッド）に繰り返し実行させます。サンプラー（HTTP Request）を並べるだけでも順番どおりには実行されますが、それだけでは「ログインは最初の1回だけ」「商品閲覧は3回繰り返す」「ときどき注文する」といった現実らしい流れは表現できません。そこで使うのが Logic Controller（ロジックコントローラ）です。

flowchart TD A["トップ表示"] --> B["ログイン（最初の1回だけ）"] B --> C["商品閲覧"] C -->|3回繰り返す| C C --> D["注文"] D -->|次のイテレーションへ| C

Logic Controller は、配下の要素をいつ・何回・どの順序で実行するかを制御する部品です。リクエストを送る機能そのものは持たず、サンプラーを入れる「入れ物」として働きます。Add → Logic Controller から追加できます。

コントローラ できること この章での節
Transaction Controller 複数のリクエストを1つの業務操作として計測する 10.2
Once Only Controller スレッドにつき最初の1回だけ実行する 10.3
Loop Controller 配下を指定回数だけ繰り返す 10.4
If Controller 条件が真のときだけ実行する 10.5
Random／Throughput Controller 操作の比率（閲覧80%・注文20% など）を表現する 10.6
While Controller 条件が真の間、繰り返す 10.7

ヒント: 「Simple Controller」は見た目を整理するだけ

Logic Controller には、実行を制御せず、サンプラーをただまとめるだけの Simple Controller もあります。タイマーやアサーションなどのスコープ（第3章）を限定したいときや、ツリーを見やすく整理したいときに使います。

10.2 Transaction Controller

利用者にとっての「1つの操作」は、実際には複数のリクエストでできていることがよくあります。たとえば「注文する」ボタンを押すと、在庫確認・決済・注文登録と、内部で3つの API が続けて呼ばれるかもしれません。利用者が感じるのは3つの合計の待ち時間です。

Transaction Controller（トランザクションコントローラ）は、配下の複数のサンプラーを1つの業務操作（トランザクション）としてまとめ、その合計の応答時間を1件のサンプルとして記録します。Add → Logic Controller → Transaction Controller で追加し、「注文」「ログイン」のように業務の言葉で名前を付けるのがコツです。

項目 既定値 説明
Generate parent sample オフ オンにすると、トランザクション全体を親サンプル1件として記録し、配下の各リクエストはその子（サブサンプル）として扱われます。集計には親だけが現れます。オフのときは、各リクエストの結果に加えて、トランザクション全体の行が別のサンプルとして追加されます
Include duration of timer and pre-post processors in generated sample オフ オンにすると、トランザクション内のタイマーの待ち時間や、Pre／Post Processor の処理時間も、トランザクションの時間に含めます。オフなら、純粋にサンプラーの時間だけです

2つの設定の影響を整理しましょう。「注文」トランザクションの中に2つのリクエスト（各 0.3秒）があり、1つ目のリクエストの子にタイマー（思考時間 2秒）を置いているとします。タイマーはサンプラーの実行前に待つので、その待ち時間がトランザクションの中に含まれるかどうかが違いになります。

Include duration of timer... 「注文」の時間 意味
オフ（既定） 約 0.6秒 システムの応答時間だけを見たいときに向いています
オン 約 2.6秒 利用者が操作を始めてから終えるまでの「体感の所要時間」を見たいときに使います

性能の目標（「注文は2秒以内」など）を評価する場合は、思考時間が混ざらないよう、オフのままにするのが一般的です。

重要ポイント: Generate parent sample の使い分け

レポートを「業務操作ごと」に見たいならオンにすると、Summary Report や HTML レポートの行が「ログイン」「注文」のように業務単位でそろいます。個々の API の遅さも知りたいならオフのままにして、リクエスト単位の行とトランザクション行の両方を見ます。本ガイドの実習では、両方の行が見えるオフを使います。

ただし、オフにしたときは集計の数え方に注意が必要です。配下の HTTP リクエストと、トランザクション全体の両方がサンプルとして記録されるからです。たとえば、3つのリクエストからなる「ログイン」トランザクションを100回実行すると、記録されるサンプルは次のようになります。

Generate parent sample がオフのときに記録されるサンプル 
ログイン（Transaction Controller）
├── GET /login       100件  ← リクエスト行
├── POST /auth       100件  ← リクエスト行
└── GET /profile     100件  ← リクエスト行
ログイン             100件  ← トランザクション行

# 実際に送った HTTP リクエストは 300件
# すべての行を足すと 400サンプルになる

注意: リクエスト行とトランザクション行を合算しない

すべての行を単純に合算すると、HTTP リクエストの件数と業務操作の件数が混ざり、件数・平均応答時間・エラー率・スループットの意味があいまいになります。業務操作の性能を評価するときはトランザクション行、個々の API（HTTP リクエスト）の性能を評価するときはリクエスト行を使いましょう。Summary Report の TOTAL 行は全行をまとめた値なので、トランザクション行のサンプルも含まれます（下の「やってみよう」で確かめます）。JTL を表計算ソフトなどで自分で集計するときも、label 列で両者を分けてから集計します。HTML レポートでの扱いは第13章で学びます。

10.3 Once Only Controller

Thread Group にループ回数を設定すると、スレッドはシナリオ全体を何周もします。しかし、現実の利用者はログインを1周ごとにやり直したりしません。ログインしたあとは、ログイン状態のまま何度も操作します。

Once Only Controller（ワンスオンリーコントローラ）は、配下の要素を各スレッドの最初のイテレーション（1周目）でだけ実行し、2周目以降は飛ばします。設定項目はありません。ログインで取得したトークン（第9章）を変数に保存し、2周目以降はその変数を使い回す、という使い方が典型です。

flowchart LR subgraph T1["1周目"] A1["Once Only：トークン取得"] --> B1["商品閲覧"] --> C1["注文"] end subgraph T2["2周目以降"] A2["Once Only：飛ばす"] --> B2["商品閲覧"] --> C2["注文"] end T1 --> T2

注意: 「1回だけ」の単位はスレッド

Once Only が1回なのは全体で1回ではなく、スレッドごとに1回です。10スレッドなら、ログインは10回（各スレッド1回ずつ）実行されます。また、Once Only を Loop Controller の中に置くと、「そのループの1周目」で実行され、次にループへ入り直すたびに再び1周目として実行されます。「スレッドにつき1回」にしたいときは、Thread Group の直下に置きましょう。

10.4 Loop Controller

Loop Controller（ループコントローラ）は、配下の要素を指定した回数だけ繰り返します。「1回のシナリオの中で、商品を3回閲覧する」といったシナリオの途中の繰り返しを表現できます。

項目 設定値の例 説明
Loop Count 3 繰り返す回数。${__P(views,3)} のように、変数やプロパティも書けます
Infinite オフ オンにすると無限に繰り返します。止めるのは別の仕組み（Thread Group の Duration など）に任せます

ここで気になるのが、Thread Group の Loop Count との違いです。2つは入れ子になります。Thread Group の Loop Count を 2、Loop Controller の Loop Count を 3 にすると、Loop Controller 内のサンプラーは各スレッドで 2 × 3 ＝ 6 回実行されます。

項目 Thread Group の Loop Count Loop Controller の Loop Count
繰り返す範囲 シナリオ全体 コントローラの配下だけ
Once Only との関係 2周目から Once Only が飛ばされる 配下に Once Only があると、2周目以降は飛ばされる
使いどころ 1人の利用者が何周も使う全体の長さ 「商品を3回見る」のような局所的な反復

ヒント: 毎回違う商品を見るには

Loop Controller の中の HTTP Request に /get?item=${__Random(1,100,)} のように関数（第8章）を使うと、3回とも別の値でアクセスできます。同じ値を3回送ってしまうとキャッシュで速くなり、現実より良い数値が出てしまいます。

10.5 If Controller

If Controller（イフコントローラ）は、条件が真のときだけ配下の要素を実行します。たとえば「トークンの取得に成功したときだけ注文する」「前のレスポンスに特定の値があったときだけ次の処理をする」といった条件分岐に使います。

項目 設定値の例 説明
Condition (default Javascript) 下のコード例 実行する条件。最終的に true になれば配下を実行します
Interpret Condition as Variable Expression? オン 条件欄を「JMeter の変数・関数の式」として評価します。オフだと JavaScript として評価され、重くて遅くなります
Evaluate for all children? オフ オフなら条件の判定は入るときの1回だけ。オンなら配下の要素1つごとに判定し直します

Interpret Condition as Variable Expression? をオンにして、__jexl3 関数で条件を書くのが推奨の形です。第9章で JSON Extractor の Default Value に NOT_FOUND を設定したことを思い出してください。抽出に失敗したときだけ値が NOT_FOUND になるので、それを判定に使えます。

If Controller の Condition 欄（トークンが取れているとき、つまり NOT_FOUND ではないときだけ実行） 
${__jexl3("${token}" != "NOT_FOUND")}
If Controller の Condition 欄（変数 orderMode が premium のときだけ実行する別の例） 
${__jexl3("${orderMode}" == "premium")}
flowchart TD A["トークン取得（/uuid）"] --> B{"token 変数は NOT_FOUND ではないか"} B -->|はい| C["注文リクエストを実行"] B -->|いいえ| D["注文を飛ばす"] C --> E["次のイテレーションへ"] D --> E

注意: 条件の書き間違いはエラーにならず、静かに飛ばされる

条件が偽になった場合も、書き間違いで評価できなかった場合も、配下の要素は実行されないだけで、画面にエラーは出ません（評価できなかった理由は jmeter.log に記録されます。GUI では右上の警告アイコンからログを表示できます）。「いつの間にか注文リクエストが1件も飛んでいない」という事態を防ぐため、最初は少人数で実行し、View Results Tree や Summary Report で期待した件数のリクエストが実行されているかを必ず確認してください。

10.6 Random Controller／Throughput Controller

現実の利用者は全員が同じ操作をするわけではありません。「閲覧だけで帰る人が大半で、注文まで進む人は一部」というように、操作には比率があります。この比率を表現するための2つのコントローラを紹介します。

Random Controller

配下の要素のうち1つだけを、イテレーションごとにランダムに選んで実行します。

どれが選ばれるかは均等です。例: 「トップ」「検索」「ランキング」のうち、毎回どれか1つ。

Throughput Controller

配下の要素を実行する割合や回数を指定します。

例: 「全体の80%は閲覧、20%は注文」のように、比率を数字で指定できます。

Throughput Controller の名前は紛らわしいのですが、第6章の Constant Throughput Timer のようにスループットを制御する部品ではありません。「このコントローラの配下を、どのくらいの割合で通すか」を決めるだけです。

項目 設定値の例 説明
Execution style Percent Executions Total Executions（合計で何回まで実行するか）か、Percent Executions（何%の割合で実行するか）かを選びます
Throughput 20 Percent なら割合（0〜100）、Total なら回数。この例では 20% の割合で実行します
Per User オフ オンにすると、数え方がユーザー（スレッド）ごとになります。オフでは全スレッドを合算して数えます

たとえば「閲覧80%・注文20%」を作るなら、シナリオの中に Throughput Controller を2つ並べ、片方に閲覧のリクエストを入れて 80、もう片方に注文のリクエストを入れて 20 を設定します。

比率を表現するテスト計画の例 

Thread Group
├── Throughput Controller「閲覧」（Percent 80）
│   └── HTTP Request  GET /get?item=...
└── Throughput Controller「注文」（Percent 20）
    └── HTTP Request  POST /anything/orders

注意: 比率はあくまで「目安」

上のように2つの Throughput Controller を並べると、それぞれが独立して判定されます。そのため、1回のイテレーションで両方が実行されたり、どちらも実行されなかったりすることがあり、「80対20に分けて1回につきどちらか1つ」とはなりません。実行回数を累計で見ると近い比率に収束しますが、少ない回数では偏ります。「必ずどちらか1つ」にしたいなら、Random Controller や、条件を分けた If Controller と組み合わせて設計します。

10.7 While Controller とコントローラの入れ子

While Controller（ホワイルコントローラ）は、条件が真の間、配下を繰り返し実行します。Condition 欄に変数や関数を書き、その結果が文字列 false になった時点で繰り返しを終えます。「処理が完了のステータスになるまで、ポーリング（状態確認）を繰り返す」といった場面で使います。

While Controller の Condition 欄（例: 変数 status が DONE ではない間、繰り返す） 
${__jexl3("${status}" != "DONE")}

注意: While Controller は無限ループになりやすい

条件がいつまでも真のままだと、スレッドは終わりのない繰り返しに入り、サーバーへ連打し続けます。繰り返しの間にタイマーを入れて間隔を空け、条件が必ず変わる設計になっているかを確認してから使いましょう。本ガイドの実習では扱いません。

コントローラは入れ子（ネスト）にできます。「Loop Controller の中に If Controller を置く」「Transaction Controller の中に Loop Controller を置く」など、組み合わせは自由です。ただし、入れ子にするほどツリーが読みにくくなり、思わぬ動きにもなりやすくなります。次の点に気を付けましょう。

注意点 具体例と対策
名前を業務の言葉にする 「Loop Controller」のままにせず、「商品閲覧×3」「注文」のように名前を付ける。ツリーが読めればシナリオも読める
繰り返し回数は掛け算になる Thread Group のループ × Loop Controller の回数 ＝ 実行回数。想定より多くの負荷になっていないか、計算で確かめる
タイマー・アサーションのスコープ コントローラの子にした要素は、そのコントローラ配下のサンプラーすべてに効く（第3章）。置き場所で効く範囲が変わる
深くしすぎない 3段を超えたら構造を見直す。複雑になるほど、実行されなかった要素に気づきにくい

やってみよう 10-1: ログイン1回・閲覧3回・注文のシナリオを作る

Once Only・Loop・Transaction の3つのコントローラを組み合わせ、次のツリーを持つ jmeter-practice/ch10-scenario.jmx を作ります。練習用サーバー go-httpbin（localhost:8080）が起動していることを確認してから始めてください。

Test Plan
├── HTTP Request Defaults（http / localhost / 8080）
└── Thread Group（Threads 2 / Ramp-up 1 / Loop Count 2）
    ├── Once Only Controller「ログイン」
    │   └── HTTP Request「GET /uuid」
    │       └── JSON Extractor（$.uuid → token）
    ├── Loop Controller「商品閲覧」（Loop Count 3）
    │   └── HTTP Request「GET /get」  /get?item=${__Random(1,100,)}
    ├── Transaction Controller「注文」
    │   └── HTTP Request「POST /anything/orders」
    └── Summary Report

手順

  1. 1 前章までに作った .jmx をもとに、または新規に、Test Plan に HTTP Request Defaults を追加し、Server Name に localhost、Port Number に 8080 を設定する。
  2. 2 Thread Group（Number of Threads 2、Ramp-up period 1、Loop Count 2）を追加する。2周させるのは、Once Only が2周目で飛ばされることを確認するためです。
  3. 3 Thread Group を右クリック → Add → Logic Controller → Once Only Controller を追加し、名前を「ログイン」にする。配下に HTTP Request（Name GET /uuid、Path /uuid）を作り、その子に JSON Extractor（Names of created variables token、JSON Path expressions $.uuid、Default Values NOT_FOUND）を追加する。
  4. 4 Thread Group の配下に Loop Controller（名前「商品閲覧」、Loop Count 3）を追加し、配下に HTTP Request（Name GET /get、Path /get、Parameters の Name item、Value ${__Random(1,100,)}）を作る。
  5. 5 Thread Group の配下に Transaction Controller（名前「注文」。Generate parent sample はオフのまま）を追加し、配下に HTTP Request（Name POST /anything/orders、Method POST、Path /anything/orders、Body Data は下のJSON）を作る。
  6. 6 Thread Group に Summary Report を追加（Add → Listener）して、緑の Start ボタンで実行する。
注文リクエストの Body Data 
{
  "token": "${token}",
  "item": 1,
  "quantity": 2
}

POST で JSON を送るので、HTTP Header Manager（Content-Type: application/json）をこの HTTP Request の子に追加するのを忘れないでください（第4章）。

確認ポイント: Summary Report の Samples 列で、2スレッド × 2周なのでGET /uuid 行の Samples が 2（各スレッド1回だけ）、GET /get 行が 12（2 × 2 × 3）、POST /anything/orders 行が 4であること。さらに、Generate parent sample をオフにしているため「注文」という名前のトランザクション行が追加され、その Samples が 4 になること。TOTAL 行の Samples は 22 になり、実際に送った HTTP リクエスト（2 ＋ 12 ＋ 4 ＝ 18件）より、トランザクション行の4件ぶん多くなることも確かめましょう。View Results Tree を一時的に追加し、注文の Request タブで ${token} が実際の UUID に置き換わっているかも確認しましょう。

理解度確認クイズ

  1. Q1. 10スレッドで実行するとき、Once Only Controller 配下のログインリクエストは全体で何回実行されますか？ また、Transaction Controller を使う利点は何ですか？

    回答を表示

    10回です。Once Only が「1回」なのはスレッドごとであり、各スレッドが最初のイテレーションで1回ずつ実行するためです。Transaction Controller の利点は、複数のリクエストを1つの業務操作（例: 注文）としてまとめ、その合計の応答時間を1件のサンプルとして計測できることです。業務単位で目標（注文は2秒以内など）を評価できます。

  2. Q2. Thread Group の Loop Count が 3、その配下の Loop Controller の Loop Count が 5 のとき、Loop Controller 内のリクエストは1スレッドあたり何回実行されますか？

    回答を表示

    3 × 5 ＝ 15回です。2つのループは入れ子になっているため、掛け算になります。スレッド数が10なら全体では150回です。意図せず負荷が増えないよう、入れ子のときは回数を掛け算で見積もります。

  3. Q3. If Controller で JMeter の変数を使った条件を書くときは、Interpret Condition as Variable Expression? をオンにするのが推奨です。それはなぜですか？ また、Throughput Controller を2つ並べて 80% と 20% に設定した場合の注意点は何ですか？

    回答を表示

    オフのままだと条件が JavaScript として評価され、処理が重く遅くなるためです。オンにすると JMeter の変数・関数の式として評価され、__jexl3 などの関数で軽く書けます。Throughput Controller は2つがそれぞれ独立に判定されるため、1回のイテレーションで両方が実行されたり、どちらも実行されなかったりすることがあり、「必ずどちらか1つ」にはなりません。比率は累計で見たときの目安です。
