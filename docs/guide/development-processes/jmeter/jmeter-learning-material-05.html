スレッドグループで負荷を設計する

性能テストの「負荷の大きさ」と「かけ方」を決めるのが Thread Group（スレッドグループ）です。この章では、スレッド数・ランプアップ・ループ回数・実行時間といった設定項目の意味を理解し、同時ユーザー数とスループットの関係を計算で見積もったうえで、実際に負荷を変えながら結果の変化を観察します。

この章で学ぶこと

  • Thread Group の主な設定項目の意味を説明できる
  • ランプアップの役割を理解し、スレッドの起動間隔を計算できる
  • 「回数で止める」方式と「時間で止める」方式を目的に応じて使い分けられる
  • リトルの法則で、目標スループットに必要なスレッド数を見積もれる

5.1 Thread Group の設定項目

Thread Group（スレッドグループ）は、仮想ユーザー（スレッド）を何人、どのように起動し、どれだけ繰り返し・どれだけの時間動かすかを決める要素です。第4章では既定値のまま（1スレッド・1回）使っていましたが、負荷を設計するときはこの画面が主役になります。追加するには Test Plan を右クリックして Add → Threads (Users) → Thread Group を選びます。

項目 既定値 説明
Number of Threads (users) 1 仮想ユーザーの人数。同時ユーザー数の上限になる
Ramp-up period (seconds) 1 全スレッドを起動し終えるまでの時間（秒）。5.2 で詳しく説明
Loop Count 1 各スレッドがシナリオを繰り返す回数。Infinite にチェックを入れると、終了条件が来るまで繰り返し続ける
Same user on each iteration チェックあり 繰り返しの2周目以降も同じユーザーとして動く（Cookie などの状態を引き継ぐ）。外すと、周回ごとに新しいユーザーとして状態をリセットする
Delay Thread creation until needed チェックなし スレッドを最初に全部作らず、各スレッドの開始時刻になってから作る。スレッド数が多くランプアップが長いときに、立ち上がり時のメモリ消費を抑えられる
Specify Thread lifetime チェックなし チェックすると下の2項目が入力できる。Duration (seconds) はテストを続ける時間、Startup delay (seconds) は Thread Group が動き出すまでの待ち時間
Action to be taken after a Sampler error Continue リクエストが失敗したときの動作（下の表を参照）

「Action to be taken after a Sampler error」では、エラー発生時の挙動を選べます。性能テストでは、エラーが起きても負荷をかけ続けてエラー率を測るのが基本なので、通常は既定の Continue のままにします。

選択肢 エラーが起きたときの動作
Continue 何もせず、次のサンプラーへ進む（負荷テストの標準）
Start Next Thread Loop そのスレッドの今の周回を打ち切り、次の周回を最初から始める
Stop Thread エラーを起こしたスレッドだけ停止する
Stop Test 実行中のリクエストの完了を待ってから、テスト全体を止める
Stop Test Now 実行中のリクエストも中断して、テスト全体を即座に止める

ヒント: 画面右上の Active Threads 表示

テスト実行中、GUI の右上に 3 / 10 のような表示が出ます。左が現在動いているスレッド数、右が設定した総スレッド数です。ランプアップで人数が増えていく様子や、終了時に 0 へ戻る様子をここで確認できます。

5.2 ランプアップの考え方

ランプアップ（Ramp-up）とは、負荷を一気にかけず、少しずつ増やしていく仕組みです。JMeter は、Number of Threads 個のスレッドを Ramp-up period の秒数をかけて均等な間隔で起動します。

スレッドの起動間隔（秒）

起動間隔 ＝ Ramp-up period ÷ Number of Threads

たとえば 10スレッド・ランプアップ10秒なら、起動間隔は 10 ÷ 10 ＝ 1秒です。最初のスレッドはすぐに動き出し、以降 1秒ごとに1スレッドずつ増えて、約9秒後に10スレッドすべてがそろいます。同じ10スレッドでも、ランプアップを 0（または 1）秒にすると、ほぼ同時に全員が動き出します。

flowchart LR S["テスト開始 0秒
スレッド1が開始"] --> T2["1秒後
スレッド2が開始"] T2 --> T3["2秒後
スレッド3が開始"] T3 --> TD["・・・"] TD --> T10["9秒後
スレッド10が開始
全員がそろう"]

設定値の違いで、負荷の立ち上がり方は次のように変わります。

スレッド数 ランプアップ 起動間隔 負荷の立ち上がり
10 10秒 1秒ごとに1人 なだらかに増える（負荷テストの基本）
10 1秒 0.1秒ごとに1人 ほぼ一斉に増える（スパイクテスト向き）
30 60秒 2秒ごとに1人 ゆっくり増える（限界を探るストレステスト向き）

ランプアップが必要な理由は2つあります。1つ目は、サーバー側の準備が整う前に全員が殺到するのを避けるためです。起動直後のキャッシュや接続プールが温まっていない状態に一気にアクセスすると、本来の性能より悪い結果が出てしまいます。2つ目は、負荷が増えるにつれて応答時間がどう変化するかを観察できるためです。人数を少しずつ増やせば、「何人を超えたあたりから遅くなるか」が読み取れます。

重要ポイント

ランプアップ中は人数が変わり続けるため、その間の計測値は「安定した負荷」の結果ではありません。結果を評価するときは、全スレッドがそろったあとの区間に注目します。Duration 方式（5.3）で、ランプアップより十分長い時間を指定するのはこのためです。

5.3 回数で止めるか、時間で止めるか

テストをいつ終わらせるかを決める方法は、大きく2つあります。

Loop Count 方式（回数で止める）

各スレッドが決めた回数だけシナリオを繰り返したら終わる。

例: 10スレッド × ループ5回 ＝ 各サンプラー50回。総リクエスト数が決まっているので、動作確認やスモークテストに向く。

Duration 方式（時間で止める）

Loop Count を Infinite にして、Specify Thread lifetime の Duration で終了時刻を決める。

例: 60秒間、10スレッドで回し続ける。負荷が一定時間続くので、負荷テスト・耐久テストに向く。

flowchart TD Q{"何を確かめたい？"} -->|"動作確認／件数を決めたい"| L["Loop Count を設定
例: 5回"] Q -->|"一定時間の負荷や安定性を見たい"| D["Loop Count を Infinite にして
Duration を設定"] L --> R1["総リクエスト数が決まる
終了時刻は応答時間次第"] D --> R2["終了時刻が決まる
総リクエスト数は応答時間次第"]

両者の違いは「何が固定されるか」です。回数方式は件数が固定で、サーバーが遅ければテストが長引きます。時間方式は実行時間が固定で、サーバーが遅ければ総リクエスト数が減ります。数時間かけ続ける耐久テストでは、終了時刻が予測できる Duration 方式が実務の標準です。

注意: Infinite のまま Duration を設定し忘れない

Loop Count を Infinite にしたのに Specify Thread lifetime のチェックを入れ忘れると、手動で Stop するまでテストが終わりません。反対に、Loop Count が有限のまま Duration も指定した場合は、どちらか早く条件を満たした時点で終了します。意図しない終わり方をしたときは、まずこの2つの設定を見直しましょう。

5.4 同時ユーザー数とスループットの関係

「毎秒50件のリクエストを処理できるか確かめたい」と言われたとき、スレッドを何個にすればよいのでしょうか。これは勘で決めず、リトルの法則（Little's Law）を簡易的に使うと見積もれます。ここでの考え方は、「1人のユーザーは、リクエストして応答を待ち、画面を見て考え、また次のリクエストをする、というサイクルを繰り返す」というものです。

簡易なリトルの法則

同時ユーザー数 ＝ スループット ×（応答時間 ＋ 思考時間）

スループットは「件/秒」、時間は「秒」で計算します。思考時間（Think Time）は、ユーザーが画面を見て次の操作を決めるまでの待ち時間で、第6章でタイマーとして再現します。

1人のユーザーが「応答時間 ＋ 思考時間」ごとに1リクエストを送る、と考えると理解しやすくなります。この1サイクルの長さを使うと、式は次のように変形できます。

リトルの法則の計算例 
# 例1: 100ユーザーが同時に使うとき、何件/秒になるか
# 1サイクル = 応答0.5秒 + 思考4.5秒 = 5秒
スループット = 同時ユーザー数 ÷ サイクル = 100 ÷ 5 = 20 件/秒

# 例2: 50件/秒を出すには、何スレッド必要か
# 1サイクル = 応答0.4秒 + 思考3.6秒 = 4秒
同時ユーザー数 = 50 × 4 = 200 スレッド

# 例3: 思考時間なし（タイマー無し）の場合
# 1サイクル = 応答時間のみ。10スレッド、応答1秒なら
スループット = 10 ÷ 1 = 約10 件/秒

例3は、5.6 の実習でそのまま確かめます。思考時間が無いと、スレッドは応答が返った瞬間に次のリクエストを送るため、ユーザー1人あたりの負荷が大きくなります。逆に言えば、現実の利用者を再現したいなら、思考時間を入れてスレッド数を現実的な人数にする必要があります。

ヒント: 見積もりは出発点

この計算は、応答時間が一定という前提の目安です。実際には負荷が増えると応答時間が伸び、同じスレッド数でもスループットは計算値より下がります。まず計算で見当をつけ、実測で調整する、という進め方をしましょう。

5.5 setUp / tearDown Thread Group

テストの本番の前後に、準備や後片付けの処理を挟みたいことがあります。そのために、通常の Thread Group とは別に2種類の特別な Thread Group が用意されています。追加は Add → Threads (Users) から行います。

種類 実行されるタイミング 主な使いどころ
setUp Thread Group 通常の Thread Group より前に実行される テストデータの登録、管理者としてのログイン、対象システムの初期化
Thread Group setUp のあと、tearDown の前に実行される（本番の負荷） 利用者の操作シナリオ
tearDown Thread Group 通常の Thread Group がすべて終わった後に実行される テストデータの削除、後始末の API 呼び出し
flowchart LR A["setUp Thread Group
データ準備"] --> B["Thread Group
本番の負荷"] B --> C["tearDown Thread Group
後片付け"]

設定項目は通常の Thread Group とほぼ同じです。Test Plan 直下に置いたリスナーには、setUp / tearDown の結果も通常のサンプルと同様に記録されます。一方、Thread Group の下に置いた Summary Report や HTTP Request Defaults は、その Thread Group の中だけに効きます（第3章のスコープ）。setUp / tearDown でも使う場合は Test Plan 直下に移してください。集計に含めたくない場合は、名前で見分けられるようにしておくと安心です。本ガイドの練習では、これらを使わなくても進められます。「準備と後片付けは専用の Thread Group に分ける」という選択肢があることを覚えておいてください。

なお、Stop（第4章）でテストを止めた場合、tearDown Thread Group は実行されません。Shutdown で止めたときに実行するかどうかは、Test Plan の「Run tearDown Thread Groups after shutdown of main threads」で決まります。

5.6 Active Threads を観察する

ここまでの理論を、実際に負荷を変えて確かめます。go-httpbin の /delay/1 は1秒待ってから応答するエンドポイントです。応答時間が約1秒で一定なので、リトルの法則の例3「タイマー無しなら、スループット ≒ スレッド数 ÷ 1秒」を確認するのにぴったりです。スレッド数を 5 → 10 → 20 と変えて、Summary Report の Throughput がどう変わるかを見ます。

項目 設定値 説明
Number of Threads (users) 5 → 10 → 20（1回ごとに変更） 実行のたびにここだけを書き換える
Ramp-up period (seconds) 5 立ち上がりをなだらかにする
Loop Count Infinite にチェック Duration で終わらせる
Specify Thread lifetime → Duration 30 30秒間実行する
HTTP Request GET　/delay/1 接続先は HTTP Request Defaults（localhost:8080）を使う

1回の実行が終わったら、Summary Report の値を記録し、Clear All（第4章）で結果を消してから、スレッド数を変えて再実行します。結果は次のように推移するはずです。ランプアップ中の人数が少ない区間も平均に含まれるため、数値は計算値より少し低めに出ます。

スレッド数 Average（応答時間） Throughput の目安
5 約1,000 ms 約4〜5 件/秒
10 約1,000 ms 約8〜10 件/秒
20 約1,000 ms 約16〜20 件/秒

スレッド数を2倍にすると、スループットもほぼ2倍になりました。応答時間が変わらない間は、人数に比例して処理件数が増えることが確かめられます。これは go-httpbin がこの程度の負荷に余裕で耐えているからです。もしスレッド数を増やしても応答時間が伸びてスループットが頭打ちになったら、それがシステムの限界に近づいたサインです。この見方は第13章で改めて学びます。

警告: 負荷は自分の環境だけにかける

スレッド数を増やせる設定画面は、手軽に大きな負荷を作れる反面、接続先を間違えると他人のサーバーへの攻撃になってしまいます。実行の前に、HTTP Request Defaults の Server Name or IP が localhost、Port Number が 8080 であることを必ず確認してください。また、JMeter と go-httpbin は同じ PC で動くため、ここで得た数値は学習用の目安であり、本番システムの性能値ではありません。

やってみよう 5-1: 回数方式で負荷をかける

10スレッド・ランプアップ10秒・ループ5回で実行し、総リクエスト数が計算どおりになることを確認します。

手順

  1. 1 JMeter を起動し、Test Plan の下に Thread Group を追加する。HTTP Request Defaults（Protocol http／Server localhost／Port 8080）、HTTP Request（GET /delay/1）、Summary Report を、それぞれ追加する。
  2. 2 Thread Group を、Number of Threads 10／Ramp-up period 10／Loop Count 5 に設定する。
  3. 3 jmeter-practice/ch05-thread-group.jmx として保存し、Start（緑の三角）で実行する。実行中、右上の Active Threads 表示が 1→2→…→5 前後まで増え、その後減っていく様子を見る（各スレッドが約5秒動くため、同時に動くのは最大5人前後）。
  4. 4 Summary Report の Samples が 50（10スレッド × 5回）になっていることを確認する。
確認ポイント: Samples が 50、Error % が 0.00% なら成功です。Loop Count はスレッドごとの回数なので、どのスレッドもちょうど5回ずつ実行します。
補足: /get のように数ミリ秒で返るリクエストだと、各スレッドは次のスレッドが起動する前に5回を終えてしまい、同時に動くのは常に1人程度になります。「スレッド数＝同時ユーザー数」になるのは、各スレッドの実行時間がランプアップの起動間隔より長いときです。

やってみよう 5-2: Duration 方式に変えて比較する

終了条件を「60秒間」に変え、回数方式との違いと、スレッド数を増やしたときのスループットの変化を確認します。

手順

  1. 1 Thread Group の Loop Count の Infinite にチェックを入れ、Specify Thread lifetime にもチェックして Duration に 60 を入力する。
  2. 2 HTTP Request の Path が /delay/1 のままであることを確認し、Clear All で結果を消してから実行する。約60秒で自動的に終わることを確認する。
  3. 3 Summary Report の Samples と Throughput を記録する。目安は 10スレッドで約 500〜600 件、約 8〜10 件/秒。
  4. 4 Number of Threads を 20（Ramp-up は 10 のまま）に変えて再実行し、Throughput がほぼ2倍になるか見る。5.6 の表と照らし合わせて考察する。
考察のヒント: 5-1 では「回数が決まっていて、終了時刻は応答時間次第」、5-2 では「終了時刻が決まっていて、件数は応答時間次第」でした。どちらを使うべきか、自分の言葉で説明してみましょう。

理解度確認クイズ

  1. Q1. 30スレッド・ランプアップ60秒に設定すると、スレッドは何秒ごとに1つずつ起動しますか？ また、ランプアップを設ける理由を1つ挙げてください。

    回答を表示

    60 ÷ 30 ＝ 2秒ごとに1スレッドが起動します。ランプアップを設ける理由は、サーバーの準備が整う前に全員が殺到することを避けられること、負荷が増えるにつれて応答時間がどう変化するかを観察できることです。

  2. Q2. 応答時間が0.5秒、思考時間が9.5秒の利用者が200人同時に使うと、スループットは約何件/秒になりますか？

    回答を表示

    1サイクルは 0.5 ＋ 9.5 ＝ 10秒です。同時ユーザー数 ＝ スループット × 10秒 なので、スループット ＝ 200 ÷ 10 ＝ 約20件/秒になります。

  3. Q3. 数時間にわたる耐久テストでは、Loop Count 方式と Duration 方式のどちらが向いていますか？ 理由もあわせて答えてください。

    回答を表示

    Duration 方式です。Loop Count を Infinite にして Duration を指定すれば、サーバーの応答が遅くなっても終了時刻が変わらず、「一定の負荷を一定時間かけ続ける」という耐久テストの目的に合うためです。Loop Count 方式では、応答時間次第で終了時刻がずれてしまいます。
