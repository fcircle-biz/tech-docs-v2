第12章 所要時間: 約1時間

CLIモードで負荷テストを実行する

ここまでは GUI でテスト計画を作り、少人数で動作を確かめてきました。この章では、いよいよ本番の負荷をかけるための CLI（非 GUI）モードを学びます。コマンド1つでテストを実行し、結果ファイル（JTL）と HTML レポートを出力するまでの流れと、実行前に確認すべきことを身につけましょう。

この章で学ぶこと

  • 負荷テストを GUI ではなく CLI モードで実行する理由を説明できる
  • 主要なコマンドラインオプション（-n -t -l -e -o -f -J -q -j）を使い分けられる
  • 実行中のコンソール出力（summary +／summary =）と JTL ファイルを読める
  • -J でプロパティを渡し、同じ .jmx を条件を変えて実行できる
  • 実行前チェックリストに沿って、測定を歪める原因を取り除ける

12.1 なぜ CLI モードなのか

JMeter の GUI は、テスト計画を作る・デバッグするための道具です。GUI を表示したまま負荷をかけると、画面の描画やリスナー（View Results Tree など）が JMeter 自身のメモリと CPU を消費します。すると、本来測りたい「サーバーの性能」ではなく「JMeter 側が苦しそうな様子」が結果に混ざってしまい、測定値が歪みます。最悪の場合、JMeter がメモリ不足で止まります。

そこで本番の負荷実行には、画面を持たない CLI モード（非 GUI モード）を使います。結果はファイルに書き出し、集計は終了後（または実行中のコンソール出力）で行います。JMeter を起動したときに「Don't use GUI mode for load testing !」と表示されたのは、まさにこのためでした。

flowchart LR A["GUI
テスト計画の作成・デバッグ"] --> B["ch12-load.jmx
を保存"] B --> C["CLI モードで実行
jmeter -n -t ..."] C --> D["結果ファイル
result.jtl"] C --> E["HTMLレポート
report フォルダ"]

GUI モードの出番

テスト計画の作成、1〜数ユーザーでの動作確認、View Results Tree でのデバッグ。

CLI モードの出番

本番の負荷実行、長時間の耐久テスト、CI やスクリプトからの自動実行。

12.2 基本コマンドとオプション

CLI モードの基本形は次のとおりです。ターミナル（Windows は PowerShell）を開き、.jmx のあるフォルダ（jmeter-practice）に移動して実行します。以下のコマンド例はフルパスで書いていますが、第2章では JMeter の bin を PATH に追加していないので、毎回フルパスを打つのが面倒なら、次のように PATH を通しておくと jmeter だけで実行できます。

PATH の追加（Windows PowerShell） 
# このウィンドウだけ JMeter の bin を PATH に追加する
$env:Path = "C:\tools\apache-jmeter-5.6.3\bin;$env:Path"
PATH の追加（macOS / Linux） 
# このターミナルだけ JMeter の bin を PATH に追加する
export PATH="$HOME/tools/apache-jmeter-5.6.3/bin:$PATH"

上の設定は、そのウィンドウ（ターミナル）を閉じるまでしか有効ではありません。macOS/Linux で恒久的にしたいときは、同じ export 行を ~/.zshrc などに追記します。

Windows（PowerShell） 
# jmeter-practice フォルダへ移動する
cd C:\Users\あなた\Documents\jmeter-practice

# CLI モードで実行し、結果(JTL)とHTMLレポートを出力する
C:\tools\apache-jmeter-5.6.3\bin\jmeter.bat -n -t ch12-load.jmx -l result.jtl -e -o report
macOS / Linux 
# jmeter-practice フォルダへ移動する
cd ~/Documents/jmeter-practice

# CLI モードで実行し、結果(JTL)とHTMLレポートを出力する
~/tools/apache-jmeter-5.6.3/bin/jmeter -n -t ch12-load.jmx -l result.jtl -e -o report

使うオプションを一覧にまとめます。以降、macOS/Linux の jmeter と Windows の jmeter.bat は同じ意味なので、本文では jmeter と書きます。PATH を通したターミナルで、jmeter-practice フォルダに移動して実行します。PATH を通さない場合は、~/tools/apache-jmeter-5.6.3/bin/jmeter（Windows は C:\tools\apache-jmeter-5.6.3\bin\jmeter.bat）のようにフルパスで書きます。

オプション 意味 補足
-n 非 GUI（CLI）モードで実行する non-GUI の n。これが無いと GUI が起動する
-t ファイル 実行するテスト計画（.jmx）を指定する 相対パスは実行したフォルダが基準
-l ファイル 結果（サンプル）を書き出すファイル（JTL） 既存ファイルがあると追記される（-e を付けた場合は、空でない JTL があるとエラーで止まる）
-e テスト終了後に HTML レポートを生成する -l と -o が必要
-o フォルダ HTML レポートの出力先フォルダ 存在しないか、空でなければならない
-f テスト開始前に、既存の結果ファイル（-l）とレポートの出力先（-o）を削除する 削除した結果は元に戻せない。前回の結果が不要だと確認できたときだけ使う
-Jname=値 JMeter プロパティを渡す .jmx の ${__P(name,既定値)} で受け取る（12.4）
-q ファイル プロパティをまとめた追加ファイルを読み込む 条件が多いとき、-J を並べる代わりに使う
-j ファイル JMeter の実行ログ（jmeter.log）の出力先 実行ごとにログを分けたいときに指定する

注意: 2回目の実行は「名前を変える」のが基本

2回目に同じコマンドを実行すると、report フォルダが既に存在するためエラーで止まります。result.jtl が残っている場合も「Results file … is not empty」で止まります。これは前回の結果を誤って消さないための安全装置です。性能テストでは過去の結果と比べることが大切なので、実行ごとに result-u20.jtl・report-u20 のように別のファイル名・フォルダ名を指定しましょう。-f は既存の結果を削除してしまうため、デバッグ中の試し実行など、前回の結果が不要だと確認できたときだけ使います。なお、-e を付けずに実行した場合は JTL に追記され、後で -g でレポートを作ると前回分が混ざります。

実務では、結果ファイルとレポートに加えて、そのとき何の条件で実行したかも同じ場所に残しておくと、後から結果を追跡・再現しやすくなります。たとえば、実行ごとにフォルダを分けて次のように保存します。

実行ごとに結果と条件をまとめて保存する例 
results/
├── test-001/
│   ├── result.jtl        ← -l results/test-001/result.jtl
│   ├── report/           ← -o results/test-001/report
│   └── conditions.txt    ← 実行日時・ユーザー数・ランプアップ・実行時間・.jmx・環境などのメモ
└── test-002/
    ├── result.jtl
    ├── report/
    └── conditions.txt

この形にするときは、results/test-001 のような実行ごとのフォルダを、実行前に作っておきます（macOS/Linux は mkdir -p results/test-001、Windows は mkdir results\test-001）。第14章の総合演習でも、この保存方法を使います。

12.3 実行中の出力を読む

CLI モードで実行すると、コンソールに集計行が一定間隔（既定は30秒ごと）で流れます。画面が無くても、これで負荷のかかり具合をリアルタイムに確認できます。

コンソール出力の例（数値は一例） 
Creating summariser <summary>
Starting standalone test @ 2026-10-18 10:00:00 JST
summary +    210 in 00:00:30 =    7.0/s Avg:   310 Min:     8 Max:  1080 Err:     0 (0.00%) Active: 10 Started: 10 Finished: 0
summary +    232 in 00:00:30 =    7.7/s Avg:   295 Min:     7 Max:  1102 Err:     2 (0.86%) Active: 10 Started: 10 Finished: 0
summary =    442 in 00:01:00 =    7.4/s Avg:   302 Min:     7 Max:  1102 Err:     2 (0.45%)
Tidying up ...    @ 2026-10-18 10:01:00 JST
... end of run
部分 意味
summary + 前回の出力から今回までの期間だけの集計（差分）。いま何が起きているかを見る
summary = テスト開始から今回までの累計の集計。全体の傾向を見る
210 in 00:00:30 = 7.0/s その期間のサンプル件数・経過時間・スループット（件/秒）
Avg / Min / Max 応答時間の平均・最小・最大（ミリ秒）
Err: 2 (0.86%) 失敗したサンプルの件数とエラー率
Active / Started / Finished 稼働中のスレッド数・起動済みの数・終了した数（summary + 行のみ）

見るときのコツは、summary + の行でAvg が上がり続けていないか、Err が突然増えていないかを確認することです。累計の summary = は平均化されるので、途中の悪化に気づきにくくなります。なお、出力間隔は user.properties の summariser.interval（秒）で変更できます。

ヒント: 実行を途中で止めるには

途中で止めるときは、別のターミナルで <JMETER_HOME>/bin の shutdown.sh（Windows は shutdown.cmd）を実行すると、実行中のサンプルを終えてから正常に停止し、-e のレポートも作られます（stoptest.sh / stoptest.cmd は即時停止）。Ctrl+C は強制終了なので、レポートが作られないことがあります。その場合は、第13章で学ぶ -g オプションで、残った JTL ファイルからレポートを作り直せます。

12.4 プロパティで負荷を切り替える

第8章で学んだ ${__P(名前,既定値)} を使うと、.jmx を書き換えずに、コマンドから負荷の条件を渡せます。ユーザー数や実行時間を変えるたびに GUI を開いて保存し直す必要がなくなり、操作ミスも防げます。

Thread Group の項目 設定値 説明
Number of Threads (users) ${__P(users,5)} -Jusers で指定。未指定なら5人
Ramp-up period (seconds) ${__P(rampup,10)} -Jrampup で指定。未指定なら10秒
Loop Count Infinite にチェック Duration（時間）で止める方式にするため
Specify Thread lifetime → Duration (seconds) ${__P(duration,60)} -Jduration で指定。未指定なら60秒

このように設定した .jmx を、条件違いで実行する例です。条件ごとに結果ファイルとレポートの名前を変えているので、前回の結果を消さずに、後から並べて比べられます。

Windows（PowerShell） 
# 既定値のまま(5人・60秒)で実行する
jmeter.bat -n -t ch12-load.jmx -l result-u05.jtl -e -o report-u05

# 20人・120秒に変えて実行する(-J で上書き。結果の名前も変える)
jmeter.bat -n -t ch12-load.jmx -l result-u20-120s.jtl -e -o report-u20-120s -Jusers=20 -Jduration=120
macOS / Linux 
# 既定値のまま(5人・60秒)で実行する
jmeter -n -t ch12-load.jmx -l result-u05.jtl -e -o report-u05

# 20人・120秒に変えて実行する(-J で上書き。結果の名前も変える)
jmeter -n -t ch12-load.jmx -l result-u20-120s.jtl -e -o report-u20-120s -Jusers=20 -Jduration=120

条件が増えてきたら、プロパティをファイルにまとめて -q で読み込む方法もあります。

load20.properties 
# 20人で2分間の条件をファイルにまとめる
users=20
rampup=20
duration=120

# 実行例: jmeter -n -t ch12-load.jmx -q load20.properties -l result-load20.jtl -e -o report-load20

12.5 実行前のチェックリスト

GUI で作った .jmx には、デバッグ用の部品や小さな試験値が残っていることがよくあります。それらを残したまま負荷をかけると、測定が歪んだり、JMeter が止まったりします。実行前に次の項目を確認する習慣をつけましょう。

確認項目 理由
View Results Tree などの重いリスナーを無効化（または削除）した 全サンプルの応答本文をメモリに保持するため、負荷中は JMeter のメモリを食いつぶす
Debug Sampler を無効化した 変数の中身を毎回出力するだけのデバッグ用。余計なサンプルとして集計に混ざる
スレッド数・ループ・Duration がデバッグ用の小さな値のままでない 1ユーザーで試した設定のまま本番を実行してしまう事故が多い。${__P()} の既定値も確認する
接続先（HTTP Request Defaults）が意図したサーバーになっている 本番や他人のサーバーに誤って負荷をかけない（12.7 の警告参照）
CSV などの外部ファイルが、.jmx から見た相対パスの場所にある 相対パスは .jmx の場所が基準。見つからないと全サンプルが失敗する
ヒープサイズ（メモリ）が足りている ユーザー数や実行時間が増えると、既定では不足することがある（下記）

JMeter 5.6.3 のヒープサイズ（Java が使えるメモリ）の既定は1GBです。変更したいときは、環境変数 HEAP に Java のメモリオプションを入れてから起動します。

Windows（PowerShell） 
# このターミナルだけヒープを 2GB にする(-Xms 初期値, -Xmx 最大値)
$env:HEAP="-Xms2g -Xmx2g"
jmeter.bat -n -t ch12-load.jmx -l result-heap2g.jtl -e -o report-heap2g
macOS / Linux 
# この1回の実行だけヒープを 2GB にする(-Xms 初期値, -Xmx 最大値)
HEAP="-Xms2g -Xmx2g" jmeter -n -t ch12-load.jmx -l result-heap2g.jtl -e -o report-heap2g

重要ポイント

リスナーを無効にしても、CLI では -l で指定した JTL ファイルに全サンプルが記録されます。結果の集計は JTL と HTML レポートで行えるので、負荷中に GUI のリスナーで眺める必要はありません。

12.6 JTL ファイルとは

-l で指定した result.jtl は、サンプル1件を1行として記録したCSV 形式の結果ファイルです。HTML レポートはこのファイルを集計して作られるため、JTL は「生データ」にあたります。テキストエディタや表計算ソフトで開いて、1件ずつ確認することもできます。

result.jtl（先頭の2行を抜粋） 
timeStamp,elapsed,label,responseCode,responseMessage,threadName,dataType,success,failureMessage,bytes,sentBytes,grpThreads,allThreads,URL,Latency,IdleTime,Connect
1792285200123,312,GET /get,200,OK,Thread Group 1-3,text,true,,612,134,10,10,http://localhost:8080/get?item=7,309,0,2
列名 意味
timeStamp サンプル開始時刻（1970年1月1日からのミリ秒）
elapsed 応答時間（ミリ秒）。レポートの Average などの元になる値
label サンプラー名（または Transaction Controller 名）。集計の単位になる
responseCode / responseMessage HTTP ステータスコードとメッセージ（例: 200 / OK）
threadName 実行したスレッド（仮想ユーザー）の名前
dataType 応答の種類（text など）
success 成功なら true、失敗（アサーション失敗を含む）なら false。Error % の元
failureMessage 失敗したときの理由（アサーションのメッセージなど）
bytes / sentBytes 受信・送信したバイト数
grpThreads / allThreads その時点で稼働していた、当該グループ／全体のスレッド数
URL リクエスト先の URL
Latency リクエスト送信から応答の最初のバイトを受け取るまでの時間（ミリ秒）
IdleTime サンプリング以外に費やした時間（ミリ秒）。通常は0で、Transaction Controller でタイマー等の時間を除いたときにその分が入る
Connect サーバーとの接続確立にかかった時間（ミリ秒）

elapsed が Latency 以上になるのは、「応答の最初のバイトが届いてから、最後まで受け取り終わるまで」の時間も含むからです（第4章で学んだ Load time と Latency の関係と同じです）。

注意: JTL は大きくなる

1サンプルにつき1行が書かれるため、長時間の耐久テストでは JTL が数百MB〜数GBになることがあります。ディスクの空き容量を確認してから実行しましょう。また、JTL にはリクエスト先の URL などが含まれるので、共有するときは内容に注意してください。

12.7 負荷をかける側の監視と、大規模テストへの道

負荷をかける JMeter 自身も、ふつうの Java プログラムです。ユーザー数が増えると JMeter が動いている PC の CPU やメモリ、ネットワーク帯域を使い切り、「サーバーが遅い」のではなく「JMeter が遅い」状態になることがあります。そうなると測定値は信用できません。

flowchart TD A["負荷を増やしていく"] --> B{"JMeter側のCPU・メモリは
余裕があるか"} B -->|"余裕あり"| C["測定値は信頼できる"] B -->|"限界に近い"| D["測定値が歪む
（実際より遅く見える）"] D --> E["対策: ヒープ拡大、リスナー削減、
負荷をかけるマシンを増やす"]

実行中は、タスクマネージャー（Windows）やアクティビティモニタ（macOS）、top コマンド（Linux）で、JMeter のプロセスが CPU やメモリをどれだけ使っているかを確認しましょう。CPU が常に90%を超えている、ヒープがほぼ満杯でメモリ不足のエラー（OutOfMemoryError）が出る、といった場合は要注意です。

1台の PC でさばき切れないほど大きな負荷が必要なときは、複数台の PC で JMeter を動かして負荷を分担する分散テスト（リモート実行）という仕組みがあります。本ガイドの学習範囲では 1 台で十分なので、詳細は扱いません。「大規模になればそういう手段がある」と覚えておけば十分です。

警告: 実行する前に「実行先 URL」を最終確認する

CLI モードは、Enter キーを押した瞬間から画面確認なしで負荷が始まります。他人・他社のサーバーに許可なく負荷をかけることは DoS 攻撃と同じ行為で、法的責任を問われる可能性があります。本ガイドの実習はすべて localhost:8080 の go-httpbin に対して行います。実行前に HTTP Request Defaults の Server Name or IP が localhost であることを必ず確認してください。実務では、対象システムの管理者から実施日時と負荷の大きさについて許可を得てから実行します。

やってみよう 12-1: CLI で 10 ユーザー・60 秒の負荷テストを実行する

第10章で作った ch10-scenario.jmx をもとに、CLI 実行用の ch12-load.jmx を作り、レポートまで出力します。go-httpbin が起動していること（docker start httpbin）を先に確認してください。

手順

  1. 1 GUI で ch10-scenario.jmx を開き、File → Save Test Plan as で ch12-load.jmx として保存する。
  2. 2 Thread Group を 12.4 の表のとおりに設定する（Threads は ${__P(users,5)}、Ramp-up は ${__P(rampup,10)}、Loop Count は Infinite、Specify Thread lifetime の Duration は ${__P(duration,60)}）。
  3. 3 12.5 のチェックリストに従い、View Results Tree と Debug Sampler を無効化（Ctrl+T）して保存し、GUI を閉じる。
  4. 4 ターミナルで jmeter-practice に移動し、jmeter -n -t ch12-load.jmx -l result.jtl -e -o report -Jusers=10 -Jrampup=10 -Jduration=60 を実行する（Windows は jmeter.bat）。12.2 の例を試して result.jtl や report が残っているとエラーで止まるので、中身が不要なことを確かめてから削除するか、そのときだけ -f を付ける。
  5. 5 summary + と summary = の行を観察し、終了後に report/index.html をブラウザで開く。
確認ポイント: コンソールの最後に ... end of run が出ること。result.jtl に1行目の列名（timeStamp, elapsed, label…）と各サンプルの行があること。report フォルダに index.html ができていること。

やってみよう 12-2: -J でユーザー数を変えて再実行する

.jmx を一切変更せず、ユーザー数だけを 20 人に変えて実行し、結果の違いを見てみましょう。

手順

  1. 1 12-1 のコマンドの -Jusers=10 を -Jusers=20 に変え、結果の保存先も -l result-u20.jtl -e -o report-u20 のように別の名前にして実行する（10人のときの結果を残して比べるため）。
  2. 2 コンソールの Active: が最大 20 になること、summary = のスループットと Avg が 10 人のときからどう変わったかを書き留める。
  3. 3 試しに手順1と同じコマンドをもう一度実行し、どんなエラーになるか確認する。このエラーが前回の結果を守る安全装置であること、-f を付けると前回の結果が削除されることを、ノートに書き留める。
ヒント: 練習環境では JMeter と go-httpbin が同じ PC で動いているため、数値は学習用の目安です。本番の性能値ではありません。

理解度確認クイズ

  1. Q1. 本番の負荷テストを GUI ではなく CLI モードで実行するのはなぜですか？

    回答を表示

    GUI の描画やリスナーが JMeter 自身の CPU・メモリを消費し、測定値を歪めたり、メモリ不足で止まったりするからです。CLI モードなら画面を持たないため、JMeter の負担が小さく、結果は JTL ファイルと HTML レポートに残せます。

  2. Q2. 同じ -o report を指定して2回目を実行したらエラーになりました。原因と対策は？

    回答を表示

    -o のフォルダは、存在しないか空でなければならないためです。result.jtl が残っている場合も、-e 付きだと開始前に「Results file … is not empty」で止まります。対策は、実行ごとにファイル名・フォルダ名を変えることです（過去の結果と比べられるように残しておくのが基本）。-f を付けると既存の結果ファイルとレポートフォルダが削除されるため、前回の結果が不要だと確認できたときだけ使います。なお -e を付けない実行では JTL に追記されるため、後で -g でレポートを作ると前回の結果が混ざる点にも注意が必要です。

  3. Q3. コンソールの summary + と summary = の違いは何ですか？ また、-Jusers=20 を有効にするには .jmx 側で何を書いておく必要がありますか？

    回答を表示

    summary + は前回の出力以降の期間だけの集計、summary = はテスト開始からの累計です。-Jusers=20 は、Thread Group の Number of Threads に ${__P(users,5)} のようにプロパティ関数を書いておくことで受け取れます。書いていなければ -J で渡しても反映されません。
