第9章 所要時間: 約90分

データを守る - プロパティとカプセル化

第8章で作ったクラスには、実は大きな落とし穴があります。フィールドを外部に公開していると、誰でも自由に値を書き換えられてしまい、「年齢がマイナス」のようなおかしなデータが平気で入り込んでしまうのです。この章では、データを決められた窓口だけを通してやり取りする「カプセル化」の考え方と、その中心的な仕組みである「プロパティ」を学びます。

この章で学ぶこと

  • カプセル化とは何か、なぜデータを直接触らせてはいけないのかを説明できる
  • Public / Private / Protected / Friend の違いを理解し使い分けられる
  • 自動実装プロパティと Get / Set を持つ完全なプロパティを書ける
  • プロパティで入力値を検証し、クラス全体で共有する Shared メンバーを扱える

9.1 カプセル化とは

第8章で作った Employee クラスを思い出してください。フィールドを Public にしていた場合、外部のコードから自由に値を代入できてしまいます。次の例を見てみましょう。

Program.vb 完全なプログラム 
Class Employee
    Public Age As Integer  ' Publicなフィールド(誰でも書き換え可能)
End Class

Module Program
    Sub Main()
        Dim emp As New Employee()
        emp.Age = -5  ' マイナスの年齢が入ってしまう!
        Console.WriteLine(emp.Age)  ' -5 とそのまま表示される
    End Sub
End Module

年齢がマイナスになることは現実にはあり得ません。しかしクラス側には「変な値を弾く仕組み」が何もないため、コンパイルは通ってしまい、実行時に不正なデータがそのまま保存されます。このような事故を防ぐ考え方がカプセル化です。

カプセル化とは、クラスの内部データを外部から直接触らせず、決められた窓口（プロパティやメソッド）を通してだけやり取りする設計の考え方です。銀行を思い浮かべてください。私たちは金庫に直接手を入れてお金を出し入れすることはできません。ATM や窓口という決められた手続きを通してのみ、入出金ができます。ATM は「残高が足りるか」「暗証番号が正しいか」を必ずチェックしてから処理を行い、不正な操作を弾いてくれます。

クラスの設計も同じです。内部のデータ（フィールド）を金庫の中身、プロパティを ATM だと考えると分かりやすいでしょう。外部のコードはプロパティという窓口を通してのみデータにアクセスでき、プロパティ側で値のチェックを行うことで、不正なデータが内部に入り込むのを防げます。

flowchart TD A["外部のコード
（他のクラスやProgram.vb）"] --> B["プロパティ
（ATM・窓口）"] B --> C{"値は正しい？"} C -->|正しい| D["内部フィールドに保存
（金庫の中身）"] C -->|不正| E["エラーを発生させる
（保存しない）"]

図の説明: 外部のコードは内部フィールドに直接触れず、必ずプロパティという窓口を経由します。プロパティは値を検証し、正しい値だけを内部フィールドに保存します。不正な値は保存される前に弾かれます。

重要ポイント: カプセル化のメリット

①不正な値の混入を防げる、②内部の実装方法を後から変更しても外部のコードに影響しない、③「どう使ってほしいか」をクラスの作者がコントロールできる、という3つの利点があります。この章では、VB.NET でカプセル化を実現する中心的な仕組み「プロパティ」を学びます。

9.2 アクセス修飾子

カプセル化を実現する第一歩は、「どこから見えるか・使えるか」を決めるアクセス修飾子です。VB.NET には主に4種類のアクセス修飾子があります。

修飾子 アクセスできる範囲
Public どこからでもアクセスできる（制限なし）
Private そのクラスの中だけからアクセスできる
Protected そのクラス自身と、それを継承した派生クラスからアクセスできる（第10章）
Friend 同じプロジェクト内であればアクセスできる

アクセス修飾子の基本方針はシンプルです。フィールドは Private にして外部から直接触れないようにし、外部に見せたい入り口だけを Public なプロパティやメソッドとして公開するのが、オブジェクト指向プログラミングの定石です。この方針を守るだけで、9.1 で見たような不正な値の混入を大きく減らせます。

用語: 情報隠蔽

フィールドを Private にして外部から見えなくすることを情報隠蔽と呼びます。カプセル化を実現する具体的な手段の1つで、「クラスの内部でどうデータを持っているか」を外部に意識させずに済むという利点があります。

9.3 プロパティの基本

プロパティは、フィールドのように emp.Name = "田中" という形で読み書きできながら、裏側では処理を挟める仕組みです。もっとも手軽に書けるのが自動実装プロパティです。

Program.vb 完全なプログラム 
Class Employee
    ' 自動実装プロパティ:Get/Setの中身を省略した簡潔な書き方
    Public Property Name As String
    Public Property Age As Integer
End Class

Module Program
    Sub Main()
        Dim emp As New Employee()
        emp.Name = "田中太郎"  ' プロパティ経由で値を設定
        emp.Age = 30
        Console.WriteLine($"{emp.Name}さん({emp.Age}歳)")
    End Sub
End Module

見た目はフィールドとほとんど同じですが、Public Property と書くだけで、VB.NET が裏側に見えない保存領域と Get（読み取り）・Set（書き込み）の処理を自動的に用意してくれます。まだ検証は入っていませんが、9.4 でこの中身を自分で書き換える方法を学びます。

プロパティには「計算した結果を返すだけで、外部からは変更させない」という使い方もできます。これを読み取り専用プロパティと呼び、ReadOnly を付けて宣言します。

Product.vb クラスの定義 
Class Product
    Public Property Price As Integer  ' 税抜価格(自動実装)

    ' 読み取り専用プロパティ:Getしかないので外部から代入できない
    Public ReadOnly Property TaxIncludedPrice As Integer
        Get
            Return CInt(Price * 1.1)  ' 消費税10%を計算して返す
        End Get
    End Property
End Class

product.TaxIncludedPrice = 1000 のように代入しようとすると、コンパイルエラーになります。「計算結果は外部から書き換えさせない」という意図を、コードそのもので表現できるのがプロパティの強みです。

項目 フィールド プロパティ
役割 データそのものを保存する場所 データへの読み書きの窓口
検証 できない（そのまま代入される） Set の中でチェックできる
推奨する公開範囲 Private（隠す） Public（公開する窓口）

9.4 Get / Setを持つ完全なプロパティ

自動実装プロパティは便利ですが、値を検証したいときは完全な形のプロパティを自分で書きます。まず、実際にデータを保存する Private なフィールドを1つ用意します。これをバッキングフィールドと呼び、名前の先頭にアンダースコア（_）を付ける慣習があります。

Employee.vb クラスの定義 
Class Employee
    Private _age As Integer  ' バッキングフィールド(実際の保存場所)

    Public Property Age As Integer
        Get
            Return _age  ' 読み取り時:保存されている値を返す
        End Get
        Set(value As Integer)  ' valueに代入しようとした値が入る
            If value < 0 OrElse value > 150 Then
                Throw New ArgumentException("年齢は0〜150で指定してください")
            End If
            _age = value  ' 検証を通った値だけをフィールドに保存
        End Set
    End Property
End Class

Get ブロックは emp.Age のように読み取られたときに実行され、値を Return します。Set ブロックは emp.Age = 30 のように代入されたときに実行され、引数の value（Value キーワード）に代入しようとした値が渡されます。この value を検証してから、はじめてバッキングフィールドに保存することで、9.1 で見た「マイナスの年齢」を確実に防げます。

用語: Throwと例外

Throw は「これは異常な値です」とプログラムに知らせて、その場で処理を中断する仕組みです。この中断のことを例外と呼びます。ここでは、不正な値をそのまま _age に受け入れてしまわず、はっきりエラーとして知らせるために Set の中で Throw を使っています。発生した例外を受け止めてプログラムが止まらないようにする方法（Try ... Catch）は、第11章で詳しく学びます。

実行結果 
Unhandled exception. System.ArgumentException: 年齢は0〜150で指定してください

Unhandled exception.（未処理の例外です）で始まるこの表示が、.NET が実際に例外を検知したときの出力です。続く System.ArgumentException が例外の種類、その後ろがメッセージ本文で、プログラムはこの時点で処理を中断しています。

注意: プロパティ名とバッキングフィールド名を混同しない

もし _age という別名を使わず、プロパティの中で自分自身に代入すると、無限ループになってしまいます。

Public Property Age As Integer
    Get
        Return Age  ' NG: Ageを読むとこのGet自身が再び呼ばれる
    End Get
    Set(value As Integer)
        Age = value  ' NG: 無限ループでスタックオーバーフローになる
    End Set
End Property

必ず「プロパティ名（Age）」と「バッキングフィールド名（_age）」を別の名前にしましょう。

9.5 Sharedメンバー

これまで学んだフィールドやプロパティは、New でオブジェクトを作るたびに、オブジェクトごとに1つずつ用意されます。それに対して Shared を付けたメンバーは、いくつオブジェクトを作ってもクラス全体でただ1つだけ存在します。「これまでに何人の社員オブジェクトが作られたか」を数えるカウンタで確認してみましょう。

Employee.vb クラスの定義 
Class Employee
    Private Shared _count As Integer  ' クラス全体で1つだけ存在

    Public Sub New()
        _count += 1  ' インスタンスが作られるたびに+1
    End Sub

    Public Shared Function GetCount() As Integer
        Return _count  ' 現在までに作られた人数を返す
    End Function
End Class

Shared メソッドはオブジェクトを作らなくても、クラス名.メソッド名という形でそのまま呼び出せます。

Program.vb Sub Main内に記述 
Dim a As New Employee()
Dim b As New Employee()
Dim c As New Employee()
' クラス名.メソッド名で呼び出す(インスタンスは不要)
Console.WriteLine(Employee.GetCount())  ' 3 と表示される

a・b・c という3つの異なるオブジェクトを作っても、_count はクラスに1つしかないため、正しく「3」を数えられます。もし Shared を付けなければ、オブジェクトごとに別々の _count が作られてしまい、正しく数えられません。

用語: SharedとConstの違い

Const（第2章）は「宣言時に決まった値を変更できない定数」です。それに対して Shared は「クラス全体で1つの変数（値は実行中に変更できる）」を表します。「消費税率のように絶対に変わらない値」は Const、「作られたオブジェクトの数のように増減する値をクラス全体で共有したい」場合は Shared を使うと覚えましょう。

重要ポイント: フィールドをPublicのままにする危険性

この章の最初に見たとおり、フィールドを Public のまま公開すると、値の検証を一切挟まずに外部から書き換えられてしまいます。「フィールドは Private、公開する窓口はプロパティ」という基本方針を徹底することが、バグの少ないクラス設計への近道です。

やってみよう 9-1: プロパティでデータを守ろう

2つの課題を通して、プロパティによる検証（バリデーション）を体験しましょう。

課題1: Employeeクラスに年齢検証を追加する

  • 1 第8章の Employee クラスの Age を、バッキングフィールドを使った完全なプロパティに書き換える。
  • 2 Set の中で「0未満・150を超える」場合に ArgumentException を投げる検証を追加する。
  • 3 emp.Age = 200 を実行し、例外が発生することを確認する。

課題2: 残高を守る銀行口座クラスを作る

  • 1 BankAccount クラスを作り、残高（_balance）は Private にする。
  • 2 残高を読み取るための ReadOnly Property Balance を用意する。
  • 3 Deposit（入金）と Withdraw（出金）メソッドを作り、残高不足のときは例外を投げる。

解答例（課題2: BankAccountクラス）

Class BankAccount
    Private _balance As Integer  ' 残高はPrivateで保護(外部から直接変更不可)

    Public ReadOnly Property Balance As Integer
        Get
            Return _balance  ' 残高を読み取り専用で公開
        End Get
    End Property

    Public Sub Deposit(amount As Integer)
        If amount <= 0 Then
            Throw New ArgumentException("入金額は正の数で指定してください")
        End If
        _balance += amount  ' 検証を通ったら残高に加算
    End Sub
    ' (BankAccountクラスの続き)
    Public Sub Withdraw(amount As Integer)
        If amount > _balance Then
            Throw New InvalidOperationException("残高が不足しています")
        End If
        _balance -= amount  ' 残高から引く
    End Sub
End Class

動作確認

Dim account As New BankAccount()
account.Deposit(1000)
account.Withdraw(300)
Console.WriteLine($"残高: {account.Balance}円")  ' 残高: 700円

理解度確認クイズ

  • Q1. 「カプセル化」とは何ですか？ ATM の例を使って説明してください。

    回答を表示

    クラスの内部データを外部から直接触らせず、決められた窓口（プロパティやメソッド）を通してだけやり取りする設計の考え方です。銀行の金庫に直接手を入れられず、ATM という窓口を通してのみ入出金できるのと同じで、窓口側で「値が正しいか」をチェックしてから処理することで、不正なデータが内部に入り込むのを防げます。

  • Q2. アクセス修飾子 Public と Private は、それぞれどこからアクセスできますか？ フィールドとプロパティにはどちらを使うのが基本方針ですか？

    回答を表示

    Public はどこからでもアクセスでき、Private はそのクラスの中だけからアクセスできます。基本方針は「フィールドは Private にして隠し、外部に見せる窓口だけを Public なプロパティとして公開する」ことです。

  • Q3. 自動実装プロパティと、Get / Set を自分で書く完全なプロパティは、それぞれどのような場面で使い分けますか？

    回答を表示

    特に値のチェックが不要で、そのまま読み書きできればよい場合は自動実装プロパティ（Public Property Name As String）で十分です。一方、代入される値を検証したい（例: 年齢が0〜150の範囲か）場合は、バッキングフィールドと Get / Set を自分で書く完全なプロパティを使います。

  • Q4. Shared を付けたフィールドは、付けていない通常のフィールドと何が違いますか？

    回答を表示

    通常のフィールドは New でオブジェクトを作るたびにオブジェクトごとに1つずつ用意されますが、Shared を付けたフィールドはいくつオブジェクトを作ってもクラス全体でただ1つだけ存在し、すべてのオブジェクトで共有されます。作られたオブジェクトの数を数えるカウンタなどに使えます。
