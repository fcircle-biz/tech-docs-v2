総合ハンズオン - 日次売上集計バッチを設計・実行・テストする

この章は、これまで学んだことの総仕上げです。新しい文法はほとんど出てきません。第1章で見た日次売上処理の全体図を、設計 → 実装 → 実行 → テスト → 説明の流れで、実際に動くバッチとして完成させましょう。SALESSUM を完成版にして3つのジョブ（JSALPREP・JSALSUM・JSALCHK）をつなぎ、正常系・異常系・再実行の8つのテストで確かめます。最後は、異常が起きたときに「何が起き、どこで検出し、どう対処して再実行するか」を、自分の言葉で説明できるようにします。

この章で学ぶこと

  • 3つのジョブ（入力データ準備・売上集計・集計結果の確認）からなる日次売上集計バッチを設計し、実行できる
  • 正常系・異常系・再実行のテストケースを作り、結果を確認して記録できる
  • 異常時に「何が起き、どこで検出し、どう対処して再実行するか」を説明できる
  • 修了時に提出する成果物①〜⑤を仕上げられる

戻りコードとメッセージ

SALESSUM は、終わり方を戻りコード（RC）で知らせます。ジョブネットは、この RC を見て後続を動かすかどうかを決めます。RC の慣習は第5章（5.7）、SALESSUM のメッセージは第4章（4.7・4.8）で学びました。

RC意味SALESSUM のメッセージジョブネットでの扱い
0正常SLS001I（開始）・SLS002I（件数と合計）・SLS003I（終了）後続を実行する
4警告SLS101W（入力が0件）※完成版で追加警告として記録し、後続は実行する
8エラーSLS905E（集計対象日の誤り）・SLS906E（数値項目の不正値）・SLS907E（桁あふれ）※完成版で追加異常終了扱い。後続を実行しない

8.3 COBOL を完成版にする

第4章で作った SALESSUM（基本版）は、正しいデータが届いたときには正しく動きます。でも、データがおかしいときにおかしいと気づけません。この節では、基本版に4つのチェックを足して完成版にします（成果物②）。

基本版のままだと、何が困るか

まず基本版を別の名前で残してから、おかしなデータを食べさせてみます。基本版の salessum.cob を salessum-basic.cob にコピーしてコンパイルし、2つのデータで実行します。このデータは、8.6 のテストケース TC03・TC05 で使うものと同じです。

おかしなデータで基本版を動かす PCで実行 
cd ~/cobol-batch
# 基本版を別名で残して、コンパイルする
cp salessum.cob salessum-basic.cob
cobc -x salessum-basic.cob
# 実験1: 2件目の数量に英字 A を混ぜたデータ（TC03 と同じ）
printf '%s' 000100200100 00020A300250 000300100120 > data/bad.dat
echo 20261020 | DD_SALESIN=data/bad.dat DD_SUMOUT=data/out-bad.dat ./salessum-basic; echo "RC=$?"
# 実験2: 最大値のレコードを101件並べたデータ（TC05 と同じ）
for i in $(seq 101); do printf '%s' 999999999999; done > data/ovf.dat
echo 20261020 | DD_SALESIN=data/ovf.dat DD_SUMOUT=data/out-ovf.dat ./salessum-basic; echo "RC=$?"

実験1では、2件目の数量 0A3 が数字ではないのに、GnuCOBOL は計算を続け、合計が 43570 という誤った値になりました。それなのに RC=0（正常）で終わっています。実験2では、正しい合計は 10,089,799,101 円（11桁）ですが、10桁の WS-TOTAL に入りきらず、上の桁が切れて 0089799101 になりました。こちらも RC=0 です。

誤った結果が「正常終了」として出るのが、いちばん危険です

止まれば、人が気づいて直せます。しかし RC=0 で終わると、ジョブネットは次のジョブ（JSALCHK）を動かし、誤った集計結果が「確認済み」の顔をして翌朝の業務に使われてしまいます。バッチ処理では、おかしいデータを黙って通さないことが大切です。

z/OS ではどうなるか

z/OS で数字ではない値を計算に使うと、データ例外（S0C7）で異常終了（ABEND）するのが典型です。ただし、データの中身やコンパイルの指定によっては、異常終了せずに誤った値のまま計算が進むこともあります。異常終了すれば誤った値のまま進まないぶん GnuCOBOL よりましですが、何件目のどんなデータが原因なのかは、プログラムが表示しない限り分かりません。

GnuCOBOL では黙って計算が続きます。z/OS では、異常終了することも、誤った値のまま進むこともあります。どちらの環境でも困るので、プログラムの中で確かめて、分かりやすいメッセージと戻りコードで知らせます。

桁あふれは、どこで起きるか

桁あふれのチェックは、「どこまでの値なら安全か」を知っていると理解しやすくなります。1件の売上金額と、合計の入れ物の大きさを比べてみましょう。

見るもの計算値
1件の売上金額の最大999（数量）× 99,999（単価）99,899,001（8桁）。WS-AMOUNT PIC 9(8) に必ず収まる
合計の入れ物の最大WS-TOTAL PIC 9(10)9,999,999,999
最大値のレコード100件の合計99,899,001 × 1009,989,900,100（収まる）
101件目を足したとき9,989,900,100 ＋ 99,899,00110,089,799,101（11桁。桁あふれ）

最大値のレコード（999999999999）を101件並べると、101件目で桁あふれが起きます。これが、あとで行うテストケース TC05 の根拠です。

このブロックは抜粋です。基本版の INIT-PROC の ACCEPT の直後に、コメント行から END-IF までの6行を足します。IS NOT NUMERIC は「数字だけでできていない」という意味の条件です（第3章 3.5）。2026102X のように数字以外が混じる場合や、202610 のように8桁に足りず後ろが空白で埋まる場合に真になります。

このチェックは OPEN の前に置きます。まだどのファイルも開いていないので、ERROR-PROC は何も閉じずに終わります（開いたファイルだけを閉じるためのフラグは第4章で学びました）。なお、調べているのは「8桁の数字か」だけです。20261340 のような存在しない日付は通り抜けます。実務では、日付として正しいかも確かめます。

           END-ADD
           PERFORM READ-PROC.

数量か単価のどちらかが数字でなければ、SLS906E を表示して中止します。REC= には読んだ件数（WS-READ-CNT）を出すので「何件目か」が分かり、DATA= にはレコードの中身をそのまま出します。これだけで、運用担当は原因のレコードを探せます（TC03 では REC=000002 DATA=00020A300250）。PERFORM ERROR-PROC の最後は STOP RUN なので、呼び出した先で処理が終わり、次の COMPUTE には進みません。

用語: ON SIZE ERROR（桁あふれの検出）

計算結果が、受け取る項目に入りきらないことをサイズエラー（桁あふれ）と呼びます。ADD に ON SIZE ERROR を付けると、桁あふれが起きたときだけ、続く文を実行します。このとき WS-TOTAL の値は変わりません。付けないと、上の桁が黙って切れます（第3章 3.4 の 9990＋20 → 0010 と同じです）。

TERM-PROC（0件の警告を追加） PROCEDURE DIVISIONの抜粋 
      * 終了処理: 集計結果を書き、ファイルを閉じる
       TERM-PROC.
           MOVE WS-TARGET-DATE TO SUM-DATE
           MOVE WS-TOTAL TO SUM-TOTAL
           WRITE SUM-REC
           IF WS-FS-OUT NOT = "00"
               DISPLAY "SLS904E WRITE ERROR SUMOUT FS=" WS-FS-OUT
               MOVE 12 TO WS-RC
               PERFORM ERROR-PROC
           END-IF
           CLOSE SALES-FILE SUM-FILE
      * 入力が0件なら警告にする（RC=4）
           IF WS-READ-CNT = 0
               DISPLAY "SLS101W NO INPUT DATA"
               MOVE 4 TO WS-RC
           END-IF
           DISPLAY "SLS002I READ=" WS-READ-CNT " TOTAL=" WS-TOTAL
           DISPLAY "SLS003I SALESSUM END RC=" WS-RC
           MOVE WS-RC TO RETURN-CODE.

集計結果は、0件でも合計0の1件として書き出します。そのあとで SLS101W NO INPUT DATA を表示して RC=4（警告）にします。ERROR-PROC は呼ばず、最後まで進みます。0件は異常とは限りませんが、毎日売上があるはずの日に0件なら、前の工程の不具合かもしれません。そこで「止めずに知らせる」警告にしました。後続は動き、運用担当が内容を確認します（8.2 の表のとおりです）。

3本の JCL は、再実行しても安全なように作ってあります。主な工夫は次のとおりです。

  • 最初のステップで前回の出力を削除する（JSALPREP と JSALSUM。STEP010・IEFBR14・DISP=(MOD,DELETE,DELETE)）。削除するものが無くてもエラーになりません。これがないと、前回（前日や失敗した回）の出力が残っているため、翌日の実行や再実行で同名のデータセットが重複して割り当てエラーになります（第5章 5.6・第7章 7.6）。
  • 入力は DISP=SHR、出力は DISP=(NEW,CATLG,DELETE)。入力を読むだけなら、ほかのジョブが同時に読んでも構いません。JSALCHK は集計結果を読むだけなので、削除のステップを持ちません。
  • 出力の LRECL は FD のレコード長と一致させる（JSALPREP が作る売上明細は 12、JSALSUM が作る売上集計結果は 18）。ブロックの大きさは JCL に書かず、システムに任せます。
  • 集計対象日は SYSIN DD * で渡す（JSALSUM）。システム日付を使うと、翌日に再実行したときに別の日付で集計されてしまうからです（第6章 6.5）。

PC 用の疑似JCL・疑似ジョブネット（4本）

PC では、JCL の代わりに4本のシェルスクリプトを使います。ジョブ①〜③に当たる jsalprep.sh・jsalsum.sh・jsalchk.sh（疑似JCL）と、ジョブネットに当たる dailysal.sh（疑似ジョブネット）です。第6章・第7章で作った人は、内容が同じかを見比べてください。まだの人は、そのまま保存してください。

疑似JCL・疑似ジョブネットは代用です

シェルスクリプトで、JCL の事前削除・データの複写・DD 文による割り当てと、ジョブネットの「戻りコードで後続を決める」判断をまねているだけです。考え方を体験するための代用で、JCL・ジョブネットそのものではありません。カレンダー・スケジュール・監視・通知などの機能はありません。

5. 再実行の方法どのジョブから、どの順で。二重処理や上書きの注意点正しい受信データが届いたら、ジョブ①（JSALPREP）から DAILYSAL を再実行します。ジョブ①の STEP010 が古い売上明細を、ジョブ②の STEP010 が空の集計結果を削除してから作り直すので、上書きや二重集計の心配はありません（TC06）。再実行後は、ジョブ③の出力で合計金額が期待どおりかを確かめます。
6. 再発防止同じ失敗を防ぐ、または早く気づくための改善受信データの項目チェックを、前の工程や受信時にも入れてもらいます。異常時の通知先と手順を運用手順書に書いておきます。同じ不正値を再現するテストケースとして、TC03 を残します。

総合理解度チェック

  • Q1. COBOL と JCL の役割はどう違う？

    回答を表示

    COBOL は、業務処理のロジック（売上金額を数量×単価で求めて合計する、など）を記述するプログラミング言語です。JCL は、実行するプログラム、必要なデータセット、実行条件などを z/OS に指示する言語です。たとえば JSALSUM では、売上金額の計算は COBOL（SALESSUM）に、SALESSUM をどのデータセットで動かすか（SALESIN・SUMOUT・SYSIN）は JCL に書きます。計算方法を変えるなら COBOL、入力のデータセットを変えるなら JCL を直します。

  • Q2. SAMファイルと CSV ファイルは同じもの？

    回答を表示

    同じではありません。SAM は Sequential Access Method（順次アクセス方式）で、ファイルを先頭から順番に読み書きする「アクセスのしかた」を表します。CSV は、カンマ区切りの「データの表現形式」です。固定長の順次データ（売上明細の12バイトのレコードなど）では、区切り文字が存在しない場合があります。その場合は、何バイト目から何バイト分かで項目を区別します。

  • Q3. COBOL の ASSIGN と JCL の DD はどう関係する？

    回答を表示

    COBOL の外部ファイル名（ASSIGN TO SALESIN の SALESIN）と JCL の DD 名（//SALESIN DD …）を対応付け、JCL 側で具体的なデータセット（TRAIN01.SALES.DETAIL）を割り当てます。そのため、プログラムを作り直さずにデータを差し替えられます。利用する COBOL 処理系や実行環境の命名規則にも注意が必要です。PC の GnuCOBOL では、同じ名前を環境変数（DD_SALESIN）で実際のファイルに結び付けました。

  • Q4. JCL とジョブネットの違いは？

    回答を表示

    JCL は、主に一つのジョブの中の実行ステップと、データセットなどの資源の割り当てを定義します。ジョブネットは、複数のジョブの実行順序、先行・後続関係、実行条件、スケジュールを管理します。DAILYSAL では、JSALSUM の中で STEP010 → STEP020 の順に動かすことは JCL が、JSALPREP → JSALSUM → JSALCHK の順序と「RC が 8 以上なら後続を実行しない」という条件は、ジョブネット（ジョブ管理製品）が受け持ちます。

  • Q5. 先行ジョブが異常終了したらどうする？

    回答を表示

    まず、後続ジョブを実行してよいかを判断します（異常終了扱いなら、実行しません）。そのうえで、戻りコード、ジョブログ、作成済みのデータセットを確認して原因を調べ、直してから再実行します。再実行のときは、二重処理や既存データの上書き・削除に注意します。このガイドの設計では、事前削除のステップで前回の出力を消し、業務日付を SYSIN で渡すことで、何度実行しても同じ結果になるようにしています（TC06・TC07）。
