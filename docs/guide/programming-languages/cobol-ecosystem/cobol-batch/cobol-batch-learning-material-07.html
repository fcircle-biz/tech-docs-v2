ジョブネット - 先行・後続関係と異常時の再実行を設計する

第6章までで、1つのジョブ（JSALSUM）を JCL で定義し、COBOL と結び付けて動かせるようになりました。ところが夜間のバッチ処理は、入力データ準備・売上集計・集計結果の確認といった複数のジョブを、決まった順序と条件で、確実に動かすことで成り立っています。この章では、そのための仕組みであるジョブネットを、日次売上処理（DAILYSAL）を題材に設計します。先行・後続関係、戻りコードによる終了判定、スケジュール、異常終了したときの対応、そして安全にやり直すための再実行の設計を学び、最後に PC のシェルスクリプトで「前のジョブが失敗したら後ろを止める」動きを体験します。

この章で学ぶこと

  • ジョブネットとジョブ管理製品の役割を説明し、JCL との違いを比べられる
  • 先行・後続関係と、戻りコードによる実行条件（終了判定）を設計できる
  • スケジュールと、異常終了したときの対応の流れを説明できる
  • 再実行で起きる上書き・二重集計の問題と、その対策を説明できる
  • 日次売上ジョブネット（DAILYSAL）の構成図と定義表を作れる

7.1 ジョブネットとジョブ管理製品 - JCL だけでは足りないこと

第5・6章では、1つのジョブ（JSALSUM）の中身 ― ステップの並びと、データセットの割り当て ― を JCL で定義しました。しかし、夜間のバッチ処理は1つのジョブでは終わりません。日次売上処理では、JSALPREP（入力データ準備）→ JSALSUM（売上集計）→ JSALCHK（集計結果の確認）の3つのジョブを、順番に動かす必要があります。

これを人の手で運用すると、22時になったらジョブを投入し、終わるのを待ち、戻りコードを見て次のジョブを投入するかどうかを判断し、失敗したら後ろのジョブを止め、休みの日は動かさない、という作業を毎晩続けることになります。見落としや、投入の順番ミスも起きます。そこで、ジョブの実行順序・実行条件・スケジュールをあらかじめ定義して、自動で動かすジョブ管理製品（ジョブスケジューラ）を使います。その定義の単位がジョブネットです。

用語: ジョブ・ジョブネット・ジョブ管理製品

ジョブは、業務を構成する最小の単位です（このガイドでは、JCL で定義する JSALPREP・JSALSUM・JSALCHK）。ジョブネットは、実行順序を関連づけたジョブの集まりで、実行すると、中のジョブが決められた順序で自動的に実行されます。ジョブネットを定義して動かすソフトウェアがジョブ管理製品です。また、運用担当は、夜間バッチの実行状況を見守り、異常のときに対応する人のことです。

図の説明: ジョブ管理製品が、各ジョブの終了を受け取りながら、次のジョブを実行するかどうかを判断します。この図では JSALSUM が戻りコード 8 で終わったため、ジョブ管理製品が異常終了と判定し、JSALCHK を実行せずに運用担当へ知らせています。

JCL とジョブネットの比較

JCL が受け持つのは1つのジョブの中身で、ジョブネットが受け持つのはジョブとジョブの間です。2つは競合せず、役割を分けて組み合わせます。

比べる点 JCL（第5・6章） ジョブネット（ジョブ管理製品）
定義するもの 1つのジョブ（ステップの並び）。どのプログラムを、どのデータセットで動かすか 複数のジョブの集まり。ジョブの実行順序・実行条件・スケジュール
順序と条件の制御 ステップを上から順に実行し、IF/THEN/ELSE/ENDIF や COND で、実行するかどうかを決める 先行ジョブ → 後続ジョブの関係と、先行ジョブの終了状態で、後続のジョブを実行するかどうかを決める
起動のきっかけ ジョブを投入する（SUBMIT） 決まった時刻（スケジュール）、ファイルの到着などの事象
休業日・遅れの扱い 扱わない 営業日カレンダー、開始遅延監視・終了遅延監視など
異常のとき 戻りコードや ABEND をジョブログに記録する。RESTART で、指定したステップからジョブを再開できる 後続を止める、運用担当へ通知する、再実行の範囲を選ぶ

ジョブを分けて、ジョブネットでつなぐ理由

3つの処理を、1つの JCL に3つのステップとして書くこともできそうです。ステップ同士の制御なら、JCL の IF/THEN/ELSE や COND でもできます（第5章）。それでも、ジョブに分けてジョブネットでつなぐ設計には、次のような利点があります。

  • 再実行の範囲を選べる: 問題のあったジョブから、必要な範囲だけをやり直せます。
  • 実行条件をジョブごとに決められる: JSALSUM の RC=4 は後続を続け、RC=8 は止める、といった使い分けができます。
  • 起動のきっかけを選べる: 時刻で動かす、ファイルの到着で動かす、といった違いを、ジョブネット単位で定義できます（7.3・7.4）。
  • 業務の区切りが名前に表れる: 「入力データ準備」「売上集計」「集計結果の確認」のように分けておくと、通知を受けたとき、どの業務で失敗したかがすぐ分かります。

7.2 先行・後続関係 - どのジョブの後に、何を動かすか

ジョブネットの基本は、ジョブとジョブの先行・後続関係です。ジョブAが終わってからジョブBを動かしたいとき、AをBの先行ジョブ、BをAの後続ジョブと呼びます。JP1/AJS3 では、ジョブとジョブを関連線と呼ぶ矢印でつなぎ、実行順序を作ります。通常の後続ジョブは、先行ジョブが正常終了したときに実行されます。

先行・後続関係は、直列・並列・合流の3つの型を組み合わせて表せます。次の図は、3つの型を説明するための例です（DAILYSAL とは別のジョブネットです）。

flowchart LR ST(["開始"]) --> R["売上データ受信"] ST --> M["商品マスタ更新"] R --> T["売上集計"] M --> T T --> C["集計結果の確認"]

図の説明: 開始の後で、売上データ受信と商品マスタ更新が同時に動きます（並列）。売上集計は、この2つが両方とも終わってから動きます（合流）。その後に、集計結果の確認が続きます（直列）。

  • 直列: 前のジョブが終わってから、次のジョブを実行します。売上集計 → 集計結果の確認が当たります。DAILYSAL の JSALPREP → JSALSUM → JSALCHK も、この型です。
  • 並列: 互いに関係のないジョブを、同時に実行します。売上データ受信と商品マスタ更新が当たります。
  • 合流: 複数の先行ジョブが、すべて正常終了するのを待ってから、後続のジョブを実行します。片方だけが終わっても動かないので、売上データ受信が異常終了すれば、商品マスタ更新が正常でも売上集計は実行されません。受信できていない売上を除いて集計してしまうことを防ぐためです。

先行・後続関係を決める3つの質問

ジョブの順序は、思いつきではなく、次の3つの質問で決めます。

  1. 前のジョブの出力を、このジョブの入力に使うか。使うなら、前のジョブを先行ジョブにして、直列でつなぎます。
  2. 同じデータセットを、同時に書き換えるおそれはないか。あるなら、並列にしません。直列にするか、同時に動かさない指定（7.3 の排他実行）を使います。
  3. 前のジョブが失敗したとき、このジョブを動かしてよいか。よくないなら、先行ジョブが正常終了したときだけ実行します（既定の動きです）。警告で終わったときも動かしてよいかは、7.3 で決めます。

重要ポイント: 順序は「データの受け渡し」で決まる

日次売上処理では、JSALPREP が作る売上明細（TRAIN01.SALES.DETAIL）を JSALSUM が読み、JSALSUM が作る売上集計結果（TRAIN01.SALES.SUMMARY）を JSALCHK が読みます。出力が次のジョブの入力になっているので、この順に直列でつなぎます。順序を入れ替えると、まだ作られていない（または前回の）データを読んでしまいます。

JP1/AJS3 では、関連線で結べるのは同じジョブネットの中のジョブ同士です。異なるジョブネットのジョブ同士は結べないので、どこまでを1つのジョブネットにまとめるかも設計の一部になります。設計の考え方は、日立のJP1/AJS3 設計ガイド（業務設計編）2.2 ジョブネットの構築のための検討で確認できます。

7.3 実行条件と終了判定 - 後続を動かしてよいかを決める

先行ジョブが終わったとき、後続を動かしてよいかどうかは、先行ジョブがどのように終わったかで決まります。ジョブ管理製品は、ジョブの戻りコード（RC。第5章）を受け取り、あらかじめ決めたしきい値（境目の値）と比べて、ジョブの終了状態を判定します。これが終了判定です。たとえば「0 は正常、1〜4 は警告、5 以上は異常」と決めます。SALESSUM の戻りコードの規約に当てはめると、JSALSUM の終了判定は次の表のようになります。

RC 意味（SALESSUM の規約） 終了判定（JP1/AJS3 の呼び名） 後続の JSALCHK 運用
0 正常（1件以上を集計できた） 正常（正常終了） 実行する なし
4 警告（入力が 0 件だった） 警告（警告検出終了） 実行する 警告として記録し、運用担当が内容を確認する
8 以上
（8・12・16）		 エラー（集計対象日の誤り、数値項目の不正値、合計の桁あふれ）、重大なエラー（ファイルの OPEN・READ・WRITE の失敗）。16 は SALESSUM では使わない 異常（異常検出終了） 実行しない 運用担当へ通知し、原因を調べる

警告のときに後続を動かすかどうかは、設計で決めることです。DAILYSAL では、RC=4（入力が 0 件）でも後続を実行し、運用担当が内容を確認する設計にします。そのとおりに動かすための設定は、使う製品のマニュアルで確認します。

RC=8 や RC=12 は ABEND ではありません。プログラム自身が異常を見つけ、戻りコードで失敗を伝えて終わっています。それをジョブ管理製品がしきい値で判定し、「異常終了と判定した」状態にするので、このガイドでは異常終了扱いと呼びます。

JP1/AJS3 では、これを「しきい値による判定」で設定します。戻り値に対して警告終了しきい値と異常終了しきい値を決めるもので、設計ガイドの例では、異常終了しきい値を 4 にすると、戻り値 4 以下は正常終了、5 以上は異常終了になります。「RC が 5 以上なら異常終了と判定する」は異常終了しきい値で、「RC=4 は警告」という区分は警告終了しきい値で表す、という考え方です。終了状態の呼び名は、ジョブが「正常終了／警告検出終了／異常検出終了」、ジョブネットが「正常終了／警告終了／異常終了」です。具体的な設定値、判定の細かな規則、設定画面の項目名は、使う製品とバージョンのマニュアルで確認してください。

ステップが実行されずに終わる2つの場合

ジョブの異常は、戻りコードだけで表れるとは限りません。ステップが実行されずに終わる場合があります。原因は大きく2つに分けられます。この2つは原因も調べ方も違うので、区別して覚えましょう。

種類 例 ステップの動き
割り当てエラー
（データセットの割り当ての失敗）		 存在しないデータセットを入力に指定した（IEF212I … DATA SET NOT FOUND）。同名のデータセットが既にあるのに、DISP=NEW で作ろうとした（例: IGD17101I DATA SET … NOT DEFINED BECAUSE DUPLICATE NAME EXISTS IN CATALOG） プログラムが動く前に失敗し、そのステップは実行されない（IEF272I … STEP WAS NOT EXECUTED）
JCL の構文エラー ジョブ名が9文字以上、継続行の前の行末にカンマが無い、など、JCL の書き方のルール（第5章 5.2）に反している JCL を正しく解釈できず、ステップが実行されない

次のジョブログは、JSALPREP で受信データのデータセットが無かったときの例です（読み方は第6章 6.7）。ジョブログの表示は環境によって異なり、ここでは読み方を学ぶための例として示しています。

JSALPREP のジョブログ（JESYSMSG の抜粋。受信データが無い例） ジョブログの例 
IEF142I JSALPREP STEP010 - STEP WAS EXECUTED - COND CODE 0000
IEF212I JSALPREP STEP020 SYSUT1 - DATA SET NOT FOUND
IEF272I JSALPREP STEP020 - STEP WAS NOT EXECUTED

ログの COND CODE（第5章）が、そのステップの戻りコードです。戻りコードとして表れているのは STEP010 の 0000 だけで、STEP020 は実行されていません。戻りコードの値だけを見ていると、この異常に気づけないことがあります。

ABEND とステップ未実行は、必ず異常として扱う

次の終わり方は、戻りコードの値にかかわらず、ジョブネットでは正常終了として扱ってはいけません。(1) ABEND（S0C7 など）で、ステップが異常終了した。(2) 割り当てエラーや JCL の構文エラーで、ステップが実行されなかった。製品がこうした終わり方をどの終了状態として扱うかは、製品や設定によって異なります。設計のときに製品のマニュアルで確かめ、異常として扱う設定になっていることを確認します。

後続を動かす条件の種類

後続を動かす条件は、先行ジョブの終了状態だけではありません。ジョブネットでは、次のような条件を組み合わせます。

条件の種類 意味（JP1/AJS3 の用語の例） 日次売上処理での使いどころ
先行ジョブの終了状態 先行ジョブがどう終わったかで、後続を実行するかどうかを決める。通常の後続は、先行ジョブが正常終了したときに実行される JSALPREP が正常終了したら、JSALSUM を実行する
判定ジョブ（条件分岐） 戻りコード、またはファイルの有無を判定し、条件が真のときだけ、後続（従属ジョブ）を実行する 受信データが届いた日だけ集計する、という設計もできる（DAILYSAL では、受信データが無いことを異常として止める）
起動条件 ファイルの更新などの事象をきっかけに、ジョブネットを動かし始める 22:00 の代わりに、受信データの到着で DAILYSAL を始める（やってみよう 7-2）
排他実行 同じ資源を使うジョブを、同時に動かさない（排他実行リソース。同じリソース名を指定したジョブ同士は、同時に実行されない） 同じ集計結果を更新する別のジョブがあるとき、JSALSUM と同時に動かさない
保留 あらかじめ、実行しないよう設定しておく。保留を解除すると実行できる システムのメンテナンス中など、動かしたくない日に DAILYSAL を保留にする

条件を組み合わせたジョブネットの定義例は、日立のJP1/AJS3 設計ガイド（業務設計編）2.4 さまざまなジョブネット定義で確認できます。

7.4 スケジュール - いつ、どの日に動かすか

ジョブネットは、順序や条件だけでなく、いつ動かすかも定義します。夜間バッチは、決められた時間帯（バッチウィンドウ。第1章）の中で、確実に終わらせなければならないからです。スケジュールでは、主に次のことを決めます。右端は、DAILYSAL に当てはめた例です。

決めること 意味 DAILYSAL の例
営業日カレンダーと起動時刻 どの日が営業日（バッチを動かす日）かを決めたカレンダーと、何時に動かし始めるか 会社の営業日カレンダーに従い、毎営業日 22:00 に起動する
休業日の扱い 起動時刻が休業日に当たったとき、動かさないのか、別の日に振り替えるのか 休業日は動かさない。振り替える場合は、集計対象日をどうするかも含めて、業務の担当者と取り決める
バッチウィンドウ バッチ処理を動かせる時間帯。翌朝の業務が始まるまでに終える必要がある 22:00 から翌朝 6:00 まで（第1章の例）
遅延の監視 予定の時刻になっても始まっていない（開始遅延）、終わっていない（終了遅延）ことを見つける 予定の開始時刻（22:00）を過ぎても始まらない場合と、実行時間を測って決めた終了予定時刻（バッチウィンドウの終わりの 6:00 より前。対処の時間を残す）を過ぎても終わらない場合に、運用担当へ通知する

遅延の監視は、「失敗したことを確実に知らせる」ための仕組みの一つです。ジョブが異常終了すれば通知が届きますが、動き続けているのに終わらない、あるいはそもそも始まっていない場合は、異常終了の通知では気づけません。時刻で見張ることで、バッチウィンドウに間に合わなくなる前に、手を打てます。予定の時刻は、本番に近いデータ量で実行時間を測って決めます。

用語: 実行登録・遅延監視（JP1/AJS3 の例）

JP1/AJS3 では、ジョブネットを実行するために登録することを実行登録と呼び、計画実行登録・確定実行登録・即時実行登録の種類があります。計画実行登録は、スケジュールの定義に従って起動する登録で、毎営業日 22:00 に動く DAILYSAL がこれにあたります。確定実行登録は、登録時に指定した回数または期間の分だけ予定を確定させて実行する登録です。即時実行登録は、登録と同時に1回だけ実行する登録です。予定の時刻までに開始・終了したかを見張る機能は開始遅延監視・終了遅延監視と呼びます。ほかの製品では呼び名や設定が異なります。

集計対象日と、実行した日は別のもの

スケジュールで特に注意したいのが日付の扱いです。DAILYSAL が 10月20日の 22:00 に起動し、10月20日分の売上を集計するなら、集計対象日（業務日付）は 20261020 です。ふだんは「実行した日」と同じですが、異常が起きて翌朝に再実行すると、実行した日は 10月21日になります。それでも集計するのは 10月20日分の売上なので、集計対象日は 20261020 のままでなければなりません。このため集計対象日は、プログラムがシステム日付から決めるのではなく、SYSIN などで外から渡します（第6章 6.5。再実行との関係は 7.6）。

7.5 異常終了したときの対応 - 止めて、知らせて、調べる

DAILYSAL のどれかのジョブが異常終了と判定されると、ジョブ管理製品は後続のジョブを実行せず、運用担当に通知します（通知の方法は、製品や運用で決めます）。後続を止めるのは、壊れた結果や、途中までしか作られていない結果を、後ろのジョブが使ってしまうのを防ぐためです。止まる範囲と、そのとき残っているデータセットは、次のようになります。

7.6 再実行の設計 - 何度やり直しても安全にする

異常終了のあとの再実行は、夜間や早朝の限られた時間で、確認を急ぎながら行います。このとき手順を間違えると、集計結果が上書きされたり、二重に集計されたりして、最初の失敗よりも大きな問題になることがあります。そこで、再実行しても安全なように、ジョブネットとジョブをあらかじめ設計しておきます。

再実行の種類（JP1/AJS3 の例）

ジョブ管理製品には、異常終了したジョブネットを再実行する機能があり、どこからやり直すかを選べます。JP1/AJS3 では、ルートジョブネット（いちばん上のジョブネット。DAILYSAL にあたります）を再実行するとき、次の5つの種類から選びます。名称や選べる範囲は製品ごとに違うので、研修先の製品の用語に読み替えてください。

再実行の種類 やり直す範囲 DAILYSAL での使いどころ（例）
異常終了ジョブから 異常終了したジョブから再実行する。直前に正常終了したジョブはやり直さない JSALSUM が RC=8 で止まり、原因が JSALSUM 側（たとえば集計対象日の指定ミス）にあるとき。JSALPREP の結果は正しいので、JSALSUM からやり直す
異常終了ジョブの次から 異常終了したジョブの次のジョブから再実行する 異常終了したジョブの処理を、別の方法で済ませたときだけ使う。飛ばしたジョブの結果が本当にそろっているかを、必ず確認する
異常終了ジョブネットから 異常終了したジョブを直下に含むジョブネットから再実行する ジョブネットを入れ子（ネストジョブネット）にしたときに使い分ける。DAILYSAL のように入れ子が無い場合は DAILYSAL 全体が対象になり、「ジョブネットの先頭から」と同じ範囲になる

再実行の種類は、原因のある場所で選びます。原因が JSALSUM にあるのに JSALPREP から全部やり直すと時間がかかり、原因が JSALPREP にあるのに JSALSUM だけをやり直すと、同じ失敗を繰り返します。詳細は、日立のJP1/AJS3 導入ガイド 4.5.11 実行が終了したジョブネットやジョブを再実行するで確認できます。

紹介: JCL の RESTART と GDG

RESTART: JOB 文に RESTART=ステップ名 を指定すると、そのステップからジョブを再開できます。ただし、再開位置より前のステップは実行されません。たとえば JSALSUM を STEP020 から再開すると、STEP010 の事前削除が行われないため、RC=8 や 12 で終わって残った集計結果と同名のデータセットが重複し、割り当てエラーになることがあります。DAILYSAL では、ジョブの先頭からやり直す設計にしています。

GDG（世代データグループ）: 同じ名前のデータセットを、世代で管理する仕組みです。JCL では (+1) が新しく作る世代、(0) が最新の世代、(-1) がその1つ前の世代を表します。失敗した実行で作られた世代を、後続のジョブが「最新」として読んでしまわないよう、扱いを決めておく必要があります。このガイドでは使いません。

再実行で起きる問題と対策

再実行で起きる問題は、パターンが決まっています。次の5つの問題と対策を、DAILYSAL がどう防いでいるかとあわせて覚えておきましょう。

問題 何が起きるか 対策 DAILYSAL での対応
1. DISP=NEW の出力が残っていて割り当てエラー（同名データセットの重複） 前回の実行で作られた同名のデータセットが残っていると、DISP=(NEW,CATLG,DELETE) で作ろうとしたときに割り当てエラーになり、そのステップは実行されない 事前削除ステップを置く（IEFBR14 と DISP=(MOD,DELETE,DELETE)）。あれば消し、無くてもエラーにしない JSALPREP と JSALSUM の STEP010 が、前回の出力（売上明細・集計結果）を削除する
2. DISP=MOD・OPEN EXTEND で追記して二重計上 出力に追記する作りだと、再実行のたびに同じレコードが末尾に追加され、二重に計上される（下の「対策2」で、PC で2回追記すると同じレコードが2件になることを確かめます） 追記せず、毎回作り直す（COBOL は OPEN OUTPUT、JCL は事前削除 ＋ DISP=NEW） SALESSUM は OPEN OUTPUT で書く。集計結果は常に1件（第8章 TC07: JSALSUM を2回続けて実行しても1件）

4. システム日付で結果が変わる プログラムがシステム日付を集計対象日に使うと、翌日に再実行したとき、別の日付で集計される 業務日付（集計対象日）を、SYSIN などで外から渡す JSALSUM は SYSIN で 20261020 を受け取る（第6章 6.5）。再実行でも同じ値を渡す
5. 途中まで書かれた出力が使われる RC=8 以上や ABEND で終わったジョブの出力（空、または途中まで）が残り、後続のジョブや利用者が、正しい結果だと思って使う 異常終了扱いになったジョブ（RC=8 以上・ABEND・ステップが実行されずに終わった）の出力は使わず、後続を止める。RC=4（警告）の出力は、運用担当が内容を確かめてから使う 異常終了と判定したら、後続の JSALCHK を実行しない（第8章 TC03: PC では集計結果のファイルが 0 バイトで残る）

対策1: 事前削除で、前回の出力を消しておく

JSALSUM の STEP010 と、STEP020 の出力 DD を並べて見ます（第5・6章で読んだ JSALSUM の JCL の一部です）。

JSALSUM の JCL の抜粋（事前削除と出力の DD） z/OS JCLの抜粋

//STEP010  EXEC PGM=IEFBR14
//DEL1     DD DSN=TRAIN01.SALES.SUMMARY,
//            DISP=(MOD,DELETE,DELETE),UNIT=SYSDA,SPACE=(TRK,0)

  1. IEFBR14 は、何も処理せずにすぐ終わるプログラムです。ここでは、DD 文によるデータセットの割り当てと、DISP による処置だけを行わせるために使います。
  2. DISP=(MOD,DELETE,DELETE) の MOD は、データセットが無ければ新しく作るものとして扱われます。そのため、前回の集計結果があれば、ステップの終了時に「正常終了時: DELETE」で削除されます。無ければ、新しく作られてすぐ削除されるので、何も残らず、エラーにもなりません。
  3. 削除が済んでいるので、STEP020 の DISP=(NEW,CATLG,DELETE) は、同名のデータセットの重複にならずに、集計結果を新しく作れます。

この事前削除は、DISP の規則を利用した方法の一つです。ほかに、既存のデータセットを消すだけなら DISP=(OLD,DELETE,DELETE) も使えますが、データセットが無いと割り当てエラーになります。IDCAMS というユーティリティの DELETE コマンド（NONVSAM を指定）と SET MAXCC=0 を組み合わせる方法もあります（紹介のみ）。

対策2: 追記せず、毎回作り直す - 二重計上を確かめる

対策1の事前削除（DEL1）では、MOD は「データセットが無くてもエラーにしない」ための指定で、実際に消しているのは DELETE の部分です。一方、出力のデータセットに DISP=MOD を指定すると、既にあるデータセットの末尾に続けて書く（追記する）指定になります。COBOL の OPEN EXTEND（第4章 4.4）も同じ追記の動きです。追記するとどうなるかを、PC で確かめましょう。PC では、シェルの >> が追記の動きをします。集計結果の1件を用意し、「1回目の実行」と「再実行」で2回追記します（~/cobol-batch で実行します）。

追記する設計は、再実行に弱い

追記は、1回だけ正しく実行された場合にしか、正しい結果になりません。異常終了のあとに再実行する設計では、追記を使わず、毎回作り直します。COBOL では OPEN OUTPUT（既存の中身を消して書き直す）、JCL では事前削除 ＋ DISP=NEW です。SALESSUM は OPEN OUTPUT を使っているので、JSALSUM を何度実行しても、集計結果は1件のままです（第8章の TC07 で確かめます）。

重要ポイント: 「何度実行しても同じ結果になる」ように作る

同じ入力と同じ集計対象日で実行すれば、1回目でも、失敗のあとの再実行でも、結果が変わらないように作ります。そのために、(1) 出力は毎回作り直す、(2) 入力は消さずに残す、(3) 日付は外から渡す、の3つを守ります。上の5つの対策は、すべてこの3つのどれかにあたります。なお、同じ操作を何度繰り返しても結果が変わらない性質を、IT の用語で冪等性（べきとうせい）と呼ぶことがあります。

再実行を始める前に確認すること

設計が整っていても、再実行の前の確認は欠かせません。次の6点を確かめてから始めます。

  1. 原因は取り除かれたか: 取り除かないまま再実行しても、同じ失敗を繰り返します。
  2. どこから再実行するか: 原因のある場所で、再実行の種類を選びます（前の表）。
  3. 残っているデータセットはどれか: 事前削除で消えるもの、手作業で消すもの、前回の結果のまま残っているものを把握します。
  4. 二重処理にならないか: 追記、二重の登録や送信など、同じ処理を2回行うと困る処理が含まれていないかを確かめます。
  5. 集計対象日は元のままか: 再実行する日ではなく、本来の集計対象日（例: 20261020）を渡します。
  6. 途中の結果が、すでに使われていないか: 後続のジョブや他のシステムが使っていた場合は、そちらの訂正も必要です。

7.7 日次売上ジョブネットを設計する - 構成図と定義表にまとめる

ここまでの内容を使って、日次売上ジョブネット DAILYSAL を設計します。設計の結果は、構成図と定義表の2つにまとめます。この2つがそろえば、ほかの担当者がジョブ管理製品に定義を入力でき、運用担当が異常時に何をすればよいかも分かります。これが修了成果物④です。設計は、次の順に進めます。

  1. ジョブを洗い出す: 業務を意味のまとまりで分けます（入力データ準備・売上集計・集計結果の確認）。
  2. 先行・後続関係を決める: 出力が次の入力になる順に、つなぎます（7.2）。
  3. 各ジョブの終了判定を決める: 正常とみなす RC、警告、異常を決めます（7.3）。
  4. 起動のきっかけとスケジュールを決める: 起動時刻、休業日、遅延の監視を決めます（7.4）。
  5. 異常時の対応と再実行の方法を決める: 通知、止める範囲、どこから再実行するかを決めます（7.5・7.6）。

ジョブネット全体の設定は、ジョブネット名が DAILYSAL（日次売上ジョブネット）、起動が毎営業日 22:00、集計対象日は SYSIN で JSALSUM に渡す（例: 20261020）、終了遅延の監視は、実行時間を測って決めた終了予定時刻（バッチウィンドウの終わりの翌朝 6:00 より前に、対処と再実行の時間を残して決める）です。設計の判断の理由は、次のとおりです。

  • 3つのジョブを直列でつなぐ: JSALPREP の出力（売上明細）を JSALSUM が読み、JSALSUM の出力（集計結果）を JSALCHK が読むからです（7.2）。
  • JSALPREP と JSALSUM を、事前削除のステップから始める: どこで失敗しても、再実行したときに同名のデータセットが重複して割り当てエラーにならないようにするためです（7.6）。
  • 異常終了と判定したら、後続を止めて通知する: 空や途中までの集計結果を、JSALCHK が「確認済みの結果」として扱ってしまうのを防ぐためです。夜間に人が見ていなくても、失敗に気づけるようにするためでもあります（7.5）。
  • 集計対象日を SYSIN で渡す: 再実行の日が変わっても、同じ集計対象日で、同じ結果になるようにするためです（7.4・7.6）。

注意: RC=4 を警告として続行する判断

この設計では、JSALSUM が RC=4（入力が 0 件）で終わっても、後続を続けます。売上が無い日なら問題ありませんが、受信データが欠けていただけかもしれません。警告は後続を止めないので、だれも気づかないまま、合計 0 円の結果が使われるおそれがあります。PC の疑似ジョブネットでも、入力が 0 件の日に JSALCHK は「合計金額 0000000000」を表示して RC=0 で終わり、警告は JSALCHK の結果には表れません（第8章の TC02）。

対策は、警告を記録し、だれが・いつまでに・何を見て確認するかを、運用の決まりとして定めておくことです。受信データの欠落だったと分かれば、JSALPREP から再実行します。

ジョブにあたる3つのスクリプト

まず、ジョブにあたる3つのスクリプトです。コメントに、z/OS で対応する処理を書いています。1つ目は、ジョブ① JSALPREP です。

jsalprep.sh（疑似JCL：ジョブ① 入力データ準備） PCで実行 
#!/bin/bash
# 疑似JCL（入力データ準備ジョブ JSALPREP）: 受信データを集計用の入力にコピーする
# STEP010: 前回の集計用入力を削除する（IEFBR14 による事前削除の代わり）
rm -f data/sales.dat
# STEP020: 受信データをコピーする（IEBGENER の代わり）
if [ ! -f data/sales-recv.dat ]; then
    echo "JSALPREP STEP020: data/sales-recv.dat が見つかりません"
    echo "JSALPREP RC=12（z/OS では割り当てエラーでステップが実行されないケース）"
    exit 12
fi
cp data/sales-recv.dat data/sales.dat
echo "JSALPREP STEP020 RC=0"
exit 0

rm -f が STEP010 の事前削除（IEFBR14）、cp が STEP020 の複写（IEBGENER）にあたります。受信データが無いときは RC=12 で終わります。z/OS では、受信データのデータセットが無いと、STEP020 は割り当てエラーで実行されません（第6章 6.4）。その「ステップが実行されずに終わった」状態を、PC では RC=12 で表しています。2つ目は、ジョブ② JSALSUM で、第6章で作ったものと同じです。

jsalsum.sh（疑似JCL：ジョブ② 売上集計。第6章と同じ） PCで実行 
#!/bin/bash
# 疑似JCL（売上集計ジョブ JSALSUM）: DD 文の代わりに環境変数で割り当てる
BIZDATE=20261020                 # 集計対象日（//SYSIN DD * の中身にあたる）
# STEP010: 前回の集計結果を削除する（IEFBR14 による事前削除の代わり）
rm -f data/summary.dat
# STEP020: SALESSUM を実行する（//SALESIN DD・//SUMOUT DD の代わり）
export DD_SALESIN=data/sales.dat
export DD_SUMOUT=data/summary.dat

rc=$?
echo "JSALSUM STEP020 RC=$rc"
exit $rc

DD_SALESIN と DD_SUMOUT が、DD 文の代わりに入力と出力のファイルを結び付けます。集計対象日 BIZDATE は、ここでは固定値で書いています（//SYSIN DD * の中身にあたります）。実務では、ジョブ管理製品などから業務日付を渡すことが多いです。3つ目は、ジョブ③ JSALCHK です。

jsalchk.sh（疑似JCL：ジョブ③ 集計結果の確認） PCで実行 
#!/bin/bash
# 疑似JCL（集計結果の確認ジョブ JSALCHK）: 集計結果を画面に出して確認する
if [ ! -s data/summary.dat ]; then
    echo "JSALCHK: data/summary.dat がないか空です RC=12"
    exit 12

集計結果が無い、または空のときは RC=12 で終わります。あるときは、先頭の8桁（集計対象日）と、9〜18桁目（合計金額）を取り出して表示します。

ジョブネットにあたる dailysal.sh

いよいよジョブネット DAILYSAL にあたるスクリプトです。ジョブを順に呼び出し、戻りコードを見て、次を実行するかどうかを決めています。

dailysal.sh（疑似ジョブネット：日次売上 DAILYSAL） PCで実行 
#!/bin/bash
# 疑似ジョブネット（日次売上 DAILYSAL）: 前のジョブの戻りコードで次を決める
./jsalprep.sh; rc=$?
if [ "$rc" -ne 0 ]; then
    echo "DAILYSAL: JSALPREP が異常終了（RC=$rc）。後続を実行しません"; exit "$rc"
fi
./jsalsum.sh; rc=$?
if [ "$rc" -gt 4 ]; then
    echo "DAILYSAL: JSALSUM が異常終了（RC=$rc）。後続を実行しません"; exit "$rc"
elif [ "$rc" -eq 4 ]; then
    echo "DAILYSAL: JSALSUM が警告終了（RC=4）。内容を確認してください"
fi
./jsalchk.sh; rc=$?
echo "DAILYSAL: 終了（最後のジョブの RC=$rc）"
exit "$rc"
  1. ./jsalprep.sh; rc=$? は、ジョブを実行し、戻りコードを rc に受け取ります。ジョブ管理製品が、ジョブの戻りコードを受け取ることにあたります。
  2. JSALPREP は、rc が 0 以外なら異常終了と判定します。後続を実行せず、exit "$rc" でジョブネットを終えます（後続を止める動きです）。
  3. JSALSUM は、rc が 4 より大きければ（5 以上なら）異常終了と判定して止めます。4 のときは、警告のメッセージを表示して先へ進みます（7.3 の終了判定）。なお、RC=1〜3 は SALESSUM が返さない値なので、この疑似ジョブネットでは区別していません。本物の製品では、しきい値で警告などに振り分けます。
  4. 最後に JSALCHK を実行し、その戻りコードを DAILYSAL の戻りコードとして返します。

このスクリプトは RC=8 や RC=12 に「異常終了」と表示しますが、これは ABEND ではありません。7.3 で説明したとおり、ジョブネットが戻りコードのしきい値で判定した「異常終了扱い」です。

手順

  • 1 7.7 の定義表で、JSALSUM の「正常とみなす RC」と「異常時の対応」を確認する。
  • 2 次の3つのケースで、JSALPREP・JSALSUM・JSALCHK が「実行される」か「実行されない」かを、ケースごとに書き出す。
    (a) JSALSUM が RC=4 で終わった。
    (b) JSALSUM が RC=8 で終わった。
    (c) JSALPREP の STEP020 が、受信データが無いために割り当てエラーとなり、実行されなかった。

解答例

  • ・(a) RC=4: 3つのジョブとも実行されます。RC=4 は警告で、後続を止めない設計だからです。運用担当は、入力が 0 件になった理由（本当に売上が無い日か、受信データの欠落か）を確認します。
  • ・(b) RC=8: JSALPREP と JSALSUM は実行され、JSALCHK は実行されません。RC=8 は異常終了扱いで、後続を実行せず通知します。運用担当は、ジョブログの SLS9xxE のエラーメッセージ（たとえば SLS906E は数値項目の不正値）から原因を調べます。
  • ・(c) 割り当てエラー: JSALPREP は STEP010 まで実行されますが、STEP020 は実行されません。JSALSUM と JSALCHK も実行されません。ステップが実行されずに終わったジョブは、戻りコードが小さく見えても、異常終了扱いにするからです。運用担当は、割り当てエラーのメッセージ（IEF212I DATA SET NOT FOUND）から、受信データが届いているかを確認します。

理解度確認クイズ

  • Q1. 「3つの処理のステップを、すべて1つの JCL に書けば、ジョブネットは要らないのではないか」という意見があります。どう答えますか？

    回答を表示

    ステップ同士の実行制御なら、JCL の IF/THEN/ELSE や COND でもできます。しかし、ジョブとジョブの間の制御 ― 実行順序、時刻やファイルの到着による起動、営業日カレンダー、遅延の監視、異常時の通知、再実行の範囲の選択 ― は、ふつうジョブ管理製品（ジョブネット）の役割です。また、1つにまとめると、再実行や判断の単位が大きくなります。RESTART でステップから再開することもできますが、その位置を人が判断して指定する必要があります。業務の区切りごとにジョブを分け、ジョブネットでつなぐほうが、実行条件の細かな設計や、必要な範囲だけの再実行がしやすくなります。

  • Q2. 夜間に「JSALPREP が異常終了と判定された」という通知が届きました。運用担当がジョブログで最初に確認することを、2つ挙げてください。

    回答を表示

    (1) どのステップで何が起きたかです。各ステップの戻りコード、ABEND コード、ステップが実行されなかったことを示すメッセージ（IEF272I など）と、その原因を示すメッセージ（割り当てエラーなら IEF212I など）を確認します。(2) その時点でデータセットがどうなっているかです。売上明細（DETAIL）が作られたか（STEP010 で削除されたままか）、前回の集計結果（SUMMARY）が前回のまま残っていること（今回の結果と取り違えないよう、先頭8桁の集計対象日を見る）、後続の JSALSUM・JSALCHK が実行されていないことを確認します。

  • Q3. 集計結果のデータセットに DISP=MOD で追記する設計は、再実行のときになぜ危険ですか？

    回答を表示

    再実行のたびに、既にある内容の後ろに同じレコードが追加され、二重計上になるからです。7.6 で試したように、2回追記すると同じレコードが2件になり、合計を求めると正しい値の倍になります。対策は、追記せず毎回作り直すことです（COBOL は OPEN OUTPUT、JCL は事前削除 ＋ DISP=NEW）。

  • Q4. 集計対象日を、システム日付ではなく SYSIN で渡す理由を説明してください。

    回答を表示

    システム日付を使うと、日をまたいで再実行したときに、実行した日の日付で集計されてしまうからです。集計対象日（業務日付）は、実行した日とは別のものです。SYSIN で外から渡せば、再実行でも同じ集計対象日（例: 20261020）になり、同じ結果になります。実務では、ジョブ管理製品などから業務日付を渡すことが多いです。

  • Q5. JSALSUM が RC=4（警告）で終わっても、後続の JSALCHK を実行する設計にしました。この判断で、注意すべきことは何ですか？

    回答を表示

    警告は後続を止めないので、だれも気づかないまま、合計 0 円の結果が使われるおそれがあります。入力が 0 件だったのが、本当に売上の無い日なのか、受信データの欠落なのかは、確認しないと分かりません。そこで、警告を記録し、だれが・いつまでに・何を見て確認するかを運用の決まりにしておきます。欠落だと分かったら、JSALPREP から再実行します。また、JSALCHK は 0 件でも RC=0 で終わるため、警告は JSALCHK の結果には表れない点にも注意が必要です。
