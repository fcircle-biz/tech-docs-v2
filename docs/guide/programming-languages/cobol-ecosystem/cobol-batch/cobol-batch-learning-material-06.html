COBOLとJCLの連携 - ASSIGNとDD名・実行結果の確認

第4章では COBOL で売上集計プログラム SALESSUM を作り、第5章では JCL で「どのプログラムを、どのデータセットで動かすか」を書く方法を学びました。この章では、この2つを名前でつなぐしくみを学びます。COBOL の中の名前、外部名（DD 名）、データセット名という「3つの名前」のつながりを理解しましょう。さらに、失敗が起きたときに「だれが」それを見つけるのか、そしてジョブログから実行結果と異常の原因を読み取る方法も学びます。

この章で学ぶこと

  • COBOL のファイル名・ASSIGN の外部名・JCL の DD 名・データセット名のつながりを説明できる
  • COBOL と JCL の抜粋から、DD 名の対応表を作れる
  • データセットの割り当てと処置（DISP）が、プログラムの実行の前と後でどう行われるかを説明できる
  • 失敗の種類ごとに「だれが検出するか」を、z/OS と PC の違いも含めて説明できる
  • ジョブログから、実行結果と異常の原因を読み取れる

この章の z/OS 用 JCL とジョブログは「例」です

この章に出てくる z/OS 用の JCL とジョブログは、IBM の資料に載っている形式に合わせて作った例で、実機で取得した結果ではありません。実際の環境では、ジョブクラス・ユニット名（UNIT=SYSDA など）・プロシージャ名・ライブラリー名・メッセージの表示などが異なります。研修先の環境に合わせて調整してください。

メインフレームが無い場合は、JCL とジョブログを「読んで理解する」教材として使い、手を動かす部分は PC の GnuCOBOL と疑似JCL（JCL の考え方を体験するための代用で、JCL そのものではありません）で体験します。PC の実行結果は、GnuCOBOL 3.1.2 で実際に実行して確かめたものです。

6.1 プログラムとデータセットをつなぐ3つの名前

第4章で作った売上集計プログラム SALESSUM は、入力の売上明細を読み、出力の売上集計結果を書きます。ところが、プログラムのどこにも、TRAIN01.SALES.DETAIL のような実際のデータセット名は書かれていません。それでも z/OS では、正しいデータセットを読み書きできます。名前を3つに分けて、JCL がつないでいるからです。まず COBOL 側の書き方を思い出しましょう。

salessum.cob のファイル定義（第4章） ENVIRONMENT DIVISIONの抜粋 
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
      * SALESIN・SUMOUT は外部名（JCL の DD 名に対応する）
           SELECT SALES-FILE ASSIGN TO SALESIN
               FILE STATUS IS WS-FS-IN.
           SELECT SUM-FILE ASSIGN TO SUMOUT
               FILE STATUS IS WS-FS-OUT.

SELECT SALES-FILE ASSIGN TO SALESIN には、2つの名前が出てきます。SALES-FILE は、プログラムの中で OPEN や READ に使う名前です。SALESIN は、ASSIGN 句で指定する外部名で、プログラムの外にあるデータセットを指す名前です。次に、JCL 側を見ます。売上集計ジョブ JSALSUM の STEP020 です。

JSALSUM の STEP020（第5章） z/OS JCLの抜粋 
//* STEP020: 売上集計プログラム SALESSUM を実行する
//STEP020  EXEC PGM=SALESSUM
//STEPLIB  DD DSN=TRAIN01.LOAD,DISP=SHR
//SALESIN  DD DSN=TRAIN01.SALES.DETAIL,DISP=SHR
//SUMOUT   DD DSN=TRAIN01.SALES.SUMMARY,
//            DISP=(NEW,CATLG,DELETE),UNIT=SYSDA,
//            SPACE=(TRK,(1,1)),DCB=(RECFM=FB,LRECL=18)

JCL の //SALESIN DD の SALESIN はDD 名で、COBOL の外部名と同じ名前になっています。その DD 文の DSN= に、実際のデータセット名が書かれています（TRAIN01 は研修用ユーザー ID の例です。実際には各自のユーザー ID や研修先で決められた名前に置き換えます）。たとえるなら、プログラムは「SALESIN と書かれた受付カウンターで荷物を受け取る」とだけ決めており、カウンターの奥でどの棚（データセット）から荷物を運ぶかは、JCL の DD 文が決めています。

外部名＝DD 名"]) B -->|"DD 文の DSN="| C[("③ TRAIN01.SALES.DETAIL

図の説明: プログラムの中の名前（①）は、COBOL の ASSIGN 句で外部名（②）に結ばれます。②は JCL の DD 名と同じ名前で、DD 文の DSN= によって実際のデータセット名（③）に結ばれます。①と②は COBOL に、②と③は JCL に書かれています。

名前 例 どこに書くか・変えるときに直すもの
① プログラムの中でのファイル名 SALES-FILE COBOL の SELECT 句・FD・OPEN・READ など。変えるときは COBOL を直して再コンパイルする
② 外部名（＝JCL の DD 名） SALESIN COBOL の ASSIGN 句と、JCL の DD 文の名前。変えるときは両方を同じ名前にそろえて直す
③ データセット名 TRAIN01.SALES.DETAIL JCL の DD 文の DSN=。変えるときは JCL だけを直す（再コンパイルは不要）

なお、COBOL の SALES-FILE は、プログラムの中だけで通じる名前です。ディスクの上にある本当のファイルの名前ではありません。PC で「ファイル名」と呼ぶもの（sales.dat など）にあたるのは、③のデータセット名です。ASSIGN 句の外部名は、COBOL の仕様書では assignment-name と呼ばれますが、このガイドでは「外部名」と呼びます。

プログラムを作り直さずに、データを差し替えられる

プログラムにデータセット名を書き込まないことで、データを差し替えても、プログラムを作り直さなくてよいという利点が生まれます。

  • テスト用のデータで動かすときは、JCL の DSN= をテスト用のデータセットにします。
  • 本番のデータで動かすときは、DSN= を本番のデータセットにします。
  • 日付ごとに分けて持っているデータを処理するときは、DSN= を処理したい日付のデータセットにします。

どの場合も、COBOL のプログラムは再コンパイルせず、そのまま使えます。計算のしかたやレコードの形のようにプログラムの中身を変えるときは COBOL を、どのデータセットを使うか、集計対象日をいつにするかのようにプログラムの外側を変えるときは JCL を直す、と覚えておきましょう。

6.2 DD 名の対応表

COBOL のソースと JCL は別のファイルに書かれ、別の人が直すことも珍しくありません。名前が1文字違うだけで、プログラムは正しいデータセットを見つけられなくなります。そこで、COBOL の外部名と JCL の DD 名を一覧にしたDD 名の対応表を作り、突き合わせる習慣をつけます。次の表は、売上集計ジョブ JSALSUM の対応表です。右端の列は、PC の GnuCOBOL で同じことをするための代わりの方法です（6.9）。

用途 COBOL の書き方 DD 名 z/OS のデータセット PC（GnuCOBOL）での代わり
売上明細（入力） SELECT SALES-FILE ASSIGN TO SALESIN SALESIN TRAIN01.SALES.DETAIL（FB・LRECL=12） DD_SALESIN=data/sales.dat
売上集計結果（出力） SELECT SUM-FILE ASSIGN TO SUMOUT SUMOUT TRAIN01.SALES.SUMMARY（FB・LRECL=18） DD_SUMOUT=data/summary.dat
集計対象日 ACCEPT WS-PARM-DATE SYSIN //SYSIN DD *（インストリームデータ） echo 20261020 |（標準入力）
メッセージ DISPLAY SYSOUT //SYSOUT DD SYSOUT=* 画面（標準出力）
プログラム本体 PROGRAM-ID. SALESSUM. STEPLIB TRAIN01.LOAD（ロードライブラリー） ./salessum（実行ファイル）
  • SELECT … ASSIGN TO で書いた外部名には、同じ名前の DD 文が必ず1つ必要です（SALESIN と SUMOUT）。
  • ACCEPT と DISPLAY は、SELECT を書かなくても、決まった DD 名を使います。FROM 句の無い ACCEPT は SYSIN から読み、UPON 句の無い DISPLAY は SYSOUT に書きます（6.5）。
  • STEPLIB はデータの読み書き用ではなく、プログラム本体を探す場所の指定です。実行できる形になったプログラムを「ロードモジュール」と呼び、それを入れておくデータセットが TRAIN01.LOAD です。COBOL の SELECT 句には出てきません（6.8）。

対応表を作ったら、外部名と DD 名のどちらか片方にしか無い名前がないかを確かめます。あれば、どこかが間違っています（SYSIN・SYSOUT・STEPLIB のように、SELECT に現れない決まった名前は除きます）。

注意: ASSIGN の書き方は1通りではありません

このガイドでは ASSIGN TO SALESIN の形に統一しています。現場の COBOL では、ASSIGN TO UT-S-SALESIN のような書き方に出会うことがあります。z/OS では、最後の SALESIN が DD 名です（UT- は装置の種類を示す書類上の表示、S- は順編成を表します）。

PC の GnuCOBOL では、UT-S-SALESIN 全体が1つの名前として扱われます。そのため DD_SALESIN では割り当てられず、DD_UT-S-SALESIN のような名前で指定する必要があります（GnuCOBOL 3.1.2 で確認）。なお、シェルでは、名前にハイフンを含む環境変数を、コマンドの前に「名前=値」と付ける形（6.9）では指定できません。env 'DD_UT-S-SALESIN=data/sales.dat' ./salessum のように、env コマンドを使います（ASSIGN TO UT-S-SALESIN と書いたプログラムを動かす場合の例です）。メインフレームのソースを PC に持ってくるときに、引っかかりやすい点です。

6.3 データセットの割り当てと処置の流れ

JCL の DD 文は、プログラムが OPEN したときに初めて効くわけではありません。ステップが始まると、システムはプログラムを動かす前に、DD 文に書かれたデータセットを使える状態にします。これを割り当て（英語では allocation。IBM の日本語の資料では「割り振り」とも書かれます）と呼びます。既存のデータセットは、第5章で学んだカタログ（データセット名と置き場所を結び付けた台帳）で探し、NEW のデータセットは新しく作ります。ステップが終わると、そのデータセットを残すか消すかを、DISP の指定に従って処理します。これを処置と呼びます。

1つのステップの中で、何がどの順番で起きるのかを、図で確かめましょう。売上集計ジョブ JSALSUM の STEP020 を例にします。

sequenceDiagram participant J as ジョブ（JCL） participant S as システム（z/OS） participant D as データセット participant P as SALESSUM J->>S: STEP020 の実行を依頼 S->>D: DD 文ごとに割り当て Note over S,D: 既存はカタログで探す、NEW は新しく作る
ここまでプログラムはまだ動いていない S->>P: プログラムを開始 P->>D: OPEN → READ・WRITE → CLOSE P->>S: RETURN-CODE を残して終了 S->>D: DISP に従って処置 S->>J: 戻りコードを記録して次へ

図の説明: ステップが始まると、システムが DD 文ごとにデータセットを割り当てます（上から2番目の矢印）。プログラムが動き出すのは、そのあとです。プログラムが終わると、システムが DISP に従ってデータセットを処置し、戻りコードを記録して次のステップへ進みます。

この流れを、STEP020 の DD 文に当てはめると、次のようになります。

DD 名 データセット DISP 割り当てのとき 終わったときの処置
STEPLIB TRAIN01.LOAD SHR 既存のデータセットをカタログで探す KEPT（そのまま残す）
SALESIN TRAIN01.SALES.DETAIL SHR 既存のデータセットをカタログで探す KEPT（そのまま残す）
SUMOUT TRAIN01.SALES.SUMMARY (NEW,CATLG,DELETE) 新しく作る（SPACE・DCB に従う） CATALOGED（カタログに登録して残す）

プログラムが OPEN で使うのは、割り当て済みのデータセットです。入力のファイルで、ASSIGN の外部名と同じ名前の DD 文が無ければ、開けるデータセットが無いので、OPEN は失敗します（FILE STATUS 35。6.4）。SYSIN と SYSOUT の DD 文も、同じように割り当てられます（6.5）。右端の処置は、ステップが途中で強制的に終わる異常終了（ABEND。第5章）をせずに終わったときのものです。ジョブログには KEPT・CATALOGED などと表示されます（6.7）。ABEND したときの処置は 6.6 で説明します。

割り当てはプログラムが動く前に行われる

割り当てに失敗すると、プログラムは一度も動かないまま、ステップが実行されずに終わります。プログラムが動いていないので、プログラム自身は失敗を知ることができず、SLS で始まるメッセージも出ません。この違いが、次の 6.4 で見る「だれが検出するか」の違いにつながります。

6.4 失敗を「だれが」検出するか

バッチ処理では、失敗を見つけるのがだれか（どの仕組みか）を知っておくことが大切です。z/OS では、プログラムが動く前にシステムが見つける失敗と、プログラムが動いている最中に見つかる失敗があり、見つける仕組みも、ジョブログに残る手がかりも違います。一方 PC（GnuCOBOL）には、データセットの割り当てという段階がありません。同じ失敗でも、見つける仕組みや表示が変わります。

同じ失敗を、z/OS と PC で比べてみましょう。「だれが」「いつ」気づくのかに注目してください。

失敗の種類 z/OS（メインフレーム） PC（GnuCOBOL）
入力データセットが存在しない システム（割り当て）が検出。ステップの開始時に割り当てエラー（IEF212I DATA SET NOT FOUND）になり、ステップは実行されません（IEF272I）。プログラムは動かないので、SLS9xxE のメッセージは出ません。 プログラムが検出。OPEN のとき FILE STATUS が 35 になり、SALESSUM が SLS901E を表示して RC=12 で終わります。
DD 文が無い（DD 名の書き間違い） プログラムが検出。JCL としては正しいので割り当ては成功し、プログラムが動きます。プログラムが探す SALESIN の DD 文が無いため、OPEN で FILE STATUS が 35 になり、SLS901E・RC=12 で終わります。書き間違えた名前の DD は、使われないだけです。 プログラムが検出。環境変数が無いので、カレントフォルダの SALESIN という名前のファイルを開こうとします。無ければ FILE STATUS 35・RC=12。同じ名前のファイルがたまたまあると、それを読んでしまい、気づけません。
FD と LRECL の不一致 プログラムが検出（OPEN のとき）。データセットは RECFM や LRECL の情報を持っているので、プログラムの FD との食い違いが OPEN で見つかります。FILE STATUS を書いていれば 39 として受け取れ、SALESSUM なら SLS901E（FS=39）を表示して RC=12 で終わります（FILE STATUS を書いていないと、実行時のエラーで異常終了することがあります）。 OPEN では、だれも検出しません。ファイルはバイトの並びで、レコード長の情報を持たないからです。読み進めると区切りがずれ、ファイルの大きさによっては、最後に短いレコードを読んだところで FILE STATUS 04 になり、プログラムが検出します（第4章の改行入りファイルと同じ）。ずれたまま集計してしまうこともあります。
数値項目の不正値 システムが検出するのが典型です。数字でない値を計算に使うと、データ例外（S0C7）の ABEND でステップが異常終了します。ただし、データの中身やコンパイルの指定によっては、異常終了せずに誤った値のまま計算が進むこともあります（その場合はだれも検出しません）。ABEND したときの異常終了コードは、ジョブログに記録されます。 だれも検出しません。GnuCOBOL の既定のコンパイルでは、エラーにならず、誤った値のまま計算が続きます（下の実験）。cobc -x -debug でコンパイルすると、「not numeric」の実行時エラーで止まります。
出力データセットが既に存在する（DISP=NEW） システム（割り当て）が検出。DISP=(NEW,CATLG,DELETE) で同名のデータセットが既にあると、割り当てに失敗します（例: IGD17101I）。ステップは実行されません。JSALSUM が STEP010 で前回の集計結果を先に消している理由です（6.6）。 だれも検出しません。OPEN OUTPUT は既存のファイルの中身を消して書き直すので、エラーにならず、前回の結果が上書きされます。
出力の容量不足 システムが検出。書き込み中に、SPACE で確保した領域を使い切ると、システムが SB37・SD37・SE37 などの ABEND でステップを異常終了させることがあります。FILE STATUS の 34（領域不足など）としてプログラムに知らされる場合もあります。 プログラムが検出。ディスクに書き込めないと WRITE が失敗し、FILE STATUS が 34 になります（書き込みが必ず失敗する特殊なファイル /dev/full を出力先にして模擬し、確かめました）。

ジョブが失敗しているのに、プログラムが出す SLS で始まるメッセージが SYSOUT に1行も無いときは、プログラムが動く前の失敗（割り当てエラー、JCL の構文エラー、プログラムが見つからない S806 など）を疑います。反対に SLS9xxE が出ていれば、プログラムが動いたうえで、プログラム自身が失敗を見つけたということです。SALESSUM は FILE STATUS を書いているので、ファイルの失敗を自分で見つけて RC=12 で終わります。FILE STATUS を書いていないと、実行環境（PC の libcob や、z/OS の COBOL の実行時ライブラリー）がエラーメッセージを出してプログラムを止めます（第4章）。FILE STATUS の主な値は第4章の表にあります（IBM のマニュアルでも確認できます）。ABEND コードの意味は第5章で扱いました。

PC で確かめてみよう: 数値項目の不正値

表の中で、PC と z/OS の差に最も注意が必要なのは「数値項目の不正値」です。2件目の数量を 0A3（数字の中に英字 A が混ざった値）にしたテストデータを作り、第4章の SALESSUM（基本版）をそのまま動かしてみます。

戻りコードは 0 で、合計も表示されているため、正常に終わったように見えます。しかし数量 0A3 は数字ではないので、TOTAL=0000043570 は誤った値です。z/OS では、数字でないデータを計算に使うと、データ例外（S0C7）で異常終了（ABEND）するのが典型です。ただし、データの中身やコンパイルの指定によっては、異常終了せずに誤った値のまま計算が進むこともあります（計算の前に数字の形に変換する命令が、各バイトの数字の部分だけを使うことがあるため、英字が混ざっていても例外にならない場合があります）。ABEND で止まるのは困りますが、止まらずに、誤った集計結果が「正常終了」として後続に渡るほうが、もっと困ります。どちらの環境でも確実なのは、プログラム自身が IS NUMERIC で数字かどうかを確かめ、不正なら RC=8 で終わることです。第8章の完成版で追加します。

6.5 SYSIN と SYSOUT

SALESSUM は、集計対象日を ACCEPT で受け取り、メッセージを DISPLAY で表示します。この2つは、ファイルの READ や WRITE と違って、SELECT 句で名前を付けません。代わりに、決まった DD 名を使います。FROM 句の無い ACCEPT は SYSIN から読み、UPON 句の無い DISPLAY は SYSOUT に書きます。

salessum.cob の初期処理（第4章） PROCEDURE DIVISIONの抜粋 
      * 初期処理: 集計対象日の受け取りとOPEN
       INIT-PROC.
           ACCEPT WS-PARM-DATE
           MOVE WS-PARM-DATE TO WS-TARGET-DATE
           DISPLAY "SLS001I SALESSUM START DATE=" WS-TARGET-DATE

これに対応する JCL の DD 文は、次のとおりです。

JSALSUM の SYSIN と SYSOUT（第5章） z/OS JCLの抜粋 
//* 集計対象日をインストリームデータで渡す
//SYSIN    DD *
20261020
/*
//* DISPLAY のメッセージをジョブの出力へ出す
//SYSOUT   DD SYSOUT=*
  • //SYSIN DD * は、次の行から /* の前の行までを、プログラムへの入力データとして渡す指定です（インストリームデータ）。ここでは 20261020 の1行です。ACCEPT がこれを読み、WS-PARM-DATE に入ります。データの行が // や /* で始まると JCL と見なされるので、注意します。
  • //SYSOUT DD SYSOUT=* は、DISPLAY の出力を、ジョブの出力として残す指定です。実行後に SDSF で見られます（6.7）。
  • PC では、echo 20261020 | ./salessum のように標準入力から日付を渡し、DISPLAY は画面（標準出力）に出ます。

集計対象日を SYSIN で渡す理由

集計対象日を、プログラムの中でシステム日付から決める作り方も考えられます。しかし、それでは困る場面があります。たとえば、10月20日分の集計が夜間の障害で止まり、翌朝（10月21日）に再実行したとします。システム日付を使っていると、再実行した日の 20261021 で集計されてしまいます。20日分のデータなのに、集計結果の日付が21日になる、という間違いです。前の工程が遅れて、ジョブが0時を過ぎてから始まったときも、同じことが起きます。SYSIN で渡す日付なら、いつ再実行しても 20261020 のままです。

用語: 集計対象日（業務日付）と実行日

集計対象日（業務日付）は「どの日の売上を集計するか」、実行日は「ジョブを動かした日」で、別のものです。夜間バッチは、日付をまたいで動いたり、翌日に再実行されたりします。集計対象日は、システム日付に任せず、外から渡すのが安全です。実務では、ジョブ管理製品などから業務日付を渡すことが多くなります（第7章）。このガイドでは、JCL の SYSIN に書いて渡します。

6.6 RETURN-CODE と戻りコード

ステップが終わるとき、プログラムは戻りコード（RC）という数字を残します（第5章）。COBOL では、RETURN-CODE という特殊レジスタ（COBOL があらかじめ用意している名前）に数字を入れておくと、プログラムの終了時に、その値が OS に渡されます。z/OS では、それがジョブログに表示されるステップの戻りコード（COND CODE）になり、PC では echo $? で見られる終了コードになります。SALESSUM は、MOVE WS-RC TO RETURN-CODE で戻りコードを決めます。

salessum.cob の異常時の処理（第4章） PROCEDURE DIVISIONの抜粋 
      * 異常時: 開いたファイルを閉じてRCを返す
       ERROR-PROC.
           IF WS-IN-OPEN = "Y"
               CLOSE SALES-FILE
           END-IF
           IF WS-OUT-OPEN = "Y"
               CLOSE SUM-FILE
           END-IF
           DISPLAY "SLS999E SALESSUM ABNORMAL END RC=" WS-RC
           MOVE WS-RC TO RETURN-CODE
           STOP RUN.

SALESSUM（基本版）が返す戻りコードは、最後まで正常に終わったときの 0 と、ファイルの OPEN・READ・WRITE に失敗したときの 12 です。RC=4 と RC=8 は、第8章の完成版で加わります。

戻りコード 12 で終わったあと、SUMMARY はどうなるか

第5章の 5.6 で、DISP の第3パラメータ（異常終了時）が使われるのはABEND したときだけで、戻りコードが 8 や 12 で終わったステップには第2パラメータ（正常終了時）が使われることを学びました。ABEND は、S0C7 のように、システムやプログラムがステップを途中で強制的に終わらせる異常終了です。SALESSUM が RC=12 で終わるときは、プログラム自身が ERROR-PROC を最後まで実行して STOP RUN しているので、システムから見れば正常に終了したステップです。SALESIN の OPEN に失敗して RC=12 になる場面で、そのあとの流れを順にたどってみましょう。

flowchart TD A["STEP020 の開始
SUMOUT が割り当てで作られる"] --> B["SALESSUM が動き出す
SALESIN の OPEN に失敗（FILE STATUS 35）"] B --> C["ERROR-PROC
RETURN-CODE に 12 を入れて STOP RUN"] C --> D["システムから見ると
ABEND していない、正常に終了したステップ"] D --> E["DISP の第2パラメータ CATLG で処置"] E --> F["中身が空の SUMMARY が
CATALOGED で残る"]

図の説明: SUMOUT は、STEP020 の始まり（割り当て）で作られています。SALESSUM が中身を書く前に RC=12 で終わっても、システムから見れば正常に終了したステップなので、第2パラメータの CATLG が使われ、中身が空の SUMMARY がカタログに残ります。ABEND したときは、第3パラメータの DELETE が使われ、SUMMARY は削除されます。

空の SUMMARY が、正常なものと同じ顔でカタログに残ると、困ったことが起きます。後続のジョブが、空の集計結果を正しい結果として読んでしまうおそれがあります。また、STEP010 のような事前削除が無いジョブだと、再実行したときに、DISP=NEW の SUMOUT が、残っている SUMMARY と同じ名前になり、割り当てエラーになります（6.4）。戻りコードが 8 や 12 で終わったジョブの出力は、使わないようにします。

再実行に備えて、STEP010 で前回の結果を削除する

JSALSUM に STEP010 があるのは、この問題への備えです。

JSALSUM の STEP010（第5章） z/OS JCLの抜粋 
//* STEP010: 前回の集計結果を削除（再実行対策）
//STEP010  EXEC PGM=IEFBR14
//DEL1     DD DSN=TRAIN01.SALES.SUMMARY,
//            DISP=(MOD,DELETE,DELETE),UNIT=SYSDA,SPACE=(TRK,0)

IEFBR14 は何もしないプログラムなので、DD 文による割り当てと処置（ここでは削除）だけが働きます。DISP=(MOD,DELETE,DELETE) は、データセットがあれば削除し、無くてもエラーにしない書き方です（5.6）。これで、ジョブを先頭から再実行するかぎり、前回の結果が残っていても、残っていなくても、STEP020 の SUMOUT を同じ名前で新しく作れます。STEP020 から再開すると STEP010 が動かないので、割り当てエラーになることがあります。再実行の設計は、第7章で詳しく学びます。

PC には DISP がありません。入力の OPEN に失敗する SALESSUM は、出力の OPEN OUTPUT より前に終わるので（第4章の 4.9）、PC では出力ファイル summary.dat は作られず、前回の内容も書き換えられません。疑似JCL（JCL の代用）では、先頭の rm -f data/summary.dat が STEP010 の代わりに前回の内容を消すので、結果として summary.dat が無い状態になります（6.9 で確かめます）。z/OS では割り当ての時点で SUMMARY が作られるため、空のデータセットが残る、という違いがあります。

6.7 ジョブログで実行結果を確認する

ジョブが終わったら、実行結果を確かめます。z/OS では、ジョブの出力は SDSF という画面で見られます。第5章の 5.1 の表のとおり、1つのジョブの出力は、別々のデータセットとして表示されます。JESMSGLG はジョブ全体のメッセージ（開始・終了など）、JESJCL は展開後の JCL（実際に実行された JCL）、JESYSMSG はステップごとの割り当て・戻りコード・処置、SYSOUT=* の DD（SYSOUT・SYSPRINT など）はプログラムが出した出力で、SALESSUM の DISPLAY のメッセージはここに出ます。

狭い意味では、JESMSGLG だけを「ジョブログ」と呼びます。このガイドでは、実行結果を確かめるための出力全体（JESMSGLG・JESJCL・JESYSMSG・SYSOUT）を指して、「ジョブログ」と呼びます。SDSF のほかに、VS Code の拡張機能 Zowe Explorer からも、ジョブの出力を参照できます（Zowe）。

それでは、3つの例を読んでみましょう。どれも実機で取得したものではなく、IBM の資料に載っている形式に合わせて作った「例」です。実際の表示は、システムの設定や版によって異なります。ここでは読みやすいように、抜粋し、時刻やジョブ番号を省略しています。実際のジョブログでは、IEF285I の行の次に、データセットが置かれているボリューム（ディスク）を示す IEF285I VOL SER NOS= … の行も続きます（例では省略しています）。

「JCL エラー」とひとまとめにしない

JCL の書き方の誤り（構文エラー）は、ジョブが実行される前にシステムが見つけます。一方、例3のように、JCL としては正しく書かれていても、データセットが見つからない、同じ名前のデータセットが既にある、といった理由で割り当てに失敗するのが割り当てエラーです。どちらもステップは実行されませんが、原因と直し方が違うので、区別して呼びます。

6.8 z/OS でのコンパイルから実行まで

ここまでは、SALESSUM がすでに「実行できる形」になっている前提で、JCL を読んできました。z/OS では、COBOL のソースをそのまま実行することはできません。コンパイル（ソースを、コンピュータが実行できる形に変換する）とリンク（必要な部品をまとめて、実行できる1つのプログラムにする）を行ってから、実行します。こうしてできた、実行できる形のプログラムをロードモジュールと呼び、ロードライブラリーというデータセットに保存します。

flowchart LR A["ソース
TRAIN01.COBOL(SALESSUM)"] -->|"JCOMPILE を実行"| B["ロードモジュール
TRAIN01.LOAD(SALESSUM)"] B -->|"JSALSUM を実行"| C["SALESSUM が動く
EXEC PGM=SALESSUM"]

図の説明: ソース（区分データセットのメンバー）を JCOMPILE でコンパイル・リンクすると、ロードモジュールが TRAIN01.LOAD にできます。JSALSUM は、STEPLIB で指定した TRAIN01.LOAD から SALESSUM を探して実行します。

用語: 区分データセットとメンバー

区分データセット（PDS）は、1つのデータセットの中に、メンバーと呼ぶ小さなファイルをたくさん入れられるデータセットです。フォルダのようなものと考えてください。TRAIN01.COBOL(SALESSUM) は、区分データセット TRAIN01.COBOL の中のメンバー SALESSUM を指します。

コンパイルとリンクをまとめて行う JCL の例です。IBM が提供するプロシージャ IGYWCL を使います。

SALESSUM をコンパイルしてリンクする JCOMPILE z/OS JCL 
//JCOMPILE JOB (ACCT),'COMPILE',CLASS=A,MSGCLASS=X,
//             MSGLEVEL=(1,1),NOTIFY=&SYSUID
//* SALESSUM をコンパイルし TRAIN01.LOAD に登録
//CL       EXEC IGYWCL
//COBOL.SYSIN  DD DSN=TRAIN01.COBOL(SALESSUM),DISP=SHR
//LKED.SYSLMOD DD DSN=TRAIN01.LOAD(SALESSUM),DISP=SHR
  • EXEC IGYWCL: IGYWCL は、コンパイルとリンクの手順をまとめて登録したプロシージャの名前です。EXEC 文にプロシージャの名前を書くと、その手順が呼び出されます。CL は、このステップの名前です。
  • COBOL.SYSIN: プロシージャの中の COBOL ステップ（コンパイル）の SYSIN DD、つまりコンパイラへの入力に、ソースのメンバー TRAIN01.COBOL(SALESSUM) を指定します。
  • LKED.SYSLMOD: プロシージャの中の LKED ステップ（リンク）の SYSLMOD DD、つまりできあがったロードモジュールの置き場所に、TRAIN01.LOAD(SALESSUM) を指定します。

コンパイラは、メッセージの重大度に応じて戻りコードを返します（I＝情報は 0、W＝警告は 4、E＝エラーは 8、S＝重大は 12、U＝回復不能は 16）。IGYWCL の中には、COBOL（コンパイル）と LKED（リンク）の2つのステップがあり、ジョブログにはそれぞれの戻りコードが出ます。LKED ステップには COND=(8,LT,COBOL) が付いていて、コンパイルの戻りコードが 8 より大きいとリンクは飛ばされます（第5章の 5.7 の COND）。JCOMPILE のジョブログも、6.7 と同じ読み方で確認します。

プログラムの名前と、再コンパイルが必要なとき

プログラムの名前にも、つながりがあります。ソースの PROGRAM-ID. SALESSUM.、ロードモジュールのメンバー名 TRAIN01.LOAD(SALESSUM)、JSALSUM の EXEC PGM=SALESSUM は、すべて SALESSUM という名前でそろっています。EXEC PGM= に書くのは、ロードモジュールのメンバー名です。STEPLIB のデータセットの中から、この名前のメンバーが探されます。PROGRAM-ID と同じ名前にそろえておくと、迷いません。

ソースを直したときに、ロードモジュールを作り直す（再コンパイルする）必要があるかどうかは、次のように考えます。

  • 入力のデータセットを TRAIN01.SALES.TEST に変える、集計対象日を変える: JCL を直すだけです。再コンパイルは不要です。
  • 売上金額の計算のしかたを変える、ASSIGN の外部名を変える: COBOL のソースを直すので、再コンパイルが必要です。JCOMPILE を実行して TRAIN01.LOAD を更新してから、JSALSUM を実行します。

手順と名前は、研修先に従います

6.9 PC で DD 文の仕組みを体験する

PC には JCL も DD 文もありません。しかし GnuCOBOL には、DD 文とよく似た割り当てのしくみがあります。ASSIGN 句の外部名を、環境変数で実際のファイルに結びつけるしくみです。

用語: 環境変数

環境変数は、シェル（ターミナル）が覚えている「名前＝値」の組です。DD_SALESIN=data/sales.dat は、「DD_SALESIN という名前に data/sales.dat を覚えさせる」という意味で、プログラムはその値を読み取れます。export を付けて設定すると、そのシェルから起動するプログラムに引き継がれます。コマンドの前に 名前=値 を付けると、そのコマンドの間だけ有効になります。

ASSIGN TO SALESIN と書かれたファイルを OPEN するとき、GnuCOBOL は、環境変数 DD_SALESIN、dd_SALESIN、SALESIN の順に探し、見つかった値をファイル名として開きます。どれも無ければ、カレントフォルダの SALESIN という名前のファイルを開きます。このガイドでは、JCL の DD 文に最も近い DD_ で始まる名前を使います。なお、この動作は GnuCOBOL 3.1.2 で確かめたもので、バージョンによって細かな動作が違うことがあります。

疑似JCL jsalsum.sh

JSALSUM を、シェルスクリプトで真似してみましょう。疑似JCLは、「名前を使ってデータを結びつける」「ステップを順に動かす」「戻りコードを確かめる」といった JCL の考え方を体験するための代用で、JCL そのものではありません。

jsalsum.sh（疑似JCL。JSALSUM の代わり） PCで実行 
#!/bin/bash
# 疑似JCL（売上集計ジョブ JSALSUM）: DD 文の代わりに環境変数で割り当てる
BIZDATE=20261020                 # 集計対象日（//SYSIN DD * の中身にあたる）
# STEP010: 前回の集計結果を削除する（IEFBR14 による事前削除の代わり）
rm -f data/summary.dat
# STEP020: SALESSUM を実行する（//SALESIN DD・//SUMOUT DD の代わり）
export DD_SALESIN=data/sales.dat
export DD_SUMOUT=data/summary.dat
echo "$BIZDATE" | ./salessum
rc=$?
echo "JSALSUM STEP020 RC=$rc"
exit $rc

コメントに書いたとおり、rm -f が STEP010、export DD_SALESIN=… と export DD_SUMOUT=… が SALESIN・SUMOUT の DD 文、echo "$BIZDATE" | が SYSIN、rc=$? 以降が戻りコードの確認にあたります。

理解度確認クイズ

  • Q1. SELECT SUM-FILE ASSIGN TO SUMOUT と書かれたプログラムを z/OS で動かします。JCL の DD 文には、どんな名前が必要ですか？ また、実際のデータセット名は、COBOL と JCL のどちらに書きますか？

    回答を表示

    SUMOUT という名前の DD 文が必要です（ASSIGN の外部名と、JCL の DD 名を同じ名前にします）。実際のデータセット名は、その DD 文の DSN= に書きます。つまり JCL 側に書き、COBOL のプログラムには書きません。

  • Q2. 入力のデータセットが存在しないとき、z/OS ではプログラムは実行されますか？ PC（GnuCOBOL）で入力ファイルが無い場合と比べて、何が違いますか？

    回答を表示

    z/OS では、ステップの開始時の割り当てエラー（IEF212I DATA SET NOT FOUND）でステップが実行されず（IEF272I）、プログラムは実行されません。PC には割り当ての段階が無いので、プログラムが動いて OPEN したときに、FILE STATUS 35 として SALESSUM 自身が気づき、SLS901E を表示して RC=12 で終わります。

  • Q3. プログラムの DISPLAY の出力は、z/OS と PC で、それぞれどこに出ますか？

    回答を表示

    z/OS では、UPON 句の無い DISPLAY は SYSOUT に書かれます。JCL の //SYSOUT DD SYSOUT=* に従ってジョブの出力に残り、SDSF で確認します。PC では、画面（標準出力）に表示されます。

  • Q4. SALESSUM が RC=12 で終わったのに、集計結果のデータセット TRAIN01.SALES.SUMMARY がカタログに残っています。なぜですか？ そのまま再実行すると、どうなりますか？

    回答を表示

    RC=12（RC=8 でも同じです）は ABEND ではなく、システムから見ると正常に終了したステップです。そのため、DISP=(NEW,CATLG,DELETE) の第2パラメータ（CATLG）が使われ、中身が空のままカタログに残ります。第3パラメータの DELETE は、ABEND したときにだけ使われます。JSALSUM は、ジョブの先頭から再実行すれば、STEP010 が残った SUMMARY を削除するので、割り当てエラーにはなりません。STEP010 が無いジョブや、STEP020 から再開した場合は、同じ名前のデータセットが既にあるため割り当てエラーになります（第7章）。なお、原因（DD 名の書き間違いなど）を直さずに再実行しても、また RC=12 で終わります。

  • Q5. 数量に英字が混ざった売上明細を、数字かどうかを確かめない SALESSUM で計算すると、z/OS と PC で何が起きますか？ だれが検出しますか？

    回答を表示

    z/OS では、データ例外（S0C7）の ABEND になるのが典型で、その場合はシステムが検出します（データの中身やコンパイルの指定によっては、ABEND せず誤った値のまま進むこともあります）。PC の GnuCOBOL は、既定のコンパイルだとエラーにならず、誤った値のまま計算が続くので、だれも検出しません。どちらの環境でも、プログラム自身が IS NUMERIC で確かめるのが確実です（第8章）。
