実践：売上集計バッチを作ろう - 総まとめと次のステップ

最終章では、これまでの知識を総動員して、順不同の売上データを並べ替え、商品ごとの小計と総合計を帳票にまとめる「売上集計バッチ」を完成させます。正しく集計するだけでなく、異常なデータやファイルに出会ったときに確実に失敗を知らせる作りにします。仕様 → 設計 → 部品ごとの実装 → 組み立て → 実行 → テストという、現場の開発と同じ流れで進めましょう。最後に、COBOL のさらに先にある学習の道すじも紹介します。

この章で学ぶこと

  • 作るものを仕様と入出力の例で整理し、段落構成に分けて設計できる
  • SORT文（SD・USING・GIVING）でデータを並べ替えられる
  • コントロールブレイク（キーが変わったら小計を出す）の仕組みを理解し、最後のグループの小計も出せる
  • 編集項目と FILLER で、桁のそろった帳票を出力できる
  • 入りうる最大の値から桁数を決め、桁あふれ・データやファイルの異常を検知して、終了コードで失敗を知らせられる
  • 期待結果を決めたテスト（0件・1件・最大値・異常なデータやファイル）で合否を判定し、COBOL の次の学習ステップを把握する

14.3 SORT文：データを並べ替える

入力データは順不同ですが、商品ごとの集計は「同じ商品が連続して並んでいる」ことが前提です（理由は 14.4 で説明します）。そこで、まず SORT文で並べ替えます。COBOL には並べ替えの命令が最初から備わっているので、自分で並べ替えの手順を書く必要はありません。

SORT文の書き方 PROCEDURE DIVISIONの抜粋 
      * 商品コード→日付の順に並べ替える
       SORT-PROC.
           SORT WK-FILE
               ON ASCENDING KEY WK-ITEM WK-DATE
               USING IN-FILE
               GIVING SORTED-FILE.

SORT文の読み方は、英語の文章そのままです。

  • SORT WK-FILE：並べ替え作業に使うソート用ファイル（WK-FILE）を指定します。
  • ON ASCENDING KEY WK-ITEM WK-DATE：並べ替えのキー（基準）です。ASCENDING は昇順（小さい順）。最初に書いたキー（商品コード）が優先で、同じ商品の中では次のキー（日付）で並べます。
  • USING IN-FILE：並べ替える前のデータを読み込む入力ファイルです。
  • GIVING SORTED-FILE：並べ替えた結果を書き出すファイルです。

ソート用ファイルは、データ部のファイル節で SD（Sort Description）という見出しで定義します。FD の代わりに SD と書き、キーに使う項目（WK-DATE・WK-ITEM）を含むレコードを定義します。環境部の SELECT には、作業用の名前を書くだけで構いません（行順の指定は不要です）。

SORT文で注意すること

USING と GIVING に指定したファイルは、SORT文が自分で開いて閉じます。SORT文の前に OPEN してはいけません（規格で禁止されている書き方です。処理系によってはエラーになり、エラーにならない処理系でも結果は保証されません）。また、SD のレコードの長さと並び（項目の位置）は、入力ファイルのレコードと同じにしてください。

メインフレームでは

メインフレームでも SORT文の基本の書き方は同じです。ファイル名の対応づけ（ASSIGN の先）は JCL（ジョブ制御言語）で行います。

14.4 コントロールブレイク：キーが変わったら小計を出す

この章でいちばん大切な考え方がコントロールブレイク（キーブレイク）です。名前は難しそうですが、考え方は単純です。

コントロールブレイクの考え方

並べ替えたデータを上から順に読み、「キー（ここでは商品コード）が前の行から変わった」ことを見つけたら、直前のグループの小計を出す。変わらない間は、数量と金額を小計に足し続ける。

たとえるなら、仕分け済みの伝票の束を1枚ずつめくりながら電卓をたたく作業です。「A001の伝票が続く間は足し続ける。B002の伝票が出てきたら、いったんA001の合計を紙に書き、電卓をクリアしてB002を足し始める」。これをプログラムにするだけです。

そのために、前の行のキーを覚えておく項目（WS-PREV-ITEM）と、小計を貯めていく項目（WS-SUB-QTY・WS-SUB-AMT）を用意します。

具体的なデータで1行ずつ追ってみよう

並べ替え後の9件を上から読んでいくとき、プログラムは次のように動きます。表の「小計の貯め箱」は、その行を処理し終えた後の WS-SUB-AMT の値です。なお、最初の1件を読んだ直後に、そのキー（A001）を前のキーに入れておくので、1行目ではブレイクが起きません（14.7 の部品6）。

最後のグループの小計を忘れない

キーが「変わった」ことをきっかけに小計を出す仕組みなので、最後のグループの次には「変わる相手」が存在せず、小計が出ません。ファイルの終わりに達したら、ループの外（終了処理）で最後のグループの小計を必ず出力してください。コントロールブレイクで最も多い間違いです。実際に忘れるとどうなるかは、14.7 で確かめます。

なぜ並べ替えが必要か

データが A001、B002、A001 のように行き来していると、「キーが変わるたび」に小計が出てしまい、同じ商品の小計が何か所にも分かれてしまいます。「同じキーが連続している」ことがコントロールブレイクの前提なので、先に SORT します。

14.5 帳票の編集：行の形を設計する

帳票は「決まった位置に決まった桁数」で並べるのが基本です。第9章で学んだ FILLER（名前のない項目）で項目の間にすき間を作り、第5章の編集項目（ZZ,ZZ9・ZZ,ZZZ,ZZ9・ZZZ,ZZZ,ZZ9）で数値を読みやすく整えます。

見出し行・明細行・小計行・合計行は、同じ位置に同じ種類の列が来るように設計します。各列の幅は、その列に入るいちばん大きな値が収まるように決めます（大きな値の決め方は 14.6 で説明します）。1行は47桁で、列は次のように割り当てます。

列位置（桁）幅明細行小計行合計行
商品コード1〜44DL-ITEMSL-ITEM（TOTAL の文字）
日付／ラベル7〜148DL-DATESUBTOTAL の文字（TOTAL の文字）
数量17〜2610DL-QTY（ZZ,ZZZ,ZZ9）SL-QTY（同じ）TL-QTY（同じ）
単価29〜346DL-PRICE（ZZ,ZZ9）空白空白
金額37〜4711DL-AMOUNT（ZZZ,ZZZ,ZZ9）SL-AMOUNT（同じ）TL-AMOUNT（同じ）

行の定義は 14.7 のデータ部で見ます。ここで押さえるのは次の3点です。

  • 各列の開始位置（上の表の「位置」）がどの行でも同じになるように、FILLER の幅を決めます。結果として、どの行も合計47桁になります。
  • 数量の列は、明細の数量（3桁）ではなく、いちばん大きくなる小計・総合計の数量（8桁）に合わせて ZZ,ZZZ,ZZ9 にしています。明細行も同じ編集項目を使うので、列がそろいます。
  • 金額は編集項目 ZZZ,ZZZ,ZZ9（数字9桁分）で桁区切りします。Z は「先頭のゼロを空白にする」記号なので、360 は [ 360] のように右寄せで表示されます（[ ] は項目の範囲で、中は11桁です）。

金額の計算は編集項目の前に

編集項目は計算の材料（足される側・式の右辺）にはできません（第5章）。COMPUTE の結果の受け取り先には指定できますが、本ガイドでは数字項目で計算してから MOVE する形にそろえます。そのため、金額は計算用の項目（WS-AMOUNT など数字だけの項目）で求めてから、書き出す直前に編集項目へ MOVE します。

14.6 異常に備える：桁数の上限とエラー処理

14.4・14.5 で、正しいデータを正しく集計する仕組みができました。しかし夜間に無人で動くバッチは、想定外のデータや環境に出会っても、黙って間違った結果を出してはいけません。この節では、完成プログラムに組み込む2つの備え（桁数の上限とエラーの検知）を設計します。

桁数は「入りうる最大の値」から決める

金額は「数量 × 単価」です。入力の数量は PIC 9(3)（最大 999）、単価は PIC 9(5)（最大 99,999）なので、1明細の金額の最大は 999 × 99,999 = 99,899,001（8桁）です。

金額の項目を7桁（PIC 9(7)）にしていると、この最大値が入りきりません。金額の項目だけを PIC 9(7) にしたプログラムに、数量 999・単価 99,999 の1件を読ませた結果が次です。

report.txt（金額の項目を PIC 9(7) にした場合） 桁が足りない例 
ITEM  DATE             QTY   PRICE       AMOUNT
-----------------------------------------------
A001  20261001         999  99,999    9,899,001
A001  SUBTOTAL         999            9,899,001
-----------------------------------------------
TOTAL                  999            9,899,001

99,899,001 円のはずの売上が 9,899,001 円と、上の桁が消えた金額で出力されました。エラーは出ず、終了コードも 0（正常）です。第4章で見た桁あふれが、そのまま帳票に出てしまうのです。

そこで、各項目の上限を先に決め、そこから桁数を求めます。本章のプログラムでは次のように決めました。

項目上限の決め方最大の値PIC
数量（入力）入力の仕様9999(3)
単価（入力）入力の仕様99,9999(5)
明細の金額（WS-AMOUNT）999 × 99,99999,899,0019(8)
件数（WS-COUNT）1回の入力は 99,999 件までと業務で取り決める99,9999(5)
数量の小計・総合計999 × 99,999 件99,899,0019(8)
金額の小計・総合計計算どおりなら13桁必要になる。1回の売上は 999,999,999 円までと業務で取り決める999,999,9999(9)

明細の金額と数量の合計は、入力の桁と件数の上限から最大値が計算できるので、これで必ず収まります。一方、件数と金額の合計は業務の取り決めで上限を決めたので、取り決めを超えるデータが届く可能性は残ります。そこで、足し込むときに ON SIZE ERROR（第6章）で桁あふれを検知し、処理を中止します。

ON SIZE ERROR で桁あふれを検知する PROCEDURE DIVISIONの抜粋 
      * 金額を小計に足し込む（部品7の DETAIL-PROC）
           ADD WS-AMOUNT TO WS-SUB-AMT
               ON SIZE ERROR
                   DISPLAY "小計が上限を超えました: "
                           SR-ITEM
                   PERFORM ABEND-PROC
           END-ADD

ON SIZE ERROR の後ろの文は、結果が受け取り側の桁に入りきらないときだけ実行されます（このとき受け取り側の値は変わりません）。ABEND-PROC は、この後で説明する「異常終了」の段落です。帳票の編集項目の桁数も、この表の最大値に合わせています（14.5）。

ファイルとデータの異常を見逃さない

第12章で学んだとおり、業務プログラムではすべてのファイルに FILE STATUS を付け、操作のたびに結果を確かめます。本章のプログラムでは、次の場所で確かめます。

READ-PROC状態を 00（読めた）・10（終わり）・それ以外（異常）に分ける読み込みの失敗
DETAIL-PROC数量・単価が数字か（IS NUMERIC。第7章）数量の欄に文字が混じっている

帳票への書き出しは、すべて WRITE-PROC という1つの段落を通します。WRITE を書くたびに状態の確認を並べると、どこかで書き忘れやすいからです。

GnuCOBOL の SORT 文の落とし穴（実機で確認）

SORT 文は USING・GIVING のファイルを自分で開くので、その結果をファイル状態で受け取れません。しかも GnuCOBOL 3.1.2 では、USING のファイルが無くても「0件のデータ」として処理が進み、GIVING のファイルに書けなくても、前回の sorted.txt が残ったまま処理が進みます。どちらもエラーにならず、SORT-RETURN も 0 のままです。何もしなければ「売上0件」や「前回の売上」の帳票が、正常終了として出てしまいます。そこで CHECK-PROC で、SORT の前に2つのファイルを自分で開いて確かめます（開いたらすぐ閉じるので、「SORT 文の前に OPEN してはいけない」という 14.3 の規則にも反しません）。

SORT-RETURN とは

SORT-RETURN は、宣言しなくても使える特別な項目で、SORT 文が終わると結果（0 = 成功、16 = 失敗）が入ります。メインフレームの COBOL では、SORT の後に SORT-RETURN を確かめるのが定番です。上のとおり GnuCOBOL ではファイルの異常をこれで検知できませんが、処理系が変わっても通用する書き方として、本章でも確かめています。

異常を見つけたら、確実に「失敗」を知らせて止める

異常を見つけた段落は、原因のメッセージを表示してから ABEND-PROC（アベンド。異常終了 abnormal end の略）を呼びます。後始末はこの1つの段落にまとめます。

図の説明: どの異常も、原因を表示してから ABEND-PROC に集まり、終了コード 8 で止まります。

大切なのは終了コードです。第13章で学んだとおり、RETURN-CODE に入れた値はプログラム全体の終了コードになります。「0 は正常、8 以上は異常」という慣習に合わせて、異常時は 8 を返します。バッチは複数のプログラムを順に動かす「ジョブ」の一部なので、失敗したのに終了コード 0 で終わると、後ろの処理が「正常に終わった」と誤解して、誤った帳票やデータを使ってしまいます。

途中まで書かれた帳票の扱い

処理の途中で中止すると、report.txt は途中までしか書かれていない状態で残ります。終了コードが 0 でなければ、その帳票は使わないのが原則です。現場では、ジョブ（メインフレームでは JCL）が終了コードを見て後ろの処理を止め、帳票やデータを次の工程へ渡すのは正常終了したときだけにします。

ABEND-PROC でファイルを閉じる理由

STOP RUN は開いているファイルを閉じてから終わりますが、GnuCOBOL では libcob: warning: implicit CLOSE という警告が表示されます。そこで ABEND-PROC では、自分で CLOSE してから止めます。まだ開いていないファイルを CLOSE すると状態 42 になりますが、FILE STATUS を付けているので、プログラムは止まらずに先へ進みます。

部品7：手続き部（INIT-PROC・READ-PROC・DETAIL-PROC）

INIT-PROC は、OPEN のたびに状態を確かめます。見出し行と罫線は、MOVE で REPORT-REC に移してから WRITE-PROC（部品9）で書き出します。READ-PROC は、AT END の代わりに EVALUATE でファイル状態を3通りに分けます。CONTINUE は「何もしない」という文で、00（読めた）のときは何もせずに先へ進む、という意味です。

DETAIL-PROCが、14.4 の考え方をそのままコードにした段落です。まず数量と単価が数字かを確かめ、IF の中でキーを比較して小計を出し、それから金額を足す順番になっています。件数と金額の小計の足し込みには ON SIZE ERROR を付けています（14.6）。本ガイドの規約どおり、IF・EVALUATE・ADD・インライン PERFORM のように END-xxx（スコープ終了符）で閉じる文は、内側にピリオドを書いていません。単純な命令文は、段落の最後の文にだけピリオドを置いています。

salesrpt.cob（部品 7/9） PROCEDURE DIVISIONの抜粋 
       INIT-PROC.
           OPEN INPUT SORTED-FILE
           IF WS-FS-SRT NOT = "00"
               DISPLAY "sorted.txt を開けません 状態=" WS-FS-SRT
               PERFORM ABEND-PROC
           END-IF
           OPEN OUTPUT REPORT-FILE
           IF WS-FS-RPT NOT = "00"
               DISPLAY "report.txt を開けません 状態=" WS-FS-RPT
               PERFORM ABEND-PROC
           END-IF
           MOVE WS-HEAD-LINE TO REPORT-REC
           PERFORM WRITE-PROC
           MOVE WS-RULE-LINE TO REPORT-REC
           PERFORM WRITE-PROC.
      * 状態 00=読めた 10=終わり それ以外=異常
       READ-PROC.
           READ SORTED-FILE
           EVALUATE WS-FS-SRT
               WHEN "00"
                   CONTINUE
               WHEN "10"
                   SET WS-EOF-YES TO TRUE
               WHEN OTHER
                   DISPLAY "sorted.txt を読めません 状態="
                           WS-FS-SRT
                   PERFORM ABEND-PROC
           END-EVALUATE.
       DETAIL-PROC.
      * 数量・単価が数字でなければ中止する（第7章）
           IF SR-QTY IS NOT NUMERIC OR SR-PRICE IS NOT NUMERIC
               DISPLAY "数字でない項目があります: "
                       SALES-REC
               PERFORM ABEND-PROC
           END-IF
      * キーが変わったら先に小計を出す
           IF SR-ITEM NOT = WS-PREV-ITEM
               PERFORM BREAK-PROC
           END-IF
           COMPUTE WS-AMOUNT = SR-QTY * SR-PRICE
           ADD 1 TO WS-COUNT
               ON SIZE ERROR
                   DISPLAY "件数が上限を超えました"
                   PERFORM ABEND-PROC
           END-ADD
           ADD SR-QTY TO WS-SUB-QTY
           ADD WS-AMOUNT TO WS-SUB-AMT
               ON SIZE ERROR
                   DISPLAY "小計が上限を超えました: "
                           SR-ITEM
                   PERFORM ABEND-PROC
           END-ADD
           MOVE SR-ITEM TO DL-ITEM
           MOVE SR-DATE TO DL-DATE
           MOVE SR-QTY TO DL-QTY
           MOVE SR-PRICE TO DL-PRICE
           MOVE WS-AMOUNT TO DL-AMOUNT
           MOVE WS-DETAIL-LINE TO REPORT-REC
           PERFORM WRITE-PROC.

BREAK-PROCは「小計行を出す」ための段落で、小計を総合計に足し込み（ここにも ON SIZE ERROR）、貯め箱を0に戻し、前のキーを新しいキーに更新するまでを担当します。TERM-PROCは、ループが終わったあとに最後のグループの小計を出し、総合計を書いてファイルを閉じます。出力ファイルは閉じるときに残りの書き込みが行われることがあるので、report.txt の CLOSE の結果も確かめます。

z/OS と JCL

z/OS は IBM のメインフレームの基本ソフト（OS）です。そこで COBOL プログラムを動かすには、JCL（ジョブ制御言語）で「どのプログラムを、どのファイルを使って実行するか」を書いたジョブを投入します。第12章のコラムで触れたとおり、ASSIGN で指定した名前と実際のファイルは JCL で結びつけられます。現場では、本章のような並べ替えを、COBOL の SORT 文ではなく JCL のソート専用ステップ（DFSORT などのユーティリティ）で行うことも多くあります。

CICS（オンライン処理）

CICS は、メインフレーム上でオンライン処理（第1章）を動かすための仕組みです。画面や端末からの操作に応じて、COBOL プログラムがその場で呼び出されます。バッチは「まとめて処理」、CICS は「その場で処理」という使い分けです。

Db2 と埋め込み SQL

本章ではテキストファイルを読み書きしましたが、現場ではデータベース（IBM Db2 など）を使うことも多くあります。COBOL のプログラムの中に EXEC SQL 〜 END-EXEC で SQL を埋め込み、データを検索・更新します。SQL の基礎を学んでおくと入りやすくなります。

VSAM・索引ファイル

本ガイドで扱った順ファイルは、先頭から順に読むファイルでした。メインフレームでは、キーを指定して目的のレコードを直接読み書きできる索引ファイルも使われます。代表が VSAM で、その中のキー順のファイル（KSDS）が索引ファイルにあたります。COBOL では ORGANIZATION IS INDEXED のように指定し、READ や WRITE にキーを使います。

理解度確認クイズ

  • Q1. コントロールブレイクで小計を出す前に、入力データを SORT しておく必要があるのはなぜですか？

    回答を表示

    同じキー（商品コード）のデータが連続して並んでいることが、コントロールブレイクの前提だからです。順不同のままだと、同じ商品が離れた場所に何度も現れ、そのたびにキーが「変わった」と判断されて、同じ商品の小計が何か所にも分かれてしまいます。

  • Q2. コントロールブレイクの処理で、「最後のグループの小計」はなぜ特別に扱う必要がありますか？ 本章のプログラムではどこで出力していますか？

    回答を表示

    小計は「キーが変わった」ことをきっかけに出す仕組みですが、最後のグループの後にはキーが変わる相手の行がないため、ループの中では小計が出ません。そこで、ファイルの終わりを検出してループを抜けた後の終了処理（TERM-PROC）で、BREAK-PROC を呼んで最後の小計を出力しています。

  • Q3. SORT文の SORT WK-FILE ON ASCENDING KEY WK-ITEM USING IN-FILE GIVING SORTED-FILE で、WK-FILE・USING・GIVING はそれぞれ何を表していますか？

    回答を表示

    WK-FILE は並べ替えの作業に使うソート用ファイル（データ部で SD として定義）、USING は並べ替える前のデータを読み込む入力ファイル、GIVING は並べ替えた結果を書き出す出力ファイルです。USING・GIVING のファイルは、SORT文が自分で開いて閉じるので、SORT文の前に OPEN してはいけません。

  • Q4. メインフレームで COBOL のバッチプログラムを実行するとき、「どのプログラムを、どのファイルを使って動かすか」を指定するために書くものは何ですか？

    回答を表示

    JCL（ジョブ制御言語）です。プログラム内の SELECT 〜 ASSIGN で付けた名前と、実際のデータセット（ファイル）を JCL で結びつけます。本ガイドの GnuCOBOL では、ASSIGN にファイル名を直接書いていましたが、メインフレームではこの部分を JCL が担当します。

  • Q5. 数量が PIC 9(3)、単価が PIC 9(5) のとき、金額（数量 × 単価）を入れる数字項目は何桁必要ですか？ 桁が足りないと何が起きますか？

    回答を表示

    最大値は 999 × 99,999 = 99,899,001 なので、8桁（PIC 9(8)）必要です。7桁にすると上の桁が消え、99,899,001 が 9,899,001 になるなど、誤った金額がエラーも出ずに出力されます。小計・総合計のように入力の桁だけでは最大値が決まらない項目は、業務で上限を取り決めて桁数を決め、ON SIZE ERROR で桁あふれを検知します。

  • Q6. バッチプログラムが異常を見つけて中止するとき、終了コード（RETURN-CODE）を 0 以外にするのはなぜですか？

    回答を表示

    バッチはジョブの中で順に実行され、後ろの処理は前のプログラムの終了コードを見て、続けるか止めるかを決めるからです。失敗したのに 0 を返すと、後ろの処理が正常に終わったと誤解し、途中までしか書かれていない帳票や誤ったデータを使ってしまいます。本章のプログラムでは、ABEND-PROC で RETURN-CODE に 8 を入れて止めています。
