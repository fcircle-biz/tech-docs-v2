既存Struts 1システムの読み方

いよいよ本ガイドの最終章です。第1章で見た「画面 → .do → struts-config.xml → ActionForm → Action → DAO → DB → ActionForward → JSP」という処理フローを、今度は逆方向に使います。「この画面のこの項目を直したい」という改修依頼から出発し、修正すべきファイルを1つずつ突き止める——それが実務で最も求められるスキルです。

この章で学ぶこと

  • 保守開発の現場で「読む力」が最重要である理由を説明できる
  • 画面から書くべきコードまでを、決まった8ステップで追跡できる
  • 実際の改修依頼をもとに、修正が必要なファイルを具体的に特定できる
  • 影響範囲の見極め方と、レガシーコードでよく出会う落とし穴を把握し、調査時に注意できる

8.1 なぜ「読む力」が最重要なのか

これまでの7つの章では、Struts 1 の部品を1つずつ「作る」側から学んできました。しかし実際の現場に配属されると、真っ白なプロジェクトから何かを新規に作る仕事はごく一部です。多くの保守開発の現場で求められるのは、すでに動いているシステムを調査し、影響範囲を見極め、必要最小限の修正を加えるという仕事です。

新規開発の場合 保守開発の場合
仕様書を読んで、ゼロからコードを書く 既存コードを読んで、どこにどう手を入れるかを決める
設計がそのままドキュメントになる ドキュメントが古い・存在しないことが珍しくない
構造を自分で決められる 既存の構造・命名規則に合わせる必要がある
影響範囲は自分のコードだけ 1行の修正が他の画面・他の機能に影響することがある

① 調査

依頼の内容を、追える単位（画面・URL・クラス名）に分解する。まずはコードを読むところから始まる。

② 影響範囲の特定

直そうとしている箇所を、他の誰か・他の画面が共有していないかを確認する。

③ 最小限の修正

依頼された内容だけを直す。ついでの整形やリファクタリングは、別の作業として切り分ける。

ドキュメントより、コードを信じる

設計書やコメントは、コードが変わった後も更新されずに残っていることがよくあります。ドキュメントと実際の挙動が食い違ったときは、常にソースコードのほうが正しいと考えてください。本章で身につける「追跡の型」は、ドキュメントが無くても・古くても通用する方法です。

8.2 追跡の型（8ステップ）

Struts 1 のシステムは、どのプロジェクトでも「画面 → 設定ファイル → Java」という同じ構造でできています。つまり、毎回同じ順番でファイルを開いていけば、必ずたどり着けるということです。以下の8ステップを型として覚えてください。

各ステップで「どのファイルを」「何を目印に」探すのかを一覧にしておきます。grep で検索するときのキーワードも一緒に覚えておくと、大規模なプロジェクトでも迷いません。

ステップ 開くファイル 探すキーワード 次に見るもの
① 画面 対象の .jsp <html:form action属性の値（=.do）
② 送信先 同じJSP .do 拡張子を除いたパス名
③ 設定 struts-config.xml path=" 同じ<action>のname属性
④ Form 同じstruts-config.xml form-bean name=" ActionFormのtype（クラス名）
⑤ Action ③のtypeが指すJavaファイル type=" execute()内で呼ぶDao/Service
⑥ DAO Dao／Serviceクラス new xxxDao() SQLを実行しているメソッド
⑦ SQL 同じDaoクラス SELECT/WHERE WHERE句・ORDER BY句
⑧ 遷移先 struts-config.xml findForward( forward先のJSP

8.3 実例で追跡してみる

実際に手を動かして追跡してみましょう。想定する改修依頼はこちらです。

改修依頼

「社員一覧画面の検索条件に『部署』を追加してほしい。現在は氏名でしか検索できない」

① 画面（JSP）を確認する

まず対象画面のJSPを開きます。検索フォームの部分を見ると、氏名だけが入力項目になっており、一覧の結果には部署列がすでに表示されていることが分かります。

list.jsp — 社員一覧画面（抜粋） 
<%-- 検索条件フォーム。department（部署）の入力欄はまだ無い --%>
<html:form action="/employee/search">
    氏名: <html:text property="name" />
    <html:submit value="検索" />
</html:form>

<logic:iterate id="employee" name="employees">
    <tr>
        <td><bean:write name="employee" property="name" /></td>
        <td><bean:write name="employee" property="department" /></td>
    </tr>
</logic:iterate>

ここで分かったこと: 送信先は /employee/search（②）。一覧の結果には既に department プロパティが表示されているので、DTOにはすでに部署の値がある可能性が高い、という当たりも付きます。次は struts-config.xml を開きます。

③④ struts-config.xmlでactionとform-beanを確認する

struts-config.xml — /employee/search の定義 
<!-- ④. name属性から対応するform-beanを探す -->
<form-bean name="employeeForm"
           type="com.example.form.EmployeeForm" />

<!-- ③. path="/employee/search" が今回たどるaction -->
<action path="/employee/search"
        type="com.example.action.SearchAction"
        name="employeeForm"
        scope="request"
        validate="false">
    <forward name="success" path="/list.jsp" />
</action>

ここで分かったこと: ActionFormは com.example.form.EmployeeForm（④）、Actionは com.example.action.SearchAction（⑤）。次はこの2つのJavaファイルを開きます。

④⑤ ActionFormとActionを開く

EmployeeForm.java — 検索条件を保持するActionForm 
public class EmployeeForm extends ActionForm {
    // 現時点では検索条件としてnameしか保持していない
    private String name;

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
}
SearchAction.java — 検索処理を実行するAction 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    EmployeeForm employeeForm = (EmployeeForm) form;
    // 現時点ではnameだけをDaoに渡している
    List employees = new EmployeeDao().search(employeeForm.getName());
    request.setAttribute("employees", employees);
    return mapping.findForward("success");
}

ここで分かったこと: EmployeeForm には name しか無く、SearchAction も EmployeeDao.search() に name しか渡していません（⑥）。つまり部署による絞り込みは、Form・Action のどちらにもまだ存在しないということが読み取れます。次はDao側のSQLを確認します。

⑥⑦ DAOのSQLを確認する

EmployeeDao.java — 検索SQLを組み立てる部分 
-- ★ WHERE句に department の条件がまだ含まれていない
SELECT id, name, department
FROM employee
WHERE name LIKE ?
ORDER BY id

SQLのWHERE句にも部署の条件が無いことが確認できました。これでForm・Action・Daoの3箇所すべてに部署対応が入っていないことが分かったので、この3つが修正対象になります。最後に⑧のforward先を確認しておくと、success は同じ /list.jsp に戻るだけなので、検索結果を再表示する画面自体に変更は不要だと分かります。

修正が必要なファイル一覧

ファイル 修正内容 修正要否
list.jsp（検索フォーム） 部署の入力欄（html:text等）を追加 要修正
struts-config.xml path・type・formの対応は変わらない 変更不要
EmployeeForm.java departmentプロパティ（getter/setter）を追加 要修正
SearchAction.java employeeForm.getDepartment()を取得し、search()の第2引数として渡すよう追加 要修正
EmployeeDao.java search()の引数にdepartmentを追加し、SQLにAND department = ?を追加（部署が未指定のときは条件を組み立てない。第6章6.5の動的SQLの方針に従う） 要修正
list.jsp（結果表示） 表示列は既にdepartmentを含んでいる 変更不要

「新規に追加」より「既に半分できている」ことのほうが多い

レガシーシステムでは、今回のように画面の表示側やstruts-config.xmlの定義はすでに用意されていて、Form・Action・DaoのSQLといったロジック側の数箇所だけが漏れている、というケースがよくあります。8ステップすべてを機械的に確認することで、「どこまでできていて、どこからやればよいか」を正確に切り分けられます。

8.4 修正箇所の特定と影響範囲の見極め

追跡できてもすぐに直してはいけません。Struts 1 のクラスや設定は、複数の画面から共有されていることが多いためです。修正前に必ず「この部品を他の誰が使っているか」を確認してください。

同じActionを複数のpathが共有

1つのActionクラスに、parameter属性違いの<action>が複数ぶら下がっていることがあります。処理を書き換えると全pathの挙動が変わります。

同じActionFormを複数画面が共有

scope="session"のFormは特に、別の画面から見えている値を書き換えてしまうことがあります。

global-forwards経由の遷移

<global-forwards>はプロジェクト全体で共有される遷移名です。名前を変えると、他の多数のActionに影響します。

共通の親Action・共通JSPインクルード

独自のBaseActionや<%@ include %>で共通化された部分を直すと、影響範囲がプロジェクト全体に広がります。

確認観点 確認方法（grep例） 見つかったらどうするか
このActionを使うpathは他にあるか grep 'type=".*SearchAction"' ヒットした全pathの画面を確認してから直す
このFormを使う画面は他にあるか grep 'name="employeeForm"' 各画面で入力項目の意味が同じか確認する
global-forwardsに巻き込まれていないか grep -A10 '<global-forwards>' 個別forwardで上書きされていないか確認する
共通JSPをincludeしていないか grep '<%@ include' include先の修正は影響範囲が広いと心得る

「動いているところは触らない」を徹底する

レガシーシステムの修正でもっとも危険なのは、依頼されていない箇所まで直してしまうことです。共有部品を見つけたら、依頼範囲だけをピンポイントで直す方法（新しいpath・新しいメソッドの追加など）が無いかを先に検討してください。

8.5 レガシーコードでよく出会う落とし穴

ここまでの型はStruts 1の「教科書どおり」の構成を前提にしていました。しかし現場のコードは、年代やプロジェクトによって少しずつ違う書き方が混ざっています。代表的なパターンと、その読み方を覚えておきましょう。

落とし穴 そう見えたら どう読むか（対処）
execute()でなくperform() public ActionForward perform(...)が定義されている Struts 1.0系の名残。中身はexecute()と同じ意味で読んでよい
DispatchActionで1クラス複数機能 parameter="method"があり、複数のpublicメソッドがある struts-config.xmlのparameter値とリクエストのmethodパラメータ名から呼ばれるメソッドを特定する
struts-configが複数（モジュール分割） web.xmlにconfig/xxxのinit-paramが複数ある 先にweb.xmlでモジュールのURLプレフィックスを確認し、対応するconfigファイルを開く
Tilesによる画面合成 forward先がJSPではなくTiles定義名を指している tiles-defs.xmlを開き、レイアウトと部品JSPの組み合わせを確認する
JSPのスクリプトレット混在 JSP内に<% %>でJavaコードが直接書かれている Strutsタグだけでなく、スクリプトレット内のロジックも追跡対象に含める
.classとソースの不一致 修正してもデプロイ後の挙動が変わらない WEB-INF/classesのタイムスタンプやビルド手順を確認し、正しくコンパイル・配置されているか調べる
独自フレームワーク層でラップ BaseAction等の独自親クラスがある 親クラスのexecute()を先に読み、実際のサブクラス処理につながる箇所を探す

DispatchActionの例

上表②の例を実物で見ておきましょう。1つのActionクラスに複数のメソッドがあり、struts-config.xmlのparameter="method"と、リクエストパラメータmethodの値の組み合わせで、呼ばれるメソッドが決まります。

EmployeeDispatchAction.java — 1クラスに複数機能をまとめる例 
public class EmployeeDispatchAction extends DispatchAction {
    // リクエストの method=search で、このメソッドが呼ばれる
    public ActionForward search(ActionMapping mapping, ActionForm form,
            HttpServletRequest request, HttpServletResponse response) throws Exception {
        return mapping.findForward("success");
    }

    // リクエストの method=delete で、このメソッドが呼ばれる
    public ActionForward delete(ActionMapping mapping, ActionForm form,
            HttpServletRequest request, HttpServletResponse response) throws Exception {
        return mapping.findForward("success");
    }
}

このパターンに出会ったら、まず画面側のリンクやボタンが ?method=search のようにmethodパラメータを送っていないかを確認してください。それが、どのメソッドに処理が入るかを決める手がかりになります。

やってみよう 8-1: 追跡演習 ― 修正すべきファイルを特定する

以下の3つのコード断片をもとに、2つの改修依頼それぞれについて「修正すべきファイル」を特定してみましょう。8.2の8ステップの型を使って、実際に指でたどりながら考えてください。

createComplete.jsp — 登録完了画面 
<h2>登録完了</h2>
<p><bean:message key="employee.create.complete" /></p>
<html:link page="/employee/search.do">一覧へ戻る</html:link>
struts-config.xml — 登録actionの定義 
<action path="/employee/create"
        type="com.example.action.CreateAction"
        name="employeeForm"
        scope="request">
    <forward name="success" path="/createComplete.jsp" />
</action>
EmployeeDao.java — findAll()（一覧取得） 
SELECT id, name, department
FROM employee
ORDER BY id

追跡の手順

  1. 1 依頼内容から、関係しそうな画面（JSP）を上のコード断片の中から探す。
  2. 2 画面にStrutsタグ（bean:message等）があれば、それが何を参照しているかを確認する。
  3. 3 struts-config.xmlのaction定義から、関係するActionとforward先を確認する。
  4. 4 依頼が一覧表示に関するものであれば、Dao側のSQLも確認する。
  5. 5 「修正すべきファイル」を1つに絞り込み、理由を言葉で説明できるようにする。

依頼1: 「登録完了メッセージの文言を変えたい」

解答例を表示

createComplete.jspの文言は<bean:message key="employee.create.complete" />で出力されており、JSPには文字列が直書きされていません。つまりJSPではなく、対応するリソースバンドル（ApplicationResources.properties等）の該当キーの値を修正する必要があります。JSP・struts-config.xml・Actionはいずれも変更不要です。

依頼2: 「一覧の並び順を、氏名の昇順に変えたい」

解答例を表示

並び順を決めているのはEmployeeDao.javaのSQLのORDER BY句です。現在はORDER BY idになっているため、これをORDER BY nameに修正します。JSP・struts-config.xml・Actionはいずれも変更不要です。表示側はDaoが返した順番をそのまま並べているだけだからです。

学習の総まとめ

全8章を通じて、Struts 1の「作る力」ではなく「読む力」を積み上げてきました。ここまでの道のりを振り返りましょう。

  • Struts 1のMVCの対応と、画面からDBまでの1本の処理フローを説明できるようになった（第1章）
  • web.xmlとstruts-config.xmlを読み、URLからActionクラスを特定できるようになった（第2章）
  • Action・ActionForm・JSPとStrutsタグの役割を理解し、実装できるようになった（第3〜5章）
  • Action→DAO→DBの連携で、一覧・検索・CRUDを組み立てられるようになった（第6〜7章）
  • 既存のレガシーStruts 1システムを読み解き、修正すべきファイルを特定できるようになった（第8章＝本章）

次の一歩

Struts 1 は2013年にEOLとなっており、新規開発の選択肢ではありません。担当システムの将来的な刷新やリプレースに関わる場合は、Struts 1 の後継にあたるSpring MVCを学ぶと、「アノテーションで設定を書く」「DIコンテナが部品を組み立てる」といった考え方の違いが、Struts 1 との対比でより深く理解できます。DAO層の実装をさらに深めたい場合はJDBCの学習も有効です。

理解度確認クイズ

  1. Q1. 保守開発の現場でまず最初にすべきことは何ですか？また、ドキュメントより優先すべきものは何ですか？

    回答を表示

    まずソースコードを実際に読んで追跡することです。設計書やコメントは実装が変わっても更新されないことが多く、ドキュメントと実際の挙動が食い違う場合は常にソースコードのほうを信じる必要があります。

  2. Q2. 「社員一覧の検索条件に部署を追加したい」という依頼の場合、struts-config.xmlの<action>定義自体は修正が必要ですか？その理由も答えてください。

    回答を表示

    通常は修正不要です。pathやtype、ActionFormとの対応関係は変わらないため、修正はActionForm（departmentプロパティの追加）・Action（Daoへdepartmentを渡す処理の追加）・DAOのSQL・画面側に限られます。

  3. Q3. 同じActionクラスを複数のaction pathが共有している場合、1つのpathのために処理を書き換えるとどんなリスクがありますか？

    回答を表示

    他のpathを利用している画面の挙動まで意図せず変えてしまう可能性があります。修正前に、そのActionクラスをtype="..."で参照しているaction定義が他に無いかをgrep等で確認する必要があります。

  4. Q4. JSPに <bean:message key="..." /> タグが使われている場合、表示文言を変更するにはどのファイルを編集すべきですか？

    回答を表示

    JSP自体ではなく、対応するリソースバンドル（ApplicationResources.propertiesなど）にある該当キーの値を編集します。JSPには文字列そのものではなくキー名しか書かれていないためです。
