CRUDを作る

これまでの章で学んだ struts-config.xml・Action・ActionForm・Struts タグ・DAO を、すべて組み合わせます。この章では「社員管理」を題材に、一覧・検索・詳細・登録・更新・削除という業務システムの基本形＝CRUD一式を作りながら、既存の Struts 1 システムに必ず存在する定番パターンを身につけます。

この章で学ぶこと

  • 社員管理の6機能（一覧・検索・詳細・登録・更新・削除）の全体像を、画面遷移図とファイル一覧で説明できる
  • struts-config.xml に6つの <action> を過不足なく定義できる
  • 一覧・検索・詳細の実装パターン（logic:iterate・findById()）を理解する
  • 登録・更新・削除で必ず問題になる「二重送信」「排他制御」「GETでの削除実行」への定番の対処法を説明できる
  • 共通化の勘所（親 Action・DispatchAction・共通ヘッダー/フッター・Tiles）を把握する

7.1 作るアプリの全体像

題材は、第6章までずっと使ってきた「社員（Employee）」です。業務システムのマスタ画面に共通して必要になる6つの機能——一覧・検索・詳細・登録・更新・削除——を、この章でひとまとめに実装します。この6機能の組み合わせを、実務では「CRUD」（Create・Read・Update・Delete）と呼びます。

一覧・検索（Read）

全件表示、または条件を絞り込んで社員を一覧表示する。第6章で作った処理をそのまま使う。

詳細（Read）

一覧から1件を選び、その社員の全項目を表示する。

登録・更新・削除

新しい社員を登録し、既存社員の情報を更新し、不要になった社員を削除する。

画面遷移図

まず全体の画面の流れを俯瞰しましょう。すべての機能は一覧画面を起点にし、一覧画面へ戻ってくる形にまとめます。これは業務システムで非常によく見る構成です。

flowchart TD A["一覧画面
list.jsp"] -->|"詳細へ"| B["詳細画面
detail.jsp"] B -->|"編集へ"| C["更新入力画面
update.jsp"] C -->|"更新実行"| D["更新完了
updateComplete.jsp"] D -->|"一覧へ戻る"| A A -->|"新規登録"| E["登録入力画面
create.jsp"] E -->|"確認へ（validate通過）"| F["登録確認画面
confirm.jsp"] F -->|"登録実行"| G["登録完了

登録・削除には「確認画面」を挟んでいる点に注目してください。理由は 7.5・7.7 で詳しく説明しますが、ユーザーの誤操作や二重送信を防ぐため、業務システムでは確認画面を1枚挟むのが定石です。

必要なファイル一式

この章で作るファイルを、機能ごとに一覧表にまとめました。実装に入る前に、これから何を書くのかを俯瞰しておきましょう。

クラス名・入れ物は1つに揃える

Action クラスは機能ごとに分けますが、ActionForm（com.example.form.EmployeeForm）・DTO（com.example.dto.Employee）・DAO（com.example.dao.EmployeeDao）は6機能で共用します。入れ物を機能ごとに増やすと、後から見た人が対応関係を追えなくなります。

7.2 struts-config.xmlをまとめて書く

第2章で学んだとおり、Struts 1 では設定ファイルが処理の入口です。実装コードを書く前に、6機能ぶんの <action> を一気に定義してしまいましょう。まずは入力値の入れ物 <form-bean> です。

struts-config.xml — form-beans（6機能で共用） 
<form-beans>
    <!-- 6機能すべてでこの1つを使い回す -->
    <form-bean name="employeeForm"
               type="com.example.form.EmployeeForm" />
</form-beans>

次に一覧です。検索条件を持たない「全件取得」の入口として定義します。

struts-config.xml — /employee/list 
<action path="/employee/list"
        type="com.example.action.ListAction"
        name="employeeForm"
        scope="request">
    <forward name="success" path="/list.jsp" />
</action>

検索は一覧と表示画面を共有します。forward 先が同じ list.jsp であることに注目してください。

struts-config.xml — /employee/search 
<action path="/employee/search"
        type="com.example.action.SearchAction"
        name="employeeForm"
        scope="request"
        validate="true"
        input="/list.jsp">
    <forward name="success" path="/list.jsp" />
</action>

詳細は、指定した id の社員が見つからなかった場合の遷移先 notFound を用意しておきます（7.4 で使います）。

struts-config.xml — /employee/detail 
<action path="/employee/detail"
        type="com.example.action.DetailAction"
        name="employeeForm"
        scope="request">
    <forward name="success" path="/detail.jsp" />
    <forward name="notFound" path="/notFound.jsp" />
</action>

登録は、入力チェック（validate="true"）と、確認画面・完了画面・二重送信時の遷移先をすべて持ちます。7.5 で流れを詳しく追います。

struts-config.xml — /employee/create 
<action path="/employee/create"
        type="com.example.action.CreateAction"
        name="employeeForm"
        scope="session"
        validate="true"
        input="/create.jsp">
    <forward name="confirm" path="/confirm.jsp" />
    <forward name="complete" path="/createComplete.jsp" redirect="true" />
    <forward name="duplicate" path="/duplicate.jsp" />
</action>

更新も同様に、画面表示（フォームへの詰め替え）と更新実行の両方をこの1つの <action> が受け持ちます。

struts-config.xml — /employee/update 
<action path="/employee/update"
        type="com.example.action.UpdateAction"
        name="employeeForm"
        scope="session"
        validate="true"
        input="/update.jsp">
    <forward name="input" path="/update.jsp" />
    <forward name="complete" path="/updateComplete.jsp" redirect="true" />
    <forward name="notFound" path="/notFound.jsp" />
</action>

削除は、確認画面からのPOST送信のみを受け付ける実行係です（理由は 7.7）。

struts-config.xml — /employee/delete 
<action path="/employee/delete"
        type="com.example.action.DeleteAction"
        name="employeeForm"
        scope="request">
    <forward name="complete" path="/employee/list.do" redirect="true" />
</action>

最後に、どの機能からも起こりうる異常系（DB接続失敗など）の遷移先を <global-forwards> にまとめておきます。個々の <action> に毎回書かずに済みます。

struts-config.xml — global-forwards（エラー画面の共通化） 
<global-forwards>
    <!-- 想定外の例外はここへ集約する -->
    <forward name="error" path="/error.jsp" />
</global-forwards>

6つの<action>を1枚の対応表として読む

既存システムを保守するときは、まさにこの6ブロックのような塊を struts-config.xml の中から探すことになります。path（URL）・type（処理クラス）・forward（遷移先）の3点を1組として読む癖をつけましょう。第8章の読み方の土台になります。

7.3 一覧と検索

ListAction と SearchAction は、第6章で作った処理とほぼ同じです。ポイントは、「検索条件が空なら全件、あれば絞り込み」という判断をどちらに持たせるかです。ここでは判断を SearchAction 側に置きます。

ListAction.java — 常に全件 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    // 検索条件を持たず、常に全件取得する
    List employees = new EmployeeDao().findAll();
    request.setAttribute("employees", employees);
    return mapping.findForward("success");
}
SearchAction.java — 条件の有無で処理を分ける 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    EmployeeForm employeeForm = (EmployeeForm) form;
    String name = employeeForm.getName();
    String department = employeeForm.getDepartment();
    EmployeeDao dao = new EmployeeDao();
    List employees;
    if (name == null || name.trim().length() == 0) {
        employees = dao.findAll();      // 条件なし → 全件
    } else {
        employees = dao.search(name, department);  // 条件あり → 絞り込み
    }
    request.setAttribute("employees", employees);
    return mapping.findForward("success");
}

表示側の list.jsp は <logic:iterate> で employees をループし、各行から詳細画面へのリンクを張ります。

list.jsp — 一覧テーブルと詳細リンク 
<table>
<logic:iterate id="employee" name="employees">
    <tr>
        <td><bean:write name="employee" property="name" /></td>
        <td><bean:write name="employee" property="department" /></td>
        <td>
            <%-- idをクエリで渡し、DetailActionへ --%>
            <html:link page="/employee/detail.do"
                       paramId="id" paramName="employee" paramProperty="id">
                詳細へ
            </html:link>
        </td>
    </tr>
</logic:iterate>
</table>

つまずきポイント: 一覧に戻ると検索条件が消える

詳細画面から「一覧へ戻る」を /employee/list.do にリンクすると、ListAction が呼ばれて必ず全件表示に戻ってしまいます。検索結果に戻したい場合は、検索条件を session に保持するか、戻るリンクのクエリに条件を付け直す（/employee/search.do?name=...）といった対処が必要です。既存システムでもよく見落とされている点です。

7.4 詳細表示

詳細画面は、一覧からリンクで渡された id を受け取り、1件分のデータを表示するだけの機能です。id の受け取り方には2通りあります。

受け取り方 書き方 特徴
request から直接 request.getParameter("id") ActionFormを介さない。1項目だけ受け取るときに手早い
ActionFormのプロパティ employeeForm.getId() GETのクエリでもActionServletが自動でセットする。他の項目とまとめて扱える

本ガイドでは、EmployeeForm を6機能で共用する方針に合わせ、ActionFormのプロパティで受け取ります。見つからなかった場合の分岐を忘れないようにしましょう。

DetailAction.java — idの変換（String→int） 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    EmployeeForm employeeForm = (EmployeeForm) form;
    int id;
    try {
        // EmployeeFormのidはString（画面からの入力）。DTO/DAOはintで扱うため変換する
        id = Integer.parseInt(employeeForm.getId());
    } catch (NumberFormatException e) {
        return mapping.findForward("notFound");  // idが数値でない不正なリクエスト
    }
    // ここから先は検索処理（下のコードへ続く）
DetailAction.java — 見つからない場合の分岐 
    Employee employee = new EmployeeDao().findById(id);
    if (employee == null) {
        // 削除済み・不正なidなど → 専用画面へ
        return mapping.findForward("notFound");
    }
    request.setAttribute("employee", employee);
    return mapping.findForward("success");
}

// ConnectionFactory: 6.3で示した接続取得処理（DriverManager/DataSource）をまとめたクラス
public Employee findById(int id) throws SQLException {
    String sql = "SELECT id, name, department FROM employee WHERE id = ?";
    Connection con = null;
    PreparedStatement ps = null;
    ResultSet rs = null;
    try {
        con = ConnectionFactory.getConnection();
        ps = con.prepareStatement(sql);
        ps.setInt(1, id);
        rs = ps.executeQuery();
EmployeeDao.java — findById()（後半） 
        if (!rs.next()) {
            return null;  // 1件も無ければnullを返す
        }
        return toEmployee(rs);
    } finally {
        // Java 7未満の現場も多く、try-with-resourcesが使えないことがある（第6章参照）

findById()がnullを返す設計にそろえる

「見つからない」を例外で表現するか、null で表現するかはプロジェクトごとに流儀が分かれます。本ガイドでは null を返す方式に統一しています。既存コードを読むときは、まずどちらの流儀かをDAOの実装かJavadocで確認してください。

7.5 登録（Create）

登録処理は6機能の中で最も工程が多い機能です。入力画面 → 検証 → 確認画面 → 登録実行 → 完了画面という5段階の流れを、1つの CreateAction と1つの /employee/create.do で受け持ちます。

flowchart LR A["入力画面
create.jsp"] -->|"POST"| B{"validate（）実行
入力チェック"} B -->|"エラーあり"| A B -->|"OK"| C["確認画面
confirm.jsp"] C -->|"POST（登録する）"| D{"CreateAction
トークン検証"} D -->|"NG（二重送信）"| E["duplicate.jsp"] D -->|"OK"| F["DBへINSERT"] F --> G["完了画面
createComplete.jsp"]

図中の validate() は第4章で学んだとおり、ActionForm に書きます。エラーがあれば input 属性で指定した画面（この場合 create.jsp）へ自動で差し戻されます。

EmployeeForm.java — validate()（登録・更新で共用） 
public ActionErrors validate(ActionMapping mapping, HttpServletRequest request) {
    ActionErrors errors = new ActionErrors();
    if (name == null || name.trim().length() == 0) {
        // メッセージリソースのキーを指定（第4章参照）
        errors.add("name", new ActionMessage("error.name.required"));
    }
    return errors;
}

CreateAction は、確認画面からの送信かどうかを隠しフィールド phase で見分けます。同じ /employee/create.do に2回リクエストが来る設計です。phase は6機能共通の項目ではなく、EmployeeForm に追加した登録・更新フロー専用の独自プロパティ（何回目の送信かを示す）です。

CreateAction.java — 1回目: 確認画面へ進む（トークン発行） 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    EmployeeForm employeeForm = (EmployeeForm) form;
    String phase = request.getParameter("phase");
    if (!"confirm".equals(phase)) {
        // 1回目：入力画面から到達。確認画面を出す直前にトークン発行
        saveToken(request);
        return mapping.findForward("confirm");
    }
    // ここから先は2回目（下のコードへ続く）
CreateAction.java — 2回目: トークン検証と登録実行 
    // 2回目：確認画面の「登録する」ボタン押下
    if (!isTokenValid(request)) {
        return mapping.findForward("duplicate");  // 二重送信を検知
    }
    resetToken(request);  // トークンは1回使ったら破棄
    new EmployeeDao().insert(toEmployee(employeeForm));
    return mapping.findForward("complete");
}

確認画面の confirm.jsp は、入力値を表示専用で見せつつ、隠しフィールドで値と phase=confirm を送り返します。

confirm.jsp — 確認画面から登録実行へ 
<html:form action="/employee/create">
    氏名: <bean:write name="employeeForm" property="name" />
    <html:hidden property="name" />
    <html:hidden property="phase" value="confirm" />
    <html:submit>登録する</html:submit>
</html:form>

実践: 二重送信対策は2段構えで考える

Struts 1 で二重登録を防ぐ方法は主に2つです。①トランザクショントークン：Action が持つ saveToken()／isTokenValid()／resetToken() で、セッションに埋め込んだ1回限りの合言葉を照合する方式（上のコード）。②PRGパターン：登録処理が終わったら forward ではなくredirect="true" で完了画面へリダイレクトさせ、完了画面をリロードしても登録処理そのものは再実行されないようにする方式です。上の struts-config.xml（7.2）の complete フォワードに redirect="true" を付けているのはこのためです。実務では両方を併用するのが安全です。

つまずきポイント: 完了画面のリロードで二重登録

redirect="true" を付け忘れて forward（内部転送）のままにすると、ブラウザのアドレスバーは create.do のままになります。ユーザーがこの状態でブラウザの再読み込みをすると、直前のPOSTリクエストが再送されます。resetToken() によってトークンはすでに無効化されているため、この再送は isTokenValid() で弾かれて duplicate.jsp に遷移しますが、もしトークンチェックを実装していない場合は、この再送によって同じ内容が再度INSERTされ二重登録になります。完了画面は必ずリダイレクトで見せ、そもそも再送が起きないようにしましょう。

7.6 更新（Update）

更新は「登録」と似た構造ですが、決定的に違う点が1つあります。入力画面を開いた時点で、すでにDBにある現在の値を画面に表示しておく必要があることです。

UpdateAction.java — 初回表示: DBの現在値をformへ詰める 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    EmployeeForm employeeForm = (EmployeeForm) form;
    if (!"submit".equals(request.getParameter("phase"))) {
        // 一覧・詳細画面からの初回表示 → DBの現在値をformへ詰める
        int id = Integer.parseInt(employeeForm.getId());  // 変換失敗時の扱いは7.4のDetailActionと同様
        Employee current = new EmployeeDao().findById(id);
        if (current == null) {
            return mapping.findForward("notFound");
        }
        copyToForm(current, employeeForm);  // DTO→ActionFormへ詰め替え
        return mapping.findForward("input");
    }
    // ここから先は更新実行（下のコードへ続く）
UpdateAction.java — 更新実行: 更新件数0件の分岐 
    // update.jspからの更新実行
    int count = new EmployeeDao().update(toEmployee(employeeForm));
    if (count == 0) {
        // 表示後に他ユーザーが削除・変更していた場合
        return mapping.findForward("notFound");
    }
    return mapping.findForward("complete");
}

ここで scope="session" を選んだ理由を説明します。更新処理には初回表示（一覧・詳細画面からDBの現在値を取得してformへ詰める）と送信（更新を実行する）という2つの操作があり、これらは別々のリクエストになります。request スコープの値はリクエストが変わった時点で消えてしまうため、リクエストをまたいで値を保持できる session スコープを使います。なお、validate() が失敗して input 画面へ差し戻される場合は同一リクエスト内のforward（第5章 5.2 参照）なので、実は request スコープのままでも ActionForm の値は JSP から参照でき、<html:text> に再表示されます。ただし session は使いすぎると、別タブでの操作が混線したりメモリを圧迫したりするため、必要な場面に絞って使いましょう。

scope 値の寿命 向いている場面
request 1リクエストの間だけ 項目が少ない・差し戻しが起きにくい画面（一覧・検索など）
session セッションが続く限り 複数画面をまたぐ更新・登録フロー
UPDATE文（EmployeeDao.update() が実行するSQL） 
-- executeUpdate()の戻り値（更新件数）を必ず確認する
UPDATE employee
   SET name = ?, department = ?
 WHERE id = ?

更新件数0件は「排他制御」の入口

UPDATE ... WHERE id = ? の戻り値（更新件数）が0件なら、そのidの行はすでに他の誰かが削除・変更した可能性があります。本ガイドでは「更新できませんでした」と伝える程度にとどめますが、実務ではさらにWHERE 句に更新前のバージョン番号や更新日時を加える「楽観的排他制御」が使われることがあります。用語だけ覚えておけば十分です。

つまずきポイント: idをhiddenで渡し忘れる

更新画面のフォームに <html:hidden property="id" /> を書き忘れると、どの社員を更新するのか分からないまま送信され、更新自体が効かない、あるいは意図しないレコードを更新してしまう不具合になります。画面に見えない値ほど、コードレビューで見落とされがちです。

7.7 削除（Delete）

削除は取り返しのつかない操作です。そのため、必ず確認画面を1枚挟み、実行は POST のみで受け付けるという2点を徹底します。

deleteConfirm.jsp — 確認画面（詳細から遷移、削除はまだ実行しない） 
<p>
    <bean:write name="employee" property="name" /> さんを削除します。
    よろしいですか？
</p>
<html:form action="/employee/delete">
    <html:hidden property="id" />
    <html:submit>削除する</html:submit>   <%-- POSTで送信 --%>
</html:form>
DeleteAction.java — 実行のみを担当 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    EmployeeForm employeeForm = (EmployeeForm) form;
    int id = Integer.parseInt(employeeForm.getId());  // 変換失敗時の扱いは7.4のDetailActionと同様
    // 論理削除フラグを立てるだけ（後述）。物理削除ならDELETE文を実行する
    new EmployeeDao().delete(id);
    return mapping.findForward("complete");  // 一覧へredirect（7.2参照）
}

削除の実装には、データを本当に消す物理削除と、削除フラグを立てるだけの論理削除の2種類があります。既存システムでは論理削除が採用されていることが多いので、必ず区別して読みましょう。

物理削除

DELETE FROM employee WHERE id = ?

行そのものがDBから消える。復元できない。関連する他テーブルの外部キー制約に注意。

論理削除

UPDATE employee SET delete_flag = 1 WHERE id = ?

行は残るが「削除済み」扱いになる。一覧・検索はWHERE delete_flag = 0を忘れないこと。

危険: GETリンクで削除を実行してはいけない

一覧の削除リンクを <html:link page="/employee/delete.do?id=..."> のようにクリックするだけで削除が実行される作りにしてはいけません。ブラウザのプリフェッチや検索エンジンのクローラがリンクを先読みするだけで削除が走ってしまう事故が実際に起きています。削除・更新のようなデータを変更する処理は、必ずPOSTで実行するのが鉄則です。今回のように確認画面を挟むことで、自然にPOST経由に矯正できます。

7.8 共通化と設計の勘所

6機能を作り終えると、機能をまたいで共通する処理が見えてきます。ここでは、既存の Struts 1 システムでも頻繁に使われる4つの共通化パターンを紹介します。第8章で他人のコードを読むときの前提知識になります。

① 共通の親Actionクラス

ログインチェックのように、ほぼ全画面で必要な処理は、Action を継承した親クラスにまとめ、各機能のActionはそれをさらに継承します。

BaseAction.java — ログインチェックを共通化 
public abstract class BaseAction extends Action {
    public final ActionForward execute(ActionMapping mapping, ActionForm form,
            HttpServletRequest request, HttpServletResponse response) throws Exception {
        if (request.getSession().getAttribute("loginUser") == null) {
            return mapping.findForward("login");  // 未ログインなら共通で弾く
        }
        return doExecute(mapping, form, request, response);  // 各機能はこちらを実装
    }
    // 個々のActionはexecute()ではなくこちらを実装する
    protected abstract ActionForward doExecute(ActionMapping mapping, ActionForm form,
            HttpServletRequest request, HttpServletResponse response) throws Exception;
}

ListAction などは extends BaseAction とし、execute() の代わりに doExecute() を実装するだけになり、ログインチェックを書き忘れる心配がなくなります。

② DispatchActionでCRUDを1クラスにまとめる

本ガイドでは学習のしやすさを優先し、機能ごとに Action クラスを分けました。しかし既存システムでは、org.apache.struts.actions.DispatchAction を使って1つのクラスにCRUDをまとめる書き方も非常によく見かけます。

EmployeeAction.java — DispatchActionの例（実務でよく見る形） 
public class EmployeeAction extends DispatchAction {
    // execute()の代わりに、パラメータ名と同じメソッド名が呼ばれる
    public ActionForward list(ActionMapping mapping, ActionForm form,
            HttpServletRequest request, HttpServletResponse response) throws Exception {
        request.setAttribute("employees", new EmployeeDao().findAll());
        return mapping.findForward("success");
    }
    public ActionForward delete(ActionMapping mapping, ActionForm form,
            HttpServletRequest request, HttpServletResponse response) throws Exception {
        new EmployeeDao().delete(Integer.parseInt(((EmployeeForm) form).getId()));
        return mapping.findForward("complete");
    }
}

struts-config.xml 側では parameter="method" を指定し、URLに ?method=delete のように渡すことで呼び分けます。クラス数は減りますが、1クラスが肥大化しやすいというトレードオフがあります。既存コードで extends DispatchAction を見かけたら、「呼ばれるメソッドはURLのパラメータで決まる」と思い出してください。

③ JSPの共通ヘッダー/フッター

6枚のJSPすべてに同じヘッダー・フッターを書くのは非効率です。JSPのディレクティブ includeで共通部分を切り出すのが最もシンプルな方法です。

list.jsp — 共通ヘッダー/フッターの取り込み 
<%@ include file="/common/header.jsp" %>
<h1>社員一覧</h1>
<%-- ここに一覧テーブル（7.3のコード）--%>
<%@ include file="/common/footer.jsp" %>

より大規模な既存システムでは、この共通レイアウトの仕組みをさらに発展させたTiles（画面をヘッダー・本文・フッターなどの部品に分けて組み立てる仕組み）が使われていることがあります。tiles-defs.xml のような設定ファイルを見かけたら、それが正体です。本ガイドでは扱いませんが、名前だけ覚えておくと既存プロジェクトの構成を見たときに戸惑いません。

④ global-forwardsによるエラー画面の共通化（再掲）

7.2 で定義した <global-forwards> の error も共通化の一種です。各Actionで例外が発生した際に個別の遷移先を用意しなくても、Struts のデフォルトの例外処理（第3章）や自作の共通例外処理からmapping.findForward("error") と書くだけで、全機能共通のエラー画面に遷移できます。

社員管理と同じ考え方を、別のマスタ「部署（department）」に当てはめてみましょう。ここでは一覧と登録の2機能ぶんを自分の手で設計します。答えを書き写すのではなく、7.2〜7.5 を見ながら自分の言葉で書き出すことが目的です。

理解度確認クイズ

  1. Q1. 登録処理で「トランザクショントークン」と「PRGパターン（redirect="true"）」を併用するのはなぜですか？

    回答を表示

    トランザクショントークンは「確認画面のフォームを2回送信した」場合の二重送信を検知して防ぎます。一方PRGパターンは、登録処理後の画面をリダイレクト表示にすることで、完了画面でのブラウザの再読み込みによるPOSTの再送信そのものを起きにくくします。原因が異なる2種類の二重送信に対応するため、両方を組み合わせるのが安全です。

  2. Q2. 更新処理で、DAOの update() が0件を返した場合、どう扱うべきですか？

    回答を表示

    画面を表示した後に、他のユーザーがその行を削除・変更した可能性があります。そのまま「更新成功」として扱わず、専用の画面（本章ではnotFound）へ遷移させ、ユーザーに再確認を促す必要があります。これは楽観的排他制御の考え方の入口です。

  3. Q3. 一覧の削除リンクを、クリックするだけで削除を実行するGETリンクにしてはいけないのはなぜですか？

    回答を表示

    GETリクエストはブラウザのプリフェッチやクローラの巡回などで、ユーザーの意図なしに送信されることがあります。データを変更する処理（登録・更新・削除）は必ずPOSTで実行し、削除のような重大な操作には確認画面を挟むことで、意図しない実行を防ぎます。

  4. Q4. DispatchAction を使う設計と、本章のように機能ごとにActionを分ける設計は何が違いますか？

    回答を表示

    DispatchAction はCRUDの各処理を1つのクラスの複数メソッド（URLのparameterで呼び分け）にまとめるため、クラス数は減りますが1クラスが肥大化しやすくなります。機能ごとにActionを分ける設計はクラス数が増える一方、1クラス1責務で見通しが良くなります。既存システムでは前者もよく使われるため、両方を読めるようにしておく必要があります。
