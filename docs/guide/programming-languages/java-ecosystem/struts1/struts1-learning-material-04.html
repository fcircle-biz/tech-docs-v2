ActionFormを理解する

第3章では Action の第2引数として ActionForm form が渡ってくることを見ました。この章では、その ActionForm がどうやって画面の入力値を受け取り、どこで入力チェックを行うのかを、社員管理画面を題材に一歩ずつ理解していきます。MVC の「Model」の一部を担う重要な部品です。

この章で学ぶこと

  • ActionForm が無い場合と比べて、何が楽になるのかを説明できる
  • HTML フォームの入力項目と ActionForm の getter/setter の対応ルールを理解する
  • reset() と validate() の役割を理解し、エラー時の画面遷移を追える
  • Action の中で ActionForm をキャストして値を取り出す定番コードを書ける

4.1 なぜActionFormが必要か

社員登録画面のように入力項目が複数あるフォームを Servlet だけで受け取ろうとすると、項目の数だけ request.getParameter() を呼び、文字列を必要な型に変換し、変換に失敗したときの処理まで自分で書く必要があります。まずは「ActionForm が無い世界」を見てみましょう。

Before: EmployeeServlet.java — 手作業での取得と変換 
// 登録画面の入力値を1つずつ手作業で取得・変換する
String name = request.getParameter("name");
String hireDateStr = request.getParameter("hireDate");
Date hireDate;
try {
    hireDate = new SimpleDateFormat("yyyy-MM-dd").parse(hireDateStr);
} catch (ParseException e) {
    // 変換に失敗した場合のエラー処理も自前で書く
    request.setAttribute("error", "入社日はyyyy-MM-dd形式で入力してください");
    request.getRequestDispatcher("/create.jsp").forward(request, response);
    return;
}
// ここまで書いて、やっと業務処理に入れる

項目が2つでもこの分量です。10項目ある画面を想像すると、うんざりする作業だと分かるはずです。ActionForm を使うと、この「取得して詰め替える」作業が肩代わりされます。

After: CreateAction.java — ActionFormが値を詰めてくれた後 
// ActionServletが既に値を詰め終えたEmployeeFormを渡してくれる
EmployeeForm employeeForm = (EmployeeForm) form;
String name = employeeForm.getName();
String hireDate = employeeForm.getHireDate();
// getterを呼ぶだけ。取得・変換の作業がそもそも登場しない

ActionFormが肩代わりしてくれる3つのこと

①画面の入力値をフィールドへ自動でセットする（getParameter()の連打が不要）。②入力チェック（validate()）の決まった置き場所を提供する。③エラー時に元の画面へ戻す仕組みと連動する。この3点を、この章で順番に見ていきます。

4.2 ActionFormクラスの書き方

ActionForm は org.apache.struts.action.ActionForm を継承した、ただの JavaBeans です。画面の入力項目ごとに private フィールド＋getter/setter を用意するだけで作れます。

EmployeeForm.java — 社員登録フォームのActionForm 
public class EmployeeForm extends ActionForm {
    // 画面のname属性と同じ名前でフィールドを用意する
    private String id;       // 更新・削除で使う社員ID（hiddenで受け取る）
    private String name;
    private String department;
    private String hireDate; // 日付項目だがStringで受ける（下のコラム参照）
    public String getId() { return id; }
    public void setId(String id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public String getDepartment() { return department; }
    public void setDepartment(String department) { this.department = department; }
    public String getHireDate() { return hireDate; }
    public void setHireDate(String hireDate) { this.hireDate = hireDate; }
}

ここで最も重要なルールは、HTML フォームの name 属性（Struts タグでは property 属性）と、setter メソッド名が対応するという点です。「JavaBeans 規約」と呼ばれるこの命名ルールに従わないと、値は一切セットされません。

画面側の指定 呼ばれるメソッド ActionForm側のフィールド
property="name" setName(String) name
property="department" setDepartment(String) department

型変換が必要な項目でも基本はStringで受ける

入社日（hireDate）のような日付項目でも、フィールドの型は Date ではなく String にするのが定石です。理由は単純で、入力欄が空文字のまま送信される可能性があるから。空文字を Date に変換（パース）しようとすると例外が発生します。日付への変換は validate() や Action 側で、入力チェックとセットで行うのが安全です。

既存システムで見かける DynaActionForm

現場のコードでは、Java クラスを一切書かず struts-config.xml の <form-property> だけでプロパティを定義する DynaActionForm という方式にも出会います。フィールド定義がすべて XML に書かれているだけで、値のセット・validate() の考え方はここまでの内容と同じです。「クラスが見当たらないのにプロパティが使える」と感じたら、struts-config.xml を確認してみてください。

4.3 <form-beans>への登録と<action>との結びつき

書いた ActionForm クラスは、そのままでは使われません。struts-config.xml の <form-beans> に「論理名（name）とクラス名（type）の対応」を登録して初めて、ActionServlet がインスタンスを作れるようになります。

struts-config.xml — form-beansの登録 
<!-- employeeFormを登録する（本ガイドでの<form-bean>初出） -->
<form-beans>
    <form-bean name="employeeForm" type="com.example.form.EmployeeForm"/>
</form-beans>

次に、<action> 側で「この URL にはどの form-bean を使うか」を name 属性で指定します。ここで指定する文字列は、<form-bean> の name と完全に一致している必要があります。

struts-config.xml — actionからemployeeFormを参照 
<action path="/employee/create"
        type="com.example.action.CreateAction"
        name="employeeForm"
        scope="session"
        validate="true"
        input="/create.jsp">
    <forward name="success" path="/employee/list.do" redirect="true"/>
</action>
属性 意味
name この<action>が使うform-beanの論理名。<form-bean>のnameと一致させる
scope ActionFormをどこに保持するか。request（1回限り）かsession（複数画面をまたぐ入力ウィザード等）
validate form.validate()を実行するかどうか。falseなら実行されない
input 入力チェックでエラーが出たときに戻る画面。validateがtrueなら必須

この一連の流れを図にすると、次のようになります。ActionForm は Action が動く前に、すでに値が入った状態で用意されているのがポイントです。

flowchart LR A["JSPのフォーム
employee/create.jsp"] -->|"送信"| B["ActionServlet"] B -->|"struts-config.xmlのnameを見てform-beanを特定"| C["EmployeeForm
（空のインスタンス）"] C -->|"setterで値をセット"| D["EmployeeForm
（値が入った状態）"] D -->|"第2引数formとして渡す"| E["CreateAction
execute()"]

4.4 値が自動でセットされる仕組み

ActionServlet は、リクエストパラメータの名前から 「set」＋先頭を大文字にした名前 というメソッド名を組み立てて、対応する setter をリフレクションで呼び出しています。難しく聞こえますが、やっていることは単純な文字列の変換です。

employee/create.jsp — 画面側（第5章で詳しく学びます） 
<%-- propertyの値とActionFormのsetter名が対応する --%>
<html:form action="/employee/create">
    <html:text property="name" />   <%-- setNameが呼ばれる --%>
    <html:text property="department" />   <%-- setDepartmentが呼ばれる --%>
    <html:submit value="登録" />
</html:form>
リクエストパラメータ名 呼ばれるメソッド
name setName("...")
department setDepartment("...")
対応するsetterが無いパラメータ 何も起きない（黙って無視される）

対応するsetterが無くてもエラーにならない

送信されたパラメータに対応する setter が ActionForm に存在しない場合、Struts はエラーを出さずに黙って無視します。これは「値が入らないのに、なぜかエラーも出ない」という不具合調査の定番の落とし穴です。値が入らないときは、まずproperty名とsetter名の綴りを疑ってください。

4.5 reset()の役割

reset() は、ActionServlet が setter を呼ぶ直前に毎回呼び出されるメソッドです。フィールドを初期値に戻す役割を持ちます。「setter が値をセットするなら、reset() は不要では？」と思うかもしれませんが、チェックボックスを考えると必要性が分かります。

HTML の仕様上、チェックボックスは「チェックが外れている」場合、そもそもパラメータ自体が送信されません。つまり setter が呼ばれないので、前回の値がフィールドに残ったままになってしまいます。特に scope="session" の場合、この問題が顕著に表れます。

EmployeeForm.java — reset()でチェックボックスを初期化 
public class EmployeeForm extends ActionForm {
    private boolean active;     // 在籍中（チェックボックス）

    @Override
    public void reset(ActionMapping mapping, HttpServletRequest request) {
        // 呼び出しごとに初期化。チェックが外れている場合は
        // setMailNotify()が呼ばれないため、ここでfalseに戻す
        this.active = false;
    }
    // getMailNotify() / setMailNotify() は省略
}

session scopeでの値の残留に注意

scope="session" の ActionForm は、リクエストをまたいで同じインスタンスが使い回されます。reset() を書き忘れると、「一度チェックを入れて送信 → 次にチェックを外して送信」しても、active が true のまま残る不具合が発生します。既存システムの原因不明のバグを調査するときは、この reset() の有無をまず確認してください。

4.6 validate()と入力チェック

値がセットし終わった後、<action> の validate="true"（省略時のデフォルトも true）であれば、ActionServlet は次に validate() を呼び出します。ここに入力チェックを書くのが Struts 1 の決まりです。

EmployeeForm.java — 必須チェックの実装 
@Override
public ActionErrors validate(ActionMapping mapping, HttpServletRequest request) {
    ActionErrors errors = new ActionErrors();
    // 社員名が空ならエラーメッセージのキーを追加する
    if (name == null || name.trim().length() == 0) {
        errors.add("name",
                new ActionMessage("error.name.required"));
    }
    return errors;
}

errors.add(プロパティ名, メッセージ) の第1引数は、どの項目のエラーかを示すキーです。第2引数の ActionMessage（Struts 1.1 以降）に渡している文字列は、実際のメッセージ本文そのものではなく、<message-resources> で指定したプロパティファイルのキーです。

ApplicationResources.properties — メッセージ本文 
# キー=メッセージ本文 の形式で1行ずつ定義する
error.name.required=社員名を入力してください。

validate() が返す ActionErrors が1件でも入っていると、Action の execute() は呼び出されず、代わりに <action> の input 属性で指定した画面へ自動的に差し戻されます。

flowchart TD A["EmployeeFormに値がセットされる"] --> B{"validateはtrueか？"} B -->|"いいえ"| E["Actionのexecute()を呼び出す"] B -->|"はい"| C["form.validate()を実行"] C --> D{"ActionErrorsは空か？"} D -->|"はい（エラーなし）"| E D -->|"いいえ（エラーあり）"| F["inputで指定した画面へ差し戻す"]

差し戻された画面では、<html:errors/> タグを使うとエラーメッセージを表示できます（詳しくは第5章）。また、Struts 1.0 系では ActionMessage の前身にあたる ActionError クラスが使われていました。ActionError を見つけたら、それは古い 1.0 系の書き方だと判断してください。なお ActionErrors は、Struts 1.1 で導入された汎用のメッセージ集約クラス ActionMessages（複数形）のサブクラスです。個々のメッセージはどちらも ActionMessage（単数形）として add() で追加します。

inputの指定忘れは実行時エラーの原因

validate="true" なのに input 属性を書き忘れると、エラーが発生した瞬間に「戻り先が分からない」状態になり、例外がスローされて画面が正しく表示されません。validate="true" の <action> を見たら、input がセットで存在するかを必ず確認する癖をつけましょう。

入力チェックの内容が複雑になると、validate() にすべて Java で書くのは大変です。Struts 1 には Validator フレームワークという仕組みもあり、validation.xml にルール（必須・桁数・書式など）を宣言的に書くことで、Java コードを書かずにチェックできます。既存システムで validation.xml を見かけたら、この仕組みが使われていると理解してください。

4.7 Actionの中でActionFormを使う

最後に、第3章で学んだ execute() の中で、ActionForm をどう扱うかを確認します。execute() の第2引数は ActionForm 型で受け取るため、自分が作ったクラスへキャストしてから使うのが定番です。

CreateAction.java — キャストして値をDTOへ詰め替える 
public ActionForward execute(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    // ActionFormをEmployeeForm型にキャストする
    EmployeeForm employeeForm = (EmployeeForm) form;

    // 値を取り出し、業務用のDTOに詰め替える（第6章でDBへ保存）
    Employee employee = new Employee();
    employee.setName(employeeForm.getName());
    employee.setDepartment(employeeForm.getDepartment());

    new EmployeeDao().insert(employee);
    return mapping.findForward("success");
}

この例では name・department ともに ActionForm と DTO で型が一致するため、そのまま getter/setter で受け渡せます。一方、4.2 で触れた入社日（hireDate）のように型が異なる項目（ActionForm では String、DTO では Date）を扱う場合は、受け取りは安全な String で、変換は validate() 済みの安心なタイミングで行うという役割分担のもと、Date への変換を Action 側などで用意する必要があります。

つまずきやすいポイント

ActionForm まわりの不具合は、既存システムの改修でも頻出します。代表的な5パターンを押さえておきましょう。

① getter/setter名の綴り違いで値が入らない

property="department" なのに setDepartmant()（typo）となっていると、対応するメソッドが見つからず値は無視されます。エラーも出ないため気付きにくい不具合です。

② <action>のnameと<form-bean>のnameの不一致

<form-bean name="employeeForm"> に対して <action name="employeForm">（1文字違い）のように書くと、struts-config.xml の解析時、または実行時に form-bean が見つからずエラーになります。

③ inputの未指定でエラー時に例外が発生する

4.6 で述べた通り、validate="true" なのに input を書き忘れると、入力エラー発生時に戻り先が特定できず実行時エラーになります。

④ session scopeでの値の残留（reset()忘れ）

4.5 で述べたチェックボックスの例のように、reset() が無いと scope="session" の ActionForm に前回値が残り続けます。

⑤ 数値・日付項目をintやDateで直接受けて変換エラーになる

フィールドを int や Date にしてしまうと、入力欄が空文字のまま送信された瞬間に NumberFormatException や ParseException が発生します。ActionForm のフィールドは基本 String で受けてください。

やってみよう 4-1: EmployeeFormに検索条件を追加する

第1章の検索フォームでは property="name" だけを検索条件として使っていました。この演習では、4.2 で作った EmployeeForm を土台に、部署（department）も条件に加えた検索フォーム用の validate() を書いてみます。

手順

  1. 1 4.2 の EmployeeForm を書き写し、id・name・department・hireDate の4つのプロパティに getter/setter が揃っていることを確認する（1つでも欠けると値が入らない）。
  2. 2 4.3 で示した <form-bean name="employeeForm" type="com.example.form.EmployeeForm"/> の定義を見直し、第1章の <action path="/employee/search" name="employeeForm" ...> が同じ EmployeeForm を指していることを確認する。
  3. 3 validate() をオーバーライドし、name と department が両方とも空文字の場合に ActionErrors へエラーを追加する入力チェックを実装する（4.6 の必須チェックの書き方を参考にする）。
  4. 4 <action path="/employee/search"> の validate="true" と input="/list.jsp" の組み合わせにより、検索条件が両方とも空のまま送信すると list.jsp へ差し戻される流れを頭の中でたどってみる。

理解度確認クイズ

  1. Q1. HTML フォームの name（Struts タグでは property）属性は、ActionForm のどのメソッドと対応しますか？

    回答を表示

    setter メソッドと対応します。例えば property="department" であれば setDepartment(String) が呼ばれます。対応する setter が存在しないパラメータは、エラーにならず黙って無視されます。

  2. Q2. チェックボックス項目を持つ ActionForm で reset() が必要なのはなぜですか？

    回答を表示

    チェックボックスは未チェック時にパラメータ自体が送信されないため、setter が呼ばれず前回の値がフィールドに残ってしまいます。reset() はsetterが呼ばれる直前に毎回実行されるため、ここで明示的に初期値へ戻す必要があります。特に scope="session" の場合に問題が顕著になります。

  3. Q3. validate() が空でない ActionErrors を返すと、処理はどこへ進みますか？

    回答を表示

    Action の execute() は呼び出されず、<action> の input 属性で指定された画面へ自動的に差し戻されます。そのため validate="true" の <action> には input の指定が必須です。

  4. Q4. ActionForm のフィールドを、数値や日付の項目でも int や Date ではなく String で受けるべき理由は何ですか？

    回答を表示

    入力欄が空文字のまま送信される可能性があり、それを直接 int や Date に変換しようとすると NumberFormatException や ParseException が発生するためです。ActionForm では String で安全に受け取り、validate() や Action の中で入力チェックとセットで型変換を行うのが定石です。
