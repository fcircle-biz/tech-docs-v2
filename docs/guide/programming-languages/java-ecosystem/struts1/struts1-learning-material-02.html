Struts 1の入口と設定

第1章では「画面 → .do → ActionServlet → struts-config.xml → …」という全体の流れを俯瞰しました。この章では、その最初の3ステップ——.do というURLの正体、web.xml による ActionServlet の登録、struts-config.xml の全体構造——を、実際の設定ファイルを読みながら理解します。

この章で学ぶこと

  • .do というURLが実ファイルではないことを説明できる
  • web.xml で ActionServlet がどう登録されているかを読める
  • struts-config.xml の4大要素（form-beans／global-forwards／action-mappings／message-resources）の役割を説明できる
  • <action> 要素の各属性（path・type・name・scope・validate・input）を1つずつ読める
  • URL から呼ばれる Action クラスを、設定ファイルだけで特定できる

2.1 リクエストの入口「.do」とは何か

Struts 1 のシステムを開くと、URL やフォームのあちこちに search.do や list.do のような .do 拡張子が出てきます。初めて見ると「.do というファイルがサーバのどこかにあるのだろう」と思ってしまいがちですが、これは誤りです。

.do は実在するファイルではない

.do は、サーバ上に置かれた .do という名前のファイルを指しているのではありません。「このURLはStrutsに処理を頼みます」という合図（拡張子マッピング）です。Webサーバ（Tomcat など）は、URL の拡張子が .do だったら、静的ファイルを探しに行くのではなくActionServletという1つのJavaクラスにすべて丸投げするよう設定されています。

これは JSP や画像ファイルの拡張子とは根本的に違う仕組みです。次の表で比較してみましょう。

拡張子 実体 サーバの動き
.jsp 実在するファイル（list.jsp など） 該当ファイルをコンパイル・実行して返す
.html／.png 実在する静的ファイル ファイルの中身をそのまま返す
.do 実在しない（合図でしかない） 拡張子だけを見て ActionServlet というServletを起動する

つまり /employee/search.do という URL を見たら、「search.do というファイルを探しに行く」のではなく、「Struts に search という機能の実行を頼んでいる」と読み替える習慣をつけてください。この読み替えができるようになることが、本章のゴールです。.do という拡張子自体に技術的な意味はなく、.action や .st など別の文字列に変更してもStrutsは動作します（次の2.2で、その変更点がどこにあるかを確認します）。

2.2 web.xmlにActionServletを登録する

「.do が来たら ActionServlet を起動する」という約束は、魔法ではなく Servlet の標準的な仕組み——web.xml の <servlet-mapping>——で実現されています。これは通常の Servlet を登録するときと全く同じ書き方です。

web.xml — ActionServletの登録 
<servlet>
    <servlet-name>action</servlet-name>
    <servlet-class>org.apache.struts.action.ActionServlet</servlet-class>
    <init-param>
        <param-name>config</param-name>
        <param-value>/WEB-INF/struts-config.xml</param-value>
    </init-param>
    <load-on-startup>2</load-on-startup>
</servlet>

<servlet-mapping>
    <servlet-name>action</servlet-name>
    <url-pattern>*.do</url-pattern>
</servlet-mapping>

1つずつ確認しましょう。要素ごとの役割を整理します。

要素 役割
<servlet-class> 起動するServletのクラス名。Struts本体が提供する org.apache.struts.action.ActionServlet を指定する（自分で書くクラスではない）
<init-param config> ActionServlet起動時に読み込む設定ファイルの場所。ここが /WEB-INF/struts-config.xml を指している
<load-on-startup> アプリ起動時（初回リクエストを待たず）にServletを初期化する順序。設定ファイルの読み込みを事前に済ませておくため、通常は小さい数値を指定する
<url-pattern>*.do</url-pattern> 「拡張子が .do のURLはすべてこのServletへ送る」という宣言。ここを *.action に変えれば、拡張子は .action になる

すべての .do は1つのServletに集まる

/employee/search.do も /employee/list.do も /order/create.do も、URLの見た目は違ってもTomcatから見るとすべて同じ1つのServletインスタンス（ActionServlet）へのリクエストです。「どの機能を呼ぶか」の振り分けは、Servlet自身ではなく、このあと読む struts-config.xml が担当します。この「入口は1つ、振り分けは設定ファイル」という構造が、Struts 1 のControllerの本体です。

2.3 struts-config.xmlの全体構造

struts-config.xml は、Struts アプリ最大の設定ファイルです。まずは全体の骨格だけを眺めて、「どこに何が書かれているファイルなのか」の地図を頭に入れましょう。

struts-config.xml — 全体の骨格 
<!DOCTYPE struts-config PUBLIC
    "-//Apache Software Foundation//DTD Struts Configuration 1.3//EN"
    "http://struts.apache.org/dtds/struts-config_1_3.dtd">
<struts-config>
    <form-beans>        <!-- ① 入力を受け取るActionFormの一覧 -->
    </form-beans>
    <global-forwards>   <!-- ② 全Action共通の遷移先 -->
    </global-forwards>
    <action-mappings>   <!-- ③ URLとActionの対応表（本体） -->
    </action-mappings>
    <message-resources parameter="resources.ApplicationResources" />
</struts-config>

<!DOCTYPE> 宣言があることにも注目してください。Struts 1 の設定ファイルはXMLの標準的な検証（DTD）を使っており、タグの綴りを間違えるとアプリ起動時にエラーで教えてくれます。直下の4要素の役割を表にまとめます。

要素 役割 詳しく学ぶ章
<form-beans> 画面の入力値を受け取る ActionForm クラスに、論理名（name）を付けて登録する場所 第4章
<global-forwards> ログイン画面・エラー画面など、複数のActionから共通に使う遷移先をまとめて定義する場所 第3章
<action-mappings> 本体。URL（path）と、呼び出すActionクラス（type）、遷移先の対応を1件ずつ <action> 要素で並べる場所 本章 2.4
<message-resources> 画面に表示するメッセージ（ラベル・エラー文言）をまとめたプロパティファイルの場所を指定する 第4章・第5章

4要素は書く順番が決まっている

DTDによって <form-beans> → <global-forwards> → <action-mappings> → <message-resources> という順序が決まっています。既存ファイルを読むときも、この順で探すと迷いません（本章では最重要の <action-mappings> を次節で深掘りします）。

2.4 <action>要素の属性を読む

<action-mappings> の中には、機能の数だけ <action> 要素が並びます。社員一覧の例で見てみましょう。

struts-config.xml — <action>要素の例 
<action path="/employee/list"
        type="com.example.action.ListAction"
        name="employeeForm"
        scope="request"
        validate="false"
        input="/list.jsp">
    <forward name="success" path="/list.jsp" />
    <forward name="error" path="/error.jsp" />
</action>

属性が多く見えますが、1つずつ意味を確認すればどれも単純です。

属性 意味
path この定義に対応するURL。/employee/list と書けば /employee/list.do にマッチする。先頭は必ず / から書く
type 呼び出すActionクラスの完全修飾名（パッケージ名込み）
name <form-beans> に登録したActionFormの論理名。このActionが使うフォームを指定する
scope ActionFormを保存する範囲。request（このリクエストだけ）か session（ログイン中ずっと）
validate true ならActionForm の validate()（入力チェック）を実行してからActionを呼ぶ
input 入力チェックでエラーになったときに戻る画面（validate="true" のときに使われる）
<forward name= path=> Action実行後の遷移先候補。Actionが mapping.findForward("success") のように論理名（name）で呼び出し、実際のJSPパス（path）はここで解決される

pathには.doを書かない

最も間違えやすいポイントです。path="/employee/list.do" のように .do まで書いてしまうと、実際のリクエストURL（/employee/list.do）と一致せず、該当するActionが見つからないエラーになります。.do はweb.xmlの <url-pattern> が既に処理してくれているので、struts-config.xmlの path には拡張子を除いた部分だけを書きます。

2.5 URLからActionが呼ばれるまで

ここまでの部品（web.xml・struts-config.xml）が、実際のリクエストでどう連携するのかを1本の流れとして図にします。第1章1.4の全体像のうち、③〜⑥、⑨のステップ（DAO・DBとのやり取りを除く、ActionServletからforward解決までの制御フロー部分）を拡大した図です。

flowchart TD A["ブラウザ
/employee/search.do にアクセス"] --> B["web.xml
url-pattern=*.do を確認"] B --> C["ActionServlet起動
（唯一の受付窓口）"] C --> D["struts-config.xmlを検索
path=/employee/search を照合"] D --> E["ActionForm生成
入力値をプロパティにセット"] E --> F["validate=trueなら
validate()で入力チェック"] F -->|OK| G["Action実行
type属性のクラス"] F -->|NG| H["input属性の画面へ戻す"] G --> I["forward名を解決
実際のJSPへ"]

この図の D（照合） が、まさに前節で読んだ <action path="..."> の役割です。「URLの文字列」と「struts-config.xmlのpath属性」が完全一致したときだけ、そのActionが呼ばれます。既存システムの調査で迷ったら、まずURLの.doより前の部分をコピーして、struts-config.xmlの中を path= で検索する——これが最短の追い方です。

RequestProcessorという裏方

実際には、ActionServletは自分ですべてを行うのではなく、RequestProcessor というクラスに照合・ActionForm生成・Action実行の処理を委譲しています。本ガイドでは「ActionServletが窓口、内部でRequestProcessorが実務を行う」程度の理解で十分です。名前だけ覚えておけば、ログやスタックトレースで見かけたときに戸惑いません。

2.6 ファイルの置き場所とライブラリ

最後に、ここまで登場した設定ファイルや必要なライブラリが、実際のWebアプリのどこに置かれているかを確認します。Struts 1 のアプリは、標準的なJava Webアプリのディレクトリ構成（WEB-INF 配下）に従います。

Struts 1アプリのディレクトリ構成 

webapp/
├── list.jsp
├── search.jsp
└── WEB-INF/
    ├── web.xml            ← ActionServletの登録（2.2）
    ├── struts-config.xml  ← Action対応表の本体（2.3〜2.4）
    ├── lib/                ← Struts本体一式（1.3では下記のように分割される）
    │   ├── struts-core.jar        （Struts 1.0〜1.2は struts.jar 1本）
    │   ├── struts-taglib.jar      （TLDはjar内META-INFに同梱。1.0のみWEB-INFへの個別配置が必要）
    │   └── commons-beanutils.jar
    └── classes/            ← コンパイル済みActionクラスなど
        └── com/example/action/ListAction.class

主な置き場所を表でも整理します。

場所 置かれるもの
WEB-INF/web.xml ActionServletの登録・URLパターン
WEB-INF/struts-config.xml Action対応表・ActionForm登録
WEB-INF/lib/*.jar Struts本体（1.0〜1.2は struts.jar 1本。1.3は struts-core.jar・struts-taglib.jar 等に分割）と依存ライブラリ（commons-beanutils・commons-digester など）
WEB-INF/classes/ 自作の Action・ActionForm・DAO のコンパイル済みクラス

ライブラリの分割はバージョンで異なる

本章のDOCTYPEはStruts 1.3のものですが、jarの構成はバージョンによって異なります。Struts 1.0〜1.2は struts.jar 1本にまとまった構成でした。Struts 1.3では機能ごとに struts-core.jar・struts-taglib.jar 等へ分割されています。なお .tld（タグライブラリ定義）は、第5章で扱う通りStruts 1.1以降はjar内の META-INF に同梱されるため、jarが1本でも分割されていても WEB-INF 直下への個別配置は不要です（個別配置が必要なのは1.0系のみ）。既存システムを調査するときは、WEB-INF/lib の中身を見れば、どの世代の構成かが判別できます。

つまずきやすいポイント

既存システムの読解・修正でよく足を止められる5つの落とし穴をまとめておきます。エラーに遭遇したら、まずここを疑ってください。

① pathに.doを書いてしまう

2.4で触れた通り、path="/employee/list.do" は誤り。path="/employee/list" が正しい書き方です。

② pathの先頭スラッシュを忘れる

path="employee/list" のようにスラッシュを書き忘れても、struts-config.xmlのDTDでは path は単なる文字列（CDATA #REQUIRED）として定義されているため、先頭スラッシュの有無は検証対象外でDTDでは検出されません。その分気づきにくく、実行時にリクエストURLと照合されず「該当する action が見つからない」エラーになります。path は必ず / から書きます。

③ typeのパッケージ名タイプミスでClassNotFoundException

type はJavaのクラス名を文字列として書くため、コンパイル時には検出されません。パッケージ名やクラス名を1文字でも間違えると、実行時に ClassNotFoundException になります。エラー発生時はこのクラス名と実際のクラスファイルの場所を突き合わせて確認します。

④ struts-config.xmlを直しても反映されない

struts-config.xmlはActionServletの起動時（初回）に1度だけ読み込まれます。修正後に画面をリロードしただけでは反映されず、アプリケーションサーバの再起動（またはWebアプリの再デプロイ）が必要です。「設定を直したのに変わらない」と感じたら、まず再起動を疑いましょう。

⑤ struts-config.xmlが複数ある（モジュール構成）

規模の大きい既存システムでは、<init-param> に config/admin・config/employee のような名前で複数の struts-config.xml（モジュール）が登録されている場合があります。目当ての <action> が1つのファイルに見つからないときは、web.xmlで他に config から始まるinit-paramが無いか確認してください。

やってみよう 2-1: 設定ファイルを読んでActionを特定する

以下の2つの抜粋だけを見て、/employee/list.do にアクセスしたときに実際に呼ばれるActionクラス名と最終的に表示されるJSPを答えてください。コードは実行せず、目で追う読解演習です。

web.xml（抜粋） 
<servlet-mapping>
    <servlet-name>action</servlet-name>
    <url-pattern>*.do</url-pattern>
</servlet-mapping>
struts-config.xml（抜粋） 
<action path="/employee/list"
        type="com.example.action.ListAction"
        name="employeeForm"
        scope="request"
        validate="false">
    <forward name="success" path="/list.jsp" />
</action>

手順

  1. 1 /employee/list.do の .do を除いた部分（/employee/list）をメモする。
  2. 2 struts-config.xmlの中で、同じ文字列が path= に書かれている <action> を探す。
  3. 3 見つけた <action> の type 属性がActionクラス、内側の <forward name="success"> の path が遷移先JSPになる。
答え合わせをする

呼ばれるActionクラスは com.example.action.ListAction、正常時に表示されるJSPは /list.jsp です。validate="false" なので入力チェックは行われず、そのままActionが実行されます。

理解度確認クイズ

  1. Q1. .do という拡張子のURLにアクセスすると、Tomcatは何を行いますか。

    回答を表示

    .do という名前のファイルを探すのではなく、web.xmlの <url-pattern>*.do</url-pattern> という設定に従って、拡張子だけを見て ActionServlet というServletを起動します。実際にどのActionを実行するかは、この後struts-config.xmlが決めます。

  2. Q2. web.xmlの <init-param> の config パラメータは何を指定していますか。

    回答を表示

    ActionServletが起動時に読み込む struts-config.xml の場所（通常は /WEB-INF/struts-config.xml）を指定しています。複数モジュール構成では config/xxx という名前で追加のstruts-config.xmlを指定することもあります。

  3. Q3. <action path="/employee/list.do" ...> という書き方が誤りである理由を説明してください。

    回答を表示

    .do はweb.xmlの url-pattern が既に処理する部分であり、struts-config.xmlの path には拡張子を除いたURLだけを書く必要があります。.do まで書いてしまうと実際のリクエストURLと一致せず、該当するActionが見つからないエラーになります。正しくは path="/employee/list" です。

  4. Q4. struts-config.xmlを修正したのに画面の動作が変わらないとき、まず何を疑うべきですか。

    回答を表示

    struts-config.xmlはActionServletの起動時に1度だけ読み込まれるため、修正後にアプリケーションサーバを再起動（またはWebアプリを再デプロイ）していない可能性を疑います。ブラウザの再読み込みだけでは設定変更は反映されません。
