JSPとStrutsタグ

第4章では、画面の入力値を受け取る ActionForm を学びました。本章はその逆方向——ActionForm や業務データを、どうやって画面（JSP）に表示するか——を扱います。JSP に直接 <% %> のスクリプトレットを書く代わりに使う「Struts タグライブラリ」の読み方を、実際のタグを1つずつ確認しながら身につけましょう。

この章で学ぶこと

  • Struts タグの3大ライブラリ（html・bean・logic）の役割を説明できる
  • html:text 等の property と ActionForm のプロパティの対応関係を理解する
  • bean:write と logic:iterate を組み合わせて一覧画面を実装できる
  • name 属性のスコープ探索順序（page → request → session → application）を理解する

5.1 Strutsタグライブラリとは

第1章で見たとおり、Servlet/JSP だけで作ると「JSP にスクリプトレットで DB アクセスや条件分岐を書いてしまう」という悩みが生まれます。Struts はこの悩みに対して、JSP の中でロジックを書かずに済むよう専用のカスタムタグを用意しました。それが Struts タグライブラリです。フォームの生成、値の出力、繰り返しと条件分岐——JSP で必要になる典型的な処理を、タグ1つで表現できます。

ライブラリ 主な役割 代表的なタグ
struts-html フォーム部品・リンク・エラー表示など画面部品の生成 html:form・html:text・html:submit・html:errors
struts-bean 変数（属性）の値を画面へ出力・定義する bean:write・bean:define・bean:message
struts-logic 繰り返し・条件分岐（if 相当）を表現する logic:iterate・logic:equal・logic:present

taglib宣言とtldファイル

Struts タグを使う JSP は、ファイルの先頭で taglib ディレクティブを宣言する必要があります。書き方は Struts のバージョンによって2通りあります。既存コードを読むときは、どちらの書き方でも戸惑わないようにしておきましょう。

list.jsp — taglib宣言（2つの書き方） 
<%-- Struts 1.0系: WEB-INF配下のtldファイルを直接指す --%>
<%@ taglib uri="/WEB-INF/struts-html.tld" prefix="html" %>

<%-- Struts 1.1以降: struts.jarに同梱されたtldをuriで参照 --%>
<%@ taglib uri="http://struts.apache.org/tags-html" prefix="html" %>
<%@ taglib uri="http://struts.apache.org/tags-bean" prefix="bean" %>
<%@ taglib uri="http://struts.apache.org/tags-logic" prefix="logic" %>

1.0 系の書き方では、.tld ファイルを WEB-INF/ 直下に配置し、web.xml の <taglib> 要素で uri と実ファイルを結びつけます。1.1 以降は struts.jar の中の META-INF/ に .tld が同梱されており、コンテナが自動的に見つけてくれるため、配置や web.xml への追記は不要です。既存プロジェクトでどちらの書き方かは、JSP の先頭を見れば一目で分かります。

prefixは自由に決められる

prefix="html" の部分は慣例であり、必須ではありません。ただし本ガイドを含め、現場のほぼすべてのコードが html・bean・logic という名前で統一しています。読み手を迷わせないため、この慣例に従いましょう。

5.2 htmlタグ（入力フォーム）

struts-html ライブラリの中心は、入力フォームを組み立てるタグ群です。第1章で見た <html:form action="/employee/search"> を思い出してください。action には struts-config.xml の <action> の path と同じ文字列をそのまま書きます。.do は書きません（Struts が自動的に付与します）。

create.jsp — 代表的なhtmlタグ 
<html:form action="/employee/create">
    <%-- propertyはEmployeeFormのgetName/setNameと対応 --%>
    氏名: <html:text property="name" size="20" />
    <%-- departmentListはActionがrequestに渡したCollection --%>
    部署: <html:select property="department">
        <html:options collection="departmentList"
                       property="value" labelProperty="label" />
    </html:select>
    <html:checkbox property="active" /> 在籍中
    <html:hidden property="id" />
    <html:submit value="登録" />
    <%-- validate()で追加されたエラーをまとめて表示 --%>
    <html:errors />
</html:form>

ここで最も重要な決まりごとは、property の値が ActionForm のプロパティ名（getter/setter）と一致していなければならないことです。property="name" であれば、ActionForm には getName()／setName() が存在している必要があります（第4章の内容そのものです）。さらに、画面を表示するときには、ActionForm が持っている値が自動的に入力欄の初期値として表示されます。入力チェックに失敗して同じ画面に戻ってきたとき、入力済みの値が消えないのはこの仕組みのおかげです。

flowchart LR F["EmployeeForm（ActionForm）
name / department / active"] -->|"画面表示時: 値をセット"| V["JSP
html:textのproperty"] V -->|"送信時: 入力値を格納"| F
タグ 用途
html:text 1行のテキスト入力欄
html:password パスワード入力欄（画面には値を表示しない）
html:select + html:options プルダウン。collection に渡したリストから選択肢を生成
html:checkbox 真偽値（boolean）プロパティに対応するチェックボックス
html:hidden 画面に表示せず値だけを送信する（例: 更新対象のID）
html:submit 送信ボタン
html:errors validate() が積んだ ActionErrors を一覧表示

5.3 beanタグ（値の出力）

入力フォームが「画面 → データ」の向きだとすれば、struts-bean は「データ → 画面」の向きを担当します。最もよく使うのが bean:write です。属性として保存されている JavaBean から、指定したプロパティの値を取り出して画面に出力します。

detail.jsp — bean:writeで値を出力 
<%-- Actionがrequestにセットしたemployee(JavaBean)からnameを取得 --%>
氏名: <bean:write name="employee" property="name" />
部署: <bean:write name="employee" property="department" />

<%-- filter="false"はHTMLエスケープを無効化する（原則使わない） --%>
備考: <bean:write name="employee" property="memo" filter="false" />

<%-- プロパティファイルからメッセージを取得する（国際化対応） --%>
<bean:message key="label.employee.name" />

name と property の違いを混同しないようにしてください。name は「スコープ内に保存されている属性の名前」（request.setAttribute("employee", ...) の第1引数に対応）、property は「その JavaBean が持つプロパティ名」（getName() に対応）です。

bean:writeは既定でHTMLエスケープされる

bean:write は、出力する値に < や > が含まれていても、既定で自動的に HTML エスケープします。これは XSS（クロスサイトスクリプティング）対策として非常に重要な挙動です。filter="false" を指定するとエスケープが無効になりますが、ユーザー入力を含む値に対しては原則として使ってはいけません。既存コードで filter="false" を見つけたら、なぜ無効化しているのかを必ず確認してください。

もう1つ、bean:define は既存の属性やプロパティから新しい変数（Bean）を定義するタグです。使用頻度は bean:write ほど高くありませんが、「同じ値を JSP 内で何度も参照したい」ときに使われます。既存コードで見かけたら「別名をつけて使い回している」程度に理解しておけば十分です。

5.4 logicタグ（繰り返しと条件）

一覧画面を作るとき、必ず登場するのが logic:iterate です。第1章の Action が request.setAttribute("employees", employees) で渡した List を、1件ずつ取り出しながら表示します。

list.jsp — logic:iterateで一覧表示 
<table>
<%-- name="employees"はrequest.setAttribute()の第1引数と一致させる --%>
<logic:iterate id="employee" name="employees" indexId="idx">
    <tr>
        <td><bean:write name="idx" /></td>
        <%-- idで宣言した1件分(employee)をbean:writeのnameに渡す --%>
        <td><bean:write name="employee" property="name" /></td>
        <td><bean:write name="employee" property="department" /></td>
    </tr>
</logic:iterate>
</table>
<logic:empty name="employees">
    該当する社員が見つかりません。
</logic:empty>

ポイントは id と name の役割分担です。name="employees" は「ループ元のリストがどの属性名で保存されているか」を指し、id="employee" は「ループ中の1件分（JavaBean）に付ける変数名」を指します。ループの中で <bean:write name="employee" ... /> と書くのは、この id の値を bean:write の name にそのまま渡しているからです。indexId を指定すると、0始まりの連番も一緒に取得できます。

条件分岐タグの使い分け

タグ 条件が成立するとき
logic:present 指定した属性・プロパティが存在するとき（ログイン済みかの判定などに使用）
logic:notPresent 属性・プロパティが存在しないとき
logic:empty コレクションや文字列が空（0件・null・空文字）のとき
logic:equal 値が指定した文字列と一致するとき（ステータスによる表示切替などに使用）

logic:equal は、name／property で指定した値と value が一致したときだけ本体を出力します。

detail.jsp — logic:equalで条件分岐 
<logic:equal name="employee" property="department" value="営業部">
    <strong>営業担当</strong>
</logic:equal>

logicタグはJavaのif/forに1対1で対応する

難しく考える必要はありません。logic:iterate は for、logic:equal・logic:present は if のタグ版だと考えれば、既存コードもJavaの制御構文として素直に読めます。

5.5 name属性はどのスコープを探すのか

bean:write や logic:iterate の name 属性は、Servlet のスコープのいずれかから属性を探しています。第3章で学んだ request / session に加えて、JSP には page（そのJSPページの中だけで有効）と application（アプリ全体で共有）もあり、4つのスコープが存在します。scope 属性を省略した場合、Struts タグは次の順番で属性を探します。

flowchart TD N["name属性で指定された
名前を探す"] --> P{"pageスコープに
あるか？"} P -->|Yes| Found["見つかった値を使用"] P -->|No| R{"requestスコープに
あるか？"} R -->|Yes| Found R -->|No| S{"sessionスコープに
あるか？"} S -->|Yes| Found S -->|No| A{"applicationスコープに
あるか？"} A -->|Yes| Found A -->|No| NotFound["見つからない（nullを返す）"]

scope="request" のように明示すれば、そのスコープだけをピンポイントで探させることもできます。重要なのは、この name の値は、Action が request.setAttribute()（または session.setAttribute()）でセットした名前と、文字どおり一致していなければならないということです。第3章の SearchAction の例を思い出してください。

SearchAction.java（第3章より抜粋）とJSPの対応 
// Action側: "employees"という名前でrequestに保存
List employees = new EmployeeDao().findAll();
request.setAttribute("employees", employees);
return mapping.findForward("success");

この "employees" という文字列と、JSP 側の <logic:iterate name="employees"> の "employees" が1文字でも違えば、値は見つからず一覧は空のまま表示されます。Action と JSP は別ファイルなのでコンパイルエラーにはならず、実行してみて初めて気づく典型的なミスです。

5.6 requestとsessionの使い分け

属性をどのスコープに置くかは、「その値を何画面分使い回すか」で判断します。基本方針はシンプルです。

スコープ 向いているデータ 具体例
request この1回の表示だけで使う一時的なデータ 一覧の検索結果、エラーメッセージ、入力フォームの選択肢
session 複数の画面をまたいで使い続けるデータ ログイン中ユーザー情報、権限、直前の検索条件

sessionに載せすぎない

一覧の検索結果のような「その場限りのデータ」まで session に置いてしまうと、①ユーザーごとにメモリを消費し続けてサーバーを圧迫する、②同じユーザーが別タブで別の検索をすると値が混線する、という2つの問題が起きます。「複数画面で本当に必要か？」を基準に、迷ったら request を選びましょう。

このスコープの方針は、第2章で学んだ <action> の scope 属性ともつながっています。scope は「ActionForm をどのスコープに保存するか」を決めるものでしたが、考え方は同じです。ActionForm 自体も、複数画面で入力を保持し続けたいときだけ session にし、それ以外は request にするのが基本です。

スクリプトレットが残っているコードとEL/JSTLについて

現場の既存 JSP には、Struts タグに置き換えられずに <% %> のスクリプトレットがそのまま残っているケースが少なくありません。読み方は Servlet の request／session のAPIそのものなので、これまでの知識で読み解けます。また、モダンな JSP でよく使われる EL 式（${...}）や JSTL（c:forEach 等）は、Struts 1.0 系が対象とする古い Servlet/JSP 仕様の環境では使えないことがあります。既存コードで見かけなくても不思議ではありません。

つまずきやすいポイント

Struts タグは書き方が独特なため、初めのうちは次のようなミスが起きがちです。エラーの症状とあわせて覚えておくと、既存コードのトラブルシューティングにも役立ちます。

① html:formのactionに.doまで書いてしまう

action="/employee/search.do" のように .do まで書いても、/employee/search.do.do のような二重拡張子にはならず404エラーにもなりません。Struts が内部で最後のドット以降を除去してから *.do を付け直すため、偶然そのまま動いてしまうことが多いのです。しかし struts-config.xml の path（/employee/search）と見た目が食い違い、読む人が対応関係を追えなくなります。規約として action には path と同じ文字列だけを書きましょう。

② propertyがActionFormに存在せず例外になる

property="deptName" のように書いても ActionForm に getDeptName() が無ければ、実行時に No getter method for property deptName のような例外が発生します。ActionForm 側のプロパティ名とスペルまで一致させてください。

③ logic:iterateのidとbean:writeのnameを取り違える

<logic:iterate id="employee" ...> の中で <bean:write name="employees" .../>（リスト全体の名前）を書いてしまう間違いです。ループ中の1件を指すのは id で宣言した employee の方です。

④ taglibのuriがtldファイルと合っていない

1.0系の書き方（/WEB-INF/struts-html.tld）と1.1以降の書き方（http://struts.apache.org/tags-html）が混在していると、JSPのコンパイルエラーになります。プロジェクト内のバージョンに合わせて統一されているか確認しましょう。

⑤ html:errorsを置き忘れてエラーが画面に出ない

validate() が ActionErrors を積んでも、JSP 側に <html:errors /> が無ければ画面には何も表示されません。「入力チェックしているはずなのに、無反応で同じ画面に戻るだけ」に見える不具合の定番原因です。

やってみよう 5-1: 社員一覧テーブルをlogic:iterateで書く

Action が request.setAttribute("employees", ...) で渡した社員一覧を、<logic:iterate> と <bean:write> を使ってテーブル表示するJSPを書いてみましょう。

手順

  1. 1 まず、Action 側が どの名前で リストを request に保存しているか（"employees"）を確認する。第3章の SearchAction を見返してもOK。
  2. 2 <table> を用意し、その中に <logic:iterate id="employee" name="employees"> で1行分の <tr> を繰り返す。
  3. 3 行の中で <bean:write name="employee" property="..."/> を使い、氏名・部署・入社日の3列を出力する。
  4. 4 テーブルの外側に <logic:empty name="employees"> を追加し、0件だった場合に「該当する社員が見つかりません」と表示できるようにする。

理解度確認クイズ

  1. Q1. <html:form action="/employee/search"> の action には何を書きますか？.do も書くべきですか？

    回答を表示

    struts-config.xml の <action> に定義された path（例: /employee/search）と同じ文字列を書きます。.do を書いても Struts が拡張子を除去してから *.do を付け直すため実際には動いてしまいますが、path と見た目が食い違い、読む人が対応関係を追えなくなります。規約として .do は書きません。

  2. Q2. <bean:write> で出力する値は、既定でHTMLエスケープされますか？されるとしたら何のためですか？

    回答を表示

    されます。既定でHTMLエスケープが行われるのは、ユーザーが入力した値をそのまま画面に出力してしまうと発生するXSS（クロスサイトスクリプティング）を防ぐためです。filter="false" を指定すると無効化できますが、ユーザー入力を含む値には原則使うべきではありません。

  3. Q3. <logic:iterate id="employee" name="employees"> の id と name は、それぞれ何を指しますか？

    回答を表示

    name はループ元のコレクションが保存されているスコープ内の属性名（例: Actionがrequest.setAttribute("employees", ...)で渡した名前）です。id はループ中の1件分のJavaBeanを指す変数名で、ループ内の bean:write の name にこの id をそのまま渡して各プロパティを出力します。

  4. Q4. name属性を省略した場合、Strutsタグはどの順序で属性を探しますか？

    回答を表示

    page → request → session → application の順に探し、最初に見つかったスコープの値を使用します。scope属性を明示すれば、そのスコープだけをピンポイントで探させることもできます。
