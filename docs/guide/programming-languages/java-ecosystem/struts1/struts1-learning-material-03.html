Actionを理解する

前章で、struts-config.xml が URL と Action クラスを結びつけていることを確認しました。この章では、その Action クラスの中身を掘り下げます。execute() の4つの引数の意味、ActionForward の探し方、JSP へのデータの渡し方、そして実務で必ず注意すべき「Action はスレッドセーフでなければならない」という原則まで、順番に理解していきます。

この章で学ぶこと

  • Action クラスの基本形（Action を継承し execute() をオーバーライドする書き方）を説明できる
  • execute() の4つの引数と戻り値 ActionForward の役割を理解する
  • mapping.findForward() の探索順序と redirect 属性の違いを説明できる
  • Action がスレッドセーフでなければならない理由を理解し、状態を持たせない書き方ができる

3.1 Actionクラスの基本形

Struts 1 の Action は、org.apache.struts.action.Action クラスを継承し、execute() メソッドをオーバーライドするだけの、実はとてもシンプルなクラスです。第1章で名前だけ登場した SearchAction を、最小の形で書き直すと次のようになります。

SearchAction.java — 最小構成のAction 
package com.example.action;

import org.apache.struts.action.*;
import javax.servlet.http.*;

// Actionを継承するだけで、Struts 1のController部品になる
public class SearchAction extends Action {

    // Struts 1.1以降はexecute()をオーバーライドする
    public ActionForward execute(ActionMapping mapping, ActionForm form,
            HttpServletRequest request, HttpServletResponse response)
            throws Exception {
        // "success"という論理名の行き先を返すだけ
        return mapping.findForward("success");
    }
}

覚えることは2つだけです。①org.apache.struts.action.Action を継承する、②execute() をこのシグネチャ通りにオーバーライドする。あとは中で業務処理を呼び出し、最後に「次はどこへ行くか」を ActionForward として返せば完成です。次節ではこの4つの引数を1つずつ見ていきます。

Actionは「呼ばれる側」であり、自分で new しない

Action のインスタンスを自分の Java コードから new SearchAction() のように生成することはありません。前章で学んだ ActionServlet が、struts-config.xml の type 属性を見て自動的に生成し、execute() を呼び出してくれます。

3.2 execute()の4つの引数

execute() の4つの引数は、どれも Struts 1 の内部で毎回自動的に用意され、渡されてくるものです。それぞれが「何の情報を持っているか」を対応表で整理します。

引数 型 何を表すか
mapping ActionMapping この Action の設定情報。struts-config.xml の <action> 要素の内容（path・forward 定義など）に対応
form ActionForm 画面の入力値が自動でセットされた入れ物。実際の型にキャストして使う（第4章で詳しく）
request HttpServletRequest 見慣れた Servlet のリクエストそのもの。setAttribute() で JSP にデータを渡す（3.5）
response HttpServletResponse レスポンスそのもの。Struts 1 では画面遷移を ActionForward に任せるため、直接使う場面は多くない

引数以外にも、押さえておきたい点が2つあります。戻り値は ActionForward 型で、「次はこの画面へ」という行き先の札です（3.4 で詳しく扱います）。そして throws Exception が宣言されているため、業務処理中に発生した例外を try-catch で握りつぶさず、そのまま投げてしまって構いません（3.6 で補足します）。

4つの引数は「4つの情報源」だと考える

既存の Action を読むときは、この4引数のうちどれを使っているかに注目すると理解が早まります。mapping を使っていれば設定と連動した処理、form を使っていれば入力値の処理、request を使っていれば画面へ渡すデータの処理だと見当がつきます。

3.3 execute()とperform()

既存の Struts 1 システムを読んでいると、execute() ではなく perform() というメソッドに出会うことがあります。これはバージョンの違いによるものです。

バージョン系列 メソッド名 現在の扱い
Struts 1.0系 perform() 1.1では非推奨（deprecated）ながらメソッド自体はまだ残っているが、1.2.0で削除されている
Struts 1.1以降 execute() 標準。今後書くコードは必ずこちら
OldSearchAction.java — 1.0系の古い書き方（読めれば十分） 
// Struts 1.0系の古い書き方（1.1で非推奨・1.2.0で削除済み）
public ActionForward perform(ActionMapping mapping, ActionForm form,
        HttpServletRequest request, HttpServletResponse response)
        throws IOException, ServletException {
    // 中身の考え方はexecute()とまったく同じ
    return mapping.findForward("success");
}

違いは throws 節だけです（perform() は IOException と ServletException、execute() は Exception 1本）。中で行っていること（mapping・form を使い、ActionForward を返す）はまったく同じなので、perform() に出会っても慌てず「execute() の古い名前」として読めば問題ありません。

perform()呼び出しはStruts 1.1限定の互換措置

Struts 1.1では、Action クラスが提供するデフォルトの execute() 実装が後方互換のために内部で perform() を呼び出す作りになっているため、perform() だけをオーバーライドした古いコードもそのまま動作します。ただし perform() は Struts 1.2.0で削除されており、1.2/1.3環境ではこの仕組み自体が存在しません。perform() だけを実装したクラスは、デフォルトの execute() が何もせず null を返すだけになるため呼び出されず、1.2以降へ上げる際は execute() への書き換えが必要です。

3.4 ActionForwardとmapping.findForward()

Action が返す ActionForward は、"success" のような論理名と、struts-config.xml に書かれた <forward> 要素の name 属性を突き合わせて決まります。mapping.findForward("success") は、この突き合わせを行うメソッドです。

forwardの探索順序

findForward() は、まずその Action 自身の <action> 要素内を探し、見つからなければ全 Action 共通の <global-forwards>を探します。

探索順 定義場所 優先度
① <action> 要素内の <forward> 最優先。見つかれば即採用
② <global-forwards> 内の <forward> ①に無い場合のみ探索される
flowchart TD A["① Action.execute()
ActionForwardを返す"] --> B["② mapping.findForward(success)"] B --> C{"③ action内にforward定義があるか"} C -->|"ある"| D["④ action内のforward
name=success"] C -->|"ない"| E["④ global-forwards内のforward
name=success"] D --> F["⑤ forwardのpath属性"] E --> F F --> G["⑥ 実際のJSP"]

forwardとredirectの違い

<forward> 要素には redirect="true" という属性を付けられます。指定の有無で挙動がまったく変わるため、必ず区別して読めるようにしてください。

項目 forward（デフォルト） redirect="true"
仕組み サーバー内部で RequestDispatcher.forward() クライアントへ HTTP 302 を返し、ブラウザに再リクエストさせる
URL 変わらない（.do のまま） 遷移先の URL に変わる
request属性 引き継がれる（同じリクエスト） 消える（新しいリクエストになる）
主な用途 通常の一覧・検索結果表示 登録・更新後の二重送信防止（PRGパターン）

redirectは第7章のPRGパターンで再登場します

「登録ボタンを押したあとにブラウザの更新ボタンを押すと、もう一度登録されてしまう」問題を防ぐために redirect="true" を使う実装パターン（Post/Redirect/Get、通称 PRG）を、第7章の CRUD 実装で扱います。ここでは「URLが変わる＝request属性が消える」という副作用だけ覚えておいてください。

3.5 JSPへデータを渡す

Action で取得した業務データを JSP へ渡す最も基本的な方法は、Servlet でおなじみの request.setAttribute() です。第1章で先取りした社員検索の例を、もう一度見てみましょう。

SearchAction.java — requestスコープでデータを渡す 
// 業務処理を実行し、結果をJSPへ渡す
List employees = new EmployeeDao().findAll();
request.setAttribute("employees", employees);   // requestスコープに格納
return mapping.findForward("success");

JSP 側では、この "employees" という名前（属性名）で値を取り出します。属性名は Action 側と JSP 側で一字一句一致させる必要があるため、既存コードを読むときはまず Action の setAttribute() の文字列を確認し、JSP 側で同じ文字列を検索するのが定石です（JSP 側の具体的な書き方は第5章）。

requestスコープとsessionスコープの使い分け

データの「生存期間」によって、置き場所（スコープ）を使い分けます。

スコープ 生存期間 使う場面
request このリクエスト～フォワード先 JSP まで 検索結果一覧など、その場限りで使い終わるデータ
session ログインからログアウトまで（複数リクエストにまたがる） ログインユーザー情報など、複数画面で使い回すデータ
LoginAction.java — sessionスコープに置く例 
// ログインユーザー情報は複数画面で使うのでsessionへ
HttpSession session = request.getSession();
session.setAttribute("loginUser", user);
return mapping.findForward("success");

redirectするとrequest属性が消える

3.4 で見た通り、redirect="true" のフォワードは新しいリクエストになるため、request.setAttribute() で渡したデータは遷移先 JSP から見えません。redirect 先でもデータを表示したい場合は session スコープに置くか、URL パラメータとして渡す必要があります。

3.6 Actionを書くときの注意点

最後に、Action を書く（あるいは既存の Action を直す）ときに必ず押さえておくべき原則を4つ紹介します。特に最初の1つは、Struts 1 の Action を扱ううえで最も重要な注意点です。

① Actionのインスタンスは1つだけ・共有される

ActionServlet は、1つの Action クラスにつきインスタンスを1つだけ生成し、以後すべてのリクエストでそれを使い回します（Servlet 自体が使い回されるのと同じ考え方です）。つまり、複数のユーザーが同時にアクセスすると、同じ Action インスタンスに複数のスレッドが同時に入り込みます。

BadSearchAction.java — やってはいけない例 
public class BadSearchAction extends Action {
    private String name;   // NG: インスタンス変数に入力値を保持

    public ActionForward execute(ActionMapping mapping, ActionForm form,
            HttpServletRequest request, HttpServletResponse response)
            throws Exception {
        name = request.getParameter("name"); // 他のリクエストと値が混ざる危険
        return mapping.findForward("success");
    }
}

このコードでは、ユーザーAとユーザーBがほぼ同時に検索すると、name フィールドの値が上書きされ合い、Aの検索結果画面にBの検索条件が表示されるといった事故が起こり得ます。Action にはインスタンス変数で状態を持たせず、必要な値はすべてローカル変数・引数（request／form）から取得するのが鉄則です。

② 業務ロジックはService/DAOに置き、Actionは薄く保つ

Action の役割は「入力を受け取り、業務処理を呼び出し、遷移先を返す」という橋渡しです。SQL の組み立てや複雑な計算ロジックまで Action に書き込んでしまうと、テストしづらく見通しの悪いクラスになります。DB アクセスは第6章で学ぶ DAO に、複雑な業務ルールは Service 層に切り出し、Action はそれらを呼び出すだけの薄い層に保ちましょう。

③ 例外処理はglobal-exceptionsに任せられる

execute() は throws Exception なので、業務処理で発生した例外を Action 内で無理に catch する必要はありません。struts-config.xml の <global-exceptions> 要素に共通のエラーハンドラを設定しておけば、投げっぱなしにした例外を Struts 側でまとめて捕まえ、エラー画面へ振り分けられます（詳細な設定方法は本ガイドの範囲外ですが、既存コードで見かけたら「共通の例外処理場所」と理解してください）。

④ 1クラスに複数メソッドを持たせるDispatchAction

「一覧」「検索」「削除」のように似た機能ごとに Action クラスを量産すると、クラス数が膨大になりがちです。現場では、1つのクラスに複数のメソッドをまとめられる DispatchAction がよく使われます。

DispatchActionはparameter属性でメソッドを振り分ける

org.apache.struts.actions.DispatchAction を継承すると、<action> 要素の parameter 属性で指定した値（例: method=list）を見て、同名のメソッド（list()）を自動的に呼び出してくれます。execute() は自分で書かず、list()・search()・delete() のように機能ごとのメソッドを並べる形になります。既存コードで extends DispatchAction を見かけたら、この仕組みを思い出してください。

つまずきやすいポイント

Action まわりで実際によく起きるトラブルを4つまとめました。既存コードの不具合調査や、自分でコードを書く際のチェックリストとして使ってください。

findForwardの名前がstruts-config.xmlと一致せずnullが返る

mapping.findForward("sucess") のように name をタイプミスすると、探索に失敗して null が返ります。null を return した Action は、Struts が遷移を行わず白画面（空レスポンス）になります。文字列は Java と XML の両方に同じスペルで登場するため、片方だけ直して直し忘れる事故が起きがちです。

execute()がnullを返すと遷移が起きない（白画面）

なお execute() の一部の分岐で return 文を書き忘れることはできません。戻り値のあるメソッドで return を欠く経路があると Java のコンパイルエラーになるためです。一方 execute() が null を返すこと自体は「レスポンスは Action 側で処理済み」という合図として使える正当な仕様です。ただし findForward() が名前を見つけられずに返した null を、意図せずそのまま return してしまうと、例外は発生せず遷移が行われず白画面（空レスポンス）になります。

Actionにフィールドを持たせて値が混ざる

本節①で見た通り、Action インスタンスは共有されます。既存コードで不可解な「他人のデータが表示される」バグを見つけたら、まず Action クラスにインスタンス変数（フィールド）が定義されていないか疑ってください。

redirectした後にrequest属性が読めない

3.5 の警告でも触れた通り、redirect="true" の先では request.setAttribute() のデータが消えています。「一覧画面に登録直後のメッセージが表示されない」といった不具合の多くは、これが原因です。

やってみよう 3-1: 遷移条件を自分で書き出す

次の <action> 定義を読んで、「どの条件でどの JSP に遷移するか」を自分の言葉で書き出してみましょう。

struts-config.xml — 演習用の設定 
<action path="/employee/update"
        type="com.example.action.UpdateAction"
        name="employeeForm"
        scope="request"
        input="/update.jsp">
    <forward name="success" path="/employee/list.do" redirect="true" />
    <forward name="failure" path="/error.jsp" />
</action>

手順

  1. 1 この設定に対応する UpdateAction の execute() を、更新が成功したら "success"、失敗したら "failure" を返す形で自分で書いてみる。
  2. 2 "success" 側の redirect="true" に注目し、「なぜここだけ redirect にしているのか」を3.4の内容を踏まえて説明してみる。
  3. 3 更新失敗時に /error.jsp へ渡したいエラーメッセージを、どのスコープの setAttribute() で渡せばよいか考える（redirectしないので request でよいか、それとも session が必要か）。
  4. 4 （担当システムがある場合）実際の Action ファイルを1つ開き、execute() または perform() がどちらを使っているか、インスタンス変数が定義されていないかを確認する。

理解度確認クイズ

  1. Q1. execute()の4つの引数のうち、struts-config.xmlの<action>要素の設定情報に対応するのはどれですか？

    回答を表示

    ActionMapping mapping です。この Action に対応する <action> 要素の内容（path や forward 定義など）を保持しており、mapping.findForward() の探索元にもなります。

  2. Q2. perform()とexecute()の違いは何ですか？既存コードでperform()を見つけたらどう読み替えればよいですか？

    回答を表示

    perform() は Struts 1.0系のメソッド名で、1.1以降は execute() が標準です。1.1 では execute() の既定実装が perform() を呼ぶため古いコードもそのまま動きますが、perform() は Struts 1.2.0 で削除されたため、1.2/1.3 環境では execute() への書き換えが必要です。throws節（perform()はIOException/ServletException、execute()はException）以外に処理の考え方の違いはなく、中で行うこと（mapping・formを使い、ActionForwardを返す）は同じなので、読むときは「execute()の古い名前」として読めば問題ありません。

  3. Q3. mapping.findForward("success")が探索する場所の優先順位を説明してください。

    回答を表示

    まず呼び出し元の <action> 要素内に定義された <forward name="success"> を探し、見つかればそれを採用します。見つからない場合のみ <global-forwards> 内の同名 forward を探します。どちらにも無ければ null が返り、それをそのまま return すると遷移が行われず白画面（空レスポンス）になります。

  4. Q4. Actionのインスタンス変数に検索キーワードなどの状態を保存してはいけないのはなぜですか？

    回答を表示

    ActionServletは各Actionクラスにつきインスタンスを1つだけ生成し、すべてのリクエストで使い回すためです。複数ユーザーが同時にアクセスすると同じインスタンスに複数スレッドが入り込むため、インスタンス変数に状態を持たせるとリクエスト間で値が混ざります。状態はローカル変数や引数（request・form）から取得し、Actionをスレッドセーフに保つ必要があります。
