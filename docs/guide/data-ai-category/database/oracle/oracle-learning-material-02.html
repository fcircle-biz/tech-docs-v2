アーキテクチャと基本用語

前章では「Oracle Database とは何者か」という大きな地図を確認しました。本章ではもう一歩踏み込んで、Oracle の内部がどのような部品で組み立てられているかを見ていきます。「インスタンス」「SGA」「表領域」「CDB」「PDB」など、聞き慣れない言葉が次々と出てきますが、どれも身近な比喩を添えながら一つずつ丁寧に説明します。ここで覚える FREEPDB1 という名前は、第3章で実際に接続文字列として入力することになる大切なキーワードです。まだ手は動かしませんが、この章を読み終えると次章の作業でつまずきにくくなります。

この章で学ぶこと

  • インスタンスとデータベースの違いを、比喩を使って説明できる
  • SGA・PGA・バックグラウンドプロセス・データファイル・REDOログ・制御ファイルの役割を1行ずつ言える
  • CDB / PDB（マルチテナント）の関係を図で説明でき、FREEPDB1 が何であるかを答えられる
  • 表領域・セグメント・エクステント・ブロックという記憶域の階層と、リスナー／サービス名の役割を説明できる

2.1 インスタンスとデータベースは別物

Oracle を学び始めた人が最初につまずく言葉の壁が、この節のテーマです。日常会話では「データベースを再起動する」のように何気なく使ってしまいますが、Oracle の世界ではインスタンスとデータベースは明確に別のものを指します。この違いを最初に押さえておくと、この先の節がぐっと理解しやすくなります。

厨房＝インスタンス

お店を開けている間だけ動く「作業中の場」。コンロも作業台もそこにありますが、閉店して片付ければ跡形もなく消えます。

食材倉庫＝データベース

建物として存在し続ける保管庫。お店が閉まっている間も、食材（データ）はそのまま倉庫に残っています。

データベースとは、ディスク上に保存されている実体のファイル群そのものです。表のデータや設定情報が、何もしなければそのままの形で保存され続けます。一方インスタンスとは、そのファイル群を実際に扱うために Oracle がメモリ上に確保した作業場と、そこで働く裏方のプログラム群のことです。インスタンスは Oracle を起動したときに作られ、停止すればメモリごと消えてしまいます。

観点 インスタンス データベース
実体 メモリ領域＋裏方プログラム（プロセス） ディスク上のファイル群
存在する場所 サーバーのメモリ（RAM） サーバーのディスク（ストレージ）
電源を切ると 消える（次の起動時に作り直される） 残る（ディスク上にそのまま存在）

つまずきポイント: 「Oracle を再起動した」＝データが消えたわけではない

サーバーを再起動すると、正しくはインスタンスが作り直されるだけです。厨房を一度片付けてまた開店するようなもので、食材倉庫（データベース）の中身は影響を受けません。次に起動したときには、後述する REDOログを使って、中断した時点の状態まで自動的に復旧されます。

2.2 メモリ構造: SGAとPGA

インスタンスの正体である「メモリ上の作業場」には、性格の異なる2種類の領域があります。厨房の比喩で言うと、誰でも使える共有の作業台と、シェフ1人ひとりが使う手元の作業スペースです。前者を SGA（System Global Area / インスタンスに接続した利用者全員で共有するメモリ領域）、後者を PGA（Program Global Area / 接続してきた利用者ごとに割り当てられる専用の作業メモリ）と呼びます。

たとえば、ある利用者が実行した SQL の並べ替え作業の一時的な計算領域は PGA（自分専用）に置かれますが、一度解析した SQL 文の解析結果は SGA（共有の棚）に置かれ、他の利用者が同じ SQL を実行したときに使い回されます。まずは「SGA ＝ みんなの共有スペース」「PGA ＝ 自分専用のスペース」という大枠だけ覚えておけば十分です。

SGA の中身は多岐にわたりますが、初心者がまず知っておきたいのは次の3つです。

バッファキャッシュ

よく使うデータを載せておく「机の上」。ディスクまで取りに行かずに済むので読み書きが速くなります。

共有プール

一度解析したSQL文の解析結果を使い回す「棚」。同じSQLが来たら、また一から解析し直さずに済みます。

REDOログバッファ

変更内容をいったん書き留めておく「伝票の一時置き場」。あとでREDOログファイルへまとめて転記されます。

重要ポイント

SGA・PGA の中身を全部暗記する必要はありません。「変更はまずメモリ上で処理され、あとでディスクに反映される」という大まかな流れと、「共有か専用か」という区別だけ持ち帰ってください。次の節で、この「あとでディスクに反映する」作業を実際に行う裏方たちを紹介します。

2.3 バックグラウンドプロセス（裏方の仕事分担）

インスタンスの中では、バックグラウンドプロセス（利用者からは見えないところで休みなく働く、常駐の裏方プログラム群）が役割分担をしながら動いています。厨房で言えば、皿洗い係・記録係・見回り係のような専門スタッフです。代表的な5つを紹介しますが、全部を暗記する必要はありません。「それぞれ担当が決まっている」という考え方さえ分かれば十分です。

プロセス 正式名 役割（たとえ）
DBWn Database Writer 机の上（バッファキャッシュ）の変更を、頃合いを見てディスクのデータファイルへ書き戻す
LGWR Log Writer 伝票（REDOログバッファ）の内容を、REDOログファイルへ書き込む
CKPT Checkpoint 「ここまでは確実にディスクへ書いた」という区切りの印を付ける
SMON System Monitor 異常終了後の後片付け・復旧作業を自動で行う
PMON Process Monitor 異常切断した利用者の後片付け（ロックの解除など）を行う

ここまでの「インスタンス（メモリと裏方プロセス）」と、これから見ていく「データベース（ディスク上のファイル）」の関係を図にまとめると、次のようになります。DBWn がデータファイルへ、LGWR が REDOログファイルへ、それぞれ書き込み先を持っていることに注目してください。

flowchart TB subgraph INST["インスタンス（メモリ＋プロセス）"] BC["バッファキャッシュ"] SP["共有プール"] RLB["REDOログバッファ"] DBWN["DBWn"] LGWR["LGWR"] end subgraph DBFILES["データベース（ディスク上のファイル）"] DF["データファイル"] RLF["REDOログファイル"] CF["制御ファイル"] end DBWN -->|書き戻す| DF LGWR -->|書き込む| RLF

図の下段に出てきた「データファイル」「REDOログファイル」「制御ファイル」が、まさに次の節のテーマです。

2.4 物理ファイルの三種

データベース（ディスク上のファイル群）は、大きく3種類のファイルで構成されています。それぞれ「何が書いてあるか」「誰が書き込むか」が異なります。

ファイル種類 何が書かれているか 誰が書き込むか
データファイル 表や索引の実データそのもの（食材倉庫の中身） DBWn
REDOログファイル 「何をどう変更したか」の変更履歴。障害時の復旧に使う LGWR
制御ファイル データベースの構成情報を持つ「目次」。どのデータファイル・REDOログファイルが存在するかを記録 Oracle本体（複数プロセスが更新）

REDOログファイルは「変更の日記」だとイメージしてください。何か変更が起きるたびに、その内容が時系列で書き留められます。障害でデータファイルの一部が壊れても、直前のバックアップとこの日記を組み合わせれば、失われた変更を再現できます。制御ファイルはデータベース全体の「目次」で、これが壊れるとどのファイルを読めばよいか分からなくなってしまうため、非常に重要なファイルです。この3種のファイルは、第14章のバックアップと復旧で再び登場します。

2.5 記憶域の階層とスキーマ

先ほどの「データファイル」は、あくまで OS から見たファイルの単位です。Oracle は自分のデータを、データファイルの中でさらに入れ子構造に整理しています。倉庫の比喩で言うと「倉庫 → 棚 → 段ボール箱 → 仕切り」のようなイメージです。

用語 倉庫のたとえ 説明
表領域（TABLESPACE） 倉庫そのもの 表や索引を格納する論理的な入れ物。1つ以上のデータファイルによって実現される
セグメント 倉庫内の棚 1つの表や索引が実際に使う領域のまとまり
エクステント 棚の上の段ボール箱 連続した領域のかたまり。セグメントが足りなくなると新しく追加される単位
データブロック 箱の中の仕切り Oracle が読み書きする最小の単位
flowchart TD A["表領域（TABLESPACE）
例: USERS"] --> B["セグメント
例: employees表の実データ"] B --> C["エクステント
連続した領域のかたまり"] C --> D["データブロック
Oracleが読み書きする最小単位"]

では「誰の表がどの倉庫に入るか」を決めるのは何でしょうか。それがスキーマ（あるユーザーが所有する表・索引などのオブジェクトのまとまり）です。Oracle ではユーザー名＝スキーマ名という原則があり、たとえば hr というユーザーが作った表は「hr スキーマの表」と呼ばれます。本ガイドで作る学習用ユーザー hr が表を作ると、既定では USERS という名前の表領域（倉庫）にしまわれます。スキーマの詳しい作成方法は第5章で扱います。

2.6 CDBとPDB（マルチテナント構成）

Oracle 12c 以降、データベースはマルチテナントという構成が標準になりました。1つの建物の中に、独立した部屋がいくつも入っているイメージです。建物全体を CDB（Container Database / コンテナデータベース）、その中の1つ1つの部屋を PDB（Pluggable Database / プラガブルデータベース）と呼びます。共通設備（管理の仕組みなど）は建物全体で共有しつつ、各部屋のデータはきちんと分離されている、という構成です。

CDB$ROOT

建物全体の共通の土台。Oracle 自身の管理用データ（カタログ）を持つ場所で、業務データは置かない。

PDB$SEED

新しい部屋（PDB）を作るための「読み取り専用の雛形」。ここにも業務データは置かない。

FREEPDB1

Oracle Database Free の既定のPDB名。私たちの業務データ（表など）はここに作る。

本ガイドで使う Oracle Database 23ai Free では、CDB の名前が FREE、既定で用意される PDB の名前が FREEPDB1 です。この関係を図にすると次のようになります。私たちが第5章で作る hr ユーザーとその表（employees・departments）は、すべて FREEPDB1 の中に置かれます。

flowchart TD CDB["CDB「FREE」
共通の土台"] --> ROOT["CDB$ROOT
共通メタデータ"] CDB --> SEED["PDB$SEED
新規PDBの雛形（読み取り専用）"] CDB --> PDB1["FREEPDB1
ここに業務データを作る"] PDB1 --> HR["hrユーザー（スキーマ）"] HR --> T1["employees表"] HR --> T2["departments表"]

実務でも起きる鉄則違反: CDB$ROOTに接続したまま作業してしまう

業務データは必ず PDB（本ガイドでは FREEPDB1）の中に作ります。うっかり CDB$ROOT に接続したまま表を作ろうとすると、意図しない場所にオブジェクトができてしまったり、権限エラーで弾かれたりします。接続するときは「今つながっている先が FREEPDB1 かどうか」を必ず確認する習慣を、次の節と第3章で身につけます。

今どのコンテナ（CDBのルートか、それともどのPDBか）に接続しているかは、次のコマンドで確認できます。実際に手元で実行するのは第4章からですが、「こういうもので確認する」ということだけ先に知っておきましょう。

SQL*Plus（今のコンテナを確認する） 
-- 今つながっているコンテナ（CDBのルートかPDBか）を表示する
SHOW CON_NAME

-- SQLでも同じことが確認できる
SELECT SYS_CONTEXT('USERENV', 'CON_NAME') AS "現在のコンテナ" FROM dual;

管理者権限を持つユーザーであれば、CDB の中にどんな PDB が存在するかも一覧できます。OPEN_MODE が READ WRITE になっていれば、そのPDBは使える状態です。

SQL*Plus（PDB一覧・管理者ユーザーで実行） 
-- CDBに含まれるPDBの一覧。OPEN_MODEがREAD WRITEなら使える状態
SELECT name, open_mode FROM v$pdbs;

2.7 接続の仕組み（リスナーとサービス名）

最後に、SQL*Plus や SQL Developer から Oracle にどうやって「たどり着く」のかを見ておきましょう。手元のパソコンから見ると、Oracle は電話番号のようなものでつながります。まずクライアントは リスナー（Listener / 接続要求を受け付ける、いわば受付係のプログラム。既定では ポート1521 で待ち受けています）に電話をかけ、次に「どの部屋につないでほしいか」を サービス名（Service Name / 接続したい PDB の名前）で伝えます。リスナーはその名前を聞いて、正しい PDB へ取り次いでくれます。

この一連の情報をひとまとめにした書き方が Easy Connect 記法です。「ユーザー名 / パスワード ＠ ホスト : ポート / サービス名」という順番で並べます。実際に第3章で入力する接続コマンドを、先取りして分解してみましょう。

SQL*Plus（接続文字列の読み方） 
-- 接続文字列の読み方
-- sqlplus  hr / パスワード @ localhost : 1521 / FREEPDB1
--          ↑ユーザー  ↑     ↑ホスト   ↑ポート  ↑サービス名(PDB名)
sqlplus hr/MyPassword1@localhost:1521/FREEPDB1

localhost は「自分のパソコン自身」を指す特別な名前、1521 はリスナーが待ち受けているポート番号、そして FREEPDB1 がここまで学んできたサービス名（＝つなぎたいPDBの名前）です。SQL Developer で接続設定をするときも、入力欄が「ホスト名」「ポート」「サービス名」に分かれているだけで、伝えている情報はまったく同じです。

用語メモ: サービス名とSIDの違い

古い資料では SID（インスタンスを識別する古い方式の名前）を使い、@localhost:1521:XE のようにコロン区切りで指定する書き方が出てきます。しかし本ガイドは一貫して、ここまで説明したスラッシュ区切りのサービス名指定を使います。マルチテナント構成が標準になった今は、PDBの名前をサービス名として指定する方法が基本だと覚えておいてください。

ここまでで、Oracle の内部構造という「地図」がひととおり揃いました。次の第3章では、この章で登場した FREEPDB1・ポート1521・サービス名を実際に使い、自分のパソコンに Oracle Database 23ai Free を導入して接続するところまでを行います。

やってみよう 2-1: 図を描いて用語を整理する

この章もまだインストールは不要です。紙とペンを用意して、覚えたばかりの用語を自分の手で図にしてみましょう。手を動かして整理すると、頭の中の地図がぐっとはっきりします。

  1. 大きな四角を1つ描いて「CDB」と書き、その中に「CDB$ROOT」「PDB$SEED」「FREEPDB1」の3つの小さな四角を描き入れる。
  2. 「FREEPDB1」の四角から矢印を伸ばし、自分の好きなユーザー名（ローマ字など）を書き添える。
  3. 別の紙に「インスタンス」と「データベース」を左右に並べて描き、今日出てきた言葉（SGA、DBWn、LGWR、データファイル、REDOログファイル、制御ファイルなど）をどちらの側に書くべきか仕分ける。

ヒント: 3番の仕分けに迷ったら「電源を切ったら消えてしまうもの＝インスタンス側」「消えずにディスクに残るもの＝データベース側」で考えてみてください。この基準さえ持てれば、今日出てきた用語はすべて仕分けられます。

理解度確認クイズ

  1. Q1. Oracle Database Free で、学習用の表を作るべき接続先はどれですか。(a) CDB$ROOT (b) PDB$SEED (c) FREEPDB1

    回答を表示

    (c) FREEPDB1。CDB$ROOT は建物全体の共通の土台、PDB$SEED は新しいPDBを作るための読み取り専用の雛形なので、どちらにも業務データは置きません。

  2. Q2. サーバーの電源を切ると、インスタンスとデータベースはそれぞれどうなりますか。

    回答を表示

    インスタンス（メモリ上の作業場と裏方プロセス）は消えますが、データベース（ディスク上のデータファイルなど）は残ります。次に起動したときは、REDOログを使って中断した時点の状態まで自動的に復旧されます。

  3. Q3. 利用者が加えた変更の内容を、実際にREDOログファイルへ書き込む役割を持つバックグラウンドプロセスはどれですか。

    回答を表示

    LGWR（Log Writer）です。似た名前の DBWn（Database Writer）は、バッファキャッシュ上の変更をデータファイルへ書き戻す役割で、書き込み先が異なる点に注意してください。
