第12章 所要時間: 約1.5時間

トランザクションとロック

第7章では COMMIT と ROLLBACK を「操作」として覚えました。本章ではその裏側にある考え方――トランザクションと ACID特性、そして Oracle 最大の特徴のひとつである読み取り一貫性――を学びます。あわせて、複数の利用者が同時にデータベースを使うときに起こるロックの競合とデッドロックにも触れ、安全にデータを扱うための土台を固めましょう。

この章で学ぶこと

  • トランザクションと ACID 特性を、身近な例を使って自分の言葉で説明できる
  • COMMIT・ROLLBACK・SAVEPOINT を使い分けられる
  • Oracle の読み取り一貫性（読み取りは書き込みをブロックしない仕組み）を説明できる
  • ロックの競合とデッドロックが起きる状況を理解し、実際に確認・回避できる

12.1 トランザクションとは

銀行振込を思い浮かべてください。Aさんの口座から1万円を引き、Bさんの口座に1万円を足す処理は、内部的には「引く」「足す」という2つの更新に分かれています。もし「引く」だけ成功した直後にシステムが停止したら、1万円がこの世から消えてしまいます。これでは誰も銀行を信用できません。

トランザクションとは、この「引く」と「足す」のように複数の処理をひとまとまりの作業として扱う単位のことです。トランザクションの中の処理は、全部成功したことにするか、全部なかったことにするかのどちらかしか許されません。これにより、「片方だけ成功して中途半端な状態になる」という事故を防ぎます。

サンプルスキーマで同じ考え方を体験してみましょう。次の例は、社員101（佐藤一郎）の給与を5万円減らし、社員102（鈴木花子）の給与に5万円足す処理です。このコードは考え方を示す例なので、まだ実行しなくて構いません。実際に手を動かす実習は、この章の後半で行います。

transaction_basic.sql 
-- 2つの更新を「まとめて成功／まとめて失敗」にする
UPDATE employees SET salary = salary - 50000 WHERE employee_id = 101;
UPDATE employees SET salary = salary + 50000 WHERE employee_id = 102;

-- 両方成功したので確定する
COMMIT;
-- もし途中で異常に気づいたら、まとめて取り消す
-- ROLLBACK;

Oracle では、トランザクションを開始する専用の命令を書く必要はありません。最初の INSERT・UPDATE・DELETE を実行した瞬間に、トランザクションが暗黙的に開始します。そして、COMMIT（確定）・ROLLBACK（取り消し）・あるいは CREATE などの DDL（Data Definition Language / データ定義言語。表を作る・消すなど"入れ物"を操作する命令）の実行によって終了します。

flowchart LR A["最初のDML実行
（INSERT・UPDATE・DELETE）"] --> B["トランザクション開始
（暗黙的）"] B --> C{"どう終える？"} C -->|COMMIT| D["確定
変更が全員に見える状態になる"] C -->|ROLLBACK| E["取り消し
開始前の状態に戻る"] C -->|DDLを実行| F["暗黙的にCOMMIT
（第7章の注意点）"]

「開始」を意識しなくてよい代わりに、「今トランザクションの中にいるのかどうか」を意識することが大切です。次の12.2〜12.3では、トランザクションが満たすべき性質と、終わらせ方の選択肢を整理します。

12.2 ACID特性

トランザクションが備えるべき4つの性質を、頭文字を取って ACID（エーシッド）と呼びます。まともな RDBMS（Oracle・PostgreSQL・SQL Server・MySQL など）は、いずれもこの4つを満たすように設計されています。

特性 英語 平易な言い換え
原子性 Atomicity 全部やるか、全部やらないか。中途半端な状態を許さない
一貫性 Consistency 制約やルールを守った状態から、別の守った状態へ移る
独立性 Isolation 他の人の処理の途中経過は見えない（12.4で詳しく学ぶ）
永続性 Durability COMMIT したら、障害が起きてもそのデータは失われない

第7章で「COMMIT を忘れるとデータが消える」と学んだ理由も、この4文字で説明できます。COMMIT するまでは永続性の保証がまだ働いておらず、接続を切ればいつでも消えてよい「仮の状態」です。また、振込の例で片方の更新だけ実行された状態を許さないのは原子性のおかげであり、ROLLBACK で「なかったこと」にできるのも原子性が保証されているからです。

用語メモ: 一貫性と制約の関係

第5章で学んだ NOT NULL・FOREIGN KEY・CHECK といった制約は、一貫性（Consistency）を機械的に守らせる仕組みです。存在しない部署番号を社員に割り当てられないのも、給与がマイナスにならないのも、すべて一貫性を保つための工夫です。

12.3 COMMIT・ROLLBACK・SAVEPOINTの整理

第7章では、INSERT や UPDATE をしただけでは確定しないこと、COMMIT で確定し ROLLBACK で取り消せることを学びました。ここではこの2つに加えて、トランザクションの途中に「しおり」を挟んで部分的に取り消せる SAVEPOINT（セーブポイント）を学び、3つを体系的に整理します。

COMMIT

ここまでの変更をすべて確定する。以降、変更は他のセッションからも見えるようになる。

ROLLBACK

ここまでの変更をすべて取り消し、トランザクション開始前の状態に戻す。

SAVEPOINT

途中に「しおり」を挟み、ROLLBACK TO でそこまでだけ巻き戻す。

たとえば、長い作業の途中で「1件目は残したいが、2件目は取り消したい」という場面があります。ROLLBACK は全部を巻き戻してしまうので、こういうときは SAVEPOINT で途中にしおりを挟んでおきます。

savepoint_demo.sql 
-- SAVEPOINT（しおり）で部分的に取り消す例
INSERT INTO departments VALUES (60, '企画部', '東京');
SAVEPOINT sp1;                    -- ここにしおりを挟む

INSERT INTO departments VALUES (70, '仮の部署', NULL);
ROLLBACK TO sp1;                  -- しおりまで戻る（60だけ残る）

COMMIT;                           -- 企画部（60）が確定する

-- 動作を確認したので、基準状態に戻す
DELETE FROM departments WHERE department_id = 60;
COMMIT;

最後にもう一度、第7章で学んだ重要な例外を思い出しておきましょう。DDL（CREATE・ALTER・DROP など）は、実行の前後で暗黙的に COMMIT されます。これはトランザクションの終わり方の1つとして、12.1の図にも登場した重要な例外です。今度は実験用の部署（300番）を新しく用意し、削除してからDDLを挟むとどうなるかを確認してみましょう。

ddl_commit_caution.sql 
-- 実験用の部署を追加して確定する（消える前の状態）
INSERT INTO departments VALUES (300, '実験部署', '大阪');
COMMIT;

-- この行を削除する（まだCOMMITしていない）
DELETE FROM departments WHERE department_id = 300;

-- ここでDDLを実行すると、前後で暗黙のCOMMITが行われる
CREATE TABLE memo_check (id NUMBER);

ROLLBACK;              -- 効果なし。DELETEはすでに確定済み
ddl_commit_confirm.sql 
-- 確認：ROLLBACKしたのに部署300は戻ってこない
SELECT department_id, department_name
  FROM departments
 WHERE department_id = 300;
-- → 0件（DDLの暗黙COMMITでDELETEがすでに確定していたため）

-- 後片付け（実験用の表と、念のため部署行も削除）
DROP TABLE memo_check PURGE;
DELETE FROM departments WHERE department_id = 300;
COMMIT;

再確認: DDLを挟むと後戻りできない

「あとで ROLLBACK すればいい」と思っていても、途中で CREATE TABLE などのDDLを実行した瞬間、それより前のDMLは確定済みになります。SQL*Plusでスクリプトを流すときは、DDLの位置に特に注意しましょう。

12.4 読み取り一貫性（MVCC）— Oracleの真骨頂

ここからが本章、そしてOracleを理解するうえで最も重要な部分です。多くの人は「誰かがデータを更新している最中は、他の人はそのデータを読めない（待たされる）」と思い込みがちです。しかしOracleでは、これは誤りです。

重要ポイント: Oracleの読み取り一貫性

読み取りは書き込みをブロックしない。書き込みは読み取りをブロックしない。ブロックし合うのは、書き込み同士だけです。これがOracleの同時実行制御の根本にある性質です。

なぜこれが可能なのでしょうか。Oracleは行を更新すると、UNDO領域（更新される前の値を一時的に保存しておく場所。ロールバックや読み取り一貫性のために使われる）に「変更前の値」を退避させます。他のセッションがその行を読もうとしたとき、更新がまだ確定（COMMIT）していなければ、OracleはUNDO領域から変更前の値を組み立てて返します。読む側は待たされることなく、コミット済みの値をすぐに受け取れる、という仕組みです。

sequenceDiagram participant A as セッションA participant U as Oracle（UNDO領域） participant B as セッションB A->>U: UPDATE employees SET salary=999999 WHERE employee_id=101 Note over U: 変更前の値（650000）をUNDO領域に退避 B->>U: SELECT salary WHERE employee_id=101 U-->>B: 650000を返す（待たされない） A->>U: COMMIT Note over U: UNDO領域の情報は不要になる B->>U: SELECT salary WHERE employee_id=101（再実行） U-->>B: 999999を返す（コミット後の新しい値）

セッションBは、セッションAが COMMIT するまで一貫して「更新前の値」を見続けます。これを読み取り一貫性と呼びます。Oracleでは1つのSQL文の実行中、その文が始まった時点のデータを一貫して見るという保証が既定で常に働いており、特別な設定は不要です。

他のRDBMS製品の中には、既定の設定のままだと読み取り（SELECT）が書き込み中の行を待ってしまうロックベースの読み取りを行うものもあります（たとえばSQL Serverは既定でロックベースであり、Oracleのような挙動にするには追加設定が必要です）。PostgreSQLはOracleと同様に常にMVCC（Multi-Version Concurrency Control / 多版型同時実行制御。1つのデータに対して複数のバージョンを保持し、読み手ごとに適切な版を見せる方式）で動作しますが、変更前の版を保持する場所が異なります（Oracleは専用のUNDO領域、PostgreSQLは表の中に残しておき後で VACUUM で回収します）。「設定なしで常にこの性質が働く」のがOracleの強みだと覚えておきましょう。

豆知識: ORA-01555（スナップショットが古すぎます）

非常に長い時間がかかる問い合わせでは、まれにUNDO領域の情報が別のトランザクションの都合で上書きされてしまい、ORA-01555 というエラーになることがあります。原因の調査や対処は運用寄りの話になるため、本ガイドでは「そういう名前のエラーがある」という程度に覚えておけば十分です。

12.5 ロックの基本

12.4で「書き込み同士はブロックし合う」と説明しました。この仕組みを支えているのがロック（他のセッションが同じデータを同時に変更できないようにする"鍵"）です。Oracleは UPDATE や DELETE をすると、対象になった行だけにロックをかけます（行レベルロック）。表全体がロックされるわけではありません。

トイレの個室を思い浮かべてください。誰かが1つの個室を使っていても、他の個室は自由に使えます。使用中の個室（＝更新中の行）にだけ鍵がかかり、それ以外の行は他のセッションが自由に更新できます。ロック待ちが起きるのは、まったく同じ行を別のセッションが更新しようとしたときだけです。

通常の UPDATE は実行した瞬間にロックがかかりますが、「更新する前に、先に行を確保しておきたい」という場面もあります。映画館の座席を仮押さえするイメージで、SELECT ... FOR UPDATE を使うと、その行を"予約席"として確保し、他のセッションに横取りされない状態にしてから、安心して後続の処理を進められます。

for_update.sql 
-- 行を先に確保する（他のセッションはこの行を更新できなくなる）
SELECT salary FROM employees WHERE employee_id = 101 FOR UPDATE;

-- ロックが取れないなら、待たずにエラーにする
SELECT salary FROM employees WHERE employee_id = 101 FOR UPDATE NOWAIT;

-- 最大5秒だけ待って、それでも取れなければエラーにする
SELECT salary FROM employees WHERE employee_id = 101 FOR UPDATE WAIT 5;

既定の FOR UPDATE はロックが解放されるまで無期限に待ち続けます。「待たずに諦めて別の処理をしたい」ときは NOWAIT、「一定時間だけ待って諦めたい」ときは WAIT 秒数 を使います。なお、ロック中の行を結果から除外したい場合の SKIP LOCKED という選択肢もありますが、まずは NOWAIT / WAIT の2つを覚えれば十分です。

ロック待ちが長引くと「フリーズした」ように見えて不安になりますが、それだけでは異常ではありません。誰が誰を待たせているかは、動的パフォーマンスビュー V$SESSION の BLOCKING_SESSION 列で確認できます。

check_blocking.sql 
-- ロック待ちのセッションと、その原因になっているセッションを表示する
SELECT sid, serial#, blocking_session, username, event
  FROM v$session
 WHERE blocking_session IS NOT NULL;

注意: V$ビューの参照には管理者権限が必要

V$ で始まる動的パフォーマンスビューを参照するには権限が必要です。hr のような一般ユーザーで実行すると ORA-00942: 表またはビューが存在しません になることが多いため、system などの管理者ユーザーで接続して実行してください。

ORA-00054: resource busy and acquire with NOWAIT specified

FOR UPDATE NOWAIT でロックが取れなかったときに出るエラーです。このエラーが出たら、別のセッションが同じ行をすでに更新中で、まだCOMMITしていない可能性を疑いましょう。少し待ってから再試行するか、12.6の方法で相手のセッションを確認します。

12.6 デッドロック

通常のロック待ちは、相手が COMMIT か ROLLBACK をすればすぐに解消します。しかし、2つのセッションが互いに相手のロックしている行を待ち合う状態になると、どちらも永遠に先へ進めなくなります。これをデッドロック（相互待ち）と呼びます。

次のように、セッションAとセッションBが互いに逆の順序で社員101・102を更新しようとすると、デッドロックが発生します。

セッションA 
-- ①社員101を更新する（Aがロックを保持する）
UPDATE employees SET salary = salary + 1000 WHERE employee_id = 101;

-- ③続けて社員102を更新しようとする → Bが保持中なので待たされる
UPDATE employees SET salary = salary + 1000 WHERE employee_id = 102;
セッションB 
-- ②社員102を更新する（Bがロックを保持する）
UPDATE employees SET salary = salary + 1000 WHERE employee_id = 102;

-- ④続けて社員101を更新しようとする → Aと相互待ちになる
UPDATE employees SET salary = salary + 1000 WHERE employee_id = 101;
-- → どちらか一方に ORA-00060 が返る

①→②→③→④の順に実行すると、③の時点でAはBの持つ行102を待ち、④の時点でBはAの持つ行101を待つことになり、両者が完全に行き詰まります。

sequenceDiagram participant A as セッションA participant O as Oracle participant B as セッションB A->>O: UPDATE employees 101（Aがロック取得） B->>O: UPDATE employees 102（Bがロック取得） A->>O: UPDATE employees 102を要求 O-->>A: Bが保持中のため待機 B->>O: UPDATE employees 101を要求 O-->>B: Aが保持中のため待機 Note over A,B: 互いに相手を待つ（デッドロック成立） O-->>B: ORA-00060（デッドロックを検出）で強制ロールバック

Oracleはこの相互待ちを自動的に検出し、片方のセッションに ORA-00060 を返して、そのセッションが実行しようとしていた文を取り消します（12.5の V$SESSION 問い合わせは、この一瞬の待ち状態を確認するのにも使えます）。ただし、それより前に同じトランザクションで行った変更は残ったままなので、エラーを受け取った側は自分で ROLLBACK して処理をやり直す必要があります。デッドロックはデータベースが壊れる異常ではなく、Oracleが安全に解消してくれる想定内の出来事です。

重要ポイント: デッドロックを避ける基本

  • 複数の行を更新するときは、常に同じ順序でアクセスする（例: 社員番号の昇順）
  • トランザクションはできるだけ短くし、不要な処理を間に挟まない
  • ORA-00060を受け取ったら、慌てず ROLLBACK してから処理をやり直す
エラー 意味 まず疑うこと
ORA-00054 resource busy（対象の行がロック中） 別のセッションが同じ行を更新中で、まだCOMMITしていないのでは
ORA-00060 デッドロックを検出（相互待ちが発生） 複数のトランザクションが異なる順序で複数行を更新していないか

この例を実際に試した場合は、両方のセッションで ROLLBACK を実行し、給与を基準状態に戻してから次に進みましょう。

12.7 分離レベル

他のトランザクションの影響をどこまで見せるか／遮断するかの強さの設定を分離レベルと呼びます。Oracleの既定は READ COMMITTED（コミット済みのデータだけが見える）で、これまでの節で見てきた「1つのSQL文の実行中は一貫した値を見る」という性質を提供します。

分離レベル 特徴 使う場面
READ COMMITTED（既定） SQL文単位で一貫した読み取りができる。ほとんどの業務処理で十分 通常のSELECT・UPDATEなど、本ガイドのこれまでの処理すべて
SERIALIZABLE トランザクション開始時点のスナップショットを最後まで見続ける、より厳格な設定 会計処理など、厳密な整合性が求められる一部の処理
READ ONLY トランザクション内を読み取り専用にする 集計レポートの作成など、参照だけを行う処理

より厳格にしたい場合は SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;、読み取り専用にしたい場合は SET TRANSACTION READ ONLY; をトランザクションの最初の文として実行します。初心者のうちは既定のREAD COMMITTEDのままで問題ありません。まずは12.4で学んだ読み取り一貫性の仕組みを理解しておけば、実務のほとんどの場面に対応できます。

次の第13章では、SQLの実行を高速にするインデックスについて学びます。ロックが競合する時間を短くするには、対象の行をすばやく絞り込むことも有効です。「正しさ」の次は、「速さ」の基礎を学んでいきましょう。

やってみよう 12-1: 読み取り一貫性とロックを2つのセッションで体験する

SQL*Plus（またはSQL Developerのワークシート）を2つ開き、両方とも hr ユーザーで FREEPDB1 に接続してください。以降、片方を「セッションA」、もう片方を「セッションB」と呼びます。

  1. セッションAで社員101（佐藤一郎）の給与を更新する。まだ COMMIT しない。
    UPDATE employees SET salary = 999999 WHERE employee_id = 101;
  2. セッションBで同じ社員の給与を確認する。
    SELECT salary FROM employees WHERE employee_id = 101;
    → すぐに結果が返り、値は 650000（更新前の値）のままであることを確認する。
  3. セッションAで COMMIT; を実行して確定する。
  4. セッションBで手順2と同じSELECTをもう一度実行する。→ 今度は 999999（更新後の値）が返ることを確認する。
  5. 【応用】もう一度セッションAで UPDATE employees SET salary = 800000 WHERE employee_id = 101; を実行し、まだCOMMITしない。この状態でセッションBが同じ行に UPDATE employees SET salary = 700000 WHERE employee_id = 101; を実行すると、今度は画面がすぐに戻ってこない（待たされる）ことを確認する。セッションAでCOMMITかROLLBACKすると、Bの処理が動き出す。
  6. 【かたづけ】セッションBが待たされている場合はROLLBACK;で処理を終わらせ、最後にどちらか一方で給与を基準状態に戻す。
    UPDATE employees SET salary = 650000 WHERE employee_id = 101;
    COMMIT;

ねらい: 手順2のSELECTは待たされず、手順5のUPDATEは待たされる――この違いこそ、12.4で学んだ「読み取りは書き込みをブロックしない。ブロックし合うのは書き込み同士だけ」という性質そのものです。「更新中は誰も読めない」と思い込んでいた人ほど、手順2の結果に驚くはずです。

理解度確認クイズ

  1. Q1. 銀行振込を例に、複数の UPDATE を1つのトランザクションとして扱う必要がある理由を説明してください。

    回答を表示

    途中で処理が中断すると、片方の口座だけ変更されて整合性が崩れてしまう（ACIDの原子性が破られる）からです。トランザクションとして扱うことで、「全部成功する」か「全部なかったことにする」かのどちらかにでき、中途半端な状態を防げます。

  2. Q2. セッションAが社員の給与を UPDATE して COMMIT していない状態で、セッションBが同じ行を SELECT するとどうなりますか。また UPDATE しようとするとどうなりますか。

    回答を表示

    SELECTは待たされず、UNDO領域から組み立てられた更新前の値がすぐに返ります（読み取り一貫性）。一方UPDATEは、同じ行にロックがかかっているため待たされます。ブロックし合うのは書き込み同士だけです。

  3. Q3. 2つのセッションが互いに相手のロックしている行を更新しようとするとどうなりますか。Oracleはどのように対応しますか。

    回答を表示

    デッドロック（相互待ち）が発生します。Oracleはこれを自動的に検出し、片方のセッションにORA-00060を返してその文を取り消します。エラーを受け取った側はROLLBACKして処理をやり直す必要があります。予防には、複数行を更新する際の順序をそろえる、トランザクションを短くする、といった対策が有効です。
