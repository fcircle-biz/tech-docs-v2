第11章 所要時間: 約1.5時間

ストアドプログラムとトリガー

第10章では、SQL*Plus に貼り付けるたびに書き直す「使い捨ての PL/SQL ブロック（匿名ブロック）」を書きました。この章では、そのブロックに名前を付けてデータベースに保存し、何度でも同じ名前で呼び出せる部品にする方法を学びます。これがストアドプロシージャとストアドファンクションです。さらに、関連する処理をひとまとめにするパッケージ、そして特定の操作をきっかけに自動的に動き出すトリガーまで扱います。

この章で学ぶこと

  • ストアドプロシージャとストアドファンクションを作成・実行・削除でき、両者を使い分けられる
  • IN・OUT・IN OUT パラメータを使い分けられ、コンパイルエラーを自力で調べられる
  • パッケージで関連する処理をひとまとめにできる
  • トリガーの仕組みを理解し、:NEW と :OLD を使った監査用トリガーを作れる

11.1 ストアドプログラムとは

第10章の匿名ブロックには、ひとつ不便な点がありました。実行するたびに DECLARE から END; までの全文を SQL*Plus に貼り付け直す必要があり、名前も付けられないので他の人と共有しづらい、という点です。

そこで登場するのがストアドプログラム（Stored Program / データベースに保存されたプログラム）です。PL/SQL のプログラムに名前を付けてデータベースの中に保存しておけば、以後は名前を呼ぶだけで何度でも同じ処理を実行できます。

比喩: 電子レンジの「あたため」ボタン

毎回「500W・2分」と手入力する代わりに、よく使う設定を「あたため」ボタン1つに登録しておけば、ボタンを押すだけで済みます。ストアドプログラムも同じ考え方で、よく使う SQL・PL/SQL の手順に名前という「ボタン」を付けておき、以後はその名前を呼ぶだけで実行できるようにします。

ストアドプログラムには主に4つの種類があります。この章では、この順番で1つずつ学んでいきます。

プロシージャ

名前を付けた「一連の処理」。11.2 で学ぶ

ファンクション

名前を付けた「値を返す計算」。11.3 で学ぶ

パッケージ

複数をまとめる入れ物。11.5 で学ぶ

トリガー

操作をきっかけに自動で動く。11.6 で学ぶ

ストアドプログラムには主に3つの利点があります。(1) 再利用性: 一度作れば、誰でも同じ名前で同じ処理を呼び出せます。(2) 性能: 処理がデータベース側でまとめて実行されるため、アプリケーションとデータベースの間の通信回数が減ります。(3) 保守性: 処理のロジックが1か所にまとまるので、修正が必要なときに直す場所を探しやすくなります。

11.2 ストアドプロシージャを作る

ストアドプロシージャ（一般には単に「プロシージャ」と呼びます）は、CREATE OR REPLACE PROCEDURE で作成します。CREATE OR REPLACE は「同じ名前のものが無ければ新しく作る、既にあれば中身を置き換える」という意味です。開発中は何度も作り直すことになるので、基本的にこの書き方を使います。

show_dept_count.sql 
-- 指定した部署の社員数を画面に表示するプロシージャ
CREATE OR REPLACE PROCEDURE show_dept_count(p_dept_id IN NUMBER) IS
  v_count NUMBER;
BEGIN
  SELECT COUNT(*) INTO v_count FROM employees WHERE department_id = p_dept_id;
  DBMS_OUTPUT.PUT_LINE('部署' || p_dept_id || 'の社員数: ' || v_count || '人');
END;
/

-- 実行する（画面出力にはSET SERVEROUTPUT ONが必要。第10章で学んだ設定）
SET SERVEROUTPUT ON
EXECUTE show_dept_count(20);
実行結果 
部署20の社員数: 4人

PL/SQLプロシージャが正常に完了しました。

作成したプロシージャは、SQL*Plus では EXECUTE 名前(引数)（EXEC と省略可）で実行するほか、PL/SQL ブロックの中から show_dept_count(20); のように呼び出すこともできます。

プロシージャの引数には向きがあります。何も書かなければ既定で IN です。3つの向きを表で確認しましょう。

種類 意味 呼び出す側での書き方
IN（既定） 値を「受け取るだけ」。プロシージャ内で書き換えても呼び出し元には反映されない 値や変数をそのまま渡す
OUT 値を「返すだけ」。渡した時点の値は無視され、プロシージャ内で設定した値が呼び出し元に返る あらかじめ受け皿の変数を用意して渡す
IN OUT 値を「受け取って、書き換えて返す」。IN と OUT の両方の性質を持つ 変数を渡す（呼び出し後に中身が変わる）

OUT パラメータを使うと、1回の呼び出しで複数の値を呼び出し元に返せます。ファンクションが返せる値は1つだけなので、複数の値がほしいときはプロシージャの OUT が便利です。

get_dept_stats.sql 
-- 部署の社員数と平均給与を、呼び出し元の変数に返すプロシージャ
CREATE OR REPLACE PROCEDURE get_dept_stats(
  p_dept_id IN  NUMBER,
  p_count   OUT NUMBER,
  p_avg     OUT NUMBER
) IS
BEGIN
  SELECT COUNT(*), ROUND(AVG(salary)) INTO p_count, p_avg
    FROM employees WHERE department_id = p_dept_id;
END;
/
get_dept_stats_call.sql 
-- OUTパラメータは、呼び出す側で受け皿の変数を用意して渡す
DECLARE
  v_cnt NUMBER;
  v_avg NUMBER;
BEGIN
  get_dept_stats(20, v_cnt, v_avg);
  DBMS_OUTPUT.PUT_LINE('人数: ' || v_cnt || '人 / 平均給与: ' || v_avg || '円');
END;
/
実行結果 
人数: 4人 / 平均給与: 467500円

最後に IN OUT です。「受け取った値をそのまま書き換えて返す」ときに使います。歩合率を2倍にする、次のような小さな例で確認しましょう。

double_rate.sql 
-- IN OUT: 受け取った値を書き換えて、そのまま呼び出し元に返す
CREATE OR REPLACE PROCEDURE double_rate(p_rate IN OUT NUMBER) IS
BEGIN
  p_rate := p_rate * 2;
END;
/

DECLARE
  v_rate NUMBER := 0.10;
BEGIN
  double_rate(v_rate);
  DBMS_OUTPUT.PUT_LINE('2倍後の歩合率: ' || v_rate);
END;
/

不要になったプロシージャは DROP PROCEDURE show_dept_count; のように DROP PROCEDURE 名前; で削除できます。

11.3 ストアドファンクションを作る

ストアドファンクション（単に「ファンクション」）は CREATE OR REPLACE FUNCTION で作成し、必ず RETURN 型 を宣言して1つの値を返すことを約束します。プロシージャとの決定的な違いは、SQL 文の中から関数のように呼び出せることです。

get_annual_salary.sql 
-- 月給から年収を計算して返すファンクション（RETURNで型と値を指定する）
CREATE OR REPLACE FUNCTION get_annual_salary(p_emp_id IN NUMBER)
  RETURN NUMBER IS
  v_salary employees.salary%TYPE;
BEGIN
  SELECT salary INTO v_salary FROM employees WHERE employee_id = p_emp_id;
  RETURN v_salary * 12;
END;
/

-- ファンクションはSELECT文の中で列のように呼び出せる（プロシージャにはできない）
SELECT last_name, get_annual_salary(employee_id) AS "年収"
  FROM employees
 WHERE department_id = 10;
実行結果 
LAST_NAME                     年収
------------------------------ ----------
佐藤                              7800000
鈴木                              5760000
高橋                              4560000

「値が欲しいならファンクション、処理をさせたいならプロシージャ」がこの章での判断基準です。使い分けを表で整理します。

観点 プロシージャ ファンクション
定義するキーワード CREATE OR REPLACE PROCEDURE CREATE OR REPLACE FUNCTION
値を返すか 必須ではない（OUT パラメータで複数返せる） 必ず1つの値を RETURN する
SQL文の中で呼べるか 呼べない（EXECUTE や PL/SQL ブロックから呼ぶ） 呼べる（SELECT の列としても使える）
主な用途 一連の処理をまとめて実行させたいとき 計算結果や導出した値がほしいとき

（RETURNで値を返す）
SELECT文の中でも呼べる"] B -->|いいえ・処理をさせたい| D["PROCEDURE

重要ポイント

プロシージャを SELECT 文の中で呼び出すことはできません。「一覧に計算列を追加したい」ときは、必ずファンクションを使いましょう。

11.4 コンパイルエラーの調べ方

プロシージャやファンクションを作るとき、必ず一度は遭遇するのが次の警告です。これはエラーではなく「保存はできたが、中身に問題がある」という警告で、詳しい原因はこのメッセージだけでは分かりません。

show_salary_ng.sql 
-- わざと列名を書き間違えている（salary → salaryy）
CREATE OR REPLACE PROCEDURE show_salary(p_emp_id IN NUMBER) IS
  v_salary employees.salary%TYPE;
BEGIN
  SELECT salaryy INTO v_salary FROM employees WHERE employee_id = p_emp_id;
  DBMS_OUTPUT.PUT_LINE(v_salary);
END;
/
実行結果 
警告: プロシージャが作成されました。ただし、コンパイル・エラーがあります。

詳しい原因を見るには、SQL*Plus の SHOW ERRORS コマンドを直後に実行します。

SQL*Plus 
-- 直前のCREATEで出た警告の詳細を表示する
SHOW ERRORS
実行結果 
PROCEDURE SHOW_SALARY のエラーです。

LINE/COL ERROR
-------- -----------------------------------------------------
4/3      PL/SQL: ORA-00904: "SALARYY": 無効な識別子です

ORA-00904（無効な識別子です）は、「その名前の列・表・変数が存在しません」というエラーです。今回は列名のタイプミスが原因だと一目で分かります。SQL で直接調べたい場合は、データディクショナリの USER_ERRORS ビューを使います。

user_errors.sql 
-- SQLで直接調べることもできる（名前は大文字で指定する）
SELECT line, position, text FROM user_errors
 WHERE name = 'SHOW_SALARY' ORDER BY sequence;

原因が分かったら、CREATE OR REPLACE なのでそのまま上書きして直せます。

show_salary.sql 
-- salaryy を salary に直して再作成する
CREATE OR REPLACE PROCEDURE show_salary(p_emp_id IN NUMBER) IS
  v_salary employees.salary%TYPE;
BEGIN
  SELECT salary INTO v_salary FROM employees WHERE employee_id = p_emp_id;
  DBMS_OUTPUT.PUT_LINE(v_salary);
END;
/

SQL Developer の場合

ワークシートでプロシージャを保存すると自動的にコンパイルが走り、画面下のログ（コンパイラ）ペインにエラーの行番号とメッセージが直接表示されます。SHOW ERRORS を打つ必要はありません。

この章のすべての例で、コンパイル・エラーが出たらまず SHOW ERRORS。これを習慣にしておくと、以降の学習がぐっと楽になります。

11.5 パッケージ: 関連する処理をまとめる

パッケージは、関連するプロシージャ・ファンクション・変数をひとつの入れ物にまとめる仕組みです。「本の目次と本文」の関係に似ていて、仕様部（CREATE PACKAGE＝外から使える処理の目次）と本体（CREATE PACKAGE BODY＝実際の処理内容）の2段構成になっています。

emp_pkg_spec.sql 
-- 仕様部：外から使える処理の"目次"を宣言する（実装は書かない）
CREATE OR REPLACE PACKAGE emp_pkg IS
  FUNCTION  get_annual_salary(p_emp_id  IN NUMBER) RETURN NUMBER;
  PROCEDURE show_dept_count(p_dept_id IN NUMBER);
END emp_pkg;
/

続けて本体を作ります。すでに作った get_annual_salary と show_dept_count の中身を、そのままパッケージの内側に移した形です。

emp_pkg_body.sql 
-- 本体：仕様部で宣言した2つの処理を実装する
CREATE OR REPLACE PACKAGE BODY emp_pkg IS
  FUNCTION get_annual_salary(p_emp_id IN NUMBER) RETURN NUMBER IS
    v_salary employees.salary%TYPE;
  BEGIN
    SELECT salary INTO v_salary FROM employees WHERE employee_id = p_emp_id;
    RETURN v_salary * 12;
  END get_annual_salary;
  PROCEDURE show_dept_count(p_dept_id IN NUMBER) IS v_count NUMBER;
  BEGIN
    SELECT COUNT(*) INTO v_count FROM employees WHERE department_id = p_dept_id;
    DBMS_OUTPUT.PUT_LINE('部署' || p_dept_id || 'の社員数: ' || v_count || '人');
  END show_dept_count;
END emp_pkg;
/

呼び出すときは パッケージ名.プログラム名 という書き方をします。

emp_pkg_call.sql 
-- パッケージ名.プログラム名 で呼び出す
EXECUTE emp_pkg.show_dept_count(10);

SELECT last_name, emp_pkg.get_annual_salary(employee_id) AS "年収"
  FROM employees WHERE department_id = 10;

小さなうちは1つずつのプロシージャ・ファンクションのままでも困りません。ただし数が増えてくると、名前の衝突を避けやすくなる、関連する処理がどこにあるか探しやすくなる、といった利点が効いてきます。本ガイドでは仕組みの理解を優先し、小さな例1つにとどめます。

11.6 トリガー: 操作をきっかけに自動で動く

トリガーは、表への INSERT・UPDATE・DELETE をきっかけに、Oracle が自動的に実行するプログラムです。ここまでのプロシージャやファンクションは「呼ばないと動かない」のに対し、トリガーは「決めておいた操作が起きたら勝手に動く」という違いがあります。

比喩: 自動ドアのセンサー

自動ドアは、人が近づくとセンサーが感知して勝手に開きます。「ドアを開けてください」とお願いする人はいません。トリガーも同じで、UPDATE のような操作が「近づいた人」の役割を果たし、Oracle が自動的に決められた処理を実行します。

トリガーには次のような設定項目があります。いつ動くか（BEFORE＝操作の前 / AFTER＝操作の後）、何が起きたら動くか（INSERT / UPDATE / DELETE）、そして行ごとに動くか（FOR EACH ROW を付けた行トリガー。付けない場合は変更全体で1回だけ動く文トリガー）です。

行トリガーの中では、:NEW（変更後の値）と:OLD（変更前の値）という特別な書き方で、その行のデータにアクセスできます。ただし操作によって使える組み合わせが決まっています。

操作 :OLD（変更前の値） :NEW（変更後の値）
INSERT 使えない（まだ行が存在しない） 使える（これから入る値）
UPDATE 使える（更新前の値） 使える（更新後の値）
DELETE 使える（消される直前の値） 使えない（行が消えた後には無い）

実際に、給与が変更されたら自動で履歴を残す監査トリガーを作ってみましょう。まず履歴を保存する表を用意します。

salary_history.sql 
-- 給与変更の履歴を残す表を作る
CREATE TABLE salary_history (
  history_id  NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  employee_id NUMBER(6),
  old_salary  NUMBER(8),
  new_salary  NUMBER(8),
  changed_at  DATE DEFAULT SYSDATE,
  changed_by  VARCHAR2(30 CHAR)
);

次にトリガー本体です。WHEN 句を付けて、給与が実際に変わったときだけ動くようにします。

trg_salary_history.sql 
-- 給与が変更されたら自動で履歴を残すトリガー
CREATE OR REPLACE TRIGGER trg_salary_history
  AFTER UPDATE OF salary ON employees
  FOR EACH ROW
  WHEN (NEW.salary <> OLD.salary)   -- 値が変わったときだけ動かす
BEGIN
  -- :OLD は変更前の値、:NEW は変更後の値
  INSERT INTO salary_history (employee_id, old_salary, new_salary, changed_by)
  VALUES (:OLD.employee_id, :OLD.salary, :NEW.salary, USER);
END;
/

動作を確認します。employees を普段どおり UPDATE するだけで、salary_history への INSERT は一度も書いていません。

trigger_test.sql 
-- トリガーの動作を確認する（employees側は普段どおりUPDATEするだけ）
UPDATE employees SET salary = 420000 WHERE employee_id = 103;
COMMIT;

-- salary_historyにはINSERTを書いていないのに、自動で記録されている
SELECT employee_id, old_salary, new_salary, changed_by FROM salary_history;
実行結果 
EMPLOYEE_ID OLD_SALARY NEW_SALARY CHANGED_BY
----------- ---------- ---------- ------------------------------
        103     380000     420000 HR

11.7 トリガーの注意点とオブジェクトの確認

トリガーは便利な反面、「見えないところで自動的に動く」という性質そのものが落とし穴にもなります。使う前に、次の注意点を必ず押さえておきましょう。

トリガーを使うときの注意点

  • 追跡しづらい: UPDATE employees しか書いていないのに、裏で別の表が変わります。何がどのトリガーで動いているか、忘れた頃に調査で困る原因になります。
  • 使いすぎない: 何にでもトリガーを付けると、処理の流れが表ごとに分散し、全体像を追うのが難しくなります。本当に「操作から自動で連動させたい」場合だけに絞りましょう。
  • トリガーの中で COMMIT しない: トリガーは呼び出し元の一連の処理の一部として動くため、中で勝手に COMMIT すると、呼び出し元がまだ処理の途中でも変更が確定してしまいます。例外は自律型トランザクション（PRAGMA AUTONOMOUS_TRANSACTION という指定を使い、トリガーの中だけ独立した取引として確定できる発展的な仕組み）を使う場合のみですが、本ガイドでは扱いません。
  • 変異表エラー（ORA-04091）: employees のトリガーの中で employees 自身を SELECT や UPDATE しようとすると発生します。今回のように「別の表（salary_history）に書き込む」設計であれば発生しません。

トリガーを一時的に止めたいだけなら削除せずに無効化できます。完全に不要になったら削除します。

trigger_disable.sql 
-- 一時的に止めたいだけなら DISABLE、削除するなら DROP TRIGGER
ALTER TRIGGER trg_salary_history DISABLE;
ALTER TRIGGER trg_salary_history ENABLE;

最後に、この章で作ったオブジェクトが実際にデータベースへ登録されているかを、データディクショナリで確認しておきましょう。

user_objects_triggers.sql 
-- 作成したプログラムの一覧と、コンパイルが通っているか（STATUS）を確認する
SELECT object_name, object_type, status
FROM user_objects
WHERE object_type IN ('PROCEDURE', 'FUNCTION', 'PACKAGE', 'PACKAGE BODY')
ORDER BY object_type, object_name;

-- 自分が作ったトリガーの一覧と有効・無効の状態
SELECT trigger_name, table_name, status FROM user_triggers;

ソースコードの中身そのものを見たいときは USER_SOURCE ビューを使います。エラー調査（11.4）でも登場した仕組みと同じです。

user_source.sql 
-- ソースコードの中身を確認する（名前は大文字で指定する）
SELECT text FROM user_source
 WHERE name = 'GET_ANNUAL_SALARY' ORDER BY line;

かたづけ: 動作確認のために変更した給与と、この章だけで使ったトリガー・履歴表を、基準状態に戻しておきましょう。show_dept_count・get_annual_salary などのプロシージャ・ファンクション・パッケージは、以降の章では参照しないのでそのまま残して構いません。

cleanup.sql 
-- 動作確認で変更した給与を元の金額に戻す
UPDATE employees SET salary = 380000 WHERE employee_id = 103;
COMMIT;

-- 今回作成したトリガーと履歴表を削除し、基準状態に戻す
DROP TRIGGER trg_salary_history;
DROP TABLE salary_history PURGE;

これで、SQL を「手続きとして組み立てる」道具がひととおり揃いました。次の第12章では視点を変え、COMMIT や ROLLBACK の裏で Oracle が何をしているのか、トランザクションとロックの仕組みを学びます。

やってみよう 11-1: ボーナス計算ファンクションを作る

hr ユーザーで接続した状態で、次の手順に沿ってファンクションを自作してみましょう。

  1. calc_bonus(p_emp_id IN NUMBER) RETURN NUMBER という名前で、指定した社員の月給2か月分（salary * 2）を返すファンクションを作成する。
  2. SELECT last_name, calc_bonus(employee_id) AS "ボーナス" FROM employees; を実行し、全社員のボーナスが一覧できることを確認する。
  3. わざと関数名や列名を書き間違えたバージョンを作ってみて、SHOW ERRORS で原因が読み取れるかを試す（調べ方は11.4と同じ要領。原因が分かったら正しい定義に書き直す）。
  4. 動作を確認できたら、DROP FUNCTION calc_bonus; を実行してファンクションを削除し、基準状態に戻しておきましょう。

ヒント: get_annual_salary（11.3）とほぼ同じ形です。RETURN NUMBER IS の後に変数を宣言し、SELECT … INTO … で給与を取り出してから RETURN 変数 * 2; とすれば完成します。

理解度確認クイズ

  1. Q1. SELECT last_name, calc_bonus(employee_id) FROM employees; のように SQL 文の中から直接呼び出せるのは、プロシージャとファンクションのどちらですか。

    回答を表示

    ファンクションです。RETURN で必ず1つの値を返すため、式として SQL 文の中に組み込めます。プロシージャは値を返すとは限らないので、EXECUTE や PL/SQL ブロックから呼び出します。

  2. Q2. UPDATE トリガーの中で、更新前の給与と更新後の給与をそれぞれ参照するには何を使いますか。

    回答を表示

    更新前は :OLD.salary、更新後は :NEW.salary です。ただしこれらを参照できるのは、FOR EACH ROW を付けた行トリガーの中だけです。

  3. Q3. CREATE OR REPLACE PROCEDURE を実行したら「警告: プロシージャが作成されました。ただし、コンパイル・エラーがあります。」と表示されました。次に何をすべきですか。

    回答を表示

    SQL*Plus で SHOW ERRORS を実行するか、SQL で USER_ERRORS ビューを調べます。行番号・列位置・ORA エラーの詳細が表示されるので、そこから原因（列名のタイプミスなど）を特定します。
