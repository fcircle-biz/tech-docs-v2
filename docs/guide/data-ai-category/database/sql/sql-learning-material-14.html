インデックス・権限・運用の基礎

いよいよ最終章です。ここまでで SQL を書いて「取り出す・変える・まとめて確定する」ことはできるようになりました。この章では、そのデータベースを長く安全に「使い続ける」ための基礎知識として、検索を速くするインデックス、誰に何を許すかを決める権限管理、もしものときのバックアップ、日々のメンテナンスを学びます。最後に全14章を振り返り、次に進む道を示します。

この章の学習目標

  • インデックスの仕組みと、利用されにくいケースがあることを説明できる
  • EXPLAIN で実行計画を読み、Seq Scan と Index Scan の違いが分かる
  • ロールと GRANT / REVOKE による最小権限の考え方を理解する
  • バックアップ・復元・VACUUM の必要性を説明できる
  • 全14章の学習内容を振り返り、次に学ぶとよいテーマを描ける

14.1 インデックスとは — 「本の索引」の考え方 必須

分厚い専門書で特定の用語を探すとき、私たちは巻末の索引を使います。索引がなければ、1ページ目から順番にすべてのページをめくって探す（全件走査）しかありません。データベースのテーブルも同じで、行数が増えるほど「先頭から1行ずつ全部確認する」検索は遅くなります。この全件走査のことを、PostgreSQL ではシーケンシャルスキャン（Seq Scan）と呼びます。

インデックスは、この本の索引にあたる仕組みです。特定の列の値を、あらかじめ検索しやすい形（既定では B-tree という木構造）に整理しておき、目的の行へすばやくたどり着けるようにします。CREATE INDEX で作成し、DROP INDEX で削除します。

create-index.sql 
-- customers テーブルの prefecture 列にインデックスを作成
-- （PostgreSQL の既定はB-tree方式）
CREATE INDEX idx_customers_prefecture
    ON customers (prefecture);

-- 不要になったインデックスは削除できる
DROP INDEX idx_customers_prefecture;

ヒント: インデックス名の慣例

idx_テーブル名_列名 のように命名すると、あとで見返したときにどのテーブルの何のためのインデックスか一目で分かります。本ガイドでもこの慣例に従っています。

14.2 どの列にインデックスを作るとよいか 必須

実は、PRIMARY KEY 制約を付けた列には、テーブル作成時に自動でユニークインデックスが作られます。第5章で customer_id などに主キーを設定したときから、皆さんは既にインデックスの恩恵を受けていたことになります。

では、主キー以外にどの列へインデックスを追加するとよいのでしょうか。目安は次の2点です。

目安 説明 具体例
WHERE / JOIN でよく使う列 絞り込みや結合の条件に頻繁に登場する列は候補になる orders.customer_id（第11章の結合条件）
カーディナリティが高い列 値の種類が多く、1つの値で行を大きく絞り込める列ほど効果が出やすい email（ほぼ全行が異なる値）

逆に、orders.status のように値の種類が「受付／発送済／キャンセル」の3つしかない列（カーディナリティが低い列）は、インデックスを作っても効果が薄いことが多くなります。次の14.3で理由を見ていきます。

14.3 インデックスが利用されにくいケース 発展

インデックスを作っても利用されにくい（＝ Seq Scan のままになりやすい）代表的なケースが3つあります。第7章・第8章で「これは後の章で説明します」と予告していた内容の回収です。

ケース 具体例 理由
列に関数を適用している WHERE upper(customer_name) = 'SATO'（第8章の文字列関数） 索引は「元の値」を並べたもの。upper() で変換した後の値は索引の中に無いため、元の列に作った通常のインデックスは利用されにくくなる
前方ワイルドカードの LIKE WHERE product_name LIKE '%ノート%'（第7章のLIKE） 先頭が不明だと、索引の「先頭文字から辿る」性質を活かせず、通常のB-treeインデックスでは利用されにくく、表全体を読む処理になりやすい
対象行が多すぎる（低選択性） WHERE status = '受付'（全体の大半を占める値） 索引を辿ってから本体を1行ずつ見に行くより、最初から全件を読んだほうが速いとプランナが判断する

つまり、インデックスを作ったからといって必ず使われるわけではありません。実際に使われているかどうかは、次の14.5で紹介する EXPLAIN で確認する必要があります。

発展 式インデックス（関数インデックス）

列そのものではなく、関数で加工した後の値にインデックスを作ることもできます。これを式インデックス（関数インデックス）と呼びます。

expression-index.sql 
-- 式インデックス：加工後の値そのものにインデックスを作る
CREATE INDEX idx_customers_lower_email ON customers (lower(email));

これを作っておくと、WHERE lower(email) = '...' という条件でもインデックスを利用できるようになります。

発展 中間一致検索を高速化したいときは — 大量データで LIKE '%文字列%' のような中間一致の検索が頻繁に必要になる場合は、全文検索や pg_trgm 拡張といった別のしくみを検討します。

14.4 インデックスの代償 — 「とりあえず全列」が誤りである理由 必須

ここまで読むと「検索が速くなるなら、全部の列にインデックスを作ればよいのでは」と思うかもしれません。しかし、インデックスは無料の仕組みではありません。主に2つの代償があります。

  • 追加・更新・削除が遅くなる — INSERT / UPDATE / DELETE のたびに、テーブル本体だけでなく、そこに付いているすべてのインデックスも更新しなければならない
  • ディスク容量を消費する — インデックス自体もデータであり、テーブル本体とは別に保存領域を必要とする

注意: 「とりあえず全列にインデックス」は誤り

検索は速くなりますが、書き込みのたびにすべてのインデックスを更新するコストがのしかかり、更新の多いテーブルほど全体が遅くなります。WHERE や JOIN の条件で実際によく使う列に絞って作るのが基本方針です。迷ったら、まずインデックス無しで運用し、実際に遅いクエリが見つかってから14.5の EXPLAIN で原因を確認し、必要な列にだけ追加しましょう。

14.5 実行計画を見る — EXPLAIN と EXPLAIN ANALYZE 発展

PostgreSQL は SELECT を実行する前に「どういう手順でデータを取り出すか」という実行計画を立てます。この計画を組み立てる部分をプランナ（オプティマイザ）と呼びます。実行計画を覗き見るのが EXPLAIN です。実際にはクエリを実行せず、計画だけを表示します。

explain-before.sql 
-- customers への検索の実行計画を確認する
EXPLAIN SELECT customer_name
FROM customers
WHERE prefecture = '東京都';

customers のような小さなテーブルでは、次のように Seq Scan（シーケンシャルスキャン＝全件走査）と表示されるのが基本です。

実行結果（customers、10件程度） 
                          QUERY PLAN
------------------------------------------------------
 Seq Scan on customers  (cost=0.00..1.12 rows=3 width=20)
   Filter: ((prefecture)::text = '東京都'::text)

重要：小さなテーブルではインデックスを作ってもSeq Scanのままのことがある — 試しに idx_customers_prefecture（14.1の CREATE INDEX で作成し、まだ DROP INDEX していない状態）で同じ EXPLAIN を実行しても、customers はわずか10件程度しかないため、PostgreSQLが「インデックスを辿るより、表を全部読んだほうが速い」と判断し、Seq Scan のままになるのが普通です。インデックスは「作れば必ず使われるもの」ではなく、PostgreSQLがコストを見積もって使うかどうかを決めるものだと覚えておきましょう。

実際に Index Scan（索引利用）へ切り替わる様子を確認するには、ある程度の件数を持つテーブルが必要です。ここでは検証専用のテーブルを作って試してみましょう（本番の shop_db のテーブルには影響しません）。

idx-demo-setup.sql 
-- 検証用の大きめのテーブルを作る（本番の shop_db のテーブルには影響しません）
CREATE TABLE idx_demo (
    id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code  integer NOT NULL,
    memo  text    NOT NULL
);

-- generate_series は「連番を行として生成する」PostgreSQLの関数
INSERT INTO idx_demo (code, memo)
SELECT g, 'memo-' || g
  FROM generate_series(1, 500000) AS g;

ANALYZE idx_demo;   -- 統計情報を最新にする（これをしないと見積もりがずれます）
idx-demo-explain.sql 
-- インデックスを作る前：Seq Scan になる
EXPLAIN ANALYZE SELECT * FROM idx_demo WHERE code = 250000;

CREATE INDEX idx_demo_code ON idx_demo (code);
ANALYZE idx_demo;

-- インデックスを作った後：Index Scan が選ばれやすくなる
EXPLAIN ANALYZE SELECT * FROM idx_demo WHERE code = 250000;

インデックス作成後は、次のように actual time（ミリ秒単位の実測値）まで含めて Index Scan に切り替わったことを確認できます。EXPLAIN ANALYZE は実際にクエリを実行してしまう点に注意してください。DELETE や UPDATE の計画を確認するときにうっかり本当に実行してしまわないよう、対象は基本的に SELECT にとどめましょう。

実行結果の例（idx_demo、インデックス作成後） 
 Index Scan using idx_demo_code on idx_demo
   (cost=0.43..8.45 rows=1 width=13)
   (actual time=0.031..0.033 rows=1 loops=1)
   Index Cond: (code = 250000)
 Planning Time: 0.112 ms
 Execution Time: 0.052 ms

注意： 実行環境やデータの状態によって、コストの数値や選ばれる実行計画は変わります。上の数値はあくまで一例です。大事なのは数値そのものではなく、Seq Scan から Index Scan に変わったという計画の種類の違いです。

idx-demo-cleanup.sql 
-- 確認が終わったら後片付け
DROP TABLE idx_demo;

cost=0.43..8.45 のような部分は「開始コスト..合計コスト」という推定の重さを表す目安の数値で、単位は秒ではありません。今の段階では「小さいほど軽いと見積もられている」とだけ覚えておけば十分です。

ヒント: pgAdmin の「Explain」ボタン

pgAdmin 4 のクエリツールには、SQL を書いたあと押すだけで実行計画を図（ツリー）として表示してくれる「Explain」ボタンがあります。文字の出力より直感的に読めるので、まずはこちらで全体の形をつかみ、細かい数値をテキスト出力で確認する、という使い分けがおすすめです。

14.6 ユーザーと権限 — ロールと GRANT / REVOKE 実務で覚える

PostgreSQL では「ユーザー」と「グループ」を区別せず、ロールという1つの概念にまとめています。ロールには、ログインしてSQLを実行できる「ログインロール」と、権限をまとめておくだけの「グループロール」がありますが、作り方はどちらも CREATE ROLE です。

roles-and-grant.sql 
-- アプリケーション専用のロールを作成する
CREATE ROLE app_user LOGIN PASSWORD 'secure_password';

-- customers テーブルの参照だけを許可する
GRANT SELECT ON customers TO app_user;

-- orders テーブルは参照と追加のみ許可する
GRANT SELECT, INSERT ON orders TO app_user;

-- 追加の権限が不要になったら取り消す
REVOKE INSERT ON orders FROM app_user;

注意：パスワードの扱い — 上記の 'secure_password' はあくまで例示用のパスワードです。実際に使うパスワードは、教材・ソースコード・チャット・チケットなどに書き残さないようにしましょう。パスワードマネージャーなどで安全に管理し、psql の \password コマンドを使うと、SQL文の履歴にパスワードを残さずに設定できます。

ここで意識したいのが最小権限の原則です。「そのユーザーが本当に必要な操作だけを許可し、それ以外はすべて拒否する」という考え方で、権限管理の基本方針になります。

注意: アプリ用ユーザーに postgres を使ってはいけない

インストール時に作られる postgres はすべての操作を行えるスーパーユーザーです。アプリケーションの接続にこれを使うと、SQLインジェクションなどでアプリが乗っ取られた場合にデータベース全体が危険にさらされます。アプリごとに最小限の権限を持つ専用ロールを作り、postgres は管理作業のときだけ使うのが鉄則です。

14.7 バックアップと復元 実務で覚える

どれだけ気をつけて運用していても、操作ミスやハードウェア障害でデータが失われる可能性はゼロにできません。だからこそ、定期的なバックアップが欠かせません。PostgreSQL には pg_dump というコマンドがあり、データベースの内容を1つのファイル（論理バックアップ）として書き出せます。

backup-and-restore.sh 
# shop_db をカスタム形式でバックアップする
pg_dump -U postgres -Fc shop_db > shop_db_backup.dump

# 復元先のデータベースを先に作っておく（pg_restore は空のデータベースを自動では作りません）
createdb -U postgres shop_db_practice
# ※ 代わりに psql -U postgres -c "CREATE DATABASE shop_db_practice;" でもよい

# 作成済みのデータベースへカスタム形式のバックアップを復元する
pg_restore -U postgres -d shop_db_practice shop_db_backup.dump

# SQL形式（プレーンテキスト）でバックアップする場合
pg_dump -U postgres shop_db > shop_db_backup.sql

# プレーンテキスト形式は pg_restore ではなく psql で復元する（復元先データベースは事前に作成しておく）
psql -U postgres -d shop_db_practice -f shop_db_backup.sql

コマンドを覚えなくても、pgAdmin 4 ではデータベースを右クリックして「Backup...」「Restore...」を選ぶだけで、同じ操作を画面から行えます。日常の運用では、こちらの GUI から実行することが多くなるでしょう。

注意: 復元は必ず練習用データベースで試す

pg_restore や「Restore」を本番のデータベースに直接試すのは絶対にやめましょう。復元先を間違えると、現在のデータが上書き・混在してしまう危険があります。まず練習用のデータベース（shop_db_practice のような別名）を作って復元を試し、手順に問題がないことを確認してから本番の運用計画に組み込みます。

実務で覚える バックアップは「取れているか」より「戻せるか」 — 本番運用では、バックアップを取得するだけでは不十分です。取得したバックアップから実際に復元できるかを定期的に確認する（リストア訓練）ことが重要です。復元できないバックアップは、バックアップが無いのと同じだと考えましょう。

14.8 メンテナンス — VACUUM と ANALYZE 実務で覚える

第13章で「PostgreSQL は更新のたびに古い行の版を残す MVCC という仕組みで動いている」と学びました。この不要になった古い版をそのままにしておくと、テーブルが無駄に膨らんでいきます。それを回収するのが VACUUM です。

maintenance.sql 
-- 不要になった古い行の領域を回収する
VACUUM customers;

-- 実行計画のもとになる統計情報を更新する
ANALYZE customers;

-- 2つをまとめて実行することも多い
VACUUM ANALYZE customers;

ここで注意したいのは、通常の VACUUM が行っているのは、不要になった行の領域を「そのテーブルの中で再利用できる状態」に戻す処理だという点です。通常はOSにディスク容量を返却するものではなく、そのテーブルの中で次の INSERT / UPDATE が領域を再利用できるようにするだけです。

テーブルを作り直して隙間を詰め、OSにディスク容量を実際に返す VACUUM FULL というコマンドもあります。ただし VACUUM FULL は処理中にそのテーブルへ強いロックがかかり、その間は読み書きができなくなります。通常は自動で動く autovacuum（PostgreSQLが自動で VACUUM を実行してくれる仕組み）に任せ、VACUUM FULL はどうしても必要なときに限って計画的に実行するのが基本です。

ANALYZE は VACUUM とは役割が異なり、「この列にはどんな値がどれくらいの割合で入っているか」という統計情報を更新するコマンドです。14.5で見た実行計画は、この統計情報をもとにプランナが立てているため、統計が古いままだと不適切な計画（本来 Index Scan にすべきなのに Seq Scan を選ぶなど）を選んでしまうことがあります。

先ほど触れた autovacuum は、テーブルの更新量に応じて VACUUM と ANALYZE を自動的に実行してくれます。個人学習やごく小規模な運用では、これに任せておくだけで基本的に困りません。日常の確認項目としては、次のようなものを覚えておきましょう。

  • バックアップが定期的に、かつ正常に取得できているか
  • ディスクの空き容量が十分にあるか
  • 特定のクエリだけ極端に遅くなっていないか（遅ければ14.5の EXPLAIN で原因を調べる）

学習を続ける際は、PostgreSQL公式ドキュメント（日本語版）を手元に置いておくことをおすすめします。本ガイドで扱いきれなかった機能や、バージョンごとの違いも正確に確認できます。

やってみよう 14-1: インデックスの前後で実行計画を見比べる

14.5で紹介した EXPLAIN を、自分の手で実行して確かめてみましょう。まずは shop_db の orders テーブルで試し、次に検証用の大きなテーブルで Index Scan への切り替わりを確認します。

手順（前半: orders で試す）

  1. 1 インデックスを作る前に EXPLAIN SELECT * FROM orders WHERE customer_id = 3; を実行し、結果に Seq Scan と表示されることを確認する。
  2. 2 CREATE INDEX idx_orders_customer_id ON orders (customer_id); を実行してインデックスを作成し、同じ EXPLAIN を再実行する。
  3. 3 orders は15件しかないため、インデックス作成後も Seq Scan のままになる場合があります。それ自体が誤りではなく、データ量が少ないときはプランナが「全部読んだほうが速い」と正しく判断しているという良い学びです。練習が終わったら DROP INDEX idx_orders_customer_id; で後片付けする。

手順（後半: 検証用テーブルで Index Scan を実際に見る）

  1. 4 14.5の idx-demo-setup.sql を実行し、50万行の検証用テーブル idx_demo を作成する。
  2. 5 インデックス作成前に EXPLAIN ANALYZE SELECT * FROM idx_demo WHERE code = 250000; を実行し、Seq Scan になることを確認する。
  3. 6 CREATE INDEX idx_demo_code ON idx_demo (code); を実行し、同じ EXPLAIN ANALYZE を再実行して Index Scan に変わったことを確認する。pgAdmin の「Explain」ボタンで図として見比べるのもおすすめ。
  4. 7 確認が終わったら DROP TABLE idx_demo; で後片付けする。

ポイント: インデックスは「作れば必ず使われるもの」ではなく、PostgreSQLがコストを見積もって使うかどうかを決めるものです。小さなテーブルで Seq Scan のままでも心配は不要で、行数が多いテーブルほどインデックスの効果がはっきり現れます。

理解度確認クイズ

  1. Q1. インデックスを作成すると検索が速くなる一方で、何が遅くなりますか。またその理由も答えてください。

    回答を表示

    INSERT / UPDATE / DELETE が遅くなります。これらの操作のたびに、テーブル本体だけでなく、そのテーブルに付いているすべてのインデックスも更新する必要があるためです。あわせてディスク容量も消費します。

  2. Q2. WHERE upper(customer_name) = 'SATO' のように書くと、customer_name に作った通常のインデックスが利用されにくくなることがあります。なぜですか。

    回答を表示

    インデックスは列の「元の値」を整理して並べたものです。upper() で変換した後の値はインデックスの中に存在しないため、元の列に作った通常のインデックスは利用されにくくなり、全件走査（Seq Scan）になりやすくなります。CREATE INDEX ... (upper(customer_name)) のような式インデックスを作れば、この条件でもインデックスを利用できます。

  3. Q3. アプリケーションの接続ユーザーに、スーパーユーザーである postgres をそのまま使うべきではない理由を説明してください。

    回答を表示

    postgres はすべての操作を無制限に行えるスーパーユーザーです。アプリがSQLインジェクションなどで乗っ取られた場合、データベース全体が危険にさらされます。最小権限の原則に従い、アプリごとに必要な操作だけを許可した専用ロールを作成して使うべきです。

  4. Q4. pg_dump で取得したバックアップを pg_restore で復元する練習をするとき、真っ先に守るべきことは何ですか。

    回答を表示

    復元先を本番のデータベースにしないことです。復元先を間違えると現在のデータが上書き・混在してしまう危険があるため、必ず練習用の別データベースを用意し、そこに復元して手順を確認してから本番の運用に組み込みます。
