データベースとテーブルを作る

いよいよ「入れ物」そのものを作る章です。CREATE DATABASE でデータベースを作り、CREATE TABLE でテーブルを作り、そこにサンプルデータを投入します。ここで作る shop_db と4つのテーブルは、第6章以降のすべての章で使い続ける共通の題材です。丁寧に作り込みましょう。

この章の学習目標

  • CREATE DATABASE でデータベースを作成し、接続先を切り替えられる
  • PostgreSQL の主要なデータ型を理解し、目的に応じて選べる
  • NOT NULL・PRIMARY KEY・FOREIGN KEY・UNIQUE・CHECK・DEFAULT の役割を説明できる
  • GENERATED ALWAYS AS IDENTITY で連番を自動採番できる
  • 外部キーの依存関係を踏まえた順序で4つのテーブルを作成し、サンプルデータを投入できる

5.1 データベースを作る — CREATE DATABASE

PostgreSQL をインストールした直後は、postgres という初期データベースにしか接続できません。ここに直接テーブルを作ることもできますが、本ガイドでは学習専用の shop_db という新しいデータベースを作り、そちらにテーブルをまとめます。データベースを作る命令はとてもシンプルです。

create-database.sql 
-- 新しいデータベースを作成する
CREATE DATABASE shop_db;

実行すると一瞬でデータベースの「箱」ができます。しかし、ここで初心者がほぼ必ずつまずくポイントがあります。CREATE DATABASE を実行した直後は、まだ shop_db に接続していません。接続先は自分で切り替える必要があります。

注意: 「テーブルが見当たらない」の9割は接続先の勘違い

shop_db を作った後、うっかり postgres データベースに接続したまま CREATE TABLE を実行すると、テーブルは postgres 側にできてしまいます。「さっき作ったはずのテーブルがない」と混乱したら、まず今どのデータベースに接続しているかを確認しましょう。

接続先の切り替え方は、ツールによって操作が異なります。

ツール 接続先を shop_db に切り替える手順
pgAdmin 4 左のツリーを更新（Databases を右クリック→Refresh）して shop_db を表示し、それをクリックして選択した状態で Query Tool を開く。ツリーで postgres を選んだまま Query Tool を開くと、SQL は postgres 側で実行されてしまう
A5:SQL Mk-2 接続設定を開き、「データベース名」の欄を shop_db に書き換えて再接続する。もしくは shop_db 専用の接続設定をもう1つ新規に作成しておくと、以降の章で postgres 側と混同しにくい

接続先が正しく切り替わったら、以降の CREATE TABLE や INSERT はすべて shop_db に接続した状態で実行してください。本章以降、特に断りがない限り「shop_db に接続している」ことを前提に進めます。

5.2 データ型を知る — 列にはどんな種類のデータが入るか

テーブルの列（カラム）を作るとき、「この列にはどんな種類のデータが入るか」を必ず1つ指定します。これがデータ型です。Excel ではセルに何を入れても自由でしたが、データベースでは列ごとに型を決めることで、間違ったデータが紛れ込むのを防ぎます。本ガイドでよく使う型を一覧にします。

データ型 使用例 用途・ポイント
integer stock_quantity（在庫数） 一般的な整数。約 ±21億まで扱える。個数・件数など普段使う整数の第一候補
bigint アクセスログの行数など integer では桁が足りなくなるような、非常に大きな整数向け。本ガイドの4テーブルでは使用しない
numeric(10,2) unit_price（単価） 全体で10桁・小数点以下2桁まで、誤差なく正確に記録できる。金額はこれを使う
varchar(n) customer_name varchar(50) 最大 n 文字までの可変長文字列。氏名や商品名など、上限を決めやすい文字列に使う
text 商品説明文など 文字数の上限を設けない自由な長さの文字列。PostgreSQL では varchar と性能差はほぼない
date order_date（注文日） 年月日のみを持つ日付。時刻は持たない
timestamp registered_at（登録日時） 年月日と時刻の両方を持つ。いつ登録・更新されたかを記録したいときに使う
boolean is_active（有効フラグ） true / false の2値のみ。「〜かどうか」を表す列に使う

警告: 金額に real・double precision を使ってはいけない

real や double precision は「浮動小数点数」という方式で数値を近似的に記録するため、0.1 を何度も足すと微妙な誤差が生じることがあります。金額のような「1円単位までぴったり合っていないと困る」値には、誤差の出ない numeric(10,2) を必ず使ってください。科学計算のように多少の誤差が許される用途では real 系も選択肢になりますが、本ガイドの4テーブルでは登場しません。

「どれを選べばよいか迷ったら」という方向けに、簡単な指針をまとめます。

  • 整数（個数・件数・ID）→ まず integer を検討する
  • お金の金額 → 必ず numeric(桁数, 小数点以下桁数)（本ガイドは numeric(10,2)）
  • 文字列で長さの上限が決めやすい（氏名・メールアドレス等）→ varchar(n)
  • 文字列で長さを制限したくない（自由記述の説明文等）→ text
  • 「いつ」を記録したい：日付だけでよいか、時刻も必要か → date か timestamp
  • 「はい／いいえ」の2値 → boolean

5.3 制約（constraint）— 間違ったデータを最初から入れさせない仕組み

データ型が「どんな種類の値が入るか」を決めるものだとすれば、制約（constraint）は「その中でも、どんな値なら許すか」を決めるルールです。制約の本質は一貫していて、アプリ側のチェック漏れやヒューマンエラーがあっても、データベース自身が間違ったデータを最初から拒否するという考え方です。代表的な6種類を押さえましょう。

制約 書き方の例 意味
NOT NULL customer_name varchar(50) NOT NULL その列を「未入力（NULL）」のままにすることを許さない
PRIMARY KEY customer_id integer PRIMARY KEY その行を一意に指し示す列。NOT NULL と UNIQUE を兼ねる、表につき原則1つ
UNIQUE email varchar(255) UNIQUE その列の値が表の中で重複しないことを保証する（同じメールアドレスで2重登録できない）
FOREIGN KEY ... REFERENCES customer_id integer REFERENCES customers(customer_id) 別の表に実在する値しか入れられないようにする（存在しない顧客IDの注文を作れなくする）
CHECK CHECK (status IN ('受付', '発送済', 'キャンセル')) 条件式を満たす値しか入れられないようにする。表記ゆれや想定外の値を防ぐ
DEFAULT status varchar(10) DEFAULT '受付' 値を指定しなかったときに自動的に入る初期値を決める

重要: 制約は「後から直す」より「最初から防ぐ」ための仕組み

制約を付けずにテーブルを作ると、動作確認の段階では問題が起きません。しかし運用が進むにつれて、typo の入った status や、存在しない customer_id を参照する注文が静かに紛れ込みます。後から汚れたデータを1件ずつ直すのは大変な作業です。テーブル設計の段階で制約を付けておくことが、結果的に一番の近道です。

5.4 連番の自動採番 — GENERATED ALWAYS AS IDENTITY

主キー（customer_id など）に毎回自分で番号を決めて入れるのは面倒ですし、番号の重複というミスも起きやすくなります。そこで PostgreSQL には、1, 2, 3, ... と自動的に連番を振ってくれる仕組みがあります。現在推奨されている書き方が GENERATED ALWAYS AS IDENTITY です。

identity-vs-serial.sql 
-- 昔からの書き方（serial）: 今も動くが新規には非推奨
customer_id serial PRIMARY KEY,

-- 現在推奨されている書き方（IDENTITY）: 意味は同じで標準SQL準拠
customer_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

serial は PostgreSQL 独自の「糖衣構文」で、実体は「integer 型の列 ＋ 自動生成される連番発行係（シーケンス）＋ そのシーケンスから値を取ってくる DEFAULT」という組み合わせを、まとめて1語で書けるようにしたものです。長年使われてきましたが、標準 SQL の書き方ではありません。PostgreSQL 10（2017年リリース）以降は、標準 SQL に準拠した GENERATED ALWAYS AS IDENTITY が使えるようになり、現在はこちらが推奨されています。

比較項目 serial（旧来の書き方） GENERATED ALWAYS AS IDENTITY（推奨）
標準SQLか PostgreSQL 独自の拡張 標準SQL準拠（PostgreSQL 10以降）
手動での値指定 通常どおり INSERT で値を指定できてしまう ALWAYS の場合は原則拒否され、誤った手動指定を防げる
今後の方針 既存コードとの互換性のために残っている 新規テーブルでは基本的にこちらを使う

本ガイドでは、これから作る4つのテーブルすべての主キーに GENERATED ALWAYS AS IDENTITY を使います。INSERT の際に主キーの列を書かなければ、1から順に自動的に番号が振られます。

5.5 4つのテーブルを作る

いよいよ本ガイド共通のサンプルデータベース「みらい商店」の骨格を作ります。customers（顧客）・products（商品）・orders（注文）・order_items（注文明細）の4つです。

重要: 作成する順序を守る

orders は FOREIGN KEY で customers を参照し、order_items は orders と products の両方を参照します。参照される側の表がまだ存在しないと REFERENCES の指定先が見つからずエラーになるため、customers → products → orders → order_items の順に、必ず「参照される側」から先に作成してください。

flowchart LR A["① customers
（顧客）"] --> C["③ orders
（注文）"] B["② products
（商品）"] --> D["④ order_items
（注文明細）"] C --> D

まずは customers（顧客）テーブルです。主キー customer_id は自動採番、email は重複を許さない UNIQUE、prefecture（都道府県）は未入力を許す（NOT NULL を付けない）列にします。

create-customers.sql 
-- 顧客テーブル（①最初に作成）
CREATE TABLE customers (
    customer_id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_name  varchar(50) NOT NULL,
    email          varchar(255) NOT NULL UNIQUE,
    prefecture     varchar(10),
    birth_date     date,
    registered_at  timestamp NOT NULL DEFAULT now()
);

次に products（商品）テーブルです。category は4種類の文字列に限定する CHECK、unit_price は誤差の出ない numeric(10,2) を使います。

create-products.sql 
-- 商品テーブル（②2番目に作成）
CREATE TABLE products (
    product_id      integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_name    varchar(100) NOT NULL,
    category        varchar(10) NOT NULL
                     CHECK (category IN ('書籍', '文具', '家電', '食品')),
    unit_price      numeric(10,2) NOT NULL CHECK (unit_price >= 0),
    stock_quantity  integer NOT NULL DEFAULT 0,
    is_active       boolean NOT NULL DEFAULT true
);

続いて orders（注文）テーブルです。customer_id に FOREIGN KEY ... REFERENCES を付け、status は3種類の値に限定します。

create-orders.sql 
-- 注文テーブル（③customersを作成した後に作成）
CREATE TABLE orders (
    order_id     integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  integer NOT NULL REFERENCES customers(customer_id),
    order_date   date NOT NULL DEFAULT current_date,
    status       varchar(10) NOT NULL DEFAULT '受付'
                 CHECK (status IN ('受付', '発送済', 'キャンセル'))
);

最後に order_items（注文明細）テーブルです。orders と products の両方を参照する外部キーを持つため、必ず一番最後に作成します。

create-order-items.sql 
-- 注文明細テーブル（④ordersとproductsの後に作成）
CREATE TABLE order_items (
    order_item_id  integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id       integer NOT NULL REFERENCES orders(order_id),
    product_id     integer NOT NULL REFERENCES products(product_id),
    quantity       integer NOT NULL CHECK (quantity > 0),
    unit_price     numeric(10,2) NOT NULL CHECK (unit_price >= 0)
);

order_items にも unit_price を持たせている点に気づいたでしょうか。これは products.unit_price と重複しているように見えますが、意図的な設計です。商品の値段は将来変わる可能性がありますが、「注文した時点の単価」は記録として残しておく必要があるため、注文明細側にも単価を保存します。この考え方は第10〜11章でも登場します。

5.6 サンプルデータを投入する — INSERT INTO

テーブルという「入れ物」ができたので、次はデータを入れていきます。データを1件（1行）追加する命令が INSERT INTO ... VALUES です。VALUES の後にカンマ区切りで複数の行をまとめて書けば、一度にたくさんのデータを登録できます。主キー列は GENERATED ALWAYS AS IDENTITY なので、列名にもVALUESにも書きません。

5.7 作成結果を確認する

データを投入したら、想定どおりの件数が入っているかを確認しましょう。count(*) は「行数を数える」関数で、詳しくは第9章で学びますが、ここでは「件数確認に使える」とだけ覚えておけば十分です。

check-counts.sql 
-- 各テーブルの件数を確認する
SELECT count(*) FROM customers;
SELECT count(*) FROM products;
SELECT count(*) FROM orders;
SELECT count(*) FROM order_items;

あわせて、pgAdmin 4 では左のツリー（Schemas > public > Tables）を展開して4つのテーブルが並んでいること、A5:SQL Mk-2 ではデータベースツリーに同じく4つのテーブルが表示されることも確認してください。ツリーに反映されない場合は、ツリーを右クリックして更新（Refresh）すると表示されます。

動作確認: shop_db が正しく構築できたか

  • pgAdmin 4／A5:SQL Mk-2 のツリーに customers・products・orders・order_items の4つが表示されている
  • SELECT count(*) FROM customers; の結果が 10
  • SELECT count(*) FROM products; の結果が 12
  • SELECT count(*) FROM orders; の結果が 15
  • SELECT count(*) FROM order_items; の結果が 30

件数が合わない場合は、INSERT のどこかでエラーが出て途中で止まっている可能性があります。エラーメッセージを確認し、該当するブロックだけ実行し直してください。

5.8 テーブルの変更と削除 — ALTER TABLE / DROP TABLE

一度作ったテーブルも、後から列を追加したり名前を変えたりできます。命令は ALTER TABLE です。

alter-table.sql 
-- 商品テーブルに「説明」列を追加する
ALTER TABLE products ADD COLUMN description text;

-- 列名を変更する（typo修正などに使う）
ALTER TABLE products RENAME COLUMN description TO product_description;

列を追加する ADD COLUMN はすでにデータが入っているテーブルにも安全に実行できます（既存の行にはその列の値が NULL として追加されます）。列名を変更する RENAME COLUMN も、データはそのままで名前だけが変わります。

一方、テーブルそのものを消す命令が DROP TABLE です。

警告: DROP TABLE は取り消せない

DROP TABLE はテーブルの構造もデータもすべて削除します。第13章で学ぶ ROLLBACK（取り消し）が使えるのはトランザクションを明示的に開始している場合に限られ、通常の操作ではやり直しがききません。実行前に「本当にこのテーブルでよいか」「今どのデータベースに接続しているか」を必ず確認してください。

さらに DROP TABLE にも制約が関わってきます。customers は orders から外部キーで参照されているため、orders を残したまま customers を消そうとするとエラーになります。削除する場合は、作成したときと逆の順序（参照している「子」の表から先）に削除してください。

drop-table.sql 
-- 削除は「参照している側（子）」から順に行う（作成と逆順）
DROP TABLE order_items;  -- ①最初に削除
DROP TABLE orders;       -- ②次に削除
DROP TABLE products;     -- ③次に削除
DROP TABLE customers;    -- ④最後に削除

本ガイドではこの後の章すべてで shop_db のデータを使い続けるため、ここで実際に DROP TABLE を実行する必要はありません。仕組みとして知っておき、練習は次の「やってみよう」で作る自分専用のテーブルで試してみましょう。

やってみよう 5-1: 自分でもう1つテーブルを設計・作成する

shop_db に、商品レビューを記録する reviews テーブルを自分で設計して作ってみましょう。customers と products の両方を参照する、5つ目のテーブルです。

手順

  1. 1 紙かメモアプリに、reviews の列を書き出す。最低限、review_id（主キー）・customer_id（誰が書いたか）・product_id（どの商品か）・rating（評価点）・comment（感想文）・posted_at（投稿日時）を含める。
  2. 2 各列に適切なデータ型を選ぶ（5.2節の表を参照）。rating は整数、comment は長さ制限のない文字列、posted_at は日時にする。
  3. 3 制約を付ける。customer_id と product_id は REFERENCES で外部キーにし、rating には CHECK (rating BETWEEN 1 AND 5) のように1〜5の範囲に収める制約を付ける。
  4. 4 CREATE TABLE reviews (...); を実行してテーブルを作成し、既存の customer_id・product_id を使って2〜3件の INSERT を試す。存在しない customer_id を指定して、外部キー制約が本当にエラーを出すことも確認してみる。

ねらい: テンプレートを写すのではなく、自分で列・型・制約を選ぶ経験をすることが目的です。うまくいかなかったら、エラーメッセージをよく読んで DROP TABLE reviews; で作り直して構いません。

理解度確認クイズ

  1. Q1. CREATE DATABASE shop_db; を実行した直後、なぜ改めて接続先を切り替える必要があるのですか。

    回答を表示

    CREATE DATABASE は新しいデータベースの「箱」を作るだけで、実行した接続先（例えば postgres データベース）はそのままだからです。切り替えないまま CREATE TABLE を実行すると、テーブルは shop_db ではなく元の接続先にできてしまいます。pgAdmin 4 ではツリーで shop_db を選んでから Query Tool を開き、A5:SQL Mk-2 では接続設定のデータベース名を shop_db に変更して再接続します。

  2. Q2. 商品の単価を保存する列に real や double precision を使ってはいけないのはなぜですか。代わりに何を使うべきですか。

    回答を表示

    real や double precision は浮動小数点数で値を近似的に扱うため、計算を繰り返すとわずかな誤差が生じることがあります。金額は1円単位までぴったり合っている必要があるため、誤差の出ない numeric(10,2) のような固定小数点型を使うべきです。

  3. Q3. なぜ customers → products → orders → order_items の順にテーブルを作成する必要があるのですか。

    回答を表示

    orders は FOREIGN KEY ... REFERENCES customers(customer_id) で customers を参照し、order_items は orders と products の両方を参照します。REFERENCES で指す先の表がまだ存在しないと外部キー制約を定義できずエラーになるため、参照される側（親）を先に、参照する側（子）を後に作る必要があります。

  4. Q4. DROP TABLE を実行するときに気をつけるべきことを2つ挙げてください。

    回答を表示

    (1) DROP TABLE は取り消せない操作であり、テーブルの構造とデータが両方とも失われるため、実行前に対象と接続先を必ず確認する。(2) 外部キーで参照されている表（親）は、参照している表（子）を先に削除しないとエラーになるため、作成時と逆順（子から親へ）に削除する必要がある。
