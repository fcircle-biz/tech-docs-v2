第9章 所要時間: 約60分

データを集計する（GROUP BY）

前章では1行ずつの値を加工する関数を学びました。この章では視点を変え、「複数の行をまとめて1つの値にする」集約関数と、行をグループ分けしてグループごとに集計する GROUP BY を学びます。「カテゴリ別の商品点数」「都道府県別の顧客数」など、業務レポートの土台になる考え方です。

この章の学習目標

  • count / sum / avg / max / min の集約関数を使い分けられる
  • count(*) と count(列名) の違い（NULL の扱い）を説明できる
  • GROUP BY でグループ集計ができ、SELECT句に書ける列のルールを守れる
  • HAVING と WHERE の違いを理解し、両方を組み合わせられる

9.1 集約関数とは — たくさんの行を1つの値にまとめる

第8章で学んだ upper や round は、1行の値を受け取って1行の値を返す関数でした（スカラ関数）。これに対し集約関数（集計関数）は、複数行の値をまとめて受け取り、たった1つの値を返す関数です。「注文は全部で何件？」「商品の平均単価はいくら？」といった質問に答えるための関数です。

flowchart LR subgraph S1["スカラ関数（第8章）"] A1["1行入力"] --> A2["upper（）など"] --> A3["1行出力"] end subgraph S2["集約関数（この章）"] B1["複数行入力"] --> B2["count・sumなど"] --> B3["1つの値に集約"] end

代表的な集約関数は次の5つです。まずは一覧で押さえましょう。

関数 意味 対象の列
count 行数を数える 任意（* も可）
sum 合計を求める 数値列のみ
avg 平均を求める 数値列のみ
max 最大値を求める 数値・日付・文字列
min 最小値を求める 数値・日付・文字列
aggregate-basic.sql 
-- products（商品）テーブル全体について
-- 商品数・合計単価・平均単価・最高値・最安値を1行で求める
SELECT count(*) AS 商品数,
       sum(unit_price) AS 単価合計,
       round(avg(unit_price), 0) AS 平均単価,
       max(unit_price) AS 最高値,
       min(unit_price) AS 最安値
FROM products;

結果イメージ:

商品数 単価合計 平均単価 最高値 最安値
12 21880.00 1823 4200.00 150.00

ヒント: 集約関数を使うと結果は必ず1行になる

GROUP BY を使わずに集約関数だけを SELECT すると、元の表が何行あっても結果は必ず1行になります。「表全体を1つの数字（またはいくつかの数字）に要約する」というイメージです。

補足：集約関数とNULLの関係 — sum と avg は、対象列の値がNULLの行を無視して計算します。特に avg（平均）は「合計 ÷ 件数」で求まりますが、この「件数」はNULLでない行の数です。全行数で割っているわけではないので、対象列にNULLが多い場合は平均値の意味合いが変わってくる点に注意してください。

9.2 count(*) と count(列名) の違い — NULL の扱いがカギ

count には書き方が3通りあり、結果が変わることがあります。共通サンプルの customers（顧客）テーブルには prefecture（都道府県）が NULL の行が意図的に含まれているので、これを例に確認します。

書き方 数えるもの
count(*) 条件に合う行そのものの数。NULLの有無を問わずすべて数える
count(列名) その列の値がNULLでない行の数
count(DISTINCT 列名) 発展 その列の重複を除いた値の種類数（NULLは数えない）
count-variants.sql 
-- 顧客の総行数、都道府県が分かる人数、都道府県の種類数を比べる
SELECT count(*) AS 総顧客数,
       count(prefecture) AS 都道府県が分かる人数,
       count(DISTINCT prefecture) AS 都道府県の種類数
FROM customers;

結果イメージ（customers のうち顧客ID 7「山本 恵子」だけ prefecture が NULL のため）:

総顧客数 都道府県が分かる人数 都道府県の種類数
10 9 6

count(*) は10のままですが、count(prefecture) はNULLの1行を除いた9になります。「全体件数」と「ある項目が入力済みの件数」を混同すると、集計レポートの数字がずれる原因になるので要注意です。

9.3 GROUP BY によるグループ集計

ここまでは「表全体」を1つに集約してきました。しかし実務で欲しいのは、たいてい「カテゴリごとの件数」のようにグループ単位の集計です。これを実現するのが GROUP BY です。GROUP BY は「指定した列の値が同じ行どうしをひとまとめにして、そのまとまりごとに集約関数を計算する」という命令です。

flowchart LR A["products全行"] --> B{"categoryで
グループ分け"} B --> C["書籍グループ"] B --> D["文具グループ"] B --> E["家電グループ"] B --> F["食品グループ"] C --> G["件数：2"] D --> H["件数：3"] E --> I["件数：4"] F --> J["件数：3"]
group-by-basic.sql 
-- カテゴリごとの商品数を数える
SELECT category, count(*) AS 商品数
FROM products
GROUP BY category;

結果イメージ:

category 商品数
書籍 2
文具 3
家電 4
食品 3

※ ORDER BY を付けていないため、表示順は実行環境や状況によって変わることがあります。GROUP BY で作られるグループの並び順も保証されないので、順序が必要な場合は次のセクション以降で扱う ORDER BY を書きます。

GROUP BY category と書くだけで、PostgreSQL が自動的にcategoryの値が同じ行をまとめ、まとまりごとにcount(*)を計算してくれます。表を4回に分けて数える手間が、たった2行のSQLで済みます。

9.4 GROUP BY の重要ルール — SELECT句に書ける列

GROUP BY には、初心者がほぼ全員つまずくルールがあります。基本ルールとして、集約関数に入れていない列は、GROUP BY にも書くと覚えてください。SELECT句に生の列（集約関数を通していない列）を書きたいなら、その列を GROUP BY にも同じように書いておく必要がある、という意味です。

最大のつまずきポイント: 「GROUPBYに無い列」をSELECTに書くとエラーになる

product_name（商品名）ごとの値はグループ内で複数あり得るため、「代表してどれを表示すればいいか」をPostgreSQLは決められません。だからエラーで止めてくれます。

エラーになる例と、修正した例を並べて確認しましょう。

ng-example.sql（エラーになる） 
-- product_nameはGROUP BYに無いのにSELECTに書いている → NG
SELECT category, product_name, count(*)
FROM products
GROUP BY category;
-- エラー: column "products.product_name" must
--         appear in the GROUP BY clause
ok-example.sql（修正版） 
-- 修正1: product_nameもGROUP BYに加える（商品ごとの集計に変わる）
SELECT category, product_name, count(*)
FROM products
GROUP BY category, product_name;

-- 修正2: product_nameを諦めてcategoryだけの集計にする
SELECT category, count(*)
FROM products
GROUP BY category;

エラーメッセージ must appear in the GROUP BY clause を見たら、「SELECT句にGROUP BY対象外の生の列がまぎれ込んでいないか」をまず疑ってください。原因のほとんどはこれです。

基本ルール: 集約関数に入れていない列は、GROUP BY にも書く

GROUP BY を使うSELECT句に書けるのは、原則として (1) GROUP BYに指定した列、(2) 集約関数（countなど）、(3) それらの計算式、の3種類です。逆に言えば、集約関数の中に入れていない生の列をSELECT句に書きたいときは、その列をGROUP BYにも書く、というのが基本ルールです。

PostgreSQL独自の例外（関数従属性） 発展

PostgreSQLには、GROUP BYに主キーを指定した場合、その表の他の列もSELECT句にそのまま書けるという例外があります（主キーの値が決まれば同じ行の他の列も一意に決まる、という「関数従属性」という考え方によるものです）。ただしこれはPostgreSQLの拡張仕様であり、他の製品のデータベースでは通用しないことがあります。本教材ではこの例外は扱わず、基本ルールどおり「集約関数に入れていない列は、GROUP BYにも書く」という書き方に統一します。

9.5 複数列でのグループ化

GROUP BY にはカンマ区切りで複数の列を指定できます。この場合、指定した列の組み合わせが同じ行だけが1つのグループになります。

group-by-multi.sql 
-- カテゴリ×販売中/停止中の組み合わせごとに商品数を数える
SELECT category, is_active, count(*) AS 商品数
FROM products
GROUP BY category, is_active
ORDER BY category, is_active;

結果イメージ:

category is_active 商品数
書籍 true 2
文具 true 3
家電 false 1
家電 true 3
食品 true 3

※ ORDER BY category を付けていても、日本語の文字列がどの順に並ぶかは照合順序（第6章）に依存するため、カテゴリの並び順は環境によって変わることがあります。

「同じ家電カテゴリでも、販売中（true）と販売停止（false）で行が分かれている」点に注目してください。家電には販売停止中の商品（旧型キーボード）が1点あるため、家電だけtrueとfalseの2グループに分かれます。他のカテゴリは全商品が販売中（true）のため1グループのままです。GROUP BYの列を増やすほど、グループはより細かく分割されます。

9.6 HAVING による絞り込み — 集計後の条件

第7章の WHERE は「集計する前の1行1行」に対する条件でした。これに対し HAVING は「GROUP BYでまとめたあとのグループ」に対する条件です。「商品が3点以上あるカテゴリだけ見たい」のように、集約関数の結果で絞り込みたいときに使います。WHERE にはまだ集計していないため集約関数を書けません。HAVING は集計後の値に条件をかけるので集約関数を書けます。

SQL文は書いた順番どおりに実行されるわけではありません。「集計前 → GROUP BYでグループ分け → 集計 → 集計後」という論理的な評価順序を図で確認しましょう（実際の実行方法はPostgreSQLのオプティマイザが決めます）。

flowchart LR subgraph G1["集計前"] A["①FROM
表を決める"] --> B["②WHERE
行を絞り込む"] end subgraph G2["GROUP BYと集計"] C["③GROUP BY
グループ分け"] --> Z["集約関数を計算
（count・sumなど）"] end subgraph G3["集計後"] D["④HAVING
グループを絞り込む"] --> E["⑤SELECT
列を出力"] --> F["⑥ORDER BY
並べ替え"] end B --> C Z --> D
句 対象 いつ効く？ 集約関数は書ける？
WHERE グループ分けする前の1行1行 集計前 書けない（まだ集計していないため）
HAVING グループ分けした後の各グループ 集計後 書ける（集計後の値に条件をかけるため）
having-basic.sql 
-- 商品数が3点以上あるカテゴリだけを表示する
SELECT category, count(*) AS 商品数
FROM products
GROUP BY category
HAVING count(*) >= 3;

WHERE と HAVING は併用もできます。「販売中の商品だけを対象に、3点以上あるカテゴリを探す」なら次のようになります。

where-and-having.sql 
-- 販売中(WHERE)の商品を対象に、3点以上あるカテゴリ(HAVING)を探す
SELECT category, count(*) AS 商品数
FROM products
WHERE is_active = true
GROUP BY category
HAVING count(*) >= 3;

ヒント: 覚え方は「WHEREは行、HAVINGはグループ」

迷ったら「集約関数（countなど）を条件に使いたいか？」で判断してください。使いたいならHAVING、使わずに1行ごとの生の値で絞りたいならWHEREです。

9.7 集計結果の並べ替えと件数制限

集計した結果も、第6章で学んだ ORDER BY と LIMIT で並べ替え・件数制限ができます。「商品数が多いカテゴリ トップ3」を出してみましょう。

order-by-count.sql 
-- 商品数が多い順にカテゴリを並べ、上位3件だけ表示する
SELECT category, count(*) AS 商品数
FROM products
GROUP BY category
ORDER BY 商品数 DESC
LIMIT 3;

ここで ORDER BY に count(*) の別名である「商品数」をそのまま書けている点に注目してください。第6章で触れたとおり、ORDER BYではSELECT句で付けた別名（AS）が使えます。一方、WHERE句では別名はまだ計算されていないため使えません（WHERE 商品数 >= 3 のようには書けず、この用途はHAVING count(*) >= 3で書きます）。もちろん ORDER BY count(*) DESC と関数のまま書いても同じ結果になります。

9.8 実務的な集計例

最後に、これまでの知識を組み合わせて実務でよく使う集計を3つ作ります。

(1) カテゴリ別の商品点数と平均単価

category-summary.sql 
-- カテゴリごとの商品点数と平均単価をまとめて集計する
SELECT category,
       count(*) AS 商品点数,
       round(avg(unit_price), 0) AS 平均単価
FROM products
GROUP BY category
ORDER BY category;

(2) 都道府県別の顧客数

prefecture-summary.sql 
-- WHEREでNULLの顧客を除外している
-- （GROUP BY自体はNULLどうしを1つのグループにまとめる）
SELECT prefecture, count(*) AS 顧客数
FROM customers
WHERE prefecture IS NOT NULL
GROUP BY prefecture
ORDER BY 顧客数 DESC;

(3) 月別の注文件数

monthly-orders.sql 
-- to_char（第8章）で日付を「年-月」の文字列に変換してグループ化
SELECT to_char(order_date, 'YYYY-MM') AS 注文月,
       count(*) AS 注文件数
FROM orders
GROUP BY to_char(order_date, 'YYYY-MM')
ORDER BY 注文月;

結果イメージ:

注文月 注文件数
2024-02 5
2024-03 5
2024-04 5

予告: 「カテゴリ別の売上合計」は第11章で完成します

「カテゴリ別の売上金額」を出すには、商品の単価（products）と注文明細の数量（order_items）という別々の表を組み合わせる必要があります。表と表をつなぐ JOIN は第11章のテーマです。この章の GROUP BY ＋ HAVING の知識は、そのままJOIN後の集計にも使えます。

やってみよう 9-1: 自力で集計SQLを書いてみる

pgAdmin 4 または A5:SQL Mk-2 で shop_db に接続し、次の4問に挑戦してください。answerの欄は自分で書いてから確認しましょう。

問題

  1. 1 customersテーブルの総顧客数と、emailが登録されている顧客数を1つのSELECTで求めてください。
    期待結果: 2つの数値が横に並んだ1行（count(*)とcount(email)）。
  2. 2 ordersテーブルを status（受付／発送済／キャンセル）ごとにグループ化し、それぞれの件数を求めてください。
    期待結果: statusと件数の2列、3行（3種類のstatus分）。
  3. 3 productsテーブルをcategoryごとにグループ化し、平均単価が2000円以上のカテゴリだけを表示してください。
    期待結果: category・平均単価の2列。条件を満たすカテゴリのみ（HAVINGを使用）。
  4. 4 order_itemsテーブルをproduct_idごとにグループ化し、注文された合計数量（quantityの合計）が多い順に上位3件を表示してください。
    期待結果: product_id・合計数量の2列、3行（ORDER BY ... DESC LIMIT 3）。

ねらい: 「まとめたい列をGROUP BYに、まとめた値の欲しい形を集約関数で、まとめた後の絞り込みをHAVINGで」という3点セットを、自分の手で組み立てられるようになることが目的です。エラーが出たら、まずSELECT句にGROUP BY対象外の生の列が無いか確認しましょう。

理解度確認クイズ

  1. Q1. count(*) と count(列名) は、何がどう違いますか。

    回答を表示

    count(*) は条件に合う行そのものの数を、NULLの有無に関係なくすべて数えます。count(列名) はその列の値がNULLでない行だけを数えるため、対象列にNULLが含まれているとcount(*)より小さい値になります。

  2. Q2. WHERE と HAVING は、それぞれ何に対する条件ですか。両方を使う例も1つ挙げてください。

    回答を表示

    WHERE はGROUP BYでグループ分けする前の1行1行に対する条件で、集約関数は書けません。HAVING はグループ分けした後の各グループに対する条件で、count(*)などの集約関数を条件に使えます。例: 「販売中の商品（WHERE is_active = true）を対象に、3点以上あるカテゴリ（HAVING count(*) >= 3）を探す」。

  3. Q3. 次のSQLはエラーになります。何が問題で、どう直せばよいですか。
    SELECT category, product_name, count(*) FROM products GROUP BY category;

    回答を表示

    product_name がGROUP BYに指定されておらず、かつ集約関数でもないままSELECT句に書かれているのが原因です（column "products.product_name" must appear in the GROUP BY clauseというエラーになります）。直すには、(1) GROUP BY category, product_name のようにproduct_nameもGROUP BYに加えるか、(2) SELECT句からproduct_nameを外す、のどちらかにします。

  4. Q4. 「売れ筋トップ3」を出すために ORDER BY count(*) DESC LIMIT 3 と書くとき、なぜ ORDER BY 商品数 DESC（AS で付けた別名）のようにも書けるのですか。

    回答を表示

    SQL文はFROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BYの順に処理されます。ORDER BY はSELECTの後に実行されるため、SELECT句で付けた別名（AS）がすでに計算済みで使えます。一方WHEREやHAVINGはSELECTより先に処理されるので、SELECT句の別名はまだ存在せず使えません。
