SELECT文でデータを取り出す

前章で作った shop_db を使い、いよいよ SQL の主役である SELECT を本格的に学びます。列の選び方・並べ方・別名の付け方・計算列・並べ替え・件数の絞り込み・重複の除去という、実務で毎日使う基本パーツを一つずつ押さえ、最後に「SQL文はどの順番で評価されるのか（論理的な評価順序という考え方）」という土台の理解にたどり着きます。

この章の学習目標

  • SELECT ～ FROM の基本形と、* を実務で避けるべき理由を説明できる
  • AS による別名付けと、四則演算・文字列連結による計算列を書ける
  • ORDER BY・LIMIT／OFFSET・DISTINCT を使い分けられる
  • SQL文を「書く順序」と「論理的な評価順序」が違うことを理解し、別名が使える場所・使えない場所を判断できる

6.1 SELECT の基本形

SELECT文の最も基本的な形は、「どの列を」「どのテーブルから」取り出すかを指定するだけのシンプルな構造です。

select-basic.sql 
-- 基本形: SELECT 列 FROM テーブル;
SELECT 列名1, 列名2 FROM テーブル名;

-- customers（顧客）テーブルの全列・全行を取り出す
SELECT * FROM customers;

*（アスタリスク）は「すべての列」を意味する特別な記号です。テーブルにどんな列があるか分からないときに、まず全体を眺めるには便利です。実行結果のイメージは次のようになります。

customer_id customer_name email prefecture birth_date registered_at
1 佐藤 花子 sato.hanako@example.com 東京都 1985-04-12 2024-01-10
2 鈴木 一郎 suzuki.ichiro@example.com 大阪府 1990-07-23 2024-01-15
7 山本 恵子 yamamoto.keiko@example.com （NULL） 1983-06-14 2024-04-02

※ この SELECT には ORDER BY を付けていないため、実際の表示順は保証されません。PostgreSQL では主キー順に並んで見えることが多いですが、これは保証された動作ではなく、並び順が重要なときは必ず ORDER BY を書きます。

しかし、実務で書く SELECT では必要な列だけを名前で指定するのが基本です。理由は2つあります。

理由 説明
列が増減した際の影響 後日テーブルに列を追加すると、SELECT * を使ったプログラムは受け取る列の数や順序が変わり、意図せず壊れることがある
転送量とパフォーマンス 使わない列まで毎回サーバーから送ってもらうのは無駄が多く、大きなテーブルほど負荷が増える
select-columns.sql 
-- 氏名とメールアドレスだけを取り出す
SELECT customer_name, email
FROM customers;

ヒント: 学習中は * を使ってもOK

テーブルの中身をまだ覚えていない学習段階では、SELECT * FROM テーブル名; で全体を確認するのは効率的な使い方です。「本番の業務システムに組み込むコードでは列を明示する」というルールだと覚えておけば十分です。

6.2 列を選ぶ・並べる

SELECT の直後に書く列の順番は自由です。テーブルを作ったときの列の並び（CREATE TABLE での定義順）とは関係なく、SELECT に書いた順番どおりに結果が表示されます。

select-order-columns.sql 
-- 氏名 → 都道府県 の順で表示
SELECT customer_name, prefecture FROM customers;

-- 都道府県 → 氏名 の順で表示（列の並びだけが逆になる）
SELECT prefecture, customer_name FROM customers;

2つのSQLは取り出す列そのものは同じですが、結果の見出し（列の並び順）が入れ替わります。

customer_name prefecture
佐藤 花子 東京都
鈴木 一郎 大阪府
山本 恵子 （NULL）

同じ列を2回書いたり、存在しない列を書くとエラーになりますが、「表示したい順番に、必要な列だけを並べる」という自由度は、レポートや画面表示のために SELECT を書くときに大いに役立ちます。

6.3 別名（AS）

customer_name のような列名はプログラムでは扱いやすい反面、そのまま画面や帳票に出すには味気ないものです。AS を使うと、結果に表示される見出し（別名）を自由に付けられます。

select-as.sql 
-- 見出しを日本語の別名に変える
SELECT customer_name AS 顧客名,
       prefecture AS 都道府県
FROM customers;
顧客名 都道府県
佐藤 花子 東京都
鈴木 一郎 大阪府

別名にスペースや記号を含めたい場合は、ダブルクォートで囲みます。囲まないと、PostgreSQL は空白を区切りとして解釈したり、英字の別名を小文字に統一したりしてしまい、意図した見出しになりません。また、AS というキーワード自体は省略できます。

select-as-quoted.sql 
-- スペースを含む別名はダブルクォートで囲む
SELECT customer_name AS "顧客 名"
FROM customers;

-- AS は省略しても同じ意味になる
SELECT customer_name 顧客名, prefecture 都道府県
FROM customers;

ヒント: AS は省略できるが書いた方が読みやすい

動作としては AS を省略しても構いませんが、「どこからどこまでが列名で、どこからが別名か」が一目で分かるよう、本ガイドでは基本的に AS を書くスタイルで統一します。

6.4 計算列

SELECT には、列名だけでなく計算式を書くこともできます。四則演算（+ - * /）や文字列をつなげる||を使えば、テーブルには保存されていない値をその場で作って表示できます。

select-calculated.sql 
-- 単価に消費税10%を加えた「税込価格」を計算する
SELECT product_name,
       unit_price,
       unit_price * 1.1 AS 税込価格
FROM products;

※ SQLの練習のため、ここでは全商品の税率を一律10%と仮定しています。実際には軽減税率など商品ごとに異なる場合があります。

product_name unit_price 税込価格
SQL入門ガイド 2800.00 3080.000
ワイヤレスマウス 2400.00 2640.000
ノートA5 280.00 308.000

※ この例も ORDER BY がないため、表示される行の順序は保証されません。

文字列同士をつなげたいときは || を使います。宛名を作る、氏名と敬称をつなげる、といった用途で頻繁に使われます。

select-concat.sql 
-- 氏名の後ろに「様」をつなげて宛名を作る
SELECT customer_name || '様' AS 宛先
FROM customers;

計算列は、あくまで結果を表示するときにその場で計算されるだけで、テーブルの中に新しい列が保存されるわけではありません。元の products テーブルには 税込価格 という列は増えていない、という点を意識しておきましょう。

6.5 並べ替え（ORDER BY）

SELECT の結果は、指定しない限りどんな順番で返ってくるか保証されません。特定の並び順にしたい場合は ORDER BY を使います。

select-order-by.sql 
-- 登録日の新しい順（降順）に並べる
SELECT customer_name, registered_at
FROM customers
ORDER BY registered_at DESC;

ASC（昇順・小さい順）が既定値で、省略すると ASC として扱われます。逆順にしたいときは DESC（降順・大きい順）を明示します。

customer_name registered_at
加藤 隆 2024-05-22
小林 麻衣 2024-05-05
中村 翔太 2024-04-18

並べ替えのキーは複数指定できます。先に書いた列で優先的に並べ、同じ値の行が複数あるときだけ次の列で並べ替えます。

select-order-by-multi.sql 
-- 都道府県ごとにまとめ、同じ都道府県内では氏名の五十音順にする
SELECT customer_name, prefecture
FROM customers
ORDER BY prefecture ASC, customer_name ASC;

用語メモ：照合順序（collation） — 文字列をどのような順番で並べるかを決めるルールのことです。customer_name や prefecture のような日本語の文字列を ORDER BY で並べ替えたとき、「五十音順に見える」かどうかは、データベースやカラムに設定された照合順序によって変わることがあります。並び順を厳密に制御したい場合は、環境の照合順序設定を確認しましょう。

ヒント: 列番号ではなく列名で書く

ORDER BY 2 のように SELECT リストの何番目かを数字で指定することもできますが、あとで SELECT の列を増減・並べ替えしたときに意図せず違う列で並べ替わってしまう事故のもとです。本ガイドでは常に列名（または別名）を書くスタイルを推奨します。

もう1つ、初心者がつまずきやすいのが NULL の並び順です。prefecture が未入力（NULL）の顧客がいる場合、PostgreSQL では既定で次のように扱われます。

並べ替え指定 NULL の位置（PostgreSQL の既定）
ORDER BY prefecture ASC NULL は最後（NULLS LAST）
ORDER BY prefecture DESC NULL は最初（NULLS FIRST）

「値が分からないもの」は一番大きな値として扱われる、とイメージすると覚えやすいでしょう。明示的に指定したい場合は ORDER BY prefecture ASC NULLS FIRST のように書くこともできます（詳しい条件指定は第7章で扱います）。

6.6 件数を絞る（LIMIT / OFFSET）

「上位10件だけ見たい」「一覧を1ページ20件で区切って表示したい」といった場面では、LIMIT と OFFSET を使います。LIMIT は取り出す最大件数、OFFSET は先頭から何件をスキップするかを指定します。

select-limit.sql 
-- 登録日が新しい順に、上位3件だけ取り出す
SELECT customer_name, registered_at
FROM customers
ORDER BY registered_at DESC
LIMIT 3;

OFFSET と組み合わせると、ページ送りのような使い方ができます。たとえば「価格の高い順で、6〜10番目の商品」を取り出したいなら次のようになります。

select-limit-offset.sql 
-- 価格が高い順に並べ、先頭5件を飛ばして次の5件を取り出す
SELECT product_name, unit_price
FROM products
ORDER BY unit_price DESC
LIMIT 5 OFFSET 5;

注意: ORDER BY のない LIMIT は「たまたま」の結果

ORDER BY を付けずに LIMIT だけを書くと、「上位◯件」に何の意味も保証されません。PostgreSQL がデータを見つけた順（多くの場合テーブル内部の格納順）で先頭から返すだけなので、データの更新や内部処理のタイミングによって結果が変わることがあります。「上位」「先頭」を意味のあるものにしたいときは、必ず ORDER BY とセットで使うと覚えてください。

豆知識: RDBMS ごとに書き方が違う

LIMIT / OFFSET は PostgreSQL や MySQL で使える書き方です。SQL Server では SELECT TOP 3 のように書き、標準 SQL では FETCH FIRST 3 ROWS ONLY という書き方も定められています（Oracle・SQL Server の新しいバージョンでも使用可）。同じ「上位N件」でも製品ごとに方言があることを覚えておきましょう。

6.7 重複を取り除く（DISTINCT）

「顧客が住んでいる都道府県の種類を知りたい」といった場合、同じ都道府県が何度も出てくる結果は見づらいものです。DISTINCT を使うと、重複した行をまとめて1行だけ表示できます。

select-distinct.sql 
-- 顧客が住んでいる都道府県の一覧（重複なし）
SELECT DISTINCT prefecture
FROM customers;
prefecture
東京都
大阪府
北海道
愛知県
福岡県
神奈川県
（NULL）

※ こちらも ORDER BY がないため、行の並び順は保証されません。並び順を固定したい場合は ORDER BY を追加します。

DISTINCT に複数の列を指定すると、「列の組み合わせ」がすべて一致する行だけを重複とみなします。たとえば注文テーブルで「どの顧客が、どの状態（受付・発送済・キャンセル）の注文を持っているか」の組み合わせ一覧を見たいときに使えます。

select-distinct-multi.sql 
-- 「顧客ID と 状態」の組み合わせで重複を除く
-- 同じ顧客が同じ状態の注文を複数持っていても1行にまとまる
SELECT DISTINCT customer_id, status
FROM orders;

ここで重要なのは、DISTINCT customer_id, status は「customer_id だけ」を重複除去するのではなく、2列の組み合わせ全体が同じ行だけをまとめる、という点です。同じ顧客でも状態が違えば別の行として残ります。

6.8 SQL文が評価される順序

ここまで SELECT → FROM → ORDER BY → LIMIT の順で書いてきましたが、SQLを理解するための論理的な評価順序は、書いた順とは異なります。この違いを知っておくと、次章で学ぶ WHERE でつまずきにくくなります。

件数を切り取る"] end 書く順 -.->|"見た目の順番と

つまり、論理的な評価順序で考えると、まず FROM でテーブルを確認し、WHERE で行を絞り込み、そのあとで初めて SELECT に書かれた列や計算式を評価し、最後に ORDER BY・LIMIT を適用する、という流れになります。ここから、次のような結論が導けます。

※ 実際にどんな手順で処理するかは、PostgreSQL のオプティマイザ（最も速いと判断した実行方法を自動的に選ぶ仕組み）が決めます。結果は、この論理的な評価順序で考えたものと同じになります。

select-alias-in-where-ng.sql 
-- ✕ WHERE の時点ではまだ SELECT が実行されていないため
-- SELECT で付けた別名「税込価格」を WHERE では使えない（エラーになる）
SELECT unit_price * 1.1 AS 税込価格
FROM products
WHERE 税込価格 > 1000;

WHERE で条件を書きたい場合は、別名ではなく元の計算式そのものを書く必要があります（第7章で詳しく扱います）。一方、ORDER BY は SELECT より後に評価されるため、SELECT で付けた別名をそのまま使うことができます。

select-alias-in-order-by-ok.sql 
-- ○ ORDER BY は SELECT より後に評価されるため
-- SELECT で付けた別名「税込価格」を使って並べ替えられる
SELECT product_name, unit_price * 1.1 AS 税込価格
FROM products
ORDER BY 税込価格 DESC;

重要: 迷ったら「論理的な評価順序」に立ち返る

「なぜこの書き方はエラーになるのか」「なぜこっちは動くのか」で迷ったときは、FROM → WHERE → SELECT → ORDER BY → LIMIT という論理的な評価順序を思い出してください。ある句の中では、それより前に評価される句の結果しか使えない、というのが基本ルールです。

やってみよう 6-1: SELECT文を自分で書いてみる

pgAdmin 4 または A5:SQL Mk-2 のクエリツールを開き、shop_db に接続した状態で、次の4問に取り組んでください。

問題

  1. 1 products テーブルから product_name と unit_price を取り出し、価格が高い順に並べ替えるSQLを書いてください。
    期待結果: 「旧型キーボード（4200.00）」が最初の行に来る。
  2. 2 customers テーブルから、住んでいる都道府県の重複のない一覧を取得するSQLを書いてください。
    期待結果: 東京都・大阪府・北海道などが1回ずつだけ表示される（NULLが含まれる場合は1行にまとまる）。
  3. 3 products テーブルから product_name・unit_price、そして消費税10%を加えた金額を「税込価格」という別名で表示し、税込価格が高い順に上位3件だけ表示するSQLを書いてください。
    期待結果: ORDER BY と LIMIT を正しい順番で組み合わせる必要がある。
  4. 4 orders テーブルから、注文日が新しい順に3件だけ取り出すSQLを書いてください。あわせて、なぜこの問題で ORDER BY を省略してはいけないのか、1文で説明してください。

ねらい: ORDER BY・LIMIT・DISTINCT・計算列・AS を組み合わせて、自力でSQLを組み立てる感覚をつかむことが目的です。うまくいかないときは、6.8節の「論理的な評価順序」に立ち返って、句の並べ方を見直してみましょう。

理解度確認クイズ

  1. Q1. 学習用の確認には便利な SELECT * FROM テーブル名; を、実務のプログラムでは避けるべきだと言われる理由を2つ挙げてください。

    回答を表示

    (1) 後日テーブルに列が追加・変更されると、受け取る列の数や順序が変わり、それを前提にしたプログラムが意図せず壊れることがある。(2) 使わない列まで毎回サーバーから送ってもらうことになり、データ量が多いテーブルほど転送量・負荷の無駄が大きくなる。

  2. Q2. ORDER BY prefecture ASC, customer_name ASC と書いた場合、2つの列はそれぞれどのような役割で並べ替えに使われますか。

    回答を表示

    最初に書いた prefecture が優先的な並べ替えキーになり、都道府県の昇順（五十音・コード順）で並びます。prefecture の値が同じ行が複数ある場合に限り、次に書いた customer_name の昇順でさらに並べ替えられます。

  3. Q3. ORDER BY を付けずに LIMIT 3 だけを書いてしまうと、どのような問題が起こり得ますか。

    回答を表示

    「上位3件」に意味のある基準がなく、PostgreSQL がデータを見つけた順（多くの場合テーブル内部の格納順）で先頭から返すだけになります。データの更新や内部処理のタイミングによって実行結果が変わる可能性があり、「上位」「先頭」を意図した取得としては信頼できません。

  4. Q4. SELECT unit_price * 1.1 AS 税込価格 FROM products WHERE 税込価格 > 1000; がエラーになる理由を、SQL文の論理的な評価順序の観点から説明してください。

    回答を表示

    SQL文は書いた順ではなく、FROM → WHERE → SELECT → ORDER BY → LIMIT という論理的な評価順序で評価されます。WHERE が評価される時点では、まだ SELECT の別名「税込価格」は作られていないため、WHERE 句の中でその別名を使うことはできません。条件を書きたい場合は元の計算式 unit_price * 1.1 をそのまま書く必要があります。
