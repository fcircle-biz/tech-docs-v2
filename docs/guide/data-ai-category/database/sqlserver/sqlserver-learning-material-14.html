14.1 SQL Server と PostgreSQL の違い・総復習

第1章から第13章までで少しずつ触れてきた「PostgreSQL との違い」を、9つの分野（製品・ライセンス／構造と用語／データ型／SQL構文／手続き型言語／同時実行制御／性能／セキュリティ／運用）に整理しました。細部を暗記する必要はありません。「この分野は方言レベルの違い」「この分野は設計思想そのものが違う」という違いの性質をつかむことが、この総復習の目的です。

分野 観点 SQL Server PostgreSQL
①製品・ライセンス 提供元とライセンス Microsoft／商用（Developer・Express は無償） PostgreSQL Global Development Group／ソフトウェア自体はオープンソースで無償（サーバー・クラウド利用料や運用にかかる費用は別途発生）
②構造と用語 サーバー全体の単位 インスタンス クラスタ
既定スキーマ dbo public
③データ型 可変長文字列 nvarchar(n) text / varchar(n)
真偽値 bit（0 または 1） boolean（true / false）
日時 datetime2 timestamp
自動採番 IDENTITY serial / GENERATED AS IDENTITY
④SQL構文 件数の絞り込み SELECT TOP n ... LIMIT n
文字列連結 演算子 + 演算子 ||
NULLの代替値 ISNULL(a, b) COALESCE(a, b)（両者とも標準の COALESCE は使用可）
更新結果の取得 OUTPUT 句 RETURNING 句
UPSERT（あれば更新・なければ挿入） MERGE 文 INSERT ... ON CONFLICT
文字列集約 STRING_AGG(列, ',') WITHIN GROUP (ORDER BY 列)（2017以降） string_agg(列, ',' ORDER BY 列)（9.0以降）※関数名は同じだが並び順の指定位置が異なる（第8章）
⑤手続き型言語 名称 T-SQL PL/pgSQL
ストアド呼び出し EXEC proc名 CALL proc名
例外処理 TRY...CATCH EXCEPTION 句（BEGIN...EXCEPTION...END）
⑥同時実行制御 既定の方式 既定はロックベースの READ COMMITTED。READ_COMMITTED_SNAPSHOT（RCSI）を有効にすると、行バージョンを使った読み取りになる MVCC が標準。読み取りが書き込みをブロックしにくい
⑦性能 テーブルの格納構造 クラスター化インデックス（リーフレベルがデータ行そのもので構成され、データがキー順に論理的に整理される） ヒープ格納が基本（別途インデックスを作成）
実行計画の確認 実行プラン（推定・実際の実行プラン） EXPLAIN / EXPLAIN ANALYZE
統計情報の更新 UPDATE STATISTICS（既定で自動更新も有効） ANALYZE（自動 VACUUM/ANALYZE で自動化可）
⑧セキュリティ 権限管理の階層 ログイン（サーバーレベル）とユーザー（DBレベル）の二層構造 ロールに一元化（サーバー・DBの区別なし）
明示的な拒否 DENY で明示的に拒否できる DENY 相当のコマンドはなく REVOKE のみ
接続元の制御 サーバー設定＋ファイアウォールで制御 pg_hba.conf で接続元・認証方式を柔軟に設定
⑨運用 バックアップ BACKUP DATABASE、復旧モデル（単純・完全・一括ログ） pg_dump / pg_basebackup＋WALアーカイブによるPITR
ジョブの自動化 SQL Server Agent cron / pg_cron 拡張など

用語ミニ解説: 表の中で使った略語

  • MVCC: 同じデータの「更新前の姿」を別に取っておき、読み取る人は更新中でも待たずに更新前の姿を読める仕組み（正式名称: MVCC＝多版型同時実行制御。SQL Server では行バージョン管理と呼びます）
  • RCSI（READ_COMMITTED_SNAPSHOT）: 読み取りがロック待ちをせず「更新前の姿」を読む、データベース単位の設定
  • WAL: データ本体を書き換える前に「何をどう変えるか」をログへ先に書き込む方式（英語で Write-Ahead Logging、略して WAL。日本語では先行書き込みログ）
  • PITR: 「何月何日の何時何分の状態」を指定して戻す復元のやり方（正式名称: PITR＝特定時点復旧）
  • CTE: クエリの中に一時的な名前付きの表を用意して、本体のクエリを読みやすくする書き方（WITH 句。正式名称: CTE＝共通テーブル式）
  • 分離レベル: 同時に動いている他のトランザクションの影響を、どこまで見せるか／遮断するかの強さの設定（正式名称: トランザクション分離レベル）

注意: UPSERTの対応表は構文の対応にすぎない

表では UPSERT（あれば更新・なければ挿入）を「SQL Server ＝ MERGE 文／PostgreSQL ＝ INSERT ... ON CONFLICT」と対応づけましたが、これはあくまで構文の対応関係です。MERGE は、複数の処理が同時に同じデータへアクセスするような同時実行性の高いシステムで競合や複雑な問題が発生する場合があることが知られており、Microsoft自身も本番環境で使う前に十分なテストを行うことを推奨しています（詳しくは第7章参照）。

重要ポイント

①〜⑤（製品・構造・型・構文・手続き型言語）はほぼ「方言の違い」で、慣れれば読み替えられます。いっぽう⑥〜⑨（同時実行制御・性能・セキュリティ・運用）は設計思想そのものの違いなので、片方の知識だけで他方を運用しようとすると事故のもとになります。表の下半分は特に意識しておきましょう。

14.2 移行するときに注意すること

SQL Server から PostgreSQL へ（あるいはその逆へ）データベースを移行する場面では、SQL の書き方以外にも「気づきにくい挙動の違い」でつまずきがちです。代表的なポイントを挙げます。

観点 つまずきやすい点 対処のヒント
識別子の大文字小文字と引用符 SQL Server は識別子を [ ] で囲むが照合順序次第で大文字小文字を区別しない場合が多い。PostgreSQL は引用符なしの識別子を自動的に小文字化し、" " で囲むと大文字小文字を区別する。 テーブル名・列名は最初から小文字＋アンダースコアで統一しておくと、移行後の引用符トラブルを避けやすい。
既定の照合順序と文字列比較 SQL Server の既定照合順序は大文字小文字を区別しない（CI）ものが多いが、PostgreSQL は既定の照合順序で大文字小文字を区別する。同じ WHERE name = 'Tanaka' でもヒット件数が変わることがある。 大文字小文字を区別したくない検索は、両DBとも LOWER() 等で明示的にそろえる。
空文字とNULLの扱い SQL Server と PostgreSQL はどちらも空文字（''）と NULL を別物として扱う点は共通だが、NULL を含む文字列連結の挙動（結果全体が NULL になる）を移行元・移行先の両方で再確認しないと、思わぬ空欄が出る。 NULL を無視して連結したい場合は、両者にある CONCAT()（NULL を空文字として扱う）や COALESCE() を活用する。
日付関数名の違い GETDATE() と NOW()、DATEADD/DATEDIFF と日付＋INTERVAL、YEAR()/MONTH() と EXTRACT() のように、関数名も引数の順序も異なる。 日付関数を使っている箇所を洗い出し、一つずつ対応表を作って置き換える。自動変換ツールに任せきりにしない。
自動採番の移行 SQL Server の IDENTITY を PostgreSQL に移す場合は GENERATED BY DEFAULT AS IDENTITY（または serial）に置き換える必要があり、既存データを移行した後は採番値がシーケンスに追いついていない。 データ移行後に setval() でシーケンスを最大値に合わせる。逆方向は DBCC CHECKIDENT で再シードする。
T-SQL固有構文の書き換え ストアドプロシージャ、TRY...CATCH、一時テーブル（#temp）、カーソルなど、T-SQL 独自の構文は PL/pgSQL に自動変換できない部分が多い。 機械的な変換に頼らず、ロジックを一度整理してから PL/pgSQL の書き方で作り直す前提で計画する（第9章参照）。
GO の除去 GO は SQL 自体の構文ではなく、SSMS や sqlcmd が使うバッチ区切りの合図。PostgreSQL 用のスクリプトにそのまま残すと構文エラーになる。 スクリプト移行時に GO をすべて削除し、必要ならセミコロン区切りのトランザクションに整理し直す。

14.3 どちらを選ぶか

「SQL Server と PostgreSQL、結局どちらが優れているのか」という質問をよく耳にしますが、実務では優劣ではなく相性で選ばれます。判断材料になる観点は主に次の5つです。

  • 既存環境: Windows Server や .NET／C# 中心の社内システムかどうか
  • チームのスキル: T-SQL と SSMS に慣れているか、標準SQLとOSSツールに慣れているか
  • ライセンス費用・運用コスト: 商用ライセンス費を許容できるか。PostgreSQL はソフトウェア自体は無償ですが、サーバー・クラウドの利用料や、構築・監視・バックアップ・サポートといった運用にかかる費用は別途発生する点も踏まえて比較する
  • クラウド戦略: Azure 中心か、マルチクラウド／OSS中心か
  • 必要な機能: 高度な可用性・分析機能が必要か、拡張機能（PostGIS等）で柔軟に足したいか
flowchart TD A["新規システムか、既存システムの延長か"] --> B{"既存がWindows／.NET中心？"} B -->|はい| C["SQL Serverが有力"] B -->|いいえ| D{"ライセンス費用を最優先で抑えたい？"} D -->|はい| E["PostgreSQLが有力"] D -->|いいえ| F{"チームにSQL Server運用の経験がある？"} F -->|はい| C F -->|いいえ| G{"クラウドネイティブ・OSS中心の技術戦略？"} G -->|はい| E G -->|いいえ| H["どちらも選択肢。要件を再確認して判断"]

ヒント: 迷ったら「今のチームが幸せに運用できるか」で考える

機能一覧を比べて選ぶよりも、「今のメンバーがこの先も安心して運用・保守できるか」で考えると失敗しにくいです。優劣ではなく相性で選ぶ、というのが本ガイドを通じての結論です。

理解度確認クイズ（総復習）

  1. Q1. SQL Server の IDENTITY 列と、PostgreSQL の serial／GENERATED AS IDENTITY は、それぞれ何のための仕組みで、両者はどう対応しますか。

    回答を表示

    どちらも「列に自動で連番を振る」ための仕組みで、目的は同じです。SQL Server では列定義に IDENTITY(1,1) のように指定し、PostgreSQL では serial 型（内部的にはシーケンス＋デフォルト値）か、より標準SQLに近い GENERATED AS IDENTITY を使います。移行時は自動採番の値そのものではなく、書き方（構文）が変わるだけと理解しておくと混乱しません。

  2. Q2. SQL Server と PostgreSQL の「同時実行制御」の既定方式の違いを説明してください。

    回答を表示

    SQL Server は既定でロックベースの READ COMMITTED を採用しており、書き込み中の行を読み取ろうとするとブロックされることがあります（READ_COMMITTED_SNAPSHOT＝RCSI を有効にすると、更新前の姿を読みに行く行バージョンベースの読み取りになり、ブロックを避けられます）。一方 PostgreSQL は MVCC（多版型同時実行制御）が標準で、読み取りが書き込みをブロックしにくい設計になっています。

  3. Q3. SQL Server の T-SQL スクリプトを PostgreSQL 用に移行するとき、そのまま置いておくと構文エラーになる代表的な記述を1つ挙げ、理由と対処法を説明してください。

    回答を表示

    代表例は GO です。GO は SQL の構文ではなく SSMS や sqlcmd が解釈するバッチ区切りの合図にすぎないため、PostgreSQL のツール（psql 等）ではそのまま構文エラーになります。移行時はスクリプトから GO をすべて削除し、必要に応じてセミコロン区切りやトランザクションで整理し直します。ほかにも TRY...CATCH や一時テーブル（#temp）など、T-SQL 固有の構文は書き換えが必要です。
