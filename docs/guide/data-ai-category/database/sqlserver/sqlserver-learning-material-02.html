アーキテクチャと基本用語

SQL Server を実際に触り始める前に、その中身がどんな構造になっているのかを押さえておきましょう。この章では「インスタンス」「データベース」「スキーマ」「オブジェクト」という階層構造、データを保存するファイルの役割、そして SQL Server 自身が使うシステムデータベースについて学びます。ここで用語を整理しておくと、第3章以降の作業でつまずきにくくなります。

この章で学ぶこと

  • インスタンス・データベース・スキーマ・オブジェクトの階層関係を説明できる
  • データファイル (.mdf/.ndf) とトランザクションログ (.ldf) の役割の違いが分かる
  • master・model・msdb・tempdb という4つのシステムデータベースの役割を説明できる
  • 「データベース.スキーマ.テーブル」という名前解決のしくみと dbo スキーマを理解する

2.1 SQL Serverの全体像

SQL Server の中身は、大きな箱の中に小さな箱が入れ子になった「階層構造」でできています。よく使われるたとえが「ビル」です。SQL Server を1棟のビルだとすると、次のように対応させて考えられます。

インスタンス＝ビル

SQL Server をインストールして起動した「1つの実体」。1台のPCに複数棟建てることもできます。

データベース＝フロア

ビルの中の「1つの階」。用途ごとに販売管理データベース、人事データベースのように分けます。

スキーマ＝部屋

フロアの中の「1つの部屋」。オブジェクトをグループ分けする名前空間です。

オブジェクト＝備品

部屋の中にある「テーブル」「ビュー」などの実体そのものです。

インスタンスとは、SQL Server をインストールして起動した「1つのサーバープロセス」のことです。1台のPC・サーバーに、名前を変えて複数のインスタンスを共存させることもできます（既定のインスタンスは無名、追加インスタンスには名前を付けます）。

1つのインスタンスの中には、複数のデータベースを作成できます。データベースはさらに複数のスキーマ（名前空間）を持ち、スキーマの中にテーブル・ビュー・ストアドプロシージャなどのオブジェクトが実際に作られます。この階層を図にすると次のようになります。

flowchart TD A["インスタンス
（ビル）"] --> B1["データベース: Sales
（フロア）"] A --> B2["データベース: HR
（フロア）"] B1 --> C1["スキーマ: dbo
（部屋）"] B1 --> C2["スキーマ: sales
（部屋）"] C1 --> D1["テーブル: Customers
（備品）"] C2 --> D2["テーブル: Orders
（備品）"] C2 --> D3["ビュー: MonthlySales
（備品）"]

用語: 「サーバー」と「インスタンス」の違い

日常会話では「SQL Serverサーバー」のようにまとめて呼ぶこともありますが、正確には サーバー（PC・マシン） の上で インスタンス（起動した SQL Server の実体） が動いている、という関係です。この章では「インスタンス」という言葉に慣れておきましょう。

2.2 データベースを構成するファイル

1つのデータベースを作成すると、SQL Server はディスク上に最低でも2種類のファイルを作成します。実際のデータそのものと、データへの変更履歴を、あえて別のファイルに分けて保存しているのがポイントです。

データファイル（.mdf / .ndf）

テーブルの中身そのものを保存するファイル。.mdf は必ず1つ存在する「主データファイル」、.ndf は容量分散のために追加できる「補助データファイル」です。

トランザクションログ（.ldf）

「いつ・何が・どう変更されたか」という更新履歴を記録するファイル。データファイルより先に書き込まれます。

「なぜログを別ファイルに分けるのか」と疑問に思うかもしれません。理由は主に2つです。1つ目は安全性です。SQL Server はデータを書き換える前に、必ず「これから何をするか」をログへ先に記録します（Write-Ahead Logging という考え方）。これにより、書き込み中に電源が落ちるなどの障害が起きても、ログを読み返して未完了の変更を取り消したり、やり直したりできます。2つ目は復旧の柔軟性です。ログを個別にバックアップしておけば、「昨日の夜10時時点の状態に戻す」といった特定時点への復旧が可能になります（詳しくは第13章で扱います）。

重要ポイント

「データが本体、ログは記録係」とだけ覚えれば、この段階では十分です。データファイルとログファイルは、別々のディスクに配置することで性能や耐障害性を高めるのが実務上のセオリーですが、学習環境では気にしなくて構いません。

2.3 システムデータベース

SQL Server をインストールすると、自分たちが作る業務用データベースとは別に、SQL Server 自身が動作するために使う4つのシステムデータベースが自動的に作成されます。SSMS のオブジェクトエクスプローラーを開くと「システムデータベース」というフォルダの中に必ず表示されるので、第4章で実際に確認します。

名前 役割
master インスタンス全体の構成情報（ログイン、設定値、他のどのデータベースが存在するか）を記録する「台帳」。壊れるとインスタンスが起動できなくなる、最重要のデータベース。
model 新しいデータベースを作成するときの「ひな形（テンプレート）」。model に変更を加えると、以降に作る新規データベースへその変更が引き継がれる。
msdb SQL Server Agent（ジョブのスケジュール実行）やバックアップ履歴など、運用の裏方情報を管理する。第13章の自動バックアップで登場する。
tempdb 一時テーブルや並べ替えの作業領域として使う「作業机」。インスタンスを再起動するたびに中身がリセットされる。

ヒント: 覚え方

「master は住所録、model は設計図、msdb はスケジュール帳、tempdb は作業机」とイメージすると覚えやすくなります。この4つには自分でテーブルを作ったりせず、業務データは必ず自分専用のデータベースに作成します。

2.4 オブジェクトの名前解決

テーブルなどのオブジェクトを正式に指し示すときは、「データベース名.スキーマ名.オブジェクト名」という3つの部分をピリオドでつないだ3部構成の名前を使います。これは 2.1 で見た「ビル → フロア → 部屋 → 備品」の住所を、そのまま文字で書いたものだとイメージしてください。

実務では、いちいち3部構成をフルで書くのは面倒です。そこで多くの場合、まず USE データベース名 文で「どのデータベースを使うか」を切り替え、スキーマ名も省略して単に テーブル名 だけで参照します。スキーマ名を省略すると、SQL Server は各ユーザーの既定スキーマを補って解決します。特別な設定をしていなければ、既定スキーマは dbo（database owner の略）です。

name-resolution.sql 
-- 使用するデータベースを切り替える
USE Sales;
GO

-- 3部構成のフルネームで参照（省略なし）
SELECT * FROM Sales.dbo.Customers;

-- USE 済みなのでデータベース名は省略できる
SELECT * FROM dbo.Customers;

-- 既定スキーマが dbo なので、スキーマ名も省略できる
SELECT * FROM Customers;

なお、別のインスタンス上のオブジェクトまで指定したい場合は「サーバー名.データベース名.スキーマ名.オブジェクト名」という4部構成も使えます（リンクサーバーという設定が必要になるため、本ガイドでは扱いません）。まずは「3部構成が正式名称、実務では省略が普通」という関係を押さえておけば十分です。

2.5 PostgreSQLとの違い

PostgreSQL にも似た階層構造がありますが、呼び方と挙動にいくつか違いがあります。PostgreSQL の経験がある方は、ここで用語の対応関係を頭の中で結び直しておきましょう。

PostgreSQL との違い（構造と名前解決）

観点 SQL Server PostgreSQL
階層の呼び方 インスタンス → データベース → スキーマ クラスタ → データベース → スキーマ
既定スキーマ dbo public
他DBの直接参照 同一インスタンス内なら3部名で直接参照可能 接続中DB外は直接参照不可（dblink／FDWが必要）
共有の一時領域 tempdb という専用データベースがある 相当する共有DBは無く、一時テーブルは各セッション内で完結
ファイル構成 データベースごとに .mdf / .ndf ＋ .ldf クラスタ共通のデータディレクトリ＋WAL（先行書き込みログ）

とくに重要なのは「既定スキーマ」の違いです。PostgreSQL で public スキーマに慣れていると、SQL Server で dbo スキーマが省略時の既定になる点を最初は忘れがちなので注意しましょう。

ヒント: 「クラスタ」という言葉の違い

PostgreSQL でいう「クラスタ」は、SQL Server の「インスタンス」に近い意味（1つの起動プロセスが管理する範囲）です。一方、一般的に「クラスタリング」というと複数台構成による高可用性をイメージしがちなので混同しないようにしましょう。

やってみよう 2-1: 身近なシステムを階層に当てはめる

SSMS がまだ手元になくても、紙とペンだけでできる練習です。2.1 で学んだ「インスタンス → データベース → スキーマ → オブジェクト」の階層に、自分の知っているシステムを当てはめてみましょう。

手順

  1. 1 身近なシステムを1つ選ぶ（例: 社内の勤怠システム、通販サイト、学校の履修管理）。
  2. 2 そのシステムを「インスタンス」1つとみなし、中に持たせる「データベース」を用途ごとに2〜3個書き出す（例: 勤怠、給与、人事マスタ）。
  3. 3 そのうち1つのデータベースを選び、中に置く「テーブル（オブジェクト）」を3つ以上書き出す（例: 勤怠データベースなら「社員」「打刻履歴」「休暇申請」）。スキーマは特にこだわらず dbo にまとめてよい。
  4. 4 書き出した内容を「データベース名.dbo.テーブル名」の形の文字列にして、3部構成の名前を実際に3つ書いてみる。

ねらい: インスタンス・データベース・スキーマ・オブジェクトという抽象的な用語を、自分の知っている具体的なシステムに結びつけて体感することが目的です。第5章で実際にこの設計を SQL に落とし込みます。

理解度確認クイズ

  1. Q1. インスタンス・データベース・スキーマ・オブジェクトの関係を、ビルのたとえを使って説明してください。

    回答を表示

    インスタンスは1棟のビル、データベースはビルの中の1つのフロア、スキーマはフロアの中の1つの部屋、オブジェクト（テーブルなど）は部屋の中にある備品にあたります。1つのインスタンスに複数のデータベース、1つのデータベースに複数のスキーマ、1つのスキーマに複数のオブジェクトを持たせられます。

  2. Q2. データファイル（.mdf/.ndf）とトランザクションログ（.ldf）は、それぞれ何を記録するファイルですか。なぜ別ファイルに分かれているかも答えてください。

    回答を表示

    データファイル（.mdf/.ndf）はテーブルの中身そのものを保存し、トランザクションログ（.ldf）は「いつ何が変更されたか」という更新履歴を記録します。変更前にログへ先に書き込むことで、障害時に未完了の変更を取り消したり特定時点へ復旧したりできるため、あえて別ファイルに分けています。

  3. Q3. SQL Server の既定スキーマ dbo は、PostgreSQL の何に対応しますか。また、テーブルを3部構成のフル名で参照する書き方を1つ挙げてください。

    回答を表示

    PostgreSQL の既定スキーマ public に対応します。3部構成の書き方は「データベース名.スキーマ名.テーブル名」で、例えば Sales データベースの dbo スキーマにある Customers テーブルなら Sales.dbo.Customers と書きます。
