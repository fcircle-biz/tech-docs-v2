テーブルの結合と集計

ここまでは1つのテーブルを操作してきましたが、実務のデータベースは複数のテーブルに分かれています。この章では、分かれたテーブルを「結合（JOIN）」してつなぎ合わせる方法と、大量の行を「集計（GROUP BY）」して意味のある数字にまとめる方法を学びます。本ガイドの中でも特にボリュームの大きい章です。なお、8.7（CTE）以降は発展的な内容です。まずは8.1〜8.6を確実に身につけることを優先し、余裕ができてから8.7以降に進みましょう。

この章で学ぶこと

  • なぜテーブルを分けるのか（正規化の考え方）を説明できる
  • INNER JOIN・LEFT/RIGHT/FULL OUTER JOIN の違いを使い分けられる
  • GROUP BY・HAVING を使い、グループごとの集計ができる
  • サブクエリで複雑な条件を整理して書ける（CTE は発展内容）
  • （発展）ROW_NUMBER() などウィンドウ関数の基本的な使い方が分かる

8.1 なぜテーブルを分けるのか

もし「注文」に関するすべての情報を1枚の巨大な表にまとめたら、どうなるでしょうか。顧客名・メールアドレス・商品名・単価などを、注文のたびに毎回書き込むことになります。これには2つの大きな問題があります。

問題 具体例
重複 同じ顧客が10回注文すれば、顧客名とメールアドレスが10回同じ内容で書き込まれる。無駄が多い。
更新漏れ 顧客がメールアドレスを変更したとき、10行すべてを更新しないと情報が食い違ってしまう。1行でも直し忘れると矛盾が生まれる。

そこで、「顧客」「商品」「注文」のように性質の異なる情報ごとにテーブルを分け、それぞれに一意な ID（主キー）を振ります。そして注文テーブルには顧客名そのものではなく顧客のID（外部キー）だけを持たせます。こうすれば、顧客名を直す場所は Customers テーブルの1行だけで済みます。この考え方を正規化と呼びます。

本ガイドではこれ以降、学習用データベース SampleShop の3つのテーブルを例に使います。それぞれは ID でつながっています。

erDiagram CUSTOMERS ||--o{ ORDERS : "注文する" PRODUCTS ||--o{ ORDERS : "注文される" CUSTOMERS { int CustomerId PK nvarchar CustomerName nvarchar Email datetime2 CreatedAt } PRODUCTS { int ProductId PK nvarchar ProductName decimal UnitPrice bit IsActive } ORDERS { int OrderId PK int CustomerId FK int ProductId FK int Quantity datetime2 OrderDate }

Orders テーブルは、CustomerId で「誰が」、ProductId で「何を」買ったかを表しています。データを取り出すときは、この ID を手がかりに3つのテーブルを結合（JOIN）して、人間が読みやすい形に組み立て直します。

用語: 主キーと外部キー

主キー（PK）はテーブル内で行を一意に識別する列（例: CustomerId）。外部キー（FK）は別テーブルの主キーを指し示す列（例: Orders.CustomerId が Customers.CustomerId を指す）です。第5章で作成した制約がこの関係を保証します。

8.2 INNER JOIN — 一致する行だけをつなぐ

もっとも基本的な結合が INNER JOIN です。「両方のテーブルに存在し、条件が一致する行」だけを組み合わせます。まず、注文（Orders）とその注文をした顧客（Customers）を結合してみましょう。

inner-join.sql 
-- 注文とその顧客名を取得する
SELECT
    o.OrderId,
    c.CustomerName,
    o.Quantity,
    o.OrderDate
FROM Orders AS o
INNER JOIN Customers AS c
    ON o.CustomerId = c.CustomerId
ORDER BY o.OrderDate;

o や c はテーブル別名（エイリアス）です。テーブル名を毎回フルで書かずに済み、どのテーブルの列かも一目で分かるため、結合を書くときはほぼ必ず使います。実行結果のイメージは次のとおりです。

OrderId CustomerName Quantity OrderDate
1 佐藤商事 3 2026-08-01
2 鈴木商店 1 2026-08-02

ここで重要なのが、ON 句と WHERE 句の役割の違いです。ON 句は「どうテーブルをつなぐか」という結合条件、WHERE 句は「つないだ結果からどの行を残すか」という絞り込み条件です。役割が違うため、混同すると意図しない結果になります（特に外部結合で顕著です。8.3で扱います）。

8.3 外部結合 — 一致しない行も残す

INNER JOIN では「一度も注文していない顧客」は結果に出てきません。両方に一致する行しか残らないからです。しかし業務では「注文が1件もない顧客を洗い出したい」という場面がよくあります。そこで使うのが外部結合（OUTER JOIN）です。

結合の種類 残る行 一致しない側の値
INNER JOIN 両方に一致する行のみ （該当なし）
LEFT OUTER JOIN 左側（FROM側）のテーブルの全行 右側の列は NULL
RIGHT OUTER JOIN 右側（JOIN側）のテーブルの全行 左側の列は NULL
FULL OUTER JOIN 両方のテーブルの全行 一致しない側は NULL

「注文がない顧客」を探すには、Customers を左側にして LEFT OUTER JOIN し、右側（Orders）の列が NULL になっている行だけを絞り込みます。ここで WHERE を使う理由が分かります。ON 句に条件を書くと結合のしかたが変わってしまい、WHERE 句に書いてはじめて「結合した後の絞り込み」になるのです。

left-join.sql 
-- 注文が一度もない顧客を探す
SELECT
    c.CustomerId,
    c.CustomerName,
    o.OrderId
FROM Customers AS c
LEFT OUTER JOIN Orders AS o
    ON c.CustomerId = o.CustomerId
WHERE o.OrderId IS NULL;

結果に出てくる OrderId 列の NULL は「一致する注文が存在しなかった」ことを意味します。この「NULL になる」という性質そのものが、外部結合の使いどころです。

なお RIGHT OUTER JOIN は、テーブルの並び順を入れ替えれば LEFT OUTER JOIN で書き直せます。実務では読みやすさの観点から LEFT OUTER JOIN に統一するチームが多いです。FULL OUTER JOIN は「両方の欠けを同時に見たい」ときに使いますが、頻度は高くありません。

補足: CROSS JOIN

CROSS JOIN は結合条件（ON句）を持たず、片方の全行ともう片方の全行のすべての組み合わせ（直積）を作ります。3商品×2顧客なら6行になります。日付一覧×商品一覧でカレンダー的な表を作る場合など特殊な用途で使い、通常の業務クエリではほとんど使いません。

8.4 3つ以上のテーブルを結合する

実務のクエリでは、2テーブルの結合だけでは足りないことがほとんどです。「誰が・何を・いくつ買ったか」を1行にまとめるには、Orders・Customers・Products の3つを結合します。JOIN は何回でも重ねて書くことができます。

three-table-join.sql 
-- 誰が何をいくつ買ったかを一覧にする
SELECT
    c.CustomerName,
    p.ProductName,
    o.Quantity,
    o.Quantity * p.UnitPrice AS SubTotal
FROM Orders AS o
INNER JOIN Customers AS c
    ON o.CustomerId = c.CustomerId
INNER JOIN Products AS p
    ON o.ProductId = p.ProductId
ORDER BY c.CustomerName;

ポイントは、「注文（Orders）を軸に、そこへ顧客情報・商品情報を1つずつ足していく」というイメージで書くことです。3つ目以降を結合するときも書き方は変わらず、INNER JOIN テーブル名 AS 別名 ON 結合条件 を続けて書くだけです。

重要ポイント

結合するテーブルが増えても、SQL Server は指定した条件を満たす組み合わせを実行計画として組み立て、結果を返します（実際にどれだけ効率よく処理できるかはインデックスの設計などにも左右されます。詳しくは第11章で扱います）。書く側は「どのテーブルとどのテーブルが、どの列で結びつくか」を1つずつ正確に指定することだけを意識すれば十分です。

8.5 集計する — GROUP BY と集計関数

「顧客ごとの注文件数」「商品ごとの合計売上」のように、行をグループにまとめてから数を数えたり合計したりする処理を集計と呼びます。SQL Server には次の集計関数があります。

関数 意味
COUNT 件数を数える
SUM 合計を求める
AVG 平均を求める
MIN / MAX 最小値・最大値を求める

集計関数は単独でも使えますが、真価を発揮するのは GROUP BY と組み合わせたときです。GROUP BY は「指定した列の値が同じ行どうしを、1つのグループにまとめる」働きをします。まずグループ分けをしてから、グループごとに集計する、という順序で考えるのがコツです。

group-by.sql 
-- 顧客ごとの注文件数と合計購入金額
SELECT
    c.CustomerName,
    COUNT(*) AS OrderCount,
    SUM(o.Quantity * p.UnitPrice) AS TotalAmount
FROM Orders AS o
INNER JOIN Customers AS c ON o.CustomerId = c.CustomerId
INNER JOIN Products AS p ON o.ProductId = p.ProductId
GROUP BY c.CustomerName
HAVING SUM(o.Quantity * p.UnitPrice) >= 10000
ORDER BY TotalAmount DESC;

ここで登場する HAVING にも注目してください。WHERE は「グループ分けする前の、1行ずつの絞り込み」に使うのに対し、HAVING は「グループ分けした後の、集計結果に対する絞り込み」に使います。SUM(...) のような集計結果で条件を書けるのは HAVING だけです。

この違いは、SQL が実際にどの順番で処理されるかを知ると腑に落ちます。SELECT 文は書いた順（SELECT → FROM → ...）ではなく、次の順番で実行されます。

flowchart LR A["1. FROM
テーブルを決める"] --> B["2. WHERE
行を絞り込む"] B --> C["3. GROUP BY
グループ分けする"] C --> D["4. HAVING
グループを絞り込む"] D --> E["5. SELECT
出力する列を決める"] E --> F["6. ORDER BY
並び替える"]

WHERE の時点ではまだグループが存在しないため集計関数は使えず、HAVING の時点ではすでにグループができあがっているため集計関数が使える、と覚えておきましょう。

用語: COUNT(*) と COUNT(列名) の違い

COUNT(*) は行そのものの数を数えます（NULLでも数える）。一方 COUNT(Email) のように列を指定すると、その列が NULL でない行だけを数えます。「登録済みの顧客数」と「メールアドレスが入力済みの顧客数」がずれるのは、この違いが原因になっていることがよくあります。

8.6 サブクエリ — クエリの中にクエリを書く

サブクエリ（副問い合わせ）とは、SELECT 文の中にさらに別の SELECT 文を書く手法です。「平均より高い商品」のように、集計結果と比較したい場合によく使います。

scalar-subquery.sql 
-- 平均単価より高い商品を調べる
SELECT ProductName, UnitPrice
FROM Products
WHERE UnitPrice > (SELECT AVG(UnitPrice) FROM Products);

カッコの中の (SELECT AVG(UnitPrice) FROM Products) のように、結果が「1行1列＝値ひとつ」になるサブクエリをスカラーサブクエリと呼びます。SELECT 句や WHERE 句に、値ひとつとしてそのまま書けるのが特徴です。値が1つに定まるからこそ、> のような比較演算子と組み合わせられます。

複数行を返すサブクエリを条件に使うときは、IN がよく使われます。「一度でも注文したことがある顧客」を、Orders テーブルに存在する CustomerId の一覧を使って求めてみましょう。

in-subquery.sql 
-- IN: サブクエリが返す値のリストに含まれるか
SELECT CustomerName
FROM Customers
WHERE CustomerId IN (SELECT CustomerId FROM Orders);

IN は「一覧の中に自分がいるか」を確認するイメージです。サブクエリが返す値の一覧に対して、外側の行の値が含まれているかどうかを調べます。読みやすく、初学者はまずこの書き方に慣れれば十分です。

発展: EXISTS — 存在確認で判定するサブクエリ

IN のほかに、EXISTS という書き方もあります。「1件でも当てはまる行があれば、それ以上探さずに即座に真と判定する」という考え方のサブクエリで、先ほどと同じ「一度でも注文したことがある顧客」を次のようにも書けます。

exists.sql 
-- EXISTS: 条件に一致する行が「存在するか」だけを確認する
SELECT CustomerName
FROM Customers AS c
WHERE EXISTS (
    SELECT 1 FROM Orders AS o
    WHERE o.CustomerId = c.CustomerId
);

「大量データでは IN より EXISTS の方が速い」と一概には言えません。実際にどちらが速いかは、データの分布・インデックスの有無・SQL Server がそのとき選ぶ実行計画によって変わります。気になる場合は実行プランを見て比較してみましょう（第11章で扱います）。初学者のうちは、読みやすいと感じる方を選べば十分です。どちらもよく使われる書き方です。

8.7 CTE（WITH句） — クエリに名前をつけて読みやすくする 発展

ここからは発展内容です

この節はいま理解できなくても先に進んで構いません。8.6までのJOIN・GROUP BY・サブクエリ（本編）を使えるようになってから戻ってくると理解しやすい内容です。

結合や集計が増えてくると、サブクエリが何重にも入れ子になり読みにくくなります。そこで使うのが、クエリの中に一時的な名前付きの表を用意して、本体のクエリを読みやすくする書き方のCTE（共通テーブル式）です。WITH 名前 AS (...) という形で、クエリの一部に一時的な名前を付けて先に定義しておけます。

8.5 で書いた「顧客別合計金額」のクエリを、CTE を使って書き直してみましょう。

cte.sql 
-- 顧客別合計金額をCTEで求めて上位だけ絞り込む
WITH CustomerTotal AS (
    SELECT
        c.CustomerId,
        c.CustomerName,
        SUM(o.Quantity * p.UnitPrice) AS TotalAmount
    FROM Orders AS o
    INNER JOIN Customers AS c ON o.CustomerId = c.CustomerId
    INNER JOIN Products AS p ON o.ProductId = p.ProductId
    GROUP BY c.CustomerId, c.CustomerName
)
SELECT CustomerName, TotalAmount
FROM CustomerTotal
WHERE TotalAmount >= 10000
ORDER BY TotalAmount DESC;

CustomerTotal という名前の「一時的な結果セット」を先に用意し、あとの SELECT ではまるで普通のテーブルであるかのように扱えます。集計結果に対する絞り込みに HAVING ではなく WHERE を使えるようになる点にも注目してください。すでに集計が終わった後の結果を見ているだけだからです。絞り込みの条件と並び順の考え方は 8.5 の HAVING を使った書き方と同じですが、「まず合計を出す→そのあと絞り込む」という手順が名前付きで分かれるため、クエリが長くなるほど読みやすさの差が出ます。

8.8 ウィンドウ関数入門 発展

ここからは発展内容です

この節はいま理解できなくても先に進んで構いません。JOIN と GROUP BY（8.2〜8.5・本編）を使えるようになってから戻ってくると理解しやすい内容です。

GROUP BY は行をまとめて1行に集約しますが、ウィンドウ関数は行をまとめずに残したまま、グループごとの計算結果を各行に付け足す関数です（OVER 句を伴う関数群。正式名称: ウィンドウ関数）。少し高度な内容なので、まずは ROW_NUMBER() だけ覚えれば十分です。慣れてきたら RANK() や SUM() OVER も試してみましょう。

row-number.sql 
-- 顧客ごとに注文を新しい順に並べて連番をつける
SELECT
    CustomerId,
    OrderId,
    OrderDate,
    ROW_NUMBER() OVER (
        PARTITION BY CustomerId ORDER BY OrderDate DESC, OrderId DESC
    ) AS OrderRank
FROM Orders;

PARTITION BY は、ウィンドウ関数で「どの単位でグループ分けするか」を指定する部分です（GROUP BY に相当しますが、行はまとめられません）。PARTITION BY CustomerId が「グループ分けの基準」、続く ORDER BY OrderDate DESC, OrderId DESC がグループ内の並び順です。全件そのまま出力され、各行に「その顧客の中で何番目の注文か」という番号が付きます。OrderRank = 1 の行だけを取り出せば「顧客ごとの最新注文」を1件ずつ取得できます。

ここで ORDER BY OrderDate DESC, OrderId DESC のように OrderId を2番目の並び順として加えている点にも注目してください。もし同じ顧客が同じ日時に複数回注文していた場合、OrderDate だけでは並び順が一意に決まりません。その結果、実行するたびに1位と2位が入れ替わってしまう可能性があります。このように同じ値が重複しうる列だけで ORDER BY を書くと、順序が安定しないことがあります。OrderId のように値が重複しない列を2番目の並び替えキー（同着を防ぐ「タイブレーク」列）として添えておくと、常に同じ結果になり安全です。

RANK() は ROW_NUMBER() に似ていますが、同順位があると番号が飛びます（1, 2, 2, 4のように）。SUM() OVER (...) のように集計関数を OVER と組み合わせると、行を保ったまま累計や小計を計算できます。これらも ORDER BY の対象列の値が重複しうる場合は、同じ理由でタイブレーク列を添えておくと安全です。

running-total.sql 
-- 顧客ごとの累計購入金額を求める
SELECT
    c.CustomerName,
    o.OrderId,
    o.OrderDate,
    o.Quantity * p.UnitPrice AS Amount,
    SUM(o.Quantity * p.UnitPrice) OVER (
        PARTITION BY c.CustomerId ORDER BY o.OrderDate, o.OrderId
    ) AS RunningTotal
FROM Orders AS o
INNER JOIN Customers AS c ON o.CustomerId = c.CustomerId
INNER JOIN Products AS p ON o.ProductId = p.ProductId;

この累計計算でも考え方は同じです。同じ顧客が同じ日時に複数回注文していると o.OrderDate だけでは順序が一意に決まらず、累計の積み上がり方が実行のたびに変わってしまう可能性があるため、o.OrderId をタイブレーク列として ORDER BY に添えています。

ヒント: 今は雰囲気だけつかめば十分

ウィンドウ関数は奥が深く、実務でも「使えると便利だが、なくても他の方法で代替できる」機能です。この段階では「GROUP BY と違って行が消えない」「PARTITION BY はグループ分け、OVER の中に書く」という感覚だけつかめば十分です。

8.9 PostgreSQLとの違い

JOIN・GROUP BY・CTE・ウィンドウ関数の基本的な構文は SQL Server と PostgreSQL でほぼ共通しており、そのまま移植できることが多い部分です。違いが出やすいのは、いくつかの専用関数や構文です。

PostgreSQL との違い（結合・集計）

観点 SQL Server PostgreSQL
JOIN / GROUP BY / CTE 標準構文とほぼ同じ 標準構文とほぼ同じ（移植しやすい）
ウィンドウ関数 ROW_NUMBER / RANK / OVER に対応 同様に対応（考え方も共通）
文字列の集約 STRING_AGG(列, ',')
WITHIN GROUP (ORDER BY 列)		 string_agg(列, ',' ORDER BY 列)
グループ内の代表行抽出 相当構文がなく ROW_NUMBER() で代替 DISTINCT ON (列) が使える
古い連結テクニック FOR XML PATH による文字列連結（STRING_AGG登場前の名残） 同様の需要は string_agg で解決済み
日付の差 DATEDIFF(day, 開始日, 終了日) 日付同士を 終了日 - 開始日 で引き算
SELECTの別名をGROUP BYで使用 不可（元の列名か式を書く） 可（出力列名を書ける独自拡張）

JOIN・GROUP BY・CTE・ウィンドウ関数の骨格は共通なので、PostgreSQL の経験があれば大きくつまずくことはありません。「専用関数の名前」と「グループ内の代表行の取り方」だけ、SQL Server 流に読み替えれば十分です。

補足: SELECTの別名をGROUP BYで使えない理由

SQL の実行順序（8.5の図）を思い出すと分かるとおり、GROUP BY は SELECT より前に処理されます。SELECT で付けた別名がまだ存在しないタイミングなので、SQL Server では GROUP BY に元の列名（または式そのもの）を書く必要があります。なお PostgreSQL は独自拡張として GROUP BY に出力列名（別名）を書くことを許容しており、ここは移植時に差が出る点です。

やってみよう 8-1: 購入金額トップ3の顧客を求める

SampleShop の Orders・Customers・Products を使い、「顧客ごとの購入金額合計」を求め、金額の多い順に上位3件だけを表示するクエリを書いてみましょう。

手順

  1. 1 Orders・Customers・Products を INNER JOIN で結合する（8.4を参照）。
  2. 2 GROUP BY で顧客ごとにまとめ、SUM(Quantity * UnitPrice) で購入金額合計を求める。
  3. 3 ORDER BY で合計金額の多い順（DESC）に並び替える。
  4. 4 第6章で学んだ SELECT TOP (3) を先頭に付けて、上位3件だけに絞り込む。

ヒント: 迷ったら、まず GROUP BY なしで3テーブルを結合した状態を SELECT * で確認し、次に GROUP BY と SUM を足し、最後に ORDER BY と TOP を足す、というように一段階ずつクエリを育てていくと間違いに気づきやすくなります。

理解度確認クイズ

  1. Q1. INNER JOIN と LEFT OUTER JOIN の結果はどう違いますか。「注文のない顧客」を例に説明してください。

    回答を表示

    INNER JOIN は両方のテーブルに一致する行だけを残すため、注文のない顧客は結果に出てきません。LEFT OUTER JOIN は左側（Customers）の全行を残し、一致する注文がなければ右側（Orders）の列は NULL になります。そのため「注文のない顧客」は WHERE 句で右側の列が NULL の行を絞り込むことで見つけられます。

  2. Q2. WHERE 句と HAVING 句の違いを、どちらが先に処理されるかを含めて説明してください。

    回答を表示

    WHERE は GROUP BY より前に処理され、集計する前の1行ずつを絞り込みます。集計関数は使えません。HAVING は GROUP BY の後に処理され、集計してできあがったグループに対して絞り込みます。SUM や COUNT のような集計結果を条件に書けるのは HAVING だけです。

  3. Q3. COUNT(*) と COUNT(Email) では、結果が異なる場合があります。なぜですか。

    回答を表示

    COUNT(*) は行そのものの数を数えるため、NULL を含む行も数えます。一方 COUNT(Email) は Email 列が NULL でない行だけを数えます。Email が未入力（NULL）の顧客がいる場合、COUNT(*) の方が COUNT(Email) より大きな値になります。
