SQL Lab入門

SQL Lab は Superset に内蔵された SQL エディタです。この章では、第4章で作成したデータベース接続に対してクエリを実行し、結果を確認・保存する一連の流れを学びます。チャートを作る前に、まず自分の目でデータを確かめる——この習慣が、後の章で作るチャートやダッシュボードの精度を大きく左右します。

この章で学ぶこと

  • SQL Lab が Superset の中でどんな役割を持つ画面かを説明できる
  • データベースとスキーマを選び、SQL を実行して結果を確認できる
  • 保存クエリとクエリ履歴を使って、実行した SQL をチームで再利用できる
  • 実行結果を仮想データセットとして保存し、チャート作成につなげる流れを理解する

5.1 SQL Lab とは

SQL Lab は、Superset に内蔵された SQL エディタです。ブラウザ上で SQL を書き、接続先のデータベースに対してその場でクエリを実行し、結果を表形式で確認できます。第1章で見たとおり Superset は「Database 接続 → Dataset → Chart → Dashboard」という積み上げでできていますが、SQL Lab はこの積み上げに入る前の場所にある、いわば作業台です。

いきなりチャート作成から始めると、「このテーブルにはどんな列があるのか」「この集計で本当に正しい数字が出るのか」を確かめないまま作業を進めてしまいがちです。SQL Lab は、チャートを作る前に、データを自分の目で確かめる場所だと考えてください。ここで試行錯誤して SQL を固め、良い結果が得られたらデータセットとして保存し、次の章以降でチャートに仕立てていきます。

SQL Lab の画面でデータベースを選ぶとき、選択肢に出てくるのはすべての接続ではありません。第4章で見た Expose database in SQL Lab（既定でオン）という設定がオフになっている接続は候補から外れます。探している接続が一覧に出てこない場合は、その接続の設定を確認してもらいましょう。

なぜ接続ごとに SQL Lab の利用可否があるのか

SQL Lab は誰でも自由に SQL を打てる強力な画面です。本番の業務データベースに対して野良のクエリを実行されると困る、という管理者は多いはずです。そのため接続単位で「SQL Lab からの利用を許可するかどうか」を切り替えられるようになっています。閲覧・分析専用の接続だけを SQL Lab に公開する、という運用が一般的です。

5.2 画面の構成

SQL Lab の画面は大きく3つの領域に分かれています。それぞれの役割を先に押さえておくと、実際に SQL を書くときに迷いません。なお、以下の名称や配置は執筆時点のものです。Superset はバージョンによって画面のラベルや位置が変わることがあるため、お使いの環境と多少異なる場合があります。

左: スキーマ／テーブル一覧

データベースとスキーマを選ぶと、その中のテーブル一覧が表示されます。テーブル名をクリックすると列名や型が展開され、プレビューでデータの中身を少件数だけ確認できます。

中央: SQL エディタ

SQL を書く欄です。タブを複数開けるので、テーブルごと・目的ごとにタブを分けて並行して試行錯誤できます。開いたタブは閉じるまで残ります。

下: 結果パネル

実行結果が表示される「Results」と、過去の実行を確認する「Query history」などのタブがあります。エディタの下に固定表示され、境界をドラッグして広さを調整できます。

初めて開くと情報量が多く感じるかもしれませんが、やることは「左でテーブルを探す → 中央で SQL を書く → 下で結果を見る」という単純な繰り返しです。タブを分けられる点も覚えておくと便利で、1つのタブで集計を試しながら、別タブで元テーブルの中身を確認する、といった使い方ができます。

5.3 クエリを実行する

クエリを実行する前に、左パネル上部のプルダウンでデータベースとスキーマを選びます。この2つを選ぶと、その下のテーブル一覧に該当するテーブルが表示されるようになります。あとは SQL を書いて実行するだけです。

実行方法は2通りあります。画面上の「Run」ボタンを押す方法と、キーボードショートカット（Ctrl+Enter、Mac では Cmd+Enter）を使う方法です。何度も書き直しながら試行錯誤するときは、ショートカットのほうが手が止まらず快適です。ショートカットキーはバージョンによって異なる場合があるため、エディタ付近の表示もあわせて確認してください。

SQL Lab: テーブルの中身を確認する形（汎用例） 
-- 自分のテーブルに置き換えて使う一般形（ordersは架空のテーブル名）
-- テーブル名・列名は環境に合わせて読み替えてください
SELECT
    order_id,
    order_date,
    customer_name,
    amount
FROM orders
LIMIT 10;

次は GROUP BY を使った集計の例です。今度は第2章のサンプルデータに実在するテーブル cleaned_sales_data を使い、この環境でそのまま実行できる形にしています。件数の多いテーブルにいきなり全件集計を投げるのではなく、まずは少件数・短期間に絞って正しい SQL かどうかを確かめる癖をつけましょう。

SQL Lab: 月ごとの売上合計を集計（cleaned_sales_dataで実行可能） 
-- 月ごとの売上合計を求める（サンプルデータ cleaned_sales_data を使用）
-- DATE_TRUNCはPostgreSQL系の書き方。DBにより関数名が異なる
SELECT
    DATE_TRUNC('month', order_date) AS sales_month,
    SUM(sales) AS total_sales
FROM cleaned_sales_data
GROUP BY 1
ORDER BY 1
LIMIT 100;

2つ目の例のように、日付を月や日で丸める関数はデータベースの種類によって名前や書き方が異なります（例: PostgreSQL 系の DATE_TRUNC、MySQL の DATE_FORMAT など）。接続しているデータベースの方言に合わせて書き換えてください。

LIMIT の既定値にも注意

SQL 自体に LIMIT を書かなくても、SQL Lab の画面には取得件数を制限するプルダウンがあり、既定でもある程度の件数（多くの場合1,000件程度）までしか結果を取得しません。この既定値は環境設定やバージョンによって異なります。とはいえ、SQL 側にも明示的に LIMIT を書き、まず少件数で結果を確かめる習慣をつけておくと安全です。

5.4 結果の確認と持ち出し

クエリを実行すると、下の結果パネルに表形式でデータが表示されます。列ヘッダーをクリックすると並べ替えができ、検索ボックスにキーワードを入れると結果内を絞り込めます。件数が多い結果でも、この画面上である程度は目視確認が完結します。

結果を外部に持ち出したいときは、CSV ダウンロードとクリップボードへのコピーという2つの手段が用意されています。CSV はファイルとして保存してほかのツールに読み込みたいとき、クリップボードコピーはチャットやドキュメントに数値を貼り付けたいときに使います。

CSV に落として Excel で作業し直すのは「BI化の逆戻り」

結果を CSV でダウンロードし、毎回 Excel で集計・グラフ化する運用を続けてしまうと、第1章で見た「Excel は版が乱立しやすい」という弱点をそのまま持ち込むことになります。SQL Lab での確認はあくまで途中の検証作業と位置づけ、繰り返し使う集計は次のセクションの手順でデータセット化し、チャートやダッシュボードとして Superset 側に残すようにしましょう。CSV 書き出しは、一時的な確認や他システムへの受け渡しに限定するのが安全です。

5.5 保存クエリとクエリ履歴

よく使う SQL は、毎回書き直す必要はありません。エディタのSaveから名前を付けて保存すると「保存クエリ（Saved queries）」になり、一覧画面からいつでも呼び出せます。「先月も似た集計をしたはず」というとき、保存クエリを探すところから始めれば、SQL をゼロから書き直す時間を省けます。

もう1つ、Query history（クエリ履歴）という画面では、保存していないものも含めてSQL Lab で実行したクエリが一覧で残ります。誰が実行したか、いつ実行したか、何行返ってきたか、成功したか失敗したかを後から確認できるため、「前に書いた SQL をもう一度使う」「エラーになったクエリを直して再実行する」「SQL Lab で実行したクエリの実行時間を調べる」といった振り返りに使えます。

Query history は「SQL Lab の履歴」— 監査ログではない

Query history に載るのは基本的に SQL Lab から実行されたクエリです。「昨日ダッシュボードが遅かった原因を探す」のようにチャート／ダッシュボードの描画で発行されたクエリを網羅的に追う用途には使えません。ダッシュボード側の調査は、チャートの View query（第8章）で発行 SQL を確認し、それを SQL Lab に貼って実行時間を測る、という手順になります。実行内容を組織的に記録したい場合は、別途イベントログや監査ログの仕組みを用意します（第14章）。

画面 何が見えるか 主な使いどころ
Saved queries 名前を付けて保存した SQL 定番の集計を再利用する
Query history SQL Lab で実行したクエリの実行者・実行時刻・行数・成否 過去の SQL を調べる・やり直す（チャート描画のクエリは対象外）

重要ポイント

保存クエリは、個人のメモ以上の価値を持ちます。チームの誰かが「この指標はこう集計する」と決めた SQL を保存しておけば、同じ定義を全員が使い回せるようになり、人によって数字が微妙に違うという事態を防げます。保存クエリには、後から探す人が中身を推測できる名前を付けておきましょう。

5.6 結果をデータセットにする

SQL Lab で試行錯誤し、「この集計で問題ない」と確認できたら、その SQL をチャートの材料にできます。エディタの Save から「Save dataset」（バージョンによっては「Save as new dataset」と表示されることがあります）を選ぶと、その SQL が仮想データセットとして登録されます。仮想データセットは、テーブルそのものではなく「この SQL の実行結果」をデータセットとして扱う仕組みで、詳しくは第6章で学びます。

データセットとして保存すると、そのままExplore画面（チャート作成画面）へ進む導線が用意されています。SQL Lab での試行錯誤とチャート作成が地続きになっている、という点は Superset の大きな特徴です。

flowchart LR A["SQL Labで
クエリを試す"] --> B["データセットとして
保存する"] B --> C["Exploreで
チャートを作成"]

ここで補足しておきたいのは、試すだけなら結果パネルの Create chart ボタンから Explore へ直行できるという点です。データセットを保存しなくても、その場の実行結果を一時的なデータソースとしてすぐにチャート化できます。ただしこの状態はあくまで一時的なもので、チャートとして保存し、あとで再利用するにはデータセット化（Save dataset）が必要です。チャートは最終的に必ずデータセットに属する、という原則は変わりません。「便利だから」といって SQL Lab のタブを増やし続けるのではなく、繰り返し使う集計はデータセット化して土台を整理していきましょう。この整理については第6章・第7章で詳しく扱います。

5.7 SQL Lab を使うときの注意

SQL Lab は手軽にクエリを試せる分、気をつけたい点もいくつかあります。ここで一度整理しておきましょう。

  • 本番データベースへ重いクエリを直接投げない — WHEREで期間や条件を絞り、LIMITを付けてから実行するのが基本です。全件スキャンになるような SQL は、本番システムの他の処理にも影響します。
  • 実行時間には上限がある — 一定時間を超えたクエリはタイムアウトとして打ち切られます。既定値はクエリ実行タイムアウト（SQLLAB_TIMEOUT）が約30秒、取得件数の上限（DEFAULT_SQLLAB_LIMIT）が1,000行です。どちらもバージョンや設定次第で変わりますが、「時間のかかる集計は SQL Lab では終わらない」ことを前提に、テーブル設計やクエリの見直しを検討する必要があります。
  • 時間のかかる集計には非同期クエリ実行を使う — 通常の実行はブラウザが応答を待ち続けますが、非同期クエリ実行を有効にすると、裏側の Celery ワーカーがクエリを処理し、完了した結果を後から画面が受け取れるようになります。設定の詳細は第14章で扱います。
  • DML は既定で禁止されている — INSERT・UPDATE・DELETEのようにデータを書き換える文は、多くの接続で初期状態では実行できません。SQL Lab は分析のために「読む」画面であり、誰かの一存で本番データが書き換わる事故を防ぐための既定動作です。第4章で見たとおり、必要な場合のみ接続側で DML を許可する設定に切り替えます。

「動く」ことと「安全」なことは別

SQL Lab は強力な画面なので、権限さえあればどんな SQL でも一応は書けてしまいます。読み取り専用ユーザーで接続する（第4章）、DML を許可しない、重いクエリには WHERE と LIMIT を付ける——これらはどれも「操作を制限して事故を防ぐ」ための仕組みです。制約を面倒に感じても、外さずに使うようにしてください。

やってみよう 5-1: 月次集計を保存クエリ＆データセットにする

サンプルデータ cleaned_sales_data に対して「月ごとの売上合計」の集計 SQL を書いて実行し、保存クエリとして保存したうえで、Save dataset で仮想データセットにするところまでを一通り体験します。

手順

  1. 1 SQL Lab で対象のデータベース・スキーマを選び、サンプルデータの cleaned_sales_data テーブル（日付列 order_date・金額列 sales を持つ）を選ぶ。まずはLIMIT 10程度で中身を確認する。
  2. 2 日付を月単位に丸めて金額を合計する SQL を書き、実行する。結果の件数・数値がおかしくないか目視で確認する。
  3. 3 問題なければSaveから名前を付けて保存クエリにする。名前には「対象データ＋集計内容」が分かるようにする。
  4. 4 続けてSave datasetを選び、仮想データセットとして保存する。データセット名も同様に分かりやすく付ける。
解答例: 月次売上集計クエリ 
-- 月ごとの売上合計と注文件数を集計する解答例
-- サンプルデータ cleaned_sales_data を使用
SELECT
    DATE_TRUNC('month', order_date) AS sales_month,
    SUM(sales) AS total_sales,
    COUNT(*) AS order_count
FROM cleaned_sales_data
GROUP BY 1
ORDER BY 1;

解答の目安

保存クエリ名は「cleaned_sales_data_月次売上集計」のように、対象テーブル＋何を集計したかが分かる形にすると後で探しやすくなります。データセット名も同様に「monthly」「by_month」のような粒度が伝わる単語を含めておくと、似た名前のデータセットが増えたときに迷わずに済みます。「test」「temp」のような中身の分からない名前は避けましょう。

理解度確認クイズ

  1. Q1. SQL Lab のデータベース選択に、すべての接続が表示されないことがあるのはなぜですか？

    回答を表示

    第4章で見た Expose database in SQL Lab（既定でオン）という項目がオフになっている接続は、SQL Lab の候補に出てきません。SQL Lab は誰でも SQL を実行できる強力な画面なので、接続単位で利用可否を切り替えられるようになっています。

  2. Q2. 結果を CSV に落として Excel で作業し続けることの何が問題なのですか？

    回答を表示

    第1章で見た「Excel はファイルの版が乱立しやすい」という弱点を、そのまま持ち込んでしまうためです。CSV 書き出しは一時的な確認や他システムへの受け渡しにとどめ、繰り返し使う集計はデータセット化して Superset 側に残すことで、元データの更新が自動的に反映される状態を保てます。

  3. Q3. SQL Lab で書いた SQL を、そのままチャートの材料にするための正しい手順は？

    回答を表示

    結果パネルの Create chart から Explore へ直行して試すこともできますが、その状態は一時的です。チャートとして保存・再利用するには Save → Save datasetで仮想データセットとして保存し、そこから Explore 画面でチャートを作成する必要があります。チャートは最終的に必ずデータセットを経由します。

  4. Q4. 時間のかかる集計クエリを SQL Lab で実行したいとき、どのような仕組みが必要になりますか？

    回答を表示

    非同期クエリ実行が必要です。通常の実行は時間内に応答が返らないとタイムアウトしてしまいますが、非同期クエリ実行を有効にしておくと、裏側の Celery ワーカーがクエリを処理し、完了した結果を後から受け取れます。設定の詳細は第14章で学びます。
