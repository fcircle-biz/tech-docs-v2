ホーム Jev 第15章
第15章 所要時間: 約30分

Coding AgentからJevを利用する

Jev は Claude Code や Codex のような Coding Agent の代わりにはなりません。この章では、両者の正しい関係を整理し、公式が配布する Agent Skill の使い方、そして Coding Agent への効果的な依頼の仕方を学びます。

この章で学ぶこと

  • Jev と Coding Agent の関係を正しく説明できる
  • Coding Agent に「Jev を使うコード」を書かせる依頼の仕方が分かる
  • 公式が提供する Agent Skill の位置づけと導入方法を理解する

15.1 よくある誤解

ここまで Jev の使い方を学んできたので、「Jev があれば Claude Code や Codex のような Coding Agent はもう要らないのでは」と考えたくなるかもしれません。第1章の終わりでも少し触れましたが、この章であらためて結論をはっきりさせておきます。答えはいいえです。

Jev は Coding Agent の代わりにはならない

公式ドキュメントは、Jev が Claude Code・Cursor・opencode・Copilot の背後で動いている LLM の置き換えにはならない（not a drop-in replacement）と明記しています。理由は、これまでの章で見てきた Jev の性質そのものです。Jev は System One モデルであり、テキストを生成せず、コードを書かず、会話も行いません。一方 Coding Agent は、テキストをストリーミングし、ツールを呼び出し、自然言語の指示にもとづいてファイルを編集する LLM に依存しています。そもそもの土台が違うため、一方がもう一方の代わりにはなれないのです。

つまり「Jev にこのリポジトリのバグを直してもらう」といった使い方は想定されていません。Jev にできるのは、あらかじめ用意された State と Question に対して、型付きの判断を1つ返すことだけです。ファイルを読む、複数ステップの計画を立てる、コードを編集するといった作業は、これまでどおり Coding Agent の仕事です。

15.2 正しい関係

Jev と Coding Agent は競合する道具ではなく、役割の異なる2つの道具です。公式ドキュメントが示す正しい関係は、「いつもどおり Coding Agent を使いながら、その中で Jev を呼び出して判断を行うコードを書く」というものです。

flowchart LR A["開発者"] --> B["Coding Agent
（Claude Code／Codex等）"] B --> C["アプリケーションの
コード"] C --> D["Jev API"]

開発者は Coding Agent に指示を出し、Coding Agent はその指示にもとづいてアプリケーションのコードを書きます。そのコードの中に Jev API の呼び出しが含まれる、という構造です。この図に Jev 自身が「会話の相手」として登場することはありません。

重要ポイント

Coding Agent が書くのは「Jev を呼び出すコード」であって、Coding Agent 自身が Jev の代わりに判断を下すわけではありません。判断そのものは実行時に Jev API が行い、Coding Agent の役割はそのための実装をあなたの代わりに書くことに限られます。

アプリケーションの中で Jev を使うべき典型的な場面は、次のような構造化された判断が必要になる箇所です。

  • ルーティング — 入力をどの処理経路・どの担当へ振り分けるか
  • 分類 — カテゴリやラベルのどれに当てはまるか
  • スコアリング — 緊急度・重大度などを段階で評価する
  • ガードレール — 不正な内容や逸脱した入力を検知して止める
  • その他、アプリケーションに必要な構造化された判断全般

Coding Agent に依頼するときは、「アプリケーションのこの判断部分に Jev を使ってほしい」という形で伝えることになります。

15.3 公式の Agent Skill

TypeSafe AI は、Coding Agent が Jev（TypeSafe API）を正しく扱えるようにするための公式 Agent Skillを配布しています。これは AI Coding Agent に TypeSafe API の完全なコンテキストを与えるドロップイン型のスキルで、3つの Question type（Choice・Score・Noul）、アーキテクチャのパターン、評価の構造に関するベストプラクティスをまとめて提供します。Claude Code・Codex をはじめとする Agent 環境に対応しています。

Claude Code の場合は、プラグインとして追加します。

ターミナル（Claude Code） 
# 公式マーケットプレイスを追加してからインストール
claude plugin marketplace add typesafe-ai/skills
claude plugin install typesafe@typesafe-ai

Claude Code 以外の Agent 環境では、次のコマンドで導入できます。

ターミナル（その他の Agent） 
# npx 経由で TypeSafe の Skill を追加
npx skills add typesafe-ai/skills --skill typesafe-ai

コマンドが使えない環境では、GitHub リポジトリ typesafe-ai/skills（https://github.com/typesafe-ai/skills）から skills/typesafe-ai ディレクトリ一式を、Agent の skills ディレクトリへ手動でコピーする方法も用意されています。

導入後は、プロンプトで「use the TypeSafe skill」と指定すれば呼び出せます。Claude Code では、スラッシュコマンド /typesafe:typesafe-ai で直接呼び出すこともできます。

Skill を入れるメリット

この Skill を導入しておくと、Coding Agent は Choice・Score・Noul の使い分けや、State ／ Question の設計パターンをすでに知った状態で作業できます。毎回のプロンプトで基礎から説明し直す必要がなくなり、Coding Agent が書くコードも TypeSafe の作法に沿った、より正確なものになります。

15.4 Coding Agent への依頼例

Agent Skill を導入していても、依頼の仕方が曖昧だと Coding Agent は的確なコードを書けません。ここまでの章で学んだ用語（State・Question・Choice／Score／Noul・confidence）を使って、具体的に依頼することが重要です。

依頼例1: 判定と振り分けをまとめて頼む 
問い合わせ本文から部署（Choice）・緊急度（Score）・
クレームかどうか（Noul）を Jev で判定し、confidence が
0.8 未満なら人間レビューへ回す関数を Python で書いて。
依頼例2: State と Question の形を指定する 
State には問い合わせ本文とアカウント種別を含めて。
Question は次の3つ。(1) department は Choice 型で
選択肢は technical/billing/sales。(2) urgency は
Score 型で1〜5の5段階。(3) is_refund_request は
Noul 型。この3問を1回のリクエストで並列評価する
コードを TypeScript で書いて。
依頼例3: 合成ロジックまで指定する 
Jev から返る urgency と is_refund_request を受け取り、
urgency が4以上、かつ is_refund_request の noul が
0.7以上なら「至急対応」に分類して。それ以外は各値の
confidence が0.8以上なら自動振り分け、未満なら人間
レビューに回すルーティング関数を書いて。判断の合成
ロジックはコード側に書き、Jev には個々の判断だけを
させて。

これらの依頼文に共通するのは、次の4点です。

  • State の形を指定する — 何を判断材料として渡すのかを明示する
  • Question の種類と criteria を自分で決める — Choice の選択肢や Score の段階数を丸投げしない
  • 合成ロジックを明示する — 複数の判断結果をどう組み合わせて結論にするかを言葉にする
  • confidence の閾値を自分で決めて渡す — 「あとはよろしく」ではなく、具体的な数値を渡す

重要ポイント

判断の設計は人間が行い、Coding Agent に任せるのは実装です。どんな State を渡し、どんな Question を立て、その結果をどう組み合わせて結論を出すかは、あなたの業務知識にもとづく設計判断です。Coding Agent はその設計を正確なコードに変換する役割を担いますが、設計そのものを代わりに考えてくれるわけではありません。

やってみよう 15-1: Coding Agent への依頼文を自分で書く

第16章では「問い合わせの自動振り分け」を題材にした実践課題に取り組みます。ここでは、その課題を Coding Agent に依頼するための文章を、自分の言葉で準備してみましょう。

手順

  1. 1 State に何を含めるか（問い合わせ本文だけか、アカウント種別なども含めるか）を決めて書き出す。
  2. 2 必要な Question を一覧化する。それぞれ Choice／Score／Noul のどれにあたるか、選択肢や段階数（criteria）も自分で決める。
  3. 3 複数の Question の結果をどう組み合わせて最終的な振り分け先を決めるか、合成ロジックを言葉で書く。
  4. 4 confidence の閾値を数値で決め、1〜3の内容とあわせて Coding Agent への依頼文を完成させる。

解答の目安

決まった正解はありませんが、依頼文の中に「State の形」「Question ごとの型と criteria」「合成ロジック」「confidence の閾値」の4点がすべて具体的な言葉で入っていれば、Coding Agent が迷わず実装できる依頼文になっています。逆にこの4点のどれかが抜けていると、Coding Agent は独自の解釈で埋め合わせることになり、意図と違うコードが出来上がりがちです。

理解度確認クイズ

  1. Q1. Jev は Claude Code や Codex のような Coding Agent の代わりになりますか。理由もあわせて答えてください。

    回答を表示

    なりません。Jev は System One モデルであり、テキストを生成せず、コードを書かず、会話も行いません。一方 Coding Agent は、テキストのストリーミング・ツール呼び出し・自然言語の指示によるファイル編集を行う LLM に依存しています。両者は前提となる土台が異なるため、一方がもう一方の置き換えにはなりません。

  2. Q2. Jev と Coding Agent の正しい関係を、開発者を起点にして一文で説明してください。

    回答を表示

    開発者が Coding Agent を使い、Coding Agent が「Jev を呼び出して判断を行うアプリケーションのコード」を書く、という関係です。図で表すと開発者 → Coding Agent → アプリケーションのコード → Jev APIとなり、Jev はコードの中から呼び出される側であって、対話の相手ではありません。

  3. Q3. Coding Agent に依頼するとき、「あとはよろしく」で済ませずに明示すべきことを4点挙げてください。

    回答を表示

    ①State の形（何を判断材料として渡すか）、②Question の種類と criteria（Choice の選択肢や Score の段階数など）、③合成ロジック（複数の判断結果をどう組み合わせて結論にするか）、④confidence の閾値（どこから人間レビューに回すか）の4点です。判断の設計は人間が行い、Coding Agent に任せるのは実装だからです。
