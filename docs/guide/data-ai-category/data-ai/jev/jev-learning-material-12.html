ホーム Jev 第12章
第12章 所要時間: 約2時間

Jev デザインパターン

公式の Patterns ガイドが紹介する代表的な設計パターンを学びます。Confidence-Gated Routing・Composite Scoring・Intent Routing・Speculative Fan-out の4つは、これまでの章で学んだ State・Question・Confidence・並列評価を、実際のアプリケーション設計に落とし込むための「型」です。本章はこれまでの学習の集大成にあたる重要章のため、他の章より内容を厚めに扱います。

この章で学ぶこと

  • Confidence-Gated Routing で自動処理・確認・人間レビューを振り分けられる
  • Composite Scoring で複数の Score をコードで重み付けできる
  • Intent Routing で入力を分類して処理先を振り分けられる
  • Speculative Fan-out の考え方を説明できる
  • 要件に応じて使うパターンを選べる

12.1 Confidence-Gated Routing（信頼度によるゲート）

公式ガイドは Confidence-Gated Routing を 「confidence を第二の軸として使う」パターンだと説明しています。原文では次のように表現されています。

公式ドキュメントより

"Use confidence as a second axis. The answer tells you what; confidence tells you whether to act."（confidence を第二の軸として使う。答えは「何であるか」を教え、confidence は「行動してよいか」を教える。）

第9章で学んだとおり、Jev の回答には confidence が付随します。Confidence-Gated Routing は、この confidence を「実行してよいかどうかの関所（ゲート）」として使う設計です。ポイントは1つだけです。

重要ポイント

重要度の高い操作ほど、高い confidence を要求する。すべての判断に同じ閾値を使うのではなく、「間違えたときの被害が大きい操作」ほど閾値を引き上げます。逆に被害が小さい操作は、多少 confidence が低くても自動実行してよい場合があります。

公式ガイドの音声バンキングの例では、「残高照会」（間違えても被害が小さい）と「送金承認」（間違えると被害が大きい）で、要求する confidence の水準を変えています。

confidence の範囲 残高照会（低リスク） 送金承認（高リスク）
0.6 未満 人間（サポート担当）へ 人間（サポート担当）へ
0.6 以上 0.85 以下 自動実行 ユーザーに確認を求める
0.85 超 自動実行 自動承認

同じ「送金承認」という Choice でも、confidence の水準によって振る舞いが3段階に分かれる点に注目してください。これをフローチャートに整理すると次のようになります。

flowchart TD A["Jevの回答＋confidence"] --> B{"confidenceが0.6未満か"} B -->|はい| C["人間（サポート担当）へ"] B -->|いいえ| D{"どの操作か"} D -->|"残高照会（低リスク）"| E["自動実行"] D -->|"送金承認（高リスク）"| F{"confidenceが0.85超か"} F -->|はい| G["自動承認"] F -->|いいえ| H["ユーザーに確認を求める"]

これをコードに落とすと、次のようにシンプルな条件分岐になります。

confidence_routing.py 
action = response.answers["intent"]

# confidenceが低い場合は無条件に人間（サポート担当）へ
if action.confidence < 0.6:
    route_to_support_agent(account_id)
elif action.choice == "check_balance":
    show_balance(account_id)                 # 低リスクなのでそのまま自動実行
elif action.choice == "approve_transfer":
    if action.confidence > 0.85:
        approve_transfer(account_id)         # 高リスクだが確信度が十分高い
    else:
        ask_user_to_confirm(account_id)      # 中間はユーザーに確認を求める
else:
    route_to_support_agent(account_id)

ヒント: 「完全自動化」を目指さない

Confidence-Gated Routing のねらいは、すべてを自動化することではありません。「自動化してよい範囲」と「人間に戻すべき範囲」の境界線を、被害の大きさに応じて意図的に引くことです。閾値（0.6・0.85 など）は固定の正解ではなく、業務のリスク許容度に合わせてチームが決める設計パラメータです。

12.2 Composite Scoring（複合スコアリング）

Composite Scoring は、公式ガイドの言葉を借りれば「複数の分析軸を1つのスコアへ統合する」パターンです。1つの複雑な評価を Jev に丸ごと判断させるのではなく、独立した複数の Score Question に分解して並列評価し、その結果をコード側で重み付けして合成します。第11章で学んだ「複数 Question の並列評価」を、評価・採点という文脈で活用する形とも言えます。

公式ガイドでは、エンジニア候補者の履歴書スクリーニングを例に、python_depth・team_leadership・system_design・generalist の4つを 0〜4 のルーブリックで独立に評価し、それぞれを4で割って 0〜1 に正規化してから重み付け合成する方法が紹介されています。ここでは同じ考え方を、より一般的な採用候補者評価の場面に置き換えて説明します。

技術スキル

重み 40%

リーダーシップ

重み 20%

設計力

重み 30%

コミュニケーション

重み 10%

4つの Score Question（各 0〜4 段階のルーブリック）を1リクエストで取得したら、コード側で正規化し、重みを掛けて合成します。

composite_scoring.py 
# 各Scoreを0〜1に正規化する（ルーブリックが0〜4段階の場合）
tech   = response.answers["technical_skill"].score / 4
lead   = response.answers["leadership"].score / 4
design = response.answers["system_design"].score / 4
comm   = response.answers["communication"].score / 4

# 重みはJevに決めさせず、コードの定数として管理する
WEIGHTS = {"tech": 0.40, "lead": 0.20, "design": 0.30, "comm": 0.10}

final_score = (
    tech * WEIGHTS["tech"] + lead * WEIGHTS["lead"]
    + design * WEIGHTS["design"] + comm * WEIGHTS["comm"]
)

公式ガイドの例でも、同じ4つの評価軸に対して「個人貢献者（IC）向け」と「エンジニアリングマネージャー（EM）向け」で異なる重みのセットを用意する例が示されています。役割によって重視したい軸が変わるなら、WEIGHTS を役割ごとに複数用意し、使い分けるだけで対応できます。

重要ポイント: 責務分担

Jev = 個々の判断／コード = 最終判断という原則が、ここでも一貫しています。Jev は「技術スキルは3」「リーダーシップは2」のように各軸を独立に評価するだけです。「技術スキルを40%、設計力を30%として重視する」という重みの決定はコードの責務であり、Jev に決めさせてはいけません。重みをコードの定数として持つことで、採用基準が変わったときもJev への問い合わせをやり直さずに重みだけ調整して再計算できます。

12.3 Intent Routing（意図による振り分け）

Intent Routing は、公式ガイドの言葉では「受信したリクエストを分類し、それぞれを最適なハンドラーへ振り分ける」パターンです。ユーザーの入力をまず Jev に通し、Choice で意図（intent）を分類してから、決定論的なコード・専門特化した LLM・人間のいずれかへ処理を渡します。Jev を LLM の前段に置くという構成が最大の特徴です。

公式ガイドのカスタマーサポートの例では、intent（Choice: 注文状況／製品に関する質問／返品交換／クレーム）と complexity（Score: 複雑度）の2つの Question を1リクエストにまとめて評価します。

flowchart TD A["ユーザーからの問い合わせ"] --> B["Jev（intentをChoiceで分類＋complexityをScoreで評価）"] B --> C{"intentのconfidenceが0.5未満か"} C -->|はい| H1["人間エージェントへ"] C -->|いいえ| D{"intentの分類結果"} D -->|"order_status"| E["データベース照会（決定論的コード）"] D -->|"product_question"| F["製品専門LLMへ"] D -->|"return_exchange"| G["返品専門LLMへ"] D -->|"complaint"| I{"complexityが高い または confidenceが低いか"} I -->|はい| H2["人間エージェントへ"] I -->|いいえ| J["クレーム対応LLMへ"]

ここでも Confidence-Gated Routing と同じ考え方が使われています。intent.confidence が低い時点で早期に人間へ回し、complaint（クレーム）に分類された場合はさらに complexity を見て、複雑度が高いか確信度が低ければ人間へエスカレーションします。パターンは単独で使うだけでなく、組み合わせて多段のゲートを作れることがわかります。

intent_routing.py 
def route_ticket(ticket_id, response):
    intent = response.answers["intent"]
    complexity = response.answers["complexity"]

    if intent.confidence < 0.5:
        return route_to_human(ticket_id)          # 分類の確信度が低い

    if intent.choice == "order_status":
        return query_database(ticket_id)          # 決定論的コードで処理
    if intent.choice == "complaint":
        if complexity.score > 1 or complexity.confidence < 0.5:
            return route_to_human(ticket_id)      # 複雑なクレームは人間へ
        return handle_with_llm(ticket_id, "complaint")
    return handle_with_llm(ticket_id, intent.choice)  # その他は専門LLMへ

注意: 「振り分け先」はLLMだけではない

Intent Routing の目的は「安いリクエストは安い手段で処理し、難しいリクエストだけ高コストな手段に回す」ことです。上の例のようにorder_status はデータベース照会という決定論的なコードで完結し、LLM をまったく呼び出しません。すべての意図を LLM に投げるのではなく、コードで確定的に処理できるものはコードで済ませるのが Intent Routing の要点です。

12.4 Speculative Fan-out（投機的ファンアウト）

公式ガイドは Speculative Fan-out を次のように説明しています。

公式ドキュメントより

"Send many questions in a single call, including speculative ones, and let your code decide what's relevant."（投機的なものも含め、多くの Question を1回の呼び出しでまとめて送り、何が関係あるかはコード側で判断させる。）

第11章で学んだように、Jev は1リクエストに含めた複数の Question を並列に評価するため、Question を追加してもレスポンス時間はほとんど変わりません。この特性を利用し、「使うかどうかまだ分からない Question」も投機的にまとめて送ってしまい、結果を見てからコード側で使う／使わないを決めるのが Speculative Fan-out です。

flowchart LR subgraph A["逐次リクエスト（往復が多い）"] A1["Question1を送信"] --> A2["結果を待つ"] A2 --> A3["分岐に応じてQuestion2を送信"] A3 --> A4["さらに結果を待つ"] end subgraph B["Speculative Fan-out"] B1["5つのQuestionを1回でまとめて送信"] --> B2["Jevが並列に評価"] B2 --> B3["コードが必要な結果だけを使う"] end

公式ガイドのサポートチケット仕分けの例では、category・bug_severity・has_reproducible_steps・refund_requested・frustration の5つの Question を1リクエストにまとめて送ります。実際に使うのは category の分類結果次第で、残りの結果は状況によって使われないこともあります。

speculative_fanout.py 
# 1回のリクエストで5つのQuestionを投機的にまとめて送る
response = client.system_one(
    state={"ticket": ticket_text},
    questions={
        "category": category_q, "bug_severity": severity_q,
        "has_reproducible_steps": repro_q, "refund_requested": refund_q,
        "frustration": frustration_q,
    },
)
category = response.answers["category"].choice
# 使うのはcategory次第。残り4つは無視されることもある
if category == "bug_report":
    handle_bug(response.answers["bug_severity"])
elif category == "billing":
    handle_billing(response.answers["refund_requested"])

公式ガイドが挙げる使いどころは、サポートチケットの自動仕分けのように、条件によって一部の分析結果が不要になる意思決定プロセスです。往復通信（レイテンシ）を減らせる点が主な利点であり、「念のため聞いておく」ことのコストがほぼゼロに近いという Jev の並列評価の特性を、設計として積極的に使うパターンだと言えます。

12.5 パターンの選び方

4つのパターンは互いに排他的ではなく、組み合わせて使うことも珍しくありません（12.3 の例では Intent Routing の中に Confidence-Gated Routing が組み込まれていました）。迷ったときは「やりたいこと」から逆引きしてください。

やりたいこと 使うパターン Jev の役割 コードの役割
自動化してよい範囲を線引きしたい Confidence-Gated Routing 判断＋confidenceを返す confidenceに応じて自動実行／確認／人間へ振り分け
複数の評価軸から総合点を出したい Composite Scoring 各軸を独立にScoreで評価 正規化して重み付け合成し最終スコアを算出
入力の内容によって行き先を変えたい Intent Routing 意図をChoiceで分類 分類結果に応じてDB／専門LLM／人間へ振り分け
後で使うかもしれない情報も先読みしたい Speculative Fan-out 複数Questionを1回で並列評価 必要になった結果だけを選んで使う
分類しつつ、怪しいものだけ人間で二重チェックしたい Intent Routing ＋ Confidence-Gated Routing 分類＋各段階のconfidenceを返す 分類結果とconfidenceの両方を見て多段に振り分け

どのパターンを選んでも共通しているのは、Jev には「個々の判断」だけを担わせ、それをどう使うか（重み・閾値・振り分け先）はコードが決めるという第8章以来の原則です。デザインパターンとは、この原則を具体的な形に落とし込むための「型」に過ぎません。

やってみよう 12-1: 社内ヘルプデスクの一次対応自動化を設計する

社内ヘルプデスクには「PCの不調」「アカウントロック」「経費精算の質問」「その他の一般的な質問」など、さまざまな問い合わせが届きます。これらの一次対応を自動化するシステムを、本章で学んだパターンを使って設計してみましょう。

手順

  1. 1 どのパターンを組み合わせるか選ぶ。「問い合わせの種類によって行き先を変えたい」「怪しい分類は人間に確認させたい」という2つの要求から、必要なパターンを逆引きしてみる。
  2. 2 Jev に投げる State と Question を設計する。問い合わせ本文をStateとし、少なくとも「カテゴリ」を判定するChoice Questionを1つ用意する。緊急度を判定するScore Questionを加えてもよい。
  3. 3 コード側の合成ロジックを設計する。confidenceが低いときに人間へ回す条件、カテゴリごとの振り分け先（決定論的コードかLLMか）を書き出す。

解答の目安

使うパターン: Intent Routing（category の分類）＋ Confidence-Gated Routing（confidence による人間へのエスカレーション）を組み合わせる。

Question設計: State ＝ 問い合わせ本文。Question は category（Choice: pc_trouble／account_lock／expense／general）と urgency（Score 0〜3）の2つ。

合成ロジック: category.confidence が 0.6 未満なら無条件で人間へ。account_lock は決定論的コードでパスワード再設定用URLを発行。pc_trouble は社内ナレッジベース検索LLMへ、expense は経費規程FAQ LLMへ。generalはそのまま一般問い合わせLLMへ。いずれの分岐でも urgency.score が2以上なら優先度「高」を付けてキューの先頭に回す。

理解度確認クイズ

  1. Q1. Confidence-Gated Routing で「重要度の高い操作ほど高い confidence を要求する」とはどういうことですか？公式ガイドの音声バンキングの例で説明してください。

    回答を表示

    間違えたときの被害が小さい「残高照会」は confidence が 0.6 以上あれば自動実行してよい一方、間違えると被害が大きい「送金承認」は confidence が 0.85 を超えて初めて自動承認とし、0.6〜0.85 の間はユーザーへの確認を挟みます。操作のリスクに応じて閾値を変えるのがこのパターンの要点です。

  2. Q2. Composite Scoring で、重みを Jev に決めさせず、コードの定数として管理するのはなぜですか？

    回答を表示

    Jev の役割は各評価軸を独立に判断することであり、それらをどう組み合わせて最終判断にするかはコードの責務だからです。重みをコード側に置けば、評価基準が変わったときも Jev へ問い合わせをやり直さずに重みだけを調整して再計算でき、基準の透明性も保てます。

  3. Q3. Intent Routing では Jev をシステムのどこに置きますか？また、その理由を説明してください。

    回答を表示

    LLM の前段に置きます。ユーザー入力をまず Jev で意図分類し、注文状況照会のように決定論的なコードだけで解決できるものはLLMを呼ばずに処理し、専門的な回答が必要なものだけを該当分野の専門LLMへ振り分けます。これにより、コストの高いLLM呼び出しを本当に必要な場合だけに絞れます。

  4. Q4. Speculative Fan-out が成立するのは、Jev のどんな特性のおかげですか？

    回答を表示

    1リクエストに含めた複数の Question が並列に評価されるため、Question を追加してもレスポンス時間がほとんど変わらないという特性です。この「追加コストがほぼゼロ」という性質を利用し、使うかどうか未確定な Question も投機的にまとめて送り、コード側で後から取捨選択します。
