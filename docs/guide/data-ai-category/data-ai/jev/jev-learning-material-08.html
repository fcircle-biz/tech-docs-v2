Atomic Question — 判断を分解する

「この問い合わせを分析して対応を決めてください」のような複合的な依頼を、Jev はそのまま扱えません。本章では、複合的な依頼を一つの判断しか含まないQuestion（Atomic Question）へ分解し、分解した判断をコードで組み立て直す方法を学びます。本教材全体の中でも中心となる、最も重要な章です。

この章で学ぶこと

  • Atomic Question（それ以上分けられない一つの判断）の条件を説明できる
  • 複合的な依頼を Atomic Question 群へ分解できる
  • 分解した判断をコードで合成して最終判断を組み立てられる
  • Jev とコードの責務分担を設計に落とし込める

8.1 Atomic Question とは

Atomic Questionとは、一つの判断しか含まないQuestionのことです。第1章で触れた基準——「その分野をよく知る人が、必要な情報を見て数秒で判断できる程度の一つの判断」——を、Question設計の実践ルールへ落とし込んだものだと考えてください。公式ドキュメントも「複雑または曖昧な問いは、それぞれ一つの性質（property）だけを評価する複数のQuestionへ分解する」ことを勧めています。

ポイントは、Atomic Questionが単に「短い質問」ではないということです。短くても複数の判断が混ざっていればAtomicではありませんし、多少長くても判断が一つに定まっていればAtomicです。次のチェックリストで見分けます。

Atomic Questionチェックリスト

  • 1つのproperty（性質）だけを評価しているか。「緊急か、かつどの部署か」のように「かつ」で2つ以上の性質を尋ねていないか
  • 個々の判断として検査・調整・合成できる粒度か。コード側でif文の条件としてそのまま使えるか
  • 短く、曖昧さがないか。前後の文脈を長々と説明しなくても意味が通るか
  • 隠れた複雑さがないか。一見シンプルな問いの裏に、複数の判断が隠れていないか

公式ドキュメントの位置づけ

TypeSafe AI のドキュメントは、Questionを性質ごとに分解するこの考え方を「おそらくこのガイドで最も重要な概念」と位置づけています。本教材が第8章を最重要章としているのも、同じ理由からです。

8.2 悪い例 — 判断が混ざったQuestion

次のQuestionを見てください。一見自然な依頼文ですが、Atomic Questionの条件を満たしていません。

Questionの例

「この問い合わせを分析して適切な対応を決定してください」

このQuestionがダメな3つの理由

  • ① 判断が複数混ざっている — 「緊急かどうか」「返金要求かどうか」「どの部署が担当か」「顧客の不満度」など、少なくとも4つの判断が1つの問いに押し込まれている。
  • ② 答えの型を定義できない — Jev の Question は Choice・Score・Noul のいずれかとして事前に型を決める必要がある。「適切な対応を決定してください」だけでは、何を選択肢（Choice）とするのか、何を段階（Score）で測るのかが定義できず、Question として成立しない。Jev は自由記述の文章を返さないため、「とりあえず文章で返してもらって後で解析する」という逃げ道もない。
  • ③ どこで間違えたか分からない — 結果が期待と違っても、緊急度の判断が間違ったのか、部署の判断が間違ったのかを切り分けられない。

公式ドキュメントも同種の問題を、スパム判定を例に説明しています。「messageはスパムですか？」という1つのQuestionは、「認証情報を要求している」「送信者名と実際の送信元が一致しない」「意外な報酬を提示している」といった複数の判断を1つの答えの中に隠してしまいます。分野が違っても、症状は同じです。

8.3 良い例 — Atomic Questionへ分解する

同じ問い合わせを、性質ごとに独立した4つのAtomic Questionへ分解します。それぞれが1つの判断だけを担当し、使うPrimitiveも明確に決まります。

Atomic Question Primitive 返る値
返金を要求しているか？ Noul 0〜1の確率
緊急性があるか？ Noul または Score 確率、または段階評価
どの部署が担当すべきか？ Choice 選択肢の中の1つ
顧客はどの程度不満か？ Score ルーブリックの段階

分解の前後を比べると、構造の違いがはっきり見えます。

4つのQuestionは同じStateに対して1リクエストの中で並列に評価されます。公式ドキュメントは「Questionは並列に実行され、コードはモデルとの直列な往復を増やすことなくそれらの信号を組み合わせられる」と説明しています。並列評価の仕組みそのものは第11章で詳しく扱います。

8.4 最終判断はコードで組み立てる【最重要】

分解しただけでは終わりません。Jevは8.3で分解した個々の判断をそれぞれ返しますが、「では返金処理を最優先で進める」といった最終的な結論は返しません。個々の判断を受け取ったあと、それらを組み合わせて実際の処理を決めるのはコードの役割です。ここでは、そのうちrefund ・ urgency ・ departmentの3つを使って合成してみます。

compose_decision.py 
# Jevから返ってきた4つのAtomic Questionの判断結果
refund = answers["is_refund_request"].noul >= 0.5  # 返金要求か
urgency = answers["urgency_score"].score             # 緊急度（1〜5）
department = answers["department"].choice            # 担当部署

# ここから先はJevを呼ばない。if文で最終判断を組み立てる
if refund and urgency >= 4:
    action = "返金チームへ最優先でエスカレーション"
elif refund:
    action = "通常の返金フローへ登録"
elif urgency >= 4:
    action = f"{department}チームへ緊急対応を依頼"
else:
    action = f"{department}チームの通常キューに登録"

refundとurgencyという2つの独立した判断をif / elifで組み合わせることで、Jev単体では出さない「最優先でエスカレーション」という結論を導いています。判断はJevから、組み合わせ方はコードから、という分業です。

条件分岐だけでなく、複数のNoulを重み付きで数値合成する方法もあります。公式ドキュメントには次のような例が示されています。

weighted_compose.py 
# 複数のNoulを重み付きで合成し、1つの品質スコアにする
quality = (
    0.4 * answers["answers_request"].noul
    + 0.4 * answers["citations_are_supported"].noul
    + 0.2 * (1 - answers["contradicts_context"].noul)
)

重要ポイント: Jevとコードの責務分担

Jev = 個々の判断を返す。コード = それらを合成して最終判断を組み立てる。条件分岐（if/elif）でも重み付き合成でも、合成ロジックそのものはJevの外、つまりあなたが書くコードの中にあります。この責務分担を守れないと、結局「1つの巨大なQuestionにJevへ丸投げする」という8.2の失敗に逆戻りします。

8.5 分解の手順

複合的な依頼をAtomic Questionへ分解するときは、次の5ステップで進めます。

  1. 1

    やりたいことを日本語で書く

    分解を意識せず、「問い合わせを分析して対応を決める」のように素直に書いてみる。

  2. 2

    その中に含まれる判断を数える

    「そして」「さらに」で文を区切り、いくつの判断が含まれているかを数える。

  3. 3

    判断ごとにPrimitiveを選ぶ

    真偽ならNoul、段階評価ならScore、選択肢から選ぶならChoice（第4章）。

  4. 4

    型とcriteriaを決める

    Choiceの選択肢、Scoreのルーブリック、Noulの判定基準を具体的に書く（第10章で詳しく扱う）。

  5. 5

    合成ロジックをコードで書く

    分解した判断をif/elifや重み付き合成で組み合わせ、最終的な処理を決める（8.4）。

分解しやすくなる自問

  • この文に「そして」「さらに」「かつ」が入っていないか？
  • 一つの答えに対して、複数の理由を説明したくならないか？
  • 主語（判断の対象になる性質）が2つ以上ないか？

8.6 分解しすぎに注意

分解はあくまで手段であり、目的ではありません。同じ判断を必要以上に細切れにすると、8.4で書いたような合成ロジックが複雑になり、かえって「何を判断しているのか」が曖昧になります。

目安は「一つの判断として説明できる粒度」で止めることです。公式ドキュメントも過度な分解を明示的に禁止してはいませんが、「Questionは短く保ち、分けて示さなければ意味がぼやけてしまう場合にのみ構造を追加する」という指針を示しています。分解のための分解は避けましょう。

注意: 別々のQuestionの確率に算術的な関係を仮定しない

「顧客は返金を要求しているか？」と「顧客は返金以外を求めているか？」という対になる2つのNoulを、同じ問い合わせに対して別々に尋ねたとします。確率の合計は1.0に近づきそうに思えますが、そうなるとは限りません。

公式ドキュメント（jev-1.13の既知の弱点）の検証では、実際にこの2つの確率の合計が1.19になった例が報告されています。Jevは各Questionを独立に評価するため、P(noul)と1 - P(否定形のnoul)が一致する保証はありません。

公式の指針は明快です。「あるNoulで調整した閾値を別のChoiceにそのまま流用しない。そして、別々のQuestionに対してモデルが算術的な恒等式を満たすことを期待しない」。この弱点は第13章でさらに詳しく扱います。

やってみよう 8-1: 採用応募書類の評価を分解する

次の複合的な依頼を、Atomic Questionへ分解してみましょう。

複合的な依頼

「この応募者の書類を確認し、書類選考を通過させるかどうかを判断してください。」

手順

  1. 1 上の依頼に含まれる判断がいくつあるかを数える。
  2. 2 判断ごとにChoice / Score / Noulのどれを使うか決める。
  3. 3 各Questionにどんなcriteria（判定基準）を持たせるかを書き出す。
  4. 4 分解した判断をどう組み合わせて「書類通過／見送り」を決めるか、擬似コードで書く。

解答の目安

Before（複合的な依頼）: 「書類選考を通過させるかどうか」という1問に、必須要件・経歴の一貫性・職種の適合・自己PRの誇張という4つの判断が混ざっている。

After（Atomic Questionへ分解）: ①必須経験年数を満たすか（Noul） ②職務経歴に矛盾や不自然な空白期間がないか（Score・1〜5の一貫性） ③どの職種区分に最も近いか（Choice） ④自己PR文に誇張表現が含まれるか（Noul）

合成ロジックの擬似コード:

required_ok = answers["meets_requirement"].noul >= 0.5
consistency = answers["consistency_score"].score   # 1〜5
category    = answers["job_category"].choice
exaggerated = answers["exaggeration"].noul >= 0.7

if not required_ok:
    result = "見送り"
elif consistency <= 2 and exaggerated:
    result = "人事が要確認"
else:
    result = f"書類通過 → {category}担当リクルーターへ"

理解度確認クイズ

  1. Q1. 「この問い合わせを分析して適切な対応を決定してください」がAtomic Questionとして不適切な理由を1つ説明してください。

    回答を表示

    緊急性・返金要否・担当部署・不満度など複数の判断が1つの問いに混ざっているためです。答えの型（Choice/Score/Noul）も決まらず、結果が誤っていてもどの判断が原因か切り分けられません。

  2. Q2. Atomic Questionへ分解したあと、複数の判断結果から最終的な処理を決めるのは何の役割ですか？

    回答を表示

    コードの役割です。Jevは個々の判断を返すところまでを担当し、if/elifや重み付き合成といったロジックで最終判断を組み立てるのはコード側の責務です。

  3. Q3. 「返金を要求しているか？」と「返金以外を求めているか？」という対になる2つのNoulを別々に尋ねた場合、確率の合計は必ず1.0になりますか？

    回答を表示

    なりません。公式の検証では合計が1.19になった例が報告されています。Jevは各Questionを独立に評価するため、別々のQuestionの確率の間に算術的な恒等式を仮定してはいけません。

  4. Q4. Questionを分解しすぎると、どんな問題が起きますか？

    回答を表示

    コード側の合成ロジックが複雑になりすぎたり、1つ1つのQuestionが「一つの判断」として説明できないほど細切れになり、意味が曖昧になったりします。分解は最終判断を組み立てるための手段であり、目的ではありません。
