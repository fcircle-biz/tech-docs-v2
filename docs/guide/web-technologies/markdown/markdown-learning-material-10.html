Mermaidで図を描く

第9章までで、文章を整えるための記法はひと通り身につきました。この章では一歩進んで、Markdownの中に図そのものを描く方法を学びます。Mermaid（マーメイド）というしくみを使えば、画像ファイルを1枚も用意することなく、テキストを書くだけでフローチャートやシーケンス図が完成します。手順の説明も仕組みの図解も、コピペではなく自分で書けるようになりましょう。

この章で学ぶこと

  • Mermaidを使うと、画像ファイルを用意せずに Markdownの中に図を描けることが分かる
  • バッククォート3つ ＋ mermaid で図を書く、基本の形を覚える
  • フローチャートを、ノードの形（[]・()・{}・([])）と矢印（-->・-->|はい|）を使い分けて自分で書ける
  • シーケンス図・円グラフなど、フローチャート以外の図も書ける
  • 日本語で書くときの注意点（半角括弧・&・改行）を押さえ、どの環境なら図が表示されるかを判断できる

10.1 Mermaid とは — テキストだけで図が描ける

これまで文書に図を入れるには、第6章で学んだ ![代替テキスト](画像のパス) を使って、どこかで作った画像ファイルを貼り込むしかありませんでした。しかし、この方法には見過ごせない弱点がいくつもあります。

①作図ツールが必要

図を描くためだけに、別のアプリやサービスを用意しなければならない。

②直すのが面倒

内容を直したいだけなのに、元の編集用ファイルを探し出して作り直す必要がある。

③どこが変わったか分からない

画像ファイルはGitで差分を追えず、「変更された」ということしか分からない。

④文字が小さいと読めない

画像として貼り付けた図は、拡大すると文字がぼやけて読みにくくなる。

Mermaid（マーメイド）は、こうした弱点を解決するしくみです。「こういう図を描いてほしい」という指示をテキストで書いておくと、表示するときに自動で図として描き替えてくれます。書くのはただの文字なので、画像ファイルを別に用意する必要はなく、.md ファイルの中に直接書き込めます。

画像と比べたときの、Mermaidの嬉しいポイントを4つ紹介します。

画像ファイルが要らない

.md ファイル1つで完結し、画像の保存場所やパス切れに悩まされない。

修正が一瞬

「レビュー」を「上長確認」に直したいときも、文字を書き換えるだけでよい。

差分が見える

Gitでどの行の図がどう変わったかを文字として追える。画像は「変わった」としか分からない。

見た目が自動で整う

線の位置や矢印の向きなどのレイアウトは、Mermaidが自動で計算してくれる。

論より証拠です。次のたった3行のテキストが、どんな図になるか見てみましょう。

書いたテキスト（Markdown）

flow.md 
```mermaid
flowchart LR
    A[原稿を書く] --> B[レビュー]
    B --> C[公開]
```

表示イメージ

flowchart LR A[原稿を書く] --> B[レビュー] B --> C[公開]

たった3行を書いただけで、矢印の位置も箱の大きさも自動的に整えられた図が完成しました。この章では、この「テキストを書くだけ」という感覚を、一つずつ確認しながら身につけていきます。

「Mermaid（マーメイド）」は人魚の意味

名前の由来は人魚（mermaid）。Markdownと同じく「書きやすさ」を大事にしたツールで、2014年ごろから開発され、いまではGitHubをはじめ多くのサービスが標準で対応しています。

10.2 書き方の基本形と、すぐ試せる場所

Mermaidの書き方は、第7章で学んだフェンス付きコードブロックとまったく同じです。違うのは、言語名として python や bash の代わりに、mermaid と書く、ただそれだけです。

中身は次の3つの層に分けて考えると理解しやすくなります。

層 書く内容 役割
①開始・終了のフェンス ```mermaid ～ ``` ここから先をMermaidの図として扱うという合図
②図の種類の宣言 フェンスの次の行に書く flowchart TD など これから描く図の種類を指定する（省略不可）
③図の中身 3行目以降に書くノードや矢印の指示 実際に描かれる箱や線の内容

②の図の種類の宣言は省略できません。書き忘れると、Mermaidはどんな図を描けばよいのか判断できず、図にならないので注意しましょう。実際の文書の中でどう使うか、地の文に混ぜた例で見てみましょう。

process.md 
書類の受付から完了までの流れです。

```mermaid
flowchart LR
    A[受付] --> B[確認] --> C[完了]
```

以上が全体の流れです。

表示イメージ

書類の受付から完了までの流れです。

flowchart LR A[受付] --> B[確認] --> C[完了]

以上が全体の流れです。

上の例のように A --> B --> C と1行につなげて書いてもかまいません。図の前後は普通の文章のままでよく、コードブロックと同じ感覚でMarkdownに自然に混ぜて書けることが分かります。

インデント（字下げ）は見やすくするためのもので、半角スペース4つが一般的によく使われますが、揃ってさえいれば個数は自由です。字下げには半角スペースを使いましょう。全角スペースは見た目で見分けがつきにくく、環境によっては正しく認識されないことがあります。日本語入力のまま字下げをしていると全角スペースが混ざりやすいので注意しましょう。

まずは試せる場所を用意しよう — Mermaid Live Editor

公式のオンラインエディタMermaid Live Editorを開くと、左に書いたコードが右に図としてすぐ表示されます。インストールも登録も不要。この先の例はすべてここに貼り付けて動かしながら読むのがおすすめです。書き方を間違えるとその場でエラーが出るので、練習にも間違い探しにも使えます。

※ ```mermaid のフェンス行は貼り付けません（flowchart TD から下だけを貼ります）。

フェンスの直後にスペースを入れない

第7章の言語名指定と同じで、バッククォート3つの直後にスペースを空けずに mermaid と書くのが基本です。``` mermaid のように空けても、多くの環境では前後の空白が取り除かれるため動きますが、スペースを詰めて書くのが確実です。対応していない環境では、ただのコードブロックとして表示されてしまいます。大文字・小文字にも注意し、すべて小文字で書きましょう。

10.3 フローチャート①：ノードと矢印でつなぐ

ここからは、Mermaidで最もよく使われるフローチャート（flowchart）の書き方を学びます。フローチャートは、箱（ノード）を矢印でつないで、手順や流れを表す図です。

1行目の図の種類は flowchart の後ろに向きを指定します。よく使うのは、上から下に流れる TD（Top-Down。手順の説明で定番）と、左から右に流れる LR（Left to Right。ステップ数が少ないときに横幅を活かせる）の2つです。ほかにも下から上の BT、右から左の RL があります。

箱の書き方は ID[表示したい文字] です。A の部分がノードID（その箱の名札）で、これ自体は画面には表示されません。[ ] の中に書いた文字だけが、実際に箱の中に表示されます。矢印は ID1 --> ID2 のようにつなぎ、一度登場したIDを2回目以降に書くときは [ ] を省略できます。

朝の身支度の流れを例に、実際に書いてみましょう。

①上から下（TD）

morning-td.md 
```mermaid
flowchart TD
    A[朝起きる] --> B[顔を洗う]
    B --> C[朝ごはんを食べる]
    C --> D[家を出る]
```
flowchart TD A[朝起きる] --> B[顔を洗う] B --> C[朝ごはんを食べる] C --> D[家を出る]

②左から右（LR）

morning-lr.md 
```mermaid
flowchart LR
    A[朝起きる] --> B[顔を洗う]
    B --> C[朝ごはんを食べる]
    C --> D[家を出る]
```
flowchart LR A[朝起きる] --> B[顔を洗う] B --> C[朝ごはんを食べる] C --> D[家を出る]

2行目以降では B[顔を洗う] のように書き直さなくても、B というIDだけで同じ箱を指せている点に注目してください。①と②は中身がまったく同じで、TD を LR に書き換えただけでレイアウトが変わりました。画像であれば図を描き直す作業になりますが、Mermaidならたった2文字の書き換えで済みます。

矢印にもいくつか種類があり、線の意味合いを描き分けられます。

書いたテキスト（Markdown）

arrows.md 
```mermaid
flowchart LR
    A[実線の矢印] --> B[基本はこれ]
    C[点線の矢印] -.-> D[補足的なつながり]
    E[太線の矢印] ==> F[特に強調したい流れ]
```

表示イメージ

flowchart LR A[実線の矢印] --> B[基本はこれ] C[点線の矢印] -.-> D[補足的なつながり] E[太線の矢印] ==> F[特に強調したい流れ]
書き方 見た目 よく使う場面
--> 実線の矢印 基本。ふつうの流れ
--- 線だけ（矢印なし） 向きのない単なる関連
-.-> 点線の矢印 補足・任意の流れ
==> 太い矢印 特に強調したい主要な流れ

ノードIDは半角英数字がおすすめ

IDには日本語も使えますが、半角英数字（A・B・step1・start など）にしておくと、後から見返したときに「どれが名札で、どれが表示される文字か」が一目で区別できます。start[受付] --> check[書類を確認] のように、意味の分かるIDを付けるのも良い方法です。

10.4 フローチャート②：形で意味を表す・条件で分岐する

フローチャートの世界には、「箱の形そのものに意味を持たせる」という世界共通のお約束があります。Mermaidでは、ノードを囲む記号を [ ] から別の記号に変えるだけで、その箱の形を変えられます。

まずは基本の3つ、それにおまけ1つを覚えましょう。[文字]は長方形で「処理」、(文字)は角丸の長方形で「やわらかい処理・データ」、{文字}はひし形で「条件分岐・判断」、([文字])はスタジアム形（角が丸くつぶれた楕円のような形）で「開始・終了」を表します。

書いたテキスト（Markdown）

shapes.md 
```mermaid
flowchart LR
    A[四角形は処理] --> B(角丸はデータ)
    B --> C{ひし形は分岐}
    C --> D([スタジアム形は開始・終了])
```

表示イメージ

flowchart LR A[四角形は処理] --> B(角丸はデータ) B --> C{ひし形は分岐} C --> D([スタジアム形は開始・終了])
書き方 形 意味
A[テキスト] 長方形 処理・作業・ステップ
A(テキスト) 角丸の長方形 やわらかい処理・データ
A{テキスト} ひし形 条件分岐・判断
A([テキスト]) スタジアム形 開始・終了

この中でとりわけ重要なのがひし形です。ひし形は「条件によって道が分かれる場所」を表すため、ふつうは矢印が2本以上出ます。ただ2本の矢印を出すだけでは「どちらがどの条件の道なのか」が分からないため、矢印にラベル（説明文）を添えます。ラベルの付け方には2通りあります。

書き方 向いている場面
A -->|はい| B 「はい」「いいえ」など短いラベル向き
A -- はい --> B 長めのラベルでも読みやすい書き方

まずは、いちばんシンプルな分岐の形を見てみましょう。

書いたテキスト（Markdown）

branch.md 
```mermaid
flowchart TD
    A{今日は雨？} -->|はい| B[傘を持っていく]
    A -->|いいえ| C[そのまま出かける]
```

表示イメージ

flowchart TD A{今日は雨？} -->|はい| B[傘を持っていく] A -->|いいえ| C[そのまま出かける]

A というひとつのIDから、ラベルの違う矢印が2本出ているだけの、とてもシンプルな構造です。次は、もう一方のラベルの書き方と、矢印を前に戻す書き方を組み合わせた例を見てみましょう。矢印は先に進むだけでなく、すでに登場したノードに戻すこともでき、やり直しや再入力といったループを表現できます。

書いたテキスト（Markdown）

approval.md 
```mermaid
flowchart LR
    A[申請する] -- 承認された --> B[手続き完了]
    A -- 差し戻された --> C[内容を修正する]
    C --> A
```

表示イメージ

flowchart LR A[申請する] -- 承認された --> B[手続き完了] A -- 差し戻された --> C[内容を修正する] C --> A

C --> A によって、「差し戻された」場合は A[申請する] へ矢印が戻り、修正して再度申請する流れが表現されています。ここまでに登場した形・矢印・ラベルという部品を組み合わせるだけで、実務でそのままREADMEに載せられるような、少し本格的な図も作れます。最後に、バグ対応の流れを例にまとめて挑戦してみましょう。

bugfix.md 
```mermaid
flowchart TD
    A([バグを見つけた]) --> B{再現できる？}
    B -->|できる| C[手順をメモする]
    B -->|できない| D[しばらく様子を見る]
    C --> E{原因が分かる？}
    E -->|分かる| F[自分で直す]
    E -->|分からない| G[Issueとして報告する]
    F --> H([対応完了])
    G --> H
    D --> H
```

表示イメージ

flowchart TD A([バグを見つけた]) --> B{再現できる？} B -->|できる| C[手順をメモする] B -->|できない| D[しばらく様子を見る] C --> E{原因が分かる？} E -->|分かる| F[自分で直す] E -->|分からない| G[Issueとして報告する] F --> H([対応完了]) G --> H D --> H

スタジアム形で始まり、ひし形で2回分岐し、複数の道筋が最後は同じ H([対応完了]) に合流する、実用的なフローチャートが完成しました。ここまでの内容を組み合わせれば、身の回りの手順のほとんどを図にできるはずです。

迷ったら「四角とひし形と矢印」だけでよい

形の種類はほかにも円形・円柱形などたくさんありますが、実務で使う図の9割は [ ]（処理）・{ }（判断）・-->（流れ）の3つで描けます。まずはこの3つを確実に使えるようにして、ほかの形は必要になったときに調べれば十分です。

( ) は「形」の記号。文字として書きたいときは要注意

A(テキスト) の丸かっこは「角丸の形にしてください」というMermaidへの指示です。そのため、表示したい文字の中に半角の ( ) を書くと、Mermaidが形の指示と勘違いしてエラーになります。日本語の文章では全角の「（）」を使うのが安全です。詳しくは10.7で扱います。

10.5 シーケンス図：登場人物のやり取りを描く

ここまでのフローチャートは、1つの作業がどんな順番で進むかという「1本の手順の流れ」を描くのに向いていました。一方で、「利用者がボタンを押す→ブラウザがサーバーに問い合わせる→サーバーが返事を返す」のように、複数の登場人物（人やシステム）の間で情報がやり取りされる様子を描きたい場面もあります。ログインの流れ、注文から発送までの連絡、APIどうしのやり取りなどが典型例です。こうした「誰が誰に、どんな順番でメッセージを送るか」を表すのがシーケンス図です。

書き方の骨組みはフローチャートとよく似ています。1行目に図の種類を書く決まりでしたね。シーケンス図では sequenceDiagram と書くだけで、flowchart のような向きの指定（TD・LRなど）は不要です。

続けて、登場人物を participant ID as 表示名 の形で宣言します。宣言した順番のとおりに左から横並びになり、それぞれの下へ時間の流れを表す縦線（ライフライン）が伸びていきます。

やり取り（メッセージ）は 送り手ID 矢印 受け手ID: メッセージ の形で書きます。矢印には2種類あり、->>（実線）は依頼や送信などの「行き」、-->>（点線）は返事や応答などの「帰り」を表します。「行きは実線、帰りは点線」と覚えておきましょう。

書いたテキスト（Markdown）

sequence1.md 
```mermaid
sequenceDiagram
    participant U as 利用者
    participant W as Webサイト
    U->>W: ページを見せてください
    W-->>U: ページを表示する
```

表示イメージ

sequenceDiagram participant U as 利用者 participant W as Webサイト U->>W: ページを見せてください W-->>U: ページを表示する

最小構成はこれだけです。今度は登場人物を1人増やし、実際によくある「ログインの流れ」を描いてみましょう。2者にまたがる補足を書きたいときは Note over A,B: 文章 を使うと、AとBの間にまたがる注釈を挿入できます。

書いたテキスト（Markdown）

login.md 
```mermaid
sequenceDiagram
    participant U as 利用者
    participant B as ブラウザ
    participant S as サーバー
    U->>B: IDとパスワードを入力
    B->>S: ログイン情報を送信
    S-->>B: ログイン成功の返事
    B-->>U: マイページを表示
    Note over B,S: 通信は暗号化されている
```

表示イメージ

sequenceDiagram participant U as 利用者 participant B as ブラウザ participant S as サーバー U->>B: IDとパスワードを入力 B->>S: ログイン情報を送信 S-->>B: ログイン成功の返事 B-->>U: マイページを表示 Note over B,S: 通信は暗号化されている

登場人物が3人以上に増えても、書く量はほとんど変わりません。もし同じ内容をフローチャートで描こうとすると、どの矢印が誰から誰へのものかを区別する工夫が必要になり、矢印同士が絡まって読みにくくなってしまいます。

フローチャートとシーケンス図の使い分け

「順番に何をするか」＝フローチャート、「誰と誰がやり取りするか」＝シーケンス図。1人（1つの主体）の作業手順ならフローチャート、複数の相手の間を情報が行ったり来たりするならシーケンス図、と覚えておけば迷いません。

「participant」は省略できる

participant の行を書かなくても、利用者->>サーバー: 送信 のようにいきなり書けば自動的に登場人物が作られます。ただし並ぶ順番が登場した順になってしまうため、順番を自分で決めたいときは participant で先に宣言しておくのが確実です。

10.6 円グラフ：割合をひと目で伝える

アンケート結果や作業時間の内訳など、全体に対する割合を伝えたいときは円グラフが便利です。Mermaidでは pie という種類を使います。書き方はシンプルで、1行目に pie title タイトル名、2行目以降に "項目名" : 数値 を必要な数だけ並べるだけです。

フローチャートのノードとの違いに注意してください。円グラフの項目名は必ずダブルクォートで囲む必要があります。また、割合（パーセント）の計算はMermaidが自動でおこなうので、数値の合計を100にそろえる必要はありません。人数・件数・時間など、手元の数をそのまま書けば大丈夫です。

書いたテキスト（Markdown）

breakfast.md 
```mermaid
pie title 好きな朝ごはん
    "パン" : 45
    "ごはん" : 35
    "シリアル" : 12
    "食べない" : 8
```

表示イメージ

pie title 好きな朝ごはん "パン" : 45 "ごはん" : 35 "シリアル" : 12 "食べない" : 8

showData というオプションを付けると、円グラフの横に項目ごとの数値も一覧表示できます。showDataを付けるときは、公式の例に倣ってタイトルを次の行に分けて書くのが一般的です。

書いたテキスト（Markdown）

timeuse.md

10.7 つまずきポイントと、表示できる環境・できない環境

Mermaidの基本的な書き方が分かったところで、最後に実際につまずきやすいポイントと、そもそもどこで使えるのかを整理しておきましょう。ここを押さえておくだけで、「書いたのに図にならない」という状況の多くを避けられます。

日本語で書くときの3つのつまずき

Mermaidの記法自体は英語圏で作られたものなので、日本語で書くときに特有のつまずきがいくつかあります。よくある順に3つ紹介します。

① 表示したい文字の中に半角の括弧を書いてしまう（最頻出）

日本語の文章では「申込書(記入済み)」のように、半角の丸括弧を使いたくなる場面がよくあります。しかし10.4で見たとおり、半角の ( ) はノードの形を指定する特別な記号なので、ラベルの中にそのまま書くと図が表示されずエラーになります。

NG: 半角括弧をそのまま書く

bad.md 
flowchart TD
    A[申込書(記入済み)] --> B[提出]

「(」を見たMermaidが角丸ノードの指示だと勘違いし、図が表示されずエラーになる（この図はここでは描画していません）。

OK例その1: 全角括弧にする

good.md 
flowchart TD
    A[申込書（記入済み）] --> B[提出]
flowchart TD A[申込書（記入済み）] --> B[提出]

日本語の文書では、全角の「（）」を使うのが基本です。

どうしても半角括弧を使いたい場合は、ノードのテキスト全体をダブルクォートで囲むという別解もあります。

OK例その2: テキスト全体をダブルクォートで囲む

good2.md 
flowchart TD
    A["申込書(記入済み)"] --> B[提出]
flowchart TD A["申込書(記入済み)"] --> B[提出]

② & をそのまま書く

& はMermaidでは、A & B --> C のように複数のノードをまとめて指定するための記号として使われます。この意味を持つのは [ ] の外側に書いたときで、ラベルの中に書くぶんには文字として扱われます。とはいえ、記号の意味が場所によって変わるのは混乱のもとなので、日本語の文章では全角の「＆」を使うのが安全です。

書いたテキスト（Markdown）

flowchart LR
    A[設計＆実装] --> B[テスト]

表示イメージ

③ 箱の中で改行したいのにダブルクォートを付け忘れる

ノードの中で文字を改行したいときは <br/> を使います。<br/> を使う行は、テキスト全体をダブルクォートで囲むのがルールです。囲まなくても動く環境が多いのですが、ほかの特殊文字と組み合わさったときに壊れやすくなります。改行を入れるときはテキスト全体をダブルクォートで囲む、と覚えておくのが安全です。

step.md 
flowchart TD
    A["第1段階<br/>要件を決める"] --> B["第2段階<br/>設計する"]
    B --> C["第3段階<br/>作って確かめる"]

↑ このように、改行を含むテキストは必ず "…" で囲みます（この図はこのページでは描画していません）。

図が表示されないときは、10.2で紹介したMermaid Live Editor（https://mermaid.live/）にコードを貼り付けてみましょう。何行目が悪いのかを教えてくれるので、原因がすぐ分かります。まずここで正しく表示されることを確かめてから、Markdownファイルに貼るのが失敗しないコツです。

どこで表示できて、どこでできない？

第9章で、Markdownには表・脚注・絵文字コードなどの拡張機能を持つ「方言（フレーバー）」があり、標準仕様のCommonMarkとGitHubの拡張GFMという関係を学びました。実はMermaidは、さらにその外側にあります。

重要なので明確にしておきます。MermaidはCommonMarkにもGFMにも含まれていません。 ```mermaid は、Markdownの側から見れば第7章で学んだ「言語名にmermaidを指定しただけの、ふつうのフェンス付きコードブロック」にすぎないのです。

Mermaidに対応しているサービスだけが、そのコードブロックを見つけて「あ、mermaidだ」と気づき、図に描き替えています。気づかないサービスでは、書いたコードがそのままコードブロックとして文字で表示されるだけで、文書そのものが壊れることはありません（安全に「劣化」します）。

書いたテキスト（Markdown）

support.md 
```mermaid
flowchart TD
    A[言語名にmermaidを指定したコードブロック] --> B{表示する場所はMermaidに対応している？}
    B -->|対応している| C[きれいな図として描画される]
    B -->|対応していない| D[コードのまま文字で表示される]
```

表示イメージ

flowchart TD A[言語名にmermaidを指定したコードブロック] --> B{表示する場所はMermaidに対応している？} B -->|対応している| C[きれいな図として描画される] B -->|対応していない| D[コードのまま文字で表示される]

対応していなくても文書は壊れません。ただし読み手には図として見えないので、使う前に表示できる場所かどうかを確認することが大切です。なお、この図自体が10.4で学んだ「ひし形（判断）＋ラベル付き矢印」の実演にもなっています。

使う前に「その場所は対応しているか」を確かめる

第9章で学んだとおり、特殊な記法を使うときは表示される場所を確認するのが鉄則です。Mermaidはその代表例。GitHubのREADMEに載せるなら安心して使えますが、チャットに貼っても図にはなりません。「読み手がどこで見るのか」を先に考えてから使うようにしましょう。図が必須の場面で対応していない環境なら、Mermaid Live Editorで描いた図を画像として保存し、第6章で学んだ ![代替テキスト](画像のパス) で貼るという手もあります。

やってみよう 10-1: 自動販売機の流れをフローチャートにしよう

この章で学んだ「形」と「ラベル付き矢印」を使って、身近な出来事を図にしてみましょう。まずは自分で書いてから、解答例と見比べてください。

手順

  1. 1 Mermaid Live Editorを開く（またはVS Codeで practice.md を作り ```mermaid のコードブロックを用意する）。
  2. 2 1行目に flowchart TD と書く。
  3. 3 「自動販売機で飲み物を買う流れ」を図にする。次の3条件を必ず満たすこと。開始と終了をスタジアム形 ([ ])で書く／「お金は足りている？」のような判断（ひし形 { }）を1つ以上入れる／判断から出る矢印に-->|はい| のようなラベルを付ける。
  4. 4 図が表示されたら1行目を flowchart LR に書き換えて、見た目の変化を確かめる。
  5. 5 余裕があれば、箱の中の文字にわざと半角の括弧を入れてエラーになることを確認し、全角括弧に直して直ることを確かめる。
解答例を表示
answer.md 
```mermaid
flowchart TD
    A([開始]) --> B[飲み物を選ぶ]
    B --> C[お金を入れる]
    C --> D{金額は足りている？}
    D -->|足りている| E[商品が出てくる]
    D -->|足りていない| F[追加でお金を入れる]
    F --> D
    E --> G{おつりはある？}
    G -->|ある| H[おつりを受け取る]
    G -->|ない| I([終了])
    H --> I
```
flowchart TD A([開始]) --> B[飲み物を選ぶ] B --> C[お金を入れる] C --> D{金額は足りている？} D -->|足りている| E[商品が出てくる] D -->|足りていない| F[追加でお金を入れる] F --> D E --> G{おつりはある？} G -->|ある| H[おつりを受け取る] G -->|ない| I([終了]) H --> I

F --> D で判断のところに矢印を戻しているのがポイントです。「足りるまで繰り返す」という動きが1行で表現できます。また、最後は2つの経路が I([終了]) の1点に合流しています。正解は1つではありません。自分の書いた図が意図どおりに読めれば、それで正解です。

理解度確認クイズ

  1. Q1. Markdownの中にMermaidの図を書くときの、正しい書き方はどれですか。

    • A. ![mermaid](図のURL) と書く
    • B. バッククォート3つの直後に mermaid と書いたコードブロックを作り、その中に図の記述を書く
    • C. <mermaid> というHTMLタグで囲む
    • D. 行頭に > を付けて引用として書く
    回答を表示

    正解: B。Mermaidは、第7章で学んだフェンス付きコードブロックの言語名に mermaid を指定するだけです。特別な新しい記法を覚える必要はありません。対応しているサービスが、そのコードブロックを見つけて図に描き替えてくれます。Aは第6章で学んだ画像の埋め込み記法で、あらかじめ用意した画像ファイルを表示するものです。Dは第7章の引用記法で、文字がそのまま引用ボックスに入るだけです。Cのようなタグは Markdown にも Mermaid にも存在しません。

  2. Q2. フローチャートで「条件によって進む先を分ける」判断のノードを書き、分かれた矢印に「はい」というラベルを付けたい。正しい書き方はどれですか。

    • A. A[条件を満たす？] --> はい --> B[次の処理]
    • B. A(条件を満たす？) ==> B[次の処理]
    • C. A{条件を満たす？} -->|はい| B[次の処理]
    • D. A<条件を満たす？> --はい--> B[次の処理]
    回答を表示

    正解: C。判断（条件分岐）を表すひし形は波かっこ { } で囲みます。[ ] は長方形（処理）、( ) は角丸の長方形で、どちらも「判断」の意味にはなりません。矢印のラベルは -->|はい| のようにパイプ記号 | で挟むか、-- はい --> のように線の中に書きます。Aのようにラベルを矢印の外に置いてもラベルにはならず、「はい」という別のノードが1つ増えてしまいます。Dの < > という形の指定はMermaidにはありません。なお ==>（太い矢印）は線を強調するだけで、ラベルにはなりません。

  3. Q3. Mermaidについての説明として、正しくないものはどれですか。

    • A. ノードの文字に半角の括弧を入れるとエラーになりやすいので、全角の「（）」を使うか、テキスト全体をダブルクォートで囲むとよい
    • B. Mermaidに対応していないサービスでは、図にならずコードブロックのまま文字で表示される
    • C. MermaidはCommonMarkとGFMの標準機能なので、Markdownが使える場所ならどこでも必ず図として表示される
    • D. GitHubのREADMEやIssueでは、Mermaidの図がそのまま図として描画される
    回答を表示

    正解: C（これが誤り）。MermaidはCommonMarkにもGFMにも含まれていない、サービスごとの拡張機能です（第9章で学んだ「方言」の話の、さらに外側にあります）。GitHub・GitLab・Notion・Zenn・ObsidianなどはMermaidに対応していますが、VS Codeの標準プレビューは拡張機能が必要で、Slackなどのチャットツールでは図になりません。ただしBのとおり、対応していない場所でも第7章で学んだふつうのコードブロックとして文字がそのまま表示されるだけなので、文書全体が壊れることはありません。Aの半角括弧の注意点も、DのGitHubの対応も、どちらも正しい説明です。

この章のまとめ

  • Mermaidを使うと、画像ファイルを1つも用意せずに、テキストを書くだけで図が描ける。修正が簡単で、Gitで差分も追える
  • 書き方は第7章のコードブロックと同じ。```mermaid で囲み、1行目に図の種類（flowchart TD / sequenceDiagram / pie など）を宣言し、2行目以降に中身を書く
  • フローチャートは []（処理）・{}（判断）・-->（流れ）の3つでほぼ描ける。分岐には -->|はい| のようにラベルを付け、矢印を前に戻せば「やり直し」も表現できる
  • 「順番に何をするか」はフローチャート、「誰と誰がやり取りするか」はシーケンス図（->> が行き、-->> が帰り）。割合を見せたいときは円グラフ（pie）
  • 日本語で書くときは、半角の ( ) と & に注意（全角の「（）」「＆」に替えるか "…" で囲む）。Mermaidは標準仕様ではないので、GitHubのように対応している場所かどうかを使う前に確認する

これで、Markdownで使う記法はすべてそろいました。見出し・段落・装飾・リスト・リンク・画像・コードブロック・引用・表・応用記法、そして図。あとは、これらを組み合わせて「人に読んでもらう1つの文書」を仕上げるだけです。次の第11章は総仕上げ。GitHubのプロジェクトの顔であるREADME.mdを、架空のツールを題材に一から書き上げます。この章で学んだフローチャートも、READMEの「使い方」の説明で早速活躍しますので、ぜひ盛り込んでみてください。
