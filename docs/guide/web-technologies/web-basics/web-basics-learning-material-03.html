HTTPの基本：リクエストとレスポンス

第2章では「相手を見つける」仕組みを学びました。この章では、見つけた相手と実際に何をやり取りするのか、つまり HTTP そのものの中身に入っていきます。リクエストとレスポンスというテキストの実物を1行ずつ読み解き、HTTP の大きな特徴である「ステートレス」の意味も押さえましょう。

この章で学ぶこと

  • HTTP が「プロトコル（約束事）」であることを説明できる
  • HTTPリクエストの構造（開始行・ヘッダー・空行・ボディ）を読める
  • HTTPレスポンスの構造を読み、ステータス行の意味が分かる
  • 「ステートレス」とは何か、その利点を説明できる
  • HTTP/1.1・HTTP/2・HTTP/3 の違いを概要レベルで説明できる

3.1 HTTPとは

HTTP（HyperText Transfer Protocol）は、クライアントとサーバーが Web 上でデータをやり取りするためのプロトコル（約束事）です。第1章で触れたとおり、プロトコルとは「電話をかけたらまず名乗る」といった、通信の手順と形式をあらかじめ決めておくルールのことでした。

HTTP の約束事はシンプルです。クライアントが「これをください」というリクエストを送り、サーバーが「はい、どうぞ」または「それはありません」というレスポンスを1つ返す。この1往復だけで成り立っています。合言葉のように、決まった書式で書かれたテキストをやり取りするだけなので、ブラウザだけでなく curl コマンドやプログラムからも、同じルールで通信できます。

HyperText とは

HTTP の名前にある「HyperText（ハイパーテキスト）」は、もともと「リンクを含む文書（HTML）」を運ぶための仕組みという意味でした。現在では HTML に限らず、JSON・画像・動画など、Web上のあらゆるデータを運ぶ共通のプロトコルとして使われています。

3.2 リクエストの構造

ブラウザが送っている HTTPリクエストは、実際には次のようなテキストです。難しく見えますが、4つのパーツに分けると読めるようになります。

HTTPリクエストの例 
GET /index.html HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html

（ボディなし）
パーツ 例 意味
①リクエスト行（開始行） GET /index.html HTTP/1.1 メソッド（何をするか）＋パス（何を）＋HTTPのバージョン
②ヘッダー Host: example.com など 「名前: 値」形式の付帯情報。誰が・何を受け取れるか等
③空行 （何もない1行） ヘッダーの終わりを示す区切り
④ボディ （GETでは通常なし） 送るデータの中身。POSTなどで使う（第4章）

リクエスト行の GET は「メソッド」と呼ばれ、「取得してください」という動作を表します。メソッドの種類は第4章でまとめて学びます。Host: example.com ヘッダーは、1台のサーバーで複数のサイトを運用している場合に「どのサイト宛てか」を伝える、実務上とても重要なヘッダーです。

重要ポイント

ヘッダーとボディの間には、必ず空行が1つ入ります。この空行があるおかげで、コンピューターは「ここまでがヘッダー、ここからがボディ」と機械的に区別できます。第6章でヘッダーの詳細を学ぶときも、この構造を思い出してください。

3.3 レスポンスの構造

サーバーが返す HTTPレスポンスも、リクエストとよく似た構造をしています。開始行が「リクエスト行」から「ステータス行」に変わる点が違いです。

HTTPレスポンスの例 
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 512

<html>
  <body><h1>ようこそ</h1></body>
</html>

ステータス行

HTTP/1.1 200 OK
HTTPのバージョン＋ステータスコード（3桁の数字）＋理由句（人間向けの短い説明）。200 は「成功しました」の意味です。詳しくは第5章で学びます。

ヘッダー・空行・ボディ

リクエストと同じ形式です。Content-Type はボディの中身の種類、Content-Length はボディのバイト数を表します。空行の後ろが実際に届く中身（この例では HTML）です。

つまり HTTPメッセージは、リクエストであってもレスポンスであっても「開始行 → ヘッダー → 空行 → ボディ」という共通の型でできています。この型さえ覚えてしまえば、これから先の章でどんなヘッダーやボディが出てきても、迷わず読めるようになります。

3.4 ステートレス

HTTP には、もう1つ大きな特徴があります。それはステートレス（stateless）、つまり「状態を持たない」という性質です。サーバーは、直前にどんなリクエストを受け取ったかを覚えていません。1回1回のリクエストは、それぞれが独立した「初対面」として処理されます。

sequenceDiagram participant C as クライアント participant S as サーバー C->>S: ①「商品一覧をください」 S-->>C: 商品一覧（HTML） Note over S: サーバーは①のことを覚えていない C->>S: ②「さっき見た商品の詳細をください」 S-->>C: エラー（「さっき」がどれか分からない）

図の②のように、「さっき」に頼ったリクエストは HTTP 単体では成立しません。クライアント側が、毎回必要な情報をすべてリクエストに含める必要があります。

ステートレスの利点

サーバーはリクエストごとの状態を保持しなくてよいため、どのサーバーが応答してもよく、故障時の切り替えや台数を増やすスケールアウトがしやすくなります。

困ること

「ログイン中かどうか」「カートに何を入れたか」のような、複数のリクエストにまたがる情報を保つ工夫が別途必要になります。この工夫（Cookie・セッション）は第8章で学びます。

3.5 HTTP/1.1・HTTP/2・HTTP/3

ここまで見てきたメソッド・パス・ステータスコード・ヘッダー・ボディといったメッセージの意味は、HTTP のどのバージョンでも変わりません。バージョンが変わっているのは、そのメッセージをより速く・効率よく運ぶ方法です。なお、「開始行・ヘッダー・空行・ボディ」というテキストの書き方そのものは HTTP/1.1 のもので、HTTP/2 以降は同じ内容をバイナリ形式（フレーム）に詰めて送ります。開発者ツールや curl は、どのバージョンでも HTTP/1.1 に近い見た目に整えて表示してくれます。

バージョン 登場 特徴
HTTP/1.1 1997年〜 テキストベース。長らくの標準。1本の接続で複数リクエストを送れる（Keep-Alive）が、順番待ちが起きやすい
HTTP/2 2015年〜 1本の接続で複数のリクエスト・レスポンスを同時に処理する多重化により高速化。テキストではなくバイナリ形式で送るが、メッセージの意味は HTTP/1.1 と同じ
HTTP/3 2022年〜 TCPの代わりに QUIC（UDPベース）という新しい土台を使い、接続開始や電波の悪い環境での遅延をさらに減らす

アプリを作る側からすると

Web API を作ったり呼び出したりするとき、どのバージョンを使うかは主にブラウザとサーバーが自動で決めます。私たちがコードの中で「GET してください」「200が返ってきた」と扱う内容は、バージョンが変わっても同じです。まずは 3.2〜3.4 で学んだメッセージの構造を確実に理解しておけば十分です。

やってみよう 3-1: 自分のリクエストを覗いてみよう

httpbin.org は、送られてきたリクエストの中身をそのまま JSON で返してくれる、学習用の便利なサービスです。ブラウザが実際にどんなリクエストを送っているかを確認してみましょう。

手順

  1. 1 ブラウザで https://httpbin.org/get を開く。
  2. 2 画面に表示された JSON の中の "headers" の項目を探す。
  3. 3 "Host" と "User-Agent" の値を見つけ、3.2 の表に出てきたヘッダーと見比べる。

この JSON 自体が、3.3 で見た「ボディ」にあたります。表示された内容は、httpbin.org のサーバーが「あなたのブラウザから、こういうリクエストを受け取りましたよ」と教えてくれているものです。

理解度確認クイズ

  1. Q1. HTTPメッセージの4つの構成要素を、順番に挙げてください。

    回答を表示

    開始行（リクエスト行またはステータス行）→ ヘッダー → 空行 → ボディ、の順です。

  2. Q2. GET /index.html HTTP/1.1 というリクエスト行は、何を表していますか。

    回答を表示

    メソッド（GET＝取得してください）、パス（/index.html＝何を）、HTTPのバージョン（HTTP/1.1）の3つを表しています。

  3. Q3. HTTP が「ステートレス」であるとは、どういう意味ですか。

    回答を表示

    サーバーが、直前に受け取ったリクエストの内容を覚えていないということです。1回1回のリクエストは独立して処理され、必要な情報はクライアントが毎回すべて含める必要があります。

  4. Q4. HTTP/1.1 と HTTP/2 で、HTTPメッセージの意味は変わりますか。変わるのはどこですか。

    回答を表示

    メッセージの意味（メソッド・ステータスコード・ヘッダー・ボディ）は変わりません。変わるのは、メッセージを運ぶ方法です。HTTP/2 ではメッセージをバイナリ形式で送り、1本の接続で複数のリクエスト・レスポンスを同時に処理する「多重化」により高速化しています。
