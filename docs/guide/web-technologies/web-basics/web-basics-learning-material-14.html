実践：APIを使う小さなWebページを作ろう

いよいよ最終章です。これまで学んだ HTTP・JSON・REST API の知識を1つにつなげて、JavaScript の fetch で実際の Web API を呼び出し、結果を画面に表示し、フォームから新しいデータを送信する小さなWebページを作ります。最後に、この教材全体で学んだことを振り返り、次に進む道を確認します。

この章で学ぶこと

  • fetch でREST APIを呼び出し、JSONを取得できる
  • 取得したJSONをDOM操作で画面に一覧表示できる
  • フォームの入力内容をJSONに変換してPOST送信できる
  • 読み込み中表示と、ネットワークエラー・HTTPエラーそれぞれの処理を書ける
  • CORS（オリジン間通信の制約）の基本と、エラーメッセージの読み方が分かる

14.1 完成イメージと準備

今回作るのは、JSONPlaceholder の投稿（/posts）を一覧表示し、フォームから新しい投稿を追加できる、HTML 1枚だけのシンプルなページです。第7章までは curl やブラウザで通信を「観察」し、第12章では curl で API を「呼び出し」ましたが、この章ではブラウザの中で動く JavaScript から API を呼び出します。

必要なのは Visual Studio Code のようなテキストエディタと、Chrome や Edge などのブラウザだけです。サーバーの用意は不要で、作った HTML ファイルをブラウザにドラッグ＆ドロップ（または「ファイルを開く」）すれば動きます。

ファイル構成

posts-app/
└── index.html   ← HTML・CSS・JavaScript をこの1ファイルにまとめる

まずは骨組みだけ用意します。<div id="posts"> に一覧を表示し、<form id="postForm"> から新規投稿を送信します。

index.html（骨組み） 
<!-- 投稿一覧を表示する場所 -->
<div id="status"></div>
<ul id="posts"></ul>

<!-- 新規投稿フォーム -->
<form id="postForm">
  <input name="title" placeholder="タイトル" required>
  <textarea name="body" placeholder="本文" required></textarea>
  <button type="submit">投稿する</button>
</form>

<script>
  // このあとの節で、この<script>の中身を作っていきます
</script>

JSONPlaceholderの書き込みは保存されない

第12章でも触れたとおり、JSONPlaceholder への POST は成功したふりをして、実際にはサーバーに保存されません。この章でも「送信できた・レスポンスが返ってきた」ことの確認が目的で、投稿が永続的に残るわけではない点に注意してください。

14.2 fetchで一覧を取得して表示

JavaScript から HTTP リクエストを送る標準の方法が fetch 関数です。fetch(URL) は「まだ結果が届いていないかもしれない値（Promise）」を返すため、async / await を使って「レスポンスが届くまで待つ」と読みやすくなります。

投稿一覧を取得する関数 
async function loadPosts() {
  // userId=1 の投稿だけに絞り込んで取得する（第12章の復習）
  const url = "https://jsonplaceholder.typicode.com/posts?userId=1";
  const response = await fetch(url); // ここでレスポンスが届くまで待つ

  // fetchはHTTPエラー（404/500など）ではrejectしない！
  if (!response.ok) {
    throw new Error("HTTPエラー: " + response.status);
  }

  const posts = await response.json(); // ボディをJSONとして読む
  return posts; // 呼び出し元へ配列を返す
}

重要: fetchは404や500でreject（例外）しない

初心者がつまずきやすい点です。fetch が失敗（catch に落ちる）するのは、通信そのものができなかったとき（オフライン・DNS失敗など）だけです。サーバーが 404 Not Found や 500 Internal Server Error を返した場合でも、fetch 自体は「成功」扱いになり、必ず自分で response.ok（またはステータスコード）を確認する必要があります。

取得した配列を、DOM操作で <ul id="posts"> に一覧表示します。

一覧を画面に表示する 
function renderPosts(posts) {
  const ul = document.getElementById("posts");
  ul.innerHTML = ""; // いったん空にする

  // 配列の各要素からli要素を作って追加する
  posts.forEach((post) => {
    const li = document.createElement("li");
    li.textContent = post.id + ": " + post.title;
    ul.appendChild(li);
  });
}

2つの関数を組み合わせて呼び出します。

ページ読み込み時に一覧を表示する 
loadPosts().then((posts) => {
  renderPosts(posts);
});
// または async 関数内なら
// const posts = await loadPosts();
// renderPosts(posts);

重要ポイント

response.json() も Promise を返します（ボディの読み込みに時間がかかることがあるため）。await をつけ忘れると、JSONの中身ではなく「Promiseオブジェクトそのもの」を扱ってしまい、意図しない結果になります。

14.3 フォームからPOSTする

次はフォームの入力内容を JSON に変換し、POST で送信します。第6章で学んだとおり、JSON のリクエストボディを送るときは Content-Type: application/json ヘッダーを付け、ボディは文字列にする必要があるため JSON.stringify を使います（第10章の復習）。

フォーム送信時にPOSTする 
document.getElementById("postForm").addEventListener("submit", async (event) => {
  event.preventDefault(); // ページの再読み込みを止める
  const form = event.target;
  const newPost = { title: form.title.value, body: form.body.value, userId: 1 };

  const response = await fetch("https://jsonplaceholder.typicode.com/posts", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(newPost), // オブジェクト→JSON文字列
  });

  if (!response.ok) throw new Error("投稿に失敗: " + response.status);
  const created = await response.json();
  console.log("作成された投稿:", created); // 201とid（101など）を確認
});

送信に成功すると、サーバーは 201 Created と、新しく割り振られた id（JSONPlaceholderでは常に 101）を返します（第5章の復習）。

動作確認

フォームに入力して「投稿する」を押し、開発者ツールのコンソールに 作成された投稿: {id: 101, title: ..., ...} が表示されれば成功です。Network タブでは、このリクエストの Status が 201 になっていることも確認しましょう（第7章の復習）。

14.4 読み込み中表示とエラー処理

実際のアプリでは、通信には時間がかかりますし、失敗することもあります。「読み込み中です」の表示と、失敗時のメッセージ表示を用意しておくと、利用者に親切なページになります。

エラーには大きく2種類あります。ネットワークエラー（オフライン、URLの打ち間違いによるDNS失敗など。fetch 自体が失敗し catch に落ちる）と、HTTPエラー（404や500などサーバーからの応答はあるが失敗を示す。14.2で見たとおり自分でチェックが必要）です。

読み込み中表示とtry/catch 
async function init() {
  const statusEl = document.getElementById("status");
  statusEl.textContent = "読み込み中..."; // まず表示
  try {
    const posts = await loadPosts(); // 14.2で作った関数
    renderPosts(posts);
    statusEl.textContent = ""; // 成功したら消す
  } catch (error) {
    // ネットワークエラー・HTTPエラーの両方がここに来る
    statusEl.textContent = "読み込みに失敗しました: " + error.message;
    console.error(error);
  }
}

init(); // ページ読み込み時に実行
種類 例 fetchの挙動
ネットワークエラー オフライン、DNS失敗、CORSエラー Promiseがreject（catchに落ちる）
HTTPエラー 404 Not Found、500 Internal Server Error Promiseはresolve（自分で response.ok を確認）

14.5 CORS

ブラウザには同一オリジンポリシーという安全のための制約があり、あるサイトの JavaScript が、別のサイト（別の「オリジン」）へ自由に通信することを既定では禁止しています。オリジンとは「スキーム＋ホスト＋ポート」の組み合わせのことです（第2章で学んだURLの構成要素です）。

CORS（Cross-Origin Resource Sharing）は、サーバー側が「このオリジンからのアクセスは許可します」とレスポンスヘッダーで宣言することで、この制約を緩める仕組みです。JSONPlaceholder はどのオリジンからのアクセスも許可するよう設定されているため、ローカルの file:// ファイルからでも問題なく fetch できます。

sequenceDiagram participant B as ブラウザ（JS） participant S as APIサーバー B->>S: リクエスト（Origin: null または元のサイト） S-->>B: レスポンス＋Access-Control-Allow-Origin: * Note over B: 許可されたオリジンなら結果を渡す
許可がなければCORSエラーでブロック

許可されていないAPIにfetchすると、コンソールに次のようなエラーが出て、JavaScript側では通信結果を受け取れません（サーバー自体は処理を行っている場合もあります）。

CORSエラーの例（開発者ツールのコンソール） 
Access to fetch at 'https://api.example.com/v1/data' from origin
'null' has been blocked by CORS policy: No 'Access-Control-Allow-Origin'
header is present on the requested resource.

PUT・DELETE、独自ヘッダー、Content-Type: application/json を付けた POST など、「単純ではない」リクエストでは（14.3 の POST もこれに当たります）、本番の通信の前にブラウザが自動で OPTIONS メソッドのプリフライトリクエストを送り、サーバーに「このリクエストを送ってよいか」を事前確認します（第4章 4.4 で名前だけ触れた OPTIONS の実際の用途です）。開発者ツールの Network タブには、この事前確認のリクエストも表示されます。

CORSはクライアント側では直せない

CORSエラーは「サーバーがそのオリジンを許可していない」ことが原因なので、解決にはサーバー側でのヘッダー設定変更が必要です。フロントエンド開発者にできることは、開発中だけプロキシを経由させるなどの回避策に限られます。「自分のJavaScriptのミスではないかもしれない」と落ち着いて切り分けましょう。

理解度確認クイズ

  1. Q1. fetchでAPIから404が返ってきたとき、fetchの返すPromiseはreject（catchに落ちる）しますか。それとも resolve しますか。

    回答を表示

    resolveします。fetchはHTTPエラー（404や500など）ではrejectしません。通信自体が成立した以上「成功」扱いになり、失敗かどうかは自分で response.ok やステータスコードを確認する必要があります。

  2. Q2. JSONをリクエストボディとして送るとき、なぜ JSON.stringify で文字列に変換する必要がありますか。

    回答を表示

    HTTPのボディはバイト列（実質的には文字列）として送られるためです。JavaScriptのオブジェクトをそのまま渡すことはできず、JSON.stringifyでJSON形式の文字列に変換してからbodyに指定します。あわせてContent-Type: application/jsonヘッダーで「これはJSONです」とサーバーに伝えます。

  3. Q3. ネットワークエラーとHTTPエラーの違いを、fetchの挙動の違いとともに説明してください。

    回答を表示

    ネットワークエラーは通信自体が成立しない状態（オフライン、DNS失敗、CORSブロックなど）で、fetchのPromiseがrejectしtry/catchのcatchに落ちます。HTTPエラーはサーバーからの応答はあるが失敗を示す状態（404や500など）で、fetch自体はresolveするため、自分でresponse.okを確認して初めて気づけます。

  4. Q4. CORSエラーが出たとき、フロントエンドのJavaScriptコードを直すだけで解決できますか。

    回答を表示

    基本的にできません。CORSエラーは「サーバーがそのオリジンからのアクセスを許可していない」ことが原因なので、解決にはサーバー側でAccess-Control-Allow-Originなどのレスポンスヘッダーを設定する必要があります。フロントエンド側の実装ミスとは限りません。

  5. Q5. この教材の第1章で示した「教材の地図」（URL・DNS → HTTP → JSON/Cookie・HTTPS → REST API → 実践）を振り返って、あなたが今回作ったページのどの部分がHTTP、どの部分がJSONに対応するか説明してください。

    回答を表示

    HTTPに対応するのは、fetchのmethod（GET/POST）・URL・ステータスコードの確認（response.ok）・ヘッダー（Content-Type）の部分です。JSONに対応するのは、response.json()でレスポンスボディを読み取る部分と、JSON.stringifyで送信データを文字列化する部分です。両者を組み合わせて、REST API（/postsというリソース）を実際に呼び出しています。
