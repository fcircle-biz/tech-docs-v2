Cookie・セッション・HTTPS

第3章で学んだとおり、HTTP は「毎回初対面」のステートレスな通信です。しかし実際のWebサイトはログイン状態やカートの中身を覚えています。この章では、その仕組みを支える Cookie とセッション、API でよく使われるトークン認証、そして通信を守る HTTPS を学びます。

この章で学ぶこと

  • Cookie が Set-Cookie / Cookie ヘッダーでやり取りされる仕組みを説明できる
  • セッションの考え方と、HttpOnly・Secure・SameSite の役割を説明できる
  • Web API でよく使われるトークン認証（Authorization: Bearer）の入口が分かる
  • HTTPS が防ぐ3つの脅威と、TLS・証明書の役割を説明できる

8.1 ステートレスの困りごと

第3章で「HTTP はステートレス（状態を保持しない）」と学びました。HTTP の各リクエストは独立して解釈されるため、HTTP の仕組みだけでは「さっきのリクエストを送ってきたのは誰か」を結び付けられません。これは仕組みをシンプルに保つ利点がある一方、次のような場面では困ります。

  • ログインしたのに、次のページに移動したらまた未ログイン扱いになってしまう
  • ショッピングサイトで商品をカートに入れたのに、別のページでカートが空になってしまう
  • 「前回の続きから」といった利用者ごとの状態を表示できない

こうした「状態」を、ステートレスな HTTP の上でどう覚えておくか。その答えが、この章で学ぶ Cookie です。

レストランのたとえで考えると

第1章のレストランのたとえでは、注文のたびに店員（サーバー）はお客さん（クライアント）を初対面として扱います。何度も来ているのに、そのたびに「本日は何名様ですか」と聞かれるようなものです。そこで店が「番号札」を渡し、次に来たときにその番号札を見せてもらえば「あ、さっきの方ですね」と分かるようにする——これが Cookie の発想です。

8.2 Cookieの仕組み

Cookie（クッキー）は、サーバーがブラウザに預ける小さなデータです。サーバーはレスポンスの Set-Cookie ヘッダーで Cookie を渡し、ブラウザはそれを保存します。以降、同じサーバーにリクエストを送るたびに、ブラウザは保存した Cookie を Cookie ヘッダーに載せて自動的に送り返します。

sequenceDiagram participant B as ブラウザ participant S as サーバー B->>S: ① GET /login（Cookie なし） S-->>B: 200 OK, Set-Cookie: sessionId=abc123 Note over B: Cookie を保存 B->>S: ② GET /mypage, Cookie: sessionId=abc123 S-->>B: 200 OK（「さっきの人だ」と認識）

Set-Cookie ヘッダーには、名前と値のほかに属性を付けて、有効期限や使われる範囲を指定できます。

レスポンスヘッダーの例 
Set-Cookie: sessionId=abc123; Max-Age=3600; Domain=example.com; Path=/
属性 意味
Expires / Max-Age 有効期限。Expires は日時、Max-Age は秒数で指定。どちらも無ければセッション Cookie となり、原則として「ブラウザを閉じるまで」有効（ただし、前回のタブを復元する機能などにより、ブラウザを再起動しても残る場合がある）
Domain どのドメイン宛のリクエストに Cookie を付けて送るか
Path どのパス配下のリクエストに Cookie を付けて送るか（例: /admin のみ）

重要ポイント

Cookie を送るのはブラウザの役目で、開発者が毎回手動でヘッダーを付ける必要はありません。一度保存されれば、条件に合うリクエストに自動的に付いてきます。この「自動で付く」性質が、8.3 で学ぶ SameSite 属性の話につながります。

8.3 セッションとセキュリティ属性

パスワードやカートの中身そのものを Cookie に入れるのは危険です。ブラウザに保存された値は本人が中身を見たり書き換えたりできてしまうためです。そこで実際のWebサイトの多くは、次のような仕組みを使います。これをセッションと呼びます。

  1. サーバー側のメモリやデータベースに「誰がログイン中か」「カートに何が入っているか」という状態そのものを保存する
  2. その状態には セッションID（ランダムな文字列）という「引換券の番号」を振る
  3. ブラウザには、セッションIDだけを Cookie として渡す

ブラウザが持っているのは番号だけなので、たとえ盗み見られても、それだけでは中身は分かりません（もっとも、その番号自体が盗まれると成りすましに使われてしまいます）。そこで、セッションIDを運ぶ Cookie には次の属性を付けるのが基本です。

属性 役割
HttpOnly JavaScript（document.cookie）からこの Cookie を読めなくする。XSS（悪意あるスクリプトの埋め込み）が起きたときに、Cookie を盗み出される被害を軽減する（XSS そのものを防ぐわけではない）
Secure HTTPS の通信でしかこの Cookie を送らないようにする。盗聴対策（8.5 の HTTPS と関係）
SameSite 他サイトを経由したリクエストで Cookie を送るかどうかを制限する。既定値はブラウザによって異なるが、Chrome・Edge など近年の主要ブラウザは指定しない場合 Lax 相当として扱う（確実にするには明示的に指定する）。Strict（同一サイトのみ）・Lax（一部の他サイト遷移は許可）・None（制限なし。Secure 必須）

セッションハイジャックとは

他人のセッションIDを盗み、その人になりすましてログイン状態を乗っ取る攻撃をセッションハイジャックと呼びます。HttpOnly・Secure・SameSite は、いずれもセッションIDが盗まれたり不正に使われたりする経路を1つずつ狭めるための設定です（どれか1つで万全になるわけではありません）。作る側になったら、この3つを既定でオンにする意識を持ちましょう。

8.4 トークン認証

Cookie はブラウザが自動で送ってくれる分、ブラウザ以外のクライアント（スマホアプリ、他サーバー、curl など）とは相性が悪い場面があります。そこで Web API の世界では、Authorization ヘッダーにトークンを載せる方式がよく使われます。

リクエストヘッダーの例 
GET /v1/users/me HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

Bearer は「このトークンを持参した人（bearer）に、トークンが示す権限を認める」という意味の認証方式（スキーム）の名前で、もともとは OAuth 2.0 のアクセストークンを送る方法として仕様（RFC 6750）で定められたものです。クライアントは、ログイン時に発行されたトークン（文字列）を保存しておき、以降のすべてのリクエストで自分から Authorization ヘッダーに付けて送ります。Cookie のような自動送信は行われないため、送り忘れると認証エラーになります。

よく使われるトークン形式に JWT（JSON Web Token）があります。JWT は、ユーザーIDや有効期限などの情報（クレーム）を運ぶための形式です。一般には署名付き（JWS）で使われ、改ざんを検知できますが、この場合は中身（ペイロード）が暗号化されていないため、トークンを手にした人なら誰でも読めます。そのため、署名付きの JWT に秘密の情報は入れません（中身を暗号化する JWE という形式もありますが、ここでは名前だけ知っておけば十分です）。詳しい仕組みや、外部サービスと連携してログインする OAuth は、この教材の範囲外の発展的なテーマです。

観点 Cookie ＋ セッション（典型例） Authorization ヘッダー ＋ トークン（典型例）
送信 ブラウザが自動で送る クライアントが自分で毎回付ける
主な用途 ブラウザで見る一般的なWebサイト Web API・モバイルアプリ・サーバー間連携
状態の場所 サーバー側（セッションID で参照） トークン自身に情報を含められる（JWT の場合）

この表は、よく見かける2つの典型的な組み合わせを比べたものです。Cookie は値をブラウザに保存して自動で送る仕組み、JWT はトークンの形式、セッションはサーバー側で状態を持つ方式で、それぞれ別の軸の話です。そのため、JWT を Cookie に入れて送る設計や、Authorization ヘッダーで受け取ったトークンを手がかりにサーバー側に保存した情報を参照する設計もあります。

8.5 HTTPS

ここまで見てきた Cookie やトークンは、盗まれると成りすましに使われてしまう重要な情報です。それを守るのが HTTPS（HTTP Secure）です。HTTPS は、通常の HTTP 通信を TLS（Transport Layer Security）という仕組みで暗号化したものです。HTTPS が防ぐ脅威は、大きく3つに整理できます。

盗聴

通信経路上で内容を覗き見られること。暗号化により、途中で盗み見ても内容が読めなくなる

改ざん

通信の途中で内容を書き換えられること。改ざんがあれば検知できる仕組みが組み込まれている

なりすまし

偽サーバーが本物のふりをすること。証明書により、通信相手が本物かを確認できる

3つ目の「なりすまし」を防ぐ鍵が証明書です。サーバーは、信頼できる第三者機関である認証局（CA: Certificate Authority）から「このドメインの持ち主である」ことを証明する証明書を発行してもらいます。ブラウザは接続時にこの証明書を確認し、問題なければ通信を続け、アドレスバーに鍵マーク（ブラウザによってはサイト情報アイコン）を表示します。問題があれば警告画面を出します。

sequenceDiagram participant B as ブラウザ participant S as サーバー B->>S: ① 接続開始（このドメインの証明書をください） S-->>B: 証明書（認証局の署名つき）を提示 Note over B: ② 証明書が信頼できる認証局のものか確認 B->>S: ③ 暗号化の鍵を交換 Note over B,S: 以降のHTTP通信はすべて暗号化される

HTTP と HTTPS が混ざる警告

HTTPS のページの中に、暗号化されていない HTTP の画像や JavaScript が混じっている状態を混在コンテンツと呼びます。JavaScript などはブラウザが読み込みをブロックし、画像などは自動で HTTPS に切り替えて読み込んだり警告を表示したりします。ページ内のすべてのリソースを HTTPS でそろえるのが基本です。

やってみよう 8-1: Cookie がセットされる様子と証明書を確認しよう

Set-Cookie を実際に受け取り、ブラウザに保存された Cookie と、通信を守る証明書の中身を自分の目で確認します。

手順

  1. 1 ブラウザで https://httpbin.org/cookies/set?lesson=web を開く（Set-Cookie で lesson=web がセットされ、/cookies へリダイレクトされる）。
  2. 2 開発者ツールを開き、Application（Chrome/Edge）または ストレージ（Firefox）タブ →「Cookie」→ httpbin.org を選び、lesson という Cookie が保存されていることを確認する。
  3. 3 アドレスバーの鍵マーク（またはサイト情報アイコン）をクリックし、「証明書は有効です」といった表示や発行先・発行元の情報を見る。

Cookie の一覧に表示される「HttpOnly」「Secure」「SameSite」の列にも注目してみましょう。8.3 で学んだ属性が、実際にどう設定されているかが確認できます。

理解度確認クイズ

  1. Q1. サーバーが Cookie をブラウザに渡すときに使うレスポンスヘッダーの名前は何ですか。

    回答を表示

    Set-Cookie ヘッダーです。ブラウザはこれを受け取って Cookie を保存し、以降のリクエストで Cookie ヘッダーに載せて送り返します。

  2. Q2. セッションの仕組みでは、なぜログイン情報そのものではなく「セッションID」だけを Cookie にするのですか。

    回答を表示

    Cookie はブラウザ側に保存されるため、本人が中身を見たり書き換えたりできてしまいます。実際の状態はサーバー側だけで持ち、ブラウザには「引換券の番号」であるセッションIDだけを渡すことで、重要な情報をクライアント側にさらさずに済みます。

  3. Q3. HttpOnly・Secure・SameSite は、それぞれ何のための属性ですか。

    回答を表示

    HttpOnly は JavaScript から Cookie を読めなくして、XSS（悪意あるスクリプトの埋め込み）が起きた場合に Cookie を盗み出されるリスクを減らします（XSS そのものを防ぐわけではありません）。Secure は HTTPS 通信でのみ Cookie を送り、暗号化されていない通信での盗聴を防ぎます。SameSite は他サイト経由のリクエストで Cookie が送られる範囲を制限します。

  4. Q4. HTTPS（TLS）が防ぐ3つの脅威と、それぞれを防ぐ仕組みを挙げてください。

    回答を表示

    盗聴（暗号化により内容を読めなくする）、改ざん（内容が書き換えられていないか検知する）、なりすまし（認証局が発行する証明書で相手が本物か確認する）の3つです。
