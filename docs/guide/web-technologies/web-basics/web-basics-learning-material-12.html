REST APIを呼び出してみよう

第11章では「リソースを URI で表し、メソッドで操作する」という REST の考え方を学びました。この章ではいよいよ、その考え方が実際の API でどう動くのかを、練習用の REST API JSONPlaceholder を相手に手を動かして確かめます。curl で GET・POST・PUT・PATCH・DELETE を一通り実行し、APIキーや API ドキュメントの読み方にも触れます。

この章で学ぶこと

  • curl を使って REST API に CRUD（作成・読み取り・更新・削除）を実行できる
  • クエリパラメータで一覧を絞り込み、リクエストボディで JSON を送信できる
  • 存在しないリソースへのアクセスや作成・更新・削除で返るステータスコードを説明できる
  • APIキーによる認証の仕組みと、API ドキュメント（OpenAPI）のおおまかな読み方が分かる

12.1 JSONPlaceholderを知る

自分の API を用意しなくても REST の練習ができるよう、無料で公開されている練習用 API JSONPlaceholder（https://jsonplaceholder.typicode.com）を使います。ダミーのブログ投稿・ユーザー・コメントなどのデータがあらかじめ用意されており、この章から先はこの API を共通の練習台にします。

リソース（コレクション） 内容 件数
/posts ブログ投稿（title・body・userId） 100件
/users ユーザー情報 10件
/comments 投稿へのコメント（postId で紐づく） 500件
/todos やることリスト（完了フラグ付き） 200件

書き込み系は「成功したふり」

JSONPlaceholder は練習用のため、POST・PUT・PATCH・DELETE は成功したかのようなレスポンスを返しますが、実際のデータベースには保存・変更・削除されません。何度実行しても、元のデータは初期状態のままです。安心して何度でも試せます。

この章のコマンドはすべて curl で実行します。curl の基本オプション（-i・-X・-H・-d）は第7章で学んだものを使います。忘れてしまった場合は第7章を見直してください（Windows では curl.exe）。

12.2 読み取り（GET）

まずは一覧取得と個別取得です。第11章で学んだとおり、コレクションには複数形の URI、個別のリソースにはその ID を付けた URI を使います。

一覧取得と個別取得 
# 投稿を全件取得（コレクション）
curl -i https://jsonplaceholder.typicode.com/posts

# id=1 の投稿を1件だけ取得（個別リソース）
curl -i https://jsonplaceholder.typicode.com/posts/1

# id=1 の投稿にぶら下がるコメント一覧（ネストしたリソース）
curl -i https://jsonplaceholder.typicode.com/posts/1/comments

一覧の中から条件に合うものだけ欲しいときは、URL の末尾に ?キー=値 の形でクエリパラメータを付けます（第2章で学んだ URL の構成要素の1つです）。

クエリパラメータで絞り込む 
# userId=1 が書いた投稿だけに絞り込む（結果は10件）
curl -i "https://jsonplaceholder.typicode.com/posts?userId=1"

存在しない ID を指定すると、第5章で学んだ 404 Not Found が返ります。「404 だから壊れている」のではなく「探したが見つからなかった、という正常な応答」だと分かることが大切です。

存在しないリソースへのアクセス 
HTTP/1.1 404 Not Found
Content-Type: application/json; charset=utf-8

{}

動作確認

curl -i https://jsonplaceholder.typicode.com/posts/9999 を実行すると、ステータス行が HTTP/1.1 404 Not Found、ボディが {}（空のオブジェクト）になることを確認しましょう（環境によってはステータス行が HTTP/2 404 と表示されますが、意味は同じです）。

12.3 作成（POST）

新しい投稿を作るときは、コレクションの URI（/posts）に対して POST を送ります。送るデータは JSON なので、Content-Type: application/json ヘッダーを必ず付け、ボディに JSON 文字列を渡します。

新しい投稿を作成する 
curl -i -X POST https://jsonplaceholder.typicode.com/posts \
  -H "Content-Type: application/json" \
  -d '{"title": "はじめての投稿", "body": "REST APIの練習です", "userId": 1}'

成功すると、第5章で学んだ「新しいリソースを作成した」ことを表す 201 Created が返り、ボディには送った内容に加えて、サーバーが割り振った id（この API では常に 101）が含まれます。

POSTのレスポンス 
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8

{
  "title": "はじめての投稿",
  "body": "REST APIの練習です",
  "userId": 1,
  "id": 101
}

id: 101 は毎回同じ

JSONPlaceholder はもともと100件の投稿を持っているため、何回 POST しても次の番号「101」が返るだけで、実際には保存されません。何度実行しても id が増え続けたりはしないので、失敗したのかと心配する必要はありません。

12.4 更新と削除（PUT・PATCH・DELETE）

更新・削除は、個別のリソースを指すコレクション+ID の URI（/posts/1）に対して行います。第4章で学んだとおり、PUT は全体の置き換え、PATCH は一部の項目だけの更新という違いがあります。

PUT：投稿全体を置き換える 
curl -i -X PUT https://jsonplaceholder.typicode.com/posts/1 \
  -H "Content-Type: application/json" \
  -d '{"id": 1, "title": "更新後のタイトル", "body": "全部書き換え", "userId": 1}'
# → 200 OK（送った内容がそのまま返る）
PATCH：titleだけを部分更新する 
curl -i -X PATCH https://jsonplaceholder.typicode.com/posts/1 \
  -H "Content-Type: application/json" \
  -d '{"title": "タイトルだけ変更"}'
# → 200 OK（body・userIdは元の値のまま、titleだけ差し替わって返る）
DELETE：投稿を削除する 
curl -i -X DELETE https://jsonplaceholder.typicode.com/posts/1
# → 200 OK、ボディは空のオブジェクト {}

3つのメソッドをまとめると、次のようになります。

メソッド 意味 送るボディ この API の応答
PUT 全体を置き換える 全項目 200 OK＋送った内容
PATCH 一部だけ更新する 変更したい項目だけ 200 OK＋更新後の全体
DELETE 削除する なし 200 OK＋空の {}

API によって204になることもある

DELETE の成功時のステータスコードは API によって異なり、「本文なし」を意味する 204 No Content を返す設計もよく使われます（第13章で扱います）。JSONPlaceholder は分かりやすさを優先し、200 と空オブジェクトを返す実装になっています。

12.5 APIキー・認証とAPIドキュメント

JSONPlaceholder は誰でも自由に使える練習用 API ですが、実際の Web API の多くは「誰が呼び出しているか」を確認するためにAPIキーを要求します。第8章で学んだトークン認証の一種で、渡し方には主に2通りがあります。

ヘッダーで渡す（推奨）

多くの API は Authorization: Bearer <キー>、または独自の X-API-Key ヘッダーでのキー送信を推奨します。

クエリパラメータで渡す

?api_key=xxxx のように URL に含める方式。手軽ですが、アクセスログや履歴に残りやすい欠点があります。

APIキーをヘッダーで送る例（架空のAPI） 
curl -i https://api.example.com/v1/weather \
  -H "Authorization: Bearer sk_live_xxxxxxxxxxxx"

APIキーは秘密情報

APIキーはパスワードと同じ扱いをします。ソースコードやGitHubに直書きしない、フロントエンドのJavaScriptに埋め込まない（誰でも見えてしまう）、他人と共有しないことが原則です。第8章の Authorization ヘッダーの復習も兼ねて覚えておきましょう。

キーが無効だったり不足していたりすると、第5章で学んだ 401 Unauthorized（誰であるか確認できない）や、決められた回数を超えて呼び出したときの 429 Too Many Requests（レート制限。「1分間に60回まで」のような上限）が返ります。

実際の API を使うときは、まずAPI ドキュメントを読みます。多くの API は OpenAPI（旧称 Swagger）という形式でエンドポイントを定義し、ブラウザで見やすく表示する Swagger UI を公開しています。エンドポイントごとに「必要なパラメータ」「返ってくるステータスコード」「レスポンスの例」が一覧になっているので、これまで学んだ用語（メソッド・エンドポイント・ヘッダー・ステータスコード）が分かれば読みこなせます。

やってみよう 12-1: JSONPlaceholderでCRUDミッション

これまでのコマンドを組み合わせて、次のミッションに挑戦しましょう。すべて curl で実行できます。

ミッション

  1. 1 /posts?userId=1 を取得し、userId=1 が書いた投稿が何件あるか数える（答え：10件）。
  2. 2 自分の名前をタイトルにした投稿を POST で新規作成し、返ってきた id を確認する。
  3. 3 /posts/1 を PATCH して title だけ変更し、body が変わっていないことを確認する。
  4. 4 /posts/1 を DELETE し、ステータスコードとボディを確認する。
  5. 5 最後に /posts/1 をもう一度 GET し、削除したはずのデータがまだ取得できることを確認する（＝実際には保存されていない証拠）。

ミッション5がこの章でいちばん大事な確認です。「削除に成功した」というレスポンスが返っても、練習用APIでは元データは変わりません。本物のAPIと練習用APIの違いを体感しておきましょう。

理解度確認クイズ

  1. Q1. /posts?userId=1 のように URL の末尾に付ける ?キー=値 の部分を何と呼びますか。

    回答を表示

    クエリパラメータです。一覧の絞り込みなど、URI が指すリソースの範囲を調整するために使います。

  2. Q2. POST で /posts に新規投稿を送ると、成功時に返るステータスコードは何番ですか。またボディには何が含まれますか。

    回答を表示

    201 Created が返ります。ボディには送った内容に加えて、サーバーが割り振った id（JSONPlaceholderでは常に101）が含まれます。

  3. Q3. PUT と PATCH の違いを、送るボディの内容に注目して説明してください。

    回答を表示

    PUT はリソース全体を置き換えるため全項目を送る必要があります。PATCH は変更したい項目だけを送り、それ以外の項目は元の値のまま残ります。

  4. Q4. JSONPlaceholderで /posts/1 を DELETE した直後にもう一度 GET すると、なぜまだデータが取得できるのですか。

    回答を表示

    JSONPlaceholderは練習用APIで、書き込み系のリクエストは成功したレスポンスを返すだけで、実際のデータベースには反映されないためです。

  5. Q5. APIキーが無効なときと、呼び出し回数の上限を超えたときに、それぞれ何番のステータスコードが返る可能性がありますか。

    回答を表示

    APIキーが無効・不足している場合は401 Unauthorized、呼び出し回数の上限（レート制限）を超えた場合は429 Too Many Requestsが返る可能性があります。
