DB設計とは — なぜ設計が必要か

SQL でデータを取り出せるようになると、次にぶつかるのが「そもそもテーブルをどう分ければよいのか」という疑問です。この章では、架空の文具通販「さくら文具」の Excel 受注一覧を題材に、設計しないまま1つの表にデータを詰め込むと何が起きるのかを体感し、DB設計の工程（概念設計・論理設計・物理設計）と本ガイド全12章の進み方をつかみます。

この章の学習目標

  • DB設計が「何を・どこに・どう貯めるかを決める作業」であることを説明できる
  • 設計せずに1つの表へ詰め込んだときに起きる問題を、具体例で3つ挙げられる
  • 概念設計・論理設計・物理設計の違いと、それぞれの成果物が分かる
  • 本ガイドの共通題材「さくら文具」の業務と、全12章の学習の流れを把握する

1.1 DB設計とは何か

DB設計（データベース設計）とは、ひとことで言えば「どんなデータを、どの表に、どんな形で貯めるかを決める作業」です。家を建てる前に間取り図を描くのと同じで、データベースも、中身を入れ始める前に「部屋割り」を決めておく必要があります。

具体的には、次のような問いに答えを出していきます。

決めること 問いの例（さくら文具の場合） 学ぶ章
何を管理するか 顧客・商品・受注・担当者…ほかに管理すべき「もの・こと」はないか 第3章
それぞれの関係 1人の顧客は何回注文できるか。1回の注文に商品は何個入るか 第4〜5章
表の分け方 顧客の住所は受注の表に書くべきか、別の表にすべきか 第6〜8章
行を見分ける目印 顧客を顧客番号で区別するか、システムが振る連番で区別するか 第2章・第9章
値の形とルール 単価は整数か小数か。数量に 0 やマイナスを許すか 第10章

SQL は「データを出し入れする言葉」でしたが、DB設計は「その言葉が相手にする入れ物の形」を決める仕事です。入れ物の形が悪いと、どんなに SQL が上手でも、正しいデータを保つのが難しくなります。

ヒント: 設計は「後から直しにくい」

画面のボタンの位置はリリース後でも比較的気軽に変えられますが、テーブルの構造は、すでに貯まった大量のデータと、それを読み書きするたくさんのプログラムに影響します。システムの中で最も長生きするのはデータだ、とよく言われます。だからこそ、最初の設計に時間をかける価値があります。

1.2 設計しないと何が起きるか — さくら文具の受注一覧

本ガイドでは全章を通して、架空の文具通販ショップ「さくら文具」を題材にします。さくら文具では、これまで注文を Excel の1枚のシートで管理してきました。見やすさを優先して「1行＝1回の注文」でまとめた、次のような表です。

受注番号 受注日 顧客番号 顧客名 顧客住所 担当者 商品コード 商品名 分類 単価 数量
1001 2025-04-01 C001 佐藤 花子 東京都港区… 山田 P01, P03 ボールペン黒, A5ノート 筆記具, ノート 120, 280 10, 5
1002 2025-04-02 C002 鈴木 一郎 大阪府北区… 田中 P01 ボールペン黒 筆記具 120 3
1003 2025-04-02 C001 佐藤 花子 東京都港区… 山田 P02 蛍光ペン黄 筆記具 150 2

人間が眺める分には分かりやすい表です。ところが、この表をそのままデータベースのテーブルにすると、業務を続けるうちに次のような困りごとが起きます。

直し漏れが起きる

佐藤さんが引っ越すと、1001 と 1003 の2行とも住所を直す必要があります。1行だけ直し忘れると「佐藤さんの住所はどれが正しいのか」分からなくなります。

登録できない

新商品「万年筆」を発売前に登録したくても、この表は「1行＝1回の注文」なので、まだ誰も注文していない商品を書く行がありません。

消すと一緒に消える

鈴木さんの注文 1002 をキャンセルで行ごと削除すると、鈴木さんが顧客だったという事実や住所まで一緒に消えてしまいます。

さらに、1つのセルに「P01, P03」のように複数の値が入っている点も問題です。「ボールペン黒が合計何本売れたか」を SQL で集計しようとしても、カンマで区切られた文字列を分解しなければならず、正確な集計が難しくなります。

重要: 問題の根っこは「同じ事実が何か所にも書かれている」こと

3つの困りごとは、どれも「顧客の情報」「商品の情報」「注文の情報」という別々の事実を1つの行に混ぜていることから生まれています。直し漏れ・登録できない・消すと一緒に消える、という現象は更新異常と呼ばれ、第6章で正式に学びます。そして、事実ごとに表を分けて更新異常を防ぐ手順が正規化（第6〜8章）です。

ちなみに、この受注一覧を事実ごとに分けていくと、最終的に次のような表の組み合わせになります。今はまだ細部を理解する必要はありません。「1枚の表が、役割ごとの6つの表に分かれ、線でつながる」というイメージだけ持っておいてください。

erDiagram customers ||--o{ orders : "注文する" staff ||--o{ orders : "受け付ける" orders ||--|{ order_details : "明細を持つ" products ||--o{ order_details : "明細に含まれる" categories ||--o{ products : "分類する"

このような図を ER図（実体関連図）と呼びます。箱がデータのまとまり（エンティティ）、線がその間の関係（リレーションシップ）です。線の端の記号の読み方は第4章で詳しく学びます。

1.3 DB設計の3つの工程

DB設計は、一度に全部を決めるのではなく、抽象的なところから具体的なところへ3つの段階を踏んで進めるのが一般的です。

flowchart LR A["業務要件
（説明・帳票・画面）"] --> B["概念設計
何を管理するか"] B --> C["論理設計
表と列をどう分けるか"] C --> D["物理設計
どの製品でどう作るか"] D --> E[("データベース")] B -.- B2["概念ER図"] C -.- C2["論理ER図・正規化済みの表"] D -.- D2["テーブル定義書・DDL"]
工程 考えること 主な成果物 製品への依存
概念設計 業務の中で管理したい「もの・こと」（エンティティ）と、その関係を洗い出す。業務担当者と会話できる粒度で描く 概念ER図、用語集 なし
論理設計 属性（列）と主キー・外部キーを決め、正規化で表を整理する 論理ER図、正規化済みのテーブル一覧 ほぼなし（リレーショナルモデルが前提）
物理設計 使う RDBMS に合わせて、データ型・制約・インデックス・命名を決める テーブル定義書、CREATE TABLE 文（DDL） あり（本ガイドは PostgreSQL）

物理設計の最終成果物は、たとえば次のような DDL です。第10章では、さくら文具の全テーブルをこの形で書き上げます。

categories.sql 
-- 商品分類テーブル（物理設計の成果物の例）
CREATE TABLE categories (
    category_id   integer     PRIMARY KEY,      -- 主キー: 行を1つに特定する
    category_name varchar(50) NOT NULL UNIQUE   -- 必須かつ重複禁止
);

ヒント: 工程は行ったり来たりしてよい

実際の現場では、論理設計の途中で「この属性は業務でどう使うのか」が分からなくなり、概念設計に戻って業務担当者に確認し直す、ということがよくあります。3つの工程は一方通行の手順というより、「今どの抽象度で考えているのか」を見失わないための目印だと考えてください。

用語メモ：DDL — Data Definition Language（データ定義言語）の略で、CREATE TABLE のようにテーブルなどの「入れ物」を作る・変える SQL の総称です。

1.4 良い設計とはどんな設計か

DB設計に「唯一の正解」はありませんが、良い設計が満たしている性質には共通点があります。本ガイドでは、次の4つを設計の判断基準として繰り返し使います。

正しさを保てる（整合性）

1つの事実は1か所にだけ書かれ、矛盾したデータが入り込む余地がない。制約でおかしな値を拒否できる。

業務を表している（妥当性）

業務のルール（1回の注文に複数の商品、など）がそのまま表の構造に表れていて、業務担当者に説明できる。

変化に強い（拡張性）

商品分類が増える、配送先を複数持てるようにする、といった変更を、表や列の追加で自然に受け止められる。

使える速さで動く（性能）

よく使う検索や集計が現実的な時間で終わる。必要なら意図的に正規化を崩す判断もする（第11章）。

初心者のうちは、まず「整合性」と「妥当性」を最優先にしてください。性能のために構造を崩すのは、正しい構造を作れるようになってから考えても遅くありません。

注意: 「画面の見た目」に表を合わせない

初心者がやりがちなのが、受注画面や Excel の帳票のレイアウトをそのままテーブルにしてしまうことです。さくら文具の受注一覧はまさにその例でした。画面は「人が見やすい形」、テーブルは「事実を1つずつ正しく貯める形」で、目的が異なります。画面に必要な形は、分けて貯めた表を SQL の JOIN で組み合わせれば作れます。

1.5 本ガイドの進み方

本ガイドは、1.3 で見た3つの工程に沿って進みます。さくら文具の受注一覧という「設計されていない表」から出発し、章を追うごとに整理して、第10章で PostgreSQL のテーブルとして完成させます。

段階 章 さくら文具の設計がどう進むか
土台 第1〜2章 受注一覧の問題点を知り、表・キー・NULL などの基本用語をそろえる
概念設計 第3〜5章 業務説明から顧客・商品・受注などを見つけ、ER図に描き、関係の多重度を決める
論理設計 第6〜9章 受注一覧を第1→第2→第3正規形へ分解し、6つの表とキー・命名を確定する
物理設計 第10〜11章 データ型と制約を決めて DDL を完成させ、単価の履歴などの実務的な課題に対処する
総合演習 第12章 新しい題材（図書館の貸出管理）で、要件から DDL までを自力で通す

ER図はガイド内ではブラウザ上に表示されるので、特別なツールは必要ありません。演習では紙とペンで十分です。DDL を実際に動かしてみたい方は、SQL入門ガイドの第3章の手順で PostgreSQL を用意しておくと、第7章・第10章の SQL をそのまま試せます。

やってみよう 1-1: 受注一覧の「困りごと」を探す

1.2 の受注一覧を見ながら、紙かメモアプリで取り組んでください。正解を当てることより、「どこに同じ情報が繰り返し書かれているか」に気づくことが目的です。

手順

  1. 1 表の中で、同じ値が2回以上書かれている情報をすべて書き出す（例: 佐藤 花子の住所）。
  2. 2 「ボールペン黒の単価が 130 円に値上がりした」とき、どの行のどのセルを直すべきか考える。過去の注文の単価も直してよいのかも考えてみる。
  3. 3 列の見出しを「顧客に関するもの」「商品に関するもの」「注文に関するもの」の3グループに分けてみる。どのグループにも入れにくい列があればメモしておく。

ねらい: 手順3のグループ分けは、第3章の「エンティティの洗い出し」と第7〜8章の「正規化」を先取りしたものです。手順2の「過去の単価を直してよいか」は、実は直してはいけない（注文時の金額が変わってしまう）ため、第11章で「注文時単価を明細に残す」設計として扱います。「数量」がどのグループに入るか迷った方は鋭い観点を持っています。数量は注文と商品の組み合わせに対して決まる値で、第5章の中間エンティティにつながります。

理解度確認クイズ

  1. Q1. さくら文具の受注一覧で、注文 1002 を行ごと削除したときに起きる問題を説明してください。

    回答を表示

    鈴木 一郎さんの情報（顧客番号・氏名・住所）は注文 1002 の行にしか書かれていないため、注文を削除すると「鈴木さんという顧客がいる」という事実まで消えてしまいます。注文の情報と顧客の情報が1つの行に混ざっていることが原因で、このような現象を削除時異常（更新異常の一種）と呼びます。

  2. Q2. 次の作業は、概念設計・論理設計・物理設計のどれにあたりますか。(a) 単価の列を numeric(10,2) 型にする (b) 「顧客」と「受注」を管理対象として洗い出す (c) 受注一覧を正規化して表を分ける

    回答を表示

    (a) 物理設計（使う RDBMS のデータ型を決めている）、(b) 概念設計（管理したい「もの・こと」を洗い出している）、(c) 論理設計（列とキーをもとに表の分け方を決めている）です。

  3. Q3. 「受注画面に顧客名・商品名・分類がすべて表示されるので、テーブルも同じ列構成にすべきだ」という意見に、どう答えますか。

    回答を表示

    画面は人が見やすい形、テーブルは事実を1か所ずつ正しく貯める形で、目的が違います。顧客・商品・受注を別々の表に分けて貯めておけば、画面に必要な形は SQL の JOIN で組み合わせて作れます。画面に合わせて1つの表にすると、直し漏れ・登録できない・消すと一緒に消える、といった更新異常を招きます。

  4. Q4. 1つのセルに「P01, P03」のように複数の商品コードを入れると、どんな不便がありますか。

    回答を表示

    「商品ごとの販売数量」のような集計や、「P03 を含む注文」の検索を行うたびに文字列を分解する必要があり、SQL が複雑で誤りやすくなります。また、商品コードの値が正しいかを外部キーなどの制約で確かめることもできません。1つのセルには1つの値だけを入れる、というのが第7章で学ぶ第1正規形の考え方です。
