業務を読み解きエンティティを見つける

前章でリレーショナルモデルの用語をそろえたので、いよいよ概念設計の第一歩を踏み出します。この章では「さくら文具」の業務説明文からエンティティ（管理したい「もの・こと」）と属性を洗い出す方法を学びます。名詞抽出法、リソース系とイベント系の分類、「住所は属性かエンティティか」の見分け方、そして業務担当者への確認質問の作り方を、実際の要件文を使って実践します。

この章の学習目標

  • 業務の説明文から名詞を抽出し、エンティティの候補を洗い出せる
  • 候補を「リソース系（マスタ）」と「イベント系（トランザクション）」に分類できる
  • 「住所」のような名詞が属性か独立したエンティティかを、判断基準を使って見分けられる
  • 抽出結果の不明点を、業務担当者への確認質問という形にまとめられる
  • さくら文具の業務要件から、実際にエンティティ・属性の一覧を作成できる

3.1 概念設計の最初の一歩 — エンティティとは何か

第1章で見たとおり、DB設計は概念設計 → 論理設計 → 物理設計の順に進みます。概念設計の最初の作業は、業務の中で「情報として管理しておきたいもの・こと」を見つけ出すことです。これをエンティティ（実体）と呼びます。

エンティティは、第2章で学んだリレーション（表）の元になる概念です。「顧客」「商品」「注文」はどれもエンティティの例で、最終的には customers・products・orders のような表になっていきます。ただしこの章では、まだ表の形は考えません。「何を管理したいか」を業務の言葉のまま洗い出すことに集中します。

用語 意味 さくら文具の例
エンティティ 管理したい「もの・こと」のまとまり。将来1つの表になる候補 顧客、商品、注文
インスタンス エンティティの具体的な1件。将来1行（タプル）になる 「佐藤 花子さん」という1人の顧客
属性 エンティティが持つ個々の特徴。将来1列（属性）になる 顧客の氏名・住所・メールアドレス

ここで注意したいのは、この段階で「エンティティ ＝ 表」「属性 ＝ 列」と完全に一致させないことです。概念設計の候補は、あとの正規化（第6〜8章）で分かれたり統合されたりします。今はあくまで「業務の中に何があるか」を過不足なく洗い出すことが目的です。

ヒント: 「名詞」を探すつもりで業務説明を読む

業務担当者の説明や仕様書には、エンティティの候補になる言葉がすでに埋め込まれています。次の3.2で使う「名詞抽出法」は、その言葉を体系的に拾い出すためのシンプルな手がかりです。

3.2 名詞抽出法で業務要件からエンティティ候補を洗い出す

名詞抽出法は、業務の説明文・帳票・画面の項目名などに出てくる名詞を1つずつ拾い出し、エンティティの候補や属性の候補として整理していく方法です。手順はシンプルです。

flowchart TD A["業務の説明文・帳票・画面"] --> B["1. 出てくる名詞をすべて抜き出す"] B --> C["2. 単なる値や動作を表す名詞を除外する"] C --> D["3. 残った名詞を候補として書き出す"] D --> E{"3.3で分類
リソース系？イベント系？"} D --> F{"3.4で判定
属性？エンティティ？"}

実際に、本ガイド共通の題材「さくら文具」の業務説明文に適用してみましょう。

「顧客（会員）が Web サイトで文具を注文する。顧客には住所を1つ登録し、注文された商品はその住所へ届ける。1回の注文で複数の商品をまとめて買える。商品は1つの商品分類（筆記具・ノート・ファイル・事務用品）に属する。注文ごとに、受付した担当者（社員）を記録する。注文の状態は『受付』『発送済』『キャンセル』のいずれか。商品の価格は改定されることがあるため、注文時点の単価を残す必要がある。なお将来は、顧客が複数の配送先住所を登録できるようにしたい。」

この文章に出てくる名詞を拾い出すと、次のようになります。下線・強調していない名詞（「Web サイト」「もの」のような一般的すぎる言葉、「価格改定」のような出来事の説明）は候補から除外し、業務で繰り返し扱う対象だけを残します。

説明文中の名詞 候補として残すか 理由
顧客（会員） 残す 注文するたびに何度も参照される、業務の主体
注文 残す 「いつ・誰が・何を」の記録が必要な出来事
商品 残す 注文の対象として繰り返し参照される
商品分類 残す 複数の商品が同じ分類を共有するため、独立して管理する価値がある
担当者（社員） 残す 注文ごとに記録する必要がある業務の主体
住所（配送先住所） 要確認（3.4で判定） 今は顧客1人に1つだが、将来は複数登録できるようにしたいとされており、単純な属性では表せなくなる可能性がある
Webサイト 除外 業務データとして貯める対象ではなく、注文の手段の説明
注文の状態 属性として保留 「受付・発送済・キャンセル」という値のバリエーションなので、注文の属性の候補
商品の価格・注文時点の単価 属性として保留 価格が改定されると「商品の今の価格」と「注文したときの価格」は食い違うため、別々の属性の候補として控えておく（第6〜7章で置き場所を決める）

重要: 名詞抽出法は「候補出し」であり「正解探し」ではない

名詞抽出法は、思いつきに頼らず候補を網羅的に洗い出すための手がかりです。抽出した候補がそのままエンティティになるとは限りません。3.3・3.4のふるい分けと、業務担当者への確認（3.5）を経て、初めて確定します。

3.3 リソース系とイベント系に分類する

エンティティの候補が出そろったら、次に「時間が経っても存在し続けるもの」と「ある時点で発生する出来事」に分類すると、業務の構造が見えやすくなります。前者をリソース系（マスタ）、後者をイベント系（トランザクション）と呼びます。

リソース系（マスタ）

注文が1件も発生していなくても存在できる、業務の「登場人物・道具」。増減はゆるやか。

例: 顧客、商品、商品分類、担当者

イベント系（トランザクション）

ある時点で発生する「出来事」。多くの場合、リソース系どうしを結びつける。日時を持ち、日々増えていく。

例: 注文（受注）

この分類が便利なのは、イベント系エンティティは多くの場合、複数のリソース系エンティティと関連を持つからです。「注文」は「いつ発生したか（受注日）」だけでなく「誰が（顧客）」「誰が受け付けたか（担当者）」「何を（商品）」という形で、リソース系を指し示します。これは必ず成り立つ規則ではなく、エンティティを見つけるための経験則（ヒューリスティック）です。それでも「イベントを見つけたら、関係するリソース系を探す」「リソース系を見つけたら、それが登場するイベントを探す」という手がかりとして役立ちます。こうした関連は、第5章で学ぶ外部キーによる関係づけの土台になります。

flowchart LR subgraph リソース系["リソース系（マスタ）"] C["顧客"] S["担当者"] P["商品"] G["商品分類"] end subgraph イベント系["イベント系（トランザクション）"] O["注文"] end C -.->|"誰が注文したか"| O S -.->|"誰が受け付けたか"| O P -.->|"何を注文したか"| O G -.->|"どの分類か"| P

さくら文具の場合、リソース系は「顧客」「商品」「商品分類」「担当者」の4つ、イベント系は「注文」の1つが見つかりました。ただし、「1回の注文で複数の商品をまとめて買える」という業務ルールを、このままの5エンティティで表現できるかは、まだ検討の余地があります。この点は第5章（多対多の解消）でくわしく扱います。

ヒント: 見分けに迷ったら「注文0件でも存在するか」を聞く

「まだ一度も注文していない新規会員は存在するか」「まだ発売していない新商品を登録できるか」を自問すると、リソース系かどうかを判定しやすくなります。答えが「はい」ならリソース系、「注文があって初めて意味を持つ」ならイベント系の可能性が高いです。

3.4 属性とエンティティの見分け方 — 「住所」は属性か独立したエンティティか

名詞抽出法で拾った候補の中には、「これはエンティティなのか、それとも既存エンティティの属性なのか」の判断が難しいものが出てきます。さくら文具の「配送先住所」はその典型例です。まず、今の要件「顧客には住所を1つ登録し、注文された商品はその住所へ届ける」だけを見れば、「顧客の住所」は顧客エンティティの1つの属性（address 列）で表せます。しかし業務要件の最後には、次の一文もありました。

「なお将来は、顧客が複数の配送先住所を登録できるようにしたい。」

1人の顧客が住所を複数持てるようになると、「顧客1件につき住所1つ」という前提が崩れます。属性は本来、1つのエンティティのインスタンスに対して1つの値を持つものです（第1章で見た「1つのセルには1つの値だけを入れる」という考え方を思い出してください）。複数の値を持たせたい情報は、属性ではなく別のエンティティとして独立させ、元のエンティティとの間にリレーションシップ（第4〜5章）を作る必要があります。

判断基準 属性のままでよい 独立したエンティティにすべき
1件に対する個数 常に1つだけ持つ 0個・複数個を持つ可能性がある
それ自体の識別 単独では意味を持たない（顧客から見てのみ意味がある） 「配送先1」「配送先2」のように、自身の識別子や状態（既定の配送先か等）を持ちたい
構造の複雑さ 郵便番号・都道府県・番地などを1つの値としてまとめて扱えばよい 複数の項目からなり、他のエンティティ（配送業者など）からも参照されうる

複数の配送先を登録できるようにするなら、さくら文具の「配送先住所」は「0個・複数個を持つ可能性がある」に当てはまるため、独立したエンティティ（例: customer_addresses）として扱う必要があります。一方、今の要件（顧客1人につき住所1つ）だけなら、顧客の属性で十分です。つまり、どちらの設計にするかは「複数の配送先がいつから必要か」で決まります。これは要件文だけでは判断できないため、次の3.5で業務担当者に確認します。

注意: 「複数」の一文を読み飛ばさない

要件文の「複数」「まとめて」「いずれか」といった言葉には、エンティティやリレーションシップの多重度を決めるヒントが隠れています。「将来は複数の配送先を登録できるようにしたい」を読み飛ばして住所を顧客の1列にすると、要望が来たときに想定外の作り直しになります。気づいたうえで「当面は1つ」と業務担当者と合意し、拡張の方針まで決めておくのは設計判断ですが、気づかずに1列で作ってしまうのは設計の見落としです。

同じ考え方で「商品分類」も検証しておきましょう。「商品は1つの商品分類（筆記具・ノート・ファイル・事務用品）に属する」とあり、商品1件につき分類は常に1つです。一見すると商品の属性（category 列に「筆記具」という文字列を入れる）で済ませられそうに見えます。しかし、分類名を独立したエンティティとして持たせるべき理由があります。

複数の商品が値を共有する

「筆記具」という分類名は多数の商品行に繰り返し登場します。文字列のまま各商品に書くと、第1章で見た「直し漏れ」（分類名の変更が一部の行にしか反映されない）が起きます。

分類自体を管理したい

「まだ商品が1つも登録されていない新しい分類を、先に用意しておきたい」という業務要求があるなら、分類はリソース系として独立させる価値があります。

このように、「値を複数のインスタンスが共有するか」「単独で管理する価値があるか」の2点が、属性かエンティティかを見分ける実務的な目安になります。「商品分類」は独立したエンティティ（categories）とし、「商品」から参照する形にします。この関係の描き方は第4章で正式に学びます。

3.5 業務担当者への確認質問の作り方

名詞抽出法とここまでの分類は、あくまで与えられた説明文の中だけでの推測です。実際の設計現場では、説明文に書かれていない前提や例外が必ず存在します。エンティティ候補を確定させる前に、業務担当者へ確認すべき質問をリストにしておくと、あとからの手戻りを減らせます。

良い確認質問には共通点があります。単に「はい／いいえ」で終わらせず、その答えがどの設計判断に影響するかを意識して聞くことです。

確認質問（さくら文具の例） 影響する設計判断
複数の配送先は最初のリリースから必要か、将来の拡張でよいか。複数持つ場合、既定（デフォルト）の配送先という概念はあるか 配送先住所を今すぐエンティティにするか、当面は顧客の属性にするか。エンティティにする場合の属性（既定フラグの有無）
商品は複数の分類に同時に属することがあるか、常に1つだけか 商品と商品分類の関係が1対多か多対多か（第5章）
注文の受付担当者は、後から別の担当者に引き継がれることがあるか 注文エンティティの担当者を「受付時」の1件だけ持てば足りるか、履歴として複数持つ必要があるか
「発送済」になった注文の商品構成（内容）を、あとから変更することはあるか 注文明細を更新可能にするか、状態ごとに変更を制限するか（第10章の制約設計）
退会した顧客の過去の注文情報は、消してよいか、残す必要があるか 削除方法（物理削除／論理削除）と参照整合性の設計（第11章）

判断できるか"} D -->|"できる"| E["エンティティ候補として確定"] D -->|"できない"| F["確認質問を作り
業務担当者へ確認"] F --> E E --> G["第4章: ER図に描く"]

本ガイドでは、業務担当者への確認は既に済んだ前提で進めます。確認の結果、複数配送先は将来の拡張とし、当面は顧客1人につき住所1つ（顧客の属性）で運用することになりました。そこで本編（第4〜10章）では住所を顧客の属性として持ち、複数配送先への拡張は第11章で行います。以上から、さくら文具のエンティティを次の6つに確定します。顧客・商品分類・商品・担当者・注文・注文明細です。「注文明細」は3.3では明示的に出てきませんでしたが、「1回の注文で複数の商品をまとめて買える」という多対多の関係を表すために必要になるエンティティで、詳しい導出は第5章で行います。

用語メモ：エンティティ抽出 — 業務要件からエンティティの候補を洗い出す作業全体を指す言葉です。名詞抽出法は、そのための代表的な手がかりの1つにすぎず、実務では画面のワイヤーフレームや既存の帳票、業務担当者へのヒアリングメモなども合わせて手がかりにします。

やってみよう 3-1: 別の業務説明文でエンティティを抽出する

紙かメモアプリを用意し、次の業務説明文に対して名詞抽出法を適用してください。「さくら文具」と同じ手順を、別の題材で練習します。

「図書館の利用者は、館内に登録された本を借りることができる。1人の利用者は同時に複数の本を借りられる。本は1つの出版社から出ている。本を借りるときは、対応した司書（職員）を記録する。借りた本の返却期限は借りた日から2週間後とする。」

手順

  1. 1 説明文に出てくる名詞をすべて書き出し、3.2の表と同じ形式で「残す／除外／要確認」を判定する。
  2. 2 残した候補を、リソース系（マスタ）とイベント系（トランザクション）に分類する。
  3. 3 「返却期限」は属性かエンティティか、3.4の判断基準を使って考える。
  4. 4 この説明文だけでは判断できない点を、業務担当者への確認質問として2つ以上書き出す。

ねらい: この図書館の題材は、第12章の総合演習で本格的に使う「市民図書館の貸出管理」の予行練習です。「利用者」「本」「出版社」「司書」がリソース系、「借りる（貸出）」がイベント系になります。「返却期限」は借りた日から自動的に決まる値なので、多くの場合「貸出」エンティティの属性として持たせれば十分ですが、「延長できるか」「延長したら履歴を残すか」は業務担当者への確認が必要な典型例です。

理解度確認クイズ

  1. Q1. 名詞抽出法とは何をする方法ですか。また、抽出した名詞がそのままエンティティとして確定するわけではないのはなぜですか。

    回答を表示

    業務の説明文・帳票・画面などに出てくる名詞を抜き出し、エンティティや属性の候補として整理する方法です。抜き出した名詞には、業務データとして貯める対象ではない一般的な言葉（「Webサイト」など）や、属性か独立したエンティティか判断が分かれるものが含まれるため、リソース系／イベント系の分類や属性・エンティティの判定、業務担当者への確認を経て初めて候補が確定します。

  2. Q2. リソース系（マスタ）とイベント系（トランザクション）の違いを説明し、さくら文具の「顧客」「注文」がそれぞれどちらに当たるか答えてください。

    回答を表示

    リソース系は、注文などの出来事が発生していなくても存在し続けられる業務の登場人物や道具（顧客・商品・担当者など）です。イベント系は、ある時点で発生する出来事（注文など）で、多くの場合リソース系どうしを結びつけます。「顧客」はリソース系、「注文」はイベント系に当たります。

  3. Q3. さくら文具で「顧客が複数の配送先住所を登録できる」ようにする場合、配送先住所を顧客の属性（1つの列）のままにできないのはなぜですか。また、本ガイドの本編で住所を顧客の属性にしているのはなぜですか。

    回答を表示

    属性は1つのインスタンスに対して1つの値しか持てないため、1人の顧客が複数の住所を持つなら、配送先住所を独立したエンティティとして切り出し、顧客との間にリレーションシップ（1対多）を作る必要があるからです。本編で属性にしているのは、業務担当者への確認（3.5）で「複数配送先は将来の拡張とし、当面は顧客1人につき住所1つで運用する」と決まったためです。要件を見落としたのではなく、確認したうえで拡張を第11章に先送りしています。

  4. Q4. さくら文具の「商品分類」を、商品の属性（文字列の列）ではなく独立したエンティティにする理由を2つ挙げてください。

    回答を表示

    (1) 分類名は多数の商品行から共有される値であり、文字列のまま各商品に持たせると分類名の変更時に直し漏れ（更新異常）が起きる。(2) まだ商品が登録されていない分類を先に用意したいなど、分類自体を独立して管理する業務上の価値がある。この2点から、商品分類は独立したエンティティ（マスタ）として扱います。
