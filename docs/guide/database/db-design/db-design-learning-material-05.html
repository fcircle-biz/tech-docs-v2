リレーションシップの設計

第4章では ER図の記号でカーディナリティを読む方法を学びました。この章では、1対1・1対多・多対多という3種類の関係を、実際にテーブル構造として書く方法を学びます。「さくら文具」の受注と商品の多対多を中間エンティティ order_details（受注明細）で解消する手順を中心に、依存／非依存リレーションシップ、自己参照、そして1対1をあえて分ける判断まで、テーブル例とともに確認します。

この章の学習目標

  • 1対1・1対多・多対多それぞれの関係を、外部キーを使ったテーブル構造で表現できる
  • 外部キーを「多」の側に置く理由を、行の重複を使わずに説明できる
  • 多対多の関係を中間（連関）エンティティで解消し、受注明細のような表を作れる
  • 依存／非依存リレーションシップと自己参照リレーションシップを区別できる

5.1 3種類の関係を、テーブルで表すとどうなるか

第4章で見たカーディナリティ（1対1・1対多・多対多）は、ER図の記号としては読めても、それを実際のテーブルの列にどう落とすかは別の話です。まず3種類を並べて、テーブル側で何が起きるかを整理します。

関係 さくら文具の例 テーブルでの表現
1対1 担当者 と ログイン認証情報（1人の担当者に1つのログイン情報） どちらかの表に外部キー（多くは UNIQUE 制約つき）を1本持つ
1対多 顧客 と 受注（1人の顧客が複数回注文する） 「多」側の表（orders）に「1」側の外部キー（customer_id）を持つ
多対多 受注 と 商品（1回の注文に複数商品、1つの商品は複数の注文に登場） 中間エンティティ（order_details）を新設し、両方への外部キーを持たせる

3つとも道具は同じ「外部キー」ですが、置く場所と本数が異なります。1対1・1対多は既存の表に外部キーを追加するだけで済みますが、多対多だけは新しい表を1つ作る必要があります。5.3 で詳しく見ます。

ヒント: リレーションシップは「線」ではなく「列」になる

ER図では関係は線として描かれますが、実際のデータベースには「線」という要素はありません。関係は、片方の表に置いた外部キー列として実現されます。ER図を見たら「この線は、どの表のどの列になるだろうか」と常に対応づける習慣をつけましょう。

5.2 外部キーはなぜ「多」の側に置くのか

顧客と受注の1対多を例に考えます。「1人の顧客が複数の注文を持つ」関係を表すには、orders（多の側）に customer_id という外部キーを1本持たせます。逆に customers（1の側）に「自分の受注番号」を持たせようとすると、うまくいきません。

erDiagram customers ||--o{ orders : "注文する"

なぜ「多」の側なのかは、列に入る値の個数を考えると分かります。

1の側に置くと破綻する

佐藤さんは注文 1001 と 1003 の2件を持ちます。customers の1行に「関連する受注番号」を書こうとすると、1つの列に2つの値を入れる羽目になり、第1正規形（第7章）に反してしまいます。

多の側に置くと1つで済む

orders の1行（1件の注文）は、必ずちょうど1人の顧客に属します。だから orders.customer_id は1行につき1つの値だけを持てばよく、そのまま列1本に収まります。

つまり「多」の側の1行は、常に相手側のちょうど1行を指すので、外部キー1本で表現しきれます。「1」の側から見ると相手は複数行あるので、列1本には収まりません。外部キーは、値が一意に決まる側（多）に置く、というのがこの判断基準です。

orders.sql 
-- 「多」の側（orders）に「1」の側の外部キーを1本だけ持つ
CREATE TABLE orders (
    order_id    integer PRIMARY KEY,
    order_date  date    NOT NULL,
    customer_id integer NOT NULL REFERENCES customers(customer_id),
    staff_id    integer NOT NULL REFERENCES staff(staff_id),
    status      varchar(10) NOT NULL
);

用語メモ：参照整合性 — orders.customer_id に入る値は、必ず customers.customer_id に実在する値でなければならない、というルールです。REFERENCES（外部キー制約）で守られます。第2章の内容を思い出してください。

5.3 多対多の解消 — 中間エンティティ「受注明細」

受注と商品の関係は多対多です。1回の注文には複数の商品が入り、1つの商品は複数の注文に登場します。5.2 の「多の側に1本だけ外部キーを置く」方法は、多対多では両側とも「多」なので、そのままでは使えません。

1

orders に product_id を置くと？

1件の注文に複数商品が入るので、1列に複数の商品コードを詰め込む必要が生じます（第1章の「P01, P03」問題の再来）。

2

products に order_id を置くと？

1つの商品は複数の注文で買われるので、今度は products 側で同じ問題が起きます。どちらに置いても解決しません。

第3の表を作る

「注文と商品の組み合わせ」を1行として持つ新しい表を作れば、それぞれへの外部キーは1本ずつで済みます。この新しい表を中間（連関）エンティティと呼びます。

さくら文具では、この中間エンティティが order_details（受注明細）です。受注1件に対して複数行の明細を持つことで「1回の注文に複数商品」を表現し、明細の1行は必ず1つの商品を指すことで「多」の制約を満たします。

erDiagram orders ||--|{ order_details : "明細を持つ" products ||--o{ order_details : "明細に含まれる"

こう見ると、多対多の関係は「1対多」が2つ組み合わさった形だと分かります。orders から order_details へ1対多、products から order_details へも1対多です。5.2 の「多の側に外部キー」を、2回繰り返しているだけです。

order_details.sql 
-- 中間エンティティ: 受注と商品、両方への外部キーを持つ
CREATE TABLE order_details (
    order_id   integer NOT NULL REFERENCES orders(order_id),
    line_no    integer NOT NULL,          -- 同じ注文内の明細の順番
    product_id integer NOT NULL REFERENCES products(product_id),
    unit_price numeric(10,2) NOT NULL,    -- 注文時点の単価（第6〜7章・第11章）
    quantity   integer NOT NULL,
    PRIMARY KEY (order_id, line_no)       -- 複合主キー（第9章）
);

order_details の主キーが order_id と line_no の組み合わせになっている点に注目してください。「注文1001の1行目」「注文1001の2行目」のように、同じ注文の中で明細を区別する必要があるからです。複合主キーの詳しい設計は第9章で扱います。

重要: 中間エンティティは「関係そのもの」を表す1つの実体

order_details は単なる技術的な仕掛けではなく、「この注文でこの商品をいくつ買ったか」という業務上の事実そのものを表しています。だからこそ、注文時点の単価（unit_price）や数量（quantity）のように、関係自体に属する属性を持たせるのに適した場所になります。

5.4 依存リレーションシップと非依存リレーションシップ

リレーションシップには、もう1つ重要な区別があります。「子」側のエンティティが、単独で存在できるか、それとも「親」の存在なしには意味を持たないか、という違いです。

種類 意味 さくら文具の例
依存リレーションシップ 子は親の主キーを自分の主キーの一部として持ち、親なしでは識別できない order_details（order_id を主キーの一部に持つ。注文が無ければ明細も存在しない）
非依存リレーションシップ 子は自分専用の主キーを持ち、親への参照は外部キー（主キーの一部ではない） orders（customer_id は外部キーだが主キーではない。顧客が居るのとは無関係に注文自体は order_id で識別できる）

見分け方は簡単です。子の主キーの中に、親の主キーが含まれているかどうかを見ます。order_details の主キーは (order_id, line_no) で、親 orders の主キー order_id を含んでいるので依存です。一方 orders の主キーは order_id 単独で、customer_id は主キーに含まれないので非依存です。

erDiagram customers ||--o{ orders : "非依存（外部キーだが主キーではない）" orders ||--|{ order_details : "依存（親の主キーを子の主キーに含む）"

この区別は、削除の挙動にも直結します。依存リレーションシップの子は、親が削除されたら一緒に削除するのが自然です（注文が消えれば明細も不要）。非依存リレーションシップでは、親の削除を安易に子へ連鎖させると、第1章で見た「消すと一緒に消える」問題を招くことがあります。ON DELETE の具体的な選び方は第10章で扱います。

注意: 「依存」は必須／任意（オプショナリティ）とは別の話

依存・非依存は「子の主キーに親の主キーが入っているか」という構造の話で、第4章の「関係が必須か任意か」（オプショナリティ）とは別の軸です。orders.customer_id は NOT NULL（必須）ですが、主キーの一部ではないので非依存リレーションシップである、という点を混同しないでください。

5.5 自己参照リレーションシップ — 同じ表の中の関係

外部キーは、必ず別の表を指すとは限りません。同じ表の中の別の行を指す自己参照リレーションシップもよく使われます。典型例は「社員の上司も社員である」という関係です。

erDiagram staff |o--o{ staff : "管理する（上司→部下）"

テーブルでは、staff テーブルの中に、自分自身の主キーを指す外部キー列（例: manager_id）を追加します。値は同じ staff.staff_id を参照します。

staff_self_reference.sql 
-- 自己参照の例（上司・部下を管理したい場合の拡張イメージ）
CREATE TABLE staff (
    staff_id   integer PRIMARY KEY,
    staff_name varchar(50) NOT NULL,
    manager_id integer REFERENCES staff(staff_id)  -- 自分自身のテーブルを参照
);

manager_id は NULL を許しています。役員など、上司が存在しない社員がいるためです。上の ER図で上司側の端を |o（0または1）にしているのもこのためです。自己参照は「1対多」の特別な形で、外部キーを置く判断基準（5.2）はそのまま当てはまります。「多」側は部下、つまり全ての行がそのまま該当します。

なお、さくら文具の到達点テーブル（第9〜10章で確定する staff）では、業務要件に上司・部下の管理が含まれていないため manager_id は採用しません。ここでは自己参照という考え方を理解することが目的です。

ヒント: 自己参照は「木構造」や「階層」を表す定番手段

上司・部下のほかにも、商品分類の「大分類・中分類」、掲示板の「返信元コメント」など、階層や木構造を持つデータは自己参照でよく表現されます。

5.6 1対1をあえて分ける場面

1対1の関係は、多くの場合は1つの表に列を追加するだけで済み、あえて表を分けなくても困りません。それでも、次のような理由で意図的に分けることがあります。

機密性・アクセス頻度が異なる

担当者の基本情報（staff_name）は誰でも参照しますが、ログインID・パスワードハッシュのような認証情報は、扱う権限や更新頻度が全く異なります。分けることで、アクセス制御やバックアップ方針を別に設定できます。

値を持つ行が一部しかない（任意の情報）

全担当者の一部しか使わない拡張情報（例: 特別な権限設定）を本体の列に追加すると、大半の行で NULL が並びます。使う行だけ表を分けて存在させれば、NULL だらけの列を避けられます。

例として、担当者の基本情報とログイン認証情報を分けると、次のような1対1の関係になります。どちらの表にも staff_id を持ちますが、staff_credentials 側では主キーであると同時に外部キーです。

erDiagram staff ||--o| staff_credentials : "ログイン情報を持つ"
staff_credentials.sql 
-- 1対1: 主キー自身を外部キーとしても使う（分割の代表パターン）
CREATE TABLE staff_credentials (
    staff_id      integer PRIMARY KEY REFERENCES staff(staff_id),
    login_id      varchar(30) NOT NULL UNIQUE,
    password_hash varchar(100) NOT NULL
);

staff_credentials.staff_id は、主キーであり、かつ staff を参照する外部キーでもあります。この形にすることで「1人の担当者に、ログイン情報は多くても1組」であることをテーブル構造そのもので保証できます。ER図の staff_credentials 側の端が o|（0または1）なのは、ログインしない担当者にはこの行が無くてもよいためです。

用語メモ：垂直分割 — 1つのエンティティの属性を、用途や特性ごとに複数の表へ分けることです。1対1リレーションシップとして表現されますが、目的は「関係の表現」ではなく「表の使い分け」にある点が、5.3 の中間エンティティとは異なります。

やってみよう 5-1: 「顧客の配送先」の関係を設計する

第3章で将来の要件として挙がった「顧客が複数の配送先住所を登録できるようにする」を、これまでの節で学んだ方法で先取りして設計してみましょう（実際にさくら文具の設計へ加えるのは第11章です）。

手順

  1. 1 「顧客」と「配送先」の関係は、1対1・1対多・多対多のどれに当たるか答える。
  2. 2 5.2 の判断基準（「多」の側に外部キーを置く）にもとづき、新しい表 customer_addresses にどの列（主キー・外部キー）を持たせるべきか考える。
  3. 3 この関係は依存リレーションシップか非依存リレーションシップか、5.4 の見分け方（子の主キーに親の主キーが含まれるか）で判定する。

ねらい: 顧客と配送先は1対多です。「多」側の customer_addresses に customer_id という外部キーを置きます。配送先自体を address_id のような専用の主キーで識別するなら非依存、customer_id と枝番の組み合わせで識別するなら order_details と同じ依存の形になります。どちらも実務では使われる形です。第11章では、この要件に実際に対応し、address_id を主キーとする非依存の形で customer_addresses を追加します（注文時の配送先を残す「スナップショット」もあわせて扱います）。

理解度確認クイズ

  1. Q1. 顧客と受注の1対多の関係で、外部キーを orders 側（多の側）に置く理由を説明してください。

    回答を表示

    orders の1行（1件の注文）は必ずちょうど1人の顧客に属するため、customer_id という外部キー1本で表現できます。反対に customers 側から見ると、1人の顧客が複数の注文を持つため、1つの列に複数の受注番号を入れることになり、第1正規形に反してしまいます。値が一意に決まる「多」の側に外部キーを置くのが正しい設計です。

  2. Q2. 受注と商品の多対多の関係を、なぜ order_details のような中間エンティティで解消する必要がありますか。orders に product_id を直接持たせる方法との違いを述べてください。

    回答を表示

    orders に product_id を直接持たせると、1件の注文に複数商品が入る場合、1つの列に複数の商品コードを詰め込む必要が生じます（第1章の複数値セル問題の再来）。中間エンティティ order_details を作れば、注文と商品の「組み合わせ」を1行として持てるため、orders → order_details、products → order_details という2つの1対多に分解でき、それぞれ外部キー1本で表現できます。

  3. Q3. order_details と orders の関係は依存リレーションシップです。この判断の根拠と、依存リレーションシップが削除の挙動に与える影響を説明してください。

    回答を表示

    order_details の主キー (order_id, line_no) が、親 orders の主キー order_id を含んでいるため依存リレーションシップです。依存関係では、子は親なしに識別・存在できないため、親（注文）が削除されたら子（明細）も一緒に削除するのが自然な挙動になります。具体的な ON DELETE の指定方法は第10章で学びます。

  4. Q4. staff テーブルに manager_id という自己参照の外部キーを追加するとき、NULL を許すべき理由を答えてください。

    回答を表示

    組織の最上位（役員など）には上司が存在しないため、manager_id に入れられる値がありません。この場合に NOT NULL 制約を付けると、その社員を登録できなくなってしまうため、上司を持たない社員が存在しうる自己参照の外部キーは NULL を許す必要があります。
