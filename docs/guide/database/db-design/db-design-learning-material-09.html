キー設計と命名規則

第8章で「さくら文具」は6つの表に正規化されました。この章では、それぞれの表にどんな主キーを持たせるか（自然キーかサロゲートキーか、複合キーが必要か）を決め、テーブル名・列名の命名規則と、status のような区分値の設計方法を整理します。ここで決めたルールが、第10章の DDL にそのまま反映されます。

この章の学習目標

  • 自然キーとサロゲートキーの長所・短所を説明し、使い分けを判断できる
  • 複合キーが適切な場面を、order_details を例に説明できる
  • テーブル名・列名の命名規則（スネークケース、単数形／複数形、接尾辞・接頭辞）を適用できる
  • 区分値の設計を CHECK 制約と区分マスタテーブルの2案で比較し、選べる

9.1 自然キーとサロゲートキー

第2章で「主キーは行を一意に特定する列」と学びました。しかし、主キーに何の値を使うかには選択の余地があります。大きく分けて2つの方法があります。

自然キー（Natural Key）

業務上すでに存在し、意味を持つ値。例: 顧客番号「C001」、商品コード「P01」、社員番号、メールアドレス。

サロゲートキー（Surrogate Key）

業務上の意味を持たず、システムが自動的に割り振る値。例: 連番（1, 2, 3…）や UUID。

どちらにも長所と短所があり、「絶対にこちらを使うべき」という単純な答えはありません。表で比較してみます。

観点 自然キー サロゲートキー
意味の分かりやすさ ◎ 値を見れば何の行か分かる（C001＝顧客） ✕ 連番だけでは何の行か分からない
値が変わるリスク ✕ 業務ルールが変われば値も変わりうる（合併・改番） ◎ 業務と無関係なので変わらない
外部キーで参照する側 △ キーが変わると参照している全表を追随させる必要がある ◎ 一度発行した値は不変。参照先の変更に強い
複合キーになりやすさ △ 自然な識別子が複数列の組み合わせになりやすい ◎ 常に単一列で済む
重複・欠番のリスク △ 入力ミスや旧システムからの移行で重複しうる ◎ システムが発行するので重複しない

重要: 実務でよく使う組み合わせ ——「主キーはサロゲート、業務コードは UNIQUE」

現在の実務では、主キーにはサロゲートキーを使い、自然キー（業務コード）は別列として UNIQUE 制約で守るという組み合わせが広く採用されています。主キーを不変にして外部キーの参照を安定させつつ、業務コードの一意性（同じ顧客番号が2つの顧客に振られない）も制約で保証できるからです。「さくら文具」の customers テーブルはこの考え方で設計します。

erDiagram customers { integer customer_id PK varchar customer_code UK varchar customer_name varchar email }

customer_id はシステムが発行する連番（サロゲートキー）で、主キー（PK）です。customer_code（例: 「C001」）は業務で使う自然キーで、UNIQUE 制約（UK）を付けて重複を防ぎます。orders など他の表からは、業務が読む「C001」ではなく、変わらない customer_id を外部キーとして参照します。

ヒント: PostgreSQL のサロゲートキーは GENERATED ALWAYS AS IDENTITY

古い教材では serial 型がよく使われますが、PostgreSQL 10 以降は標準 SQL 準拠の GENERATED ALWAYS AS IDENTITY が推奨されています。連番の自動発行という同じ機能を、より明示的な構文で提供します。第10章の DDL では、この構文で customer_id などのサロゲートキーを定義します。

customers_key.sql 
-- サロゲートキー（customer_id）＋ 自然キー（customer_code）の組み合わせ
CREATE TABLE customers (
    customer_id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_code varchar(10) NOT NULL UNIQUE,  -- 業務コード。重複禁止
    customer_name varchar(100) NOT NULL,
    email         varchar(255)
);

9.2 複合キーを使う場面 — order_details

第7章で order_details（受注明細）を作ったとき、主キーを2つの列の組み合わせ（受注番号＋商品コード）にしました。これを複合キー（Composite Key）と呼びます。本ガイドの到達点では、明細の並び順（注文書の何行目か）を保持でき、同じ商品を条件違いで2行に分けることも許せるように、商品ではなく明細行番号 line_no を組み合わせた (order_id, line_no) を主キーにします。すべての表にサロゲートキーを機械的に振るのではなく、「複数列の組み合わせで自然に一意になる」表では複合キーを検討する価値があります。

order_id (PK, FK) line_no (PK) product_id (FK) unit_price quantity
1001 1 1（P01 の商品） 120 10
1001 2 3（P03 の商品） 280 5

order_id だけでは「注文 1001 の何行目か」が分からず、line_no だけでは「どの注文の1行目か」が分かりません。2つを組み合わせて初めて1行が一意に決まるため、この2列を複合主キーにするのが自然です。ここに新たに order_detail_id というサロゲートキーを追加することも技術的には可能ですが、以下の判断基準で「不要」と考えられます。

判断基準 複合キーが向く サロゲートキーが向く
親への従属性 親（orders）が無いと単独で存在意義がない（依存エンティティ、第5章） それ自体が独立した管理対象（customers など）
識別子の自然さ 「注文の何行目か」のように業務上も複合で識別する 単一の連番で識別するのが自然
他表からの参照 他表からほとんど参照されない（末端の表） 他の多くの表から外部キーとして参照される

ヒント: 迷ったらサロゲートキーでも構わない

複合キーは「その組み合わせを外部キーとして参照する表がすべて複数列を持つ」ため、参照が増えるほど定義が煩雑になります。判断に迷う場合や、将来他表からの参照が増えそうな場合は、無理に複合キーにせず order_detail_id のようなサロゲートキーを主キーにし、(order_id, line_no) は UNIQUE 制約として残す、という選択も実務ではよく使われます。「さくら文具」では明細が他表から参照されないため、本ガイドでは複合キーを採用します。

order_details_key.sql 
-- 複合主キー: (order_id, line_no) の組み合わせで1行を識別
CREATE TABLE order_details (
    order_id   integer NOT NULL REFERENCES orders(order_id),
    line_no    integer NOT NULL,
    product_id integer NOT NULL REFERENCES products(product_id),
    unit_price numeric(10,2) NOT NULL,  -- 注文時点の単価（第11章）
    quantity   integer NOT NULL,
    PRIMARY KEY (order_id, line_no)     -- 複合主キー
);

9.3 テーブル名・列名の命名規則

キーの設計と並んで大切なのが名前の付け方です。ばらばらな命名は、後から読む人（未来の自分を含む）を確実に混乱させます。PostgreSQL の慣例に沿った、本ガイド共通のルールを4つ整理します。

1. スネークケース・小文字

customer_name のように単語を _ でつなぎ、大文字は使わない。PostgreSQL は識別子を暗黙に小文字化するため、CustomerName のような表記は引用符が必要になり事故のもと。

2. テーブル名は複数形・列名は単数形

テーブルは行の集合を表すので複数形（customers）。列は1行あたり1つの値なので単数形（customer_name）。

3. 主キー・外部キーは "_id"

主キーは 単数形テーブル名_id（customer_id）。外部キー列も参照先と同じ名前にすると、JOIN の条件が一目で分かる。

4. 日時は "_at"・真偽は "is_"

日時列は created_at のように _at、日付だけの列は order_date のように _date を付けて種類が分かるようにし、真偽値は is_active のように接頭辞で「はい／いいえ」と分かるようにする。

「さくら文具」の6テーブルに、このルールを当てはめて確認しておきます。

テーブル名（複数形） 主キー（_id） 代表的な列
customers customer_id customer_code, customer_name, email
categories category_id category_name
products product_id product_code, product_name, category_id (FK), unit_price
staff staff_id staff_name
orders order_id order_date, customer_id (FK), staff_id (FK), status
order_details (order_id, line_no) product_id (FK), unit_price, quantity

用語メモ：staff は単数形のまま — 英語で staff（社員・スタッフ）は集合名詞で複数形にしないため、テーブル名としてもそのまま使います。news や data なども同様に、無理に複数形化しないのが慣例です。

注意: 予約語・あいまいな略語を避ける

order（ORDER BY の ORDER で、SQL の予約語）や group（予約語）のような単語を単独の列名・テーブル名に使うと、クォートが必要になったり読みにくくなったりします。「さくら文具」でも受注テーブルは order ではなく orders（複数形）にすることで、この問題を避けています。略語も cst_nm のように短くしすぎず、customer_name と書いた方が誤解を防げます。

9.4 区分値（コード値）の設計 — status をどう持つか

「さくら文具」の要件では、注文の状態は「受付」「発送済」「キャンセル」のいずれかでした（第3章）。このような区分値（コード値）の持ち方には、主に2つの方法があります。

flowchart LR A["区分値の設計"] --> B["方法1
CHECK制約で値を限定"] A --> C["方法2
区分マスタテーブルに分ける"] B --> B2["orders.status
varchar ＋ CHECK"] C --> C2["order_statuses マスタ
＋ 外部キー参照"]

方法1: CHECK 制約で値を限定

status 列に varchar を使い、CHECK 制約で許される値を列挙する。表を増やさずに済み、値の種類が少なく将来も増減しない場合に向く。

方法2: 区分マスタテーブルに分ける

区分値ごとに1行を持つマスタ表（例: order_statuses）を作り、外部キーで参照する。値の追加・並び順・表示名の管理が容易で、値の種類が増えたり画面表示用の情報を持たせたい場合に向く。

status_check.sql 
-- 方法1: CHECK制約で3つの状態だけを許可
CREATE TABLE orders (
    order_id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_date  date NOT NULL,
    customer_id integer NOT NULL REFERENCES customers(customer_id),
    staff_id    integer NOT NULL REFERENCES staff(staff_id),
    status      varchar(10) NOT NULL DEFAULT '受付'
        CHECK (status IN ('受付', '発送済', 'キャンセル'))
);
status_master.sql 
-- 方法2: 区分マスタテーブルに分けて外部キーで参照
-- （方法1の status 列の代わりに、次の ALTER で列を追加する）
CREATE TABLE order_statuses (
    status_code varchar(10) PRIMARY KEY,  -- '受付' など。自然キーのまま使う例
    sort_order  integer NOT NULL          -- 画面表示の並び順
);

ALTER TABLE orders
    ADD COLUMN status varchar(10) NOT NULL DEFAULT '受付'
        REFERENCES order_statuses(status_code);

重要: 「さくら文具」では CHECK 制約を選ぶ

受注の状態は「受付・発送済・キャンセル」の3種類で固定され、業務担当者への確認（第3章）でも今後増える予定はないとされています。このように値の種類が少なく変化しにくい区分値は、表を1つ増やすコストに見合わないため CHECK 制約で十分です。第10章の DDL でもこの方針を採用します。値の種類が多い、頻繁に追加される、表示名や並び順など付随情報を持たせたい、という場合は区分マスタテーブルを検討してください。

やってみよう 9-1: products テーブルのキーと名前を決める

「さくら文具」の products（商品）テーブルを例に、この章で学んだ判断をもう一度自分の手でなぞってみます。

手順

  1. 1 主キーをサロゲートキー（product_id）とサロゲートを使わない場合（自然キー product_code をそのまま主キーにする）の2案を書き出し、9.1 の判断基準表でどちらが向くか根拠を1つ挙げる。
  2. 2 9.3 の命名規則に沿って、products テーブルの列名（商品コード・商品名・分類・単価に対応する列）をすべて書き出す。
  3. 3 「商品には『販売中』『取扱終了』の区分がある」という新しい要件が追加されたとして、9.4 の方法1・方法2のどちらで持つか、理由を1文で書く。

ねらい: 手順1の答えは、9.1 のとおり「サロゲートキー（product_id）＋ product_code に UNIQUE」が基本方針です。手順2は product_id, product_code, product_name, category_id, unit_price が期待される答えです。手順3は種類が少なければ CHECK 制約、将来商品分類のように種類や属性が増えそうならマスタテーブル、と考えれば両方とも正解になり得ます。判断の根拠を説明できることが目的です。

理解度確認クイズ

  1. Q1. customers テーブルで、主キーを customer_id（サロゲート）にしつつ customer_code に UNIQUE 制約を付ける設計には、どんな利点がありますか。

    回答を表示

    他表からの外部キー参照は業務上変わりうる customer_code ではなく不変の customer_id を使えるため、業務コードが将来変更・改番されても参照先の表を直す必要がありません。一方 customer_code の UNIQUE 制約により、業務コードが重複して登録されることも防げます。

  2. Q2. order_details の主キーを (order_id, line_no) の複合キーにする理由を、依存リレーションシップ（第5章）の観点から説明してください。

    回答を表示

    order_details は orders が存在しないと意味を持たない依存エンティティで、「注文の何行目か」という識別子は親の order_id と明細内の line_no の組み合わせで自然に一意になります。他表からほとんど参照されない末端の表であるため、複合キーのままで不都合が少なく、新たにサロゲートキーを追加する必要性が低いといえます。

  3. Q3. テーブル名を複数形、列名を単数形にする理由を説明してください。また staff テーブルが複数形にならない理由は何ですか。

    回答を表示

    テーブルは行の集合（複数の顧客や複数の注文）を表すため複数形にし、列は1行あたり1つの値しか持たないため単数形にします。staff（社員・スタッフ）は英語で集合名詞であり、そもそも複数形の語形を持たないため、そのまま単数形の見た目で使います。

  4. Q4. orders.status を CHECK 制約で持つか、区分マスタテーブルに分けるかを判断するときの基準を2つ挙げてください。

    回答を表示

    (1) 値の種類が少なく将来も増減しにくいか（少なければ CHECK 制約、増えそうならマスタテーブル）、(2) 表示名・並び順など値に付随する情報を持たせる必要があるか（必要であればマスタテーブルの方が管理しやすい）、の2点が代表的な基準です。「さくら文具」の受注状態は種類が少なく固定的なため CHECK 制約を選びました。
