リレーショナルモデルの基礎

第1章では「設計しないと何が起きるか」を体感しました。この章では、これから設計を進めるための土台となるリレーショナルモデルの用語をそろえます。表・行・列を正式には何と呼ぶのか、表が満たすべき性質、主キー・外部キーなどキーの種類、そして初心者がつまずきやすい NULL の扱いを学びます。

この章の学習目標

  • リレーション・タプル・属性・ドメインという正式用語と、表・行・列・値の範囲という実務用語を対応づけて説明できる
  • 「行の順序に意味はない」「同じ行は2つ存在しない」という表の性質を理由とともに説明できる
  • スーパーキー・候補キー・主キー・代替キー・外部キーの違いを、さくら文具のテーブルで見分けられる
  • NULL が「未知・不明」を表すこと、NULL同士の比較が常に不明になることを説明できる
  • 参照整合性がどのような矛盾を防ぐ仕組みかを説明できる

2.1 リレーション・タプル・属性・ドメイン

私たちは普段「表」「行」「列」という言葉を使いますが、リレーショナルモデル（表の形でデータを扱う理論）にはそれぞれに対応する正式な用語があります。設計の教科書や製品のドキュメントでは正式用語も登場するため、対応関係を知っておくと迷いません。

正式用語 実務用語 意味
リレーション（relation） 表・テーブル 同じ形（同じ列構成）の行の集まり。customers など
タプル（tuple） 行・レコード 1件分のデータ。顧客1人分、注文1件分など
属性（attribute） 列・カラム・フィールド タプルを構成する項目の1つ。customer_name など
ドメイン（domain） 値の範囲・データ型 その属性が取り得る値の集合。「整数」「50文字以内の文字列」など

「さくら文具」の顧客マスタ customers を例に当てはめると、次のようになります。

customer_id customer_code customer_name address
1 C001 佐藤 花子 東京都港区…
2 C002 鈴木 一郎 大阪府北区…

この表全体がリレーション、佐藤さんの行1本がタプル、customer_name という列が属性です。そして「customer_name のドメインは100文字以内の文字列」「customer_id のドメインは正の整数」というように、属性ごとに許される値の範囲＝ドメインが決まっています。

ヒント: 「テーブル」でも通じるが、教科書は「リレーション」を使う

実務では「テーブル」「行」「列」で十分に通じます。本ガイドもこれ以降は基本的に実務用語を使いますが、正規化（第6〜8章）の説明では「タプル」「関数従属」など正式用語が出てくるため、ここで対応関係を押さえておきます。

2.2 表が満たすべき2つの性質

Excel の表と違い、リレーショナルモデルにおける「表」には、集合論に基づく2つの約束があります。この約束を知らないと、SQL の結果が「思っていた順番と違う」「重複行が混ざる」といった予想外の動きに戸惑うことになります。

行の順序に意味はない

表は行の集合であり、上から何番目か、という位置情報を持ちません。「入力した順に並ぶはず」という思い込みは誤りで、見たい順序が必要なら ORDER BY で明示します。

同じ行は2つ存在しない

集合には同じ要素が2つ入りません。表の中のどの2行を選んでも、必ずどこかの列の値が異なる必要があります。これを保証する仕組みが次節の主キーです。

たとえば「注文 1001 の行」と全く同じ値を持つ行が2本あったら、どちらが本物の注文なのか区別できません。だからこそ、行を一意に見分けられる目印をあらかじめ決めておく必要があります。それが2.3で扱うキーです。

用語メモ：PostgreSQL の現実 — 実際の PostgreSQL のテーブルは、内部的には行の格納順序が生じますが、これは実装の都合であり、SELECT の結果として保証される順序ではありません。「順序に依存しない」という考え方はリレーショナルモデルの理論であり、製品の実装細部とは別のレイヤーの話だと理解してください。

2.3 キーの種類 — スーパーキー・候補キー・主キー・代替キー・外部キー

「行を一意に見分けられる目印」を表す言葉にはいくつかの段階があります。範囲が広いものから絞り込んでいくと、次のようになります。

flowchart TD A["スーパーキー
行を一意に特定できる列の組（全部）"] --> B["候補キー
これ以上減らせない最小のスーパーキー"] B --> C["主キー
候補キーから選んだ代表1つ"] B --> D["代替キー
主キーに選ばれなかった残りの候補キー"]

「さくら文具」の顧客マスタ customers（customer_id・customer_code・customer_name・email）で具体的に見てみましょう。

キーの種類 意味 customers での例
スーパーキー 行を一意に特定できる列（の組）。余分な列を含んでもよい {customer_id, customer_name} も一意なのでスーパーキーだが、customer_name は不要
候補キー これ以上列を減らせない、最小のスーパーキー customer_id 単独、customer_code 単独の2つが候補キー
主キー（PK） 複数ある候補キーから、テーブルの代表として選んだ1つ customer_id を主キーに選ぶ（第9章でサロゲートキーとして詳解）
代替キー 主キーに選ばれなかった、残りの候補キー customer_code（業務上の顧客番号）が代替キーになる
外部キー（FK） 別の表の主キーを参照する列。表と表を結びつける orders.customer_id が customers.customer_id を参照する

これを PostgreSQL の制約として表すと、次のようになります。代替キーは UNIQUE 制約で「重複させない」ことを保証しますが、行の識別に使う「主役」の目印としては選ばれていない、という位置づけです。

customers.sql 
-- customer_id が主キー、customer_code は代替キー（業務コード）
CREATE TABLE customers (
    customer_id   integer      PRIMARY KEY,       -- 主キー
    customer_code varchar(10)  NOT NULL UNIQUE,    -- 代替キー（候補キーの一つ）
    customer_name varchar(100) NOT NULL,
    email         varchar(255) UNIQUE,             -- NULL可・値があれば重複禁止
    address       text
);

重要: 主キーは「業務の都合で変わらない」ものを選びたい

customer_code のような業務コードは、会社の制度変更で桁数や採番ルールが変わることがあります。一方 customer_id のような連番は業務の都合に左右されません。この「自然キーとサロゲートキー、どちらを主キーにするか」という判断は第9章で詳しく扱います。

2.4 NULL の意味と扱いの難しさ

NULL は「値が入っていない」という状態を表しますが、正確には「値が未知・不明である」「そもそも該当しない」ことを表すマーカーです。数値の 0 や空文字列 '' とは全く別の概念で、この違いを混同すると設計や集計で思わぬ誤りを招きます。

値 意味 さくら文具での例
0 「ゼロである」という確定した値 在庫数が 0 個（値は分かっている）
''（空文字列） 「長さ0の文字列がある」という確定した値 備考欄に何も書かなかった（値は分かっている）
NULL 値が未知・不明、または項目自体が該当しない 顧客がメールアドレスを登録していない（値そのものが無い）

NULL が特に厄介なのは、比較演算の結果です。SQL では真偽値が「真・偽」の2値ではなく、「真・偽・不明（UNKNOWN）」の3値で扱われます。

NULL = NULL は真ではない

「不明」と「不明」を比べても、同じ値かどうかは分からないため、結果は「不明」になります。true にはなりません。

WHERE は「不明」を除外

WHERE email = 'x' は、email が NULL の行では「不明」となり、結果に含まれません。NULL を探すには IS NULL を使います。

演算に NULL が混ざると NULL

単価 * NULL のように、NULL を含む計算の結果は NULL（不明）になります。合計金額が思わぬ NULL になる原因のひとつです。

注意: 「とりあえず NULL 可にしておく」は設計を弱くする

NULL を許すと、その列を使うすべての SQL で「NULL だったらどうするか」を考える必要が生まれます。本当に「値が無いことがある」列だけを NULL 可にし、そうでない列には NOT NULL を付けるのが基本方針です。データ型・NULL可否の判断基準は第10章でまとめて学びます。

2.5 参照整合性 — 表と表のつながりを守る

外部キーは「表と表を線でつなぐ」だけの飾りではありません。参照整合性（referential integrity）とは、外部キーの値が「参照先の表に実在する主キーの値」または「NULL」のどちらかでなければならない、という制約です。

erDiagram customers ||--o{ orders : "注文する" customers { int customer_id PK string customer_code "業務上の顧客番号" string customer_name "氏名" } orders { int order_id PK date order_date int customer_id FK string status }

この図では orders.customer_id が customers.customer_id を参照する外部キーです。参照整合性が守られていると、次のような矛盾が起こりません。

防ぎたい矛盾 具体例
存在しない親を参照する 存在しない customer_id = 999 を持つ注文が登録されてしまう
参照されている親が消える 注文が残っているのに、参照先の顧客だけが削除されてしまう

PostgreSQL では FOREIGN KEY 制約でこれを自動的に守らせます。「参照されている親を削除しようとしたらどうするか」（削除を拒否する／子も一緒に削除する、など）を指定する ON DELETE の書き方は、第10章の物理設計で詳しく扱います。

ヒント: 外部キーは「多」の側に置く

1人の顧客が複数の注文を持てる（1対多）ので、外部キー customer_id は「多」の側である orders に置きます。「1」の側である customers に注文の情報を持たせることはできません。この考え方は第5章のリレーションシップ設計でさらに深めます。

やってみよう 2-1: 商品マスタのキーを見分ける

「さくら文具」の商品マスタ products（product_id・product_code・product_name・category_id・unit_price）について、紙かメモアプリで考えてください。

手順

  1. 1 product_id と product_code（商品コード、例: P01）は、それぞれ単独で行を一意に特定できるか考える。両方とも一意なら、どちらも候補キーである。
  2. 2 2つの候補キーのうち、どちらを主キーに選ぶべきか、理由も含めて決める。「商品コードの採番ルールが将来変わる可能性」を考慮に入れる。
  3. 3 category_id が外部キーだとすると、どの表の主キーを参照しているはずか答える。その表を削除しようとしたときに何を防ぐべきか説明する。

ねらい: 手順1・2は2.3のキーの種類、手順3は2.5の参照整合性の理解を確認するものです。「商品コードは変わりうるので主キーには使わず、連番の product_id を主キーにする」という判断は、第9章で自然キー／サロゲートキーとして体系的に学びます。

理解度確認クイズ

  1. Q1. リレーション・タプル・属性は、それぞれ実務でどう呼ばれますか。

    回答を表示

    リレーションは「表・テーブル」、タプルは「行・レコード」、属性は「列・カラム」と呼ばれます。加えてドメインは「値の範囲・データ型」に対応します。

  2. Q2. ある表で customer_id と customer_code がそれぞれ単独で行を一意に特定できるとき、主キーに選ばれなかった側は何と呼ばれますか。

    回答を表示

    代替キーと呼ばれます。両方とも「これ以上減らせない一意な組」なので候補キーですが、テーブルの代表として選ばれた1つが主キー、残りが代替キーです。

  3. Q3. email 列の値が2行とも NULL のとき、WHERE customers.email = customers2.email のような比較の結果はどうなりますか。

    回答を表示

    「不明（UNKNOWN）」になります。NULL は「不明な値」を表すため、不明と不明を比べても「同じ」とは判定されず、true にはなりません。SQL の真偽値は真・偽・不明の3値で扱われます。

  4. Q4. 参照整合性が守られているとき、orders.customer_id にはどのような値しか入りませんか。

    回答を表示

    参照先である customers.customer_id に実在する値、または NULL のいずれかしか入りません。存在しない顧客番号を持つ注文が登録される、という矛盾を防ぎます。
