第3正規形とボイス・コッド正規形

第7章で第2正規形にした「受注」「商品」「受注明細」の3表には、まだ主キー以外の列を経由した従属（推移的関数従属）が残っています。この章では、それを取り除いて「さくら文具」の6テーブル構成（customers・categories・products・staff・orders・order_details）に到達し、第3正規形に仕上げます。さらにボイス・コッド正規形（BCNF）の例と、第4・第5正規形の概要、正規化チェックの手順をまとめます。

この章の学習目標

  • 推移的関数従属（X→Y→Z）を、第2正規形の受注表・商品表の具体例で指摘できる
  • 受注表を顧客・担当者・受注に、商品表を分類・商品に分解し、6テーブル構成へ到達できる
  • 第3正規形の定義を説明し、ボイス・コッド正規形（BCNF）との違いを例で示せる
  • 第4・第5正規形の概要と、実務での正規化チェックの手順を把握する

8.1 第2正規形にまだ残る問題 — 推移的関数従属

第7章では、非正規形の受注一覧を第1正規形（繰り返し項目の除去）→第2正規形（部分関数従属の除去）まで進めました。その結果、次の3つの表になっています。

表 主キー 列
受注 受注番号 受注番号・受注日・顧客番号・顧客名・顧客住所・担当者
商品 商品コード 商品コード・商品名・分類・単価
受注明細 受注番号・商品コード 受注番号・商品コード・数量

受注明細はすでに主キー（受注番号・商品コード）のすべての列に完全従属しているので問題ありません。しかし受注と商品には、まだ「直し漏れ」が起きる余地が残っています。受注表を見てみましょう。

flowchart LR A["受注番号
（主キー）"] -->|決まる| B["顧客番号"] B -->|決まる| C["顧客名"] B -->|決まる| D["顧客住所"] A -.->|"間接的に決まる（推移的）"| C A -.->|"間接的に決まる（推移的）"| D

顧客名と顧客住所は、受注番号に直接決まるわけではありません。「受注番号 → 顧客番号」が決まり、その顧客番号によって初めて「顧客名」「顧客住所」が決まります。このように、X → Y かつ Y → Z が成り立つとき X → Z も成り立ってしまう関係を推移的関数従属と呼びます（Y は主キーの一部ではない列です）。

重要: 推移的従属があると何が困るか

佐藤さんが複数回注文すると、受注表の複数の行に同じ「顧客名」「顧客住所」が書かれます。佐藤さんが引っ越すと、それらの行をすべて直す必要があり、1行でも直し忘れると矛盾したデータが残ります。第1章・第6章で見た更新異常と同じ現象が、第2正規形の表にもまだ残っているのです。

同じ理由で、担当者も見直しが必要です。今は「受注番号 → 担当者名」という1本の従属しか見えませんが、担当者は業務上「誰が受け付けたか」を管理する独立した存在（社員）であり、将来メールアドレスや所属部署のような属性が増えることを考えれば、「受注番号 → 担当者番号 → 担当者名」という推移的な構造で捉えるのが自然です。同じ担当者が複数の受注を受け付けるたびに担当者名が繰り返し書かれる点は、顧客名とまったく同じ問題を抱えています。

商品表にも同様の芽があります。分類（筆記具・ノート・ファイル・事務用品）は商品コードに直接決まりますが、分類名だけを見ると「筆記具」という値が何十もの商品行に繰り返し書かれます。分類ごとに分類コードを振って管理するなら「商品コード → 分類コード → 分類名」という推移的関数従属そのものになりますし、分類に表示順や説明文のような属性を持たせたくなった時点で、分類を独立した表に切り出す必要が出てきます（第3章で「商品分類」を独立したエンティティとした理由も同じです）。

8.2 受注表を分解する — 顧客・担当者を切り出す

推移的関数従属を取り除く手順は、部分関数従属を取り除いたとき（第7章）と同じ考え方です。「Y → Z」の関係にある列（顧客番号と、顧客名・顧客住所）を、Y を主キーとする別の表へ移します。

分解前 分解後
受注［受注番号・受注日・顧客番号・顧客名・顧客住所・担当者］ customers［顧客番号・顧客名・顧客住所］
staff［担当者番号・担当者名］
orders［受注番号・受注日・顧客番号(FK)・担当者番号(FK)］

受注（orders）は、顧客番号・担当者番号を外部キーとして持つだけになり、顧客名や顧客住所そのものは持ちません。必要なときは JOIN で結合して取り出します。PostgreSQL で定義すると次のようになります。

customers_staff.sql 
-- 顧客マスタ（推移的従属していた顧客名・顧客住所の受け皿）
CREATE TABLE customers (
    customer_id   integer      PRIMARY KEY,
    customer_name varchar(100) NOT NULL,
    address       varchar(200)
);

-- 担当者（社員）マスタ
CREATE TABLE staff (
    staff_id   integer      PRIMARY KEY,
    staff_name varchar(50)  NOT NULL
);
orders.sql 
-- 受注ヘッダ：顧客名・顧客住所・担当者名は持たず、番号だけを参照する
CREATE TABLE orders (
    order_id    integer  PRIMARY KEY,
    order_date  date     NOT NULL,
    customer_id integer  NOT NULL REFERENCES customers(customer_id),
    staff_id    integer  NOT NULL REFERENCES staff(staff_id)
);

分解しても情報は失われません。第7章で確認した無損失分解と同じく、orders と customers を customer_id で結合すれば、分解前の受注表を完全に復元できます。

ヒント: 「番号で参照する」がすべての土台

正規化の各段階で行っていることは、結局すべて同じです。「同じ事実を繰り返し書かない」ために、その事実を1つの表にまとめ、他の表からは番号（主キー）で参照する。第2正規形では受注明細から商品を切り出し、第3正規形では受注から顧客・担当者を切り出しました。やっていることの本質は同じだと気づけば、正規化は怖くありません。

8.3 商品表を分解する — 6テーブル構成に到達する

同じ手順を商品表にも適用します。分類に分類番号（category_id）を振ってcategoriesという別表に切り出し、商品表は分類番号を外部キーとして参照するだけにします。

categories_products.sql 
-- 商品分類マスタ（商品行に繰り返し書かれていた分類名の受け皿）
CREATE TABLE categories (
    category_id   integer     PRIMARY KEY,
    category_name varchar(50) NOT NULL UNIQUE
);

-- 商品マスタ：分類名は持たず、分類番号を参照する
CREATE TABLE products (
    product_id   integer      PRIMARY KEY,
    product_name varchar(100) NOT NULL,
    category_id  integer      NOT NULL REFERENCES categories(category_id),
    unit_price   numeric(10,2) NOT NULL
);

ここまでで、受注明細（第7章で作成済み）と合わせて、ちょうど6つの表がそろいました。これが本ガイドの到達点、「さくら文具」の論理設計です。

erDiagram customers ||--o{ orders : "注文する" staff ||--o{ orders : "受け付ける" orders ||--|{ order_details : "明細を持つ" products ||--o{ order_details : "明細に含まれる" categories ||--o{ products : "分類する" customers { int customer_id PK string customer_name string address } staff { int staff_id PK string staff_name } categories { int category_id PK string category_name } products { int product_id PK string product_name int category_id FK numeric unit_price } orders { int order_id PK date order_date int customer_id FK int staff_id FK } order_details { int order_id PK int product_id PK int quantity }

どの表を見ても、列は主キーに完全に、かつ直接従属しています。もう「ある列を直すのに、複数の行・複数の表を探し回る」必要はありません。なお、customer_code（業務上の顧客番号）やorder_detailsの注文時単価・ordersのステータスのような列は、キー設計（第9章）と物理設計（第10章・第11章）で追加していきます。また、この章のSQLとER図では、顧客番号・商品コードで識別していた行を customer_id・product_id という番号列で表し、受注明細の主キーも第7章のまま（受注番号＋商品）にしています。業務コード（customer_code・product_code）とシステム用の番号の使い分けや、受注明細の主キーを (order_id, line_no) にする理由は第9章で扱います。この章では「推移的従属をなくす」ことに焦点を絞ります。

8.4 第3正規形の定義とチェック手順

ここまでの作業を、正式な定義でまとめておきます。

第3正規形（3NF）：第2正規形であり、かつ、主キー以外のすべての列が、主キーに推移的に従属していない（＝主キー以外の列を経由して決まる列がない）表。

少し厳密に言うと、表の中のすべての関数従属 X → A について、次のどちらかが成り立てば3NFです。

条件 意味
X がスーパーキーである X だけで行が一意に決まる（第2章のスーパーキー）
A が候補キーの一部である A 自身が別の候補キーを構成する列（例外的に許容される）

実務でチェックするときは、この定義を丸暗記するより、次の質問を表の列1つずつに当ててみるほうが分かりやすいです。

Q1. 主キーで直接決まるか

この列の値は、主キーの値だけを見れば決まるか。それとも「別の非キー列」を知らないと決まらないか。

Q2. 値が繰り返し出てくるか

同じ値（顧客名、分類名など）が複数の行に何度も現れるなら、推移的従属の疑いが強い。

Q3. その列は独立して増やせるか

「注文がまだ1件もない新分類」を登録したいのに登録できないなら、その列は別表に分けるべき合図。

8.5 ボイス・コッド正規形（BCNF） — 3NFでは足りない場合

3NFの定義には「A が候補キーの一部なら例外を許す」という条件がありました。この例外のせいで、3NFなのに更新異常が残るケースがあります。それを取り除いたのがボイス・コッド正規形（BCNF）です。教科書でよく使われる「講座担当」の例で見てみましょう。

ある学習塾では、1人の受講者が複数の科目を受講でき、受講者は科目ごとに1人の講師に習います。1つの科目は複数の講師が担当しますが、各講師は1つの科目しか担当しないというルールがあります（さくら文具とは別の、正規化の練習用の例です）。

受講者番号 科目 講師
S001 数学 高橋
S001 英語 中村
S002 数学 伊藤
S003 数学 高橋

この表の関数従属は「受講者番号＋科目 → 講師」と「講師 → 科目」の2つです（数学は高橋・伊藤の2人が担当するので「科目 → 講師」は成り立ちません）。候補キーは（受講者番号・科目）と（受講者番号・講師）の2つあり、講師も科目もどちらかの候補キーの一部です。「講師 → 科目」の決定項である講師はスーパーキーではありませんが、決まる側の科目が候補キーの一部なので3NFの例外条件に当たり、この表は3NFを満たしてしまいます。しかし、この表には以前と同じ更新異常が残っています。「高橋先生が担当科目を変えた」場合、高橋先生が関わる行（S001 と S003）をすべて直さないと矛盾が生じます。

flowchart LR A["講師
（スーパーキーではない）"] -->|決まる| B["科目
（候補キーの一部）"] C["受講者番号 ＋ 科目
（候補キー）"] -->|決まる| D["講師"]

注意: BCNFは「決定項は必ずスーパーキー」を要求する

BCNFの定義はシンプルです。表の中のすべての関数従属 X → A について、X が必ずスーパーキーであること。3NFのような「A が候補キーの一部なら例外」という救済はありません。「講師 → 科目」は 講師 がスーパーキーではないため、この表はBCNFを満たしません。

BCNFにするには、「講師 → 科目」の関係を別表に分けます。

bcnf_example.sql 
-- 講師ごとの担当科目（講師が主キー＝スーパーキー）
CREATE TABLE teacher_subjects (
    teacher     varchar(50) PRIMARY KEY,
    subject     varchar(30) NOT NULL
);

-- 受講者と講師の組み合わせ（科目は teacher_subjects から分かる）
CREATE TABLE enrollments (
    student_id  varchar(10) NOT NULL,
    teacher     varchar(50) NOT NULL REFERENCES teacher_subjects(teacher),
    PRIMARY KEY (student_id, teacher)
);

ヒント: 実務でBCNFまで意識する場面は多くない

なお、この分解では「1人の受講者は1科目につき講師1人」というルールを1つの表の制約では守れなくなる（関数従属が保存されない）というトレードオフがあります。BCNFが問題になるのは、複合的な候補キーが複数あって重なり合い、スーパーキーでない列が候補キーの一部を決めてしまう、という比較的まれな状況です。「さくら文具」の6テーブルは、実は3NFの時点でBCNFも満たしています（各表の決定項はすべてスーパーキーです）。実務ではまず3NFを目標にし、複数の候補キーが絡む複雑な表に出会ったときだけBCNFを確認する、という進め方で十分です。

8.6 第4正規形・第5正規形の概要

BCNFより先の正規形は、関数従属（1つの値が1つの値を決める）ではなく、複数の値の組み合わせに関する冗長性を扱います。名前だけ知っておけば実務では十分です。

正規形 扱う冗長性 一言でいうと
第4正規形（4NF） 多値従属性（1つのキーに対し、互いに無関係な複数の値の集合が結びつく） 「講師が教える科目」と「講師が使う教材」のように無関係な多対多を1つの表に混ぜない
第5正規形（5NF） 結合従属性（3つ以上の表に分けないと元に戻せない冗長性） 「メーカー・商品・地域」のような3方向の組み合わせ制約がある表を細かく分ける

例えば、ある講師が「数学・英語」の2科目を教え、「教科書A・教科書B」の2種類の教材を（科目とは無関係に）使うとします。これを1つの表に (講師, 科目, 教材) の全組み合わせ4行で表すと、科目を1つ追加するたびに教材の行も増やさなければならず、両者を別々の表 (講師, 科目) と (講師, 教材) に分ければ冗長性が消えます。これが4NFの考え方です。5NFはさらにまれで、3つ以上の表の組み合わせでしか元に戻せない特殊な制約がある場合にだけ関係します。

用語メモ：多値従属性（MVD） — 「X が決まれば、Y の値の集合が（他の列とは無関係に）決まる」という、関数従属より緩い依存関係です（X →→ Y と書きます）。4NFはこのMVDに関する冗長性を取り除きます。

8.7 正規化チェックの手順まとめ

第6〜8章で学んだ正規化の手順を、実務で使えるチェックリストとしてまとめます。

段階 確認すること 見つかったらどうするか
1NF 1つのセルに複数の値、または繰り返し項目の列がないか 行を分ける、または別表にして1対多にする
2NF 複合主キーの一部だけで決まる列がないか その列と、決める側の主キー部分を別表に分ける
3NF 主キー以外の列を経由して決まる列がないか 経由している列と、決まる列を別表に分け、番号で参照する
BCNF スーパーキーでない列が、他の列を決めていないか その関係を別表に分ける（実務で複合候補キーが絡む場合のみ確認）
4NF・5NF 無関係な多対多や3方向の組み合わせ制約を1表に混ぜていないか まれなケース。混在に気づいたら組み合わせごとに表を分ける

重要: 実務ではまず「第3正規形」を目標にする

世の中の業務データベースの大半は、3NF（多くはBCNFも満たす）で設計されています。4NF・5NFの状況は非常にまれで、意識しすぎるとテーブル数が増えすぎて逆にJOINが複雑になります。「まず1NF→2NF→3NFを順に確認し、複合候補キーが絡む複雑な表に出会ったときだけBCNFを確認する」という進め方が実務的です。なお、性能上の理由であえて正規化を崩す判断（非正規化）は第11章で扱います。

やってみよう 8-1: 推移的従属を見つけて分解する

次の「配送」表（受注番号を主キーとする、1つの受注に1つの配送記録が対応する表）を見て、推移的関数従属を見つけ、BCNFまで分解してください。

配送［受注番号（主キー）・配送業者コード・配送業者名・配送業者の連絡先電話番号・配送予定日］

手順

  1. 1 「受注番号 → 配送業者コード → 配送業者名・連絡先電話番号」という推移的従属があることを、8.1のやり方に沿って矢印の図で示す。
  2. 2 配送業者名・連絡先電話番号を carriers（配送業者マスタ）表に分け、「配送」表は配送業者コードを外部キーとして参照する形に直す。
  3. 3 分解後の2つの表について、8.4のQ1〜Q3を当てて3NFになっていることを確認し、決定項がすべてスーパーキーであることからBCNFも満たすことを説明する。

ねらい: 8.2・8.3で行った「顧客・担当者・分類を切り出す」作業と、まったく同じパターンを新しい題材（配送業者）で自力で再現できるかを確認します。答えが不安な場合は、8.2の customers／staff の分解手順を見比べてください。列名を置き換えるだけで同じ手順が使えるはずです。

理解度確認クイズ

  1. Q1. 推移的関数従属とは何か、「X → Y → Z」の形を使って説明してください。

    回答を表示

    主キー X が非キー列 Y を決め、その Y がさらに別の非キー列 Z を決めるとき（X → Y かつ Y → Z）、結果として X → Z も成り立ってしまう関係です。Z は X に「直接」ではなく「Y を経由して間接的に」決まっているため、推移的関数従属と呼ばれます。受注番号 → 顧客番号 → 顧客名がその例です。

  2. Q2. 受注表から顧客・担当者を切り出したとき、orders テーブルにはどのような列が残りますか。また、顧客名を知りたいときはどうすればよいですか。

    回答を表示

    orders には受注番号・受注日と、customer_id・staff_id という外部キーだけが残り、顧客名や顧客住所そのものは持ちません。顧客名を知りたい場合は、orders と customers を customer_id で JOIN して取得します。

  3. Q3. 8.5の「講座担当」の表が3NFを満たすのにBCNFを満たさないのはなぜですか。3NFとBCNFの違いを一言で述べてください。

    回答を表示

    「講師 → 科目」という従属があり、決定項の講師はスーパーキーではありませんが、決まる側の科目は候補キー（受講者番号・科目）の一部です。3NFは「決定項がスーパーキーでなくても、決まる側の列が候補キーの一部なら例外的に許す」ため、この表は3NFを満たします。一方BCNFは、そうした例外を認めず「すべての決定項がスーパーキーである」ことを要求するため、この表はBCNFを満たしません。

  4. Q4. 実務で正規化のチェックをするとき、どこまで正規化を進めるのが一般的な目安ですか。理由も含めて答えてください。

    回答を表示

    まず第3正規形（多くの場合BCNFも自然に満たす）を目標にするのが一般的です。第4・第5正規形が問題になる状況（無関係な多対多や3方向の組み合わせ制約）は実務ではまれで、意識しすぎるとテーブル数が増えJOINが複雑になるため、複合候補キーが絡む複雑な表に出会ったときだけBCNFを確認する、という進め方で十分です。
