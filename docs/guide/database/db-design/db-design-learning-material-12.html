総合演習 — 小さな業務システムを設計する

これまでの11章では「さくら文具」を題材に、要件の読み解きからDDLまでの流れをステップごとに確認してきました。この最終章では題材を変え、「市民図書館の貸出管理」という新しい業務を使って、要件の読み解き → エンティティ抽出 → 概念ER図 → 論理ER図と正規化の確認 → 物理設計（DDL）までを自力で通して行います。各ステップには「やってみよう」と模範解答・解説を用意しているので、まず自分で考えてから答えを確認してください。

この章の学習目標

  • 新しい業務の説明文から、自力でエンティティ・属性・リレーションシップを抽出できる
  • 「資料（書誌）」と「所蔵本（個々の実物）」のように、似ているが分けるべきエンティティを見分けられる
  • 概念ER図・論理ER図を描き、第3正規形まで整っているかを自分でチェックできる
  • 論理設計を PostgreSQL の CREATE TABLE 文に落とし込み、業務ルールを制約で守れる
  • 設計レビューのチェックリストを使って、自分の設計を見直せる

12.1 総合演習の進め方

本ガイドは第1〜11章で、概念設計 → 論理設計 → 物理設計という3つの工程（第1章 1.3）を、「さくら文具」の受注管理という1つの題材で一通り体験してきました。総合演習では、次のように工程をさらに細かい5つのステップに分け、それぞれを新しい題材で自分の手で行います。

各ステップの「やってみよう」には模範解答を用意していますが、答えを先に見てしまうと「なぜそうなるのか」を考える練習になりません。紙かメモアプリに自分の答えを書いてから、<details> を開いて解説と比べてください。模範解答は「唯一の正解」ではなく、考え方の一例です。

新しい題材: 市民図書館の貸出管理

本市の市民図書館では、これまで貸出台帳（紙のノート）で本の貸し借りを記録していましたが、利用者数の増加にともないシステム化を検討しています。業務担当者への聞き取りで、次のような説明を得ました。

図書館には多数の利用者が登録されている。利用者には利用者番号・氏名・住所・電話番号を記録し、いつ登録したかも残す。
図書館が所蔵する本には、まず「タイトル・著者・出版社・ISBN」で決まる資料（書誌）という単位がある。同じ資料を複数冊（複数コピー）購入している場合があり、1冊1冊には貸出のために蔵書番号（バーコード）を付けて管理している。同じ資料の本でも、1冊が貸出中でも別の1冊は借りられる。
資料は必ず1つの分類（日本十進分類法のような区分）に属する。
利用者が本を借りるときは、どの蔵書番号の本を、いつ借りて、いつまでに返す予定かを記録し、返却されたら返却日を記録する。貸出の受付は職員が行うので、どの職員が対応したかも残す。
借りたい資料が全冊貸出中のとき、利用者は予約できる。予約は「どの資料が欲しいか」であって、「どの蔵書番号の本か」ではない（どの1冊が返ってきても構わない）。予約には申込日時と状態（予約中・取り置き中・キャンセル・完了）を記録する。予約された資料の本が返却されたら、予約者のためにその1冊をカウンターに取り置き、どの蔵書番号の本を取り置いたかを記録する（取り置いた本は、ほかの利用者には貸し出さない）。

重要: 「資料」と「本」は同じものではない

この要件文には、第3章で扱った「属性かエンティティか」の判断力を試す仕掛けがあります。「吾輩は猫である」という資料（書誌）と、その資料を図書館が3冊持っているときの1冊ごとの本（所蔵本）は、別のエンティティとして扱う必要があります。貸出は「どの1冊か」を特定する必要があるので所蔵本に対して行い、予約は「どの資料か」だけが分かればよいので資料に対して行います。この違いに気づけるかどうかが、この章の最初の関所です。

12.2 ステップ1: 要件を読み解く

第3章で学んだ名詞抽出法を使い、12.1 の要件文から「管理したいもの・こと」になりそうな名詞と、それが持つ情報（属性）を拾い出します。

やってみよう 12-1: 要件文から名詞を拾い出す

12.1 の要件文を読み、次の手順で名詞を分類してください。

手順

  1. 1 要件文に出てくる名詞をすべて書き出す。
  2. 2 それぞれを「リソース系（マスタになりそうな、比較的変化しないもの）」と「イベント系（いつ・誰が・何をした、という出来事）」に分ける。
  3. 3 「資料」「本（蔵書番号のついた1冊）」のように、似ているが別物と思われる名詞のペアが無いか確認する。
模範解答・解説を表示

リソース系（マスタ寄り）: 利用者、職員、資料（書誌）、本（所蔵本・個々のコピー）、分類

イベント系（出来事）: 貸出、予約

「資料」と「本」は要件文の中で明確に区別されています。「資料（書誌）」は ISBN・タイトル・著者・出版社という本のタイトルとしての情報を持ち、「本（所蔵本）」は蔵書番号という物理的な1冊を識別する情報を持ちます。「同じ資料を複数冊持てる」「1冊が貸出中でも別の1冊は借りられる」という説明が、この2つが別エンティティである決定的な根拠です。

12.3 ステップ2: エンティティを抽出する

12.2 で拾った名詞を、エンティティ（管理単位）と属性（エンティティが持つ情報）に整理します。エンティティには、それを一意に識別するための項目（主キー候補）が必要です。

やってみよう 12-2: エンティティ一覧表を作る

12.2 で分類したリソース系・イベント系の名詞を1つずつ検討し、「エンティティ名・種別・主な属性」の一覧表を作ってください。

模範解答・解説を表示
エンティティ 種別 主な属性
利用者 リソース系 利用者番号、氏名、住所、電話番号、登録日
職員 リソース系 職員番号、氏名
分類 リソース系（マスタ） 分類コード、分類名
資料（書誌） リソース系 ISBN、タイトル、著者、出版社、分類
所蔵本 リソース系 蔵書番号、資料、状態（在架／貸出中／取り置き中／除籍）
貸出 イベント系 所蔵本、利用者、職員、貸出日、返却期限、返却日
予約 イベント系 資料、利用者、申込日時、状態、取り置いた所蔵本（取り置き中になってから）

「所蔵本の状態」を資料側に持たせてしまう間違いがよくあります。状態（在架・貸出中など）は1冊ごとに変わるため、資料の属性ではなく所蔵本の属性です。

また、予約の「予約中」と所蔵本の「取り置き中」を混同しないようにしましょう。予約中は、資料単位で順番を待っている予約の状態で、まだどの1冊かは決まっていません。取り置き中は、特定の1冊を予約者のために確保した所蔵本の状態で、ここで初めて予約と所蔵本が結びつきます。

12.4 ステップ3: 概念ER図を描く

エンティティ同士の関係を洗い出し、第4〜5章で学んだ IE記法のカーディナリティ・オプショナリティで表します。「1人の利用者は何回予約できるか」「1冊の所蔵本は1つの資料にしか属さないか」のように、要件文を読み返しながら関係を確認してください。

やってみよう 12-3: 概念ER図を描く

12.3 のエンティティ一覧を使い、紙かお絵描きツールで概念ER図を描いてください。特に「貸出は所蔵本に対して行うのに、予約は資料に対して行う」という違いを、線をどこから引くかで表現してみましょう。

模範解答・解説を表示
erDiagram categories ||--o{ works : "分類する" works ||--o{ books : "所蔵される" works ||--o{ reservations : "予約される" users ||--o{ reservations : "予約する" users ||--o{ loans : "借りる" staff ||--o{ loans : "受け付ける" books ||--o{ loans : "貸し出される" books |o--o{ reservations : "取り置かれる"

予約（reservations）の申込みは、books（所蔵本）ではなく works（資料）から線が伸びている点に注目してください。貸出（loans）は逆に books から線が伸びます。同じ「利用者が本を求める」行為でも、貸出と予約ではどの粒度のエンティティに対する行為かが異なるのが、この演習のポイントです。

books から reservations へも線がありますが、これは取り置きの段階で特定の1冊が決まることを表す線です。予約中の間は相手の1冊がまだ無いため、books 側の端は任意（|o：0または1）になっています。

12.5 ステップ4: 論理ER図と正規化の確認

概念ER図のエンティティを論理設計の表に落とし、各表の列が主キーに完全関数従属しているか（第2正規形）、主キー以外の列を経由した推移的関数従属が無いか（第3正規形）を、第6〜8章の手順でチェックします。

やってみよう 12-4: 各表が第3正規形か確認する

12.4 のER図を7つの表（users・staff・categories・works・books・loans・reservations）に落としたと仮定し、books・loans・reservations について、部分関数従属・推移的関数従属が残っていないかを確認してください。

模範解答・解説を表示

books（所蔵本）: 主キー book_id に対し、work_id・book_code・status はすべて1つの値に決まり、単一主キーなので部分関数従属は起きません。タイトルや著者を books に直接持たせると work_id 経由の推移的関数従属になるため、works 側に置いたままにします。

loans（貸出）: 主キー loan_id に対し、book_id・user_id・staff_id・各日付はすべて直接決まります。もし「利用者の氏名」や「本のタイトル」まで loans に持たせると、user_id・book_id 経由の推移的関数従属となり、第3正規形に違反します。氏名やタイトルは JOIN で取得します。

reservations（予約）: 主キー reservation_id に対し、work_id・user_id・申込日時・状態と、取り置き後に入る book_id は直接決まります。取り置き後は book_id からも資料が分かるため work_id は冗長に見えますが、取り置くまでは book_id が NULL で、何を予約したかは work_id でしか表せないため省けません。その代わり、「取り置いた本が、予約した資料の1冊であること」は取り置きの処理の中で確かめる必要があります。

複合主キーを持つ表が無いため部分関数従属の心配はありませんが、複合主キーがある設計（例: 受注明細の order_id + line_no、第9章）では常にこの確認が必要です。

12.6 ステップ5: 物理設計（DDL）

最後に、論理設計を PostgreSQL 17 の CREATE TABLE 文に落とします。命名などの規則は、本ガイドで採用している規則（第9章）と「さくら文具」に合わせて、小文字のスネークケース・テーブル名は複数形・主キーは GENERATED ALWAYS AS IDENTITY を使います。

やってみよう 12-5: CREATE TABLE 文を書く

12.5 で確認した7つの表について、データ型・NOT NULL・UNIQUE・CHECK・外部キー制約を決めて CREATE TABLE 文を書いてください。特に books.status のように取りうる値が決まっている列は CHECK 制約で守ることを検討しましょう。また、「1冊の本を同時に2人へ貸し出さない」「返却日が貸出日より前にならない」といった業務ルールも、制約としてDBに守らせられないか考えてみましょう。

模範解答・解説を表示

分類・利用者・職員のようにほかの表から参照される「土台」の表から先に作ります（第10章の順序と同じ考え方）。

categories.sql 
-- 分類マスタ
CREATE TABLE categories (
    category_id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    category_name varchar(50) NOT NULL UNIQUE
);
users.sql 
-- 利用者マスタ
CREATE TABLE users (
    user_id      integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_code    varchar(20)  NOT NULL UNIQUE,  -- 利用者番号（業務コード）
    user_name    varchar(100) NOT NULL,
    address      varchar(200),
    phone        varchar(20),
    registered_date date NOT NULL DEFAULT CURRENT_DATE
);
staff.sql 
-- 職員マスタ
CREATE TABLE staff (
    staff_id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    staff_name varchar(100) NOT NULL
);
works.sql 
-- 資料（書誌）マスタ
CREATE TABLE works (
    work_id     integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    isbn        varchar(20) UNIQUE,       -- 無い資料もあるためNOT NULLにしない
    title       varchar(200) NOT NULL,
    author      varchar(100),
    publisher   varchar(100),
    category_id integer NOT NULL REFERENCES categories(category_id)
);
books.sql 
-- 所蔵本（個々のコピー）
CREATE TABLE books (
    book_id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    work_id   integer NOT NULL REFERENCES works(work_id),
    book_code varchar(20) NOT NULL UNIQUE,  -- 蔵書番号（バーコード）
    status    varchar(20) NOT NULL DEFAULT '在架'
              CHECK (status IN ('在架', '貸出中', '取り置き中', '除籍'))
);
loans.sql 
-- 貸出（イベント。1件の貸出は所蔵本1冊に対応する）
CREATE TABLE loans (
    loan_id     integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    book_id     integer NOT NULL REFERENCES books(book_id),
    user_id     integer NOT NULL REFERENCES users(user_id),
    staff_id    integer NOT NULL REFERENCES staff(staff_id),
    loan_date   date NOT NULL DEFAULT CURRENT_DATE,
    due_date    date NOT NULL,
    return_date date,  -- NULLのうちは未返却
    CHECK (due_date >= loan_date),                           -- 返却期限は貸出日より前にならない
    CHECK (return_date IS NULL OR return_date >= loan_date)  -- 返却日は貸出日より前にならない
);

-- 1冊の所蔵本を同時に2人へ貸し出さない（未返却の貸出は1冊につき1件まで）
CREATE UNIQUE INDEX uq_loans_active_book
    ON loans (book_id)
    WHERE return_date IS NULL;
reservations.sql 
-- 予約（イベント。資料単位で申し込み、取り置いた時点で1冊が決まる）
CREATE TABLE reservations (
    reservation_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    work_id     integer NOT NULL REFERENCES works(work_id),
    user_id     integer NOT NULL REFERENCES users(user_id),
    book_id     integer REFERENCES books(book_id),  -- 取り置いた1冊（取り置くまでは NULL）
    reserved_at timestamptz NOT NULL DEFAULT now(),  -- 申し込んだ時点（第10章）
    status      varchar(20) NOT NULL DEFAULT '予約中'
                CHECK (status IN ('予約中', '取り置き中', 'キャンセル', '完了')),
    CHECK (status <> '取り置き中' OR book_id IS NOT NULL)  -- 取り置き中なら、どの1冊かが必ず決まっている
);

-- 1冊の所蔵本を、2件の予約のために同時に取り置かない
CREATE UNIQUE INDEX uq_reservations_held_book
    ON reservations (book_id)
    WHERE status = '取り置き中';

制約で守る業務ルール: loans の2つの CHECK 制約は、返却期限や返却日が貸出日より前になる誤入力を防ぎます。さらに WHERE return_date IS NULL 付きの UNIQUE インデックス（部分一意インデックス、第11章）で、「未返却の貸出は1冊につき1件まで」、つまり「1冊の本を同時に2人へ貸し出さない」ことをDBに保証させます。返却済みの行は条件から外れるので、同じ本の過去の貸出履歴は何件あっても構いません。reservations では、CHECK 制約で「取り置き中なら book_id が必ず入っている」ことを、部分一意インデックスで「1冊の本を2件の予約のために同時に取り置かない」ことを守ります。申込日時の reserved_at は「申し込んだ瞬間」を記録する列なので、第10章の方針どおり timestamptz にしています。

loans.book_id は所蔵本（books）を参照し、reservations.work_id は資料（works）を参照している点が、12.4 の概念ER図と一致していることを確認してください。reservations.book_id は、取り置きの段階で所蔵本と結びつく任意の線に対応します。

注意: 「借りられるか」を状態列だけで判定しない

books.status のような区分値は便利ですが、loans の更新と books.status の更新がずれると、実際には返却済みなのに「貸出中」のままになる、といった不整合が起きます。状態列の「貸出中」は loans から、「取り置き中」は reservations から導ける情報を、検索しやすくするために重ねて持つ意図的な非正規化（第11章）です。正の情報源は loans（返却日が NULL の行があるか）と reservations（取り置き中の予約があるか）で、どちらも部分一意インデックスによって「1冊につき1件まで」がDBで保証されていることを忘れないでください。

12.7 設計レビューのチェックリスト

自分（あるいは他の人）の設計を見直すときに使えるチェックリストです。「良い設計の4つの基準」（第1章 1.4：整合性・妥当性・拡張性・性能）に沿って整理しています。

観点 確認項目
整合性 各エンティティに主キーがあり、重複行が入り得ないか。外部キー制約で参照先の存在を保証しているか。
整合性 同じ事実（利用者の氏名、資料のタイトルなど）が2つ以上の表に書かれていないか。書かれている場合、注文時単価（第11章）のような意図的なスナップショットか。
整合性 「1冊を同時に2人へ貸し出さない」「返却日が貸出日より前にならない」「価格の適用期間が重ならない」のような業務ルールを、CHECK 制約・部分一意インデックス・排他制約などでDBに守らせているか（第11章・12.6）。
妥当性 「貸出は所蔵本単位、予約は資料単位」のような業務ルールが、外部キーの参照先としてそのまま表れているか。
妥当性 1セルに複数値（カンマ区切りなど）を入れていないか（第7章・第11章のアンチパターン）。
拡張性 「1人の利用者が複数の連絡先を持つ」「本を電子書籍にも対応させる」といった将来の変更を、表や列の追加で受け止められそうか。
性能 検索・JOIN や親の削除でよく使う外部キー列に、インデックスを付けたか（第10章）。区分値のような非正規化を入れる場合、更新のたびに正の情報源と一致させる仕組みがあるか。
命名 テーブル名は複数形・小文字スネークケースか。主キーは 〇〇_id、日時は 〇〇_at のように第9章の命名規則に沿っているか。

12.8 ガイド全体の振り返り

第1章で「さくら文具」の Excel 受注一覧から出発したとき、あなたはまだ「表をどう分ければいいのか」が分からない状態でした。ここまでの12章で、次のスキルを身につけています。

読み解く力（第1〜3章）

設計しない表の問題点を体感し、業務の説明文からエンティティ・属性を抽出できるようになった。

図で表す力（第4〜5章）

IE記法のER図でカーディナリティ・オプショナリティを読み書きし、多対多を連関エンティティで解消できるようになった。

整える力（第6〜9章）

更新異常と関数従属性を理解し、第3正規形までの正規化と、キー・命名の設計判断ができるようになった。

形にする力（第10〜12章）

データ型・制約を選んでDDLに落とし込み、非正規化の判断とアンチパターンの回避を意識できるようになり、この章で新しい題材に自力で応用できた。

「さくら文具」と「市民図書館」という2つの題材を通して、業務は違っても要件を読み解く → ER図で表す → 正規化で整える → DDLに落とすという設計の型は同じであることを確認できたはずです。この型は、今後どんな業務システムを設計するときも変わらない土台になります。

12.9 次に学ぶテーマ

本ガイドは「正しい表の分け方（論理設計）」を中心に扱いました。実務ではこの先に、次のようなテーマが待っています。今すぐ深く学ぶ必要はありませんが、名前だけでも知っておくと、必要になったときに調べやすくなります。

テーマ どんな課題に対処するか
性能設計（インデックス戦略・実行計画） 正規化された表を、実際のアクセスパターンに合わせて速く検索・集計できるようにする。第10章で触れたインデックスの基本の先にある領域。
パーティション loans のように行数が増え続ける表を、年月などで物理的に分割し、検索や保守を軽くする手法。
NoSQL との使い分け 本ガイドが前提とするリレーショナルモデル（表・正規化・JOIN）が向く場面と、ドキュメント指向・キーバリュー型などのNoSQLが向く場面の判断基準。

まずは、設計したテーブルを実際に操作するSQL入門ガイドで、SELECT・JOIN・集計をひととおり確認するのがおすすめです。製品ごとの物理設計の違いを知りたい方はOracle Database 入門やSQL Server 入門も参考にしてください。

理解度確認クイズ

  1. Q1. 「資料（works）」と「所蔵本（books）」を1つのエンティティにまとめてしまうと、どんな問題が起きますか。

    回答を表示

    同じ資料を複数冊持っている場合に、タイトル・著者・出版社・ISBNが行ごとに繰り返し書かれ、更新時異常（第6章）が起きます。また「借りたい資料はあるがどの1冊でもよい」という予約と、「特定の1冊を借りる」という貸出を区別できなくなり、業務ルールを正しく表現できません。

  2. Q2. loans テーブルに book_id だけでなく work_id も持たせるべきでしょうか。理由も答えてください。

    回答を表示

    不要です。books.work_id を経由すればどの資料かは分かるため、loans に work_id を追加すると book_id 経由の推移的関数従属になり、第3正規形に違反します（12.5 の確認と同じ考え方）。資料名が必要な場面では books と works を JOIN して取得します。なお reservations は work_id と book_id の両方を持ちますが、book_id は取り置くまで NULL で、work_id が無いと何を予約したかを表せないため、両方が必要です（12.5 参照）。book_id が必ず入っている loans とはこの点が違います。

  3. Q3. books.status のような区分値を持たせる設計は、正規化の観点からどう位置づけられますか。

    回答を表示

    本来「貸出中かどうか」は loans（返却日が NULL の行があるか）から、「取り置き中かどうか」は reservations（取り置き中の予約があるか）から導ける情報であり、books.status として別に持たせるのは第11章で学んだ意図的な非正規化です。検索を速くするメリットがある一方、loans・reservations の更新と同期させ続けるという運用上の責任が発生します。

  4. Q4. あなたが設計したテーブルをレビューしてもらうとき、12.7 のチェックリストのどの観点を一番最初に確認してもらいたいですか。理由も含めて自分の言葉で答えてください。

    回答を表示

    決まった正解はありません。ただし第1章 1.4 で学んだとおり、初心者のうちは整合性（同じ事実が複数箇所に書かれていないか、主キー・外部キーが正しく機能するか）と妥当性（業務ルールが構造に表れているか）を最優先にするのが基本方針です。性能面の調整は、正しい構造を作れるようになってから検討します。
