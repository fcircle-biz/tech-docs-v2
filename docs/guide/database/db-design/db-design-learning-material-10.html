論理設計から物理設計へ

第9章までで、さくら文具の受注一覧は customers・categories・products・staff・orders・order_details の6テーブルへ整理され、キーと命名規則も定まりました。この章では、その論理ER図を PostgreSQL 17 の実際のテーブルへ落とし込みます。列のデータ型・NULL許可・制約（NOT NULL／UNIQUE／CHECK／FOREIGN KEY）を1つずつ判断し、テーブル定義書とインデックスを整えて、6テーブル全部の CREATE TABLE 文を完成させます。

この章の学習目標

  • 論理設計の属性を PostgreSQL のデータ型（numeric・timestamptz・date など）に対応づけられる
  • 列ごとに NULL を許すかどうかを、業務上の理由を添えて判断できる
  • CHECK 制約と外部キーの ON DELETE を、理由を説明しながら選べる
  • テーブル定義書を書き、外部キー列にインデックスを付けるかどうかを、検索・JOIN・削除の頻度から判断できる
  • さくら文具の6テーブルの CREATE TABLE 文を、作成順を守って完成させる

10.1 論理設計を物理設計へ変換する

論理設計では「顧客名は文字列」「単価は数値」という抽象的な決め方で十分でした。物理設計では、これを使う RDBMS（本ガイドは PostgreSQL 17）が実際に持つデータ型に落とし込みます。データ型を誤ると、桁あふれ・小数の誤差・検索の遅さといった問題が後から発覚し、直すのが大変になります。

本ガイドでは PostgreSQL 17 を基準とします。ここで扱う DDL は、より新しいバージョンの PostgreSQL でもそのまま使えます。

論理設計での属性の種類 PostgreSQL の型 さくら文具での例 選ぶ理由
サロゲートキー（連番） integer GENERATED ALWAYS AS IDENTITY customer_id・order_id など 第9章の結論通り、DBに連番を自動生成させる。挿入時に値を指定しない
業務コード・短い文字列 varchar(n) customer_code・product_code 長さの上限が業務上決まっている文字列。上限 n は余裕を持って決める
お金 numeric(10,2) current_unit_price・unit_price float系は誤差が出るため金額には使わない。10桁・小数2桁で十分な業務規模
個数・回数 integer quantity 小数を持たない数量。マイナスも本来不要（10.2 の CHECK で防ぐ）
日付のみ（時刻不要） date order_date 受注日は「何月何日か」だけが業務上意味を持つ
日時（実際に起きた時点） timestamptz （さくら文具では未使用。第12章の予約の申込日時のほか、作成日時・ログなどで使う型） 「いつ起きたか」を時刻まで残し、後から正しく比較・集計できるようにする（下のヒント参照）
区分値（有限の選択肢） varchar(n) + CHECK status 第9章の方針通り、コード表テーブルは作らずアプリ側の定数と揃えた文字列＋制約で表現

ヒント: なぜ金額に float を使ってはいけないのか

real・double precision は2進数で小数を近似するため、0.1 + 0.2 のような単純な計算でも誤差が出ることがあります。金額の合計がずれると業務上の信頼を失うので、10進数を正確に扱える numeric を必ず使います。numeric(10,2) は「整数部分と小数部分を合わせて最大10桁、うち小数点以下2桁」を意味し、最大 99999999.99 まで表現できます。

ヒント: 日時は timestamp より timestamptz を基本にする

PostgreSQL の timestamp は、正式には timestamp without time zone です。タイムゾーンを持たない「日付と時刻の数字」をそのまま保存するため、それが日本時間なのか協定世界時（UTC）なのかは DB からは分かりません。一方 timestamptz（timestamp with time zone）は、入力された日時を UTC の「時点」に換算して保存し、取り出すときに接続（セッション）のタイムゾーン設定に合わせて表示します。申込日時・作成日時・ログのように実際に起きた瞬間を記録する列は、サーバーや利用者のタイムゾーンが違っても同じ瞬間を指せる timestamptz を選ぶのが基本です。なお、名前に反してタイムゾーン名そのものは保存されません。また、現在日時を返す now() の型も timestamptz です。

10.2 NULL許可と制約の設計

列を1つ追加するたびに、「この値は必ず入るか」「重複してよいか」「入れてよい値の範囲はどこまでか」を判断します。この判断を NOT NULL・UNIQUE・CHECK・FOREIGN KEY という4種類の制約でデータベースに宣言すると、アプリ側のバグや操作ミスがあっても、DB自身が誤ったデータの保存を拒否してくれます。

問い 制約 さくら文具での例
この値は必ず入るか NOT NULL customer_name・order_date は登録時点で必ず分かる
重複を許してよいか UNIQUE customer_code・product_code（第9章: 自然キーはUNIQUEで守る）
値の範囲・形式に決まりはあるか CHECK quantity > 0、status IN ('受付','発送済','キャンセル')
他の表の行を必ず指しているか FOREIGN KEY orders.customer_id は必ず customers に存在する行を指す

NULLを許すかどうかは「入力を強制すべきか」より一段深く、「その時点で値が存在しない状態が業務上ありえるか」で判断します。さくら文具では、メールアドレスは会員登録の必須項目にしていないため、email だけ NULL を許し、他の主要な列はすべて NOT NULL にします。

注意: 「とりあえずNULL許可」は後で痛い

列を追加するとき、迷ってすべて NULL 許可にしてしまう設計をよく見かけます。しかし NULL を許すと、集計 SQL で COALESCE や IS NULL の分岐が増え、比較や集計の結果も直感と食い違うことがあります（第2章）。「値が無いことに業務的な意味があるか」を毎回自問し、無ければ NOT NULL にしてデフォルト値や入力チェックで埋めましょう。

外部キーで最も重要な判断が ON DELETE です。参照される側の行が削除されたとき、参照する側をどう扱うかを決めます。

ON DELETE 動作 向いている場面
RESTRICT 参照している行が残っている限り削除を拒否する マスタ（顧客・商品・担当者・分類）— 取引の証跡を誤って消させない
CASCADE 親の削除に合わせて子も自動で削除する 親がなければ意味を持たない明細行（受注が消えたら明細も不要）
SET NULL 参照先が消えたら外部キー列を NULL にする 参照先が消えても子の行は残したく、参照が不明になっても困らない場合（第11章の注文の配送先の参照で使用）

さくら文具では、order_details だけ受注（orders）への参照を CASCADE にします。受注明細は受注そのものが無ければ存在意味を持たないためです。それ以外の外部キー（orders → customers・orders → staff・products → categories・order_details → products）はすべて RESTRICT にします。取引履歴が残っている顧客や商品、注文を受け付けた担当者を誤って削除できないようにするためです。退職した担当者は削除せず、第11章で扱う論理削除（deleted_at のような「削除済みの印」を付ける方法）で管理します。

重要: ON DELETE は「もし削除したら」の話に集中する

ON DELETE の選択は、通常の INSERT・SELECT の動きには一切影響しません。「親を消そうとしたときに何が起こるべきか」だけを考えれば十分です。迷ったら RESTRICT を既定にし、「親が消えたら子も意味を失う」ことが明確なときだけ CASCADE を選ぶと、事故の少ない設計になります。

10.3 テーブル定義書を書く

CREATE TABLE 文を書く前に、テーブル定義書という一覧表に列の仕様を整理すると、抜け漏れや型の揺れに気づきやすくなります。テーブル定義書は実務でも設計レビューの標準的な成果物です。orders テーブルを例に作ってみます。

列名 論理名 型 NULL PK/FK 制約・備考
order_id 受注ID integer 不可 PK IDENTITYで自動生成
order_date 受注日 date 不可 — 既定値は本日
customer_id 顧客ID integer 不可 FK customers参照・ON DELETE RESTRICT
staff_id 担当者ID integer 不可 FK staff参照・ON DELETE RESTRICT
status 状態 varchar(10) 不可 — CHECK: 受付／発送済／キャンセル、既定値は受付

このように「列名・論理名・型・NULL許可・PK/FK・制約」の6項目を横並びで書けば、レビューする人はDDLを読まなくても仕様を確認できます。実務ではExcelやツール（A5:SQL Mk-2 のテーブル定義書出力など）で管理することが多いですが、考え方は表計算ソフトでも十分実践できます。

ヒント: 定義書とDDLは常に一致させる

定義書を書いてからDDLを直接編集し続けると、いつの間にか2つの資料が食い違います。小規模なら「DDLを正典にして、定義書はDDLから生成する」運用にすると食い違いを防げます。本ガイドでは、まず定義書で考えを整理し、それをそのままDDLに翻訳する流れで進めます。

10.4 インデックスの基本

インデックスは、本の索引のように「特定の値を持つ行をすばやく見つけるための道しるべ」です。索引が無いと、該当する行を探すたびに表全体を1行ずつ確認する全表スキャンが発生します。

PostgreSQL は主キー（PRIMARY KEY）と一意制約（UNIQUE）の列には自動でインデックスを作成します。一方、外部キーの列には自動でインデックスが付きません。外部キー列は JOIN の条件になりやすく、親の行を削除・更新するときの参照チェック（その親を指す子の行が残っていないかの確認）でも検索されるため、インデックスを付けると効果が大きい場面がよくあります。

列 自動でインデックスが付くか 理由
主キー（PK） 付く PostgreSQLが一意性を保証するために内部で作成
UNIQUE制約の列 付く 同上。重複チェックに使う
外部キー（FK）の列 付かない FK制約は参照整合性を守るだけで、索引は作らない。必要かどうかを判断して自分で作る

ただし、外部キー列のインデックスは常に必要とは限りません。付けるかどうかは、次の3点を見て判断します。

判断の観点 考え方の例
その列で検索・JOIN する頻度 マイページで「この顧客の注文履歴」を毎回表示するなら、orders.customer_id での検索が多いので付ける
親の行を削除・更新する頻度 親の削除が日常的にあるなら、そのたびに子の表を探すので付ける。さくら文具では、顧客・担当者のように過去の注文から参照されるマスタは削除せず論理削除する（第11章）ので、この観点の効果は小さい
既存のインデックスで代用できないか 複合主キーなど、既存の複合インデックスの先頭列になっていれば、その列での検索には既存のインデックスが使えるので、新たに作る必要はない

さくら文具では、画面や集計でよく使う検索に合わせて、次の外部キー列に CREATE INDEX を追加します。order_details.order_id は、複合主キー (order_id, line_no) のインデックスの先頭列なので、そのインデックスで検索でき、別途作る必要はありません。

indexes.sql 
-- 外部キー列への索引（よく使う検索・JOINに合わせて付ける）
CREATE INDEX idx_orders_customer_id ON orders (customer_id);              -- 顧客ごとの注文履歴
CREATE INDEX idx_order_details_product_id ON order_details (product_id);  -- 商品別の販売数の集計
CREATE INDEX idx_products_category_id ON products (category_id);          -- 分類別の商品一覧
CREATE INDEX idx_orders_staff_id ON orders (staff_id);                    -- 担当者別の受注一覧
-- staff_id は担当者別の検索がめったに無いなら付けない判断もあり得る

用語メモ：全表スキャン — 索引を使わず表の全行を1行ずつ確認する検索方法。行数が少ないうちは問題になりませんが、行数が増えるほど遅くなります。

注意: インデックスは無条件に増やせばよいものではない

インデックスは検索を速くする一方、INSERT・UPDATE・DELETEのたびに索引自体も更新するコストと、保存領域を増やします。初心者のうちは「主キー・一意制約には自動で付く」「外部キー列は、検索・JOIN や親の削除・更新でよく使われるなら付ける（既存の複合インデックスの先頭列なら不要）」の2点を押さえれば十分です。それ以上の細かなチューニングは、実際の検索の遅さを計測してから検討します（性能設計は第11章の非正規化の議論にも関連します）。

10.5 物理ER図で全体を確認する

DDLを書く前に、これまでの判断（型・NULL許可・ON DELETE）を反映した物理ER図で全体を見渡しておきます。論理ER図（第4章）では型を string のような製品に依存しない名前で書いていましたが、物理ER図では PostgreSQL の実際の型名（varchar・numeric など）で書きます（int は integer の別名です）。

erDiagram customers ||--o{ orders : "注文する" staff ||--o{ orders : "受け付ける" orders ||--|{ order_details : "明細を持つ" products ||--o{ order_details : "明細に含まれる" categories ||--o{ products : "分類する" customers { int customer_id PK varchar customer_code UK varchar customer_name varchar email varchar address } categories { int category_id PK varchar category_name } products { int product_id PK varchar product_code UK varchar product_name int category_id FK numeric current_unit_price } staff { int staff_id PK varchar staff_name } orders { int order_id PK date order_date int customer_id FK int staff_id FK varchar status } order_details { int order_id PK,FK int line_no PK int product_id FK numeric unit_price int quantity }

order_details だけ主キーが2列（order_id・line_no）の複合主キーである点に注目してください。1つの受注（order_id）の中で明細行を1・2・3…と区別するline_noを組み合わせて、明細1行を一意に特定します。

10.6 CREATE TABLE 文を完成させる

いよいよ6テーブル全部のDDLを書きます。作成順は親→子が原則です。外部キーは参照先のテーブルがすでに存在していないと作れないため、参照される側（マスタ）を先に作り、参照する側（トランザクション）を後に作ります。

flowchart LR A["① categories
（分類マスタ）"] --> D["④ products
（商品マスタ）"] B["② customers
（顧客マスタ）"] --> E["⑤ orders
（受注ヘッダ）"] C["③ staff
（担当者マスタ）"] --> E D --> F["⑥ order_details
（受注明細）"] E --> F

① categories（商品分類） — 他のどのテーブルも参照しない、最初に作れるマスタです。

01_categories.sql 
-- ① 商品分類マスタ（他テーブルに依存しない）
CREATE TABLE categories (
    category_id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    category_name varchar(50) NOT NULL UNIQUE  -- 分類名は重複させない
);

② customers（顧客） — email のみ会員登録の必須項目にしていないためNULLを許可します。住所は、第3章で確認したとおり当面は顧客1人につき1つなので、customers の列として持ちます（複数配送先への拡張は第11章）。

02_customers.sql 
-- ② 顧客マスタ（他テーブルに依存しない）
CREATE TABLE customers (
    customer_id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_code varchar(10)  NOT NULL UNIQUE,  -- 業務上の会員番号
    customer_name varchar(100) NOT NULL,
    email         varchar(255) UNIQUE,           -- 未登録の会員がいるためNULL許可
    address       varchar(200) NOT NULL           -- 配送先として必須（当面は1人1住所）
);

③ staff（担当者） — 最もシンプルなマスタです。

03_staff.sql 
-- ③ 担当者マスタ（他テーブルに依存しない）
CREATE TABLE staff (
    staff_id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    staff_name varchar(50) NOT NULL
);

④ products（商品） — categories を参照します。分類が使われている間は削除できないよう ON DELETE RESTRICT にします。current_unit_price は、これから受ける注文に使う現在単価です（第6〜7章）。

04_products.sql 
-- ④ 商品マスタ（categoriesを参照）
CREATE TABLE products (
    product_id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_code       varchar(20)  NOT NULL UNIQUE,
    product_name       varchar(100) NOT NULL,
    category_id        integer NOT NULL
        REFERENCES categories (category_id) ON DELETE RESTRICT,
    current_unit_price numeric(10,2) NOT NULL
        CHECK (current_unit_price >= 0)  -- 現在単価（これから受ける注文に使う）
);

⑤ orders（受注ヘッダ） — customers・staff を参照し、状態は CHECK で3値に限定します。

05_orders.sql 
-- ⑤ 受注ヘッダ（customers・staffを参照）
CREATE TABLE orders (
    order_id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_date  date NOT NULL DEFAULT CURRENT_DATE,
    customer_id integer NOT NULL
        REFERENCES customers (customer_id) ON DELETE RESTRICT,
    staff_id    integer NOT NULL
        REFERENCES staff (staff_id) ON DELETE RESTRICT,
    status      varchar(10) NOT NULL DEFAULT '受付'
        CHECK (status IN ('受付', '発送済', 'キャンセル'))
);

⑥ order_details（受注明細） — 複合主キー、そして受注が削除されたら明細も一緒に消える ON DELETE CASCADE を使う、唯一のテーブルです。unit_price には、注文を受け付けた時点の商品マスタの現在単価（current_unit_price）をコピーして保存します（注文時単価）。商品マスタの現在単価が後から改定されても、過去の受注明細の金額は変わりません。

06_order_details.sql 
-- ⑥ 受注明細（orders・productsを参照、複合主キー）
CREATE TABLE order_details (
    order_id   integer NOT NULL
        REFERENCES orders (order_id) ON DELETE CASCADE,
    line_no    integer NOT NULL,             -- 受注内の明細行番号（1から連番）
    product_id integer NOT NULL
        REFERENCES products (product_id) ON DELETE RESTRICT,
    unit_price numeric(10,2) NOT NULL CHECK (unit_price >= 0),  -- 注文時単価
    quantity   integer NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, line_no)
);

重要: order_details だけCASCADEにした理由を説明できるようにする

「受注を1件削除すると、その受注に属する明細行はすべて自動的に削除される」という動きは、order_details が orders と1対多の強い依存関係（第5章の依存リレーションシップ）にあるからこそ許される設計です。一方 orders → customers をCASCADEにしてしまうと「顧客を削除したら過去の受注記録まで消える」という、業務上あってはならない事故につながります。CASCADEは「親が消えたら子も存在価値を失う」関係だけに限定しましょう。

最後に、10.4 のインデックスを追加すれば、さくら文具の物理設計は完成です。作成順は categories → customers → staff → products → orders → order_details → インデックス です。

やってみよう 10-1: テーブル定義書とDDLの対応を確かめる

10.6 の6つのDDLを見ながら、紙かメモアプリで次に取り組んでください。

手順

  1. 1 orders テーブルについて、10.3 の書式（列名・論理名・型・NULL・PK/FK・制約）で自分なりのテーブル定義書を書き、本文の例と一致するか確認する。
  2. 2 6つのテーブルを作成順（① categories → ⑥ order_details）に並べ、それぞれが「どのテーブルを参照しているか」を矢印で書き出す。10.6 のflowchartと一致するか確認する。
  3. 3 もし products → categories の ON DELETE を RESTRICT ではなく CASCADE にしてしまったら、どんな事故が起きるかを具体的な商品名で説明する。

理解度確認クイズ

  1. Q1. 単価を real 型ではなく numeric(10,2) 型にする理由を説明してください。

    回答を表示

    real のような浮動小数点型は2進数で小数を近似するため誤差が生じ、金額の合計がずれる恐れがあります。numeric(10,2) は10進数の小数を正確に扱えるため、金額のように誤差が許されない値に使います。

  2. Q2. order_details.order_id の外部キーが orders だけ ON DELETE CASCADE になっている理由を、orders.customer_id がRESTRICTである理由と対比しながら説明してください。

    回答を表示

    受注明細は受注そのものが無ければ存在意味を持たない「強い依存関係」なので、受注が削除されれば明細も自動的に削除してよいと判断できます（CASCADE）。一方、顧客は受注とは独立して存在する主体であり、顧客を削除しても過去の受注記録は業務上残すべき証跡なので、削除を禁止します（RESTRICT）。

  3. Q3. 外部キーの列（例: orders.customer_id）に、主キーや一意制約の列と同じように自動でインデックスが付かないのはなぜですか。また、索引を追加するかどうかは何を見て判断しますか。

    回答を表示

    主キー・一意制約は「値の重複を防ぐ」ために内部的に索引が必須ですが、外部キー制約は「参照先に値が存在するか」を確かめる仕組みで、参照する側の列の索引を前提としません。必要かどうかは使い方次第なので、PostgreSQL は自動では作りません。判断の目安は、その列で検索・JOIN する頻度、親の行を削除・更新する頻度（そのたびに子の表を探す処理が走る）、既存の複合インデックスの先頭列で代用できないか、の3点です。orders.customer_id は顧客ごとの注文履歴の検索で頻繁に使うため、CREATE INDEX で索引を追加します。

  4. Q4. order_details の主キーが order_id 単独ではなく、(order_id, line_no) の複合主キーになっている理由を説明してください。

    回答を表示

    1回の受注には複数の商品が含まれるため、order_id だけでは同じ受注の複数の明細行を区別できません。受注内で明細行を連番で識別する line_no を組み合わせることで、明細1行を一意に特定できます。
