14.1 この章の進め方 — 3つの総合演習

ここまでの13章で、ファイル操作・検索・テキスト処理・権限・プロセス・パッケージ管理・シェルスクリプトと、Linuxを使いこなすための道具を一通り学んできました。この章では新しいコマンドをほとんど覚えません。代わりに、今まで学んだ道具を組み合わせて、実際の現場で使えそうな仕組みを3つ作ります。

演習1: ログ集計

14.2 演習1: ログ集計レポートスクリプトを作る

access.log を手作業で cut や grep にかけて調べるのは、第7・8章でやったとおりです。しかし毎日同じ集計をするなら、それをスクリプトにまとめておいたほうが確実です。ここでは、ログファイル名を引数で受け取り、総件数・ステータスコード別件数・アクセス数上位のIP・エラー行を表示する log_report.sh を作ります。

図1: log_report.sh の処理の流れ

flowchart TD A["起動
log_report.sh access.log"] --> B{"引数はあるか？"} B -->|いいえ| E1["使い方を表示して
exit 1"] B -->|はい| C{"そのファイルは存在するか？"} C -->|いいえ| E2["エラーメッセージを表示して
exit 1"] C -->|はい| D["総件数・ステータス別件数・
上位IP・エラー行を集計"] D --> F["結果を表示する
（teeで保存も可能）"]

図のとおり、先にエラーになりうる条件を弾いてから本処理に入るのが、第13章で学んだ「引数チェック→存在チェック→本処理」という安全なスクリプトの型です。まずは総件数・ステータス別件数・上位IPまでの「基本版」から作ってみましょう。

第6章で学んだ nano でファイルを新規作成します。

ターミナル 
# nanoでスクリプトファイルを新規作成する
nano log_report.sh

エディタが開いたら、次の内容をそのまま入力してください。引数チェックと存在チェックは、第13章の if・$#・exit 1・>&2 をそのまま使い、集計部分は第7・8章の cut | sort | uniq -c | sort -rn の組み合わせです。コードを15行以内に収めるため、if〜fi を第8章で学んだ ;（コマンドの連続実行）で1行にまとめて書いています。動作は複数行に分けて書いた場合とまったく同じです。3行目の set -eu は、第13章 13.6 で学んだ安全装置です。

log_report.sh（基本版） 
#!/bin/bash
# ログ集計レポート（基本版）：総件数・ステータス別・上位IPを表示する
set -eu   # エラーや未定義の変数があればその場で止める（第13章）
if [ $# -eq 0 ]; then echo "使い方: log_report.sh ログファイル" >&2; exit 1; fi   # 引数チェック
LOGFILE="$1"
if [ ! -f "$LOGFILE" ]; then echo "エラー: $LOGFILE が見つかりません" >&2; exit 1; fi   # 存在チェック（!は否定）

echo "総件数: $(wc -l < "$LOGFILE") 件"
echo "--- ステータスコード別件数 ---"
cut -d' ' -f9 "$LOGFILE" | sort | uniq -c | sort -rn
echo "--- アクセス数上位3件のIP ---"
cut -d' ' -f1 "$LOGFILE" | sort | uniq -c | sort -rn | head -3

入力できたら Ctrl+O → Enter で保存し、Ctrl+X で nano を終了します。実行権限を付けて動かしてみましょう。

ターミナル

./log_report.sh access.log
出力結果（例）

--- ステータスコード別件数 ---

      3 404
      2 500

      4 10.0.0.2

基本版が動いたところで、「どのアクセスがエラーだったか」も分かるように改良しましょう。第7章で確認した grep -E ' (4|5)[0-9]{2} '（ステータスコードが4xxまたは5xxの行）を末尾に追加します。もう一度 nano log_report.sh を開き、下の「改良版」の内容に書き換えてください（基本版の続きに2行足すだけです）。

log_report.sh（改良版・完成形） 
#!/bin/bash
# ログ集計レポート（改良版）：件数集計に加えエラー行も抽出する
set -eu   # エラーや未定義の変数があればその場で止める（第13章）
if [ $# -eq 0 ]; then echo "使い方: log_report.sh ログファイル" >&2; exit 1; fi   # 引数チェック
LOGFILE="$1"
if [ ! -f "$LOGFILE" ]; then echo "エラー: $LOGFILE が見つかりません" >&2; exit 1; fi   # 存在チェック（!は否定）

echo "総件数: $(wc -l < "$LOGFILE") 件"
echo "--- ステータスコード別件数 ---"
cut -d' ' -f9 "$LOGFILE" | sort | uniq -c | sort -rn
echo "--- アクセス数上位3件のIP ---"
cut -d' ' -f1 "$LOGFILE" | sort | uniq -c | sort -rn | head -3
echo "--- エラー行（ステータス4xx/5xx） ---"
grep -E ' (4|5)[0-9]{2} ' "$LOGFILE"

14.3 演習2: バックアップを自動化する

ログの集計ができるようになったところで、次は、これまでの章で作ってきた練習環境そのものを守る「バックアップ」を自動化しましょう。~/linux-practice フォルダ全体を、日付入りの圧縮ファイルとして ~/backups に保存する backup.sh を作ります。ここで初めて tar コマンドを使います。

オプション 意味
c create：新しいアーカイブ（まとめたファイル）を作成する
x extract：アーカイブを展開する
t list：展開せずに中身の一覧を表示する
z gzip：gzip形式で圧縮・伸長する（.tar.gzにする）
f file：続けてアーカイブのファイル名を指定する（必ず最後に置く）

これらを組み合わせた tar -czf（c＋z＋f）が「圧縮して作成する」、tar -xzf（x＋z＋f）が「展開する」、tar -tzf（t＋z＋f）が「中身を見るだけ」だと覚えておくと迷いません。nanoで作成します。

ターミナル 
# nanoでバックアップスクリプトを新規作成する
nano backup.sh
backup.sh 
#!/bin/bash
# ~/linux-practice を日付付きtar.gzでバックアップする
set -eu   # エラーや未定義の変数があればその場で止める（第13章）
mkdir -p ~/backups
file=~/backups/practice_$(date +%Y%m%d).tar.gz

tar -czf "$file" -C "$HOME" linux-practice
echo "バックアップ完了: $file"

# 7日より古いバックアップだけを削除する
find ~/backups -name "practice_*.tar.gz" -mtime +7 -delete

2つ、初心者がつまずきやすいポイントを解説します。

  • なぜ保存先を ~/backups にするのか — バックアップの保存先は、必ずバックアップ対象の外に置きます。もし ~/linux-practice の中に保存すると、作ったばかりのバックアップファイルまで次回のバックアップに巻き込まれ、実行するたびにアーカイブがどんどん膨らんでしまいます。
  • なぜ -C "$HOME" を付けるのか — -C "$HOME" は「まず $HOME に移動してから」という意味です。これを付けずに ~/linux-practice のような絶対パスを渡すと、tar は先頭の / だけを取り除いて home/student/linux-practice/... という深いパスのまま保存します。展開すると home/student という余計な階層ができ、別の場所や別のユーザーで復元しづらくなります。-C で移動してから linux-practice という相対パスを渡すことで、アーカイブの中身が linux-practice/... というシンプルな相対パスになります。

find に -delete を付ける前に、必ず -print で対象を確認する

find ... -delete は、条件に一致したファイルを確認なしにその場で削除します。第7章の -mtime のように条件を組み合わせるコマンドは、書き方を1つ間違えるだけで意図しないファイルまで削除対象になりえます。新しい find の条件を書いたら、まず -delete の代わりに -print を付けて「何が消えるか」を目で見て確認し、想定どおりだった場合だけ -delete に変える習慣をつけましょう。

保存できたら、実行権限を付けて動かしてみましょう。

ターミナル 
# 実行権限を付与して実行する
chmod +x backup.sh
./backup.sh
出力結果（例） 
student@ubuntu:~/linux-practice/ch14$ ./backup.sh
バックアップ完了: /home/student/backups/practice_20260923.tar.gz
ターミナル 
# 削除する前に -print で対象を確認する（このコマンドではまだ削除しない）
find ~/backups -name "practice_*.tar.gz" -mtime +7 -print

作ったばかりのバックアップは7日より古くないので、今の時点では何も表示されません。7日より古いファイルがあれば、ここに一覧表示されます。

バックアップができたら、必ず中身を検証してから安心しましょう。「作っただけで確認しない」バックアップは、いざ必要になったときに壊れていても気づけません。

ターミナル 
# 作成されたバックアップファイルを確認する
ls -lh ~/backups
出力結果（例） 
student@ubuntu:~/linux-practice/ch14$ ls -lh ~/backups
total 4.0K
-rw-r--r-- 1 student student 3.1K Sep 23 09:15 practice_20260923.tar.gz

表示されたファイル名を変数に入れておくと、この後のコマンドが楽になります（第13章の変数とコマンド置換の応用です。スクリプトの中だけでなく、ターミナルで直接入力するときにも変数は使えます）。バックアップを作った日から日付が変わっている場合は、上の ls で確認した実際のファイル名を指定してください。

ターミナル 
# 今日作ったバックアップのファイル名を変数に入れる（コマンド置換）
latest=~/backups/practice_$(date +%Y%m%d).tar.gz

# アーカイブの中身を一覧表示する（展開はしない）
tar -tzf "$latest"
出力結果（例・一部省略） 
linux-practice/
linux-practice/ch05/
linux-practice/ch07/
linux-practice/ch07/sales.csv
linux-practice/ch07/access.log
linux-practice/ch14/
linux-practice/ch14/access.log
linux-practice/ch14/log_report.sh
linux-practice/ch14/backup.sh
（以下省略）

中身が home/student/linux-practice/... のような深いパスではなく linux-practice/... から始まっていれば、-C "$HOME" が効いている証拠です。最後に、実際に別のフォルダへ展開して復元できるかも確かめておきましょう。

ターミナル 
# 展開先を作り、そこへ展開して中身を確認する
mkdir -p ~/restore-test
tar -xzf "$latest" -C ~/restore-test
ls ~/restore-test/linux-practice
出力結果（例） 
student@ubuntu:~/linux-practice/ch14$ ls ~/restore-test/linux-practice
ch05  ch06  ch07  ch08  ch09  ch10  ch12  ch13  ch14

表示されるフォルダは、これまでの章で作ったものによって多少異なります。

重要ポイント

「バックアップを取る」だけでなく「復元できることを確かめる」までが1セットです。tar -tzf で中身の一覧を確認し、tar -xzf で実際に展開して元どおりのフォルダ構成になっているかを見る、この2ステップを習慣にしましょう。

やってみよう 14-2: backup.sh でバックアップと復元を試す

14.4 演習3: crontabで定期実行する

backup.sh が完成したら、あとは「決まった時刻に自動で実行される」ようにするだけです。Linuxには cron（クーロン）という、指定した時刻にコマンドを自動実行してくれる仕組みが標準で備わっています。自分専用の実行スケジュール表を編集するコマンドが crontab -e です。

ターミナル 
# 自分のスケジュール表を編集する
crontab -e

第11章で ~/.bashrc に export EDITOR=nano を追記していれば、no crontab for student - using an empty one と表示されたあと、すぐに nano が開きます。追記していない場合は、初回だけ次のようなエディタの選択画面が出るので、第6章で学んだ nano（選択肢の1）を選びます。

出力結果（例・EDITOR を設定していない場合） 
no crontab for student - using an empty one

Select an editor.  To change later, run 'select-editor'.
  1. /bin/nano        <---- easiest
  2. /usr/bin/vim.basic
  3. /usr/bin/vim.tiny
  4. /bin/ed

Choose 1-4 [1]: 1

nano には # で始まる説明文（テンプレート）が最初から書かれているので、その一番下に1行追加します。nanoが開いたら、1行に「いつ」「何を」実行するかを書きます。書式は次の6つの項目を半角スペースで区切った並びです。

位置 項目 指定できる値 例（0 3 * * * での値）
1 分 0〜59 0
2 時 0〜23 3
3 日 1〜31 *
4 月 1〜12 *
5 曜日 0〜7（0と7は日曜） *
6 実行するコマンド 絶対パスで書く /home/student/linux-practice/ch14/backup.sh

いずれの項目も *（アスタリスク）を書くと「毎分」「毎時」のように指定しない＝すべてを意味します。たとえば「毎日午前3時に backup.sh を実行する」なら、次のように書きます。

crontab（nanoで編集中の内容に1行追加する） 
0 3 * * * /home/student/linux-practice/ch14/backup.sh >> /home/student/backup.log 2>&1

0 3 * * * は「分=0、時=3、日・月・曜日は指定なし」なので「毎日3時0分」です。後ろの >> /home/student/backup.log 2>&1 は、第8章で学んだ追記リダイレクトと標準エラー出力の統合で、実行結果とエラーをまとめて記録に残します。ここには2つ、cron特有の注意点があります。

  • 必ず絶対パスで書く — cronはあなたが普段使っているターミナルとは違う、ごく限られた環境でコマンドを実行します。~ や相対パスに頼らず、/home/student/... のような絶対パスで書きます。
  • ユーザー名を自分の環境に置き換える — student の部分は、第2章で確認した自分のユーザー名（Multipassなら ubuntu）に読み替えてください。

crontabの行に % を直接書かないのはなぜ？

crontabの行の中では、% が改行として扱われるという特別な意味を持ちます。もし date +%Y%m%d のような % を含むコマンドをcrontabの行に直接書くと、%以降が別の意味に解釈されて正しく動きません。だからこそ、backup.shの中では $(date +%Y%m%d) のような日付処理をスクリプトの内部で行い、crontabの行からは backup.sh を呼び出すだけにしています。

追加した行の末尾で Enter を押して改行してから、保存して終了します（Ctrl+O → Enter → Ctrl+X）。登録できたかは crontab -l で確認できます。最後の行に改行が無いと new crontab file is missing newline before EOF, can't install. と表示されて登録されません。その場合は y を押して編集し直し、行末で Enter を押してから保存します。

ターミナル 
# 登録したスケジュールを一覧表示する
crontab -l
出力結果（例・先頭の # コメント行は省略） 
student@ubuntu:~/linux-practice/ch14$ crontab -l
0 3 * * * /home/student/linux-practice/ch14/backup.sh >> /home/student/backup.log 2>&1

毎分実行で動作を確かめる前に、cron の仕組み（cron デーモン）自体が動いているかを確認しておきましょう。第10章で実行した systemctl status cron と同じコマンドです。

ターミナル 
# cronサービスが動いているか確認する
systemctl status cron
出力結果（例） 
● cron.service - Regular background program processing daemon
     Loaded: loaded (/usr/lib/systemd/system/cron.service; enabled; ...)
     Active: active (running) since ...

Active: active (running) であれば問題ありません。もし inactive と表示されたら、次のコマンドで起動します（start は今回初めて使うサブコマンドですが、status と同じ systemctl の仲間で、そのサービスを起動させる働きをします）。

ターミナル 
# 停止していた場合はcronサービスを起動する
sudo systemctl start cron

WSLでは systemctl が使えないことがある

WSL環境では、設定によって systemd（systemctlの土台となる仕組み）が無効になっている場合があります。その場合は、古くからある service コマンドで代わりに起動できます。

ターミナル 
# WSLでsystemdが無効な場合の代替コマンド
sudo service cron start

ただし「毎日午前3時」のままでは、動作しているかを確かめるのに1日待つことになってしまいます。動作確認のときだけ、crontab -e を開いて次のように「毎分実行」に変更すると、1〜2分でログにコマンドが記録されるかを確認できます。

crontab（動作確認用に一時的に変更） 
*/1 * * * * /home/student/linux-practice/ch14/backup.sh >> /home/student/backup.log 2>&1

確認できたら、必ず元に戻す

tail -f /home/student/backup.log（第6章）で1〜2分待ち、「バックアップ完了」が記録されれば正常に動いています。確認できたら crontab -e を開き、*/1 * * * * を元の 0 3 * * * に戻しておきましょう。戻し忘れると、1分ごとにバックアップの作り直しが走り続け（ファイル名は日付単位なので、その日のファイルが毎分上書きされます）、backup.log にも1分ごとに記録が溜まり続けます。

cron は Ubuntu が動いている間だけ働く

cron は、指定の時刻に Ubuntu が動いていなければ実行されません。WSL はターミナルを閉じてしばらくすると停止し、Multipass も Mac のスリープ中や VM の停止中は動きません。学習環境では午前3時の実行は行われないことが多いので、動作確認は毎分実行で行いましょう。常に動いている本番のサーバーでは、この心配はありません。

やってみよう 14-3: crontab に登録して定期実行を確認する

backup.sh をcrontabに登録し、実際に自動実行されることを確かめましょう。

手順

  1. 1 crontab -e で backup.sh を毎日3時に実行する行を、絶対パス・自分のユーザー名で登録する。
  2. 2 systemctl status cron（systemd が無効な WSL なら service cron status）でcron自体が起動していることを確認する。
  3. 3 動作確認のため一時的に */1 * * * *（毎分）に変更し、1〜2分待ってから backup.log を確認する。
  4. 4 動作を確認できたら、crontab -e で 0 3 * * * に戻す。

確認問題

  1. Q1. log_report.sh で、引数が無い場合や指定されたファイルが存在しない場合に、エラーメッセージを >&2 に出して exit 1 する理由を説明してください。

    回答を表示

    >&2（標準エラー出力）に出すことで、正常な集計結果（標準出力）とエラーメッセージを区別でき、結果だけをファイルに保存したいときにエラーメッセージを混ぜずに済みます。また exit 1 で0以外の終了ステータスを返すことで、このスクリプトを呼び出す側（人やcronなど）が「正常に終わったか失敗したか」を判定できるようになります。

  2. Q2. backup.sh で、バックアップの保存先（~/backups）をバックアップ対象（~/linux-practice）の外に置く必要があるのはなぜですか。

    回答を表示

    もし保存先を ~/linux-practice の中に置くと、作成したバックアップファイル自体が次回のバックアップ対象に含まれてしまい、実行するたびにアーカイブの中に古いアーカイブが積み重なって際限なく膨らんでいきます。バックアップ対象と保存先は必ず分けておく必要があります。

  3. Q3. find ~/backups -name "practice_*.tar.gz" -mtime +7 -delete を実行する前に、-print で対象を確認する習慣が大切なのはなぜですか。

    回答を表示

    -delete は確認なしに一致したファイルをその場で削除し、元に戻せません。find の条件（-name や -mtime の書き間違いなど）が意図と違っていた場合、-print であれば「何が一致するか」を安全に確認できますが、-delete のままだと想定外のファイルまで削除されてから気づくことになります。まず-printで確認し、想定どおりのときだけ-deleteに変える習慣が事故を防ぎます。

  4. Q4. crontabの行に date +%Y%m%d のような % を含むコマンドを直接書くとどうなりますか。日付の処理はどこで行うべきですか。

    回答を表示

    crontabの行の中では % が改行として特別に解釈されるため、% を含むコマンドをそのまま書くと意図した動作をしません。そのため、日付を使う処理はcrontabの行に直接書かず、呼び出す側のスクリプト（backup.shなど）の中で $(date +%Y%m%d) のように行い、crontabの行からはそのスクリプトを呼び出すだけにします。
