第11章 所要時間: 約50分

ログイン画面のカスタマイズとセキュリティ強化

ログイン画面は、利用者が最初に触れる場所であると同時に、攻撃者が最初に狙う場所でもあります。この章では、表示や使い勝手を整える設定と、パスワードポリシー・ブルートフォース検知・二要素認証（OTP）といった「守り」を固める設定の両方を、実際の画面項目に沿って学びます。

この章で学ぶこと

  • Login タブの各設定項目（自己登録・パスワード再設定など）の意味を理解する
  • メール送信設定とテーマ・ブランディングの位置づけを把握する
  • パスワードポリシーとブルートフォース検知でアカウントを守る設定ができる
  • OTP（ワンタイムパスワード）による二要素認証を設定し、実際に体験する

11.1 この章の位置づけ — 「使いやすさ」と「守り」の両立

第10章までで、レルム・クライアント・ユーザー・ロールを設定し、実際にログインしてトークンを取得できるようになりました。ここまでは「動く」状態を作る章でしたが、この章からは「安全に運用する」ための設定を扱います。ログイン画面は、利用者にとって最初の入り口であると同時に、攻撃者にとっても最初の標的です。Keycloakは、画面の見た目を整える設定と、不正ログインを防ぐ設定の両方を、コードを書かずに管理コンソールから調整できます。

図1: ログイン画面を守る4つの層

flowchart TD A["ログイン画面
表示設定・テーマ"] --> B["パスワードポリシー
弱いパスワードを拒否"] B --> C["ブルートフォース検知
総当たり攻撃を検知しロック"] C --> D["二要素認証（OTP）
パスワード漏えい後の最終防衛線"]

図のとおり、どれか1つだけを設定しても十分ではありません。パスワードポリシーを強くしても、総当たり攻撃を検知しなければ延々と試行され続けますし、ブルートフォース検知があっても、漏えいしたパスワードそのものをそのまま使われれば通ってしまいます。複数の層を重ねるという考え方が、この章全体を貫くテーマです。

11.2 ログイン画面の表示設定（Realm settings → Login）

管理コンソールで対象のレルムを開き、Realm settings → Login タブを見てみましょう。ここには、ログイン画面にどんな機能を表示するかを切り替えるスイッチが並んでいます。

設定項目 意味
User registration 利用者自身が「新規登録」できるようにするか。有効にするとログイン画面に登録リンクが表示される
Forgot password 「パスワードをお忘れですか？」リンクを表示するか。有効にはメール送信設定（11.3節）が必要
Remember me ログイン状態を長く保持するチェックボックスを表示するか
Email as username ユーザー名の代わりにメールアドレスをログインIDとして使うか
Login with email ユーザー名に加えて、メールアドレスでもログインできるようにするか
Verify email 初回ログイン時にメールアドレスの確認（本人のメールかどうか）を求めるか
Duplicate emails 同じメールアドレスを複数のユーザーに登録できるようにするか（通常は無効のまま）

社内システムと一般公開サービスで選び方が変わる

社内の業務システムでは、アカウントは情報システム部門が発行するのが普通なので User registration は無効のままにすることが多いです。一方、会員登録型の一般公開サービスでは、利用者自身が登録できる必要があるため User registration を有効にし、なりすまし登録を防ぐために Verify email も有効にするのが定石です。

11.3 メール送信の設定（Realm settings → Email）

「パスワードを忘れた」からの再設定メールや、メールアドレス確認メールを送るには、KeycloakにSMTPサーバー（メール送信用サーバー）の情報を教える必要があります。Realm settings → Email タブで設定します。

項目 内容
From 送信元として表示されるメールアドレス
Host / Port SMTPサーバーのホスト名とポート番号
Encryption（SSL/TLS） 通信を暗号化するかどうか。本番では有効にするのが基本
Authentication SMTPサーバーへのログインが必要な場合に有効化し、ユーザー名・パスワードを入力する

学習中は「開発用SMTPサーバー」が便利

本物のメールサーバーを用意しなくても、Mailpit のような開発用SMTPサーバーをDockerで立てれば、送信されたメールをブラウザ上で確認できます。実際に届く必要はなく「送信できたか」を確かめたいだけの学習には十分です。

ターミナル 
# 開発用SMTPサーバー（Mailpit）を起動する
# 8025: メール確認用のWeb画面 / 1025: SMTP受信ポート
docker run -d --name mailpit -p 8025:8025 -p 1025:1025 axllent/mailpit

起動後、Realm settings → Email で Host に localhost（またはコンテナ名）、Port に 1025 を設定すれば、Keycloakから送られたメールを http://localhost:8025 のWeb画面で確認できます。

11.4 テーマとブランディング（Realm settings → Themes / General）

ログイン画面の色やロゴを自社のデザインに合わせたい場合は、Realm settings → Themes タブでテーマを切り替えます。Keycloakでは、画面の種類ごとに別々のテーマを指定できます。

テーマ種別 適用範囲
Login theme ログイン画面・パスワード再設定画面など
Account theme 利用者自身がプロフィールを管理するアカウントコンソール
Email theme パスワード再設定メールなどのメール本文の見た目

独自テーマを作る場合は、Keycloakのthemes/ディレクトリの下に自分のテーマフォルダを用意し、Dockerであれば -v オプションでコンテナの /opt/keycloak/themes/ にマウントして読み込ませます。テーマの作り方（HTMLテンプレート・CSSの構成など）は本教材の範囲を超えるため、詳細は公式ドキュメントを参照してください。もっと手軽にブランドを反映したい場合は、Realm settings → General の Display name（表示名）・HTML Display name（HTML表示名）でログイン画面上部のタイトルを変更するだけでも印象は変わります。

11.5 パスワードポリシー（Authentication → Policies）

Authentication → Policies → Password policy では、新しいパスワードが満たすべき条件を1つずつ追加できます。「Add policy」から選んで組み合わせます。

ポリシー 内容
Minimum Length パスワードの最小文字数
Uppercase / Lowercase Characters 大文字・小文字をそれぞれ何文字以上含むか
Digits 数字を何文字以上含むか
Special Characters 記号を何文字以上含むか
Not Recently Used 過去に使ったパスワードの再利用を、直近何回分まで禁止するか
Not Username / Not Email ユーザー名やメールアドレスと同じ（含む）文字列を禁止する

近年は「長さ」を最優先する考え方が主流

記号や大文字を無理に混ぜさせるルールは、利用者が「Passw0rd!」のような覚えやすいパターンに逃げがちで、実は効果が薄いことが分かってきました。近年のガイドライン（NISTなど）は、ある程度の長さ（例: 12文字以上）を確保することの方が、複雑な文字種の組み合わせより効果的だとしています。Keycloakでも Minimum Length を優先的に設定するとよいでしょう。

11.6 ブルートフォース（総当たり）攻撃の検知

Realm settings → Security defenses → Brute force detection を有効にすると、同じアカウントに対してログイン失敗が続いた場合、一時的にログインをロックできます。パスワードを次々に試す「総当たり攻撃」への対策です。

設定項目 内容
Max Login Failures ロックまでに許容する連続失敗回数
Wait Increment ロックのたびに待機時間をどれだけ延ばすか
Max Wait 待機時間の上限
Permanent Lockout 有効にすると一時ロックではなく、管理者が手動で解除するまで永続的にロックする

アカウントロックは諸刃の剣

ブルートフォース検知は攻撃者だけでなく、正規の利用者にも影響します。攻撃者が他人のユーザー名を狙ってわざと何度も失敗させることで、その本人を締め出す「サービス妨害」の手口としても悪用され得ます。Max Login Failures を極端に少なくしすぎない、Permanent Lockout は慎重に使う、といったバランス感覚が必要です。

11.7 二要素認証（OTP）を設定する

パスワードだけに頼らず、スマートフォンの認証アプリ（Google Authenticator・Microsoft Authenticator・FreeOTP など）が生成するワンタイムパスワード（OTP）を追加で要求するのが二要素認証です。パスワードが漏えいしても、スマートフォンを持っていない攻撃者はログインできません。

設定は次の手順で行います。

  1. 1 Authentication → Required actions を開き、Configure OTP の行を「有効（Enabled）」にする。これでレルム全体としてOTP設定が使える状態になる。
  2. 2 OTPを必須にしたいユーザーを Users から開き、Required user actions に Configure OTP を追加して保存する。
  3. 3 そのユーザーが次にログインすると、パスワード入力後にQRコードが表示された設定画面へ自動的に進む。
  4. 4 スマートフォンの認証アプリでQRコードを読み取ると、アプリ内に6桁の数字（30秒ごとに変わる）が表示される。その数字を画面に入力して登録を完了する。
  5. 5 以降のログインでは、パスワードに続いてアプリの6桁コードの入力を求められるようになる。

11.8 OTPポリシー（Authentication → Policies → OTP Policy）

OTPの生成方式には主に2種類あり、OTP Policy タブで切り替えられます。通常はデフォルトのTOTPのままで問題ありません。

項目 内容
Time-based（TOTP） 現在時刻をもとにコードを生成する方式。デフォルトで、多くの認証アプリが対応
Counter-based（HOTP） 使うたびにカウンターを1つ進めてコードを生成する方式。時計のズレの影響を受けない
Number of Digits コードの桁数。通常6桁
OTP Token Period TOTPでコードが有効な秒数。デフォルト30秒

11.9 さらに高度な守り方（予告）

Keycloakでは、Authentication flow（ログイン時に何を要求するかの流れ）をコピーして自由に組み替えることができます。たとえば「管理者ロールを持つユーザーだけOTPを必須にする」といった条件付き多要素認証も、コードを書かずにフローの部品を組み合わせて実現できます。また、指紋認証やセキュリティキーを使うWebAuthn（パスキー）にも標準で対応しています。これらは応用的な内容のため本教材では扱いませんが、「Keycloakは設定次第でここまで守りを固められる」ということは覚えておいてください。

やってみよう 11-1: パスワードポリシー・ブルートフォース検知・OTPを設定する

この章で学んだ3つの守りを、実際に自分の学習用レルムに設定して体験してみましょう。

手順

  1. 1 Authentication → Policies → Password policy で「Add policy」から Minimum Length を追加し、値を 12 にして保存する。
  2. 2 Realm settings → Security defenses → Brute force detection を有効化し、Max Login Failures を確認・保存する。
  3. 3 自分のユーザーを Users から開き、Required user actions に Configure OTP を追加して保存する。
  4. 4 一度ログアウトし、あらためてログインする。QRコードが表示されたら、スマートフォンの認証アプリで読み取り、表示された6桁のコードを入力する。
  5. 5 もう一度ログアウトし、パスワードに続いてアプリの6桁コードの入力を求められることを確認する。

この章のまとめ

  • Realm settings の Login タブで自己登録・パスワード再設定・メール確認などの表示を切り替えられる。
  • パスワード再設定やメール確認にはSMTP設定が必要。学習には Mailpit のような開発用SMTPサーバーが便利。
  • パスワードポリシー・ブルートフォース検知・OTPによる二要素認証を重ねることで、ログインの守りを多層化できる。
  • ブルートフォース検知には、正規利用者を締め出すリスクとのバランスが必要。

確認問題

  1. Q1. 「パスワードをお忘れですか？」機能を使えるようにするために、Login タブの設定に加えて何を設定する必要がありますか。

    回答を表示

    SMTP（メール送信）の設定（Realm settings → Email）です。再設定リンクをメールで送るため、SMTPサーバーの情報を登録しておく必要があります。

  2. Q2. ブルートフォース検知を有効にする際に注意すべきトレードオフは何ですか。

    回答を表示

    攻撃者が正規利用者のユーザー名を狙ってわざと何度もログインを失敗させることで、本人を締め出す嫌がらせ（サービス妨害）に悪用され得る点です。失敗回数の設定や Permanent Lockout の使用は慎重に判断する必要があります。

  3. Q3. あるユーザーに二要素認証（OTP）を必須にしたいとき、Keycloak上でどのような設定を行いますか。

    回答を表示

    そのユーザーの Required user actions に Configure OTP を追加します。次回ログイン時にQRコードが表示され、認証アプリで読み取って6桁のコードを入力することでOTPが登録され、以降のログインで求められるようになります。
