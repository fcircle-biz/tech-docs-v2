ホーム Keycloak 第10章
第10章 所要時間: 約45分

セッション・トークン・ログアウトの管理

前章で、アプリをKeycloakで保護できるようになりました。次に気になるのは「このログイン状態は、いつまで続くのか」です。この章では、アクセストークンの有効期限・リフレッシュトークンによる更新・SSOセッションという3つの層を整理し、Keycloak側から強制ログアウトさせる方法、そしてOIDCのログアウトの仕組みまでを学びます。

この章で学ぶこと

  • アクセストークン・リフレッシュトークン・SSOセッションという3つの層の関係を説明できる
  • アクセストークンがなぜ短命に設定されているのかを理解する
  • リフレッシュトークンでアクセストークンを取り直す流れを、curlコマンドで確認できる
  • Sessionsタブ・Tokensタブの主な設定項目と、変更するときの考え方を知る
  • 管理コンソールから特定ユーザーを強制ログアウトさせ、OIDCログアウトの仕組みを理解する

10.1 「いつまでログインしたままなのか」を決める3つの層

「ログインしたままになる時間」は、実は1つの設定ではなく、性質の異なる3つの層が重なって決まっています。それぞれ役割が違うので、まずは全体像をつかみましょう。

  • ①アクセストークンの有効期限 — アプリがAPIを呼ぶときに提示する入館証そのものの寿命。非常に短い（既定は数分程度）。
  • ②リフレッシュトークンの有効期限 — 切れたアクセストークンを、ログイン画面を出さずに取り直すための鍵の寿命。アクセストークンより長い。
  • ③KeycloakのSSOセッション — Keycloak側が「この人はログイン済み」と覚えている状態そのもの。①②の更新が効くかどうかは、このSSOセッションが生きているかどうかで決まる。

（Keycloakが覚えている

アクセストークンが切れても、SSOセッションが生きていればリフレッシュトークンで静かに取り直せます。SSOセッション自体が切れたときだけ、利用者はもう一度ログイン画面を見ることになります。

10.2 アクセストークンが短命な理由

第8章で学んだ通り、アクセストークンはJWT（署名付きの文字列）です。アプリはこのトークンを受け取ると、署名が正しいか・有効期限が切れていないかだけを見て、中身（誰であるか・どんな権限か）を信頼します。ここに、アクセストークンを短命にする理由が隠れています。

重要ポイント: 発行済みトークンは基本的に取り消せない

アプリはKeycloakに問い合わせず、トークン自体の署名と有効期限だけで正しさを判断します。つまり、一度発行したアクセストークンは、有効期限が来るまで基本的に取り消せません。もしトークンが漏れてしまった場合、被害が及ぶ時間は「有効期限が切れるまで」に限られます。だからこそKeycloakは、既定でアクセストークンの有効期限を5分程度という短い時間にしているのです。短くしておけば、万一漏れても被害を短時間に抑えられます。

「毎回5分でログインし直すのは面倒では」と思うかもしれません。そこで登場するのが、次に学ぶリフレッシュトークンです。アクセストークンだけを短命にしつつ、利用者にはログイン画面を出さずに更新し続けられる仕組みになっています。

10.3 リフレッシュトークンによる更新

リフレッシュトークンは、切れたアクセストークンをログイン画面を出さずに取り直すための専用の鍵です。アプリはアクセストークンの期限が近づいたら（あるいは切れたら）、リフレッシュトークンを添えてKeycloakのトークンエンドポイントに問い合わせます。実際にcurlで試してみましょう。

refresh-token.sh 
# 切れたアクセストークンをリフレッシュトークンで取り直す
curl -X POST "http://localhost:8080/realms/demo-realm/protocol/openid-connect/token" \
  -d "grant_type=refresh_token" \
  -d "client_id=demo-app" \
  -d "refresh_token=ここにリフレッシュトークン"

成功すると、次のような新しいトークンの組が返ってきます。新しいaccess_tokenと、次回の更新に使う新しいrefresh_tokenが含まれている点に注目してください（Keycloakはリフレッシュのたびにリフレッシュトークン自体も入れ替えます）。 

{
  "access_token": "新しいアクセストークン(JWT)",
  "expires_in": 300,
  "refresh_token": "新しいリフレッシュトークン",
  "refresh_expires_in": 1800,
  "token_type": "Bearer"
}

利用者からすれば、この更新はすべてアプリの裏側で自動的に行われるため、「ログインしたまま作業を続けられている」ように感じます。実際には数分おきに静かにトークンが交換され続けているのです。ただし、このリフレッシュトークンにも有効期限があります。それを決めているのが、次に学ぶSSOセッションです。

10.4 SSOセッション — Keycloakが覚えているログイン状態

SSOセッションとは、Keycloak側が持っている「この利用者はログイン済みである」という記録そのものです。リフレッシュトークンで更新できるのは、あくまでこのSSOセッションが生きている間だけです。SSOセッションには、性質の異なる2つの時間設定があります。

設定項目 意味 具体例
SSO Session Idle
（無操作タイムアウト）		 操作をしない状態が続いたときに、セッションを切る時間 30分操作がなければ切れる、など
SSO Session Max
（最長セッション時間）		 操作を続けていても、ログインしてからの合計時間がこれを超えたら強制的に切る時間 10時間経ったら操作中でも切れる、など

たとえるなら、Idleは「一定時間だれも入館証を使わなかったら無効にする」ルール、Maxは「発行してからどれだけ使い続けても、この時刻が来たら必ず入館証を回収する」ルールです。この2つを組み合わせることで、「使い続けているのに突然切れる」ことも「放置しっぱなしのセッションがいつまでも生き続ける」ことも防ぎます。

クライアント単位の設定もある

Keycloakにはレルム全体のSSOセッションとは別に、Client Session Idle / Client Session Maxという、クライアント（アプリ）ごとに個別のセッション時間を設定する項目もあります。未設定の場合はレルムのSSOセッション設定がそのまま使われます。「このアプリだけ短くしたい」場合に使う応用的な設定、と覚えておけば十分です。

10.5 設定場所 — Sessionsタブ／Tokensタブ

ここまで登場した設定は、すべて管理コンソールの Realm settings の中にあります。「Sessions」タブがSSOセッション関連、「Tokens」タブがトークンの有効期限関連です。

画面 主な項目 既定値の目安
Realm settings
→ Sessions		 SSO Session Idle 30分程度
Realm settings
→ Sessions		 SSO Session Max 10時間程度
Realm settings
→ Tokens		 Access Token Lifespan 5分程度
Realm settings
→ Tokens		 Client Session Idle / Max 未設定時はSSOセッション設定に従う

既定値はあくまで目安

上表の既定値は、Keycloakのバージョンによって多少変わることがあります。実際にお使いの環境の値は、必ずRealm settingsの画面自体で確認してください。数値そのものより、「Idleは無操作、Maxは合計時間、Access Token Lifespanは入館証そのものの寿命」という役割の違いを理解しておくことが大切です。

これらを変更するときの考え方はシンプルです。短くするほど安全ですが、利用者は再ログインを求められる回数が増えます。逆に長くするほど利便性は上がりますが、盗まれたトークンやセッションが使われ続けるリスクの窓が広がります。次の10.9節で、用途別の目安を整理します。

10.6 セッションの確認と強制ログアウト

設定した有効期限が来る前に、「今すぐこの人をログアウトさせたい」という場面があります。退職者が出たとき、不正アクセスの疑いがあるときなどです。Keycloakは、管理コンソールから現在ログイン中のセッションを一覧表示し、その場で切断できます。

  • 左メニュー Sessions — レルム内で現在ログイン中の全セッションを一覧表示。ユーザーごと・クライアントごとに確認でき、個別または一括で「Logout」できる。
  • Users → 対象ユーザー → Sessionsタブ — 特定の1人のセッションだけを確認・ログアウトしたいときはこちら。退職者の対応など、対象者が決まっている場合に使いやすい。

強制ログアウトを実行すると、そのSSOセッションが無効になり、対応するリフレッシュトークンも使えなくなります。次に述べるように、すでに発行済みのアクセストークンだけは有効期限まで生き残る点には注意してください（だからこそ10.2節の「短命にする」考え方が効いてきます）。

10.7 ログアウトのしくみ — OIDCログアウトエンドポイント

利用者が自分で「ログアウト」ボタンを押したときも、アプリはKeycloakのログアウトエンドポイントを呼び出します。これによってSSOセッションそのものが終了します。

http://localhost:8080/realms/demo-realm/protocol/openid-connect/logout?id_token_hint=<IDトークン>&post_logout_redirect_uri=<戻り先>
パラメータ 意味
id_token_hint ログイン時に受け取ったIDトークン。「誰のセッションを終了させるか」をKeycloakに伝える
post_logout_redirect_uri ログアウト完了後にブラウザを戻す先のURL

戻り先URLは事前登録が必要

post_logout_redirect_uriには、任意のURLを指定できるわけではありません。第5章で設定したクライアントのValid post logout redirect URIsに、あらかじめ登録済みのURLしか指定できません。未登録のURLを指定するとログアウト自体がエラーになります。リダイレクトURIの登録が必要なのは、ログインだけでなくログアウトも同じです。

10.8 「アプリからログアウトしたのに、まだログインできてしまう」問題

初心者がよくつまずくのがこの現象です。アプリ側で「ログアウト」ボタンを押しても、アプリ自身のセッション（クッキーなど）を消しているだけのことがあります。この場合、KeycloakのSSOセッションはまだ生きているため、もう一度そのアプリにアクセスすると、ログイン画面を経由せずに自動的にログインし直されてしまいます。

ログイン済み扱いになる"] end subgraph OK["正しいログアウト"] B1["アプリのログアウトボタン"] --> B2["Keycloakのログアウト
エンドポイントを呼ぶ"] B2 --> B3["KeycloakのSSOセッションが終了"] B3 --> B4["再アクセス時は
ログイン画面が表示される"] end

正しく対応するには、アプリ自身のセッションを消すだけでなく、Keycloakのログアウトエンドポイントも必ず呼ぶ必要があります。多くのOIDCライブラリは、ログアウト処理の中でこれを自動的に行ってくれます。

さらに一歩進んだ仕組みがシングルログアウト（バックチャネルログアウト）です。1つのSSOセッションに複数のアプリがぶら下がっている場合、利用者がどこか1つのアプリでログアウトすると、Keycloakが他の連携アプリすべてに「このセッションは終了した」と裏側から通知してくれます。この通知先は、各クライアントのBackchannel logout URLという設定項目に登録します。これにより、「勤怠アプリではログアウトしたのに、経費精算アプリではまだログインしたままだった」というズレを防げます。

10.9 用途に応じた設計のヒント

セッション時間の「正解」は用途によって変わります。利便性と安全性のどちらを優先するかを、システムの性質に合わせて決めましょう。

やってみよう 10-1: アクセストークンの短命さとリフレッシュ、強制ログアウトを体験する

Access Token Lifespanをわざと短く変更し、トークンが本当に期限切れになること、そしてリフレッシュトークンで取り直せることを自分の目で確認します。

手順

  1. 1 Realm settings → Tokens で Access Token Lifespan を「1分」など短い値に変更して保存する。
  2. 2 第8章で使ったログインフロー（またはAPI呼び出し）でアクセストークンとリフレッシュトークンを取得する。
  3. 3 1分以上待ってから、そのアクセストークンでAPI（または保護されたページ）にアクセスし、期限切れとして拒否されることを確認する。
  4. 4 10.3節のcurlコマンドを使い、リフレッシュトークンで新しいアクセストークンを取得できることを確認する。
  5. 5 最後に左メニュー Sessions から自分のセッションを探し、Logoutを実行する。その後は同じリフレッシュトークンで更新できなくなることを確認し、設定を元の値に戻しておく。

この章のまとめ

  • ログイン状態はアクセストークン・リフレッシュトークン・SSOセッションという3つの層が重なって成り立つ。
  • アクセストークンは取り消せないため、漏洩の被害を抑えるために既定で短命（数分程度）にされている。
  • リフレッシュトークンにより、SSOセッションが生きている間はログイン画面なしで更新し続けられる。
  • Sessions画面から現在ログイン中のセッションを確認・強制ログアウトできる。退職者対応や不正アクセス対応に使う。
  • アプリ側だけのログアウトではKeycloakのSSOセッションは残る。ログアウトエンドポイントを呼び、必要ならバックチャネルログアウトで他アプリにも通知する。

確認問題

  1. Q1. アクセストークンの有効期限が、既定で数分程度という短い時間に設定されているのはなぜですか。

    回答を表示

    発行済みのアクセストークンは、署名と有効期限だけで正しさが判断されるため、基本的に途中で取り消すことができません。もしトークンが漏れてしまっても、有効期限を短くしておけば被害が及ぶ時間を短時間に抑えられるためです。

  2. Q2. SSO Session IdleとSSO Session Maxの違いを説明してください。

    回答を表示

    SSO Session Idleは「一定時間、操作がなかったらセッションを切る」無操作タイムアウトです。SSO Session Maxは「ログインしてからの合計時間がこれを超えたら、操作中であっても強制的にセッションを切る」最長時間の上限です。

  3. Q3. 「アプリのログアウトボタンを押したのに、再アクセスすると自動的にログインし直されてしまう」のはなぜですか。また、どう対応すればよいですか。

    回答を表示

    アプリ側のセッション（クッキーなど）を削除しただけで、KeycloakのSSOセッションは残ったままになっているためです。アプリはログアウト時に、KeycloakのOIDCログアウトエンドポイントも必ず呼び出し、SSOセッション自体を終了させる必要があります。複数アプリが連携している場合は、Backchannel logout URLを設定したシングルログアウトで他のアプリにも通知できます。
