第1章 所要時間: 約40分

Keycloakとは何か

Keycloak（キークローク）は、アプリの「ログイン機能」をまとめて引き受けてくれるソフトウェアです。この章では、なぜログイン機能を自分で作ると大変なのか、Keycloakがそれをどう解決するのかを、身近な例えを使ってつかみます。まだインストールもコマンド入力もしません。まずは「何のための道具なのか」をしっかり理解しましょう。

この章で学ぶこと

  • アプリごとにログイン機能を自作すると何が問題になるのかを理解する
  • Keycloakを「ビルの共用受付」にたとえて、その役割を説明できる
  • シングルサインオン（SSO）とIAMという言葉の意味をつかむ
  • Keycloakでできること・本教材で学ぶ範囲を知る

本教材の進め方について

本教材では、Keycloakを Docker で起動して学習します（第3章で手順を解説します）。Dockerを使ったことがなくても、コマンドは1行ずつ意味を説明しながら進めるので心配ありません。また、画面操作は Keycloak 26 系 の管理コンソールを前提にしています。バージョンによってメニュー名が少し異なる場合がありますが、考え方は同じです。この章ではまだ何もインストールしません。「Keycloakとは何か」という考え方だけに集中しましょう。

1.1 ログイン機能を自分で作ると、何が大変なのか

Webアプリを作るとき、ほとんどの場合「ログイン機能」が必要になります。ユーザー名とパスワードを入力してもらい、正しければ中のページを見せる——最初は単純に思えます。しかし、実際に業務で使えるレベルのログイン機能を用意しようとすると、次のような項目をすべて自分で作り、ずっと守り続ける必要があります。

  • パスワードの安全な保管 — そのまま保存してはいけない。適切な方式で変換して保存する必要がある
  • パスワードを忘れたとき — メール送信、再設定リンクの発行と有効期限の管理
  • 不正ログインへの対策 — 何度も間違えたアカウントの一時ロック、二要素認証
  • 権限の管理 — 一般利用者と管理者で見せる画面を分ける仕組み
  • 退職・異動への対応 — アカウントの停止や権限の変更をすばやく反映する

さらに厄介なのは、アプリが増えるたびに同じ作業を繰り返すことになる点です。社内に「勤怠アプリ」「経費精算アプリ」「社内ポータル」の3つがあれば、ログイン機能も3つ。利用者はアプリごとに別々のパスワードを覚えることになり、管理者は退職者が出るたびに3か所のアカウントを止めて回ることになります。

自作が危険になりやすい理由

ログイン処理は、攻撃者から最も狙われる部分です。自作したログイン機能に見落としがあると、認証情報や利用者情報の漏えいなど、重大なセキュリティ事故につながる可能性があります。また、ユーザー情報がアプリごとにバラバラに存在すると、「本当に全部止めたか」を誰も確認できなくなります。だからこそ、ログインは専門の仕組みに任せるのが現在の主流です。

1.2 Keycloakとは — 「ビルの共用受付」で考える

Keycloak（キークローク）を一言でいうと、複数のアプリのログインと権限管理を、まとめて引き受けてくれるオープンソースのソフトウェアです。無料で使え、自分たちのサーバーやパソコンの上で動かせます。この役割を、オフィスビルの受付にたとえてみましょう。

たとえ話: ビルの共用受付と入館証

複数の会社が入っているオフィスビルを想像してください。部屋ごとに受付があると、訪問者は行く先ごとに身分証を見せ、名前を書かされます。そこで、ビルの入口に共用の受付を1つ置きます。訪問者はそこで一度だけ本人確認を受け、入館証を受け取ります。各部屋の担当者は、もう身分証を確認しません。入館証が本物か、どの階に入れる証かだけを見ればよいのです。Keycloakはこの「共用受付」で、発行される入館証にあたるのが後の章で学ぶトークンです。

この仕組みにすると、ログイン画面はKeycloakが1つだけ持ち、各アプリは「Keycloakが発行した入館証（トークン）を確認するだけ」になります。アプリ側はパスワードを一切受け取らず、保存もしません。ここが非常に重要な点です。

ここでは仕組みを単純化しています

実際のアプリは、利用者をKeycloakのログイン画面へ転送（リダイレクト）し、戻ってきた認可コードをトークンと交換する、という手順を踏みます。また、トークンにも用途の違う種類（IDトークン・アクセストークン・リフレッシュトークン）があります。詳しい流れは第8章、トークンの寿命や失効は第10章で学びます。

ログインを一手に引き受ける

ログイン画面・パスワード管理・本人確認をKeycloakが担当。アプリは作らなくてよくなります。

1回のログインで複数アプリ

一度ログインすれば、つながっている他のアプリにもそのまま入れます（SSO）。

権限をまとめて管理

ロールや権限の情報をKeycloakで一元管理し、アプリはその情報を使って「この操作を許可してよいか」を判断できます。

似たサービスとの関係

同じ役割を持つサービスに、Microsoft Entra ID（旧 Azure AD）・Okta・Auth0 などがあります。これらは事業者が運営するクラウドサービスですが、Keycloakは自分たちで動かすオープンソースである点が大きな違いです。使う技術（OpenID Connect など）は共通なので、Keycloakで学んだ考え方は他の製品でもそのまま活きます。

1.3 シングルサインオン（SSO）とIAM

Keycloakを学ぶうえで必ず出てくる2つの言葉を、ここで押さえておきます。どちらも「難しそうな略語」ですが、中身は先ほどの受付のたとえそのものです。

SSO ＝ 一度のログインで全部に入れる

シングルサインオン（Single Sign-On）は、1回ログインすれば、連携している他のアプリでもログイン画面が出ない仕組みです。ビルの入館証を一度受け取れば、各部屋で再び身分証を見せなくてよいのと同じです。利用者はパスワード入力の回数が減り、企業は「使い回しの弱いパスワード」を減らせます。

IAM ＝ 誰が何をしてよいかの管理

IAM（Identity and Access Management／ID・アクセス管理）は、利用者の情報（ID）と、その人にどこまで許すか（アクセス権）を一元的に管理する考え方と、その仕組み全般を指します。入社したらアカウントを作り、異動したら権限を変え、退職したら止める——この一連の流れを1か所で扱えるようにするのがIAMです。Keycloakは、このIAMを実現する製品の1つです。

「Googleでログイン」はSSOではありません

よく混同されますが、SSOは「一度ログインすれば、連携する他のアプリで再びログイン画面が出ない」仕組みです。一方、Webサービスでよく見る「Googleでログイン」「GitHubでログイン」は、本人確認を外部のサービスに任せる仕組みで、ソーシャルログイン（Keycloakでは外部ID連携／Identity Brokering）と呼びます。Keycloakはどちらも提供しますが、別の機能です。外部ID連携は第12章で扱います。

IAMの視点で見ると、Keycloakの価値は「ログインが楽になる」ことだけではありません。アカウントの一生（作成 → 権限変更 → 停止）を1か所で追えることこそが、組織にとって最大のメリットです。下の表で、自作の場合とKeycloakを使う場合を比べてみましょう。

観点 各アプリで自作した場合 Keycloakにまかせた場合
ログイン画面 アプリの数だけ作る Keycloakの1つを共用する
パスワードの保管 アプリごとに保管。方式もバラバラになりがち Keycloakだけが保管。アプリは受け取らない
利用者の負担 アプリごとにID・パスワードを覚える 1回のログインで複数アプリを利用できる
退職者の停止 全アプリを回って止める。漏れが起きやすい Keycloakで1か所止めれば、以後の認証やトークンの更新を一元的に止められる
二要素認証の追加 アプリごとに実装が必要 Keycloakの設定を変えるだけ

1.4 Keycloakでできること

Keycloakは機能が非常に多い製品です。ここでは「入門者が最初に知っておくとよい代表的な機能」を挙げます。それぞれ、本教材のどの章で扱うかも示しておきます。今は覚える必要はありません。「こういうことができるんだ」と眺めておけば十分です。

できること 内容 扱う章
ログイン画面の提供 すぐ使えるログイン・パスワード再設定・新規登録の画面が最初から用意されている 第5・8章
ユーザーと権限の管理 管理画面からユーザーを作成し、ロール（役割）やグループで権限を割り当てる 第6・7章
標準仕様での連携 OpenID Connect や SAML という共通ルールでアプリとつながる 第2・9章
二要素認証 スマートフォンのワンタイムパスワードなどを、設定だけで追加できる 第11章
ソーシャルログイン GoogleやGitHubのアカウントでログインできるようにする 第12章
既存ユーザーの活用 社内のLDAP / Active Directory にあるユーザーをそのまま使う 第12章

重要ポイント

Keycloakを使うと、アプリ側のプログラムは「Keycloakから渡されたトークンを確認する」だけになります。パスワードを受け取らず、保存もしません。つまり、アプリを作る人がセキュリティの難所をまるごと避けられる——これがKeycloakを導入する最大の理由です。なお、アプリとKeycloakが実際にどうやり取りしてトークンを受け取るのかは、第8章で手を動かしながら確認します。

1.5 この章で出てきた重要用語の整理

たとえ話で理解した内容を、正式な用語で整理しておきましょう。これらの言葉は、これからの章で何度も登場します。今の段階では「なんとなくの意味」がつかめていれば大丈夫です。

用語 たとえ 意味
Keycloak ビルの共用受付 複数アプリのログインと権限管理をまとめて引き受けるオープンソースのソフトウェア。
認証 身分証の確認 「あなたは本当にその人か」を確かめること。第2章で詳しく学ぶ。
認可 入れる階の指定 「その人に何を許すか」を決めること。第2章・第7章で詳しく学ぶ。
トークン 入館証 ログインに成功した人へKeycloakが発行する電子的な証明。アプリはこれを確認する。
SSO 入館証の使い回し シングルサインオン。1回のログインで、連携する複数アプリを利用できる仕組み。
IAM 入館管理台帳 ID・アクセス管理。利用者と権限を一元的に管理する考え方と仕組み全般。
レルム ビルの区画 Keycloak内で利用者や設定を区切る単位。第4章で詳しく学ぶ。
クライアント 受付に登録した部屋 Keycloakに登録したアプリのこと。第5章で詳しく学ぶ。

やってみよう 1-1: 身近な「まかせるログイン」を探してみる

まだコマンドは打ちません。この章で学んだ考え方を、自分の身のまわりの出来事と結びつけてみましょう。手を動かす前に「人に説明できる」状態にしておくと、第2章以降の理解がぐっと深まります。

手順

  1. 1 普段使っているサービスの中で、「Googleでログイン」「GitHubでログイン」のようなボタンを見たことがあるものを1つ思い出す。
  2. 2 そのとき、パスワードをどこに入力したかを思い出してみる。サービス側ではなく、GoogleやGitHubの画面に入力していたはずです。これがこの章で学んだ「受付にまかせる」形です。
  3. 3 次に、会社や学校のシステムで「一度ログインしたあと、別のシステムを開いてもパスワードを聞かれなかった」経験がないか思い出す。こちらがSSOです。手順1・2の「Googleでログイン」は本人確認を外部に任せるソーシャルログインで、SSOとは別の機能である点に注意しましょう。
  4. 4 「ビルの共用受付」のたとえを使って、Keycloakの役割を3行以内で書き出してみる。第2章では、この受付が使う共通ルール（OpenID Connect）を学びます。

この章のまとめ

  • ログイン機能の自作は、安全対策・権限管理・退職対応まで含めると負担が大きく、アプリが増えるほど破綻しやすい。
  • Keycloakは、複数アプリのログインと権限管理をまとめて引き受けるオープンソースの「共用受付」。
  • アプリはパスワードを受け取らず、Keycloakが発行したトークン（入館証）を確認するだけでよくなる。
  • SSOは1回のログインで複数アプリを使える仕組み、IAMは利用者と権限を一元管理する考え方。

確認問題

  1. Q1. アプリごとにログイン機能を自作すると、どのような問題が起きますか。2つ挙げてください。

    回答を表示

    例: (1) 同じような安全対策（パスワード保管・再設定・不正ログイン対策）をアプリの数だけ作り、守り続ける必要がある。(2) ユーザー情報がアプリごとにバラバラになるため、退職者のアカウント停止に漏れが生じやすい。ほかに「利用者がアプリごとにパスワードを覚える必要がある」なども正解です。

  2. Q2. Keycloakを使うと、アプリ側はパスワードをどう扱うことになりますか。

    回答を表示

    アプリはパスワードを一切受け取らず、保存もしません。利用者はKeycloakのログイン画面にパスワードを入力し、アプリはKeycloakが発行したトークン（入館証）が正しいかどうかだけを確認します。

  3. Q3. SSO と IAM の違いを、それぞれ一言で説明してください。

    回答を表示

    SSO（シングルサインオン）は「1回のログインで、連携する複数のアプリを使える仕組み」。IAM（ID・アクセス管理）は「利用者の情報と、その人に許す権限を一元的に管理する考え方・仕組み全般」です。SSOはIAMが提供する機能の1つ、という関係になります。
