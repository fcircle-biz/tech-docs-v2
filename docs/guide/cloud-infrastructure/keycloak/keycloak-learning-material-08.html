ホーム Keycloak 第8章
第8章 所要時間: 約55分

ログインを体験する — 認可コードフローとトークン

第3〜7章で、Keycloakの起動・レルム・クライアント・ユーザー・ロールをひととおり作りました。この章では、いよいよ実際にブラウザでログイン画面を通り抜け、Keycloakから認可コードを受け取り、それをトークンに交換して中身を読みます。第2章で言葉だけ学んだ「認可コードフロー」を、自分の手で最初から最後まで体験する章です。

この章で学ぶこと

  • 認可コードフローの流れを、実際のURLとレスポンスで追える
  • ブラウザで受け取った認可コードを、curlでトークンに交換できる
  • JWT（トークン）の構造を理解し、ペイロードをデコードして読める
  • IDトークンとアクセストークンの違いを、実際のクレームで説明できる

8.1 この章でやること

普段アプリを使うときは「ログインボタンを押したら、いつの間にか使えるようになっていた」という体験しかできません。裏側でどんな通信が行われているかは見えないようになっています。この章では、その裏側をあえて手動でなぞります。具体的には次の3ステップです。

  1. 1ブラウザでKeycloakの認可エンドポイントにアクセスし、ログイン画面を通って認可コードを受け取る
  2. 2その認可コードをcurlでトークンエンドポイントに送り、トークンと交換する
  3. 3受け取ったトークンの中身をデコードし、自分のユーザー名やロールが入っていることを確認する

実際のアプリでは、これらはすべてライブラリが自動でやってくれます（第9章で扱います）。しかし、一度手動で通しておくと「アプリが裏で何をしているのか」が具体的にイメージできるようになり、トラブルが起きたときの原因調査にも役立ちます。

8.2 認可コードフローの流れ

まず全体の流れを図で確認しましょう。登場人物は「利用者のブラウザ」「アプリ」「Keycloak」の3者です。

図1: 認可コードフローの全体像

sequenceDiagram autonumber participant B as 利用者のブラウザ participant A as アプリ participant K as Keycloak B->>A: ページを開く A->>B: Keycloakの認可エンドポイントへリダイレクト B->>K: 認可エンドポイントにアクセス K->>B: ログイン画面を表示 B->>K: ユーザー名とパスワードを送信 K->>B: 認可コードを付けてredirect_uriへリダイレクト B->>A: 認可コード付きでアプリに戻る A->>K: トークンエンドポイントへ認可コードを送信 K-->>A: アクセストークン・IDトークンを返す A-->>B: ログイン後の画面を表示

番号にそって解説します。

  • ①〜② — 利用者がアプリを開くと、アプリはまだログインしていないことに気づき、Keycloakの認可エンドポイントへ転送する。
  • ③〜④ — ブラウザがKeycloakにアクセスすると、Keycloak自身が用意したログイン画面が表示される（この時点でアプリは何もしていない）。
  • ⑤ — 利用者がユーザー名とパスワードを入力する。パスワードはKeycloakだけが受け取り、アプリには一切渡らない。
  • ⑥〜⑦ — 認証に成功すると、Keycloakは短命の認可コードを発行し、あらかじめ登録されたredirect_uri（第5章で設定したもの）へブラウザを送り返す。
  • ⑧〜⑨ — アプリは受け取った認可コードを、ブラウザを介さずアプリ自身からKeycloakへ直接送り、トークンと交換する。

なぜ2段階に分けるのか

もし⑥〜⑦で認可コードの代わりにトークンそのものを返してしまうと、トークンがブラウザのURL（アドレスバーや履歴、閲覧履歴、Referer）にそのまま残ってしまいます。認可コードは「トークンと交換できる引換券」にすぎず、単体では何もできません。しかも1回しか使えず、有効期限も数十秒〜数分と短いため、たとえURLに残って誰かに見られても実害が出にくい仕組みになっています。トークンの受け渡しは、ブラウザを経由しない⑧〜⑨のサーバー間通信でのみ行われます。

8.3 手を動かす準備

実際に試す前に、第5章で作成したクライアントdemo-appの設定を確認しておきましょう。管理コンソールで「Clients」→「demo-app」を開き、次の2点を確認します。

  • Standard flow が有効（ON）になっている — これが認可コードフローを許可する設定
  • Valid redirect URIs に http://localhost:8081/* が登録されている — Keycloakがコードを送り返してよい戻り先

戻り先にサーバーは要りません

http://localhost:8081/callback に実際のWebサーバーを立てる必要はありません。ブラウザはそのアドレスへの接続に失敗し、エラーページ（「サイトにアクセスできません」など）を表示しますが、それで問題ありません。この章で見たいのは、ページの中身ではなくアドレスバーに表示されるURLだからです。

8.4 認可エンドポイントにアクセスする

次のURLをブラウザのアドレスバーに直接入力してアクセスします（改行はURLを見やすくするために入れているだけで、実際は1行で入力します）。

認可エンドポイントURL 
http://localhost:8080/realms/demo-realm/protocol/openid-connect/auth
  ?client_id=demo-app
  &response_type=code
  &scope=openid
  &redirect_uri=http://localhost:8081/callback
  &state=xyz123

クエリパラメータの意味は次のとおりです。

パラメータ 値 意味
client_id demo-app 第5章で登録したクライアントID。どのアプリからのログイン要求かをKeycloakに伝える。
response_type code 「トークンではなく、まず認可コードがほしい」という指定。認可コードフローの目印。
scope openid OpenID Connectを使う宣言（第2章）。これがないとIDトークンが発行されない。
redirect_uri http://localhost:8081/callback ログイン成功後にコードを届ける戻り先。クライアント設定に登録済みのURIと一致している必要がある。
state xyz123 アプリが最初に決める任意の値。戻ってきたときに同じ値かを確認し、なりすましリクエストを見分けるために使う。

8.5 ログインして認可コードを受け取る

アクセスするとKeycloakのログイン画面が表示されます。第6章で作成したユーザーのユーザー名とパスワードでログインしてください。成功すると、ブラウザは自動的に次のようなURLへ移動します（ページ自体は「接続できません」というエラー表示になりますが、それで問題ありません）。

ログイン後のアドレスバー 
http://localhost:8081/callback?state=xyz123&session_state=xxxxxxxx&code=yyyyyyyy...

state=xyz123が自分が指定した値と一致していることを確認し、code=の後ろに続く文字列（認可コード）をコピーしておきます。次のセクションで使います。

認可コードは短命・1回限り

この認可コードは、発行から数十秒〜数分程度で失効し、一度トークンと交換すると再利用できません。時間を置きすぎたり、うっかりページを再読み込みしたりすると無効になるため、次の8.6の操作はコピーしたらすぐに行ってください。失敗したら8.4からやり直せば、新しいコードが発行されます。

8.6 コードをトークンに交換する

取得した認可コードを、Keycloakのトークンエンドポイントに送ります。これは本来アプリが自動で行う通信ですが、ここではcurlで手動で再現します。ターミナルで次のコマンドを実行してください（ここにコピーした認可コードの部分を、実際にコピーした値に置き換えます）。

terminal 
# 認可コードをトークンに交換するリクエスト
curl -X POST "http://localhost:8080/realms/demo-realm/protocol/openid-connect/token" \
  -d "grant_type=authorization_code" \
  -d "client_id=demo-app" \
  -d "code=ここにコピーした認可コード" \
  -d "redirect_uri=http://localhost:8081/callback"

redirect_uriは8.4で使ったものと完全に一致させる必要があります（Keycloakが「同じログイン要求の続きか」を確認するために使うため）。もしdemo-appを機密クライアント（confidential）として作成していた場合は、クライアントシークレットを示す-d "client_secret=..."もあわせて送る必要があります。パブリッククライアントとして作成していれば、この行は不要です。

8.7 返ってくるJSONの読み方

成功すると、次のような項目を含むJSONが返ってきます（値は長いため、一部を省略して表記しています）。

項目 値（例） 意味
access_token eyJhbGciOi... APIへのアクセス時に提示するトークン。第2章の「訪問証」にあたる。
expires_in 300 アクセストークンの有効秒数。この例では300秒（5分）で失効する。
refresh_token eyJhbGciOi... アクセストークンを再ログインなしで更新するためのトークン。第10章で扱う。
refresh_expires_in 1800 リフレッシュトークンの有効秒数。多くの場合アクセストークンより長い。
id_token eyJhbGciOi... 「誰がログインしたか」を表すトークン。アプリが利用者情報を知るために使う。
token_type Bearer トークンの種類。APIに送るときはAuthorization: Bearer <access_token>の形で使う。
scope openid email profile 実際に許可されたスコープの一覧。

8.8 トークンの中身を読む

access_tokenやid_tokenはJWT（JSON Web Token）という形式で、ヘッダー.ペイロード.署名のように、3つの部分がドット（.）でつながれています。真ん中のペイロード部分は暗号化されているわけではなく、Base64URLという方式で変換されているだけです。つまり、その気になれば誰でも中身を読めます。ターミナルで次のように、ペイロード部分だけを取り出してデコードしてみましょう。

terminal 
# JWTの2番目（ペイロード）部分だけをデコードする
# 桁数が4の倍数でないとエラーになるため == でパディングしておく
echo "ここにペイロード部分を貼り付け==" | base64 -d

jwt.ioのようなサイトに貼り付けてデコードする方法もありますが、注意が必要です。

本物のトークンを外部サイトに貼らない

学習中に発行された本物のトークンを、インターネット上の外部サイトへ貼り付けるのは避けましょう。仕組みを確認するだけなら、ローカル環境のbase64コマンドで十分です。どうしても外部サイトで確認したい場合は、本番の利用者情報が含まれない使い捨てのテスト用トークンに限定してください。

8.9 ペイロードの主なクレーム

デコードすると、次のような項目（クレームと呼びます）が並んだJSONが出てきます。

payload.json（例・一部省略） 
{
  "iss": "http://localhost:8080/realms/demo-realm",
  "sub": "3f7a9c1e-...",
  "aud": "demo-app",
  "exp": 1738000600,
  "iat": 1738000300,
  "azp": "demo-app",
  "preferred_username": "taro",
  "email": "taro@example.com",
  "realm_access": {
    "roles": ["viewer", "editor"]
  }
}
クレーム 意味
iss 発行者（issuer）。どのレルムが発行したトークンかを示すURL。
sub 主体（subject）。ユーザーを一意に識別するID。ユーザー名が変わっても値は変わらない。
aud 対象者（audience）。このトークンがどのクライアント向けかを示す。
exp 有効期限（expiration）。UNIX時刻でいつまで有効かを表す。
iat 発行時刻（issued at）。トークンが作られたUNIX時刻。
azp 認可された関係者（authorized party）。トークンの発行を要求したクライアントID。
preferred_username ログインに使ったユーザー名。第6章で設定した値。
email ユーザーのメールアドレス。
realm_access.roles 割り当てられたレルムロールの一覧。第7章で割り当てたロールがここに現れる。

realm_access.rolesに第7章で自分が割り当てたロール名がそのまま入っていることを確認してください。アプリはこの配列を見て「この利用者に管理画面を見せてよいか」などを判断します。

8.10 IDトークンとアクセストークンの違い（再確認）

第2章で学んだ「IDトークンは誰かを知るため、アクセストークンはAPIに渡すため」という違いを、実際のクレームで確認しましょう。両方のトークンをデコードして見比べると、次のような違いに気づきます。

観点 IDトークン（id_token） アクセストークン（access_token）
typ（ヘッダー内） JWT JWT（実装によりBearerと表現される場合もある）
主な用途 アプリ自身が「誰がログインしたか」を知るために読む APIサーバーに渡し、「このリクエストを許可してよいか」を確認してもらう
名前・メールの有無 preferred_username・emailなどプロフィール情報を含みやすい プロフィール情報は最小限。ロールなど認可判断に必要な情報が中心
外部への送信 原則としてアプリの外（他のAPI）には送らない 保護されたAPIへAuthorizationヘッダーで送る前提

「利用者の名前をアプリの画面に表示したい」ならIDトークンを、「バックエンドAPIにこのユーザーがアクセスしてよいか確認したい」ならアクセストークンを使う——この使い分けを覚えておきましょう。

8.11 発展: PKCEという追加の防御

今回はターミナルで手動操作したため意識しませんでしたが、スマートフォンアプリやシングルページアプリケーションのようなクライアントシークレットを安全に保管できないアプリ（パブリッククライアント）では、認可コードが途中で盗まれて悪用されるリスクへの対策が重要になります。

PKCE（プルーフキー）とは

PKCE（Proof Key for Code Exchange）は、アプリが認可コードを要求する前に自分だけが知る合言葉（コードベリファイア）を用意し、コードと交換するときに同じ合言葉を提示させる仕組みです。途中で認可コードだけを盗んでも、合言葉を知らない攻撃者はトークンに交換できません。Keycloakでは、クライアントの「Advanced」タブにあるProof Key for Code Exchange Code Challenge MethodをS256に設定することで有効化できます。パブリッククライアントでは有効化が強く推奨されています。

やってみよう 8-1: 自分のトークンを取得してロールを確認する

8.4〜8.9の手順を実際に自分の手で通し、自分のトークンの中身を確認しましょう。

手順

  1. 1 8.4の認可エンドポイントURLをブラウザに入力し、第6章で作成したユーザーでログインする。
  2. 2 アドレスバーに表示されたcode=の値をコピーする。時間をおかず次の手順に進む。
  3. 3 8.6のcurlコマンドのcode=を置き換えて実行し、JSONレスポンスを受け取る。
  4. 4 access_tokenまたはid_tokenのペイロード部分を8.8の方法でデコードする。
  5. 5 デコードした結果のpreferred_usernameが自分のユーザー名と一致し、realm_access.rolesに第7章で割り当てたロールが含まれていることを確認する。

この章のまとめ

  • 認可コードフローは「認可コードを受け取る」→「トークンに交換する」の2段階。これはトークンをブラウザのURLに出さないための設計。
  • 認可コードは短命かつ1回限りで使えなくなる、単体では価値のない「引換券」。
  • JWTのペイロードはBase64URLエンコードされているだけで、暗号化はされていない。誰でもデコードして読める。
  • IDトークンは「誰か」をアプリに伝えるため、アクセストークンはAPIへの認可判断のために使う。
  • パブリッククライアントでは、認可コードの横取りに備えてPKCE（S256）を有効にすることが推奨される。

確認問題

  1. Q1. なぜKeycloakは、ログイン成功時にトークンそのものではなく、いったん認可コードを返すのですか。

    回答を表示

    トークンを直接返すと、ブラウザのアドレスバーや履歴・Refererなどにトークンが残ってしまい、漏えいのリスクが高まります。認可コードは単体では使い道のない「引換券」であり、アプリがブラウザを経由しないサーバー間通信でトークンに交換するため、トークン自体がURLに現れません。

  2. Q2. 認可コードには、トークンと比べてどのような性質がありますか。2つ挙げてください。

    回答を表示

    (1) 有効期限が数十秒〜数分と非常に短い（短命）。(2) 一度トークンと交換すると再利用できない（1回限り）。この2点により、万一漏れても悪用できる時間・回数が限られます。

  3. Q3. JWTのペイロードに、パスワードのような機密情報を入れてはいけないのはなぜですか。

    回答を表示

    JWTのペイロードは暗号化されておらず、Base64URLという「変換」がされているだけだからです。この変換は誰でも簡単に元に戻せるため、ペイロードの中身は暗号化なしで読める前提で扱う必要があります。
