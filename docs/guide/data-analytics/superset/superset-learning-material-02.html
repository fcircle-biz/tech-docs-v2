ホーム Apache Superset 第2章
第2章 所要時間: 約60分

環境構築 — Dockerで動かす

この章では、Docker Compose を使って学習用の Apache Superset 環境を実際に起動します。用意するもの、起動コマンド、初期ログイン、起動している各コンテナの役割、サンプルデータの読み込み、そしてうまく起動しないときの確認ポイントまでを、手を動かしながら学びます。

本教材の検証環境: Apache Superset 6.1.0

本教材は Apache Superset 6.1.0（2026年5月リリース）で動作確認しています。Superset はバージョンによって画面のラベル・機能フラグの既定値・Docker Compose の構成が変わることがあります。異なるバージョンを使う場合は、必ず公式ドキュメントも併せて確認してください。

この章で作る環境は「学習・評価用」— 本番には使えない

公式の Docker Compose 構成は開発・評価用途を主目的としており、本番用途には推奨・サポートされていません（単一ホスト前提で冗長化できず、データも Docker ボリュームに置かれるためバックアップされません）。本番相当の構成で動かす場合は Kubernetes（Helm チャート）など別の方式を使います。本番構成で考えるべきことは第14章で扱います。

Windows で進める場合の注意

公式ドキュメントは Docker Compose での起動を Linux / macOS 向けに案内しており、Windows は公式サポート対象外とされています。Windows で学習する場合は WSL2 上の Linux（Docker Desktop の WSL2 バックエンド）で進めるのが無難です。本章のコマンドは PowerShell でも動く場合がありますが、行継続やパスの扱いで差異が出ることがあります。

この章で学ぶこと

  • Docker Compose を使って Superset を起動できる（用意するものと起動手順を理解する）
  • 初期管理者アカウントでログインし、既定パスワードを直ちに変更すべき理由を説明できる
  • 起動している各コンテナ（Superset本体・メタデータDB・キャッシュ・Celeryワーカー）の役割を説明できる
  • サンプルデータを読み込み、起動トラブル時に確認すべきポイントを把握している

2.1 用意するもの

Superset を実際に動かすには、画面を表示する Web アプリ本体だけでなく、設定を保存する場所や非同期処理の仕組みなど、いくつかの部品が同時に必要です。まずは何を用意すればよいか、そしてそれらを個別にインストールせず Docker でまとめて用意する理由を確認しましょう。

項目 目安・条件 理由
Docker Desktop（または Docker Engine ＋ Docker Compose v2） 最新の安定版がインストール済み docker compose コマンドを使うため
メモリ 8GB以上をDockerに割り当て
（公式の最低要件ではなく本教材の推奨値）		 Superset本体・メタデータDB・Redis・Celeryワーカーを同時に動かすため。4GB程度でも起動することはあるが、サンプルデータ投入や非同期クエリで詰まりやすい
空きポート 8088番 ブラウザからSupersetの画面にアクセスするため（使用中なら変更も可能）
git インストール済み 公式リポジトリを clone するため

上の4つさえあれば、Python のインストールやライブラリのバージョン調整を自分で行うことなく学習を始められます。理由は、Superset が単体のアプリではなく複数のコンポーネントが連携して動くシステムだからです。

Dockerを使わずに個別構築する場合

  • Python本体と、バージョンを合わせた依存ライブラリを用意する
  • 設定保存用にPostgreSQLを別途構築する
  • キャッシュ・非同期処理用にRedisとCeleryを構築し連携させる
  • どれか1つでも壊れると、1つずつ切り分けて調べる必要がある

Docker Composeを使う場合

  • 1つのコマンドで全コンポーネントがまとめて起動する
  • 組み合わせるバージョンは公式が検証済みの構成を使える
  • 環境がおかしくなっても、作り直して最初からやり直せる
  • 学習が終われば、PCを汚さず丸ごと削除できる

用語: Docker Compose とは

複数のコンテナ（Webアプリ・データベース・キャッシュなど）をまとめて定義し、1つのコマンドで起動・停止できるようにするツールです。Superset のように多くの部品で構成されるアプリケーションの学習環境を用意するのに向いています。

2.2 Docker Compose で起動する

公式リポジトリを取得し、付属の Compose ファイルで起動します。タグを指定せずに起動すると、その時点の最新（開発中のコード）が起動してしまうため、公式が案内するリリースタグへ切り替えてから起動します。ターミナル（macOS / Linux。Windows は WSL2 上の Linux を推奨）で、次のコマンドを順に実行してください。

セットアップ 
# 公式リポジトリを取得する（タグを後で切り替えるため--depth=1は付けない）
git clone https://github.com/apache/superset.git
cd superset

# 本教材の検証バージョンのタグに切り替える（番号は公式手順でも確認する）
git checkout tags/6.1.0

# Docker Composeで起動する（-dはバックグラウンド実行の意味）
docker compose -f docker-compose-image-tag.yml up -d

初回はSuperset本体やPostgreSQL、Redisなどのイメージのダウンロードと、メタデータDBの初期化（テーブル作成・管理者ユーザーの作成など）が走るため、環境やネットワーク回線によっては数分〜十数分かかります。ターミナルの入力待ちが戻ってきても、内部の初期化がまだ終わっていないことがあります。

タグ番号・compose ファイル名は公式ドキュメントで確認する

上記の 6.1.0 は本教材の検証バージョンです。学習中は同じ結果を得るためこのタグを推奨しますが、実務で新しい版を使いたい場合は公式クイックスタートで現行リリースを確認してください。Compose ファイルの名前やイメージタグの指定方法も、Superset のバージョンによって変わることがあります。上記のコマンドでエラーになる場合や、より新しい手順を使いたい場合は、公式ドキュメント（Quickstart）を必ず確認してください。

起動コマンドを実行したら、docker compose -f docker-compose-image-tag.yml ps でコンテナの状態を確認します。

状態確認 
# 起動しているコンテナの一覧と状態を確認する
docker compose -f docker-compose-image-tag.yml ps

各コンテナの状態が Up（起動中）になっていれば正常です。一部のコンテナは初期化作業だけを行い、完了すると Exited (0) のように終了する設計になっていますが、これは異常ではありません。詳しくは 2.4 で解説します。

2.3 ログインして初期状態を確認

ブラウザで http://localhost:8088 を開きます。ログイン画面が表示されたら、初期管理者アカウントでログインしましょう。多くの構成では、既定のユーザー名・パスワードはいずれも admin です（利用する compose ファイルやバージョンによって異なる場合があります）。

既定パスワードのまま使わない

admin / admin は学習用に最初から設定されている、誰でも知っているパスワードです。ローカルで自分だけが触る学習環境であっても、早めに変更する習慣をつけてください。社内サーバやクラウド上など、他の人からアクセスできる環境では絶対にこのままのパスワードで運用してはいけません。変更は管理画面のユーザー編集から行えます（ロールと権限は第13章で詳しく扱います）。

ログインに成功すると、上部に Dashboards・Charts・Datasets・SQL Lab などのメニューが並んだ画面が表示されます。この章では「ログインできること」の確認までとし、画面の細かい見方は第3章でじっくり扱います。

2.4 起動しているコンテナの役割

docker compose -f docker-compose-image-tag.yml ps に並んでいたコンテナは、それぞれ別の役割を持っています。第1章で確認した「Superset は分析対象のデータを持たない」という性質を思い出しながら、自分が起動したものが何なのかを整理しましょう。なお、起動するコンテナの数とコンテナ名は使用する Compose ファイルと Superset のバージョンによって変わります。以下は本教材の検証環境（6.1.0 ＋ docker-compose-image-tag.yml）で起動する代表的なものです。手元の一覧と完全に一致しなくても問題ありません。

コンテナ 何をしているか 分析対象DBとの関係
superset
（コンテナ名: superset_app）Webアプリ本体		 画面を表示し、ブラウザからの操作を受けてSQLを発行する 分析対象DBに接続しにいく側。データそのものは持たない
db
（コンテナ名: superset_db）メタデータDB（PostgreSQL）		 チャート・ダッシュボードの定義、ユーザー、権限、保存クエリなどSuperset自身の設定を保存する メタデータ用のsupersetデータベースとは別物だが、学習環境では同じPostgreSQLコンテナに同居する（詳しくは下記）
redis
（コンテナ名: superset_cache）キャッシュ		 実行済みクエリ結果を一時保存して表示を高速化する。Celeryへの処理依頼の仲介もする 分析対象DBとは無関係。一時データのみ扱う
superset-worker
（コンテナ名: superset_worker）Celeryワーカー		 重い集計や非同期のクエリ実行など、時間のかかる処理を裏側で行う 処理の中で分析対象DBにSQLを発行することがある
superset-worker-beat
（コンテナ名: superset_worker_beat）Celery Beat		 定期実行のスケジューラ。決まった時刻・間隔でCeleryワーカーに処理を依頼する 分析対象DBには直接関与しない（第14章のアラート／レポートで利用）
superset-init
（コンテナ名: superset_init）初期化用コンテナ		 初回起動時にメタデータDBのテーブル作成・管理者ユーザー作成などを行い、完了すると終了する 分析対象DBには関与しない

（Webアプリ）"] I["初期化用コンテナ
（起動時のみ動作し完了後に終了）"] -.->|初期化| D S --> D[("メタデータDB
PostgreSQL")] S --> R[("キャッシュ＆

図とあわせて確認したいのは、ここまでの手順で起動したデータベース（メタデータDB）は、分析したい業務データが入るデータベースとは別物だという点です。ただし学習環境では、この同じ db コンテナの中に、サンプルデータ用の examples データベースも作られています。同じ PostgreSQL サーバに同居していても、メタデータ用の superset データベースとは別のデータベースです。売上や顧客データのような、あなたが本当に分析したいデータは、この後の第4章で別途用意したデータベースに接続して読み込みますが、その最初の練習として第4章ではまずこの examples データベースに接続します。

混同しやすいポイント

docker compose で一緒に立ち上がる PostgreSQL コンテナ（db）には、Superset自身の設定を保存するメタデータDB（superset）と、サンプルデータ用のexamplesデータベースが同居しています。両者は同じサーバにあっても別のデータベースであり、メタデータDBに売上データなどを直接書き込む使い方はしません。本来、分析対象のデータは既存の業務データベースやデータウェアハウスに接続して読みにいきます（第4章）。

2.5 サンプルデータを読み込む

空の状態から始めるより、動いているダッシュボードを見ながら触るほうが理解が早いため、公式が用意しているサンプルデータセットとダッシュボードを使います。既定では環境変数 SUPERSET_LOAD_EXAMPLES=yes が設定されており、初回起動時（superset-init コンテナの処理中）に自動でサンプルデータが読み込まれます。まずは手を動かす前に、すでに読み込まれているかどうかを確認しましょう。

ブラウザで上部メニューの Dashboards を開き、サンプルダッシュボードがすでに一覧に並んでいるか確認してください。並んでいれば、この節の作業は完了です。2.6 や第3章へそのまま進んで構いません。

並んでいない場合は手動で読み込む

環境変数の設定や初期化のタイミングによっては、自動読み込みが行われないことがあります。Dashboards に何も表示されていない場合は、Superset 本体のコンテナの中で、サンプルデータを投入する管理コマンド superset load_examples を次の手順で手動実行してください。

サンプルデータ読み込み（手動・補助手段） 
# Dashboardsにサンプルが見当たらない場合のみ実行する
# コンテナ名は環境により異なる（docker compose -f docker-compose-image-tag.yml psで確認できる）
docker exec -it superset_app superset load_examples

実行にはデータ量に応じて数分かかることがあります。完了すると、Dashboards の一覧に複数のサンプルダッシュボードが表示されるようになります（具体的なダッシュボード名や数はバージョンによって異なる場合があります）。すでに読み込まれている状態でもう一度このコマンドを実行しても、通常は大きな問題にはなりません。

2.6 うまく起動しないときのチェックリスト

初めて Docker で複数のコンテナを起動すると、何かしらでつまずくことは珍しくありません。焦らず、次の観点で順に確認しましょう。

症状 疑うべき原因 対処
ブラウザで localhost:8088 に繋がらない 8088番ポートを既に別のプロセスが使っている 使用中のプロセスを止めるか、composeファイルのポート指定を変更する
コンテナがすぐ落ちる・動作が極端に遅い Docker Desktopに割り当てているメモリが不足している Docker Desktopの設定でメモリ割り当てを8GB以上に増やす
ログイン画面が出ない・ログインできない 初期化用コンテナの処理（DB初期化・管理者ユーザー作成）がまだ終わっていない docker compose -f docker-compose-image-tag.yml ps で初期化用コンテナの終了を確認し、数分待ってから再アクセスする
原因がはっきりしない 対象コンテナのログをまだ見ていない docker compose -f docker-compose-image-tag.yml logs -f に続けて対象のサービス名を指定して確認する（前の-fはcomposeファイル指定、後の-fはログ追尾の意味）

表の中でも特に有効なのが、対象のコンテナのログをその場で見る方法です。

ログ確認 
# サービス名は docker compose -f docker-compose-image-tag.yml ps の表示名を指定する（例: superset）
docker compose -f docker-compose-image-tag.yml logs -f superset

一旦環境を止めて作り直したいときは、次のコマンドを使います。

停止・再開 
# 停止する（コンテナは削除されるが、ボリューム＝データは保持される）
docker compose -f docker-compose-image-tag.yml down

# 再び起動する
docker compose -f docker-compose-image-tag.yml up -d

docker compose -f docker-compose-image-tag.yml down -v は使い方に注意

-v オプションを付けると、コンテナだけでなくボリューム（データの保存領域）ごと削除します。ここには、これまでの設定、接続情報、読み込んだサンプルデータ、そして今後の章で作成するデータセットやダッシュボードもすべて保存されています。単に一時停止したいだけなら、-v を付けない docker compose -f docker-compose-image-tag.yml down を使ってください。-v は「学習環境を完全に作り直したいとき」だけの操作です。

やってみよう 2-1: Supersetを起動してサンプルダッシュボードを開く

実際に手を動かして、Superset を起動するところまでを体験しましょう。うまくいかない場合は 2.6 のチェックリストを見直してください。

手順

  1. 1 2.2の手順でまだ起動していなければ docker compose -f docker-compose-image-tag.yml up -d で起動する（すでに起動済みならそのままでよい）。
  2. 2 ターミナルで docker compose -f docker-compose-image-tag.yml ps を実行し、表示されたコンテナの名前と状態をすべて書き出す（コンテナの数と名前は Compose 構成やバージョンによって変わるため、一覧に出たものをそのまま書き出す）。
  3. 3 ブラウザで http://localhost:8088 を開き、admin / admin でログインする。
  4. 4 上部メニューの Dashboards を開き、サンプルダッシュボードを1つクリックして表示する。

解答の目安

docker compose -f docker-compose-image-tag.yml ps の出力には、superset・db・redis・superset-worker・superset-worker-beat・superset-init の6つのサービスに相当する行が並びます（実際のコンテナ名はそれぞれ superset_app・superset_db・superset_cache・superset_worker・superset_worker_beat・superset_init です）。superset-init は処理完了後に「Exited」のような終了状態で表示されていれば正常です。2.4 の表と照らし合わせて、全行の役割を確認できれば、このステップは完了です。

理解度確認クイズ

  1. Q1. なぜ、Python環境やデータベースを1つずつ手動で構築せずにDockerを使うのですか？

    回答を表示

    Superset を動かすには本体（Webアプリ）だけでなく、設定を保存するメタデータDB、キャッシュ、非同期処理用のCeleryワーカーなど複数のコンポーネントが連携して動く必要があります。これらを個別にインストールしてバージョンを合わせるのは手間がかかり失敗もしやすいため、Docker Composeでまとめて起動できるようにしてあります。壊れても環境を丸ごと作り直せる手軽さもメリットです。

  2. Q2. 初期管理者アカウント（admin / admin）は、どのような場面でなら使ってよいですか？

    回答を表示

    自分のPC上だけで完結する学習・検証目的に限られます。誰か他の人がアクセスできるサーバやクラウド上の環境、まして本番運用では絶対に使わず、ログインできたらすぐにパスワードを変更してください。

  3. Q3. docker compose down と docker compose down -v の違いは何ですか？（compose ファイル指定は省略）

    回答を表示

    docker compose -f docker-compose-image-tag.yml down はコンテナとネットワークを停止・削除しますが、データを保存しているボリュームは残ります。-v を付けると、そのボリュームごと削除するため、メタデータDBに保存されていたユーザー設定・接続情報・作成済みのチャートやダッシュボードなどがすべて消えてしまいます。

  4. Q4. docker compose -f docker-compose-image-tag.yml ps で一緒に起動しているデータベース（PostgreSQL、db コンテナ）に、売上などの分析したい業務データを直接書き込んでもよいですか？

    回答を表示

    いいえ。それはメタデータDBであり、Superset自身の設定（チャート・ダッシュボードの定義、ユーザー、権限など）を保存するための場所です。分析したい業務データはこれとは別の「分析対象のDB」に用意し、第4章で学ぶ手順でSupersetから接続して読みにいきます。
