ユーザー・ロールと行レベルセキュリティ

ここまでの章で、ダッシュボードを組み立て、Jinja テンプレートでフィルタやユーザー名に応じた動的な SQL まで書けるようになりました。しかし、そのダッシュボードを社内の誰にどこまで見せるかは、また別の設計です。この章では、Superset の権限モデルの基本である「ユーザー・ロール・権限」の関係を理解し、既定ロール（Admin / Alpha / Gamma / sql_lab / Public）の違いと使い分け、Gamma ユーザーへのデータアクセス権の組み合わせ方、ダッシュボード単位のアクセス制御、そして同じダッシュボードでも見る人によって行を絞り込む行レベルセキュリティ（RLS）までを、実務で使う設計の考え方として学びます。

この章で学ぶこと

  • Superset の権限が「ユーザー → ロール → 権限」の3層構造で、1人に複数のロールを付けられることを説明できる
  • Admin・Alpha・Gamma・sql_lab・Public という既定ロールの違いを理解し、一般利用者には Gamma を基本にする方針を説明できる
  • Gamma ユーザーに業務ロールでデータアクセス権を組み合わせ、「誰に何を見せるか」を設計できる
  • 行レベルセキュリティ（RLS）を設定し、同じダッシュボードでも部署ごとに見える行を絞り込める

13.1 「誰に何を見せるか」を決める

ここまでの12章で、データベースに接続し、データセットとメトリクスを整え、チャートを作り、複数のチャートをダッシュボードにまとめ、さらに Jinja テンプレートでフィルタ値やユーザー名に応じた動的な SQL まで書けるようになりました。ダッシュボードは、もう画面の中では完成しています。しかし、それを社内の誰でも見られる状態のまま共有してよいでしょうか。

たとえば「全社売上ダッシュボード」を営業担当者全員に共有したとき、ある担当者に他の担当者の成績や、他部署の原価データまで見えてしまってよいかは、技術の話ではなく業務上の判断です。「表示できる」ことと「見せてよい」ことは別物であり、後者を制御する仕組みが Superset の権限（セキュリティ）機能です。

Superset の権限は、土台となっている Web フレームワーク（Flask-AppBuilder）の仕組みに沿って、ユーザー → ロール → 権限という3層で管理されます。

  • ユーザー — ログインする個々のアカウント。
  • ロール — 権限をひとまとめにした「役割」の単位。ユーザーに割り当てる。
  • 権限 — 「このメニューを使える」「このデータソースにアクセスできる」といった個々の許可。

ここで重要なのは、1人のユーザーに複数のロールを同時に付けられることです。そのユーザーが実際に持つ権限は、割り当てられた全ロールの権限を合算したものになります。下の図は、2人のユーザーがそれぞれ複数のロールを持ち、ロールごとに異なる権限がぶら下がっている様子です。

flowchart LR U1["ユーザー: 田中"] --> R1["ロール: Gamma"] U1 --> R2["ロール: 営業部ロール"] U2["ユーザー: 鈴木"] --> R1 U2 --> R3["ロール: Alpha"] R1 --> P1["権限: 自分の作成物を編集"] R2 --> P2["権限: 売上データセットの閲覧"] R3 --> P3["権限: 全データソースの閲覧＋作成"]

重要ポイント: ロールは「足し算」

ロールは掛け算（絞り込み）ではなく、足し算（合算）で効きます。この性質が、13.3で行う権限設計の土台になります。「基本の役割（Gammaなど）」と「業務ごとのデータアクセス（営業部ロールなど）」を別々のロールとして用意し、ユーザーには両方を付ける、という組み合わせ方が基本パターンです。

13.2 既定のロール

Superset にはあらかじめ代表的なロールが用意されており、管理者としてログインすると Settings → List Roles から確認できます。まずはこの5つの役割を理解しておきましょう。

ロール できること 想定する利用者
Admin ユーザー・ロールの作成／編集を含む全機能を利用できる。全データソースにアクセスでき、他人が作ったダッシュボードやチャートも編集できる システム管理者・運用担当
Alpha 全データソースを閲覧でき、データセットやチャートも新規作成できる。ただしユーザーやロールの管理はできず、変更できるのも自分が所有するオブジェクトのみ（Admin と異なり、他人が作成したダッシュボードやチャートは編集できない） 分析基盤を整備する中核メンバー
Gamma 自分に許可されたデータソースだけを閲覧できる。チャートの作成や、自分が作成したダッシュボード／チャートの編集が中心 一般の利用者（閲覧・自分用の分析が中心）
sql_lab SQL Lab 機能へのアクセス権を与える。実際にクエリを実行するには、対象データベースへのアクセス権を別途付与する必要がある SQL を書ける一般利用者（Gamma などの基本ロール＋データアクセス用ロールと併用）
Public ログインしていない利用者に自動的に割り当てられる。既定では権限を持たず、実質的に無効化された状態 匿名公開が必要な場合のみ、管理者が個別に設定

sql_lab ロールは「SQL Lab を開く権利」だけを与える

sql_lab ロールが与えるのは SQL Lab 機能へのアクセス権です。データへのアクセス権は含まれないため、実際にクエリを実行するには対象データベースへのアクセス権を別途付与する必要があります（Admin は既定で全データベースにアクセスできますが、Alpha・Gamma はデータベース単位で付与が必要です）。そのため実務では、Gamma などの基本ロール ＋ 業務に必要なデータアクセス用のカスタムロール ＋ sql_lab を組み合わせて使います（組み合わせ先は Gamma / Alpha に限らず、カスタムロールでも構いません）。

なお、SQL Lab のクエリコスト見積り（can_estimate_query_cost）と SQL の整形（can_format_sql）は sql_lab に含まれないため、必要な場合は該当ロールへ個別に権限を追加します。

重要ポイント: 一般利用者はGammaを基本にする

特別な理由がない限り、一般利用者には Alpha ではなく Gamma を割り当てます。Alpha を安易に広く配ると、全データソースが誰にでも見える状態になってしまいます。「見せたいデータだけを、必要な人にだけ見せる」という設計は、次の13.3で説明する Gamma と業務ロールの組み合わせで実現します。

13.3 Gammaユーザーにデータを見せる仕組み

Gamma ロールだけをユーザーに付けて満足していると、多くの人が同じところでつまずきます。「Gamma を付けたのに、ログインしてもダッシュボードが1つも表示されない」という現象です。これは不具合ではなく、Superset の権限設計として意図された動作です。

Gamma ロール自体が持つ権限は、「許可されたものだけを見てよい」という基本方針にすぎません。具体的にどのデータベース・どのスキーマ・どのデータセットにアクセスしてよいかという情報は、Gamma には含まれていません。この「見てよい対象」は、ロールの権限一覧にデータアクセス権限を追加して初めて成立します。

Gammaロールだけを付けた場合

データアクセス権を追加しない限り、原則としてダッシュボード・チャート・データセットは見えません（通常は一覧が空になります）。ナビゲーションメニューは表示されるが、中身は空のまま。

Gamma＋営業部ロールを付けた場合

営業部ロールに許可した売上データセットに基づくチャート・ダッシュボードだけが見える。他部署のデータは引き続き見えない。

データアクセス権限には、粒度の異なる3段階があります。

  • データベース単位 — 接続したデータベース全体へのアクセスを許可する。粒度は粗いが管理は楽。
  • スキーマ単位 — 特定のスキーマ（テーブルの集まり）だけを許可する。
  • データセット単位 — 個別のデータセット（テーブルまたは保存済みSQL）だけを許可する。最も細かく制御できるが、データセットが増えるほど管理の手間も増える。

実践では、業務ロールを用意する方法が扱いやすくなります。たとえば「営業部ロール」を作り、そこには営業部が使ってよいデータセットへのアクセス権限だけを追加します。そして、営業部のユーザーにはGamma と営業部ロールの両方を割り当てます。Gamma が「閲覧が中心の一般利用者」という基本ふるまいを、営業部ロールが「どのデータが見えるか」を、それぞれ別の役割として担う形です。

この分担には利点があります。複数の部署にまたがるデータを扱う利用者がいれば、その人にだけ業務ロールをもう1つ追加すればよく、Gamma 自体やほかの利用者のロールには手を加えずに済みます。

データセット側からロールを指定できる場合もある

バージョンによっては、データセットの編集画面にも「アクセスを許可するロール」を直接指定できる項目が用意されていることがあります。ロール編集画面から権限を1つずつ追加する方法と、データセット側から許可するロールを指定する方法のどちらが使えるかは環境によって異なるため、実際の画面を確認しながら進めてください。

13.4 ユーザーとロールを作る手順

実際に、業務ロールとテストユーザーを作る手順を確認しましょう。どちらもAdmin ロールを持つユーザーでログインし、画面右上の歯車アイコン（Settings）を開いて行います。Settings のドロップダウンには Security という見出しの下に List Users・List Roles・Row Level Security・Action Log などの項目が並んでいます。

ユーザーを追加する

  1. ① Settings メニューから List Users を開く。
  2. ② 一覧右上のボタンから新規ユーザーの追加画面を開く。
  3. ③ First Name・Last Name・Username・Email を入力する。
  4. ④ Roles で付与するロールを選択する（複数選択可。例: Gamma ＋ 営業部ロール）。
  5. ⑤ Password・Confirm Password を入力する。
  6. ⑥ Save をクリックする。

ロールを作成する

  1. ① Settings メニューから List Roles を開く。
  2. ② 一覧右上のボタンから新規ロールの追加画面を開く。
  3. ③ Name にロール名を入力する（例: 営業部ロール）。
  4. ④ Permissions で必要な権限を検索して追加する（対象のデータベース・スキーマ・データセットへのアクセス権など）。
  5. ⑤ Save をクリックする。

画面表記はバージョンによって変わることがある

ボタンの位置や項目名は Superset のバージョンによって多少異なる場合があります。「ユーザー一覧・ロール一覧から追加する」という流れ自体は共通なので、見当たらない場合は一覧画面のメニューやアイコンを探してみてください。

13.5 ダッシュボード単位のアクセス制御

13.3で設定したデータアクセス権限は、データセット・チャート単位の制御でした。Superset にはこれとは別に、ダッシュボード単位で閲覧者を絞り込む機能もあります。

ダッシュボード画面のプロパティ編集を開くと、Owners（そのダッシュボードを編集できるユーザー）に加えて、Roles という項目で閲覧を許可するロールを指定できる場合があります。これは Dashboard RBAC と呼ばれる機能で、バージョンによっては機能フラグ DASHBOARD_RBAC を有効にしないと画面に表示されないことがあります。

ロールを指定した時点で、そのダッシュボード上のデータが見えるようになる

公式ドキュメントが明言しているとおり、ダッシュボードの Roles 欄にロールを指定すると、データセット単位のアクセス権チェックは迂回されます。つまり、そのダッシュボードへのアクセス権を持つことは、ダッシュボード上の全チャート、ひいては関連する全データセットへの read 権限を暗黙に付与するのと同じ効果を持ちます。「データセット側にアクセス権が無いから安全」という判断は誤りで、Roles を指定した瞬間にそのデータは見えるようになると考えてください。ダッシュボードに1つもロールが指定されていない場合に限り、通常どおりデータセット単位のアクセス権が適用されます。導入前に必ず公式ドキュメント（Security）の該当箇所を確認してください。

13.6 行レベルセキュリティ（RLS）

データセット単位・ダッシュボード単位の制御は、「見せる・見せない」という表そのものの制御でした。これに対して行レベルセキュリティ（Row Level Security、RLS）は、同じダッシュボード・同じデータセットを共有しながら、見る人によって表示される行を絞り込む仕組みです。たとえば「全社売上ダッシュボード」を1つだけ作り、営業担当者には自分の部署の行だけを、経営層には全部署の行を見せる、といった使い方ができます。

設定は Settings → Row Level Security から行います。

  1. ① Row Level Security の一覧画面から、新規ルールの追加画面を開く。
  2. ② Name にルール名を入力する（例: 部署別フィルタ）。
  3. ③ Filter Type で Regular か Base を選ぶ。
  4. ④ Tables で対象データセットを、Roles で対象ロールを選ぶ。
  5. ⑤ Group Key（任意）に、他のルールと組み合わせるグループ名を入力する。同じ Group Key のルール同士は OR、Group Key が無い、または異なるルール同士は AND で連結される。
  6. ⑥ Clause に絞り込み条件（SQL の条件式）を入力し、Save する。

Group Key を付け忘れると、複数ルールが必ず0件になる

同じ department 列を絞り込む部署フィルタを2本作ったとき、Group Key を指定しなければ2つのルールは AND で連結され、department='営業部' AND department='経理部' のような条件になって常に0件になります。複数のルールのどれかに一致させたい（OR で連結したい）場合は、必ず同じ Group Key を付けてください。

Filter Type には2種類あり、意味が逆になるので注意してください。

  • Regular — 指定したロールを持つユーザーに条件を適用する。「この人たちだけ絞り込む」という指定。
  • Base — 指定したロール以外のユーザーに条件を適用する。全員に適用する土台のフィルタを作り、Admin などの一部ロールだけを例外的に除外したいときに使う。

Clause には、データセットの SQL に条件として追加される式を書きます。固定値で絞り込む例と、ログイン中のユーザー名を使って動的に絞り込む例を見てみましょう。

RLSのClause例（SQL） 
-- 例1: 固定の部署名で絞り込む、最もシンプルなルール
department = '営業部'

-- 例2: ログイン中のユーザー名から部署を引いて絞り込む
-- current_username() はログインユーザーのユーザー名に置き換わる
department = (
    SELECT department
    FROM user_department
    WHERE username = '{{ current_username() }}'
)

2つめの例のように {{ current_username() }} を使うと、部署ごとにルールを増やさなくても、1つのルールで「自分の部署の行だけ」を絞り込めます。ただし部署とユーザー名の対応表（user_department のようなテーブル）を別途用意して整合性を保つ必要があり、Jinja テンプレートの考え方は第12章の内容がそのまま前提になります。

Jinja を使うには ENABLE_TEMPLATE_PROCESSING が前提

RLS の Clause で {{ current_username() }} のような Jinja テンプレートを使えるのは、機能フラグ ENABLE_TEMPLATE_PROCESSING（第12章 12.3 で有効化した設定）がオンのときだけです。無効のままだとテンプレートが展開されず、文字列のまま WHERE 句に渡って SQL構文エラーになります。

保存したら必ずテストユーザーで確認する

RLSルールは画面上の設定だけでは正しく動いているか分かりません。対象ロールを持つテストユーザーで実際にログインし直し、ダッシュボードを開いて、意図した行だけが表示されているかを毎回確認する習慣をつけてください。

13.7 権限設計の実務

最後に、ここまでの内容を、権限設計を運用に乗せるときの実務チェックリストとしてまとめます。1つずつ、自分の環境に当てはめて確認してください。

1. 最小権限の原則で始めているか

まず何も見えない状態を基準にし、必要な範囲だけを足していく。

2. ロールを「人」ではなく「役割」で作っているか

部署・チーム単位でロールを作る。異動時はロールの付け替えだけで済む。

3. 異動・退職時に棚卸しをしているか

不要になったロールの割り当てを確実に外し、定期的に List Users を確認する。

4. SQL Lab権限を慎重に配っているか

RLSは、機能フラグRLS_IN_SQLLABが有効なときにのみSQL Labに適用される。既定は無効（False）のため、何もしなければRLSはSQL Labの生SQLに効かない。必要な人に限定するか、データベース側のユーザー権限でも行の見える範囲を守る。

5. 監査ログ（Action Log）を確認しているか

誰がいつ何を操作したかを、Settings → Action Log から追跡できるようにしておく。

6. 本番投入前に公式ドキュメントを再確認したか

権限まわりはバージョンによって挙動が異なる。思い込みで判断せず、都度確認する。

7. 組み込みロールを直接いじらず、カスタムロールで足しているか

superset init は、Superset が管理する組み込みロール（Admin / Alpha / Gamma / sql_lab など）の権限を既定状態へ再同期する。そのため、これらの組み込みロールを直接カスタマイズすると、バージョンアップ時の superset init で手で加えた権限が上書きされるおそれがある。追加の権限は自分で作ったカスタムロール側に持たせるのが公式の推奨（カスタムロールは同期対象ではないため、既定値に戻されることはない）。

権限設計は一度作って終わりではなく、組織の変化に合わせて育てていくものです。次の「やってみよう」で、実際に業務ロールとテストユーザーを作り、RLSまでを一通り体験してみましょう。

やってみよう 13-1: 業務ロールとRLSで「誰に何を見せるか」を体験する

ここまで学んだ内容を、実際に手を動かして確認します。既定ロールの組み合わせと、行レベルセキュリティの両方を一通り体験しましょう。

手順

  1. 1 業務用ロールを1つ作り（例: 営業部ロール）、特定のデータセット（例: 売上データセット）だけへのアクセス権を付与する。
  2. 2 Gamma ＋ 手順1で作ったロールを持つテストユーザーを作成する。
  3. 3 そのテストユーザーでログインし直し、Dashboards / Charts / Datasets それぞれに何が表示されるかを確認する。
  4. 4 Row Level Security にルールを追加し（対象ロール: 手順1のロール、条件: 部署列で絞り込むSQL句）、部署ごとに見える行が変わることを確認する。

解答の目安

最もよくつまずくのは、「Gamma と業務用ロールを付けたのに、ログインしても何も見えない」という状態です。原因のほとんどは、業務用ロールにデータソースへのアクセス権限を追加し忘れていることにあります。Gamma 自体は「許可されたものだけを見てよい」という方針を与えるだけで、具体的な許可対象（データベース・スキーマ・データセット）は業務用ロール側に権限として追加しない限り空のままです。ロールの Permissions 欄を開き、目的のデータセットへのアクセス権が本当に追加されているかを確認しましょう。RLSについても同様に、ルールで指定した Tables と Roles が意図した組み合わせになっているかを見直すと、多くの場合原因が見つかります。

理解度確認クイズ

  1. Q1. Gammaロールをユーザーに付与しただけで、そのユーザーはダッシュボードのデータを見られるようになりますか？

    回答を表示

    見られません。Gamma ロール自体は「許可されたものだけを見られる」という基本方針を与えるだけで、具体的にどのデータソースにアクセスしてよいかは含まれていません。データベース・スキーマ・データセットへのアクセス権限を業務ロールなどに別途付与して初めて、そのデータが見えるようになります。

  2. Q2. Admin・Alpha・Gammaの違いを一言で説明してください。

    回答を表示

    Adminはユーザー・ロール管理を含む全権限を持つ管理者向けのロールです。Alphaは全データソースを閲覧・作成できますが、ユーザーやロールの管理はできません。Gammaは付与されたデータソースだけを閲覧でき、主に自分の作成物を編集する一般利用者向けのロールです。

  3. Q3. 行レベルセキュリティ（RLS）のFilter Typeで、RegularとBaseはそれぞれどのユーザーに条件を適用しますか？

    回答を表示

    Regularは、指定したロールを持つユーザーに条件を適用します。Baseは、指定したロール以外のユーザーに条件を適用します。全員に適用する土台のフィルタを作り、Adminなど一部のロールだけを例外的に除外したいときにBaseを使います。

  4. Q4. SQL Lab権限を配る際に、RLSとの関係で注意すべきことは何ですか？

    回答を表示

    RLSのルールは、Supersetがデータセットから生成するチャート／ダッシュボードのクエリには効きますが、SQL Labでは機能フラグRLS_IN_SQLLABが有効なときにのみ適用されます。このフラグの既定値は無効（False）のため、何も設定しなければSQL Labの生SQLはRLSで絞り込まれません。RLSで守りたいデータに対しては、SQL Lab権限をむやみに配らないか、配る場合はデータベース側のユーザー権限でも行の見える範囲を制御するなど、二重の対策を検討してください。
