Jinjaテンプレートで動的SQL

SQL Lab や仮想データセットで書く SQL の中には、Jinja というテンプレート構文で変数や条件分岐を埋め込めます。この章では、ダッシュボードのフィルタで選ばれた値やログイン中のユーザー名を SQL に反映させる方法と、この強力な機能をどこまで使ってよいかの判断基準を学びます。

この章で学ぶこと

  • Jinjaテンプレートが「SQLの中身そのものを実行前に書き換える」仕組みであることを、フィルタとの違いを踏まえて説明できる
  • {{ }}・{% %}・{# #} という3種類の記法の役割を区別できる
  • filter_values() や current_username() などの代表的なマクロを使って、動的なSQLを書ける
  • Jinjaを使いすぎないための判断基準を理解し、「素直なSQL→RLS→Jinja」という優先順位で検討できる

12.1 何のための機能か

第10章・第11章で、複数のチャートをダッシュボードにまとめ、ネイティブフィルタで「見る範囲」を絞り込めるようになりました。ですが実務では、フィルタだけでは足りない場面に出会います。たとえば「全社共通のダッシュボードを1つだけ作り、開いた人の部署に応じて自動的に自分の部署の行だけを表示したい」「選ばれた期間によって、参照する集計テーブルそのものを日次用と月次用で切り替えたい」といった要望です。これらはダッシュボードを開いた後から結果を絞り込むのではなく、SQLの文字列そのものを状況に応じて書き換える必要があります。

Superset は、SQL Lab（第5章）や仮想データセット（第6章）のように自分でSQLを書く場所で、Jinjaというテンプレート構文を使えます。Jinja自体がどんなテンプレートエンジンかは12.2で詳しく説明するので、ここでは「SQLの中に変数や条件分岐を書き込めるようになる」という程度に押さえておいてください。

フィルタ（第11章）

  • 利用者が書いたSQL（データセット定義）の文字列自体は変わらない
  • Supersetが最終的なSQLを組み立てる際、外側のWHEREとして条件を足す
  • 画面上の操作だけで完結する

Jinjaテンプレート（第12章）

  • SQLの文字列そのものに変数・条件分岐を仕込む
  • データベースに送る前にSQLを書き換える（展開）
  • SQL Lab・仮想データセットに加え、Exploreのフィルタやメトリクスの Custom SQL（第7章）でも使える

つまりフィルタは、利用者が書いたSQL（データセット定義）の文字列自体は変えずに、Supersetが最終的なSQLを組み立てるときに外側のWHEREとして条件を足す仕組みです。データベースへ送る前に組み込まれるのであって、結果を取得した後から絞り込んでいるわけではありません（第1章で触れたとおり、Supersetはそのつど新しいSQLを発行します）。一方Jinjaは、SQLの文字列そのものに変数や条件分岐を仕込む仕組みです。両者は排他的ではありません。実際には12.5で見るように、Jinja自身がダッシュボードのフィルタで選ばれた値を読み取ってSQLを組み立てることもあり、むしろ組み合わせて使う場面の方が多くあります。

12.2 Jinja の基本文法

Jinja は Python で書かれたテンプレートエンジンで、Superset のサーバ側フレームワークである Flask（第1章）でも標準的に使われています。ふつうのWeb開発ではJinjaは主にHTML画面を組み立てるために使われますが、Supersetでは組み立てる対象がHTML画面ではなくSQL文字列になっている、と考えると理解しやすくなります。基本となる記法は3種類だけです。

記法 役割 例
{{ }} 値の埋め込み。式を評価した結果を、その場所にテキストとして挿入する {{ current_username() }}
{% %} 制御構文。if による分岐や for による繰り返しなど、処理の流れを制御する {% if %} ... {% endif %}
{# #} コメント。展開結果には一切出力されない、書いた人向けのメモ {# ここは実行されない #}

重要なのは、この展開処理がSQLがデータベースへ送られる直前に行われるという点です。データベース自身はJinjaのことを一切知りません。受け取るのは、変数もif文もすべて解決し終えた、ごく普通のSQL文だけです。

flowchart LR A["テンプレートSQL
（プレースホルダを含む文字列）"] -->|"① Jinjaが展開"| B["展開後のSQL
（プレースホルダを値に置換済み）"] B -->|"② データベースへ送信"| C[("実行結果")]

展開後のSQLはあとから確認できる

SQL LabやチャートのView query（第8章）では、テンプレートを書いたままのSQLではなく、展開が終わった後の実際のSQLが表示されます。「今どんなSQLが実行されているか」を確認する習慣は、12.7で扱うデバッグのしやすさにも直結します。

12.3 使えるようにする設定

ここまで説明したSQLテンプレート機能は、Supersetでは既定で無効になっています。使うには、設定ファイル superset_config.py の FEATURE_FLAGS で、テンプレート処理を有効にするフラグをオンにする必要があります。

superset_config.py 
# 既存のFEATURE_FLAGSがあれば上書きせず追記する
FEATURE_FLAGS = {
    # SQL Labや仮想データセットのSQL内でJinja記法({{ }}など)を使えるようにする
    "ENABLE_TEMPLATE_PROCESSING": True,
    # 他のフラグがすでにある場合はここに並べて追記する
}

この設定はsuperset_config.pyを書き換えただけでは反映されません。Superset のWebサーバーとワーカーのプロセスを再起動して、初めて有効になります。

この機能はサーバー上でテンプレートコードを実行する

ENABLE_TEMPLATE_PROCESSING を有効にすると、SQLの中に書かれたJinjaのコードはSupersetのサーバー上で実際に実行されます。データセットやチャートを編集できる権限を信頼できない利用者に与えると、この仕組みを悪用されるSSTI（サーバーサイド・テンプレート・インジェクション）脆弱性につながりえます。有効化してよいのは、データセット／チャートを編集できる人＝信頼できる人に限られると言い切れる場合だけです（権限設計は第13章で扱います）。リスクを理解し、受け入れられないのであれば有効化しないでください。

フラグ名はバージョンによって変わることがある

機能フラグの名前や既定の有効・無効、利用できる設定項目はSupersetのバージョンによって変わる場合があります。設定する前に、必ず公式ドキュメント（superset.apache.org/admin-docs/configuration/sql-templating）で、使用しているバージョンの正確な設定項目を確認してください。

12.4 よく使うマクロ

Superset は、Jinjaの中で使えるマクロ（あらかじめ用意された関数）をいくつも提供しています。自分でユーザー名やフィルタの値を取得するコードを書く必要はなく、用意された呼び出しを埋め込むだけで済みます。代表的なものを整理します。

マクロ／変数 得られるもの 主な用途
{{ current_username() }} ログイン中のユーザー名 ユーザーごとの出し分け（12.6）
{{ current_user_id() }} ログイン中のユーザーのID（数値） ユーザー管理テーブルとの突き合わせ
{{ filter_values('列名') }} ダッシュボードのそのフィルタで選ばれている値の配列 IN句の組み立て（12.5）
{{ get_filters('列名', remove_filter=True) }} フィルタ条件をより詳しい形で受け取りつつ、Superset側の自動付与を止める 自前のWHERE句に完全に置き換えたいとき
{{ get_time_filter('列名') }} 選択されている時間範囲を from_expr／to_expr／time_range として受け取る 時間範囲をSQLに反映する現行の推奨手段。remove_filter=True で外側の自動付与を止められる
{{ from_dttm }} ／ {{ to_dttm }} 選択されている時間範囲の開始・終了
（非推奨。上の get_time_filter を使う）		 期間条件を自分のWHERE句に反映する（既存SQLの読解用）
{{ url_param('パラメータ名') }} ダッシュボードのURLに付いたクエリパラメータの値
（URLは閲覧者が自由に書き換えられる＝信用できない入力）		 埋め込み表示先ごとの出し分け。値をそのままSQLに埋めない（下の警告を参照）
{{ cache_key_wrapper(...) }} 指定した値をキャッシュキーの計算に含める 独自のテンプレート関数の戻り値など、自動では含まれない値でキャッシュを分ける（12.7）

url_param() の値は無条件にSQLへ入れない

URL のクエリパラメータは閲覧者が自由に書き換えられる入力です。WHERE code = '{{ url_param('code') }}' のように直接埋め込むと、意図しない条件の注入につながります。エスケープの挙動は文脈や設定によって変わるためそれに頼らず、次のいずれかで必ず値を検証してください。

  • 許可リスト（allowlist）で照合する — 想定した値だけを通し、それ以外は既定値に落とす
  • 配列として扱えるなら |where_in を通す — 自分で文字列を連結しない

from_dttm ／ to_dttm の注意点

この2つは関数（マクロ）ではなくJinjaのコンテキスト変数なので、{{ from_dttm() }} のように () を付けてはいけません。また値は日時、または時間範囲が指定されていないときはNoneになります。WHERE dt >= '{{ from_dttm }}' とそのまま書くと、Noneのときに文字列'None'がWHERE句に入ってしまう事故につながるため、値の有無を{% if %}で確認してから使ってください。なおSuperset 5.0以降ではfrom_dttm／to_dttmは非推奨となり、代わりにget_time_filterの利用が案内されています。

利用できるマクロはバージョンによって異なる

上表は代表的なマクロの一例です。名前や引数、挙動はSupersetのバージョンによって追加・変更されることがあります。実際に使う前に、公式ドキュメント（superset.apache.org/admin-docs/configuration/sql-templating）で、使用しているバージョンで利用できるマクロを確認してください。

12.5 実例1: フィルタの値をSQLに渡す

第11章のネイティブフィルタは、Supersetが組み立てたクエリの一番外側にしかWHERE条件を追加できません。ところが仮想データセットのSQLが、集計済みの中間結果を作ってから最終的な列を計算しているような場合、集計に到達する前の生データの段階で絞り込みたいことがあります。こうした「クエリの内側」に条件を入れたいときこそ、filter_values()マクロの出番です。

filter_values('category') は、ダッシュボードの category 列に対するフィルタで、現在選ばれている値の一覧を配列として返します。これを使って、カテゴリごとの件数と金額を集計する仮想データセットに絞り込み条件を加えてみましょう。

sales_by_category.sql 
-- categoryフィルタで選ばれた値だけに絞り込む仮想データセット
-- where_inフィルタがIN句の形へ安全に変換する（未選択時はNoneを返す）
SELECT
    category,
    COUNT(*) AS order_count,
    SUM(amount) AS total_amount
FROM sales
{% set categories = filter_values('category') | where_in(default_to_none=True) %}
{% if categories %}
WHERE category IN {{ categories }}
{% endif %}
GROUP BY category

ポイントは | where_in というJinjaフィルタを経由している点です。filter_values() が返す値をそのまま文字列連結でSQLへ埋め込むと、値の中にクォートなどの特殊文字が含まれていた場合にSQLの構文が壊れる、あるいは意図しない条件を注入される恐れがあります。where_in フィルタは、渡された配列の値を適切にエスケープしたうえで IN (...) の形に変換してくれるため、自分で文字列を組み立てるより安全です。

default_to_none=True を付けると、フィルタで何も選ばれていないとき categories はNoneになります。これを {% if categories %} で受けて分岐させることで、値が1つ以上あるときだけWHERE句を出力し、未選択時はWHERE句自体を出さず全件を返す、という挙動になります。{% if %} で囲まずに使うと空のIN句が生成されて構文エラーになりうる点は変わらないため、この分岐は引き続き必要です。

もう1つ知っておきたいのが、filter_values() の正式なシグネチャ filter_values(column, default=None, remove_filter=False) です。remove_filter は既定でFalseのため、上の例のようにJinjaの中でWHERE句へ自分で条件を組み込んでも、Superset側は同じフィルタの条件を外側のクエリにも重ねて付与します。多くの場合は同じ条件が二重にかかるだけで実害はありませんが、「Jinjaで書いた条件だけを効かせたい」ときはremove_filter=Trueを指定するか、12.4で紹介したget_filters('列名', remove_filter=True)を使って、Superset側の自動付与を止めてください。なお公式ドキュメントで remove_filter が明記されているのは get_filters() と get_time_filter() です（filter_values() も実装上は同じ引数を受け取りますが、ドキュメントには記載がありません）。チームで共有するSQLでは、意図が明確に伝わる get_filters()（時間条件なら get_time_filter()）側で指定するほうが無難です。

この展開結果は、Explore画面のView query（第8章）で確認できます。フィルタを選んだ状態と選んでいない状態それぞれで開いてみると、実際に生成されるSQLの違いを目で確認できます。12-1のやってみようで実際に試します。

12.6 実例2: ログインユーザーで出し分ける

もう1つの代表的な使い方が、current_username() でログイン中のユーザー名を取得し、そのユーザーに応じた行だけを返すというものです。たとえば「部門ごとの担当者対応表」を別テーブルとして持っておき、ログインユーザーの所属部門に一致する行だけをSQL側で絞り込む、という書き方ができます。

sales_by_department.sql 
-- ログイン中のユーザー名から所属部門を引き、その部門の行だけ返す例
SELECT
    order_id,
    department,
    amount
FROM sales
WHERE department IN (
    -- ユーザーと部門の対応表を都度参照する
    SELECT department FROM department_members
    WHERE username = '{{ current_username() }}'
)

画面に表示する内容をユーザーごとに自動で変えられるので、一見便利な仕組みに見えます。ですが、これをアクセス制御の手段として使うのは避けてください。

これはアクセス制御ではない

Jinjaによる出し分けは、あくまでその1つのデータセットのSQLに書かれた条件にすぎません。このデータセットやチャートを編集できる人であれば、WHERE句ごと書き換えたり取り除いたりできてしまいます。これに対して行レベルセキュリティ（RLS、第13章）は、データセットに対してSuperset側が管理者権限で強制する仕組みで、どのチャートからそのデータセットを使っても対象ユーザーには常に適用されます。「見た目を使う人ごとに変える」ためにJinjaを使うのは便利ですが、「見せてはいけない人に見せない」というアクセス制御の目的には、必ずRLSを使ってください。

まとめると、current_username() によるユーザー別の出し分けは、「ログインした人向けに初期表示を親切にする」といった補助的な用途にとどめ、権限そのものの管理は第13章で学ぶロールとRLSに任せるのが適切な役割分担です。

12.7 使いすぎない判断基準

Jinjaは強力な機能ですが、SQLのあちこちに埋め込むほど、後から見たときの負担が大きくなっていきます。使う前に、次の4点を考えてみてください。

  • 可読性が落ちる — 条件分岐や埋め込みが増えるほど、SQLの本来のロジックが見えづらくなります。半年後の自分を含め、他の人が読み解ける量にとどめましょう。
  • デバッグが難しい — エラーが出たとき、テンプレートの構文の問題か、展開後のSQLの問題か、値そのものの問題か切り分けが必要です。12.2で触れたView queryで展開後のSQLを確認する習慣を必ず持ちましょう。
  • キャッシュがユーザー・フィルタごとに分かれる — current_username()のようにユーザーごとに異なる文字列を生成すると、実行されるSQLもユーザーの数だけ異なるものになり、キャッシュ（第14章）が効きにくくなってデータベースへの負荷が増えます。current_username()／current_user_id() の値は既定でキャッシュキーに含まれる（add_to_cache_keys=True）ため、これらのために cache_key_wrapper() を書き足す必要はありません。cache_key_wrapper() が必要になるのは、独自に追加したテンプレート関数の戻り値など、Superset が自動でキャッシュキーに含めない値を含めたいときです。なお current_username(add_to_cache_keys=False) を指定すればユーザーをまたいでキャッシュを共有できますが、ユーザーごとに結果が変わるSQLでこれを行うと他人のデータが見えてしまうため、使ってはいけません。
  • DB側にビューを作る方がよい場合がある — 複雑な条件分岐をJinjaで頑張るより、データベース側にVIEWや集計テーブルを用意し、Superset側はシンプルなSELECTだけにする方が、見通しがよく他のツールからも再利用しやすいことがあります。

重要ポイント: 検討する順番

迷ったら、①まず素直なSQL（Jinjaなし）で書けないか、②それでも足りない「誰に見せるか」の制御はRLS（第13章）で解決できないか、③それでも解決しない一時的・複雑な要件だけにJinjaを使う、という順番で検討してください。Jinjaは「使えるから使う」ものではなく、他の手段で解決できないときの選択肢として持っておくくらいがちょうどよいバランスです。

やってみよう 12-1: フィルタ値をSQLに組み込み、View queryで確認する

第11章で作ったダッシュボードのカテゴリフィルタと、仮想データセットのSQLを連動させてみましょう。展開後のSQLが選択状況によって変わることを、実際に目で確認するところまでが今回のゴールです。

手順

  1. 1 superset_config.py の FEATURE_FLAGS に ENABLE_TEMPLATE_PROCESSING が設定され、再起動済みであることを確認する（12.3）。
  2. 2 第6章で作った仮想データセット（なければSQL Labで新規に作成）のSQL定義を開く。
  3. 3 WHERE句に filter_values('category') | where_in(default_to_none=True) を使った絞り込みを追加し、フィルタが未選択のときに備えて {% if %} で分岐させる（12.5を参考にする）。
  4. 4 データセットを保存し、そのデータセットを使うチャートをダッシュボードに配置する（またはすでに配置済みのものを使う）。ダッシュボードのネイティブフィルタでカテゴリ列を対象にしておく（第11章）。
  5. 5 フィルタでいずれかの値を選び、対象チャートのExploreを開いてView query（第8章）をクリックし、展開後のSQLに実際の値が埋め込まれていることを確認する。
  6. 6 フィルタの選択をすべて解除し、再度View queryを確認する。{% if %} の分岐によりWHERE句が消え、全件を返すSQLに変わっていることを確認する。

解答の目安

{% set categories = filter_values('category') | where_in(default_to_none=True) %} で値を安全な IN (...) の形へ変換し、{% if categories %} 〜 {% endif %} で囲んで、フィルタが選ばれているときだけ WHERE category IN {{ categories }} を出力する、という書き方がポイントです。文字列を自分で連結せず where_in を経由することで、値のエスケープをSuperset側に任せられます。未選択時は categories が None になりWHERE句自体が消え、SELECT ... FROM sales GROUP BY category だけが実行されて全件が返ります。View queryで確認したとき、選択時と未選択時でSQLの行数そのものが変わっていれば、想定どおりに分岐できています。

理解度確認クイズ

  1. Q1. Jinjaテンプレートは、第11章のダッシュボードフィルタと比べて、SQLに対して「いつ」働きかけますか？

    回答を表示

    フィルタは、Supersetが組み立てたSQLに対して結果を絞り込む条件を後から追加します。これに対しJinjaテンプレートは、SQLがデータベースに送られる前に文字列そのものを書き換えます（展開）。データベースが受け取る時点では、Jinjaの構文はすでに消えて普通のSQLになっています。

  2. Q2. {{ }}・{% %}・{# #} は、それぞれ何のための記法ですか？

    回答を表示

    {{ }} は式の評価結果をテキストとして埋め込む記法、{% %} はif・forなどの制御構文（分岐・繰り返し）、{# #} は展開結果に一切出力されないコメントです。

  3. Q3. filter_values('category') を使ったSQLで、{% if %} による分岐が必要なのはなぜですか？

    回答を表示

    フィルタが何も選ばれていないとき、filter_values() は空の配列を返します。{% if %} で囲まずに使うと WHERE category IN () のような構文エラーになりうるSQLが生成されてしまうため、「値があるときだけWHERE句を出力する」という分岐が必要です。

  4. Q4. ログインユーザーに応じてJinjaで行を絞り込むことは、行レベルセキュリティ（RLS、第13章）の代わりになりますか？

    回答を表示

    なりません。Jinjaによる出し分けはその1つのデータセットのSQLに書かれた条件にすぎず、データセットやチャートを編集できる人であれば書き換えられてしまいます。誰に何を見せるかを確実に制御するアクセス制御には、Superset側が強制するRLSを使う必要があります。Jinjaでの出し分けは、あくまで利便性のための補助的な使い方と位置づけてください。
